# 04. 描画

<p align="center">
  <img src="../.github/readme/earth-rendering.svg" alt="地球表面と大気レイヤーの描画構造" width="100%">
</p>

`src/render/` は Three.js / WebGPU を使って、モデルから導出された表示状態を実際の画面へ写す層です。ここで重要なのは、**描画資源を所有するが、ゲーム世界の意味そのものは所有しない**ことです。

## 1. Scene が描画装置の根

`src/render/scene.ts` は描画側の大きな入口です。

ここから、

- WebGPU renderer
- Three.js scene
- camera
- viewport
- GPU 計測
- 描画パイプライン

などが組み上がります。

Run から見ると、Scene はページ上の「描く装置」です。

## 2. 描画資源の寿命

描画側では、資源の寿命を意識する必要があります。

### 構築

- geometry
- material
- texture
- buffer
- instanced pool
- worker

などを作ります。

### 同期

毎フレーム、表示状態へ合わせて、

- 座標
- 姿勢
- 可視性
- 色
- LOD
- テクスチャ
- uniform / node input

を更新します。

### 破棄

ラン終了や資源入れ替え時に GPU / Three.js 資源を dispose します。

この3段階を混ぜると、毎フレーム新しい GPU 資源を作るなどのリークにつながります。

## 3. WebGPU と TSL

Three.js の WebGPU renderer を使い、ノードベースの TSL でマテリアルやシェーダ処理を組む部分があります。

WebGPU を使う理由は単に新しい API だからではなく、

- 大規模な地球描画
- 複雑な材質
- 体積表現
- GPU 側の計算
- 多数インスタンス

を扱いやすくするためです。

## 4. 地球表面は一枚絵ではない

地球表面は高解像度データを必要な場所だけ読み込むストリーミング方式です。

主な流れは、

```text
表示需要
  ↓
必要タイル決定
  ↓
要求キュー
  ↓
HTTP
  ↓
デコード
  ↓
常駐管理
  ↓
ページテーブル
  ↓
GPU 材質
```

です。

## 5. Earth surface source

`earth-surface-source.ts` 系は、タイルの配信元やデータの所在を扱います。

描画側が直接 URL 文字列を散在させるのではなく、どのキーがどのデータへ対応するかを source にまとめます。

## 6. タイルキー

`earth-surface-tile-key.ts` は、地球表面の「どの区画か」を識別する基礎です。

LOD があるタイルシステムでは、

- レベル
- x
- y
- 面 / 投影

などを一意に扱える識別が必要です。

## 7. 要求キュー

`earth-surface-tile-queue.ts` は、タイル取得を制御します。

ここでは、

- 同一タイル要求の重複排除
- 世代管理
- HTTP 同時実行制限
- デコード同時実行制限
- 待機枠
- 中断
- 再試行
- 失敗記録

を扱います。

### なぜ段ごとに同時実行数を分けるか

ネットワーク、画像デコード、GPU へ渡す前の待機ではボトルネックが違います。

すべてを一つの「最大8件」のような枠にすると、一段が詰まっただけで他段の資源利用まで不自然になります。

## 8. 世代管理

カメラが高速に移動すると、「少し前に必要だったタイル」が到着した頃には不要になっていることがあります。

世代を持つことで、古い要求を新しい需要へ混入させず、不要なら中断できます。

## 9. 常駐管理

`earth-surface-resident.ts` などは、取得済みタイルの常駐を扱います。

GPU メモリは有限なので、「読み込んだものを永遠に保持する」ことはできません。

重要なのは、

- いま必要
- 近く必要
- 代替に使える親タイル
- 捨ててよい

を区別することです。

## 10. ページテーブル

`earth-surface-page-table.ts` は、論理タイルと GPU 上の実データの対応を扱います。

地表マテリアルは「この緯度経度ならこの巨大画像のこの位置」と直接参照するのではなく、現在常駐しているタイルをページテーブル経由で引けます。

## 11. デコード

地形・画像データはそのまま GPU へ送れない場合があります。

`earth-surface-terrain-worker.ts` などは、重いデコードを main thread から分離するための仕組みです。

### Worker を使う理由

数十 ms の同期デコードでも、ゲーム側ではフレーム落ちとして見えます。

ストリーミングでは「総処理時間」だけでなく「メインスレッドを止めない」ことが重要です。

## 12. 地表材質

`earth-surface-material.ts`、`earth-surface-material-node.ts`、`earth-surface-material-binding.ts` などは、地表データを GPU 材質へ渡します。

ここで、

- ベース色
- 地形
- 光
- 表示モード
- タイル参照

などが合成されます。

## 13. 大気

`src/render/atmosphere.ts` は、惑星の大気を描画する入口です。

宇宙から見た大気では、

- 地平線のリム
- 昼側散乱
- 夜側への遷移
- 太陽方向
- 視線方向

が重要です。

地表色の上へ単純な透明青を重ねるだけでは、軌道上から見た厚みや角度依存を表せません。

## 14. 雲

`src/render/cloud/` は雲表現を分離しています。

README にあるように、雲は地表の一部ではなく独立した描画系です。

描画経路には、

- 不透明に近い雲
- 体積的な雲
- 薄い雲
- 光学的な合成

など、性質の異なる処理があります。

雲のゲーム上の物理状態と、最終的な光学表現は同じ概念ではありません。

## 15. 不透明雲と体積雲

`opaque-cloud-surface-renderer.ts` は、地球表面へ近い方式で扱える雲の描画経路です。

一方、体積表現では ray marching のような視線方向サンプリングが必要になります。

両者を一つの巨大シェーダへ無理に統合するより、必要な光学特性に応じて描画経路を分ける方が責務を保ちやすくなります。

## 16. レイマーチング

`ray-march.ts` は、視線に沿って空間をサンプルする処理の基礎です。

体積雲や発光層では、

```text
camera
  ↓
ray
  ↓
sample 0
  ↓
sample 1
  ↓
...
  ↓
透過率と発光を累積
```

という処理が必要になります。

## 17. ブルーノイズ

`blue-noise.ts` は、サンプリングの規則的な縞を目立ちにくくするためのノイズを提供します。

ランダムノイズなら何でもよいわけではなく、空間周波数分布が見た目へ影響します。

## 18. 大気光

`airglow.ts` は夜側の淡い発光を扱います。

大気光はオーロラと違い、磁極付近だけに集中する現象ではありません。別レイヤーとして持つことで、地球夜側の見え方を分離できます。

## 19. オーロラ

`aurora-field.ts` はオーロラ場を扱います。

地球表面テクスチャに焼き込むのではなく、空間的な発光として扱うことで、

- 視線角
- 高度
- 夜側
- 発光分布

を独立に表現できます。

## 20. 天体

`render/celestial/` と天体関連ファイルは、月・惑星・太陽などの描画を扱います。

物理層の天体状態から、

- 位置
- 姿勢
- 半径
- テクスチャ
- アルベド
- 照明

を表示へ写します。

## 21. 線描画

`render/lines/` は、

- 軌道線
- 予測線
- 計画軌道
- ガイド線

などを描きます。

線は単なる Three.js Line ではなく、広い距離スケール・基準座標系・カメラ投影を考える必要があります。

## 22. スケール

宇宙ゲームでは、数 m の宇宙船と数十万 km の天体系を同時に扱います。

そのため描画側では、

- camera scale
- schematic rendering
- LOD
- marker
- line representation

を使い分けます。

「物理座標をそのまま float の mesh 座標へ入れるだけ」では精度と視認性の両方に問題が出ます。

## 23. schematic 表現

遠距離の機体や小物体は、実寸そのままでは数ピクセル未満になります。

schematic 系の表示は、物理サイズを変えるのではなく、**画面上で認識可能にする表示上の表現**です。

これはモデルの半径や衝突判定を書き換えるものではありません。

## 24. インスタンスプール

弾丸、薬莢、破片のように多数出る物体は、個別 Mesh を大量生成すると負荷が高くなります。

`instanced-pool.ts` や dynamic render 系では、同種の表示をまとめて GPU へ渡す仕組みがあります。

## 25. 熱放射

`thermal-emissive.ts` と `blackbody.ts` は、温度に応じた発光表現に関係します。

物理温度をそのまま RGB にするのではなく、黒体放射に近い色・輝度へ変換して表示します。

## 26. 描画設定

`graphics-settings.ts` と `render-style.ts` は、描画品質と見せ方を分ける入口です。

- GPU 負荷に関係する品質
- 世界をどう見せるかというスタイル

を同じ設定へ潰さないことで、設定の意味が明確になります。

## 27. Render Lab

`npm run render-lab` は、ゲーム全体を立ち上げずに描画を検証するための環境です。

描画変更では、

1. Render Lab で対象だけ確認
2. shot を取る
3. compare で比較
4. 必要なら本ゲームで確認

という順が効率的です。

## 28. Cloud Lab

`npm run cloud-lab` は雲専用の検証環境です。

雲は気象データ・体積表現・光学・時間変化が絡むため、通常ゲーム画面だけで調整すると原因切り分けが難しくなります。

## 29. 描画変更で壊しやすい境界

### render がモデル意味を持つ

「敵だから赤」ではなく、上位が色を決める方がよい場合があります。

### GPU 資源を毎フレーム生成

同期と構築の混同です。

### 表示キャッシュを正本として読む

表示をオフにしただけで進行結果が変わる危険があります。

### 座標系変換を個別マテリアルで勝手に行う

同じ対象の HUD、線、3D 位置が一致しなくなります。
