# 08. 開発方針

<p align="center">
  <img src="../.github/readme/development-docs.svg" alt="仕様、アーキテクチャ、コーディング規約、実装、検証の関係" width="100%">
</p>

この章は「このリポジトリで変更を加えるとき、何を正本として、どう進めるか」を説明します。最終的な規則は [AGENTS.md](../AGENTS.md)、[CODING-RULE](../DEVELOP/CODING-RULE.md)、[ARCHITECTURE](../DEVELOP/ARCHITECTURE.md) が正本です。

## 1. 文書ごとの役割を混ぜない

### README

ゲームと技術の入口です。

### WIKI

コードベースを理解するための地図です。

### SPEC

ゲームが**どう振る舞うべきか**を定義します。

### ARCHITECTURE

値をどこへ置き、誰が所有し、どう接続するかを定義します。

### CODING-RULE

コードの書き方、命名、コメント、設計、テストを定義します。

### CONTEXT

ドメイン用語の正本です。

### memos

計画・検討・作業記録です。明示指示がない限り書き換えません。

## 2. 「現在」はコードが原本

WIKI にファイル名が書かれていても、最終的に現在の構造を決めるのはコードです。

文書を見て「このクラスがあるはず」と決めつけず、実際に検索します。

これは、説明文がコードより先に古くなることを避けるための方針です。

## 3. SPEC は実装報告ではない

SPEC は「実装済み一覧」ではありません。

未実装の内容があっても正常です。

実装が終わったから SPEC に追記する、という使い方はしません。

## 4. 変更を始める前に読むもの

通常のコード編集ではまず CODING-RULE を読みます。

次に、変更が、

- 状態所有
- import 境界
- 新しい層
- 直列化
- 装置との接続
- フレーム位相

へ影響するなら ARCHITECTURE を読みます。

ゲームの振る舞い自体を変更するなら、対応する SPEC を先に読みます。

## 5. 物理変更

物理変更では、

- 単位
- 座標系
- 時刻
- 現実のモデル
- 数値積分
- 誤差

を確認します。

見た目を合わせるためだけのマジックナンバーを physics に入れるのは避けます。

## 6. 一般化しすぎない

CODING-RULE では、目の前の要求から離れた将来を勝手に想定して巨大な抽象化を作らないことが重要です。

一般化は、

- 既に複数の実例がある
- 共通性が明確
- 将来仕様が確定

しているときに行います。

## 7. 責務を名前でなく状態から決める

「Camera だから render」ではなく、そのクラスが何を所有するかで置き場を決めます。

論理カメラ選択は Viewer、Three.js Camera は render、というように同じ「カメラ」でも層が違います。

## 8. 正本の書き手を一つにする

同じ値を複数クラスが勝手に書く設計を避けます。

外部から変更したい場合は、所有者が提供する命令を通します。

## 9. public mutable field を避ける

モデル状態が public で自由に代入できると、誰が整合性を守るか分からなくなります。

所有者のメソッドを通し、内部で必要なキャッシュ破棄や検証をまとめます。

## 10. 一つの意味に一つの値

「A または B」を合成した boolean を正本として保存すると、なぜ true なのかという情報を失います。

原因が複数あるなら原因を別々に持ち、最終的な表示や判断で合成します。

## 11. 配列と外部対応表

配列要素へ付随するデータを、別配列や index map で外部管理すると同期漏れが起きやすくなります。

その要素自身が所有すべき状態なら、要素側へ持たせます。

## 12. mutable オブジェクトの流用

同じオブジェクトの中身を全交換して「別の意味の物体」へ使い回す設計は避けます。

意味が変わるなら新しいインスタンスにします。

例外は、明確な性能上の理由がある場合です。

## 13. 座標系を明示する

ベクトルが、

- ECI
- body local
- camera
- rotating frame
- screen

のどれなのかを曖昧にしません。

特に同じ `Vec3` 型で複数座標系を表す場合、変数名・関数境界・コメントで意味を保ちます。

## 14. 単位を明示する

物理量は、使用前に単位を確認します。

典型例:

- 距離 [m]
- 速度 [m/s]
- 加速度 [m/s²]
- 時間 [s]
- 角度 [rad]
- 角速度 [rad/s]
- 質量 [kg]
- 慣性モーメント [kg·m²]
- 力 [N]
- トルク [N·m]

## 15. コメント

コメントは「コードを日本語に言い換える」ためではなく、

- なぜこの境界なのか
- なぜこの順序なのか
- 何をしてはいけないか
- どの物理前提か
- なぜ例外なのか

を残すために使います。

## 16. 名前

名前は、実装手段より意味を表します。

例えば「Manager」を何でも付けるのではなく、

- Selection
- Store
- System
- Presenter
- View
- Rules
- Queue

など、その責務に近い語を使います。

## 17. コマンドと出来事

### Command

これからモデルへ行わせたいこと。

### Event

モデル進行の結果、起きたこと。

この2つを同じ message 型へ混ぜない方が、データの向きが明確です。

## 18. Presenter

Presenter はモデルの意味を知り、装置の語彙へ変換します。

- モデルを直接描画オブジェクトにしない
- render がゲーム意味を知らない
- HUD がモデルの内部構造へ直接依存しない

ための中間層です。

## 19. キャッシュ

キャッシュを持つ場合は、

- 何をキーにしているか
- いつ無効化されるか
- 捨てても再生成できるか

を明確にします。

キャッシュがないと復元できないなら、それはキャッシュではなく正本です。

## 20. 例外

ARCHITECTURE の規則どおりに分けられない場合、例外理由を具体的に残します。

規則を弱めたり、名前を変えて検査を避けたりしません。

## 21. boundary check

`tools/check-boundaries.mjs` は import 境界などを自動検査します。

これは ARCHITECTURE の代理です。

「検査が通ったから設計的に正しい」ではありませんが、既知の禁止依存を早く検出できます。

## 22. allowlist

`boundary-allowlist.json` は既存違反を管理するためのもので、新しい例外を気軽に追加する場所ではありません。

新規変更では違反数を増やさないのが基本です。

## 23. ブランチ

通常の変更は、

```text
main
  ↓ branch
作業
  ↓ review / test
PR
  ↓
main
```

で進めます。

## 24. release

`release` は公開用で、main への push を受けた CI が生成します。

手で編集しません。

## 25. PR 前レビュー

PR を出す前に、

- 不要差分
- デバッグコード
- コメント
- import 境界
- テスト
- generated asset
- 文書リンク
- UI 崩れ

を見直します。

## 26. generated file

生成物には、生成コマンドと正本が別にある場合があります。

生成済みファイルだけを直接直すと、次回生成で消えます。

変更前に、

- source
- generator
- generated output

のどれかを確認します。

## 27. asset export

`npm run export-assets` は全アセットの識別子へ影響するため、必要な変更時だけ実行します。

識別子だけ変わった不要差分を commit しないことも規約にあります。

## 28. UI 変更

UI / DOM / CSS を変える場合は、

- レスポンシブ
- 入力占有
- モーダル
- タッチ
- テーマ
- GitHub / browser 上の実表示

を確認します。

## 29. 描画変更

描画変更は、可能なら Render Lab や専用ショットで目視確認します。

数値テストだけでは、

- clipping
- banding
- aliasing
- 色
- LOD 境界

を確認できません。

## 30. 変更報告

変更報告では、

- 何を変えたか
- なぜ
- どの検証をしたか
- できなかった検証
- 例外
- 既知の制約

を明確にします。
