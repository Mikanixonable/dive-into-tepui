# 03. ゲームモデル

<p align="center">
  <img src="../.github/readme/gameplay-loop.svg" alt="目標捕捉から交戦までのゲームプレイループ" width="100%">
</p>

`src/game/` は、一回のランの「何が存在し、何が起き、何を選んでいるか」をまとめる層です。物理計算そのものは `physics/`、GPU 表示そのものは `render/` に分離し、ゲーム上の意味と進行をここで組み合わせます。

## 1. Game が持つもの

`src/game/game.ts` の `Game` は1ランのモデル層の根です。

代表的には次の所有者を束ねます。

- `CelestialSystem`: 天体系
- `DynamicSystem`: 動的エンティティ群
- `SimSpeedManager`: 時間加速
- `ControlSelection`: 操作対象
- `Stage`: ステージの進行
- `PlanNodeRules`: 軌道計画の進行規則
- `Viewer`: セーブごとの視点状態
- `Predictor`: 未来予測
- `RunEventLog`: 直近の出来事
- `CommandQueue`: モデル外から来た命令

Game が「全部の内部フィールドを直接持つ」のではなく、**各責務の所有者を束ねる**点が重要です。

## 2. 新しいランと復元ラン

Game には概ね2つの生成経路があります。

### 新規開始

```text
StageClass
   ↓
CelestialSystem を構築
   ↓
DynamicSystem
   ↓
時間加速・操作対象
   ↓
Stage
   ↓
Viewer
   ↓
Game
```

初期配置が天体系や動的エンティティを必要とするため、構築順には意味があります。

### セーブから復元

復元では、保存された元期・動的エンティティ・操作対象・ステージ・視点を再構成します。

重要なのは、GPU オブジェクトや DOM をそのまま復元するのではなく、**モデルの保存記録から新しい表示資源を作り直す**ことです。

## 3. DynamicSystem

`src/game/dynamic/dynamic-system.ts` は、動く実体の集合を扱う大きな入口です。

主な責務は、

- エンティティの保持
- spawn の受付
- 上限管理
- 寿命終了した実体の回収
- ID 採番
- 1フレームの前進
- NaN などの異常検出
- 一部の描画プールとの接続

です。

### 実体と運動を分ける

動的エンティティは「ゲーム上の個体」と「運動状態」を同一概念に潰さないように設計されています。

例えば宇宙船なら、

- 船体構造
- HP / 損傷
- 武器
- AI / プレイヤー操作
- 位置・速度
- 姿勢

は関連しますが、すべて同じ責務ではありません。

## 4. Simulator

DynamicSystem 内部の進行では `Simulator` が運動を進めます。

大まかには、

1. そのフレームの制御量を決める
2. 物理状態を積分する
3. 接触・寿命・破壊などを反映する
4. 次の時刻へ進める

という流れです。

表示用の軌道線を更新するために世界状態を書き換える、といった逆流を作らないことが重要です。

## 5. 時間加速

`SimSpeedManager` はシミュレーション速度を管理します。

時間加速は単純に「描画を飛ばす」ものではなく、モデル進行で使うシミュレーション時間の進み方へ影響します。

### 注意点

時間加速とポーズは別概念です。

- ポーズ: シミュレーション進行を止める
- 時間加速: 進行する時間量を変える

一時停止中でも UI 命令は受け付けられる必要があるため、「入力自体を止める」わけではありません。

## 6. CommandQueue

モデル外から状態を変えたいときは、命令をキューへ積みます。

対象には、

- ビュー切り替え
- 航法ターゲット変更
- 軌道計画編集
- 操作対象変更
- 時間倍率変更
- カメラ選択
- 表示選択

などがあります。

命令を所有者のメソッドへ直結させず、一度キューへ集めることでフレーム位相を守ります。

## 7. RunEventLog

イベントは「状態」と違い、一回だけ意味を持つ記録です。

例として、

- 被弾
- 破壊
- 操作対象変更
- ステージ上の出来事
- 通知対象
- 音を鳴らす契機

などがあります。

表示側はイベントを読み、通知・効果音・閃光へ変換します。

## 8. Stage

`src/game/stages/` はステージごとのルールを持ちます。

ステージが担うのは、主に、

- 初期配置
- 勝敗条件
- ステージ固有ルール
- ステージ固有 HUD
- 敵の編成
- プレイ終了条件

です。

### Stage と Game の違い

Game は「ラン全体の共通モデル」、Stage は「そのランで選ばれたルール」です。

ステージ固有の処理を Game 本体へ積み上げていくと、ステージ追加のたびに共通モデルが分岐だらけになるため、境界を分けます。

## 9. 操作対象

`ControlSelection` は、プレイヤーがどの controllable を操作しているかを持ちます。

船体が複数存在したり、操作対象を切り替えたりできるため、「プレイヤー = 1機の固定船」という設計にはしていません。

表示側は操作対象を読めますが、操作対象そのものを DOM 側で所有しません。

## 10. Viewer

`src/game/viewer/viewer.ts` は、セーブごとに残る「視点」の根です。

含まれる代表的な選択は、

- 戦闘 / マップビュー
- カメラ
- 航法ターゲット
- 軌道ガイド
- 個体表示
- 軌道要素の基準
- 予測パネル

です。

### Settings との違い

Viewer は**そのセーブで何を見ているか**です。

Settings は**アプリ全体でどう見せたいか**です。

例えば、

- 現在注視している天体 → Viewer
- テーマ色 → Settings
- マップの座標基準 → Viewer
- 描画品質 → Settings

という分け方になります。

## 11. Predictor

未来軌道は `Predictor` が扱います。

重要なのは、予測軌道を正本として進行しないことです。

予測は、

- HUD
- マップ
- マニューバー計画
- 会合確認

のために必要ですが、世界の真実はその時点の実状態です。

## 12. 軌道計画

<p align="center">
  <img src="../.github/readme/maneuver-navigation.svg" alt="マニューバーノードとラグランジュ点を使った軌道計画" width="100%">
</p>

`src/game/plan/` は、プレイヤーが未来の軌道を編集する仕組みです。

### ノードが表すもの

マニューバーノードは、単なる「矢印」ではありません。

- 実行時刻
- Δv
- ノード前の予測
- ノード後の予測
- 上流ノードとの依存

を持つ計画要素です。

上流ノードを変更すると、下流の予測前提も変わります。そのため計画は単なる独立点の集合ではなく、順序を持つ系列です。

## 13. PlanDisplay と PlanPath

モデル内の計画と、画面に出す折れ線・ハンドルは別です。

表示側では、

- 計画軌道
- ノードマーカー
- Δv 操作
- 実行ガイド

を組み立てます。

この分離により、描画上の線が消えても計画そのものは失われません。

## 14. 航法ターゲット

航法ターゲットは戦闘ターゲットと近い概念ですが、単なる敵選択ではありません。

天体・機体・その他の対象へ相対運動を表示したり、カメラやマーカーの基準にしたりするために使われます。

`NavTargetPresenter` は、モデルのターゲット選択を画面上の相対交点・再接近点などへ変換します。

## 15. 戦闘

`src/game/combat/` と動的エンティティ群が、射撃・被弾・破壊を扱います。

戦闘は独立したアーケード層ではなく、

- 相対運動
- 弾道
- 時間加速
- 姿勢
- 船体構造
- 破片

と同じシミュレーションに乗っています。

## 16. CREATIVE

`src/game/creative/` は、通常ステージの勝敗ルールから離れて実体を配置するための機能群です。

CREATIVE でも軌道・物理層は共通です。つまり「別エンジン」ではなく、同じ Game / DynamicSystem 上で初期状態を自由に組む方向です。

## 17. GamePresentation

`src/game/game-presentation.ts` は表示導出の根です。

非常に多くの協力者を組みますが、役割をまとめると、

- 入力をゲーム命令へ変換
- カメラ状態を導出
- HUD を同期
- マーカーを作る
- 軌道線を作る
- 音声を宣言
- 描画側へ状態を渡す

です。

### GamePresentation が大きい理由

ゲームの意味を知る表示導出が集まる場所だからです。

一方で、GPU 資源の詳細は render、モデルの正本は Game に残します。

## 18. 入力フェーズと表示フェーズ

GamePresentation 内でも、入力処理と表示処理を分けています。

- `GameInputPhase`: 生入力から操作量・命令を作る
- `DisplayPhase`: 進行後のモデルから表示宣言を作る

同じクラスの中にあっても「いつ動く処理か」を混ぜないことが重要です。

## 19. モデルを読むときのコツ

`game/` は大きいため、フォルダを上から全部読むより「正本の所有者」を探すと理解しやすくなります。

### 例: 時間倍率

1. `SimSpeedManager` が所有
2. コマンド側が変更要求
3. Game の進行で反映
4. HUD は読み取って表示

### 例: 航法ターゲット

1. Viewer の選択が所有
2. コマンドで変更
3. Presenter が表示へ変換
4. Marker / Camera が読む

## 20. コードを読む順番

1. `src/game/game.ts`
2. `src/game/dynamic/dynamic-system.ts`
3. `src/game/game-presentation.ts`
4. `src/game/viewer/viewer.ts`
5. 興味のあるサブフォルダ
6. そこで呼ばれる `physics/` と `render/`
