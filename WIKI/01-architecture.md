# 01. アーキテクチャ

<p align="center">
  <img src="../.github/readme/runtime-structure.svg" alt="物理、ゲームモデル、表示導出、描画の実行時構造" width="100%">
</p>

Dive into Tepui のアーキテクチャを理解する中心概念は、**状態の種類、正本の所有者、フレーム位相、装置との境界**です。詳細な規則の正本は [DEVELOP/ARCHITECTURE.md](../DEVELOP/ARCHITECTURE.md) にあります。この章は、その規則が実際のコードを読むときにどう見えるかを説明します。

## 1. 状態を4種類に分ける

### 定義

実行中に変化しない値です。型、定数、データ表、純関数、数学ユーティリティなどが該当します。

代表的な場所は `src/math/` と `src/theme.ts` です。ここに可変なゲーム状態が入り始めると、誰がいつ書き換えるのかが不明になります。

### 時刻から決まる層

構築時に決まった不変値と時刻 `t` から答えが決まるものです。軌道・天体暦・座標変換など、物理層の多くがこれに属します。

`src/physics/` が主な置き場です。結果に影響しないメモ化は持てますが、ゲーム進行そのものの正本はここに置きません。

### モデル

捨てると他の層から作り直せない値です。

- 宇宙船の位置・速度
- 燃料・弾薬
- 損傷状態
- ステージの進行
- 現在の時間加速
- 操作対象
- セーブごとの視点状態
- プレイヤーが置いた軌道計画

これらはゲーム世界の「事実」なので、書き手を一つにします。

### 導出

正本から作り直せる値です。

- 軌道線
- HUD 文面
- 画面上のマーカー
- Three.js オブジェクト
- GPU バッファ
- ピック用の一時形状
- 描画のキャッシュ

導出値は便利だからといって正本へ昇格させません。表示物からゲーム状態を逆算して進行に使う設計は避けます。

## 2. import は不変な側へ向ける

概念的には次のような依存方向です。

```text
math / physics
      ↑
   game model
      ↑
presentation derivation
      ↓
render / hud / audio / input
```

「上」「下」の言い方より重要なのは、**装置がゲーム意味を import しない**ことです。

`render/` が「これは敵だから赤くする」と判断するのではなく、表示導出側が色や形を決めて宣言として渡す方が境界を保ちやすくなります。同様に `audio/` は「敵を倒した」というモデル意味ではなく、鳴らすべき効果音の宣言を受け取る側です。

## 3. Game は1ランのモデルの根

`src/game/game.ts` の `Game` は、一回のランのモデル層の根です。

大きく見ると次の所有者を束ねます。

- 天体系
- 動的エンティティ群
- 時間加速
- 操作対象
- ステージ
- 軌道計画の進行規則
- 実行中の出来事
- 視点
- 予測器

Game 自身がすべての値を直接持つのではなく、それぞれの所有者を束ねる「根」になっています。

### なぜ根が必要か

セーブ、復元、ランの開始・終了、進行順序を一か所から組み立てるためです。モデルの根が曖昧だと、表示側やランチャーが各サブシステムの内部状態へ直接触れ始めます。

## 4. Run はモデルと表示を組み合わせる

`src/run/run.ts` の `Run` は、`Game` と `GamePresentation`、ページ上の装置群を組み合わせます。

`Run.create()` / `Run.resume()` は、モデルを作る・復元する入口です。その後 `launch()` で表示導出を接続し、描画資源を暖機します。

この場所は「ゲームルール」ではなく**アプリケーションの組み立て**です。

## 5. 1フレームの4位相

### 1) 入力の解釈

生の入力を読み、モデルへ渡す命令と操作量を作ります。

この段階でモデルの正本を直接変更しません。DOM イベントはフレーム外で発生するため、そこから直接ゲーム状態を書き換えると処理順が壊れます。

### 2) 進行

`Game.advance()` がモデルの進行を担当します。

- 積まれた命令を適用
- パイロット操作を反映
- 動的システムを進める
- ステージルールを進める
- 軌道計画の実行条件を進める
- 出来事を記録

物理的な `dt` が世界へ影響するのはこの位相です。

### 3) 導出と同期

進行後の状態から、表示に必要な情報を作ります。

- カメラ追従
- 表示フレームの解決
- 予測軌道の需要
- HUD
- マーカー
- 軌道線
- Three.js / DOM への同期

この段階でモデルを書き換えないことが重要です。

### 4) 描画

WebGPU / Three.js へ描画命令を発行します。

ここは世界を進める段階ではありません。

## 6. 命令キュー

モデル層の外から来た「書き換え要求」は、その場で正本へ代入せず命令キューへ積みます。

これにより、クリック、キー押下、HUD 操作などがフレームのどの瞬間に発生しても、モデル側では進行位相の決まった場所で適用できます。

### 命令キューが解決する問題

直接書き換えでは、次のような違いが生まれやすくなります。

- 描画前にクリックした場合
- 描画後にクリックした場合
- 一時停止中に操作した場合
- DOM イベントが連続した場合

キューへ集めれば、モデルにとっては「受け付けた順に進行先頭で処理する」という一つの規則になります。

## 7. 出来事と状態を分ける

「燃料が 40% である」は状態です。「今のフレームで被弾した」は出来事です。

一回きりの効果音、通知、閃光などを状態として持つと、次のフレームにも残って二重再生される危険があります。そのためモデルは出来事を記録し、表示導出がそれを装置の宣言へ変換します。

## 8. 進行と視点

モデル層の中でも、世界の進行とプレイヤーの視点を分けます。

### 進行

- 位置
- 速度
- 燃料
- ステージ
- 勝敗
- 操作対象
- マニューバーノード
- 時間加速

### 視点

- カメラ
- 注視対象
- マップの表示原点
- 軌道表示の基準フレーム
- 表示期間
- セーブごとの表示選択

視点は進行を読めますが、**進行は視点を読まない**のが基本です。画面を切り替えただけで宇宙船の物理が変わらないようにするためです。

## 9. 「需要」は計算量だけを変える

表示側は「この対象の予測軌道を何秒先まで欲しい」と要求できます。この要求は予測計算の長さを変えます。

ただし、需要の違いで世界の進行結果が変わってはいけません。

これは大量の予測軌道を必要な範囲だけ計算しながら、表示設定がシミュレーションを変えることを防ぐ考え方です。

## 10. セーブは位相の間で取る

セーブは、モデル進行が確定し、表示同期へ入る前の状態を読むのが自然です。

`Run` は `SnapshotSource` としてモデルの直列化を外へ提供します。表示用 GPU 資源や DOM の一時状態はセーブへ入りません。

## 11. build と frame を混ぜない

描画オブジェクトを初めて構築する処理と、毎フレーム同期する処理は別物です。

- build: 資源を作る、シーンへ登録する
- sync: 既存資源へそのフレームの表示状態を反映する
- render: 描画命令を出す
- dispose: 所有資源を捨てる

この寿命管理が曖昧だと GPU 資源リークや二重登録が起きます。

## 12. 変更時の判断

新しい値を足すときは、まず次を問います。

1. 捨てたら再生成できるか
2. 誰が唯一の書き手か
3. セーブへ入るべきか
4. ランを跨いで残るか
5. 表示選択で世界が変わらないか
6. 装置がゲーム意味を知る設計になっていないか

この6問だけで、多くの置き場判断を絞れます。
