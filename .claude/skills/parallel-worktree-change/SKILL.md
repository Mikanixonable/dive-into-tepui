# worktree で並列実装し、統合する

この Skill は、実装作業の実行主体ではなく、計画・委譲・レビュー・統合を管理する
オーケストレーターである。ユーザーの明示的な指示とリポジトリの `AGENTS.md` / `CLAUDE.md`
を最優先する。

## 1. 適用するか判定する

次のいずれかに該当する中〜大規模な変更に適用する。

- 複数ファイルまたは複数レイヤーにまたがる
- 新機能、仕様変更、機能削除、相互作用の変更を伴う
- 実装・テスト・仕様書など、独立した作業へ分解できる
- 実装後にレビューと回帰確認が必要になる

単一ファイルの単純修正、軽微なバグ修正、短い文書修正には適用しない。
分解できる作業がない場合も、worktree は使うが、Luna を無理に起動しない。

ユーザーが「計画を書いて」と明示した場合は `/write-plan` の規則に従って計画で停止する。
それ以外の段取りが必要な変更では `/write-and-run-plan` を併用し、計画は一時ファイルに置いて
完了後に削除する。

## 2. 開始時に状態を固定する

実装前に次を記録する。

- 起点ブランチ名
- 起点 HEAD (`git rev-parse --short HEAD`)
- 起点 worktree のパス
- `git status --short` の内容

既存の未コミット変更をユーザーの変更として扱い、`reset`、`checkout`、強制 stash、上書きで
破壊しない。変更が今回の作業と衝突する、または作業がその未コミット変更を前提とする場合は、
それを明示して統合前に停止する。無関係な変更を勝手にコミットへ含めない。

起点ブランチが `main` または `release` の場合は、リポジトリ規約を優先する。中〜大規模変更を
直接コミットせず、必要なら `/send-pr` のフローへ切り替える。作業中に起点ブランチが移動した
場合も、ユーザーの新しい変更を暗黙に取り込まず、統合前に停止する。

## 3. 専用 worktree を作る

起点 HEAD から、衝突しない一時ブランチ名と専用 worktree を作る。実装、仕様更新、テスト、
レビュー修正は専用 worktree 内で行い、起点 worktree では行わない。

worktree の作成に失敗した場合や、作業対象を安全に分離できない場合は、無理に実装を始めず
理由を報告する。

## 4. 実装前の規約・仕様確認

専用 worktree で、実装前に以下を確認する。

- `AGENTS.md` と `CLAUDE.md`
- `DEVELOP/CODING-RULE.md`
- 変更に関係する `DEVELOP/SPEC/`
- 変更内容に応じた既存 Skill（`/modify-feature`、`/add-feature`、`/ui-design`、
  `/rendering-workflow` など）

機能の追加・変更・削除では、`/modify-feature` の手順を通し、仕様をコードより先に確定する。
仕様書を更新する必要がある場合も、実装前に更新する。実装完了後にコードの現状を SPEC/ へ
写し戻して整合させない。

コードの現在状態を説明するだけの文書は作らない。`memos/` はユーザーが明示的に指示した場合
のみ変更する。必要な仕様書・ユーザー向け文書・設計文書は、今回の変更の成果物としてのみ更新する。

## 5. 作業を分解し、Luna に委譲する

依存関係とファイル所有範囲を先に整理する。各作業には少なくとも次を渡す。

- 目的と受け取りたい成果物
- 担当ファイルと、触ってはいけない範囲
- 読むべき規約、仕様、関連 Skill
- 前提となる判断と完了条件
- 担当分で実行すべき検証

依存関係がなく、担当ファイルが重複しない作業は、利用可能なサブエージェント機構で Luna に
並列委譲する。共有インターフェース、仕様の分岐、共通化の可否など判断そのものはメイン
エージェントが担当する。依存する作業は先行作業の結果を確認してから委譲する。

同じファイルを複数のエージェントに触らせない。分割できない作業や、Luna を利用できない環境
ではメインエージェントが直列に実施し、フォールバックを最終報告に残す。

委譲するときは `/delegate` の指示とレビュー手順に従う。サブエージェントの報告だけを成果物と
みなさず、受け取った後に実際の差分を読み、担当範囲・規約・検証結果をメインエージェントが確認する。

## 6. 実装後にレビューし、必要なら修正する

全作業が揃ったら、変更全体を次の観点でレビューする。

- 要件・仕様を満たしているか
- 既存の呼び出し元、状態の所有者、実行順を壊していないか
- 重複実装、旧名・旧実装、不要なデバッグコードが残っていないか
- エラー処理、境界条件、後方互換性、テストの不足がないか
- `DEVELOP/CODING-RULE.md` と関連 Skill に違反していないか

可能なら、実装担当とは独立した Luna のレビューを追加する。今回の変更が原因のバグ、回帰、
仕様違反、または正しさに必要なリファクタリングは修正する。修正後は影響するレビューと検証を
再実行する。

今回の変更と無関係な既存バグやリファクタリング候補は修正せず、最終報告だけに記載する。
ただし今回の変更を安全に統合できない重大な問題は、統合せず停止する。

## 7. 検証する

検証は変更箇所に対応させ、リポジトリ規約を優先する。このリポジトリでは既定として、

- `npm run typecheck` は常に実行する
- 触った層の回帰テスト（`test:physics`、`test:math`、`test:game`、`test:render`）を実行する
- ヘッドレス実行検証は、ユーザーが実行時の動作確認を求めた場合だけ実行する

テストが失敗したら、今回の変更が原因か、既存・環境起因かを切り分ける。今回の変更が原因なら
修正して再実行する。既存・環境起因であっても、結果と根拠を報告し、未検証のまま成功扱いにしない。

## 8. 起点ブランチへ統合し、コミットする

レビューと検証が完了したら、統合前に次を再確認する。

- 起点ブランチが開始時の想定から移動していない
- 起点 worktree の既存変更を巻き込まない
- 作業対象外のファイルを staging しない

条件を満たす場合のみ、専用ブランチの成果を起点ブランチへ統合する。コミットメッセージは
リポジトリの既存規約を確認して決め、関係するファイルだけを明示的に stage する。

統合、コミット、検証のいずれかに失敗した場合は、強制操作で辻褄を合わせず、専用 worktree を
残して失敗箇所と復旧に必要な状態を報告する。

## 9. cleanup と最終報告

統合とコミットが成功した場合のみ、一時 worktree を削除する。一時ブランチも、この作業のために
作成したもので、統合済みであることを確認できた場合に限り削除する。削除に失敗した場合は、
パスと状態を報告する。

最終報告には次を含める。

- 実装内容と変更したファイル
- 起点ブランチと commit hash
- Luna に委譲した作業、または利用できず直列化した理由
- 実行した検証と結果
- worktree と一時ブランチの cleanup 結果
- 修正したレビュー指摘
- スコープ外として残したバグ・リファクタリング候補（ファイル、箇所、影響、推奨対応）
