# 計画を書く

**書くのは「これから何をするか」であって、現状の説明ではない。** 文書にする目的は2つ —
作業中に出うる問題を着手前に洗い出すことと、**ユーザーが着手前に計画を検査できるようにすること。**

**この手順は、ユーザーが「計画を書いて」と明示したときだけ通す。** 明示がないまま段取りの要る変更を
任されたなら `/write-and-run-plan` — 計画を書くかどうかは自分で決めてよいが、書いて止まるのは
ユーザーが検査すると言ったときだけ。

**この手順では実施しない。** 書き終えたら止まり、検査を待つ。実施は `/run-plan`。

## 1. 書き先を確定させる

ユーザーが指定したファイル(典型的には `memos/*/*.md`)に書く。指定がなければ **どこへ書くかを問う。**
`memos/` は指示があったときだけ書き換える領域なので、既存ファイルへ追記するのか新規に作るのかを
勝手に決めない。

## 2. 目的を書く

計画の冒頭に、**なぜこれをやるのか** を置く。

- **バグ修正・リファクタリング** — 現状の問題と、修正後に期待される状態。
- **新機能** — `DEVELOP/SPEC/` へ追記する文面をそのまま書く。仕様はコードより先行するので、
  **SPEC/ の更新自体を最初のステップにする**(手順は `/modify-feature`)。

## 3. 変更が必要な箇所を洗い出す

コードから調べ、ファイル単位で列挙する。**「たぶんこの辺」で書かない** — 洗い出しの漏れは実施中に
必ず表面化し、そのとき計画は既に信用を失っている。

広い走査が要るならサブエージェントへ委譲する(`/delegate`)。
状態の持ち主が絡むなら `/ownership`、実行順が絡むなら `/callstack`。

## 4. 達成目標を書く

**何が満たされたら終わりなのか** を、確認できる形で書く。「軽くなる」ではなく「◯◯が 0 になる」。
全ステップ実施後のレビューでここを1つずつ当てるので、判定できない書き方をしない。

## 5. 手順を着手順に書く

- **上から順に着手できる並びにする。** 依存があるものは後ろへ置く。
- 1ステップは **独立して commit できる単位** にする。中途半端な状態で終わるステップを作らない。
- 各ステップに、そのステップの完了条件を書く。

## 6. 見積りを書く

**導出式を併記する。** 「30分」ではなく「1歩あたり◯µs × 300歩/frame = ◯ms」。実測が得られたら
実測値で置き換える。**導出式のない数字は後から検証できない** ので書かない。

## 7. リスクと落とし穴を書く

**無言で間違う壊れ方** を列挙し、「リスク / 影響 / それが露見する場所」の表にする。全ステップ
実施後のレビューでこの表を1つずつ当てるので、**当てられる書き方をする** — 「注意する」は当てられない。

## 書かないこと

- **他文書・過去版・会話への参照。** 必要な事実は本文へ埋め込み、**この文書単体で読んで着手できる
  状態** を保つ。「前回の議論のとおり」は、次のセッションでは何も指していない。
- **経緯・棄却の履歴。** 検討の過程は計画ではない。ただし却下した案の **問題そのものが残る** なら、
  概要・却下理由・残る問題だけを書く(同じ案を再提案しないため)。
- **コードの現状の解説。** コードを読めば分かることを書き写せば、次の変更で嘘になる。
