# 計画を書く

**書くのは「これから何をするか」であって、現状の説明ではない。** 文書にする目的は2つ —
作業中に出うる問題を着手前に洗い出すことと、**ユーザーが着手前に計画を検査できるようにすること。**

**この手順は、ユーザーが「計画を書いて」と明示したときだけ通す。** 明示がないまま段取りの要る変更を
任されたなら `/write-and-run-plan` — 計画を書くかどうかは自分で決めてよいが、書いて止まるのは
ユーザーが検査すると言ったときだけ。

**この手順では実施しない。** 書き終えたら止まり、検査を待つ。実施は `/run-plan`。

## 文書の骨格

```text
目的
決めたこと(必要なら)
達成目標
手順
  手順 N. <名前>
    目的 / 変更が必要な箇所 / 達成条件と検証
見積り
リスクと落とし穴
```

## 1. 書き先を確定させる

ユーザーが指定したファイル(典型的には `memos/*/*.md`)に書く。指定がなければ **どこへ書くかを問う。**
`memos/` は指示があったときだけ書き換える領域なので、既存ファイルへ追記するのか新規に作るのかを
勝手に決めない。

## 2. 目的を書く

計画の冒頭に、**なぜこれをやるのか** を置く。

- **バグ修正・リファクタリング** — 現状の問題と、修正後に期待される状態。
- **新機能** — `DEVELOP/SPEC/` へ追記する文面をそのまま書く。仕様はコードより先行するので、
  **SPEC/ の更新自体を最初の手順にする**(手順は `/modify-feature`)。

計画の中で**自分が決めたこと**があるなら、目的の直後に「決めたこと」の節を置く。
何を、何を根拠に決めたか。**ユーザーが覆せる形で書く** — 覆されたときにどの手順が変わるかまで書く。

## 3. 達成目標を書く

**計画全体として、何が満たされたら終わりなのか** を、確認できる形で書く。
「軽くなる」ではなく「◯◯が 0 になる」。全手順の実施後のレビューでここを1つずつ当てるので、
判定できない書き方をしない。

手順ごとの「達成条件」(下の 4)とは別物である。こちらは**計画全体**の合格条件。

## 4. 手順を着手順に書く

- **上から順に着手できる並びにする。** 依存があるものは後ろへ置く。
- 1手順は **独立して commit できる単位** にする。中途半端な状態で終わる手順を作らない。
- **各手順は次の3つを持つ。**

### 目的

**その手順が何を変えるのか、なぜそれが要るのか。** 1〜3文。
計画全体の目的の写しではなく、**この手順だけの理由**を書く。
挙動を変えない手順(移動・集約・改名)なら「**この時点で挙動は変えない**」と明記する。

### 変更が必要な箇所

依存関係、作業範囲を調査し、列挙する。
**コードから調べ、ファイル単位で列挙する。** 表にして、ファイルと「何をするか」を並べる。
**「たぶんこの辺」で書かない** — 洗い出しの漏れは実施中に必ず表面化し、そのとき計画は既に
信用を失っている。新規ファイルは「(新規)」と明示する。

広い走査が要るならサブエージェントへ委譲する(`/delegate`)。
状態の持ち主が絡むなら `/ownership`、実行順が絡むなら `/callstack`、既存の呼び出し元が絡むなら
`/inv-callstack`。

### 達成条件と検証

**その手順が終わったと言える状態。** 観測できる形で書く。 走らせるコマンドと、目で見る場所を具体的に書く。

- 既定は `npm run typecheck`。**常に書く。**
- `src/physics/` を触る手順は `npm run test:physics`。
- 絵が変わりうる手順は、**どの画面のどこを見るか**まで書く。
- グレップで確かめられる達成条件は、**その検索語を書く。**
- リファクタリングや一元化なら「〜が `src/` から 0 件になる」「〜の分岐が消える」

**「動作を確認する」は検証ではない。** 何を打って、何が出れば通ったのかを書く。

## 5. 見積りを書く

**導出式を併記する。** 「30分」ではなく「1歩あたり◯µs × 300歩/frame = ◯ms」。実測が得られたら
実測値で置き換える。**導出式のない数字は後から検証できない** ので書かない。

手順ごとに分かれているなら手順ごとに出す。

## 6. リスクと落とし穴を書く

**無言で間違う壊れ方** を列挙し、「リスク / 影響 / それが露見する場所」の表にする。全手順
実施後のレビューでこの表を1つずつ当てるので、**当てられる書き方をする** — 「注意する」は当てられない。

「露見する場所」には**手順番号**を書く。どの手順で気を付ければよいのかが表から読めるようにする。

## 書かないこと

- **他文書・過去版・会話への参照。** 必要な事実は本文へ埋め込み、**この文書単体で読んで着手できる
  状態** を保つ。「前回の議論のとおり」は、次のセッションでは何も指していない。
- **経緯・棄却の履歴。** 検討の過程は計画ではない。ただし却下した案の **問題そのものが残る** なら、
  概要・却下理由・残る問題だけを書く(同じ案を再提案しないため)。
- **コードの現状の解説。** コードを読めば分かることを書き写せば、次の変更で嘘になる。
  ただし**手順の「変更が必要な箇所」に書く行番号付きの参照は現状の解説ではない** — 着手点である。
