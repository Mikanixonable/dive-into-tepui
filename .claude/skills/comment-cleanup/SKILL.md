# コメントのクリンナップ

**判定基準は `.claude/skills/comment/SKILL.md`(`/comment`)が正本。** ここにあるのは作業手順だけで、
「何を残し何を消すか」「何を書き足すか」は必ずそちらを読んで決める。

**点検は過剰と不足の両方向で行う。** 冗長なコメントを削るだけでは片手落ちで、書くべきコメントが
書かれていない箇所も同じだけ問題になる。下の手順 A(過剰)と手順 B(不足)は両方通す。

**いつ通すか**: 大規模な変更(責務の移動・モジュールの分割/統合・大きな機能追加)を終えた後と、
ユーザーが整理を求めたとき。個々の変更で自分が書いたコメントを見直すのは `/comment` の側の常時義務で、
この手順を毎回通す必要はない。

## 手順 A — 過剰なコメントを削る

1. **検出。** 連続する複数行コメントを一覧する。

   ```
   node .claude/skills/comment-cleanup/scan-comments.mjs [対象ディレクトリ=src] [最小行数=2]
   ```

   出力はファイル・行番号つきのブロック一覧と、末尾のブロック数/行数の合計。**合計は作業前後で
   記録し、報告に載せる。**

2. **判定。** 各ブロックを `/comment` の禁止リストに当て、該当する行を削る。行数の目安
   (モジュール先頭 5 行 / 関数 3 行 / 関数内 1 行)を超えているブロックは特に疑う。

3. **書き直し。** 残った内容を「なにをするか」「どう使うか」へ圧縮する。ブロック全体が禁止
   パターンだけなら、コメントごと消す。**単に行を削るだけでなく、残す情報を書き直して短くする。**

## 手順 B — 不足しているコメントを足す

1. **検出。** コメントが不足している関数・メソッドを一覧する。

   ```
   node .claude/skills/comment-cleanup/scan-missing-comments.mjs [--threshold=10] [対象ファイル/ディレクトリ...=src]
   ```

   2種類を報告する。**件数は作業前後で記録し、報告に載せる。**

   - `[呼出規約なし]` — 宣言の直前に1行もコメントがない関数・メソッド。
     (1行だけの getter/setter と本文が空のものは自明として除外済み)
   - `[文脈コメントなし]` — 本文が `--threshold` 行以上あるのに、本文中にコメントが1行もない関数・メソッド。

2. **[呼出規約なし] を直す。** 宣言の直前に、`/comment` の「関数・フィールド」の項に従って
   **1〜3行(原則1行)** で「なにをするか」「どう使えばよいか」を書く。書くのは引数と返り値の意味、
   副作用、呼び出し規約、事前条件。関数名の言い換えにしかならないなら、その関数の**契約のうち
   名前から読み取れない部分**(返り値が null になる条件、破壊する状態、満たすべき順序)を書く。

3. **[文脈コメントなし] を直す。** 本文を数行単位の**意味ブロック**に分け、各ブロックの頭に
   **ごく簡潔な**文脈コメントを置く(3〜5行に1行程度)。文脈を与えるにとどめ、実装の説明はしない。
   本文が単調な列挙(DOM/CSS の設定、定数テーブル、メッシュの組み立て)で意味ブロックに割れない
   場合は1〜2行で足りる。**埋めるために増やさない。**

4. **どちらも `/comment` の禁止リストを再度当てる。** 足したコメントが「どう実装しているか」
   「誰が呼ぶか」「なにをしないか(否定形)」になっていないかを、書いた直後に必ず見直す。
   足りないから書くのであって、検出器を黙らせるために書くのではない。

## 共通

- **コードは変えない。** クリンナップで挙動を変えない。コードの問題(不要な処理・悪い命名など)に
  気づいたら、直さずに報告する。
- **仕上げ。** `npm run typecheck` を通す。`src/physics/` を触っていれば `npm run test:physics` も。
  コメントだけの変更なので設計文書(`/develop-docs`)の更新は原則不要だが、**コメントに書かれていた
  仕様や理由を消す場合は、それが `DEVELOP/SPEC.md` や CLAUDE.md に残っているかを確認してから消す。**
- **新しい冗長パターン・新しい不足パターンを見つけたら、`/comment` の側へ追記する。** 手順ではなく
  判定基準なので、追記先はこのファイルではない。検出を機械化できるなら、あわせてスキャナへ足す。

## 分担して行う場合

対象が広いときは、ファイル群を分けてサブエージェントへ配る。各エージェントへは次を必ず渡す:

- 担当ファイルの一覧(重複させない)
- `/comment` を読んでから作業すること
- **コメント以外を1文字も変えないこと**
- 通す手順(A / B / 両方)と、良い例・悪い例
- 作業後に自分の担当分だけ再スキャンし、件数を報告すること
