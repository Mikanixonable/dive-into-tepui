# 描画の作業手順

**何をどう見せるべきかは `DEVELOP/SPEC/RENDERING.md`(UI は `SPEC/UI-DESIGN.md`)が正本。**
ここに置くのは、それをこの基盤の上で書くときに踏む地雷と、render-lab で再現して前後を確かめる手順だけ。

## 1. 描画基盤(WebGPU 上の three.js)の制約

- ループ状に閉じた線や、点のサイズ指定は使えない。線は端点を重ねて手動で閉じた普通の折れ線として
  描き、点のような表示は三角形ベースのスプライトで代用する。
- 加算合成のマテリアルは透過を明示しないと効かない。
- **頂点データやインスタンスの変換は、確保済みのバッファへ直接書き込んで更新する。** ジオメトリや
  その属性そのものを差し替えても、描画には反映されず古い内容のまま描かれ続ける
  — 例外も警告も出ないので、「変えたのに絵が変わらない」ときは真っ先にここを疑う。
- **特定の GPU 側の処理に失敗すると、例外は出ないまま画面がまるごと黒くなる**(そのフレームの
  描画命令全体が無効になるため)。原因の手がかりはブラウザ側のログにしか出ない。
- 視錐台の外を描画しない仕組み(カリング)は基本的に有効なまま使う。無効化してよいのは、カメラに
  追従して常に画面内に留まる球殻(星・天球グリッド)、頂点バッファを直接書き換えていて包含球が
  自動更新されない線(軌道線・軌跡線)、インスタンスが共有ジオメトリの包含球よりはるかに広い
  範囲へ散らばる描画(点群など)に限る。

## 2. 重い機能・見え方を大きく変える機能は、描画設定で切れるようにする

**計算量やコード量が大幅に増える描画機能を足すとき、描画スタイルを大幅に変えるときは、描画品質設定
(`src/render/graphics-settings.ts` の `GRAPHICS_OPTIONS`)へ項目を足し、オフにするか処理負荷を選べる
ようにする。** 負荷の段を刻むのが難しいなら、既存の軽い簡易実装へ戻せる選択肢を残す — 新しい実装で
置き換えるときに、置き換える前の簡易実装を消さない。

- 目的は2つ。**ユーザーの好みとマシンの性能に合わせること**と、**バグやアーティファクトが見えた
  ときに、その機能を切って原因を切り分けること**。
- アーティファクトの除去・バグ修正・微調整では項目を足さない。
- 項目を足すことは見え方の仕様の変更なので、`DEVELOP/SPEC/RENDERING.md`「描画品質設定」を先に直す
  (`/modify-feature`)。品質プリセット(低/中/高)それぞれの値もそこで決める。
- 新しい描画パスや GPU で焼く処理を足したら、その GPU 時間をデバッグ情報ウィンドウで読めるようにする
  (`GpuTimings.beginPass` で `GPU_PASS` の行へ計上する)。負荷を選ばせるなら、選んだ差が数字で
  見えないと選べない。

## 3. 目で確かめる

| 見たいもの | 使うもの |
| --- | --- |
| 描画単体を切り出して見る・調整する | `npm run render-lab`(http://localhost:8082) |
| 画像として残す | `npm run render-lab:shot -- <組の名前>`(`.render-lab-shots/<組の名前>/`) |
| 変更の前後を見比べる | `npm run render-lab:compare`(4 節) |
| ゲームの中での見え方 | `npm run dev` |
| 実行時例外の有無まで込みで | `/verify` |

**render-lab のボタンはケース(物体の配置 1 つ)に対応し、カメラ・恒星・地球の置き方は観察のつまみで
動かす。** 地球は天体照の光源にも観察の対象にもなり、方位・仰角・高度・直下点の緯度経度で置く。
ケースは撮影(`LabShot` — つまみの差分と描画品質設定の差分)を宣言し、撮影名がそのまま PNG の名前に
なる。画面の「撮影」プルダウンで撮影を選んで反映すると自動撮影と同じ絵になるので、撮影に写ったものを
手で動かして調べるときはそこから始める。

**比べる撮影には組の名前を付ける。** `npm run render-lab:shot -- <組の名前>` は全ケースの全撮影を
`.render-lab-shots/<組の名前>/` へ書く。名前を省くと `.render-lab/shots/` へ書かれ、ビルドのたびに
消える。

**撮影が待つのは、ケースが `ready` を宣言した部品の読み込みだけ。** 実写テクスチャを貼る天体(地球・
火星・土星)は画像が GPU へ届くまで待ってから撮る。非同期に読み込む部品を足すときは、ケースに
`ready` を持たせる — 持たせないと、読み込み前の姿が撮られる。

ヘッドレスでの撮影には GPU 関連の特別な起動オプションが必要で、不安定なため複数回の試行が要る
ことがある。失敗が続くときは、環境ではなく描画そのものが黒くなっていないかを 1 節で切り分ける。

## 4. 描画の変更は、再現してから書き、前後の撮影で確かめる

**描画の機能追加・改善は、いまの問題を render-lab で再現してから書き始め、前後の撮影を比べて閉じる。**

1. **着手前に、いまの問題を render-lab で再現する。** 修正前のコードで問題が写る撮影を撮り、画像を
   開いて問題を目で確かめてから書き始める。
2. **再現の手段は次の順で選ぶ。** 既存の撮影で足りるならそれを使う。足りなければ既存のケースへ
   **撮影を足す** — 観察のつまみ(カメラ・恒星・地球の置き方)と描画品質設定の差分で表せるものは
   すべてこちら。物体の配置そのものが新しく要るときだけ**ケースを足す**。**撮影の追加で足りることを
   新規ケースにしない。**
3. **lab へシーンや機能を足すときは、実機のコードを import する。** 実機の部品や計算をコピーして
   lab に別実装を作らない。カメラ・光源・大気・影の渡し方が実機と大きく異なる描画環境も作らない —
   lab で直ったことが、実機で直ったことの証拠にならなくなる。lab 側で実機の計算を書き直したく
   なったら、実機の側に共有できる口を作り、lab からそれを使う。
4. **実施の前後で撮って比べる。** 修正前のコードで撮影の組を 2 組以上、修正後に 1 組撮り、
   `npm run render-lab:compare -- .render-lab-shots/<after> .render-lab-shots/<before1> .render-lab-shots/<before2>`
   で比べる。確かめるのは、**狙った撮影が改善したか**と、**ほかの撮影に悪影響が出ていないか**の 2 つ。
   **封筒外に出た撮影は、差分画像を見て説明できるまで閉じない。**
5. **再現のために足した撮影は残す。** 次に同じ問題が戻ってきたときに捕まえる。

**before の組は、再現用の撮影を足し終え、描画の修正に手を付ける前のコードで撮る。** 撮影を足す前に
撮ると、足した撮影が比較で「追加」と出るだけで、前後を比べられない。

**比較の読み方。** 撮影ごとに、after を before の組のうち最も近い組とブロック差(8 画素四方の平均の
差の最大)で比べ、before どうしの差の最大と下限 6 LSB の大きいほうを超えたものが封筒外になる。
封筒外の撮影の差分画像は `.render-lab-shots/compare-<after>/` に出る。片方の組にしか無い撮影は
「追加」「消滅」と出る。

**before を 2 組以上撮るのは、撮り直しの揺らぎを測るため。** 揺らぎはセッションごとに離散的な
モードを取り、同じコードでも組によってビット一致だったり数万画素違ったりする。before が 1 組では、
揺らぎと変更による差を区別できない。

**ブロック差 6 LSB を下回る小さな変化は、この比較では揺らぎと区別できない。** 描画設定で切り替え
られる変化を厳密に比べたいときは、同じセッションの中で `window.renderLab.shoot(ケース名, 描画設定の差分)`
の第 2 引数だけを変えて撮り比べる。

## 5. 書き終えたら

- `npm run typecheck`。
- **見た目を変えたなら、4 節の前後比較を通してから閉じる。** 「動いたはず」で閉じない。
- **見え方の仕様そのものを変えたなら、コードより先に `DEVELOP/SPEC/RENDERING.md` を直す**
  (`/modify-feature`)。実装に合わせて後から書き足さない。
