# 設計文書の同期

`src/` への変更は、**同じ変更セットの中で** 該当文書へ反映する。文書が実装から遅れると
リファクタリングの判断材料が壊れるため、「あとでまとめて」は禁止。

| 文書 | 内容 | 更新が必要になる変更 |
| --- | --- | --- |
| `CLAUDE.md`(Architecture / Controls) | モジュールの責務と「なぜそうなっているか」の散文解説 | ファイルの新設・削除・移動・改名、責務の移動、公開 API/メソッド名の変更、キー割り当て・操作系の変更、定数の意味の変更 |
| `DEVELOP/CALLSTACK.md` | per-frame 呼び出し依存木(update / sync / render) | 毎フレーム走る関数の追加・削除・改名・**呼び出し順の変更**・実行条件の変更 |
| `DEVELOP/OWNERSHIP.md` | インスタンス保持木と状態の正本 | クラスの新設・削除・改名、フィールド(状態)の移動、参照共有の増減、キャッシュの追加 |
| `DEVELOP/SPEC.md` | 「どう振舞うべきか」の仕様 | ゲーム挙動・数値・操作の変更(内部構造の変更だけなら不要) |

役割の切り分け: CLAUDE.md は**散文**(責務と理由)、DEVELOP/ の2文書は**機械的な事実**(順序と所有)。
同じ内容を両方に書き写すのではなく、この役割どおりに書き分ける。食い違いを見つけたら
DEVELOP/ を正として CLAUDE.md を直す。

`dev.md` は人間専用。**絶対に編集しない。**

## 1. まず差分を見て、更新対象を決める

```
git status --short
git diff --stat HEAD -- src/
```

判定は自然言語の類似ではなく **依存関係** で行う:

- ファイルの場所・名前・責務・公開メソッド名・キー割り当てが動いたか → CLAUDE.md
  (`grep` で旧名・旧パスが CLAUDE.md に残っていないか必ず確認する)
- 変更したファイルが per-frame の呼び出し経路(`update` / `sync` / `behave` / `render` から辿れる)に
  いるか → CALLSTACK.md
- `new` の位置、フィールドの所有、状態の書き換え主体が動いたか → OWNERSHIP.md
- プレイヤーから見える挙動・数値が変わったか → SPEC.md

いずれにも該当しないなら「更新不要」と明示的に結論づける(黙って飛ばさない)。

## 2. 部分更新(既定。差分が局所的なとき)

該当箇所だけを Edit する。そのとき次を必ず守る:

- **記述粒度を周囲と揃える**。新規モジュールだけ詳しく書く、という不均衡を作らない。
- CLAUDE.md は「**なぜ**そうなっているか」を書く場所。実装を追認するだけの記述(「A は B を呼ぶ」)は
  CALLSTACK.md の役割なので書かない。逆に、非自明な判断の理由(なぜその責務配置か、なぜその定数か、
  なぜ2つに分かれているか)は必ず残す。旧実装との対比(「以前は〜だった」)は書かない。
- CALLSTACK.md は **呼び出し順が実装と一致していること** を最優先で確認する(順序の誤りは
  この文書の存在価値を消す)。条件分岐(`// 条件`)も実装から読み直す。
- OWNERSHIP.md は、増えた状態が「正本」なのか「導出値・キャッシュ」なのかを判定し、後者は
  付録の表へ入れる。正本の表に導出値を混ぜない。
- 消えたモジュール・関数の記述を必ず削除する。古い記述が残る方が無いより有害。
- **改名・移動したら旧名を全文検索する**: `grep -n "<旧名>" CLAUDE.md DEVELOP/*.md`。
  文書中の相対パス・クラス名・メソッド名は実物と一字一句合わせる。

## 3. 全面再生成(大規模リファクタリング後・記述が信用できなくなったとき)

対象の文書を読み捨てて、以下のプロンプトを自分自身へ課して書き直す。読む範囲は
`src/main.ts` と `src/game/game.ts` を起点に、そこから per-frame で辿れる全モジュール
(`player/` `camera/` `plan/` `predict/` `orbit-entity/` `stages/` `marker/` `hud/` `vfx/`
`input/` `render/environment-scene.ts` など)。**推測で書かず、必ずファイルを読む。**

### CALLSTACK.md 再生成プロンプト

> `main.ts` から `game.ts` へ per frame で呼び出している処理が update / sync / render に分かれていて、
> そこからサブルーチン的に他の関数を呼んでいる。この依存関係を調べて木構造にせよ。例えば
> `main/foo` が `game.bar` と `game.bra` をこの順で呼び、`game.bar` が `game.brabra` を呼ぶなら:
>
> ```
> - main/foo()
>    - game.bar()
>      - game.brabra()
>    - game.bra()
> ```
>
> 原則、per frame にちょうど一度だけ呼ぶもの、複数箇所から参照されていない関数についての調査だが、
> mapMode・phase・paused などによって分岐する部分(per frame の呼び出し回数が 0 回から 1 回に
> なるもの)があれば、呼び出し条件を `// 条件` として付記せよ。多少簡略化されていても構わない。
>
> 調査対象は `main.ts` と `game.ts` だけでなく、そこから呼び出されている player・camera・plan・
> predict・stage・simulator・hud・marker などの更新関数を含む。典型的には `update~~` や `sync~~`
> という名前だが、そうでないものもある(`behave`・`checkLoss`・`cleanup`・`resolve` など)。
>
> いまは呼び出し順(コールスタック)の流れだけを追いたいので、引数の情報は省略せよ。また、
> 呼び出し順に対する影響が小さいもの(値を計算して返すことが主な責務の、副作用のない関数)も除外する。
>
> 結果を `DEVELOP/CALLSTACK.md` に出力する。冒頭に読み方(何を省略したか)と更新義務の節を残す。

### OWNERSHIP.md 再生成プロンプト

> クラス/モジュール間の保持関係について調べ、`DEVELOP/OWNERSHIP.md` に書け。「正本
> (source of truth)」についてのみ扱い、キャッシュや参照共有については所有関係として扱わない
> (混同しやすいものだけ末尾の付録に「正本でないもの」として列挙する)。
>
> 構成は次の4つ:
> 1. **インスタンス保持木** — `new` した側を所有者とする木。`main.ts` を根に、Game 以下の全インスタンスを
>    列挙する。木に現れない特殊なインスタンス(モジュールスコープのもの、別途 new されるもの)は別記する。
> 2. **参照共有** — 所有者と参照する側の対応表。所有権が移らないことを明記する。
> 3. **状態の正本** — 「状態 / 正本の所有者 / 備考(誰が書き換えるか)」の表。正本が分かれていることに
>    意味がある組み合わせ(独立責務が同時にトグルされているだけのもの等)は節を立てて説明する。
> 4. **付録: 正本でないもの** — 導出値・メモ化・キャッシュと、その無効化の契機。
>
> 調べる過程で「正本が二重化している」「無効化されないキャッシュがある」等の不整合を見つけたら、
> 勝手に直さず「既知の不整合」として記録し、報告せよ。

### CLAUDE.md 追従プロンプト

CLAUDE.md は全面再生成せず、**節ごとに実装と突き合わせて直す**(人手で足された経緯・理由の記述を
失わないため)。

> `CLAUDE.md` の記述を現在の実装に追従させよ。全面書き換えではなく、節ごとに実装と突き合わせて
> 誤りを直す。手順:
>
> 1. `find src -name "*.ts"` でファイル一覧を取り、CLAUDE.md に書かれているパス・クラス名・
>    メソッド名を実物と照合する。**存在しないもの(改名・削除・移動された記述)を洗い出す。**
> 2. 逆方向も見る: 一覧にあって CLAUDE.md に出てこないファイル・フォルダを洗い出し、責務を
>    1行で足す。
> 3. Architecture 節は「フォルダ = 関心事」の構造を保ったまま、各モジュールの**責務と非自明な
>    判断の理由**を書く。実装を追認するだけの記述(呼び出し順・保持関係)は DEVELOP/ の担当なので
>    重複させない。
> 4. Controls 節は `input/input.ts`、`player/player.ts` の `handleEdgePress`、`game.ts` の
>    `handleEdgePress`、`player-throttle.ts` の `buildThrustAccel`/`updateTorque`、
>    `plan-editor.ts` の `updateEditing` を**実際に読んで**キー割り当てを確定させる。
>    数値を引くときは `const.ts` の現在値を確認する。
> 5. 「Not yet implemented」の記述が本当に未実装かを確認する。
> 6. 旧実装との対比(「以前は〜だった」)・否定形の羅列は書かない(`refactor_instruction.md` の
>    コメント方針に従う)。ただし「なぜこの値/構造なのか」の理由は残す。
>
> コード側に見つけた不整合(古いラベル文字列・呼ばれない関数など)は勝手に直さず、文書に
> 「既知の不整合」として書いて報告せよ。

## 4. 仕上げ

- `npm run typecheck` が通ること(文書だけの変更なら不要)。
- 更新した文書名と「何をどう直したか」を1〜2行で報告する。更新不要と判断した文書があれば
  その理由も述べる。
