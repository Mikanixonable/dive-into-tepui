# 機能を追加・変更・削除する手順

**仕様が先、コードが後。** `DEVELOP/SPEC/` は「どう振舞うべきか」の原本で、**常にコードより
先行していなければならない。** コードを書いてから文書を合わせるのは、この関係を逆転させる。

「小さい変更だから」「数行だから」は例外にならない。

---

## 1. 何を実現したいのかを聞き出す

**要求を受けた時点では、たいてい仕様として書けるほど具体的になっていない。** そのまま実装に
入らず、まず SPEC/ に1文で書ける粒度まで具体化する。

- 曖昧なところ、複数の読み方ができるところを見つけ、**ユーザーに問う。** 推測で埋めない。
- 問うときは選択肢を具体的に示す。「どうしますか」ではなく「A か B か、それとも両方か」。
- ありふれた判断(既定値、命名、置き場所)まで一々問わない。問うのは、答えが違えば
  **出来上がるものが変わる** ところだけ。

## 2. `DEVELOP/SPEC/` を更新する

`DEVELOP/SPEC/README.md` の分野表から該当ファイルを選び、**コードを書き始める前に** 更新する。

**何を書き、何を書かないかは `DEVELOP/SPEC/README.md`「何を書くか」が正本。** ここでは繰り返さない。
書く前に読む。要点は1つ — **その文を消したとき失われるのが「作るべきもの」なら書き、
「作り方」なら書かない。** 実装の都合・手続き・性能のための妥協は、これから決める仕様ではない。

- **既存の記述と矛盾する提案なら、矛盾を文書内に残さない。** 古い記述を消して整合させる。
  どちらが正しいかユーザーと協議してから書く。
- **未確定のものは本文に書かない。** 共通化判断の材料になる「実装するかもしれない機能」は、
  該当ファイル末尾の「未確定の案」節へ1〜3行で記録する。そこにも収まらない構想は SPEC/ に書かない。

ここまでで一度立ち止まり、**更新した仕様をユーザーに示して合意を取る。** 認識がずれていれば、
コードを書く前に分かる。

## 3. 既存の類似実装を探す

探すのは「同じ名前の関数があるか」ではなく、**「同じ計算・同じ処理が既にどこかに書かれていないか」**。
名前が違っても、式の形と意味が同じなら重複実装である。

1. `/overview` の手順で当たりを付ける。
2. そのうえで **処理の中身で** grep する。関数名ではなく、特徴的な識別子・演算・定数で引く。
3. 状態の持ち主が絡むなら `/ownership`、実行順が絡むなら `/callstack`、既存の呼び出し元が
   絡むなら `/inv-callstack` でコードから調べる。

## 4. 2軸で判定する

見つかったら、「再利用可能な形に切り出されているか」と「適切なモジュールにあるか」を
**別々に** 見る。

| 再利用可能な形 | 適切なモジュール | すること |
| --- | --- | --- |
| ○ | ○ | **追加実装しない。** それを呼ぶ。引数が足りなければ最小限だけ拡張する。 |
| ○ | ✗ | 適切なモジュールへ**移動**し、参照を全部張り替える。 |
| ✗ | ○ | そのモジュール内で**関数として切り出し**、既存の処理をその呼び出しに置き換える。 |
| ✗ | ✗ | 適切なモジュールに再利用可能な形で実装し、既存の処理をその呼び出しに置き換える。 |

見つからなければ、適切なモジュールに新規実装する。置き場所は `DEVELOP/CODING-RULE.md`「1.2 モジュール化」
「1.3 フォルダの境界」「1.4 責務分割の見つけ方」で決める。**呼ぶ側のファイルに書くことを既定に
しない。** 配線と呼び出し順の決定で占められたモジュールには、なおさら書かない。

**どの場合も、既存側を置き換えるまでが1つの変更セット。** 共通関数を新しく足して古い実装を
残すのは、重複を1つ増やしただけで最悪の結果になる。旧実装・旧名は痕跡を残さず消す
(`DEVELOP/CODING-RULE.md`「1.11 改名・移動」)。

**共通化するかどうかは参照箇所の数で決めない** — 判断基準は `DEVELOP/CODING-RULE.md`
「1.5 重複実装の禁止と早急な一般化の分かれ目」。決まらなければユーザーに問う。

## 5. 書く

`DEVELOP/CODING-RULE.md` に従う。HUD/UI/DOM/CSS に触れるなら、書き始める前に `/ui-design`。

## 6. 仕上げ

- `npm run typecheck`。触った層の回帰テスト(`npm run test:physics` / `test:math` / `test:game` / `test:render`)も。
- **書き上げたコードを SPEC/ へ突き合わせに行かない。** 実装できたことも、実装しきれなかったことも、
  SPEC/ へ書き足す理由にならない。**仕様を変える必要が出たときだけ、手順 1 へ戻る。**
- 大きな変更だったなら `/refactor` で規約からの逸脱を点検し、`/comment-cleanup` で
  コメントを点検する。
