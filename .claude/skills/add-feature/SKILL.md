# 大規模な機能追加を要件定義・計画書に具体化する

**このSKILLが要るのは、1回の `/modify-feature` の SPEC 更新では収まらない規模のときだけ。**
数行の変更や、SPEC/ のどの節を直せばよいか自明な変更には使わない。目安は、要求を実装可能な
粒度まで具体化するのにコードベース調査や複数の判断が要り、かつサブエージェントへ調査を分担
させる価値がある規模。

対象になるのは主に以下の形の要求:

- 「実装案/計画をファイルにまとめて」「サブエージェントが読めば分かる指示書にして」という指示。
- 曖昧・抽象的な要求(「〜を正確に再現して」「〜をリッチに」など)で、具体化に価値判断や
  外部調査が要るもの。
- 一度に大量の要件が箇条書きで来て、個別に調査・具体化してから着手すべきもの。

このSKILLは**要件定義書/実装計画書を書く(1〜4)までを主目的とする。** 実装への移行は
ユーザーの承認を経てから(5)。承認を経ずに書き始めない。

---

## 1. 曖昧な箇所を先に洗い出す

要求文を読み、**具体化に価値判断が要る箇所**を先に列挙する。ありふれた判断(命名・既定値)は
含めない。答えが違えば出来上がるものが変わる箇所だけを拾う。

- 選択肢を作れるものは、AskUserQuestion で **具体的な案を示して** 問う。「どうしますか」ではなく
  「A か B か」。
- この時点で全部解決しなくてよい。**コードベース調査や文献調査をしないと選択肢すら作れない
  箇所は、2 の調査を経てから改めて問う。**

## 2. 調査を並列サブエージェントへ切り出す

**判断そのものは委譲しない。調査だけを委譲する。** 独立して進められる調査は Agent (Sonnet) で
並列に投げる — `/delegate` の「範囲を分ける」「渡す指示に必ず含める」に従う。

調査対象の例:

- コードベース調査 — 既存の類似実装、関連クラス・関数・データフロー(`/overview`
  `/ownership` `/callstack` `/inv-callstack` の要領)。
- 数値計算・シミュレーション — 要件を具体化するのに必要な計算。
- **文献調査(ドメイン知識が要るとき)** — 軌道力学・天文学など、コードベースだけでは
  裏付けが取れない要求。**このSKILL自体は文献の探し方・信頼できる情報源の基準を持たない。**
  軌道力学・天文学の要求は `/orbital-mechanics-research` を呼ぶ。該当するドメインスキルが
  無い分野なら、その旨を計画書に明記し、調査はこのSKILLの手順内で素朴に(WebSearch 等で)行う。

各サブエージェントには **文脈込みの自己完結した指示** を渡す(要求の背景・関連ファイル・
何を返してほしいか)。cold start である前提は `/delegate` と同じ。

## 3. 要件定義書/実装計画書を書く

`memos/mikanixonable/<内容が分かる英語スラグ>_<YYYY-MM-DD>.md` に書く。**このファイルだけを
読んだサブエージェントが文脈を再現できる**ことを基準にする。

- **相対表現を避け、絶対表現で書く。** 「現在より強く」ではなく、具体的な値・方向・条件を書く。
- 意図・効果(なぜそうするか)も含める — 実装者が価値判断に迷ったときの拠り所にする。
- 具体化のために複数案がありうる箇所は、**案を複数提示し、採用案とその理由を書く。**
  不採用案は消さず「不採用: 理由」として残す — あとで蒸し返さないため。
- 曖昧な箇所・ユーザーが言及した「今後使うかもしれない」話は、SPEC/ の「未確定の案」節と
  同じ要領でこの文書内に記録する。

## 4. 自分でレビューする

書き終えたら、**書いた本人が疑うつもりで読み返す。**

- 文書内で矛盾している記述がないか(前半と後半で違う値・違う方針を書いていないか)。
- まだ曖昧なまま残っている箇所がないか。
- 数値・仕様が不正確でないか(調査結果と食い違っていないか)。

見つかったら、**その場で決めず** 必要な追加調査(2 へ戻る)や追加の質問(1 へ戻る)を行って
から直す。レビューを終えるまでは「書けた」扱いにしない。

## 5. ユーザーへ提示する

書き上げた計画書をユーザーに示し、実装へ進めてよいか確認する。**この確認を飛ばして実装に
入らない。** ユーザーが計画の一部だけを承認したら、承認された範囲だけ 6 へ進む。

## 6. 実装する(承認後)

- 計画書のステップのうち、**互いに依存しないものは並列サブエージェント(Sonnet)で実装する。**
  同じファイルを複数のエージェントに触らせない(`/delegate` の「範囲を分ける」)。
- 規模に応じて `EnterWorktree` で作業を分離し、完了後に main へ統合する。
- 各ステップが実装・検証(`npm run typecheck`、該当すれば `npm run test:physics`)できた時点で
  commit する。まとめて最後に1回commitしない。
- push はユーザーから明示されたときだけ。

## 7. 完了した計画書を archived へ移す

実装が計画書の範囲を満たしたら、その計画書を `memos/mikanixonable/archived/` へ移動する
(ディレクトリが無ければ作る)。移動時に文面を書き換える:

- 実装済みの箇所は「〜する」という設計案の文体から「〜した」という決定の記録に直す。
- 不採用案は「不採用」のまま残してよい(なぜその設計にしなかったかの記録として有用)。
- **archived 後の文書は「今どう動いているか」の正本を主張しない。** CLAUDE.md の
  「コードの現状はコードだけが原本」という原則との整合を保つため、文書冒頭に一言
  (例: 「本文書は当時の設計判断の記録であり、現状の実装を保証しない」)を添える。

計画の一部だけが完了し、残りが未着手のままなら archived へは移さない。全体が完了してから
移す。部分完了のまま長期間放置されそうなら、その旨をユーザーに報告する。
