# 機能追加の手順

**追加要求を受けたら、コードを書き始める前にこの手順を通す。** 「小さい関数だから」「数行だから」は
例外にならない — 重複実装はそこから生まれる。

## 1. 既存の類似実装を探す

探すのは「同じ名前の関数があるか」ではなく、**「同じ計算・同じ処理が既にどこかに書かれていないか」**。
名前が違っても、式の形と意味が同じなら重複実装である。

1. `/overview` の手順で当たりを付ける。CLAUDE.md の Architecture 節はモジュールごとに「何を持って
   いるか」を書いてあるので、探索の目次として使える。
2. そのうえで **処理の中身で** grep する。関数名ではなく、特徴的な識別子・演算・定数で引く。

探し先の見当(責務の正本は CLAUDE.md の Architecture 節):

| 追加したいもの | まず見る場所 |
| --- | --- |
| ベクトル演算・乱数ベクトル | `physics/vec3.ts` |
| 軌道要素・Kepler・RK4・楕円サンプリング | `physics/orbital.ts` |
| 姿勢・クォータニオン | `physics/attitude.ts` |
| 状態列の積分・記録・任意時刻の引き当て | `physics/dynamic-trajectory.ts` / `physics/state-queue.ts` |
| 偏差射撃・迎撃時刻 | `physics/intercept.ts` |
| 空気抵抗・J2・三体加速度 | `physics/envaccel.ts` / `physics/atmosphere.ts` |
| 表示座標系の変換 / スクリーン投影 | `physics/frame.ts` / `physics/projection.ts` |
| 太陽・月・ラグランジュ点の位置 | `physics/ephemeris.ts` |
| 数値・距離・時刻の文字列化 | `game/hud/utils.ts` |
| ボタン列・ポップアップメニュー | `game/hud/buttons.ts` / `game/hud/context-menu.ts` |
| 画面マーカー | `game/marker/` と、各対象の所有者の `sync` |
| 線・メッシュ・ビルボードの生成 | `render/orbit-line.ts` / `render/sampled-line.ts` / `render/ships.ts` / `render/billboard.ts` |
| 敵の生成 | `game/stages/spawner/` |
| 色・チューニング定数 | `game/theme.ts` / `game/const.ts` |

## 2. 見つからなかった → 適切なモジュールに追加する

置き場所は `/refactor-fixed`(確定済みの境界)→ `/refactor`(責務分割の見つけ方)の順で決める。
**呼ぶ側のファイルに書くことを既定にしない。** 特に `main.ts` / `game.ts` にはオーケストレーション
以外を書かない。

## 3. 見つかった → 2軸で判定する

「再利用可能な形に切り出されているか」と「適切なモジュールにあるか」を **別々に** 見る。

| 再利用可能な形 | 適切なモジュール | すること |
| --- | --- | --- |
| ○ | ○ | **追加実装しない。** それを呼ぶ。引数が足りなければ最小限だけ拡張する。 |
| ○ | ✗ | 適切なモジュールへ**移動**し、参照を全部張り替える。 |
| ✗ | ○ | そのモジュール内で**関数として切り出し**、既存の処理をその呼び出しに置き換える。 |
| ✗ | ✗ | 適切なモジュールに再利用可能な形で実装し、既存の処理をその呼び出しに置き換える。 |

**どの場合も、既存側を置き換えるまでが1つの変更セット。** 共通関数を新しく足して古い実装を残すのは、
重複を1つ増やしただけで最悪の結果になる。旧実装・旧名は痕跡を残さず消す(`/refactor` の「改名・移動」)。

## 4. 迷ったらユーザーに問う

早急な一般化も重複実装と同じ悪。分かれ目は **共通化した側を今後も使う可能性があるか** と、
**共通化した側が変更された際に、参照側の挙動も変更されるべきであるか** であって、
参照箇所の数ではない(基準は `/refactor` の「重複実装の禁止と早急な一般化の分かれ目」、既に決着した
論点は `/refactor-fixed` の「一般化しないと決めたもの」)。

- `DEVELOP/SPEC.md`「実装される可能性のある機能」節を見る。
- そこで決まらなければ **ユーザーに問う。推測で一般化しない。** 問うときは、見つけた類似実装の場所と、
  「共通化する / それぞれ個別に持つ」の選択肢を具体的に示す。
- ユーザーが将来の実装可能性に言及したら SPEC.md の同節へ、責務配置の判断を下したら
  `/refactor-fixed` へ、同じ変更セットで記録する。

## 5. 仕上げ

- `npm run typecheck`。`src/physics/` を触ったなら `npm run test:physics` も。
- 設計文書を同じ変更セットで更新する(`/develop-docs`)。
