# UI/デザイン変更の手順

**規約の全文はここに書かない。** 正本は `DEVELOP/SPEC/UI-DESIGN.md`。このファイルは「どう手順を
踏むか」と「よくある誤り」だけを持つ。

## 1. `DEVELOP/SPEC/UI-DESIGN.md` を読む

見た目・配置・操作に関わる変更(パネルの追加、ボタンの追加、色/寸法の変更、開閉挙動の変更、
タッチ対応)の前に必ず通す。触る箇所に対応する節を確認する:

| やろうとしていること | 見る節 |
| --- | --- |
| 色・文字サイズ・角丸・余白・トランジションを決める | §2 トークン |
| 押せる/切り替えられる/入力できる要素を足す | §3 ウィジェット |
| モーダル・ポップアップ・ウィンドウを開く/閉じる | §4 オーバーレイ |
| パネルをどこに置くか決める、レスポンシブ対応する | §5 レイアウト |
| タッチでの到達性を確保する | §6 タッチ |
| 既存のパネルに手を入れる | §8 HUD の画面・パネル一覧 |

**画面から見える挙動を変えるなら、それは仕様変更。** `/modify-feature` の手順で
`DEVELOP/SPEC/UI-DESIGN.md`(および影響する他の SPEC/ ファイル)を先に更新する。
見た目を変えずに実装だけ直すなら、SPEC/ は更新しない。

## 2. 既存のウィジェット/トークンに同じものが無いか探す

新しい対話要素・新しい色・新しい寸法を書き始める前に:

1. 既存のウィジェット10種(ボタン/トグルスイッチ/セグメンテッドコントロール/ホールドボタン/
   クローズボタン/値入力/メーター/タブバー/スライダー/折りたたみトグル)に、やりたいことを
   果たせるものが無いか確認する。無ければ **追加実装せず既存を呼ぶ** か、最小限の引数拡張で
   足りないか検討する。
2. 既存のトークン(色・文字サイズ・角丸・余白・トランジション段)に要る値が無いか確認する。
   無い値が本当に要るなら、それが汎用値としてトークンに追加すべきものか、その場限りのローカル
   定数(3D シーンだけで使う色など)かを見極める(§2)。
3. モーダル/ポップアップ/ウィンドウを開くなら、コンテキストメニュー(使い捨て)とプロパティ
   ウィンドウ(継続観察)のどちらの役割かを先に決める — 迷ったら「右クリックした対象に
   プロパティがあるか」で判断する(§4)。

## 3. 置き場4種のどれに属するかを決めてから組む

新しいパネル/表示を作る前に、レール/シェルフ/中央モーダル/画面固定バッジのどれに属するかを
決める(§5)。決まらないまま絶対座標を書き始めない — 迷ったら「動かせる/畳める/レイアウトに
参加すべきか」で判断し、参加すべきならレールかシェルフへ、一点固定でよいものだけ画面固定
バッジにする。

## 4. タッチでの到達性を確認する

- 新しい操作がキーボード/マウス専用になっていないか(タップ・長押し・ドラッグのどれかで
  到達できるか)を確認する。到達できないなら、タップ可能な代替 UI を足す。
- タップ領域は 44px 以上。視覚サイズを変えずに広げたいだけなら、既存の当たり判定拡張を使う。
- 画面投影してから距離でヒット判定する新しいピック処理は、固定半径ではなく既存のポインター
  精度別の判定半径を経由する。

## よくある誤り

- **色/寸法をリテラルで書いてしまう。** CSS 文字列の中で色コードや生の px 値を書かず、トークンを
  参照する。逆に、JS が組み立てるインラインスタイル属性はトークンの TS 定数を直接読んでよい —
  この2つを混同すると片方を過剰に、もう片方を過小にトークン化してしまう。
- **オーバーレイの管理へ登録せず、自分で `document`/`window` に `keydown`/`pointerdown` を
  張ってしまう。** ESC・外側クリック・排他・入力ゲートは全部オーバーレイ管理が持つ。
- **コンテキストメニューとプロパティウィンドウを役割で選ばず、既存コードの見た目で選んでしまう。**
  対象にプロパティ(距離・軌道要素・装甲など)があるなら必ずプロパティウィンドウ。使い捨てで
  よいのは対象がそもそもプロパティを持たない(空域など)ときだけ。
- **新しい状態クラス名を作ってしまう。** 点灯/押下中/無効の3つで表せないか先に疑う。
- **2値の ON/OFF にセグメンテッドコントロールを使ってしまう。** 2値はトグルスイッチ。
  セグメンテッドコントロール/タブバーは3択以上の排他選択専用。
- **`vh` を単独で使ってしまう。** iOS Safari のアドレスバー伸縮でずれる — `vh` を書くときは
  必ず同じセレクタ・同じ値で `dvh` を後続させる(フォールバック→上書きの順)。
- **入力欄の `keydown` を止め忘れる。** キー入力は `window` で購読されているので、止めなかった
  打鍵はそのままゲーム操作になる(検索欄に "w" と打つと機体が噴射する)。新しい入力系
  ウィジェットは必ず `keydown` の伝播を止める。

## 5. 完了判定

`DEVELOP/SPEC/UI-DESIGN.md` §7「やってはいけないことの一覧」を自分の変更範囲に当て、新しい違反を
増やしていないか確認する(既存の違反をゼロにすることまでは求めない — それは別の変更セットで
直すべき既存の gap であり、自分の変更が原因でないかだけを確かめる)。
加えて `npm run typecheck`。`src/physics/` を触っていなければ `npm run test:physics` は不要。
