# UI/デザイン変更の手順

**規約の全文はここに書かない。** 正本は `DEVELOP/DESIGN-RULES.md`(7原則・トークン・ウィジェット・
オーバーレイ・置き場4種・タッチ対応・禁止一覧)。このファイルは「どう手順を踏むか」と「よくある
誤り」だけを持つ——`/refactor-fixed` と `/refactor` の関係と同じ形。責務の置き場所(どのクラスが
何を持つか)は引き続き `/refactor-fixed` の判断。

## 1. `DEVELOP/DESIGN-RULES.md` を読む

見た目・配置・操作に関わる変更(パネルの追加、ボタンの追加、色/寸法の変更、開閉挙動の変更、
タッチ対応)の前に必ず通す。とくに触る箇所に対応する節を確認する:

| やろうとしていること | 見る節 |
| --- | --- |
| 色・文字サイズ・角丸・余白・トランジションを決める | §2 トークン |
| 押せる/切り替えられる/入力できる要素を足す | §3 ウィジェット |
| モーダル・ポップアップ・ウィンドウを開く/閉じる | §4 オーバーレイ |
| パネルをどこに置くか決める、レスポンシブ対応する | §5 レイアウト |
| タッチでの到達性を確保する | §6 タッチ |

## 2. 既存のウィジェット/トークンに同じものが無いか探す

`/add-feature` の「まず探す」姿勢と同じ。新しい対話要素・新しい色・新しい寸法を書き始める前に:

1. `hud/widgets/index.ts` の10種(Button/ToggleSwitch/SegmentedControl/HoldButton/CloseButton/
   ValueInput/Meter/TabBar/Slider/buildCollapseToggle)に、やりたいことを果たせるものが無いか
   確認する。無ければ**追加実装せず既存を呼ぶ**か、最小限の引数拡張で足りないか検討する。
2. `theme.ts` の色・文字サイズ・角丸・余白・トランジション段に、要る値が既に無いか確認する。
   無い値が本当に要るなら、それがトークンに追加すべき汎用値か、その場限りのローカル定数
   (3D シーンだけで使う色など)かを見極める(`DESIGN-RULES.md` §2 の「同じ色を DOM と 3D の
   両方で使うものだけ theme に置く」規則)。
3. モーダル/ポップアップ/ウィンドウを開くなら、`ContextMenu`(使い捨て)と `PropertyWindow`
   (継続観察)のどちらの役割かを先に決める——迷ったら「右クリックした対象にプロパティがあるか」
   で判断する(§4)。

## 3. 置き場4種のどれに属するかを決めてから組む

新しいパネル/表示を作る前に、レール/シェルフ/中央モーダル/画面固定バッジのどれに属するかを
決める(`DESIGN-RULES.md` §5)。決まらないまま `position: absolute` で座標を書き始めない——
迷ったら「動かせる/畳める/レイアウトに参加すべきか」で判断し、参加すべきならレールかシェルフへ、
一点固定でよいものだけ画面固定バッジにする。

- 幅・高さがブレークポイントで変わるなら、値は `layout-tokens.ts` の CSS 変数へ足す
  (複数箇所へ寸法を複製しない)。
- ブレークポイントの閾値を判定するメディアクエリ文字列は `hud/breakpoints.ts` の `MQ_*` を使う
  (`@media (max-width: …px)` を新しく書かない)。
- 折りたためるパネルは `hud/panel-shell.ts` の `PanelShell` に載せる(独自の折りたたみ実装を
  作らない)。ゲーム状態由来の表示/非表示は `.hidden`、利用者の折りたたみは `.collapsed` —
  混同しない。

## 4. タッチでの到達性を確認する

- 新しい操作がキーボード/マウス専用になっていないか(タップ・長押し・ドラッグのどれかで
  到達できるか)を確認する。到達できないなら、`hud/status-panel.ts` の R/F/G/T 代替ボタンのように
  タップ可能な代替 UI を足す。
- タップ領域は `--hit-target-min`(44px)以上。視覚サイズを変えずに広げたいだけなら
  `widget-base.ts` の `expandHitTarget` を使う。
- 画面投影してから距離でヒット判定する新しいピック処理は、固定半径ではなく
  `input/pointer-precision.ts` の `pickRadiusSq(fine, coarse)` を経由する。

## よくある誤り

- **色/寸法をリテラルで書いてしまう。** `<style>` へ注入する CSS 文字列の中で `#rrggbb`/`rgba()`/
  生の px 値を書かず、`var(--…)` を使う。逆に、JS が組み立てるインライン `style="..."` 属性は
  `theme.ts` の TS 定数を直接読んでよい(`var(--…)` を経由する必要はない)——この2つを混同すると
  片方を過剰に、もう片方を過小にトークン化してしまう。
- **`OverlayManager` に登録せず、自分で `document`/`window` に `keydown`/`pointerdown` を張って
  しまう。** ESC・外側クリック・排他・入力ゲートは全部 `OverlayManager` が持つ——新しいモーダル/
  ポップアップ/ウィンドウを作ったら `open(id, handle, spec)` で登録する。
- **`ContextMenu` と `PropertyWindow` を役割で選ばず、既存コードの見た目で選んでしまう。** 対象に
  プロパティ(距離・軌道要素・装甲など)があるなら必ず `PropertyWindow`。使い捨てでよいのは
  対象がそもそもプロパティを持たない(空域など)ときだけ。
- **新しい状態クラス名を作ってしまう。** `.on`/`.pressed`/`.disabled` の3つで表せないか先に疑う。
  `.clipped` は `PropertyWindow` 専用の意味であり、他のウィジェットの状態には使わない。
- **`SegmentedControl` を2値の ON/OFF に使ってしまう。** 2値は `ToggleSwitch`。`SegmentedControl`/
  `TabBar` は3択以上の排他選択専用。
- **`vh` を単独で使ってしまう。** iOS Safari のアドレスバー伸縮でずれる——`NNvh` を書くときは
  必ず同じセレクタ・同じ値で `NNdvh` を後続させる(フォールバック→上書きの順)。
- **入力欄の `keydown` を止め忘れる。** `input/input.ts` の `Input` は `window` でキー入力を
  購読しているので、止めなかった打鍵はそのままゲーム操作になる(検索欄に "w" と打つと機体が
  噴射する)。新しい入力系ウィジェットは必ず `keydown` の `stopPropagation()` を持つ。

## 5. 完了判定

`DEVELOP/DESIGN-RULES.md` §7 の grep をそのまま実行し、自分の変更が新しい違反を増やしていないか
確認する(既存の違反件数が既知の値から増えていないかだけを見ればよい——ゼロ件を新たに要求しない。
既知の違反があれば、それは別の変更セットで直すべき既存の gap であり、自分の変更が原因でないか
だけを確かめる)。加えて `npm run typecheck`(常に)。`src/physics/` を触っていなければ
`npm run test:physics` は不要。
