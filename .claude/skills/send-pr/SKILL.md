# main へ送る

`main` が開発最新版、`release` が安定版(公開されるもの)。変更は main / release 以外のブランチで
行い、この手順を通して main へ入れる。**この手順書が「main へ入る前に何を通すか」の正本。**

**なぜここだけ全部通すのか。** CI(`.github/workflows/build.yml`)は main への push を受けて
`npm run typecheck` → `npm run test` → `npm run build` を順に回し、**どれか1つでも落ちれば
deploy がそこで止まる** — `release` が更新されず、公開版が古いまま取り残される。テストが赤い
まま常態化するのも困るが、**deploy が止まったまま常態化するほうがはるかにマズい。**

PR を立てず直マージで済ませる場合も、**1〜4 は同じように通す。** 飛ばせるのは 5 だけ。

## 1. ブランチの作業内容を掴む

```
git fetch origin
git log --oneline --no-merges origin/main..HEAD
git diff --stat origin/main...HEAD
```

- **commit の列ではなく、テーマで捉える。** PR 本文も点検範囲も、テーマ単位で決まる。無関係な
  仕事が2つ混ざっているなら、分けて送れないかを先に考える。
- commit メッセージだけで意図が読めない差分は、その場でコードを読む。**ここで掴んだものが
  そのまま 5 の材料**になるので、後から読み直さずに済む形で控える。
- 触ったファイルが数十に及ぶなら、テーマごとに分けてサブエージェントへ読ませる(`/delegate`)。

## 2. main を作業ブランチへ取り込む

```
git merge origin/main
```

- **衝突は中身を読んで解く。** `-X ours` / `-X theirs` で潰さない。どちらかを捨てる判断が要る
  なら、捨てる側が何を意図していたかを commit から確かめる。
- **衝突が出なくても壊れる。** 双方が別のファイルを触った結果、型や呼び出し規約が合わなくなる。
  取り込んだ直後に `npm run typecheck` を1回通してから 3 へ進む。
- 取り込んだあとの `git diff origin/main...HEAD` が、**PR に載る差分そのもの。**

## 3. 作業範囲へ `/refactor` と `/comment-cleanup` を通す

点検範囲は 2 で確定した差分のファイル。

```
git diff --name-only origin/main...HEAD -- src/
```

- **順番は `/refactor` → `/comment-cleanup`。** 逆にすると、責務を動かした先でコメントを
  書き直すことになる。
- **範囲外のファイルに見つけた違反は直さない。** 会話で報告する(PR 本文には書かない)。
- 直した分は作業本体と分けて commit する。5 で「規約点検で直したもの」として1節にまとめられる
  形にしておく。

## 4. 検証 — このときだけは変更箇所によらず全部回す

```
npm run typecheck
npm run test
npm run build
```

**CI と同じ3つを、触った層がどこであっても回す。** 「検証は変更箇所に対応させる」(CLAUDE.md
「作業のルール」)の例外はここだけ。

- **`npm run ci` は使わない。** この3つの外に `smoke:browser` などを含み、環境起因で落ちる。
- ヘッドレス実行検証(`/verify`)は、ユーザーが実行時の動作確認を求めたときだけ。
- **赤いまま送らない。** 原因が自分の変更の外にあっても同じ — 赤いものを通した時点から先の
  deploy が全部止まる。自分の変更が原因でないなら先に直す。**直さずに送る判断はユーザーへ
  委ねる**(黙って送らない)。
- `npm run typecheck` がヒープ不足で落ちるのは型エラーではない。
  `NODE_OPTIONS=--max-old-space-size=8192 npx tsc --noEmit` で通る。

通した結果は数字で控える(テストは件数、build は警告の有無)。5 の「検証」節へそのまま載せる。

## 5. PR 本文を書く

日本語で書く。タイトルは commit と同じ `type(scope): 要約`。

```text
## 目的
なぜこの変更が要るのか。何をやめて何にするのか。規約に基づく整理なら CODING-RULE の節番号を、
仕様に基づく変更なら SPEC のどこを先に更新したかを添える。

## 変更
テーマごとに小見出しを立て、その中を箇条書きにする。commit の列挙ではない。
数値を決めた箇所は、根拠(出典・実測値・導出)を1行添える。

## 注意
後方互換性を壊すもの(セーブ形式・URL・アセットの識別子)があるときだけ立てる。
何が起きるかを、読む人が自分の環境で判断できる形で書く。

## 検証
4 で実際に通したものを、結果つきで並べる。

🤖 Generated with [Claude Code](https://claude.com/claude-code)
```

**書かないもの**

- コードを読めば分かる実装の写経。書くのは「どう振舞うべきか」と「なぜそうしたか」。
- commit の羅列。
- 走らせていない検証。

**送る**

本文はスクラッチパッドのファイルへ書き、`--body-file` で渡す(コマンドラインへ直接埋めると
改行と引用符が壊れる)。**確認は取らず、そのまま送る。** PR は出したあとでも直せるので、
タイトル・本文・base はレビューで覆せばよい。

```
git push -u origin HEAD
gh pr create --base main --title "<title>" --body-file <path>
```

送ったら本文のファイルを消す。3 で見つけて直さなかった範囲外の違反は、ここで会話へ報告する。
