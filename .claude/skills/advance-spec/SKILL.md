# 仕様を先へ進める

**この手順では `src/` を一切触らない。** 触った時点で、書いているのは仕様ではなく、これから書く
コードの説明文になる。実装のために SPEC を更新するなら、この手順ではなく `/modify-feature`。

**何を書き、何を書かないかは `DEVELOP/SPEC/README.md`「何を書くか」が正本。** ここでは繰り返さない。
始める前に読む。

## 1. 分野を1つ選ぶ

`DEVELOP/SPEC/README.md` の分野表から1つ選ぶ。**複数を同時に開かない** — 通して読める分量に
収まっているかを見ることがこの手順の一部で、並行すると読み通せない。

ユーザーの指定がなければ、この順で選ぶ。

1. ユーザーが直前に話題にした分野。
2. 「未確定の案」節が空のまま、`memos/` にその分野の案が溜まっている分野。

## 2. 本文を通読して、現状記述を削る

**先頭から末尾まで読む。** 拾い読みをしない — 現状記述は、書いた当人には仕様に見える。

- `DEVELOP/SPEC/README.md`「書かないもの」の表と「判定に迷いやすい2つ」を、1文ずつ当てる。
- **削るかどうかを決めるのにコードを見に行かない。** 実装がどうなっているかは判断に要らない。
  要るのは「その一文が破られたらバグになるか」だけである。
- **「奇妙だが意図してそうしている」挙動は現状記述ではない。** 破られたらバグになるものは残す —
  ここに書かれていない挙動は、挙動不変を謳う変更で直されてよいものとして扱われる
  (`DEVELOP/SPEC/README.md`「いつ読むか」B)。意図かどうか判断が付かないならユーザーに問う。
- 削った結果、何も残らなくなった節は、節ごと消す。

## 3. `memos/` から取り込む

`memos/` にはユーザーが管理している検討の経緯・進行中の todo・開発ノートが置かれている。
選んだ分野に当たるものを読み、次のどちらかへ写す。

- **どう振舞うべきかが確定しているもの** → 本文へ。
- **実装しうるが、まだ確定していないもの** → 「未確定の案」節へ1〜3行で。

**`memos/` 側は書き換えない。取り込んだ印も残さない** — あちらはユーザーの領域である。
検討の経緯・案の比較・実装の見通しは写さない。写すのは「どう振舞うべきか」だけ。

## 4. 「未確定の案」節を点検する

- 実現の可能性が消えた案、方針が変わって不要になった案を、経緯を残さず消す。
- 本文へ入ったものが節に残っていたら消す。

## 5. 示して、単独で commit する

書き換えた分野をユーザーへ示す。削った記述と足した記述を伝え、**削った理由を「実装と違うから」
ではなく「作るべきものを何も決めていないから」で説明する。** 説明できないものは、削ってはいけない
記述だった。

`docs(spec): ` で始まる単独の commit にする。`src/` の変更を同じコミットに入れない
(`DEVELOP/SPEC/README.md`「この文書とコードの関係」)。
