# 規約からの逸脱を点検して直す

**判定基準は `DEVELOP/CODING-RULE.md` が正本。** ここにあるのは作業手順だけで、「何が違反か」は
必ずそちらを読んで決める。この手順書に規則そのものを書き足さない — 規則が変わったなら
`CODING-RULE.md` を直す。

**いつ通すか**: 責務の移動・モジュールの分割/統合・大きな機能追加を終えた後と、ユーザーが整理を
求めたとき。個々の変更で規約に従うのは常時の義務であって、この手順を毎回通す必要はない。

## 1. 点検範囲を決める

**リポジトリ全体を一度に点検しない。** 直前の変更セットが触ったファイルと、そこから1段だけ
辿れる範囲を既定にする。

```
git status --short
git diff --stat HEAD -- src/
```

ユーザーが範囲を指定していて、それが広い(数十ファイル以上)なら、**どこを対象にどの深さまで
見るかを問う。** 勝手に全体へ広げない。

## 2. 機械的に見つかるものから当たる

`src/**/*.ts` を編集すると PostToolUse フック(`.claude/hooks/check-boundaries.mjs`)が、
フレーム位相の混線・トップレベルへのロジック混入・`physics/` の依存汚染を編集直後に指摘する。
点検時はまとめて確認する:

- 200行を超えるモジュール、100行を超える関数を洗い出す。
- 同じ形の式・同じ形の処理が複数のモジュールに散っていないか、特徴的な識別子・演算・定数で grep する。
- 旧名の残骸が無いか。改名した名前をリポジトリ全文検索して 0 件を確認する。

## 3. `CODING-RULE.md` の各節を当てる

範囲内のコードに、順に当てていく。**該当した箇所だけ**を直す。

| 見るもの | 節 |
| --- | --- |
| モジュール・関数の大きさ、責務の有無、たらい回し | 1.2 モジュール化 |
| 置き場所が適切か(依存関係だけを見る) | 1.3 責務分割の見つけ方 |
| 重複実装か、早急な一般化か | 1.4 重複実装の禁止と早急な一般化の分かれ目 |
| 状態の重複・導出可能なステート・整合性責務の漏洩 | 1.5 データ構造 |
| 中身を差し替えて転用しているオブジェクト | 1.6 オブジェクトの流用の禁止 |
| `update` / `sync` / `render` / `build` の混線 | 1.7 フレーム処理の位相 |
| 旧名・互換エイリアスの残骸 | 1.8 改名・移動 |
| TypeScript の書き方、公開範囲、二段初期化 | 1.9 |
| CSS のリテラル直書き | 1.10 |
| 命名 | 2. 命名規則 |
| コメント | 3. コメント規約(一括点検は `/comment-cleanup`) |

## 4. 直す — ただし勝手に広げない

- **好ましくないパターンを好ましいパターンへ書き換えることは常に歓迎される。** 見つけたら直す。
- ただし、**プレイヤーから見える挙動を変えない。** 挙動を変える必要があると判断したら、
  それはリファクタリングではなく仕様変更なので、直さずに報告し `/modify-feature` へ回す。
- 共通化するかどうかで迷ったら、推測で一般化せず `memos/hedalu244/possible_features.md` を見る。
  そこで決まらなければユーザーに問う。
- 範囲外のファイルに違反を見つけたら、直さずに報告する。

## 5. 仕上げ

- `npm run typecheck`。`src/physics/` を触ったなら `npm run test:physics` も。
- **何を直したかを、規則の節番号つきで報告する。** 「見つけたが直さなかったもの」と、
  その理由も述べる。
- 挙動を変えたなら `DEVELOP/SPEC/` の該当ファイルを同じ変更セットで直す(`/modify-feature`)。
  挙動を変えていないなら SPEC/ は更新しない。
- **`CODING-RULE.md` 自体を書き換えるのは、規則そのものが変わったときだけ。** 現状を正当化する
  ための例外節を足さない。違反を見つけたらコードを直す。
