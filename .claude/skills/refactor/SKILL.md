# リファクタリングの方針

## 0. 判断の前に読むもの

1. `.claude/skills/refactor-fixed/SKILL.md` — **このプロジェクトで確定済みの責務境界**。
   そこに答えがある論点は蒸し返さず、それに従う。
2. `DEVELOP/OWNERSHIP.md`(状態の正本・保持木)と `DEVELOP/CALLSTACK.md`(per-frame 呼び出し順)。
   全体像はコードではなくこの2つから掴む(手順は `.claude/skills/overview/SKILL.md` = `/overview`)。
3. `memos/hedalu244/` — `refactoring_todo.md`(やることリスト)と、論点ごとの `*_todo.md`。
   CLAUDE.md より新しい。

## 基本原則

可能な限り単純で簡潔な実装を求める。長大なファイル、非自明なコードは人間にもエージェントにも
読めないため、簡潔になるように書き直すべきである。

要求した仕様を超えて実装が複雑になるような判断を勝手に追加すべきでない。実装が自明であることは、
仕様が自明であることと相関する。非自明な実装は非自明な挙動を生み、悪いUXに繋がる。

いついかなる時も、好ましくないパターンを好ましいパターンに書き換えることは歓迎される。
好ましくないものは作るべきでないし、残すべきでない。

## モジュール化

良いモジュール化とは、それぞれが明確に分割された単一の責務を持った、疎結合なモジュール群である。

悪いモジュール化:

- 責務が大きすぎるモジュール、関数。
- 長大なファイル、モジュール、関数。モジュールは200行、関数は100行を基準とする。
- 責務がないモジュール。例えば不要なたらい回しをするだけの薄すぎるラッパーなど。
- 1箇所からしか参照されていない小さな関数を、再利用性や責務の違いといった正当性なしに別モジュール
  へ置くこと。正当性が無いなら、たらい回しモジュールと同じ悪いパターンである。
- 実装の重複。同じ処理が複数箇所に分散して書かれているもの。
- 早急な一般化。

責務の有無とコードの規模には多少の相関はあるが、絶対ではない。どんなに行数が少なくても、責務を
持っているのであれば単独のモジュールとして維持すべきである。行数が長くても無駄なたらい回しを
しているだけであれば、削除すべきである。

## データ構造

良いデータ構造とは、少ないステート設計と、適切に構造化されたデータである。

悪いデータ構造:

- 正データが複数箇所に分散、重複しているデータ。
- 軽微な計算で求まるものをステートとして持っているデータ。
- 複数箇所が一定の整合性を保つことが要求されるデータ。メモ化アルゴリズムなどでどうしてもそのように
  扱わなければならない場合は、適切に隠蔽しなければならない。**整合性保持責務の漏洩は重大な違反。**
- 同一の意味、同一の情報量を持つ型を複数作ること。これは重複実装である。

## 命名

良い命名とは、振る舞いと扱い方が明快で、混同の恐れがなく、適切な長さの命名である。

悪い命名:

- 類義語の混雑。同じものを異なる言葉で指している命名。
- 曖昧な区別。区別すべきものを同じ名前で指す命名。
- 漠然とした命名。`process` や `data` などの命名は意味を持たない。
- スコープの狭さ、混同のおそれのなさに対して、不必要に長大な命名。スコープが十分に狭ければ、
  前述の漠然とした命名も許される。一行のラムダ式規模であれば一文字変数名も許される。

per-frame 関数の `render` / `update` / `build` / `sync` の使い分けは CLAUDE.md の
「Naming: render / update / build / sync」節が正本。`draw` は使わない。

## 改名・移動

**改名は痕跡を残さず完全に置き換える。** 歴史的経緯はコードとコメントの責務ではない
(必要なら git history が持っている)。

- 旧名が 0 件になるまで消す: `grep -rn "<旧名>" src DEVELOP CLAUDE.md .claude memos`
- **「旧」「former」「previously」「〜だった」「(旧 xxx)」と書くのは禁止。** コメント・文書には
  新しい姿だけを記述する。何を何に変えたかは、コードではなく変更セットの報告文に書く。
- 互換のための旧名エイリアス・ラッパー・再エクスポートを残さない。呼び出し側を全部直す。
- 文書(CLAUDE.md / DEVELOP/)の旧名も同じ変更セットで消す(`/develop-docs`)。

## コメント

**方針は `.claude/skills/comment/SKILL.md`(`/comment`)が正本。** コメントを1行でも足す/直す前に
読む。リファクタリングでコードを書き換えたら、**自分が書いたコメントを同じ基準で必ず見直す**
(この種の冗長なコメントは書き換えのたびに増える)。

大規模なリファクタリング(責務の移動・モジュールの分割/統合)を終えた後は、`/comment-cleanup` で
既存コメントを一括点検する。

## 仕様書

良い仕様書とは、適切な粒度で「どのように振舞うべきか」が書かれたものである。

仕様書はコメントとは分離される。コードが「どのように振舞うか」を記述し、仕様書が「どのように
振舞うべきか」を記述する(`DEVELOP/SPEC.md`)。これは将来的に一致すべきものであり、開発途中に
おいては一致していなくてよい。

## TypeScript のコーディング規則

- `const` を原則使用し、どうしても破壊的な更新が必要なときだけ `let` を使う。`var` は絶対に
  使うべきではない。
- `camelCase` を原則とする。
- 配列 like なものの処理については、イテレーターが存在すれば `for...of` を使い、存在しない場合のみ
  `for (;;)` を使う。`filter` や `map` が適している可能性があればそちらを使う。`reduce` は総和を
  求めるなどの単純な場合を除き、使わない。
- **「状態を更新し、副産物を返す関数」を作らない。** 副産物である値が欲しいときに状態が更新されて
  しまうと困る。副作用のある void 型(成否を boolean で返すくらいならよい)の関数と、副作用がなく
  返り値が意味を持つ純粋関数のいずれかであるべき。計算関数は何度呼んでも、1度だけ呼んで値を
  使いまわしても同じ結果になる — 呼び出し回数に対する冪等性があるべき。
- 不要なクロージャ注入は行わない。特定のオブジェクトに影響を及ぼしたいなら、その mutable な
  オブジェクトを直接渡す。関数を引数にするのは柔軟性が高い反面、複雑なクロージャ関係が生まれて
  可読性を下げる。

## CSS のコーディング規則

- CSS は CSS ファイルに書き、tsx からはクラス名を指定するのみとする。
- CSS では細部までクラス名で指定するのではなく、変更されにくい文書構造に対しては子要素セレクタに
  よって指定する。

## 責務分割の見つけ方

**関数名やコメントの自然言語的な関連性には注目せず、依存関係だけに注目する。**

- クラス外から情報をもらいまくっていて、クラス内の情報に全然手を付けていない関数は、置き場所が
  適切でない懸念がある。
- 特定のクラスが常にある情報を外部からもらっているとき、その情報はそのクラスに参照コピーなどで
  事前に共有しておくべき懸念がある。特にその情報が外部で使用される頻度が低いときには、正所有権を
  そのクラスへ移動するべき懸念がある。
- 異なるクラスにまたがって存在する複数の情報が頻繁にセットで受け渡されているとき、その2つの情報は
  同じクラスに配置されるべき可能性がある。
- 漠然とした多数の情報がひとつのクラスに入っていて、関数ごとに一定のパターンが見られないときは、
  そもそもそのクラスの責務が定まっていない可能性がある。
- 外部から一度しか呼ばれていない関数は、本当にそこで処理を区切るべきだったのか熟考する必要がある。
  形式的には、多数の引数や ctx 引数を受け取っている関数は I/F の切り方に失敗している可能性がある。
  意味的には、クラスオブジェクトとして強い独立性を主張できない限り、疑いの余地がある。
- 類似した形の式、類似した形の処理が異なるモジュールに分散して書かれているときは、重複実装の疑いが
  ある。

トップレベル(`main.ts` / `game.ts`)に実装が直接書かれるべきでない。そこにあってよいのは
オーケストレーション — 呼び出し順の決定だけである。

## 新機能を追加するとき

手順は `.claude/skills/add-feature/SKILL.md`(`/add-feature`)が正本 — 既存の類似実装を探し、
再利用可能な形で適切なモジュールにあるかを判定してから書き始める。その中で使う判断基準が下記。

## 「重複実装の禁止」と「早急な一般化」の分かれ目

判断基準は **共通化したコードを今後も使う「可能性」があるか**。参照箇所の数ではない。

- **1箇所からしか参照されていなくても、** 一般化した側を今後使う可能性があるなら、あるいは巨大な
  責務を分割するためなら、**分割する。**
- **2箇所以上あっても、** それらが個別に調整されうる要素なら、多少の共通実装があっても**一般化しない**。
**共通化した側が変更された際に、参照側の挙動も変更されるべきであるか** で判断する。

これはコードからは判別できない。将来実装される可能性のある機能を知る必要がある。

1. `DEVELOP/SPEC.md` の「実装される可能性のある機能」節を見る(決定事項とは分けて記録してある)。
2. そこで決まらないなら **ユーザーに問う**。推測で一般化しない。
3. ユーザーが「実装するかもしれない」と言及したものは、**決定事項と区別できる形で SPEC.md の
   同節へ記録する**。次回以降の判断材料になる。

判断の結果は `/refactor-fixed` の「一般化しないと決めたもの」へ書く(そこに既に載っている論点は
再検討しない)。

## 仕上げ

- `npm run typecheck` を通す。`src/physics/` を触ったときだけ `npm run test:physics` も走らせる。
- 責務配置の判断を新たに下した/変えたなら、`.claude/skills/refactor-fixed/SKILL.md` を
  **同じ変更セットで書き換える**(追記ではなく、全体が整合するように書き直す)。
- ユーザーが将来の実装可能性に言及したなら、`DEVELOP/SPEC.md` の「実装される可能性のある機能」節へ
  記録する。
- 完了した `refactoring_todo.md` の項目を消す。
- 設計文書(CLAUDE.md / DEVELOP/)を同じ変更セットで更新する(`/develop-docs`)。
