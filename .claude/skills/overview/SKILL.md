# 全体像の掴み方

**コードの現状はコードだけが語る。** 保持関係も呼び出し順も文書には保存されていないので、必要な
分だけコードから読み取る。読む範囲を絞ることがこの手順の主眼で、全体を総なめしない。

## 1. 問いから入口を選ぶ

| 問い | 入口 |
| --- | --- |
| 本来どう振舞うべきなのか(仕様・数値・操作) | `DEVELOP/SPEC/` の該当ファイル |
| 何と名付け、どう書くのか | `DEVELOP/CODING-RULE.md` |
| 誰がその状態を持っていて、誰が書き換えるのか / どこで `new` されるのか | `/ownership`(コードから調べる) |
| いつ・どの順で・どんな条件で走るのか(per-frame) | `/callstack`(コードから調べる) |
| これから直すことになっている問題・進行中の検討 | `memos/hedalu244/`、`memos/mikanixonable/` |
| 設計の方向性・未実装の構想 | `memos/mikanixonable/dev.md`(人間専用。**読むだけ、編集しない**) |

## 2. 起点になるファイル

per-frame の入口は `src/main.ts` の rAF ループ → `src/game/game.ts` の `update` / `sync` /
`render`。`src/game/` は関心事ごとのフォルダ(`player/` `game-entity/` `simulation/` `camera/`
`plan/` `stages/` `hud/` `marker/` `vfx/` `input/` `celestial/`)、`src/physics/` は THREE/DOM に
依存しない純粋な計算、`src/render/` は THREE のメッシュ構築と描画パイプライン。

## 3. 絞ってから読む

- 関係するモジュールを 1〜3 個に絞り、そのファイルだけを読む。
- 広域 grep やファイル一覧の総なめは、特定の識別子の全参照箇所を探すときだけ使う。
  「全体像を掴むため」には使わない。
- 読んだ範囲が足りなければ 1 段だけ広げる。最初から広く取らない。

## 4. 仕様と実装が食い違っていたら

`DEVELOP/SPEC/` はコードより **先行** する文書なので、食い違いは「未実装」か「仕様違反」の
どちらかである。どちらなのかを判断して報告する。勝手に SPEC/ をコードへ合わせて書き換えない
(それは仕様を捨てる行為になる)。
