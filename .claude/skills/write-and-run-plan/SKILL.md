# 計画を書いて、最後まで実施する

**このSKILLにおいては、計画は自分のための道具であって、提出物ではない。** 着手前に問題を洗い出すために書き、実施し終えたら
消す。ユーザーが読むのは計画ではなく、終わったあとの報告。

**この手順の中でユーザーに問わない。** 書き先も、計画に残った判断も、実施の順序も、自分で決める。
判断材料が足りないなら、問う前に `DEVELOP/SPEC/`・コード・実測から集める。決めたことは 6 で報告し、
ユーザーはそこで覆せる。

ユーザーが「計画を書いて」と明示したときは、この手順ではなく `/write-plan` — 書いて止まり、検査を待つ。

## 1. 一時ファイルへ計画を書く

**置き場所は自分で決める。問わない。** リポジトリの外(セッションの一時ディレクトリ)に置く。
`memos/` は人間が管理している領域なので使わない。commit もしない。

書く内容は `/write-plan` と同じ — 目的 / 変更箇所 / 達成目標 / 着手順の手順 / 見積り / 落とし穴。
`.claude/skills/write-plan/SKILL.md` を読み、その各節に従って書く。

## 2. 計画に残った判断を洗い出す

書き終えた計画を読み返し、**自分が決めた箇所** に印を付ける。仕様が決めていることは判断ではない。

- 仕様にもコードにも根拠がなく、書きながら決めたこと。
- 「たぶんこの辺」で済ませた変更箇所。
- 導出式のない見積り。

## 3. 監査する — 根拠を集めてから計画を直す

印を付けた1つずつについて、**問う代わりに調べる。**

- `DEVELOP/SPEC/` — 既に決まっていないか。末尾の「未確定の案」節に該当する話が置かれていないか。
- コード — 同じ問題を既に解いている実装がないか(`/overview`、走査が広いなら `/delegate`)。
  状態の持ち主が絡むなら `/ownership`、実行順が絡むなら `/callstack`。
- 実測 — 数字で決まる判断は測る。導出式も実測もない数字は計画から消す。

調べても決まらないなら、**後戻りが安いほうを採る。** 採らなかった案と理由は報告のために控える。
根拠が変わったなら、着手前にこの時点で計画を書き直す。**古い版を残さない。**

## 4. 全ステップを実施する

**どのステップを実施するかを問わない。上から順に、最後まで実施する。**

進め方と各ステップの閉じ方(レビュー / 検証 / commit / 計画ファイルの更新)は `/run-plan` に従う
(`.claude/skills/run-plan/SKILL.md`)。ただし実施中に出た判断も、問わずに 3 と同じやり方で決め、
報告のために控える。

**止まるのは、実施が安全でないと判明したときだけ。** そのときも問いを立てず、判明した事実と、
そこまでで済んだ範囲を報告する。

## 5. 全ステップ後にレビューする

`/run-plan` の最終節に従う — 達成目標を1つずつ当て、落とし穴の表を1つずつ当て、残骸を探し、
`DEVELOP/SPEC/` と実装が一致しているかを確かめる。ただし **計画ファイルの扱いは問わない** — 6 で消す。

## 6. 一時ファイルを消して、報告する

**実施し終えたら一時ファイルを消す。** 役目は終わっている。途中で止まったなら消さず、残っている
場所と残工程を報告に書く。

報告に含めるもの:

- **やったこと** — 触ったファイルと、commit の並び。
- **決めた判断** — 何を、何を根拠に決めたか。採らなかった案があるならそれも。
- **覆すために必要なもの** — どの commit を戻せば、どの判断が消えるか。

**報告は計画の写しではない。** 計画から外れたこと、途中で変えたことこそ書く。
