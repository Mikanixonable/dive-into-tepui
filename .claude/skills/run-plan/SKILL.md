# 計画のステップを実施する

**正本は計画ファイル。** 実施のたびに更新し、**次のセッションが計画ファイルだけを読んで続きから
着手できる状態** を保つ。会話の記憶に依存する進め方をしない。

## 1. どのステップを実施するかを問う

計画ファイルを読み、**どのステップを実施するかユーザーに問う。** 例外的な指示がない限り、書かれた
ステップを上から順に着手する。何ステップまとめて実施するかも確定させる。

## 2. 着手前に目的を再確認する

目的と達成目標を読み直し、**これから実施するステップがそこへ向かっているか** を確かめる。逸れて
いたら、コードを書く前に計画を直す。**計画を黙って外れて進めない。**

前提が変わって失効したステップは、節ごと削除する(経緯は残さない)。

## 3. 実施する

- 該当する SKILL を通す。機能の追加・変更・削除なら `/modify-feature`、HUD/UI/DOM/CSS に触れるなら
  `/ui-design`。書き方は `DEVELOP/CODING-RULE.md`。
- ステップが互いに独立しているなら、サブエージェントへ配って並行させる(`/delegate`)。

## 4. 途中で出たものを取りこぼさない

実施中に **判断が必要な事項** や、**そのステップ内で解決できない問題** が出たら、その場で計画へ書く。

- 新規ステップを足すか、後続のステップのどれかへ追記する。**会話の中だけに残さない。**
- 判断がユーザーのものなら(仕様の分岐、共通化の可否)、その場で問う。推測で埋めて進めない。

## 5. ステップを閉じる

各ステップの終わりに、順に:

1. **コードレビュー** — `/code-review`、または自分で `DEVELOP/CODING-RULE.md` を当てる。
2. **検証** — **計画のそのステップの「達成条件と検証」に書かれたものを走らせる。** 書かれていなければ
   既定は `npm run typecheck`(`src/physics/` を触ったなら `npm run test:physics` も)。
   変更と無関係な検証に時間を使わない。
3. **git commit** — そのステップで1コミット。
4. **計画ファイルの更新** — **実施したステップの手順を削除する。** 部分実施なら残工程だけを残す。
   確定した値は前提の節へ移し、見積りは実測値で置き換える。目的・達成目標・落とし穴の表は
   最後まで残す。

## 6. 全ステップを実施したらレビューする

- **達成目標を1つずつ当てる。** 達成できていない項目があれば、それを埋めるステップを計画へ
  書き足す。**達成したことにしない。**
- **落とし穴の表を1つずつ当てる。** 「露見する場所」を実際に見る。表を眺めて終わりにしない。
- **残骸がないか見る。** 旧実装・旧名・要求されていないデバッグコード。改名した名前はリポジトリ
  全文検索で 0 件を確認する。
- **`DEVELOP/SPEC/` と実装が一致しているかを確認する。** 食い違っていたら「未実装」か「仕様違反」の
  どちらなのかを判断して報告する。**勝手に SPEC/ をコードへ合わせない。**
- 大きな変更だったなら `/refactor`、コメントが広範囲に散ったなら `/comment-cleanup`。
- **役目を終えた計画ファイルをどうするかユーザーに問う。** `memos/` は人間が管理している領域なので、
  勝手に消さない・移動しない。
