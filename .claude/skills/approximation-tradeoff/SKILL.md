# 精度と費用の落としどころを決める

**何を優先するかは `DEVELOP/SPEC/INVARIANTS.md` §7 が正本** — 違和感は物理的な正確さに優先して消し、
消し方はまず物理的に正しくすることを探し、正しくする費用が見合わないときだけ正確さを譲る。ここに
あるのは、その「見合うか」を決める手順だけ。

**この手順が防ぐのは、正確さを理由に費用の見合わない作り方を選ぶこと。** 正しくする方向の変更は
疑われずに入るが、作り方を変えて精度を上げる案の多くは、費用が物体の数・距離・解像度・時間加速倍率に
対して際限なく伸びる。

- すべての当たり判定をメッシュどうしで解く。
- RK4 の刻みを、誤差が消えるまで際限なく細かくする。
- 画面空間の追跡で足りない映り込みを、画面空間でないレイトレーシングへ素朴に置き換える。

どれも正確にはなるが、違和感の解消に見合わない費用を、すべてのフレーム・すべての物体に払わせる。
**このリポジトリでは物理側で踏んだ前例が多い。** 描画側は処理の予算がさらに厳しく、近似の出番が多い。

## 1. 違和感を言葉にして再現する

- 何が、どの場面で、どう見える(振る舞う)のが違和感なのかを1文で書く。**「不正確だから」は違和感
  ではない** — 遊ぶ人に何が届くかを書く。
- 再現する。描画は render-lab の撮影(`/rendering-workflow` 4 節)、物理は回帰テストか再現の
  スクリプト。**再現できない違和感に費用を払わない。**

## 2. 原因を切り分ける

- **物理的な誤り** — 式・単位・座標系・時刻軸の取り違え、抜けた項、誤った境界条件。
- **近似の誤差** — 標本の数と引き方、積分の刻み、画素の格子、判定に使う形、打ち切り。

**物理的な誤りで、正しくしても費用が大きく変わらないなら、正しくして終える。** 3 へ進まない。

## 3. 候補を並べる

近似の誤差なら、次の2種類を両方並べる。作り方を変える案だけを見ない。

- **いまの作り方の中で直す** — 刻み・標本数・しきい値を変える。偏りを受け入れて揺らぎを消す(輝点を
  作る裾を切る、小さく明るいものを均す)。違和感の出る場面だけ精度を上げる(適応刻み、近いものだけ
  細かい形で判定する)。
- **作り方を変える** — より正確な方法へ置き換える。

## 4. 費用を見積もる

候補ごとに次を書く。

- **費用が何に対してどう伸びるか** — 物体の数・刻みの数・画素数・距離・時間加速倍率に対して。
  **最悪の場面**(物体が最も多い、倍率が最大、描画解像度が最も高い)の伸び方で比べる。典型の場面で
  安くても、最悪の場面で際限なく伸びるなら見合わない。
- **実測** — 描画は `node tools/render-lab-measure.mjs`(比べるビルドは同じ session で交互に測る)、
  物理は `tests/perf/` の実験とデバッグ情報ウィンドウの計測。見積もりだけで決めない。
- **違和感がどれだけ消えるか** — 1 の再現で確かめる。

## 5. 落としどころを決める

- **予算は SPEC が求める性能**(「どの時間加速倍率でもフレームが落ちない」など)。描画では、重い機能は
  描画品質設定で切れるようにする(`/rendering-workflow` 2 節)。
- 予算に収まり違和感を消す候補のうち、**いちばん安いもの**を選ぶ。違和感の消え方が同じで費用が
  大きく変わらないなら、物理的に正しい側を選ぶ。
- **見合う候補が無い、または違和感と費用の釣り合いが価値判断になるなら、候補と見積もりを並べて
  ユーザーに問う。** 推測で高い方へ倒さない。
- 物理的な正確さを譲ったら、採用したモデルと適用範囲・限界をそのモジュールの先頭コメントに書く
  (`DEVELOP/CODING-RULE.md` 1.1)。比べて採らなかった候補と見積もりは、計画書があればそこへ残す —
  次に同じ違和感が来たときに蒸し返さない。
