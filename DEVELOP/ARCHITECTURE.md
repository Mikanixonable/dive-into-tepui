# ARCHITECTURE — 層と境界、繋ぎ方

値とモジュールを**どの層に置き、層と持ち主をどう繋ぐか**の規則の正本。import の向き、正本の書き手、
フレームの位相、直列化と復元、部品と協力者の構築、`entity` / `motion` / `view` の責務を持つ。
コードの書き方一般は `CODING-RULE.md`。**いつ読むかは `CODING-RULE.md` 1.3 が決める。**

**ここに書くのは、検査で固定した規則と、今後も徹底する規則だけ。** 次のものは書かない —
コードの変更のたびに嘘になり、読むたびに context を食う。

- 個々のモジュール・クラスの責務と挙動。コードが語る。
- 1回ごとの置き場・命名の判断。規則から導けるなら規則だけで足り、導けないなら足りないのは規則である。
- 変わり続ける現状(ファイルの一覧、違反の件数、進行中の作業)。

**規則を書き換えるのは、ユーザーが始める計画的な再設計のときだけ。** 1件の違反のために規則を
変えない。変えるときは、同じ変更の中で検査(`tools/check-boundaries.mjs`)も直す。

## 規則に合わないとき

**機能を足すときは、まずその時点の規則どおりに責務を分ける。** ほとんどの場合はこれで足りる。
`npm run check:boundaries` か編集後のフックが違反を出したら、その行が指す規則をここで読み、
規則の目的に照らしてコードを直す。

**規則どおりに分けられないときだけ、例外にする。** 規則どおりでは実装できないか、実装できても
読みやすさ・処理の追いやすさ・責務の分け方が著しく損なわれるとき。判定が規則の目的を外して
当たるとき(誤検出)も同じ扱いにする。例外にするかは実装する側が決め、ユーザーへ問わない。

- 理由には、規則どおりに分けた形と、それで何が損なわれるかを具体的に書く。書けないなら例外にしない。
- 書く場所は、判定のある規則なら `tools/check-boundaries.mjs` の `exempt` の行のコメント、判定の
  無い規則なら違反箇所のコメント(`例外(ARCHITECTURE Rn):` で始める)。
- 足した例外は、作業の報告と PR 本文に理由つきで挙げる。ユーザーはそこで覆す。
- **規則の文面と検査の判定は書き換えない。** 名前を替えて判定を避けるのも同じ — 検査は規則の
  代理であって、通ったことは規則を満たした根拠にならない。
- 許可リスト(`tools/boundary-allowlist.json`)は例外の置き場ではない。規則か判定を足した変更の中で
  既存の違反を載せ、消していく残りで、減らすことしか許さない。

**同じ規則に例外が重なってきたら、再設計を提案する。** 例外が重なるのは、規則のほうが誤っている
徴候である。例外を足すときは同じ規則の既存の例外を見て、重なっているなら報告でそう伝える。
再設計に着手するか、いつ着手するか(追加機能の全貌が見えてからがよい)はユーザーが決める。

## 層 — 状態の種類で層を決め、import は不変な側へ向く

**R1. 状態の種類で層を決める。**

| 層 | 持ってよい mutable な値 | その層に入る条件 |
| --- | --- | --- |
| 定義層 | なし | 実行中に値が変わらない(定数・データ表・型・純関数) |
| 時刻層 | 結果を変えないメモ化キャッシュだけ | 構築時に決めた immutable な値と時刻 t だけで答えが決まる |
| モデル層 | 正本 | 捨てたら、ほかの層からは作り直せない |
| 導出層 | R5 の5種だけ | 捨てても、ほかの層から毎フレーム作り直せる |

- 値の置き場は「その値を捨てたら作り直せるか」で判定する。作り直せないならモデル層(セーブを跨いで
  共通の設定なら、アプリ寿命の正本。R10)。作り直せるなら導出層のキャッシュ。
- 乱数で決めた値は作り直せないのでモデル層に置き、結果を保存する。乱数の系列そのものは保存しない。
  ランの再現性は目標にしない。

**R2. import は不変な側へだけ向く。**

- 定義層と時刻層は、どこから import してもよい。不変な値は、誰に読まれても整合性を壊さない。
- 装置が import してよいのは、定義層・時刻層と自分自身だけ。**装置どうしは import し合わない。**
  装置を import するのは、表示の導出とアプリの組み立てだけ。
- 時刻層が import してよいのは定義層と時刻層だけ、定義層は定義層だけ。
- **import を1本も持たないモジュール**(union や定数だけの語彙)は、どのフォルダにあっても定義層
  として扱う。
- **フォルダは層に揃える。** 導出層は、意味を知る**表示の導出**と、意味を知らない**装置**(R7)に
  分かれる。

| フォルダ | 層 |
| --- | --- |
| `math/`、`theme.ts`、import を1本も持たないモジュール | 定義 |
| `physics/` | 時刻 |
| `render/`、`marker/`、`audio/`、`input/` | 装置 |
| `hud/`、`game/` | 表示の導出(段 6・段 8 で割る) |
| `game/viewer/` | モデル層のうち視点(R4) |
| `settings/` | アプリ寿命の正本 |
| `launcher/`、`run/`、`main.ts` | アプリの組み立て |

**`hud/` は装置ではなく表示の導出として扱う。ただしモデル層とアプリ寿命の正本
(`game/`・`settings/`・`launcher/`)への import は、装置と同じく禁じる。**(暫定 — 段 8 で外す)

**`game/` はモデル層と表示の導出の同居として扱い、中を割らない。**(暫定 — 段 6 で外す)

**表示の導出の置き場は当面 `src/game/` の中**(`hud`・`marker`・`view`・`pickable`・`map`・
`lines`)。(暫定 — 段 8 で外す)

層の中身について、さらに次が決まっている。

- **`math/`** — 物理でも描画でもゲームでもない**汎用の道具**(ベクトル・幾何変換・データ構造・
  数値探索・乱数)。
- **`physics/`** — THREE.js に依存しない**物理・軌道力学そのもの**。置くのは定数・純関数と、結果を
  変えないメモ化キャッシュ(R1)と、意味を持たない容器(`StateQueue` の類)である。容器のインスタンスが
  持つ可変な値は、それを持つ者の層に属する。
  **`dynamic-trajectory.ts` は、実軌跡と予測の弧の可変な記録と積分を持ったまま `physics/` にあり、
  運動はそれを読み手へそのまま渡す。**(暫定 — 段 6 で外す)
- **`render/`** — **3D 資源の所有・構築・破棄**と、供給された表示状態の GPU/THREE への同期。
  表示出力とキャッシュ以外の副作用を持たない。
- **`input/`** — キーの割り当てと、生の入力(キーボード・ポインタ)の受け口。**画面に出る操作パッドは
  入力ではなく UI なので、ここではなく `game/hud/` に置く。**
- **`hud/`** — **画面の器と共通部品。** `#hud` ルートと重なり順のレイヤ、モーダルの排他制御、
  ウィジェット、ドラッグ可能ウィンドウ、一時停止メニューと設定ビュー、数値の整形。**ゲームの盤面を
  映すパネル(軌道・艦・敵・計画・天体)は `game/hud/` に置く。**
- **`theme.ts`** — 見た目の定数(色・寸法・書体・重なり順)。
- **`game/`** — **1ランの中身だけを持つ。**
- **`settings/`** — **セーブを跨いで共通のユーザー設定と UI の選択**(R10)。
  保存先への読み書きと、変更の購読をここだけが持つ。
- **`launcher/`** — **ランの外側。** どのランを・いつ始めて・いつ畳むかの判断と、ラン跨ぎの
  記録(解放状況・セーブスロット・スナップショット)。`location.*` を知ってよいのはここだけ。
  **`launcher/` は `game/` を import してよく、`game/` は `launcher/` を import しては
  ならない。** ランの中からラン跨ぎの記録へ書き戻さない。ユーザーが選んだ状態は記録ではない —
  セーブを跨いで共通の設定は `settings/` が持ち、そのゲームの選択は視点としてスナップショットに入る
  (R4・R11)。
- `src/` 直下に置いてよいのは **`main.ts`(組み立てと rAF ループ)と `theme.ts`** だけ。

## 正本には書き手が1つあり、書くのは進行の位相だけ

**R3. 正本には書き手が1つあり、書くのは進行の位相だけ。**

- **モデル層の値を書くのは、その値を所有するモジュールだけ。所有者は、その欄を宣言したクラスである。**
  外から変えるときは、所有者が公開する**命令**(メソッド)を呼ぶ。実体と運動、運動と behavior、持ち主と
  部品のような所有の木の中でも、他のクラスの欄へ代入しない。継承した欄を `this` で書くのは、自分の欄
  なので当たらない。
- **モデル層の口は、命令・読み取り面・出来事(R7)の3つである。** 命令の名前の形は問わない。
  命令 API の禁止(R7)は装置の規則で、モデル層には当てない。
- **整合性は所有者が命令の中で保つ。** 呼び手に所有者の整合性の世話(キャッシュの破棄など)をさせず、
  そのための口を公開しない。
- **モデル層のクラスは、可変な public 欄と `set` アクセサを持たない。モデル層が export する型も、
  可変な欄を持たない。** 代入の形は、それが命令であることを呼び手から隠し、書き手を1つに保てなくする。
- **モデル層の外**(入力の解釈・DOM のイベント・アプリの組み立て)から来た命令は、**受け付けた時点では
  状態を変えない。** 列に積み、次の進行の位相の先頭で、**受け付けた順に**適用する(R8)。一時停止中も
  適用する — 止まっているのはシミュレーションであって、操作ではない。
- **モデル層の中では、所有者の命令をその場で呼んでよい。** 進行の位相の中で走るので、列を経由する
  意味がない。列は「フレームのどこから来たか分からない書き込み」を位相の先頭へ集めるためにある。
- 外から読むときは、所有者が公開する**読み取り専用の面**を通す。可変オブジェクトそのものを外へ渡さない。
- **毎フレーム導出元から作り直される値は、それ自体は正本ではない。** 正本は導出元で、フィールドは
  進行の位相が鮮度を保証するキャッシュである。それでも**書くのは所有者だけ**で、導出元は引数で受けるか、
  所有者が読みに行く。所有者以外が「ついでに」書き足す形にしない。

## モデル層は進行と視点に分け、進行は視点を読まない

**R4. モデル層は「進行」と「視点」に分け、進行は視点を読まない。**

- **進行**は、規則が読む値である。積分、接触、AI、ステージの進行と勝敗、計画の実行、spawn、
  操作対象、計画、時間加速の段がこれに当たる。
- **視点**は、遊ぶ人の選択のうち**セーブごとに持つもの**である。別のセーブを読み込めばそのセーブの
  値になり、新しく始めたゲームでは既定から始まる。カメラ、ビュー、航法ターゲット、軌道要素の基準、
  計画軌道の座標系、表示期間と表示時刻、軌道ガイド、実体ごとの表示設定がこれに当たる。
- **視点を設定と取り違えない。** 「何をどう見ているか」は視点の条件にならない。描画品質・表示
  スタイル・配色・表示トグル・パネルの畳みとタブも見え方を決めるが、セーブを跨いで共通なので設定
  (`settings/`、R10)に置く。**どちらに置くかは SPEC が決める**(`SPEC/INVARIANTS.md` §6)。
  **SPEC が決めていない値は、1つの所有者の状態をセーブと設定へ割らない側に置く** — 画角と投影は、
  注視距離や正射影の半高さと換算し合うので、カメラの他の値と一緒に視点に置く。
- **進行は視点を import しない。** 視点が進行へ効いてよいのは、表示の導出がフレームごとに渡す
  **需要**だけである。需要とは、予測を伸ばす対象と長さ、履歴を残す長さのように、**どこまで計算して
  ほしいか**の表明を指す。
- **需要が変えてよいのは計算量だけ。** 同じ命令の列と同じ操作量からは、**需要によらず同じ進行の状態に
  ならなければならない。** 予測の弧をなぞって積分を省く最適化がこの条件を満たすのは、**弧の刻みが
  需要に依存しない**かぎりである — 伸ばす長さを変えても、同じ時刻には同じ値が並ぶ必要がある。
- **視点は進行を読んでよい。** 注視している対象が消えたら注視を戻す、のように、視点の規則は進行の
  状態を条件にしてよい。

需要について、さらに次が決まっている。

- **何を弧で置き換えてよいかは、進行の側が決める。** それはその運動の性質であって、誰が何を見ているか
  ではない。表示の選択で弧の有無が決まると、軌道線を点けただけで積分の経路が変わる。需要が決めて
  よいのは **どこまで伸ばすか** だけである。

## 導出層は捨てても作り直せるものだけを持つ

**R5. 導出層は、捨てても作り直せるものだけを持つ。**

- 導出層が持ってよい mutable な値は次の5種だけ。
  1. 結果に効く入力をすべてキーにしたキャッシュ。
  2. GPU・DOM・音声の資源。
  3. 外界の写し(押下中のキー、ポインタ、画面寸法、タブの可視状態)。
  4. 捨ててよい操作途中の状態(ドラッグ中の量、入力途中の文字、開いているメニューやプロパティ窓)。
  5. 表示を安定させるための前フレームの記憶(ヒステリシス、猶予)。
- **4 と 5 は、表示と入力の解釈以外に影響してはならない。** 影響するなら視点に置く。
- **どれにも当たらない値は、視点か `settings/` に置く。** ユーザーが選んだもの、時間をかけて
  積み上がったもの、他へ影響するものがこれに当たる。セーブごとに持つなら視点、セーブを跨いで共通なら
  `settings/` に置く(R4)。
- **導出層のアニメーション(遷移・寿命・フェード)は dt で積まず、開始時刻とそのフレームの実時刻から
  計算する。** 実時刻はフレームの先頭で1度だけ読み、入力として配る。

## 装置は宣言だけを受ける

**R7. 装置は意味を知らず、宣言だけを受ける。**

- 装置の入力は、そのフレームに見せる(鳴らす)べきものの**全体の宣言**である。装置は内部で前回との
  差分を取る。`show` / `hide` / `set` / `play` / `stop` の類の命令 API を外へ公開しない。
- **装置の入力型は、装置が自分の語彙で定義する。** 実体の種別、ステージ、選択といったモデルの意味を
  持ち込まない。意味から装置の語彙への写しは、表示の導出が行う。
- **一回きりの出来事**(効果音、通知、閃光)を、モデル層が装置へ直に渡さない。モデル層は進行の位相で
  「直近の進行で起きた出来事」を**記録**するだけにする。出来事は**種別と値と通し番号**を持ち、装置の
  語彙も文面も持たない。表示の導出がそれを読んで装置の宣言へ写し、装置は同じ通し番号を二度扱わない。
  記録は進行の位相の先頭で空にする — 進めなかったフレームに前のフレームの出来事が残ると、同じ音が
  鳴り続ける。
- 装置の出力(描いた線の点列、マーカーを出したか、投影)を読んでよいのは、表示の導出の入力解釈
  (ピック判定)だけ。
- ブラウザの制約(音声のロック解除、タブの可視状態)は、その制約を受ける装置が自分で扱う。

## フレームの位相

**R8. フレームの位相はデータの流れに合わせる。**

毎フレームの処理は、値がどちらへ流れるかで4つの位相に分かれる。**位相の境界を跨ぐコードを書かない。**

1. **入力の解釈**(表示の導出)— 生の入力と、前フレームの装置の出力(投影・描いた点列)を読み、
   **命令**(R3)とそのフレームの**操作量**を作る。**モデル層を書かない。**
2. **進行**(モデル層)— 積み上がった命令を受け付けた順に適用し、操作量と `dt` でシミュレーションを
   進め、出来事(R7)を記録する。**`dt` を受け取るのはこの位相だけ。** 一時停止中も命令は適用するが、
   シミュレーションは進めない。**THREE.js オブジェクトと DOM に触らない。** **進行の末尾で、表示の
   導出が進行の結果から作った材料 — 視点の追従の材料(`CameraFrameSamples`)と需要(R4)— を受け、
   視点を追従させ、予測と履歴を伸ばす。** 材料を作る処理はモデル層を書かない。
3. **導出と同期**(表示の導出 → 装置)— 読み取り専用の面と表示時刻から、そのフレームに見せる(鳴らす)
   べきものの宣言を作り、装置へ渡す。**モデル層を書かない。** したがって `dt` を受け取らない。
4. **描画**(装置)— 描画命令を発行するだけ。

- **実時刻はフレームの先頭で1度だけ読み、入力として配る**(R5)。各位相が自分で壁時計を読まない。
- **DOM のイベントはフレームの外で起きる。** そこで作ってよいのは、命令(R3)と R5-4 の状態だけ。
  ハンドラの中でモデル層を書かない。
- **セーブは位相 2 と 3 の間**で、モデル層だけを直列化する。
- **`build`**(表示オブジェクトを構築してシーンへ登録する)は毎フレームの処理ではない。

**位相の順序はランの組み立て(`src/run/`)が持つ**(R10)。

**モデル層が装置・生の入力・出来事の装置を import しない規則は、層の対応表ではなく `src/game/` の中の
パスで当てる**(`tools/check-boundaries.mjs` の禁止パターン)。`game/` の中がまだ層で割れていないため。
(暫定 — 段 6 で層の規則へ置き換える)

## アプリ寿命の正本と組み立て

**R10. アプリ寿命の正本と組み立て。**

- `settings/` は、セーブを跨いで共通のユーザー設定の正本である。**パネルの折り畳みやタブ選択のように、
  どのゲームにも共通する UI の選択もここに含む。** そのゲームの空間と時間に依拠する選択は、ページを
  読み込み直しても残す値であってもここに置かず、視点としてセーブで運ぶ(R4)。表示の導出へは、
  **読み取り専用の面と変更の callback で渡す。** モデル層がセーブを跨いで共通の設定を要するなら、
  ランの構築時の値として受ける。**値の型・妥当性の
  判定・保存文字列との変換は、その値を解釈する層が持つ**(描画品質なら `render/`、音量なら
  `audio/`、配色なら `theme.ts`)。書き換えられる正本を渡した先が握ると、誰がいつ変えたのかが
  追えなくなり、消したはずの逆依存が戻る。
- **ランの組み立て(`src/run/`)は、1ランのモデル層の根と表示の導出の根を組み、R8 の位相の順序を持つ。**
- `main.ts` は、ページの寿命のもの(装置、HUD の外枠、設定、`launcher/`)の組み立てと、rAF の登録を
  持つ。**位相の順序は持たない。**

## セーブはモデル層そのものである

**R11. セーブはモデル層そのものである。**

- **スナップショットは、モデル層(進行と視点)の直列化である。** 表示の導出と設定は含めない。
  読み込みはモデル層を組み直すだけで、表示の導出はモデル層から作り直され、設定は読み込みの前後で
  変わらない。
- **モデル層の値は、例外なくすべてセーブする。** セーブしないのは次の3つだけで、キャッシュは所有者の
  コメントにキャッシュであることを書く。
  - 正本から計算し直すキャッシュ(予測の弧など)。作り直すと数値計算の近似を超えて保存前と違う値に
    なるもの(復元した id から数え直す採番など)は、キャッシュではなく正本である。
  - R1 が保存しないと決めた乱数の系列。
  - 需要が残させている過去の記録(軌跡の履歴)。残す長さが需要で決まるので、R4 の「需要によらず同じに
    なる進行の状態」に入らない。

## 直列化は所有者が書き、復元は静的ファクトリが行う

**R12. 直列化は所有者が書き、復元は静的ファクトリが行う。**

- **モデル層が知るのは「直列化」だけである。** セーブ(スロット、記録、自動セーブ、形式の版の照合)は
  `launcher/` の語彙で、モデル層の型・メソッド・変数の名前に `save` / `restore` を使わない
  (`CODING-RULE.md` 2.2)。
- `T` の直列化された形は `SerializedT` と呼び、`T` のモジュールに置く。JSON の素の値だけで組む。
  **不変で、JSON の素の値だけから成る値の型は、そのまま直列化の形に使い、`SerializedT` を別に
  作らない**(`CODING-RULE.md` 1.6 の同じ情報量の型の禁止)。
- `serialize(): SerializedT` は引数を受けない。逆は `static deserialize(serialized: SerializedT, …): T`
  で、`serialized` の後ろに受けてよいのは、直列化に含まれない協力者(R13)と復元時刻、どの種類として
  組むかを呼び手が決める不変な定義(カメラの設定・種別ごとの慣性など)だけ。
- **コンストラクタは直列化された形を受けず、新しく作るか復元するかで分岐しない。** 受けるのは、
  復元済みの部品と状態、部品を作る材料になる復元済みの値、協力者である。構築した後で状態を流し込む
  メソッドを作らない。
- **記録に無い項目は、新しく作ったときの初期値で補う。** 初期値はコンストラクタの既定引数に1か所だけ
  書き、`deserialize` は欠けた項目を `undefined` のまま渡す。`deserialize` に書くのは、初期値と違う
  値で補うものと、ほかの項目から導くものだけ。
- 子を持つなら、親の `deserialize` が子の `deserialize` を呼び、できた子をコンストラクタへ渡す。
  多態の子は、タグ辞書が具象の `deserialize` を引く(下の「多態を保存し、復元する」)。
- **1つの記録に、2つの所有者の値を混ぜない。** 所有者の `serialize` へ、ほかの所有者の値を渡さない。
  形式が混ぜているなら、直すのは形式のほうである。

### 多態を保存し、復元する

**保存された状態からタグを読んで具象クラスを引き当てるまでが読み込み機構の仕事で、そこから先の
復元は各クラスの責任である。** 読み込み機構に具象クラスの知識(コンストラクタの引数、既定値、
検証)を持たせない。形は次の3点で固定する。

- **静的側インターフェース。** 具象が自分のタグと静的な `deserialize` を宣言する。基底は
  `this.constructor` から自分の静的側を引く getter を持つ。
- **クラス辞書は独立したモジュールに置く。** 基底のモジュールに置くと基底 → 具象 → 基底の実行時
  循環になり、`extends` の評価時に落ちる。呼び出し元に `switch` を直書きするのも、分岐を呼び出し元
  へ戻すだけなので不可。
- **`deserialize` のシグネチャを全具象で揃える**(直列化された形と協力者)。新しく作る
  引数は具象ごとに違ってよく、辞書を通さない。

## 部品は持ち主が作り、協力者は受ける

**R13. 部品は持ち主が作り、協力者は受ける。**

- **部品**(持ち主だけが参照し、持ち主と寿命が同じで、持ち主の直列化に含まれるもの)は、持ち主の
  モジュールが作る。新しく作るときはコンストラクタ(既定引数を含む)か静的ファクトリ `create`、
  復元するときは `deserialize` が作る。上位から注入しない。部品が持ち主への参照を要するなら、
  持ち主のコンストラクタが復元済みの値から作ってよい。
- **協力者**(複数の持ち主が参照するもの、持ち主より長く生きるもの、ほかの所有者が直列化するもの)は、
  コンストラクタか `deserialize` で受ける。受けた側は作らず、直列化せず、破棄しない。**同じ協力者を
  「構築時に受けて持つ」と「呼ぶたびに受ける」の両方で受けない。**
- 協力者を作るのは、その寿命の根である。ランの寿命ならモデル層の根と表示の導出の根、ページの寿命なら
  `main.ts`。
- 種別で具象が変わる部品は、新しく作るときは種別を知る規則(spawn など)が選び、復元するときは
  タグ辞書が選ぶ。持ち主は狭い型で受ける。
- **構築を上へ集めるのは層の根までである。** 層の根は自分の層の部品を作る。ランの組み立ては2つの根を
  作り、ページの寿命の装置を渡すだけ。
- **層を跨いで渡すのは、所有者ごとの読み取り面を所有の木のまま辿れる根である。** 層の入力として値を
  平らに並べた型を作らない(`CODING-RULE.md` 1.6)。
- テストのために注入しない。テストは本物の部品で組む。

## `launcher/` が `game/` を見てよいのは、ランを起こすときだけ

`launcher/` から `game/` への import は、**どのステージがあるか・ランをどう起こし畳み記録するか**
に限る。**自分の画面を組むために `game/` を見ない。** タイトル画面もセーブ一覧も負荷確認ウィンドウも
`hud/` の部品で組む。`launcher/` が `game/hud/` を引き始めたら、それは共通部品が `game/` に
置かれているサインで、直すのは import ではなく置き場所のほう。

## `physics/` に物理でないものを持ち込まない

THREE 非依存かつ純粋であっても、次のものは `physics/` に置かない。

- **ゲームバランスの調整値** — 散布界の倍率、命中判定の甘さ、ダメージ量、演出のための補正。
- **見やすさのための歪め** — 表示距離の圧縮、フェード、マーカーの寄せ。
- **フローティングオリジン** — 描画のための平行移動であって物理ではない。
- **THREE.js への依存。**

境界は「用途が表示かどうか」ではなく「**厳密な数学・物理そのものか、調整の入った歪めか**」。
射影変換や視線遮蔽の判定は表示のために使われるが、調整値を含まない厳密な幾何なので
`physics/` に属する。

## 接触判定は重力の関心事ではない

2球が触れているかどうか、触れたときにどう跳ね返るかは、厳密な幾何・力学として `physics/` に
属するが、「重力源かどうか」「大気を持つかどうか」とは無関係な**別の関心事**である。重力の
モジュールは何が何を**引くか**にだけ答え、何が何に**触れたか**には一切答えない。同じ理由で、
大気による焼失(地球にしか無い現象)と固体表面への接触(天体一般に効く幾何)は別の判定であり、
どちらか一方のマージンをもう一方の代用にしない。

## a と b の接触の帰結は a と b の責務である

「2つの物体が触れたときに何が起きるか」(ダメージ・破壊・音・エフェクト)は、接触を検出した
モジュールにも、まして `Game` にも書かない。各当事者自身が、**自分が受けるものだけ**を書く —
相手が受けるものは相手が書くので、二重に効くことも抜け落ちることもない。列挙・順序付けの層は
ペアを見つけて剛体解決を通し、両当事者に接触の記述を渡すだけで、ダメージも音も消滅も知らない。
検出側やオーケストレータで当事者の型を分岐するコードは、この境界が破れているサインである。

## `entity` / `motion` / `view`

### `entity`

**`entity` は「物体ひとつの動きと見た目を統合するもの」。** `celestialEntity` も `dynamicEntity` も
この意味で揃えてあり、族語が変わっても語の意味は変わらない。動きの正本は自分では持たず
(`CelestialMotion` / `DynamicTrajectory`)、そこから引いた状態へ見た目を同期する。

動きだけを扱うもの、見た目だけを扱うものに `entity` を付けない。

Entity は1体ぶんの Motion と View を所有し、その組をゲーム上の名前・選択・意思決定・勝敗の帰結へ
結び付ける。**Motion / View の公開 API を同名の getter やメソッドで転送しない。** 物理を読む側は
`entity.motion`、表示を操作する側は `entity.view` を明示して使う。Entity が両者を同時に扱ってよいのは、
構築・破棄と、Motion を View の同期へ渡す結節点だけである。

**具象 Entity の継承で物理処理や表示同期を差し替えない。** 種別ごとの物理差は Motion、表示差は View、
接触後のゲーム上の反応は構築時に Motion へ注入する反応オブジェクトが持つ。Entity の継承に
`step*` / `sync*` / `collide*` の override が現れたら、責務が Entity へ逆流している。

### `motion`

**`motion` は、物体1体のシミュレーション状態と時刻問い合わせを担う。** 天体では時刻から状態を
定め、動的物体では実状態・予測・姿勢・物性を一体として進める。表示資源・表示座標・表示設定を持たず、
`render/` と THREE.js を import しない。

動的物体の位置・速度だけを包むものは Motion ではない。姿勢、質量・形状、推力、熱、接触判定用の形、
接触代理、実軌跡・予測軌跡、積分と寿命境界まで、シミュレーション結果を決める状態と処理を同じ Motion が
所有する。Simulator と接触解決は Entity でなく Motion の狭い面を参加者として受ける。

接触による速度・熱などの物理応答は Motion に閉じる。ダメージ・死亡記録・音・エフェクト・spawn など
ゲーム上の帰結は反応オブジェクトとして構築時に注入し、Motion はその契約だけを呼ぶ。具象 Entity の
型判定や override dispatch を接触解決へ持ち込まない。

シミュレータや予測器が物体へ求める値は、具体 Entity や具体 Motion でなく、必要な物理操作だけを
表す狭い interface から受ける。顔ぶれを列挙する面も、その consumer が実際に扱う参加者の型を返す。

### `view`

**`view` は、物体1体の 3D 表示資源を所有し、そのフレームに外から供給された表示状態を THREE / DOM
へ同期する。** THREE の object・GPU 資源・DOM マーカー要素・プールと、再構築・再転送を避ける
描画キャッシュを保持してよい。
ゲーム進行・物理状態・入力・AI・表示設定の正本を持たず、simulator・predictor・input・stage を import
しない。

**本体の表示可否、軌道線・軌跡線、交点や方向のマーカー、プルーム・パフ、表示トグルを含む表示状態は、
View の外に正本を置き、毎フレーム `sync` の入力として渡す。** View は `show` / `hide` / `set` のような
準備用の命令 API を公開せず、1回の同期で渡された表示状態を描画資源へ反映する。View 内の mutable な
値は描画資源と、同じ資源の無駄な再構築・再転送を避けるキャッシュだけに限る。キャッシュは結果へ影響する
全入力をキーに含める。

1体の View は配下の表示部品をすべて所有し、Entity に兄弟の `FooView` を複数持たせたり、同じ THREE
object の生成者と破棄者を別の View に分けたりしない。

種別ごとの View が、自分の表示同期を最初から最後まで行う。共通 View を生成・破棄だけのラッパーとして
重ね、Entity の `syncModel` / `placeModel` / `orientModel` の override から実処理を呼ぶ形は分離ではない。
