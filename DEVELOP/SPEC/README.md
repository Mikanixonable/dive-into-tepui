# SPEC/ — dive-into-tepui の仕様

**「どう振舞うべきか」だけを書く。** 「どう振舞っているか」はコードだけが語る。

## コンセプト

地球-月圏を舞台とする、軌道力学のシューティングゲーム。Web ゲームとして遊べることを前提とする。

- 現実的な軌道マニューバと、物理的に正確な弾道計算を遊びの中心に置く。
- 地球の大気、宇宙船、宇宙船の破壊を、ローポリでありながら見応えのある形で描く。
- 軌道計算は太陽-地球-月の三体力学・大気抵抗・潮汐力を考慮する。ラグランジュ点、太陽同期回帰軌道、
  ハロー軌道、低エネルギー遷移と弾道捕獲、二重月スウィングバイ、こうのとり式の漸増接近マニューバ
  といった概念を扱えることを目指す。
- 見た目の目標: 地球のオーロラ、太陽嵐によるオーロラ、戦闘で生じた荷電粒子によるオーロラ、
  夕方側の雲に落ちる地球の影、破壊された破片のジャニベコフ効果。

## 書き方の規則

- **コードより先行する。** 新機能は SPEC/ を更新してからコードを書く(手順は `/modify-feature`)。
  未実装であることを理由に記述をためらわない。逆に、実装したことを理由に書き足さない。
- **本文には確定した意図だけを書く。** 未確定のものは各ファイル末尾の「未確定の案」節へ。
  そこにも収まらない構想段階のものは SPEC/ に書かない。
- **識別子を書かない。** クラス名・ファイル名・メソッド名・定数名は、コードが変われば嘘になる。
  数値は値そのものを単位つきで書く。画面に出る文字列・キー名だけは実物どおりに書く。
- **達成した精度・刻み幅を書かない。** 書くのは「どういう状況で、何が正しく見えていなければ
  ならないか」だけである。そこから許せる誤差を見積もり、性能とアルゴリズムの許すかぎり刻み幅や
  許容量をその内側へ収めるのは実装の仕事になる。実装が出した数値や、それが理論値と一致したと
  いう検証結果を仕様へ写すと、調整のたびに嘘になる。
- **歴史を残さない。** 「以前は」「旧」「〜だった」「〜に変更した」は書かない。古くなった記述は
  経緯を残さず書き換える。
- **矛盾を残さない。** 既存の記述と食い違う仕様を足すときは、古い方を消して整合させる。

## 「未確定の案」節の運用

各ファイルの末尾に置く。**「どの拡張性を残すべきか」を判断するための材料**であり、それ以外の
用途で使わない — やることリストでも、思いつきの置き場でもない。分野ごとに分けてあるのは、
その分野の確定仕様を読むときに必ず目に入り、古くなったことに気付けるようにするため。

- **ユーザーが「実装するかもしれない」と言及したものを、その都度ここへ記録する。**
  共通化・一般化の判断で迷ったとき、ここに無ければユーザーに問い、返答をここへ足す。
- **確定したら本文へ移し、この節からは消す。**
- **可能性が消えたら消す。** ある変更によって実現が難しくなった案、方針が変わって不要になった案は、
  経緯を残さず削除する。
- **1件は1〜3行。** 検討の過程・比較・実装案は書かない。それらは `memos/` が持つ。
- 該当する分野が無い、あるいは複数分野にまたがるだけの漠然とした構想は、ここには書かない。
