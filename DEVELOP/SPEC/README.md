# SPEC/ — dive-into-tepui の仕様

**ここに書くのは、ゲームが「どう振舞うべきか」だけ。** 実装がいまどう動いているかは、コードだけが語る。

## コンセプト

地球-月圏を舞台とする、軌道力学のシューティングゲーム。Web ゲームとして遊べることを前提とする。

- 現実的な軌道マニューバと、物理的に正確な弾道計算を遊びの中心に置く。
- 地球の大気、宇宙船、宇宙船の破壊を、ローポリでありながら見応えのある形で描く。
- 軌道計算は太陽-地球-月の三体力学・大気抵抗・潮汐力を考慮する。ラグランジュ点、太陽同期回帰軌道、
  ハロー軌道、低エネルギー遷移と弾道捕獲、二重月スウィングバイ、こうのとり式の漸増接近マニューバ
  といった概念を扱えることを目指す。
- 見た目の目標: 地球のオーロラ、太陽嵐によるオーロラ、戦闘で生じた荷電粒子によるオーロラ、
  夕方側の雲に落ちる地球の影、破壊された破片のジャニベコフ効果。

## この文書とコードの関係

**仕様が先、コードが後。** ここには、これから作る挙動・まだ実装されていない挙動が書かれている。

- **未実装の記述が残っているのは正常な状態である。** 是正待ちの食い違いではないし、
  作業が終わっていない印でもない。**仕様と実装が一致することを目標にしない。**
- **コードの現状を知るために SPEC/ を読まない。** 「いまどう動いているか」に答えられるのは
  コードだけである。SPEC/ を現状の説明として引用しない。
- **SPEC/ を開くのは、これから作るものを決めるときだけ**(`/modify-feature`)。
  **実装を終えたあとに SPEC/ を見に行って突き合わせる手順は存在しない。**
- **実装できたことを理由に書き足さない。** 書くのは意図であって、報告ではない。
  実装が意図に届いていない箇所は、コードのコメントと `memos/` の計画書が持つ。

## 何を書くか

**判定の問い — その一文を消したとき、失われるのは「作るべきもの」か、「作り方」か。**
作るべきものだけを書く。作り方は実装の裁量であり、書けば実装を調整するたびに嘘になる。

### 書かないもの

| 書かないもの | こういう文が該当する | なぜ |
| --- | --- | --- |
| アルゴリズム・データ構造・手続きの順序 | 「重い順に15天体まで合算する」「区間を分割して積む」 | 差し替えても振舞いは変わらない |
| 性能のための妥協 | 「費用のため高い倍率では解かない」「〜は無視する」 | 諦めたことは意図ではない |
| 原理上できないことの言い訳 | 「〜を持たないため判定できないので」 | いまの限界であって、どう振舞うべきかではない |
| 達成した精度・誤差・実測値 | 「加速度は 3.96×10⁻⁴ m/s²」「境界は高度28〜54 km」 | 実装の結果 |
| 識別子 | クラス名・ファイル名・関数名・定数名 | コードが変われば嘘になる |
| 経緯と現況 | 「以前は」「旧」「暫定」「まだそうなっていない」 | 歴史も進捗も仕様ではない |

### 書くもの

- **どういう状況で、何が正しく見えていなければならないか。** そこから許せる誤差を見積もり、
  刻み幅・許容量・アルゴリズム・どの判定を省くかを決めるのは実装の仕事である。
- **性能の「要求」は書く。** 「どの時間加速倍率でもフレームが落ちない」「倍率を上げたことが
  軌道の変化として見えてはならない」は、どう振舞うべきかである。
  **そのために何を諦めたかは書かない。**
- **遊ぶ人が観測できる値。** 画面に出る数値・文字列・キー名は実物どおりに、物理量は単位つきで。
- **現実の物理のうち、どのモデルを扱うと決めたか。** 採ると決めたことは作るべきものである。
  **その中で何を無視したかは書かない。**
- **ゲームプレイのために意図して物理から外す例外。** これは妥協ではなく意図なので、通常どおり書く。

### どこに書くか — 責務の外へ書かない

**1つのことは1箇所にだけ書く。** 分野表のどのファイルの担当かを決め、そこにだけ書く。

- **他のファイルの担当を書き写さない。** 必要なら「(ORBIT.md)」のように参照だけ置く。
  同じことが2箇所にあると、片方を直したときにもう片方が嘘になる。
- **担当でないことを、ついでに書かない。** ある機能の説明の流れで隣接分野の挙動へ話が及んだら、
  それはそちらのファイルの持ち物である。
- **担当が変わったら移す。** 書く場所が違うと気付いたら、参照を残さず移動させる。
- どのファイルの担当でもないなら、それは SPEC/ に書くことではない(実装の都合・作業の手順・
  検討の経緯)。

### 粒度と整合

- **分野ごとに、通して読める分量に収める。** 数式・定数表・段階的な手続きが並び始めたら、
  それは作り方を書いている。
- **既存の本文を、書き方の根拠にしない。** 周りが細かく書いてあることは、細かく書いてよい理由に
  ならない。
- **矛盾を残さない。** 既存の記述と食い違う仕様を足すときは、古い方を消して整合させる。
  古くなった記述は経緯を残さず書き換える。
- **確定していないことは可能形で書く。** 「そう扱ってよい」「そうなりうる」で足りるものを、
  「必ずそうする」と書き切らない。逆に、意図して禁じることは断定で書く。

## 「未確定の案」節の運用

各ファイルの末尾に置く。**「どの拡張性を残すべきか」を判断するための材料**であり、それ以外の
用途で使わない — やることリストでも、思いつきの置き場でもない。分野ごとに分けてあるのは、
その分野の確定仕様を読むときに必ず目に入り、古くなったことに気付けるようにするため。

- **ユーザーが「実装するかもしれない」と言及したものを、その都度ここへ記録する。**
  共通化・一般化の判断で迷ったとき、ここに無ければユーザーに問い、返答をここへ足す。
- **確定したら本文へ移し、この節からは消す。**
- **可能性が消えたら消す。** 実現が難しくなった案、方針が変わって不要になった案は、
  経緯を残さず削除する。
- **1件は1〜3行。** 検討の過程・比較・実装案は書かない。それらは `memos/` が持つ。
- **本文から追い出した実装詳細の退避先ではない。** 性能のために諦めたことは、ここにも書かない。
- 該当する分野が無い、あるいは複数分野にまたがるだけの漠然とした構想は、ここには書かない。
