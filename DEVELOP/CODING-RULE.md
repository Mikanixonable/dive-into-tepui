# CODING-RULE — 設計方針・命名規則・コメント規約

`src/**/*.ts`、`tests/**/*.ts`、および HUD の CSS を書くときの規約の正本。**コードを編集する
ときは常にこれを参照する。** 新しいコードと変更範囲を本書へ揃える。既存コードに残る違反は、
本書の規則を弱める根拠にしない。

ゲームがどう振舞うべきかは `SPEC/`。本書はコードをどう書くべきかだけを持つ。

---

# 1. 設計方針

## 1.1 基本原則

可能な限り単純で簡潔な実装を求める。長大なファイル、非自明なコードは人間にもエージェントにも
読めないため、簡潔になるように書き直すべきである。

要求した仕様を超えて実装が複雑になるような判断を勝手に追加すべきでない。実装が自明であることは、
仕様が自明であることと相関する。非自明な実装は非自明な挙動を生み、悪い UX に繋がる。

いついかなる時も、好ましくないパターンを好ましいパターンに書き換えることは歓迎される。
好ましくないものは作るべきでないし、残すべきでない。

**優先順位は、物理的正確さ > 実装の適切さ > 実行時パフォーマンス > 変更コスト。**
下位のために上位を崩さない。

## 1.2 モジュール化

良いモジュール化とは、それぞれが明確に分割された単一の責務を持った、疎結合なモジュール群である。

悪いモジュール化:

- 責務が大きすぎるモジュール、関数。
- 長大なファイル、モジュール、関数。モジュールは200行、関数は100行を基準とする。
- 責務がないモジュール。例えば不要なたらい回しをするだけの薄すぎるラッパーなど。
- 1箇所からしか参照されていない小さな関数を、再利用性や責務の違いといった正当性なしに別モジュール
  へ置くこと。正当性が無いなら、たらい回しモジュールと同じ悪いパターンである。
- 実装の重複。同じ処理が複数箇所に分散して書かれているもの。
- 早急な一般化。

責務の有無とコードの規模には多少の相関はあるが、絶対ではない。どんなに行数が少なくても、責務を
持っているのであれば単独のモジュールとして維持すべきである。行数が長くても無駄なたらい回しを
しているだけであれば、削除すべきである。

**トップレベル(`main.ts` / `game.ts`)に実装を直接書かない。** そこにあってよいのは
オーケストレーション — サブシステムの生成・配線と、呼び出し順の決定だけである。条件分岐を伴う
判断、状態の組み立て、メニュー項目表、座標計算は、たとえ1箇所からしか使われなくても、
その関心を持つモジュールへ置く。

## 1.3 責務分割の見つけ方

**関数名やコメントの自然言語的な関連性には注目せず、依存関係だけに注目する。**

- クラス外から情報をもらいまくっていて、クラス内の情報に全然手を付けていない関数は、置き場所が
  適切でない懸念がある。
- 特定のクラスが常にある情報を外部からもらっているとき、その情報はそのクラスに参照コピーなどで
  事前に共有しておくべき懸念がある。特にその情報が外部で使用される頻度が低いときには、正所有権を
  そのクラスへ移動するべき懸念がある。
- 異なるクラスにまたがって存在する複数の情報が頻繁にセットで受け渡されているとき、その2つの情報は
  同じクラスに配置されるべき可能性がある。
- 漠然とした多数の情報がひとつのクラスに入っていて、関数ごとに一定のパターンが見られないときは、
  そもそもそのクラスの責務が定まっていない可能性がある。
- 外部から一度しか呼ばれていない関数は、本当にそこで処理を区切るべきだったのか熟考する必要がある。
  形式的には、多数の引数をまとめて受け取っている関数は I/F の切り方に失敗している可能性がある。
  意味的には、クラスオブジェクトとして強い独立性を主張できない限り、疑いの余地がある。
- 類似した形の式、類似した形の処理が異なるモジュールに分散して書かれているときは、重複実装の疑いが
  ある。

## 1.4 「重複実装の禁止」と「早急な一般化」の分かれ目

判断基準は **共通化したコードを今後も使う「可能性」があるか**。参照箇所の数ではない。

- **1箇所からしか参照されていなくても、** 一般化した側を今後使う可能性があるなら、あるいは巨大な
  責務を分割するためなら、**分割する。**
- **2箇所以上あっても、** それらが個別に調整されうる要素なら、多少の共通実装があっても
  **一般化しない**。
- 決め手は **共通化した側が変更されたとき、参照側の挙動も変更されるべきか**。

これはコードからは判別できない。将来実装される可能性のある機能を知る必要がある。
`memos/hedalu244/possible_features.md` を見て、そこで決まらないなら **ユーザーに問う。**
推測で一般化しない。ユーザーが「実装するかもしれない」と言及したものは同ファイルへ記録する。

## 1.5 データ構造

良いデータ構造とは、少ないステート設計と、適切に構造化されたデータである。

悪いデータ構造:

- 正データが複数箇所に分散、重複しているデータ。
- 軽微な計算で求まるものをステートとして持っているデータ。
- 複数箇所が一定の整合性を保つことが要求されるデータ。メモ化アルゴリズムなどでどうしてもそのように
  扱わなければならない場合は、適切に隠蔽しなければならない。**整合性保持責務の漏洩は重大な違反。**
- 同一の意味、同一の情報量を持つ型を複数作ること。これは重複実装である。

**不在は `T | null` で表す。** 代役のダミー値を立てたり、不在を表す別の真偽値を併置したりしない。

**キャッシュキーには、結果に影響する入力をすべて入れる。** 一つでも漏れると、静かに古い値を返す。

## 1.6 オブジェクトの流用の禁止

同一の参照の中身を丸ごと書き換えて別用途に転用するのは禁止。
基本的なデータ型は極力 immutable に設計するべきである。
状態を孕んでいて immutable にできないオブジェクトについても、丸ごと中身を差し替えるメソッドは
禁止。そのような操作が発生するときは、ほぼ確実にオブジェクトの意味自体が変化しているので、
インスタンスを作り直すべきである。例外は、可読性を犠牲にするに足る相当のパフォーマンス上の理由が
ある場合のみ。

## 1.7 フレーム処理の位相

毎フレームの処理は `update` → `sync` → `render` の3位相に分かれ、**位相ごとに触れてよいものが
決まっている。** 位相の境界を跨ぐコードを書かない。

- **`update`** — 論理状態・シミュレーション状態を進める。**THREE.js オブジェクトと DOM に触らない。**
  時間刻み `dt` を受け取るのはこの位相だけ。
- **`sync`** — 既に生成済みの表示物(メッシュ・HUD の DOM)を、計算済みの論理状態へ一致させる。
  **論理状態を進めない。** したがって `dt` を受け取らない。表示側の更新頻度を落としたい場合は、
  実時刻の締切を自分で持つ。
- **`render`** — 描画命令を発行するだけ。
- **`build`** — 表示オブジェクトを構築してシーンへ登録する。毎フレームの処理ではない。

## 1.8 改名・移動

**改名は痕跡を残さず完全に置き換える。** 歴史的経緯はコードとコメントの責務ではない
(必要なら git history が持っている)。

- 旧名が 0 件になるまで消す。`src` `tests` `DEVELOP` `CLAUDE.md` `.claude` `memos` を全文検索する。
- **「旧」「former」「previously」「〜だった」「(旧 xxx)」と書くのは禁止。** コメント・文書には
  新しい姿だけを記述する。何を何に変えたかは、コードではなく変更セットの報告文に書く。
- 互換のための旧名エイリアス・ラッパー・再エクスポートを残さない。呼び出し側を全部直す。

## 1.9 TypeScript の書き方

- `const` を原則使用し、どうしても破壊的な更新が必要なときだけ `let` を使う。`var` は絶対に
  使うべきではない。
- 配列 like なものの処理については、イテレーターが存在すれば `for...of` を使い、存在しない場合のみ
  素の `for` 文を使う。`filter` や `map` が適している可能性があればそちらを使う。`reduce` は総和を
  求めるなどの単純な場合を除き、使わない。
- **「状態を更新し、副産物を返す関数」を作らない。** 副産物である値が欲しいときに状態が更新されて
  しまうと困る。副作用のある void 型(成否を boolean で返すくらいならよい)の関数と、副作用がなく
  返り値が意味を持つ純粋関数のいずれかであるべき。計算関数は何度呼んでも、1度だけ呼んで値を
  使いまわしても同じ結果になる — 呼び出し回数に対する冪等性があるべき。
- **不要なクロージャ注入は行わない。** 特定のオブジェクトに影響を及ぼしたいなら、その mutable な
  オブジェクトを直接渡す。関数を引数にするのは柔軟性が高い反面、複雑なクロージャ関係が生まれて
  可読性を下げる。
- **雑多な値をまとめた引数オブジェクトを作らない。** 必要な値を明示的な引数として渡すか、
  参照を共有する。
- オブジェクトの公開契約と、クラスが実装できる契約には `interface` を使う。union、intersection、
  mapped type、関数型には `type` を使う。
- 再代入しないフィールドは原則 `readonly` とする。入力データ型のプロパティも原則 `readonly` とする。
- 読み取り専用の配列引数と返り値は `readonly T[]` とする。所有者自身が変更する配列だけ `T[]` とする。
- exported 関数と public / protected メソッドは戻り値型を明示する。
- 型アサーション `as` と非 null アサーション `!` は、その前提が型以外の仕組みで保証されている場合に
  限る。

### クラスメンバーと公開範囲

- クラスのメンバーには `public`、`protected`、`private` のいずれかを明示する。コンストラクタにも
  明示する。
- 外部利用をそのクラスの契約として意図したメンバーだけ `public` にする。継承先へ提供することを
  意図したメンバーだけ `protected` にする。それ以外は `private` にする。現在外部から使われて
  いないという理由ではなく、その操作を外部へ約束するかどうかで判断する。
- 外部へ公開するフィールドは原則 `readonly` とする。mutable な public フィールドは禁止しないが、
  状態の所有者と変更条件を明確にできる場合に限る。
- 状態変更時に不変条件、連動する更新、副作用がある場合は、public フィールドへの代入ではなく、
  状態を所有するクラスのメソッドに変更を閉じる。
- クラスが保持する別オブジェクトを外部へ公開するときは、private フィールドを正本とし、public
  getter から渡す。
- コンストラクタ引数を同じ値のままフィールドとして保持するときは、コンストラクタ引数プロパティを
  使う。値の検証、変換、条件付き代入、遅延初期化が必要なときはフィールドを別に宣言する。
- **二段初期化を作らない。** 初期状態はコンストラクタで受ける。生成後に「初期状態を流し込む」
  メソッドを設けない。

### ファイルと export

- 一つのファイルには原則として一つの主要な公開クラスまたは主要概念を置き、ファイル名を主要 export
  に対応させる。
- default export は使わず、named export を使う。
- `index.ts` による一括再 export は、公開境界として意図的に設計したディレクトリに限る。
- import は、外部パッケージ、プロジェクト内の value import、`import type` の順にまとめる。

### 表記

- インデントは空白2文字とし、タブを使わない。
- 文字列は、文字列内の引用符との衝突を避ける場合を除いてシングルクォートを使う。
- 文末にはセミコロンを付ける。
- 複数行の配列、オブジェクト、引数、型引数には末尾カンマを付ける。
- 一行には一つの文または一つのメンバー宣言を書く。
- 一行120文字を目安とし、名前や文字列を不自然に分割せず、意味のまとまりで改行する。
- 一行のガード節では波括弧を省略できる。複数の処理を持つ条件分岐では波括弧を使う。
- 数値に領域上の意味、単位、複数の利用箇所がある場合は名前付き定数にする。短い数式に固有の係数は
  数式の近くに置ける。
- クラスメンバーは機械的なアクセス範囲順ではなく、責務ごとに関連するフィールド、アクセサ、メソッド
  を近くへ置く。

## 1.10 CSS の書き方

- CSS は CSS として書き、TypeScript 側からはクラス名を指定するのみとする。
- 細部までクラス名で指定するのではなく、変更されにくい文書構造に対しては子要素セレクタによって
  指定する。
- 色・寸法・角丸・余白のリテラルを直書きしない。トークンを参照する。トークンの定義は1箇所に置く。
- UI の見た目・操作の規約そのものは `SPEC/UI-DESIGN.md` が正本。

# 2. 命名規則

## 2.1 一般規則

良い命名とは、振る舞いと扱い方が明快で、混同の恐れがなく、適切な長さの命名である。

悪い命名:

- 類義語の混雑。同じものを異なる言葉で指している命名。
- 曖昧な区別。区別すべきものを同じ名前で指す命名。
- 漠然とした命名。`process` や `data` などの命名は意味を持たない。
- スコープの狭さ、混同のおそれのなさに対して、不必要に長大な命名。スコープが十分に狭ければ、
  前述の漠然とした命名も許される。一行のラムダ式規模であれば一文字変数名も許される。

表記:

- クラス、interface、type、enum は `PascalCase`。
- 関数、メソッド、getter、setter、フィールド、変数、引数は `camelCase`。
- TypeScript のファイル名とディレクトリ名は `kebab-case`。
- 固定値として共有するモジュール定数と static 定数は `UPPER_SNAKE_CASE`。単に `const` で宣言した
  ローカル変数は `camelCase`。
- 略語は `camelCase` / `PascalCase` の中では一つの単語として扱う(`bodyId`、`toEci`、`jdTdb`)。
  `UPPER_SNAKE_CASE` では略語も大文字にする(`SIM_EPOCH_JD_TDB`)。
- JavaScript、Web API、ライブラリが定めた表記(`URLSearchParams`、`getUTCDate`、`WebGPU`)は
  変更しない。
- 一文字名は、短い数式、狭いコールバック、ループ添字など、意味が慣習とスコープから一意に決まる
  場所に限る。

# 3. コメント規約

コードを書く・書き換えるあらゆる変更で、この規約に従う。

## 3.1 大原則

**そのモジュールの責務外のことに言及しない。**
コメントもコードと同じく、モジュールの責務外のことに触れてはいけない。下の禁止リストのほとんどは
ここから導かれる。「どのように扱うべきか」(= そのモジュールが提供する契約 = 責務の内側)は書き、
「どのように扱われているか」(= 呼び出し側の事情 = 責務の外側)は書かない。他モジュールの内部処理・
他モジュールの責務の説明も同様に書かない。

**関数の冒頭、モジュールの冒頭のコメントでは、実装詳細に言及しない。**
モジュールや関数の先頭では、その概観やインターフェイス(公開責務)を明言する。モジュールの内部
実装の詳細、他モジュールの内部実装、外部モジュールでの扱われ方は書かない。

**コメントはコードを読む人(人間にもエージェントにも)の context を消費する。**
書いてよいのは「コードを読んでも分からないこと」だけであり、それ以外は書かないほうが良い。
分量の少なさそれ自体が価値である。

十分に良い命名・良い設計で書かれたコードは自然言語のように読める。コメントが必要な非自明な
コードは、まず命名や設計が悪さをしていることを疑う。

**言語は日本語に統一する。** 英語のコメントを見つけたら書き直す。

## 3.2 書いてよいもの、書くべきであるもの

- **モジュール先頭**: そのモジュールの責務(なにを担当するか)。目安 **5行**。
- **関数・フィールド**: 「なにをするか」「どのように使えばよいか」(引数と返り値、副作用、
  呼び出し規約など)。目安 **1〜3行**。
  **直前に1行もコメントがない関数・メソッドは、それだけで不足とみなす。** 例外は自明なもの —
  1行だけからなる getter/setter と、本文が空のもの。名前の言い換えにしかならないなら、
  **名前から読み取れない契約**(返り値が null になる条件、破壊する状態、満たすべき事前条件)を書く。
- **数値を扱う変数、定数**: 単位系や座標など必要な情報。`// ECI [m/s]` など。目安 **1行**。
- **関数内**: 「現状なぜそのように実装されているのか」が **相当に** 非自明なときだけ。目安 **1行**。
  書いてよいのは次の3つに限る:
  - **安直に単純化すると起きるバグ。** 「この項を省くと発散する」「この順序でないと〜が壊れる」など、
    次に触る人が単純化して壊す道筋が具体的に見えているもの。
  - **複雑な計算式・特殊な条件分岐の意図。** 式や分岐そのものからは読み取れない意味を1行で与える。
  - **安直に想像できる実装(このプロジェクトではたいてい物理的な正しさ)とコードが異なり、それが
    明言された仕様に基づくとき — その根拠。** 明言された仕様とは、コメント以外の場所
    (`DEVELOP/SPEC/`・`memos/mikanixonable/dev.md` など)に書かれているものを指す。
- **中規模以上の関数の文脈コメント**: 非コメント行が10行以上にわたる関数では、実装を数行単位の
  **意味ブロック** に分割できるはずなので、各ブロックの文脈を追いやすいよう **数行に1行の頻度で**
  ごく簡潔なコメントを置く。どのように実装されているかの詳細ではなく、文脈を与えるのみにとどめる。
  **無いこと自体が不足** とみなす。
- **将来修正すべきこと(TODO)。** 安直に想像できる実装と異なるのに **明言された仕様に基づかない**
  箇所は、潜在的なバグか将来是正すべき箇所である可能性が高い。弁明を書いて済ませず、TODO として
  マークする。

行数は機械的な上限ではなく目安。基準は意味の側にあり、上を超えるときは「本当にその情報が要るか」を
下の禁止リストで確かめる。

## 3.3 書いてはいけないもの

以下はすべて **context を圧迫するだけで利益がない**。一切書かない。

1. **どのように実装されているか。** 実装の唯一の正はコードであり、書けば変更のたびに矛盾する
   (「なぜ」を書いてよいのは 3.2 の3条件に当たるときだけ)。
2. **なにをしないか(否定形)。** 「〜は行わない」「〜には依存しない」「〜を持たない」
   「〜する必要はない」「〜だけ」「〜のみ」など。責務境界を説明したいなら、そのモジュールが
   「なにをするか」を書く。
3. **誰が使うか・どこから呼ばれるか。** 呼び出し側の事情はそのモジュールの責務ではない。
4. **現状どのように使われているか。** 継承先での使われ方、現在の唯一の呼び出し元、
   「いまは使っていないが」の類。
5. **過去の実装でなにをしていたか・従来実装との対比。** 「旧」「以前は」「〜だった」
   「かつては〜していた」「〜より無駄が少ない」。かつてより複雑な実装をしていた痕跡も同様、
   単純になった今のコードは、それ自体で読める。
6. **変更の差分。** 「〜を倍にした」「〜を追加した」「×0.7 でスリム化」「1/10 に減速」。
   コードは常に「現在の姿」だけを語る。何を何に変えたかは変更セットの報告文と git history が持つ。
7. **外部モジュールへ委譲したことの痕跡。** 「〜は X の責務になった」「実体は X が持つ」。
   委譲後のコードは委譲先を呼ぶだけなので、その事実はコードが語っている。
8. **他モジュール・下位モジュールの内部処理の説明。** 責務外への言及。
9. **検討メモ・課題管理文書への参照。** `memos/` 以下の章番号、課題票の項番など。
   決着した検討の経緯は、コードを読むのに必要ない。
10. **コメントがコメントを参照する。** 「〜のコメント参照」。
11. **引数名・型から自明な説明の列挙。** 「playerPos: 自機の位置」の類。
12. **その場に書かれた実装と同じことを言っているもの。**
13. **実装と矛盾したもの・古くなったもの。**

## 3.4 採らなかった実装の弁明

想起しうる他の実装を採らなかったとき、単に弁明を書くべきでなく、以下のいずれに該当するかを
明確にする。

- **外部で(人間によって)明言された仕様に基づくなら、その根拠を書く。** 根拠はコメント以外の場所
  (`DEVELOP/SPEC/`・`memos/mikanixonable/dev.md`)に明言されているものを引用する。
- **明言された仕様に基づかないなら、潜在的なバグか、将来是正すべき箇所である可能性が高い。**
  単に弁明を書いて済ませず、**TODO としてマークする。**
- **今後その形へ書き換える動機のない、想起しえない実装に言及しているだけなら、書かない。**
  例えば、より複雑で安直でない過去の実装に言及しているだけなら、その経緯はコメントに書かない。

## 3.5 なぜこの規約か

リファクタリングの目的は、**過去の複雑な実装の経緯を知らなくてもコードを理解できるようにすること**
である。経緯をコメントに残すのは、その目的を自分で打ち消す行為でしかない。

そしてこの種のコメントは、**リファクタリングや変更要求でコードを書き換えるたびに増えていく。**
「なぜ変えたか」「前はどうだったか」「他はどうしているか」を書き残したくなるのは、変更した本人の
視点であって、次にそのコードを読む人の視点ではない。**コードを書き換えたら、その変更セットの中で、
自分が書いたコメントをこの基準で必ず見直す。**

新しい冗長パターンを見つけたら、3.3 の禁止リストへ追記する。
