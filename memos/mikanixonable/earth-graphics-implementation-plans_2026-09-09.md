# 地球描画の不足分 — 優先順位と3つの実装計画

作成日: 2026-09-09。調査対象: `workspace3` の **`95f9cfc1`**。
状態: 計画案。ゲームコード・SPEC の変更、実行時の描画検証はこの文書の作成には含めない。

## 目的

地球の雲・地表・発光現象を、次の優先順位で実現する。既存の機能を再実装せず、要求との差に作業を割り当てる。
推奨は **案B: 既存の生成場を保ち、必要な場所から描画と解像度を拡張する**。
案Aは変更規模を抑える場合、案Cは雲や地形を近距離から見た品質まで追う場合の選択肢とする。

### SPEC へ反映する要求文案

以下は作るべき振る舞いの案であり、実装時の最初の手順で SPEC へ反映する。

1. 地球の雲は立体と影を持ち、表示時刻に応じて移動・変形する。
2. 平常時の雲は海で小粒、大陸で広がりを持つ傾向を示す。海陸の境界では連続的に変わり、天候・低気圧・前線による例外を許す。
3. 雲の形と高さは緯度に応じて変わる。対流圏界面の目安は赤道16 km・高緯度8 kmとし、熱帯の積乱雲・かなとこ雲、中緯度の低い積雲、高緯度の薄く広がる雲を描き分ける。かなとこ雲には平らな雲頂と、その中央で圏界面を突き抜ける凸部を設ける。
4. 孤立した島の風下には、刷毛で擦ったように小粒の雲が列をなし、流れる。
5. 南北緯30°±5°では背景の雲が発生しにくくなる。低気圧・前線が作る雲はこの抑制を上回る。
6. 約5日の天候変動によって、海にも広がりのある雲、低緯度にも薄く広がる雲が発生する。
7. 台風は緯度30°付近の海上へ約7日に1回発生し、約5日生存する。位置の移動は必須としない。
8. 雲が流れる向きには貿易風・偏西風の違いが現れる。
9. 直径約1000 kmの低気圧は、背景の海陸・緯度・高圧帯の条件より強く広がりのある雲を作る。低気圧から螺旋状の前線が延び、その両側で雲の有無が変わる。低気圧によって偏西風の流れも曲がる。
10. 約30日に1回、巨大火山の噴火による灰色のかなとこ雲が現れる。
11. 雲の輪郭は夜から朝方に曖昧になり、現地の太陽時で朝8時頃から雲が発達する。
12. 発達した雷雲の上空に、短時間発光するスプライトを描く。
13. 地表は海と陸で材質を描き分ける。オーロラには細い発光筋、折れ重なるカーテン、部分的な明滅を持たせる。
14. エアグローを地球周囲の淡い発光層として描く。暗所ではプルキンエ現象による相対的な色の明るさと彩度の変化を表す。
15. 植生は季節に応じて変化する。地形は標高による起伏と詳細を持つ。海には流氷、河口から広がる河川水、プランクトンの増殖による水色の分布と渦を伴う動きを加える。

特に **プルキンエ現象を雲のアニメーションやオーロラより先に実装しない**。

島の雲に既存の風を使うこと、雲の海陸判定に地理データを使うことは、その後の「風の追加」「地形の描画」を前倒しすることには数えない。

### 暫定の解釈と、変更された場合の影響

| 論点 | 計画で置く案 | 覆す場合に変わる手順 |
| --- | --- | --- |
| 「日」の基準 | 台風・天候・噴火は表示時刻の86400秒を1日とする。現実の経過時間やフレーム数に依存させない | C2、C7、C8、C11、C13 |
| 台風の頻度の数え方 | 全球で7日ごとに1イベント、北・南半球の海域を順に選ぶ。海域ごとに7日ではない | C8 |
| 台風の位置 | 発生は南北緯25〜35°の海上候補点。既存の移動を保つ案を基本とし、固定化は変更量と表現の比較で決める。「動かなくていい」を移動禁止とは解釈しない | C8 |
| 雲の海陸差 | 平常時の傾向として実装する。海洋性層積雲などの既存表現は天候側の例外へ位置付ける。単純に海の広い雲を全部消さない | C3、C7、C10 |
| 雲の緯度差 | 8/16 kmは今回の描画モデルの目安。雲種を緯度で完全排他にはせず、前線・台風で例外を許す | C4、C10 |
| 前線の螺旋の向き | 要求の「北は時計回り・南は反時計回り」は、まず**中心から外側へ線をたどる向き**の候補として保持する。風が低気圧を周回する向きとは別に定義する | S0、C10 |
| 火山・スプライトの細部 | 噴火間隔30日を固定し、噴煙寿命は初回案2日。スプライトは雷雲に結び付いた短時間イベントとし、発生頻度・表示時間はC13の比較画像で調整する | C11、C13 |

地表の低気圧を回る風は、地球の外から見て北半球が反時計回り、南半球が時計回りである。
螺旋の線をたどる方向、雲の移流方向、カメラから見た回転を混同しない。要求が風そのものの回転を指定している場合は、S0で演出上の指定かを確定してからC10へ進む。
根拠: [NOAA/NWS: Pressure Systems and Fronts](https://www.weather.gov/lmk/basic-fronts)。

## 3案の比較

どの案も、S0→C1〜C13→E1〜E7という機能の優先順位と、同時刻の再現性を守る。
差は画質を得る方法、投入する基盤の量、各段階で到達できる近距離の品質にある。

| 観点 | 案A: 小さく順次改良 | 案B: 生成場と描画を段階拡張【推奨】 | 案C: 近景品質を重視 |
| --- | --- | --- | --- |
| 雲の描画 | 雲頂の高さ場と薄い殻を維持。必要な項だけ足す | 高さ場を基本とし、近景の細部と有限の雲底を必要な段階で足す | 遠景は高さ場、近景は密度を積分するボリュームへ移行 |
| 小島・小粒への対応 | 対象地域と細部を解析的に補う | 全球の低周波場と、視点近傍の高解像度場を共有して読む | 局所的な密度・照明の場も持つ |
| 時間更新 | 既存更新を保ち、入力更新漏れを直す | 更新時刻の間隔と補間を、画面上の移動誤差から決める | 密度場の更新と画面履歴を再利用。時刻ジャンプ時は履歴を捨てる |
| 天候・イベント | 既存の場へ解析的な地域差・イベントを足す | 既存の気圧・風・湿度を共用し、背景と例外の優先を明示する | Bの気象モデルを使い、雲底・上端・密度形状を細かく表現 |
| 海陸・地形 | 水面法線、標高法線と粗い変位 | 海陸の独立マスク、近景の標高タイル | 海面・地形も近景の詳細と遮蔽まで拡張 |
| 季節・水色 | 少数の季節係数と解析的な分布 | 月別の植生データと、地域別の水色分布 | 月別・地域別データの高解像度配信と近景表現 |
| 主な利点 | 各機能へ早く到達する | 希望の特徴を残しながら、全球の計算量増加を抑えやすい | 雲の側面・内部や地形の輪郭を最も細かく作れる |
| 主な限界 | 雲の内部・側面、小島を広範囲に細かく描く表現には限界 | 投影境界・補間・影との整合の実装が必要 | 雲の最初の段階が長く、後続の海陸・オーロラへ届くまで遅い |

**案Bを勧める理由:** 既に動く雲と影があるため、その全面置換から始める理由は弱い。一方で、全球1024×512の場を使うだけでは小島の雲列や細かなかなとこ形状を扱いにくい。
必要な段階で近傍の解像度と表現を足す方が、作りたい特徴と変更範囲を対応させやすい。
案A・Cは保留案であり、今回の文書作成で方式を確定した扱いにはしない。

## 共通の手順

### 検証の記法

全手順で **`npm run typecheck`** を実行する。
以下の「R」は加えて **`npm run test:render`**、「G」は **`npm run test:game`**。
`src/physics/` や `src/math/` を変更する場合に限り、それぞれ **`npm run test:physics`**、**`npm run test:math`** も実行する。

描画が変わる手順では `/rendering-workflow` に従い、対象が写る画像を最低1枚残す。
生成場は `npm run cloud-lab` / `npm run cloud-lab:shot`、地球の立体・陰影は `npm run render-lab` / `npm run render-lab:shot` を使う。
テクスチャの到着が必要な比較は読み込み完了を待つ。画像が未到着の単色画像を合格資料にしない。
ゲーム本体のヘッドレス操作確認は、実行時確認を明示的に依頼された場合に `/verify` で行う。

新規テストは、決定論性、境界の連続性、寿命、単位・回転方向などの不変条件を対象にする。
見た目の調整値や生成画像そのものを正解として固定しない。各手順は実装・対応する検証を含め、単独でcommitできる単位にする。

### S0. 対象の仕様をコードより先に確定する

目的: 採用案と、海陸差・周期・前線の向きなどの意味を実装可能な要求へ確定する。

| 変更箇所 | 行うこと |
| --- | --- |
| `DEVELOP/SPEC/README.md` | 実装に着手する時点で仕様の書き方と担当分野を読む |
| `DEVELOP/SPEC/RENDERING.md` | 本文の要求文案のうち、採用した実装範囲を先に反映する。実装方式・キャッシュの都合は仕様へ混ぜない |

達成条件: 実装する範囲、全体と雲の優先順位、表示時刻の意味、螺旋をたどる方向が確定している。
`npm run typecheck`。コードを変えてから SPEC と突き合わせる作業は設けない。

## 達成目標

1. C1〜C13、E1〜E7の各行に、達成条件に対応する比較結果がある。基礎ありの項目を作り直しただけで進捗と数えない。
2. 雲の立体・散乱・影・イベントは、同じ表示時刻と地球固定座標で一致する。停止、巻戻し、時間ジャンプで履歴依存の別の空にならない。
3. 雲の海陸差・緯度差・高圧帯は背景の傾向となり、天候・台風・前線は必要な例外を作れる。
4. 台風は7日間隔・約5日寿命、噴火は30日間隔で再現される。日変化は現地太陽時、季節はゲームの開始暦と表示時刻に対応する。
5. 同じデータ・時刻で全球表示から近景へ移っても、雲・影・地形・海岸の対応が切れない。
6. 変更した各層の型検査・回帰テストが通り、対象の画像が残る。性能は同一GPU・画面解像度・視点・時刻の変更前後で比較する。

### 計算量とメモリの目安

以下は実測値ではなく、方式比較のための導出。

| 対象 | 導出と意味 |
| --- | --- |
| 全球場の地上解像度 | 赤道で `2π×6371 km÷1024 ≈39.1 km/texel`。24 kmの粒を4点で表すなら6 km/texelが必要で、全球幅は約6672 texel以上になる。幅8192へ増やすと面積は `(8192/1024)²＝64倍`。近傍だけを細かくする理由になる |
| 雲の出力テクスチャ | RGBA16F、1024×512なら `1024×512×4×2 bytes＝4 MiB`。前後2時刻で8 MiB。**気圧・湿度・前線などの中間場、mip、GPU内部の配置分は別** |
| 局所場 | RGBA16F、1024²なら `1024²×8＝8 MiB/枚`。全球場と局所場を各2時刻保持する場合、最終出力だけで `8+16＝24 MiB`。中間場も個別に足して予算を決める |
| 更新間隔 | 速度v、1画素が張る実距離p、許容ずれε画素なら `Δt ≤ εp/v`。例としてv=20 m/s、p=1000 m、ε=0.5なら25表示秒。p=100 mなら2.5秒。時間倍率を含めて実フレームで何回生成するかへ換算する |
| 時間補間の限界 | 上の移動式だけでは誕生・消滅や形の変化を保証しない。イベント境界では強制更新し、生成場の差も比較する。長い間隔の線形混合で雲が二重に見えるなら間隔を縮める |
| ボリュームの標本数 | 1920×1080、画面の25%が雲、半解像度、32標本なら `1920×1080×0.25÷4×32 ≈415万標本/frame`。照明を各点で6回読むなら追加約2488万標本。これをFPSの保証には使わない |
| 季節画像 | RGBA8、4096×2048を2枚なら `4096×2048×4×2＝64 MiB`、mip込みで約85 MiB。12枚常駐は同条件で約512 MiBとなるため、隣接月の入替えを基本にする。配信用圧縮容量とGPU展開後の容量は別 |

計測には `tools/render-lab-measure.mjs` と既存のGPU時間計測を利用する。平均だけでなく更新フレームの山を比較する。
キャッシュ・LODの追加は、必要な入力をキーへ含めることと、各読み手で同じ場を参照することを達成条件にする。

## 最初に実施する範囲の提案

案Bの **S0→C1→C2→C3→C4** を最初のまとまりとする。
これで「影がある」「時刻で動く」という土台を使いながら、海陸の雲の傾向、雲頂高度、かなとこの凸部という具体的な不足へ進める。
C3の局所場で海の小粒を表せるようにし、次のC5でもその場を使って島の雲列を成立させてから、C6以降を順に進める。
