# 地球大気・発光現象の不足分 — 優先順位と3つの実装計画

作成日: 2026-09-09。調査対象: `workspace3` の **`95f9cfc1`**。
状態: 計画案。ゲームコード・SPEC の変更、実行時の描画検証はこの文書の作成には含めない。

## 目的

この計画は、**地表タイル計画の実行後**に、地球の雲・気象・発光現象・時間変化する海の表現を実装するためのものとする。
地表の静的な材質、標高、法線、水域・氷の分類、タイル配信、LODは
[earth-surface-tiles-plan_2026-09-09.md](earth-surface-tiles-plan_2026-09-09.md)の責任範囲であり、この計画では再実装しない。

推奨する要件解釈は **気象学と実装の均衡案**、実装方式は **案B: 生成場と描画を段階的に拡張** とする。
案Aは変更量を抑える場合、案Cは雲を近距離から見る品質まで追う場合の保留案である。

この計画では、次の共有データ契約を前提にする。データの生成・配信・GPUタイル管理は地表計画が所有し、ここでは読み取り専用の入力として使う。

```text
EarthSurfaceContext
  landSeaMask / waterMask
  elevation または terrainNormal
  staticIceMask
  coast または島境界を判定できる地理情報
```

地表計画が提供する形式と異なる場合は、現在の計画側に薄い変換アダプターを置く。雲側で別の原データ取得、`earth-land-mask.png`の独自生成、標高タイルの独自配信を追加しない。

### SPEC へ反映する要求文案

以下は作るべき振る舞いの案であり、地表計画の完了後にS0でSPECへ反映する。実装方式やキャッシュ容量はSPECへ書かない。

#### 雲・気象

- **C1** 雲は立体的な雲頂・雲底・厚みを持ち、既存の雲場を使って影を落とす。雲本体と雲影は同じ時刻・座標の場を読む。
- **C2** 雲は表示時刻に応じて風で移流し、雲の発生・消滅・発達も連続的に変化する。
- **C3** 海陸は固定的な粒度規則にせず、海面温度、湿度、安定度、地表加熱、上昇流から層積雲・浅い積雲・発達した積雲の傾向を決める。
- **C4** 対流圏界面は緯度・季節の代表値としておよそ8〜18 kmの範囲で変化する。積乱雲の雲頂はそこで平らになり、強い対流だけが上へ突出する。
- **C5** 孤立した島では風上側の上昇流と、風下側の小粒の雲列を表現する。
- **C6** 亜熱帯高圧帯では下降流と安定度によって深い対流雲を抑える。ただし海上の低い層積雲は残ることがある。
- **C7** 天候の変化は全球一様な周期ではなく、地域ごとに数日持続する気象レジームとして変化する。5日は代表的な持続時間とする。
- **C8** 熱帯低気圧は暖かい海面、高湿度、十分なコリオリ力などの条件を満たす海域で発生する。描画上の出現間隔約7日、寿命約5日は演出用スケジューラの値とし、発生緯度を30度に固定しない。
- **C9** 地表付近の貿易風と中緯度の偏西風を分け、雲種ごとに適切な高度層の風を使う。
- **C10** 低気圧は気圧偏差・上昇流・雲帯・前線を別々の効果として持つ。中緯度の偏西風は全球規模の波動で南北へ蛇行し、低気圧の周辺では局所的に曲がる。低気圧・前線・雲の移流は同じ合成風場から求める。
- **C11** 火山灰は通常の水雲とは別の灰色エアロゾルとして、噴火地点と上空の風に従って広がる。約30日の発生間隔は演出用とする。
- **C12** 雲の日変化は現地太陽時と地表・海面の違いから決め、固定UTC時刻で急に雲を出現させない。
- **C13** スプライトは発達した雷雲に結び付く短時間の上層大気イベントとして描く。

## 3案の比較

どの案も、地表タイル計画の完了後に共有データを接続し、S0→C1〜C13→E2〜E5→E7の順で進める。
差は画質を得る方法、投入する基盤の量、各段階で到達できる近距離の品質にある。

| 観点 | 案A: 小さく順次改良 | 案B: 生成場と描画を段階拡張【推奨】 | 案C: 近景品質を重視 |
| --- | --- | --- | --- |
| 雲の描画 | 雲頂の高さ場と薄い殻を維持。必要な項だけ足す | 高さ場を基本とし、近景の細部と有限の雲底を必要な段階で足す | 遠景は高さ場、近景は密度を積分するボリュームへ移行 |
| 小島・小粒への対応 | 対象地域と細部を解析的に補う | 全球の低周波場と、視点近傍の高解像度場を共有して読む | 局所的な密度・照明の場も持つ |
| 時間更新 | 既存更新を保ち、入力更新漏れを直す | 更新時刻の間隔と補間を、画面上の移動誤差から決める | 密度場の更新と画面履歴を再利用。時刻ジャンプ時は履歴を捨てる |
| 天候・イベント | 既存の場へ解析的な地域差・イベントを足す | 気圧・風・湿度を共用し、背景と例外の優先を明示する | Bの気象モデルを使い、雲底・上端・密度形状を細かく表現 |
| 地表データ | 地表計画のデータを読むだけ | `EarthSurfaceContext`を共有し、雲・季節・水色で同じ地理を読む | 同じ共有データを近景の密度・合成へ渡す |
| 季節・水色 | 少数の季節係数と解析的な分布 | 月別の植生データと、地域別の水色分布 | 月別・地域別データの高解像度配信と近景表現 |
| 主な利点 | 各機能へ早く到達する | 希望の特徴を残しながら、全球の計算量増加を抑えやすい | 雲の側面・内部や地形の輪郭を最も細かく作れる |
| 主な限界 | 雲の内部・側面、小島を広範囲に細かく描く表現には限界 | 投影境界・補間・影との整合の実装が必要 | 雲の最初の段階が長く、後続の海陸・オーロラへ届くまで遅い |

案Bを採用する。既に動く雲と影を再利用しながら、地表計画の共有データを唯一の静的地理入力にできる。全球1024×512の場だけでは小島の雲列や細かなかなとこ形状を扱いにくいため、必要な段階で近傍の解像度と表現を足す。案A・Cの表は、実測後に変更する場合の比較対象として残す。

## 共通の手順

### 検証の記法

全手順で **`npm run typecheck`** を実行する。
以下の「R」は加えて **`npm run test:render`**、「G」は **`npm run test:game`**。
`src/physics/` や `src/math/` を変更する場合に限り、それぞれ **`npm run test:physics`**、**`npm run test:math`** も実行する。

描画が変わる手順では `/rendering-workflow` に従い、対象が写る画像を最低1枚残す。
生成場は `npm run cloud-lab` / `npm run cloud-lab:shot`、地球の立体・陰影は `npm run render-lab` / `npm run render-lab:shot` を使う。
テクスチャの到着が必要な比較は読み込み完了を待つ。画像が未到着の単色画像を合格資料にしない。
ゲーム本体のヘッドレス操作確認は、実行時確認を明示的に依頼された場合に `/verify` で行う。

新規テストは、決定論性、境界の連続性、寿命、単位・回転方向などの不変条件を対象にする。
見た目の調整値や生成画像そのものを正解として固定しない。各手順は実装・対応する検証を含め、単独でcommitできる単位にする。

### P0. 地表計画の成果を共有入力へ接続する

目的: 地表タイル計画の実行後に、雲・季節・水色が同じ地理データを読む接点を作る。

| 変更箇所 | 行うこと |
| --- | --- |
| 地表タイル計画の生成マニフェスト・水域・標高入力 | `EarthSurfaceContext`として海陸、水域、静的氷、標高または法線、島境界を読み取れるようにする |
| `src/render/earth-surface-context.ts`（必要なら新規） | 地表タイルの配信・GPU常駐責任を持たず、雲・植生・水色が読む座標変換とマスク参照だけをまとめる |
| `src/render/cloud/climate-map.ts`、`src/render/cloud/weather-model.ts` | 雲側の独自海陸マスク生成を削除し、共有入力を読む |
| `src/game/celestial/solar-system/earth-system.ts` | 地表データと大気データの寿命・表示時刻を同じ地球インスタンスへ接続する |

達成条件: 地表計画の資源を二重取得せず、同じ緯度経度で地表・雲・水色の海岸が一致する。地表計画が未完了ならC1以降へ進まない。
`npm run typecheck`。この手順で地表の材質や標高表現を追加しない。

## 達成目標

1. 地表タイル計画の完了後、P0の共有入力接続を通ってC1〜C13、E2〜E5、E7の各行に達成条件に対応する比較結果がある。E1/E6は委譲済みで重複実装しない。
2. 雲の立体・散乱・影・イベントは、同じ表示時刻と地球固定座標で一致する。停止、巻戻し、時間ジャンプで履歴依存の別の空にならない。
3. 雲の海陸差・緯度差・高圧帯は気象条件による背景の傾向となり、天候・台風・前線・偏西風の蛇行は同じ合成風場から必要な例外を作れる。
4. 台風の約7日間隔・約5日寿命と噴火の約30日間隔は演出用スケジューラとして再現される。台風の発生条件は暖かい海・湿度・コリオリ力を使い、日変化は現地太陽時、季節はゲームの開始暦と表示時刻に対応する。
5. 同じ共有地表データ・時刻で全球表示から近景へ移っても、雲・雲影・地表・海岸・水色の対応が切れない。
6. 変更した各層の型検査・回帰テストが通り、対象の画像が残る。性能は同一GPU・画面解像度・視点・時刻の変更前後で比較する。

## 見積り

### 実装作業量

時間の断定ではなく、比較用の作業単位Uを置く。**1U＝既存の1機能について、コード変更・1回の比較・型検査と対象テストまで終える作業量**。
新規の表現やデータ調達は複数Uとする。実測時間が得られたら `所要時間＝Uの合計×実測時間/U` で置き換える。

### 計算量とメモリの目安

以下は実測値ではなく、方式比較のための導出。

| 対象 | 導出と意味 |
| --- | --- |
| 全球場の地上解像度 | 赤道で `2π×6371 km÷1024 ≈39.1 km/texel`。24 kmの粒を4点で表すなら6 km/texelが必要で、全球幅は約6672 texel以上になる。幅8192へ増やすと面積は `(8192/1024)²＝64倍`。近傍だけを細かくする理由になる |
| 雲の出力テクスチャ | RGBA16F、1024×512なら `1024×512×4×2 bytes＝4 MiB`。前後2時刻で8 MiB。**気圧・湿度・前線などの中間場、mip、GPU内部の配置分は別** |
| 局所場 | RGBA16F、1024²なら `1024²×8＝8 MiB/枚`。全球場と局所場を各2時刻保持する場合、最終出力だけで `8+16＝24 MiB`。中間場も個別に足して予算を決める |
| 更新間隔 | 速度v、1画素が張る実距離p、許容ずれε画素なら `Δt ≤ εp/v`。例としてv=20 m/s、p=1000 m、ε=0.5なら25表示秒。p=100 mなら2.5秒。時間倍率を含めて実フレームで何回生成するかへ換算する |
| 時間補間の限界 | 上の移動式だけでは誕生・消滅や形の変化を保証しない。イベント境界では強制更新し、生成場の差も比較する。長い間隔の線形混合で雲が二重に見えるなら間隔を縮める |
| ボリュームの標本数 | 1920×1080、画面の25%が雲、半解像度、32標本なら `1920×1080×0.25÷4×32 ≈415万標本/frame`。照明を各点で6回読むなら追加約2488万標本。これをFPSの保証には使わない |
| 季節画像 | RGBA8、4096×2048を2枚なら `4096×2048×4×2＝64 MiB`、mip込みで約85 MiB。12枚常駐は同条件で約512 MiBとなるため、隣接月の入替えを基本にする。配信用圧縮容量とGPU展開後の容量は別 |

計測には `tools/render-lab-measure.mjs` と既存のGPU時間計測を利用する。平均だけでなく更新フレームの山を比較する。
キャッシュ・LODの追加は、必要な入力をキーへ含めることと、各読み手で同じ場を参照することを達成条件にする。

## 最初に実施する範囲の提案

地表タイル計画を完了し、案Bの **P0→S0→C1→C2→C3→C4** を最初のまとまりとする。
これで「既存の影を使う」「時刻で動く」という土台を確認し、共有地表入力を使って環境条件による雲種、雲頂高度、かなとこの凸部という不足へ進める。
C3の局所場で海上層積雲や小粒の雲を表せるようにし、次のC5でも同じ共有地表入力と局所場を使って島の雲列を成立させてから、C6以降を順に進める。
