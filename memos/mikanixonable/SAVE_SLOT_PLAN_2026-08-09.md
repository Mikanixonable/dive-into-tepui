# セーブデータ二階層化(セーブデータ / スナップショット)実装計画

対象: `src/game/save-manager.ts` / `save-data.ts` / `unlock-manager.ts` / `main.ts` /
`launch-select.ts` / `hud/settings-panel.ts` / `input/key-mapping.ts`。

現状は「1スロット・1件・`tepui.save` 固定キー・F5/F9 と設定メニューの手動セーブのみ」。
要件は「歴史線(セーブデータ)を複数持ち、その中に自動/手動のスナップショットが並ぶ」二階層。

---

## 1. 用語と階層

| 層 | 呼称 | 実体 | 個数 |
|---|---|---|---|
| 上 | **セーブデータ(歴史線)** `SaveSlot` | メタ情報 + 進行状況 + スナップショット集合 | ユーザーが任意に作成 |
| 中 | **ステージ履歴** `StageHistory` | ステージモード時のみ。ステージ ID ごとのスナップショット集合 + クリア記録 | スロット内にステージ数だけ |
| 下 | **スナップショット** `Snapshot` | 今の `GameSaveData` そのもの + 表示用メタ | 自動 N 件 + 手動 M 件 |

クリエイティブモードのスロットは `StageHistory` を1つだけ持つ(`stageId: 'creative'`)。
つまり **スナップショット集合の所有者は常に `StageHistory`** で、モードによって
その数が 1 か複数かが変わるだけ。ここを揃えておくと、ロード UI もセーブ経路も分岐しない。

---

## 2. データ構造

`save-data.ts` は型定義のみという既存の役割を維持し、以下を追加する。

```ts
export type SnapshotKind = 'auto' | 'manual' | 'checkpoint';

// kind(由来)と pinned(保持ポリシー)は別の軸で、混ぜてはいけない。
// クリップは「自動で撮られた 1 件を永続化する」操作であって、由来を書き換える操作ではない
// — `kind: 'auto'` のまま `pinned: true` になる。由来を manual に塗り替えると
// 「どのトリガで撮られたか」という情報が失われ、剪定の優先度(§6-3c)も判定できなくなる。
// 語彙は hud/property-window.ts の 📌 クリップと揃える(同じ意味・同じ記号)。

// 一覧 UI が本体を読まずに描ける情報だけを持つ。ここに入る値は
// すべて GameSaveData から導出可能で、二重の正本ではなく「索引」。
export interface SnapshotMeta {
  id: string;              // 生成時に一意な文字列(スロット複製で衝突しないこと。§11-4)
  kind: SnapshotKind;      // 由来: どう撮られたか
  pinned: boolean;         // 保持: 自動剪定の対象外か(= クリップ済み)
  name: string;            // 手動命名 / 自動生成(§6)
  createdAtReal: number;   // Date.now()
  simTime: number;         // MET
  // 位置サマリ
  centerBodyId: AttractorId;
  altitude: number;
  speed: number;
  // ステータスサマリ
  hpRatio: number;
  maxHp: number;
  magazines: number;
  money: number;
  playerCount: number;
  enemyAliveCount: number;
  phase: GamePhase;
}

export interface StageHistoryMeta {
  stageId: string;
  clearCount: number;
  lastPlayedAtReal: number;
  snapshots: SnapshotMeta[];   // 新しい順
}

export interface SaveSlotMeta {
  id: string;
  name: string;
  mode: GameMode;              // 'stage' | 'creative'
  createdAtReal: number;
  lastPlayedAtReal: number;
  lastStageId: string;         // 「続きから」で開くステージ
  stages: StageHistoryMeta[];
}

export interface SaveIndex {
  version: number;
  slots: SaveSlotMeta[];
  activeSlotId: string | null;
}
```

`GameSaveData` は**変更しない**(スナップショット本体としてそのまま使う)。
ただし `stageId` は既にあるので、本体側に slot 情報は持たせない —
どのスロットに属するかは索引の側の事実であり、本体に書くと二重管理になる。

### 永続化レイアウト

```
tepui.saveIndex                      → SaveIndex(全スロットのメタ)
tepui.snapshot.<snapshotId>          → GameSaveData(本体, JSON)
```

索引と本体を分けるのは、選択 UI が **全スナップショットの本体を読まずに**
一覧を描けるようにするため(本体は艦・敵・基地・部品を含み数十 KB になる)。

### 容量

localStorage は 5MB 前後。1 スナップショット ≒ 20–60KB(敵数依存)とすると
80–250 件で溢れる。以下で対処する:

**保持は `pinned` の一軸で決まる。**

- `pinned: false` の自動スナップショットは、ステージ履歴ごとに **既定 12 件**の
  リングバッファ。溢れたら §6-3c のトリガ優先度で捨て、同優先度なら古い順。
  (当初 5 件としていたが、§6-3c の Tier 1 トリガは 1 プレイで数十件出るので足りない)
- `pinned: true` は**剪定対象外**。件数上限は **30 件/ステージ履歴**とし、
  超過時は新規クリップを拒否して「先に何か外してください」と促す
  — 勝手に消さない。クリップとは「これは消さない」という宣言だから。
- 書き込み時に `QuotaExceededError` を捕捉し、**未クリップの自動スナップショットを
  古い順に**退避して再試行 → それでも失敗したら明示的に失敗を報告する
  (現状の「失敗しても成功表示」は `SAVE_FIX_PLAN` A-3 で既知)。
- 将来の逃げ道として `SaveStore` を差し替え可能なインターフェースにしておき、
  IndexedDB 実装へ移せる形にする(今回は localStorage 実装のみ)。

## 3. モジュール構成(責務)

現 `SaveManager`(静的メソッド 2 つ)は 3 つの責務を負い切れないので分割する。

- `src/game/save/save-store.ts` — **永続化のみ**。`SaveStore` インターフェース
  (`readIndex`/`writeIndex`/`readSnapshot`/`writeSnapshot`/`deleteSnapshot`)と
  その localStorage 実装。`Game` を知らない。JSON 以外の知識も持たない。
- `src/game/save/save-slots.ts` — **索引の操作**。`SaveSlots` クラスが `SaveIndex` を抱え、
  スロット作成/削除/リネーム/アクティブ切替、ステージ履歴の取得、スナップショット
  メタの追加とリングバッファ剪定(本体の削除は `SaveStore` へ委譲)を行う。ここも `Game` を知らない。
- `src/game/save/snapshot-service.ts` — **`Game` ↔ `GameSaveData` の橋**。
  `capture(game, kind, name?)` が本体を作り `SnapshotMeta` を導出して `SaveSlots`/`SaveStore` に渡し、
  `restore(game, snapshotId)` がその逆を行う。現 `SaveManager.save/load` の中身はここへ移る。
  `SnapshotMeta` の導出は `hud/orbit-info.ts` の `orbitInfo` を使う(中心天体・高度・速度を
  再実装しない)。
- `src/game/save/autosave.ts` — **いつ自動セーブするか**だけを持つ(§4)。

`SaveManager` は削除し、旧名は残さない(CLAUDE.md「改名は痕跡を残さない」)。
`Game` はこれらを所有せず、`main.ts` が `SaveSlots`/`SnapshotService` を作って
`Game` と `SettingsPanel`・`launch-select` に参照で渡す(`UnlockManager` と同じ形)。

## 4. 自動セーブ / 自動ロード

**自動ロード**: 起動時、`activeSlotId` のスロットの `lastStageId` の履歴の
最新スナップショット(自動・手動問わず)を読む。タイトル画面の「つづきから」が既定選択。
URL に `?stage=` / `?mode=` がある場合は従来どおり選択画面を飛ばすが、
その場合も**そのスロット内の該当ステージ履歴**に接続する(スロット指定は `?slot=` を追加)。

**自動セーブ**(`autosave.ts`)。実時間の一定間隔ではなく、**節目**で撮る。
理由: 軌道ゲームは時間加速で数日進むので実時間間隔は意味が薄く、
やり直したくなるのは常に「何かが起きた直後」だから。

自動スナップショットは **2 系統**あり、どちらも `pinned: false` で積まれ、
どちらも同じリングバッファ(§2、既定 12 件)を共有する。

- **直前枠** — 「今」に最も近い 1 件を常に持つ。永続化のタイミングは
  一時停止時・ビュー遷移時・`AUTOSAVE_MIN_INTERVAL_REAL_SEC`(既定 60 実秒)経過時。
  やり直しの最短経路(`Shift+F9`)が指す先。
- **重要イベント枠** — §6-3c のトリガ。撮る時点は**イベントの検出時ではなく、
  その原因より前**(§6-3b(a) のロールバックバッファから遡って選ぶ)。

トリガ一覧と優先度は §6-3c、PNR 検出は §6-3b に一本化する(ここには重複して書かない)。
連続発火の抑制は `AUTOSAVE_MIN_INTERVAL_REAL_SEC` だが、**優先度が上のトリガはこれを無視する**
(§6-3c)。

ステージ決着時も 1 件撮るが、これは記録用で戻り先にはならない(§6-3)。
現状 `Game.update` は決着後に早期 return するため、**ロード時は結果画面を再生せず**、
その前の自動スナップショットへ誘導する UI にする
(現行の「決着後は F5 を拒否」という制約をそのまま活かす)。

一時停止(設定メニュー)中は新規に撮らない。時間加速中も撮らない
(重要イベント枠は節目トリガなので自然に満たされ、直前枠はワープ完了時に撮られる)。

## 5. UI

### 5-1. スロット選択(タイトル画面)

`launch-select.ts` にタブを 1 枚追加するのではなく、**タイトル → スロット選択 → モード/ステージ選択**
の順に変える。スロット選択は:

- 行 = スロット。`name` / モード / 最終プレイ日時 / 進行(ステージモードなら「クリア 3/5」、
  クリエイティブなら「艦 4・基地 1」)/ 最新スナップショットの MET。
- 「つづきから」(最新へ即ロード)/「スナップショットを選ぶ」/ リネーム / 複製 / 削除。
- 「新しいセーブデータ」= 新規スロット作成 → 初期化されたゲームへ。

### 5-2. スナップショットブラウザ

`src/game/hud/save-browser.ts` に `SaveBrowser` を新設(全画面ビュー、`DockView` と同じ
`ViewManager` 管轄ではなく **`SettingsPanel` と同じシステム窓帯**に置く。`dom.ts` の
z-index 帯は 40 の `[Esc]` メニューと同帯とし、`dom.ts` の STYLE に帯を明記する)。

**`[Esc]` メニューからの遷移が正規の入口**(`SettingsPanel` に「スナップショット」項目を足し、
`SaveBrowser.open()` を呼ぶ。`SettingsPanel` は開いた時点でゲームを一時停止しているので、
ブラウザを開くために追加の停止処理は要らない)。

- 左: ステージ履歴タブ(ステージモード時のみ複数)。
- 右: スナップショット一覧(新しい順)。カードに `SnapshotMeta` の全項目を出す:
  MET(`fmtTime`)・実時刻(`fmtDateTime`)・中心天体名(`ATTRACTOR_NAMES`)・高度(`fmtDist`)・
  速度(`fmtSpeed`)・HP バー・弾倉数・所持金・敵残数、`kind` バッジ(自動/手動/決着)、
  危険度注記(§6-3b(c))。
- **📌 クリップボタン**をカードごとに置く(`hud/property-window.ts` の 📌 と同じ記号・同じ意味
  — 「自動で消えないようにする」)。押すと `pinned` が立ち、そのカードは
  「自動」区画から「クリップ済み」区画へ移る。**一覧は `pinned` で 2 区画に分ける**:
  上に「クリップ済み(N/30)」、下に「自動(N/12・古い順に消えます)」。
  区画を分けるのは、下の区画のものは放っておくと消えるという事実を、
  操作する前に見えるようにするため。
- クリップ時に命名ダイアログを出す(空欄なら自動生成名、§6-1)。
  要件の「手動セーブ = 明示的にスナップショットを撮り、命名もできる」はこの操作が担う。
- 操作: ロード / クリップ・解除 / 命名変更 / 削除 / 「ここから分岐して新しいセーブデータを作る」(§6-2)。
  クリップ解除は即削除ではなく、自動区画の末尾へ戻す(次の剪定で消える)。
- 一覧は 1 フレームごとに再構築しない一発モーダル(`DockView` と同じ扱い)。

### 5-3. キー・メニュー

- `[Esc]` → 「スナップショット」 = ブラウザを開く(**正規の入口**)。
- `F5` = **今この瞬間をクリップする**(`pinned: true` で 1 件撮り、命名ダイアログを出す)。
  ブラウザを開かずに「ここは残したい」と宣言できる最短経路。
- `F9` = ブラウザを開く(`[Esc]` 経由のショートカット)。
- `Shift+F9` = 直前枠へ即ロード(やり直しの最短経路)。
- 設定メニューの現「セーブ/ロード」ボタンはこれらに置き換える。

## 6. 要件への追加提案

### 6-1. スナップショット名の自動生成
命名を必須にすると撮る回数が減る。空欄時は `MET 3d04h ・ 月周回 高度 120km` のように
`SnapshotMeta` から組み立てた名前を入れる。命名は「意味づけしたい時だけ」で済む。

### 6-2. スナップショットからの分岐(歴史線の複製)
「少し前に戻ってやり直す」を**上書き**にすると、戻る前の未来が消える。
スナップショットブラウザから「ここから分岐」でスロットを複製し(そのスナップショット
以前だけを引き継ぐ)、元の歴史線を残せるようにする。要件の「歴史線」という語と素直に噛み合う。

### 6-3. 決着時スナップショット
`Stage.recordPlayerLost` / 決着の直前に `Game` が 1 件撮る(喪失判定の所有者を増やさない)。
ただしこれは**やり直し用ではなく記録用** — 戻り先としては役に立たないので(§6-3b)、
`SaveBrowser` では「決着」バッジを付けて既定の戻り先候補から外す。

### 6-3b. 「引き返し不能点」より前へ戻す(§4 トリガ4 の置き換え)

**喪失の直前スナップショットは役に立たない。** 軌道ゲームでは喪失が*確定する*瞬間と、
喪失が*避けられなくなった*瞬間が数周回ぶんずれる — 近地点が大気圏に沈んだ時点で
数十分後の再突入はもう決まっており、燃料を使い切った時点でその軌道から出る手段は無い。
撃破も同様で、会敵して相対速度を殺した時点で離脱不能になっている。
直前に戻しても、詰んだ状態から詰みをやり直すだけになる。

必要なのは **「引き返し不能点(point of no return, PNR)より前」へ戻すこと**。
これは実装上、2つの独立した仕組みに分解できる。

#### (a) 事後に過去の一点を確定させる — メモリ内リングバッファ

セーブの契機(いつ撮るか)と、保存する時点(いつの状態を残すか)を分離する。
`AutoSave` が **`GameSaveData` をメモリ上のリングバッファに継続的に積み**、
節目や PNR 検出のタイミングで**そのバッファから過去の1件を選んで永続化する**。
スポーツ中継のインスタントリプレイと同じ構造で、「原因より前」を、原因が判明した後から
選べるのはこの形しかない。

- 積む間隔は実時間ではなく **`localOrbitPeriod` の一定割合**(既定 1/8 周期)。
  ただし時間加速 ×131072 では毎フレームになるので、実時間 2 秒の下限を併置する。
- 保持は既定 16 件(= 約 2 周回ぶん)。`GameSaveData` は 20–60KB なので
  メモリ上で 1MB 程度、永続化しない限り容量制限に触れない。
- 永続化するのは選ばれた 1 件だけ。リングバッファ自体はセーブしない。

#### (b) PNR をいつ検出するか

**既存の計算をそのまま読むだけで済むものが多い** — 新しい物理は要らない。

| 詰みの種類 | 既存の判定材料 | 実装 |
|---|---|---|
| 再突入 | `GameEntity` の `truncated`(予測積分が `hitCelestialBody` に達すると立つ) | `private truncated` に getter を足して読む。自機の予測が初めて truncate した瞬間が再突入 PNR |
| 燃料切れ | `Ship.totalFuel` と、近地点を大気圏上へ上げるのに要る Δv | `orbitalElementsOf` から必要 Δv を出し、`totalFuel` から出せる Δv を下回った瞬間 |
| 熱暴走 | `ThermalSystem.hullTemp` の上昇率とラジエーター残存 | 冷却能力 < 入熱が定常化した瞬間 |
| 撃破 | 相対距離・相対速度が敵の射程内で単調減少 | 優先度低(§下記) |

自機が生きているうちに (b) が立ったら、リングバッファから
**「その PNR の推定発生時刻より前の最も新しい件」**を永続化し、
`SnapshotKind` を `'checkpoint'`、名前を「再突入回避可能な最後の時点」等にする。
推定発生時刻は、再突入なら「予測が truncate した時点」ではなく
**「近地点高度が大気圏を割った時点」** — これは `apsisAltitudes` を毎フレーム見て
符号が変わった瞬間として拾える(そしてその時刻より前の件を選べばよい)。

撃破(戦闘)の PNR は判定が曖昧で、上の3つのように「物理的に不可逆」と言い切れない
(残 HP と腕次第で覆る)。よって**戦闘は PNR 検出の対象にせず**、代わりに
「敵グループの検知/会敵の直前」を §4 の節目トリガとして扱う。詰み判定を無理に作るより、
戦闘に入る前の状態が常に1件ある方が確実で、実装も軽い。

#### (c) UI 側の担保

検出漏れは必ず出るので、最終的な保険は「戻り先を選べること」。
`SaveBrowser` のスナップショット一覧に、各件について
**その時点から見た危険度**を注記する:

- 予測軌道が再突入する → 「再突入まで T+1h20m」(赤)
- 燃料で近地点を大気圏上へ戻せない → 「回復不能」(赤)
- どちらでもない → 注記なし

これは `SnapshotMeta` に `recoverable: boolean` と `dangerNote: string | null` を
持たせて撮影時に確定させる(ロード時に再計算しない — 一覧のために全件を
再積分することになるため)。詰んだ時点のスナップショットを**選ばせない**のではなく、
**見えるようにして避けさせる**。プレイヤーの判断を奪わない方がこのゲームには合う。

#### (d) 採らない案: 決定的リプレイによる巻き戻し

入力列とシードだけ保存して任意時点へ巻き戻す方式は、状態量が桁違いに小さく魅力的だが、
このゲームでは成立しない。`dt` が実フレームレート由来で、RK4 の分割数が
`ceil(simDt / SUBSTEP_MAX_DT)` とフレーム毎に変わり、浮動小数の累積差が
軌道スケールでは数キロメートルに増幅する。再生が元と一致しない。

**優先度**: (a) と (b) の再突入・燃料切れは Phase 3 に含める(自動セーブの本体はここ)。
(c) は Phase 3 の後半、撃破 PNR は実装しない。

### 6-3c. 撮るべき時点の一覧

#### 統一原理: 「危険の直前」ではなく「選択肢が最も多い瞬間」

戻り先として価値があるのは、**そこから選べる未来がいちばん広い状態**であって、
危険に近い状態ではない。燃料が満タンで、軌道がまだ自由で、時間の余裕がある時点。
以下の候補はすべてこの基準で選んでいる。

#### 「直前」を予測する必要はない

§6-3b(a) のリングバッファがあるので、トリガは **「X が起きたことを検出する」** だけでよく、
「X が起きそうだと予測する」必要はない。起きた時点で、バッファから X より前の件を選べばよい。
これは実装量を大きく減らす — 予測が要るのは PNR の3種(§6-3b(b))だけになる。

#### 候補(優先度順)

**Tier 1 — 実装する。不可逆かつ検出が容易**

| 時点 | なぜ | 検出 |
|---|---|---|
| ステージ開始 / スロット作成 | 「最初から」の保証 | `Stage.init` 直後 |
| マニューバノード実行 | 燃料と軌道が同時に不可逆に変わる。計画のやり直しはここへ戻るしかない | `PlanGuide` の達成通知。バッファから `node.t - NODE_APPROACH_LEAD` より前を選ぶ |
| ドック出航 | **選択肢が最大の瞬間** — 補給・修理・部品交換が済んでいる。最も価値の高い戻り先 | `Docking` の出航処理 |
| ドッキング捕獲 | ランデブーのやり直し。捕獲後に戻っても意味がないので、接近開始まで遡る | `Docking.checkProximity` の捕獲成立時 → バッファから相対距離が縮み始めた時点へ |
| 敵との会敵 | 戦闘は PNR 判定を作らない(§6-3b)代わりに、入る前を必ず1件持つ | 生存敵との最小距離が `ENEMY_ENGAGE_DIST` を初めて割った時 → バッファから割る前へ |
| 影響圏の遷移 | `strongestAttractor` が変わる = 軌道設計上の最大の分岐。地球↔月の遷移をやり直せる | `strongestAttractor(player.state.r, attractors).id` の変化 |
| 長時間ワープの完了 | 数日飛ばした後に事故ると、戻り先が「数日前」しか無くなる | `SimSpeedManager` の auto-warp 終了時、および累積ワープ時間が閾値を超えた時 |

**Tier 2 — 実装してよい。価値はあるが Tier 1 と重複しがち**

| 時点 | なぜ |
|---|---|
| 弾薬ピックアップ取得 | 補給後は選択肢が広がる。ただしドック出航と性質が重複 |
| 部品交換・購入の確定 | 所持金の不可逆な消費。ただし直後にドック出航トリガが来るので実質不要 |
| 大気圏かすめ(エアロブレーキ)の突入前 | 近地点が `REENTRY_ALT` 近傍を初めて通過する時。PNR(再突入)と紙一重だが、意図的な操作でもある |
| ラグランジュ点・ハロー軌道投入 | クリエイティブ向け。到達自体が目的になりやすい |
| HP が段階(75/50/25%)を初めて割った | 「まだ戦えたはずの時点」への戻り先。ただし会敵前トリガがあれば大半は不要 |

**Tier 3 — 実装しない**

- 実時間の一定間隔 — 時間加速があるので意味を持たない。`AUTOSAVE_MIN_INTERVAL_REAL_SEC` の
  下限としてだけ機能させ、単独のトリガにはしない。
- 周回ごと(近地点通過ごと)— LEO では 90 分ごと = 高倍速で数秒ごとになり、一覧が埋まる。
  リングバッファが実質これを担うので、永続化する必要はない。
- 被弾ごと / 撃墜ごと — 頻度が高すぎて一覧が使えなくなる。

#### 一覧が埋まらないようにする

Tier 1 だけでも 1 プレイで数十件出る。自動スナップショットのリングバッファ(§2、既定 5 件)
に対して**トリガに優先度を持たせ、剪定時は低優先度から捨てる**:

```
ドック出航 > 影響圏遷移 > 会敵前 > ノード実行前 > ワープ完了 > その他
```

同じ優先度なら古い方から捨てる。加えて `AUTOSAVE_MIN_INTERVAL_REAL_SEC`(既定 60 実秒)
で連続発火を抑える — ただし**優先度が上のトリガはこの下限を無視する**
(ドック出航の直後に影響圏遷移が来るのは正常な流れであって、抑制すべきではない)。

### 6-4. サムネイル
`WebGPURenderer` のフレームを縮小して data URL 化し `SnapshotMeta` に載せると
一覧の識別が一気に楽になる。ただし容量に直撃するので **96×54 JPEG 品質 0.5 程度**に抑え、
容量逼迫時に最初に捨てる対象とする。優先度は低(Phase 5)。

### 6-5. エクスポート / インポート
スロット単位で JSON をファイル保存/読込。localStorage が消える環境(シークレット窓・
ブラウザ設定)への保険で、実装コストは小さい。

### 6-6. クリア記録の所在
現状 `UnlockManager` の `clearCounts` は `tepui.clearCounts` にグローバル保存されている。
要件の「ステージモードのセーブデータは攻略したステージの記録を持つ」に従い、
**クリア回数はスロット内(`StageHistoryMeta.clearCount`)へ移す**。`UnlockManager` は
localStorage を直接触るのをやめ、アクティブスロットの `SaveSlots` を参照する
(`isUnlocked` が純粋述語であるという現在の構造はそのまま)。
既存の `tepui.clearCounts` は初回起動時に「既定スロット」へ移送して削除する(§8)。

## 11. レビュー所見(クリップ要件の追加を受けての見直し)

### 11-1. リングバッファが 2 つあり、混同しやすい【修正済み】

別物が同じ語で呼ばれていた。名前を分けて区別する:

| | 実体 | 場所 | 既定 | 役割 |
|---|---|---|---|---|
| **ロールバックバッファ** | `GameSaveData` | メモリのみ | 16 件 | 「原因より前」を事後に選ぶため(§6-3b(a))。永続化しない |
| **自動スナップショット枠** | 永続化された `pinned: false` の集合 | localStorage | 12 件 | 一覧に出る。古い順に消える |

前者から 1 件を選んで永続化した結果が後者に入る、という一方向の関係。
`autosave.ts` が前者を、`save-slots.ts` が後者を持つ。

### 11-2. 自動枠 5 件では足りなかった【修正済み】

§6-3c の Tier 1 トリガは 1 プレイで数十件出る。5 件だとドック出航のような
価値の高い件が数分で流れる。12 件へ引き上げ、剪定をトリガ優先度順にした。
それでも足りなければ、消えて困るものはクリップする — というのが要件の意図のはずで、
自動枠を無闇に増やすのは筋が悪い(一覧が読めなくなる)。

### 11-3. `kind` と `pinned` を 1 つの列挙で表さない【修正済み】

クリップを `kind: 'auto' → 'manual'` の書き換えとして実装すると、
「どのトリガで撮られたか」が失われて剪定の優先度判定ができなくなり、
一覧のバッジも由来ではなく保持状態を表すことになって意味がずれる。由来と保持は直交。

### 11-4. スナップショット id をスロット複製に耐える形にする【修正済み】

当初案の `${slotId}:${stageId}:${連番}` は、§6-2 の「ここから分岐」でスロットを複製した際、
複製元と複製先で連番が衝突する(本体は `tepui.snapshot.<id>` の 1 キーなので、
片方を消すともう片方が壊れる)。生成時に一意な id を振り、
どのスロットに属するかは索引側の事実に留める。

### 11-5. ロード後、未クリップの自動枠をどう扱うか【要決定】

スナップショット A へ戻ってプレイし直すと、A より後の未クリップ自動枠は
「もう起きなかった未来」になる。3 案:

- (a) そのまま残す — 一覧に矛盾した時系列が並ぶ。混乱する。
- (b) ロード時に A より後の未クリップ枠を破棄する — `Plan` のノード編集が
  下流ノードを捨てるのと同じ規則で、このコードベースの既存の考え方に一致する。**推奨。**
- (c) 常に分岐スロットを作る — 安全だがスロットが増えすぎる。

**(b) を採る。クリップ済みは破棄しない**(消さないという宣言なので)。
結果として、クリップ済みだけが分岐後も残り、一覧上は「別の歴史の記録」として並ぶ。
これが嫌なら §6-2 の明示的な分岐を使う、という二段構えにする。

### 11-6. `AUTOSAVE_MIN_INTERVAL_REAL_SEC` の記述が 2 箇所にあった【修正済み】

§4 と §6-3c で別々に書かれ、優先度による無視ルールが片方にしか無かった。
§6-3c を正とし、§4 は参照に留めた。

### 11-7. 残る未決事項

- クリップ済み 30 件の上限に達した時の UI(拒否のみで足りるか、
  「最も古いクリップを外して置き換える」を出すか)。
- `SaveBrowser` を `[Esc]` メニューと同じ z-index 帯に置くと、
  メニューの上に重ねるのか、メニューを閉じて置き換えるのかを決める必要がある。
  **後者(置き換え)を推す** — `DockView` と同じ「全画面ビュー」の扱いにすれば、
  戻り先が `SettingsPanel` 1 つに定まる。
- 直前枠の永続化タイミング(一時停止時・ビュー遷移時・60 実秒)が
  実プレイで多すぎないか。Phase 2 の実測で決める。

## 12. エクスポート / インポート / 削除 / 複製

localStorage は「ブラウザ設定を消すと消える」「別端末へ持っていけない」ので、
歴史線を財産として扱うならファイルへの出し入れは必須。§6-5 を要件へ格上げする。

### 12-1. 単位はスロット(歴史線)

出し入れの単位は**スロット1件**とする。スナップショット単体のエクスポートは提供しない —
単体では属する歴史線が分からず、インポート先で宙に浮くため。
スロットには索引メタと、そのスロットが参照する全スナップショット本体を同梱する。

```ts
export interface SlotExport {
  format: 'tepui.slot';      // 別 JSON を読ませない識別子
  formatVersion: number;
  exportedAtReal: number;
  slot: SaveSlotMeta;
  snapshots: Record<string, GameSaveData>;  // id → 本体
}
```

`format` を持つのは、無関係な JSON を読ませたときに「壊れたセーブ」ではなく
「これはセーブファイルではない」と言えるようにするため。

### 12-2. エクスポート

`Blob` + `URL.createObjectURL` + `<a download>` でファイル保存。
ファイル名は `tepui-<スロット名を安全化>-<yyyymmdd-hhmmss>.json`。
巨大化するのでクリップ済みだけを含める選択肢を出す(既定は全件)。

### 12-3. インポート

`<input type="file">` で読み、以下を順に検証して、1つでも落ちたら**何も書き込まずに**中止する:

1. `format === 'tepui.slot'` か
2. `formatVersion` が読める範囲か
3. `slot.stages[].snapshots[].id` がすべて `snapshots` に存在するか(参照の完全性)
4. 各 `GameSaveData.version` が現行と一致するか(一致しない件だけ落とす)

**インポートは常に新しいスロットとして追加する**(既存の上書きはしない)。
id は振り直す — 元の id をそのまま使うと、同じファイルを2回読んだ時や、
エクスポート元の端末へ戻した時に既存スロットを破壊する。
名前が衝突したら `(2)` を付ける。

### 12-4. 削除

- **スナップショット削除** — 索引からメタを外し、本体キーも消す(孤児を残さない)。
  クリップ済みも削除できる(クリップは自動剪定の対象外という意味であって、
  手動削除まで拒む意味ではない)。
- **スロット削除** — そのスロットが参照する全スナップショット本体を消してから索引から外す。
  確認ダイアログでスロット名を表示する。アクティブスロットを消した場合は
  `activeSlotId` を `null` にし、次回起動でスロット選択へ落ちる。
- 起動時に**孤児掃除**を1回だけ走らせる — `tepui.snapshot.` で始まるキーのうち、
  索引のどこからも参照されていないものを消す。書き込み途中の中断で必ず出るため。

### 12-5. 複製

- **スロット複製** — 全スナップショット本体をコピーし、id を振り直して新スロットにする。
  名前は `<元の名前> のコピー`。§6-2 の「ここから分岐」は**この複製に、
  基準スナップショットより後の件を落とす処理を足したもの**として実装する
  (2つの別実装を作らない)。
- **スナップショット複製は提供しない** — 同じ状態が2件並ぶ意味がなく、
  「名前を変えて残したい」ならクリップ + 命名で足りる。

### 12-6. モジュール

エクスポート/インポートは `src/game/save/save-transfer.ts` に置く。
`SaveSlots`(索引の操作)にも `SaveStore`(永続化)にも属さない — ファイル I/O と
外部フォーマットの検証という別の責務で、この2つが `File`/`Blob`/`<a download>` を
知る必要はない。削除・複製は索引と本体の両方を触る操作なので `SaveSlots` が持つ
(本体の削除は `SaveStore` へ委譲、という既存の分担のまま)。
