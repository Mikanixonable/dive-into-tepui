# 軌道ガイド拡張 要件定義・実装計画(2026-08-25・実装完了)

**本文書は当時の設計判断の記録であり、現状の実装を保証しない。** 確定した仕様は
`DEVELOP/SPEC/MAP.md` の 5.2 / 5.3 節が正本で、コードの現状はコードだけが語る。

マップの軌道ガイドを、CR3BP の周期軌道ファミリー全体を科学的に正しく描けるところまで広げた。
あわせて表示の自由度(本数・族範囲・色・グラデーション・進行方向・安定度)を与え、
ガイドタブへゼロ速度曲線を追加した。

## 実装後の記録

- 焼き込みは JPL 周期軌道 API から取得した初期条件を種に、各系の質量比で1周期積分して作る。
  主要2系(地球-月・太陽-地球)をバンドルへ埋め、残る5系は系ごとの別ファイルへ分けて遅延ロードする。
- 実装中に判明して計画から外れたもの:
  - **spatial DRO は対象外**(JPL の `dro` は平面のみで面外メンバーを含まない)。
  - **UI はフェーズを分けず最終形で一度に作った**。3回作り直す非効率を避けるため。
  - **`s=0` は必ず族の中で最も小さい軌道**に揃えた(JPL が返す向きは族によって違う)。
  - 焼き込みの約5%(7,290 中 371)は、副天体へ深く近接して固定刻み積分が閉じないため除外した。
- 検証: `npm run typecheck` / `npm run test:physics`(620件)/ `npm run build` / `npm run smoke:browser`、
  および実機での目視(平面リヤプノフ族が小振幅から涙滴形へ連続に変化し、ゼロ速度曲線が
  C の値に応じてネックを開閉すること)。

## 2. 調査で確定した事実

### 2.1 軌道ファミリーの全体像

出典: NASA/TP-20220014814 *Astrodynamics Convention and Modeling Reference for Lunar, Cislunar,
and Libration Point Orbits* 6.11節、および JPL 周期軌道カタログ。

| 群 | ファミリー | 中心 | 対称性 | 備考 |
| --- | --- | --- | --- | --- |
| 共線点 | 平面リヤプノフ | L1/L2/L3 | xz面 | 振幅増大で涙滴形→副天体へ衝突して終端 |
| 共線点 | 垂直リヤプノフ | L1/L2/L3 | xz面 | 8の字。族末端では主天体を包む大きな軌道へ |
| 共線点 | ハロー(北/南) | L1/L2/L3 | xz面 | 平面リヤプノフからの分岐。末端が NRHO |
| 共線点 | axial | L1/L2/L3 | x軸 | 平面リヤプノフと垂直リヤプノフを結ぶ閉じた族 |
| 共線点 | butterfly(北/南) | L2 | xz面 | ハローからの周期倍化分岐 |
| 共線点 | dragonfly(北/南) | L2 | xz面 | JPL カタログにあり |
| 三角点 | short period | L4/L5 | — | 平衡点の2つの振動モードのうち短周期側 |
| 三角点 | long period | L4/L5 | — | 同じく長周期側 |
| 三角点 | vertical | L4/L5 | — | 面外の8の字 |
| 三角点 | axial | L4/L5 | — | vertical と L1 ハローに接続する閉じた族 |
| 副天体周回 | DRO | 副天体 | x軸 | 逆行。大きくなると主天体へ近接 |
| 副天体周回 | DPO | 副天体 | x軸 | 順行 |
| 副天体周回 | LPO(E/W) | 副天体 | x軸 | 低高度順行。族末端は L1 近傍 |
| 副天体周回 | spatial DRO | 副天体 | — | 平面 DRO からの面外分岐。**JPL では取得できないため今回の対象外**(9.1) |
| 共鳴 | p:q 共鳴 | 系全体 | 場合による | 1:2 / 2:1 / 3:1 / 2:3 / 4:3 / 3:4 |

L4 と L5 の軌道は y 軸反転で互いに移り合う(同文献 6.11.2)。

**この表のうち文献で裏が取れていない項目**(推測で埋めていない、という記録):

- 各族の存在範囲(ヤコビ定数・周期の上限下限)の数値。NASA/TP-20220014814 は族ごとに代表1点の
  値しか載せていない。**族の範囲は JPL API が返すメンバーの実際の値域から決める**
- 平面リヤプノフ族が振幅増大でどこで終わるかの判定条件・臨界値。文献は「主天体への近接通過に
  至る」という定性的記述のみ。**焼き込み時に、近点が副天体の半径を下回った点で打ち切る**
  (現在の実装が既に採っている判定を踏襲する)
- axial 軌道の対称性の明示的な定式化。一般理論からは x 軸対称と読めるが、文献に明記がない。
  **JPL から初期条件を取る方式(3.2)ではこの定式化が不要になる**ため、実害はない

### 2.2 初期条件の入手先

**JPL Three-Body Periodic Orbits API** が上表のすべてを機械可読で配信している。

- エンドポイント: `https://ssd-api.jpl.nasa.gov/periodic_orbits.api`
- `family`: `halo` `vertical` `axial` `lyapunov` `longp` `short` `butterfly` `dragonfly`
  `resonant` `dro` `dpo` `lpo` の12種
- `libr`(1〜5)、`branch`(halo/butterfly/dragonfly は `N`/`S`、lpo は `E`/`W`、resonant は共鳴比)
- 各メンバーが初期状態 `x,y,z,vx,vy,vz` と `period` `jacobi` `stability` を持つ
- ドキュメント: https://ssd-api.jpl.nasa.gov/doc/periodic_orbits.html

自前で分岐追跡(モノドロミー固有値が +1 を通過する点の検出と固有ベクトルからの乗り換え)、
擬弧長継続(折り返し点の通過)、対称性を持たない族のための多重シューティングを実装するのに比べ、
桁違いに小さい労力で全ファミリーが揃う。**焼き込み生成時に一度取得し、結果をリポジトリへ
コミットする**ので、通常の開発・実行時に外部依存は残らない。

### 2.3 質量比の不一致(重要)

| 系 | このリポジトリの値 | JPL の値 | 相対差 |
| --- | --- | --- | --- |
| 地球-月 | 0.0121556504 | 0.0121505856 | 4.2×10⁻⁴ |

レジストリの重力定数から導く μ と JPL の μ は一致しない。**JPL の初期条件をそのまま我々の
積分器へ入れても軌道は閉じない。** 取得した初期条件は「種」として扱い、我々の μ で微分修正を
かけ直してから焼き込む。

### 2.4 ゼロ速度面

- 擬ポテンシャル Ω = (x²+y²)/2 + (1−μ)/r₁ + μ/r₂、ヤコビ定数 C = 2Ω − v²(この流儀で統一する)
- v² = 2Ω − C なので **2Ω ≥ C の領域が到達可能、2Ω < C が禁止領域**
- ゼロ速度曲線は Ω = C/2 の等高線そのもの。ポテンシャル等高線とゼロ速度曲線は同じものを
  別の切り口で呼んでいるにすぎない
- C を下げるにつれ L1 → L2 → L3 → L4/L5 の順にネックが開く
- C(L4) = C(L5) = 3 − μ + μ²(閉じた式)。L1〜L3 は五次方程式を解いてから Ω に代入する
- 断面上の格子で f = 2Ω − C を評価し、マーチングスクエア法で f = 0 を追うのが定石。
  両天体の位置で Ω が発散するので、その近傍を除外するマスクが要る
- 臨界値の近くではネックが極端に細くなるため、格子が粗いと開いている穴が閉じて見える

### 2.5 コードベースの制約

| 事項 | 現状 | 拡張に要ること |
| --- | --- | --- |
| 線の色 | `Curve` は単色マテリアルのみ。`CurveSampler` は位置しか返さない | 頂点カラー化(`color` 属性の追加とサンプラーの型変更)。`protein-ribbon.ts` に `vertexColors` の前例あり |
| 面の描画 | 動的メッシュの前例は `ring.ts`(半透明の環)・`protein-ribbon.ts` | ゼロ速度曲線は「線」で描けば `Curve` を流用でき、島ごとに1本ずつ割り当てる |
| 三角形マーカー | `InstancedPool` が使える(向きは行列、色は個別指定可) | 画面上で一定サイズに保つ計算は呼び出し側の責務。`curve.ts` の `scaleAtLocal` が参考 |
| カラーピッカー | 存在しない | `ValueInput` に `'color'` 型を足すのが規約に沿う。プリセットなら `SegmentedControl` |
| パネルのスクロール | 左レールが `overflow-y: auto` を既に持つ | レールのスクロールに任せる。パネル個別の `max-height` は不要 |
| 入れ子タブ | 前例なし | 設計判断が要る(下記 4.1) |
| 焼き込みデータ | `lagrange-orbits.json` 2.94MB を静的 import でバンドルへ埋め込み | 全網羅すると素朴な JSON で 14MB 規模。圧縮が必須(下記 3.4) |
| モノドロミー行列 | `cr3bp.ts` に無い(半周期の STM までしか持たない) | **新設しない。** JPL が配信する `stability` を焼き込み表へ併記する(3.2 で JPL の μ のまま焼くと決めたので、その値がそのまま使える) |

### 2.6 JPL API の実測値

`sys` は `earth-moon` `sun-earth` `sun-mars` `jupiter-europa` `saturn-titan` `saturn-enceladus`
`mars-phobos` の7系。**このゲームが扱う2系はどちらも使える。**

- 有効な組み合わせ(実測): `halo` は libr(1〜3)と branch(N/S)の両方が必須。`vertical` `axial` は
  libr 必須・branch 不可。`lyapunov` は libr(1〜3)必須。`longp` `short` は libr(4/5)必須。
  `butterfly` `dragonfly` は libr 指定不可・branch(N/S)必須。`dro` `dpo` はパラメータ不要。
  `lpo` は branch(E/W)必須。`resonant` は branch に**整数連結表記**(`12` が 1:2、`21` が 2:1。
  コロン表記は 400 になる)
- 初期条件は有効数字17桁の無次元量。`period` `jacobi` `stability` を併せ持ち、`stability` は単一値
- 同一クエリの結果は完全に再現する
- **データ量は膨大**: earth-moon 単独・37クエリで 220,798 件 / 47.9MB。2系ぶんではその倍近く
- レート制限・利用規約はドキュメントに明記がない

**実装前に検算が要る点(ドキュメントに定義が書かれていないもの):**

- `jacobi` が C = 2Ω − v² と C = Ω − v²/2 のどちらの流儀か。**文献によって factor 2 が違い、
  ラグランジュ点での値が全く別の数に見える。** 取得した初期条件から自前で Ω と v² を計算し、
  返ってきた `jacobi` と突き合わせて確定する
- `stability` が ν = (λ+1/λ)/2(安定の閾値 1)か k = |λ+1/λ|(閾値 2)か。JPL のドキュメントは
  「stability index ≤ 1 が安定」と書いており前者と読めるが、`limits.stability` の実際の値域を
  見て確かめる

取得したメンバーをそのまま全部焼くことはできない。**族に沿って等間隔に間引いた 20〜40 メンバー**
だけを使う(取得自体は生成時の一度きりなので、数十MBのダウンロードは許容する)。

## 3. 決定事項

### 3.1 全ファミリーを焼き込みに統一する

Richardson 三次近似を実行時に評価する経路を**廃止**し、すべてのファミリーを焼き込み表の補間で
描く。これで問題1(非物理的な平面リヤプノフ)が根本から消える。解析近似が残るのはリサジュー軌道
だけ(3.5)。

### 3.2 JPL の質量比のまま焼き、微分修正し直さない

2.3 のとおり μ が 4.2×10⁻⁴ 違う。**JPL の μ で積分した無次元形状をそのまま焼き込み、実行時に
その瞬間の実際の両天体の位置・距離・公転面へ写す。**

- 我々の μ で解き直す案も検討したが、対称性を持たない族(axial・共鳴軌道)には完全な周期性拘束を
  課す多重シューティングが要り、フェーズ1の範囲に対して重すぎる
- μ の差が形として現れるのは重心位置の 4.2×10⁻⁴ ぶん(地球-月系で約 160 km)で、
  月軌道のスケールでは視認できない
- ガイド線が近似であることは SPEC に既に書いてある

**後戻りは安い** — 焼き込みツールの中で微分修正を1段挟むだけなので、将来必要になれば足せる。

### 3.3 点列は弧長等間隔、各点に時刻の割合を併記する

進行方向マーカーを**実際の軌道速度に比例**して動かすため、点ごとに「周期に対する経過時刻の割合」
を持たせる。折れ線の見た目は弧長等間隔が良い(NRHO の近点で粗くならない)一方、マーカーは時刻で
進める必要があるため、両方を1つの表で賄う。

### 3.4 焼き込み形式は Float32 のバイナリ

現在の「小数5桁の JSON テキスト」から、**Float32 配列を base64 で埋めた形式**へ変える。
座標の精度は無次元で 10⁻⁷ 程度あれば足り、Float32(有効約7桁)で十分。

- 目標: **バンドルの増加を +2MB 以内**に収める(現在の `lagrange-orbits.json` 2.94MB を置き換える
  ので、新しい表が 4.9MB 以内なら満たす)
- 系ごとの組み合わせ数は 37(ハロー 3点×2枝、vertical 5点、axial 5点、lyapunov 3点、
  longp 2点、short 2点、butterfly 2枝、dragonfly 2枝、dro、dpo、lpo 2枝、共鳴 6比)。
  2系で 74 組
- 1メンバーあたり 96点 × 4値(x, y, z, 時刻割合)= 384 値 = 1,536 バイト
- 74組 × 30メンバー = 2,220 メンバー = 3.41MB → base64 で 4.55MB。**増加は +1.61MB で目標内**
- 余裕は小さいので、超えたときに効かせる手を順に用意しておく:
  - 点数を 96 → 64 に落とす(適応分割が線を滑らかにするので、粗い点列でも見た目は保たれる)
  - メンバー数を族ごとに可変にする(形が単純な族は少なく、複雑な族は多く)
  - フーリエ係数で持つ(滑らかな閉曲線なら16次で十分。データ量が点数に依存しなくなる)
- 実装時に実測して確かめる。**目標を超えたまま進めない。**
- **対象が7系に広がったため、この節の見積りは 8.1 で更新している。** バンドルへ埋めるのは
  地球-月・太陽-地球の2系だけで、残る5系は遅延ロードする

### 3.5 リサジュー軌道は解析近似を維持し、振幅に上限を設ける

厳密な不変トーラス計算(フーリエ表現の不変曲線をニュートン法で解く)は実装コストに見合わない。
線形/Lindstedt-Poincaré 近似のまま、面内振幅・面外振幅・両者の位相・周回数を自由に指定できる
ようにする。**近似が破綻する振幅には上限を設け、それ以上は指定できないようにする**
(上限は実装時に、同じ振幅の周期軌道と数値解の差から決める)。

### 3.6 色は「族内位置のグラデーション」と「安定度」を混ぜて示す

- グラデーションが族内の位置(色相・明度)を担い、**安定度は線の太さ**で重ねる(8 の #8)。
  どちらか一方が他方を打ち消すことはない
- 実装は `Curve` の頂点カラー化が要る(2.5)

### 3.7 UI は「群ごとの折りたたみ節」でまとめる

ファミリーは2系あわせて約37種になり、現在の「1種類=1区画を縦に並べる」形は破綻する。

- 軌道ガイドタブの中を **基本 / 共線点 / 三角点 / 副天体周回 / 共鳴** の群に分け、群ごとに
  折りたためるようにする
- **入れ子タブは採らない** — `TabBar` を入れ子にした前例がコードベースに無く、UI-DESIGN.md の
  語彙もタブを「パネルの表示面そのものの切り替え」と定めている。折りたたみなら既存の
  `buildCollapseToggle` に乗り、複数の群を開いて見比べることもできる
- **表示 ON にした種類だけ、その設定行が現れる**(OFF の間は見出しの1行だけ)。これが縦の長さを
  抑える最大の効き目になる
- 左レールは既に `overflow-y: auto` を持つので、スクロールの追加実装は要らない

## 4. 仕様(SPEC/MAP.md へ反映する内容)

### 4.1 軌道ガイドタブの構造

軌道ガイドタブは、参照として描く軌道を種類ごとに選ぶ。種類は次の群に分かれ、**群ごとに
折りたためる**。

画面に出す名前は**日本語訳と英語の併記**とする(8 の #12)。次の表を正本にする。

| 群 | 画面に出る種類名 | JPL の family | 持つ軸 |
| --- | --- | --- | --- |
| 基本 | 静止軌道 | — | なし |
| 共線点 | 平面リヤプノフ軌道 | `lyapunov` | 点(L1/L2/L3) |
| 共線点 | 垂直リヤプノフ軌道 | `vertical` | 点(L1/L2/L3) |
| 共線点 | ハロー軌道 | `halo` | 点(L1/L2/L3)・南北 |
| 共線点 | 軸方向軌道(axial) | `axial` | 点(L1/L2/L3) |
| 共線点 | 蝶形軌道(butterfly) | `butterfly` | 南北(L2 のみ) |
| 共線点 | トンボ形軌道(dragonfly) | `dragonfly` | 南北(L2 のみ) |
| 共線点 | リサジュー軌道 | —(解析近似) | 点(L1/L2/L3) |
| 三角点 | 短周期軌道(short period) | `short` | 点(L4/L5) |
| 三角点 | 長周期軌道(long period) | `longp` | 点(L4/L5) |
| 三角点 | 垂直軌道(vertical) | `vertical` | 点(L4/L5) |
| 三角点 | 軸方向軌道(axial) | `axial` | 点(L4/L5) |
| 副天体周回 | 遠距離逆行軌道(DRO) | `dro` | なし |
| 副天体周回 | 遠距離順行軌道(DPO) | `dpo` | なし |
| 副天体周回 | 低高度順行軌道(LPO) | `lpo` | 東西 |
| 共鳴 | 1:2 / 2:1 / 3:1 / 2:3 / 4:3 / 3:4 共鳴軌道 | `resonant` | なし(比が種類そのもの) |

- 各種類の見出しはその種類の表示トグルを兼ね、表示可否の最終的なゲートになる
- **表示が OFF の間、その種類の設定行は現れない**(見出しの1行だけになる)
- **系のトグルは群ごとに1つ**持ち、その群のすべての種類に効く。系は7つ(地球-月・太陽-地球・
  太陽-火星・木星-エウロパ・土星-タイタン・土星-エンケラドス・火星-フォボス)あるので、
  よく使う2つを前に出し、残りは折りたたみの中へ入れる。ただし**「基本」群(静止軌道)は
  CR3BP の軌道ではないので系の軸を持たない**
- ラグランジュ点・南北・東西の軸は、その種類が持つものだけを種類ごとに独立に持つ
- **「軸方向軌道」と「垂直軌道」は共線点群と三角点群の両方にあり、別の族である。**
  群が違うので画面上は取り違えないが、内部では群と種類の組で識別する

### 4.2 種類ごとの表示設定

表示 ON の種類は、次の設定を持つ。

| 設定 | 内容 | 既定 |
| --- | --- | --- |
| 本数 | 族から何本描くか。1 なら族ではなく代表の1本 | 5 |
| 族の範囲 | 族に沿った位置の下限と上限(0〜1)。本数が1のときは下限だけを使う | 0.15〜0.60 |
| 色(始) | 族の下限側の色 | 群ごとの色相・種類ごとの明度(8 の #10) |
| 色(終) | 族の上限側の色 | 同じ色相の明るい側 |
| 反転 | 始と終を入れ替える | OFF |
| 透明度 | 線の不透明度 | 0.4 |
| 進行方向 | 表示しない / 1周に1つ / 多数 | 表示しない |
| 進行方向のアニメーション | 動かすかどうか | OFF |
| 安定度を示す | 安定な軌道を**太い線**で描くか(8 の #8) | OFF |
| 色をリセット | 既定色へ戻す | — |

- **本数が1のとき、グラデーションと族範囲の上限は意味を持たない**ため、その行は現れない
- **リサジュー軌道だけは族の概念を持たない**(3.5 のとおり解析近似で、連続な族として焼き込まない)。
  本数・族の範囲の代わりに、面内振幅・面外振幅・両者の位相・周回数を指定する。色・透明度・
  進行方向・反転の設定は他の種類と同じように持つ。安定度の色分けは持たない(周期軌道ではなく
  安定性指数が定義できないため)
- 進行方向マーカーは、頂点が進行方向を向いた小さな正三角形で、その軌道と同じ色で描く。
  画面上の大きさはズームによらず一定に保つ
- アニメーションは**実際の軌道速度に比例**して進む。近点で速く、遠点で遅く動く
- 安定度を示すと、その族のうち**線形安定な軌道**(安定性指数の絶対値が 1 以下)が太く描かれる。
  色はグラデーションが担い続けるので、族内の位置と安定度を同時に読める。
  **安定の境界値は JPL が返す `stability` の流儀に合わせる**(2.6 の検算で確定させる)
- **選んだ軌道の実際の値**(面内振幅・面外振幅・周期・ヤコビ定数・安定性指数)を、族位置の
  スライダーの近くに読み取り専用で表示する(8 の #1)

### 4.3 ゼロ速度面(ガイドタブ)

ガイドタブに、指定したヤコビ定数のゼロ速度曲線を描く行を追加する。

- **断面**は4つで、2つの系それぞれの回転座標系の xy 面と xz 面にあたる。それぞれ独立に
  ON/OFF できる

  | 画面に出る名前 | 系 | 面 |
  | --- | --- | --- |
  | 月軌道面 | 地球-月 | xy 面(両天体を含む面) |
  | 地球と月を通る垂直な断面 | 地球-月 | xz 面 |
  | 地球公転面 | 太陽-地球 | xy 面 |
  | 太陽と地球を通る垂直な断面 | 太陽-地球 | xz 面 |

  ガイドタブには既に「月軌道面」「月赤道面」の縮尺グリッドの行があるため、**同じ名前が別の
  意味で2箇所に出ないよう、節を分けて見出しを付ける**
- **表示方式**は2つから選ぶ:
  - 1本 — 指定したヤコビ定数の曲線を1本だけ描く
  - 多数 — ヤコビ定数の範囲と本数を指定し、その範囲を等分した値それぞれの曲線を描く
- ヤコビ定数はスライダーと数値入力の両方で指定できる。**そのラグランジュ点の値**(L1〜L5)へ
  一発で合わせるボタンを添える —— ネックが開く瞬間を見るのがこの表示の主な使い道であるため
- 断面の描画範囲は**その系のスケールに固定**する(両天体間距離を基準にした固定範囲)。
  ズームしても格子の粗さが変わらず、表示がちらつかない
- **曲線だけを描き、面の塗りは持たない**(8 の #11)。到達可能領域と禁止領域の別は曲線の形と、
  ラグランジュ点の位置から読み取る

## 7. リスクと落とし穴

| リスク | 兆候 | 対処 |
| --- | --- | --- |
| **焼き込みサイズが目標を超える** | `npm run build` の増分が +2MB を超える | 点数を減らす → メンバー数を族ごとに調整 → フーリエ係数化、の順に効かせる。3.4 |
| **JPL API が将来変わる/落ちる** | 焼き込みの再生成が失敗する | 取得結果を `assets-src/` へ生キャッシュとして残す。再生成に API 接続が必須にならないようにする |
| **`Curve` 改修が既存の線を壊す** | 軌道線・計画線・予測線の見た目が変わる | 単色の呼び出し元は色属性を書かない経路をそのまま残す。フェーズ2の最初に単独で仕上げて検証する |
| **線の本数が増えて描画が重くなる** | マップのフレーム落ち | 種類×系×点×本数の直積は容易に数百本になる。**上限を超えたらパネルに警告を出すが、指定どおり描く**(8 の #9)。上限値は実測で決める |
| **進行方向マーカーの数が膨大になる** | 同上 | 「多数」の間隔は軌道の長さに応じて決め、1軌道あたりの上限を設ける |
| **共鳴軌道の族が長大** | 焼き込みが終わらない | JPL の返す件数が1万件を超える族がある。等間隔に間引く処理を取得直後に置く |
| **太陽-地球系の族が地球-月系と混同される** | L点の位置が違うのに同じ設定が効く | 系のトグルは群ごとに1つ(4.1)で、種類ごとには持たない。**同じ種類を両系で同時に出せるので、線の色だけでは系が判別できない。** 系ごとに既定色の系統を変えるか、片方を破線にする |
| **ゼロ速度曲線のネックが偽って閉じる** | 臨界値付近で穴が見えない | 格子解像度を上げるか、ラグランジュ点近傍だけ細かくする。2.4 |
| **Ω の特異点で NaN** | 等高線が壊れる | 両天体の近傍を計算対象から外すマスクを置く |

## 8. ユーザーと確定させた判断

以下はいずれも実装前にユーザーへ問い、返答を得て確定した。**独断で決めていない。**

| # | 論点 | 決定 | 採らなかった案と理由 |
| --- | --- | --- | --- |
| 1 | 軌道の指定方法 | **族位置(0〜1)で指定し、選んだ軌道の振幅・周期・ヤコビ定数を読み取り専用で添える** | 振幅(km)指定: 族に沿って振幅が単調でない区間で軌道が一意に決まらない。ヤコビ定数指定: 直感的でない |
| 2 | 質量比の不一致 | **JPL の μ のまま焼く**(3.2) | 我々の μ で解き直す: 非対称族に多重シューティングが要る。レジストリを JPL に合わせる: 重力定数は全シミュレーションの根幹で影響が広すぎる |
| 3 | 生データの保管 | **族ごとに間引いた初期条件(数MB)だけリポジトリへコミットする。** 生の100MBは置かない | コミットしない: API が変われば再生成できなくなる。全部コミット: clone が重い |
| 4 | UI の分け方 | **群ごとの折りたたみ**(3.7) | 入れ子タブ: 前例が無く規約の語彙にも無い。上位タブを増やす: タブが横に並びすぎる。別ウィンドウ: マップを覆う |
| 5 | 要求外の軌道 | **JPL カタログにある12ファミリーをすべて網羅する**(dragonfly を含む) | 挙がったものだけ: 取得経路が同じなので追加コストがほぼ無い |
| 6 | 対象の系 | **JPL が配信する7系すべて**(地球-月・太陽-地球・太陽-火星・木星-エウロパ・土星-タイタン・土星-エンケラドス・火星-フォボス) | 2系だけ: レジストリに該当天体が存在するので、出せるなら出す |
| 7 | データの出し方 | **系ごとに遅延ロード。** 地球-月と太陽-地球はバンドルへ埋め、他の5系は別ファイルにして表示時に取得する | 全部埋める: バンドルが 19MB → 32MB。全部遅延: 主要2系にも待ちが入る |
| 8 | 安定度の見せ方 | **線の太さ。** 安定な軌道を太く描く | 彩度: 暗い背景で読み取りにくい。破線: 線が多いと煩雑。強調のみ: 不安定側の情報が落ちる |
| 9 | 線数の上限 | **警告を出すが、指定どおり描く。** ユーザーの指定を勝手に曲げない | 自動間引き: 指定した本数と画面が食い違う。頭打ち: 意図した表示ができない |
| 10 | 既定色 | **群ごとに色相を分け、群の中の種類は明度で分ける** | 種類ごとに別色: 37種は覚えられず画面が騒がしい。系ごとに色相: 種類の区別がつかない |
| 11 | 禁止領域 | **曲線だけを描く。** 面の塗りは持たない | 塗る/片側に影: 等高線から面を組む実装が新規に要る |
| 12 | 用語の表記 | **日本語訳と英語を併記する**(例:「軸方向軌道(axial)」) | 日本語のみ: 文献との照合がしにくい。英語のみ: 初見で意味が取れない |

### 8.1 決定の反映で変わる見積り

7系すべてを対象にしたことで、3.4 のサイズ見積りは次のように変わる。

- 7系 × 37組 × 30メンバー = 7,770 メンバー = 11.9MB → base64 で 15.9MB
- **バンドルへ埋めるのは地球-月・太陽-地球の2系のみ**(2,220 メンバー = 4.55MB。現行 2.94MB を
  置き換えるので増加は +1.61MB で、目標 +2MB 以内を満たす)
- **残る5系(5,550 メンバー = 11.4MB)は系ごとの別ファイル**にして、その系の表示を初めて ON に
  したときに取得する。webpack に現在コード分割の設定が無いので、`asset/resource` で別ファイルとして
  出すか動的 import を足す必要がある(フェーズ3で判断する)
- 遅延ロード中は、その系のガイド線を描かず、読み込み中であることをパネルに示す

1. ~~spatial DRO の取得可否~~ → **確定: 取得できない。対象から外す。**
   `sys=earth-moon&family=dro` の全 10,998 メンバーを調べたところ、z と ż が厳密に 0 のものだけで、
   面外のメンバーは1つも含まれていなかった。平面 DRO からの分岐を自前で追うのはフェーズ3の範囲を
   超えるため、**立体遠距離逆行軌道は今回の対象から外す**。
2. ~~`jacobi` の流儀~~ → **確定: C = 2Ω − v²。**
   DRO の先頭メンバーの初期条件から Ω と v² を計算したところ、2Ω − v² = 1.5410005957354045 に対し
   API の `jacobi` は 1.5410005957354 で一致した(Ω − v²/2 は半分の値になり一致しない)。
3. ~~`stability` の流儀~~ → **確定: 1 が中立で、1 に近いほど安定。**
   `limits.stability` は DRO(安定な族)で [1, 1.0002]、L2 北ハロー(末端が不安定な族)で
   [1, 606.1] だった。**値は常に 1 以上**で、下限が 1 に張り付く。したがって安定の判定は
   「**1 に十分近いか**」で行い、閾値は実装時に見た目で決める(1.0 との厳密比較にはしない)。
4. **系ごとに存在する族。** どの系にどの族があるかを推測で決めず、生成時に取得を試みて
   空なら選択肢から外す(フェーズ3-4)。
5. **リサジューの振幅上限。** 近似が破綻する振幅を、同じ振幅の周期軌道の数値解との差から決める
   (フェーズ1-4)。
6. **遅延ロードの方式。** webpack に現在コード分割の設定が無い。`asset/resource` で別ファイルとして
   出すか、動的 import を足すかを実測して決める(フェーズ3)。
