# 他の軌道シミュレータ・ゲームとの比較による不足領域の分析

作成日: 2026-08-08
対象コードベース: dive-into-tepui2 (`src/` 配下 151 ファイル / 約 22,400 行)

## この文書の目的と読み方

「他の軌道シミュレータやゲームと比較して、このプロジェクトに何が足りないか」を調査した結果をまとめる。

比較対象として想定するのは以下の 3 系統である。それぞれ目指すものが違うため、「足りない」の意味も系統ごとに異なる。

| 系統 | 代表例 | 何を評価軸にするか |
|---|---|---|
| 軌道力学ゲーム | Kerbal Space Program、Simple Rockets 2 | プレイヤーの自由度、目標設定、習熟の階段 |
| 宇宙船シミュレータ | Orbiter | 機体運用の忠実さ、計器と手順 |
| 軌道力学解析ツール | GMAT、STK、Orekit | 力学モデルの網羅性、数値解法の妥当性 |

**行数の比較は本文書では行わない。** KSP・Orbiter はいずれもソース行数が公開されておらず、公開情報から検証できる数値が存在しない。また機能範囲が違うプロジェクト同士で行数を比べても、規模の妥当性の判断材料にはならない。本文書は「機能・モデルとして何が有るか無いか」だけを比較軸にする。

各項目には以下を明記する。

- **現状**: コードベースを実際に読んで確認した事実
- **他と比べて何が足りないか**
- **既存の記録との関係**: `memos/mikanixonable/dev.md` の todo、`DEVELOP/SPEC.md` 14 節(未実装)に既出かどうか

「既出」の項目は本文書の新規発見ではなく、優先度判断のために再掲している。**既出でない項目には「★未記録」を付ける。** そこが本文書の主たる価値である。

## 1. 力学モデルの網羅性 — 解析ツール系との比較

### 1.1 現状の摂動モデル

`src/physics/dynamics.ts` の `accel()` が加速度合成の唯一の場所であり、含まれる項は以下がすべてである。

1. 全登録天体(地球・月・木星・太陽)の点質量重力 — `attractor.ts` の `attractorAccel`。ECI 原点自体が各天体へ自由落下する分の補正項を含む
2. 地球の J2 帯状調和項 — `j2Accel`
3. 大気抵抗 — `atmosphere.ts` の `dragAccel`(地球のみ、Vallado の指数テーブル、地球自転に共回転する大気)
4. 推力(呼び出し側が渡した場合のみ)

### 1.2 含まれていない摂動

GMAT や Orekit のような解析ツールが標準で持ち、このコードベースに無いものは以下。

- **太陽輻射圧 (SRP)**: 未実装。★未記録
  - 低軌道では大気抵抗が支配的なので影響は小さいが、`dev.md` が目標に掲げるラグランジュ点・ハロー軌道の領域では大気抵抗がゼロになるため、SRP が残る唯一の非重力摂動になる。ハロー軌道の維持を扱おうとした時点で必ず問題になる。
  - 実装コストは低い。太陽方向・遮蔽率(`shadow.ts` の `sunlitFactor` が既にある)・面積質量比があれば済み、`bcInv` と同じ形で per-entity 定数として渡せる。
- **地球の J2 より高次の帯状調和項 (J3, J4...) と非帯状項**: 未実装。★未記録
  - 実用上の影響は J2 に比べて 3 桁小さいため、ゲームとしては欠落と言い切れない。
- **固体地球潮汐**: 未実装。`dev.md` に「軌道計算に関わる摂動に固体地球潮汐、月の J2 摂動を追加したい」と既出。
- **月の J2 摂動**: 未実装。同上、`dev.md` に既出。
  - `j2Accel` は地球専用としてハードコードされており(CLAUDE.md も「Earth-specific and deliberately not generalized」と明記)、月周回軌道を扱う以上いずれ一般化が要る。月の J2 は地球より相対的に大きく(月は扁平ではないが質量分布が不均一で、実際には J2 より非帯状項の効き方が特徴的)、低月軌道の長期安定性を左右する。
- **相対論補正**: 未実装。この規模のゲームでは不要。欠落として数えない。

### 1.3 数値解法

- **現状**: 固定ステップ RK4 のみ(`stepOrbitRK4`)。ステップ幅は呼び出し側が「その場の支配天体まわりの円軌道周期 ÷ 固定分割数」で決める方式(`localOrbitPeriod`)。
- **足りない点**: 適応ステップ制御と埋め込み誤差評価が無い。★未記録
  - 解析ツールは Dormand-Prince (RKF45/DP853) のような埋め込み型を使い、局所誤差推定でステップを伸縮させる。
  - ただし本プロジェクトの「周期を固定分割する」方式は、円軌道に近い限り実質的に同じ効果を持つ。**問題が出るのは離心率が高い軌道と、天体近傍を高速通過するフライバイである。** 近点で必要なステップ幅は遠点の数桁小さく、周期基準の一律分割では近点通過の精度が落ちる。`plan-arc.ts` が `PLAN_ARC_MAX_STEPS` (20000) の上限に当たって軌道を打ち切る設計になっているのは、この構造的な帰結が既に表面化している徴候と読める。
  - `memos/hedalu244/better_simulation_todo.md` は計算量削減(N 体側の空間分割)を扱っており、ステップ制御の話とは別問題。したがって未記録扱いとする。
- **エネルギー保存の検証手段が無い**: ★未記録
  - `npm run test:physics` は 1 周期のドリフトを測定値ピン留めで検証しているが、長期積分でのエネルギー/角運動量ドリフトを継続監視する仕組みは無い。シスルナ長期積分に進むなら、シンプレクティック性の無い RK4 では系統的なエネルギードリフトが必ず出る。テストに保存量の監視を足すのが低コストな備えになる。

### 1.4 ハロー軌道の扱い

- **現状**: `physics/halo.ts` は Richardson の三次振幅拘束まで実装しており(ISEE-3 ハローを 1% 以内で再現)、これは教育用ツールの水準として十分に高い。ただし `SPEC.md` 17 節が明記するとおり、**ゲームの積分器は制限三体問題ではないため、配置した機体はハロー軌道を維持せずドリフトする。**
- **足りない点**: station-keeping(軌道維持マニューバ)の概念が無い。★未記録
  - 実際のハロー軌道運用は「不安定平衡なので定期的に微小な Δv を当て続ける」ことが本質であり、そこがゲーム性になり得る箇所である。現状は「置いたら流れていく」だけで、流れることに対してプレイヤーができることが無い。
  - 差分修正 (differential correction) で周期解に落とす機能があれば「維持できる軌道」になるが、これは実装コストが大きい。より安価な代替は、ドリフト量を可視化して手動 station-keeping をプレイヤーに委ねること。既存のマニューバ計画 UI がそのまま使える。

## 2. 機体運用の忠実さ — Orbiter 系との比較

### 2.1 推進剤と質量

- **現状**: RCS 推進剤は実装されている。`ship.ts` の `rcs_tank` パーツが `fuel`/`maxFuel` を持ち、`player-throttle.ts` が並進・回転の両方で `consumeFuel` を呼び、残量が尽きると出力が絞られる。ドックビューで有償補給できる。
- **足りない点 (a): 推進剤消費による質量減少が無い。** ★未記録
  - `Player.mass` は `C.PLAYER_MASS` の定数で、燃料を使っても変わらない。つまり**ツィオルコフスキーの式が成立しない**。加速度は常に `totalThrust / mass` で一定になる。
  - Orbiter も KSP も質量減少を扱う。宇宙機の運動として最も基本的な非線形性がここで失われている。
  - なお `Part.weight` はデータとしては全パーツに定義されているが(`parts.ts` の `weight: number // kg`、ショップカタログにも価格と並んで載っている)、**どこからも質量計算に読まれていない。** CLAUDE.md も「`Part.weight` is still unread」と明記している。つまりパーツ構成が実際の運動性能に効かない。重い装甲を積んでも加速は鈍らない。
  - 修正の筋: `Ship.mass` を「パーツ重量の総和 + 残推進剤」の getter にする。`player-throttle.ts` は既に `ship.mass` を読んでいるので、その一箇所の変更で加速度側は自動的に追従する。ただし `collision.ts` の換算質量も同じ値を読むため、剛体接触の挙動が変わる点は要検証。
- **足りない点 (b): Δv 予算が戦闘ビューに表示されない。** ★未記録
  - 推進剤残量が見えるのはドックビューのパーツ一覧だけで、飛行中のステータスウィンドウ(装甲・エンジン出力・温度・電力)に燃料も Δv も無い。
  - **軌道力学ゲームにおいて Δv 予算は最も中心的な資源である。** KSP はステージごとの Δv を常時表示し、マニューバノードは必ず「必要 Δv」と「残 Δv」を並べる。本プロジェクトはマニューバ計画で必要 Δv を出しているが、それを払えるかどうかがプレイヤーに見えない。
  - これは実装コストが最も小さく、ゲーム性への効果が最も大きい項目だと考えられる。既に `totalFuel` と `totalFuelConsumptionRate` の getter があるため、表示の追加が主な作業になる。

### 2.2 姿勢制御

- **現状**: RCS による手動回転、RCS 減衰、プログレード保持オートパイロット(PD 制御)。慣性テンソルは三軸非対称でジャニベコフ効果が出る。角速度に上限が無い設計。
- **足りない点: リアクションホイール / CMG が無い。** ★未記録
  - 実機の姿勢制御は推進剤を消費しないホイールが主体で、RCS はホイールのアンローディングと大トルク時に限られる。現状は全ての姿勢変更が推進剤を消費する。
  - ゲーム性としては「推進剤を使わない微調整」と「推進剤を使う大回転」の使い分けが生まれるので、資源管理に一段深みが出る。既に微動モード (`FINE_ATTITUDE_SCALE`) があるため、UI 上の接続先も用意されている。
- **足りない点: 重力傾斜安定化・磁気トルカなど受動的姿勢擾乱が無い。** シミュレータとしての忠実さの話であり、ゲーム性への寄与は薄い。優先度は低い。

### 2.3 ドッキング

- **現状**: `docking.ts` の `checkProximity()` が、基地と各艦の距離 500 m 未満かつ相対速度 20 m/s 未満で自動的にドッキングする。
- **足りない点: ドッキング操作そのものがゲームプレイになっていない。** ★未記録
  - 姿勢の一致、ドッキングポートの方向、接近軸(V-bar / R-bar アプローチ)、接近速度プロファイルのいずれも判定に入らない。「近づいて減速する」だけで吸着する。
  - Orbiter はドッキング MFD による軸合わせが主要な操作の一つであり、KSP でもドッキングポートの向き合わせは習熟の山場になっている。`dev.md` が言及する「こうのとりの ISS 接近マニューバ」はまさにこの領域(R-bar 接近、ホールドポイント、把持)であり、目標として掲げられている割に現在の判定は最も単純な形にとどまっている。
  - 500 m / 20 m/s という閾値は、軌道ランデブーの感覚からするとかなり緩い。実際の宇宙機のドッキングは相対速度 0.1 m/s のオーダーで行う。

### 2.4 打ち上げ・着陸フェーズ

- **現状**: 初期状態は最初から高度 420 km の LEO に配置される(`INITIAL_ALT`)。
- **足りない点**: 大気圏内飛行、多段ロケット、重力ターン、着陸のいずれも無い。
  - これは KSP との最大の機能差だが、**欠落ではなく設計判断と読むべきである。** `dev.md` は一貫して「低軌道シューティング」を掲げており、打ち上げは範囲外。本文書では不足として数えない。

## 3. ゲームとしての自由度 — KSP 系との比較

### 3.1 機体設計の自由度

- **現状**: 固定形状の機体に対し、8 種のパーツ(本体・コックピット・装甲・スラスタ・RCS タンク・放熱板・ソーラーパドル・武装)を交換できる。ドックビューにショップがあり、種類ごとに 2 種程度の選択肢がある。
- **足りない点**: 機体の形そのものは設計できない。パーツ数・配置・接続関係は固定で、交換は同じスロットの性能違いに限られる。
  - KSP の中心的な魅力は「機体を組む」ことそのものであり、そこは意図的に採っていない設計と読める。
  - ただし **パーツ交換が運動性能に効かない**(3.1 の質量問題)ため、現状のパーツ制は「HP と数値が変わる」だけになっており、パーツ制を入れた意味がまだ回収できていない。`Part.weight` を質量に接続するのが、既存の実装を活かす最短の手になる。

### 3.2 敵 AI

- **現状**: `enemy.ts` に推力に関するコードは存在しない(`grep` で `thrust` が 0 件)。敵は軌道上を自由落下しながら、`intercept.ts` の `solveLeadTime` で偏差射撃してくるのみ。
- **足りない点: 敵が一切軌道機動を行わない。** `SPEC.md` 14 節に「敵 AI(現状ターゲットは受動的で、回避・反撃を行わない)」として既出。CLAUDE.md も唯一の未実装項目として名指ししている。
  - **軌道力学ゲームとしては、これが最も本質的な欠落である。** 敵が機動しないということは、遭遇の幾何が最初の配置で決定してしまい、プレイヤーの軌道選択に対する応答が存在しないことを意味する。軌道力学が「読み合い」にならず、「移動手段」にとどまる。
  - 実装のための土台は既にある。`Plan`/`PlanArc` による軌道計画の積分、`GameEntity.thrust` スロット、`Enemy.behave` の毎フレーム呼び出し、`CreativeStage.advanceFollowPlan` の「計画を自動追従する」機構(現在は自機用)がすべて揃っている。**敵に `Plan` を持たせて `followPlan` 相当を走らせるだけで、最小限の機動 AI は成立する。** CLAUDE.md が「`Player.behave` の推力即時反映は deliberately player-only であり、将来 `Enemy` の推力が即時リセットしない余地を残している」と書いているのは、この拡張を見越した設計判断である。

### 3.3 プログレッションと目標設定

- **現状**: ステージ制(0/00/1/2 + デバッグ)。`UnlockManager` がクリア回数を localStorage に保存し、ステージ 2 はステージ 1 クリアで解放。ドックビューにゲーム内通貨とショップがある。
- **足りない点**: 研究ツリー・ミッション契約・長期的な目標体系は無い。
  - `dev.md` に「ステージ 000 とかを新しく作ってそこでまた実験的なことを繰り返すと思う。しかし今やりたいのは通信、データベース永続化、サンドボックスモード」とあり、ステージという枠組み自体を超える方向が既に意識されている。本文書として新規に提案するものは無い。

### 3.4 セーブと永続化

- **現状**: `save-manager.ts` が実装済み。`localStorage` に単一キー (`tepui.save`) で 1 件のセーブを保存し、ステージ ID が一致しない場合は復元を拒否する。
- **足りない点**: ★未記録
  - **セーブスロットが 1 つしかない。** 軌道力学ゲームは「マニューバ前に保存してやり直す」使い方が中心になるため、複数スロットとクイックセーブは実用上の要求が強い。
  - **軌道計画そのものが保存対象かどうかが不明瞭。** `dev.md` に「軌道計画は、保存できるようにする」という項目があるので既出だが、`save-data.ts` の内容を確認して現状の保存範囲を明らかにしておく必要がある。
  - サーバー側永続化は `dev.md` で「通信、データベース永続化」として既出。

### 3.5 MOD・拡張性

- **現状**: 無い。天体の追加は `SOLAR_SYSTEM` と `CELESTIAL_VIEWS` の 2 つのレジストリに登録するだけで済む設計になっており(木星がその実証として登録されている)、内部的な拡張性は高い。
- **足りない点**: 外部から拡張する仕組みは無い。Web ゲームとして配布する以上、KSP 的な MOD 文化は前提にしにくい。優先度は低いと判断する。

## 5. 優先度の提案

「実装コストの小ささ」と「このプロジェクトが掲げる目標への寄与」の両面から並べる。

### 第 1 群 — 低コストかつ効果が大きい

1. **飛行中の推進剤残量 / Δv 予算の表示**(2.1-b)
   - 既存の `totalFuel` getter を戦闘ビューのステータスウィンドウに出すのが主な作業。マニューバ計画の「必要 Δv」と対にすることで、既にある計画機能の意味が変わる。
2. **`Part.weight` を `Ship.mass` に接続し、推進剤消費で質量が減るようにする**(2.1-a, 3.1)
   - パーツ制を入れた投資が回収される。`player-throttle.ts` は既に `ship.mass` を読んでいるため接続点は 1 箇所。`collision.ts` の換算質量への影響のみ要検証。

### 第 2 群 — 中コストだが目標の核心

3. **敵の軌道機動 AI**(3.2)
   - `Plan` と `followPlan` の既存機構を敵に転用するのが最小実装。「軌道力学が読み合いになる」という、このプロジェクトが目指すゲーム性の核心にあたる。
4. **ドッキング操作のゲーム化**(2.3)
   - 姿勢一致とポート方向の判定を足す。`dev.md` が掲げる「こうのとり式接近」への前提になる。

### 第 3 群 — シスルナフェーズに進む前に必要

5. **太陽輻射圧の追加**(1.2)
   - ラグランジュ点領域で大気抵抗がゼロになった後、唯一残る非重力摂動。`bcInv` と同じ形で入れられる。
6. **J2 の天体一般化と月の J2**(1.2)
   - 低月軌道を扱う時点で必要になる。`dev.md` に既出。
7. **積分ステップの適応制御、または高離心率・フライバイ時のステップ幅見直し**(1.3)
   - `PLAN_ARC_MAX_STEPS` による打ち切りとして既に表面化している。

## 6. 総括

**力学モデルの精度に関しては、このプロジェクトは軌道力学ゲームとしてはむしろ踏み込んでいる側にある。** 多体点質量重力を毎ステップ合成し、ECI 原点の非慣性補正を各項に持たせ、J2 と共回転大気抵抗を含み、ハロー軌道は Richardson の三次振幅拘束まで実装している。KSP のパッチドコニック近似(影響圏を切り替える単一天体モデル)より明確に精密である。`test:physics` の網羅性も、この規模の個人プロジェクトとしては例外的に高い。

**不足が集中しているのは、力学モデルではなく「力学がゲームの意思決定に接続される部分」である。**

- 推進剤は消費されているのに、飛行中に見えない → 資源として意思決定に入らない
- 質量は変化せず、パーツ重量も読まれない → 機体構成が運動に効かない
- 敵は機動しない → 軌道選択に対する応答が存在しない
- ドッキングは距離と相対速度だけで成立する → ランデブーの終端が操作にならない

この 4 つは互いに独立ではなく、いずれも「正確に計算されている物理量が、プレイヤーの選択と噛み合っていない」という同じ形をしている。したがって**力学モデルをさらに精密にするより、既に計算されている量をゲームの意思決定に接続する方が、投資対効果は高いと判断する。** 第 1 群・第 2 群をその順序で並べたのはこの理由による。
