# 模式図(Schematic)スタイルの追加 — 実装計画

## 目的

マップビュー・戦闘ビューの左ドックへ「スタイル」パネルを新設し、画面全体の見せ方を
**写実(realistic)** と **模式図(schematic)** の2つから選べるようにする。模式図は、
軌道や位置関係そのものを読ませるための表示で、質感・光源・背景を持たない。

`DEVELOP/SPEC/RENDERING.md` へ次の節を追記する(手順1でそのまま入れる)。

> ## 表示スタイル
>
> 画面全体の見せ方を2つから選ぶ。マップビュー・戦闘ビューの左ドックの「スタイル」パネルで
> 切り替え、選択はブラウザに保存されて次回起動でも引き継がれる。**選択は3D世界を描くすべての
> 画面が共有する** — マップビュー・戦闘ビューだけでなく、基地ビューやクリエイティブステージでも
> 同じスタイルで描かれる。同じ世界を別の縮尺・別の目的で見ているだけであり、画面ごとに
> 別のスタイルであることに意味がないため。切り替え手段(スタイルパネル)を置くのは
> マップビュー・戦闘ビューの左ドックだけとする。タイトル画面は世界を描いていないため対象外。
>
> - **写実** — 既定。光源・質感・大気・星野を持つ通常の描画。
> - **模式図** — 白い背景の上に、天体・艦艇・敵を**テクスチャも陰影も持たない輪郭線**だけで
>   描く。輪郭は物体の外形と、面の向きが折れる稜線に出る。天体には**経度・緯度15°刻みの
>   グリッド**が天体自身の自転に貼り付いて回る。惑星の環は外周・内周の輪郭線として描く。
>   星野・大気・オーロラ・環の質感・噴射炎・爆発・煙は描かない。
>   太陽は光源の方向を読ませるため、グローを持たない**輪郭の円**として描く。大気圏は描かない。
>   軌道線・軌跡線・天球グリッド・Δv ギズモ・マーカーは**描く** — 模式図が読ませたいものそのものであるため。それらの色は
>   白背景の上で読める明度へ入れ替わる。
> - デバッグ表示(この文書「デバッグ表示」節)は写実スタイルのときだけ選べる。模式図は
>   パイプラインの後半を通らないため、中間結果を映しても通常のフレームの説明にならない。

`DEVELOP/SPEC/UI-DESIGN.md` §8「常設パネル」へ次を追記する。

> - **スタイル**(左レール、戦闘・マップ共通) — 画面全体の見せ方を選ぶ。選択肢は縦に並ぶ
>   リストで、1つだけが選ばれる(将来の追加を前提に、2択でもセグメントコントロールではなく
>   リスト形式を採る)。選択は即座に反映され、ブラウザに保存される。**何が変わるかは
>   RENDERING.md「表示スタイル」。**

## 決めたこと

判断の根拠と、覆されたときに影響する手順を併記する。

1. **輪郭は合成段の後処理で出す(手順4)。** G バッファは既に深度(32bit float)と法線
   (octahedral 圧縮)を全画面ぶん持っており、`LIT_OPAQUE_LAYER` に居る天体の球・艦艇・敵が
   すべてそこに描かれている。深度差と法線差から線を出せば、描画物モジュール(`ships.ts`・
   `celestial-surface.ts`・`protein-*`)を1行も触らずに全物体へ一律で効く。
   *覆された場合:* 手順4を各メッシュのマテリアル差し替えへ書き換える。手順5〜8は変わらない。

2. **模式図ではマテリアルパス・大気パス・world パスを実行しない(手順4)。** これらの出力は
   模式図の合成が読まないので、走らせるだけ無駄になる。同時に、星野(マテリアルパスが描く背景層)・
   大気・環・点群・ビルボード(噴射炎・フラッシュ・太陽グロー)が**自動的に画面から消える** —
   ユーザーの「星空・大気・オーロラ・環の質感/VFX を消す」という指定が、個別のフラグ分岐を
   1つも増やさずに満たされる。
   *覆された場合:* 手順4で各パスを実行したまま合成だけ差し替え、代わりに消す要素ごとの分岐を
   `environment-scene.ts` へ足すことになる(分岐は5箇所以上に増える)。

3. **3D UI パス(軌道線・軌跡線・天球グリッド・Δv ギズモ)の色は、線ごとに定義を書き換えず、
   パス全体を専用ターゲットへ描いてから明度を反転して合成する(手順5)。** 線色は
   `game/const.ts` と各生成箇所に散っており、スタイルごとの第二パレットを持たせると
   「色を決める場所」が2倍になる。反転は1箇所で済み、暗背景向けに選ばれた明色が
   そのまま白背景向けの暗色になる。
   *覆された場合:* 手順5を「線色をスタイル別トークンから引く」形へ書き換える。
   `LineStyle.color` を組み立てている全箇所が変更対象になり、手順5の規模が数倍になる。

4. **環と太陽は輪郭線として描き足す(手順7)。** どちらも自照式で深度を書かないため
   G バッファに乗らず、決めたこと2の帰結として模式図では丸ごと消える。惑星の識別に環の有無は
   効き、太陽の位置は昼夜と加熱の向きを読む基準になるため、環は外周・内周の円、太陽は
   カメラへ正対する1つの円として、3D UI パスの線で描き足す。大気圏は描かない
   (高度の基準を決める必要があり、それは模式図の目的ではない)。
   *覆された場合:* 手順7のうち該当部分を落とす。他の手順は変わらない。

5. **切り替え手段は左ドックのパネルだけ、効果は3Dを描く全画面(手順2・3)。**
   `RenderPipeline.render()` の呼び出し元は `game.ts` の1箇所だけなので、パイプラインが
   スタイルを見るだけで基地ビュー・クリエイティブステージにも自動的に効く。追加の配線は要らない。
   タイトル画面(`render/title-scene.ts`)はパイプラインを通さず自前で `renderer.render()` する
   別経路なので、対象外とする。

6. **経緯度グリッドは球として描かれている天体すべてに出し、模式図のときだけ出す(手順6)。**
   写実スタイルでは天体テクスチャの上に線が乗ることになり、既存の見た目を壊す。

## 達成目標

全手順の実施後、次がすべて満たされていること。

1. マップビュー・戦闘ビューのどちらでも、左レールに「スタイル」パネルがあり、「写実」「模式図」を
   選べる。片方で切り替えるともう片方も同じ選択になっている。
2. 模式図を選ぶと、背景が白になり、天体・自機・敵・基地が輪郭線だけで表示される。
   テクスチャ・陰影・昼夜境界が画面から消えている。
3. 模式図で、星野・大気・オーロラ・小天体の点群・噴射炎・フラッシュ・太陽グローが
   画面に出ていない。太陽は輪郭の円として出ている。
4. 基地ビュー・クリエイティブステージでも模式図が効いている(タイトル画面は写実のまま)。
5. 模式図で、球として描かれている天体に経度・緯度15°刻みのグリッドが出ており、
   天体の自転に追従して回る。
6. 模式図で、軌道線・軌跡線・天球グリッド・Δv ギズモ・HUD マーカーが白背景の上で読める。
7. リロード後も直前に選んだスタイルが復元される。
8. `npm run typecheck` が通る。
9. `npm run render-lab:shot` の撮影が両スタイルで成功する。

### 手順 4. 合成段に模式図の輪郭抽出を実装する

**目的.** 模式図の本体。白背景と輪郭線を作り、模式図では読まれないパスを実行しないようにする。

**着手前に `/rendering-workflow` を通す。**

**変更が必要な箇所**

| ファイル | 何をするか |
| --- | --- |
| `src/render/pipeline/schematic-composite.ts`(新規) | 輪郭抽出の TSL グラフ。`gbuffer.depthTexture` の view 空間 z(`view-ray.ts` の `viewPositionAt`)と `octDecodeNormal(gbuffer.normalTexture)` を上下左右の4近傍で取り、**深度の相対差**(絶対差では遠景で必ず線になる)と**法線の内積**をしきい値と比べて線の濃さを出す。背景色・線色は `schematic-style.ts` から取る。深度が far(物体なし)の画素は線を出さず背景色 |
| `src/render/pipeline/render-pipeline.ts` | `render()` に `style: RenderStyle` を受け、模式図では `materialPass.render` / `atmospherePass.render` / world パスの `renderer.render` を呼ばない。`quad.material` は模式図用の1枚を選ぶ。この材質も既存と同じく `depthNode` に G バッファ深度を書く(**手順5・6・7 と 3D UI パスの深度テストがこれに依存する**)。`compositeMaterials` の構築規則(表示ごとに別マテリアル)に倣い、模式図用も構築時に1枚だけ作る |
| `src/game/hud/panels/graphics-panel.ts` | デバッグ表示の選択欄を、模式図のあいだ無効(disabled)にする |

(a) 背景が白、(b) 地球・自機・敵が輪郭線として見え、テクスチャと昼夜境界が消えている、

### 手順 5. 3D UI パスの線を白背景で読める明度にする

**目的.** 軌道線・軌跡線・天球グリッド・Δv ギズモは暗背景向けの明色で定義されている。
模式図の白背景の上ではほぼ見えないため、パス全体の明度を反転して合成する。

**変更が必要な箇所**

| ファイル | 何をするか |
| --- | --- |
| `src/render/pipeline/overlay-pass.ts` | 模式図のときだけ、キャンバスへ直接ではなく RGBA の専用ターゲットへ描き、そのあと `QuadMesh` 1枚で「色は明度反転・アルファはそのまま」の透過合成としてキャンバスへ重ねる。深度テストは従来どおり合成パスが複製した深度に対して行う必要があるため、専用ターゲットには**合成パスと同じ G バッファ深度**を与える |
| `src/render/schematic-style.ts` | 反転の式(単純な `1-c` か、明度だけ反転して色相を保つか)の係数を持つ |

**達成条件と検証.** `npm run typecheck` が通る。`npm run dev` で模式図にし、
(a) 自機・ターゲット・計画軌道の各軌道線が白背景の上で判別できる、
(b) 線どうしの色の違い(参照/自機/ターゲット/計画/予測)が保たれている、
(c) 天体の手前を通る軌道線が天体に隠れる(深度テストが生きている)。
写実スタイルへ戻して線の色が従来どおりであること。

## 見積り

**輪郭抽出の GPU 負荷(手順4).** 4近傍を取るので画素あたり深度4回+法線4回=8フェッチ。
1920×1080 = 2.07M px、深度32bit・法線 RG16F = 4B/フェッチとして
2.07e6 × 8 × 4B ≈ 66 MB/frame。一般的なノート GPU の実効帯域 200 GB/s で **≈ 0.33 ms/frame**。
一方で模式図では、マテリアルパス・大気パス・world パスを実行しない。この3つは現在の負荷計測で
フレームの主要部を占めるため、**模式図は写実より軽くなる**見込み(手順4の検証で実測へ置き換える)。

**経緯度グリッドの頂点数(手順6).** 経線24本 × 128分割 + 緯線11本 × 128分割 = 4,480 セグメント
= 8,960 頂点。ジオメトリは全天体共有なので VRAM は 8,960 × 12B ≈ 105 KB の1つだけ。
描画は天体1つにつき 1 draw call で、球として描かれる天体は同時に多くて5個程度 → +5 draw call。

**3D UI パスの反転合成(手順5).** 全画面 1 フェッチ = 2.07e6 × 4B ≈ 8 MB/frame ≈ **0.04 ms**。
専用ターゲット RGBA8 1枚 = 1920×1080×4B ≈ 8 MB の VRAM 増。

**作業量.** 新規5ファイル・既存の変更11ファイル。うち TSL を書くのは手順4の輪郭抽出と
手順5の反転合成の2箇所で、ここが唯一の未知(three/webgpu の TSL は型が緩く、
書き間違えると絵が黒くなるだけで型検査を通る)。

## リスクと落とし穴

| リスク | 影響 | 露見する場所 |
| --- | --- | --- |
| G バッファに乗るのは `LIT_OPAQUE_LAYER`(= `MeshStandardMaterial` を持つ物体)だけ。タンパク質型の敵の外殻・リボンが標準マテリアルでない場合、模式図で**無言で消える** | 敵が画面から消えるが、エラーは出ない | 手順4の検証(c)。消えていたら、その物体を G バッファへ乗せるか、輪郭を別途線として描く |
| 深度の**絶対差**でエッジ判定すると、遠い天体は隣接画素の深度差が巨大になり全面が線になる。逆に近い物体では線が出ない | 縮尺を変えたときだけ壊れる。1つの縮尺で確認すると気付かない | 手順4の検証。マップビューで縮尺を最小・最大まで振って確かめる |
| 模式図で world パスを止めると HDR ターゲットを誰もクリアしなくなる。デバッグ表示を選ぶと**前フレームの残骸**が映る | デバッグ表示が嘘をつく | 手順4。デバッグ表示を模式図のあいだ無効にすることで塞ぐ |
| 合成パスが G バッファ深度をキャンバスの深度バッファへ複製しなくなると、3D UI パスの線が**天体を貫通して手前に出る** | 軌道線が天体の裏側でも見える | 手順4。模式図用マテリアルにも `depthNode` を書く。検証は手順5の(c) |
| 3D UI パスを専用ターゲットへ移すと、アンチエイリアス済みの線のアルファが合成で二重に掛かり線が薄くなる | 線が細く霞む | 手順5の検証(a)。プリマルチプライドアルファで合成する |
| 経緯度グリッドを天体の親と別の変換の下へ置くと、自転や公転から1フレームずれる。静止画では気付かない | 時間加速したときだけグリッドが滑る | 手順6の検証(b) |
| 反転合成は色相も反転させるため、色で意味を持たせている線(参照/計画/予測の区別)が別の意味の色になりうる | 色の意味が壊れる | 手順5の検証(b)。壊れるなら明度だけ反転する式へ切り替える |
| スタイルパネルの実体を1つにして DOM を移動する方式のため、ビュー切替の順序次第でパネルが**どちらのレールにも居ない**状態になりうる | パネルが消える | 手順3の検証(b) |
| タイトル画面はパイプラインを通さない別経路(`render/title-scene.ts`)。全画面へ効かせたつもりでもここだけ写実のまま残る | 仕様どおりだが、実施中に「効いていない」と誤診しやすい | 手順4。タイトルは対象外と決めてある |
| 太陽の円をカメラへ正対させ忘れると、視点によって線分に潰れる。正面から見ている間は気付かない | 太陽が消えたように見える | 手順7の検証(c) |
| `render-lab` は本編とは別のシーンを組むため、模式図の合成が本編でだけ壊れていても撮影は成功しうる | 撮影が通ったことを根拠にできない | 手順4。`npm run dev` の目視を主とし、撮影は補助に留める |
