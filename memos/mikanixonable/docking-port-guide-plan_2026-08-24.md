# ドッキングポートとドッキングガイドの導入計画 (2026-08-24)

## 目的

現状のドッキングは「船の位置が基地スロット/ハッチの正面コーン内にあり、距離と相対速度が閾値内」
という位置ベースの判定で、船側には接続点という概念がなく、船の姿勢(どちらを向いているか)も
問われない。また、閾値を満たしているかどうかがプレイヤーから見えず、コンテキストメニューに
「ドッキング」が出るかどうかで結果だけが分かる。

これを次の状態にする:

- **船にもドッキングポートを設け**、判定を「船ポートと基地スロット(または相手船ポート)の
  距離・軸整合・相対速度」に置き換える。船の姿勢がドッキング成立の条件になる。
- **ドッキングガイドを設け**、接近中のプレイヤーに「どのスロットへ・あとどれだけ寄せ・
  どれだけ向きを合わせればよいか」を戦闘ビュー上で見せる。

## 決めたこと

| 決定 | 根拠 | 覆された場合に変わる手順 |
| --- | --- | --- |
| 船のポートは機首方向(+forward)に 1 基 | 船は `Attitude` を持ち forward が定義済み。複数ポートは仕様上の必要が出てから | 手順 2(ポート定義)・手順 3(判定) |
| 船対船ドッキングも互いのポート同士の判定に変更(現状は距離 500 m のみ) | 「よりリアリティーを持って」という要求を船対船にも適用。ポートを設けて片方だけ位置判定のままにすると整合しない | 手順 3 |
| ガイドは (a) 戦闘ビューの 3D 表示(対象スロットの進入軸線+整列リング)と (b) 数値読み出し(距離・軸ずれ角・相対速度)の 2 層 | KSP 等の慣行。3D だけでは残差が読めず、数値だけでは方向が掴めない | 手順 4・手順 5 |
| ガイドは「canDock 候補として最も近いスロット」に対し、距離 `DOCK_GUIDE_SHOW_DIST`(案: 300 m)以内で自動表示。手動 ON/OFF は設けない | 表示条件が自明で、設定項目を増やさない | 手順 4 |
| 既存の中央ハッチ判定は残す(ハッチにもガイドを出す) | ハッチ廃止は仕様の削除であり、今回の要求(ガイド追加)を超える | 手順 1・手順 3 |

## 達成目標

- `DEVELOP/SPEC/GAME.md` のドッキング節が、船ポート・軸整合条件・ガイド表示を記述している。
- 船の向きがスロット進入軸から大きく外れている(軸ずれ角 > 閾値)と、距離・速度を満たしても
  コンテキストメニューに「ドッキング」が出ない。
- 基地へ 300 m 以内に接近すると、戦闘ビューに対象スロットの進入軸線・整列リングと、
  距離・軸ずれ角・相対速度の数値が表示され、条件を満たすと表示が「可」状態に変わる。
- 船対船で、互いのポートを向け合ったときだけドッキングできる。
- `npm run typecheck` が通る。

## 手順

### 手順 1. SPEC/ の更新

**目的** — 仕様はコードより先行するため、まず GAME.md のドッキング節を書き換えて振舞いを
確定させる(`/modify-feature` の手順)。この時点でコードは変えない。

**変更が必要な箇所**

| ファイル | 何をするか |
| --- | --- |
| `DEVELOP/SPEC/GAME.md` 173-178行のドッキング節 | 下記の文面へ書き換え |

書き換え文面(案):

> - **ドッキングポート**: 船は機首に 1 基のドッキングポートを持つ。基地は 4 基のドックスロットと
>   中央ハッチを接続点として持つ(従来どおり)。
> - **ドッキング条件**: 船のポートと相手接続点について、距離・相対速度・**軸整合**(船のポート軸と
>   接続点の進入軸の向かい合い)がそれぞれ閾値内のとき、相手のコンテキストメニューに「ドッキング」が
>   現れる。船対船も同じ条件(互いのポート同士)。位置だけ合っていても、船が接続点へ機首を
>   向けていなければドッキングできない。
> - **ドッキングガイド**: canDock 候補の最寄り接続点へ一定距離まで接近すると、戦闘ビューに
>   その接続点の進入軸線と整列リング、および距離・軸ずれ角・相対速度の数値が表示される。
>   全条件を満たすと表示色が「可」に変わる。マップビューには出さない。
> - 格納・発進・基地パネルの振舞いは従来どおり。

**達成条件と検証** — `npm run typecheck`(SPEC のみだが規約どおり常に走らせる)。
`grep -n 'ドッキングポート' DEVELOP/SPEC/GAME.md` が 1 件以上。

作る。この時点で挙動は変えない(まだ誰も呼ばない)。

**変更が必要な箇所**

**達成条件と検証** — `npm run typecheck`。`grep -n 'getPortWorld' src/game/player/player.ts` が 2 件。

### 手順 3. 判定のポート化

**目的** — `Docking.canDock` を「船の位置がコーン内」から「船ポートの位置と軸整合」へ置き換え、
船対船も距離のみ判定からポート同士の判定へ変える。

**変更が必要な箇所**

| ファイル | 何をするか |
| --- | --- |
| `src/game/docking.ts` 69-106行 `canDock` | 基地: スロット/ハッチごとに「ポート位置が正面エリア内」かつ「`dot(shipPortNormal, -slotNormal) >= PORT_DOCK_MIN_ALIGNMENT`」へ。船対船: 互いの `getPortWorldNormal` の向かい合いと `PORT_DOCK_MAX_DIST` で判定 |
| `src/game/docking.ts` | ガイド・判定で共用する「最寄りの候補接続点(位置・軸・充足状況)を返す」内部関数を切り出す(手順 4 が使う) |

**達成条件と検証** — `npm run typecheck`。実機(`npm run dev`)で基地スロット正面に位置だけ
合わせ機首を横へ向けた状態ではコンテキストメニューに「ドッキング」が出ず、機首を向けると出る。

## リスクと落とし穴

| リスク | 影響 | 露見する場所 |
| --- | --- | --- |
| 判定を厳しくした結果、既存の難易度で実質ドッキング不能になる(RCS で姿勢を合わせつつ並走する操作が現行機体で可能か未実測) | 遊べない | 手順 3 の実機検証。`PORT_DOCK_MIN_ALIGNMENT` を cos 60° 程度の緩い値から始める |

## 実装詳細 (2026-08-24)

- 候補評価は `Docking.evaluateCandidate` を正本とし、距離・進入面の正面側・軸整合・相対速度を個別の boolean として返す。基地のスロットは既存の 50 m、中央ハッチは 80 m を接続点種別の捕捉距離として維持し、`PORT_DOCK_MAX_DIST` は船対船ポート間距離に適用する。候補には基地スロット番号を保持し、成立時の `dockTo`/`storeInBase` に同じ番号を渡す。
- 船ポートは機首局所 `+Z` の `SHIP_PORT_OFFSET` を `qRotate` でワールド化する導出値とし、セーブデータには追加しない。基地に対する船軸は接続点法線の逆向き、船対船は双方のポート法線が向かい合うことを判定する。
- ガイドは候補の `canDock` が false でも `DOCK_GUIDE_SHOW_DIST` 内の最寄り候補を表示する。Three の線・リングは初回生成して再利用し、`Game.sync` のカメラ/FloatingOrigin 確定後に transform を同期する。戦闘ビュー以外は非表示にし、`dispose` で scene、GPU、ラベルを片付ける。
- 数値は既存 `MarkerManager` の combat マーカーラベルに「対象名/スロット・距離 m・軸ずれ deg・相対速度 m/s・ドッキング可/調整中」を載せ、テーマの success/warning 色を利用する。
