未解決のものだけを扱う。方針は「コードベース自体を軽く保つ。新しい抽象層(サービス・
スケジューラ・スナップショット)を安易に足さず、負荷の原因になっている少数の箇所を直す」。
主眼は一時オブジェクトの削減ではなく、計算量そのものを下げることにある。

「確定した短期改善」、施策2・4・7・9は「要設計・独立変更」とする。品質設定とロード最適化は
本線完了後の別フェーズとし、施策19〜21は計測で必要になるまで廃止する。

## 目標と現在地

数値目標は絶対値で置く。

**戦闘ビュー。** Apple M4 Pro の MacBook(Retina、`window.devicePixelRatio = 2`)での実測は
**約 50 fps(1 フレーム 20 ms)**
最低限の目標は 60 fps だが、**これはハイエンド機での値であり、一般的な実行環境ではさらに落ちる**。
加えて**今後エンティティは増えていく**。したがって余裕を確保するため、
**M4 Pro で 100 fps 相当(1 フレーム 10 ms)の処理余力を目標とする。**
60 Hz の VSync 下で表示 fps 自体は検証できないため、VSync 無しまたは 120 Hz 以上の環境で計測し、
平均だけでなく p95 も判定に使う。

**マップビューの時間加速。** 同じ機体で ×131072 が 6 fps(166 ms/frame)、×65536 が
20 fps 前後(50 ms/frame)。**全ワープ段で 60 fps(16.7 ms/frame)を目標とする。**

予算として書くと:

| 目標 | 1 フレーム | CPU(update + sync) | GPU(render) |
|---|---|---|---|
| 戦闘ビュー 100 fps | 10 ms | 5 ms | 5 ms |
| マップ全ワープ段 60 fps | 16.7 ms | — | — |

マップ側の 16.7 ms は下の分岐モデルの節で substep 費用と固定費に分解する。

## 高ワープの構造 — 分岐(bifurcation)モデル

**これは「重い」問題ではなく、正のフィードバックが発散している問題である。**
最上位ワープ段を扱うときは必ずこの定式化から入ること。

`src/game/game.ts` の `update` は `const dt = Math.min(dtRaw, 0.1)` で実フレーム時間を
0.1 秒に飽和させる。`src/game/const.ts` の `SUBSTEP_MAX_DT = 20`(秒)。
`Simulator.advance` の substep 数に上限は無い。simDt = フレーム時間 × 倍率 なので、
**フレームが伸びれば substep が増え、substep が増えればフレームが伸びる。**

```
frame = (frame · W / maxStep) · c + fixed
  ⇒ frame = fixed / (1 − W·c/maxStep)      安定条件: W·c < maxStep
```

W = 名目倍率、c = 1 substep の費用、maxStep = `SUBSTEP_MAX_DT` = 20、
fixed = substep に依らないフレーム固定費。

**実測 2 点がこのモデルに一致する**(c = 236 µs、fixed = 11 ms):

| 段 | W·c/maxStep | 判定 | モデル値 | 実測 |
|---|---|---|---|---|
| ×65536 | 0.773 | 安定 | 11/0.227 = 48.5 ms = 20.6 fps | 50 ms / 20 fps |
| ×131072 | 1.547 | **発散** | 0.1 秒飽和に張り付き 656 × 236 µs + 11 = 165.8 ms = 6.0 fps | 166 ms / 6 fps |

**×131072 だけが安定領域の外にある唯一の段である。** 安定領域に戻れば
`simDt = frame · W` が厳密に成立し、**実効倍率が名目倍率と一致する — フレームレートと
待ち時間が同時に改善する。トレードオフではない。**

発散段では実効倍率が名目の 60%(×78,962)へ落ちている。この乖離は 2 経路でプレイヤーから
見える: (1) 倍率表示は名目値のまま、(2) `src/game/sim-speed-manager.ts` の
`estimatedRealSecondsToWarpEnd` は残り sim 時間を名目 `SIM_SPEED_LEVELS[i]` で割っており、
フレーム時間も 0.1 秒飽和も考慮していないため、**最上位段で残り時間表示が 1.67 倍過小に出る
(「あと 30 秒」と表示して実際は 50 秒待たされる)。**

**60 fps(16.7 ms)の予算配分。** fixed = 11 ms が予算の 3 分の 2 を占めるので、
**substep 全体に使えるのは 5.7 ms しかない。** したがって「×131072 で 60 fps」は
substep 側の課題であると同時に、**この 11 ms の固定費を今後増やさないという制約**でもある。

## 前提 — 現在のコードの状態

施策の議論の前提として、いま何がどうなっているかを記す。数値はすべて実測値。

### 天体暦の評価

node 実測(Apple M4 Pro、`tsconfig.test.json` 経由で `src/physics/` を直接呼んだ値):

- 天体は **101 体**登録(恒星 1・`kind: 'planet'` 49・`kind: 'satellite'` 51)。うち重力源
  (`mu !== 0`)は **64 体**。残り 37 体は `mu = 0` の表示専用だが**固体表面を持つ**ので、
  地表接触判定からは外せない。
- `Ephemeris.attractorsAt(t)`(101 体窓)= **126 µs/回**。
  `Ephemeris.gravityAttractorsAt(t)`(64 体窓)= **78〜85 µs/回**。
- 費用の **96.6% が `stateOf`**(Kepler 解と惑星-衛星系の重心補正)。`orientationOf`(姿勢モデル)は
  1.6%、`degree2` の構築と月の摂動級数(34 項)はいずれも 1% 未満。
  **「重い天体が数体ある」のではなく、101 体を毎 substep 全部評価している構造そのものが原因。**
- 時刻キャッシュ `TIME_CACHE_SLOTS = 32` は時刻の厳密一致でしか当たらない。中間キャッシュ
  `planetHelioCache` / `satelliteRelCache` も同様で、**substep ごとに時刻が変わるため毎回 101 ミス
  する**(実測確認済み: 未評価の t で miss +101、同じ t で miss 0、t+20 で再び miss +101)。
- `attractorsAt` 1 回あたりのヒープ増分は **約 10.1 KB**(101 個の `Attractor` + 101 個の
  `KinematicState` + 中間の `Vec3` 群)。
- **`Simulator.advance` は substep ごとに異なる 2 つの時刻で窓を引く**: `substep()` が重力用に
  `gravityAttractorsAt(simTime + subDt/2)`(**中点**)、`simulator.ts` の `advance` 内で
  `attractorsAt(simTime)`(**終端**)。後者は `EntityManager.cleanup` と
  `ContactPhysics.resolveSubstep` が使う。時刻が違うので中間キャッシュも共有されない。

### `attractorAccel` の実測ランキング(重力源 64 体、閾値 1e-10 m/s²)

- **LEO 420 km**: earth 8.643e+0 / moon 1.344e-6 / sun 3.510e-7 / jupiter 1.777e-12 /
  venus 1.891e-13 / saturn 1.085e-13 …。**4 体目で 1e-10 を下回る。**
  16 位以降 49 体の総和は 4.6e-17 m/s²。
- **月近傍(月から 1e7 m)**: moon 4.908e-2 / earth 2.901e-3 / sun 2.483e-5 /
  jupiter 1.203e-10 / venus 1.293e-11 …。**5 体目で 1e-10 を下回る。**
- **地球-月 L2 近傍**: earth 2.235e-3 / moon 1.370e-3 / sun 2.845e-5 / jupiter 1.376e-10 …。
  同じく 5 体目。

3 シナリオとも上位 4 体で 1e-10 まで完全に説明が付き、**残り 60 体の寄与総和は 1e-11 を下回る。
払っている費用と得ている精度が釣り合っていない。**

### RK4 の重力源スナップショットは中点評価が意図的である(維持すべき性質)

`src/physics/dynamics.ts` の `stepDynamics` は `stepRK4(state, dt, クロージャ)` を呼び、
**クロージャが束ねる `attractors` は k1〜k4 の全段で同一の配列**である。RK4 の各段は自前の時刻を
持たず、天体位置はステップ全体で 1 つのスナップショットに凍結される。スナップショットを区間の
中点で取ると誤差が O(dt²)、端点で取ると O(dt)。**中点評価はスナップショット近似を 2 次精度に
上げるための意図的な選択であり、維持しなければならない。**

### 姿勢積分

`src/physics/attitude.ts` の `ATT_MAX_SUB_DT = 0.04`、`ATT_MAX_DYNAMIC_STEPS = 12`。
刻みは `min(remaining, 0.04, 0.25/|ω|)`。**`subDt = 20` 秒に対して反復は必ず上限 12 に達し**、
残り 19.52 秒は解析 coast で畳まれる。**トルクも角速度もゼロのエンティティでも同じ 12 反復を払う。**

### `EntityManager.cleanup` と地表到達判定

- `cleanup` は `Simulator.advance` の **substep ごと**に走り、渡されている天体配列は
  **101 体の全天体窓**(`Ephemeris.attractorsAt`)である。`mu = 0` の 37 体も固体表面を持つので、
  これは意図どおりで 64 体窓には切り替えられない。
- `reachedBody` に到達する種別: `GameEntity` 既定(= `Ammo` / `Base` / `Asteroid`)、
  `DebrisPiece`(薬莢と破片の両方)、`Player`。到達しない種別: `Bullet`(`containingBody` の
  点判定のみ)、`Enemy`(`isBurnedUp` のみ)。
- `reachedBody` は全天体に `sweptHermiteSphereToi` を回し、命中が無ければ末尾で
  `containingBody` を **2 回**(区間の始点と終点)回す。`containingBody` は 1 体につき `Vec3` を
  1 個割り当てる。
- **`passiveWarpLod`(`simulator.ts` の高ワープ用 LOD、対象は `Bullet` と `DebrisPiece`)は、
  軌道積分・姿勢積分・イベント時刻走査からは対象を除外しているが、`cleanup` からは除外して
  いない。** 高ワープ中、弾・薬莢・破片は積分も姿勢更新もされないのに substep ごとに
  `checkLoss` をフルで払う。1 体あたり約 9 µs(101 体の掃引 + 202 体の距離計算と `Vec3` 割り当て)。
  薬莢は最大 260、破片は最大 600 なので、残存していれば 1 substep で 7 ms を超え、
  他の全項を一桁圧倒する。
- `sweptHermiteSphereToi` は遠方天体を軸平行箱テストで棄却するが、**その棄却に到達する前に
  Bezier 制御点の構築を全部済ませている**(約 100 基本演算)。最も安い「弦の始点から天体中心
  までの距離」は一度も計算されない。

## 施策一覧

### 施策 1 — substep の天体窓を 1 本に統一する【最優先・マップ】

**対象**: `src/game/simulation/simulator.ts` の `substep` / `advance`。

現在 substep ごとに 2 つの窓を引いている: 重力用 `gravityAttractorsAt(simTime + subDt/2)`
(64 体・中点)と、`cleanup` / `ContactPhysics.resolveSubstep` 用 `attractorsAt(simTime)`
(101 体・終端)。**101 体窓を中点で 1 回だけ引き、重力用の 64 体はそこから `mu !== 0` で絞る。
終端窓は廃止する。**

- filter の費用は実測 0.184 µs(101→64 の新規配列生成)で、評価費用 126 µs の 0.13%。
  **64 体窓という第二の全評価経路を持つ理由は無い。**
- `cleanup` / 接触が終端ではなく中点の天体位置を見ることになるが、**中点の方が安全側**である:
  `reachedBody` は天体を区間全体で同一位置に固定して掃引するので、引数の天体配列は既に
  「区間内のどこか 1 点のスナップショット」でしかない。区間内の最大ずれは終端なら
  `v_body · dt`、中点なら `v_body · dt/2` で、**中点は最大誤差が半分になり、かつ区間の前後に
  対称**。dt = 20 秒で太陽は 5.9e5 → 2.9e5 m、月は 2.2e4 → 1.1e4 m に減る。
- 実装: `substep` が中点で引いた 101 体窓を `advance` 側へ返す(戻り値にするか `private`
  フィールドに置く)。`advance` 内の `const attractorsNow = this.ephemeris.attractorsAt(this.simTime)`
  をそれに差し替える。`subDt <= 1e-9` の分岐と `stepPassiveWarpEntities` / `resolveBelt`
  (いずれもフレームに 1 回)は `ephemeris.attractorsAt` のままでよい。

**効果**: 暦費用が substep あたり 208 µs → 126 µs。マップ ×131072 のフレーム 166 ms → 112 ms

### 施策 2 — 天体ごとの鮮度階層(`AttractorWindow`)【マップの本命】

**対象**: 新規 `src/game/simulation/attractor-window.ts`、`src/game/simulation/simulator.ts`、
`src/physics/ephemeris.ts`(可視性の変更 1 箇所のみ)。

**すべての天体を毎 substep 評価する必要はない。** 天体ごとに据え置き可能時間を導く規則を入れる。

#### 規則

天体 b について、前回評価時刻からの経過を `age`、`δ = |v_b| · age`、エンティティ群の外接球を
中心 `c`・半径 `ρ` として `d = max(0, |r_b − c| − ρ)`。**次を全て満たす間だけ据え置く**:

1. `δ ≤ ε · min(|r_b|, d)³ / (2 μ_b)` (ε = `GRAVITY_NEGLIGIBLE_ACCEL`、`src/game/const.ts`)
2. `δ ≤ CONTACT_SLACK`(1 m 程度) **または** `d > radius_b + REACH_MARGIN + δ`
3. `age ≤ ATTRACTOR_HOLD_MAX_SEC`

条件 1 の根拠: 天体位置を `δ` 誤らせたときの加速度誤差は `|Δa| ≲ 2 μ_b δ / min(d, D)³`
(D = 原点からの距離)。第 2 項(ECI 原点補正項)は問い合わせ位置に依らないので、
`|r_b|` と `d` の小さい方で測る必要がある。係数 2 を条件側に入れ、1 天体あたりの加速度誤差を `ε` 以下とする。

条件 2 の根拠: 据え置いた天体の表面判定は半径 `δ` ぶんの誤差になる。条件 2 は
「**据え置き天体には誰も触れられない**」を直接述べる。ただし、この主張は substep 内のエンティティ移動量を
安全な上界で覆った場合に限る。門が落ちればその天体は新鮮になり判定は厳密。

条件 3 の `ATTRACTOR_HOLD_MAX_SEC` は既存の `ATTRACTOR_REBUILD_SEC = 3600` を流用する。
`Predictor.advanceBudget` と `PlanArc.integrate` が同じ判断で既に使っている値で、
本体シミュレーションが予測より緩くならない担保になる。

**読む量は `μ_b`・`radius_b`・`|r_b|`・`|v_b|` と、エンティティ群の外接球だけ。天体の id を
一切含まない**(登録レジストリは差し替え可能で、`src/game/stages/stage-debug-alt-system.ts` は
太陽も地球も無い独自レジストリを使う)。`mu = 0` の表示天体 37 体は条件 1 が常に真になり、
遠ければ永久に据え置かれる。

**据え置きは凍結する(線形外挿しない)。** 外挿は誤差をさらに下げるが `|a_b|` の見積もりを要し、
レジストリ非依存に得るには「前回の外挿残差から曲率を学習する」フィードバックが必要になる —
これは「重力が静かに間違う」経路を 1 本増やす。凍結だけで 43 倍が取れているので採らない。

**原点天体は永久に据え置ける**: `stateOf(originId, t)` は定義上ゼロが厳密に恒等で、
`pole: 'eciPole'` / `c22 = 0` なので `degree2` も時刻に依らない(t = 1e5 と t = 9e7 の
`Attractor` が完全一致することを実測で確認済み)。

#### 置き場所は `game/simulation/`。`Ephemeris` の中には入れない

理由は 3 つ:

- `Ephemeris.attractorsAt(t)` の契約は「同じ t なら同じ配列参照を返す」で、返り値は t だけの
  関数である。据え置きを入れると返り値が呼び出し履歴に依存し、この契約が偽になる。
- 据え置きの門はエンティティの外接球を要求するが、`Ephemeris` はゲーム側のエンティティを
  知らないし知ってはいけない。
- `TimeRing` は「同じ時刻を再度引いたら計算を省く」メモ化で返り値は厳密。据え置きは
  「違う時刻を同じ値で答える」近似で、種類が違う。

**`Ephemeris` に必要な変更は 1 つだけ**: `private attractorAt(id, t): Attractor` を public に
する(1 天体ぶんの評価が外から引けないと、更新したい天体だけを評価できない)。
任意の追加最適化として `stateOf(id, t)` の冒頭で `id === this.originId` なら即ゼロを返す短絡
(厳密に等価)。

#### `AttractorWindow` の形

- `held: Attractor[]`(`ephemeris.ids` と同じ長さ・同じ順序)
- `evaluatedAt: number[]`
- `phaseGeneration: number`(`Ephemeris.phaseGeneration` の控え)
- 出力用の再利用配列 2 本

公開メソッドは `at(t, clusterCenter, clusterRadius): { all, gravity }` の 1 本。
`phaseGeneration` が変わっていたら全数再評価する(**セーブ/ロード整合**。`setPhaseOffsets` が
全キャッシュを捨てるので世代値を見張るだけで足りる)。**返り値は次の `at()` 呼び出しまでしか
有効でない**(`attractorsNearInto` と同じ所有規約)ことをコメントに明記する。

`Simulator` 側は、外接球を `entities.all()` の生存個体の `state.r` から min/max で作る
(O(N)、N = 400 で約 2 µs)。半径に足す substep 内移動上界を `最大速度 × subDt` だけで済ませない。
推力・近傍天体重力・接触インパルス・区間内イベントを考慮した保守的な上界(概念的には
`vMax · dt + 1/2 · aMax · dt²`)を導出する。安く厳密な `aMax` を得られない場合は、近接可能な天体を常に更新する側へ倒し、
「見逃しが構造的に不可能」とは主張しない。
**動的重力天体(`Asteroid` 等)は据え置き対象外**で、`entities.attractors()` を毎 substep
そのまま `mergeAttractors` で合流させる(実位置を持っているので評価費用がゼロ)。

#### 効果(実測)

substep あたりの暦費用 208 µs → **4.8 µs(43 分の 1)**。1 日ぶんの積分での位置誤差は
LEO 420 km で **1.66e-2 m**、低月周回 1.9e6 m で 1.29e-4 m。7 日で 0.14 m。
64 体中 62 体が実質凍結し、太陽だけが毎 substep 更新、月は約 5 回に 1 回。

**分岐モデルへの反映**: 施策 1 + 2 で c が 236 µs → 約 33 µs になり、×131072 で
`W·c/maxStep = 0.216 < 1` となって**安定領域に戻る**。frame = 11/(1 − 0.216) =
**14.0 ms = 71 fps**。**`SUBSTEP_MAX_DT` を触る必要が無くなる**(積分精度を落とす判断を回避できる)。

#### 危険度: 高(失敗すると重力が静かに間違う)

実装ミスと症状の対応表:

| 実装ミス | 症状 |
|---|---|
| `evaluatedAt` を更新し忘れる | 天体が永久凍結。太陽が動かなくなり数日のワープで軌道が徐々に狂う。**画面上は完全に正常に見える**(太陽の描画は表示経路の厳密値を使うため) |
| `min(D, d)` を `D` だけにする | 月周回・木星圏で近傍天体が据え置かれ、艦がその天体の重力を数十 km ずれた位置から受ける。軌道が静かにずれ、**再突入判定が「大気圏突入により喪失」の誤表示として表面化する**(`NanWatchdog` は非有限値しか見ない) |

| `phaseGeneration` を見ない | セーブロード直後だけ軌道が飛ぶ |

**既存テストは 1 件もこの変更を検出しない**(`tests/physics/ephemeris.test.ts` /

2. 据え置いた重力和の誤差が `GRAVITY_NEGLIGIBLE_ACCEL × 天体数` を超えない(1 日ぶんの刻みで

3. エンティティ群の外接球を月の位置に置くと月は必ず毎回更新され、原点近傍へ戻すと据え置かれる

4. 据え置かれている天体はすべて `|r_b − c| − ρ > radius_b + REACH_MARGIN + δ` を満たす

### 施策 4 — `reachedBody` に凸包球による O(1) 棄却を入れる【マップ・戦闘の両方】

**対象**: `src/physics/sphere-contact.ts`(純関数を 1 本追加)、`src/physics/attractor.ts` の
`reachedBody`、`tests/physics/`。

`reachedBody` は全天体に `sweptHermiteSphereToi` を回し、命中が無ければ `containingBody` を
2 回(始点・終点)回す。掃引の棄却は現在、Bezier 制御点の構築(約 100 基本演算)を全部
済ませてから行われる。

Hermite を 3 次 Bezier に直したときの制御点は `P0 = r_s`、`P1 = P0 + T0/3`、`P2 = P3 − T1/3`、
`P3 = r_e`(いずれも**天体相対**、`T = (v − v_body)·dt`)。曲線は制御点の凸包に含まれるので、
`P0` 中心の球で覆える:

```
L    = |r_e − r_s|                 (弦長)
hull = max( |T0|/3 , L + |T1|/3 )  (P0 からの最大到達距離)
棄却条件: |r_s − r_body|² > (hull + body.radius + margin)²
```

**真の交差を落とすことは原理的にない**(凸包の包含から導かれる十分条件)。
**天体自身の速度を無視すると壊れる** — `T` は `v_entity − v_body` でなければならない
(ECI で太陽は約 30 km/s、月は 1 km/s で動く)。`L` の計算に天体の始点位置と終点位置の
どちらを使うかで最大 `|v_body|·dt` ずれるので、安全側に倒すなら `hull` に `|v_body|·dt` を加算する。

**さらに `containingBody` の 2 × 101 体走査を同じループへ畳める**: 棄却された天体は
`|r_s − r_body| > hull + radius + margin ≥ radius + margin` なので `prev.r` を含まず、
`r_e` は `hull` 球の内側なので `next.r` も含まない。**棄却された天体に対して
`containingBody` を回す必要が無いことが証明できる。**

**効果**: 掃引の定数が約 100 演算 → 約 8 演算(**約 12 倍**)。加えて `containingBody` の
`Vec3` 割り当てが実質 0 になる(マップ高ワープでは毎フレーム 1700 万個規模)。

**危険度**: 低(数学的に安全側)。**依存**: なし。

**回帰テスト 4 件**(`tests/physics/sphere-contact.test.ts` または新規
`tests/physics/reached-body.test.ts`):

- (a) **`hermiteHullRadius` が上界であること** — `mulberry32`(`src/math/vec3.ts`)固定シードで
  入力を生成し、`hermiteInterpolate`(`src/physics/kinematic-state.ts`)で u = 0..1 を
  1000 分割して評価、全点が `|C(u) − prev.r| ≤ hullRadius` を満たすことを数百ケースで assert。
  **上界性の直接のピン留めで、本案の安全性の要。**
- (b) **棄却前後の等価性** — 同じ乱数列で天体配列を作り、棄却を入れない参照実装(テスト内で
  ベタに全数掃引する版)と `reachedBody` の返り値が全ケースで一致すること。
  **掠める配置(距離が `radius + margin` の ±0.1%)を明示的に混ぜること。**
- (c) 既存 2 件(「1 フレームで完全に貫通する高速個体」「弦は外れているが曲線が膨らんで届く通過」)を
  `reachedBody` 経由でも捕まえること
- (d) エンティティがほぼ静止し天体が 30 km/s で近づいて到達する配置 —
  **エンティティ速度だけで `hull` を作る実装ミスを確実に殺す**

### 施策 9 — `InstancedPool` の毎フレーム全容量アップロードをやめる【戦闘】

**対象**: `src/render/instanced-pool.ts`。

`count` を容量に固定したまま未使用枠をゼロ行列で潰す設計のため、実在数に関わらず毎フレーム
14,788 インスタンス・約 248,000 三角形ぶんの頂点シェーダが走り、`instanceMatrix` 約 946 KB +
`instanceColor` 約 131 KB を毎フレーム転送する。**弾が 0 発でも 1200 枠ぶん走る。**

この施策は二つに分ける。

- **9A 転送削減**: `BufferAttribute.updateRanges` で使用範囲だけを GPU へ転送する。
- **9B draw 削減**: チャンク分割や小容量プール化により、未使用インスタンスの頂点シェーダ実行も止める。

9A だけでは `count` が容量固定のままなので頂点シェーダ実行数は減らない。9B は three の

**危険度**: 中(three の内部挙動に依存する。black screen になる類の失敗がありうるので、

### 施策 11 — 最大ワープでの予測列の破棄ループ【マップ】

**対象**: `src/game/game-entity/game-entity.ts` / `src/game/simulation/predictor.ts`。

**ヘッドレス実測で実在を確認済み**: マップ ×65536 と ×131072 のどちらでも
`予測 tracked 6 / complete 0 / discard 6` が毎フレーム続く。予測列が毎フレーム破棄され
作り直されている。`discardPredictionIfDiverged` が `predictedTrajectory.at(simTime) === null` を
無条件破棄にしている分岐が、最大ワープでは常に成立していると見られる。列生成直後は `history` が
空で、最初の push は「前回 state が最新サンプルから `sampleInterval` 以上離れたとき」なので、
それまで `at(t)` は `t === state.t` 以外すべて `null` を返す。

分岐させる: `history` が空(生成直後)なら破棄せず猶予、先端が `simTime` より後ろなら破棄。

**予測は計画軌道の重力源・衝突候補でもある**(`planAttractorsAt` が `displayState(t)` を読む)
ので、破棄ループは表示だけの問題ではない。破棄が止まらない限り、計画軌道が見る重力源集合が
毎フレーム揺れる。

**効果**: マップ高ワープの `予測` 区間 0.9 ms と、計画軌道の再積分の安定化。
**危険度**: 低。**依存**: なし。

### 施策 19 — `classifyAttractors` のメンバーシップ再利用【廃止】

**対象**: `src/game/simulation/attractors.ts`。

高ワープでは substep ごとに `classifyAttractors` が μ の sort と `SpatialGrid` 構築を
やり直す(×131072 で 656 substep/frame)。再利用してよいのは分類**構造**(μ の sort 結果 =
always/grid のメンバーシップ)だけで、`Attractor` は `state`(位置)を抱えているため配列ごと
凍結すると重力源の位置まで凍結してしまう。よって always/grid の構成だけを有効期間付きで
再利用し、state は substep ごとに差し替える。全エンティティが同一分類を見る対称性は保つ。

**ただし μ が時刻に依らない一方で天体の位置は substep ごとに変わるため、グリッドへの挿入は
やり直しになり、省けるのは 64 要素の sort だけ。効果は小さいと見込まれる。加えて失敗すると
重力が静かに間違う。実測で必要と分かってから着手する。**

`isOccluded` を全候補について毎フレーム走査している。カメラまたは対象位置が閾値以上に変化した

ため、他の項目の後に回す。** 遮蔽判定自体は 291 件で 0.055 ms/frame と軽く、単独では急がない。

### 施策 22 — substep 数のガードレール

**対象**: `src/game/simulation/simulator.ts`、`src/game/sim-speed-manager.ts`。

**主策としてではなく、最悪フレーム時間の保証として。** 1 フレームの substep 数に上限を設ける。
`debug-load`(小惑星 300 + 破片 500)の 1 フレーム 12 秒は施策 1・2 でも救えず(必要な
`SUBSTEP_MAX_DT` が 2,400 秒になる)、上限だけが救う。

**同時に `SimSpeedManager.estimatedRealSecondsToWarpEnd` を実測フレーム時間ベースへ直すこと。**
現在は残り sim 時間を名目 `SIM_SPEED_LEVELS[i]` で割っており、フレーム時間も 0.1 秒飽和も
考慮していないため、**最上位段で残り時間が 1.67 倍過小に出る(「あと 30 秒」で実際は 50 秒)。
これは新しい案の副作用ではなく既存の欠陥の修正である。**

**プレイヤーから見える変化**: 上限に当たった段では実効倍率が下がり、待ち時間が延びる。

**危険度**: 低。**依存**: 施策 1・2 の後に、まだ発散する条件が残っているかを測ってから。

## 否定された仮説(同じ調査をやり直さないための記録)

- **戦闘ビューの重さはエンティティ数に比例する費用である**: 誤り。ヘッドレス実測で CPU 側は
  放置 4.7 ms・連射中 6.7 ms にとどまり、実機の 20 ms を説明しない。差の 13〜15 ms は GPU 側で、
  解像度に比例する固定フラグメント負荷(`devicePixelRatio` 上限なし + MSAA 4× + 全画面パス 3 枚)
  である。**「どの局面でも 50 fps」という観測そのものが、エンティティ数に依らない固定費で
  あることの証拠である。**
- **地球のジオメトリ分割が重い**: 誤り。`src/render/earth.ts` は `src/render/screen-lod.ts` の
  `SPHERE_LOD_LADDER`(64×48 / 160×120 / 384×288)による 3 段 LOD を持ち、戦闘ビュー
  (見かけ直径 1,586 px)では最下段 64×48 = **6,144 三角形**が選ばれる。地球のジオメトリは既に
  安く、削る余地が無い。**「157 万三角形 / 約 44 MB」という前提は現在のコードに当てはまらない。**
- **高ワープの支配項は軌道積分そのものである**: 誤り。マップ ×131072 の `積分` 185.35 ms のうち
  `軌道積分` は 72.04 ms で、残る約 107 ms は substep ごとに引く 101 体の天体窓と `cleanup` である。
  暦評価だけで 1 フレーム 137 ms(観測 166 ms の約 83%)を占める。
- **接触グリッドのセル幅を膨らませている支配項は弾の移動量である**: 誤り。区間移動量の絶対値を
  見ていたために、全参加者が共通して持つ ECI の軌道速度(1 substep で km 単位)がそのまま
  セル幅を決めていた。接触の成否を決めるのは相対変位なので、参加者集合の平均変位を差し引いた
  量で測ると、弾も薬莢も同じ軌道に乗っている限りセル幅には効かない。
- **放熱板の接触代理体の作り直し**: 起きていない。`src/game/player/radiator.ts` は
  `RadiatorFold` をプールし、以後は状態を書き直すだけ。プロファイルに現れない。
- **薬莢・破片の姿勢積分が戦闘ビューの主因である**: 誤り。時間加速なしでは substeps が 1 で、
  `stepAttitude` は self time 上位 25 位に入らない(ヘッドレス実測の `姿勢` 区間も
  戦闘放置 0.00 ms / 連射中 0.02 ms)。
- **`Enemy.radius` がセル幅の支配項である**: 誤り。`ENEMY_RADIUS`(180 m)ではなくメッシュの
  バウンディング球から取った 67.2 m(`src/game/game-entity/enemy.ts`)。

## 保留(着手しない判断が済んでいるもの)

- **multi-rate 積分**(エンティティ別の許容誤差刻み): 高ワープの実測上の主因は per-entity 刻みの
  不在そのものではなく構造増幅である。構造増幅を除いた後の実測で、なお艦 50 の巡航が支配的な
  場合のみ検討する。propagator 切替の連続性・保存決定性の検証コストが大きい。
- **`toEvaluatorEphemerisPack` の boxed 配列の除去**: .epk 復号後に payload 全体を
  `Array.from(...)` で約 53 万個の boxed number へ変換し、`ChebyshevEphemeris` のコンストラクタ
  (`copyBody`)がさらにコピーしている。起動時にしか効かず、分量も小。着手するなら
  `ChebyshevEphemeris` の「入力配列をスナップショットして凍結する」性質(呼び出し側が後から
  元配列を壊しても評価器が汚染されない)を落とさないこと。
- **コード分割**(webpack chunk): .epk とテクスチャは既に個別ファイルで遅延 fetch 可能。
  js 本体の分割は three が大半を占めるため効果が薄い。施策 15 の後に再評価。
- **`physics/` の可変スクラッチ再導入**: immutability は明文化された意図的トレードオフ
  (`CLAUDE.md`)であり、`*Into` の再導入はしない。GC が問題になる場合の答えは substep 数の
  削減で、割り付けの「回数」を減らす。
- **テクスチャの `createImageBitmap` 非同期デコード**: 施策 16 と直交に、ロード時のメイン
  スレッドブロック(JPEG デコード)を消す。要計測。
- **KTX2/BasisU 圧縮テクスチャ**: 配信サイズだけでなく VRAM とアップロード時間も削る。
  jpg 縮小より効果が大きい可能性があるが、パイプライン(変換ツール・ローダ)の導入コストと
  引き換え。
- **マップビュー中の物理の停止・タイムワープの停止・積分頻度の低下・再突入/寿命/衝突判定の
  間引き・マップ表示設定による重力源の削除**: いずれもゲーム挙動を変える。描画軽量化の
  解決策として採用しない。

## 負荷確認ウィンドウの使い方

**今後の作業では必ずこれを使う。**

- **開き方**: `F3`、または ESC メニューの項目。`?perf=1` を付けて起動すると最初から開いている。
  窓は非モーダルで、ゲームは止まらない。
- **窓**: `src/game/hud/property-window.ts` の `PropertyWindow` をそのまま使っている。
  ヘッダをドラッグして移動、📌 でクリップ(常駐)、✕ で閉じる。セクション見出しのクリックで
  各群を開閉する。レイヤは `hud.layers.window`。
- **計測は窓が開いている間だけ走る。** 閉じていれば `performance.now()` は計測目的で 1 回も
  呼ばれず、通常プレイに計測費用がかからない。**逆に、窓を閉じた状態の数値は取れない。**
- **更新は 500 ms ごとのフラッシュ。** 行の差分更新は `PropertyWindow.syncRows` が内蔵している。
- **割合は塗り文字**(`████░░░░ 12.3ms`)で示す。基準は 16.7 ms(60 fps の 1 フレーム)。

読める値:

| 群 | 行 |
|---|---|
| (常時表示) | `fps` / `frame`(update+sync+render の合計 avg・p95)/ `warp`(現在倍率) |
| フレーム時間 | `update` / `sync` / `render` 各 avg・p95・max |
| update内訳 | `update` の区間別 avg・max — 入力 / 自機 / ステージ / 積分(内訳として字下げで 軌道積分・接触・姿勢)/ 予測 / 演出 / 計画 / マップ候補 / カメラ / ポインタ / **その他**。通らなかった区間も 0.0 ms の行として出る |
| 計画軌道 | `recompute`(再積分回数/frame)/ `steps`(積分ステップ/frame) |
| 予測 | `tracked` / `complete` / `discard` / `steps` |
| シミュレーション | `substeps` / `entitySteps` / `gravitySources` |
| 暦キャッシュ | `attractorsAt hit/miss` / 全リング `hit/miss` |
| 表示 | `view`(combat/map)/ `pickables` / `labels` / 表示期間 |
| エンティティ | `players` / `enemies` / `bullets` / `casings` / `debris` / `ammos` / `asteroids` / `bases` |
| メモリ | `JS heap` |

暦キャッシュのヒット/ミスは `Ephemeris` 側では累積値で、窓が前回との差分を取って表示する
(`Ephemeris` はフレームの概念を持たない)。セーブロードを跨いでもリセットしない。

**`update` の区間は入れ子ではない。** 積分の内訳 3 区間(軌道積分・接触・姿勢)は表示上だけ
字下げしてあり、合計が親の「積分」を成すわけではない。`その他` は計測点を持たず、`update` 全体から
各区間の合計(積分の内訳は除く)を引いた差として出るので、区間の外へ時間が逃げていればここに
現れる — `src/game/nan-watchdog.ts` の全エンティティ走査、`docking.checkProximity`、
`targeter.updateBoardMarks` はどの区間にも属さずここへ落ちる。

## 検証の作法

### 固定ベンチマークと完了条件

各施策は、成功指標・許容差・撤退条件を実装前に数値で書く。計測は同一ブラウザ、同一ウィンドウサイズ、
同一 DPR、同一 seed、同一ウォームアップ時間、同一観測秒数で before/after を取り、平均と p95 を記録する。

固定シナリオは次の通り:

- stage1 戦闘放置
- stage1 連射中
- 弾・薬莀・破片が上限に近い状態
- stage1 マップ ×65536 / ×131072
- `stage-debug-load`
- 移動天体との接触・表面到達
- 1 日 / 7 日積分後の位置・速度差

代表的な完了条件:

- 施策 6: DPR 2 / 1.5 / 1.0 の A/B でフレーム時間がピクセル数に応じて下がり、DPR 1.5 で実機戦闘ビューの
  p95 が 12 ms 以下。改善が 15% 未満なら DPR 律速の仮説を棄却して再調査する。
- 施策 1・3・5・11: 対象区間の p95 が下がり、物理・イベント順が所定の絶対誤差内で一致する。
- 施策 2・4: 記載した不変条件テストを全て通し、1 日 / 7 日の軌道差と接触結果を絶対値で判定する。

施策 1・2 後は allocation bytes/frame、minor GC 回数、最大 GC 停止時間、JS heap の鋸歯状変動も再計測する。
一時オブジェクト削減を目的化するのではなく、substep 数を減らした後に GC が p95 の律速項として残ったかを確認する。

- **各施策ごとに `npm run typecheck`。** これは常に走らせる。
- **`npm run test:physics` は `physics/` を触ったときだけ。** 施策 2(新規
  `attractor-window.test.ts`)、施策 4(`sphere-contact` / `attractor`)、施策 5(`attitude`)が
  これに当たる。
- **`npm run build` は総合検証時のみ。** `docs/` の公開バンドルを書き換えるので、ロードサイズを
  記録する必要があるときに走らせる。
- **物理不変条件**: 同じ初期スナップショット・同じ経過 sim time に対し、表示設定を変えても
  物理 state(位置・速度・イベント順・破壊結果)が一致すること。表示設定と無関係の常時挙動を
  変える施策(施策 1〜5)は、変更前後で「許容誤差内の一致」を `stage-debug-load` +
  スナップショット比較で確認する。**許容誤差は絶対値で置く。**
- **設定の検証**: 保存・復元・不正値フォールバック・preset→カスタム遷移。
- **ロードの検証**: `docs/` 合計サイズと、キャッシュ無効での初回表示時間(WebGPU init 〜
  初フレーム)を before/after で記録する。

ヘッドレス検証(`/verify`)の注意点:

- **`--mode development --no-client-overlay` が要る。** production ビルドをそのまま headless で
  開くと dev-server のオーバーレイが被る条件がある。
- **`localStorage.clear()` が要る。** 前回のセーブスロット・トグル状態・品質設定が残っていると
  起動先(タイトル/ステージ/クリエイティブ)も表示条件も再現しない。
- **CDP の `Input.dispatchKeyEvent` は `rawKeyDown` では DOM の `keydown` が届かない。
  `type: 'keyDown'` + `text` が要る**(Space を含む全キー)。
- **`?stage=debug` はマップ高ワープの定常観測に使えない。** 起動 18 秒の時点で至近の敵編隊との
  接触により「SHIP LOST 高速接触により機体を喪失した」となり `isPlaying` が false になって
  `ViewManager` が戦闘ビューへ強制復帰する。**マップ高ワープの観測は `?stage=1` のマップビューで
  取る**(高ワープ中は `canEnemyFire` で敵の射撃が止まるため 25 秒程度の定常観測が持つ)。
- 負荷確認ウィンドウの値は DOM から直接読む方が確実(`src/game/hud/property-window.ts` の
  行要素を CDP の `Runtime.evaluate` で辿る)。**`update内訳` 群は既定で折りたたまれている。**
- **ホイールズームが効かない。** 遠距離ズームに依存する確認(ラベル混雑、小天体の表示、
  リングの線/面クロスフェード)はヘッドレスでは取れない。
- **stage1 は約 2 分で撃墜される。** それより長い定常観測が要る条件では、`stage-debug` 系
  (`checkWin()` が常に false)を使う。
- render の絶対値は実機と乖離する。カウンタ類だけが環境非依存であることを踏まえて読む。
