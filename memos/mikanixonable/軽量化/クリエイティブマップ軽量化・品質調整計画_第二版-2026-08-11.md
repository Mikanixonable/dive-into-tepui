# クリエイティブマップ軽量化・品質調整計画 第二版

第一版のレビューにもとづく全面改訂。第一版の負荷モデルはオーダー推定だったが、本版は
コードの現物確認と node 上での実測(本番と同じ暦パックを読み込んだ `Ephemeris` に対する
ベンチ)にもとづく。方針も改める: **コードベース自体を軽く保つことを第一とし、新しい抽象層
(サービス・スケジューラ・スナップショット)を足すのではなく、負荷の原因になっている少数の
箇所を直す。** 計測の結果、支配的な負荷のほとんどは「アーキテクチャの不在」ではなく
「既存の正しい仕組みを無効化している具体的な数行」に由来することが分かったためである。

**現況**: P0(第 1 弾)・E 群・C 群(C-1/C-2/C-3 のセル鍵)まで実施済み。×1 マップの支配項、
長い表示期間での計画積分の永続化、高ワープでの暦キャッシュ崩壊、debug-load(小惑星 300)の
高ワープでのタブ無応答は、いずれも解消した。debug-load ×16384 は無応答から 1.4〜1.6 s/frame、
×4096 は約 2,046 ms から 357〜381 ms になっている。残る未解決は、最大ワープでの予測列の
毎フレーム全数破棄と、`classifyAttractors` のメンバーシップ再利用(C-3 の残り)。
残る作業の主眼は「一時オブジェクトの削減」ではなく「計算量そのものを下げること」にある。

## 実施済み

表から外した項目。何が済んだかを失わないためにここに残す。

- **A-1**(plan provider の revision から `simTime` を外す) — P0 で実施。ノードを触らない
  ×1 マップでの PlanArc 再積分は 0/frame。
- **A-7**(`TIME_CACHE_SLOTS` 4 → 32) — P0 で実施。高ワープでのミス 1 回あたりの費用は
  下記 E-2 で下げた。
- **A-11**(ラグランジュ点の二重評価解消) — codex が `focus-markers.ts` の
  `cacheBodyPickable` + `bodyPickables` のキャッシュで達成。
- **B-5**(`Predictor` の固定費と予算配分) — P0 で実施。
- **E-1**(長い表示期間での計画積分の永続化) — 実施。直したのは 3 点:
  ①`planSourceRevision` が畳み込む予測の寄与を、先端時刻の量子化値から
  **「その個体の予測が計画の終端まで届いたか」の 3 値**(予測を持たない/届いていない/
  届いた)へ変更。届くまでの間は値が変わらないので再積分しない。単調なので振動しない。
  ②`PlanArc.integrate` が重力源・衝突体・空間分類を `ATTRACTOR_REBUILD_SEC` ごとにだけ
  組み直すようにした(`Predictor` が既に使っていた方式)。中点・終点の時刻は毎ステップ一意で
  暦の時刻キャッシュに当たらないため、1 ステップごとに引くと区間全体の費用がその 1 点で
  決まっていた。定数は予測と計画で共有(旧 `PREDICT_ATTRACTOR_REBUILD_SEC` から改名)。
  ③あわせて B-1 の一部(`findImpact` の線形探索の Map 引き化)も実施。
- **E-2**(高ワープでの天体窓) — 実施。`Ephemeris.gravityAttractorsAt(t)` を追加し、
  `mu !== 0` の天体(101 → 64 体)だけを最初から組む専用の窓とした。`gravityBodiesAt` が
  これを使う。全天体の窓は遮蔽・地表接触・中心天体の解決に引き続き必要なので残る。
  `attractorsAt` の対応要素と値が厳密に一致することを `test:physics` で検証している。
- **C-1**(イベント時刻走査の substep 間キャッシュ) — 実施。エンティティ側の最小イベント時刻を
  `advance` の中で控え、`EntityManager.collectionRevision`(顔ぶれの世代。public getter を
  新設)が変わったとき・イベント時刻を通過したとき・LOD の切替時にだけ引き直す。
  **ステージ側は控えない** — `PlanExecutor` の点火時刻は艦の現在の Δv と加速度から毎回決まる
  生きた値だから。あわせて、まとめ積分に回る個体(弾・薬莢・破片)を境界の候補から外し、
  LOD の意図と実装のズレを解消した。`CreativeStage` の毎 substep の配列生成も除去。
- **C-2**(再突入刻みのグローバル適用) — 実施。**当初案(低高度個体だけを substep 内で
  細分する)は採らず、原因を分解して組み替えた。** 細かい刻みが要る理由は「検出」と
  「加熱・動圧の積分」の 2 つで、性質が違う。
  - 検出: `physics/attractor.ts` に `reachedBody(prev, next, bodies, margin)` を追加し、
    前ステップ位置から現ステップ位置までを**掃引**して判定する(`sphere-contact.ts` の
    `sweptHermiteSphereToi` を再利用 — 1 ステップで軌道が明確に曲がる長さなので直線掃引では
    足りない)。粗い刻みでも天体を貫通して素通りしない。
  - 積分: 本当に細かい刻みが要るのは艦だけなので、substep 上限の判定に含めるエンティティを
    `players` と `enemies` に限定した。**判断の根拠は「加熱・動圧の積分結果が存続を左右し、
    その帰結をプレイヤーが観測するのは艦だけ」**で、他の種別は大気圏に入れば失われるだけ。
  - **副産物のバグ修正**: 高ワープでは接触物理が止まるうえ `Player.checkLoss` に地表到達の
    判定が無く、**自機がどの天体も素通りできた**。喪失理由として追加した
    (`DEVELOP/SPEC.md` にも記載済み)。
- **C-3 の一部**(セル鍵の文字列生成) — 実施。入れ子の `Map`(cx → cy → cz)へ置き換えて
  解消した(畳み込みハッシュは異なるセルの衝突が静かな破壊を招くので採らない)。
  メンバーシップ再利用は未実施で、C 群に残る。

## codex が入れた計画外の改善

同じ調査を繰り返さないための記録。

1. `Game.resolveWindowIfStale()` — simTime・表示設定・自機状態が変わらなければ
   `currentOrbitPeriod()`(101 天体走査)を呼ばない。フレーム 2 回 → 1 回。
   `DisplayTimeManager` に revision を新設。
2. `Game.mergedAttractorsAt()` — update と sync で同じ合流配列を再利用。
3. `MapVisibilityPolicy` の結果メモ化(`bodyResults`/`entityResults`)。
4. `EntityManager.getCombatTargets` のキャッシュ。
5. `Ship` のパーツ type 別参照テーブル — `totalThrust`/`totalTorque`/`totalFuel` 等の
   getter から `filter`+`reduce`+spread を除去。getter は毎フレーム多数呼ばれるため効果が大きい。
6. `ContactPhysics` と `Simulator` の全面 scratch 化。
7. `PlanPath.unbakeTransform` — `frameTransformAt` を update 単位 1 回に。
8. `mapPickables()` の配列キャッシュ(`nav-target.ts` / `equator-node-markers.ts`)、
   `PredictedTrajectoryLine` の `new Set` 除去。
9. `PointBody.outerRadius` の事前計算と `sunDirFrom` の重複呼び除去。

**性格づけ**: codex の変更は一貫して「アロケーション削減(一時オブジェクトの再利用)」であり、
**計算量そのもの(O(N²) の線形探索・全候補走査・毎 substep の再分類)にはほとんど手が
入っていない。** したがって B 群・C 群に残っているのは、より効果の大きい「次数を下げる」
側の作業である。

C 群 についての補足:

- **恒久的な無応答は解消した。** debug-load ×4096 の軌道積分回数は 123,795 → 約 6,770
  (約 1/18)。
- **stage1(小惑星なし)の substeps は 656 のまま変わらない。** C-2 は低高度に個体がいるとき、
  つまりエンティティが多い状況でのみ効く。stage1 ×131072 に残る約 190 ms は
  656 substep ×(暦 + 分類 + エンティティ)の素の費用。
- エンティティの一斉消滅は起きていない(小惑星 300 は全ワープ段で維持、破片は緩やかな
  再突入減衰のみ)。描画も正常。例外は全条件で 0 件。
- **残る問題**: stage1 ×131072 で `pred-discard` が毎フレーム全数(マップ 6 / 戦闘 1)。
  最大ワープでは予測列が毎フレーム破棄され作り直されている。B-5 で予算配分は直したが、
  最大ワープではまだ破棄ループが残っている。
- debug-load ×131072 は 1 フレーム 12 秒で、スクリーンショットの取得すらタイムアウトする
  (数値は取得できる)。

E 群 についての補足:

- 28 日表示では `plan-arcs` が押下直後から 0。再積分は**単発のスパイクが数回だけ**
  (3 秒・10 秒・18〜22 秒時点)で、以降は 0 のまま。これは各個体の予測が計画の終端に
  届いた瞬間の 1 回ずつで、設計どおりの挙動。
- `pred-complete` は 20〜35 秒で全数に到達(E 群 前は 0 のまま)。
- 戦闘 ×131072 の `eph-attr` は hit 24 / miss 1,971(E 群 前は hit 18 / miss 2,626)。
  **ミス自体は減らない**(substep ごとに本当に別の時刻を引くため)が、1 回のミスの費用が下がった。
- 描画は正常。28 日表示では数百周ぶんの軌道が重なって帯状になるが、途切れや異常形状はない。
- 例外・コンソールエラーは全計測で 0 件。
- **未解決の観測**: 1 回目の計測でのみ、28 日表示で update 約 7,300 ms が 50 秒間持続し
  `plan-arcs` が 1 に張り付く状態を観測した(以降の 2 回は再現せず)。他プロセスとの競合下
  だった可能性が高いが、フレームが長くなること自体が再積分を誘発する経路が残っていないかは
  未確認。**28 日表示で再現したら真っ先に疑う。**
- **既知の制限**: 28 日表示では `plan-steps` が `PLAN_ARC_MAX_STEPS` = 20,000 の上限に達して
  おり、28 日ぶん全部は積分していない(区間が上限で打ち切られる。既存の仕様)。
- **可読性の問題(性能とは別)**: 28 日表示では計画軌道のルーラーの日時ラベルが数十個重なって
  地球面が読めない。負荷とは無関係だが、表示期間を長くしたときの実用性の問題として記録する。

## 第一版からの主な変更

**採用(縮小して)**: 計測先行の姿勢(専用ベンチ基盤ではなく `PerfMeter` の区間拡張と既存の
`?stage=` デバッグステージで行う)、render scale、背景密度・天体詳細の設定化、preset。

**削除**:
- `TrajectoryComputationService` — 不要。PlanArc には既に丁寧な再計算判定
  (`plan-arc.ts` の `tracksLiveAnchor`/`anchorJumped`/サンプル間隔閾値)が実装済みで、
  それを `game.ts` が provider の `revision` に連続変化する `simTime` を渡して無効化していた
  だけだった(A-1 で解消済み)。新サービスは同じ判定の二重実装になる。
- `MapFrameSnapshot` — 不要。共有すべき値は実質 `attractorsAt` の結果と
  `MapVisibilityPolicy`/`systemMembersAt` の 2 つで、前者は `Ephemeris` のキャッシュ拡張
  (A-7)、後者は既存の「フレーム毎の値を引数で配る」パターン(B-6)で足りる。
- `MapWorkingSetPolicy` — 不要。`celestial/map-visibility.ts` の `MapVisibilityPolicy` +
  `alwaysFullyVisibleIds` + `systemMembersAt` が既にその責務そのもの(フォーカス系の昇格、
  カメラ所在系の常時表示、クラス別トグル)。hot/warm/cold という新語彙を重ねない。
- `MapPresentationScheduler` — 汎用多段 Hz 機構は過剰。間引きが要る箇所は個別に少なく
  (B-4, B-7, A-6)、点群(1/8 分割更新)と HUD(100/250ms 間引き)には既に同じ手が
  個別実装で入っている。汎用機構は「何 Hz か」を新たな設定面として増やすだけ。
- `PerformanceController` — 不要。設定は既存の `bodyClassToggles`/`gridVisibility` と同じ
  「所有者が値を持ち、localStorage へ load/save」パターンで各所有者に直結する(下記
  「設定の実装」)。
- 自動調整(目標 fps 追従) — 初版から外す。ヒステリシス・cooldown・custom 保護の実装と
  10 分規模の検証が必要な割に、原因修正(A 群)後は必要性自体が下がる。preset 手動選択で
  出荷し、要望が残れば後日。
- multi-rate 積分(第一版 P3-3) — 保留。高ワープの実測上の主因は per-entity 刻みの不在
  そのものではなく、C-1〜C-3 の構造増幅(イベント全走査・グローバル再突入刻み・
  分類再構築)であり、それらを除いた後に再計測して判断する。

**追加**(第一版が見落としていた実測上の大物):
- `Ephemeris.attractorsAt` のキャッシュ(当時 4 スロット・完全一致キー)がマップ表示中
  毎フレーム 6〜10 回ミスし、ミス 1 回 0.16 ms + 101 オブジェクト割り付け(A-7 で 32 スロット化、
  E-2 で重力源専用窓 64 体化。残りは B-2)。
- PlanArc 積分 1 ステップごとの `findImpact` が O(天体数²) の線形探索(E-1 の③で解消)。
- 再突入高度に 1 体でもエンティティがいると全体の刻みが 1 s になり、最大ワープで
  2,185 substeps/frame・上限なし(C-2 で解消)。
- ロード時: 地球球 1024×768 分割(157 万三角形・約 44 MB)、8k_moon.jpg 15 MB、
  未使用アセット 6.8 MB、フォント 10 MB 全部デプロイ、`three` と `three/webgpu` の
  二重バンドル、.epk の要素ごと `getFloat64` デコード(A 群後半)。
- マーカー引き出し線 SVG の毎フレーム全破棄・全再構築(codex が差分化済み)と、ラベル衝突
  解決の毎フレーム文字列キー Map 構築(B-4、未着手)。

**非問題と確認されたもの**(第一版が重いと推定していたが実測で軽い):
遮蔽判定(291 件で 0.055 ms/frame)、小天体点群(0.32 ms/frame、更新は既に 1/8 分割・
instanceMatrix は dirty 分のみ)、既定トグルでの参照軌道線(8 本 0.17 ms)、HUD パネル
(既に間引き済み)。これらへの投資は後回しでよい。

## 実測にもとづく負荷内訳

### ×1・マップビュー(CPU)

| 負荷源 | 実測/根拠 | 大きさ |
|---|---|---|
| PlanArc の再積分 | A-1 で編集時・予測更新時のみに限定。E-1 で停止条件を「予測が計画終端に届いたか」の 3 値にし、長い表示期間でも永続化しない | 解消済み |
| `attractorsAt` キャッシュミス | A-7 で 32 スロット化、E-2 で重力源専用窓(64 体)を分離。ミス回数自体は高ワープで残るが 1 回の費用が下がった | 1 回の費用は解消。回数は B-2 |
| `MapPicker.refresh` 距離ループ | 候補約 240 件 × `strongestAttractor`(101 天体走査)×2。`{...item}` 全件再生成は codex が解消済み | ~5 万ベクトル演算/frame |
| `MarkerManager.resolveCollisions` | 5 反復 × 文字列キー Map 再構築。SVG の全破棄・全再構築は codex が差分化済み | 数千の文字列生成/frame |
| `MapVisibilityPolicy`/`systemMembersAt` の重複生成 | sync フェーズ内は codex が 1 本化(4 個以上 → 2 個)。`MapPicker.refresh`(update フェーズ)が別に 1 個作る | 小 |
| `Predictor` の固定費 | B-5 で解消済み。`pred-complete` は E-1 後、28 日表示でも 20〜35 秒で全数に到達する | 解消済み |
| `currentOrbitPeriod` | codex の `resolveWindowIfStale()` でフレーム 1 回に | 解消済み |

### 高ワープ(CPU)

- substep 数 = `ceil(simDt / maxStep)`、上限クランプなし。×131072・60 fps で 656。
  再突入高度の刻みは C-2 で艦(`players`/`enemies`)だけに限定したため、低高度に破片が
  いても全体には波及しない。
- substep 1 回ごとに: `attractorsAt`(ミス確定)+ `classifyAttractors`(sort + SpatialGrid
  構築)+ 全エンティティ `stepActual`(1 体あたり Vec3 等約 90〜120 個割り付け)+
  `stepAttitudes` + `cleanup` 全走査。`nextEventTime` の全エンティティ走査は C-1 で
  フレーム単位に減り、セル鍵の文字列生成は C-3 の一部で除去済み。
- 姿勢積分は substep 内部で 0.04 s 刻みだが、`ATT_MAX_DYNAMIC_STEPS = 12` で剛体力学の
  反復は 12 回で打ち切られ、残時間は解析 coast で消化される(`attitude.ts`)。つまり
  1 呼び出しの上限は 12 反復であり、姿勢積分は高ワープの主因では**ない**
  (第二版の初期草稿はここを約 40 倍過大に見積もっていた — レビューで訂正)。
- passiveWarpLod と `nextSimulationEventTime` のズレ(まとめ積分に回る個体の寿命時刻でも
  substep 境界を切る)は C-1 で解消。`CreativeStage.applySimulationEvents` の毎 substep の
  配列生成も同時に除去した。

### GPU・ロード時

- `setPixelRatio(devicePixelRatio)` 上限なし + `antialias: true`(`scene.ts`)。DPR 2 で
  fill 4 倍。**1 行で最大の GPU 差。**
- 地球 `SphereGeometry(R_EARTH, 1024, 768)` = 78.8 万頂点 / 157 万三角形 / 約 44 MB。
  テクスチャ解像度が見た目を決めるため、分割は 256×128 でもほぼ視覚差なし。
- テクスチャ実測: 8k_moon.jpg **15.0 MB**(戦闘視点で数十 px の月に使用)、
  8k_clouds.jpg **11.6 MB**(r チャンネルしか使わない)、earth.jpg 4.6 MB、
  8k_stars.jpg 1.9 MB、2k 惑星・衛星系 13 枚 ≈ 5.2 MB。起動時デコード対象 ≈ 38 MB。
- **未使用アセット**: 8k_earth.jpg(earth.jpg と同一バイト)+ earth.png = 6.8 MB が
  リポジトリに死蔵(バンドル外)。
- docs/ 58 MB の内訳: 画像 38.3 MB、**フォント 21 ファイル 10.0 MB**(`@fontsource/jetbrains-mono`
  と `@sarap422/font-hackgen` のパッケージ丸ごと import)、.epk 2 本 8.6 MB、js 5.57 MB。
- js 5.57 MB の一因: `glow-texture.ts` と `floating-origin.ts` だけが `'three'`(WebGL コア)
  を import しており、`three/webgpu` と**二重バンドル**(three.module ≈ 1.3 MB)。
  esbuild target `es2015` も出力を膨らませる。
- 101 天体の mesh・マテリアル(TSL シェーダ 101 本コンパイル)・テクスチャ 13 枚・リング
  約 84 オブジェクトが `EnvironmentScene` コンストラクタで**全部即時構築**。点群・参照線は
  既に遅延化済みなのに天体本体だけ遅延がない。
- .epk デコードが 53 万要素を 1 個ずつ `DataView.getFloat64` + `Number.isFinite` 検査、
  さらに payload を `.slice()` コピーしてから SHA-256。
- Aurora 4 枚が毎フレーム約 5,200 回の sin/cos + 8 本のバッファ再アップロード
  (位相は `simTime*0.02` で非常に遅く、間引いても見えない)。
- 天体・リング・点群の多くが `frustumCulled = false` で、全表示時 300〜400 draw call が
  カリングされずに submit される。

## 計測

専用ベンチ基盤は作らない。既存の資産を使う:

- `PerfMeter` にカウンタを足す: simulation(substep 数・entity-step 数)/
  prediction(消費 step・破棄数 — 実装済み)/ plan(**再積分回数・step 数**)/
  `attractorsAt` のヒット・ミス数。**時間の区間分解(サブフェーズのタイマ)は入れない** —
  P0 で知りたいことはすべて回数で直接読め、時間より因果がはっきりするうえ、
  `Game` に計測状態を撒くことになるため。
- **表示は `PropertyWindow` を流用した負荷ウィンドウにする**(`F3` と ESC メニューから開く)。
  `PropertyWindow` は MapPicker 依存のない汎用部品で、ドラッグ・折り畳み・行の差分更新を
  内蔵しているため新規部品は書かない。`PerfMeter` が `document.body` 直下に div を作って
  いる現在の実装(HUD のレイヤ体系を迂回する唯一の箇所)はこれに置き換える。
  計測は**窓が開いている間だけ**走らせ、通常プレイの費用をゼロに保つ。
  グラフ/スパークラインの前例はコードベースに無いので、割合は `████░░░░ 12.3ms` の
  塗り文字で示し、新しい描画基盤は持ち込まない。
- 固定シナリオは既存の `?stage=` デバッグステージで賄う: `stage-debug-load`
  (小惑星 300 + 破片 500、seed 固定)+ クリエイティブで艦 0/1/10/50 を配置した
  スナップショット(セーブ機構で再現可能)。×1 / ×4096 / ×131072、再突入境界に 1 体
  置いた状態、28 日表示 + ノード 3 個の計画、を比較条件とする。
- 比較は p50 だけでなく p95 と最大フレーム。A-1 で「計画を触らない ×1 マップで PlanArc
  再積分回数が 0/frame になり、ノード編集・表示期間変更では必ず 1 回走る」ことはカウンタで
  確認済み。長い表示期間についても E-1 後に同じことが成立する — `plan-arcs`/`plan-steps`/
  `pred-complete` の 3 つを同時に見て、`pred-complete` が全数に到達したあと `plan-arcs` が
  0 のままであることを確認条件にする。

## 検証

- 各施策ごとに `npm run typecheck`。`physics/` に触るのは A-9・C-4(attitude)のみで、
  その時だけ `npm run test:physics`。
- **設計文書の更新は各変更セットに含める**(CLAUDE.md の義務)。特に C-5(構築タイミング)は
  `DEVELOP/CALLSTACK.md`/`OWNERSHIP.md` の記述対象そのもの。「あとでまとめて」にしない。

  変えても物理 state(位置・速度・イベント順・破壊結果)が一致する。C 群は表示設定と

  スナップショット比較で確認する。
