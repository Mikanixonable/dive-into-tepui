# 軽量化 P0 実行計画

対象は第二版の第 1 弾 — **計測カウンタ + A-7 + B-5 + A-1**。順序は「測れるようにしてから、
安全な順に効かせる」。S0 → S1 → S2 → S3 の 4 段階で、各段階は単独でコミット可能・
単独でロールバック可能とする。

段階の順序はリスクの低い順であり、期待効果の順ではない(最大の効果は最後の S3)。
先に S0 を入れるのは、S3 の完了条件が「カウンタで再積分回数が 0/frame になること」で
あり、計測なしには S3 を正しく入れたかどうか判定できないためである。

---

## S0 — 計測カウンタ(効果測定の土台)

既存の作法に完全に従う: **所有者が public な素のフィールドを持ち、フレーム冒頭で 0 クリア、
その場で `++`、`Game.perfCounts()` が読み、`PerfMeter` がテンプレート文字列に出す。**
`Simulator.lastSubsteps` と `Predictor.tracked/finished/discarded/lastSteps` が既にこの形。
新しい計測フレームワークは作らない。

### S0-1 `PerfCounts` 型の切り出し(先に済ませる整理)

現状 `perf-meter.ts` の `PerfCountSource.perfCounts()` と `game.ts` の `perfCounts()` 戻り値
注釈が**同じ形を二重に手書き**している。カウンタを 1 つ足すたびに 2 箇所を直すことになるので、
先に named type へ切り出す。

- `src/perf-meter.ts` に `export type PerfCounts = { ... }` を定義し、
  `PerfCountSource` は `{ perfCounts(): PerfCounts }` にする。
- `src/game/game.ts` は `perfCounts(): PerfCounts` と書く(`perf-meter.ts` から型 import)。

`game.ts` が `perf-meter.ts` を型のみ import する向きは、`main.ts` が `PerfMeter` を所有し
`Game` を渡している現在の所有関係と矛盾しない(`Game` は `PerfMeter` を知らないまま、
構造的に満たす形が保たれる)。

### S0-2 `Ephemeris` の TimeRing ヒット/ミス

`TimeRing` に `hits`/`misses` の `number` フィールドを足し、`get()` で加算する。
`Ephemeris` に `get cacheStats(): { hits: number; misses: number }` を足し、3 つのリング群
(`allAttractorsCache` / `planetHelioCache` / `satelliteRelCache`)を合算して返す。
`allAttractorsCache` は A-7 の効果を直接見る対象なので**別立てで公開する**
(`attractorHits`/`attractorMisses`)。

- `clear()`(`setPhaseOffsets` 経由)ではカウンタを**リセットしない** — セーブロードを跨いで
  累積してよい値であり、リセットするとロード直後の統計が読めなくなる。
- リセットは `Game.perfCounts()` 側では行わず、`PerfMeter` の 500ms フラッシュが
  「前回との差分」を取る形にする(累積値を渡し、表示側で差を出す)。既存の
  `Predictor` 系が毎フレーム 0 クリア方式なのに対しここだけ累積なのは、`Ephemeris` が
  フレームの概念を持たない(持たせるべきでもない)ため。

**規約上の確認**: `physics/` の不変条件は「base data type(`Vec3`/`KinematicState`/`Quat`/
`Attitude`)が immutable」であり、禁じているのは `*Into`/out パラメータとモジュールレベルの
scratch buffer。`Ephemeris` は既に `phaseOffsets`・3 つの TimeRing・`frameCache` という
可変状態を持ち、クラス冒頭コメント自身が「状態(初期位相とメモ)を持つサンプラクラス」と
宣言している。カウンタは返り値に影響しないので、メモ化の契約(「どの順に呼んでも返る値は
変わらない」)を壊さない。既存メソッドのシグネチャは変えない。

### S0-3 計画軌道の再積分回数と積分ステップ数

- `PlanArc.update()` の戻り値を `void` → `boolean`(再積分したか)に変える。
  `Predictor.advanceBudget` が消費ステップ数を返すのと同じ流儀。
- `PlanArc.integrate()` が回したステップ数を `lastIntegrateSteps` として持つ。
- `PlanPath` に `lastRecomputes`/`lastIntegrateSteps` を持たせ、`update()` の arc ループ
  (全 arc を 1 箇所で回している既存のループ)で集計する。`arcs` は private のままでよい。
- `Game.perfCounts()` までの経路は `editor` → `planDisplay` → `path`。
  `PlanEditor` に `get planRecomputes()` 相当の転送 getter を 1 つ足す(`PlanDisplay.path` は
  既に public)。

**これが S3 の完了条件を判定する唯一の手段**なので、S0 の中では最も重要。

### S0-4 entity-step 数

`Simulator` に `lastEntitySteps` を足す。`lastSubsteps` と同じパターン(`advance()` 冒頭で
0 クリア、`substep()` の `stepActual` ループ内で `++`)。姿勢積分は含めない
(含めると「軌道積分が何回走ったか」が読めなくなる)。含めるなら別カウンタにする。

### S0-5 表示 — 負荷確認ウィンドウ

**人間がプレイ中に負荷を読めることを P0 の要件に含める。** 現行の `?perf=1` オーバーレイは
`document.body` 直下に生成される固定位置のテキスト塊で、行が増えるほど読みにくく、
起動時に URL を付け直さないと出せない。ここを作り直す。

#### 部品は新規に作らない — `PropertyWindow` を流用する

調査の結論として、`hud/property-window.ts` の `PropertyWindow<A>` は
**MapPicker 依存が一切ない汎用部品**である(import にも実装にも `MapPickable`/`kind`/`id`
が現れない)。次がすべて既に入っている:

- ヘッダのドラッグ移動、📌 クリップ、✕ クローズ、`bringToFront`、viewport 再クランプ
- `PropertyRow` = `{key, label, value, group?, collapsible?}` の **値はすべて `string`**
- `syncRows` が**差分更新を内蔵**: 行の構成(`shapeKey`)が同じなら値の変わった行だけ
  書き換え、構成が変わったときだけ組み直す。`panel.ts` の間引きと
  `stage-status-panel.ts` の永続 DOM 使い分けの両方を、呼び出し側に書かせずに satisfy する
- `group` 付き行が名前付きセクションに畳まれる(既定は畳んだ状態)
- `rows` も `items` も**空配列で成立する**(MapPicker 自身が `rows: []` で開いている)

したがって「毎フレーム数値を並べるドラッグ可能な窓」に必要なものは全部あり、
**新しいウィンドウ部品を書くのは規約違反**(`/add-feature`: 再利用可能な形で適切な
モジュールにあればそれを呼ぶ)。

置き場所は `hud.layers.window` レイヤ。`PropertyWindow` の現行唯一の利用先と同じで、
`panel`(固定レイアウトの常設 HUD)でも `system`(ゲームを止めるモーダル)でもない。
**CSS は 1 行も書かない**(`PropertyWindow` が自前の `ensureStyle()` を持つ)。

#### 所有と、既存 PerfMeter との関係

`PerfMeter` は `main.ts` 所有で `Game` の外(`CLAUDE.md`/`OWNERSHIP.md` に明記)。
計測点が `game.update/sync/render` の**呼び出し境界** = rAF ループ = `main.ts` の責務だから
である。ウィンドウはその表示先にすぎないので、**所有は `main.ts` のまま変えない**。
`main.ts` は `Hud` も所有しているので `hud.layers.window` を渡せる。

**表示経路は二本にしない。** `PerfMeter` が自前で `document.body` に div を作っている
現在の実装(HUD のレイヤ体系を迂回している唯一の箇所)を、`PropertyWindow` に置き換える。
`PerfMeter` の責務は「計測・集計・ゲート」のまま、`createElement()` が
`PropertyWindow` の生成に、`flush()` のテンプレート文字列組み立てが
`PropertyRow[]` の組み立て + `syncRows` に変わる。コンストラクタは
`(counts: PerfCountSource, root: HTMLElement)` になる。**旧オーバーレイの痕跡は残さない**
(規約: 互換用の旧経路を残さない)。

#### 行構成

`group` 無しの行は常に見えるので、**最重要の 3 行だけを group 無し**にし、残りは
セクションへ畳む(既定で畳まれている = 開いた直後は 3 行の小さな窓)。

| group | 行 |
|---|---|
| (無し) | `fps` / `frame` (update+sync+render の合計 avg・p95) / `warp` (現在倍率) |
| フレーム時間 | `update` / `sync` / `render` 各 avg・p95・max |
| 計画軌道 | `recompute`(回/frame)/ `steps`(積分ステップ/frame) ← **S3 の完了判定に使う行** |
| 予測 | `tracked` / `complete` / `discard` / `steps` |
| シミュレーション | `substeps` / `entitySteps` / `gravitySources` |
| 暦キャッシュ | `attractorsAt hit/miss` / `全リング hit/miss` ← **S1 の効き目を見る行** |
| 表示 | `view`(combat/map)/ `pickables` / `labels` / `表示期間` |
| エンティティ | `players` / `enemies` / `bullets` / `casings` / `debris` / `ammos` / `asteroids` / `bases` |
| メモリ | `JS heap` |

`entities` の `ammos`/`asteroids`/`players`/`bases` は既に public だが現行の `perfCounts()` が
読んでいない。クリエイティブの負荷は艦数と小惑星数で決まるので、ここで加える。

**横棒は文字で描く。** 時系列グラフやスパークラインの前例はコードベースに一つも無く、
SVG/canvas の新規基盤を持ち込むことになる。`PropertyRow.value` は文字列なので、
`████░░░░ 12.3ms` のように**塗り文字で割合を示す**だけにする。基準は 16.7 ms
(60 fps の 1 フレーム)。これで「どの区間が予算のどれだけを食っているか」は一目で読め、
新しい描画基盤は不要。**本物のグラフは P0 には入れない**(必要になってから)。

#### 開き方と、計測コストのゲート

- `input/key-mapping.ts` に 1 エントリ追加(**キー割り当ての唯一の定義**なので必ずここ)。
  空いている F キーのうち `F3` を使う。ブラウザ既定を奪うため `SCROLL_GUARD_KEYS` にも
  追加する(`F5`/`F9` が既にそうしている)。
- `SettingsPanel`(ESC メニュー)にも項目を 1 つ足す。`onOpenSnapshots` と同じ形で
  `onOpenPerfWindow` コールバックを足し、`main.ts` で配線する。窓は非モーダルなので
  `ModalController` には触らない(触ると入力ゲートが立ってゲームが操作不能になる)。
  ESC から開くときは設定パネルを閉じる(スナップショットと同じ扱い)。
- **`?perf=1` は残す**(起動直後から測りたい場合の既存の入口)。ただし `PerfMeter.on` を
  `readonly` から可変にし、**窓が開いている間だけ計測が走る**ようにする。
  `main.ts` の `perf.on ? performance.now() : 0` という既存の書き方がそのまま活き、
  **窓を閉じていれば通常プレイに計測費用が一切かからない**という現在の性質が保たれる。

#### 区間計測(サブフェーズのタイマ)は P0 に入れない

`update` の内訳(`simulator.advance` / `predictor.update` / `updateMapPresentation` など)を
時間で分解したくなるが、**P0 では入れない**。理由:

- 規約は「デバッグ用のコードは頼まれたことだけを頼まれた形で書く。毎フレーム走る仕掛け、
  状態(カウンタ・フラグ)は要求されない限り書かない」であり、`Game` は
  `perfCounts()` で**値を答えるだけ**の口に留まっている(`refactor-fixed` の
  「Game にロジックを書かない」)。区間タイマは `Game` の中に計測状態と
  `on ? now() : 0` の三項を十数箇所ばら撒くことになる。
- そして**そもそも必要ない**。P0 で知りたいのは「計画軌道が毎フレーム再積分されているか」
  「暦キャッシュが当たっているか」「予測が破棄ループに入っているか」であり、
  これらは時間ではなく**回数**で直接読める。S0-2〜S0-4 のカウンタがその答えそのもので、
  時間の内訳より因果がはっきりする。
- S1〜S3 を終えてなお `update` の内訳が読めないことが実際に困った場合に、
  そのとき改めて要否を判断する。

### S0 の完了条件

- `F3` と ESC メニューの両方から負荷ウィンドウが開き、ドラッグで動かせ、📌 で常駐でき、
  ✕ で閉じられる。セクションの開閉ができる。
- 窓を閉じている間は `performance.now()` が計測目的で 1 回も呼ばれない
  (`perf.on` が false)。
- `?perf=1` 付きで起動すると最初から窓が開いている。
- **ベースライン測定を記録する**(この時点の値が S1〜S3 の比較対象になる):
  - クリエイティブ・マップ・×1・艦 1 隻・ノード 0 個 / ノード 3 個
  - 同・28 日表示
  - ×4096 / ×131072
  - `stage-debug-load`(小惑星 300 + 破片 500、seed 固定)
  - 各条件で `plan recompute`/`ephem miss`/`substeps`/`entitySteps` と p50/p95 frame time。
- `npm run typecheck` が通る。`physics/` を触るので `npm run test:physics` も通す。

## S1 — A-7: TimeRing のスロット拡張

`TIME_CACHE_SLOTS` を 4 → 32。それだけ。線形走査は 32 スロットでも number 比較 32 回で、
ミス 1 回 0.16 ms に対し無視できる。per-body リング(約 200 個)も一律拡張されるが、
1 リング 32 スロットでもメモリ影響は自明に小さい。

### 完了条件

- S0 のベースラインに対し `ephem miss` が減る条件と減らない条件を記録する。
- **この時点では劇的には減らない見込み**: PlanArc が毎フレーム数千の一意時刻でリングを
  洗い流している間は、スロットを増やしても押し出しが続く。S3 の後に再測定して初めて
  「ミス 6〜10 回 → 2 回程度」が観測されるはず。**S1 単体で効果が出ないことをもって
  A-7 を無効と判断しない**(この依存関係が、第二版で A-1 と A-7 を同じ弾に置いた理由)。

## S2 — B-5: Predictor の固定費と破棄ループ

**調査で計画の前提が 1 つ覆った。** 第二版は破棄の原因を「高ワープで `at(simTime)` が
保持窓の外に落ちる」と書いたが、コードを追うと予測列の全長は設計上 horizon + 1 step で、
`cleanup(keepDuration = horizon, minCount = 2)` が古い側を落とすことは基本的に起きない。
実際の破棄経路は次の 2 つ:

- **(A) 先端の置き去り**: 列を新規生成した直後 `state.t = 生成時の simTime`。翌フレームの
  simTime はすでにそれより先で、`at(t &gt; state.t)` は `null`。
- **(B) history が空の窓**: 生成直後 history は空で、最初の push は「前回 state が最新
  サンプルから sampleInterval 以上離れたとき」。それまで `at(t)` は `t === state.t` 以外
  すべて `null`。

そして両者を毎フレーム再現させているのが **round-robin が `budget` を丸ごと 1 体に渡す
実装**である。ある個体が 0〜9 ステップしか回れなかったフレームがあると、次フレームで
確実に破棄され、また最初から作り直しになる。**したがって B-5 の本体は「破棄条件の緩和」
ではなく「予算配分の是正」である。** `StateQueue` に過去側トリムの新 API を足す案は
不要になったので取り下げる(第二版の当該記述を修正する)。

### S2-1 `predictsFuture` の判定を前に出す

`update()` の全走査ループで `discardPredictionIfDiverged` を呼ぶ前に
`if (!e.predictsFuture) continue;` を置く。弾・薬莢・破片(map モードの `all` の大多数)が
呼び出し 1 回分すら消える。**最も効いて最もリスクが低い。**

### S2-2 `divergenceTolerance` の走査削減

現状 1 エンティティあたり全天体配列を 2 回走査している(`strongestAttractor` を直接 1 回、
`localOrbitPeriod` の内部でもう 1 回)。

- `localOrbitPeriod(r, attractors)` の呼び出しを、既に求めた `center` を使う
  `keplerPeriod(len(sub(r, center.state.r)), center.mu)` に置き換える(`localOrbitPeriod` の
  実装と同じ式で、走査が半減する)。
- 渡す配列を、`update()` 冒頭で 1 回だけ組んだ `classifyAttractors(...)` から
  `attractorsNearInto(e.state.r, classified, scratch)` で絞ったものにする。
  `always` 15 本 + 27 近傍セルなので全天体走査より短い。
- **スクラッチ配列は `advanceBudget` が使う `nearbyAttractorsScratch` とは別に用意する。**
  時系列的には競合しないが、共有は事故のもと。
- `strongestAttractor`/`localOrbitPeriod` のシグネチャは `readonly Attractor[]` のまま
  変えない。`ClassifiedAttractors` は `game/simulation/` の型で、`physics/` に持ち込むのは
  層違反。

### S2-3 予算配分の是正

`while (budget > 0 && visited < all.length)` のループが `advanceBudget(e, budget, ...)` と
残額を丸ごと渡している。これを「1 体あたりの上限」を設けた形に変える。上限は
**予測列を成立させるのに要る最小ステップ数**(sampleInterval / dt ≒ 10 ステップ)を
下回らないこと。具体的には `max(minStepsToSample, floor(budget / 残り訪問数))` のような
配分にし、余りは次の個体へ回す(既存の `budget -=` の形は保つ)。

- 28 日表示・LEO の実測値で `dt = horizon / PREDICT_MAX_STEPS = 120.96 s`、
  `sampleInterval = max(period/32, horizon/2000) = 1209.6 s` なので、
  **history に最初の 1 サンプルが積まれるのに 10 ステップ**。この 10 を下回る配分を
  受けた個体が破棄ループに入る。
- 先端の前進速度は 1 フレーム 250 ステップ × 120.96 s ≒ 8.4 時間 = 実時間比 1.8×10⁶ 倍で、
  最大ワープ 131,072 より速い。**定常状態では追いつけるので、破棄ループさえ潰せば
  高ワープでも列は維持される。**

### S2-4 破棄判定の分岐(S2-3 で足りなければ)

S2-3 を入れて計測してもなお `discarded` が毎フレーム立つ場合のみ、
`discardPredictionIfDiverged` の `at(simTime) === null` 無条件破棄を分岐させる:
history が空(生成直後)なら破棄せず猶予、先端が simTime より後ろなら破棄。
**S2-3 の計測結果を見てから着手を判断する** — 不要なら入れない。

### S2 の完了条件

- `?perf=1` の `predict discard` が、×1 マップ・定常状態で 0 に張り付く。
- ×131072 でも `discard` が毎フレーム全個体数にならない。
- `tracked`/`complete` が艦数と整合する。
- `npm run typecheck`。`physics/` は触らない見込み(`keplerPeriod` は既存)。

## S3 — A-1: 計画軌道の再積分トリガを意味的 revision へ

**P0 の本命。** `planAttractorProvider(..., revision)` の `revision` は provider 内では
一切使われず、`PlanArc.update` の `key.sourceRevision` 比較のためだけに存在する
ラベルである。そこに `simTime` を渡しているため `inputChanged` が常時 true になり、
`PlanArc` の閾値ロジック(`tracksLiveAnchor`/`anchorJumped`/サンプル間隔)が丸ごと
デッドコードになっている。

### S3-0 revision が拾わねばならないもの(判定式から機械的に導いた完全リスト)

`planAttractorsAt` の時間依存入力は `ephemeris.attractorsAt(t)` と各エンティティの
`displayState(t)` の 2 系統だけ。それ以外(`alive`/`collides`/`radius`/`mu`/集合)は
フレーム内で固定。`PlanArc` の key が既に拾うのは `state0` の参照同一性・`end`・
`apsisCenterId` のみ。したがって revision が担うのは次の 4 つ:

1. **Plan の編集** — `state0` の参照差し替えで拾えるが、`end` が変わらない編集
   (末尾ノードの Δv 変更など)で下流区間の `state0` が同一参照のまま残る経路があり得る。
   編集カウンタで確実に拾う。
2. **`entities.attractors()` / collision 対象の顔ぶれ** — `EntityManager.collectionRevision`
   (private、public getter を足す)。ただし**`alive` が false になっただけでは
   `collectionRevision` は増えない**。`cleanup` が毎フレーム `prune` を呼ぶので実害は
   1 フレーム以内だが、この穴は認識しておく。
3. **`Ephemeris.setPhaseOffsets`**(セーブロード) — `Ephemeris` に世代カウンタを足し、
   キャッシュ `clear()` と同じ場所で `++` する。`restore` は全エンティティを作り直すので
   実運用上は 2 でも拾えるが、独立させる。
4. **予測列の伸長・破棄** — これが設計上の核心。

### S3-1 予測依存の畳み込み(核心)

`displayState(t)` は `t > actualTrajectory.state.t` では `predictedTrajectory.at(t)` を引く。
予測列が伸びると、それまで `null` だった時刻が非 null になり、**その天体が provider の
重力源集合と衝突候補集合に突然出現する**。逆に破棄されると全時刻から消える。

素朴に「予測先端 `predictedTrajectory.state.t`」を revision に入れると毎フレーム変わって
A-1 が無効化される。**先端を計画の終端で頭打ちにする**ことで停止性が得られる:

```
contribution(e) = e.predictedTrajectory === null ? -1 : quantize(min(tip.t, planEnd))
```

- `planEnd` は `PlanPath.timeRange()` の `max`(既存)。
- `quantize` の幅は区間のサンプル間隔相当(区間長 / `PLAN_ARC_MAX_SAMPLES`)。
  それ未満の先端の伸びは、そもそも描画上も衝突判定上も差が出ない。
- 予測が計画範囲を覆いきった後は `min` が効いて値が固定される = **再積分が止まる**。
- 覆うまでの間(28 日表示・map で約 80 フレーム = 1.3 秒)は revision が変わり続け
  再積分される。これは現状と同じであり、**計画範囲外まで予測が伸びていないうちは
  再積分が正しい**ので、意図どおりの挙動である。
- 高ワープ中は `planEnd` 自身も進むので変化が続き得る。量子化幅を粗く取ることで
  「重力源として意味のある差でのみ変わる」意味付けにする。

畳み込み対象のエンティティは provider が実際に読む集合に限る(gravity 側 =
`entities.attractors()`、collision 側 = `alive && collides && radius > 0 && !excluded`)。
畳み込みは順序付き加重和で十分(完全なハッシュは不要 — 衝突しても「再積分し損ねる」
だけであり、その確率と影響は `anchorDrifted` 等の他の判定に吸収される。ただし
**衝突が疑われる不具合が出たら真っ先にここを疑う**)。

### S3-2 実装の置き場所

- `Plan` に編集カウンタ(`private _revision`、public getter)。bump するのは実際に
  `_nodes`/`_anchor` を変更したときだけ:
  `addNode`(`-1` 返し時は bump しない)/ `removeNode`(範囲外なら不要)/
  `consumeNodesUpTo`(`dropped === 0` なら不要)/ `clear` / `replaceNode`(`null` 返し時は不要)。
  **`applyNodeDv` は内部で `replaceNode` を呼ぶので二重 bump に注意**(`replaceNode` 側だけで
  bump する)。**`trackAnchor` では bump しない** — ノード 0 本の間は毎フレーム `_anchor` を
  差し替えるので、bump すると A-1 が無効化される。この経路は `PlanArc` の
  `tracksLiveAnchor` 側の閾値判定(`anchorDrifted`/`durationChanged`)が担当する、という
  役割分担を保つ。
- 畳み込み関数は `game/simulation/attractors.ts` に置く(provider と同じ場所、
  provider が何を読むかを知っている唯一のモジュール)。
  シグネチャ案: `planSourceRevision(ephemeris, entities, excludedEntityIds, planEnd): number`。
- `game.ts` の `updateMapPresentation` が `simulator.simTime` の代わりにこれを渡す。
  `planEnd` は `editor` 経由で `PlanPath.timeRange()` から取る。ここで
  「provider を作るのに plan の情報が要る」順序依存が生じるので、
  `planEnd` が未確定の初回フレームは従来どおり必ず再積分される値(例: 前フレームと
  必ず異なる値)を返す形にしておく。
- `EntityManager.collectionRevision` に public getter。
- `Ephemeris` に `get phaseGeneration()`、`setPhaseOffsets` 内で `++`。

### S3-3 検証(取りこぼしが最大のリスク)

以下を**それぞれ 1 ケースずつ手で確認する**。`?perf=1` の `plan recompute` が
「変化のないフレームで 0、操作したフレームで 1 以上」になることを見る。

| 操作 | 期待 |
|---|---|
| 何もせず ×1 でマップを眺める(ノード 3 個) | 0/frame(**S3 の主目的**) |
| ノード追加 / 削除 | その瞬間だけ再積分 |
| Δv 編集(ドラッグ・キー・ボタン) | 編集中は再積分、離すと止まる |
| ノードのドラッグ(時刻変更) | 同上 |
| 表示期間の変更(1周/1日/7日/28日/任意) | 1 回再積分(`end` 経由で拾う) |
| 未来ゴーストのスライダ操作 | 再積分しない(計画の形は変わらない) |
| ノード 0 個で放置(`tracksLiveAnchor`) | 閾値ぶんの間隔で再積分(0 ではない。これは正しい) |
| クリエイティブで小惑星を配置 / 削除 | 再積分 |
| 操作艦の切り替え | 再積分(`excludedEntityIds` 変化) |
| セーブロード | 再積分 |
| 予測が計画範囲を覆いきるまで(表示期間を長くした直後) | 数十フレーム再積分し、その後止まる |
| 戦闘ビューでノードを持ったまま放置 | 0/frame(**現状は戦闘ビューでも毎フレーム走っている**) |

### S3 の完了条件

- 上表がすべて期待どおり。
- ×1 マップ・ノード 3 個・28 日表示で frame time の p50/p95 が S0 ベースラインから
  明確に改善(この条件が最も差が出る — 現状は毎フレーム 20,000 step 積分)。
- **S1 の再測定**: `ephem miss` が 6〜10 → 2 程度に落ちることをここで確認する。
- 計画軌道の描画が目視で従来と一致(ノード編集直後・warp 中・表示期間切替直後)。
- `npm run typecheck`。`physics/` に触る(`Ephemeris` の世代カウンタ)ので
  `npm run test:physics`。

## リスクと落とし穴

| リスク | 影響 | 対処 |
|---|---|---|
| **S3 の revision 取りこぼし** | 計画軌道が古い重力源・古い衝突候補で描かれ続ける。無言で間違う最悪の壊れ方 | S3-3 の表を機械的に全部通す。疑わしければ `?perf=1` に「revision の内訳」を一時的に出す |
| **S3 の畳み込みハッシュ衝突** | 同上(低確率) | 加重和の重みを素数にする。不具合時に真っ先に疑う |
| **`trackAnchor` で bump してしまう** | A-1 が丸ごと無効化される(現状と同じ挙動に戻り、しかも直したつもりになる) | S3-3 の「ノード 3 個で 0/frame」で必ず露見する。この項目を最初に確認する |
| **S2-3 の配分で最小ステップ数を割る** | 破棄ループが残る/悪化する | `discard` カウンタが 0 に張り付くことを完了条件にしている |
| S1 単体で効果が見えない | A-7 を無効と誤判断 | S1 の完了条件に「S3 後に再測定」と明記済み |
| `PlanArc.update` の戻り値変更 | 呼び出し側の見落とし | 呼び出しは `PlanPath.update` の 1 箇所のみ(確認済み) |
| **負荷ウィンドウ自身が重い** | 測定対象を歪める | `syncRows` は差分更新内蔵。更新は既存の 500 ms フラッシュのまま毎フレームにしない。窓を閉じれば計測ごと止まる |
| `PropertyWindow` の item shortcut が誤爆 | 非クリップ時に `[F]` 等を奪う | `items` を空にすれば `handleKeyDown` は実質無害(空ループ) |
| `Ephemeris` へのフィールド追加 | `test:physics` の破壊 | シグネチャを変えない。カウンタは返り値に影響しない |
