# 軽量化計画 第三版

未解決のものだけを扱う。方針は「コードベース自体を軽く保つ。新しい抽象層(サービス・
スケジューラ・スナップショット)を足さず、負荷の原因になっている少数の箇所を直す」。
残る作業の主眼は一時オブジェクトの削減ではなく、計算量そのものを下げることにある。

## 前提 — 現在のコードの状態

施策の議論の前提として、いま何がどうなっているかを記す。

- **物理はビューに依らず走る。** マップビューを開いても `Simulator.advance` は毎フレーム
  走る。マップ表示のために物理を止める設計は採らない。シーンとレンダラは全体で 1 つずつで
  (`render/scene.ts`)、マップと戦闘の違いはアクティブカメラ・表示ポリシー・HUD だけ。
- **計画軌道の再積分は、意味的 revision が変わったときだけ走る。** `PlanArc.update` の
  再積分判定に渡す revision は `simTime` ではなく `simulation/attractors.ts` の
  `planSourceRevision` が畳み込む値で、予測の寄与は「その個体の予測を持たない/計画の終端まで
  届いていない/届いた」の 3 値。届いた後は値が固定されるので再積分は止まる。
  ノードを触らない ×1 マップでの再積分は 0/frame。
- **`PlanArc.integrate` は重力源・衝突体・空間分類を `ATTRACTOR_REBUILD_SEC` ごとにだけ
  組み直す**(`Predictor` と同じ方式・同じ定数)。衝突天体の引き当ては `Map` 引き。
- **重力源専用の暦窓がある。** `Ephemeris.gravityAttractorsAt(t)` が `mu !== 0` の 64 体だけを
  組み、`gravityBodiesAt` がこれを使う。全 101 天体の窓(`attractorsAt`)は遮蔽・地表接触・
  中心天体の解決に引き続き要る。時刻キャッシュ `TIME_CACHE_SLOTS` は 32。
- **substep 境界のイベント時刻は毎 substep 走査しない。** エンティティ側の最小イベント時刻を
  `Simulator.advance` が控え、`EntityManager.collectionRevision` の変化・イベント時刻の通過・
  LOD 切替のときだけ引き直す。ステージ側は控えない(`PlanExecutor` の点火時刻は艦の現在の
  Δv と加速度から毎回決まる生きた値のため)。
- **再突入の細かい刻みは艦だけに効く。** substep 上限の判定に含めるのは `players` と
  `enemies` のみ。天体の貫通は `physics/attractor.ts` の `reachedBody(prev, next, bodies, margin)`
  が掃引判定で拾うので、粗い刻みでも素通りしない。自機の地表到達は `Player.checkLoss` の
  喪失理由に入っている。
- **空間分類のセル鍵は入れ子 `Map`**(cx → cy → cz)。文字列生成もハッシュ畳み込みもしない。
  同じ方式が `marker-manager.ts` と `focus-markers.ts` のラベル衝突解決にも入っている。
- **`MapVisibilityPolicy` はフレームに 1 つ。** update フェーズの `MapPicker.refresh` が組み、
  `Game.sync` が読む。`systemMembersAt` も同様に共有する。
- **`ObjectListPanel` の区画選別・並べ替え・親子構造は、入力が変わったフレームか、保持順序が
  今フレームの値で整列条件を満たさなくなったフレームだけ組み直す**(距離は既定の並び順の
  キーなので、入力比較だけでは停止しない)。
- **`physics/` の base data type は immutable。** `*Into`/out パラメータもモジュールレベルの
  scratch buffer も持ち込まない(`CLAUDE.md` の明文化された意図的トレードオフ)。関数の外へ
  出ない一時領域の使い回しだけは行っている。返り値そのものの使い回しは採らない。
- **姿勢積分は高ワープの主因ではない。** 剛体力学の反復は `ATT_MAX_DYNAMIC_STEPS = 12` で
  打ち切られ、残時間は解析 coast で消化される(`physics/attitude.ts`)。
- **`PerformanceSettings`(品質設定)は存在しない。** ESC メニューに品質項目は無く、
  描画解像度・地球分割・背景密度を切り替える手段が無い。
- **ロードの現状**: `docs/` 合計 35 MB(画像 18.3 MB、フォント 6 ファイル 7.87 MB、
  .epk 2 本 8.6 MB、js 1.81 MB)。`main.js` 1.81 MB。THREE の import は `'three/webgpu'` に
  統一済み。`8k_moon.jpg` 3.10 MB / `8k_clouds.jpg` 2.78 MB(グレースケール)/
  `earth.jpg` 4.6 MB / `8k_stars.jpg` 1.9 MB / 2k 惑星・衛星系 13 枚 ≈ 5.2 MB。
  .epk の Float64 復号はリトルエンディアン環境で一括コピー + ビュー。
- **`EnvironmentScene` のコンストラクタは 101 天体の mesh・マテリアル(TSL シェーダ 101 本の
  コンパイル)・テクスチャ 13 枚・リング約 84 オブジェクトを全部即時構築する。** 点群と
  参照線だけは遅延化されている。
- **地球は `SphereGeometry(R_EARTH, 1024, 768)`** = 78.8 万頂点 / 157 万三角形 / 約 44 MB。
- **`setPixelRatio(devicePixelRatio)` に上限が無く、`antialias: true`**(`render/scene.ts`)。
- **天体・リング・点群の多くが `frustumCulled = false`** で、全表示時 300〜400 draw call が
  カリングされずに submit される。
- **Aurora 4 枚が毎フレーム約 5,200 回の sin/cos と 8 本のバッファ再アップロードを行う。**
  位相は `simTime * 0.02` で非常に遅い。
- **非問題と実測で確定しているもの**(投資は後回しでよい): 遮蔽判定(291 件で 0.055 ms/frame)、
  小天体点群(0.32 ms/frame、1/8 ラウンドロビン更新・dirty index だけ `instanceMatrix` 反映)、
  既定トグルでの参照軌道線(8 本 0.17 ms)、HUD パネル(間引き済み)。

## 戦闘ビューの update が重い問題

戦闘ビューで発砲を続けると `update` が伸び、弾切れまで戻らない。`sync` と `render` は
0.9〜1.5 ms で不変で、`update` だけが跳ねる。占めているのは剛体接触の解決と、
`EntityManager.cleanup` の地表到達判定。

**残っているのは参加者そのものを減らす方向の手**(薬莢の寿命短縮、`collides` の途中解除)で、
これはプレイヤーから見える挙動を変えるので、**費用側の手を尽くしたあとの再計測を待って判断する。**
再計測は「検証が要るもの」節の項目として持つ。

### 発砲・被弾が引き金になる理由

薬莢(発砲)と破片(被弾・撃破)は、どちらも**自機至近に居座り、`collides = true` で、寿命が
長い**参加者を一気に増やす。薬莢の寿命は `CASING_LIFETIME` = 1,800 sim 秒、破片は再突入する
まで消えない。開始直後が軽いのは、その時点の参加者が弾だけだから。

### 否定された仮説(同じ調査をやり直さないための記録)

- **接触グリッドのセル幅を膨らませている支配項は弾の移動量である**: 誤り。区間移動量の絶対値を
  見ていたために、全参加者が共通して持つ ECI の軌道速度(1 substep で km 単位)がそのまま
  セル幅を決めていた。接触の成否を決めるのは相対変位なので、参加者集合の平均変位を差し引いた
  量で測ると、弾も薬莢も同じ軌道に乗っている限りセル幅には効かない。「速い 1 体をグリッドから
  外して別に持つ」という形の対策は、この誤診に基づいていたので不要。
- **放熱板の接触代理体の作り直し**: 起きていない。`game/player/radiator.ts` は `RadiatorFold` を
  プールし、以後は状態を書き直すだけ。プロファイルに現れない。ただしこの最大 12 体も
  自機至近セルの参加者としては効く。
- **薬莢・破片の姿勢積分**: 効いていない。時間加速なしでは substeps が 1 で、`stepAttitude` は
  self time 上位 25 位に入らない。
- **参加者数の上限到達**: 上限(破片 600・薬莢 260)に達する前、薬莢 96・破片 24 の時点で既に
  184 ms に達していた。件数の上限ではなく 1 体あたりの費用の問題。
- **`Enemy.radius` がセル幅の支配項である**: 誤り。`ENEMY_RADIUS`(180 m)ではなくメッシュの
  バウンディング球から取った 67.2 m(`game/game-entity/enemy.ts`)。

## 施策一覧

各施策は独立に着手できる。依存があるものは項目内に書く。

### 施策 1 — 最大ワープでの予測列の破棄ループ

**対象**: `game/game-entity/game-entity.ts` / `game/simulation/predictor.ts`

stage1 ×131072 で `pred-discard` が毎フレーム全数(マップ 6 / 戦闘 1)。最大ワープでは予測列が
毎フレーム破棄され作り直されている。`discardPredictionIfDiverged` が
`predictedTrajectory.at(simTime) === null` を無条件破棄にしている分岐が、最大ワープでは常に
成立していると見られる。列生成直後は `history` が空で、最初の push は「前回 state が最新
サンプルから `sampleInterval` 以上離れたとき」なので、それまで `at(t)` は `t === state.t` 以外
すべて `null` を返す。

分岐させる: `history` が空(生成直後)なら破棄せず猶予、先端が `simTime` より後ろなら破棄。

**予測は計画軌道の重力源・衝突候補でもある**(`planAttractorsAt` が `displayState(t)` を読む)
ので、破棄ループは表示だけの問題ではない。破棄が止まらない限り、計画軌道が見る重力源集合が
毎フレーム揺れる。

**効果**: 最大ワープでの予測の再構築ループの除去。

### 施策 2 — `toEvaluatorEphemerisPack` の boxed 配列の除去

**対象**: `physics/ephemeris-pack/format.ts` / `physics/ephemeris-pack/evaluator.ts`

.epk 復号後に `toEvaluatorEphemerisPack` が payload 全体を `Array.from(...)` で約 53 万個の
boxed number に変換し、`ChebyshevEphemeris` のコンストラクタ(`copyBody`)がさらにコピー
している。Float64 の復号ループ自体は一括コピー + ビューになっているので、起動時間への寄与は
現在こちらの方が大きい可能性が高い。

`ChebyshevEphemeris` が持つ「入力配列をスナップショットして凍結する」性質(呼び出し側が
後から元配列を壊しても評価器が汚染されない)は落とさないこと。

**効果**: 起動時。分量は小。

### 施策 3 — `classifyAttractors` のメンバーシップ再利用

**対象**: `game/simulation/attractors.ts`

高ワープでは substep ごとに `classifyAttractors` が μ の sort と `SpatialGrid` 構築を
やり直す(×131072・60 fps で 656 substep/frame)。再利用してよいのは分類**構造**
(μ の sort 結果 = always/grid のメンバーシップ)だけで、`Attractor` は `state`(位置)を
抱えているため配列ごと凍結すると重力源の位置まで凍結してしまう。よって always/grid の構成
だけを有効期間付きで再利用し、state は substep ごとに差し替える。全エンティティが同一分類を
見る対称性は保つ。

**ただし μ が時刻に依らない一方で天体の位置は substep ごとに変わるため、グリッドへの挿入は
やり直しになり、省けるのは 64 要素の sort だけ。効果は小さいと見込まれる。加えて失敗すると
重力が静かに間違う。実測で必要と分かってから着手する。**

### 施策 4 — `equator-node-markers.ts` の単発時刻での全窓引き

**対象**: `game/marker/equator-node-markers.ts`

`update` が source ごとに `state.t` で天体窓を引く。source ごとに時刻が異なり、フレーム内で
共有できる単一の時刻が無いため、フレーム 1 回にまとめられない。時刻キャッシュ 32 スロットと
相補で、ミスの回数そのものを減らす余地がここに残っている。

**効果**: 暦キャッシュミスの回数削減。分量は小。

### 施策 5 — 遮蔽判定の間引き

**対象**: `game/map-picker.ts`

`isOccluded` を全候補について毎フレーム走査している。カメラまたは対象位置が閾値以上に変化した
場合だけ再評価する形にする。**見た目(アイコンの出現・消失)が数フレーム遅れる副作用がある
ため、他の項目の後に回す。** 遮蔽判定自体は 291 件で 0.055 ms/frame と軽く、単独では急がない。

### 施策 6 — `PerformanceSettings` と ESC メニューの品質設定

**対象**: `game/performance-settings.ts`(新設)/ `game/hud/settings-panel.ts` / `main.ts`

**丸ごと未実装。** 施策 7・施策 8・施策 9 の受け皿でもあるので、それらより先に器を作る。
露出するのは preset 1 つ + 詳細 4 項目。

| 項目 | 値 | 適用 | 接続先 |
|---|---|---|---|
| 品質プリセット | 高 / 標準 / 軽量 / 最軽量 / カスタム | 即時 | この表の残り4項目を一括で設定する。個別に変更するとカスタムへ移る |
| 描画解像度 | 端末そのまま / 1.5 / 1.0 | 即時 | 施策 8 |
| 地球・天体の詳細 | 高 / 標準 / 軽量 | 地球分割は再起動時、テクスチャ tier は施策 14 の後に即時 | 施策 9 / 施策 14 |
| マップ背景密度 | 高 / 標準 / 低 | 即時 | 施策 7 |
| エフェクト量 | 高 / 標準 / 低 | 即時 | 破片・薬莢の生成上限と billboard 数 |

**物理の正しさ(軌道積分・イベント判定・衝突)は設定で変えない。** 高ワープの改善は常時挙動の
改善として全員に適用するもので、設定項目にしない。antialias は renderer 生成時指定のため
露出しない。自動調整(目標 fps 追従)は載せない。

実装は新しい store/controller 層を作らず、既存パターンに従う:

- `game/performance-settings.ts` に型付きの `PerformanceSettings`(preset キー + 各項目の
  リテラル union)と `loadPerformanceSettings()`/`savePerformanceSettings()`
  (`tepui.performanceSettings`、不正値は既定へフォールバック)を置く。
  `bodyClassToggles`/`gridVisibility` の load/save と同じ形。
- 所有者は `main.ts`(renderer 生成前に読む必要がある描画解像度・地球分割)と `Game`
  (実行時項目)。`SettingsPanel` は値の表示と変更通知だけを行い、`main.ts` が既存の
  `onSettingsOpenChange` と同じ形で各所有者へ配線する。
- preset は保存時に個別値へ展開する便宜であり、実行コードの分岐キーにしない。

### 施策 7 — マップ背景密度を設定へ接続

**対象**: `game/celestial/` と `game/camera/` の既存トグル

点群の group 別表示・点数上限、ラグランジュラベルのクラス既定、参照線トグルの既定値を
preset へ接続する。**仕組みは既存トグルのまま、既定値だけ設定が与える。**
施策 6 の後に着手する。

**効果**: 全表示時の参照線 100 本で 2.2 ms を設定で回避できる。分量は小。

### 施策 8 — render scale 設定

**対象**: `render/scene.ts`

`setPixelRatio(window.devicePixelRatio)` に上限が無い。`setPixelRatio(min(devicePixelRatio, scale))`
にして設定値化する(既定 = 端末 DPR、軽量 preset で 1.5 / 1.0)。resize 時にも再適用する。
毎フレーム呼ばない。施策 6 の後に着手する。

**効果**: 高 DPI で GPU fill が最大 4〜9 倍差。**1 行で最大の GPU 差。** ただし現状のヘッドレス
計測では全条件で render 3〜10 ms にとどまるので、**実機(高 DPI)での再計測を先に行い、
そこで優先度を決め直す。**

### 施策 9 — 地球ジオメトリ分割の縮小

**対象**: `render/earth.ts`

`SphereGeometry(R_EARTH, 1024, 768)` = 157 万三角形 / 約 44 MB。既定 512×256、軽量 256×128
(設定 tier)にする。見た目はテクスチャ解像度が支配するため視覚差はほぼない。
施策 6 の後に着手する。

**効果**: ロード時スパイクと約 44 MB → 数 MB。三角形 157 万 → 10〜39 万。
before/after のスクリーンショット比較(戦闘視点の地球リム・月・雲)で確認する。

### 施策 10 — Aurora tick の間引き

**対象**: `render/earth.ts` / `render/aurora.ts`

地球が表示される毎フレームに Aurora 4 枚の頂点・色バッファを書き換えている(約 5,200 回の
sin/cos と 8 本のバッファ再アップロード)。位相は `simTime * 0.02` と非常に遅いので、
4〜8 フレームに 1 回の更新にしても視覚差は小さい。`needsUpdate` も更新回のみ立てる。
物理状態・地球位置・軌道・入力・衝突・勝敗には影響しない。

**効果**: 毎フレームの sin/cos とバッファ転送を 1/4〜1/8 に。描画側で優先度は低い。

### 施策 11 — esbuild target を es2020 へ

**対象**: `webpack.config.js`

target が `es2015` で出力が膨らんでいる。WebGPU を前提にしている時点で対応ブラウザは es2020 より
広い。`keepNames` は TSL の都合で維持する。

**効果**: js サイズ削減。分量は小。

### 施策 12 — フォントパッケージの差し替え

**対象**: `package.json` / `main.ts`

出力フォントは 6 ファイル 7.87 MB で、うち 4.64 MB がレガシー `.woff`。**これを落とせない。**
`@sarap422/font-hackgen` 同梱の `HackGen-Bold.woff2` が壊れており(brotli 復号に失敗。
`fontTools` でも Chrome でも同じ)、Bold の日本語は `.woff` からしか読めていない。レガシー形式を
落とすと豆腐にならないまま合成フォントへ劣化する — スクリーンショットでは見落とす失敗なので、
`document.fonts` の状態と字幅の実測で確認する。

7.87 MB → 3.2 MB にするにはパッケージの差し替えが要る。**依存の追加・変更を伴う。**

### 施策 13 — 姿勢積分の torque-free 早期 coast

**対象**: `physics/attitude.ts`

剛体力学の反復は既に `ATT_MAX_DYNAMIC_STEPS = 12` で打ち切られ残時間は coast 済みなので、
余地は「トルクゼロなら 12 反復を待たず即 coast に入る」程度(削減率は高々 12 → 数回)。
既存ゲートに条件を足すだけで成立する。

**効果見込みが小さいため、他の項目の後に再計測して要否を判断する。**
`physics/` に触るので `npm run test:physics` が要る。

### 施策 14 — 天体 view の遅延構築

**対象**: `game/celestial/environment-scene.ts` / `game/celestial/celestial-registry.ts`

`EnvironmentScene` のコンストラクタが 101 天体を即時 build している(TSL シェーダ 101 本の
コンパイル、テクスチャ約 18 MB のデコード、リング約 84 オブジェクト)。点群・参照線は既に
遅延化されているのに天体本体だけ遅延が無い。同じ遅延パターンに揃える: 初期表示に要る集合
(地球・月・太陽 + 既定トグルで見える惑星)だけ build し、残りは `MapVisibilityPolicy` が
初めて表示可と判定したフレームで build する。テクスチャ tier(2k → 1k)も施策 6 の設定へ
接続する。

**効果**: 起動時のシェーダコンパイル・デコード・リング構築の大半を先送り。分量は大。
構築タイミングが変わるので `DEVELOP/CALLSTACK.md` と `DEVELOP/OWNERSHIP.md` の記述対象そのもの。

### 施策 15 — `frustumCulled` の見直し

**対象**: `render/` / `game/celestial/`

天体・リング・点群の多くが `frustumCulled = false` で、全表示時 300〜400 draw call が
カリングされずに submit される。実位置に描く天体・リング・参照線はカリング可能
(camera-relative に置く billboard と星空シェルは不可のまま)。boundingSphere が floating
origin の更新と整合するかを確認したうえで有効化する。

**効果**: draw call の submit 削減。分量は中。

| 対象 | なぜ残っているか |
|---|---|
| 戦闘ビューで連射したときの `update` 内訳 | 接触の費用側の手が入った後の実測がまだ無い。**`?stage=1&perf=1` で連射し、`update内訳` の 接触 / その他 / 予測 がどう分布するかを見る。** 参加者そのものを減らす手(薬莢の寿命短縮、`collides` の途中解除)に着手してよいかはこの数値で決まる |

## 保留(着手しない判断が済んでいるもの)

- **multi-rate 積分**(エンティティ別の許容誤差刻み): 高ワープの実測上の主因は per-entity 刻みの
  不在そのものではなく構造増幅だった。構造増幅を除いた後の実測で、なお艦 50 の巡航が支配的な
  場合のみ検討する。propagator 切替の連続性・保存決定性の検証コストが大きい。
- **コード分割**(webpack chunk): .epk とテクスチャは既に個別ファイルで遅延 fetch 可能。
  js 本体の分割は three が大半を占めるため効果が薄い。施策 11 の後に再評価。
- **`physics/` の可変スクラッチ再導入**: immutability は明文化された意図的トレードオフ
  (`CLAUDE.md`)であり、`*Into` の再導入はしない。GC が問題になる場合の答えは substep 数の
  削減で、割り付けの「回数」を減らす。
- **テクスチャの `createImageBitmap` 非同期デコード**: 施策 14 と直交に、ロード時のメイン
  スレッドブロック(JPEG デコード)を消す。要計測。
- **KTX2/BasisU 圧縮テクスチャ**: 配信サイズだけでなく VRAM とアップロード時間も削る。
  jpg 縮小より効果が大きい可能性があるが、パイプライン(変換ツール・ローダ)の導入コストと
  引き換え。
- **地球以外の天体球の分割数**: `CelestialSurface` は 48×24 / 32×16 で既に軽く、優先度は低い。
  月(64×32)含め要計測。
- **マップビュー中の物理の停止・タイムワープの停止・積分頻度の低下・再突入/寿命/衝突判定の
  間引き・マップ表示設定による重力源の削除**: いずれもゲーム挙動を変える。描画軽量化の
  解決策として採用しない。

**ヘッドレス Chrome、1600×1000、production ビルド。fps と render の絶対値はこの環境固有だが、

| マップ・表示期間 28 日 | 17〜32 ms(定常) |
| マップ ×4096 | 約 162 ms |
| マップ ×131072 | 189〜195 ms(substeps 656) |
| 戦闘 ×1 | 10〜18 ms |

| debug-load マップ ×1 | 36〜39 ms(substeps 1) |
| debug-load ×4096 | 357〜381 ms(substeps 21) |
| debug-load ×16384 | 1,388〜1,596 ms(substeps 82) |
| debug-load ×65536 | 5,646〜6,428 ms(substeps 328) |
| debug-load ×131072 | 11,705〜12,041 ms(substeps 656) |

`debug-load` は `stage-debug-load`(小惑星 300 + 破片 500、seed 固定)。

補足:

- **stage1(小惑星なし)の substeps は 656。** 再突入刻みの艦限定化はエンティティが多く低高度に
  個体がいる状況でのみ効く。stage1 ×131072 の約 190 ms は 656 substep ×(暦 + 分類 +
  エンティティ)の素の費用。
- debug-load ×131072 は 1 フレーム 12 秒で、スクリーンショットの取得がタイムアウトする
  (数値は取得できる)。
- 28 日表示では `plan-arcs` が 0 で定常。再積分は各個体の予測が計画の終端に届いた瞬間の
  1 回ずつだけスパイクする。`pred-complete` は 20〜35 秒で全数に到達する。
- 戦闘 ×131072 の `eph-attr` は hit 24 / miss 1,971。**ミス自体は減らない**(substep ごとに
  本当に別の時刻を引くため)が、1 回のミスの費用は重力源専用窓(64 体)で下がっている。
- 28 日表示では `plan-steps` が `PLAN_ARC_MAX_STEPS` = 20,000 の上限に達しており、28 日ぶん
  全部は積分していない(区間が上限で打ち切られる。既存の仕様)。
- 28 日表示では計画軌道のルーラーの日時ラベルが数十個重なって地球面が読めない。負荷とは無関係
  だが、表示期間を長くしたときの実用性の問題として記録する。
- エンティティの一斉消滅は起きていない(小惑星 300 は全ワープ段で維持、破片は緩やかな再突入
  減衰のみ)。例外・コンソールエラーは全条件で 0 件。

## 負荷確認ウィンドウの使い方

**今後の作業では必ずこれを使う。**

- **開き方**: `F3`、または ESC メニューの項目。`?perf=1` を付けて起動すると最初から開いている。
  窓は非モーダルで、ゲームは止まらない。
- **窓**: `hud/property-window.ts` の `PropertyWindow` をそのまま使っている。ヘッダをドラッグして
  移動、📌 でクリップ(常駐)、✕ で閉じる。セクション見出しのクリックで各群を開閉する。
  レイヤは `hud.layers.window`。
- **計測は窓が開いている間だけ走る。** 閉じていれば `performance.now()` は計測目的で 1 回も
  呼ばれず、通常プレイに計測費用がかからない。**逆に、窓を閉じた状態の数値は取れない。**
- **更新は 500 ms ごとのフラッシュ。** 毎フレームは書き換えない。行の差分更新は
  `PropertyWindow.syncRows` が内蔵している。
- **割合は塗り文字**(`████░░░░ 12.3ms`)で示す。基準は 16.7 ms(60 fps の 1 フレーム)。
  グラフやスパークラインは無い。

読める値:

| 群 | 行 |
|---|---|
| (常時表示) | `fps` / `frame`(update+sync+render の合計 avg・p95)/ `warp`(現在倍率) |
| フレーム時間 | `update` / `sync` / `render` 各 avg・p95・max |
| update内訳 | `update` の区間別 avg・max — 入力 / 自機 / ステージ / 積分(内訳として字下げで 軌道積分・接触・姿勢)/ 予測 / 演出 / 計画 / マップ候補 / カメラ / ポインタ / **その他**。通らなかった区間も 0.0 ms の行として出る |
| 計画軌道 | `recompute`(再積分回数/frame)/ `steps`(積分ステップ/frame) |
| 予測 | `tracked` / `complete` / `discard` / `steps` |
| シミュレーション | `substeps` / `entitySteps` / `gravitySources` |
| 暦キャッシュ | `attractorsAt hit/miss` / 全リング `hit/miss` |
| 表示 | `view`(combat/map)/ `pickables` / `labels` / 表示期間 |
| エンティティ | `players` / `enemies` / `bullets` / `casings` / `debris` / `ammos` / `asteroids` / `bases` |
| メモリ | `JS heap` |

暦キャッシュのヒット/ミスは `Ephemeris` 側では累積値で、窓が前回との差分を取って表示する
(`Ephemeris` はフレームの概念を持たない)。セーブロードを跨いでもリセットしない。

**`update` の区間は入れ子ではない。** 積分の内訳3区間(軌道積分・接触・姿勢)は表示上だけ字下げして
あり、合計が親の「積分」を成すわけではない。`その他` は計測点を持たず、`update` 全体から各区間の
合計(積分の内訳は除く)を引いた差として出るので、区間の外へ時間が逃げていればここに現れる —
`game/nan-watchdog.ts` の全エンティティ走査、`docking.checkProximity`、
`targeter.updateBoardMarks` はどの区間にも属さずここへ落ちる。

固定シナリオは既存の `?stage=` デバッグステージで賄う: `stage-debug-load`(小惑星 300 +
破片 500、seed 固定)と、クリエイティブで艦 0/1/10/50 を配置したスナップショット
(セーブ機構で再現可能)。比較条件は ×1 / ×4096 / ×131072、再突入境界に 1 体置いた状態、
28 日表示 + ノード 3 個の計画。比較は p50 だけでなく p95 と最大フレームを見る。

## 検証の作法

- **各施策ごとに `npm run typecheck`。** これは常に走らせる。
- **`npm run test:physics` は `physics/` を触ったときだけ。** 施策 2(ephemeris-pack)、
  施策 13(attitude)がこれに当たる。
- **`npm run build` は総合検証時のみ。** `docs/` の公開バンドルを書き換えるので、ロードサイズを
  記録する必要があるときに走らせる。
- **物理不変条件**: 同じ初期スナップショット・同じ経過 sim time に対し、表示設定を変えても
  物理 state(位置・速度・イベント順・破壊結果)が一致すること。表示設定と無関係の常時挙動を
  変える施策は、変更前後で「許容誤差内の一致」を `stage-debug-load` + スナップショット比較で
  確認する。
- **設定の検証**: 保存・復元・不正値フォールバック・preset→カスタム遷移。
- **ロードの検証**: `docs/` 合計サイズと、キャッシュ無効での初回表示時間(WebGPU init 〜
  初フレーム)を before/after で記録する。

ヘッドレス検証(`/verify`)の注意点:

- **`--mode development --no-client-overlay` が要る。** production ビルドをそのまま headless で
  開くと dev-server のオーバーレイが被る条件がある。
- **`localStorage.clear()` が要る。** 前回のセーブスロット・トグル状態・品質設定が残っていると
  起動先(タイトル/ステージ/クリエイティブ)も表示条件も再現しない。
- **ホイールズームが効かない。** 遠距離ズームに依存する確認(ラベル混雑、小天体の表示、
  リングの線/面クロスフェード)はヘッドレスでは取れない。
- **stage1 は約 2 分で撃墜される。** それより長い定常観測が要る条件では、`stage-debug` 系
  (`checkWin()` が常に false)を使う。
- render の絶対値は実機と乖離する。カウンタ類だけが環境非依存であることを踏まえて読む。

## 設計文書の更新義務

`CLAUDE.md` の「設計文書 — 更新は義務」に従い、**`src/` を変更したら同じ変更セットの中で次の文書も
更新する。「あとでまとめて」にしない。**

- **`CLAUDE.md`** — モジュールの責務と「なぜそうなっているか」。ファイルの新設・削除・移動・改名、
  責務の移動、キー割り当てや操作系の変更、定数の意味が変わる変更で更新する。
  古い記述を残すより消す方がよい。旧記述は書き換える(歴史的経緯を書かない)。
- **`DEVELOP/CALLSTACK.md`** — per-frame 呼び出し依存木。毎フレーム走る関数の追加・削除・改名・
  順序変更・条件変更で更新する。施策 14(構築タイミング)が該当する。
- **`DEVELOP/OWNERSHIP.md`** — インスタンス保持木と状態の正本。クラスの new 位置・フィールドの
  所有・参照共有・キャッシュが動いたら更新する。施策 6(`PerformanceSettings` の所有)と
  施策 14 が該当する。
- **`DEVELOP/SPEC.md`** — プレイヤーから見える挙動・数値が変わったら更新する。ここに挙げた施策は
  いずれも表示・キャッシュ・予算・ロードの変更で、**プレイヤーから見える物理挙動は変えない想定。
  もし変わったならそれは不具合** — この確認自体を検証項目とする。品質設定(施策 6)だけは
  見える挙動なので `SPEC.md` に載る。
