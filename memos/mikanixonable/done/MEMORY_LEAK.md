# 戦闘中のメモリリーク・ブラックアウト（WebGPU Device Lost）の調査結果

ご推察の通り、**複数のメモリリークと、共有リソースの誤破棄が複合して起きていました。** 
WebGPU は WebGL に比べてリソース管理が厳密なため、解放済みのバッファ（破棄された Geometry）にアクセスして描画しようとした瞬間、`Device Lost`（クラッシュしてブラックアウト）が発生します。
リロードすると復帰するのは、WebGPU デバイスのコンテキストが新しく作り直されるためです。

調査の結果、以下の3つの主要な問題（リークと誤破棄）を特定しました。

## 1. 致命的バグ: `DebrisPiece.dispose()` による共有ジオメトリの破壊（ブラックアウトの直接原因）
- **対象**: 薬莢 (Casing)、爆発破片 (debrisChunk, debrisPanel, debrisRod)、排出マガジン
- **問題**: `DebrisPiece` が寿命を迎えて `dispose()` される際、自身のマテリアルだけでなく `mesh.geometry.dispose()` を呼んでいます。しかし、これらのジオメトリは `memoParse()` によって**全個体で共有**されています。
- **結果**: 1つの薬莢（または破片）が消滅すると、**共有されているジオメトリが破壊**されます。次のフレームで、まだ生きている他の薬莢や破片を描画しようとすると、WebGPU が「破壊済みのバッファを参照した」としてクラッシュ（Device Lost = ブラックアウト）します。
- **対処**: 全デブリ・薬莢は共有ジオメトリを使っているため、`mesh.geometry.dispose()` を呼び出してはいけません。マテリアルの破棄のみを行います。

## 2. メモリリーク: `Enemy` がマテリアルを破棄していない
- **対象**: 敵機 (Enemy)
- **問題**: `buildEnemyShip` は `memoParse()` を経由して作られ、個体ごとにマテリアルが `clone` されて独立した GPU リソース（マテリアル）を持ちます。しかし、`Enemy.dispose()` は実装されておらず、基底クラスの `scene.remove(this.obj)` しか呼ばれません。
- **結果**: 敵を撃破するたびに、独立したマテリアルが GPU メモリに残り続けます（メモリリーク）。これが蓄積すると OOM (Out Of Memory) や処理落ちの原因になります。
- **対処**: `Enemy` クラスに `dispose()` を実装し、トラバースして `mesh.material.dispose()` を呼ぶようにします（ジオメトリは共有なので破棄しません）。

## 3. メモリリーク: `Ammo` (補給) がマテリアルを破棄していない
- **対象**: 補給ビーコン (Ammo)
- **問題**: `Ammo` も Enemy と同様にマテリアルが `clone` されていますが、`dispose()` 時にマテリアルが解放されていません。また、`count != 4` のケースでは都度 `new THREE.OctahedronGeometry` が作られ、これもリークします。
- **結果**: 補給が取り込まれたり寿命で消えたりするたびにマテリアル（および非規定数の場合はジオメトリ）がリークします。
- **対処**: ビーコン用のジオメトリとマテリアルをモジュールスコープで共有・キャッシュし、`Ammo` クラスでも `dispose()` をオーバーライドしてクローンされたマテリアルを解放するようにします。

---

※補足: `Bullet`（弾）と `FlashEffect`（閃光）について
- 弾丸とプラズマ弾は、マテリアルもジオメトリも完全に共有する `memoParseShared` を使っており、個体ごとのリークは発生しません。
- 閃光（Billboard）は毎度生成と破棄を行っていますが、自身の `dispose()` で正しくジオメトリとマテリアルを解放しているため、リークはしていません。

## 結論と修正方針
ユーザー様の見通しは完全に正しかったです。
ブラックアウトの直接の引き金は「薬莢・破片の共有ジオメトリの誤破棄（1）」であり、これに加えて敵機と補給アイテムの「マテリアル破棄忘れ（2, 3）」によるメモリリークが重なっていました。

これらを修正する実装計画を `implementation_plan.md` にまとめます。

# メモリリークとブラックアウトの修正計画

調査メモ (`memos/MEMORY_LEAK_ANALYSIS.md`) にて特定した、メモリリークおよび WebGPU クラッシュ（ブラックアウト）の原因を修正します。

## Goal Description
1. **ブラックアウトの直接原因の解消**: 薬莢やデブリが消滅する際、他の個体と共有しているジオメトリごと破棄してしまうバグ（WebGPU Device Lostの引き金）を修正する。
2. **メモリリークの解消**: 敵機や補給アイテムが消滅する際、クローンされた独自マテリアルが GPU 上に残り続けるリークを解消する。

## 修正内容

### [MODIFY] [entities.ts](file:///d:/lab2/dive-into-tepui/src/game/orbit-entity/entities.ts)
`dispose` のリソース管理を修正し、マテリアルの破棄漏れとジオメトリの誤破棄を直します。

1. **`DebrisPiece.dispose()` の修正**
   - 既存コードにあった `mesh.geometry.dispose();` の行を**削除**します。デブリ・薬莢はすべて共有ジオメトリを使っているため、破棄してはいけません。
2. **`Ship` クラスに `dispose()` を追加**
   - 敵機は個体ごとに独自のマテリアル（色違いなど）を持っています。`scene.remove()` だけでなく、トラバースして `mesh.material.dispose()` を行う処理を追加します。
3. **`Ammo` クラスに `dispose()` を追加**
   - 補給アイテムもクローンされたマテリアルを持っています。同様に `mesh.material.dispose()` を行う処理を追加します。

### [MODIFY] [ships.ts](file:///d:/lab2/dive-into-tepui/src/render/ships.ts)
`Ammo` 生成時のリーク箇所を最適化します。

1. **`buildAmmo()` の修正**
   - 補給ビーコンの光（`OctahedronGeometry` と `MeshBasicMaterial`）が呼び出しのたびに `new` されてリークする状態でした。これをモジュールスコープにキャッシュして共有するように書き換えます。
2. **`cloneIndependent` の方針はそのまま維持**
   - 前回(B13)の修正案では `debrisPanel` などで `geometry.clone()` を行うアプローチをとりましたが、これは GPU メモリ効率を悪化させるため破棄します。元の「すべて `memoParse` でジオメトリを共有し、マテリアルだけクローンする」設計は正しかったので、それを維持したまま **破棄（dispose）側のロジックだけを直す** のが正しいアプローチです。
