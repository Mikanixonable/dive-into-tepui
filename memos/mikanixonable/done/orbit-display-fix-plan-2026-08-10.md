## 0. この計画書の目的と適用範囲

Tepui の軌道表示は3つの線が同じ画面に重なる構造になっている。

- **解析楕円**(`src/render/orbit-line.ts` の `OrbitLine`) — 現在の接触軌道要素から閉じた楕円を1本描く。
- **積分予測線**(`src/game/predicted-trajectory-line.ts` の `PredictedTrajectoryLine`) — `Predictor` が
  RK4 で実際に伸ばした未来の状態列を実線で描く。解析楕円の置き換えであり、追加ではない。
- **計画軌道線**(`src/game/plan/plan-arc.ts` の `PlanArc` を `PlanPath` が区間ごとに並べたもの) — まだ
  実行されていない要求としての軌道を破線で描く。

この3本が「いつどちらを出すか」「どの座標系に焼くか」「どの状態を起点にするか」を、それぞれ別の
モジュールが別の判断基準で決めている。2026-08-10 に実施した調査で、その判断基準の不整合に由来する
不具合と、責務の置き場所の誤りが見つかった。この計画書はその修正を5つのフェーズに分けて記述する。

適用範囲は `src/game/plan/`、`src/game/simulation/predictor.ts`、`src/game/game-entity/game-entity.ts`、
`src/render/orbit-line.ts`、`src/render/sampled-line.ts`、`src/game/predicted-trajectory-line.ts`、
`src/game/debug-trajectory-line.ts`、`src/game/map-picker.ts`、`src/game/object-list-panel.ts`、
`src/game/display-time-panel.ts`、`src/game/frame-controls.ts`、`src/game/view-manager.ts`。

各フェーズは独立してコミットできる。フェーズ1から順に実施することを想定しているが、フェーズ間に
コード上の依存はない(フェーズ3はフェーズ2の `EMPTY` 定数を利用するが、無くても成立する)。

## フェーズ1: 入力の取りこぼしと暴走の停止

このフェーズは「操作しているつもりのない副作用が起きる」種類の不具合だけを扱う。いずれも変更範囲が
数行で、他のフェーズと衝突しない。

### 1-1. Δv アームのラッチが要素削除で解除されない

**現状** — `src/game/plan/node-gizmo.ts` の `NodeGizmo` は、マニューバノードの Δv 編集アームを
DOM 要素として持つ。アームを一定ピクセル(`C.DV_DRAG_LATCH_PX`)以上ドラッグすると「ラッチ」状態に
入り、`NodeGizmo.latch` に軸と超過ピクセル量が入る。`PlanEditor.updateEditing` は毎フレーム
`latch` を読み、超過量に比例した Δv を加算し続ける。ポインタを止めても加算が続くのは意図した挙動で、
大きな Δv を指で描き切らずに入力できるようにするためのもの。

ラッチを解除するのは、アーム要素自身に張られた `pointerup` / `pointercancel` ハンドラだけである。
一方 `NodeGizmo.sync` は、表示すべきアームの本数が減ったときに `this.axisEls.pop()!.remove()` で
要素を DOM から取り除く。このとき `latch` も `activeAxis` も触らない。

**何が起きるか** — ラッチ中に Δv を加算した結果、下流のノードが `Plan.applyNodeDv` によって破棄され、
選択が外れる、あるいは `PlanEditor.removeSelectedIfEmpty` が走ってノード自体が消える。すると次の
`sync` でアーム要素が `remove()` され、そのポインタの `pointerup` は永久に届かない。`latch` は
残ったままなので、`updateEditing` は**指を離した後も毎フレーム Δv を加算し続ける**。ユーザーから
見ると、マップを開いている限り計画軌道が勝手に変形し続け、止める手段がない。

**修正** — `NodeGizmo.sync` がアーム要素を `remove()` する経路で、`this.latch = null` と
`this.activeAxis = null` を同時に行う。アーム要素の存在とラッチ状態は同時に切り替わるべき対であり、
片方だけを更新してよい場面が存在しない。

**何が良くなるか** — 「入力を受け付ける DOM 要素が消えたのに、その要素が生んだ継続入力だけが
生き残る」という状態そのものを構造的に消す。この種のバグは再現条件が偶然に依存し、発生後も
原因が画面に現れないため、テストでも目視でも捕まえにくい。要素と状態の寿命を揃えることで、
今後アームの表示条件を変更しても同じバグが再発しなくなる。

### 1-2. HUD の文字入力がゲーム操作キーとして解釈される

**現状** — `src/game/input/input.ts` の `Input` は `window` に対して直接 `keydown` を購読している。
HUD 上の入力欄がキーイベントの伝播を止めなければ、欄に文字を打った瞬間に同じキーがゲームの操作
として解釈される。

`src/game/hud/object-picker.ts` の絞り込み欄は、`keydown` に対して `stopPropagation` を行っており
正しい。これに対し、`src/game/display-time-panel.ts` の `DurationValueInput` の数値入力欄は
`pointerdown` の伝播しか止めておらず、`src/game/object-list-panel.ts` の検索欄も同様に
`pointerdown` しか止めていない(行として散らばった `stopPropagation` は、それぞれパネル全体に
対する `pointerdown` と、一覧の行に対する `keydown` のもので、入力欄自身のものではない)。

**何が起きるか** — PREDICT バーの表示期間欄に「1」と打つとスロットル段が切り替わり、軌道オブジェクト
一覧の検索欄に「m」と打つとマップビューが閉じる。入力欄が受け取ったつもりのキーが、同時にゲームの
状態を変える。

**修正** — `DurationValueInput` の数値入力欄と、`ObjectListPanel` の検索欄の両方に、
`object-picker.ts` と同じ形の `keydown` 伝播停止を追加する。

**何が良くなるか** — HUD の入力欄という同じ役割の要素が、モジュールごとに異なる扱いになっている
状態を解消する。「`Input` が window を購読している以上、テキスト入力欄は必ず `keydown` を止める」と
いう規約を全入力欄で満たすことで、今後入力欄を追加するときの判断が一意になる。

### 1-3. 選択中ノードを index で保持しているため、別ノードへ黙って移る

**現状** — `src/game/plan/plan-editor.ts` の `PlanEditor.selectedNodeIdx` は `number | null` で、
`Plan.nodes` 配列への添字である。`PlanEditor.deleteNode` と `PlanEditor.setActivePlayer` は
削除・艦切替に伴って選択を解除するが、`Plan.dropNodesBefore` による補正は行われていない。

`Plan.dropNodesBefore` は実行時刻を過ぎたノードを配列の**前方から** `splice` で取り除く。この
メソッドはマップを開いているかどうかに関係なく走る。具体的には、クリエイティブモードで
`planExecution` が `'instant'` または `'powered'` の艦がノードを消化したときに、
`CreativeStage.applySimulationEvents` および `PlanExecutor.finish` から呼ばれる。

**何が起きるか** — マップを開いてノードを選択したまま時間が進み、選択したノードより前のノードが
消化されると、配列が前方に詰まって `selectedNodeIdx` は**別のノード**を指す。以後の Δv 編集
(キー入力・アームドラッグ・ボタン長押しのすべて)は、ユーザーが選んだのとは違うノードに入る。
画面上はギズモが別ノードへ移動するだけなので、原因が推測できない。

**修正** — 選択をノードの参照(`KinematicState`)で保持する。`Plan` のノードは不変オブジェクトで
あり、編集のたびに新しい `KinematicState` へ置き換わる(この不変性は `GameEntity.orbitalElementsAround`
のメモ化と `DynamicTrajectory` の履歴記録が依存している、プロジェクト全体の前提である)。したがって
参照で持てば「編集で置き換わったノード」と「消化されて消えたノード」の両方を、配列位置ではなく
同一性で判定できる。index が必要な箇所(`Plan.applyNodeDv` の引数など)は、参照から
`Plan.nodes.indexOf` で表示時に引き直す。

**何が良くなるか** — ノード列の途中が外部要因で消えるという事象が、選択状態を壊さなくなる。
index による保持は「配列が前方から詰まらない」という、`Plan` が保証していない仮定に依存していた。
参照保持はその仮定を不要にする。加えて `deleteNode` と `setActivePlayer` に散っている選択補正の
特別扱いも不要になり、選択のライフサイクル管理が1箇所に収束する。

### 1-4. クラスフィルタの押下表示が「近傍」ボタンの表示を消す

**現状** — `src/game/object-list-panel.ts` の `ObjectListPanel` は、ヘッダに `object-list-tools`
クラスの `div`(変数名 `tools`)を1つ作り、そこへ「近傍のみ」トグルボタンと、天体クラス別の
フィルタボタン群を**同居させている**。クラスフィルタのクリックハンドラは
`tools.querySelectorAll('button')` で `tools` 配下の全ボタンを走査し、押されたボタン以外の
`aria-pressed` を `'false'` に落とす。

**何が起きるか** — 「近傍のみ」を有効にした状態でクラスフィルタを押すと、`nearOnly` フィールドは
`true` のままなのに、近傍ボタンの `aria-pressed` だけが `'false'` に書き換わる。絞り込みは効いて
いるのに、効いていないように見える。スクリーンリーダーに対しても誤った状態を報告する。

**修正** — 排他選択の走査範囲を、クラスフィルタボタンだけを含む配列に限定する(ハンドラ生成時に
クラスフィルタのボタン参照を配列へ集めておき、それを走査する)。DOM の親子関係を状態の
グルーピングに流用しない。

**何が良くなるか** — 「同じ親要素に入っている」ことと「同じ排他グループに属する」ことは別の概念で
あり、前者を後者の代わりに使うと、レイアウト都合の要素追加が状態表示を壊す。参照配列に切り替える
ことで、今後 `tools` に何を追加しても排他ロジックが影響を受けなくなる。

## フェーズ2: 再 bake・再積分ガードの正常化

このフェーズは「毎フレーム同じ計算をやり直している」種類の非効率と、そのガードが壊れていることに
起因する表示の誤りを扱う。

### 2-1. 空配列リテラルが線の再 bake ガードを常時無効化している

**現状** — `src/render/sampled-line.ts` の `SampledLine.syncGeometry` は、渡されたサンプル列が
前回と**同じ配列参照**であれば頂点の焼き直し(bake)を省略する。`DynamicTrajectory.samplesOldestFirst`
は結果をメモ化しており、`step` / `reset` が呼ばれない限り同じ配列参照を返すので、このガードは
本来成立する。

`src/game/predicted-trajectory-line.ts` の `PredictedTrajectoryLine.sync` は
`entity.predictedTrajectory?.samplesOldestFirst() ?? []` と書いており、予測軌道が存在しない間は
**毎フレーム新しい空配列**を作る。`src/game/debug-trajectory-line.ts` も同じ形の `?? []` を持ち、
さらに過去列と未来列を連結した結果をキャッシュする `concatCache` が、入力配列の参照同一性で
ヒット判定を行っているため、この空配列によって**キャッシュが絶対にヒットしなくなる**。

**何が起きるか** — 予測が空の間、`syncGeometry` は毎フレーム bake 経路を通る。頂点は0本なので
描画結果は変わらないが、`SampledLine` が内部に持つ「最後に bake したときの m/px」
(`lastScale`)が意味のない値(1)に書き換わる。その後に実際のサンプル列が届くと、スケール比較の
基準が壊れているため不要な再 bake が誘発される。デバッグ線に至っては、毎フレーム
`[...currentSamples]` のスプレッドと全頂点の焼き直しが走る。

**修正** — モジュールスコープに `const EMPTY: readonly KinematicState[] = []` を1つ置き、両方の
`?? []` をこれに置き換える。あわせて `SampledLine.syncGeometry` が、サンプル数0のときには
`lastScale` を更新しないようにする。

**何が良くなるか** — 参照同一性に依存したキャッシュは、呼び出し側がうっかりリテラルを書いた
瞬間に、無言で全面的に無効化される。壊れても動作は正しいままなので、性能計測をしない限り
気づけない。共有定数にすることで、この失敗の可能性そのものを潰す。

### 2-2. スケール評価点がサンプル列の中央にある

**現状** — `SampledLine.syncGeometry` は、bake が必要かどうかの判定に「サンプル列の中央の点に
おける m/px」を使う。カメラが動けば線の見え方が変わるので、スケール変化で再 bake するのは正しい。

しかし予測軌道の列は毎フレーム先端が伸びるため、**カメラが静止していても中央のサンプルが移動する**。
その結果 m/px が変動し、再 bake 条件に効いてしまう。

**修正** — 評価点を列の先頭サンプル(あるいは表示座標系の原点)に固定する。先頭は予測列が伸びても
移動しない。

**何が良くなるか** — 「カメラのズームが変わったから焼き直す」という本来の意図と、実装が一致する。
現状は「列が伸びたから焼き直す」が混入しており、伸長が続く限りガードが利かない。

### 2-3. 計画軌道の起点交代が非連続として扱われない

**現状** — `src/game/plan/plan-arc.ts` の `PlanArc.update` は、再積分するかどうかを判定する。
計画にノードが1つも無い間、末尾区間の起点(`state0`)は自艦の現在状態に毎フレーム追随する
(`tracksLiveAnchor` が `true`)。この場合 `state0` は毎フレーム別オブジェクトなので、同一性比較は
役に立たない。そこで「区間長の変化」と「起点時刻の前進量」を、いずれもサンプル間隔と比較する
閾値判定に委ねている。描画結果が目に見えて変わらない程度の差なら再積分しない、という設計である。

この閾値判定は「同じ軌道が時間方向に進んだだけ」という前提の上でのみ正しい。前提が崩れるのは、
起点が**別の軌道へ飛ぶ**ときである。具体的には `Game.setActivePlayer` による操作艦の切替、
ドックからの発進、衝突による状態上書きが該当する。この非連続を拾うために `anchorSwapped` という
条件が置かれているが、その定義は

    state0 !== this.key.state0 && state0.t <= this.key.state0.t

であり、**時刻が前進していない場合しか非連続と認めない**。

**何が起きるか** — 艦を切り替えると、新しい艦の状態は当然ながら前回の再積分時刻より後の時刻を
持つ。したがって `anchorSwapped` は `false` になり、区間長も起点時刻の前進量もサンプル間隔未満
なので、他の条件も `false` になる。結果として `PlanArc` は再積分を行わず、**前の艦の軌道を
描き続ける**。サンプル間隔ぶんの時間が経てば `anchorDrifted` が立って直るが、その間ユーザーは
存在しない軌道を見ている。

**修正** — 非連続の判定に状態値の差を加える。`state0` の同一性が変わったとき、前回の
`key.state0` から予測される位置・速度と実際の値の差が閾値を超えていれば、時刻の前後に関係なく
再積分する。判定に使うのは位置差(例: 数 km)と速度差(例: 数 m/s)で、いずれも「同じ軌道が
1フレーム進んだ」場合には到達し得ない大きさに取る。

**何が良くなるか** — 「時刻の前後」という代理指標で非連続を検出しようとした設計を、非連続そのもの
(状態の飛び)を見る形に改める。代理指標は、代理として成立する条件が暗黙のうちに崩れたときに
無言で機能を失う。値の比較に置き換えることで、今後どのような経路で起点が差し替わっても検出できる。

### 2-4. 再積分キャッシュキーに基準天体が含まれていない

**現状** — `PlanArc.update` が保存するキャッシュキー(`ComputeKey`)は、起点状態・終了時刻・重力源
プロバイダのリビジョンから成る。近地点/遠地点の検出基準となる `apsisCenter` は含まれていない。
`apsisCenter` は `PlanPath` が末尾区間についてのみ `strongestAttractor` で解決して渡す。

**何が起きるか** — 起点も終端も変わらないまま、影響圏の境界を越えて `strongestAttractor` の
結果だけが変わると、再積分が行われず、近地点/遠地点アイコンが**古い天体を基準にした位置に
残り続ける**。

**修正** — `ComputeKey` に `apsisCenter?.id` を加え、比較対象に含める。

**何が良くなるか** — キャッシュキーは、計算結果に影響する入力をすべて含まなければならない。
`apsisCenter` は `integrate` に渡され結果を変えるので、キーに含まれないのは単純な漏れである。

### 2-5. 死にコードの除去

**現状** — 以下の3箇所が到達不能または恒真である。

- `src/game/plan/plan-path.ts` の `hasFinalSegment` は `segments.length > plan.nodes.length` で
  定義されているが、`buildSegments` は常にノード数+1本の区間を作るため**恒真**である。これに
  依存する `finalSegmentStart` / `finalSegmentSamples` / `finalPeriapsisPoint` /
  `finalApoapsisPoint` の4つの三項演算子は、`null` 側の枝へ決して入らない。
- `src/game/plan/plan-arc.ts` の `at()` にある `trajectory === null` の分岐は、`integrate()` が
  必ず `trajectory` を代入するため初回 `update` 前にしか到達せず、そこでは `_samples` も空である。
  さらにその分岐の後段にもう一度置かれた `if (this.trajectory === null) return null;` は完全に
  到達不能である。
- `src/game/plan/plan-arc.ts` の `recomputed` フィールドは、リポジトリ全体から外部参照が無い。

**修正** — `hasFinalSegment` を削除して4フィールドを非 null にする。`at()` の到達不能な分岐を
削除する。`recomputed` をローカル変数に降格する。

**何が良くなるか** — 恒真な条件は「そうでない場合がある」という誤った読みを次の実装者に強制する。
`finalSegmentStart` が `null` になり得ると読めば、その `null` を扱う分岐が呼び出し側にも増殖する。
実際 `Game.equatorNodeSources` と `PlanDisplay.apsisIconsOf` は、決して来ない `null` のための
分岐を持っている。恒真条件の除去は、それらを連鎖的に単純化する起点になる。

## フェーズ3: 解析楕円と積分予測線の切替の一本化

### 3-1. 抑制条件が「頂点が2本以上あるか」でしかない

**現状** — 解析楕円(`OrbitLine`)は、積分予測線が描かれている間は重ねて出さない設計である。
その判定は `src/game/game.ts` の `Game.sync` にあり、
`ship.orbitLine.setSuppressed(this.predictedTrajectoryLine.hasLineFor(ship))` と書かれている。
`PredictedTrajectoryLine.hasLineFor` は、対象が今フレーム同期された集合に含まれ、かつ
`SampledLine.visible` が真であることを返す。`SampledLine.visible` は「頂点が2本以上ある」ことしか
意味しない。

**何が起きるか** — 予測が破棄された直後、`Predictor` の予算で数百メートルぶんだけ伸びた切れ端でも
`visible` は真になる。その瞬間から完全な解析楕円が消え、短い線分だけが残る。とくに
`Player.behave` は推力が非 null になるたびに `invalidatePrediction()` を呼び、`stepPredicted` は
推力中の伸長を拒否するため、**噴射のたびに予測が空になり、楕円が消えては戻るフリッカーが起きる**。
これは軌道表示の中で最も目につく不具合である。

**修正** — 抑制条件を「予測列の先端が現在の表示ホライズンに到達しているか」に変える。この判定は
`Predictor` が既に `complete` カウンタのために行っているものと同一なので、新たな計算は要らない。
`PredictedTrajectoryLine` には `hasLineFor` の代わりに
`coversHorizon(entity, simTime, horizon): boolean` を持たせる。

**何が良くなるか** — 解析楕円は「積分予測が間に合っていないときの代替表示」である。したがって
抑制すべき条件は「代替が不要になったか」すなわち「予測が必要な範囲を覆ったか」であって、
「線が1本でも描けたか」ではない。条件を意味に一致させることで、噴射中・高時間加速中・艦を
配置した直後という、まさに代替表示が必要な場面で楕円が正しく出るようになる。

### 3-2. `synced` 集合の廃止

**現状** — `PredictedTrajectoryLine` は `synced: Set<GameEntity>` を持つ。これは `hasLineFor` が
`EntityLineSet.lineFor` を呼ぶと、**問い合わせただけで線を新規作成してしまう**ため、その副作用を
打ち消す目的だけで存在する。

**修正** — `src/game/entity-line-set.ts` の `EntityLineSet` に、副作用のない
`peek(entity): SampledLine | undefined` を追加し、`synced` を廃止する。

**何が良くなるか** — 「存在を問い合わせる」操作が「存在させる」副作用を持つ API は、呼び出し側に
防御的な状態を持つことを強制する。`peek` の追加はその強制を取り除き、`PredictedTrajectoryLine` から
1つ状態が減る。

### 3-3. renderOrder の集約

**現状** — 解析楕円(`OrbitLine`)と積分予測線(`PredictedTrajectoryLine` が構成する `SampledLine`)
は、どちらも `renderOrder` に 1 を割り当てている。フェーズ3-1 の修正後も、抑制が切り替わる境界の
1フレームでは両方が描かれ得る。同値の `renderOrder` では透明描画の順序が未定義になる。

さらに `renderOrder` の割り当ては、自機軌道=1、副目標=2、主目標=3、計画線=4、参照線=0 と、
複数のファイルに散っている。

**修正** — `renderOrder` の割り当て表を1箇所(`src/game/const.ts`)に集約し、積分予測線を解析楕円と
異なる値にする。

**何が良くなるか** — 描画順序は線どうしの相対関係であり、個々の線が単独で決められる性質のもの
ではない。表を1箇所に置くことで、線を追加するときに既存の順序全体を見て決められるようになる。

## フェーズ4: ノード消化 API の一本化と予測ホライズンの整合

### 4-1. ノード消化が3経路に分散し、アンカー方針が食い違う

**現状** — マニューバノードを「実行済みとして消化する」処理は、次の3経路にある。

1. `src/game/plan/plan-executor.ts` の `PlanExecutor.finish` — `Plan.dropNodesBefore` を呼んだ後、
   `Plan.overwriteAnchor(ship.state)` で**実際に到達した状態**をアンカーにする。
2. `src/game/plan/plan-guide.ts` の `PlanGuide.update` および `notifyAchieved` — `dropNodesBefore` を
   呼ぶだけ。
3. `src/game/stages/creative-stage.ts` の `CreativeStage.applySimulationEvents`(`'instant'` 実行) —
   `dropNodesBefore` の戻り値(最後に落としたノード)を艦の状態に直接代入する。

`Plan.dropNodesBefore` は、落としたノードのうち最後のものへ**アンカーを再凍結する副作用**を持つ。
このため経路2では、以降の計画軌道の起点が「ノードの理想値」になる。経路1では直後に
`overwriteAnchor` が上書きするので「実到達値」になる。

**何が起きるか** — 同じ「ノードを消化した」というイベントに対して、以降に描かれる計画軌道の起点が
誤差込みか誤差なしかで分岐する。`'powered'` 実行の目的は「計画との誤差を可視化すること」なので、
経路2が誤差を消してしまうのは目的と矛盾する。また `notifyAchieved` は残ノード数を
`nodes.length - 1` で計算した後に `dropNodesBefore` を呼ぶが、同時刻ノードが複数ある場合は複数落ちる
ため、HUD の表示件数が実際と合わない。

**修正** — `Plan` に `consumeNodesUpTo(t: number, actualState: KinematicState): number` を追加し、
落としたノード数を返す。この中でアンカーは常に `actualState` に設定する。`dropNodesBefore` が
持つ暗黙のアンカー書き換えは廃止する。3経路すべてを `consumeNodesUpTo` に置き換える。
経路3(`'instant'`)は、艦の状態をノードの値に代入した上で、その値を `actualState` として渡す
(瞬間移動では理想値と実到達値が一致するため、これで従来と同じ結果になる)。

**何が良くなるか** — 「ノードを消化したら、以降の計画は実際に到達した状態から描く」という
規則がひとつになる。現状は同じ規則を3箇所が別々に(うち1箇所は副作用として暗黙に)実装しており、
どれか1つを直しても他が食い違ったままになる。API に `actualState` を必須引数として持たせることで、
呼び出し側は「何を起点にするか」を明示せざるを得なくなり、暗黙の分岐が生じ得なくなる。

### 4-2. 予測の許容誤差が「現在の表示期間」に追随して破棄を誘発する

**現状** — `src/game/game-entity/game-entity.ts` の `GameEntity.resyncPrediction` は、予測列が実際の
状態からどれだけ乖離したかを見て、閾値を超えていれば列を破棄する。この閾値
(`resyncTolerance`)は固定値ではなく、「予測列の間引き間隔における Hermite 補間の誤差」に
合わせて広げられている。長い表示期間では列が粗く間引かれ、補間誤差そのものが数十キロメートルに
達するため、固定閾値では正しい予測が「乖離した」と誤判定されてしまうからである。

問題は、この閾値も、間引き間隔を決める `sampleInterval` も、**現在の表示期間**から導かれるのに対し、
実際の列は**それが積まれた時点の表示期間**で間引かれていることである。表示期間を変更したときに
予測列を無効化する経路は存在しない(`DisplayTimeManager` の `onDurationSelect` はスライダー位置を
0 に戻すだけである)。

**何が起きるか** — 表示期間を「28日」から「90分」に切り替えると、粗い間隔で積まれた既存の列に
対して閾値だけが数十キロメートルから500メートル級に縮む。その結果、正しい列が毎フレーム破棄され、
**予測が二度と伸びきらなくなる**。逆向きの切替では、閾値が広がりすぎて本当の乖離を見逃す。

**修正** — 間引き間隔を `DynamicTrajectory` 自身に記録し(`step` に渡された `sampleInterval` を
保持する)、`resyncTolerance` はその記録値から導く。加えて、`resyncTolerance` の上限が現在
「最強重力源からの距離の2%」になっている点を改め、局所軌道スケールに基づく上限に変える
(惑星間区間で最強重力源が恒星になると、上限が実質無制限になり、乖離した列が描かれ続けるため)。

**何が良くなるか** — 「この列はどれだけ粗いか」は列自身の属性であり、現在の UI 設定から推定する
べきものではない。列に記録することで、表示期間の変更が予測の生存に影響しなくなる。ユーザーから
見ると、表示期間を切り替えても未来位置のゴーストと予測線が消えなくなる。

### 4-3. 予測予算の配分で他エンティティが停止する

**現状** — `src/game/simulation/predictor.ts` の `Predictor.update` は、まず操作対象艦に
`PREDICT_STEP_BUDGET` の予算を渡し、その残りで全エンティティのラウンドロビンを回す。艦の予測が
未完成の間は予算が使い切られ、ラウンドロビンに入らず `cursor` も進まない。

**何が起きるか** — 長い表示期間では操作艦の予測完成に数十フレームかかり、その間 `Base` /
`Asteroid` / `Ammo` の予測が完全に停止する。これらの予測は表示だけでなく、
`predictedAttractorsAt` を通じて**計画軌道の重力源**としても消費されるため、計画軌道の形が
操作艦の予測進捗に依存してしまう。

**修正** — 操作対象艦に渡す予算に上限(全体の半分など)を設け、残りを必ずラウンドロビンに回す。

**何が良くなるか** — 「操作艦を優先する」という意図を保ちつつ、「優先が独占になる」ことを防ぐ。
予測の消費者が表示だけでないという事実(計画軌道の重力源、衝突判定の相手)が、配分方針に
反映される。

### 4-4. 予測1ステップごとの重力源再構築

**現状** — `Predictor.advanceBudget` は、予測の1ステップごとに `predictedAttractorsAt` で重力源
配列を作り直し、`classifyAttractors` で空間グリッドを構築し直す。`Simulator.substep` が
「サブステップごとに1回組んで、そのサブステップの全エンティティで使い回す」形を取っているのと
対照的である。

**修正** — 一定ステップ数ごと、あるいは時刻をバケット化した単位で重力源構造を組み直す形に改め、
`Simulator` と同じ「1回組んで使い回す」規約に揃える。予測は本質的に近似であり、数ステップぶんの
重力源位置の遅れは、RK4 のステップ幅そのものが持つ誤差より小さい。

**何が良くなるか** — 予算を増やしたときに費用が線形以上に増える構造を解消する。フェーズ4-3で
ラウンドロビンに回す予算を確保しても、1ステップあたりの費用が高いままでは効果が出ない。

## フェーズ5: マップ UI の再構成

このフェーズは操作体系の変更を含むため、フェーズ1から4までを終えて挙動が安定してから着手する。

### 5-1. 座標系パネルが支配する対象を明示する

**現状** — `src/game/frame-controls.ts` の `FrameControls` が構成する「座標系」パネルは、
`AnchorZone`(原点)と `RotationZone`(回転)の2行を縦に並べている。しかし**原点の行は計画軌道の
折れ線が焼かれる座標系(`PlanDisplay.planFrame`)を書き換え、回転の行はマップカメラの座標系
(`OverviewCamera.cameraFrame`)を書き換える**。見た目は同じパネルの隣り合う2行なのに、支配する
対象が別物である。

さらに、`planFrame` の `rotatingWith`(計画軌道を描く座標系の回転)を設定する UI がコード中に
存在しない。`FrameControls` はこの値を読み出して持ち回すだけである。したがって「カメラの座標系」
「カメラの回転」「計画軌道の座標系」「計画軌道の回転」という4つの独立な選択のうち、**1つが
UI から到達できない**。カメラを地球-月回転系にしても、計画軌道は慣性系のまま描かれる。

**修正** — パネルを「カメラ(視点)」と「軌道計画(描画基準)」の2セクションに分け、各セクションの
中に「中心」と「回転」を並べる。欠落している計画軌道側の回転セレクタを追加する。あわせて、
現在の選択内容を1行のサマリ(例:`地球中心・地球-月回転系`)として常時表示する。

**何が良くなるか** — 「何の座標系を変えているのか」がパネルの構造そのものから読めるようになる。
現状の2行構成は、たまたま片方がカメラ、片方が計画軌道を指しているという実装上の事情を、
UI のレイアウトとして固定してしまっている。セクション分割は、UI の構造をデータの構造に一致させる。

### 5-2. 用語を物理用語の直訳から操作の語彙へ

**現状** — 「原点」「回転」という物理用語の直訳がラベルになっている。`RotationZone` の非選択状態を
表す語は「解除」で、`AnchorZone` には解除の選択肢が無い(`releaseLabel` が `null`)ため、
2行で「解除」の有無が非対称になっている。

**修正** — 「基準にする天体」「視点を一緒に回す」のような、操作の結果を述べる語彙に置き換える。
非選択状態は「解除」ではなく「固定なし(慣性系)」のように実体を述べる。選択肢のラベルは
セグメントコントロールに収まる短縮形(「地-月」など)にし、正式名称はツールチップに置く。

**何が良くなるか** — 「原点」「回転」は、それが何に対する原点・回転なのかを補わなければ意味が
決まらない語である。操作の結果を述べる語彙は、その補いを不要にする。

### 5-3. フォーカス移動の副作用を明示トグルにする

**現状** — `FrameControls.setFocus` は、フォーカス先が登録天体である場合に、計画軌道の座標系の
中心も同じ天体へ移す。マップ上のダブルクリックや一覧の行クリックといった「見る場所を変えるだけ」の
操作で、計画軌道の描画基準が変わり、線の形が変わる。元に戻す手段は用意されていない。

**修正** — 「計画軌道の中心をフォーカスに追随させる」を明示的なトグルにする。既定値は追随ありで
よいが、追随したことがユーザーに見える(サマリ行が変わる)ようにする。

**何が良くなるか** — 表示を変える操作と、描画基準を変える操作が分離される。現状は前者が後者を
巻き込むため、ユーザーは「なぜ線の形が変わったのか」を推測できない。

### 5-4. 操作艦の切替を単クリックから外す

**現状** — `src/game/map-picker.ts` の `handleLeftClick` は、マップ上の自艦を単クリックすると
`Game.setActivePlayer` を呼び、操作対象を切り替える。取り消し手段は無い。

**修正** — 操作艦の切替は、プロパティウィンドウの項目、またはダブルクリックに限定する。単クリックは
選択(プロパティ表示)までに留める。

**何が良くなるか** — 一般的なアプリケーションにおいて、単クリックは選択、ダブルクリックまたは
明示的なコマンドが実行という区別が確立している。取り消せない操作を単クリックに割り当てるのは
この慣習に反しており、マップ上でカメラを操作している最中の誤爆を招く。

### 5-5. 記号体系の整理

**現状** — マーカーの記号が用途を越えて重複している。`▲` は自艦、基地、弾薬、法線方向
(NORMAL)、昇交点、バーン方位、黄道極、および PREDICT バーの折りたたみボタンの8用途で使われて
いる。`▽` は降交点、反法線、赤道降交点で重複する。`◇` は近地点/遠地点アイコンと照準方位で重複する。
`●` は天体アイコン、表示パネルのアイコントグル、タッチ操作の「前進」で重複する。

折りたたみの記号は3系統あり、しかも意味が一致していない。軌道オブジェクト一覧は `▸`(閉)/
`▾`(開)、プロパティウィンドウは `▲` / `▼`、PREDICT バーは**展開中が `▼`** で他と逆、
HUD ドックは `◀` / `▶` である。同一画面内に「▼ = 開く」と「▼ = 閉じる」が同居している。

**修正** — 記号を「意味の軸」で族に分ける。実体(艦・基地・天体・弾薬)は塗り、方向(prograde・
normal・radial・照準・バーン方位)は矢、軌道上の点(近地点・遠地点・昇降交点)は中空、という
3族に割り当て直す。UI の折りたたみ記号は `▸`(閉)/ `▾`(開)に統一し、マップのマーカーとは
字形の族を分ける。

**何が良くなるか** — 記号が3D空間内の実体を指すのか、方向を指すのか、軌道上の特異点を指すのかは、
ユーザーが最初に判断すべき区別である。字形の族をこの区別に対応させれば、個々の記号を覚える前に
「何の話をしているか」が読める。折りたたみ記号の統一は、同一画面内で同じ字が逆の意味を持つという、
学習を能動的に妨げる状態を解消する。

### 5-6. PREDICT バーの情報設計

**現状** — `src/game/display-time-panel.ts` の `DisplayTimePanel` には、同じ見た目の
`DurationValueInput`(数値欄+単位セグメント)が2つ並ぶ。一方は表示期間の手動指定、他方は
時刻ジャンプだが、どちらの見出しも「単位」であり、行の意味を示すラベルが無い。要素の並びは
期間 → 手動 → ジャンプ → スライダー → 「現在に戻す」ボタン → 目盛り → ラベルとなっており、
スライダーの目盛りがボタンを挟んで離れている。

入力は `input` イベントごとに反映されるため、「12時間」と打つ途中の「1」で一度ジャンプが走る。
単位を「時」から「年」に変更すると数値がそのまま流用され、8760倍のジャンプが黙って起きる。
下限クランプが入力中に値を書き戻すため、欄を空にして打ち直すことができない。

**修正** — 各行の左に「表示期間」「T+ へ移動」の見出しを付ける。目盛りはスライダーの直下に移す。
確定を `change` イベントおよび Enter に変え、`input` ごとの反映をやめる。単位変更時は秒数を保った
まま表示値を換算する。クランプは確定時にのみ行う。パネル名「PREDICT」は、他パネル(「座標系」
「表示」「軌道オブジェクト」)に合わせて日本語にする。

**何が良くなるか** — 数値と単位の組を入力するという同じ操作が、2つの異なる意味を持つのに区別が
付かない状態を解消する。確定タイミングの変更は、入力途中の状態が副作用を持つという、テキスト
入力として異例の挙動をなくす。

### 5-7. パネルの折りたたみ状態を保持する

**現状** — `src/game/view-manager.ts` の `ViewManager.applyChrome` は、マップビューから離れるたびに
`resetHudDocks` を呼び、左右のドックと PREDICT バーの折りたたみ状態を強制的に展開へ戻す。
軌道オブジェクト一覧は個別の折りたたみを持たず、マップビューの間は常時表示される(最大高
544ピクセル)。

**修正** — `resetHudDocks` の無条件呼び出しをやめ、折りたたみ状態を保持する。軌道オブジェクト
一覧にも個別の折りたたみトグルを付ける。

**何が良くなるか** — 「畳んでおく」はユーザーが意図的に行った設定であり、ビューの往復で破棄して
よいものではない。現状は、マップに戻るたびに畳み直す作業を強いている。

### 5-8. 用語の統一

**現状** — 同じ対象が「宇宙船」(MAP VIEW パネル)、「自艦」(オブジェクトグループ、軌道オブジェクト
一覧)、「自機」(マップのヒント文)と3通りに呼ばれている。軌道オブジェクト一覧のフィルタ行には、
天体クラス4つと並んで「船」があるが、実際に絞り込まれるのはフォーカス系内の非天体すべて
(弾薬・基地を含む)であり、ラベルが内容と一致しない。

**修正** — 自機を指す語を「自艦」に統一する。一覧のフィルタ「船」は、実際の絞り込み内容に合わせて
改名する(内容を変えるなら「船」の定義を艦のみに限定する)。

**何が良くなるか** — 同一対象の呼称が揺れると、ユーザーは別々の概念だと解釈する。ラベルと
内容の不一致は、フィルタの結果を予測できなくする。

## 5+. 個別の小規模修正(フェーズに属さない)

以下はいずれも独立して適用でき、他の修正と衝突しない。

- **`src/game/map-picker.ts` の `handleDoubleClick`** — `pickable !== false` によるフィルタが常に真で
  ある。`pickable` を立てるのは `FocusMarkers.allLabels` 側だが、ダブルクリックの候補列は
  `FocusMarkers.allBodyPickables` が別途生成しており `pickable` を持たない。結果として
  「ラベル衝突で隠れた天体は、手前のラベルの背後から拾わない」という設計意図が機能していない。
  候補生成側に `pickable` を伝播させる。
- **`src/game/map-picker.ts` の `refresh`** — 候補全件のループ内で `Ephemeris.attractorsAt(simTime)` を
  毎要素呼び直している(同じ値をループ外で既に取得済み)。ループ外の値を使う。同ループ内の
  速度計算は、天体や弾薬に対しては常に0を返す無駄な計算になっている。
- **`src/game/map-picker.ts` の `priority`** — 「一覧の距離ソート鍵」と「近傍フィルタの距離」を
  1フィールドで兼ねているが、自艦だけ距離ではなく定数(-100 / 0)が入る。このため自艦セクションの
  距離ソートが機能せず、近傍フィルタが自艦をどれだけ遠くても除外しない。ソート順と距離を
  別フィールドに分ける。
- **`src/game/camera/focus-markers.ts`** — 同一ラベルに対して `isOccluded` を2回計算している。
  1回に減らす。ラベル衝突判定が毎フレーム O(n²) である点は、登録天体が101体ある現状では
  無視できない。
- **`src/game/hud/context-menu.ts`** — 項目ラベルとサブラベルを `innerHTML` への文字列連結で
  組み立てている。現在の呼び出しは空域メニューのみだが、`MenuItem` にはユーザーが改名できる
  名前(`Player.displayName` / `Base.name`)が流れる経路が同じ `MapPicker.itemsFor` 上に存在する。
  `textContent` による組み立てに変える。
- **`src/game/display-time-panel.ts` の `setSliderSteps`** — つまみ位置の比を保つが
  `onSliderChange` を発火しないため、表示期間を切り替えた直後は表示時刻とつまみ位置が丸め誤差ぶん
  ずれたままになる。
- **`src/game/plan/plan-executor.ts` の `thrustGateOpen`** — `update` でのみ更新されるフィールドだが、
  `applyIgnitionAndCutoff` と `nextEventTime` はサブステップ境界で読む。呼び出し順への暗黙依存が
  あるため、`simSpeed` を引数として渡す形に変えてフィールドを廃止する。
- **`src/game/plan/plan-executor.ts` の加速度計算** — `ship.mass > 0 ? ship.totalThrust / ship.mass : 0`
  が4箇所に重複している。`plan-executor-math.ts` に `maxAccelOf(thrust, mass)` として切り出す。
- **`src/game/plan/plan-executor.ts` の `finish`** — `Plan.dropNodesBefore` の戻り値を見ずに
  アンカーを上書きする。何も落ちなかった場合にもアンカーだけが変わる。フェーズ4-1の
  `consumeNodesUpTo` 化で同時に解消する。
- **`src/game/plan/plan-executor.ts` の時間加速ゲート** — 時間加速ゲートが閉じている間、実行状態は
  `burn` のまま保持され、点火時に凍結した噴射方向(`burnDirWorld`)も保持される。高い時間加速で
  長時間経過した後にゲートが開くと、既に軌道上の別位置・別速度にいるのに古い方向へ噴射を再開する。
  ゲートが閉じた時点で `burn` を中断し、`armed` 以前へ戻す。
- **`src/game/plan/plan-editor.ts` の Δv 基底の不一致** — 増分 Δv は**噴射後**状態の軌道基底で
  組まれるのに、パネルの数値表示と3Dギズモの矢印方向は**到着(噴射前)**状態の基底で組まれている。
  Δv が大きいほど両者がずれ、「PRO の矢印方向にドラッグしたのに PRO 成分の数値が期待どおりに
  増えず、他の成分も動く」という挙動になる。基底を到着状態に統一する。
- **`src/game/plan/plan-editor.ts` の `nodeDv`** — ノードと到着状態がそれぞれ独立に
  `strongestAttractor` を引くため、影響圏の境界付近では異なる中心天体に対する相対速度の差を
  取りうる。一方 `rebuildDraggedNode` は素の ECI 差を使う。Δv は ECI 差で定義し、表示のときだけ
  基底へ射影する形に統一する。
- **`src/game/plan/plan-editor.ts` の `rebuildDraggedNode`** — ノードより後ろの区間のサンプルを
  掴んだ場合、自ノード1つぶんの Δv しか差し引いていない。`Plan.nodeTimeRange` の上限は前状態から
  表示期間ぶん伸びるため、2つ以上先の区間のサンプルが範囲に入りうる。その場合は中間ノードの Δv が
  残ったまま噴射前速度として使われ、ドラッグ後の軌道が跳ぶ。候補を1区間先までに限定するか、
  間にあるすべてのノードの Δv を差し引く。
- **`src/game/plan/plan.ts` の `addNode`** — `postState.t` がアンカー時刻以前である場合を弾いていない。
  アンカーより前のノードが生成されると、`nodeTimeRange(0)` の下限がアンカー時刻であることと矛盾する。
- **`src/game/plan/plan-path.ts` の `nearestSample`** — 全区間の全サンプルに対して遮蔽判定と投影を
  行い、そのそれぞれが座標系変換を2回ずつ引く。座標系変換をループ外で1回求めて共有する。
  タイブレークが浮動小数の等値比較に依存している点も、明示的な許容誤差に改める。
- **`src/render/orbit-line.ts` の `applyFade`** — `excludeNearBody` が指定されている限り、天体が
  軌道の反対側にいて全頂点が不透明であっても、毎フレーム2048頂点のループと GPU 転送が走る。
  前回の値との差が閾値未満なら省略する。
- **`src/render/orbit-line.ts` の可視判定** — `line.visible` を決める式が3箇所にあり、うち1箇所だけ
  条件が異なる(`snap !== null` の有無)。現状は他の条件に救われて事故になっていないが、
  `SampledLine.applyVisible` と同じ形の private メソッドに一本化する。
- **`src/render/orbit-line.ts` の原点ジッター** — 原点が (0,0,0) のときに座標へランダムな微小値を
  加える処理は、WebGPU の頂点バッファ更新に関する回避策であり、フェードや再生成の判断ロジックと
  同じ関数に同居している。専用の private メソッドへ隔離し、対象となる three.js のバージョンを
  コメントに明記する。

## 6. 改名一覧

改名は痕跡を残さない。旧名のエイリアスは残さず、旧名で全文検索して0件になるまで置換する。
下表の改名は、対応する修正フェーズと同じ変更セットの中で行う。

| 現在の名前 | 新しい名前 | 理由 |
|---|---|---|
| `Plan.retimeNode` | `Plan.replaceNode` | 主な用途である `PlanEditor.setNodeDvLocal` は時刻を変えず速度だけ差し替えるため、現在の名前が実体と乖離している |
| `Plan.deleteFollowingNodes` | `Plan.truncateAfter` | `Plan.removeNode` が行う切り詰めと対称な名前にし、境界の含み方の違いを名前で表す |
| `GameEntity.resyncPrediction` | `GameEntity.discardPredictionIfDiverged` | 再同期は行わず、乖離時に破棄するだけである |
| `PlanPath.finalSegmentStart` / `finalSegmentSamples` / `finalPeriapsisPoint` / `finalApoapsisPoint` | `PlanPath.finalSegment()` に統合 | 他の出力はすべてメソッドであるのに、末尾区間だけが public な可変フィールドとして露出しており、更新前の値を外部が読める |
| `OrbitLine` の `perRadius` | `radiiPerRadian` | 実体は「長半径 ÷ 天体半径」であり、現在の名前は単位も意味も逆を示す |
| `SampledLine.lastScale` | `SampledLine.bakedScale` | 「最後に頂点を焼いたときの m/px」であり、早期 return では更新されないという意図が現在の名前から読めない |
| `PlanExecutor.reset` | `PlanExecutor.stopIfActive` | `clearState` との差が「待機中なら何もしない早期 return の有無」であることが名前から読めない |
| `Predictor.complete` | `Predictor.finished` | 打ち切り(`truncated`)を含める判定に変えるため |
| `PlanArc.recomputed` | 削除 | 外部参照が無く、ローカル変数で足りる |
