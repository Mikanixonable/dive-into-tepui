# タイトル画面・表示パネル・起動ガイド(ヘルプ)のユーザビリティ改善計画

スナップショット: `4325b278`(2026-08-25 時点の main)

## 目的

タイトル画面(ステージ選択画面)・表示パネル(`#hud-view-options`)・起動ガイド(`H` キーで開く
ヘルプパネル)を調査した結果、以下の問題が見つかった。

1. 表示パネルは既定で全タブ折りたたみ済みのため、初見のプレイヤーが存在に気づけない。
2. ヘルプパネルを開く手段が `H` キー押下のみで、マウス/タッチ操作者向けの発見可能な導線
   (アイコン等)が画面上のどこにも無い。しかもヘルプの存在自体をヘルプの中でしか説明していない
   自己言及構造になっている。
3. タップ最小寸法(`--hit-target-min`、44px)を守れていないボタンが複数ある
   (`.body-class-icon-btn`・`.help-close-button`)。`UI-DESIGN.md` §6 の規約に反する実装バグ。
4. `z-index` がプロジェクト全体で9ファイルに分散してリテラル値のまま書かれており、
   `overlay-layer.ts` の「z-index を持つのはこのモジュールだけ」という宣言(コメント)と実態が
   食い違っている。値の系統(10刻み/100刻み/1000)も統一されていない。

## 決めたこと

- **z-index の一元管理は二層構造にする**: (a) ページ直下(`body` の子)の要素間の重なりは
  `theme.ts` へ新設するトークン群が持つ、(b) `#hud` の子孲(パネル/ウィンドウ/ポップアップ等)の
  重なりは既存の `overlay-layer.ts` の8層(`marker`〜`system`、z-index 10〜17)が引き続き持つ。
  根拠: `overlay-layer.ts` は既に「#hud 直下の重なり順を決める固定レイヤ」として機能している
  唯一の一元管理箇所であり、これを壊して1つのテーブルに統合すると、レイヤ名で子を分類する
  既存の設計(`buildOverlayLayers`)まで壊すことになる。壊れているのはページ直下の7ファイルが
  各々バラバラにリテラルを書いている方であり、そこだけを直す。ユーザーが「1つのテーブルに
  完全統合したい」を望むなら手順2の設計をやり直す。
- **z-index トークンは、参照元ファイルが元々使っている参照方式(`var(--token)` か直接の
  JS 定数展開 `${TOKEN}` か)を維持する。** `loading-overlay.ts`・`fatal-error.ts`・
  `stage-select.ts`・`touch.ts`・`node-gizmo.ts` は `injectThemeVariables()`
  (`hud-root.ts:365`、`Hud` 構築時にのみ呼ばれる)より前に画面へ出ることがあるため、
  `var(--z-*)` を使うと未定義になる。これらは全て今も色・フォント等を直接 JS 定数の
  テンプレート展開で書いており、その既存パターンに合わせる。
- **表示パネルの既定状態は「開く」に変える。** 折りたたみの選択自体は永続化する既存の
  仕組み(`loadPanelCollapsed`/`savePanelCollapsed`)を変えず、**未操作時のデフォルト値だけ**
  `true`(畳む)から `false`(開く)へ変える。

## 達成目標

- `view-options-panel.ts` の初回表示で、`#hud-view-options` の本文が畳まれていない
  (`localStorage` を消した状態でマップビューを開くと展開されている)。
- マウス/タッチいずれの操作でも、キーボードの `H` を知らずにヘルプパネルを開ける導線が
  画面上に常設されている。
- `.body-class-icon-btn` と `.help-close-button` が、`pointer: coarse` 環境で
  `--hit-target-min`(44px)以上のタップ領域を持つ(`pointer: fine` では詰めた見た目を保つ)。
- `grep -rn "z-index: [0-9]" src/game/hud/style/hud-layout-style.ts src/game/input/touch.ts
  src/game/plan/node-gizmo.ts src/loading-overlay.ts src/fatal-error.ts
  src/game/hud/windows/resource-transfer-dialog.ts` が **0件**になっている(すべてトークン参照
  へ置き換わっている)。**当初の目標には `src/game/stage-select.ts` も含めていたが、実施中に
  同ファイル内の `z-index: 0/1/2`(110・121・188・195行目)は `isolation: isolate` を持つサブ要素
  内で完結する局所スタッキングであり、「決めたこと」で述べた二層構造(ページ直下/`#hud`内部)の
  どちらにも属さないため対象外と判断した(スコープの訂正であり、未対応の見落としではない)。**
- `npm run typecheck` が通る。

## リスクと落とし穴

| リスク | 影響 | 露見する場所 |
| --- | --- | --- |
| `injectThemeVariables()` が呼ばれるより前に描画される画面(ローディング・タイトル・致命的エラー)で誤って `var(--z-*)` を使ってしまう | その要素の `z-index` が `auto` 扱いになり、重なり順が崩れる(特に起動直後のローディング画面や、WebGPU 初期化失敗時の致命的エラー画面) | 手順3の目視確認。特に致命的エラー画面はブラウザの WebGPU を強制的に無効化するなどして意図的に再現しないと通常のプレイでは踏まない経路なので注意する。 |
| `overlay-layer.ts` の10〜17と `theme.ts` の `Z_HUD`(10) が同じ数値に見えるため、将来どちらかを読んだ人が「衝突している」と誤解して片方をずらしてしまう | 実際には別のスタッキング文脈なので衝突していないが、無用な「修正」で意図せず重なり順を変えてしまう恐れ | 手順2で追加するコメント(`theme.ts`)がこの説明を持つので、そこを読まずに変更された場合に発生。将来の変更レビューで気づく。 |
| 手順4(既定展開)により、マップビューを開いた瞬間に表示パネルが常に展開されるため、左レールの縦方向の専有面積が増える | 低い画面高さ(`MQ_SHORT`)や他の左レールパネルと合わせて縦に溢れ、スクロールが必要になる画面が増える | 手順4の目視確認時に、低解像度・スマホ縦持ち相当のビューポートでも確認する。 |
| 手順6で追加する `#hud-help-badge` の固定位置(右上)が、既存の画面固定バッジ(トースト・ヒント等、`UI-DESIGN.md` 365行目)や `#hud-viewbadge` と重なる | 見た目の衝突、タップ領域の奪い合い | 手順6の目視確認。特にコンパクト幅(`MQ_COMPACT`)でHUD要素が密集する画面。 |
| 手順5で `.body-class-icon-btn` に `min-width`/`min-height` を足すと、`grid-template-columns: repeat(4, minmax(24px, 1fr))`(`map-view-style.ts:264`)のグリッド内で44pxを確保しようとして行の折り返しやはみ出しが起きる | マップビューの表示パネルでボタン列が崩れる | 手順5の目視確認、特にタッチエミュレーション+コンパクト幅の組み合わせ。 |
