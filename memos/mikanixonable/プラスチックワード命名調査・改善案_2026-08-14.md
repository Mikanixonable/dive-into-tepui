# プラスチックワード命名調査・改善案

調査日: 2026-08-14
対象: `src/**/*.ts`、`DEVELOP/CODING_STYLE.md`
目的: 変数・クラス・メソッド・ファイルの名前に、修飾なしでは責務を特定できない広い語（いわゆるプラスチックワード）が現れる箇所を見つけ、改名または責務分割の方針を定める。

## 1. 結論

`System`、`Manager`、`Service`、`-er` を語尾だけで禁止するのは適切ではない。既存規約のとおり、次の問いで判定する。

> 名前と所属先を合わせたとき、保持する状態・対象・副作用・ライフサイクルが、実装を読まずに推測できるか。

この基準では、`Panel`、`View`、`Registry`、`Guide`、`Service` の一部は役割名として有効である。一方、複数の責務を抱えるクラスに `Manager` や `System` を付けて責務の広さを隠している例、対象や結果を示さない動詞、単位・座標系・対象を欠く公開名は改善効果が大きい。

優先順位は次のとおり。

- **P0**: 広い利用範囲または基底クラスの契約に波及し、誤読が大きい。最初に改名する。
- **P1**: 公開クラス・公開メソッド・保存データなどの意味を誤読しやすい。責務分割と合わせて改名する。
- **P2**: 改善効果はあるが、機能変更や大規模な参照更新に合わせてよい。
- **除外**: 一般語でも所属先または専門領域から意味が一意で、改名の利益が小さい。

## 3. `System` / `Manager` / `Service` の使い分け案

### `Manager`

一つの概念に属する状態・選択・方針を所有し、その概念の操作をまとめる場合だけ使う。例: `SimSpeedManager` は速度レベルと自動ワープ方針を所有するため、現時点では許容できる。

改善対象は、クラスが複数の対象群、描画、入力、永続化を同時に扱い、名前がその幅を隠しているケースである。まず分割し、分割後に残った状態所有者へ `Manager` を付ける。

### `System`

フレーム処理、または多数の対象にまたがる一機能を構成し、下位オブジェクトを統括する場合だけ使う。`Simulator`、`CameraSystem` はこの意味に近い。

単一のPlayer部品や単一のカメラの切替ファサードには、より具体的な状態名・部品名を優先する。`ThermalSystem`、`PowerSystem`、`RadiatorSystem`、`CombatCameraSystem` は候補である。

### `Service`

画面やフレーム周期の状態を所有せず、保存・読込・変換などの呼び出し単位のユースケースを提供する場合だけ使う。`SnapshotService` はスナップショットの捕捉・読込を提供するので許容範囲にある。

`Sfx` を `AudioService` と呼ぶ案は避ける。実際にはAudioContext、効果音ループ、BGMスケジューラ、音量状態を所有するため、`GameAudio` または `GameAudio` と `BackgroundMusic` へ分ける方が正確である。

### `-er`

`Targeter`、`Predictor`、`Generator`、`Spawner` のような動作主体を示す語は、対象と操作が名前から特定できる場合だけ残す。対象が明白でない場合は対象を補う（例: `TrajectoryPredictor`）。複数責務を抱える `Targeter` は `CombatTargetController` などへ分割する。

## 8. 規約違反だが、プラスチックワードとは別に直すもの

### 8.1 不要な `_` 接頭辞

`DEVELOP/CODING_STYLE.md` は、対応するpublic getter/setterがないprivateフィールドに `_` を付けないとしている。次のような依存フィールドは通常形へ改名する。

- `camera-system.ts` の `_elStatus`、`_elStageStatus`、`_elOrbit` → `elStatus`、`elStageStatus`、`elOrbit`
- `game.ts` の `_scene`、`_hud`、`_sfx` → `scene`、`hud`、`sfx`
- `player.ts` の `_hud`、`_sfx`、`_fx` → `hud`、`sfx`、`effects`
- `player-fire.ts`、`thermal.ts`、`bullet.ts`、`debris-piece.ts`、`rcs-effects.ts`、`thrust-effects.ts`、`plan-guide.ts` 等の未公開依存
- `game-entity.ts` の `_memoState`、`_memoCenterId`、`_memoElements` → `memoState`、`memoCenterId`、`memoElements`

getterの正本である `_visible`、`_isOpen`、`_focus`、`_cameraFrame`、`_trajectory` などは除外する。

### 8.2 `Idx`、略語、単位欠落

- `THROTTLE_DEFAULT_IDX` → `THROTTLE_DEFAULT_INDEX`
- `throttleIdx` → `throttleIndex`
- `muzzleIdx` → `muzzleIndex`
- `currentTrackIdx` → `currentTrackIndex`
- `RAD_AREA` → `HULL_RADIATIVE_AREA`
- `HULL_EMISS` → `HULL_EMISSIVITY`
- `ENV_TEMP` → `RADIATIVE_ENVIRONMENT_TEMP`
- `MAX_DYN_PRESSURE` → `MAX_DYNAMIC_PRESSURE`

これらはプラスチックワードそのものではないが、修飾不足・略語過多によって同じ誤読を起こすため、同じ改名パスで処理する。

## 9. 改名を見送る名前

次は一般語を含むが、現責務と規約に合っている。

- `SnapshotService`: スナップショットの捕捉・読込という呼び出し単位のユースケース。
- `SimSpeedManager`: 速度レベル、自動ワープ、操作可否の方針を所有する。
- `PlanExecutor`: 軌道計画の実行という対象が明確。
- `PlanEditor`: 計画の選択・編集状態を所有する。
- `PlanGuide`: 計画から案内情報を導出する。
- `ObjectPicker`: 候補集合から選択対象を特定するUI部品。
- `ModalController`: モーダルの開閉状態と入力ゲートを制御する。
- `CameraSystem`、`Simulator`: フレーム処理をまたぐ機能を統括するため `System` が役割を表す。
- `Ephemeris`、`Attractor`、`SpatialGrid`、`DynamicTrajectory`、`StateQueue`、`ContactPhysics`: 領域上の専門語であり、一般語の置換は意味を弱める。
- `update`、`sync`、`render`、`clear`、`dispose`: 所属先または `update → sync → render` のフレーム境界で意味が一意。
- `handleInput`、`handleRightClick`、`handleRepairPart`、`handleTargetSelectKey`: 対象イベントが名前に含まれる。
