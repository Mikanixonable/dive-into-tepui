# 第4講：Game の中身を読む――世界・個体・物理・ルールの責務地図

第1講〜第3講では、起動からフレームループ、入力の解釈までを見てきました。
今回は、いよいよゲームの心臓部である `Game`（`src/game/game.ts`）の内部構造へ足を踏み入れます。

```text
Game (1ランの進行モデルの正本)
  │
  ├─ DynamicSystem     自機・敵・弾など「動く個体」の一覧と生成・削除
  ├─ Simulator         多体サブステップ積分、大気抵抗、表面接触
  ├─ CelestialSystem   太陽系天体（地球・月・太陽）の公転・暦・座標系
  ├─ Stage             ミッションの台本（敵の湧き、勝敗条件、スコア）
  ├─ SimSpeedManager   物理時間の進行倍率（ポーズ・等倍・早送り）
  ├─ ControlSelection  操作対象艦の選択
  └─ RunEventLog       1フレームで起きた出来事の記録（撃破・被弾・補給など）
```

今回の目標は、各サブシステムの「責務（役割分担）」と「所有権（誰がマスターデータを持っているか）」を明確に区別できるようになることです。

---

# 1. Game は「巨大な実装」ではなく「モデルのオーケストレーター」

`src/game/game.ts` の `Game` クラス自体には、敵のAI思考アルゴリズムや軌道計算の数式は直接書かれていません。
`Game` の役割は、**「時間を進めるために必要な専門サブシステムを集め、決められた順序で協調動作させること」** です。

1フレームの `game.advance(dt, commands, pilotControls)` の中では、次の順序で処理が進みます。

```ts
public advance(dt: number, commands: CommandQueue, pilotControls: PilotControls): void {
  // 1. 出来事ログをリセットし、命令を適用する (ポーズ中も命令は適用)
  this.eventLog.clear();
  this.applyCommands(commands);

  // 2. 時間倍率を計算する
  const simDt = this.simSpeedManager.stepDelta(dt);
  if (simDt <= 0) return; // ポーズ中は物理とステージを進めない

  // 3. ステージの進行 (湧き・勝敗判定・タイマー更新)
  this.stage.update(simDt, this.eventLog);

  // 4. 動的物体の更新 (敵AIの指令・自機スラスタ・サブステップ物理積分)
  this.dynamicSystem.update(simDt, pilotControls, this.eventLog);
}
```

# 2. 主要サブシステムの役割分担

### 1. DynamicSystem (`src/game/dynamic/dynamic-system.ts`)
- **責務**: 自機、敵艦、弾、ミサイル、デブリといった「動くエンティティ（`DynamicEntity`）」の全コレクションを管理。
- **所有する状態**: エンティティ配列、保留中の新規生成（pending spawn）、ユニークID採番器。
- **物理との接続**: 各エンティティの推力やAI操縦を集約し、後述の `Simulator` へ渡して座標を更新させる。

### 2. Simulator (`src/game/dynamic/simulator.ts`)
- **責務**: 厳密な軌道力学と物理法則に従ったサブステップ数値積分。
- **所有する状態**: 進行時刻 `simTime`（ゲーム内宇宙の絶対時刻）。
- **計算内容**: 重力加速度、大気密度による抗力（ドラッグ）、天体表面との着陸・接触判定。

### 3. CelestialSystem (`src/game/celestial/celestial-system.ts`)
- **責務**: 地球、月、太陽などの天体系階層と暦（エフェメリス）。
- **提供機能**: 指定された時刻における各天体の位置・速度、参照座標系、重力源パラメータ。
- **特徴**: `Simulator` や `Predictor`（軌道予測）に対して「この時刻の天体位置」を純粋計算して提供する。

### 4. Stage (`src/game/stages/stage.ts`)
- **責務**: ステージごとの勝敗ルール、敵の出現ウェーブ、作戦目標の監視。
- **特徴**: 勝敗が決まったら `StageResult` を確定させ、`RunEventLog` に結果を記録する。

### 5. RunEventLog (`src/game/run-event-log.ts`)
- **責務**: 「敵が撃破された」「弾が命中した」「燃料が切れた」といった、そのフレームで1回だけ起きた出来事を記録するリングバッファ。
- **表示への橋渡し**: 表示層（`GamePresentation`）がこれを読み取り、爆発エフェクトの発生、SEの再生、HUD通知メッセージの表示へと変換する。

# 3. 表示系（Camera / HUD）が Game の中にいない理由

かつての初期設計では、`Game` クラスの中にカメラやHUDの管理コードが同居していました。
しかし現在の設計では、これらはすべて **`GamePresentation`（表示層）** へ完全に追い出されています。

なぜなら、**「ゲーム内世界で何が起きたか（物理事実）」** と **「それを画面のどの角度からどう見せるか（カメラ・UI演出）」** は、完全に別の関心事だからです。
この分離があるからこそ、ゲームモデルを一切汚すことなく、戦闘カメラ・マップカメラの切り替えや、軌道予測線の表示、UIの再構築を自由に行うことができます。
