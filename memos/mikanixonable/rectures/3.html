Lecture 3 / Input Phase & Command Flow

第3講：入力解釈と進行
――生イベントから命令・操舵量への変換

ユーザーのキーボードやマウス操作がどのようにゲーム内部へ届くのか。ブラウザの生イベントを直接使わず、入力解釈フェーズで「連続操舵量（PilotControls）」と「不連続命令（CommandQueue）」へ純粋変換する堅牢なデータフローを学ぶ。

1. 入力パイプラインの全体フロー

Dive into Tepui では、入力イベントのリスナーの中で直接キャラクターを動かすことは絶対にしません。イベントは一度 Input バッファに溜められ、フレームの先頭の GamePresentation.interpretInput() で一括して意味づけ（解釈）されます。

2. 連続量（PilotControls）と不連続命令（CommandQueue）

不連続命令: CommandQueue

キーが押された瞬間（立ち上がりエッジ）に1度だけ発生するイベントです。

  • 主砲・ミサイルの発射
  • ターゲットのロックオン切替
  • 時間倍率の変更（ポーズ、等倍、3倍速など）
  • 軌道計画マニューバノードの追加

game.advance() の先頭で消化されます。ポーズ中であっても「ポーズ解除」や「マニューバノードの編集」命令は受け付けられます。

連続操舵量: PilotControls

スティックの傾きやキーの押し込み時間に応じた $[-1, 1]$ や $[0, 1]$ の連続量です。

  • スロットル（主推進推力）
  • ピッチ・ヨー・ロール（RCS姿勢制御）
  • 並進スラスター（上下左右の平行移動）

DynamicSystem 内の自機実体へ渡され、スラスタ燃料の消費と運動方程式（$\vec{F} = m\vec{a}$）のサブステップ数値積分に直接使用されます。

3. ゲームが使わなかったキーの「外部ポート返却」

なぜゲームモデルにセーブや再起動のキー処理を書かないのか？
もし Game クラスの中で「F5 が押されたらセーブする」「R が押されたらステージをリトライする」と書いてしまうと、ゲーム進行モデルが LocalStorage や 画面遷移の仕組み（Launcher）に依存してしまい、コードが結合してテストもできなくなります。
Dive into Tepui では、「ゲームが使わなかったキーを戻り値として外へ返し、main.ts の外部ポートが処理する」 というクリーンな責務分離を徹底しています。
