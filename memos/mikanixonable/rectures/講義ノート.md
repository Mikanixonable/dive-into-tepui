# 講義ノート：Dive into Tepui コード読解シリーズ

このファイルは、ユーザー向け講義そのものではなく、今後の講義を組み立てるための参照用ノートである。
講義では必要な内容だけを初心者向けに言い換える。コードベースが変わった場合は、このノートも更新する。

## 学習者の前提と目的

ユーザーはコーディング初心者である。バイブコーディングでこのゲームを作ってきたが、コードを読めるようにもなりたい。

- JavaScriptでWebサイトを約3年作っている。
- Pythonは少しだけわかる。
- 変数、関数、型、その他の簡単な概念、ポインタくらいはわかる。
- モデル、継承、コンポーネントなどは定義はわかるが、体で覚えている感じではない。
- 複数ファイルからなる巨大なコードベースになると読む気が失せる。
- このコードベースを、大から小へ、エントリーポイントからユーザーとの接点まで読んで理解したい。
- 特に、ゲームのエントリーポイント、毎フレーム行われる操作、各UIの状態遷移、ゲーム内部状態の全貌を理解したい。
- 最初の講義では全体のガイダンス、前提知識、エントリーポイントを扱う。

説明方針:

1. いきなり全ファイルを読ませず、呼び出しの幹を先に示す。
2. 「誰が誰を作るか」「誰が誰を呼ぶか」「どの状態を誰が所有するか」を毎回明示する。
3. 定義はわかっている概念でも、具体的なコードの中でどう働くかを繰り返し説明する。
4. ユーザーが知っているJavaScriptのDOMイベント・コールバック・オブジェクト参照から、ゲームループ・状態機械・コンポジションへ橋を架ける。
5. 物理やThree.jsの細部は、上位の呼び出し関係を理解してから読む。
6. 講義の最後に、次回どこへ進むかと、少量のコード読解課題を置く。
7. 文章を長くしすぎない。巨大なコードベースを読む気力を保つため、一回の講義の焦点を限定する。

## 現在のmain.tsの責務

src/main.ts はゲームルールの実装場所ではなく、次を担当する。

- フォントCSSのimport
- 起動時のステージクラス決定
- セーブスロット・スナップショット・旧形式移行の準備
- Canvas / WebGPU Sceneの初期化
- HUD / Sfx / SettingsPanelの生成と所有
- 外部天体暦の読み込み
- Game の生成
- 起動時のスナップショット選択とロードデータの受け渡し
- SaveBrowser と SnapshotControls の遅延接続
- PerfMeter と FrameSections の準備
- requestAnimationFrame ループ
- 起動時とフレーム実行中の致命的エラー表示

重要な現在形:

- 以前の LaunchSelection / resolveLaunchSelection / launch.mode 中心の構造ではない。
- 現在は StageClass を resolveLaunchStage() が返す。
- ?title=1 でステージ選択画面を強制する。
- ?stage=... が有効ならそのステージクラスを使う。
- URL指定がなく、title指定もない場合は、アクティブスロットの直近ステージを再開可能か調べる。
- 再開できなければ selectStage() でステージ選択画面を表示する。
- CreativeStage は STAGE_CLASSES に含まれるステージクラスである。昔の「モード選択」説明をそのまま使わない。
- スナップショットのロードは、同じGameへ直接復元するのではなく、sessionStorage にロード要求を書き、ページを再読み込みして initialSave としてGameへ渡す方式になっている。
- SaveBrowser はGameを必要とするためGameの後に作り、コールバックを通してページ再読込などをmain.ts側へ返す。
- PerfMeter は計測境界がrAFループにあるためmain.tsが所有し、Gameには後から setPerfMeter() で渡す。
- SnapshotControls は Game.update() の後に、Gameが消費しなかった入力エッジを扱う。F5/F9などのスナップショット操作の専任である。

### ステージ決定の優先順位

resolveLaunchStage() は次の順で決める。

~~~text
?title=1 が付いている
  → 自動再開をせず、selectStage()で選択画面

?title=1 ではなく、?stage=... が有効
  → そのStageClass

URL指定なしで、アクティブスロットのlastStageIdが
存在し、hiddenFromSelectではなく、解放済み
  → そのStageClassを再開

それ以外
  → selectStage()でユーザーの選択を待つ
~~~

ここでは「ゲームモードを選ぶ」というより、「起動するStageClassを選ぶ」と説明する。

StageClass はクラスの静的側の設定で、id、天体暦設定、初期自機数、ステータス表示、選択画面ラベル、解放条件、コンストラクタを持つ。
Stage のインスタンスはGame生成中に new stageClass(...) で作られる。

## 現在のGameの責務と所有関係

src/game/game.ts はオーケストレーターである。
ゲームの細部をすべて実装するのではなく、システムを生成・保持し、毎フレームの呼び出し順を決める。

Gameの重要な状態:

- input: Input
- entities: DynamicSystem
- activePlayers: ActivePlayerController
- player getter: activePlayers.current を返す
- activeStage: Stage
- simulator: Simulator
- simSpeedManager: SimSpeedManager
- cameraSystem: CameraSystem
- viewManager: ViewManager
- displayWindowManager: DisplayWindowManager
- editor: PlanEditor
- targeter、navTarget
- environment、navball
- docking
- isPaused
- floatingOrigin
- sections: FrameSections
- perfMeter（後から注入される）

現在はGame自身がPlayerを直接newする説明は不正確。
Gameのコンストラクタでは、StageClassとinitialSaveを使ってDynamicSystemを作る。

~~~text
initialSaveあり
  → DynamicSystem({ saved: initialSave })
  → 保存されていたPlayer群などを復元

initialSaveなし
  → DynamicSystem({ playerCount: stageClass.initialPlayerCount })
  → 新規Player群を作る
~~~

その後、entities.initialActivePlayer を取得して、CameraSystem、PlanEditor、ActivePlayerControllerなどへ渡す。

依存関係の要点:

~~~text
DynamicSystem
  ↓ initialActivePlayer
CameraSystem / PlanEditor / ActivePlayerController
  ↓
ViewManager / MapPicker / Docking
~~~

ActivePlayerController は操作対象艦の正本である。

- 複数Playerのうち、現在操作するPlayerを持つ。
- Game.player はそのcurrentを読むgetter。
- 操作対象を切り替えると、カメラ、PlanEditor、Targeterなども切り替わる。
- 操作対象の喪失時は、生存している別艦へ引き継ぐか、nullへ戻す。
- DynamicSystem は全Playerを保持する。操作対象と存在する艦の一覧は別概念。

この区別を必ず講義で強調する。

~~~text
DynamicSystem.players = 世界に存在する自機群
ActivePlayerController.current = そのうち現在操作する一隻
Game.player = currentへの読み取り口
~~~

## 学習者が追加でつまずいている点：main.tsとgame.tsの使い分け

ユーザーは、`main.ts` と `src/game/game.ts` の使い分け、および `Game` から分岐した処理がどこへ進むかをまだ一枚の図として把握できていない。以後の講義では、メソッド単体だけでなく、必ず「この処理はmainの外側か、Gameの内側か」「Gameからどの担当へ分岐するか」を示す。

### main.ts

`main.ts` はアプリケーションの外側にある組み立て役・ライフサイクル役である。

- WebGPU、Scene、HUD、Sfx、セーブ、StageClassなど、ゲームセッションより長く生きることがある部品を作る。
- 依存関係がそろったところで `new Game(...)` を呼び、部品をGameへ渡す。
- `PauseMenu` の開閉と `game.pause()` / `game.resume()` のような、部品同士をつなぐコールバックを配線する。
- `requestAnimationFrame` を所有し、`game.update(dt)`、Game後の補助処理、`game.sync()`、`game.render()`を呼ぶ。
- `Game.update()`が消費しなかった入力エッジを、SnapshotControls、Launcher、PerfMeterなどへ渡す。

main.tsは「ゲームのルールを計算する場所」ではなく、「誰を作り、誰を呼び、いつセッションを開始・更新するかを決める場所」と説明する。

### game.ts

`src/game/game.ts` の `Game` は、ひとつのゲームセッション内部のオーケストレーターである。

- DynamicSystem、ActivePlayerController、Stage、Simulator、CameraSystem、ViewManager、PlanEditorなどを保持する。
- `update()`の中で、入力、プレイヤー行動、Stage、物理積分、予測、エフェクト、カメラ、ポインタ処理の順序を決める。
- すべての細部を自分で計算するのではなく、各担当のメソッドを呼ぶ。
- `handleInput()`はprivateで、Game.update()から呼ばれる入力の配分役である。実際の自機の推力・姿勢・射撃は、後段の`Player.behave()`やその内部担当が行う。
- `sync()`は内部状態をHUD、マーカー、Three.jsの表示オブジェクトへ反映し、`render()`は現在のカメラで描画する。

### Gameから分岐した処理の読む順番

  │    ├─ Stage.update()
  │    ├─ Simulator.advance()
  │    ├─ Predictor.update()
  │    └─ EffectsSystem.update()
  │

「Gameから分岐した」ときは、まず分岐先の責務だけを見る。例えばWを読んだときは、いきなり物理へ飛ばず、`Game.handleInput()`で消費されるかを確認し、残れば`DynamicSystem.updatePlayers()` → `Player.behave()` → `PlayerThrottle`へ進む。

### TypeScriptの理解状況

ユーザーはpublic、private、getter、依存性注入は学習済み。`readonly`は今後、実コードで重点的に説明する。

- `readonly input: Input` は「`input`という参照先を別のInputへ差し替えない」という意味で、`this.input.update()`のように参照先オブジェクトを操作することは禁止しない。
- `private readonly stack: OverlayEntry[] = []` は、`stack`変数を別の配列へ差し替えないが、`push()`や`splice()`で配列の中身を変更することは許す。配列の中身まで読み取り専用にする`readonly OverlayEntry[]`とは異なる。
- `constructor(private readonly _hud: Hud)` は、フィールド宣言・private指定・readonly指定・コンストラクタでの代入を一行に省略した構文。
- `readonly`は主にTypeScriptのコンパイル時の契約として説明し、参照の固定とオブジェクトの不変性を混同させない。

### 現在の作業ツリーについての注意

現時点では`git status`上、`src/game/game.ts`などに未解決マージ状態(`UU`)があり、`<<<<<<<` / `=======` / `>>>>>>>`の競合マーカーも確認できる。したがって、Gameからポインタ入力へ進む枝などには二つの実装案が同時に残っている可能性がある。講義では、まず競合の影響を受けにくい`Input.update()`、`Game.handleInput()`、`Player.behave()`の共通する呼び出し幹を読み、競合枝の整理は別課題として扱う。

## 現在のUI・ビュー状態

### ViewManager

ViewManagerが3Dビューとドックの状態を持つ。

~~~ts
type ViewId = 'combat' | 'map' | 'dock';
~~~

現在の実装は、次の2軸を内部に持つ。

- worldView: combat または map
- isDockOpen: boolean

current getterは次を返す。

~~~text
isDockOpenならdock
それ以外はworldView
~~~

つまり、ドックはcombat/mapを消すのではなく、その上に重なるUIである。
ドックを閉じると、背後のworldViewへ戻る。

setView()が遷移の唯一の入口。

- 同じビューならapplyChrome()だけ再実行する。
- dockへ入る前に現在のworldViewを保持する。
- mapから出るとPlanEditorの後始末とMapPickerのcloseを行う。
- mapへ入ると選択ノードを解除する。
- applyChrome()でHUDのclass、navball配置、TouchControls、CameraSystemのmap mode、PlanEditorのmap mode、DisplayWindowのforceCurrentを揃える。
- combatへ入れる条件は ActivePlayerController.current !== null。
- dockへ入れる条件はDockingが判断する。

MはViewManager.handleInputが処理する。

- dock中は処理しない。
- map中はcombatへ戻す。ただし操作対象艦がいなければヒントだけ出す。
- combat中はmapへ移る。
- ビュー切替後にヒントを出す。

### ModalController

HUDモーダルはSetで状態を管理する。

~~~ts
type HudModalId = 'help' | 'settings' | 'save-browser';
~~~

DOMのdisplayだけを見て開閉状態を推測しない。
開閉側が setOpen() を呼び、ModalControllerが入力ゲートとbody classを同期する。

- help: Hud.handleInputがHの押下エッジを処理する。
- settings: SettingsPanelが開閉し、main.tsのコールバックがGame.pause/resumeを呼ぶ。
- save-browser: SaveBrowserが開閉し、自身でGame.pause/resumeを呼ぶ。
- settingsは allowBackgroundInput=true で、設定画面を開いても背景のカメラ操作などを許す設計。
- save-browserは通常の入力ゲートとして背景を遮る。

### Stageのゲームフェーズ

Stageは次のフェーズを持つ。

~~~ts
type GamePhase = 'playing' | 'won' | 'lost' | 'timeup';
~~~

isPlaying getterはphaseがplayingかを返す。

- Stageのコンストラクタは保存されたStageSaveDataがあればscore、phase、logisticsなどを復元する。
- 新規開始なら具象Stageが末尾で begin() を呼び、初期配置、初期弾薬、ブリーフィングを行う。
- 決着後のrestartは ?stage=id でページを再読み込みする。
- recordEnemyDeath()やrecordPlayerLost()がphaseを変更し、結果画面を表示する。
- StageClassの静的設定とStageインスタンスの実行時状態を区別する。

### SaveBrowser / SnapshotControls

保存関連は、通常のゲームルールから切り離して読む。

- SaveBrowserはスロット一覧とスナップショット履歴のDOM UIを持つ。
- 開くとGame.pause()、閉じるとGame.resume()。
- スナップショットのロードは onLoadSnapshot でsessionStorageにIDを置き、location.assignでページを作り直す。
- SnapshotControlsはmain.tsのフレームループでGame.update後に呼ばれる。
- GameがEsc/F5/F9などを消費した後の残りを扱うため、入力の優先順位を説明する際に重要。

## 入力の現在形

src/game/input/input.ts がブラウザイベントを集約する。

イベント発生時:

- keydownでpendingPressesへ押下エッジを入れ、keysに押下中コードを追加。
- keyup、blur、pagehide、visibilitychangeで押下状態を解除する。
- pointerdown/pointermove/pointerupで左ドラッグ、右クリック、中央パン、タッチピンチを集約。
- 左短押しはクリック候補、右短押しは右クリック候補になる。
- wheelは量を蓄積する。
- 初回ジェスチャでonFirstGestureを呼び、AudioContext/Sfxをunlockする。
- TouchControlsはsetVirtualKey()でキーボードと同じpending/key状態へ入る。

毎フレーム先頭のInput.update():

~~~text
pendingPresses / pendingClicks / pendingMouse
  ↓
framePresses / frameClicks / frameMouseへスナップショット
  ↓
pending側を空にする
~~~

消費:

- down(key): 現在押下中か。WASDQEやカメラキーなど、押している間の操作。
- takeKey(key): 今フレームの押下エッジを1件消費。
- takeKeys(handler): 未消費キーを順に渡し、handlerがtrueなら消費。
- takeClicks / takeDoubleClicks / takeMiddleClicks / takeRightClicks: 同じくイベントを消費。
- Inputのキューは、呼ぶ順番が入力の優先順位になる。

ユーザー操作の説明は、次のように段階を分ける。

~~~text
DOM / windowイベント
  ↓
Inputのpendingキュー
  ↓ Input.update()
今フレームのスナップショット
  ↓ takeKey / down / takeClicks
Gameまたは担当システム
  ↓
Player / Stage / View / Editorの状態
~~~
