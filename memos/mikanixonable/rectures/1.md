# 第1講：このゲームを読むための地図――最新アーキテクチャ版

このゲームは、低軌道を舞台にした3D宇宙軌道シューティングゲームです。
ただし、最初から軌道力学やThree.js (WebGPU/TSL) の詳細を暗記する必要はありません。

まずは、ゲームがどのように起動し、誰が全体を動かし、毎フレームどんな順で処理するのかという「呼び出しの幹」を掴みます。

```text
ブラウザ (public/index.html)
  ↓
src/main.ts (ページ寿命の装置生成)
  ↓
PageDevices (シーン・HUD・音声・セーブ・設定)
  ↓
Launcher (周回遷移・ステージ選択・セーブ復元)
  ↓
Run (1ランのライフサイクル)
  ↓
requestAnimationFrame (毎フレーム: run.frame)
  ├─ 1. 入力の解釈 (GamePresentation.interpretInput)
  ├─ 2. モデル進行 (game.advance)
  ├─ 3. 表示の導出 (GamePresentation: カメラ・予測・HUD宣言)
  └─ 4. 装置同期・描画 (PageDevices.sync & GameScene.render)
```

今回の目標は、全ファイルを読むことではありません。

1. **このゲームの大きな部品（主要アクター）は何か**
2. **起動時に何が作られ、どこへ渡されるか**
3. **毎フレーム、内部状態（モデル）と画面表示（プレゼンテーション）がどう更新されるか**

この3つを理解します。

# 1. 巨大なコードベースは「ファイル一覧」ではなく「呼び出しの幹」から読む

現在の `src/` 以下には、ゲーム進行、HUD、カメラ、物理、セーブ、マップ、エフェクト、雲描画など、多数のモジュールがあります。

しかし、最初から全部読む必要はありません。まずは次の幹だけを見ます。

```text
main.ts (起動とページ装置)
  ↓
Launcher (周回の選択と復元)
  ↓
Run (1フレームの交通整理役)
  ├── Game (1ランの進行モデル)
  │     ├─ DynamicSystem (艦・敵・弾のエンティティと物理積分)
  │     ├─ CelestialSystem (太陽系天体・暦・座標系)
  │     ├─ Stage (ステージルール・勝敗・湧き)
  │     ├─ SimSpeedManager (倍速・ポーズ)
  │     └─ ControlSelection (操作対象の自機選択)
  │
  └── GamePresentation (入力解釈と表示導出)
        ├─ GameInputPhase (キー・マウスから命令と操作量へ)
        ├─ CameraSystem (戦闘カメラ・マップカメラ)
        ├─ DisplayWindowManager (軌道計画と表示窓)
        └─ ViewManager (combat / map 視点モード)
```

### 主要サブシステムの役割と配置一覧

| 役割 | 現在の主な場所 | 責務の要約 |
|---|---|---|
| **起動とページ装置** | `src/main.ts` | ページで1つの装置群（シーン・HUD・音声・設定・セーブ）を組む |
| **周回・遷移管理** | `src/launcher/launcher.ts` | ステージ選択、ランの生成・破棄、セーブ復元を制御 |
| **フレーム調停役** | `src/run/run.ts` | 入力解釈・進行・導出・描画のフェーズ順序を所有するオーケストレータ |
| **1ランの進行モデル** | `src/game/game.ts` | 時間・天体系・動的物体・ステージルール・操作対象を束ねる正本 |
| **動的物体の管理** | `src/game/dynamic/dynamic-system.ts` | 自機・敵・弾の生成・削除・ID管理と物理積分ループ |
| **天体系と暦** | `src/game/celestial/celestial-system.ts` | 太陽系天体の運動方程式、暦、重力源・大気モデルの提供 |
| **ステージ進行** | `src/game/stages/stage.ts` | ミッション条件、勝敗、敵湧き、スコア、イベント記録 |
| **入力解釈と表示導出** | `src/game/presentation/` | 生入力をコマンドへ変換し、表示窓・カメラ・HUD描画内容を導出 |
| **軌道力学・物理** | `src/physics/` | Three.js や DOM を知らない純粋計算層（ケプラー軌道・重力・数値積分） |
| **描画パイプライン** | `src/render/` | WebGPU/TSL による天体表面、大気散乱、雲レイマーチング、ポストプロセス |

# 2. エントリーポイントと起動の流れ

Webpack / Vite によるバンドルのエントリーポイントは `src/main.ts` です。
ブラウザが `public/index.html` を開くと、スクリプトが読み込まれ、`main.ts` の最下部にある次のコードから実行が始まります。

```ts
main().catch((err) => {
  showFatalError(err);
});
```

`main()` 関数の中で行われるのは「ゲームルールの実行」ではなく、**「ページ全体で共有される装置の組み立て」** です。

1. **設定の読み出し**: `UserSettings` をローカルストレージから読み込み、テーマ変数（CSSカスタムプロパティ）を DOM に適用する。
2. **WebGPU シーンの初期化**: `initScene()` でキャンバスを作り、WebGPU レンダラーと `GameScene` を構築。
3. **HUD・音声・セーブの配線**: `HudShell`, `MarkerDevice`, `PauseMenu`, `AudioEngine`, `SnapshotService`, `SaveSlots` を準備。
4. **Launcher の生成**: これらすべての装置（`PageDevices`）を束ねて `Launcher` へ渡し、初期ステージまたはセーブデータからの起動を準備。
5. **アニメーションループの開始**: `requestAnimationFrame(animate)` により、毎フレーム `run.frame()` を呼び出すループを開始。

# 3. 毎フレームの処理順序：4つの位相

ゲームが動いている間、毎フレーム（約1/60秒ごと）に何が起きているのでしょうか？
現行コードでは、`src/run/run.ts` の `Run.frame()` がその順序を厳密に管理しています。

```text
1. 入力の解釈 (interpretInput)
   ブラウザのキー押下・マウス移動から、ゲーム側への CommandQueue（命令列）と
   PilotControls（自機の操舵量）を生成する。
     │
     ▼
2. モデル進行 (game.advance)
   命令を適用し、シミュレーション時間 simTime を進める。
   敵AI、自機の推力積分、天体運動、弾の衝突、勝敗判定がここで一気に確定する。
     │
     ▼
3. 表示の導出 (derive)
   確定した最新モデルから、カメラ位置、表示窓（表示時刻・天体中心）、
   軌道予測線、HUDやマーカー、音・通知の要求を純粋に関数的に導出する。
     │
     ▼
4. 装置同期・描画 (sync & render)
   導出された要求に基づき、WebGPU シーンを描画し、DOM HUD や音声を更新する。
```

### なぜ「モデル進行」と「表示導出」を分けるのか？
もし自機の移動計算の途中でカメラやHUDを直接更新してしまうと、
「まだ弾が当たっていないのにHUDのHPバーが減る」「カメラの追随が1フレーム遅れて画面がガタつく」といったバグが多発します。

Dive into Tepui では、**「まず物理世界を確定させ、その結果から画面と音を導出する」** という単方向データフローを徹底することで、極めて安定したフレーム実行を実現しています。
