# 1. Gameは「巨大な実装」ではなく「オーケストレーター」

[src/game/game.ts](file:///Users/pandeaconica/lab/dive-into-tepui/src/game/game.ts) を開くと、たくさんの import が並んでいます。

~~~ts
import { CameraSystem } from './camera/camera-system';
import { Stage, StageClass } from './stages/stage';
import { DynamicSystem } from './dynamic/dynamic-system';
import { CelestialSystem } from './celestial/celestial-system';
import { ViewManager } from './view/view-manager';
import { ControlSelection } from './control-selection';
// ...
~~~

ここで大事なのは、**「Game 自身がカメラの計算や弾の当たり判定をすべて実装しているわけではない」** という点です。

Game の主な仕事は、各専門システムを生成して保持し、毎フレームそれらを正しい順序で呼び出すことです。音楽のオーケストラで言えば、楽器を演奏する奏者たち（各システム）を取りまとめる「指揮者」にあたります。

`Game` のプロパティを見ると、1回のゲームセッション（ラン）で必要となる主要な部品が一目でわかります。

~~~text
Game
  ├─ input                 キーボード・マウス・タッチ入力
  ├─ dynamicSystem         自機・敵・弾・基地などの動的エンティティ群
  ├─ celestialSystem       太陽・地球・月などの天体と宇宙環境
  ├─ activeStage           進行中のステージ（勝敗や出現スクリプト）
  ├─ controlSelection      現在操作している機体・基地の選択状態
  ├─ cameraSystem          戦闘カメラ・マップカメラ
  ├─ viewManager           戦闘ビューとマップビューの管理
  ├─ displayWindowManager  画面に表示する時刻・期間・座標系の決定
  ├─ planDisplay           軌道計画の予測線やノード表示
  ├─ targeter / navTarget  ロックオン対象や航法ターゲット
  ├─ markerManager         画面上に浮かぶアイコンやラベル（DOM）
  └─ flashEffects          被弾や爆発などの一過性の演出
~~~

## 1.1 `create()` とコンストラクタを分けて読む

`Game` クラスの生成には、少し特徴があります。
外側からは `new Game(...)` を直接呼ぶのではなく、[src/game/game.ts:123](file:///Users/pandeaconica/lab/dive-into-tepui/src/game/game.ts#L123) の `static async create()` という非同期ファクトリ関数を入口にしています。

~~~text
StageClass.createCelestialSystem()
  ↓ 天体暦の計算やテクスチャのロード（非同期）
CelestialSystem.build()
  ↓ 天体のメッシュを Three.js の Scene へ登録
new Game(...)
  ↓ ゲームセッション内の各部品をコンストラクタで配線
game.update(0, viewport)
game.sync(...)
  ↓ 最初の表示状態を1フレーム分組み立てる
pipeline.compile(...)
  ↓ 必要なシェーダを事前にコンパイル
game.render(...)
~~~

なぜ `async create()` になっているかというと、天体の軌道データ（天体暦）の読み込みや、最初の描画に必要な GPU シェーダの事前コンパイルなど、非同期で待機すべき準備処理があるからです。

それらの重い準備が整ったあと、実際のコンストラクタ（[src/game/game.ts:186](file:///Users/pandeaconica/lab/dive-into-tepui/src/game/game.ts#L186)）が呼ばれます。コンストラクタの中では、部品同士の依存関係に従って順番にオブジェクトが組み立てられていきます。

~~~text
DynamicSystem
  ↓ 個体が存在する世界ができる
CameraSystem / NavTarget / ControlSelection
  ↓ 現在の操作対象やターゲットを参照できるようになる
ObjectWindows / Pickables
  ↓ クリック可能な対象や情報窓を作れる
CombatView / MapView
  ↓ 2つの画面モードを作れる
ViewManager
  ↓ ビューの切り替え役が完成する
~~~

例えば、`ViewManager` は `CombatView` と `MapView` の2つを受け取って作られます。このように、コンストラクタのコードを上から順に読むと、「誰が誰を必要としているか（依存関係）」が自然と見えてきます。

## 1.2 1フレームの3段階：update / sync / render

`main.ts` のアニメーションループから、`Game` は毎フレーム次の3つのメソッドが順番に呼ばれます。

~~~text
1. game.update(dt)     内部の時間を進め、物理やルールを更新する
     ↓
2. game.sync(...)       内部の計算結果を画面表示用のメッシュやDOMへ写す
     ↓
3. game.render(...)     Three.js を通じて実際にGPUで画面を描画する
~~~

ここで特に意識しておきたいのが、**「sync は描画そのものではない」** という点です。

- **update**: ゲームの時間を進め、入力を解釈し、位置や速度、弾の当たり判定、勝敗を計算します（画面の描画は一切行いません）。
- **sync**: update で決まった最新の位置・姿勢・カメラの向きに合わせて、3Dモデルの位置を動かしたり、画面上のUIマーカーや軌道線の頂点データを揃えたりします。
- **render**: 揃えられた3Dシーンを Three.js のレンダラーで画面にピクセルとして出力します。

ゲームの処理を「状態の更新」「表示への反映」「GPUへの描画」の3段階にきれいに分けることで、コードの見通しが良くなり、描画の都合でゲームロジックがバグるのを防いでいます。

# 3. 動く世界の中心：`DynamicSystem`

自機、敵、弾、基地、破片など、空間を飛び交うすべての物体を束ねているのが [src/game/dynamic/dynamic-system.ts](file:///Users/pandeaconica/lab/dive-into-tepui/src/game/dynamic/dynamic-system.ts) です。

その主な役割は次の4つです。

1. **個体の保持とライフサイクル管理**（生成・追加・上限チェック・破棄）
2. **毎フレームの指令決定**（推力やAI行動の更新）
3. **物理時間の進行**（`Simulator` に積分を依頼）
4. **描画への同期**（全個体の見た目を更新）

## 3.1 個体の正本は `entities` 配列

`DynamicSystem` の中核には、次の配列があります。

~~~ts
private readonly entities: DynamicEntity[] = [];
~~~

この配列が、今ゲームの世界に実在している全個体の正本です。
「自機専用の配列」「敵専用の配列」を個別に持っているわけではありません。すべての物体を `DynamicEntity` として1つの配列で管理し、必要なときに絞り込んで取り出します。

例えば、プレイヤーが操作可能なオブジェクトの一覧は次のように getter で取得します。

~~~ts
get controllables(): readonly Controllable[] {
  return this.entities.filter(isControllable);
}
~~~

ここで使われている `isControllable` は、TypeScriptの「型ガード（Type Guard）」と呼ばれる関数です。配列の中から操作可能なものだけを安全に絞り込み、型を確定させるために使われています。

## 3.2 個体の追加・待機・回収のライフサイクル

個体を世界に登場させる入口は `add()` メソッドです。

~~~ts
public add(entity: DynamicEntity): void { ... }
~~~

ただし、3Dモデルやテクスチャのロードが終わるまで実体化できない敵（タンパク質敵など）も存在します。そうした非同期な個体は、`spawnWhenReady()` を使って待機列に入れます。

~~~text
spawnWhenReady(gate, build)
  ├─ gate が通過（ロード完了） → build() を実行して add()
  └─ gate が未通過（ロード中） → pendingSpawns 配列で待機
~~~

中途半端に読み込まれた未完成の個体が `entities` 配列に入ってしまうと、当たり判定や描画でエラーが起きてしまいます。そのため、「準備が完全に整ってから初めて `entities` へ登録する」という安全な二段階構造になっています。

役目を終えた個体（撃墜された敵や寿命を迎えた弾）の片付けは `cleanup()` が担当します。

~~~text
cleanup()
  ↓
1. processPendingSpawns()  ロード完了した待機個体を実体化
2. 各 entity の寿命・逸脱判定
3. enforceCaps()            弾や破片の最大数オーバーを古い順に整理
4. prune()                  消滅した個体の dispose() を呼び、配列から除去
~~~

個体の `motion.alive = false` になった瞬間と、配列から完全に除去される瞬間が分かれている点に注目してください。撃破時の爆発エフェクトを出したり、スコアに加算したり、次の操作対象へカメラを引き継いだりする処理が、個体が配列から消える前に必要となるためです。

## 3.3 `update()` の中での処理分担

`DynamicSystem.update()` は、1フレームの中で次のステップを厳密な順序で実行します。

~~~text
DynamicSystem.update()
  ↓
1. updateThrusts()        ブースターなど、個体自身のタイマーで決まる推力を進める
  ↓
2. updateControllables()  操作対象の機体に入力を渡し、推力や姿勢指令を決める
  ↓
3. behaveAll()            敵AIに思考させ、旋回や射撃の指令を出させる
  ↓
4. Simulator.advance()    全員の推力・重力・姿勢を元に物理時間を進め、衝突を解く
~~~

ここで大事なのは、**「推力や旋回の指令を出す処理」と「実際に位置や速度を計算する物理積分」が明確に分かれている** ことです。
全員の意図（指令）が出揃ってから、最後に `Simulator` が全員の時間を一括して進めます。

## 3.4 個体（エンティティ）の構造：`DynamicEntity`、`DynamicMotion`、`DynamicView`

このゲームの設計で非常に美しいのが、個体（エンティティ）の「存在」「物理」「見た目」が綺麗に分かれている点です。

[src/game/dynamic/dynamic-entity/dynamic-entity.ts](file:///Users/pandeaconica/lab/dive-into-tepui/src/game/dynamic/dynamic-entity/dynamic-entity.ts) を見ると、`DynamicEntity` は次の2つの主要な部品を持っています。

~~~ts
export class DynamicEntity {
  public readonly id: string;
  public readonly motion: DynamicMotion;  // 物理・運動・衝突・熱
  public readonly view: DynamicView;      // 3Dメッシュ・描画表現
  // ...
}
~~~

- **`DynamicEntity`（ゲーム上の存在）**: 個体の ID、名前、マップでの表示設定、寿命の管理などを担当します。
- **`DynamicMotion`（物理と運動）**: 位置・速度・姿勢・質量・空気抵抗・重力・温度・当たり判定など、物理シミュレーションに関するすべての数値を担当します。
- **`DynamicView`（画面上の見た目）**: Three.js のメッシュやインスタンス描画、マテリアルなど、画面にどう映すかを担当します。

このように「物理の計算」と「描画の処理」を完全に分離しているため、描画を行わないヘッドレステストでも物理コードがそのまま動きますし、描画方式（通常メッシュかインスタンス描画か）を変えても物理挙動には一切影響しません。

## 3.5 `Ship`、`Player`、`Enemy`、`Base` の役割分担

個体のクラス継承は、次のようになっています。

~~~text
DynamicEntity
  ├─ Ship                   機体共通のパーツ構造・耐久値・熱特性
  │   ├─ Player             自機固有の入力処理、武装、HUD警告
  │   └─ Enemy              敵共通のAI思考、バースト射撃、被弾処理
  │       ├─ MetalEnemy     通常の金属製メカ敵
  │       └─ ProteinEnemy   分子構造を持つ特殊な敵
  ├─ Base                   基地（Controllable だが Ship ではない）
  ├─ Bullet                 弾丸
  ├─ AmmoPickup / RcsFuel   補給アイテム
  └─ DebrisPiece            破片・残骸
~~~

- **`Ship`**: 船体（Hull）、コクピット、スラスター、RCSタンク、放熱板、太陽電池、武装といった「パーツ群（Parts）」を持ちます。壊れたパーツに応じて推力や発電量が落ちる仕組みはここで処理されます。
- **`Player`**: キーボードやマウスの入力を受け取ってスロットル（`Throttle`）や射撃管制（`FireControl`）に伝え、機体を動かします。
- **`Enemy`**: プレイヤー機を追尾するAIや、旋回制御、射撃のトリガーを自律的に行います。
- **`Base`**: プレイヤーが乗り移って操作できる（`Controllable` を満たす）構造物ですが、宇宙船ではないため `Ship` は継承していません。共通の interface だけを共有し、無駄な継承を避けています。

## 3.6 `Simulator` は「時間の刻みと相互作用」を管理する

[src/game/dynamic/simulator.ts](file:///Users/pandeaconica/lab/dive-into-tepui/src/game/dynamic/simulator.ts) の役割は、個々の個体を詳しく知ることではなく、**「どう時間を刻み、誰と誰の衝突を計算するか」** を統括することです。

1フレームの間に長い時間が進む場合（高速ワープ時など）、一度に大きく時間を進めると当たり判定をすり抜けてしまいます。そのため、`Simulator` は時間を安全な小さな刻み（サブステップ）に分割して進めます。

~~~text
サブステップごとの進行:
  1. 全個体の物理（DynamicMotion）を少し進める
  2. SurfaceContactPhysics   天体地表との接触・衝突を判定
  3. EntityContactPhysics    個体同士（弾と敵、自機と敵など）の衝突を判定
  4. Stage.applySimulationEvents()  特定時刻のイベント（ノード実行など）を適用
~~~

天体（地球や月）の地表との衝突は、天体の位置が自機の衝突によって変わることはないため、個体ごとに独立して計算できます。
一方、個体同士の衝突（自機と敵、弾と敵）は互いの状態に影響を与えるため、衝突の候補をリストアップして時間順に解いていきます。

## 3.7 未来の軌道予測（`Predictor` と `PredictedArc`）

マップ画面で未来の軌道線を見たり、戦闘中に敵の見越し点（リードマーカー）を表示したりするために、**「今から先、この物体はどう飛ぶか？」** を先回りして計算する仕組みがあります。それが `Predictor` と `PredictedArc` です。

- **`PredictedArc`**: ある時点の状態（位置・速度）を出発点として、重力や大気抵抗を受けながら進む未来の軌道を1ステップずつ計算して伸ばす計算機です。
- **`Predictor`**: フレームごとの計算負荷が重くなりすぎないよう、「今フレームは何歩まで未来を計算してよいか（計算予算）」を各個体に賢く配分するマネージャーです。

現在進行中の実シミュレーションとは別の独立した軌道計算機を持つことで、ゲーム自体の進行を乱すことなく、プレイヤーに正確な未来予測を提供しています。

# 4. 天体系の中心：`CelestialSystem`

プレイヤーや敵が戦う宇宙の舞台を管理するのが [src/game/celestial/celestial-system.ts](file:///Users/pandeaconica/lab/dive-into-tepui/src/game/celestial/celestial-system.ts) です。

~~~text
CelestialSystem
  ├─ CelestialEntity[]     天体の表示（メッシュ、リング、選択判定）
  ├─ CelestialMotion[]     天体の物理（位置、速度、質量、重力場の計算）
  ├─ 星空・天球グリッド    背景の描画
  ├─ 太陽光・惑星光・影    宇宙のライティング
  └─ ラグランジュ点ガイド  重力の安定点・ゼロ速度曲線の表示
~~~

## 4.1 `solar-system/` は宣言、`CelestialSystem` は運用

天体に関するコードは、2つの役割に分かれています。

- **`src/game/celestial/solar-system/`**: 「地球の半径は何kmか」「月はどの軌道を回っているか」「どんなテクスチャを貼るか」といった静的な定義を組み立てる場所です。
- **`CelestialSystem`**: その定義を受け取り、毎フレームの自転や公転を計算し、3Dシーンに配置して動かす「運用の場」です。

天体の正確な軌道力学計算や天体暦（エフェメリス）の計算式そのものは、ゲームルールから切り離されて [src/physics/](file:///Users/pandeaconica/lab/dive-into-tepui/src/physics/) フォルダの純粋な数学・物理モジュールが担当しています。

## 4.2 `build()` と `sync()` の分離

天体系でも「初期化」と「毎フレームの更新」が明確に分かれています。

- **`build()`**: ゲーム開始時に一度だけ呼ばれ、惑星や衛星の球体メッシュ、大気のエフェクト、星空の背景を Three.js のシーンに登録します。

## 4.3 物理の `CelestialMotion` と 表示の `CelestialEntity`

ここでも「物理」と「見た目」が綺麗に分かれています。

~~~text
physics/CelestialMotion
  = 天体の質量・現在位置・速度・重力場の計算（物理計算）

game/celestial/CelestialEntity
  = その天体をどう描画し、クリックしたときにどう反応するか（表示とUI）
~~~

「自機にかかる地球の重力を計算したい」ときは `CelestialMotion` を見に行き、「地球のメッシュや夜側の街の明かりテクスチャをどう描いているか」を知りたいときは `CelestialEntity` を見に行きます。

# 5. 「いつ、どの座標系で見るか」をそろえる仕組み

宇宙を舞台にしたゲームで特に難しいのが、「どこを中心に、いつの時刻を見るか」という視点の管理です。

太陽系スケールの中で地球の周りを秒速数kmで周回しているとき、視点や時刻の基準が1箇所でもずれると、宇宙船のメッシュ、軌道予測線、UIマーカーがバラバラにずれて表示されてしまいます。これを防ぐための仕組みが用意されています。

## 5.1 `DisplayWindowManager`

[src/game/display-window-manager.ts](file:///Users/pandeaconica/lab/dive-into-tepui/src/game/display-window-manager.ts) は、**「このフレームで画面に表示すべき時刻と座標系」** を一括管理します。

~~~ts
interface DisplayWindow {
  frame: ReferenceFrame;  // どの座標系で見るか（地球中心か、太陽中心かなど）
  simTime: number;        // 現在のシミュレーション時刻
  displayTime: number;    // 画面が表示している時刻（未来スライダーの位置）
  duration: number;       // 未来へ何秒先まで軌道線を描くか
  pastDuration: number;   // 過去何秒前まで航跡を描くか
  epochUnixSec: number;   // 基準日時のUNIX秒
}
~~~

マップ画面では、プレイヤーがスライダーを動かして未来の軌道を確認することができます。このとき、実際のシミュレーション時刻（`simTime`）と画面に表示している時刻（`displayTime`）が異なります。
`DisplayWindowManager` がそのフレームの表示窓（`DisplayWindow`）を一度確定させ、カメラ、軌道線、マーカー、3Dメッシュのすべてが同じ表示時刻を共有して描画されます。

## 5.2 `FrameAnchors`

座標系が「地球」や「太陽」といった固定の天体であれば話は簡単です。
しかしプレイヤーは、「現在操作している自機を中心に見た座標系」や「ターゲットに指定した敵を中心に見た座標系」で軌道を見たいこともあります。

[src/game/frame-anchors.ts](file:///Users/pandeaconica/lab/dive-into-tepui/src/game/frame-anchors.ts) は、そうした「動いている機体やターゲット」を座標系の原点として解決するための中継役です。

~~~text
座標変換が「自機中心の座標系」を要求する
  ↓
FrameAnchors が現在の操作対象（ControlSelection）を調べる
  ↓
指定された時刻（displayTime）における自機の位置・速度を返す
  ↓
その位置を基準にして周囲の軌道線を描画する
~~~

## 5.3 `FloatingOrigin`（浮動原点）によるGPU精度の確保

3Dグラフィックスを扱う上で避けて通れないのが、「浮動小数点数の丸め誤差」という問題です。
太陽系のスケール（数億km）を GPU の単精度浮動小数点数（Float32）でそのまま扱うと、自機の周りの細かいポリゴンや弾丸がガタガタと震えてしまいます。

これを解決するのが [src/game/camera/floating-origin.ts](file:///Users/pandeaconica/lab/dive-into-tepui/src/game/camera/floating-origin.ts) です。

~~~text
物理シミュレーション（CPU）:
  太陽系全体の絶対座標を倍精度（Float64）で高精度に計算する。

描画処理（GPU）:
  カメラの位置を「描画原点 (0, 0, 0)」とし、
  すべての物体の位置から「カメラの絶対位置」を引いた相対座標を Three.js に渡す。
~~~

カメラのすぐ近くを常に原点とすることで、GPU に渡す座標値が常に小さくなり、広大な宇宙空間でも自機の周りをミリメートル単位の精度で滑らかに描画できます。

## 8.1 `MarkerManager` は表示と間引きの専任役

[src/game/marker/marker-manager.ts](file:///Users/pandeaconica/lab/dive-into-tepui/src/game/marker/marker-manager.ts) は、画面上に浮かぶアイコンやテキストラベル（HTMLのDOM要素やSVG）を管理する専任役です。

# 10. 軌道計画（Plan）：状態・計算・編集・表示の分離

マップ画面で軌道上にノードを置き、「ここで何秒間、どの方向にエンジンを噴射すればどこへ行けるか」を試行錯誤する軌道計画機能（Plan）。
この機能は、4つのクラスが綺麗に役割を分担して実現されています。

~~~text
1. Plan (状態)
   ユーザーが置いた計画ノード列（データそのもの）の正本。

2. PlanPath (区間計算)
   自機の現在位置からノード、そしてその先の未来軌道を区間ごとに予測計算する。

3. PlanEditor (編集)
   マップ画面上でのドラッグ操作や Δv（速度変化量）ハンドルの操作を受け付ける。

4. PlanDisplay (表示)
   計算された軌道予測線やノードマーカーを Three.js のシーンや DOM に反映する。
~~~

## 10.1 `Plan` は軌道計算を行わない

[src/game/plan/plan.ts](file:///Users/pandeaconica/lab/dive-into-tepui/src/game/plan/plan.ts) を見ると、`Plan` クラス自体は軌道の計算式を一切持っていません。

`Plan` が持っているのは、**「ノードの配列（噴射予定時刻と噴射後の速度ベクトル）」** だけです。

~~~ts
private data: {
  anchor: KinematicState;     // 計画の起点となる位置・速度
  nodes: KinematicState[];    // ユーザーが置いたノードの配列
} | null = null;
private _revision = 0;        // 計画が変更されたことを示す世代番号
~~~

特に重要なルール（不変条件）として、**「前のノードの噴射時刻や方向を変更したら、それより未来にある下流のノードは自動的に破棄される」** という仕様があります。過去の噴射が変われば未来の軌道は根本から変わってしまうためです。
こうしたデータ整合性のルールを `Plan` クラスが一元管理しています。

## 10.2 `_revision`（世代番号）による効率的な再計算

プレイヤーがノードをドラッグして動かしたとき、毎回重い軌道計算を最初からやり直すのは非効率です。
そこで `Plan` は、ノードが追加・変更されるたびに `this._revision++` で世代番号をカウントアップします。

表示側（`PlanPath`）は「前回の revision と同じなら計算結果をそのまま使い回す」「revision が変わったときだけ新しく軌道を再計算する」というキャッシュ判定を行うことができます。

# 11. ステージと敵の出現：ルールと配置の分離

ゲームの「勝利条件」や「敵の出現パターン」を司るのが [src/game/stages/](file:///Users/pandeaconica/lab/dive-into-tepui/src/game/stages/) です。

## 11.1 `StageClass` と `Stage`

ステージ関係のファイルには、`StageClass`（インターフェース）と `Stage`（抽象クラス）という似た名前が登場します。

- **`StageClass`（静的定義）**: ゲーム開始前に参照される情報です。ステージの名前、説明文、解放条件、開始時の太陽系設定などを持ちます。
- **`Stage` インスタンス（実行時状態）**: ゲームプレイ中に1回ごとの周回状態を管理します。現在のスコア、残り時間、敵の撃破数、勝敗判定（playing / won / lost / timeup）などを持ちます。

## 11.2 具象ステージの例

ゲームモードやステージごとに、`Stage` を継承したクラスが作られています。

- **`Stage0`**: 制限時間付きのスコアアタック。敵のクラスタが配置され、タイマーがゼロになるとタイムアップ判定を行います。
- **`Stage00`**: 波状攻撃（WaveAttack）モード。敵の全滅を検知して次のウェーブをスポーンさせます。
- **`CreativeStage`**: 敵や機体を自由に配置して実験できるクリエイティブモード。

ステージクラスは「いつ、何を出現させるか」という台本（シナリオ）に専念し、敵の3Dモデル生成や物理パラメータの組み立ては `stages/spawner/` 配下のスポナーに任せることで、ステージの追加が簡単に行えるようになっています。

# 12. 実際のコードを追う5本の道筋

ここまでに登場した各システムが実際にどう連携しているのか、プレイヤーの操作を起点にした5つの代表的なシナリオで追ってみましょう。

## 12.1 Wキーを押して自機のエンジンを噴射するまで

~~~text
1. ブラウザで keydown イベントが発生
     ↓
2. Input.update() がキーの押下状態を確定
     ↓
3. Game.update() → Game.handleInput()
   （Escや設定などのUIで消費されなければスルー）
     ↓
4. DynamicSystem.update() → updateControllables()
   操作対象である Player に input を渡す
     ↓
5. Player.updateControls()
   Throttle.updateThrustState() がキー入力と機体の向きから推力ベクトルを計算
     ↓
6. Player.motion.thrust に推力がセットされる
     ↓
7. Simulator.advance()
   推力と重力加速度を足し合わせて積分し、次のフレームの位置・速度を更新！
~~~

## 12.2 Tキーを押して画面内の敵をロックオンするまで

~~~text
1. T キーが押される
     ↓
2. CombatView.handleInput() がキー入力を検知
     ↓
3. Targeter.handleTargetSelectKey() が呼ばれる
     ↓
4. DynamicSystem の全個体の中から「敵（CombatTarget）」を絞り込み、
   カメラの中心（視線方向）に最も近い敵を見つける
     ↓
5. NavTarget.setCombatTarget(enemy.id) でターゲットを確定
     ↓
6. 次の sync フェーズで Targeter.sync() が呼ばれ、
   敵の周囲にターゲット枠、そして見越し点（リードマーカー）が計算されて表示される！
~~~

## 12.3 Mキーを押してマップ画面へ切り替えるまで

~~~text
1. M キーが押される
     ↓
2. Game.handleInput() → ViewManager.handleInput() が M キーを消費
     ↓
3. ViewManager.setView('map') が実行される
     ├─ CombatView.onLeave()   戦闘用UIや照準器を非表示にする
     ├─ MapView.onEnter()      マップ用の軌道線や天体ラベルを有効化する
     ├─ Hud.setView('map')     HUDをマップ用のレイアウトへ切り替える
     └─ TouchControls.setView('map') モバイル操作ボタンを切り替える
     ↓
4. 次フレームから MapView が入力と描画同期を受け持つようになる！
~~~

## 12.4 敵が出現して画面に描画されるまで

~~~text
1. Stage が addEnemy(enemy) を呼び、DynamicSystem へ登録
     ↓
2. DynamicSystem.update() で敵の AI（behave）が動き、Simulator が位置を進める
     ↓
3. Game.sync() のタイミングで DynamicSystem.sync() が呼ばれる
     ↓
4. Enemy.view.sync() が実行され、Three.js のインスタンス描画バッファへ
   最新の位置・回転・色データが書き込まれる
     ↓
5. Targeter や Enemy.markerItem() がマーカー情報を MarkerManager へ登録
     ↓
6. Game.render() が Three.js を通じて画面に描画！
~~~

## 12.5 クイックセーブ（F5）を押して保存されるまで

~~~text
1. F5 キーが押される
     ↓
2. SnapshotControls が検知し、Game.serialize() を呼ぶ
     ↓
3. Game.serialize() が各システムの serialize() を順に呼んで1つのJSONにまとめる
     ├─ CelestialSystem.serialize() （天体の位置・自転位相）
     ├─ DynamicSystem.serialize()   （全個体の位置・速度・HP・パーツ状態）
     ├─ Stage.serialize()           （スコア・残り時間・ウェーブ進行度）
     └─ CameraSystem / NavTarget    （カメラ位置・ターゲット選択）
     ↓
4. まとまった GameSaveData がローカルストレージへ書き込まれる！
~~~

# 13. コードを読むときのポイント（TypeScriptの設計）

このコードベースを読み進める上で、頻出する TypeScript の構文やオブジェクト指向のテクニックを整理しておきます。

### 1. `interface`（インターフェース）は「能力の契約」
`Controllable` や `ViewFrame` など、`interface` で定義された型が多く登場します。
これは「このクラスにはこのメソッドが必ずある」という約束（契約）です。
使う側（`DynamicSystem` や `Game`）は、相手が `Player` か `Base` かを細かく気にすることなく、「`Controllable` の契約を満たしているから `updateControls()` を呼べば安全に動く」と信じてコードを書くことができます。

### 2. `extends`（継承）と `implements`（実装）の違い
- **`class Player extends Ship`**: `Ship` が持っているHP計算やパーツ管理の「具体的なプログラムコード」を丸ごと受け継いで使います。
- **`class Player implements Controllable`**: 「私は操作可能なオブジェクトとしてのルール（約束）をすべて満たしています」と TypeScript のコンパイラに宣言します。

### 3. `type import`（型のみのインポート）
~~~ts
import type { DynamicEntity } from './dynamic-entity';
~~~
このように `import type` と書かれている場合、それはプログラムの実行時に何かを読み込んでいるのではなく、**「TypeScript の型検査のためだけに使っている」** という意味です。JavaScript へ変換された際にはこの行は完全に消去されます。ファイル同士がお互いを参照し合って循環参照エラーになるのを防ぐため、非常によく使われます。

### 4. `getter`（ゲッター）は「計算された読み出し口」
~~~ts
get activeControllable(): Controllable | null {
  return this.controlSelection.current;
}
~~~
`game.activeControllable` のように、あたかも普通のプロパティのように読める関数です。`Game` 自身が別の変数として二重に値を持たず、常に正本（`controlSelection.current`）から最新の値を取り出すために活用されています。

### 5. `override`（オーバーライド）の明示
~~~ts
public override sync(...): void { ... }
~~~
親クラスにすでにあるメソッドを、子クラス独自の実装で上書きしていることを示すキーワードです。もし親クラスのメソッド名がリファクタリングで変わった場合、TypeScript が「親クラスにそんなメソッドはありません」とエラーで教えてくれるため、タイポなどのバグを未然に防げます。

# 14. 今回のまとめ

`Game` の中身とサブシステムの全体像をまとめると、次のようになります。

~~~text
Game
  ＝ ゲーム全体の指揮者。各部品を所有し、毎フレームの順序を決める

DynamicSystem & Simulator
  ＝ 動く個体（自機・敵・弾）の登録・ライフサイクル・物理時間の進行

DynamicEntity (Motion / View)
  ＝ 個体自身の「ゲーム上の存在」「物理計算」「画面表示」を綺麗に分離

CelestialSystem
  ＝ 太陽系の惑星・衛星・照明・大気・参照座標系を管理

ViewManager (CombatView / MapView)
  ＝ 戦闘画面とマップ画面の振る舞いや操作を切り替えるステートマシン

ControlSelection / NavTarget / Targeter
  ＝ 「操縦対象」「航法ターゲット」「戦闘ターゲット」の明確な役割分離

Plan / PlanPath / PlanDisplay
  ＝ 軌道計画の「データ保持」「区間予測」「画面描画」を分離して管理

Hud & panel-presenter
  ＝ ゲーム内部の値を表示用ViewModelに変換し、安全にDOMへ反映する

Stage
  ＝ 各ステージのルール、敵の出現シナリオ、勝敗判定
~~~

ファイル単体をいきなり1行目から読み始めるのではなく、**「今自分が追いたい現象（入力、射撃、描画など）はどの道筋を通るのか」** を意識して、関連するクラスをピンポイントで追いかけてみてください。

次回（第5講）では、この構造をさらに深く理解するために、コードベース全体を貫く「4本の設計の軸（指令・時間・未来・保存）」について詳しく読み解いていきます。
