第1講ではコードベース全体の地図、第2講では`main.ts`の起動、第3講では入力が`Game`へ届くまでを読みました。

今回は、`Game`の中で呼ばれているファイルへ降りていきます。
目標は、すべてのファイルの細部を暗記することではありません。

~~~text
Game
  ↓ 呼び出し順を決める
  ├─ DynamicSystem       動く個体の集合とシミュレーション
  ├─ CelestialSystem      天体・光・軌道ガイド
~~~

# 1. Gameは「巨大な実装」ではなく「オーケストレーター」

[src/game/game.ts](/Users/pandeaconica/lab/dive-into-tepui/src/game/game.ts)の先頭を見ると、たくさんのimportがあります。

~~~ts
import { CameraSystem } from './camera/camera-system';
import { Stage, StageClass } from './stages/stage';
import { PlanEditor } from './plan/plan-editor';
import { DynamicSystem } from './dynamic/dynamic-system';
import { CelestialSystem } from './celestial/celestial-system';
import { ViewManager } from './view/view-manager';
~~~

ここで大事なのは「Gameがカメラの細かい計算までしている」という意味ではないことです。
Gameは、それぞれの担当を生成して保持し、どの順番で呼ぶかを決めています。

`Game`のフィールドは、そのまま一つのゲーム周回が持つ主要な状態の目録になっています。

~~~text
Game
  ├─ input                 生の入力
  ├─ dynamicSystem         自機・敵・弾・基地など
  ├─ celestialSystem       天体とその表示
  ├─ activeStage           ステージの進行状態
  ├─ controlSelection      いま操作する自機/基地
  ├─ cameraSystem           カメラ
  ├─ viewManager            combat / map
  ├─ displayWindowManager   表示する時刻と座標系
  ├─ planDisplay            計画軌道
  ├─ targeter / navTarget   戦闘・航法ターゲット
  ├─ markerManager          画面上のマーカー
  └─ flashEffects           一時的な演出
~~~

## 1.1 `create()`とconstructorを分けて読む

`Game`は通常の`new Game(...)`ではなく、[game.ts:106](/Users/pandeaconica/lab/dive-into-tepui/src/game/game.ts:106)付近の`static async create()`を入口にしています。

~~~text
StageClass.createCelestialSystem()
  ↓
CelestialSystem.build()       天体メッシュなどをシーンへ登録
  ↓
new Game(...)                  周回内部の部品を配線
  ↓
game.update(0)
game.sync(...)
  ↓
シェーダをcompile()
  ↓
game.render(...)
~~~

`async`なのは、天体暦やシェーダ準備を待つ必要があるからです。
一方、constructorは[game.ts:199](/Users/pandeaconica/lab/dive-into-tepui/src/game/game.ts:199)付近で、すでに作られた天体系を受け取り、ゲーム内の部品を組み立てます。

constructorの呼び出し順には依存関係が表れています。

~~~text
DynamicSystem
  ↓ 個体ができる
CameraSystem / NavTarget / ControlSelection
  ↓ 現在の操作対象・ターゲットを参照できる
ObjectPickables / ObjectWindows
  ↓ クリック候補と窓を組める
CombatView / MapView
  ↓ 2つのビューを持てる
ViewManager
~~~

特に、`ViewManager`は`CombatView`と`MapView`ができたあとに作られています。
これは単なるファイルの並びではなく、「ViewManagerが2つのビューを持つ」という所有関係です。

## 1.2 1フレームは3つの段階に分かれる

`main.ts`は、毎フレーム次の順番でGameを呼びます。

~~~text
game.update(dt)   内部状態を進める
  ↓
game.sync(...)     内部状態を画面用の値へ写す
  ↓
game.render(...)   Three.jsで描く
~~~

`sync`は「描画そのもの」ではありません。
メッシュの位置、カメラ、DOM、マーカー、軌道線を「今フレームに表示すべき状態」へそろえる段階です。
実際のGPU描画を呼ぶのは`render()`だけです。

この区別を持つと、次のようなコードを読めるようになります。

~~~ts
this.dynamicSystem.sync(...);
this.markerManager.resolveCollisions(...);
this.pipeline.render(...);
~~~

前2つは表示データの準備、最後が描画です。

# 3. 動く世界の中心：`DynamicSystem`

[dynamic-system.ts](/Users/pandeaconica/lab/dive-into-tepui/src/game/dynamic/dynamic-system.ts)の先頭コメントは、責務をそのまま説明しています。

~~~text
エンティティの保持・追加・上限管理・寿命回収
1フレームぶんの前進
指令決定と積分
描画同期
~~~

ただし、DynamicSystem自身が敵のAIや弾の運動式を全部持っているわけではありません。
「全個体へ同じ処理を配る」ことが責務です。

## 3.1 顔ぶれの正本は`entities`

`DynamicSystem`には次の配列があります。

~~~ts
private readonly entities: DynamicEntity[] = [];
~~~

この配列が、いま周回に存在する個体の正本です。
自機だけの配列、敵だけの配列を別々に持つのではなく、必要なときに`filter`して取り出します。

~~~ts
get controllables(): readonly Controllable[] {
  return this.entities.filter(isControllable);
}
~~~

ここで出てくる`isControllable`は、単なる真偽値関数ではなく、TypeScriptへ「この配列の要素はControllableとして扱える」と教える型ガードです。

## 3.2 追加・待機・回収

個体を追加する入口は`add()`です。
外部アセットの読み込みが終わるまで実体化できない敵などは、`spawnWhenReady()`へ回します。

~~~text
spawnWhenReady(gate, build)
  ├─ gateが通る → build() → add()
  └─ gateが未通過 → pendingSpawnsで待つ
~~~

この設計では、アセット待ちの敵を「半分だけ作られた個体」として`entities`へ入れません。
未完成の個体が通常のシミュレーションや表示へ混ざらないのがポイントです。

`cleanup()`は、待機中の生成、寿命判定、個体数上限、死亡個体の破棄をまとめて行います。

~~~text
cleanup()
  ↓
processPendingSpawns()
  ↓
各entity.checkLoss(...)
  ↓
enforceCaps()
  ↓
prune()  → dispose()してentitiesから外す
~~~

`alive = false`になった瞬間と、配列から取り除いて`dispose()`する瞬間は別です。
撃破演出や所有者による引き継ぎが、配列から消える前に必要になるためです。

## 3.3 `update()`の中の責任分担

Gameの[game.ts:406](/Users/pandeaconica/lab/dive-into-tepui/src/game/game.ts:406)付近では、ステージを先に更新してからDynamicSystemへ渡しています。
DynamicSystemの[dynamic-system.ts:241](/Users/pandeaconica/lab/dive-into-tepui/src/game/dynamic/dynamic-system.ts:241)付近は、次の順です。

~~~text
DynamicSystem.update()
  ↓
updateThrusts()       個体自身で決まる推力を更新
  ↓
updateControllables() 操作対象へ入力を渡す
  ↓
behaveAll()           敵AIを動かす
  ↓
Simulator.advance()   全個体を積分し、接触を解く
~~~

`operable`が偽のとき、操作対象でない個体へは`input`として`null`が渡ります。
しかし、それは「その個体を止める」という意味ではありません。
燃焼やAIなど、操作されなくても進むものは進みます。

## 3.4 個体の型の階層

`DynamicEntity`を基底に、現在はおおむね次のように分かれています。

~~~text
DynamicEntity
  ├─ Ship
  │   ├─ Player
  │   └─ Enemy
  │       ├─ MetalEnemy
  │       └─ ProteinEnemy
  ├─ Base                  ControllableだがShipではない
  ├─ Bullet
  ├─ AmmoPickup
  ├─ RcsFuelPickup
  ├─ DetachedBooster
  └─ DebrisPiece
~~~

`DynamicEntity`の[dynamic-entity.ts:89](/Users/pandeaconica/lab/dive-into-tepui/src/game/dynamic/dynamic-entity/dynamic-entity.ts:89)付近を見ると、位置・姿勢・生死・半径・推力・軌道線・予測線などを持っています。

個体は、自分の次の内容を答えるメソッドを持ちます。

~~~text
どんな条件で失われるか     checkLoss()
1区間をどう進むか          stepSimulation()
どう表示へ反映するか       syncModel()
どんなマーカーを出すか     markerItem()など
どう保存するか              serialize()
破棄するとき何を解放するか dispose()
~~~

DynamicSystemはこれらを一体ずつ呼びます。
このため、DynamicSystemに「敵ならこの演出、自機ならこのダメージ」という分岐が増えません。
当事者の違いは当事者側へ閉じています。

## 3.5 `Ship`、`Player`、`Enemy`を分けて読む

`Ship`は、機体共通の部品ベースの状態を持ちます。
例えば[ship.ts:290](/Users/pandeaconica/lab/dive-into-tepui/src/game/dynamic/dynamic-entity/ship.ts:290)付近では、壊れていないスラスターの合計推力、燃料、放熱、電力、武装性能をパーツから計算しています。

`Player`は、自機特有の入力と装備を持ちます。
コンストラクタでは、[player.ts:174](/Users/pandeaconica/lab/dive-into-tepui/src/game/player/player.ts:174)付近で次の部品を生成します。

~~~text
Throttle          並進・姿勢操作
FireControl       射撃・弾薬・砲身
Belt              マガジンベルトの物理と表示
AeroLoad          動圧
AltitudeAlarm     高度低下の警告
RadiatorSystem    放熱板
PowerSystem       太陽電池と蓄電
AttachedBoosters  接続中ブースター
各種 Effects      プルーム・再突入・RCS
~~~

`Player.updateControls()`はこれらを決められた順で呼びます。
「Wを押した結果の最終的な運動」はPlayerだけで完結せず、Throttleが加速度を作り、DynamicEntityの積分へ渡ります。

`Enemy`は、敵共通のAI、バースト射撃、被弾、撃破、敵マーカーを持ちます。
敵のメッシュや被弾形状など、敵の種類ごとの差は`MetalEnemy`と`ProteinEnemy`へ下ろされています。

`Base`は`Ship`の子ではありませんが、`Controllable`を実装しています。
つまり「操作できる」という共通の契約は共有しつつ、艦体の共通実装まで無理に共有していません。

## 3.6 Simulatorは「いつ進めるか」を持つ

[simulator.ts](/Users/pandeaconica/lab/dive-into-tepui/src/game/dynamic/simulator.ts)の冒頭には、Simulatorの責務が書かれています。

~~~text
simTime / lastSimDtを保持する
サブステップの区切りを決める
その区間の天体窓を決める
誰と誰が相互作用するかを決める
~~~

一方、「個体1つを1区間進める」ことは`DynamicEntity.stepSimulation()`の責任です。
この分け方により、Simulatorは敵・自機・弾の具体的なクラスを詳しく知る必要がありません。

サブステップ内では、次のように接触の種類が分離されています。

~~~text
DynamicEntityを積分
  ↓
SurfaceContactPhysics       天体表面との接触
  ↓
EntityContactPhysics        個体どうしの接触
  ↓
Stage.applySimulationEvents
  ↓
DynamicSystem.cleanup
~~~

天体は状態を書き換えられないので個体ごとに独立して解けます。
個体どうしは互いの状態を変えるため、`entity-contact-physics.ts`が接触候補を並べ、時間順に解きます。
衝突したときのダメージや消滅は、接触判定側ではなく各個体の`collideWithEntity()`などが担当します。

## 3.7 予測は実シミュレーションと別の読者

`Predictor`と`PredictedArc`は、マップの未来軌道、計画軌道、航法ターゲットなどの「未来を読む人」が必要とする弧を伸ばします。

~~~text
DynamicSystemの実状態
  ├─ 実シミュレーション用のstate
  └─ 表示・分析用のPredictedArc
~~~

実シミュレーションは全個体を同時に進めますが、予測は個体や計画区間ごとの弧を予算内で伸ばします。
そのため、`predictor.ts`は「1歩の物理式」ではなく「どの弧へ何歩配るか」を持ちます。

# 4. 天体系の中心：`CelestialSystem`

自機や敵が動く舞台は、[celestial-system.ts](/Users/pandeaconica/lab/dive-into-tepui/src/game/celestial/celestial-system.ts)です。
ここは単なる天体の配列ではありません。

~~~text
CelestialSystem
  ├─ CelestialEntity[]     天体の表示・選択・参照線
  ├─ CelestialMotion[]     天体の位置・速度・重力
  ├─ ReferenceFrames        座標系
  ├─ 星・天球グリッド
  ├─ 照明・影・大気
  ├─ 参照軌道線
  └─ ラグランジュ軌道ガイド / ゼロ速度曲線
~~~

## 4.1 `solar-system/`は宣言、`CelestialSystem`は運用

`StageClass.createCelestialSystem()`から`solarSystem(...)`が呼ばれます。
`solar-system/earth-system.ts`や`jupiter-system.ts`などは、天体の定義、テクスチャ、親子関係、軌道を組み立てる材料です。

~~~text
StageClass.createCelestialSystem()
  ↓
solarSystem()
  ↓
天体定義 / CelestialMotion / CelestialEntity
  ↓
new CelestialSystem(...)
~~~

厳密な軌道計算は`physics/`にあります。
例えば重力、軌道要素、天体暦、座標変換はゲームルールの表示都合とは分けて、`physics/`の関数やクラスが担当します。

## 4.2 `build()`と`sync()`を分ける

`CelestialSystem.build()`は一度だけ、Three.jsのSceneへ天体メッシュ、星、グリッドなどを登録します。

~~~ts
for (const body of this.entities) body.build(scene, this.ringMaterials);
~~~

毎フレームの`sync()`では、表示時刻とカメラに合わせて次を更新します。

~~~text
天体の表示/非表示
天体メッシュの位置・姿勢
恒星光・惑星光・環の影・天体の影
大気
参照軌道線
星・グリッド・縮尺グリッド
ラグランジュのガイド線
~~~

つまり`build()`は「存在する表示物を作る」、`sync()`は「このフレームの状態に合わせる」です。

## 4.3 `CelestialEntity`は物理そのものではない

`CelestialEntity`は、天体の運動を持つ`CelestialMotion`と、Three.jsでの表示をつなぐ層です。
`SphereEntity`、`PointEntity`、`StarEntity`は、形状や描画方法の違いを実装します。

~~~text
physics/CelestialMotion
  = 天体がどこにいるか・どれだけ重いか

game/celestial/CelestialEntity
  = その天体をどう表示し、クリック対象にするか
~~~

この区別を使うと、天体の位置が知りたいときは`CelestialSystem.stateAt()`や`CelestialMotion`へ、メッシュの表示が知りたいときは`CelestialEntity.sync()`へ進めます。

# 5. 「どこを、いつ見るか」をそろえるファイル

宇宙ゲームで難しいのは、位置の計算だけではありません。
同じ対象を、異なる時刻や異なる座標系で描くと、メッシュ・マーカー・軌道線がずれて見えます。
そのため、表示用の時刻と座標系をまとめるファイルがあります。

## 5.1 `DisplayWindowManager`

[display-window-manager.ts](/Users/pandeaconica/lab/dive-into-tepui/src/game/display-window-manager.ts)の`DisplayWindow`は、名前の通り単なる時間幅ではありません。

~~~ts
interface DisplayWindow {
  frame: ReferenceFrame;
  simTime: number;
  duration: number;
  pastDuration: number;
  displayTime: number;
  epochUnixSec: number;
}
~~~

マップでは未来の軌道を見られるため、`simTime`と`displayTime`が違うことがあります。
`resolve()`がこのフレームの表示窓を一度決め、Gameの後続処理がそれを共有します。

~~~text
simTime       = シミュレーションの現在
displayTime   = 画面がいま表示している時刻
duration      = 未来へ何秒ぶん描くか
pastDuration  = 過去へ何秒ぶん描くか
frame         = どの座標系で描くか
~~~

## 5.2 `FrameAnchors`

座標系が「地球」や「月」だけなら、天体のIDから状態を引けます。
しかし「操作対象」や「航法ターゲット」は、毎フレーム変わる個体です。
`FrameAnchors`は、`controlled`や`navTarget`のような役割名を、時刻`t`の状態へ解決する中継点です。

~~~text
座標変換が「操作対象」を要求
  ↓
FrameAnchors
  ↓
ControlSelection.current または NavTarget
  ↓
その時刻のKinematicState
~~~

Gameは`update()`の早い段階で`frameAnchors.update(displayTime)`を呼びます。
その後の計画・カメラ・マーカーが同じ表示時刻を読むためです。

## 5.3 `FloatingOrigin`

[floating-origin.ts](/Users/pandeaconica/lab/dive-into-tepui/src/game/camera/floating-origin.ts)は、物理の絶対座標を描画用の相対座標へ変換します。

~~~text
物理・ゲームロジック
  = ECI上の大きな絶対座標を倍精度で扱う

描画
  = カメラ付近を原点にして、絶対位置 - 描画原点をThree.jsへ渡す
~~~

これがないと、太陽系のような大きな座標をGPUの単精度で扱うときに、カメラ付近の細かい動きが丸め誤差に埋もれます。
`FloatingOrigin`は物理位置を変えるものではなく、表示直前の差し引きです。

# 6. カメラとビュー：同じ世界を2つの画面で見せる

## 6.1 `CameraSystem`の中身

`CameraSystem`は、カメラの状態とThree.jsカメラへの同期を持ちます。
その下に、性格の違うカメラがあります。

~~~text
CameraSystem
  ├─ FocusCamera    対象を中心にした視点。combat / mapの主カメラ
  ├─ GunsightCamera  照準中の視点
  ├─ CameraOrientation 姿勢や追従方向の合成
  ├─ FocusTarget    天体・機体・固定点などの注視対象
  └─ FloatingOrigin 描画原点
~~~

`FocusTarget`は判別共用体です。

~~~ts
type FocusTarget =
  | { kind: 'object'; id: string }
  | { kind: 'point'; frame: ReferenceFrame; point: FramePoint };
~~~

`kind`を見ると、TypeScriptは`object`なら`id`、`point`なら`frame`と`point`があると判断できます。
このように、`kind`は単なる文字列ではなく、データの形を安全に分けるタグとして働いています。

## 6.2 `ViewManager`はビューの状態機械

[view-manager.ts](/Users/pandeaconica/lab/dive-into-tepui/src/game/view/view-manager.ts)は、現在のビューを1つだけ持ちます。

~~~ts
public get current(): View { return this.view; }
public get activeView(): ViewFrame { return this.views[this.view]; }
~~~

`View`は`'combat' | 'map'`というunion型です。
`ViewFrame`は、各ビューが必ず答える処理の契約です。

~~~text
canEnter()       入れるか
onEnter()        入ったときの準備
onLeave()        出るときの片付け
handleInput()    ビュー固有のキー
handlePointer()  ビュー固有のクリック
update()         候補やビュー状態の確定
syncLabels()     ラベルの表示
syncPanels()     ビュー固有の表示
dispose()        表示物の解放
~~~

`MapView`と`CombatView`がこの契約を`implements`しています。
Gameは「いまcombatかmapか」をあちこちで分岐する代わりに、`activeView`へ委譲できます。

## 6.3 combatとmapの違い

~~~text
Game.handleInput()
  ↓
ViewManager.handleInput()
  ↓
activeView.handleInput()
~~~

戦闘ビューでは、`CombatView`が計画破棄、自動ワープ、照準選択、右クリックのプロパティ窓を扱います。
マップビューでは、`MapView`がノード編集、候補集合、軌道線の右クリック、空域メニューを扱います。

更新と同期にも差があります。

| ビュー | `update()` | `sync()` |
|---|---|---|
| combat | `PlanGuide`を進める | タッチ操作ボタン、ノード実行ガイド、戦闘用マーカー |
| map | `ObjectPickables`、`FrameControls`、`PlanEditor`を更新 | 天体ラベル、計画編集UI、表示期間、物体一覧 |

`ViewManager.setView()`がビュー切替の唯一の入口です。
切り替え時に、HUDの表示、タッチ操作、未来表示の強制フラグを一緒にそろえます。

# 7. 操作対象・ターゲット・選択対象は別物

名前が似ているので、ここは特に分けて覚えます。

~~~text
ControlSelection.current
  = いま自分が操作する艦または基地

NavTarget
  = マップで選んだ航法ターゲット
    天体・ラグランジュ点・艦・基地を含む

Targeter.aliveTarget
  = NavTargetを戦闘対象として解決したもの
    敵・自艦・基地だけ。天体は戦闘対象ではない

ObjectPickables.pickables
  = このフレームにクリックで選べる候補の配列
~~~

## 7.1 `ControlSelection`

[control-selection.ts](/Users/pandeaconica/lab/dive-into-tepui/src/game/control-selection.ts)は操作対象の正本です。
コンストラクタで、保存されたIDに一致するもの、なければ生存中の先頭を選びます。

選択を変えると、古い対象の連続指令を消し、航法ターゲットを解除し、必要なら操作案内を出します。
操作対象が失われたときには、`reclaimAfterLoss()`で別の生存個体へ引き継ぎます。

このため、Gameの`activeControllable`はPlayerを直接持っているのではなく、`controlSelection.current`を読むgetterです。

## 7.2 `NavTarget`

`NavTarget`は対象のIDと表示名を保持し、毎フレームそれを解決します。
対象が天体なら天体の状態、ラグランジュ点なら回転系から求めた状態、艦や基地なら個体の状態を返します。

さらに、同じ軌道面のAN/DNや、最初の最接近点を`RelativeNodeMarker`として管理します。
ここが「ターゲットの対象そのもの」と「ターゲットに付随する表示」をまとめる境界です。

## 7.3 `Targeter`

[targeter.ts](/Users/pandeaconica/lab/dive-into-tepui/src/game/targeter.ts)は、戦闘用の対象表示を担当します。

~~~text
Tキー
  ↓
画面中心に近いCombatTargetを探す
  ↓
NavTarget.setCombatTarget()
  ↓
Targeter.sync()
  ├─ 敵・自機・基地マーカー
  ├─ ターゲット方向/反対方向マーカー
  ├─ 弾薬・燃料マーカー
  ├─ 見越し点(lead marker)
  └─ タンパク質敵の機能部位マーカー
~~~

「どれをターゲットにするか」はTargeter、「ターゲットをどう保持するか」はNavTargetです。

# 8. マーカー、軌道線、クリック窓は表示の別々の層

画面に敵アイコンが出ているとき、敵クラスが直接`document.createElement()`しているわけではありません。
表示をいくつかの層へ分けています。

## 8.1 `MarkerManager`は表示機構、表示理由は持ち主

[marker-manager.ts](/Users/pandeaconica/lab/dive-into-tepui/src/game/marker/marker-manager.ts)の責務は、マーカーDOMの生成・更新・削除です。

~~~text
Player / Enemy / CelestialMarkers / Targeter
  ↓ 何をどこに出すか決める
MarkerManager.setPosition() / setDirection()
  ↓ 投影してDOMを更新
MarkerManager.resolveCollisions()
  ↓ 重なったラベル・アイコンを間引く
~~~

敵がマーカーを出すかどうか、敵マーカーの内容は`Enemy.markerItem()`が答えます。
画面上で重なったときにどれを残すかは`MarkerManager`の責務です。

`Game.sync()`の最後に`resolveCollisions()`があるのは、天体、個体、ターゲット、軌道ノードなど、全マーカーが出そろってからでないと間引けないからです。

## 8.2 `EntityLineManager`と個体の線

`lines/`には、軌道線を描くための線オブジェクトがあります。

~~~text
EllipseLine          解析的な楕円軌道
TrajectoryLine       時系列サンプルを結ぶ折れ線
TargetRelativeLine   ターゲットとの相対軌跡
EntityLineManager    個体の線を列挙して表示へ同期
~~~

線の種類を決めるのは個体や計画側で、全体の同期順を決めるのはGameです。
`Game.sync()`では、天体系・個体・計画を同期した後に`entityLines.sync()`を呼びます。
同じフレームの座標系、カメラ、表示時刻を使う必要があるためです。

## 8.3 `ObjectPickables`は「見えているもの」ではなく「選べるもの」を作る

[object-pickables.ts](/Users/pandeaconica/lab/dive-into-tepui/src/game/pickable/object-pickables.ts)は、マップ上の候補を毎フレーム作り直します。

~~~text
天体
  + ObjectPickableを名乗る動的個体
  + NavTargetのAN/DN/最接近点
  + 近地点・遠地点
  + 赤道交点
~~~

それぞれについて、次を確認して候補へ入れます。

~~~text
消滅していないか
表示トグルで有効か
表示時刻の位置が求まるか
フォーカスした系に属するか
天体に遮蔽されていないか
~~~

表示と選択で別々の判定を使うと、「見えないものをクリックできる」「見えているものを選べない」という不具合になります。
そのため、`MapVisibilityPolicy`を表示と選択で共有しています。

## 8.4 `ObjectWindows`は窓の台帳

`ObjectWindows`は、クリックされた対象に対してプロパティウィンドウやコンテキストメニューを開き、毎フレーム内容を更新します。

~~~text
MapView / CombatView
  ↓ 何に当たったかを決める
ObjectWindows.open(target)
  ↓
PropertyWindowを作る
  ↓
ObjectPickable.propertyRows() / menuItems()
  ↓
毎フレーム最新状態へ更新
~~~

対象ごとのメニュー項目は、`Player`や`Enemy`などの`ObjectPickable`が答えます。
実際に計画を削除する、操作対象を変える、といったゲーム操作は`ObjectCommands`の形で呼び出し側へ戻します。

# 9. HUDはGameの状態をViewModelへ変換して表示する

[hud.ts](/Users/pandeaconica/lab/dive-into-tepui/src/game/hud/hud.ts)は、ゲーム専用HUDのDOMとパネルを保持します。
`hud-root.ts`がDOMの骨格を作り、`Hud`が`TopBar`、`VesselPanel`、`OrbitPanel`などを生成します。

~~~text
Hud
  ├─ combatRoot / mapRoot
  ├─ TopBar
  ├─ VesselPanel
  ├─ OrbitPanel
  ├─ TargetPanel
  ├─ EnemiesPanel
  ├─ BurnManagementPanel
  └─ OrbitAnalysisWindow
~~~

GameがHUDの各パネルへ直接ゲームオブジェクトを渡していない点に注目してください。
`panel-presenter.ts`の`topBarViewOf(game)`などが、Gameから表示に必要な値だけを取り出します。

~~~text
Game / DynamicSystem / Stage
  ↓
panel-presenter.ts
  ↓ 表示用のViewModel
Hud.syncPanels()
  ↓
各Panel.sync(viewModel)
~~~

例えばTopBar用のViewModelは、シミュレーション時刻、速度倍率、一時停止、自動ワープ残り時間を持ちます。
TopBar自身は「速度倍率をどう計算したか」を知りません。

`Hud`がGameを直接importしないように、軌道分析ウィンドウとの接続は`OrbitAnalysisAdapter`という小さな契約で後から差し込まれています。
これは、DOM部品とゲーム状態を分離するための境界です。

# 10. 軌道計画は「状態」「計算」「編集」「表示」を分ける

マップでノードを置く機能は、いくつかのファイルに分かれています。

~~~text
Plan
  = ノード列というゲーム状態

PlanPath
  = 起点とノード列を予測弧・折れ線へ変換

PlanEditor
  = マップのクリック、ノード選択、Δv編集

PlanDisplay
  = シーン・マーカー・表示用パスとの接続

PlanGuide
  = 戦闘ビューで直近ノードの実行を案内
~~~

## 10.1 `Plan`は計算結果を持たない

[plan.ts](/Users/pandeaconica/lab/dive-into-tepui/src/game/plan/plan.ts)のコメントには、計画の中心的な不変条件があります。

~~~text
ノードは噴射直後の絶対KinematicStateとして保存する
Δvは保存値ではなく導出値
上流ノードを変更したら下流ノードを捨てる
計画軌道の計算やキャッシュはPlan自身が持たない
~~~

`Plan`は、ノードを追加・削除・消化し、`revision`を増やします。
どの天体を引くか、何秒先まで描くかは`PlanPath`や`PredictedArc`の仕事です。

## 10.2 `PlanPath`が区間へ分解する

ノードが複数ある計画は、次のような区間の列になります。

~~~text
自機の現在状態 → ノード0
ノード0の噴射後 → ノード1
ノード1の噴射後 → 末尾
~~~

`PlanPath`は各区間へ`PredictedArc`を対応づけ、時系列サンプルを`TrajectoryLine`へ渡します。
ノードを編集したときに上流から先の結果を作り直すのは、この構造だからです。

## 10.3 マップでクリックしたときの道筋

~~~text
MapView.handlePointer()
  ↓
MapPicking / PlanEditor
  ↓
PlanPath上のサンプル、または既存ノードを選ぶ
  ↓
Plan.addNode() / Plan.replaceNode() / Plan.applyNodeDv()
  ↓
次のGame.update()
  ├─ PlanDisplay.update()
  ├─ Predictor.update()
  └─ PlanPathを伸ばす
  ↓
Game.sync()
  ↓
PlanDisplay.sync() / EntityLineManager.sync()
~~~

「クリックした瞬間に軌道線を直接書き換える」のではなく、まず`Plan`の状態を変え、次の更新で予測と表示を組み直します。

# 11. ステージは「ルール」、Spawnerは「配置」

[stage.ts](/Users/pandeaconica/lab/dive-into-tepui/src/game/stages/stage.ts)には、静的な`StageClass`と、周回中の`Stage`があります。

~~~text
StageClass
  = id、epoch、選択画面ラベル、解放条件、生成方法

Stage instance
  = この周回のスコア、phase、補給、敵の進行、勝敗
~~~

Gameは`new stageClass(...)`で周回ごとのStageインスタンスを作ります。
`StageClass`の静的情報と、`Stage`の実行時状態を混ぜないのがポイントです。

## 11.1 基底Stage

基底の`Stage`は、共通処理を持ちます。

~~~text
ScoreCounter       発射・命中・撃破・喪失
Logistics          弾薬/RCS燃料の補給
StatusPanel        ステージ状況HUD
phase              playing / won / lost / timeup
serialize()        共通のセーブ形
~~~

`addPlayer()`や`addEnemy()`もStageのヘルパーです。
ここから`DynamicSystem`へ登録するため、各ステージは個体配列の内部構造を直接操作しません。

## 11.2 具象Stage

具象ステージは、初期配置と毎フレームの台本だけを追加します。

~~~text
Stage0
  = 制限時間つきスコアアタック、色分けクラスタ

Stage00
  = 無限耐久、WaveAttackによる波状攻撃

Stage1 / Stage2
  = 敵の初期軌道パターンが異なる攻略ステージ

CreativeStage
  = 自由配置、補給/波状攻撃の任意切替
~~~

敵の置き方そのものは`stages/spawner/enemy-generator.ts`や`enemy-spawner.ts`へ切り出されています。
ステージは「何を何体、いつ置くか」を決め、Spawnerは「そのパラメータからどんなEnemyを作るか」を決めます。

`stage-utils/`には、スコア、タイマー、補給、ウェーブ、状況パネルなど、複数ステージで共有する小さなルール部品があります。

## 11.3 CreativeとProteinは専門の枝

`creative/`は、軌道要素やラグランジュ点のフォームをDOMへ表示し、入力値を検証します。
物理状態そのものの構築は、既存の`physics/`関数へ渡します。

`protein/`は、アセットの読み込み、表示形式、機能部位、モーション、衝突球、戦闘状態を扱います。
`ProteinEnemy`は敵として`dynamic-entity/`に参加し、タンパク質固有の細部は`protein/`へ委譲します。

このような専門枝は、「GameがProteinの全事情を知る」ために存在するのではありません。
Gameから見れば、どちらもDynamicEntityとして動き、同期し、保存されます。

~~~ts
  case 'metal-enemy':

  case 'base':         return ...;
}
~~~

これはTypeScriptの判別共用体の実例です。
`kind`を増やしたら、復元、保存、表示などの網羅箇所を探せます。

# 13. TypeScript初心者がファイル間で見るポイント

## 13.1 `interface`は「できることの契約」

`Controllable`や`ViewFrame`は、「このクラスにはこのメソッドがある」と約束する型です。
実装の親子関係とは別に、同じ契約を複数のクラスが実装できます。

~~~ts
class MapView implements ViewFrame { ... }
class CombatView implements ViewFrame { ... }
~~~

Gameは、どちらが現在の実装かを`ViewManager.activeView`から受け取ればよく、具体クラスの詳細を毎回分岐しません。

## 13.2 `extends`と`implements`は違う

~~~text
extends Ship
  = Shipの実装を継承して、その上へEnemy固有の処理を足す

implements Controllable
  = Controllableという操作可能の契約を満たす
~~~

Playerは`Ship`をextendsし、`Controllable`をimplementsします。
Baseは`Ship`をextendsせず、`Controllable`をimplementsします。

## 13.3 `type import`は実行時の部品を作らない

~~~ts
import type { Controllable } from './dynamic-entity/controllable';
~~~

これは型検査のための参照です。
実行時にControllableのオブジェクトを読み込んで生成するimportではありません。
ファイル間の循環を減らすため、型だけ必要なときに使われます。

## 13.4 getterは「計算された読み取り口」

~~~ts
get activeControllable(): Controllable | null {
  return this.controlSelection.current;
}
~~~

`Game.activeControllable`という状態をGameが別に保存しているのではありません。
正本である`ControlSelection.current`を読む便利な入口です。
同じ値を二重に持たないためのgetterです。

## 13.5 `override`は親のメソッドを置き換える印

`Player`の`syncModel()`や`Enemy`の`checkLoss()`に付く`override`は、基底クラスの同名メソッドをこのクラス用に実装している印です。
親に存在しない名前を間違って書いたとき、型検査で気づけます。

# 14. 次にコードを読むときの実践手順

現象から入ると、次の順で追えます。

~~~text
1. Game.update / sync / renderのどこにあるか確認
2. Gameが次に呼ぶ担当のメソッドへ移動
3. その担当が「状態を持つ側」か「配る側」か判断
4. interface / type / extends / implementsを確認
5. 実際に状態を変える行を探す
6. 最後にsyncModelやPanel.syncなど表示側へ進む
~~~

例えば「敵がなぜ消えたか」なら、次の道筋です。

~~~text
Game.advanceSimulation()
  → DynamicSystem.update()
  → Simulator.advance()
  → DynamicEntity.checkLoss()
  → Enemy.despawn() / collideWith...()
  → Stage.recordEnemyDeath()
  → DynamicSystem.cleanup()
~~~

「マップで地球が選べない」なら、次の道筋です。

~~~text
MapView.update()
  → ObjectPickables.refresh()
  → MapVisibilityPolicy
  → CelestialEntity.mapVisibility()
  → pickablesへ入る/入らない
  → MapPicking
~~~

このように、ファイル名を順番に読むのではなく、ひとつの状態変化を呼び出しの線として読みます。
