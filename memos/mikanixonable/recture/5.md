# 第5講：コードベースを読む四本の軸――指令・時間・未来・保存

第4講では、`game/`のフォルダを外側から眺め、`DynamicSystem`、`CelestialSystem`、`ViewManager`、`Hud`などの大きな担当を地図にしました。

今回は、ファイルを横にたくさん並べて紹介することをやめます。
このゲームのコードを読み始めるときに、最初に掴むと多くのファイルが読みやすくなる「設計の境界」を4本だけ選びます。

~~~text
入力の意味づけ       時間の進行       未来の計算       保存と復元
      │                  │                │                │
      ▼                  ▼                ▼                ▼
ControlSelection    Stage           Plan / Predictor   GameSaveData
Controllable        Simulator       PredictedArc       restorationFor
      │                  │                │                │
      ▼                  ▼                ▼                ▼
Playerの指令       DynamicEntityの   軌道計画・予測線   新しい実行時
Throttle / Fire    stateを進める     を更新する        オブジェクトを組む
~~~

この4本を選んだ理由は、ゲームの「進行」が単なる1本の呼び出し列ではなく、次の4つの問いに分かれているからです。

1. いま、誰が操作されているのか。
2. どのルールで時間を進め、いつイベントを発生させるのか。
3. 実際の世界とは別に、未来をどう計算するのか。
4. 実行中のオブジェクトを、どうデータにして戻すのか。

この講義の目的は、クラス名を暗記することではありません。
コードを読んだときに、次のように言えるようになることです。

~~~text
この状態の正本はどこか？
このクラスは何を決め、何を決めないか？
この値は現在の実体か、派生値か、未来の予測か、保存用データか？
新しい仕様を入れるなら、どの境界の内側へ置くべきか？
~~~

以下は現在のコードを基準にしています。コードと説明が食い違った場合は、コードが正しい読み方です。

# 1. まず「クラスの一覧」ではなく「設計の境界」を見る

## 1.1 このゲームには同じ対象を別の形で表す層がある

たとえば、自機という1つの対象でも、コードの中では一つの型だけで表されません。

~~~text
ブラウザ入力
  ↓
Input                 物理デバイスのイベントをフレーム単位へそろえる
  ↓
ControlSelection      いま指令を受ける個体を1つ選ぶ
  ↓
Controllable          「操作できる個体」が答える契約
  ↓
Player.updateControls 入力を推力・姿勢・射撃の指令へ変換する
  ↓
DynamicEntity.state   位置・速度・姿勢など、現在の物理状態
  ↓
Simulator             時間を進める
  ↓
Player / DynamicEntity の履歴・表示用データ
~~~

ここには少なくとも次の別物があります。

| 形 | 例 | 役割 |
|---|---|---|
| 入力 | `Input` | キーやポインタの事実を集める |
| 選択 | `ControlSelection.current` | その入力を受ける相手を決める |
| 指令 | `throttle`、`thrust`、射撃状態 | 次の物理計算へ渡す意図・内部指令 |
| 現在状態 | `DynamicEntity.state` | いまの位置・速度・時刻 |
| 予測状態 | `PredictedArc` | 現在から先を仮に積分した結果 |
| 保存状態 | `GameSaveData` | 次回に再構築できるデータ |

これらを一つのクラスに詰め込むと、「入力を変えたのか」「物理状態を変えたのか」「予測を捨てるべきなのか」「セーブ形式を変えたのか」が分からなくなります。
このゲームは、同じ自機を複数の境界に分けて扱うことで、変更の影響範囲を限定しています。

## 1.2 読むときは「正本」と「派生値」を分ける

コードを開いたら、フィールドを見て次の3種類に印を付けます。

~~~text
正本       そこを変えない限り、世界の事実は変わらない
派生値     正本から再計算できる
キャッシュ  派生値を速く読むために保持している
~~~

このリポジトリでの例です。

- `ControlSelection._current` は現在の操作対象の正本です。
- `DynamicSystem.entities` は世界に存在する個体の顔ぶれの正本です。
- `DynamicEntity.state` は、その個体の現在の物理状態です。
- `Stage._phase` と`Stage._result`は、その周回の勝敗状態の正本です。
- `Plan.data`は、ユーザーが置いた軌道計画の正本です。
- `PlanPath.sources`や`PredictedArc.trajectory`は、計画を表示・予測するための派生データです。
- `GameSaveData`は正本そのものではなく、実行時の正本を再構築するためのスナップショットです。

「この値を変えると何が変わるか」を知りたければ、その値への書き込みを探します。
読み取りの数だけを見ていると、派生値を正本と誤解しやすくなります。

# 2. 軸その1：`ControlSelection`と`Controllable`――入力を誰へ渡すか

最初の軸は「Wキーが何をするか」ではなく、「Wキーを誰が受け取るか」です。

入力の細部は第3講で扱いました。[`Input.update()`](/Users/pandeaconica/lab/dive-into-tepui/src/input/input.ts:458)は、ブラウザから届いたイベントをそのフレームのスナップショットへ確定します。
しかし、`Input`は「Wは推力」というゲームの意味を知りません。

## 2.1 `ControlSelection`は選択状態の所有者

[`ControlSelection`](/Users/pandeaconica/lab/dive-into-tepui/src/game/control-selection.ts)の中心は、次のフィールドです。

~~~ts
private _current: Controllable | null;

get current(): Controllable | null { return this._current; }
~~~

現在の操作対象は、`Game`の中に別の`activePlayer`として複製されているのではありません。
`ControlSelection`が`_current`として持っています。

constructorでは、セーブされたIDを優先し、見つからなければ生存中の操作可能な個体を選びます。

~~~ts
const candidates = dynamicSystem.controllables;
this._current = candidates.find((c) => c.id === savedId)
  ?? candidates.find((c) => c.alive)
  ?? null;
~~~

ここから読み取れる設計は次の通りです。

- 操作対象は1つである。
- 操作対象の候補は`DynamicSystem`の顔ぶれから導く。
- セーブから戻すときも、オブジェクト参照ではなくIDで再接続する。
- IDが無効でも、次善の生存個体へフォールバックできる。

つまり、`ControlSelection`は艦を動かすクラスではありません。
「操作という関係」を持つクラスです。

## 2.2 `select()`は1行の代入ではなく、関係の切り替え

[`ControlSelection.select()`](/Users/pandeaconica/lab/dive-into-tepui/src/game/control-selection.ts:29)を見ると、選択対象を代入する前後に処理があります。

~~~ts
select(target: Controllable): void {
  if (this._current === target) return;
  this._current?.clearTransientCommands();
  this._current = target;
  this.navTarget.clear();
  if (target.controlHint !== null) this.hud?.hint(target.controlHint);
}
~~~

ここには、責務の境界がよく表れています。

1. 前の対象に残った一時指令を消す。
2. 正本である`_current`を差し替える。
3. 対象に依存する航法ターゲットを消す。
4. 新しい対象の操作案内を出す。

このクラスがカメラやHUDを直接全部実装しているわけではありません。
対象が変わったときに、対象の変更で無効になる関係へ通知する「接続点」を持っています。

削除も同じです。[`remove()`](/Users/pandeaconica/lab/dive-into-tepui/src/game/control-selection.ts:51)は、操作対象だった個体を消す前に、航法ターゲットとカメラのフォーカスを解除し、その後に別の生存個体へ引き継ぎます。

このコードを読むときは、`_current = target`という代入だけを抜き出してはいけません。
状態の変更には、必ず「その状態を参照している相手の後始末」が付いている可能性があります。

## 2.3 `Controllable`は「自機クラス」ではなく能力の契約

[`Controllable`](/Users/pandeaconica/lab/dive-into-tepui/src/game/dynamic/dynamic-entity/controllable.ts:17)は`class`ではなく`interface`です。

~~~ts
export interface Controllable extends CombatTarget {
  readonly totalThrust: number;
  readonly throttle: Throttle;
  readonly fire: FireControl | null;
  readonly plan: Plan;
  planExecution: PlanExecutionMode;

  updateControls(
    input: Input | null,
    dt: number,
    simDt: number,
    registry: EntityRegistry,
    activeStage: Stage,
    celestialSystem: CelestialSystem,
  ): void;

  clearTransientCommands(): void;
}
~~~

`Controllable`は「Playerを継承している」という意味ではありません。
「この相手は、操作指令を受け取り、推力や燃料などを答えられる」という能力の契約です。

この契約があるため、基地も操作対象になれます。
`DynamicSystem`は、具象クラスを`Player`と決め打ちせず、次のように契約だけを使って呼びます。

~~~ts
for (const controllable of this.controllables) {
  if (!controllable.alive) continue;
  controllable.updateControls(
    controllable === active && operable ? input : null,
    dt, simDt, this, activeStage, this.celestialSystem,
  );
}
~~~

このコードの重要な点は、全ての操作可能な個体に毎フレーム`updateControls()`を呼ぶことです。
ただし、現在の対象にだけ`Input`を渡し、それ以外には`null`を渡します。

~~~text
input !== null
  = このフレーム、プレイヤーの入力を受けてよい

input === null
  = 操作対象ではない、または操作ゲート中
  = ただし、エンジン内部で進むものは進める
~~~

`null`は「何もしない」という意味ではありません。
「ユーザー入力は渡さないが、燃焼や状態維持は必要」という意味です。
このように、引数の`null`が状態機械の分岐を表すことがあります。

## 2.4 `Player.updateControls()`は入力をゲーム内の指令へ翻訳する

[`Player.updateControls()`](/Users/pandeaconica/lab/dive-into-tepui/src/game/player/player.ts:262)は、`Input`をそのまま物理計算へ渡しません。
複数の下位系へ意味を翻訳します。

~~~ts
this.hpRegen(dt);
if (input !== null) this.handleEdgeInput(input, registry);

if (input === null) {
  this.clearTransientCommands();
  this.boosters.step(simDt);
  this.thrust = this.boosters.thrust;
  return;
}

this.boosters.step(simDt);
this.updateTorque(input, dt, simDt);
this.fire.updateFireState(dt, input, activeStage, registry, celestialSystem);
this.throttle.updateThrustLatches(input);
const rcsThrust = this.throttle.updateThrustState(input, this.att, simDt, this);
~~~

ここで処理を分類できます。

| 呼び出し | 受け持つ意味 |
|---|---|
| `handleEdgeInput` | 押した瞬間の切り替え・ピックアップなど |
| `boosters.step` | 入力が無くても続くブースター燃焼 |
| `updateTorque` | 姿勢操作の指令 |
| `fire.updateFireState` | 射撃の状態と弾薬 |
| `throttle.updateThrustLatches` | 推力操作のエッジ・ラッチ |
| `throttle.updateThrustState` | 現在の推力ベクトルと燃料消費 |

`Player`が全部の計算を実装しているように見えても、実際には「自機というまとまりを組み立てる」役割が中心です。
射撃の装填規則を変更するなら`Player`へ直接足すより、まず`FireControl`の責務か確認します。
推力キーの意味を変更するなら`Input`ではなく、`Throttle`や`Player.updateControls()`の境界を確認します。

## 2.5 この軸から分かるリファクタリングの指示

仕様変更を次のように翻訳できます。

| 要望 | 最初に見る場所 | 置かない場所 |
|---|---|---|
| 操作対象を切り替えたらターゲットも解除したい | `ControlSelection.select/remove` | `Player`の各武装 |
| 基地にも推力操作を許可したい | `Controllable`の契約と基地の実装 | `Game.handleInput`の`instanceof Player`増殖 |
| 非操作中もブースターを燃焼させたい | `Player.updateControls(input === null)` | `Input`のイベント処理 |
| 射撃キーの連射規則を変えたい | `FireControl`と`Player.updateControls` | `Simulator` |

指示の形としては、「Gameにifを追加する」より、「操作可能という契約を満たす側へ責務を寄せる」と言える方が、設計を読めています。

# 3. 軸その2：`Stage`・`NextEventTime`・`Simulator`――ルールと時間を接続する

次の軸は、ゲームの「何をすれば勝ちか」と、物理の「何秒進めるか」を分けて読むことです。

## 3.1 `StageClass`は起動前、`Stage`は周回中

[`src/game/stages/stage.ts`](/Users/pandeaconica/lab/dive-into-tepui/src/game/stages/stage.ts)には、`StageClass`というinterfaceと、`Stage`というabstract classがあります。
名前が似ていますが、見ている時間が違います。

~~~text
StageClass  = クラスの静的側。ステージ選択・元期・星系生成・復元用constructor
Stage       = 1回の周回の実体。スコア・勝敗・補給・毎フレームの台本
~~~

`StageClass`には次のような起動前の情報があります。

~~~ts
export interface StageClass {
  readonly id: StageId;
  readonly epoch: TdbJulianDate;
  readonly picksStartEpoch: boolean;
  readonly selectLabel: string;
  readonly selectSub: string;
  isUnlocked(clearCounts: ClearCounts): boolean;
  new (saved: StageSaveData | undefined, ...deps: StageDeps): Stage;
}
~~~

一方、`Stage`のインスタンスは次の状態を持ちます。

~~~ts
private _phase: GamePhase;
private _result: StageResult | null = null;
public readonly scoreCounter: ScoreCounter;
protected readonly logistics: Logistics;
~~~

TypeScriptでは、クラスには「インスタンス側」と「静的側」があります。
`new Stage0(...)`で作られたオブジェクトが`Stage`のインスタンス側、`Stage0.id`や`Stage0.epoch`が静的側です。
`StageClass`は後者を読むための契約です。

初心者が迷いやすいのは、次のgetterです。

~~~ts
public get stageClass(): StageClass {
  return this.constructor as unknown as StageClass;
}
~~~

これは「現在のインスタンスから、そのインスタンスを作った具象クラスの静的宣言へ戻る」橋です。
`this.constructor`の型を、ここでゲームが必要とする`StageClass`として扱っています。

## 3.2 `Stage`はゲームの勝敗を知るが、物理の積分は知らない

基底の[`Stage`](/Users/pandeaconica/lab/dive-into-tepui/src/game/stages/stage.ts:110)を見ると、勝敗とステージ状態の責務が集まっています。

~~~ts
protected decide(
  phase: Exclude<GamePhase, 'playing'>,
  result: StageResult,
): void {
  this._phase = phase;
  this._result = result;
  this._worldSfx.setThrust(false);
  this._worldSfx.setRcs(false);
  this.onDecided?.();
}
~~~

`decide()`は、勝敗の値だけを変えているのではありません。

- `phase`と`result`を同時に確定する。
- 決着後に積分が止まるため、継続音も止める。
- `onDecided`で外側へ通知する。

`phase`と`result`を別々の場所で変更すると、画面は勝利なのに本文が未設定、あるいは敗北後も音が鳴る、といった中間状態が生まれます。
そのため、状態遷移の入口を`decide()`へ集めています。

敵が失われたときも、個体側が勝利を直接決めるのではありません。

~~~ts
public recordEnemyDeath(
  enemy: Enemy,
  simTime: number,
  cause: EnemyDeathCause = 'killed',
): void {
  if (cause === 'killed') this.scoreCounter.recordKill();
  else this.scoreCounter.recordEnemyLoss();

  if (this.isPlaying && this.checkWin()) this.onWin(simTime);
}
~~~

敵は「自分が失われた」ことを伝え、ステージが「それで勝利条件を満たしたか」を判定します。
この分担にすると、自然損耗でも勝利判定するか、ステージごとに撃破数をどう数えるかを`Stage`側で変更できます。

## 3.3 具象Stageは「台本」と「配置」を持つ

[`Stage0`](/Users/pandeaconica/lab/dive-into-tepui/src/game/stages/stage0.ts:30)は、スコアアタックの固有状態としてタイマーを持ちます。

~~~ts

  super(saved, ...deps);
  this.timer = new ScoreAttackTimer(
    (saved as Stage0SaveData | undefined)?.timeLeft ?? STAGE0_TIME_LIMIT,
  );
  this.begin();
}

protected init(): void {
  const player = this.addPlayer({ ammo: { mags: 0, rounds: 0 } });
  for (...) this.logistics.spawnForPlayer(player, ...);
  const enemies = generateCluster(player.state, ...);
  for (const enemy of enemies) this.addEnemy(enemy);
}

update(dt: number, simTime: number, simSpeed: SimSpeedManager): void {
  const player = this.ship;
  if (!player) return;
  this.logistics.updateLogistics(simTime, player, simSpeed);
  if (this.timer.update(dt)) this.decide('timeup', ...);

~~~

ここで、`dt`と`simTime`の使い分けが見えます。

- `dt`は実時間のフレーム間隔。制限時間のカウントに使う。
- `simTime`はシミュレーション上の絶対的な経過時刻。補給の投入時刻などに使う。

これは単なる引数の違いではありません。
ワープ中に制限時間を現実時間で減らすのか、シミュレーション時間で減らすのかという、ゲームデザイン上の選択が表れています。

[`Stage00`](/Users/pandeaconica/lab/dive-into-tepui/src/game/stages/stage00.ts:10)は、同じ基底を使いながら`WaveAttack`を組み込みます。

~~~ts
this.waveAttack.update(
  dt,
  player,
  this._dynamicSystem.all().filter(isEnemy),
  simTime,
  this,
  (enemy) => this.addEnemy(enemy),
);
~~~

`Game`は「stage 00ならウェーブを進める」という分岐を持ちません。
ステージ固有の台本が、`Stage00.update()`の中から自分の補助クラスを呼びます。
これが、ステージ追加で`Game`を肥大化させないための境界です。

## 3.4 ステージは時間を直接進めず、イベントの境界を答える

ステージ固有の処理には、毎フレームの`update()`とは別に、次の2つのhookがあります。

~~~ts
public nextSimulationEventTime(_simTime: number): number | null {
  return null;
}

public applySimulationEvents(_simTime: number): void { }
~~~

この2つは、未来のイベントを物理エンジンへ知らせるための口です。

`CreativeStage`では、`instant`実行の軌道計画に待機ノードがあると、最初のノード時刻を返します。

~~~ts
nextSimulationEventTime(simTime: number): number | null {
  let next: number | null = null;
  for (const ship of this._dynamicSystem.all().filter(isPlayer)) {
    const t = ship.planExecution === 'instant'
      ? ship.plan.firstNode()?.t
      : undefined;
    if (t !== undefined && t >= simTime && (next === null || t < next)) next = t;
  }
  return next;
}
~~~

実際にその時刻へ到達した後で、`applySimulationEvents()`が計画の状態へ移します。

~~~ts
ship.plan.consumeNodesUpTo(simTime, reached);
ship.state = reached;
~~~

ここで重要なのは、`Stage`が`Simulator.simTime`を直接書き換えていないことです。

~~~text
Stage              「次にイベントがある時刻」を答える
NextEventTime      Stageと個体の締切から最も早い時刻を選ぶ
Simulator           その時刻を越えない幅で刻む
Stage.apply...      境界へ到達した後にイベントを適用する
~~~

## 3.5 `NextEventTime`と`simulationStepDuration()`を読む

[`NextEventTime.at()`](/Users/pandeaconica/lab/dive-into-tepui/src/game/dynamic/next-event-time.ts:12)は、ステージ側と個体側の締切を比較します。

~~~ts
const stage = activeStage.nextSimulationEventTime(simTime);
const entity = this.entityEventTime(simTime, dynamicSystem);
if (stage === null) return entity;
if (entity === null) return stage;
return Math.min(stage, entity);
~~~

つまり、弾の寿命、ブースターの切り離し、軌道計画の実行時刻などを、それぞれの所有者から集めます。
「全イベントの配列」を1つの巨大なクラスが持つ設計ではありません。

その値は[`simulationStepDuration()`](/Users/pandeaconica/lab/dive-into-tepui/src/game/dynamic/time-step.ts:46)へ渡されます。

~~~ts
let end = Math.min(targetTime, simTime + maxStep);
if (nextEventTime !== null && nextEventTime >= simTime && nextEventTime < end) {
  end = nextEventTime;
}
return Math.max(0, end - simTime);
~~~

この関数は「最大幅」と「イベント時刻」を合成する純粋な規則です。
ここにサウンドやHUDの処理を入れるべきではありません。
純粋な時間規則として切り出されているから、境界条件をテストしやすく、物理の都合とゲームルールの都合を同じ場所へ混ぜずに済みます。

## 3.6 この軸から分かるリファクタリングの指示

| 要望 | 最初に見る場所 | 設計上の理由 |
|---|---|---|
| 新しい勝利条件を追加したい | `Stage.checkWin/onWin/record...` | 勝敗の正本はStageにある |
| ステージごとのウェーブを追加したい | 具象Stageと`stage-utils` | Gameはモードの詳細を知らない |
| 特定時刻のイベントを追加したい | `Stage.nextSimulationEventTime/applySimulationEvents` | Simulatorにルールを埋め込まない |
| 弾の寿命で正確に切りたい | 個体の`nextSimulationEventTime` | 個体固有の締切は個体が知っている |
| サブステップの計算規則を変えたい | `time-step.ts`と`Simulator` | Stageの台本と分ける |

「イベントを追加するから`Simulator`にifを足す」という指示は、動く可能性はあっても責務の境界を壊しやすい指示です。
まずイベントの所有者を決め、その所有者が「時刻を答える」「到達後に適用する」の2つを提供できるか考えます。

# 4. 軸その3：`Plan`・`Predictor`・`PredictedArc`――現在と未来を分ける

軌道ゲームでは、現在の自機と、ユーザーが計画した未来と、画面に表示する線が似て見えます。
しかしコード上では別の責務です。

~~~text
Player / DynamicEntity.state
  = 現在の実体

Plan.data
  = ユーザーが置いた、凍結されたノード列

PredictedArc
  = ある状態を起点にした未来の積分列

Predictor
  = どの弧を、どの予算で、どこまで伸ばすか

PlanPath
  = ノード列を区間と表示線へ組み立てる
~~~

## 4.1 `Plan`は「軌道を計算するクラス」ではない

[`Plan`](/Users/pandeaconica/lab/dive-into-tepui/src/game/plan/plan.ts:56)のコメントには、責務の範囲がはっきり書かれています。
`Plan`は起点とノード列を持ちますが、計算結果やThree.jsの線は持ちません。

~~~ts
private data: {
  anchor: KinematicState;
  nodes: KinematicState[];
} | null = null;
private _revision = 0;
~~~

ノードがないときは`null`です。
このゲームでは、「ノードがない計画」は自機の現在軌道そのものなので、現在状態を重複して保存しません。

~~~ts
anchorOr(fallback: KinematicState): KinematicState {
  return this.data?.anchor ?? fallback;
}

displayData(shipState: KinematicState): PlanData {
  return this.data ?? { anchor: shipState, nodes: NO_NODES };
}
~~~

`fallback`を呼び出し側から受け取ることで、`Plan`が`Player`への参照を持つ必要がなくなります。
これは小さいようで重要な分離です。

~~~text
Planは「自機の現在状態を読みに行く」のではなく、
呼び出し側から渡された状態を「計画が無い場合の起点」として使う。
~~~

## 4.2 ノードを編集すると下流を捨てる

[`Plan.addNode()`](/Users/pandeaconica/lab/dive-into-tepui/src/game/plan/plan.ts:96)は、ノードを単に配列へpushしていません。

~~~ts
const idx = data.nodes.filter((node) => node.t < postState.t).length;
data.nodes.length = idx;
data.nodes.push(postState);
return idx;
~~~

上流のノードが変わると、その後のノードは「上流ノードの実行後状態を起点にした凍結値」なので、もう意味がありません。
だから新しいノードの時刻より後ろを捨てます。

これはデータ構造上のルールであり、UIの都合ではありません。
マップのドラッグ操作から編集しても、キーボード操作から編集しても、`Plan`を通れば同じ不変条件を守れます。

`replaceNode()`も同じ考えです。

~~~ts
data.nodes.length = idx + 1;
data.nodes[idx] = postState;
this._revision++;
~~~

## 4.3 `_revision`は「中身が変わった」を伝える設計

`Plan`には世代値があります。

~~~ts
get revision(): number {
  return this._revision;
}
~~~

配列を直接比較すると、同じ配列を使い回した場合に変更を検出できません。
また、計画を空にしてから同じ形を作り直したとき、単純な`null / non-null`だけでは過去のキャッシュと衝突することがあります。

そこで編集操作のたびに世代を進め、計画を読む側が次のように判断できます。

~~~text
前回見た revision と同じ
  → 計算を使い回してよい

revision が違う
  → 下流の予測・表示・入力判定を再構築する
~~~

このパターンは、UIフレームワーク固有の機能ではありません。
「可変なオブジェクトを複数の読者が共有する」ための一般的な設計です。

## 4.4 `PredictedArc`は、1本の未来を少しずつ伸ばす

[`PredictedArc`](/Users/pandeaconica/lab/dive-into-tepui/src/game/dynamic/predicted-arc.ts:70)は、ある`state0`から始まる積分弧です。

~~~ts
constructor(
  readonly state0: KinematicState,
  sources: FutureCelestialBodyProvider,
  private readonly radius: number,
  private readonly bcInv: number,
  private readonly srpCoeff: number,
  private readonly keplerTail: boolean,
  private readonly consumable: boolean,
) { ... }
~~~

`requiredEnd`までの全未来をconstructorで計算するのではなく、`step()`を呼ぶたびに1歩ずつ伸びます。
これで、画面の予算に合わせて予測を中断できます。

また、予測弧は「何でも予測する」わけではありません。
現在の実体側が持つ熱・姿勢・細かな接触状態を運ばないため、弧が答えられる範囲を限定しています。

~~~text
PredictedArcが答える
  = 自由落下の経路、重力源、固体表面への到達、近地点・遠地点

PredictedArcが答えない
  = 実体の熱の蓄積による焼失、姿勢制御の複雑な結果、剛体接触
~~~

これは「予測の精度が低い」という単純な話ではありません。
持っていない状態を無理に近似すると、その近似を実体側と保守し続ける二重実装になります。
答えられないものを答えないことも、責務の一部です。

## 4.5 `Predictor`は計算式ではなく予算配分を持つ

[`Predictor.update()`](/Users/pandeaconica/lab/dive-into-tepui/src/game/dynamic/predictor.ts:46)を見ると、操作対象・計画・その他の個体へ計算予算を配っています。

~~~ts
const targets = this.dynamicSystem.all()
  .filter((e) => e.hasFutureReader(canDisplayFuture));
const interactive = controlled !== null
  && controlled.hasFutureReader(canDisplayFuture)
  ? controlled
  : null;
~~~

続いて、操作対象と計画へ優先枠を配り、残りをラウンドロビンで配ります。

~~~ts
const consumed = this.advanceBudget(
  interactive,
  interactiveBudget,
  simTime,
  horizon,
  maxStep,
);
~~~

ここから分かるのは、`Predictor`が「未来の軌道をどう積分するか」の所有者ではないことです。
1歩の積分は`PredictedArc.step()`が持ち、`Predictor`は次を決めます。

- どの個体に予測読者がいるか。
- どの弧を優先するか。
- 1フレームで何歩まで許すか。
- 予測が不要になった個体を伸ばさないこと。

この分離があるから、予測の数学を変えずに、優先順位やフレーム予算を調整できます。

## 4.6 `PlanPath`は計画を区間へ分解する表示側の組み立て役

計画にノードが複数あると、軌道は次の区間になります。

~~~text
現在状態 ── 区間0 ── node0 ── 区間1 ── node1 ── 区間2 ── …
~~~

[`PlanPath.update()`](/Users/pandeaconica/lab/dive-into-tepui/src/game/plan/plan-path.ts:123)は、`PlanData`をこの区間列へ分解します。
各区間に`PredictedArc`を割り当て、必要なら作り直し、`TrajectoryLine`へ渡せるサンプル列にします。

ここで`Plan`へThree.jsの`Group`や線を持たせていないことが重要です。

~~~text
Plan       = 計画の意味と不変条件
PredictedArc = 1区間の未来計算
PlanPath   = 区間の組み立てと表示用サンプル
TrajectoryLine = 実際の線の描画資源
~~~

「計画を表示する」という1つの機能でも、状態・計算・表示資源を4段に分けています。

## 4.7 実体の予測と計画の予測は似ていても同じではない

実体側の未来を読むときも`PredictedArc`を使います。
計画側も`PredictedArc`を使います。
しかし、弧の使い方には違いがあります。

- 実体側の弧は、予測線やターゲットリードなどの読者へ消費される。
- 計画側の弧は、ユーザーが置いたノード区間の表示へ使われる。
- 実体側は場合によって二体ケプラー外挿を尾として使う。
- 計画側は、外挿の尾の上に次のノードを置くと実積分とつながらないため、外挿を使わない。

共通化されているのは「1歩の未来を計算する」という部分だけです。
違いまで一つのモードフラグや巨大な`if`へ押し込むと、実体予測と計画表示の条件が混ざります。

## 4.8 この軸から分かるリファクタリングの指示

| 要望 | 最初に見る場所 | 確認する不変条件 |
|---|---|---|
| ノードを編集したら下流線を更新したい | `Plan.replaceNode`と`revision` | 上流変更後の下流ノードは捨てる |
| 予測線が重い | `Predictor.update` | 読者のある弧だけ、予算内で伸ばす |
| 予測と実体の結果を揃えたい | `PredictedArc`と実体側の積分境界 | 共有できる物理だけ共有する |
| 計画データを保存したい | `Plan.frozenData`と`PlanSaveData` | Three.jsの線やキャッシュを保存しない |
| 計画のマウス判定を追加したい | `PlanPath`のサンプル・投影処理 | 表示線と同じ変換を読む |

「計画が変わったら予測を再計算する」という仕様を実装するとき、`Plan`に予測計算を追加するのは避けます。
`Plan`は正本と不変条件を管理し、`revision`を変化の合図として、`PlanPath`や`Predictor`が再計算します。

# 5. 軸その4：`GameSaveData`・`serialize()`・`restorationFor()`――実行時とデータを分ける

最後の軸は、ゲームを保存できる設計を見ることで、実行時オブジェクトの責務を逆算することです。

## 5.1 セーブデータはオブジェクトのコピーではない

[`Game.serialize()`](/Users/pandeaconica/lab/dive-into-tepui/src/game/game.ts:163)は、ゲーム本体をそのままJSON化していません。

~~~ts
return {
  version: SAVE_VERSION,
  stageId: this.activeStage.id,
  simTime: this.simTime,
  ephemerisContext: { ...ephemerisContextFor(this._celestialSystem.epoch) },
  phaseOffsets,
  earthSpinPhase0,
  entities: this.dynamicSystem.serialize(),
  activeControlledId: this.activeControllable?.id ?? null,
  stage: this.activeStage.serialize(),
  camera: { view: this.viewManager.current, ...this.cameraSystem.serialize() },
  navTarget: ...,
};
~~~

保存されるのは、次回にゲームを再構築するために必要な値です。

保存しないものの例です。

- Three.jsの`Mesh`や`Scene`への参照
- DOM要素
- 現在のメソッドやイベントリスナー
- 予測線の計算キャッシュ
- 実行時だけ必要な一時オブジェクト

つまり、セーブデータは「実行中のオブジェクトを浅くコピーしたもの」ではありません。
「再構築のための入力」です。

## 5.2 `GameSaveData`はラン全体、個体とStageは内訳を持つ

[`GameSaveData`](/Users/pandeaconica/lab/dive-into-tepui/src/game/save/save-data.ts:270)は、ラン全体を表します。

~~~ts
export interface GameSaveData {
  version: number;
  stageId: string;
  simTime: number;
  phaseOffsets: Partial<Record<string, number>>;
  entities: EntitySaveDataUnion[];
  activeControlledId: string | null;
  stage: StageSaveData;
  camera?: CameraSaveData;
  navTarget?: NavTargetSaveData | null;
}
~~~

全体の保存を`Game`がまとめ、個体の中身は`DynamicEntity.serialize()`へ委譲し、ステージの中身は`Stage.serialize()`へ委譲します。

~~~text
Game.serialize()
  ├─ CelestialSystem.serialize()
  ├─ DynamicSystem.serialize()
  │    └─ 各 DynamicEntity.serialize()
  ├─ Stage.serialize()
  ├─ CameraSystem.serialize()
  └─ NavTargetのID
~~~

この構造から、「セーブに新しい値を足すとき誰がその値を知っているか」を判断できます。

- ステージの残り時間なら`Stage0`。
- ウェーブ数なら`WaveAttack`と`Stage00`。
- 自機の弾薬なら`Player`と`PlayerSaveData`。
- カメラのフォーカスなら`CameraSystem`と`CameraSaveData`。
- 操作対象なら`Game`がIDをまとめ、復元時に`ControlSelection`へ渡す。

## 5.3 `kind`が具象クラスを復元する

個体の保存型は、[`EntitySaveDataUnion`](/Users/pandeaconica/lab/dive-into-tepui/src/game/save/save-data.ts:163)です。

~~~ts
export type EntitySaveDataUnion =
  | PlayerSaveData
  | MetalEnemySaveData
  | ProteinEnemySaveData
  | AmmoPickupSaveData
  | RcsFuelPickupSaveData
  | DetachedBoosterSaveData
  | BaseSaveData;
~~~

各型には`kind`というタグがあります。

~~~ts
export interface MetalEnemySaveData extends EnemySaveData {
  kind: 'metal-enemy';
  typeIndex: number | null;
}
~~~

復元側の[`restorationFor()`](/Users/pandeaconica/lab/dive-into-tepui/src/game/dynamic/dynamic-entity/entity-dictionary.ts:27)は、タグを見て組み立てるクラスを選びます。

~~~ts
switch (data.kind) {
  case 'player':
    return {
      gate: null,
      build: () => new Player(..., { saved: data, simTime }),
    };
  case 'metal-enemy':
  case 'protein-enemy': {
    const enemyClass = findEnemyClass(data.kind);
    if (enemyClass === null) return null;
    return {
      gate: enemyClass.spawnGate(data),
      build: () => new enemyClass({ saved: data, simTime }, ...),
    };
  }
  case 'ammo':
    return { gate: null, build: () => new AmmoPickup({ saved: data, simTime }, ...) };
  // ...
}
~~~

TypeScriptでは、`data.kind`を`switch`で分岐すると、各`case`の中で`data`が対応する型に絞り込まれます。
これを判別可能なunionと呼びます。

また、未知の`kind`を`skipUnknownKind()`で読み飛ばします。
保存データが常に現在のコードだけから来るとは限らないため、復元側が壊れた入力に対して「知らないものを無視する」という境界を持っています。

## 5.4 `EntityRestoration`は「今すぐ作る」と「条件が揃ったら作る」を分ける

復元関数の戻り値は、個体そのものではありません。

~~~ts
export interface EntityRestoration {
  readonly gate: SpawnGate | null;
  build(): DynamicEntity;
}
~~~

これは、外部アセットが必要な個体を同期的に作れないからです。
例えばProtein敵は、アセットがロードされるまで`gate`が開きません。

`DynamicSystem.restoreFromSave()`は、この手順を受け取って待ち行列へ登録します。

~~~ts
for (const data of save.entities) {
  const restoration = restorationFor(...);
  if (restoration === null) continue;
  this.spawnWhenReady(restoration.gate, () => restoration.build());
}
~~~

ここで、次の3段が分かれています。

~~~text
save data       何を復元するかを表す
restorationFor  どのconstructorとgateかを選ぶ
DynamicSystem   gateが通った時点で顔ぶれへ登録する
~~~

復元関数が直接`dynamicSystem.add(new ...)`まで行わないのは、復元の判断と世界への登録を分けるためです。

## 5.5 保存型を見ると、クラスの責務を逆算できる

たとえば`PlayerSaveData`には次のようなフィールドがあります。

~~~ts
plan: PlanSaveData | null;
fire: FireSaveData;
thermal: ThermalSaveData;
radiator: RadiatorSaveData;
power: PowerSaveData;
throttle: ThrottleSaveData;
parts: AnyPart[];
~~~

これは単に保存形式の一覧ではありません。
`Player`が、射撃・熱・放熱・電力・推力・計画という複数の下位責務を所有していることの証拠です。

逆に、`PlayerSaveData`へカメラのFOVが入っていたら不自然です。
カメラの状態は`CameraSaveData`の責務だからです。

保存構造は、依存関係の監査にも使えます。

~~~text
PlayerSaveDataがFireSaveDataを持つ
  → PlayerがFireControlを所有している

GameSaveDataがactiveControlledIdを持つ
  → ラン全体が操作対象の関係を所有している

EntitySaveDataがidとkindを持つ
  → 復元時に参照をIDで再接続し、具象をkindで選ぶ
~~~

## 5.6 この軸から分かるリファクタリングの指示

| 要望 | 必要な変更点 | 注意点 |
|---|---|---|
| 新しい個体種別をセーブしたい | 保存interface、union、`serialize()`、`restorationFor()` | `kind`の分岐漏れを型検査で見つける |
| 外部アセットを使う個体を復元したい | `EntityRestoration.gate`と`spawnWhenReady` | constructorで未ロード資源を同期取得しない |
| 旧セーブを読めるようにしたい | optional fieldと既定値、必要ならversion分岐 | 実行時に無いフィールドを想定する |
| Stage0固有のタイマーを保存したい | `Stage0SaveData`と`Stage0.serialize()` | `GameSaveData`へタイマーを直書きしない |
| 計算キャッシュを再起動後も保持したい | まず本当に正本か再確認 | 通常は復元後に再計算できる派生値 |

「セーブできるようにGameのフィールドをJSON化する」という指示より、「どの正本を再構築に必要なデータへ変換するかを各所有者に実装する」という指示の方が適切です。

# 6. 4本を一つの進行としてつなぐ

ここまでの4本は独立した話ではありません。
「プレイヤーが計画を置き、それを実行し、セーブして再開する」という1つの流れに並べると、責務の境界が見えます。

## 6.1 軌道計画を置く

~~~text
MapView / PlanEditor
  ↓
Plan.addNode() / replaceNode()
  ↓
Plan.revision が増える
  ↓
PlanPath.update() が区間を組み直す
  ↓
Predictor が PlanPath.growableArcs() を予算内で伸ばす
  ↓
計画線・アプシス・ノード候補を表示する
~~~

この流れで、`Plan`がThree.jsの線を直接触っていないことが分かります。
編集、計算、表示の3つが世代値で接続されています。

## 6.2 実行する

`instant`の計画実行は、単に`Player.state = node`を毎フレーム行う機能ではありません。

~~~text
CreativeStage.nextSimulationEventTime()
  ↓ ノード時刻を返す
NextEventTime.at()
  ↓ もっとも早い締切を返す
simulationStepDuration()
  ↓ ノード時刻を越えない幅を返す
Simulator
  ↓ 境界まで進む
CreativeStage.applySimulationEvents()
  ↓ ノードの状態を実体へ適用する
Plan.consumeNodesUpTo()
  ↓ 実行済みノードを消し、実到達状態を次の起点にする
~~~

この流れの面白い点は、ステージが「時間を進める」のではなく「イベントの境界を返す」ことです。
時間の正本は`Simulator`にあり、ステージの正本は勝敗と台本にあります。

## 6.3 セーブして再開する

~~~text
Game.serialize()
  ↓
GameSaveData
  ├─ stageId / stage
  ├─ simTime / celestial context
  ├─ entities: EntitySaveDataUnion[]
  ├─ activeControlledId
  └─ camera / navTarget
  ↓
Game.create()
  ↓ 星系を保存時の元期・位相で再構築
  ↓ new Game(..., initialSave)
  ↓ DynamicSystem.restoreFromSave()
  ↓ restorationFor(data.kind)
  ↓ gateが通った個体をDynamicSystemへ登録
  ↓ ControlSelectionがactiveControlledIdを再接続
~~~

保存は「オブジェクトを凍結する機能」ではありません。
起動手順と同じ境界を逆向きにたどって、もう一度オブジェクトグラフを組む機能です。

# 7. TypeScript初心者が、この4本から中級者へ進むポイント

## 7.1 `interface`は「実装を隠す」ための入口

`Controllable`や`StageClass`のようなinterfaceを見たら、すぐに実装を全部読もうとしません。
まず、interfaceのメソッドを「利用側が期待している能力」として読みます。

~~~text
Controllable.updateControls(...)
  → DynamicSystemは、誰が実装しているかを知らなくてよい

StageClass.createCelestialSystem(...)
  → Gameは、どのステージの星系生成かを決め打ちしなくてよい

EntityRegistry.add/spawnWhenReady(...)
  → PlayerやSpawnerは、DynamicSystemの全実装を知らなくてよい
~~~

interfaceを「ファイル間の依存を減らす契約」として読めるようになると、具象クラスを読む順番を自分で選べます。

## 7.2 `extends`と`implements`を役割で読む

~~~ts
export interface Controllable extends CombatTarget { ... }
export class Player extends Ship implements Controllable { ... }
~~~

`extends`は、既存の型やクラスの性質を引き継ぎます。
`implements`は、クラスがinterfaceの契約を満たすことを宣言します。

ここから、次のように読めます。

~~~text
Player is-a Ship
Player satisfies Controllable
Controllable is-a CombatTargetの契約も含む
~~~

「継承しているから操作できる」のではなく、「操作に必要な契約を満たしているから操作できる」と読むのが大切です。

## 7.3 判別可能なunionは、復元や状態遷移の設計図

次のような型は、単なる文字列の候補ではありません。

~~~ts
type GamePhase = 'playing' | 'won' | 'lost' | 'timeup';
type EnemyDeathCause = 'killed' | 'burnup' | 'collision' | 'despawn';
~~~

値を限定することで、状態機械の状態を明示できます。
さらに、次の記述があります。

~~~ts
phase: Exclude<GamePhase, 'playing'>
~~~

これは「`decide()`は進行中へ戻すためには使えない」と型で表しています。
型が仕様の一部になっています。

`EntitySaveDataUnion`の`kind`も同じです。
`switch`の各分岐で具象データへ絞り込めるため、復元コードがタグとconstructorの対応表になります。

## 7.4 `null`、`undefined`、`optional`を意味で読む

このコードでは、似た記号でも意味が違います。

| 表現 | 読み方の例 |
|---|---|
| `Controllable \| null` | 今は操作対象が存在しない可能性がある |
| `firstNode(): KinematicState \| undefined` | ノードが無いので値を返せない |
| `camera?: CameraSaveData` | 旧セーブにフィールド自体が無い可能性がある |
| `fire: FireControl \| null` | 基地のように装備を持たないことが仕様としてある |

`null`を見つけたら、「何が存在しないのか」を確認します。
対象が無いのか、値がまだ決まっていないのか、古いデータに無いのかで、復旧方法が変わります。

## 7.5 `private`は、リファクタリングの境界を示す

`Plan.data`や`ControlSelection._current`が`private`なのは、単に外から触らせたくないからだけではありません。
変更のルールをメソッドへ集中させるためです。

~~~text
dataを直接書き換える
  → 下流ノードを捨て忘れる、revisionを増やし忘れる

Plan.addNode/replaceNodeを通す
  → 不変条件とrevision更新が一箇所で守られる
~~~

privateフィールドをpublicへ変更するリファクタリングは、呼び出し側を楽にする代わりに、不変条件の所有者を失わせる可能性があります。

# 8. 実際にコードを読む手順

新しい仕様やバグを調べるときは、次の順番で十分です。

## 手順1：仕様文を「状態の変化」へ翻訳する

例として「自動ウェーブを追加する」を考えます。

~~~text
何が変わる？
  → Stageの進行状態、敵のspawn、勝敗判定、セーブ内容

誰が知る？
  → Stage00 / WaveAttack

いつ起きる？
  → Stage.update。特定時刻ならevent hookも確認

何を描く？
  → HUDは最後に結果を読むだけ
~~~

最初から`Game`、`Hud`、`DynamicEntity`を全部開く必要はありません。

## 手順2：正本を見つける

次のように質問します。

- 操作対象の正本は`ControlSelection._current`か。
- 勝敗の正本は`Stage._phase`か。
- 物理状態の正本は`DynamicEntity.state`か。
- 計画の正本は`Plan.data`か。
- セーブは正本か、それとも復元入力か。

## 手順3：書き込みメソッドを読む

getterや表示側より先に、値を変更するメソッドを読みます。

~~~text
ControlSelection.select/remove
Stage.decide/recordEnemyDeath
Plan.addNode/replaceNode/consumeNodesUpTo
DynamicEntity.stateへの代入
serialize/restorationFor
~~~

特に、書き込みの前後に何が呼ばれているかを見ます。
前処理が古い関係を切るもの、後処理がキャッシュを更新するものかもしれません。

## 手順4：interfaceの呼び出し側と実装側を一つずつ読む

interfaceを見つけたら、参照を全部追うのではなく、まず次の2点を取ります。

1. 誰がそのinterfaceを引数として受け取るか。
2. 代表的な具象クラスがどう実装するか。

例えば`Controllable.updateControls`なら、利用側は`DynamicSystem.updateControllables()`、代表実装は`Player.updateControls()`です。
この2つを読めば、契約の「呼ばれ方」と「実装の分解」が分かります。

## 手順5：変更の波及範囲を予測する

次の表へ書き出すと、リファクタリングの指示になります。

| 変更するもの | 直接の所有者 | 影響を受ける読者 |
|---|---|---|
| `ControlSelection.current` | `ControlSelection` | カメラ、航法ターゲット、HUD、計画編集 |
| `Stage.phase` | `Stage` | シミュレーション実行可否、結果画面、音 |
| `DynamicEntity.state` | 個体 / `Simulator` | 履歴、予測、表示、衝突 |
| `Plan.revision` | `Plan` | `PlanPath`、予測、マーカー、入力判定 |
| `kind`付き保存データ | 保存型と復元辞書 | 新規起動、ロード、旧データ互換 |

影響を受ける読者が多いからといって、所有者をGameへ移す理由にはなりません。
むしろ、読者へどう通知するか、revisionやhookが不足していないかを検討します。

# 9. リファクタリング指示へ変換する練習

## 9.1 悪い指示と良い指示

### 例1：自機選択時に古い射撃指令が残る

悪い指示：

~~~text
Game.update()の最後で射撃状態をリセットする。
~~~

良い指示：

~~~text
操作対象を切り替える唯一の境界はControlSelection.select/removeなので、
切り替え元へclearTransientCommands()を通し、Player側の一時指令の所有権は維持する。
~~~

なぜなら、問題は毎フレームの更新ではなく「操作対象の関係が変わる瞬間」に起きるからです。

### 例2：瞬間実行のノードを飛び越える

悪い指示：

~~~text
Simulatorのループの後で、ノード時刻を過ぎていたらstateを設定する。
~~~

良い指示：

~~~text
Stage.nextSimulationEventTime()で次ノードを境界として返し、
Simulatorがその時刻で刻んだ後、Stage.applySimulationEvents()で適用する。
~~~

時間を進めた後で状態を補正するのではなく、境界を先に時間系へ渡すのがポイントです。

### 例3：計画線の更新が重い

悪い指示：

~~~text
Plan.update()の中で毎回すべての軌道線を再計算する。
~~~

良い指示：

~~~text
Planはnodesとrevisionだけを管理する。
PlanPathは区間ごとの弧を再利用し、PredictorはARC_STEP_BUDGETの範囲で弧を伸ばす。
~~~

「計画の状態」「未来の計算」「線の描画」を混ぜないことが、重さを局所化する鍵です。

### 例4：新しい敵をセーブ可能にする

悪い指示：

~~~text
敵をJSON.stringifyできるようにする。
~~~

良い指示：

~~~text
EnemySaveDataの判別タグを追加し、具象enemyのserialize()、
EntitySaveDataUnion、restorationFor()、必要ならspawnGateを追加する。
THREEの資源や実行時参照は保存しない。
~~~

保存の境界では、実行時オブジェクトをデータへ変換する責務と、データから再構築する責務を確認します。

# 10. 今回のまとめ

今回覚えるべきクラス名は4群だけです。

~~~text
ControlSelection / Controllable
  → 入力を誰へ渡すか。操作対象という関係を持つ

Stage / NextEventTime / Simulator
  → ルールを誰が決め、時間を誰が進めるかを分ける

Plan / Predictor / PredictedArc
  → 計画の正本、未来の計算、計算予算を分ける

GameSaveData / serialize / restorationFor
  → 実行時オブジェクトを再構築可能なデータへ変換する
~~~

4群を読むときの最終チェックは次の通りです。

1. 正本を持っているクラスはどれか。
2. そのクラスの状態を変更する入口はどれか。
3. 変更を読む派生側・表示側・復元側はどれか。
4. 境界をまたぐ値は、interface・hook・union・IDのどれで渡されているか。
5. 新しい仕様を入れるとき、Gameへ分岐を足さずに所有者へ置けるか。

この5問に答えられれば、コードを「何が書いてあるか」だけでなく、「なぜここに書かれているか」という責務分担として読めています。

次にコードを読むなら、次の順番がおすすめです。

~~~text
1. ControlSelection.select/remove
2. ControllableとPlayer.updateControls
3. Stage.decide / Stage0.update / Stage00.update
4. NextEventTime.at / simulationStepDuration
5. Plan.addNode / consumeNodesUpTo
6. Predictor.update / PredictedArc.step
7. Game.serialize / EntitySaveDataUnion / restorationFor
~~~

細部のファイルを無限に読む必要はありません。
まず、状態の持ち主と境界を押さえ、変更したい仕様がどの軸に属するかを判断します。
その後で、その軸の内側だけを深く読めば、コードベース全体を少しずつ中級者の視点で扱えるようになります。
