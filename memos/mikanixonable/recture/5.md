# 第5講：コードベースを読む4本の軸――指令・時間・未来・保存

第4講では、`src/game/` 以下の全体を見渡し、`DynamicSystem` や `CelestialSystem`、`ViewManager`、`Hud` といった各サブシステムの担当領域を地図にしました。

今回は、さらに一歩進んでコードの「設計の意図」に踏み込みます。
何十個ものファイルをただ順番に眺めるのではなく、このゲームの設計を支えている **4本の中心軸** を押さえることで、コードベース全体の構造が驚くほどクリアに見えるようになります。

~~~text
第1の軸：指令（Command）  第2の軸：時間（Time）   第3の軸：未来（Future）  第4の軸：保存（Save）
       │                       │                      │                     │
       ▼                       ▼                      ▼                     ▼
入力を誰へ渡すか？      ルールと物理をどう繋ぐ？ 軌道予測をどう計算する？ 状態をどう保存・再開する？
（ControlSelection）     （Stage / Simulator）  （Plan / Predictor）   （GameSaveData）
~~~

この4本が理解できると、新しい機能を追加したりバグを調査したりするときに、次のような判断が自分自身で下せるようになります。

~~~text
・このデータの「正本（マスターデータ）」は誰が持っているか？
・この値は「現在の実体」なのか、「派生した計算結果」なのか、「未来の予測」なのか？
・新機能を足すとき、Game に直接 if 文を書くべきか、それとも専門の担当クラスへ任せるべきか？
~~~

それでは、最初の視点から順番に見ていきましょう。

# 1. まず「クラスの羅列」ではなく「設計の境界」を見る

## 1.1 同じ「自機」でも、レイヤーごとに姿を変える

巨大なコードベースを読むときに初心者が最も戸惑いやすいのが、**「同じ1隻の自機なのに、ファイルによってまったく別の型や名前で扱われている」** という点です。

自機がプレイヤーの操作を受けて宇宙を飛ぶまでには、次のような段階を踏んでいます。

~~~text
1. 入力層 (Input)
   キーボードやマウスの生イベントをフレーム単位のスナップショットへまとめる。
     ↓
2. 選択層 (ControlSelection)
   「今どの個体がプレイヤーの操作対象か」を決める。
     ↓
3. 契約層 (Controllable)
   「操作を受け取って推力や燃料を管理できる」という能力のインターフェース。
     ↓
4. 指令層 (Player / Throttle / FireControl)
   入力を解釈し、推力ベクトルや姿勢トルク、射撃トリガーなどの「意図」に変換する。
     ↓
5. 物理層 (DynamicMotion / KinematicState)
   推力や重力を受け、運動方程式を積分して実際の位置・速度・温度を進める。
     ↓
6. 予測層 (PredictedArc)
   現在の位置と速度から、未来の軌道を先回りして計算する。
     ↓
7. 表示層 (DynamicView / MarkerManager)
   3Dモデルを動かし、画面上にUIアイコンやゲージを表示する。
     ↓
8. 保存層 (PlayerSaveData)
   ゲーム終了時に、次回まったく同じ状態を復元できる最小限のデータに変換する。
~~~

もしこれらを1つの巨大な `Player` クラスの中にすべて詰め込んでしまったらどうなるでしょうか？
「射撃の連射速度を調整しただけなのに、なぜかセーブデータが壊れた」「3Dモデルを差し替えたら当たり判定がずれた」といった予測不能な不具合が多発してしまいます。

このゲームでは、自機という存在を「入力」「操作関係」「指令」「物理」「予測」「表示」「保存」という **明確な境界（レイヤー）** に分けて扱うことで、変更の影響範囲を最小限に抑えています。

## 1.2 「正本」「派生値」「キャッシュ」を見分ける

コードを読むときは、クラスのプロパティを見て次の3つのどれにあたるかを意識すると、構造がすっきりと整理できます。

~~~text
1. 正本 (Source of Truth)
   そこを書き換えない限り、世界の事実は変わらないマスターデータ。

2. 派生値 (Derived Value)
   正本の値からいつでも計算して導き出せるデータ。

3. キャッシュ (Cache)
   計算の重い派生値を、毎フレーム再計算しなくて済むように一時保存した控え。
~~~

このコードベースでの具体例を見てみましょう。

- **`ControlSelection._current`** は、「現在誰を操作しているか」の正本です。
- **`DynamicSystem.entities`** は、世界に実在する全個体の顔ぶれの正本です。
- **`DynamicMotion.state`** は、その個体の現在の位置・速度・時刻の正本です。
- **`Stage._phase`** と **`Stage._result`** は、その周回の勝敗状態の正本です。
- **`Plan.data`** は、ユーザーが設定した軌道計画ノードの正本です。
- **`PredictedArc` や軌道線の頂点配列** は、正本（位置・速度・ノード）から計算される「派生値」です。
- **`GameSaveData`** は正本そのものではなく、正本を次回再構築するための「スナップショット」です。

バグを直すときは、まず **「書き換えるべき正本はどこにあるか？」** を探します。派生値やキャッシュの側だけを無理にいじっても、根本的な解決にはならないからです。

# 2. 第1の軸：指令（Command）――「入力を誰へ渡すか」

最初の軸は、**「入力されたキー操作を誰が受け取り、どうやって機体の運動指令へ変換するか」** という流れです。

## 2.1 `ControlSelection` は「操作対象という関係」の正本

プレイヤーが操縦している相手を管理するのが [src/game/control-selection.ts](file:///Users/pandeaconica/lab/dive-into-tepui/src/game/control-selection.ts) です。

その中心には、次のプロパティがあります。

~~~ts
export class ControlSelection {
  private _current: Controllable | null;

  get current(): Controllable | null { return this._current; }
  // ...
}
~~~

`Game` は自機オブジェクトを直接抱え込んでいるわけではありません。
`Game.activeControllable` という getter を通じて、`ControlSelection.current` を参照しています。

コンストラクタを見ると、起動時に操作対象をどのように決定しているかがわかります。

~~~ts
constructor(...) {
  const candidates = dynamicSystem.controllables;
  this._current = candidates.find((c) => c.id === savedId)
    ?? candidates.find((c) => c.motion.alive)
    ?? null;
}
~~~

1. セーブデータに記録された ID の個体がいれば、それを復元する。
2. なければ、世界に存在する操作可能な個体のうち、生きている最初の個体を選ぶ。
3. 1隻もいなければ `null`（未操作状態）にする。

このように、`ControlSelection` は船そのものではなく、**「プレイヤーと船を結ぶ操作関係」** を所有するクラスです。

## 2.2 `select()` と `remove()` は「関係の切り替え」

操作対象を切り替える `select()` メソッドを見ると、単にプロパティを書き換えるだけでなく、その前後に重要な後始末を行っていることがわかります。

~~~ts
select(target: Controllable): void {
  if (this._current === target) return;
  this._current?.clearTransientCommands();  // 1. 前の艦の噴射や射撃を止める
  this._current = target;                   // 2. 正本を差し替える
  this.navTarget.clear();                   // 3. 古い艦基準のターゲットを解除
  if (target.controlHint !== null) {        // 4. 新しい艦の操作ガイドを表示
    this.notifier?.hint(target.controlHint);
  }
}
~~~

操作対象が変わるときには、必ず次の後始末が必要です。

- 切り替え前の艦で押しっぱなしになっていたスロットルや射撃を安全に停止させる。
- 古い艦を基準に設定されていた航法ターゲットをリセットする。
- 新しい艦に特有の操作説明（例：「基地モード：推力なし」など）を HUD に通知する。

同様に、艦が撃沈されたり削除されたりする `remove()` でも、カメラの追従を外し、残っている別の味方艦へ操作権を自動で引き継ぎます（`reclaimAfterLoss()`）。

状態を変更するときは、**「その状態を参照していた周囲のシステムの後始末がセットになっている」** というのが重要な設計ポイントです。

## 2.3 `Controllable` はクラスではなく能力の契約（interface）

[src/game/dynamic/dynamic-entity/controllable.ts](file:///Users/pandeaconica/lab/dive-into-tepui/src/game/dynamic/dynamic-entity/controllable.ts) は、クラスではなく `interface` として定義されています。

~~~ts
export interface Controllable extends CombatTarget {
  readonly totalThrust: number;
  readonly throttle: Throttle;
  readonly fire: FireControl | null;
  readonly plan: Plan;
  planExecution: PlanExecutionMode;

  updateControls(
    input: Input | null, dt: number, simDt: number,
    registry: EntityRegistry, activeStage: StageOutcome, celestialBodies: CelestialBodies,
  ): void;

  clearTransientCommands(): void;
}
~~~

これは、「`Player` クラスでなければ操作できない」という制限をなくすための工夫です。
宇宙船（`Player`）だけでなく、宇宙ステーション（`Base`）であっても、このインターフェースを満たしていれば誰でもプレイヤーの操作対象になることができます。

`DynamicSystem` は、操作可能な全個体に対して毎フレーム次のように `updateControls()` を呼び出します。

~~~ts
for (const controllable of this.controllables) {
  if (!controllable.motion.alive) continue;
  controllable.updateControls(
    controllable === active && operable ? input : null,
    dt, simDt, this, activeStage, this.celestialBodies,
  );
}
~~~

ここで非常に面白いのが、**「現在操作していない個体に対しても、`input` に `null` を渡して呼び出している」** 点です。

- **`input !== null`**: プレイヤーのキー入力を受け取り、推力や射撃を更新してよい。
- **`input === null`**: プレイヤーの入力は受け付けないが、すでに点火された固体ブースターの燃焼や、自然冷却などの内部状態は進める。

`null` を「何もしない」ではなく、「外部からの操作入力がない自律状態」として扱うことで、操作対象でない味方機も自然に物理世界の中で動き続けることができます。

## 2.4 `Player.updateControls()` は入力をゲーム内の指令へ翻訳する

[src/game/player/player.ts](file:///Users/pandeaconica/lab/dive-into-tepui/src/game/player/player.ts) の `updateControls()` は、キー入力をそのまま物理の加速度にするのではなく、それぞれの専門モジュールへ仕事を振り分けます。

~~~ts
// 1. 押されたキーに応じたモード切り替え（RCS減衰、プログレード維持など）
if (input !== null) this.handleEdgeInput(input, registry);

// 2. ブースターの燃焼進行
this.motion.attachedBoosters.step(simDt);

// 3. 姿勢制御トルクの計算
this.updateTorque(input, dt, simDt);

// 4. 射撃トリガーと弾薬管理
this.fire.updateFireState(dt, input, activeStage, registry, celestialBodies);

// 5. スロットルキーから推力ベクトルを計算し、motion へセット
this.throttle.updateThrustLatches(input);
const rcsThrust = this.throttle.updateThrustState(input, this.motion.att, simDt, this);
this.motion.thrust = rcsThrust;
~~~

`Player` クラス自身が推力方程式や射撃間隔の計算をベタ書きしているわけではありません。
- 姿勢やスロットルの計算は `Throttle`
- 弾薬や射撃間隔の管理は `FireControl`
- ブースターの燃焼時間は `AttachedBoosters`

といったように、役割ごとに作られた専門部品に委譲されています。

## 2.5 設計の勘所：機能追加や変更でどこを触るべきか

この「指令の軸」が頭に入っていると、仕様変更の際にどこを修正すべきかが即座に判断できます。

| 実現したいこと | 触るべき場所 | 触るべきでない場所 |
|---|---|---|
| 操作対象を切り替えたときに特定の処理を挟みたい | `ControlSelection.select()` / `remove()` | 個々の武装やエフェクトクラス |
| 宇宙基地にも姿勢制御をさせたい | `Base` クラスと `Controllable` interface | `Game.handleInput` に if 文を増やす |
| 射撃の連射速度やリロード時間を変えたい | `FireControl` クラス | `Player` や `Simulator` |
| スロットルのキー割り当てや加速カーブを変えたい | `Throttle` クラス | `Input` クラス（入力機器の判定） |

# 3. 第2の軸：時間（Time）――「ゲームルール」と「物理の時間」の接続

次の軸は、ゲームとしての「勝敗・ルール・台本」と、物理エンジンとしての「時間の進め方」をどう接続しているかです。

## 3.1 `StageClass`（静的宣言）と `Stage`（実行時状態）

[src/game/stages/stage.ts](file:///Users/pandeaconica/lab/dive-into-tepui/src/game/stages/stage.ts) には、`StageClass` と `Stage` があります。

~~~text
StageClass (静的な定義)
  ・ステージ ID、名前、説明文
  ・解放条件（isUnlocked）
  ・開始時の太陽系元期（epoch）
  ・ステージインスタンスを生成するコンストラクタ

Stage (実行時のインスタンス)
  ・現在のスコア、残り時間
  ・進行フェーズ（playing / won / lost / timeup）
  ・補給物資の投入管理（Logistics）
  ・毎フレームの台本（update）
~~~

ゲーム開始前にタイトル画面でステージ一覧を並べるときは `StageClass` を参照し、ゲームが始まって実際に遊んでいる間は `Stage` インスタンスが状態を持ちます。

## 3.2 `Stage` は勝敗を知っているが、物理の積分は知らない

基底クラスの `Stage` にある `decide()` メソッドは、ステージの決着を確定させる唯一の窓口です。

~~~ts
protected decide(
  phase: Exclude<GamePhase, 'playing'>,
  result: StageResult,
): void {
  this._phase = phase;
  this._result = result;
  this._worldSfx.setThrust(false);  // 決着後は噴射音を止める
  this._worldSfx.setRcs(false);
  this.onDecided?.();              // 結果画面などの表示通知
}
~~~

勝敗フェーズ（`_phase`）と結果データ（`_result`）を同時に確定させ、鳴りっぱなしになっているエンジン音を止め、外側へ決着を通知します。
あちこちで勝敗フラグをバラバラに書き換えるのを防ぎ、必ずこのメソッドを通すことで、一貫した状態遷移を保証しています。

敵が全滅したかどうかの判定も同様です。

~~~ts
public recordEnemyDeath(enemy: Enemy, simTime: number, cause: EnemyDeathCause): void {
  if (cause === 'killed') this.scoreCounter.recordKill();
  else this.scoreCounter.recordEnemyLoss();

  if (this.isPlaying && this.checkWin()) this.onWin(simTime);
}
~~~

敵自身が勝敗を直接決めるのではなく、敵は「撃墜された」という事実をステージへ報告し、ステージが「これでクリア条件を満たしたか」を判定します。

## 3.3 具象Stageは「台本」と「初期配置」を担当する

個々のステージ（`Stage0`, `Stage00` など）は、基底の `Stage` を継承して、そのステージ独自の台本（シナリオ）を記述します。

~~~ts
// Stage0 の例（スコアアタック）
update(dt: number, simTime: number, simSpeed: SimSpeedManager): void {
  const player = this.ship;
  if (!player) return;
  this.logistics.updateLogistics(simTime, player, simSpeed);
  if (this.timer.update(dt)) this.decide('timeup', ...);
}
~~~

ここで注目したいのが、**`dt`（現実の経過時間）と `simTime`（ゲーム内シミュレーション時刻）の使い分け** です。
- 制限時間のタイマーカウントダウンには、高速ワープ中でも現実の秒数で減るように `dt` を使います。
- 敵の増援や補給物資の投入タイミングには、ゲーム世界の進行度に合わせるため `simTime` を使います。

## 3.4 時間を直接書き換えるのではなく、「イベント時刻」を物理に教える

ゲームルールと物理エンジンが連携する上で最も洗練されているのが、次の2つのメソッドです。

~~~ts
// 「次にゲーム上の重要イベントが起きる時刻はいつか？」を答える
public nextSimulationEventTime(simTime: number): number | null { return null; }

// 「そのイベント時刻に到達したときに何をするか？」を実行する
public applySimulationEvents(simTime: number): void { }
~~~

例えば、自動実行の軌道計画がある場合、ステージは「次のマニューバ噴射は simTime = 1200秒 の瞬間です」と予告します。
物理エンジン（`Simulator`）はこれを聞いて、**「じゃあ 1200秒 を飛び越えてしまわないように、ちょうど 1200秒 で一度サブステップを区切って時間を進めよう」** と判断します。

そして 1200秒 にぴったり到達した瞬間に、`applySimulationEvents()` が呼ばれて噴射イベントが適用されます。
物理エンジンの中にステージ固有のルールを埋め込むことなく、イベントを秒単位で正確なタイミングで発生させることができる仕組みです。

## 3.5 `NextEventTime` による安全な刻み幅計算

[src/game/dynamic/next-event-time.ts](file:///Users/pandeaconica/lab/dive-into-tepui/src/game/dynamic/next-event-time.ts) は、ステージ側からの予告と、個体側（弾丸の寿命など）の予告を突き合わせ、最も早い締切時刻を割り出します。

~~~ts
at(simTime: number, activeStage: StageSimulationEvents, roster: DynamicSimulationRoster): number | null {
  const stage = activeStage.nextSimulationEventTime(simTime);
  const entity = this.entityEventTime(simTime, roster);
  if (stage === null) return entity;
  if (entity === null) return stage;
  return Math.min(stage, entity);
}
~~~

物理のサブステップ幅を決める関数 `simulationStepDuration()` は、この最短イベント時刻を越えないように刻み幅を小さく調整します。
これにより、高速早送り中であっても「弾の寿命切れ」や「マニューバ噴射」をすり抜けるバグが完全に防がれています。

# 4. 第3の軸：未来（Future）――「現在」と「未来の予測」を分ける

3つ目の軸は、軌道シミュレーターならではの「未来の予測軌道」を扱う設計です。

~~~text
DynamicMotion.state  ＝ 現在の実体（今この瞬間の位置と速度）
Plan.data            ＝ ユーザーが置いた計画ノードのデータ列
PredictedArc         ＝ ある時点から先の軌道を1ステップずつ伸ばす計算機
Predictor            ＝ 毎フレームの計算予算（負荷）を管理する司令塔
PlanPath             ＝ ノード列を区間ごとに繋いで表示用の線にする組み立て役
~~~

## 4.1 `Plan` は軌道計算を行わない

[src/game/plan/plan.ts](file:///Users/pandeaconica/lab/dive-into-tepui/src/game/plan/plan.ts) の `Plan` クラスは、軌道の計算式を一切持っていません。

持っているのは、起点となる宇宙船の状態（`anchor`）と、ユーザーが配置したノードの配列（`nodes`）だけです。

~~~ts
private data: {
  anchor: KinematicState;
  nodes: KinematicState[];
} | null = null;
private _revision = 0;
~~~

ノードが1つもないときは `data = null` になります。
「ノードのない計画軌道」は自機の現在の飛行軌道そのものなので、余計なメモリを消費しないように共通の現在軌道を参照します。

## 4.2 ノード編集時は上流の変更により下流ノードを破棄する

`Plan.addNode()` や `replaceNode()` には、軌道力学に基づいた厳格なデータ整合性ルール（不変条件）が組み込まれています。

~~~ts
// 新しいノードの時刻より未来にある既存ノードをすべて配列から切り捨てる
const idx = data.nodes.filter((node) => node.t < postState.t).length;
data.nodes.length = idx;
data.nodes.push(postState);
this._revision++;
~~~

過去の時点でエンジンを噴射して軌道が変われば、その未来に置いてあったはずのノードは物理的にもう到達できない無効なものになります。
そのため、過去のノードをいじった瞬間、それより下流のノードは自動的に切り捨てられます。
このルールが `Plan` クラスの中でカプセル化されているため、UI側がどんな操作をしても不正な計画データが生まれません。

## 4.3 `_revision`（世代番号）による変更通知

`Plan` には `revision` という数値プロパティがあります。ノードを追加したり編集したりするたびに、`this._revision++` でカウントアップされます。

計画軌道を描画する側（`PlanPath`）は、毎フレーム次のように判断します。

~~~text
前回の revision と同じ
  → 計画内容は変わっていないので、前フレームの計算結果（キャッシュ）を使い回す。

前回の revision と違う
  → 計画が編集されたので、未来予測線を新しく再計算して引き直す。
~~~

重い軌道積分計算を、必要なときだけ最小限に実行するための重要な工夫です。

## 4.4 `PredictedArc` と `Predictor` による計算負荷の分散

未来の軌道を描くには、現在位置から数時間〜数日先までの運動方程式を何千ステップも解く必要があります。これを毎フレーム一気に計算すると、画面が激しくカクついてしまいます。

そこで使われているのが、**「少しずつ伸ばす」** という設計です。

- **`PredictedArc`**: 1回の `step()` 呼び出しで、未来へ向けて数ステップ分だけ軌道を伸ばします。全区間を一瞬で解くのではなく、呼び出された分だけ徐々に長くなります。
- **`Predictor`**: 1フレームあたりに計算してよい総ステップ数（計算予算：`ARC_STEP_BUDGET`）を定めておき、操作中の自機や軌道計画の弧に優先的に計算予算を配分します。

これにより、どれだけ長い未来予測線であっても、60FPS の滑らかな描画を維持したまま少しずつ先へと描画を伸ばしていくことができます。

# 5. 第4の軸：保存（Persistence）――「実行時オブジェクト」と「保存データ」の分離

最後の軸は、ゲームのセーブとロードを司る設計です。
この設計を理解すると、実行時オブジェクト同士の所有関係が最もはっきりと見えてきます。

## 5.1 セーブデータは「オブジェクトのコピー」ではない

[src/game/game.ts:167](file:///Users/pandeaconica/lab/dive-into-tepui/src/game/game.ts#L167) の `serialize()` を見ると、ゲームのオブジェクトを丸ごと JSON にしているわけではないことがわかります。

~~~ts
public serialize(): GameSaveData {
  const { phaseOffsets, earthSpinPhase0 } = this._celestialSystem.serialize();
  return {
    version: SAVE_VERSION,
    stageId: this.activeStage.id,
    simTime: this.simTime,
    ephemerisContext: { ...ephemerisContextFor(this._celestialSystem.epoch) },
    phaseOffsets,
    earthSpinPhase0,
    entities: this.dynamicSystem.serialize(),
    activeControlledId: this.activeControllable?.id ?? null,
    stage: this.activeStage.serialize(),
    camera: { view: this.viewManager.current, ...this.cameraSystem.serialize() },
    navTarget: ...,
  };
}
~~~

セーブデータに保存されるのは、**「次回ゲームを再起動したときに、まったく同じ世界をゼロから組み立て直すために必要な最小限の材料」** だけです。

- Three.js のメッシュやマテリアルは保存しません（再起動時にロードして作ればよいため）。
- DOM 要素やイベントリスナーは保存しません。
- 軌道予測線の計算キャッシュは保存しません（起動後に再計算できるため）。

セーブデータを「再構築のための入力レシピ」として設計することで、セーブファイルのサイズを極限まで小さくし、クラス構造のリファクタリングにも強い柔軟性を保っています。

## 5.2 階層的なシリアライズ（委譲）

全体のセーブ処理は、綺麗なツリー構造で各担当へ委譲されています。

~~~text
Game.serialize()
  ├─ CelestialSystem.serialize()  天体の自転・公転位相
  ├─ DynamicSystem.serialize()    全個体のリスト
  │    └─ 各 DynamicEntity.serialize()  個体ごとの位置・HP・パーツ
  ├─ Stage.serialize()            スコア・残り時間
  ├─ CameraSystem.serialize()     カメラの視点・ズーム
  └─ NavTarget                    ターゲットのID
~~~

`Game` が敵の残りHPや弾薬数を直接読みに行くことはありません。
「個体の内訳は個体自身にシリアライズさせる」という委譲の原則が守られています。

## 5.3 `kind` タグによる復元（Discriminated Union）

保存されたデータから元のオブジェクトを復元する処理は、[src/game/dynamic/dynamic-entity/entity-dictionary.ts](file:///Users/pandeaconica/lab/dive-into-tepui/src/game/dynamic/dynamic-entity/entity-dictionary.ts) の `restorationFor()` に集約されています。

セーブデータには、必ず `kind` という識別用の文字列タグが付いています。

~~~ts
switch (data.kind) {
  case 'player':
    return { gate: null, build: () => new Player(..., { saved: data, simTime }) };

  case 'metal-enemy':
  case 'protein-enemy': {
    const enemyClass = findEnemyClass(data.kind);
    return {
      gate: enemyClass.spawnGate(data),
      build: () => new enemyClass({ saved: data, simTime }, ...),
    };
  }

  case 'ammo':
    return { gate: null, build: () => new AmmoPickup({ saved: data, simTime }, ...) };
  // ...
}
~~~

TypeScript では、`switch (data.kind)` で分岐させると、それぞれの `case` の中で `data` の型が自動的に `PlayerSaveData` や `MetalEnemySaveData` へと安全に絞り込まれます。これを **「判別可能な直和型（Discriminated Union）」** と呼びます。

## 5.4 `SpawnGate` による非同期アセットの安全な復元

復元関数の戻り値は、インスタンスそのものではなく `{ gate, build }` という構造になっています。

~~~ts
export interface EntityRestoration {
  readonly gate: SpawnGate | null;  // アセット読み込み完了の条件判定
  build(): DynamicEntity;            // 実際にオブジェクトを生成する関数
}
~~~

なぜこのような二段階になっているかというと、タンパク質敵のように **「外部の 3D データをダウンロードしてパースするまでコンストラクタを呼べない敵」** がいるからです。

ロードが完了するまでは `gate` が開きません。`DynamicSystem` は `gate` が開いたのを確認してから `build()` を呼び、安全に世界へ参加させます。セーブデータの復元時に画面が一瞬フリーズするのを防ぐための優れた設計です。

# 6. 4本の軸が繋がる1つのストーリー

ここまでに見てきた4本の軸は、独立して動いているのではなく、実際のゲームプレイの中で美しく連動しています。

「プレイヤーがマップで軌道計画を立て、自動実行し、セーブする」という一連の流れで確認してみましょう。

~~~text
1. 軌道計画を置く【未来の軸】
   ・プレイヤーがマップ上でノードを動かす。
   ・Plan.addNode() が呼ばれ、_revision が進む。
   ・PlanPath が区間を分割し、Predictor が計算予算の中で新しい未来予測線を伸ばす。

2. 時間を進めて実行する【時間の軸】
   ・プレイヤーがマニューバの自動実行をオンにする。
   ・Stage.nextSimulationEventTime() が「次の噴射時刻」を予告する。
   ・Simulator がその時刻ぴったりまで時間を刻み、噴射イベントを適用する。

3. 自機が新軌道へ遷移する【指令の軸】
   ・噴射後の新しい速度ベクトルが Player.motion.state にセットされる。
   ・ControlSelection が追従カメラやターゲットマーカーの位置を新しい軌道へ更新する。

4. 状態を保存する【保存の軸】
   ・クイックセーブを押すと、現在の simTime、新軌道の状態、残りの計画ノードが
     GameSaveData へシリアライズされて安全に保存される。
~~~

このように、指令・時間・未来・保存の4つの境界がそれぞれの役割をきっちり果たしているからこそ、複雑な宇宙の軌道ゲームが破綻することなく動いています。

# 7. TypeScript 初心者から中級者へステップアップするためのポイント

このコードベースをスラスラ読めるようになるために、押さえておきたい TypeScript の重要テクニックを整理します。

### 1. `interface` による依存の切り離し
クラス同士が直接お互いを知りすぎると、コードの結合度が高くなってしまいます。
例えば `Controllable` というインターフェースを間に挟むことで、`DynamicSystem` は「自機の詳細」を知る必要がなくなり、コードの独立性が保たれます。

### 2. 判別可能な直和型（Discriminated Union）
~~~ts
type GamePhase = 'playing' | 'won' | 'lost' | 'timeup';
~~~
単なる `string` 型ではなく、取りうる文字列リテラルを限定して定義します。
タイポがあればコンパイル時にエラーになりますし、`switch` 文で分岐を書くときに「すべてのケースを網羅しているか」を TypeScript がチェックしてくれます。

### 3. `null` と `undefined` の使い分けの意図を読む
このコードベースでは、似たような「値がない」状態でも明確に意図が使い分けられています。
- **`Controllable | null`**: 「今は操作対象がいない（全滅した、または手動で外した）」という仕様上の状態。
- **`firstNode(): KinematicState | undefined`**: 配列が空なので値を返せないという関数の結果。
- **`camera?: CameraSaveData`**: 古いバージョンのセーブデータにはこの項目が存在しない可能性がある（オプショナルプロパティ）。

### 4. `private` フィールドと不変条件の保護
`Plan.data` や `ControlSelection._current` が `private` になっているのは、単なる気取りではありません。
「外から勝手に配列を書き換えられたら、下流ノードの破棄やキャッシュの破棄（revision++）が漏れてバグるから」です。
状態の変更を必ず専用のメソッド（`addNode` や `select`）経由に限定することで、データの整合性（不変条件）を守っています。

# 9. 良い設計と避けるべきアンチパターン

コードに手を入れるときに、設計を綺麗に保つための指針です。

### ケース1：自機を切り替えたとき、前の機体の射撃が止まらない
- **避けるべきアプローチ**: `Game.update()` のループの最後で、無理やり射撃フラグを false にリセットする。
- **良いアプローチ**: 操作対象が切り替わる唯一の境界である `ControlSelection.select()` の中で、切り替え元の `clearTransientCommands()` を呼ぶ。

### ケース2：自動噴射のノード時刻を飛び越えてしまう
- **避けるべきアプローチ**: `Simulator` の物理ループの後で、「もし現在時刻がノード時刻を過ぎていたら無理やり位置をワープさせる」コードを追加する。
- **良いアプローチ**: `Stage.nextSimulationEventTime()` でノード時刻を物理エンジンに予告し、物理エンジンにその時刻ぴったりでサブステップを区切らせる。

### ケース3：軌道計画の線が重い
- **避けるべきアプローチ**: `Plan` クラスの中で、ノードが動くたびに全区間の軌道線を同期的に一気に計算する。
- **良いアプローチ**: `Plan` はデータと `revision` の管理に専念し、計算は `Predictor` が毎フレームの計算予算（`ARC_STEP_BUDGET`）の範囲内で少しずつ非同期的に進める。

# 10. 今回のまとめ

第5講では、コードベースの骨格を成す「4本の設計の軸」を学びました。

~~~text
1. 指令の軸 (Command)
   Input（入力）→ ControlSelection（選択）→ Controllable（契約）→ Player（指令）

2. 時間の軸 (Time)
   Stage（ルール）と Simulator（物理）を nextSimulationEventTime で安全に接続

3. 未来の軸 (Future)
   Plan（データ）と Predictor / PredictedArc（計算）を分離し、負荷を分散

4. 保存の軸 (Persistence)
   実行時オブジェクトと GameSaveData（再構築レシピ）を切り離し、Discriminated Union で復元
~~~

この4本の境界線が頭に入っていれば、何千行もの TypeScript コードに出会っても「これはどの軸の、どのレイヤーの話をしているのか」が直感的に見分けられるようになります。

まずは気になった機能（推力の発生、ターゲットのロックオン、セーブデータの追加など）を1つ選び、その軸に沿ってコードを実際に追いかけてみてください！
