# 第3講：入力の入口を読む――Input.update()とGame.handleInput()

第1講ではコードベース全体の地図、第2講ではmain.tsの起動処理とフレームループを読みました。

今回は、ユーザーのキー操作がどのようにゲーム内部へ届くのかを読みます。

~~~text
ブラウザのkeydown / pointerイベント
  ↓
Inputがイベントを一時保存
  ↓
Game.update()
  ↓
Input.update()
  ↓
Game.handleInput()
  ↓
HUD / ワープ / ビュー / 軌道計画へ分岐
  ↓
Player.behave()
  ↓
推力・姿勢・射撃の内部状態へ変換
~~~

今回の目標は次の3つです。

1. Input.update()がなぜ必要なのか理解する。
2. down()、takeKey()、takeHeld()の違いを理解する。
3. Game.handleInput()から各担当へどのように分岐するか理解する。

この講義は現行コードを基準にしています。第2講に以前の名前が残っている場合がありますが、現在の設定メニューはPauseMenuとして構成されています。

# 1. main.tsとgame.tsの境界

今回の処理はmain.tsとgame.tsの両方にまたがります。

## main.tsは外側の運転係

[src/main.ts](/Users/pandeaconica/lab/dive-into-tepui/src/main.ts)は、ゲームセッションの外側にあります。

- WebGPUやSceneを準備する
- HUD、音声、セーブ関連の部品を作る
- Gameを作る
- requestAnimationFrameを回す
- Gameの前後に補助処理を呼ぶ

毎フレームの外側の流れは次の通りです。

~~~text

  ↓
game.update(dt)
  ↓
SnapshotControls / Launcher / PerfMeter
  ↓
AutoSave
  ↓
game.sync()
  ↓
game.render()
~~~

この順番は[main.ts:137](/Users/pandeaconica/lab/dive-into-tepui/src/main.ts:137)付近にあります。

## game.tsはセッション内部の司令塔

[src/game/game.ts](/Users/pandeaconica/lab/dive-into-tepui/src/game/game.ts)のGameは、一つのゲームセッションの内部状態をまとめます。

~~~text
Game
  ├─ Input
  ├─ EntityManager
  ├─ ActivePlayerController
  ├─ Stage
  ├─ Simulator
  ├─ CameraSystem
  ├─ ViewManager
  ├─ PlanEditor
  └─ HUDなどへの参照
~~~

main.tsが毎フレーム呼ぶ入口は、基本的に次の3つです。

~~~ts
game.update(dt);
game.sync();
game.render();
~~~

Gameの中では、update()がさらに多くの担当へ分岐します。

~~~text
Game.update()
  ├─ Input.update()
  ├─ Game.handleInput()
  ├─ advanceSimulation()
  ├─ 計画・環境・カメラ更新
  └─ ポインタ入力処理
~~~

Wによる推力の全処理はGame.handleInput()だけには書かれていません。
後段のPlayer.behave()、さらにPlayerThrottleへ分岐します。

つまりgame.tsは「処理の終点」ではなく「大きな分岐点」です。

# 2. TypeScriptの準備：readonly

今回のコードを読むと、readonlyが頻繁に出てきます。

~~~ts
readonly input: Input;
~~~

これは、inputというプロパティを、初期化後に別のInputへ差し替えないという意味です。

~~~ts
this.input = new Input(element); // 初期化時は代入できる
this.input = anotherInput;        // 以後は代入できない
this.input.update();              // Inputオブジェクトの操作はできる
~~~

readonlyはオブジェクト全体を凍結する命令ではありません。

~~~text
readonly input
  = inputが指す相手を差し替えない

this.input.update()
  = その相手のメソッドを呼ぶことはできる
~~~

## 配列のreadonly

OverlayManagerには、次のようなフィールドがあります。

~~~ts
private readonly stack: OverlayEntry[] = [];
~~~

この場合、配列そのものは差し替えられません。

~~~ts
this.stack = [];       // できない
~~~

しかし中身は変更できます。

~~~ts
this.stack.push(entry);    // できる
this.stack.splice(0, 1);   // できる
~~~

一方、次のように書くと配列の変更も禁止されます。

~~~ts
readonly stack: readonly OverlayEntry[] = [];
~~~

~~~ts
this.stack.push(entry); // できない
~~~

覚え方は次の通りです。

~~~text
readonly entries: Entry[]
  = 参照は固定。配列の中身は変更可能

readonly entries: readonly Entry[]
  = 参照も配列の中身も変更不可
~~~

## コンストラクタ引数の省略記法

次の記述もよく登場します。

~~~ts
constructor(private readonly _hud: Hud) {}
~~~

これは、次のコードを省略したものです。

~~~ts
private readonly _hud: Hud;

constructor(hud: Hud) {
  this._hud = hud;
}
~~~

private readonlyにより、クラス外から直接読めず、別のHUDへ差し替えることもできません。

## KeyBindingのreadonly

[key-mapping.ts](/Users/pandeaconica/lab/dive-into-tepui/src/game/input/key-mapping.ts)には、キー割り当ての型があります。

~~~ts
export interface KeyBinding {
  readonly code: string;
  readonly altCodes?: readonly string[];
  readonly label: string;
  readonly altLabel?: string;
}
~~~

これは、キー定義を後から書き換えないための型です。

~~~ts
K.fire.code = 'KeyF'; // TypeScriptエラー
~~~

ファイル末尾には次の記述もあります。

~~~ts
} as const satisfies Record<string, KeyBinding>;
~~~

今は次の理解で十分です。

- as const：値を固定されたリテラルとして扱う
- satisfies：KeyBindingの形を満たすか確認する
- どちらも主にTypeScriptのコンパイル時チェックである

# 3. Inputはイベントと状態を分けて持つ

[src/game/input/input.ts](/Users/pandeaconica/lab/dive-into-tepui/src/game/input/input.ts)の役割は、ブラウザのイベントをGameが読みやすい形に変換することです。

Inputは大きく2種類の情報を持ちます。

~~~text
押下中の状態
  keys

一度だけ起きたイベント
  pendingPresses
  pendingClicks
  pendingRightClicks
  マウス移動量・ホイール量
~~~

## 押下中の状態

keydownでは次の処理をします。

~~~ts
this.keys.add(e.code);
~~~

Wを押している間、keysにはKeyWが残ります。
keyupで次の処理が行われます。

~~~ts
this.keys.delete(e.code);
~~~

これが、後でinput.down(K.thrustForward)を判定できる理由です。

## 押した瞬間

同じkeydownの中で、リピートでない場合だけ押下イベントも保存します。

~~~ts
if (!e.repeat) {
  this.pendingPresses.push(e.code);
}
~~~

同じWでも、keysとpendingPressesは別の意味を持ちます。

~~~text
Wを押した瞬間
  keys            にKeyWを追加
  pendingPresses  にKeyWを追加

Wを押し続ける
  keys            にはKeyWが残る
  押下イベント    は何度も追加しない
~~~

その結果、

~~~text
一度だけ反応する操作
押している間ずっと反応する操作
~~~

を区別できます。

## InputがGameへ直接通知しない理由

Inputは入力を集めるだけで、入力の意味は担当側が解釈します。

~~~text
Input
  = KeyWが押されたという事実を保存する

PlayerThrottle
  = KeyWは前方向の推力だと解釈する

CameraSystem
  = ArrowLeftはカメラ旋回だと解釈する
~~~

この分離によって、InputがPlayerやSfxをimportする必要がなくなります。

## onUserGesture

Inputには、ユーザー操作を外側へ知らせる通知口があります。

~~~ts
onUserGesture: (() => void) | null = null;
~~~

Gameでは次のように接続されています。

~~~ts
this.input.onUserGesture = () => this._sfx.unlock();
~~~

Input自身は音声を知りません。
ユーザー操作があったという事実だけを通知し、GameがSfxの処理を接続しています。

# 4. Input.update()を読む

[Input.update()](/Users/pandeaconica/lab/dive-into-tepui/src/game/input/input.ts:418)は、Game.update()の最初に呼ばれます。

~~~ts
this.sections.enter(SECTION.input);
this.input.update();
const dt = Math.min(dtRaw, 0.1);
this.handleInput(dt);
this.sections.exit(SECTION.input);
~~~

## pendingからframeへ移す

Input.update()の中心は次の代入です。

~~~ts
this.framePresses = this.pendingPresses;
this.frameClicks = this.pendingClicks;
this.frameRightClicks = this.pendingRightClicks;
this.frameMouse = {
  dx: this.dx,
  dy: this.dy,
  panDx: this.panDx,
  panDy: this.panDy,
  wheel: this.wheel,
};
~~~

その後、次フレーム用にpending側を空へ戻します。

~~~ts
this.pendingPresses = [];
this.pendingClicks = [];
this.pendingRightClicks = [];
this.dx = 0;
this.dy = 0;
this.panDx = 0;
this.panDy = 0;
this.wheel = 0;
~~~

ここで、入力の受け付けと読み取りを分けています。

~~~text
イベント発生中
  pending側へ記録

Input.update()
  frame側へ確定

Gameの各担当
  frame側を読む・消費する
~~~

Input.update()の後に起きたイベントは、次回のInput.update()までpending側に残ります。
そのため、1フレームの途中で入力キューの意味が変わりません。

## claimedCodes

Input.update()の先頭では、次の処理も行います。

~~~ts
this.claimedCodes.clear();
~~~

claimedCodesは、そのフレーム中にtakeHeld()で確保されたキーを記録します。

~~~text
毎フレーム開始
  前フレームの確保をリセット

処理中
  takeHeld()したキーをclaimedCodesへ登録
~~~

キーの確保は永続的ではなく、フレーム単位です。

# 5. down、takeKey、takeHeld

## down(key)

[down()](/Users/pandeaconica/lab/dive-into-tepui/src/game/input/input.ts:404)は、現在キーが押されているかを返します。

~~~ts
down(key: KeyBinding): boolean {
  return this.isDown(key.code)
    || (key.altCodes?.some((c) => this.isDown(c)) ?? false);
}
~~~

主に、押している間ずっと続く操作に使います。

~~~ts
const keyHeld = input.down(K.fire);
~~~

~~~text
Spaceを押す
  down(Space) = true

Spaceを押し続ける
  毎フレームtrue

Spaceを離す
  false
~~~

## takeKey(key)

[takeKey()](/Users/pandeaconica/lab/dive-into-tepui/src/game/input/input.ts:442)は、今フレームに押下イベントがあれば、それを削除してtrueを返します。

~~~ts
if (input.takeKey(K.warpFaster)) {
  this.shift(1);
}
~~~

一度消費されたイベントは、後の担当から見えません。

~~~text
framePresses = [Period]

SimSpeedManager.handleInput()
  takeKey(Period) → true
  framePressesからPeriodを削除

後のモジュール
  Periodを受け取れない
~~~

## takeKeys(handler)

[takeKeys()](/Users/pandeaconica/lab/dive-into-tepui/src/game/input/input.ts:451)は、未消費のキーを順番にhandlerへ渡します。

~~~ts
input.takeKeys((code) => {
  return this.handleEdgePress(code);
});
~~~

handlerがtrueを返すと、そのキーは消費されます。

~~~text
true
  = この担当が処理した
  = 後の担当には渡さない

false
  = この担当の操作ではない
  = キューに残す
~~~

これはDOMイベントのバブリングではありません。
ブラウザの親子要素へ伝播するのではなく、InputのキューをGameが担当順に読んでいます。

## takeHeld(key)

[takeHeld()](/Users/pandeaconica/lab/dive-into-tepui/src/game/input/input.ts:409)は、押し続けているキーを、この担当がフレーム単位で確保するメソッドです。

~~~ts
if (input.takeHeld(K.dvPrograde)) {
  // WによるΔv編集
}
~~~

takeHeld()がキーを確保すると、そのフレーム中は後続の処理からそのキーが見えなくなります。

~~~text
PlanEditor
  takeHeld(W)
    ↓
  WをΔv編集へ使う

PlayerThrottle
  input.down(W) = false
~~~

これにより、同じWをPlanEditorとPlayerThrottleが同時に使いません。

# 6. Game.handleInput()の順番

[Game.handleInput()](/Users/pandeaconica/lab/dive-into-tepui/src/game/game.ts:326)はprivateメソッドです。Game.update()だけが呼ぶ、Game内部の入力配分用メソッドです。

現在の順番は次の通りです。

~~~text
1. ESC
   ↓
2. OverlayManagerのショートカット
   ↓
3. HUD / HelpPanel
   ↓
4. SimSpeedManager
   ↓
5. ViewManager
   ↓
6. PlanEditor
~~~

## ESCとPauseMenu

~~~ts
if (this.input.takeKey(K.pauseMenu)) {
  if (!this._hud.overlayManager.closeTopmostOnEscape()) {
    this.pauseMenu.toggle(true);
  }
}
~~~

ESCの意味は、Gameが個々のUIを直接判断するのではなく、OverlayManagerに尋ねています。

~~~text
開いているオーバーレイがある
  → 最前面のものを閉じる

何も閉じられない
  → PauseMenuを開く
~~~

PauseMenuとGameの接続はmain.ts側にあります。

~~~ts
pauseMenu.onPauseMenuOpenChange = (open) => {
  if (open) game.pause();
  else game.resume();
};
~~~

main.tsが部品同士を配線している具体例です。

## OverlayManagerのショートカット

~~~ts
this.input.takeKeys((code) =>
  this._hud.overlayManager.dispatchShortcut(code)
);
~~~

開いているUIがショートカットを持つ場合、そのUIへ先に渡します。処理したものがあればtrueを返し、イベントを消費します。

## Hud.handleInput()

現在のHud.handleInput()は、主にHelpPanelへ入力を渡します。

~~~ts
handleInput(input: Input): void {
  this.helpPanel.handleInput(input);
}
~~~

HelpPanelはHを受け取ります。

~~~ts
if (input.takeKey(K.help)) this.toggle();
~~~

Hの分岐は次の通りです。

~~~text
H
  ↓
Game.handleInput
  ↓
Hud.handleInput
  ↓
HelpPanel.handleInput
  ↓
OverlayManagerへhelpを登録
~~~

UIの開閉状態はHelpPanel自身が持ち、UI同士の重なり順やESCの扱いはOverlayManagerが持ちます。

## SimSpeedManager

~~~ts
handleInput(input: Input): void {
  if (input.takeKey(K.warpSlower)) this.shift(-1);
  if (input.takeKey(K.warpFaster)) this.shift(1);
}
~~~

コンマとピリオドは、今フレームに押された瞬間だけ時間加速の段階を変更します。

~~~text
ワープ減速 / ワープ加速
  ↓
SimSpeedManagerの状態を変更
  ↓
次のシミュレーションでsimSpeedを使う
~~~

## ViewManager

~~~ts
if (!input.takeKey(K.toggleMapMode)) return;
~~~

Mが押されると、combatとmapのビューを切り替えます。
ViewManagerはカメラや表示モードを管理し、物体の位置や速度を進めるSimulatorとは別の責務です。

## PlanEditor

~~~ts
if (input.takeKey(K.deleteNode)) this.clearPlanByKey();

if (!this.editMode && input.takeKey(K.autoWarpToNode)) {
  this.simSpeedManager.toggleAutoWarpToFirstNode(...);
}

this.updateEditing(input, dt);
~~~

Xによるノード削除、Nによる自動ワープ、WASDQEによるΔv編集などを処理します。
Δv編集中はtakeHeld()でキーを確保するため、同じWを後段の推力処理へ渡さないことがあります。

# 7. Game.handleInput()の後にPlayerへ進む

Game.handleInput()が終わっても、入力処理がすべて終わったわけではありません。

Game.update()では、ポーズ中でなければ次にadvanceSimulation()を呼びます。

~~~text
Game.update()
  ↓
Game.handleInput()
  ↓
advanceSimulation()
  ↓
EntityManager.updatePlayers()
  ↓
Player.behave()
~~~

[EntityManager.updatePlayers()](/Users/pandeaconica/lab/dive-into-tepui/src/game/simulation/entity-manager.ts:297)は各Playerにbehave()を呼びます。

~~~ts
const operable = simSpeed.canShipAct;
const simDt = dt * simSpeed.simSpeed;

for (const ship of this.players) {
  ship.behave(
    ship === activePlayer && operable ? input : null,
    dt,
    simDt,
    this,
    activeStage,
    ephemeris,
  );
}
~~~

現在操作中のPlayerで操作可能な場合だけInputを渡し、それ以外のPlayerにはnullを渡します。

## Player.behave()

[Player.behave()](/Users/pandeaconica/lab/dive-into-tepui/src/game/player/player.ts:203)の内部は次の順番です。

~~~ts
this.updatePassive(dt);

if (input === null) {
  this.clearTransientCommands();
  return;
}

this.handleEdgeInput(input);
this.updateTorque(input, dt, simDt);
this.fire.updateFireState(...);
this.throttle.updateThrustLatches(input);
this.thrust = this.throttle.updateThrustState(...);
~~~

ここで入力がゲーム内部の状態へ変換されます。

~~~text
Input
  ↓
Player
  ├─ RCS制動、姿勢保持、スロットル
  ├─ PlayerThrottleによる推力・トルク
  └─ PlayerFireによる射撃
~~~

Game.handleInput()はPlayerのすべての操作を代わりに実行しているのではありません。
Playerへ入力を届ける前段の交通整理をしています。

# 8. Wを押したときの完全な流れ

Wを戦闘ビューで押している場合を追います。

## ブラウザイベント

~~~text
keydown: code = "KeyW"
~~~

Inputの中では次の状態になります。

~~~text
keys = { "KeyW" }
pendingPresses = [ "KeyW" ]
~~~

## Input.update()

次のフレームの開始で、次のようになります。

~~~text
keys = { "KeyW" }
framePresses = [ "KeyW" ]
pendingPresses = []
~~~

## Game.handleInput()

ESC、H、ワープ、M、計画編集の処理を順に試します。
通常のWがそれらに消費されなければ、framePressesにはWが残ります。

## Player.behave()

PlayerThrottle.updateThrustLatches()は、ダブルタップによる推力ラッチ判定のためにtakeKey(W)を使います。
その後、推力の計算では別にdown(W)を使います。

~~~text
takeKey(W)
  = このフレームで押した瞬間があったか

down(W)
  = 現在もWを押しているか
~~~

押下イベントを調べた後でも、Wを押している間の推力は続きます。

## 推力の内部状態

PlayerThrottleはWASDQEから機体座標系の推力加速度を作ります。

~~~text
W
  ↓
機体の前方向
  ↓
姿勢Quaternionでワールド方向へ回転
  ↓
thrustAccelVec
  ↓
Simulator.advance()
~~~

ここで初めて、ユーザーのキー入力が物理シミュレーションへ参加します。

# 9. H、ESC、M、ワープ加速の比較

同じキーボード入力でも、状態への影響は異なります。

| 入力 | 最初の担当 | 変わる状態 |
|---|---|---|
| H | HelpPanel | ヘルプオーバーレイの開閉 |
| ESC | Game / OverlayManager | オーバーレイ、PauseMenu、ポーズ状態 |
| M | ViewManager | combat/mapビュー |
| ワープキー | SimSpeedManager | 時間加速段階 |
| W | PlayerThrottle / PlanEditor | 推力または計画Δv |
| Space | PlayerFire | 射撃状態・弾薬・弾エンティティ |

Game.handleInput()は入力と状態の対応表そのものではありません。
入力を各オブジェクトへ配り、各オブジェクトが自分の状態を変更します。

# 10. カメラ入力はどこか

カメラ入力もGame.handleInput()の中で直接処理されるわけではありません。

Game.update()の後半で、CameraSystem.update()へInputが渡されます。

~~~ts
this.cameraSystem.update(
  this.player,
  this.simulator.simTime,
  this.input,
  dt,
  ...,
);
~~~

[CameraSystem.update()](/Users/pandeaconica/lab/dive-into-tepui/src/game/camera/camera-system.ts:155)は次のように入力を読みます。

~~~ts
const keyYaw =
  (input.down(K.cameraYawLeft) ? 1 : 0) +
  (input.down(K.cameraYawRight) ? -1 : 0);

const mouse = { ...input.mouse() };
~~~

~~~text
キーの押下状態 → down()
マウス移動量   → mouse()
~~~

中クリックによるカメラリセットのような一回限りのイベントは、takeMiddleClicks()で消費されます。

# 11. Game.update()の大きな分岐

今回読んだ範囲をGame.update()全体の中に置き直します。

~~~text
main.tsのrAF
  ↓
Game.update(dt)
  ├─ Input.update()
  ├─ Game.handleInput()
  │    ├─ OverlayManager / PauseMenu
  │    ├─ Hud / HelpPanel
  │    ├─ SimSpeedManager
  │    ├─ ViewManager
  │    └─ PlanEditor
  │
  ├─ ポーズ中でなければadvanceSimulation()
  │    ├─ EntityManager.updatePlayers()
  │    │    └─ Player.behave()
  │    │         ├─ PlayerThrottle
  │    │         └─ PlayerFire
  │    ├─ Stage.update()
  │    ├─ Simulator.advance()
  │    ├─ Predictor.update()
  │    └─ EffectsSystem.update()
  │
  ├─ 計画表示・環境更新
  ├─ CameraSystem.update()
  └─ ポインタ入力処理
~~~

# 12. 今回のまとめ

## Input.update()

ブラウザイベントを、現在フレームのスナップショットへ確定します。

~~~text
pending → frame
~~~

## down()

押下中の状態を読みます。
推力、姿勢、射撃、カメラなどに使います。

## takeKey()

押した瞬間のイベントを一度だけ消費します。
トグル、モード変更、ワープ、UI開閉などに使います。

## takeHeld()

押し続けている入力を、担当がフレーム単位で確保します。
計画編集と通常操作の優先順位を作るために使います。

## Game.handleInput()

入力の意味をすべて実装する場所ではなく、担当モジュールへ先着順に配る場所です。

## Player.behave()

Inputを自機の推力・姿勢・射撃の状態へ変換する場所です。

# 読解課題

次の3つをコードを見ながら説明してみてください。

1. Spaceを押し続ける操作にtakeKey()ではなくdown()が使われる理由は何か。
2. Input.update()でpendingPressesを空にする理由は何か。
3. Game.handleInput()でMを消費した後、MがPlayerへ届かないのはなぜか。

答えは次の通りです。

1. 射撃は押している間、毎フレーム判定する必要があるから。
2. 次フレームの入力と今フレームの入力を混ぜないため。
3. takeKey()がイベントをframePressesから削除するから。

次回は、Player.behave()からPlayerThrottle、PlayerFireへ進み、入力が具体的なゲーム内部状態へ変わるところを読みます。
