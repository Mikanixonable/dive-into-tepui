# 第1講：このゲームを読むための地図――現在のコードベース版

このゲームは、低軌道を舞台にしたシューティングゲームです。
ただし、最初から軌道力学やThree.jsの詳細を読む必要はありません。

まずは、ゲームがどのように起動し、誰が全体を動かし、毎フレームどんな順で処理するのかを掴みます。

~~~text
ブラウザ
  ↓
src/main.ts
  ↓
起動用の部品を準備
  ↓
起動するStageClassを決定
  ↓
Gameを作る
  ↓
requestAnimationFrame
  ↓
毎フレーム:
  Game.update()
  SnapshotControls / AutoSave
  Game.sync()
  Game.render()
~~~

今回の目標は、全ファイルを読むことではありません。

1. このゲームの大きな部品は何か
2. 起動時に何が作られ、どこへ渡されるか
3. 毎フレーム、内部状態と画面表示がどう更新されるか

この3つを理解します。

# 2. エントリーポイントはどこか

Webpackの設定には、次の指定があります。

~~~js
entry: './src/main.ts'
~~~

Webpackがブラウザ向けのJavaScriptを作るときの入口はsrc/main.tsです。

ブラウザが最初に読むHTMLはpublic/index.htmlです。
ただし、ゲーム本体の処理をHTMLへ直接書いているわけではありません。

~~~text
public/index.html
  ↓
Webpackが生成したJavaScript
  ↓
src/main.tsと、そのimport先が実行される
~~~

main.tsを読むとき、ファイルの上から下へすべての関数が自動実行されるわけではないことに注意してください。

~~~ts
function greet() {
  console.log('こんにちは');
}
~~~

この関数は、定義されただけでは何も表示しません。

~~~ts
greet();
~~~

と呼ばれて初めて実行されます。

したがって、関数定義を見つけたら、

~~~text
これはどこから呼ばれるか？
起動時に一度だけか？
毎フレームか？
~~~

を確認します。

main.tsのファイル末尾にある次の呼び出しが、起動処理の入口です。

~~~ts
main().catch((err) => {
  ...
});
~~~

ここからmain()の中へ入り、呼び出される関数を追いかけます。

# 3. main.tsの役割

main.tsは、敵AIや軌道計算を実装する場所ではありません。

主な役割は次の通りです。

~~~text
1. セーブ関連を準備する
2. CanvasとWebGPUを準備する
~~~

つまりmain.tsは、

~~~text

~~~

です。

ゲーム内部の指揮はGameが担当します。
ただし、Gameが使う部品の一部はmain.tsが先に作って渡します。

# 5. 先に理解しておきたい前提知識

## TypeScriptの型

このゲームはTypeScriptで書かれています。

~~~ts
function add(a: number, b: number): number {
  return a + b;
}
~~~

numberは型です。

~~~ts
const player: Player | null
~~~

は、

~~~text
playerにはPlayerまたはnullが入る
~~~

という意味です。

このコードベースでは、nullがゲームの状態を表すことがあります。

~~~text
player === null
  = 現在操作できる艦がない

activeStage.isPlaying === false
  = ステージが決着済み
~~~

nullは必ずしもバグによる空っぽではありません。

---

## classとinstance

~~~ts
const game = new Game(...);
~~~

は、Gameというクラスから実際のGameインスタンスを作る処理です。

クラスを設計図、インスタンスを実物と考えるとよいでしょう。

このゲームでは、Game、Player、Enemy、Stage、Simulator、CameraSystemなどがインスタンスです。

ただし、newしたからすぐ動き始めるとは限りません。

Gameをnewしても、毎フレーム処理は始まりません。
後でstartAnimationLoop()が呼ばれて初めて、継続的に動きます。

---

## 継承

ゲーム内エンティティには、次のような継承があります。

~~~text
DynamicEntity
  └─ Ship
       ├─ Player
       └─ Enemy
~~~

~~~ts
class Player extends Ship
~~~

は、

~~~text
PlayerはShipの一種である
~~~

という意味です。

DynamicEntityは、軌道上の物体に共通する位置、速度、姿勢、メッシュ、生死などを持ちます。

Shipは、DynamicEntityに加えて、名前、HP、質量、パーツなどを持ちます。

PlayerはShipに加えて、スロットル、射撃、弾薬ベルト、熱、電力、軌道計画などを持ちます。

EnemyはShipに加えて、敵AIや敵固有の射撃状態などを持ちます。

---

## コンポジション

Playerは継承だけでできているわけではありません。

~~~text
Player
  ├─ PlayerThrottle
  ├─ PlayerFire
  ├─ Belt
  ├─ ThermalSystem
  ├─ RadiatorSystem
  ├─ PowerSystem
  ├─ PlanExecutor
  └─ 各種エフェクト
~~~

これは、

~~~text
Playerは、これらの部品を組み合わせてできている
~~~

という構造です。

この考え方をコンポジションと呼びます。

~~~text
継承:
PlayerはShipである

コンポジション:
PlayerはPlayerFireとPlayerThrottleを持っている
~~~

## オブジェクト参照

JavaScriptやTypeScriptのオブジェクトは、値のコピーではなく参照として渡されることがあります。

~~~ts
const player = new Player(...);
const controller = new ActivePlayerController(player, ...);
~~~

このとき、controllerが持つPlayerと、元のplayerは同じPlayerインスタンスです。

現在の構造を概念的に描くと次のようになります。

~~~text
DynamicSystem.players ─────┐
ActivePlayerController ────┤
CameraSystem ──────────────┤
PlanEditor ────────────────┘
                 ↓
             同じPlayer
~~~

C言語の生ポインタではありません。
ただし、

~~~text
複数のオブジェクトが同じ実物を指している
~~~

という感覚で読むと理解しやすくなります。

## DynamicSystemが自機を準備する

GameはPlayerを直接newしていません。

~~~ts
this.entities = new DynamicSystem(
  ...,
  initialSave ? { saved: initialSave } : { playerCount: stageClass.initialPlayerCount },
);
~~~

ここで、

- 保存データがあればPlayer群や敵などを復元する
- 保存データがなければStageClassの初期自機数で新規Player群を作る

という分岐になります。

その後、

~~~ts
const initialPlayer = this.entities.initialActivePlayer;
~~~

で最初に操作するPlayerを取得します。

CameraSystemやPlanEditorは、このPlayerを必要とするため、DynamicSystemの後に作られます。

## ActivePlayerControllerが操作対象を束ねる

複数のPlayerが世界に存在できるため、

~~~text
世界に存在するPlayer
現在操作するPlayer
~~~

を分けています。

ActivePlayerControllerは、操作対象の切り替えを一か所に集めています。

操作対象が変わると、カメラ、PlanEditor、Targeterなどの対象も更新されます。

操作対象の喪失時は、生存している別艦へ引き継ぐか、操作対象をnullへ戻します。

# 9. 現在のUI・ビュー状態

## ViewManager

現在のビュー型は次の通りです。

~~~ts
type ViewId = 'combat' | 'map' | 'dock';
~~~

ただし、内部では単純にcurrentという1個の値だけを持っているわけではありません。

~~~text
worldView: combat または map
isDockOpen: true または false
~~~

currentは次のように計算されます。

~~~text
isDockOpenがtrue
  → dock

それ以外
  → worldView
~~~

dockはcombat/mapの上に重なるUIです。

~~~text
combat + dock open
  → currentはdock
  → 背後のworldViewはcombat

map + dock open
  → currentはdock
  → 背後のworldViewはmap
~~~

dockを閉じると、閉じる前のworldViewへ戻ります。

setView()がビュー遷移の中心です。

- 同じビューならapplyChromeだけ再実行する
- mapから出るとPlanEditorの後始末とMapPickerのcloseを行う
- mapへ入ると選択ノードを整える
- HUDのclassを切り替える
- CameraSystemとPlanEditorへmap modeを伝える
- DisplayWindowManagerのforceCurrentを切り替える
- dockへ入る条件はDockingが判断する
- combatへ入る条件は操作対象Playerが存在すること

Mキーの経路は次の通りです。

~~~text
Input
  ↓
Game.handleInput()
  ↓
ViewManager.handleInput()
  ↓
ViewManager.setView()
  ↓
applyChrome()
~~~

main.tsのstartAnimationLoop()は、現在次の順に処理します。

# 11. dtとゲーム内時間

animateは、前回のフレームからの経過時間を計算します。

~~~ts
const dt = (now - lastTime) / 1000;
~~~

requestAnimationFrameのnowはミリ秒なので、1000で割って秒に変換します。

例えば、

~~~text
前回: 1000.0 ms
今回: 1016.7 ms
差分: 16.7 ms
dt:   0.0167 秒
~~~

dtは、今回のフレームで現実時間として何秒ぶん進んだかです。

Game.update()では次のように上限を設けています。

~~~ts
const dt = Math.min(dtRaw, 0.1);
~~~

ブラウザがバックグラウンドになったあとに大きなdtが来ても、物理計算へそのまま渡さないためです。

時間加速は、dtを書き換えるのではなく、SimSpeedManagerの倍率からsimDtを作ります。

~~~text
dt
  = 現実のフレーム間隔

simSpeed
  = ゲーム内時間の倍率

simDt
  = dt × simSpeed
~~~

この違いは、次にSimulatorを読むときに重要です。

# 12. update、sync、renderの意味

## update

~~~ts
game.update(dt);
~~~

ここでは、

- 入力をフレーム単位へ確定する
- EscやMなどの入力を担当システムへ配る
- Playerに操作指令を作らせる
- Stageのルールを進める
- Simulatorで軌道・姿勢・接触を進める
- 敵や弾を更新する
- 未来軌道を予測する
- マップ候補やカメラ内部状態を更新する

などを行います。

この段階でゲームの内部状態が変わります。

## sync

~~~ts
game.sync();
~~~

updateで変更された内部状態を、DOMやThree.jsの表示用オブジェクトへ写します。

~~~text
Playerの物理状態
  player.state.r
  ↓ sync
Three.jsのObject3D
  player.obj.position
~~~

HP、軌道線、敵マーカー、ナビボール、カメラ、未来表示もsyncの対象です。

## render

~~~ts
game.render();
~~~

最終的に、SceneとactiveCameraをレンダラーへ渡します。

~~~ts
this.renderer.render(this._scene, this.cameraSystem.activeCamera);
~~~

dock viewではGame.render()がreturnします。
ドックは不透明なDOM画面なので、3D Sceneを描く必要がないためです。

まとめると、

~~~text
update
  = 世界の状態を計算する

sync
  = 計算された状態を見た目へ反映する

render
  = 反映済みの見た目を画面へ描く
~~~

~~~text
FrameSectionsの入力区間へ入る
  ↓

  ↓

  ↓
Game.handleInput()
  ↓
入力区間を出る
  ↓
ポーズ中でなければadvanceSimulation(dt)
  ↓
DisplayWindowManager.resolve()
  ↓
updateMapPresentation(dt)
  ↓
マップまたは戦闘のポインタ入力
~~~

ポーズ中もhandleInput()は先に呼ばれます。
そのため、Esc、ヘルプ、設定などを処理できます。

ポーズ中はadvanceSimulation()を呼びません。
シミュレーション時計や物理状態は進みませんが、表示とカメラは更新されます。

Stageが決着済みでもGame.update()自体は継続します。
決着後のカメラ、演出、表示を維持する必要があるためです。

# 14. advanceSimulation()の現在の順番

通常プレイ時のゲーム世界の更新は、advanceSimulation()にまとまっています。

~~~text
1. 操作対象Playerを処理
2. Stageを処理
3. 時間加速の状態を更新
4. Simulatorで物理を進める
5. 表示窓を確定する
6. 数値異常を確認する
7. ターゲット情報を更新する
8. 死んだ操作艦を回収・引き継ぎする
9. ドッキング判定をする
10. 未来軌道を予測する
11. エフェクトを更新する
12. 軌道計画とガイドを更新する
~~~

## Player

Stageがplayingで、操作対象Playerが存在するとplayer.behave()が呼ばれます。

Player.behave()は、入力から推力、トルク、射撃などの指令を作ります。

~~~text
WASDQE
  ↓
PlayerThrottle
  ↓
Player.thrust

姿勢キー
  ↓
PlayerThrottle
  ↓
Player.torque

射撃キー
  ↓
PlayerFire
  ↓
弾の生成など
~~~

入力が位置を直接変えるわけではありません。
実際の軌道・姿勢の更新は、この後のSimulatorが行います。

## Stage

Stage.update()では、

- 敵AI
- 敵の出現
- 補給
- タイマー
- 勝敗条件
- ステージ固有のUI

などを処理します。

Stageは自機の操作ではなく、ミッションのルールを担当します。

## Simulator

SimSpeedManagerの倍率からゲーム内時間simDtを作り、Simulator.advance()へ渡します。

まずは次の順番だけを覚えます。

~~~text
Playerが指令を作る
  ↓
Stageがルールを進める
  ↓
Simulatorが世界の物理を進める
~~~

# 15. 表示窓、マップ、カメラ

物理更新の後、表示用の計画・候補・カメラ内部状態を更新します。

updateMapPresentation()の概略は次の通りです。

~~~text
EnvironmentScene.update()
  ↓
PlanEditor.update()
  ↓
Targeter.updateEquatorNodes()
  ↓
DynamicSystem.updateBaseEquatorNodes()
  ↓
MapPicker.refresh()
  ↓
CameraSystem.update()
~~~

DisplayWindowManagerは、単なる未来時刻スライダーではありません。

~~~text
frame
  = どの座標系で見るか

simTime
  = シミュレーションの現在時刻

referencePeriod
  = 軌道表示の基準周期

duration
  = 未来表示する長さ

displayTime
  = 実際に表示する時刻
~~~

マップの未来スライダーが動くと、現在の物理状態ではなく、表示する未来時刻が変わります。

そのため、

~~~text
シミュレーションの現在
  と
画面に表示している未来
~~~

を区別します。

# 17. 内部状態の地図

このゲームの状態は、Gameに全部入っているわけではありません。

| 状態 | 主な所有者 |
|---|---|
| 現在のシミュレーション時刻 | Simulator.simTime |
| ゲームの勝敗 | Stage.phase |
| 世界に存在する艦・弾・敵 | DynamicSystem |
| 現在操作する艦 | ActivePlayerController.current |
| 一時停止 | Game.isPaused |
| combat/map/dock | ViewManager |
| 開いているHUDモーダル | ModalController |
| 現在押されているキー | Input.keys |
| 今フレームの押下エッジ | Input.framePresses |
| 表示する未来時刻 | DisplayWindowManager.current |
| マニューバ計画 | Player.plan / PlanEditor |
| ワープ倍率 | SimSpeedManager |
| ターゲット | Targeter / NavTarget |
| カメラ角度・距離 | CameraSystem |
| セーブスロット | SaveSlots |
| スナップショットの内容 | SnapshotService / SaveStore |

この表から分かることは、

~~~text
Gameは状態を一つに集める箱ではない
複数の状態所有者を束ねる司令塔である
~~~

ということです。

# 18. ユーザー操作が画面へ届くまで

ユーザーがキーを押してから画面が変わるまでを、最も大きく見ると次の通りです。

~~~text
キーボード / マウス / タッチ
  ↓
Inputのブラウザイベントリスナー
  ↓
pendingPresses / pendingClicks / keys
  ↓ 次のフレーム
Input.update()
  ↓
framePresses / frameClicks / frameMouse
  ↓
Game.handleInput()
  ↓
View / Hud / Stage / Editor / Player
  ↓
内部状態が変わる
  ↓
Game.sync()
  ↓
HUD / Three.js / マーカーへ反映
  ↓
Game.render()
  ↓
画面に見える
~~~

入力処理やPlayerの詳細は次の講義で扱います。
今回覚えるのは、ユーザーのイベントが直接画面を変えるのではなく、

~~~text
イベント
  → Input
  → 担当システム
  → 内部状態
  → sync
  → render
~~~

という経路を通ることです。

# 19. これからの講義の順番

次の順で読むと、巨大なコードベースを少しずつ理解できます。

## 第1段階：入口

~~~text
main.ts
  起動とフレームループ
~~~

今回扱った範囲です。

## 第2段階：入力

~~~text
Input.update()
  ↓
Game.handleInput()
~~~

ブラウザイベントが1フレーム入力になるまでを読みます。

## 第3段階：自機操作

~~~text
Player.behave()
  ↓
PlayerThrottle / PlayerFire
~~~

WASDQE、姿勢操作、射撃、マップモード、時間加速による制限を読みます。

## 第4段階：物理

~~~text
Simulator.advance()
  ↓
DynamicEntity.stepActual()
  ↓
軌道・接触・姿勢・環境
~~~

ここで初めて、軌道力学の細部へ進みます。

## 第5段階：表示

~~~text
Game.sync()
  ↓
DynamicSystem.sync()
  ↓
HUD / マーカー / Three.js
~~~

内部状態が画面へ出る仕組みを読みます。

## 第6段階：UI状態

~~~text
ViewManager
ModalController
Stage.phase
SaveBrowser
ResultScreen
~~~

combat/map/dock、設定、ヘルプ、セーブ一覧、勝敗画面の状態遷移を読みます。

## 第7段階：継承とコンポジション

~~~text
DynamicEntity
  └─ Ship
       ├─ Player
       └─ Enemy

Player
  ├─ PlayerThrottle
  ├─ PlayerFire
  ├─ ThermalSystem
  └─ その他の部品
~~~

ここで、モデル、継承、コンポーネントという考えを、実際のコードの関係として整理します。

# 今日の要点

~~~text
1. Webpackのエントリーはsrc/main.tsである
2. main.tsはゲームルールではなく、部品の生成・配線・ループ開始を担当する
3. 現在のStageはStageClassの設定とStageインスタンスの状態に分かれている
4. Player群はDynamicSystemが持ち、現在操作するPlayerはActivePlayerControllerが持つ
5. 毎フレームは、update → 周辺処理 → sync → renderの順で進む
6. 内部状態の所有者はGame一つではなく、複数のシステムへ分かれている
~~~

特に、次の図を覚えてください。

~~~text
main.ts
  ↓ 起動時に部品を組み立てる
Game
  ↓ 毎フレーム指揮する
Input → Player / Stage → Simulator
  ↓
内部状態
  ↓
sync
  ↓
HUD / Three.js / マーカー
  ↓
render
  ↓
画面
~~~

次回は、Game.update()の先頭にあるInput.update()から始めて、
キーボード、マウス、タッチのイベントがどのように今フレームのゲーム入力へ変換されるかを読みます。
