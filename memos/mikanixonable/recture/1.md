
# 1. このコードベースの大分類

このゲームは、おおまかに次の4層に分かれています。

```text
main.ts
  └─ Game
       ├─ 入力
       ├─ ゲームルール
       ├─ シミュレーション
       ├─ エンティティ
       ├─ カメラ
       ├─ HUD
       └─ 描画
```

役割で分けると、次のようになります。

| 役割 | 主なファイル |
|---|---|
| 起動・全体配線 | `main.ts` |
| ゲーム全体の指揮 | `game.ts` |
| キーボード・マウス | `input/input.ts` |
| 自機の操作・射撃 | `player/player.ts` |
| 敵・自機・弾の集合管理 | `simulation/entity-manager.ts` |
| 軌道・衝突・姿勢の更新 | `simulation/simulator.ts` |
| ステージルール | `stages/stage.ts`, `stage1.ts` など |
| 戦闘/マップ/ドック切替 | `view-manager.ts` |
| DOM UI | `hud/` |
| Three.jsの世界 | `render/`, 各エンティティの `obj` |

重要なのは、`Game` がすべてを自分で実装しているわけではないことです。

`Game` は「指揮者」です。

実際の仕事は、`Player`、`Simulator`、`Stage`、`CameraSystem` などへ委譲しています。

# 2. 先に理解しておきたい前提知識

## TypeScript

このプロジェクトはJavaScriptではなくTypeScriptです。

例えば、

```ts
function add(a: number, b: number): number {
  return a + b;
}
```

この `: number` は型注釈です。

```ts
const player: Player | null
```

は、

```text
player には Player または null が入る
```

という意味です。

このプロジェクトで頻出する記法は次の通りです。

```ts
readonly player
```

一度代入した変数そのものは差し替えない。

```ts
private input
```

そのクラスの外側から直接触らせない。

```ts
player?.pause()
```

`player` が `null` や `undefined` でなければ `pause()` を呼ぶ。

```ts
a ?? b
```

`a` が `null` または `undefined` なら `b` を使う。

```ts
type GamePhase = 'playing' | 'won' | 'lost'
```

文字列を自由に使わず、指定された値のどれかだけに制限する。

---

## クラスとインスタンス

```ts
const game = new Game(...)
```

これは `Game` クラスから、実際に動くGameオブジェクトを1つ作っています。

クラスは設計図、インスタンスは実物です。

```ts
class Player {
  hp = 100;

  damage(amount: number) {
    this.hp -= amount;
  }
}

const player = new Player();
player.damage(20);
```

この場合、`player.hp` は80になります。

このゲームでは、`Game`、`Player`、`Simulator`、`Stage`、`Hud` などがそれぞれインスタンスです。

---

## 継承

このゲームには次のような継承があります。

```text
GameEntity
  └─ Ship
       ├─ Player
       └─ Enemy
```

つまり、

```ts
class Player extends Ship
```

は、

```text
Player は Ship の一種である
```

という意味です。

`Ship` は名前、HP、質量、パーツなどを持ちます。

`Player` はそれに加えて、スロットル、射撃、弾薬、放熱板などを持ちます。

ただし、このゲームを読むときは継承よりも、まず「何を持っているか」を見る方が重要です。

たとえば `Player` は次のものを持っています。

```text
Player
  ├─ PlayerThrottle
  ├─ PlayerFire
  ├─ Belt
  ├─ ThermalSystem
  ├─ RadiatorSystem
  ├─ PowerSystem
  └─ PlanExecutor
```

これは「Playerがこれらの部品を持っている」という構成です。

このような構成を、継承に対して「コンポジション」と考えます。

このゲームは、継承よりもコンポジションをかなり多く使っています。

---

## オブジェクト参照

JavaScriptのオブジェクトは、値のコピーではなく参照として渡されることが多いです。

```ts
const player = new Player();
game.player = player;
```

この場合、`game.player` と `player` は同じPlayerを指しています。

そのため、

```ts
game.player.hp -= 10;
```

とすると、元の `player.hp` も変わります。

このゲームでは、`Game` が `Player` への参照を持ち、`CameraSystem` や `PlanEditor` も同じPlayerを参照しています。

```text
Game
 ├─ player ─────┐
 ├─ CameraSystem ┤
 └─ PlanEditor ──┘
                 ↓
              同じ Player
```

ここが「ポインタに近い感覚」で理解すべき部分です。

ただし、JavaScriptにはC言語のような生のポインタ演算はありません。あくまでオブジェクトへの参照です。

---

## コールバック

次のようなコードがあります。

```ts
settingsPanel.onSettingsOpenChange = (open) => {
  if (open) game.pause();
  else game.resume();
};
```

これは、

```text
設定画面が開いたとき、後でこの関数を呼んでください
```

という登録です。

設定画面自身は、ゲームを直接停止しません。

設定画面は、

```ts
this.onSettingsOpenChange?.(show);
```

を呼びます。

すると、`main.ts` で登録した関数が実行されます。

このような仕組みはイベント駆動と呼ばれます。

# 4. main.tsの起動処理

`main.ts` の最後に、次があります。

```ts
main().catch((err) => {
  ...
});
```

`main()` は非同期関数です。

つまり、起動時に時間のかかる処理を待ちながら、順番に初期化します。

大まかな流れはこれです。

```text
main()
  ↓
セーブデータ準備
  ↓
Three.js / WebGPU準備
  ↓
HUD・音声・設定画面準備
  ↓
起動するステージを決定
  ↓
天体暦を読み込み
  ↓
Gameを生成
  ↓
セーブデータを復元
  ↓
セーブブラウザを接続
  ↓
毎フレーム処理を開始
```

## セーブデータ準備

```ts
const unlockmanager = new UnlockManager();
const saveStore = new LocalStorageSaveStore();
const slots = initSaveSlots(saveStore);
```

ここでは、

- ステージ解放情報
- `localStorage` の保存場所
- セーブスロット

を準備しています。

この段階ではまだゲーム世界は動いていません。

---

## Three.js / WebGPU準備

```ts
const gs = await initScene();
```

`initScene()` は、まずローディング画面を表示します。

その後、

```ts
const canvas = document.createElement('canvas');
document.body.appendChild(canvas);
```

で描画用のCanvasを作ります。

さらに、

```ts
const gs = await createGameScene(canvas);
```

でThree.jsのシーンとWebGPUレンダラーを初期化します。

ここで重要なのは `await` です。

WebGPUの初期化が終わるまで、次の処理へ進みません。

---

## 起動先の決定

```ts
const launch = await resolveLaunchSelection(unlockmanager, slots);
```

ここで、

- ステージモード
- クリエイティブモード
- 前回のセーブを再開
- ステージ選択画面を表示

のどれにするか決まります。

URLパラメータも見ています。

```text
?title=1
?mode=creative
?stage=1
```

`selectLaunch()` は、画面上のボタンが押されるまで結果を返せません。

そのため、次のようなイメージです。

```text
resolveLaunchSelection()
  ↓
選択画面を表示
  ↓
ユーザーがクリック
  ↓
Promiseを解決
  ↓
main()のawaitから続きが実行される
```

ここで「関数が途中で止まり、後から再開する」という非同期処理の感覚を身につけると、Webアプリのコードが読みやすくなります。

これは依存性注入と呼ばれる形です。

# 6. 毎フレームの処理

[main.ts](/Users/pandeaconica/lab/dive-into-tepui/src/main.ts:143) に、ゲームループがあります。

```ts
function animate(now: number) {
  const dt = (now - lastTime) / 1000;

```

ゲームでは、この処理を何度も繰り返します。

```text
update
  ↓

  ↓
render
  ↓

```

この3つを混ぜないことが、コードを読むときの最大のポイントです。

## update：ゲーム世界を進める

[Game.update](/Users/pandeaconica/lab/dive-into-tepui/src/game/game.ts:409) は、ゲームの論理を進めます。

```ts
this.input.update();
const dt = Math.min(dtRaw, 0.1);
this.handleInput();
```

最初に入力を確定します。

`dt` は前のフレームから経過した秒数です。

例えば60FPSなら、およそ、

```text
dt = 0.016秒
```

です。

### Inputの仕組み

ブラウザのキーボードイベントは、フレームとは別のタイミングで発生します。

そのため `Input` はイベントをいったんキューに入れます。

```text
ブラウザイベント
  ↓
pendingPressesへ保存
  ↓
Input.update()
  ↓
今フレームの入力として確定
```

入力には2種類あります。

```ts
input.down(K.thrustForward)
```

これは「現在押し続けているか」。

```ts
input.takeKey(K.pauseMenu)
```

これは「今フレームに押された瞬間があるか」。

この区別は非常に重要です。

Wキーのように押している間ずっと効く操作は `down()`。

Escのように一度だけ実行する操作は `takeKey()` です。

---

## handleInput：UI操作を振り分ける

`Game.handleInput()` では、入力を各担当者へ渡します。

```ts
this.docking.handleInput(this.input);
this.settingsPanel.handleInput(this.input);
this._hud.handleInput(this.input);
this.activeStage.handleInput(this.input);
this.simSpeedManager.handleInput(...);
this.viewManager.handleInput(...);
this.editor.handleInput(this.input);
```

上から順番に処理されます。

同じキーを複数の機能が使える可能性があるため、処理したモジュールが入力を消費します。

例えばEscは、

```text
ドックを閉じる
  ↓
セーブブラウザを閉じる
  ↓
設定画面を開閉する
```

のように、優先順位があります。

---

## 通常プレイ時のupdate

通常のゲームプレイでは、概ね次の順です。

```text
Player.behave()
  ↓
Stage.update()
  ↓
Simulator.advance()
  ↓
Predictor.update()
  ↓
Effects.update()
  ↓
マップ・カメラ・ターゲット更新
```

### Player.behave

`Player.behave()` は、

- RCS入力
- 姿勢トルク
- スロットル
- 射撃
- リロード
- 弾薬
- 放熱板
- 電力
- 自動操縦

などを処理します。

ここで重要なのは、入力した瞬間に位置を直接変更していないことです。

Playerはまず、

```ts
this.thrust = ...
this.torque = ...
```

という「物理への指令」を設定します。

その後、`Simulator` がその指令を使って位置や速度を更新します。

---

### Stage.update

ステージはゲームルールを担当します。

例えば、

- 敵AIを動かす
- 敵を出現させる
- 弾薬を補給する
- タイムアップを判定する
- 敵撃破数を確認する

といった処理です。

つまり、

```text
Player = 自機の操作
Stage = ミッションのルール
```

です。

---

### Simulator.advance

`Simulator` が物理世界を進めます。

ここで、

- 重力
- 軌道
- 推力
- 姿勢
- 衝突
- 弾の移動
- 大気抵抗
- 熱や電力

などが計算されます。

時間加速中は、

```ts
const simDt = dt * this.simSpeedManager.simSpeed;
```

のように、現実の経過時間 `dt` より大きなシミュレーション時間を進めます。

```text
現実時間: 0.016秒
ゲーム内時間: 0.016 × ワープ倍率
```

# 7. update内の状態分岐

`Game.update()` は常に同じ処理をするわけではありません。

主な分岐は次の通りです。

```text
ポーズ中
  ↓
自機なし
  ↓
ステージ決着後
  ↓
通常プレイ
```

## ポーズ中

```ts
if (this._isPaused) {
  ...
  return;
}
```

物理シミュレーションは止まります。

ただし、カメラ操作や一部のマップ表示は動きます。

---

## 自機がnull

```ts
if (this.player === null) {
  ...
  return;
}
```

主にクリエイティブモードの「まだ艦を配置していない状態」です。

この状態でも、残骸や弾の時間は進みます。

---

## ステージ決着後

```ts
if (!this.activeStage.isPlaying) {
  ...
  return;
}
```

`Stage` の状態が `won`、`lost`、`timeup` のいずれかになった状態です。

この後は自機の操作を止めますが、爆発エフェクトやカメラなどは更新します。

---

## 通常プレイ

自機が存在し、ステージが `playing` のときだけ、通常の操作・敵AI・物理計算を行います。

# 8. sync：内部状態を表示へ反映する

`update()` がゲーム世界を変更したあと、`sync()` が表示を更新します。

[Game.sync](/Users/pandeaconica/lab/dive-into-tepui/src/game/game.ts:704) では、

- カメラ
- Earthや天体
- 自機メッシュ
- 敵メッシュ
- 弾
- 軌道線
- HUD
- マーカー
- ナビボール
- 軌道計画

などを現在の内部状態に合わせます。

ここで大切なのは、

```text
内部状態
  ↓ sync
Three.jsのObject3DやDOM
```

という方向です。

例えば自機の物理位置は、

```ts
player.state.r
```

にあります。

しかし、Three.jsの画面に出る位置は、

```ts
player.obj.position
```

です。

`syncPlayer()` が、この2つを対応させます。

# 10. このゲームの主な状態

このゲームには、状態がひとつの変数にまとまっているわけではありません。

複数のクラスに分散しています。

## ステージ状態

`Stage` が持ちます。

```ts
type GamePhase = 'playing' | 'won' | 'lost' | 'timeup';
```

## 自機状態

`Game.player` と `Player.alive` は別物です。

```text
game.player === null
```

操作対象の艦が存在しない。

```text
game.player.alive === false
```

艦のオブジェクトは存在するが破壊されている。

## 画面状態

`ViewManager.current` が持ちます。

```ts
type ViewId = 'combat' | 'map' | 'dock';
```

## 一時停止状態

`Game._isPaused` が持ちます。

## モーダル状態

`ModalController` が持ちます。

```text
help
settings
save-browser
```

## シミュレーション状態

`Simulator` が持ちます。

```text
simTime
lastSimDt
lastSubsteps
```

このように、このゲームのUI状態はひとつの巨大な状態機械ではなく、複数の小さな状態機械が協調しています。

# 今日の読解ポイント

このコードベースを読むときは、各クラスについて次の5つを確認してください。

```text
1. このクラスは何を所有しているか
2. どのクラスから呼ばれるか
3. どんな状態を変更するか
4. 毎フレーム呼ばれるメソッドは何か
5. DOMやThree.jsへ反映する場所はどこか
```

今回の最重要結論はこれです。

```text
main.ts
  └─ Game.update()
       ├─ 入力を読む
       ├─ Player/Stageへ指令を作らせる
       ├─ Simulatorで世界を進める
       └─ カメラや計画を更新

  └─ Game.sync()
       └─ 内部状態をHUD・Three.jsへ反映

  └─ Game.render()
       └─ 画面へ描画
```

次はこの幹から枝として、`Input → Game.handleInput → Player.behave` の順に、実際にWASDQEや射撃キーがどのように自機へ届くかを読むのが最適です。
