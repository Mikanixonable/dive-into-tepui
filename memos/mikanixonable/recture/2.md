# 第2講：main.tsを読む――起動とフレームループ

第1講では、このゲームを読むための大きな地図を作りました。
今回は、その地図の入口である [src/main.ts](/Users/pandeaconica/lab/dive-into-tepui/src/main.ts) を、上から下へ読んでいきます。

今回の目標は、細かいゲーム処理を理解することではありません。

~~~text
ブラウザがページを開く
  ↓
main.ts が読み込まれる
  ↓
ゲームを動かすための部品を準備する
  ↓
Game を作る
  ↓
requestAnimationFrame で毎フレーム処理する
~~~

この順番が頭に入ると、次回から Game の中身を読んだときに、
「これは起動時に1回だけ呼ばれるのか」「毎フレーム呼ばれるのか」を区別できるようになります。

---

# 1. main.tsは何をするファイルか

main.tsは、ゲームのルールを実装するファイルではありません。

このファイルの役割は、主に次の4つです。

~~~text
1. 起動時に必要なオブジェクトを作る
2. それらをGameに渡して接続する
3. 毎フレームGameを呼ぶ
4. 初期化失敗・実行中の例外を画面に表示する
~~~

言い換えると、main.tsはゲームの「組み立て」と「運転開始」を担当しています。

敵がどう動くか、弾がどう飛ぶか、軌道がどう計算されるかはmain.tsの仕事ではありません。
それらはGameやStage、Simulatorへ渡されます。

~~~text
main.ts   = 工場の組み立て担当 + エンジンを始動する担当
Game      = ゲーム全体の指揮者
Player    = 自機の担当
Stage     = ミッションの担当
Simulator = 物理世界の担当
~~~

# 2. ファイルが読み込まれると何が起きるか

Webpackの設定には、次の指定があります。

~~~js
entry: './src/main.ts'
~~~

ブラウザ向けのJavaScriptを作るとき、Webpackはここを入口にします。

ブラウザが最初に読むHTMLは [public/index.html](/Users/pandeaconica/lab/dive-into-tepui/public/index.html) ですが、
HTMLの中にゲーム本体を直接書いているわけではありません。
Webpackがmain.tsと、そのファイルから辿れるimport先をまとめて、ブラウザ用のJavaScriptを作ります。

~~~text
public/index.html
  ↓ Webpackが生成したJavaScriptを読み込む
生成されたJavaScript
  ↓
main.tsのコードが実行される
~~~

## importは準備だけではない

main.tsの先頭には、例えば次のようなimportがあります。

~~~ts
import '@fontsource/jetbrains-mono';
import { createGameScene } from './render/scene';
import { Game } from './game/game';
~~~

importには2種類の見方があります。

~~~ts
import { Game } from './game/game';
~~~

これはGameという名前を使えるようにするimportです。

一方で、次のように名前を受け取っていないimportもあります。

~~~ts
import '@fontsource/jetbrains-mono';
~~~

これは、そのファイルを読み込んだときに発生する副作用を利用しています。
この場合はフォントのCSSをWebpackへ取り込むことが目的です。

「値を受け取らなくても、読み込むこと自体に意味があるimportがある」と覚えておきましょう。

# 3. 補助関数を先に読む

main.tsの上部には、main()から呼ばれる補助関数が並んでいます。


初心者がコードを読むとき、ファイルの上から順番に「実行される」と考えがちです。
しかし、関数は定義されただけでは実行されません。

~~~ts
function greet() {
  console.log('こんにちは');
}
~~~

この時点では何も表示されません。

~~~ts
greet();
~~~

と呼んで初めて実行されます。

したがってmain.tsを読むときは、関数定義を見つけたら、
「これはどこから呼ばれるか」を探します。

今回の中心は、ファイルの最後にある次の呼び出しです。

~~~ts
main().catch((err) => {
  ...
});
~~~

ここからmain()の中へ入り、そこから呼ばれる関数を追いかけます。

# 4. main()の起動順序

main()の大きな流れは次の通りです。

~~~text
UnlockManagerを作る
  ↓
保存場所とセーブスロットを作る
  ↓
スナップショットサービスを作る
  ↓
WebGPUのシーンを作る
  ↓
HUD・音声・設定画面を作る
  ↓
起動するモード/ステージを決める
  ↓
必要なら天体暦を読み込む
  ↓
Gameを作る
  ↓
最新スナップショットを復元する
  ↓
セーブブラウザを接続する
  ↓
アニメーションループを開始する
~~~

コードの構造を簡略化すると、次のようになります。

~~~ts
async function main() {
  const unlockmanager = new UnlockManager();
  const saveStore = new LocalStorageSaveStore();
  const slots = initSaveSlots(saveStore);
  const snapshotService = new SnapshotService(saveStore, slots);

  const gs = await initScene();
  const { hud, sfx, settingsPanel } = initHud();
  const launch = await resolveLaunchSelection(unlockmanager, slots);

  const game = new Game(
    gs, launch, hud, sfx, settingsPanel,
    unlockmanager, snapshotService, absoluteEphemeris,
  );

  const saveBrowser = new SaveBrowser(...);
  game.setSaveBrowser(saveBrowser);

  startAnimationLoop(game, perf, new AutoSave(snapshotService));
}
~~~

実際のコードでは引数がもっとありますが、見るべき構造はこの形です。

## なぜこの順番なのか

Gameは、すでに存在する部品を使って自分を構築します。
例えばGameのコンストラクタは、HUDや音声を引数として受け取ります。

そのため、HUDと音声はGameより先に作られていなければなりません。

~~~text
Hudを作る ─────────┐
Sfxを作る ─────────┤
SettingsPanelを作る ─┤
                    ↓
                  Gameに渡す
~~~

これは、部品を先に作ってから、それを使う大きな部品を作るという依存関係です。

例えば、まだ存在しないものを渡すことはできません。

~~~ts
const game = new Game(hud); // hudが先に作られている必要がある
~~~

このように、コンストラクタ引数の並びを見ると、オブジェクト同士の依存関係が見えてきます。

# 5. asyncとawait――起動時に待つ処理

main()にはasyncが付いています。

~~~ts
async function main() {
  ...
}
~~~

これは、この関数の中で「時間のかかる処理を待てる」という意味です。

例えば、

~~~ts
const gs = await initScene();
~~~

では、initScene()が終わるまで次の行へ進みません。

initScene()の内部では、WebGPUを初期化しています。

~~~ts
const gs = await createGameScene(canvas);
~~~

GPUの準備が終わる前にGameを作っても、描画できる状態になっていません。
そこで、初期化が終わるまで待ちます。

## Promiseの感覚

awaitの右側にある処理は、すぐに結果が返るとは限りません。

~~~text
initScene()を開始
  ↓
WebGPU初期化中
  ↓
完了
  ↓
gsにGameSceneが入る
~~~

selectLaunch()も似ています。
選択画面を出したあと、ユーザーがボタンを押すまで結果が決まりません。

~~~text
resolveLaunchSelection()
  ↓
選択画面を表示
  ↓
ユーザーがステージをクリック
  ↓
LaunchSelectionが決まる
  ↓
awaitの次の行へ進む
~~~

この処理は、関数が完全に停止しているというより、
「結果が届くまで、この続きの実行を保留している」と考えると分かりやすいです。

# 6. initScene()――Three.jsの世界を作る

initScene()は、WebGPUの準備中にローディング画面を表示します。

~~~ts
hideLoading = showLoading();
const canvas = document.createElement('canvas');
document.body.appendChild(canvas);

const gs = await createGameScene(canvas);

hideLoading();
hideLoading = null;
return gs;
~~~

ここには、いくつか大切な考え方があります。

## 関数が関数を返している

showLoading()の戻り値は、ローディング画面を消す関数です。

~~~ts
function showLoading(): () => void {
  ...
  return () => {
    div.remove();
    style.remove();
  };
}
~~~

戻り値の型である、

~~~ts
() => void
~~~

は、

~~~text
引数を取らず、戻り値もない関数
~~~

という意味です。

つまり、

~~~ts
const hide = showLoading();
~~~

と書くと、hideに「あとでローディング画面を消すための関数」が入ります。

~~~ts
hide();
~~~

で、その関数を実行できます。

これはクロージャと呼ばれる仕組みの一例です。
返された関数が、外側のdivやstyleを覚えています。

# 7. initHud()――画面UIと音声を作る

~~~ts
function initHud(): { hud: Hud; sfx: Sfx; settingsPanel: SettingsPanel } {
  const hud = new Hud();
  const sfx = new Sfx();
  const settingsPanel = new SettingsPanel(hud.layers.system, hud.modalController);
  ...
  return { hud, sfx, settingsPanel };
}
~~~

この関数は3つのオブジェクトを返します。

~~~ts
const { hud, sfx, settingsPanel } = initHud();
~~~

これは分割代入です。

次のコードと同じ意味です。

~~~ts
const result = initHud();
const hud = result.hud;
const sfx = result.sfx;
const settingsPanel = result.settingsPanel;
~~~

SettingsPanelは、設定画面を表示するだけでなく、イベントの通知口も持っています。

~~~ts
settingsPanel.onBgmVolumeChange = (vol) => sfx.setBgmVolume(vol);
~~~

このコードは、

~~~text
設定画面の音量が変更されたら、Sfxの音量を変更する
~~~

という接続を作っています。

また、設定画面とGameの一時停止も、main.tsで接続されています。

~~~ts
settingsPanel.onSettingsOpenChange = (open) => {
  if (open) game.pause();
  else game.resume();
};
~~~

ここで大切なのは、SettingsPanelがGameを直接作ったり探したりしていない点です。
main.tsが両者を知っていて、橋渡しをしています。

~~~text
SettingsPanel ──通知──→ main.tsで登録した関数 ──→ Game.pause()
~~~

このような「main.tsで各部品を配線する」設計は、イベントや依存関係を追うときの重要な読みどころです。

# 9. startAnimationLoop()――ゲームを毎フレーム動かす

このゲームの心臓部は、startAnimationLoop()の中にあります。

簡略化すると、次のコードです。

~~~ts
function startAnimationLoop(game: Game, perf: PerfMeter, autoSave: AutoSave): void {
  let lastTime = performance.now();

  function animate(now: number) {
    const dt = (now - lastTime) / 1000;
    lastTime = now;

    game.update(dt);
    autoSave.update(game);
    game.sync();
    game.render();

    requestAnimationFrame(animate);
  }

  requestAnimationFrame((now) => {
    lastTime = now;
    animate(now);
  });
}
~~~

## requestAnimationFrameとは

requestAnimationFrameは、ブラウザに対して、

~~~text
次に画面を更新するタイミングで、この関数を呼んでください
~~~

と依頼するAPIです。

1回呼んだら自動的に繰り返されるわけではありません。
次のフレームでも動かしたい場合は、関数の最後で再度呼びます。

~~~ts
function animate(now: number) {
  ...
  requestAnimationFrame(animate);
}
~~~

この1行が、次のフレームを予約しています。

~~~text
animate
  ↓
ゲームを更新
  ↓
次のanimateを予約
  ↓
animate
  ↓
ゲームを更新
  ↓
次のanimateを予約
~~~

この自己再登録によって、ゲームループが続きます。

---

# 10. nowとdt――時間の扱い

requestAnimationFrameが渡してくるnowは、ブラウザの時計です。

~~~ts
const dt = (now - lastTime) / 1000;
~~~

前回のフレームから何秒経ったかを計算しています。

例えば、

~~~text
前回: 1000.0 ms
今回: 1016.7 ms
差分: 16.7 ms
dt:   0.0167 秒
~~~

このdtは、ゲームを「何秒ぶん進めるか」を決める値です。

## なぜフレーム数ではなく秒数を使うのか

次のように書くとします。

~~~ts
player.x += 1;
~~~

これは1フレームごとに1だけ進みます。
60FPSなら1秒で60進み、30FPSなら1秒で30しか進みません。

一方、次のように書くとします。

~~~ts
player.x += speed * dt;
~~~

これなら、フレームレートが変わっても、おおむね1秒あたりspeedの速度になります。

物理シミュレーションでは、このdtが特に重要です。

## Game.update()での上限

main.tsは生のdtをGame.update(dt)に渡します。
その後、Game.update()側で次のように上限を設けています。

~~~ts
const dt = Math.min(dtRaw, 0.1);
~~~

ブラウザが一時停止から復帰したときなどに、前回から数秒経っている場合があります。
そのまま数秒ぶんを1フレームで処理すると、物体が飛びすぎたり、物理計算が不安定になったりします。

そこで、通常の1フレームの処理に使う実時間は最大0.1秒に制限しています。

# 11. 1フレームの3段階

このゲームのフレーム処理は、次の3段階です。

~~~text
update
  ↓
sync
  ↓
render
~~~

## 1. update：内部世界を進める

~~~ts
game.update(dt);
~~~

ここでは、例えば次のようなことが起きます。

~~~text
入力を読む
自機の操作を決める
敵AIを動かす
推力・トルクを決める
物理シミュレーションを進める
弾の衝突を判定する
勝敗を判定する
カメラの状態を更新する
~~~

この段階で「ゲームの事実」が変わります。

例えば、弾が敵に当たったなら、敵のHPやaliveが変わります。

## 2. sync：表示用オブジェクトへ写す

~~~ts
game.sync();
~~~

updateで変更された内部状態を、画面に表示するオブジェクトへ反映します。

~~~text
player.state.r
  ↓ sync
player.obj.position
~~~

~~~text
player.hp
  ↓ sync
HUDのHP表示
~~~

物理の位置やHPを変更しただけでは、画面上のメッシュやDOMが自動で変わるわけではありません。
sync()がその橋渡しをします。

## 3. render：GPUに描画させる

~~~ts
game.render();
~~~

最後にThree.jsのレンダラーへ、次の処理を呼びます。

~~~ts
this.renderer.render(this._scene, this.cameraSystem.activeCamera);
~~~

ここで初めて、現在のSceneとカメラの状態が画面の画像になります。

~~~text
内部状態
  ↓ update
新しい内部状態
  ↓ sync
Three.jsオブジェクト / DOM
  ↓ render
画面のピクセル
~~~

# 12. autoSave.update()はどこにあるか

実際のループは、updateとsyncの間に自動保存を呼びます。

~~~ts
game.update(dt);
autoSave.update(game);
game.sync();
game.render();
~~~

自動保存は、ゲームの内部状態をスナップショットに変換する処理です。

この順番から分かることは、

~~~text
ゲーム状態を更新した後
  ↓
表示へ反映する前
  ↓
自動保存する
~~~

ということです。

自動保存は、描画そのものを担当していません。
そのため、main.tsのループに置かれていますが、Game.update()の中ではありません。

これは「どのタイミングで呼ぶか」という責務と、
「何を保存するか」という責務を分けている例です。

# 13. 初期化時のエラーと実行中のエラー

最後のコードは次の形です。

~~~ts
main().catch((err) => {
  console.error(err);
  showFatalError(
    'ゲームの初期化に失敗しました。',
    'ブラウザやGPUの状態を確認し、ページを再読み込みしてください。',
    err,
  );
});
~~~

main()はasync関数なので、途中でエラーが起きるとPromiseが失敗します。
その失敗を.catch()で受け取っています。

例えば、

~~~text
WebGPU初期化に失敗
天体暦の読み込みに失敗
Game生成中に例外
~~~

といった起動時の問題は、この経路へ来ます。

一方、毎フレームの処理には別のtry/catchがあります。

~~~ts
try {
  game.update(dt);
  autoSave.update(game);
  game.sync();
  game.render();
} catch (e) {
  console.error(...);
  showFatalError(...);
}
~~~

フレーム処理中に例外が起きた場合、次のrequestAnimationFrameを予約しません。
つまり、壊れた状態のゲームを動かし続けず、ループを止めてエラー画面を出します。

~~~text
初期化中のエラー → main().catch()
実行中のエラー   → animate()内のtry/catch
~~~

エラー処理が2か所あるのは、起きるタイミングが違うからです。

# 15. 起動から1フレーム目までの全体図

ここまでを、一本の流れにまとめます。

~~~text
ブラウザ
  ↓
WebpackがまとめたJavaScriptを実行
  ↓
main()
  ├─ セーブを準備
  ├─ Canvas/WebGPUを準備
  ├─ HUD/音声/設定を準備
  ├─ ステージ選択を待つ
  ├─ Gameを生成
  ├─ 必要ならセーブを復元
  └─ startAnimationLoop()
       ↓
     requestAnimationFrame
       ↓
     animate(now)
       ├─ dtを計算
       ├─ game.update(dt)
       ├─ autoSave.update(game)
       ├─ game.sync()
       ├─ game.render()
       └─ 次のanimateを予約
~~~

この図のうち、次回は次の部分を詳しく読みます。

~~~ts
game.update(dt);
~~~

ここから、

~~~text
Input.update()
  ↓
Game.handleInput()
  ↓
Player.behave()
  ↓
Stage.update()
  ↓
Simulator.advance()
~~~

というゲーム内部の流れに入っていきます。

# 今日覚えること

今回の最重要ポイントは次の5つです。

~~~text
1. main.tsはゲームルールではなく、部品の生成と配線を担当する
2. Gameはmain.tsから渡された部品を束ねる指揮者である
3. requestAnimationFrameは次の描画タイミングで関数を呼ぶ
4. 毎フレームはupdate → sync → renderの順で進む
5. dtは前フレームからの経過秒数であり、物理計算の時間刻みである
~~~

特に、次の2つを混同しないようにしてください。

~~~text
Gameを作ること      = ゲームの部品を準備する
フレームループを回す = 準備されたゲームを毎秒何十回も動かす
~~~

new Game(...)だけではゲームは動きません。
startAnimationLoop()が呼ばれ、さらにその中でrequestAnimationFrameが再登録されて、初めてゲームが継続的に動きます。

# 小さな練習問題

最後に、実際にmain.tsを開いて次を探してみてください。
