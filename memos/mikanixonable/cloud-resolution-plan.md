# 生成雲の近距離解像度を修正する計画

## 目的

低軌道から見た生成雲の輪郭と内部が数百 km 単位にぼやける問題を直す。近距離の雲形を、質量・高度・表示時刻が整合した局所場から描き、地表からの見え方・大気中の雲・影に同じ分布を渡す。

## 決めたこと

- 全球格子の寸法だけを増やす方法は採らない。イベント供給の代表間隔が約 450 km のままでは細部が増えず、格子変更だけで堆積質量が大きく変わりうるため。全球場は遠景の低周波成分として維持し、近距離は有限範囲の局所場で解像する。
- 局所タイルは質量場から導き、既存の局所光学場と時刻・中心・世代を揃える。独立ノイズを雲の主形状に使わない。局所場と全球場の境界では、晴天・被覆・相別質量の対応を検査する。2D の被覆だけを細かくし、3D の消散を粗いまま残す構成は合格としない。
- 2 km の構造を 4 標本以上で評価する撮影は、200 km・中品質、または 250 km・高品質で行う。250 km・中品質の内部画素は約 3.47 px / 2 km なので、そこで 4 画素の合格を宣言しない。中品質の見た目も別途比較する。
- この計画は近距離解像度の修正に絞る。全雲種の形態と観測分布の完成判定は含めない。

## 達成目標

1. 生成雲の 2 km の被覆変化が、200 km・中品質と 250 km・高品質の固定撮影で、入力から画面まで 4 標本以上を通って識別できる。250 km・中品質では内部画素数の上限を明記し、画質を修正前と比較する。
2. 局所場の質量積分と全球側への集約値が、液水・氷それぞれで独立した質量収支検査を通る。タイル境界で雲の輪郭・高さ・影に円形の継ぎ目が現れない。
3. 地表、大気、影が同じ表示時刻・同じ局所場を読む。生成と実写の切替、時刻の後退、視点移動で旧タイルや異なる世代が混ざらない。
4. 基準機の GPU 時間、CPU 導出時間、更新待ち、交換時メモリを修正前後の同じ撮影条件で測り、決めた予算との合否を数値で記録する。計測できない項目は合格扱いにしない。

## 手順

### 手順 1. 問題と計測条件を固定する

**目的:** 現在の粗さを、生成・実写、近距離・遠距離、内部描画解像度を分けて再現する。見た目の変化と計算費用を同じ条件で比較できるようにする。

| 変更が必要な箇所 | 作業 |
| --- | --- |
| `tools/render-lab/earth-cases.ts` | 生成・実写の 200 km 中品質、250 km 中／高品質、遠景、斜視、タイル境界の固定撮影を揃える。既存撮影で足りるものは再利用する。 |
| `tools/render-lab/lab.ts`、`tools/render-lab/cloud-detail-diagnostic.ts` | 撮影ごとの内部画素数・局所標本間隔・雲の応答幅を同じ基準で記録する。既存の計測口で足りるなら変更しない。 |

**達成条件と検証:** 修正前の撮影を独立に 2 組撮り、画像で粗さを確認する。内部解像度と 2 km 当たりの入力標本数・画素数を記録する。CPU、GPU、交換時ピークの修正前値を同じ環境で測る。`npm run typecheck`、`npm run test:render`。

### 手順 2. 局所の質量分布から詳細な被覆を導く

**目的:** 局所光学場の実イベントから、描画に使える高密度の被覆・雲頂・薄雲量を導く。細部の追加で質量が増減したり、全球の晴天域に無関係な雲が出たりすることを防ぐ。

| 変更が必要な箇所 | 作業 |
| --- | --- |
| `src/game/cloud/cloud-local-field-supply.ts` | 局所イベントを連続した footprint から詳細格子へ堆積し、2D/3D の両方へ同じ相別・層別質量を渡す。再焼の seed、表示時刻、中心を一致させる。 |
| `src/game/cloud/cloud-global-field-supply.ts` | 全球のイベント・面積・質量を局所側へ対応づける入口を整理する。必要な低周波量だけを渡し、局所側が異なるイベントを独立に加算する状態を解消する。 |
| `src/render/cloud/cloud-global-condensation.ts` | 局所と全球で同じ質量から被覆・雲頂・薄雲量を導く関数を共有する。 |
| `src/render/cloud/cloud-local-field.ts`、`src/render/cloud/cloud-optical-volume.ts`、`src/render/cloud/cloud-local-field-baker.ts` | 2D/3D の同一世代を一括公開する契約、詳細体積の形式・量子化・交換時寿命を扱う。 |
| `src/render/cloud/cloud-detail-field.ts`（新規） | 有限範囲の詳細場を焼き、世代・配置・所有権を持つ。候補は 500 km 幅の 1024² または 250 km 幅の 512²。どちらも約 0.488 km/texel。 |
| `tests/game/cloud-local-field-supply.test.ts`、`tests/game/cloud-global-field-supply.test.ts`、`tests/render/cloud-global-condensation.test.ts`、`tests/render/cloud-detail-field.test.ts`（新規） | 質量収支、同一時刻、晴天、境界、解像度変更時の不変量を独立期待値で検査する。 |

**達成条件と検証:** 同一イベントを粗格子・詳細格子へ積分した液水／氷質量が、それぞれ入力と一致する。2D 被覆と 3D 消散は同じ詳細質量から導かれる。晴天は詳細場でも晴天のままで、同じ時刻・中心・seed は同じ結果を返す。RG16F を使う場合は薄い雲と厚い雲の光学厚誤差を RG32F と照合する。`npm run typecheck`、`npm run test:game`、`npm run test:render`。

### 手順 3. 詳細場を三つの描画経路へ同期して接続する

**目的:** 詳細場が実際の雲の輪郭・大気中の透過・影へ同じ時刻に反映されるようにする。既存の局所光学場との二重計上とタイルの継ぎ目を除く。

| 変更が必要な箇所 | 作業 |
| --- | --- |
| `src/render/cloud/cloud-presentation.ts`、`src/game/celestial/solar-system/earth-system.ts` | 詳細場を生成 source の寿命へ接続し、光学場と一組の binding として更新・破棄する。実写には注入しない。 |
| `src/render/cloud/cloud-field-sampler.ts` | 局所詳細の合成、外縁の減衰、晴天域の扱いを一箇所で確定する。 |
| `src/render/opaque-cloud-surface-renderer.ts`、`src/render/pipeline/cloud-atmosphere-renderer.ts`、`src/render/pipeline/shadow/cloud-shadow-renderer.ts` | 同じ詳細場が各経路へ届くことを確認し、必要な読み取りだけを変更する。 |
| `tests/render/cloud-field-sampler.test.ts`、`tests/render/cloud-local-field-baker.test.ts` | 切替、時刻後退、視点移動、旧世代の保持・破棄を検査する。 |

**達成条件と検証:** 固定撮影で詳細が生成雲にのみ現れ、地表・大気・影の位置が一致する。タイルの内外で輪郭・光学量に段差がなく、再焼途中でも前の完全な世代が描かれる。`npm run typecheck`、`npm run test:render`、`npm run test:game`。手順 1 の修正前 2 組と修正後 1 組を `npm run render-lab:compare` で比較し、封筒外の撮影を画像で説明する。

### 手順 4. 費用と画質を測って方式を確定する

**目的:** 高解像度化による画質改善が画面に届くか、更新費用と交換時ピークが実用範囲かを判定する。成立しない場合はタイル範囲・解像度・更新方式を実測値から再設計する。

| 変更が必要な箇所 | 作業 |
| --- | --- |
| `src/render/gpu-timings.ts`、`tools/render-lab/lab.ts` | 既存計測で不足する局所焼き・転送・交換の時間と容量を記録する。十分なら変更しない。 |
| `tools/render-lab/earth-cases.ts` | 同じ時刻・カメラ・品質の生成／実写、雲あり／なしを比較する。 |
| `src/render/cloud/cloud-detail-field.ts` | 計測で定めた範囲・形式・更新条件へ調整する。 |

**達成条件と検証:** 200 km・中品質と 250 km・高品質で 2 km の画面応答を画像と数値で判定し、250 km・中品質の内部画素限界も明記する。GPU scoped p50/p95、CPU 導出、初回待ち、更新時ピーク容量を修正前後で報告する。暫定の雲所有 48 MiB と scoped 増分 3 ms を超えた場合は合格とせず、方式と予算を実測付きで再計画する。`npm run typecheck`、`npm run test:render`、手順 1 の撮影との前後比較。

## 見積り

- 500 km / 1024 = 250 km / 512 = 約 0.488 km/texel。2 km / 0.488 km ≈ 4.10 texel。500 km の 1024² RGBA8 は 4 MiB/枚、4 層 RG16F 体積は 1024² × 4 層 × 4 byte = 16 MiB/枚。2D と 3D の旧新 2 世代を同時保持すると基底レベルだけで 40 MiB。250 km の 512² なら同じ計算で 10 MiB。CPU 配列・転送領域・driver allocation はどちらも含まないため、寸法と形式は実測で選ぶ。
- 現行の局所光学場は 500 km / 256 = 約 1.95 km/texel。詳細タイルの 4.10 標本/2 km が実際の雲形へ届くには、局所質量から 1024 側へ情報を与える必要がある。256 の場を補間して焼くだけでは達成しない。
- 導出費用は候補寸法で 1024² / 256² = 16 倍のセル数となる。ただし処理の全段が線形とは限らないため、手順 1・4 の CPU/GPU 実測で更新間隔と最大範囲を確定する。過去の一回の値を恒常的な費用とは見なさない。
- 作業量は、固定撮影と基準値の確定、質量の対応づけ、GPU binding と三経路、性能診断の 4 単位。それぞれ独立に検証・commit できる単位とする。

## リスクと落とし穴

| リスク | 影響 | 露見する場所 |
| --- | --- | --- |
| 全球格子を細かくするだけで質量が変わる | 被覆率・明るさが大きく変わる | 手順 2 の相別質量収支と格子変更試験 |
| 256² 光学場の補間を 1024² 詳細と数える | テクスチャ寸法だけ増え、雲形は粗い | 手順 2 の 2 km 入力応答、手順 4 の画面応答 |
| 全球と局所で別イベントを二重に足す | 白い斑点、影と厚みの不一致 | 手順 2 のイベント対応・質量試験、手順 3 の三経路撮影 |
| タイルを視点とともに動かして局所模様が滑る | 視点移動で雲が地表に対して動く | 手順 3 の中心移動・再焼前後撮影 |
| 更新の途中で世代が混ざる | 雲と影がずれ、時刻ジャンプで点滅する | 手順 3 の寿命・時刻後退試験 |
| 2D 面の容量だけを計算する | 更新時に CPU/GPU 容量が予算を超える | 手順 4 の交換時ピーク計測 |
| 250 km・中品質へ入力だけ増やす | 内部画素の上限で 4 画素条件を満たせない | 手順 1・4 の内部解像度記録 |
