# 機能追加スキル 要件定義の経緯記録

> 本文書は `/add-feature` SKILL(`.claude/skills/add-feature/SKILL.md`)を新設した際の設計判断の
> 記録であり、現状の実装を保証しない。「今どう動いているか」は SKILL 本体を読むこと。

`done.md` の過去プロンプトから、大規模な機能追加要求で繰り返し現れるパターンを抽出し、
`/add-feature` SKILL として固定した。以下はその際に抽出した根拠と、検討の過程で決めた判断。

## 抽出根拠(該当プロンプトの例)

- L445-446: 「まずは以下の要件の実装案を別ファイルにまとめて。サブエージェントがそれだけを見て
  理解できるように文脈を含めた指示書となるようにして。具体化のために価値判断が必要な選択肢に
  ついては案を提案して。以降複雑な判断を伴わない作業はSonnetをサブエージェントとして用いて
  実行し、あなたはそのレビュー、監督に徹して。」
- L599-601: 「以上の要件の追加を、調査、検証含めて行い実装案を修正。修正後レビューして。
  あなたが複雑なタスクに集中できるように、複雑な判断を伴わない作業、単純作業は最大限Sonnetを
  サブエージェントとして実行して。並列実行しても構わない。必要なコードベースの調査やデータの
  収集を行なって。」
- L615: 「これは大きな計画なので、計画的に実行したい。要件を定義し、実装方法を調査し、単体で
  文脈が取れるような実装計画を別ファイルに書き出して。相対的な表現を避け、絶対的な表現で文脈と
  意図や効果を含めて記載して。」
- L595-599(ラグランジュ点安定性の例): 「安定性の検証は追加で文献調査と計算が必要」→
  外部の学術的裏付け(軌道力学の文献)が要る要求では、コード調査だけでなく文献調査が伴う。
- L238-244, L537-541: 軽量化計画・リファクタリング計画は「まだコードは変更しないでください」
  「計画を @xxx.md に書き出してください」という、実装に進まず計画だけを求めるパターン。
- L479: 「実装計画に従って実装に移って。並列作業可能なものについては可能な限りサブエージェント
  で並列し、それぞれ実装が終わり次第commitし、すべて終わればpushして。」→ 計画承認後の実装
  フェーズも定型化されている。
- L685, L691-692, L700-701, L706-707, L710-711, L735, L743, L750: 「別worktreeで作業し完了後
  mainに統合しコミット」「実装はSonnetをサブエージェントとして用い可能ならば並列実行して」が
  中規模タスクで定型句として繰り返される。
- L763: 「まずは実装せず要件を吟味し必要なら修正、追加、廃止して実装案を複数提案して。」→
  ユーザー自身が出した要件案も、鵜呑みにせず精査・対案を出すことが期待されている。

## 固定した特徴(採用)

1. **成果物は独立ファイル。** `memos/mikanixonable/` 配下に、サブエージェントが単体で読んで
   文脈を再現できる指示書として書き出す。相対表現("現在より"など)を避け、絶対的な記述にする。
2. **調査は並列サブエージェント(Sonnet)に切り出す。** 文献調査・コードベース調査・計算など、
   互いに依存しない作業は同時に複数投げる。判断そのもの(仕様確定、要件の要否)は委譲しない。
3. **曖昧な箇所・価値判断が要る箇所は先に潰す。** 具体化に選択肢が要る場合は案を提示してから
   ユーザーに問う(AskUserQuestion)。ユーザーが決めた判断・言及した可能性は計画書に記録する。
4. **書いたら自分でレビューする。** 矛盾点・曖昧な箇所・不正確な箇所を計画書自身で洗い出し、
   必要なら追加調査や再度の質問を行ってから初めて完成とする。書きっぱなしで終わらない。
5. **計画フェーズと実装フェーズは分離できる。** 「計画を書いて」だけの依頼(軽量化計画・
   リファクタリング計画など)は計画止まりでよい。実装まで進める場合は、ステップごとに
   コミットし、全体が終わればユーザーの指示があれば push する。
6. **規模に応じて worktree を使う。** 中規模タスクは「別worktreeで作業し完了後mainに統合し
   コミット」が定型。大規模な要件定義タスクは worktree 分離への言及がなく、直接メインで計画
   ファイルを書いている(まだファイル作成段階で衝突が起きないため)。
7. **ユーザーが出した要件案も鵜呑みにしない。** 提示された要件でも、ゲームデザイン・実装難易度
   の観点から吟味し、必要なら修正・追加・廃止を提案する余地を残す。

## 既存 SKILL との関係(決定)

- **独立 SKILL とする。** `/modify-feature` の分岐にはしない。`/modify-feature` は
  「SPEC/ を更新して振る舞いを確定させる」ことが正本のまま維持し、今回のスキルは
  「文献調査+コードベース調査+並列サブエージェント+計画書ファイルへの外出し+自己レビュー」
  を主目的とする別 SKILL として新設する。CLAUDE.md の表に発火条件を追加する。
- **軌道力学・天文学などドメイン知識の外部調査は、別スキルに分ける。** 本スキールは
  「調査を並列サブエージェントへ切り出し、計画書を書き、レビューする」という手順そのものが
  正本であり、ドメイン固有の調査観点(文献の探し方、信頼できる情報源の基準など)は含めない。
  ドメイン調査が必要な要求では、本スキールから当該ドメインスキルを呼び出す形にする。
  軌道力学・天文学向けに `orbital-mechanics-research` SKILL
  (`.claude/skills/orbital-mechanics-research/SKILL.md`)を新設した。

## 計画書ファイルの扱い(決定)

- 計画書は **恒久的に保存する。** ただし完成直後の置き場所と、実装完了後の置き場所を分ける。
  - 作成中・レビュー中: `memos/mikanixonable/` 直下(現状の `done.md` 運用と同じ)。
  - 実装が完了した項目: `memos/mikanixonable/archived/` へ移動する。
  - 移動時、計画書の内容のうち実装が完了した箇所は「未実装の設計案」ではなく
    「実装済みの記録」として文面を更新する(例: 「〜する」→「〜した」、選定した案以外の
    未採用案は削除するか「不採用」として明記するなど)。**CLAUDE.md の「コードの現状はコード
    だけが原本」という原則と、この archived 記録が矛盾しないよう、archived 後の文書は
    「なぜその設計にしたか」という決定の経緯を残す位置づけとし、「今どう動いているか」の
    正本は主張しない旨を明記する必要がある。**
- 一部完了・一部未着手の計画書をどう分割するか(ファイルごと archived に移すか、実装済み節
  だけ抜き出すか)は、実際に SKILL を書く際に詳細化する。
