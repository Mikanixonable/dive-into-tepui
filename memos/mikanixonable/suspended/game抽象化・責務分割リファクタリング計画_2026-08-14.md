# Game 抽象化・責務分割リファクタリング計画

作成日: 2026-08-14

調査基準: `d797606`

対象: `src/game/game.ts` と、その公開状態へ依存するモジュール

方針: 挙動・セーブ形式・ゲーム仕様を変えない構造リファクタリング

## 1. 結論

このリファクタリングは妥当である。

現在の `Game` は、ゲーム全体の順序を決めるオーケストレータである一方、個々のサブシステムの生成、具体的な引数の組み立て、表示同期、入力配分、診断値の集計まで直接行っている。さらに `MapPicker`、`Docking`、HUD、保存系が `Game` 全体を参照しており、`Game` が構成の頂点であると同時に共有サービス置き場にもなっている。

目標は `Game` を空の委譲ラッパーにすることではない。`Game` には次の高水準な責務を残す。

- 1フレームの大きな実行順序を決める。
- `update`、`sync`、`render`、`pause`、`resume` というセッション境界を提供する。
- wall clock の `dt` をゲームが受け付ける上限へ制限する。

具体的な生成と処理は、次の層へ分ける。

- `GameSession`: 具象オブジェクトの生成、所有、配線を行う composition root。
- `InputCoordinator`: 入力スナップショット確定と優先順位付き配分。
- `SimulationCoordinator`: 自機、ステージ、積分、予測、エフェクト、計画追従の更新。
- `PresentationCoordinator`: 表示時刻、マップ候補、カメラ、floating origin、各描画物の同期。
- `RenderCoordinator`: 描画可否と renderer 呼び出し。
- `SessionControl`: pause 状態と pause/resume 時の副作用。

この分割と同時に、`Game` 全体を引数に取るモジュールを狭い読み取り口・操作口へ変更する。ここまで行って初めて、import を別ファイルへ移しただけではない責務分割になる。

| --- | --- |

`Game -> MapPicker -> Game`、`Game -> Docking -> Game`、`Game -> Hud -> HudPanels -> Game` は、`import type` が消去されるため現状の emitted JavaScript の実行時循環ではない。しかしソース上の依存方向は循環しており、構成の頂点へ下位モジュールが逆依存している。

### 2.4 現在の更新順は仕様である

次の順序は暗黙のAPIであり、抽出時に変えてはならない。

1. `Input.update()` で入力スナップショットを確定する。
2. グローバル入力を先着順で配る。
3. pause 中でなければ自機・ステージ・積分・予測・エフェクト・計画を進める。
4. 表示窓を確定する。
5. 環境、計画表示、選択候補、カメラの順に更新する。
6. 更新済みの候補とカメラを使って pointer 入力を配る。
7. `sync()` で camera matrix を先に確定し、3D・HUD・marker を同期する。
8. marker が出揃った後で collision layout を解決する。
9. dock view でなければ renderer を呼ぶ。

特に、pointer 配分をカメラ・pickable 更新より前へ動かすこと、marker collision 解決を途中へ動かすこと、display window の確定回数を無造作に減らすことは禁止する。

## 3. 妥当性の判断

### 3.1 実施する理由

- `Game` の変更理由が、入力、物理、マップ、HUD、保存、描画の追加で増え続けている。
- 具体クラスを公開フィールドとして多数露出しているため、周辺モジュールが `Game` を service locator のように使える。
- constructor の生成順と `this` の引き渡しが循環を隠しており、単体テストしにくい。
- `sync()` の正しい順序は重要だが、現在は長いメソッドの並び順としてしか固定されていない。
- 既存の `DEVELOP/OWNERSHIP.md` と過去のレビューでも、frame phase 抽出と `Game` 全体への依存縮小が未解決事項として認識されている。

### 3.2 過剰抽象化を避ける条件

次は行わない。

- 全クラスに1対1の interface を作らない。
- `GameContext`、`Services`、`Deps` のような巨大な汎用バッグを作らない。
- service locator、DI container、汎用 event bus、scheduler framework を導入しない。
- barrel export で import 数だけを隠さない。
- callback の束で具象依存を隠さない。変更される所有者オブジェクトは明示的に渡す。
- この作業と同時に ECS 化、simulation/render の全面分離、Stage 再設計を行わない。

interface を置くのは、`Game` と各フェーズ、セッション外部と読み書きポート、という実際の境界だけにする。各Coordinatorは、その責務を実行するために必要な具象クラスへ明示的に依存してよい。

## 4. 目標構造

```text
main.ts
  └─ GameSession                       具象の生成・所有・配線
       ├─ Game                          抽象フェーズの実行順だけを決める
       ├─ SessionControl                pause状態と遷移副作用
       ├─ InputCoordinator              入力確定・グローバル入力配分
       ├─ SimulationCoordinator         実時間からsimulationを進める
       ├─ PresentationCoordinator       表示準備・sync
       ├─ InteractionCoordinator        更新後のpointer配分
       ├─ RenderCoordinator             描画可否・renderer呼び出し
       ├─ GameDiagnostics               PerfCountsの合流
       ├─ GameSnapshotSource            保存用スナップショット生成
       └─ 既存の具象サブシステム群
```

### 4.1 `Game` の最終責務

最終的な `game.ts` は Three.js、Player、EntityManager、Simulator、CameraSystem、HUD、MapPicker、PlanEditor などを import しない。フェーズ境界だけを import する。

概念形は次のとおり。

```ts
export class Game {
  constructor(
    private readonly input: GameInputPhase,
    private readonly simulation: GameSimulationPhase,
    private readonly presentation: GamePresentationPhase,
    private readonly interaction: GameInteractionPhase,
    private readonly output: GameOutputPhase,
    private readonly session: SessionControl,
  ) {}

  update(dtRaw: number): void {
    const dt = Math.min(dtRaw, 0.1);
    this.input.beginFrame();
    this.input.dispatchGlobal();
    if (!this.session.isPaused) this.simulation.advance(dt);
    this.presentation.update(dt);
    this.interaction.dispatchPointer(dt);
  }

  sync(): void {
    this.presentation.sync();
  }

  render(): void {
    this.output.render();
  }

  pause(): void { this.session.pause(); }
  resume(): void { this.session.resume(); }
  get isPaused(): boolean { return this.session.isPaused; }
}
```

これは最終形の責務を示す例であり、メソッド名は実装時に既存語彙へ合わせて確定する。重要なのは、順序は `Game` に残し、具体処理はフェーズ側に置くことである。

### 4.2 `GameSession` の責務

`GameSession` は現在の constructor にある `new` と配線を引き受ける。ここでは import が多くても問題としない。具象を組み立てることだけが責務だからである。

ただし、現在の constructor をそのまま別名で移すだけにはしない。

- フレーム処理はCoordinatorへ渡し、`GameSession`自身には置かない。
- 外部へ公開するのは `game` と狭いポートだけにする。
- 既存サブシステムを public に一括公開しない。
- 生成順の理由と、構築後注入が必要な箇所をコメントで明示する。

想定する外部公開は次の範囲である。

```ts
interface GameSessionPorts {
  readonly game: Game;
  readonly inputEdges: InputEdges;
  readonly diagnostics: PerfCountSource;
  readonly snapshots: GameSnapshotSource;
  readonly status: GameSessionStatus;
  readonly control: SessionControl;
}
```

単一の汎用contextとして各所へ渡すのではなく、`main.ts` が必要なポートだけを各利用者へ渡す。

### 4.3 状態の所有先

| 状態・所有物 | 現在 | 変更後 |
| --- | --- | --- |
| 1フレームの大順序 | `Game` | `Game`のまま |
| pause状態 | `Game._isPaused` | `SessionControl` |
| pause時の `lastSimDt`・SFX・Player command処理 | `Game.pause()` | pause遷移を所有する `SessionControl` |
| 具象サブシステムの所有 | `Game` | `GameSession` |
| floating origin | `Game` | `PresentationCoordinator` |
| 入力配分順 | `Game.handleInput()` | `InputCoordinator` |
| pointer配分順 | `Game.handleMapPointerInput()` | `InteractionCoordinator` |
| simulation更新順 | `Game.advanceSimulation()` | `SimulationCoordinator` |
| 表示更新・同期順 | `Game.updateMapPresentation()` / `sync()` | `PresentationCoordinator` |
| PerfCounts合流 | `Game.perfCounts()` | `GameDiagnostics` |

この変更を実装した変更セットでは `DEVELOP/OWNERSHIP.md` も必ず更新する。

## 5. 下位・周辺モジュールの依存変更

### 5.1 `MapPicker`

現在は `Game` から、操作対象、Stage capability、FrameControls、CameraSystem、simTime を取得している。変更後は所有者を個別に受け取る。

- 操作対象の参照と変更: `ActivePlayerController`
- 配置・複製・計画実行可否: 狭い `StageMapCapabilities`
- フォーカス変更: `FrameControls`
- 現在時刻: メソッド引数、または読み取り専用の `SimulationClock`
- CameraSystem: 既に直接受け取っているものを継続

`ActivePlayerController` が `MapPicker.close()` を呼ぶ逆依存は外す。削除済み対象のメニュー・ウィンドウを閉じる責務は、既に対象の生存確認を持つ `MapPicker.refresh/sync` 側へ寄せる。操作対象削除、戦闘中の死亡、ドック収容の3経路で同一フレーム内に stale UI が閉じることを回帰確認する。

### 5.2 `Docking`

`Game` の代わりに次を受け取る。

- `SessionControl`
- `ActivePlayerController`
- free procurement の読み取り口
- 既存の EntityManager、ViewManager、CameraSystem など

`Docking` から `MapPicker.close()` を直接呼ぶ依存も、MapPickerの対象生存同期へ寄せられるか確認する。即時closeが仕様上必要なら、ドック操作だけを表す狭い `MapSelectionControl` を使い、`Game`へ戻さない。

### 5.3 HUD

`HudPanels.sync(game, attractors)` を廃止し、`HudPresenter` が必要値を集めて pure data の `HudFrame` を渡す。

- `HudPanels` はDOM更新と更新間隔だけを担当する。
- 軌道情報やターゲット情報の導出は `HudPresenter` へ置く。
- `HudFrame` は表示に必要な値だけを持ち、EntityManagerやCameraSystem自体を持たない。

これにより HUD が composition root を読む依存をなくす。

### 5.4 保存・自動保存・保存ブラウザ

`SnapshotService.capture(game, ...)` は次の二責務に分ける。

- `GameSnapshotSource.captureData()`: 実行中状態から `GameSaveData` とメタデータ材料を生成する。
- `SnapshotService`: slot選択、永続化、loadを担当する。

`AutoSave` は `GameSessionStatus` と `GameSnapshotSource` を受け取る。`SaveBrowser` は `SessionControl` と `StageStatus` を受け取る。これらは `Game` の具象サブシステムを読まない。

セーブJSONのschema、既存snapshotの互換性、snapshot名の生成規則は変更しない。

### 5.5 診断

`GameDiagnostics` が EntityManager、Predictor、Simulator、PlanEditor、Ephemeris、MapPicker の `perfCounts()` を合流する。`PerfMeter` は既存どおり `PerfCountSource` だけを見る。

`Game.setPerfMeter()` は最終的に廃止し、入力側には `PerfToggle` のような狭い操作口を構築後に配線する。遅延配線が残る場合も `Game` の公開フィールドにはしない。

### 5.6 `main.ts`

`main.ts`へ40個の具象importを移さない。`main.ts`は `GameSession` を生成し、外部ポートをアニメーションループ、保存、PerfMeterへ配る。

`startAnimationLoop` は具象 `Game` ではなく、少なくとも次のライフサイクル契約だけに依存させる。

```ts
interface GameLoop {
  update(dt: number): void;
  sync(): void;
  render(): void;
}
```

## 7. 段階的な実装計画

### Phase 0: 挙動契約の固定

1. 既存の競合マーカーを別変更で解消し、全検証が通るbaselineを作る。
2. 現在の update/sync/render 順序をテスト名とコメントで明文化する。
3. `Game` がフェーズinterfaceだけで動けるようになった時点で、fake phaseによる順序テストを追加する。
4. 現在の browser smoke の `stage=00` と creative zero-player 起動をbaselineとして保存する。
5. map、pause、dock、snapshot、time warp の手動確認項目をチェックリスト化する。

受入条件:

- `npm run typecheck`
- `npm run test:physics`
- `npm run build`
- `npm run smoke:browser`
- `SMOKE_QUERY='?stage=creative' npm run smoke:browser`
- 既存セーブがロードできる。

### Phase 1: `Game` への逆依存を解く

1. `ActivePlayerController` から `MapPicker` 依存を外し、MapPicker自身が消滅対象を閉じる。
2. `FrameControls` を `MapPicker` より前に構築できる順へ変更する。
3. `MapPicker` の `Game` 引数を、ActivePlayerController、Stage map capability、FrameControls、clockへ置換する。
4. `SessionControl` を追加し、pause状態とpause時副作用を移す。
5. `Docking` の `Game` 引数を SessionControl、ActivePlayerController、Stage capabilityへ置換する。

受入条件:

- `map-picker.ts` と `docking.ts` が `Game` を importしない。
- 操作対象の切替・解除・削除・死亡・収容・発進が従来どおり動く。
- map上の消滅対象のメニューとproperty windowが残らない。

### Phase 2: composition root を抽出する

1. `GameSession` を追加し、現constructorの生成と配線を順序を保って移す。
2. `Game` へ渡すフェーズと外部向けポートを `GameSession` が組み立てる。
3. `main.ts` は `new Game(...)` ではなく `new GameSession(...)` を使う。
4. ephemeris構成、save復元、touch有無、初期view決定の分岐をそのまま移し、同時に仕様変更しない。

受入条件:

- `game.ts` にサブシステムの `new` がない。
- 生成順による未初期化参照がない。
- `GameSession` 以外に新しいcomposition rootを作らない。

### Phase 3: 具体的なフレーム処理をCoordinatorへ移す

1. `handleInput()` を InputCoordinatorへ移す。
2. `advanceSimulation()` を SimulationCoordinatorへ移す。
3. `updateMapPresentation()` を PresentationCoordinatorへ移す。
4. `handleMapPointerInput()` を InteractionCoordinatorへ移す。
5. `sync()` の具体処理と floating origin を PresentationCoordinatorへ移す。
6. `render()` の dock判定と renderer呼び出しを RenderCoordinatorへ移す。
7. `FrameSections.enter/exit` は各処理の所有Coordinatorへ移し、区間名と計測範囲を変えない。

移動は原則として既存コードの切り出しとし、ロジックの書き換えを同じ変更に混ぜない。

受入条件:

- `Game.update()` に現在の大きな順序が読み取れる。
- `game.ts` は具象サブシステムをimportしない。
- `game.ts` は200行未満を目安とし、行数より依存制約を優先する。
- fake phaseテストが順序、pause中のsimulation skip、`dt <= 0.1` を固定する。

### Phase 4: 読み取り系を狭いポートへ移す

1. HudPresenterとHudFrameを導入する。
2. GameSnapshotSourceを導入する。
3. SaveBrowser、AutoSave、SnapshotControlsをSessionControl・StageStatus・InputEdgesへ切り替える。
4. GameDiagnosticsへPerfCounts合流を移す。
5. `Game` の具象公開getter・fieldを段階的に削除する。

受入条件:

- `GameSession` とgame loop境界以外が `Game` 型をimportしない。
- `Game` から `entities`、`cameraSystem`、`simulator`、`activeStage` 等を直接取得するコードがない。
- snapshotのJSONが、乱数初期位相など既存仕様上変動する項目を除いて移行前後で同値になる。

### Phase 5: 文書と依存制約を確定する

1. `DEVELOP/OWNERSHIP.md` の所有木、pause正本、参照共有、更新義務を更新する。
2. `memos/hedalu244/refactor_game.md` のうち現状と矛盾する記述は、同文書の運用方針に従って整理する。履歴保管文書なら変更せず、新文書から参照する。

## 8. テスト計画

### 8.1 新規characterization test

抽出後の `Game` はDOM・Three.js非依存になるため、fake phaseで次をテストできる。

- 通常時: input begin → global dispatch → simulation → presentation update → pointer の順。
- pause時: simulationだけを飛ばし、input・presentation・pointerは呼ばれる。
- `dtRaw > 0.1` は0.1として渡される。
- `sync()` はpresentation syncだけを呼ぶ。
- `render()` はoutput phaseを呼ぶ。
- `pause()` / `resume()` はSessionControlへ委譲される。

テストを既存の `test:physics` に無理に混ぜず、DOM非依存の `test:game-runtime` を追加するか、テストtsconfigを一般化する。どちらにするかはPhase 0で決める。

## 9. リスクと対策

### 更新順の変化

最大のリスクである。既存メソッドを最初にそのまま移し、最適化や引数整理を同時に行わない。fake phaseの順序テストとbrowser smokeで固定する。

### 構築順の循環

現在の `MapPicker(this, ...)`、`ActivePlayerController -> MapPicker`、`MapPicker.setDocking()` が循環を隠している。Phase 1で依存方向を解いてからconstructorを移す。未初期化参照をcallbackや巨大contextで回避しない。

### pause意味論の変化

pauseは単なるbooleanではなく、`lastSimDt`、SFX、Player commandに副作用がある。SessionControlへの移動時に呼び出し順も含めて保持する。設定、保存ブラウザ、dockの各入口を個別に確認する。

### 表示時刻と実時刻の混同

`simTime`、`displayTime`、`displayWindow` をCoordinator内部でも混同しない。既存の引数名を維持し、1つの汎用frame contextへまとめない。

### `GameSession` の巨大化

importと`new`が集中すること自体はcomposition rootとして許容する。ただし条件分岐、update、sync、ゲームルールを置かない。200行を大きく超える場合は、`GameSession` のprivate構築メソッドを領域別に分け、`new` と保持はGameSessionに残す。

### interface増殖

interfaceは境界にだけ作る。既存クラスを直接渡して責務上問題がないCoordinator内部では、無理に抽象化しない。

## 10. 完了条件

- `game.ts` が具体的なゲームサブシステムをimportしていない。
- `game.ts` が個別のEntity、HUD、MapPicker、PlanEditor、Camera、rendererを直接操作していない。
- `game.ts` から読み取れるのは、1フレームの高水準な順序とsession lifecycleだけである。
- 具象の生成・所有は `GameSession` に一元化されている。
- 入力、simulation、presentation、interaction、renderの責務が別Coordinatorに分かれている。
- `Game` 全体を下位・周辺モジュールへ渡していない。
- 巨大context、service locator、汎用event busを導入していない。
- 更新順、pause、map、dock、save、HUD、描画、Perfの挙動が維持されている。
- `DEVELOP/OWNERSHIP.md` が新しい所有関係と一致している。
- `npm run ci` が成功する。

## 11. 推奨する変更単位

レビュー可能性を保つため、少なくとも次の4変更に分ける。

1. Game逆依存の除去とSessionControl導入。
2. GameSessionへの生成・所有の移動。
3. frame phaseのCoordinator抽出とGameの薄化。
4. HUD・save・diagnosticsのread port化、文書更新。

各変更は単独でtypecheck・build・browser smokeを通せる状態にする。途中で互換用getterを置く場合は、削除予定を同じ計画内の後続変更へ明記し、恒久APIにしない。
