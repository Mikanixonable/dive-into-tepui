# 地球大気・発光現象の不足分 — 優先順位と3つの実装計画

作成日: 2026-09-09。調査対象: `workspace3` の **`95f9cfc1`**。
状態: 案BのE2・C9・C10を実装済み。C2・E3も先行実装済み。C1・C3〜C8・C11〜C13・E5・E7は未着手。

## 目的

この計画は、地球の雲・気象・発光現象・時間変化する海の表現を実装するためのものとする。E2・C9・C10は地表タイル計画と並行して着手でき、C3・C5・E5・E7の共有地表入力が必要な部分は地表タイル計画の完了後に接続する。
地表の静的な材質、標高、法線、水域・氷の分類、タイル配信、LODは
[earth-surface-tiles-plan_2026-09-09/](./)の責任範囲であり、この計画では再実装しない。

推奨する要件解釈は **気象学と実装の均衡案**、実装方式は **案B: 生成場と描画を段階的に拡張** とする。
案Aは変更量を抑える場合、案Cは雲を近距離から見る品質まで追う場合の保留案である。

この計画では、次の共有データ契約を前提にする。データの生成・配信・GPUタイル管理は地表計画が所有し、ここでは読み取り専用の入力として使う。

```text
EarthSurfaceContext
  landSeaMask / waterMask
  elevation または terrainNormal
  staticIceMask
  coast または島境界を判定できる地理情報
```

地表計画が提供する形式と異なる場合は、現在の計画側に薄い変換アダプターを置く。雲側で別の原データ取得、`earth-land-mask.png`の独自生成、標高タイルの独自配信を追加しない。

### SPEC へ反映する要求文案

以下は作るべき振る舞いの案であり、E2・C9・C10は地表計画と独立したS0でSPECへ反映できる。E5・E7の地表依存部分は地表計画の共有入力確定後に反映する。実装方式やキャッシュ容量はSPECへ書かない。

#### 雲・気象

- **C1** 雲は立体的な雲頂・雲底・厚みを持ち、既存の雲場を使って影を落とす。雲本体と雲影は同じ時刻・座標の場を読む。
- **C2** 雲は表示時刻に応じて風で移流し、雲の発生・消滅・発達も連続的に変化する。
- **C3** 海陸は固定的な粒度規則にせず、海面温度、湿度、安定度、地表加熱、上昇流から層積雲・浅い積雲・発達した積雲の傾向を決める。
- **C4** 対流圏界面は緯度・季節の代表値としておよそ8〜18 kmの範囲で変化する。積乱雲の雲頂はそこで平らになり、強い対流だけが上へ突出する。
- **C5** 孤立した島では風上側の上昇流と、風下側の小粒の雲列を表現する。
- **C6** 亜熱帯高圧帯では下降流と安定度によって深い対流雲を抑える。ただし海上の低い層積雲は残ることがある。
- **C7** 天候の変化は全球一様な周期ではなく、地域ごとに数日持続する気象レジームとして変化する。5日は代表的な持続時間とする。
- **C8** 熱帯低気圧は暖かい海面、高湿度、十分なコリオリ力などの条件を満たす海域で発生する。描画上の出現間隔約7日、寿命約5日は演出用スケジューラの値とし、発生緯度を30度に固定しない。
- **C9** 地表付近・対流圏上部・巻雲高度の風を1つの高度依存風場から求め、雲の移流・気団・前線が同じm/s単位の風を読む。ノイズ場の位相変換は風場と別にする。
- **C10** 中緯度の偏西風はロスビー波で南北へ蛇行し、低気圧はその基本流へ重なる局所的な気圧・渦の偏差として扱う。前線は温度・湿度勾配と収束・上昇流から求め、低気圧・前線・雲の移流は同じ合成風場から求める。
- **C11** 火山灰は通常の水雲とは別の灰色エアロゾルとして、噴火地点と上空の風に従って広がる。約30日の発生間隔は演出用とする。
- **C12** 雲の日変化は現地太陽時と地表・海面の違いから決め、固定UTC時刻で急に雲を出現させない。
- **C13** スプライトは発達した雷雲に結び付く短時間の上層大気イベントとして描く。

## 3案の比較

どの案も、地表依存部分は地表タイル計画の共有データを接続してから進める。E2・C9・C10はS0と既存のClimateMapLike境界だけで先行でき、全体の接続後はS0→C1〜C13→E2・E3・E5→E7の順を基本とする。
差は画質を得る方法、投入する基盤の量、各段階で到達できる近距離の品質にある。

| 観点 | 案A: 小さく順次改良 | 案B: 生成場と描画を段階拡張【推奨】 | 案C: 近景品質を重視 |
| --- | --- | --- | --- |
| 雲の描画 | 雲頂の高さ場と薄い殻を維持。必要な項だけ足す | 高さ場を基本とし、近景の細部と有限の雲底を必要な段階で足す | 遠景は高さ場、近景は密度を積分するボリュームへ移行 |
| 小島・小粒への対応 | 対象地域と細部を解析的に補う | 全球の低周波場と、視点近傍の高解像度場を共有して読む | 局所的な密度・照明の場も持つ |
| 時間更新 | 既存更新を保ち、入力更新漏れを直す | 更新時刻の間隔と補間を、画面上の移動誤差から決める | 密度場の更新と画面履歴を再利用。時刻ジャンプ時は履歴を捨てる |
| 天候・イベント | 既存の場へ解析的な地域差・イベントを足す | 気圧・風・湿度を共用し、背景と例外の優先を明示する | Bの気象モデルを使い、雲底・上端・密度形状を細かく表現 |
| 地表データ | 地表計画のデータを読むだけ | `EarthSurfaceContext`を共有し、雲・季節・水色で同じ地理を読む | 同じ共有データを近景の密度・合成へ渡す |
| 季節・水色 | 少数の季節係数と解析的な分布 | 月別の植生データと、地域別の水色分布 | 月別・地域別データの高解像度配信と近景表現 |
| 主な利点 | 各機能へ早く到達する | 希望の特徴を残しながら、全球の計算量増加を抑えやすい | 雲の側面・内部や地形の輪郭を最も細かく作れる |
| 主な限界 | 雲の内部・側面、小島を広範囲に細かく描く表現には限界 | 投影境界・補間・影との整合の実装が必要 | 雲の最初の段階が長く、後続の海陸・オーロラへ届くまで遅い |

案Bを採用する。既に動く雲と影を再利用しながら、地表計画の共有データを唯一の静的地理入力にできる。全球1024×512の場だけでは小島の雲列や細かなかなとこ形状を扱いにくいため、必要な段階で近傍の解像度と表現を足す。案A・Cの表は、実測後に変更する場合の比較対象として残す。

## 共通の手順

### 検証の記法

全手順で **`npm run typecheck`** を実行する。
以下の「R」は加えて **`npm run test:render`**、「G」は **`npm run test:game`**。
`src/physics/` や `src/math/` を変更する場合に限り、それぞれ **`npm run test:physics`**、**`npm run test:math`** も実行する。

描画が変わる手順では `/rendering-workflow` に従い、対象が写る画像を最低1枚残す。
生成場は `npm run cloud-lab` / `npm run cloud-lab:shot`、地球の立体・陰影は `npm run render-lab` / `npm run render-lab:shot` を使う。
テクスチャの到着が必要な比較は読み込み完了を待つ。画像が未到着の単色画像を合格資料にしない。
ゲーム本体のヘッドレス操作確認は、実行時確認を明示的に依頼された場合に `/verify` で行う。

新規テストは、決定論性、境界の連続性、寿命、単位・回転方向などの不変条件を対象にする。
見た目の調整値や生成画像そのものを正解として固定しない。各手順は実装・対応する検証を含め、単独でcommitできる単位にする。

目的: 地表タイル計画の実行後に、雲・季節・水色が同じ地理データを読む接点を作る。

| 変更箇所 | 行うこと |

## 達成目標

1. 地表タイル計画の完了後、P0の共有入力接続を通ってC1〜C13、E2・E3・E5、E7の各行に達成条件に対応する比較結果がある。E1/E6は委譲済みで重複実装しない。
2. 雲の立体・散乱・影・イベントは、同じ表示時刻と地球固定座標で一致する。停止、巻戻し、時間ジャンプで履歴依存の別の空にならない。
3. 雲の海陸差・緯度差・高圧帯は気象条件による背景の傾向となり、天候・台風・前線・偏西風の蛇行は同じ合成風場から必要な例外を作れる。
4. 台風の約7日間隔・約5日寿命と噴火の約30日間隔は演出用スケジューラとして再現される。台風の発生条件は暖かい海・湿度・コリオリ力を使い、日変化は現地太陽時、季節はゲームの開始暦と表示時刻に対応する。
5. 同じ共有地表データ・時刻で全球表示から近景へ移っても、雲・雲影・地表・海岸・水色の対応が切れない。
6. 変更した各層の型検査・回帰テストが通り、対象の画像が残る。性能は同一GPU・画面解像度・視点・時刻の変更前後で比較する。

### 実装作業量

新規の表現やデータ調達は複数Uとする。実測時間が得られたら `所要時間＝Uの合計×実測時間/U` で置き換える。

### 計算量とメモリの目安

以下は実測値ではなく、方式比較のための導出。

| 対象 | 導出と意味 |
| --- | --- |
| 全球場の地上解像度 | 赤道で `2π×6371 km÷1024 ≈39.1 km/texel`。24 kmの粒を4点で表すなら6 km/texelが必要で、全球幅は約6672 texel以上になる。幅8192へ増やすと面積は `(8192/1024)²＝64倍`。近傍だけを細かくする理由になる |
| 雲の出力テクスチャ | RGBA16F、1024×512なら `1024×512×4×2 bytes＝4 MiB`。前後2時刻で8 MiB。**気圧・湿度・前線などの中間場、mip、GPU内部の配置分は別** |
| 局所場 | RGBA16F、1024²なら `1024²×8＝8 MiB/枚`。全球場と局所場を各2時刻保持する場合、最終出力だけで `8+16＝24 MiB`。中間場も個別に足して予算を決める |
| 更新間隔 | 速度v、1画素が張る実距離p、許容ずれε画素なら `Δt ≤ εp/v`。例としてv=20 m/s、p=1000 m、ε=0.5なら25表示秒。p=100 mなら2.5秒。時間倍率を含めて実フレームで何回生成するかへ換算する |
| 時間補間の限界 | 上の移動式だけでは誕生・消滅や形の変化を保証しない。イベント境界では強制更新し、生成場の差も比較する。長い間隔の線形混合で雲が二重に見えるなら間隔を縮める |
| ボリュームの標本数 | 1920×1080、画面の25%が雲、半解像度、32標本なら `1920×1080×0.25÷4×32 ≈415万標本/frame`。照明を各点で6回読むなら追加約2488万標本。これをFPSの保証には使わない |
| 季節画像 | RGBA8、4096×2048を2枚なら `4096×2048×4×2＝64 MiB`、mip込みで約85 MiB。12枚常駐は同条件で約512 MiBとなるため、隣接月の入替えを基本にする。配信用圧縮容量とGPU展開後の容量は別 |

計測には `tools/render-lab-measure.mjs` と既存のGPU時間計測を利用する。平均だけでなく更新フレームの山を比較する。
キャッシュ・LODの追加は、必要な入力をキーへ含めることと、各読み手で同じ場を参照することを達成条件にする。

## E2・C9・C10 詳細実装計画

### 目的

オーロラの位置・明滅と、雲を運ぶ風・中緯度の蛇行を、地表タイルの配信や材質へ依存せずに実装する。既存のオーロラメッシュ、循環ノイズ、ロスビー波、低気圧・気団の部品は再利用するが、物理的な風とノイズを動かすための座標変換を同じクラスへ混在させない。

E2は磁気圏の実測を再現する機能ではなく、表示時刻から再現できる簡易な地磁気モデルとして扱う。C9・C10は数値予報モデルではなく、気圧・温度・風の関係を保った総観規模の見えを作るモデルとして扱う。実測のKp指数、IGRF、ERA5の風を導入する場合は別のデータ契約へ切り出す。

### 要件の修正案

#### E2 オーロラ

- オーロラの中心は地理緯度へ固定せず、磁極を中心とする簡易な地磁気双極子座標で決める。磁極の位置は地球設定として保持し、`PointEntity`が持つ地球の姿勢とは別に扱う。
- オーロラオーバルは磁気地方時(MLT)で非一様にする。夜側の幅と明るさを大きくし、昼側のカスプ付近は細く弱くする。オーバルの拡大・縮小は決定論的な活動度代理値から計算し、実際のKp観測値とは名乗らない。
- 発光の色は酸素の緑線・赤線を中心にし、場所ごとの強度変化と鉛直方向の色変化を分ける。カーテンの形状、活動度、発光色を1つのランダムノイズへまとめない。
- オーロラは昼側にも物理的には存在する。表示では太陽高度と大気の明るさによって見えにくくするが、昼夜境界でイベント自体を突然消さない。
- 同じ表示時刻・同じ地球姿勢では同じオーロラになる。フレーム乱数、FPS、時間加速倍率を入力にしない。

根拠: NOAAの説明ではオーロラオーバルは磁極を中心とする環状領域で、磁気活動に応じて広がり、概ね磁気緯度60〜70度に現れる。[NOAA SWPC Aurora](https://www.swpc.noaa.gov/sites/default/files/images/u2/Aurora.pdf)、[NASA GSFC Polar Auroral Oval](https://pwg.gsfc.nasa.gov/polar_plan/booklet/oval_booklet.html)。

#### C9 高度層の風

- 地表付近・対流圏上部・巻雲高度の風を、緯度と高度を入力にする1つの`WindField`から得る。貿易風・偏西風・極偏東風の平均は、南北半球で連続的に接続する。
- 物理量としての風速・風向はm/sで保持する。雲ノイズを動かす角度・位相への変換は別の`CloudPatternTransport`に置き、角速度を風速として扱わない。
- 雲の湿度、対流、前線、低気圧の移流は、同じ高度層の`WindField`を読む。読み手ごとに別の固定風表を持たない。
- 上空の偏西風は地表付近より強くなりうるが、地表の貿易風をそのまま上空へ足し合わせない。鉛直層間の風向・風速差は風の鉛直シアとして扱う。

#### C10 偏西風の蛇行・低気圧・前線

- 中緯度の偏西風の蛇行は、全球規模のロスビー波の位相として作る。低気圧の存在を蛇行の発生源にしない。低気圧は蛇行する基本流に乗る局所的な気圧・渦度の偏差として扱う。
- ロスビー波は流線関数またはジオポテンシャルの波を定義し、風の南北成分をその勾配から求める。波の位相速度は平均偏西風より遅く、時間とともに東へ進むか停滞する。
- 低気圧の風は、背景風へ渦を足すだけでなく、合成された気圧場の勾配とコリオリ力から求める。赤道付近でコリオリ力を無理に割らず、熱帯の風は別の連続した摩擦項へ遷移させる。
- 前線は低気圧中心から固定半径の螺旋を描く線ではなく、温度・湿度の勾配が強まり、収束・上昇流が生じる帯として求める。低気圧、前線、雲の移流は同じ合成風場・気団場へ接続する。
- 北半球の低気圧は反時計回り、南半球の低気圧は時計回りとする。低気圧の雲帯と前線の雲帯は別のスカラー要因として凝結へ渡し、雲の形状を風向だけから直接描かない。

根拠: NOAA/NWSは前線を異なる温度・風・水分特性を持つ気団の境界と説明し、前線強化を温度勾配と風の収束・発散の変化として扱っている。[NWS Basic Fronts](https://www.weather.gov/lmk/basic-fronts)、[NWS Frontogenesis](https://www.weather.gov/lmk/winterpt2)。偏西風・ジェット気流は位置と向きが変化し、低気圧の移動や前線と関係するが、局所低気圧が全球のロスビー波を生成するとは扱わない。[NWS Jet Stream Glossary](https://marine.weather.gov/glossary.php?word=Jet+Stream)。

### 案Bの責務境界

- **`AuroraField`（新規）**: 磁極、簡易磁気座標、MLT、オーバル境界、活動度代理値、局所発光強度を決める。Three.jsのメッシュを所有しない。
- **`Aurora`**: `AuroraField`のフレーム値を受け取り、カーテンの頂点・色・GPU更新とdisposeだけを担当する。星や地表タイルを参照しない。
- **`AtmosphericWindField`（`src/render/cloud/atmospheric-wind.ts`）**: 高度層の平均風をCPU/TSLの両方で返す。単位はm/sで統一し、ロスビー波や局所低気圧を所有しない。
- **`CloudPatternTransport`（同ファイル）**: `AtmosphericWindField`のm/sを、ノイズ場の有限な位相移流へ変換する。大気の風そのものや低気圧の発生条件を持たない。
- **`CycloneTracks`**: 低気圧の発生・寿命・中心経路を決定論的に返す。風の計算や雲の色を持たない。
- **`RossbyWave`**: ロスビー波の位相・流線関数を返す。局所低気圧を生成せず、`WindField`が勾配から風へ変換する。
- **`AirMass`**: 気団の温度・湿度差と圧縮を追跡する。`WindField`の風を入力にし、雲の描画やオーロラを知らない。
- **`WeatherModel`**: `ClimateMapLike`、`AtmosphericWindField`、気圧・RossbyWave・Cyclones、`AirMass`の組み立てと`WeatherSample`の公開を担当する。局所気圧風と背景風をここで合成するが、雲頂・影・オーロラのメッシュを持たない。
- **`Condensation` / `CloudField`**: `WeatherSample`を雲量・雲頂・薄い雲へ変換する。風場の式を複製しない。

`EarthSurfaceContext`はこの3項目の必須入力にしない。勾配・地形性上昇流・気候画像を読む既存の`ClimateMapLike`境界は残し、地表タイル計画のA4で共有データへ切り替えられるようにする。

### 実装結果（2026-09-10）

案BのE2・C9・C10を workspace3 へ統合した。実装の責務は計画時の仮名から次の実ファイルへ確定した。

- E2: `AuroraField`が簡易双極子の磁極、MLT、活動度代理値、太陽方向による昼側減衰、酸素の緑・赤発光を計算し、`Aurora`は頂点・色バッファとGPU資源だけを管理する。`PointEntity`は表示時刻の太陽方向を地球固定座標へ変換して渡す。
- C9: `AtmosphericWindField`が緯度・高度からm/sの背景風を返す。`CloudPatternTransport`がそのm/sをノイズ位相へ変換し、`Circulation`は物理風を再実装しない。WeatherModel・AirMass・前線・上層雲は同じ背景風を読む。
- C10: `RossbyWave`は流線関数とそこからの風摂動を公開し、局所低気圧は既存の気圧場・コリオリ・摩擦の経路で別に合成する。前線は気団圧縮に気圧由来の上昇流を加えたスカラーとして凝結へ渡す。

コミットは`1c88550b`（初回実装）、`f2e80204`（コードレビューによる磁気座標・共通m/s風場の修正）、`bea13471`（ロスビー波の流線関数境界）である。`npm run typecheck`、`npm run test:render`（85件）、`npm run test:game`（200件）、`git diff --check`を通過した。`npm run cloud-lab:shot`は0 h/25 hの46画像を生成した。`npm run render-lab:shot`は地球を含む対象ケースを生成したあと、既存の未登録タンパク質ケース`pdb-5i4r`で停止したため、その失敗はE2の実装失敗とは分けて記録する。
