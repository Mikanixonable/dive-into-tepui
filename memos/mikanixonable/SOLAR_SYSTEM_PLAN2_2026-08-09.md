## 3. 要件定義

### 3.1 機能要件

- **F-1 衛星**: §2.2 の44衛星を、JPL が公開する平均軌道要素(§4.1)で実装する。
  **JPL の表は基準面がまちまち**(ラプラス面/惑星赤道面/黄道面)であり、その基準面極の
  赤経・赤緯まで同じ表で公開されている。この基準面差を型で表現する(E-3)。
- **F-2 歳差**: JPL の表が公開する昇交点歳差周期 `Pnode [yr]` と近点歳差周期
  `Papsis [yr]` をそのまま使う。これは「軌道要素の変動」の要求に対する直接の答えであり、
  **既存 `satelliteOrbit` の引数形と一致するため新しい摂動モデルを要さない**(E-4)。
- **F-3 太陽周回小天体**: §2.2 の33天体を JPL SBDB の単一エポック接触軌道要素で実装する。
  永年変化率の公開値が無いため rate は 0(第1次計画 R-2 と同じ方針)。
- **F-4 形状(歪み)**: 全天体に形状を持たせる。回転楕円体(惑星の扁平)と三軸楕円体
  (ハウメア・フォボス・ヒペリオン・アマルテア・エロス等)を表現し、メッシュに反映する(E-6)。
  **これは第1次計画に存在しない軸である。**
- **F-5 環の拡張**: §2.2 の6環系。海王星のアダムス環は経度限定のアーク構造を持つ(E-7)。
- **F-6 自転軸・自転**: §2.2 の全天体について、判明しているものは IAU WGCCRE の pole モデル、
  同期回転する衛星はカッシーニ状態(既存の `'cassini'`)、不明なものは自転を持たせない。
- **F-7 テクスチャ**: 実写全球モザイクが存在する天体のみ実写を使う。存在しない天体
  (§4.1 の「テクスチャ」列で「なし」のもの)は**単色**とする — 捏造テクスチャは使わない。
- **F-8 マップ統合**: 追加天体は既存機構(フォーカスラベル・座標系選択・オブジェクト一覧・
  プロパティウィンドウ・クリエイティブモード基準天体)に自動で乗る。ただし規模が
  一桁変わるため、UI 側に階層化が要る(E-10)。
- **F-9 点群の一般化**: 第1次計画 D-4 の `asteroid-field.ts` を、分布定義をデータで受け取る
  汎用の点群系統に一般化し、§2.2 の5群を追加する(E-11)。
- **F-10 重力源**: **μ が判明している全天体を重力源にする。** 今後プレイヤーが惑星・衛星を
  フライバイするミッションを行う予定であり、第1次計画 D-1 が置いた
  「その天体の近傍にプレイヤーが存在しうるか」という判定基準は、**全天体について真になった**。
  この要求は `gravitySource` フラグの**判定基準を変える**のではなく、
  **フラグごと廃止する**ことで満たす(E-14) — 静的フラグの本来の意図(計算の軽量化、
  遠いときはオフ・近いときはオン)は `relevantAttractors` が位置依存で、しかも
  静的フラグより厳密に果たしているため、重ねて絞る理由がもう無い。
  重力積分が舐める配列を短く保つ構造(E-13)は Step3 で実装済み。
- **F-11 ラグランジュ点の生成基準**: ラグランジュ点は「力学的に意味のある系」だけに
  生成する。判定は計算で決め、手で立てたフラグをテストが検証する(E-15)。
  L4/L5 は Routh の線形安定条件(μ < 0.0385209)、L1/L2/L3 はヒル半径が天体半径を
  十分上回ること(r_Hill/R₂ ≥ 10)。**2条件は別々の点集合を独立に許可する** —
  土星-テティス/ディオネのように「L4/L5 は生成するが L1/L2/L3 は生成しない」系がある。
- **F-12 表示の重要度階層**: MAP VIEW のラベル・軌道オブジェクト一覧・配置UIの基準天体が
  **1つの可視性状態を共有する**(E-16)。可視性は「クラス別トグル」と
  「フォーカス中の系の親・兄弟・子」の和で決まり、既定ではトグルを触らずとも
  フォーカスを動かすだけで関係する天体が出入りする。
  100項目規模を選ばせるウィジェットは `SegmentedControl` では成立しないので、
  優先候補+ツリー+絞り込みを持つ `BodyPicker` を新設し、3箇所で共有する(E-17)。

### 3.2 非機能要件

- **NF-1 性能**: 天体数が 27 → 103 になっても、`update`/`sync` フェーズの増分が
  **合わせて 1.5ms を超えない**こと。達成手段は E-1(表示側の空間足切り)、
  E-13(重力窓の位置依存化)、既存の t リングキャッシュ。
  受け入れは固定値ではなく `?perf=1` の実測とする。
  **F-10 により、この要件を満たすことは本計画で最も難しい部分になった** —
  重力積分は RK4 の4ステージ × 全エンティティ(~400)で配列を舐めるため、
  ここだけは天体数に比例させてはならない(E-13)。
- **NF-2 精度の定義**: 第1次計画 NF-2 を継承 — 「科学的に正確」とは**モデルの内部整合性**を
  指し、実在の日付の実際の空の再現ではない。追加で本計画では
  **「出典に無い値を推定で埋めない」**を精度の定義に含める。§4 の表で「データなし」の欄は
  そのまま実装せず、その天体の該当属性を持たせないか、天体自体を対象から外す。
- **NF-3 バンドルサイズ**: `docs/` 配信物の増分は第1次計画 P3 の完了状態からさらに
  **15MB 以下**。達成手段は F-7(実写のある天体だけテクスチャを持つ)と、
  形状モデルメッシュを非目標にすること(§3.3 N-3)。
- **NF-4 型安全**: 新天体は既存の閉じた union に追加し、`SOLAR_SYSTEM` の
  コンパイル強制を維持する。ただし `CELESTIAL_BODIES` の必須項目は**日本語名だけ**に
  縮める(E-9)。点群だけが union の外(第1次計画 N-1 と同じ)。
- **NF-5 セーブ互換**: 第1次計画 NF-5 を継承。`phaseOffsets` は
  `Partial<Record<AttractorId, number>>` なので新 ID は位相0にフォールバックし、
  `SAVE_VERSION` の更新は不要。ただし **F-10 で重力源が増えるぶん、旧スナップショットから
  復元した軌道の将来は保存時点の予測と厳密には一致しなくなる** — 第1次計画 NF-5 が
  土星について受け入れたのと同じ乖離を、本計画でも仕様として受け入れる。
  乖離の大きさは、地球近傍では新規重力源の潮汐差分項が太陽輻射圧(~7e-8 m/s²)より
  さらに桁で小さいため、実用上は検出できない。

### 3.3 非目標(明示的にやらないこと)

- **N-1 放物線・双曲線軌道**(e ≥ 0.98)。第1次計画 N-2 を継承。§2.2 の全天体は
  e < 0.98 に収まる(最大はセドナ e=0.860、ネレイド e=0.751)。
- **N-2 彗星の非重力加速度**。SBDB は Marsden の A1/A2/A3 を公開しており(67P では
  A1=1.0425e-9 au/d²)、既存の `dynamics.ts` の加速度合成に組み込む形は取れる。しかし
  **天体の位置は積分ではなくケプラー要素の解析評価**であって加速度を積む口が無く、
  非重力効果を要素の永年変化率として表すこともできない(a そのものが変わるため)。
  効果の大きさもエンケ彗星で公転周期の 0.009%/周(§4.5)であり、ゲームの時間スケールで
  視認できない。**A1/A2/A3 を SBDB から転記だけしておき、評価はしない。**
- **N-3 探査機由来の形状モデルメッシュ**。エロス・イトカワ・ベンヌ・リュウグウ・67P には
  PDS の高精度形状モデルが公開されているが、数万頂点あり NF-3 と釣り合わない。
  三軸楕円体近似(F-4)で代替する。
- **N-4 共鳴の秤動の再現**。ガリレオ衛星のラプラス共鳴の自由秤動(周期2060日・振幅0.061°)、
  ポリデュークスの秤動(振幅33.9°〜91.4°)、TNO の海王星共鳴の秤動(プルーティノで
  振幅45°〜160°)はいずれも視認できないか、閉形式の公開値が無い(§4.6)。
  ヤヌス/エピメテウスの軌道交換(4年周期、半長軸差48km)だけは**視覚的に意味があるが
  実装しない** — 区分ケプラー軌道の切替という、この系だけのための機構になるため(§7 へ)。
- **N-5 ラプラス共鳴の厳密な保存**。イオ・エウロパ・ガニメデの平均運動は
  `n₁ − 3n₂ + 2n₃ = 0` を満たすが、JPL の公転周期を独立に転記するとこの条件は
  厳密には満たされない。整数比 1:2:4 に固定する手もあるが、**実測周期を優先する**
  (共鳴角のドリフトはゲームの時間スケールで視認できない。受け入れはテストでピン留め)。
- **N-6 小惑星族の proper elements の厳密再現**。族の中心値・広がりは本来、長期の
  準周期展開または数値積分による平均化を要する準不変量である。点群としては接触要素を
  族中心付近にランダム配置すれば見た目は成立する(E-11)。
- **N-7 環の影・環越しの減光**(第1次計画 N-6 を継承)。

## 5. アーキテクチャ上の設計判断

### E-1 表示・判定側の線形走査(重力側は E-13 が済んでいる)

天体が 27 → 103 になる。重力積分側は Step3 の `relevantAttractors` が既に位置依存で
絞っている(C-7、E-13)ので、残るのは **`attractorsAt` を読む表示・判定側**である。
t リングキャッシュが効くので配列の**生成**は1フレームに数回だが、
`strongestAttractor`(`attractor.ts:86`)は呼ばれるたびに全 `Attractor` に対して
`attractorAccel` を計算する。`map-picker.ts` はピック候補ごとにこれを呼ぶため、
候補 150 件 × 103 体 ≈ 15,000 回/フレームになる。

**対処: 静的な `influenceRadius` フィールドは追加しない。既存の `relevantAttractors` を
そのまま流用する。**

- 当初この節は `CelestialBodyDef` に静的な `influenceRadius: number` を持たせる案だったが、
  Step3 が採った `relevantAttractors`(実際の `attractorAccel` 値と閾値の比較)は
  **静的半径より厳密で、天体ごとの定数を1つも要求しない**。閾値を重力用より緩めた値で
  同じ関数を呼べば、`strongestAttractor` の候補削減にそのまま使える。
  **判断: 静的フィールドを新設せず、`relevantAttractors` の閾値引数を使い分ける。**
- `hitCelestialBody`/`isOccluded` は寄与ではなく `radius`(+ margin)そのもので
  棄却できるので、「距離の2乗が(半径+margin)の2乗を超えたら次へ」の平方根回避で足りる。
  これは結果が厳密に不変な純粋最適化。
- **正しさの形**: `strongestAttractor` 側の絞り込みは保守的(実際より広い)であればよく、
  棄却された天体が勝つことはない。テストで「全天体を走査した場合の結果と一致する」ことを
  assert する。
- **第3のフラグ(`physicalPresence` のような)は追加しない**。「火星の裏のラベルが選べる/
  表示専用天体を艦がすり抜ける」という第1次計画 D-1 が明示的に避けた4系統の破綻が、
  フラグの立て方次第で再発する。値による絞り込みは**結果を変えない**ので、その危険が
  構造的に無い。

### E-13 重力窓の位置依存化 — **実装済み(Step3)。設計は当初案より良い形になった**

F-10 により重力源が 5 → 最大71体になる。第1次計画 D-1 が
「RK4 の4ステージ × 全エンティティで舐める配列なので重力側は要素数を5体に固定する
必要がある」と書いた制約に正面から違反するため、重力窓を位置依存にする構造が要る。
**この構造は `for_agent.md` の Step3(コミット `e277e91`)で既に入っている。**

実装された形(C-7):

```ts
// attractor.ts:74-79
export function relevantAttractors(
  r: Vec3, attractors: readonly Attractor[], negligibleAccel: number,
): readonly Attractor[] {
  const thresholdSq = negligibleAccel * negligibleAccel;
  return attractors.filter((attractor) => lenSq(attractorAccel(r, attractor)) >= thresholdSq);
}
```

**当初案(静的な `influenceRadius` との距離比較)より実装の方が良い**:

- 静的半径は天体ごとに1つ定数を要求し、その値の妥当性を人が保証しなければならない。
  **実際の寄与値との比較は定数を1つも要求せず、しかも厳密**(保守的である必要すらない)。
- したがって**`influenceRadius` は新設しない**(E-1 も同じ判断に揃えた)。
  この計画の当初案は撤回する。
- コストは `attractorAccel` を候補数ぶん計算する形になるが、選別は substep ごと
  1回で RK4 の外側(`simulator.ts:108-116`)なので、4ステージぶんの節約がそれを上回る。

**閾値**: `GRAVITY_NEGLIGIBLE_ACCEL = 1e-10` [m/s²](`game/const.ts:204`)。
SRP(~7e-8 m/s²)より2桁小さいので、天体が窓に出入りする瞬間の加速度の不連続は
RK4 の打ち切り誤差に埋もれる。**不連続を消すためのフェードイン係数は採らない** —
係数を掛けた加速度は物理的に間違った値であり、「小さすぎて見えない不連続」を
「常に少しだけ間違った重力」と引き換えにするのは割に合わない。

**残作業(E-B5)**: **3経路のうち `plan-arc.ts:144-149` だけが `mergeAttractors` を
経由していない。** `simulator.ts` と `predictor.ts` は
`mergeAttractors(ephemeris.gravityAttractorsAt(t), entities.attractors())` を通すが、
`plan-arc.ts` は `ephemeris.gravityAttractorsAt(t)` を直接呼ぶため、
**計画線だけが `Asteroid` の重力を無視する**。E-13 が挙げた
「3経路が同じ重力源集合を選ぶこと」という正しさの要件が、現時点で破れている。
症状は「計画どおりに飛んだのに小惑星の近くで軌道がずれる」で、しかも
「計画が当たらない」という形でしか現れないため目視では原因に到達しにくい。
**EP0 の残作業として直し、3経路の一致をテストで固定する。**

**F-10 が連れてくる副次的な要求**(本計画で扱うか否かを明示する):

- **クリエイティブモードの基準天体**: E-14 で `gravitySource` を UI の判定から
  切り離すので、この不変条件は無くなる。基準天体は 5 → 全公転天体になり、
  ウィジェットの作り替えが要る(E-17)。
- **degree2 の欠落**: 水星・金星・火星・天王星・海王星と全衛星は `degree2` を持たない
  (C-1)。**火星の J2 は 1.96e-3 で地球の 1.08e-3 より大きい**ため、火星低軌道の
  ミッションでは昇交点歳差が実際と食い違う。**本計画では扱わず、フライバイの範囲では
  影響しないことを明記するに留める**(低軌道に入るミッションを設計する時点で必要になる)。
- **地球以外の大気**: `atmosphere.ts` は地球専用で、`hitCelestialBody` の margin も
  `REENTRY_ALT`(地球の大気圏突入高度)。火星・金星・タイタン・トリトンには大気があり、
  無大気天体では margin が 0 であるべき。**本計画では扱わない** — フライバイは
  大気圏に入らないため。ただし margin が天体によらず一定である現状は、
  無大気天体の表面すれすれの飛行を不当に禁じるので、§8 に記録する。

### E-2 衛星の親と連星重心 — 既存パイプラインで足りることの確認

`kind: 'satellite'` の `planet: AttractorId` 制約(`solar-system.ts:139`)は、本計画の
衛星すべてで満たされる。カロンの親は冥王星、ディモルフォスの親はディディモス、
ヴァンスの親はオルクス — いずれも第1次計画 D-3 が「`kind: 'planet'` は『太陽を回る天体』の
意味であり IAU の惑星定義とは独立」と決めた通り `kind: 'planet'` で登録される。
**C-2 のとおり ID は `string` に開かれたので、union の手書き更新すら要らない。**
**`attractor.ts` の「太陽系に安定な衛星の衛星は存在しないので表現は要らない」という
コメントは本計画でも真のまま**で、階層を深くする必要はない。

`Ephemeris` の3段パイプライン(恒星 → 惑星-衛星系重心 → 惑星/衛星)は、惑星本体を
「重心 − Σ(μ_衛星/Σμ)·(衛星の惑星相対状態)」で求める。**冥王星-カロンの質量比 0.122
(≈1:8.2、§4.6)でもこの式は正しい** — 月-地球の 1:81 と違って共通重心が冥王星本体の外側に
出るだけで、式は同一である。**追加実装は不要**だが、テストで
「冥王星本体が共通重心の周りを実際に振れる(振幅 ≈ a×μ_Charon/Σμ ≈ 19,600 × 0.109 ≈ 2,130 km、
冥王星半径 1,188 km を超える)」ことをピン留めする — これが「連星系である」ことの機械的な検査になる。

**注意**: 冥王星に5衛星、木星に14衛星(既存4+本計画10)、土星に15衛星が付くと、
`planetHelioState` の重心補正がその惑星の全衛星の `satelliteRelState` を要求する。
第1次計画 D-2 が入れた `satelliteRelState` の t リングキャッシュ(C-7)が効くのは
このためで、キャッシュのスロット数(現在4)が**同時に評価される衛星の数ではなく
時刻の数**であることを確認しておく(実装は id ごとに独立キャッシュ、`ephemeris.ts`)。

### E-3 基準面 — JPL の公開する基準面極をそのまま持つ

第1次計画 D-3b は `KeplerOrbit` に `basisToEci: Quat` を持たせ、衛星の基準面を
「親惑星の赤道面」にして pole モデルから組む方針を決めている。本計画は**その方針を
一段一般化する**必要がある。理由は §4.1 が示す事実:

- JPL の衛星平均要素表は基準面を衛星ごとに使い分ける — **ラプラス面**(木星・土星の
  内側規則衛星、海王星のプロテウス/ラリッサ)、**惑星赤道面**(天王星系、冥王星系)、
  **黄道面**(木星の不規則衛星、ネレイド)。
- ラプラス面は親の赤道面でも軌道面でもなく、**「衛星の昇交点歳差が平均的に含まれる面」**
  = 歳差極に垂直な面である。内側衛星では扁平摂動が支配的で赤道面に近く、外側衛星では
  太陽潮汐が支配的で親の公転面に近づく。親の pole から導出することはできない。
- **JPL は同じ表に基準面極の赤経・赤緯と「基準面と赤道面のなす角(tilt)」を載せている。**
  つまり導出する必要がなく、転記すればよい。

**判断: 基準面を `SatelliteBasis` として型で表し、`basisToEci` はそこから組む。**

```ts
export type SatelliteBasis =
  | { readonly kind: 'ecliptic' }                                  // 既定。月・不規則衛星
  | { readonly kind: 'parentEquator' }                             // 親の pole モデルから組む
  | { readonly kind: 'poleRaDec'; readonly raDeg: number; readonly decDeg: number }; // JPL のラプラス面極
```

- `'poleRaDec'` の ICRF → ECI 変換は、第1次計画 D-6 が決めた
  `ecliptic.ts` の `stdToEci` の export 経由(`raDecToEci`)を**共有する** —
  軸置換の定義元を2箇所に増やさない。
- **月は `'ecliptic'`(既定)のまま変更しない**。既存の摂動テーブル・カッシーニ実装・
  テストがすべて黄道基準で書かれており正しく動いている(第1次計画 D-3b と同じ判断)。
- `'parentEquator'` は天王星系・冥王星系が使う。親の pole モデル(`'iau'` variant)は
  P2 で実装済み(C-8)なのでそのまま読める。ラプラス面の衛星(木星・土星の内側)は
  `'poleRaDec'` で親の pole を要さない。
- **黄道基準の衛星(木星の不規則衛星6体・ネレイド)は基準面の変更を一切要さない**ため、
  `kepler-orbit.ts` の改修(D-3b)すら不要で、既存コードにそのまま乗る。
  → **本計画の最初のフェーズはここから始める**(§6 の EP1)。

第1次計画 D-3b の「衛星の要素は親の赤道面基準のまま登録し、`Ephemeris` が親の pole から
`basisToEci` を組む」という記述は、`'parentEquator'` という1 variant に縮む。
D-3b の残りの指摘(3関数を1箇所で書き換える、`satelliteState` の空テーブル早期 return)は
そのまま有効。

### E-4 歳差率の入力形は既に一致している — 罠は「0 = 歳差なし」

`satelliteOrbit` は `nodePeriodSec`/`perigeePeriodSec` を**正の秒数**で受け取り、
符号は関数自身が付ける(C-5)。JPL の `Pnode [yr]`/`Papsis [yr]` はそのまま入る。
新しい摂動モデルは要らない — **「軌道要素の変動」の要求は、既存の型に値を入れるだけで満たされる。**

**ただし JPL は「歳差しない」を `0.000` で表す**(イオ `Pnode=0.000`、エンケラドゥス
`Pnode=0.000`、ディオネ `Pnode=0.000`、トリトン `Papsis=0.000`、テティス `Papsis=0.005`)。
周期0を素直に `2π/T` に入れると**無限大の歳差速度**になる。

- **`satelliteOrbit` の中で 0 を「歳差なし」(rate = 0)に写す**。変換を1箇所に閉じ、
  呼び出し側に「0 を Infinity に読み替えて渡せ」という規約を作らない。
- テティスの `Papsis = 0.005 yr`(= 1.8日)は**0 ではないが公転周期 1.888 日とほぼ同じ**で、
  近点が1公転につき1周する = 実質的に近点が定義できない円軌道であることを意味する。
  e = 0.001 なので視覚的な影響はない。これを 0 と同じに扱うか値通りにするかは、
  **値通りにする**(NF-2: 出典の値を書き換えない)。テストで「テティスの位置が
  歳差の有無で 1km 以上変わらない」ことを確認して、値通りで問題ないことを裏取りする。

### E-5 形状(歪み)— `ShapeDef` を `CelestialBodyDef` 直下に置く

`CelestialBodyDef` に `shape?: ShapeDef` を追加する。

```ts
export type ShapeDef =
  | { readonly kind: 'spheroid'; readonly equatorRadius: number; readonly polarRadius: number }
  | { readonly kind: 'triaxial'; readonly a: number; readonly b: number; readonly c: number };
```

- **省略時は真球**(半径 `radius`)。これで既存10体は無変更のまま。
- **置き場所の判断**: 表示側(`celestial-registry.ts`)ではなく `physics/` の
  `CelestialBodyDef` に置く。三軸半径は `pck00011.tpc` という物理データの一次ソースから
  来る量であり、表示の都合ではない。表示側が physics から読めば定義が重複しない。
- **`radius`(スカラー)は残す**。`Attractor.radius` は `hitCelestialBody` の衝突球と
  `apsisAltitudes` の高度基準に使われており、**当面は楕円体化しない**。
  値は**赤道半径**を入れる(現在の土星 5.8232e7 = 赤道半径と整合)。
  楕円体の内接球ではなく外接球になるので、極方向で最大 10%(土星)余裕を取ることになり
  **安全側**である。この選択の理由をコメントに書く。
- **`degree2` の `refRadius` とは別の量**。`refRadius` は重力係数が定義された基準半径で、
  形状ではない(C-3 の月の例)。両者を混ぜない。
- **メッシュ側は1箇所の変更で全天体に効く**: `sphere-body.ts:35-58` の
  `mesh.scale.setScalar(r)` を `mesh.scale.set(rx, ry, rz)` に一般化する。
  ECI は Y = 極軸なので、`spheroid` なら `(Re, Rp, Re)`、`triaxial` なら `(a, c, b)` を
  自転姿勢(第1次計画 D-6)より内側の座標で与える — **形状は天体固有の量なので
  自転軸に固定され、ECI 軸には固定されない**。したがって
  `mesh.quaternion`(自転)を書いたうえで `mesh.scale` を書く順序でよい
  (THREE は scale → rotation → translation の順に合成するため、scale は
  ローカル軸で効く)。
- **戦闘ビューの圧縮表示**(`visDist × radius/trueDist`)は3軸すべてに同じ係数を掛ける。
  真の視角を保つという `SphereBody` の性質は変わらない。

### E-6 環 — `RingSystemDef` と、幅が半径の 1/10,000 になる細環

`CelestialBodyDef` に `rings?: RingSystemDef` を追加する。

```ts

  readonly outerRadius: number;  // [m]
  readonly thickness: number;    // [m]。0 なら平坦な annulus
  readonly arcs?: readonly { readonly fromDeg: number; readonly toDeg: number }[]; // 省略時は全周
};
export type RingSystemDef = {
  readonly bands: readonly RingBandDef[];
  readonly texture?: /* アセット識別 */;  // 省略時は単色
};
```

3つの形が要る(§4.4 が示す実データの幅):

1. **テクスチャ焼き込み annulus**(土星 D–A)。P5 の既存実装そのまま。
   `bands` 1本 + テクスチャで、間隙は α で表す。
2. **細環**(天王星の11環、海王星のル・ヴェリエ/アラゴ/アダムス、土星の F 環)。
   幅が 2–100 km に対し半径が 4–10 万 km で、比が **1:10,000 以上**。annulus として
   描くとサブピクセルになり消える。**`outerRadius − innerRadius` が視角で 1px 未満なら
   `THREE.Line` の円で描く**(WebGPU で `LineLoop` が使えないので、始点を重ねた
   `THREE.Line` で閉じる — CLAUDE.md の既知の制約)。判定はカメラ距離依存なので `sync` 側。
3. **扁平トーラス**(木星のハロー環・ゴサマー環2本、土星の E 環)。厚みが半径の
   1〜10% あり平坦ではない。`thickness > 0` の band は半透明の扁平球殻で描く。

- **アーク**(海王星アダムス環)は `arcs` の経度範囲だけ不透明度を上げる。
  経度の基準は §4.4 の通り 1989-08-18 固定の経度系で、**アーク自身も公転している**が、
  その運動は非目標(静止させる)。
- 環の姿勢は P5 の既存実装(pole から組む)を共有する。
- マテリアルは第1次計画 §5.4 の通り
  `{transparent: true, side: THREE.DoubleSide, depthWrite: false}` + 通常アルファ、
  `renderOrder` は惑星本体+1。
- **フェーベ環**(半径 400万–1300万 km、土星本体の 200 倍)は他の環と縮尺が3桁違う。
  同じ `bands` に入れると、土星の環を見るズームでは画面外・土星系を見るズームでは
  他の環がサブピクセルになる。**band ごとに「この band が意味を持つズーム範囲」を
  持たせるのではなく、フェーベ環を独立した band として登録し、2 の細環判定と同じく
  視角で表示を切り替える**(小さすぎるものは点/線に落とし、大きすぎるものは
  そのまま描く)。追加のフィールドは要らない。

### E-7 表示 LOD — 「戦闘/マップ」ではなく「視直径」で切り替える

第1次計画 D-8 は、戦闘ビューの惑星を `SphereBody` とは別の `PointBody`(星シェル上の
輝点スプライト)として登録する方針を決めている。本計画では天体が 103体になり、
**マップビューでも大半の天体が 1px 未満**になる(ベンヌの直径 484m を 1 AU から見た視角は
10⁻⁹ rad)。ビューで実装クラスを分ける方式では、この「マップだが小さすぎる」場合を
表せない。

**判断: `SphereBody` の中に LOD を入れ、視直径が閾値未満なら輝点、超えたら楕円体を描く。
`PointBody` は作らない(第1次計画 D-8 の該当部分を上書きする)。**

- 判定は `sync` の中で、その天体の視角(`2·radius/距離`)を
  `physics/projection.ts` の `metersPerPixel` と突き合わせて行う。この関数は既に
  `ScaleFn` として使われており、新規の投影計算は要らない。
- 輝点の明るさは**視等級ではなく実際の見かけの大きさと反射率**で決めない — 実装が
  重くなるだけで、マップビューでは「そこに何かがある」ことが分かれば足りる。
  第1次計画 D-8 の「等級に応じた3段階のスプライトサイズ」は、
  **戦闘ビューで金星・木星が実際の明るさで見えることに意味がある**ので維持する。
  つまり明るさの決め方だけは2系統残る — 戦闘ビュー(等級)とマップ(一律)。
  **これを1つに統合しない**理由は、前者が「肉眼で見た夜空の再現」、後者が
  「地図上の目印」という別の目的だから。
- **1天体1メッシュのまま**にする(87 draw call)。輝点をインスタンス化して1 draw call に
  まとめる案は、点群(E-11)と違って天体ごとに位置の出所も表示切替も異なるため、
  得るものに対して複雑さが見合わない。87 draw call は現行の弾丸・デブリの規模
  (~400 エンティティ)より小さい。

### E-8 `Ephemeris` の評価コストと衛星の階層

103体の `attractorsAt(t)` 1回は、各天体につきケプラー方程式の Newton 反復を含む評価になる。
キャッシュミスは1フレームあたり数回(C-7 の4スロットリング)なので、**評価回数そのものは
問題にならない**。問題は §E-2 で触れた重心補正の連鎖:

- `planetHelioState('jupiter', t)` は木星の全衛星(既存4 + 本計画10 = 14)の
  `satelliteRelState` を要求する。
- `satelliteRelState('io', t)` は `planetAngles(木星の重心軌道)` を要求する。
- **循環しない**のは、`planetAngles` が惑星-衛星系**重心**の日心ケプラー軌道から
  取られるためで、これは衛星の状態に依存しない(既存の設計)。

したがって階層は深くならず、コストは「惑星ごとに(衛星数)回の衛星評価 + 1回の重心評価」の
線形和にとどまる。**新しい構造は要らない**。ただし:

- **重心補正に入れる衛星を、質量が判明しているものに限る**。§4.1 で GM が
  「データなし」「実質未決定」の衛星(木星の不規則衛星6体、ダフニス、パック、
  ネレイド・プロテウス・ラリッサ)は `mu` を持たない。`mu = 0` として重心補正に
  入れれば寄与0で無害だが、**L 点生成(`lagrangeAt`)が μ=0 で破綻する**。
  → E-15 の判定で L 点を持たない(μ が無ければ Routh の質量比もヒル半径も計算できない)。
- 木星の不規則衛星の質量は不明でも、**既知の質量の総和に対して無視できる**
  (ヒマリア GM=0.15 に対しガニメデ 9887)ので、重心補正から外しても位置は変わらない。

### E-9 レジストリの記述量 — 追加時に必須なのは日本語名だけにする

`CELESTIAL_BODIES`(`celestial-registry.ts:103`)は現在
`Record<SolarSystemId, {name, create(): CelestialBody}>` で、**天体ごとに `create` を
手書きさせる**。103体でこれをやるのは現実的でない。

**判断: `create` を省略可能にし、省略時は `SOLAR_SYSTEM` の `shape`/`radius` と
`BodyClass`(E-16)から既定の `SphereBody`(E-7 の LOD 込み)を組む。
追加時に必須なのは日本語名と `BodyClass` だけ。**

```ts
export const CELESTIAL_BODIES: Record<SolarSystemId, {
  readonly name: string; readonly cls: BodyClass; readonly color?: number; create?(): CelestialBody;
}> = { … }
```

- `color` も省略可能にし、省略時は共通の既定色(灰)。実写テクスチャのある天体だけが
  `create` を書く(地球・月・惑星8、および §4.1 の「全球あり」の衛星)。
- `EarthBody`/`SunBody` のような特別な実装は今まで通り `create` を書く。
- **`name` と `cls` を省略可能にしない**。日本語表示名は導出できない情報であり、
  ID をそのまま表示するフォールバックを許すと、表示名が抜けたまま出荷される。
  `BodyClass` も同様に編集上の判断で導出できない(E-16)。型で必須のまま残すことが
  唯一の防止手段。
- **`fallbackCelestialView`(`celestial-registry.ts:136-141`)は残す**が、これは
  `CELESTIAL_BODIES` の抜けを埋めるためのものではなく、**カスタムレジストリ
  (`stage-debug-alt-system.ts` のような、`SOLAR_SYSTEM` とは別の天体系)の id を
  描くためのもの**。`Record<SolarSystemId, …>` の網羅性はコンパイラが保証し続ける。

### E-14 `gravitySource` フラグの廃止 — 1つのフラグが無関係な3つの問いに答えている

**このフラグは今、3つの別々の問いに使われている**(grep で確認した全消費者):

| 消費者 | 答えている問い |
|---|---|
| `ephemeris.ts:131` | **重力積分の候補にするか**(本来の意図) |
| `ship-placer-panel.ts:85` | **配置UIの基準天体として選べるか** |
| `frame-labels.ts:25-26` | **座標系選択に出すか** |

`.claude/skills/refactor-fixed/SKILL.md` の「同時に切り替わるフラグの分離」の裏返しで、
**無関係な問いが1つのフラグに相乗りしている**。実害は既に出ている —
P1〜P6 で追加した水星・金星・火星・天王星・全衛星・全準惑星・彗星は
`gravitySource: false` なので、**基準天体としても座標系としても選べない**(E-B7)。
ユーザー報告の「新しく追加された天体を基準天体に選べない」はこれが原因。

**判断: `gravitySource` フラグを廃止する。3つの問いをそれぞれ本来の根拠へ差し戻す。**

1. **重力積分の候補** — フラグの本来の意図は「計算の軽量化」であり、
   「遠い時はオフ、近い時はオン」という切り分けである。**それは既に
   `relevantAttractors` が位置依存で、しかも静的フラグより厳密に行っている**(E-13)。
   静的フラグが重ねて絞る理由はもう無い。`gravityAttractorsAt(t)` の候補集合は
   **`mu > 0` の全天体**とし、実際の絞り込みは `relevantAttractors` に任せる。
   - **`mu === 0` を除く理由**: §4.1 の「データなし」「実質未決定」の約15体
     (木星の不規則衛星、ダフニス、パック、ネレイド・プロテウス・ラリッサ、
     ケルベロス・ステュクス、大半の TNO)は質量が測定されていない。
     `mu = 0` なら `attractorAccel` は厳密に 0 を返すので `relevantAttractors` が
     必ず落とすが、**候補集合の段階で除いておくほうが「なぜ落ちたか」が明示的**になる。
   - **候補集合の大きさ**: 現在の27体はすべて μ が判明しているので、EP0 の時点で
     **5 → 27** になる。全天体を足し終えた時点(103体)では、§4.1 で μ が
     「データなし」「実質未決定」の約15体が `mu: 0` で外れるので **≈ 88** に落ち着く。
     走査が伸びるぶんはあるが、選別は substep ごと1回・RK4 の外側なので、
     4ステージぶんの節約がそれを上回る(E-13)。
2. **配置UIの基準天体** — これは物理ではなく**UI の関心事**なので、
   UI 側が自前の基準で決める(E-16 の可視性状態を読む)。
3. **座標系選択** — 同上。

**この廃止は F-10(全天体を重力源にする)の実装そのものでもある。**
判定基準を「近傍に行きうるか」から「μ の有無」へ変えるだけでは 2・3 の相乗りが残るので、
**フラグごと消すのが正しい形**になる。

`solar-system.ts:94` の `GravitySourceFlag` 型と `solar-system.ts:111-114` の
コメント(「クリエイティブモードで基準天体・ラグランジュ系として選択できる天体は
必ず true」という不変条件)は削除する。第1次計画 D-1 の記述と
`.claude/skills/refactor-fixed/SKILL.md` も同じ変更セットで直す。

### E-15 ラグランジュ点を持つ天体の基準 — 力学的に意味を持つ系だけに絞る

現在は `lagrangeLabels?: boolean` を手で立てる(地球・月・木星・土星の4体、
`solar-system.ts:253/279/410/469`)。103体化にあたり**基準を明文化し、計算で決める**。

判定は**2つの独立した条件の論理積**で、両方とも既知の値から機械的に計算できる。

#### 条件1(L4/L5): Routh の線形安定条件

質量比 μ = m₂/(m₁+m₂) が **μ < μ_c ≈ 0.0385209**(27μ(1−μ) < 1、同値で
M₁/M₂ > (25+3√69)/2 ≈ 24.96)を満たすこと。満たさない系では L4/L5 は
**線形不安定**であり、秤動する軌道が存在しないので「行き先」として無意味。
出典: [Lagrange point (Wikipedia)](https://en.wikipedia.org/wiki/Lagrange_point)。

**この条件で落ちる系(計算値)**:

| 系 | μ | 判定 |
|---|---|---|
| 冥王星-カロン | 0.1087 | **不安定**。一次資料も「Pluto–Charon cannot host long-lived Trojan companions」と明言([arXiv:2510.13479](https://arxiv.org/html/2510.13479)) |
| オルクス-ヴァンス | 0.121 | **不安定**。ALMA による重心直接測定で質量比 13.7%±1.3%([Vanth (moon)](https://en.wikipedia.org/wiki/Vanth_(moon))) |

**地球-月(μ=0.0122)は条件1を通るが、太陽摂動により実際には L4/L5 に天体が
留まらない**ことが知られている([MNRAS 535, 2619](https://academic.oup.com/mnras/article/535/3/2619/7905891))。
ただし**この「第三体摂動による不安定化」を判定するクローズドフォームの式は
文献に存在しない**(調査で確認済み)ため、条件として実装しない。
実在するトロヤ天体を持つ系は μ が 10⁻⁷〜10⁻³ に収まるという経験則はあるが、
これは相関であって因果的な閾値ではないので、**推定で閾値を作らない**(NF-2)。
地球-月 L4/L5 は既にゲームに存在し、ハロー軌道の配置先としても使われているので、
**現状どおり生成する**。

#### 条件2(共線点 L1/L2/L3): ヒル半径が天体自身の半径を十分上回ること

L1/L2 の二次天体からの距離は r_Hill = a·(μ/3)^(1/3)。
**r_Hill が二次天体の物理半径 R₂ より小さい/同程度なら、L1/L2 は天体の内部か
表面すれすれに来て、行き先にもハロー軌道の中心にもならない。**
この条件式は幾何学的に自明な計算的事実で、文献引用を要さない
(逆に、この現象を具体例で論じた文献は調査で見つからなかった)。

**閾値は r_Hill / R₂ ≥ 10 とする。** 根拠: `physics/halo.ts` のハロー軌道は
振幅が γ·a(= r_Hill)のオーダーで、その軌道が天体表面と交差しないためには
少なくとも1桁の余裕が要る。**この値は理論値ではないので、実装時に
`CREATIVE_HALO_*` の既定振幅と突き合わせて調整する余地を残す。**

**計算結果**(μ・r_Hill・R₂ は §4.1/§4.2/§4.3 の値から算出):

これが「2つの独立した条件の論理積」ではなく「点ごとの2つの条件」である理由。

**したがって `lagrangeLabels: boolean` を2つに分ける**:

```ts
// solar-system.ts
readonly lagrangeCollinear?: boolean;  // L1/L2/L3(条件2: r_Hill/R₂ >= 10)
readonly lagrangeTriangular?: boolean; // L4/L5(条件1: μ < 0.0385209)
```

- **手で立てるのではなく、レジストリ登録時に計算して立てる**のが望ましいが、
  `μ` は `SOLAR_SYSTEM` 内で親の `mu` を参照する必要があり、オブジェクトリテラルの
  自己参照になる。**実装時に「登録は手書き、テストが計算値と一致することを検査する」
  形にする** — 値の正しさはテストが保証し、レジストリは読んで分かる形を保つ。
- **テスト**: 全公転天体について、条件1・条件2を計算した結果が
  レジストリのフラグと一致すること。閾値のすぐ近くにある系(土星-テティス 3.96、
  海王星-トリトン 10.79)は、閾値を動かすと判定が変わるので特に明示的に assert する。

### E-16 表示の重要度階層 — **3つのUIが1つの可視性状態を共有する**

天体27体+L点20 = 47 件でも既に `ObjectListPanel` は使いにくく(E-B6)、
103体化で MAP VIEW のラベル・軌道オブジェクト一覧・配置UIの3つが同時に溢れる。

**判断: 3つそれぞれにフィルタUIを作るのではなく、「今なにが関心の対象か」という
1つの状態を3つが共有する。**

理由は性能ではなく**メンタルモデル**である。3つに別々のフィルタがあると、
「マップには出ているのに一覧に無い」「一覧で見えているのに配置で選べない」が起きる。
**「マップに出ているものが一覧に出て、配置でも選べる」**が唯一覚えやすい規則で、
ユーザー要求の「意図したボタンに迷わずすぐ辿り着ける」はこの一貫性で担保される。

#### 16-1. 天体の重要度クラス — `physics/` ではなく表示側に置く

```ts
// game/celestial/celestial-registry.ts
export type BodyClass = 'star' | 'planet' | 'dwarf' | 'satellite' | 'smallBody';
```

- **置き場所の判断**: `solar-system.ts` の `kind`(star/planet/satellite)は
  **力学上の分類**(中心が恒星か惑星か)であって重要度ではない。現に本計画は
  準惑星・小惑星・彗星をすべて `kind: 'planet'` として登録する(第1次計画 D-3)。
  重要度は**編集上の判断**なので、日本語表示名と同じく `celestial-registry.ts` に置く。
  CLAUDE.md の「日本語表示文字列は `physics/` に現れない」と同じ線引き。
- ラグランジュ点は天体ではないので `BodyClass` を持たず、独立したトグルにする。

#### 16-2. 可視性の決まり方 — 「クラスのトグル」と「フォーカスの文脈」の和

```ts
// 可視性の唯一の判定。3つのUIがこれを読む。
visibleBodyIds(focusId, classToggles): ReadonlySet<AttractorId>
```

1. **常に見えるもの**: 恒星と惑星(`'star'`/`'planet'`)。太陽系の骨格であり、
   これが消えると現在地を見失う。
2. **文脈で自動的に見えるもの**: **フォーカス中の天体の親・兄弟・子**。
   木星にフォーカスすればガリレオ衛星が現れ、離れれば引っ込む。
   親子関係は既存の `primaryOf(registry, id)`(`solar-system.ts`)から導出でき、
   **新しいデータを1つも要さない**。
3. **トグルで足すもの**: 準惑星・衛星・小天体・ラグランジュ点の4トグル。
   既定は全部 OFF(1 と 2 で足りるため)。

**ユーザー要求「表示していないものはデフォルトで収納される」への答えは 2 である** —
トグルを触らなくても、フォーカスを動かすだけで関係するものが出入りする。
トグルは「常に全部の衛星を見たい」という明示的な意思表示のときだけ触る。

**所有者**: `visibleBodyIds` はカメラのフォーカス(`OverviewCamera.focus`)と
クラストグルの両方を要求する。トグルの状態は **`CameraSystem` が持つ** —
既にフォーカスと MAP VIEW パネルを所有しており(CLAUDE.md の「MAP VIEW パネルの
全コントロールは `overviewCamera` の状態を書く」)、同じ場所に置くのが自然。
`visibleBodyIds` 自身は DOM も THREE も要らない純関数として
`celestial-registry.ts` 側に置き、`CameraSystem` が状態を渡して呼ぶ。

#### 16-2b. 「距離が遠いもの」を軸にしない理由

ユーザー要求には「距離が遠いもの」でフィルタしたい、という項目がある。
**これを直接の軸にはしない。** カメラのズーム距離は連続的に変わるので、
閾値でオン/オフすると**ズーム操作の途中でラベルや一覧の行が明滅する**。
一覧の行が出たり消えたりする画面は、探しているものを見つける役に立たない。

代わりに、距離が本当に意味しているもの —「今どの系を見ているか」— を
**フォーカスの親子関係(2)で表す**。これは離散的で、ユーザーが明示的に
動かしたときだけ変わるので明滅しない。木星にフォーカスすればガリレオ衛星が出る、
というのは「木星に近づいた」ことの安定な言い換えになっている。

ただし**マップ上のラベルの描画密度だけは距離に連動させてよい** —
既にある `FOCUS_LABEL_PRIORITY_PX` の近接判定(`focus-markers.ts:83-85`)が
画面距離で間引く仕組みなので、そこを拡張する。これは
「一覧から消える」のではなく「画面が混んでいるので重なりを避ける」処理であり、
探し物の妨げにならない。

#### 16-3. 3つのUIへの反映

| UI | 反映のしかた |
|---|---|
| MAP VIEW のラベル(`focus-markers.ts`) | `visibleBodyIds` に無いラベルは `update` の位置計算ごと飛ばす。**E-B4 の毎フレーム全数 `positionOf`/`lagrangeAt` がここで同時に解決する** — 見えないものは計算もしない |
| 軌道オブジェクト一覧(`ObjectListPanel`) | 天体セクションを**親子ツリー**(太陽 > 惑星 > 衛星)にし、`visibleBodyIds` の外は畳んだ「その他 (N)」に入れる。**完全に隠さない** — 一覧は「何が存在するか」の窓でもあるため |
| 配置UIの基準天体(`ship-placer-panel.ts`) | `visibleBodyIds` を優先順に並べ、外のものは検索で辿れる(E-17) |

**トグルUIの置き場所は MAP VIEW パネル**(`overview-camera-panel.ts`)。
「マップに何を表示するか」の設定であり、視点・座標系と同じ場所にあるのが自然。
一覧パネル側にも同じトグルを重複して置かない — 状態が1つであることが
見た目でも分かるようにする。

### E-17 100項目規模を選ばせるウィジェット — `SegmentedControl` では成立しない

`SegmentedControl`(`hud/buttons.ts:18`)は `.hud-seg` に項目を横並びに積むだけで、

**判断: 新ウィジェット `BodyPicker` を1つ作り、3箇所すべてで使う。**

- **形**: 現在の選択を表示するボタン → クリックでポップアップ。ポップアップは
  (a) **優先候補の数個**(フォーカス中の天体・自艦の現在の中心天体・地球・月)を
  上部にボタンで、(b) その下に E-16 の親子ツリー、(c) 最上部に絞り込み入力。
- **「迷わずすぐ辿り着ける」への答えは (a)** — 実際に選ばれる天体はほぼ常に
  「今見ているもの」か「今いるところ」なので、それを1クリック目に置く。
  ツリーと検索は「それ以外」のための退避路であって、主経路ではない。
- **既存のポップアップ機構を流用する**。`hud/context-menu.ts` の `ContextMenu<T>` は
  画面位置指定・外側クリックで閉じる・キャプチャフェーズのリスナーを既に持っており、
  `hud/layout.ts` の `clampOverlayPosition` も共有できる。**新しい閉じ方の規則を
  発明しない**(`/add-feature` の手順どおり、既存の再利用可能な実装を先に探す)。
- **座標系選択は2段にする**(第1次計画 D-9/本計画 E-10 の方針)。
  `ReferenceFrame` は `{center, rotatingWith}` の直積(`frame.ts:23-26`)なので、
  **`BodyPicker` で天体を選び、慣性/回転をトグルで選ぶ**だけで 205 項目が

- **`SegmentedControl` は残す**。項目が数個で固定のもの(期間・単位・種類・

### EP1: 黄道基準の衛星(木星の不規則衛星6体 + ネレイド)

既存の `satelliteOrbit` に値を入れるだけで動く7体を先に入れ、**衛星の追加が
既存機構にそのまま乗ることを実証する**。P4 で8衛星が同じ手順で入っているので、
形は既に実証済み。

1. `SOLAR_SYSTEM` に §4.1 の値を登録(**`AttractorId` が `string` に開かれ
   `SolarSystemId` が自己生成されるので、union の手書き更新は不要** — C-2)。
   この7体はいずれも μ が未測定なので `mu: 0`、L点フラグは両方 false、
   周期項テーブルは空配列。
2. `satelliteOrbit` の「`Pnode`/`Papsis` = 0 は歳差なし」変換(E-4)。
3. `CELESTIAL_BODIES` の `create`/`color` 省略可能化(E-9)。
4. GM 不明の6体を重心補正から外す(E-8)。
5. **`satelliteState` の空テーブル早期 return**(第1次計画 D-3b の数値ガード)—
   周期項が空の衛星は黄経・黄緯・動径への分解を通さず二体解をそのまま返す。
   これがないと、`rho0 = hypot(x,y)` の除算で黄道極付近を通る軌道
   (パシファエ i=148.3°、シノーペ i=157.3°)の速度が NaN になる。
   **本計画で最初に NaN を踏むのはここ**なので EP1 に置く。

## 7. 検証方針

- 各フェーズで `npm run typecheck`(常時)+ `npm run test:physics`
  (physics/ を触るフェーズ: EP0, EPU, EP1, EP2, EP3, EP5, EP6, EP7)。
- 追加するテストの型は第1次計画 §7 を継承 — 公転周期のケプラー第3法則一致、
  既知の幾何値のピン留め、高離心率ソルバの往復精度、リファクタの非破壊性。
  本計画で新しく加わる型:
  - **最適化の結果不変性**(E-1 の足切りが全走査と一致する)
  - **積分・予測・計画の3経路が同じ重力窓を選ぶ**(E-13。これだけは性能ではなく
    正しさのテストで、破れると「計画線が実際の軌道とずれる」形でしか表面化しない。
    **現時点で実際に破れている**ので、EP0 では「まず落ちるテストを書く」)
  - **フラグ廃止の非破壊性**(E-14。候補集合が 5 → 27 に増えても LEO・低月軌道の
    結果が機械精度で変わらないこと = `relevantAttractors` が正しく落としている証明)
  - **ラグランジュ点フラグと計算値の一致**(E-15。閾値の近くにある系
    — 土星-テティス 3.96、海王星-トリトン 10.79 — を明示的に assert する)
  - **基準面の取り違え検出**(天王星系が黄道基準で登録されていたら i が 98° ずれる)
  - **形状の外接性**(`radius >= max(shape の3軸)`)
  - **連星重心の実在性**(冥王星本体の振幅が自身の半径を超える)
- **UI は `test:physics` では検査できない**(DOM に依存する)。EPU の受け入れは
  `npm run dev` での目視と `?perf=1` の実測に限る。ただし
  **`visibleBodyIds`(E-16)と `BodyClass` の分類、E-15 の判定式は DOM を持たない
  純粋な関数として切り出し**、そこだけはテスト対象にする — UI の「見え方」ではなく
  「何が見えるべきか」の規則は機械的に検査できる形に保つ。
- 実行時確認(`/verify`)はユーザーが求めたときのみ。フェーズ受け入れの「見える」系
  条件は `npm run dev` での目視を想定する。

## 8. 将来拡張(本計画の非目標だが要求が出うるもの)

- **ヤヌス/エピメテウスの軌道交換**(N-4)。4年周期・半長軸差48km の区分ケプラー軌道の
  切替。視覚的には意味があるが、この系だけのための機構になる。
- **トロヤ衛星**(テレスト・カリプソ・ヘレネ・ポリデュークス)。前3者は
  「親衛星と同一要素 + 平均黄経 ±60°」で表せる(§4.6)。ポリデュークスの秤動は
  閉形式の公開値がない。
- **探査機由来の形状モデルメッシュ**(N-3)。エロス・イトカワ・ベンヌ・リュウグウ・67P。
  `tools/export-models.mjs` 型のアセットパイプラインで PDS の形状モデルを
  低ポリゴン化して焼き込めば NF-3 に収まる可能性がある。
- **彗星の非重力加速度の評価**(N-2)。天体位置を積分に切り替える必要がある。
- **彗星の尾**(第1次計画 §8 を継承)。反日方向のイオンテイルと軌道遅れ方向のダストテイル。
- **半球だけ観測されている天体の「未観測」表現**(E-12)。天王星系の5衛星は
  南半球のテクスチャしか存在しない。
- **小惑星族の proper elements**(N-6、§4.6)。AstDyS からの取得が前提。
- **TNO の海王星共鳴の秤動**(N-4)。プルーティノ・トゥーティノの分類ごとの表現。
- **`hitCelestialBody` の楕円体化**(E-5)。土星の極方向で 10% 保守的になっている
  現状が、実際に問題になった場合。
- **第三体摂動によるラグランジュ点の実効的な不安定化**(E-15)。地球-月 L4/L5 は
  Routh の線形安定条件を通るが、太陽摂動により実際には天体が留まらない
  ([MNRAS 535, 2619](https://academic.oup.com/mnras/article/535/3/2619/7905891))。
  これを判定するクローズドフォームの式は文献に存在せず、系ごとの数値積分でしか
  確かめられない。ゲームとして「行っても留まれない点」を区別して見せたくなったときに、
  数値積分による事前計算(実行時ではなく、実装時に一度だけ)で判定する余地がある。
- **土星-テティス/ディオネのトロヤ衛星**(テレスト・カリプソ・ヘレネ・ポリデウケス)。
  E-15 でこの2系は L4/L5 を生成すると決めたので、**実在の天体をそこに置く**のが
  自然な次の一歩になる。前3者は「親衛星と同一要素 + 平均黄経 ±60°」で表せる(§4.6)。
- **地球以外の天体の `degree2`**(E-13 の副次要求)。火星の J2 = 1.96e-3 は
  地球の 1.08e-3 より大きく、火星低軌道の昇交点歳差に効く。木星・土星の J2 は
  1.47e-2 / 1.63e-2 とさらに一桁大きく、ガリレオ衛星軌道以内の運用では無視できない。
  フライバイでは影響しないが、周回ミッションを設計する時点で必要になる。
- **天体ごとの大気と表面接触 margin**(E-13 の副次要求)。`atmosphere.ts` は地球専用、
  `hitCelestialBody` の margin は全天体一律。火星・金星・タイタン・トリトンには
  大気があり、逆に無大気天体では現状の margin が表面すれすれの飛行を不当に禁じる。
  エアロブレーキを使う遷移や、月面・小惑星への接近運用を作る時点で必要になる。
