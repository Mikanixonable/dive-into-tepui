### 1.2 コードの事実(本計画が前提とする形)

- **C-1 登録済み天体は10体**: 太陽・地球・月・水星・金星・火星・木星・土星・天王星・海王星
  (`solar-system.ts:136-343` の `SOLAR_SYSTEM`)。`gravitySource: true` は
  太陽・地球・月・木星・土星の5体、残る4惑星は `false`。
- **C-2 天体IDは閉じた文字列リテラル union**(`attractor.ts:10-16`):
  ```ts
  export type StarId = 'sun';
  export type PlanetId = 'earth' | 'mercury' | 'venus' | 'mars' | 'jupiter' | 'saturn' | 'uranus' | 'neptune';
  export type SatelliteId = 'moon';
  export type AttractorId = StarId | PlanetId | SatelliteId;
  export type OrbitingId = PlanetId | SatelliteId;
  ```
  ID を1つ追加してコンパイルエラーで登録を強制されるレジストリは **2つ**に減っている —
  `SOLAR_SYSTEM`(`satisfies Record<AttractorId, CelestialBodyDef>`)と
  `CELESTIAL_BODIES`(`celestial-registry.ts:29-40`、`Record<AttractorId, {name, create}>`)。
  第1次計画 §1 が挙げた3つ目の `LAGRANGE_DEFAULT_AMPLITUDE_KM` は
  `Partial<Record<OrbitingId, …>>` 化済み(`ship-placer-panel.ts:111`)なので強制されない。
  日本語表示名は `CELESTIAL_BODIES` の1箇所が定義元で、`ATTRACTOR_NAMES`・
  `focus-markers.ts:28` の `LABEL_NAMES`・`FRAME_ITEMS` はすべてそこからの導出。
- **C-3 形状はスカラー半径1個しか持たない**。`CelestialBodyDef` の `radius`
  (`solar-system.ts:59,64,72`)も `Attractor` の `radius`(`attractor.ts:37`)も
  `number` 1個で、扁平率・三軸楕円体を表す型・フィールドは**存在しない**。
  メッシュ側も `SphereBody` が `THREE.SphereGeometry(1,48,24)` の単位球に
  `mesh.scale.setScalar(...)` を掛けるだけで(`sphere-body.ts:35-58`)、
  XYZ非等方スケールを掛けている箇所はコードベース全体に無い。
  `Degree2GravityDef`(`solar-system.ts:45-50`)は重力ポテンシャルの2次係数であって
  幾何形状ではない — 地球が `R_EARTH`(平均半径)と `R_EARTH_EQ`(赤道半径)、月が
  `R_MOON` と `R_MOON_GRAVITY` を別定数で持つのは、重力の基準半径と表面半径が別の量
  だからで、表面形状そのものは依然として球である。
- **C-4 環(ring)の実装は一切存在しない**。`src/physics`・`src/game/celestial`・`src/render`
  を横断しても、天体の環に関するフィールド・クラス・メッシュは無い(`ring` の文字列は
  `render/ships.ts` のデブリ形状名と `ephemeris.ts` の `TimeRing<T>` キャッシュのみ)。
- **C-5 衛星モデルは月1体に最適化されている**。`satelliteOrbit`(`satellite-orbit.ts:41-54`)の
  引数は `{a, e, incDeg, raan0Deg, lonPeri0Deg, l0Deg, periodSec, nodePeriodSec,
  perigeePeriodSec, lonTerms, latTerms, distTerms}`。**歳差は「昇交点歳差の周期」と
  「近点歳差の周期」を正の秒数で受け取り、符号(昇交点は逆行・近点は順行)は
  `satelliteOrbit` 自身が付ける**(同ファイルの関数コメント)。
  §4.1 で示す通り、この入力形は JPL が公開する衛星平均要素表の列とそのまま一致する。
- **C-6 基準面は黄道面に固定**。`kepler-orbit.ts:94/102-106/113-116/129` が
  `eclToEci`/`Q_ECL_TO_ECI`/`ECL_POLE`/`ECL_VERNAL`/`Q_ECLY_TO_ECI` を直接使う。
  この3関数(`normalFromAngles`/`directionFromAngles`/`rotationFromAngles`)は
  `Ephemeris` の `orbitFrameRotationAt`/`orbitNormalAt`/`lagrangeAt`/`frameTransformAt` が
  読むため、位置評価だけを差し替えると回転座標系・軌道法線・ラグランジュ点が
  黄道基準のまま残る(第1次計画 D-3b と同じ指摘)。
- **C-7 `Ephemeris` の窓は2つ**。`attractorsAt(t)`(全10体、`ephemeris.ts:296`)と
  `gravityAttractorsAt(t)`(5体、`ephemeris.ts:306`)。どちらも4スロットの
  t リングキャッシュ付きで、**同一 t には同一配列参照を返す(書き換え禁止)**。
  `attractorsAt` を読むのは遮蔽判定(`map-picker.ts` の `isOccluded`)・表面接触
  (`hitCelestialBody`)・中心天体解決(`strongestAttractor`)・積分刻み
  (`localOrbitPeriod`)・クリエイティブモードの基準天体解決。
- **C-8 自転軸は `Degree2GravityDef` の中にしか存在しない**(`PoleModel`、
  `solar-system.ts:40-42`)。`'eciPole'`(地球)と `'cassini'`(月)の2 variant のみで、
  `degree2` を持たない6惑星は自転軸を持たない。`SphereBody` は姿勢を一切書かない
  (`mesh.position`/`mesh.scale` のみ)。

## 3. 要件定義

### 3.1 機能要件

- **F-1 衛星**: §2.2 の44衛星を、JPL が公開する平均軌道要素(§4.1)で実装する。
  **JPL の表は基準面がまちまち**(ラプラス面/惑星赤道面/黄道面)であり、その基準面極の
  赤経・赤緯まで同じ表で公開されている。この基準面差を型で表現する(E-3)。
- **F-2 歳差**: JPL の表が公開する昇交点歳差周期 `Pnode [yr]` と近点歳差周期
  `Papsis [yr]` をそのまま使う。これは「軌道要素の変動」の要求に対する直接の答えであり、
  **既存 `satelliteOrbit` の引数形と一致するため新しい摂動モデルを要さない**(E-4)。
- **F-3 太陽周回小天体**: §2.2 の33天体を JPL SBDB の単一エポック接触軌道要素で実装する。
  永年変化率の公開値が無いため rate は 0(第1次計画 R-2 と同じ方針)。
- **F-4 形状(歪み)**: 全天体に形状を持たせる。回転楕円体(惑星の扁平)と三軸楕円体
  (ハウメア・フォボス・ヒペリオン・アマルテア・エロス等)を表現し、メッシュに反映する(E-6)。
  **これは第1次計画に存在しない軸である。**
- **F-5 環の拡張**: §2.2 の6環系。海王星のアダムス環は経度限定のアーク構造を持つ(E-7)。
- **F-6 自転軸・自転**: §2.2 の全天体について、判明しているものは IAU WGCCRE の pole モデル、
  同期回転する衛星はカッシーニ状態(既存の `'cassini'`)、不明なものは自転を持たせない。
- **F-7 テクスチャ**: 実写全球モザイクが存在する天体のみ実写を使う。存在しない天体
  (§4.1 の「テクスチャ」列で「なし」のもの)は**単色**とする — 捏造テクスチャは使わない。
- **F-8 マップ統合**: 追加天体は既存機構(フォーカスラベル・座標系選択・オブジェクト一覧・
  プロパティウィンドウ・クリエイティブモード基準天体)に自動で乗る。ただし規模が
  一桁変わるため、UI 側に階層化が要る(E-10)。
- **F-9 点群の一般化**: 第1次計画 D-4 の `asteroid-field.ts` を、分布定義をデータで受け取る
  汎用の点群系統に一般化し、§2.2 の5群を追加する(E-11)。
- **F-10 重力源**: **μ が判明している全天体を重力源にする。** 今後プレイヤーが惑星・衛星を
  フライバイするミッションを行う予定であり、第1次計画 D-1 が置いた
  「その天体の近傍にプレイヤーが存在しうるか」という判定基準は、**全天体について真になった**。
  したがって `gravitySource` の意味は「近傍に行きうるか」から
  **「μ の測定値が存在するか」**へ変わる(E-13)。この変更により、重力積分が舐める配列の
  長さが 5 → 最大 71 になるため、**重力窓を位置依存にする構造変更が必須**になる(E-13)。

### 3.2 非機能要件

- **NF-1 性能**: 天体数が 10 → 86 になっても、`update`/`sync` フェーズの増分が
  **合わせて 1.5ms を超えない**こと。達成手段は E-1(表示側の空間足切り)、
  E-13(重力窓の位置依存化)、既存の t リングキャッシュ。
  受け入れは固定値ではなく `?perf=1` の実測とする。
  **F-10 により、この要件を満たすことは本計画で最も難しい部分になった** —
  重力積分は RK4 の4ステージ × 全エンティティ(~400)で配列を舐めるため、
  ここだけは天体数に比例させてはならない(E-13)。
- **NF-2 精度の定義**: 第1次計画 NF-2 を継承 — 「科学的に正確」とは**モデルの内部整合性**を
  指し、実在の日付の実際の空の再現ではない。追加で本計画では
  **「出典に無い値を推定で埋めない」**を精度の定義に含める。§4 の表で「データなし」の欄は
  そのまま実装せず、その天体の該当属性を持たせないか、天体自体を対象から外す。
- **NF-3 バンドルサイズ**: `docs/` 配信物の増分は第1次計画 P3 の完了状態からさらに
  **15MB 以下**。達成手段は F-7(実写のある天体だけテクスチャを持つ)と、
  形状モデルメッシュを非目標にすること(§3.3 N-3)。
- **NF-4 型安全**: 新天体は既存の閉じた union に追加し、`SOLAR_SYSTEM` の
  コンパイル強制を維持する。ただし `CELESTIAL_BODIES` の必須項目は**日本語名だけ**に
  縮める(E-9)。点群だけが union の外(第1次計画 N-1 と同じ)。
- **NF-5 セーブ互換**: 第1次計画 NF-5 を継承。`phaseOffsets` は
  `Partial<Record<AttractorId, number>>` なので新 ID は位相0にフォールバックし、
  `SAVE_VERSION` の更新は不要。ただし **F-10 で重力源が増えるぶん、旧スナップショットから
  復元した軌道の将来は保存時点の予測と厳密には一致しなくなる** — 第1次計画 NF-5 が
  土星について受け入れたのと同じ乖離を、本計画でも仕様として受け入れる。
  乖離の大きさは、地球近傍では新規重力源の潮汐差分項が太陽輻射圧(~7e-8 m/s²)より
  さらに桁で小さいため、実用上は検出できない。

### 3.3 非目標(明示的にやらないこと)

- **N-1 放物線・双曲線軌道**(e ≥ 0.98)。第1次計画 N-2 を継承。§2.2 の全天体は
  e < 0.98 に収まる(最大はセドナ e=0.860、ネレイド e=0.751)。
- **N-2 彗星の非重力加速度**。SBDB は Marsden の A1/A2/A3 を公開しており(67P では
  A1=1.0425e-9 au/d²)、既存の `dynamics.ts` の加速度合成に組み込む形は取れる。しかし
  **天体の位置は積分ではなくケプラー要素の解析評価**であって加速度を積む口が無く、
  非重力効果を要素の永年変化率として表すこともできない(a そのものが変わるため)。
  効果の大きさもエンケ彗星で公転周期の 0.009%/周(§4.5)であり、ゲームの時間スケールで
  視認できない。**A1/A2/A3 を SBDB から転記だけしておき、評価はしない。**
- **N-3 探査機由来の形状モデルメッシュ**。エロス・イトカワ・ベンヌ・リュウグウ・67P には
  PDS の高精度形状モデルが公開されているが、数万頂点あり NF-3 と釣り合わない。
  三軸楕円体近似(F-4)で代替する。
- **N-4 共鳴の秤動の再現**。ガリレオ衛星のラプラス共鳴の自由秤動(周期2060日・振幅0.061°)、
  ポリデュークスの秤動(振幅33.9°〜91.4°)、TNO の海王星共鳴の秤動(プルーティノで
  振幅45°〜160°)はいずれも視認できないか、閉形式の公開値が無い(§4.6)。
  ヤヌス/エピメテウスの軌道交換(4年周期、半長軸差48km)だけは**視覚的に意味があるが
  実装しない** — 区分ケプラー軌道の切替という、この系だけのための機構になるため(§7 へ)。
- **N-5 ラプラス共鳴の厳密な保存**。イオ・エウロパ・ガニメデの平均運動は
  `n₁ − 3n₂ + 2n₃ = 0` を満たすが、JPL の公転周期を独立に転記するとこの条件は
  厳密には満たされない。整数比 1:2:4 に固定する手もあるが、**実測周期を優先する**
  (共鳴角のドリフトはゲームの時間スケールで視認できない。受け入れはテストでピン留め)。
- **N-6 小惑星族の proper elements の厳密再現**。族の中心値・広がりは本来、長期の
  準周期展開または数値積分による平均化を要する準不変量である。点群としては接触要素を
  族中心付近にランダム配置すれば見た目は成立する(E-11)。
- **N-7 環の影・環越しの減光**(第1次計画 N-6 を継承)。

## 5. アーキテクチャ上の設計判断

### E-1 天体数が一桁増えることへの対処 — 「窓を増やさず走査を減らす」

天体が 10 → 86 になる。第1次計画 D-1 が確立した二窓構成
(`attractorsAt` = 全天体 / `gravityAttractorsAt` = 重力源のみ)は**維持する**が、
F-10 により後者の中身が 5 → 71 に膨らむので、重力側には別途 E-13 の位置依存の第3段が要る。
本節は**表示・判定側**(`attractorsAt` を読む側)だけを扱う。

問題は `attractorsAt` を読む側の**線形走査**(E-B1/E-B2)である。t リングキャッシュ
(C-7)が効くので配列の**生成**は1フレームに数回だが、`strongestAttractor` は
呼ばれるたびに全 `Attractor` の `attractorAccel` を計算する。`map-picker.ts` は
ピック候補ごとにこれを呼ぶため、候補 150 件 × 87 体 = 13,000 回/フレームになる。

**対処: `CelestialBodyDef` に静的な `influenceRadius: number` [m] を持たせ、
`strongestAttractor`/`hitCelestialBody`/`isOccluded` は距離での早期棄却を先に行う。**

- `influenceRadius` は「**この天体の重力寄与が無視できなくなる最大距離**」で、
  `attractorAccel` の潮汐差分項の大きさが閾値 `GRAVITY_NEGLIGIBLE_ACCEL` を
  超えうる距離を静的に見積もった値。太陽・地球・月・木星・土星は `Infinity`。
  **1つの半径が E-1(中心天体解決の足切り)と E-13(重力窓)の両方に使える**のは、
  「重力寄与が無視できる天体は、最強の引力源にもなりえない」から — 前者にとって
  この半径は必要以上に広い保守的な値であり、保守的でありさえすれば正しい。
- **正しさの形**: 棄却は保守的(実際より広い)であればよく、棄却された天体が
  勝つことはない。テストで「全天体を走査した場合の結果と一致する」ことを assert する。
- `hitCelestialBody`/`isOccluded` は `influenceRadius` ではなく `radius`(+ margin)
  そのもので棄却できるので、より単純に「距離の2乗が半径の2乗を超えたら次へ」の
  平方根回避で足りる。これは結果が厳密に不変な純粋最適化。
- **この判断は「窓をもう1つ増やす」案の代わりに採る**。`physicalPresence` のような
  第3のフラグを足すと、「火星の裏のラベルが選べる/表示専用天体を艦がすり抜ける」という
  第1次計画 D-1 が明示的に避けた4系統の破綻が、フラグの立て方次第で再発する。
  静的な距離足切りは**結果を変えない**ので、その危険が構造的に無い。

### E-13 重力窓の位置依存化(F-10 が要求する最重要の構造判断)

F-10 により `gravitySource: true` が 5 → 71 体になる。第1次計画 D-1 が
「RK4 の4ステージ × 全エンティティで舐める配列なので重力側は要素数を5体に固定する
必要がある」と書いた制約に、正面から違反する。放置すると重力積分だけで
**4ステージ × 400エンティティ × 71体 = 11.4万回/substep** の `attractorAccel` になり、
NF-1 を桁で超える。

**判断: `gravityAttractorsAt(t)` を「μ が判明している全天体(候補集合)」とし、
その配列から実際に効く天体だけを位置で選ぶ純関数を `attractor.ts` に置く。**

```ts
// 位置 r において重力寄与が無視できない天体だけを返す。候補は呼び出し側が渡す。
export function relevantAttractors(r: Vec3, attractors: readonly Attractor[]): readonly Attractor[]
```

- **選別は `influenceRadius`(E-1)との距離比較だけ**で行う。平方根を避けた
  2乗比較で 71 回、`attractorAccel` は計算しない。
- **選別は substep ごとに1回、RK4 の外側で行う。** これが成立するのは
  `dynamics.ts` の `stepDynamics(state, dt, attractors, bcInv, thrust)` が
  **既に配列を引数で受け取っている**からで、変えるのは「誰がその配列を組むか」だけ。
  物理そのものには一切手を入れない。RK4 の4ステージは選ばれた配列を共有する
  (substep 内で天体の出入りが起きないのは、substep が `SUBSTEP_MAX_DT` で
  区切られており、その間の移動距離が `influenceRadius` の余裕より十分小さいため)。
- **3つの呼び出し経路すべてが同じ関数を通る**必要がある —
  `GameEntity.stepActual` / `GameEntity.stepPredicted`(`Predictor` 経由)/
  `PlanArc.update`。1つでも別の選別をすると、**予測線・計画線が実際の軌道と
  ずれる**(しかも「予測が当たらない」という形でしか現れないので発見が遅れる)。
  これは性能の話ではなく**正しさの話**なので、テストで3経路の一致を assert する。
- **閾値の決め方**: `GRAVITY_NEGLIGIBLE_ACCEL` は SRP(~7e-8 m/s²)より
  さらに2桁小さい **1e-10 m/s²** を採る。この値なら、天体が窓に出入りする瞬間の
  加速度の不連続が RK4 の打ち切り誤差に埋もれる。**不連続そのものを無くすために
  フェードイン係数を掛ける案は採らない** — 係数を掛けた加速度は物理的に間違った値で
  あり、「小さすぎて見えない不連続」を「常に少しだけ間違った重力」と引き換えにする
  のは割に合わない。
- **配列の割り当て**: エンティティごと・substep ごとに新しい配列が1本できる
  (~400 × 1〜4 本/frame)。`physics/` の純粋性(CLAUDE.md の不変性の規約)を
  破ってまで使い回すバッファを持つ理由にはならない規模。
- **期待される効果**: LEO のエンティティが選ぶのは地球・月・太陽の3体で、
  現行の5体より**むしろ短くなる**。木星系にいる艦だけが木星+ガリレオ衛星4+土星+太陽の
  7体前後を選ぶ。**重力積分のコストは天体数ではなく「今いる場所の混み具合」で決まる**
  ようになり、これが F-10 を NF-1 と両立させる唯一の道である。

**μ が判明していない天体は `gravitySource: false` のまま残る**(§4.1 で
「データなし」「実質未決定」の約15体 — 木星の不規則衛星、ダフニス、パック、
ネレイド・プロテウス・ラリッサ、ケルベロス・ステュクス、大半の TNO)。
フラグは消えず、**判定基準だけが「近傍に行きうるか」から「μ の測定値が存在するか」へ
変わる**。この書き換えは `solar-system.ts:52-56` の `GravitySourceFlag` の
コメントに対する変更であり、第1次計画 D-1 の記述と
`.claude/skills/refactor-fixed/SKILL.md` も同じ変更セットで直す。

**F-10 が連れてくる副次的な要求**(本計画で扱うか否かを明示する):

- **クリエイティブモードの基準天体**: D-1 の不変条件「選択可能な天体は必ず
  `gravitySource: true`」は維持されるので、基準天体リストが 5 → 71 項目になる。
  E-10 の UI 階層化に**このリストも含める**(`ship-placer-panel.ts` の
  `SegmentedControl` は 71 項目を並べられない)。
- **degree2 の欠落**: 水星・金星・火星・天王星・海王星と全衛星は `degree2` を持たない
  (C-1)。**火星の J2 は 1.96e-3 で地球の 1.08e-3 より大きい**ため、火星低軌道の
  ミッションでは昇交点歳差が実際と食い違う。**本計画では扱わず、フライバイの範囲では
  影響しないことを明記するに留める**(低軌道に入るミッションを設計する時点で必要になる)。
- **地球以外の大気**: `atmosphere.ts` は地球専用で、`hitCelestialBody` の margin も
  `REENTRY_ALT`(地球の大気圏突入高度)。火星・金星・タイタン・トリトンには大気があり、
  無大気天体では margin が 0 であるべき。**本計画では扱わない** — フライバイは
  大気圏に入らないため。ただし margin が天体によらず一定である現状は、
  無大気天体の表面すれすれの飛行を不当に禁じるので、§8 に記録する。

### E-2 衛星の親と連星重心 — 既存パイプラインで足りることの確認

`SatelliteId` の `planet: PlanetId` 制約(`solar-system.ts:73`)は、本計画の衛星すべてで
満たされる。カロンの親は冥王星、ディモルフォスの親はディディモス、ヴァンスの親はオルクス —
いずれも第1次計画 D-3 が「`kind: 'planet'` は『太陽を回る天体』の意味であり IAU の惑星定義
とは独立」と決めた通り `PlanetId` に入る。**`attractor.ts` の「太陽系に安定な衛星の衛星は
存在しないので表現は要らない」というコメントは本計画でも真のまま**で、階層を深くする必要はない。

`Ephemeris` の3段パイプライン(恒星 → 惑星-衛星系重心 → 惑星/衛星)は、惑星本体を
「重心 − Σ(μ_衛星/Σμ)·(衛星の惑星相対状態)」で求める。**冥王星-カロンの質量比 0.122
(≈1:8.2、§4.6)でもこの式は正しい** — 月-地球の 1:81 と違って共通重心が冥王星本体の外側に
出るだけで、式は同一である。**追加実装は不要**だが、テストで
「冥王星本体が共通重心の周りを実際に振れる(振幅 ≈ a×μ_Charon/Σμ ≈ 19,600 × 0.109 ≈ 2,130 km、
冥王星半径 1,188 km を超える)」ことをピン留めする — これが「連星系である」ことの機械的な検査になる。

**注意**: 冥王星に5衛星、木星に14衛星(既存4+本計画10)、土星に15衛星が付くと、
`planetHelioState` の重心補正がその惑星の全衛星の `satelliteRelState` を要求する。
第1次計画 D-2 が入れた `satelliteRelState` の t リングキャッシュ(C-7)が効くのは
このためで、キャッシュのスロット数(現在4)が**同時に評価される衛星の数ではなく
時刻の数**であることを確認しておく(実装は id ごとに独立キャッシュ、`ephemeris.ts`)。

### E-3 基準面 — JPL の公開する基準面極をそのまま持つ

第1次計画 D-3b は `KeplerOrbit` に `basisToEci: Quat` を持たせ、衛星の基準面を
「親惑星の赤道面」にして pole モデルから組む方針を決めている。本計画は**その方針を
一段一般化する**必要がある。理由は §4.1 が示す事実:

- JPL の衛星平均要素表は基準面を衛星ごとに使い分ける — **ラプラス面**(木星・土星の
  内側規則衛星、海王星のプロテウス/ラリッサ)、**惑星赤道面**(天王星系、冥王星系)、
  **黄道面**(木星の不規則衛星、ネレイド)。
- ラプラス面は親の赤道面でも軌道面でもなく、**「衛星の昇交点歳差が平均的に含まれる面」**
  = 歳差極に垂直な面である。内側衛星では扁平摂動が支配的で赤道面に近く、外側衛星では
  太陽潮汐が支配的で親の公転面に近づく。親の pole から導出することはできない。
- **JPL は同じ表に基準面極の赤経・赤緯と「基準面と赤道面のなす角(tilt)」を載せている。**
  つまり導出する必要がなく、転記すればよい。

**判断: 基準面を `SatelliteBasis` として型で表し、`basisToEci` はそこから組む。**

```ts
export type SatelliteBasis =
  | { readonly kind: 'ecliptic' }                                  // 既定。月・不規則衛星
  | { readonly kind: 'parentEquator' }                             // 親の pole モデルから組む
  | { readonly kind: 'poleRaDec'; readonly raDeg: number; readonly decDeg: number }; // JPL のラプラス面極
```

- `'poleRaDec'` の ICRF → ECI 変換は、第1次計画 D-6 が決めた
  `ecliptic.ts` の `stdToEci` の export 経由(`raDecToEci`)を**共有する** —
  軸置換の定義元を2箇所に増やさない。
- **月は `'ecliptic'`(既定)のまま変更しない**。既存の摂動テーブル・カッシーニ実装・
  テストがすべて黄道基準で書かれており正しく動いている(第1次計画 D-3b と同じ判断)。
- `'parentEquator'` は天王星系・冥王星系が使う。親の pole モデル(第1次計画 D-6 の
  `'iau'` variant)が要るので、**本計画の天王星系・冥王星系の衛星は第1次計画 P2 に依存する**。
  ラプラス面の衛星(木星・土星の内側)は `'poleRaDec'` で親の pole を要さないので、
  P2 の完了を待たずに着手できる。
- **黄道基準の衛星(木星の不規則衛星6体・ネレイド)は基準面の変更を一切要さない**ため、
  `kepler-orbit.ts` の改修(D-3b)すら不要で、既存コードにそのまま乗る。
  → **本計画の最初のフェーズはここから始める**(§6 の EP1)。

第1次計画 D-3b の「衛星の要素は親の赤道面基準のまま登録し、`Ephemeris` が親の pole から
`basisToEci` を組む」という記述は、`'parentEquator'` という1 variant に縮む。
D-3b の残りの指摘(3関数を1箇所で書き換える、`satelliteState` の空テーブル早期 return)は
そのまま有効。

### E-4 歳差率の入力形は既に一致している — 罠は「0 = 歳差なし」

`satelliteOrbit` は `nodePeriodSec`/`perigeePeriodSec` を**正の秒数**で受け取り、
符号は関数自身が付ける(C-5)。JPL の `Pnode [yr]`/`Papsis [yr]` はそのまま入る。
新しい摂動モデルは要らない — **「軌道要素の変動」の要求は、既存の型に値を入れるだけで満たされる。**

**ただし JPL は「歳差しない」を `0.000` で表す**(イオ `Pnode=0.000`、エンケラドゥス
`Pnode=0.000`、ディオネ `Pnode=0.000`、トリトン `Papsis=0.000`、テティス `Papsis=0.005`)。
周期0を素直に `2π/T` に入れると**無限大の歳差速度**になる。

- **`satelliteOrbit` の中で 0 を「歳差なし」(rate = 0)に写す**。変換を1箇所に閉じ、
  呼び出し側に「0 を Infinity に読み替えて渡せ」という規約を作らない。
- テティスの `Papsis = 0.005 yr`(= 1.8日)は**0 ではないが公転周期 1.888 日とほぼ同じ**で、
  近点が1公転につき1周する = 実質的に近点が定義できない円軌道であることを意味する。
  e = 0.001 なので視覚的な影響はない。これを 0 と同じに扱うか値通りにするかは、
  **値通りにする**(NF-2: 出典の値を書き換えない)。テストで「テティスの位置が
  歳差の有無で 1km 以上変わらない」ことを確認して、値通りで問題ないことを裏取りする。

### E-5 形状(歪み)— `ShapeDef` を `CelestialBodyDef` 直下に置く

`CelestialBodyDef` に `shape?: ShapeDef` を追加する。

```ts
export type ShapeDef =
  | { readonly kind: 'spheroid'; readonly equatorRadius: number; readonly polarRadius: number }
  | { readonly kind: 'triaxial'; readonly a: number; readonly b: number; readonly c: number };
```

- **省略時は真球**(半径 `radius`)。これで既存10体は無変更のまま。
- **置き場所の判断**: 表示側(`celestial-registry.ts`)ではなく `physics/` の
  `CelestialBodyDef` に置く。三軸半径は `pck00011.tpc` という物理データの一次ソースから
  来る量であり、表示の都合ではない。表示側が physics から読めば定義が重複しない。
- **`radius`(スカラー)は残す**。`Attractor.radius` は `hitCelestialBody` の衝突球と
  `apsisAltitudes` の高度基準に使われており、**当面は楕円体化しない**。
  値は**赤道半径**を入れる(現在の土星 5.8232e7 = 赤道半径と整合)。
  楕円体の内接球ではなく外接球になるので、極方向で最大 10%(土星)余裕を取ることになり
  **安全側**である。この選択の理由をコメントに書く。
- **`degree2` の `refRadius` とは別の量**。`refRadius` は重力係数が定義された基準半径で、
  形状ではない(C-3 の月の例)。両者を混ぜない。
- **メッシュ側は1箇所の変更で全天体に効く**: `sphere-body.ts:35-58` の
  `mesh.scale.setScalar(r)` を `mesh.scale.set(rx, ry, rz)` に一般化する。
  ECI は Y = 極軸なので、`spheroid` なら `(Re, Rp, Re)`、`triaxial` なら `(a, c, b)` を
  自転姿勢(第1次計画 D-6)より内側の座標で与える — **形状は天体固有の量なので
  自転軸に固定され、ECI 軸には固定されない**。したがって
  `mesh.quaternion`(自転)を書いたうえで `mesh.scale` を書く順序でよい
  (THREE は scale → rotation → translation の順に合成するため、scale は
  ローカル軸で効く)。
- **戦闘ビューの圧縮表示**(`visDist × radius/trueDist`)は3軸すべてに同じ係数を掛ける。
  真の視角を保つという `SphereBody` の性質は変わらない。

### E-6 環 — `RingSystemDef` と、幅が半径の 1/10,000 になる細環

`CelestialBodyDef` に `rings?: RingSystemDef` を追加する。

```ts
export type RingBandDef = {
  readonly innerRadius: number;  // [m]
  readonly outerRadius: number;  // [m]
  readonly thickness: number;    // [m]。0 なら平坦な annulus
  readonly arcs?: readonly { readonly fromDeg: number; readonly toDeg: number }[]; // 省略時は全周
};
export type RingSystemDef = {
  readonly bands: readonly RingBandDef[];
  readonly texture?: /* アセット識別 */;  // 省略時は単色
};
```

3つの形が要る(§4.4 が示す実データの幅):

1. **テクスチャ焼き込み annulus**(土星 D–A)。第1次計画 P5 の方式そのまま。
   `bands` 1本 + テクスチャで、間隙は α で表す。
2. **細環**(天王星の11環、海王星のル・ヴェリエ/アラゴ/アダムス、土星の F 環)。
   幅が 2–100 km に対し半径が 4–10 万 km で、比が **1:10,000 以上**。annulus として
   描くとサブピクセルになり消える。**`outerRadius − innerRadius` が視角で 1px 未満なら
   `THREE.Line` の円で描く**(WebGPU で `LineLoop` が使えないので、始点を重ねた
   `THREE.Line` で閉じる — CLAUDE.md の既知の制約)。判定はカメラ距離依存なので `sync` 側。
3. **扁平トーラス**(木星のハロー環・ゴサマー環2本、土星の E 環)。厚みが半径の
   1〜10% あり平坦ではない。`thickness > 0` の band は半透明の扁平球殻で描く。

- **アーク**(海王星アダムス環)は `arcs` の経度範囲だけ不透明度を上げる。
  経度の基準は §4.4 の通り 1989-08-18 固定の経度系で、**アーク自身も公転している**が、
  その運動は非目標(静止させる)。
- 環の姿勢は第1次計画 D-6/P5 が決めた「pole から純関数で組む」(`ringOrientation(pole)`)を
  共有する。**したがって本計画の環は第1次計画 P2(pole モデル)に依存する。**
- マテリアルは第1次計画 §5.4 の通り
  `{transparent: true, side: THREE.DoubleSide, depthWrite: false}` + 通常アルファ、
  `renderOrder` は惑星本体+1。
- **フェーベ環**(半径 400万–1300万 km、土星本体の 200 倍)は他の環と縮尺が3桁違う。
  同じ `bands` に入れると、土星の環を見るズームでは画面外・土星系を見るズームでは
  他の環がサブピクセルになる。**band ごとに「この band が意味を持つズーム範囲」を
  持たせるのではなく、フェーベ環を独立した band として登録し、2 の細環判定と同じく
  視角で表示を切り替える**(小さすぎるものは点/線に落とし、大きすぎるものは
  そのまま描く)。追加のフィールドは要らない。

### E-7 表示 LOD — 「戦闘/マップ」ではなく「視直径」で切り替える

第1次計画 D-8 は、戦闘ビューの惑星を `SphereBody` とは別の `PointBody`(星シェル上の
輝点スプライト)として登録する方針を決めている。本計画では天体が 86体になり、
**マップビューでも大半の天体が 1px 未満**になる(ベンヌの直径 484m を 1 AU から見た視角は
10⁻⁹ rad)。ビューで実装クラスを分ける方式では、この「マップだが小さすぎる」場合を
表せない。

**判断: `SphereBody` の中に LOD を入れ、視直径が閾値未満なら輝点、超えたら楕円体を描く。
`PointBody` は作らない(第1次計画 D-8 の該当部分を上書きする)。**

- 判定は `sync` の中で、その天体の視角(`2·radius/距離`)を
  `physics/projection.ts` の `metersPerPixel` と突き合わせて行う。この関数は既に
  `ScaleFn` として使われており、新規の投影計算は要らない。
- 輝点の明るさは**視等級ではなく実際の見かけの大きさと反射率**で決めない — 実装が
  重くなるだけで、マップビューでは「そこに何かがある」ことが分かれば足りる。
  第1次計画 D-8 の「等級に応じた3段階のスプライトサイズ」は、
  **戦闘ビューで金星・木星が実際の明るさで見えることに意味がある**ので維持する。
  つまり明るさの決め方だけは2系統残る — 戦闘ビュー(等級)とマップ(一律)。
  **これを1つに統合しない**理由は、前者が「肉眼で見た夜空の再現」、後者が
  「地図上の目印」という別の目的だから。
- **1天体1メッシュのまま**にする(87 draw call)。輝点をインスタンス化して1 draw call に
  まとめる案は、点群(E-11)と違って天体ごとに位置の出所も表示切替も異なるため、
  得るものに対して複雑さが見合わない。87 draw call は現行の弾丸・デブリの規模
  (~400 エンティティ)より小さい。

### E-8 `Ephemeris` の評価コストと衛星の階層

87体の `attractorsAt(t)` 1回は、各天体につきケプラー方程式の Newton 反復を含む評価になる。
キャッシュミスは1フレームあたり数回(C-7 の4スロットリング)なので、**評価回数そのものは
問題にならない**。問題は §E-2 で触れた重心補正の連鎖:

- `planetHelioState('jupiter', t)` は木星の全衛星(既存4 + 本計画10 = 14)の
  `satelliteRelState` を要求する。
- `satelliteRelState('io', t)` は `planetAngles(木星の重心軌道)` を要求する。
- **循環しない**のは、`planetAngles` が惑星-衛星系**重心**の日心ケプラー軌道から
  取られるためで、これは衛星の状態に依存しない(既存の設計)。

したがって階層は深くならず、コストは「惑星ごとに(衛星数)回の衛星評価 + 1回の重心評価」の
線形和にとどまる。**新しい構造は要らない**。ただし:

- **重心補正に入れる衛星を、質量が判明しているものに限る**。§4.1 で GM が
  「データなし」「実質未決定」の衛星(木星の不規則衛星6体、ダフニス、パック、
  ネレイド・プロテウス・ラリッサ)は `mu` を持たない。`mu = 0` として重心補正に
  入れれば寄与0で無害だが、**L 点生成(`lagrangeAt`)が μ=0 で破綻する**。
  → E-9 の `lagrangeLabels` フラグ(第1次計画 D-9)を、これらの天体で false にする。
- 木星の不規則衛星の質量は不明でも、**既知の質量の総和に対して無視できる**
  (ヒマリア GM=0.15 に対しガニメデ 9887)ので、重心補正から外しても位置は変わらない。

### E-9 レジストリの記述量 — 追加時に必須なのは日本語名だけにする

`CELESTIAL_BODIES`(`celestial-registry.ts:29-40`)は現在
`Record<AttractorId, {name, create(): CelestialBody}>` で、**天体ごとに `create` を
手書きさせる**。86体でこれをやるのは現実的でない。

**判断: `create` を省略可能にし、省略時は `SOLAR_SYSTEM` の `shape`/`radius`/`rings` から
既定の `SphereBody`(E-7 の LOD 込み)を組む。追加時に必須なのは日本語名だけ。**

```ts
export const CELESTIAL_BODIES: Record<AttractorId, { readonly name: string; readonly color?: number; create?(): CelestialBody }> = { … }
```

- `color` も省略可能にし、省略時は共通の既定色(灰)。実写テクスチャのある天体だけが
  `create` を書く(地球・月・惑星8、および §4.1 の「全球あり」の衛星)。
- `EarthBody`/`SunBody` のような特別な実装は今まで通り `create` を書く。
- **`name` を省略可能にしない**。日本語表示名は導出できない情報であり、
  ID をそのまま表示するフォールバックを許すと、表示名が抜けたまま出荷される。
  型で必須のまま残すことが唯一の防止手段。

### E-10 UI — 86体 + L点 + 座標系の爆発

第1次計画 D-9 は 25体規模でのラベル爆発に階層フィルタで対処する方針を決めている。
86体ではさらに3つが破綻する:

1. **座標系選択**(E-B3)。`FRAMES` は 87 慣性系 + 86 回転系 = 173 項目になり、
   `SegmentedControl`(1行のボタン列)では表示不能。
   **判断: フレーム選択を「天体を選ぶ」+「慣性/回転を選ぶ」の2段に分ける。**
   `ReferenceFrame` の型そのものが `{center, rotatingWith}` の直積(`frame.ts`)なので、
   UI をその直積の形に合わせるだけで、新しい概念は要らない。天体の選択は
   後述のツリーを共有する。
2. **オブジェクト一覧**(`ObjectListPanel`)の天体セクション。87行のフラットな
   リストは実用にならない。**判断: 太陽 > 惑星 > その衛星 の親子ツリーにする。**
   親子関係は `solar-system.ts` の `primaryOf(id)`(既存、`solar-system.ts:32-35`)から
   導出でき、新しいデータは要らない。`ObjectListPanel` は既に kind ごとの
   アコーディオンを持つので、天体セクションだけ2階層にする。
3. **ラグランジュ点**。第1次計画 D-9 の `lagrangeLabels: boolean` を採用し、
   **主要系(月・木星・土星、および §2.2 のうち質量が判明していて系として意味のある
   ガリレオ衛星・タイタン・カロン)に限る**。E-8 の通り、μ が未決定の天体では
   `lagrangeAt` 自体が意味を持たない。フラグは第1次計画 D-9 の指摘通り
   **`LABEL_NAMES` の生成と `update(t)` 内の `lagrangeAt` ループの両方**を絞る。
4. **フォーカスラベル**は第1次計画 D-9 の階層フィルタ(引いた視点では惑星+太陽のみ、
   惑星にフォーカスするとその系の衛星が現れる)を採用する。判定は 2 のツリーと同じ
   `primaryOf` から導出し、D-5 の衛星軌道線の表示判定とも共有する。

### E-11 点群の一般化

第1次計画 D-4 の `asteroid-field.ts`(メインベルト + 木星トロヤ群、`InstancedMesh`、
seed 固定の決定論的生成、`overviewMode` 中のみ評価)を、**分布定義をデータで受け取る
汎用クラスに一般化する**。

```ts
export type PointFieldDef = {
  readonly seed: number;
  readonly count: number;
  readonly aRange: readonly [number, number];        // [m]
  readonly gaps?: readonly { readonly a: number; readonly sigma: number }[]; // 共鳴間隙
  readonly eRange: readonly [number, number];
  readonly incRange: readonly [number, number];      // [rad]
  readonly librationAboutDeg?: readonly number[];    // トロヤ群なら [60, -60]
  readonly librationWidthDeg?: number;
  readonly center: AttractorId;
};
```

追加する5群(§2.2):

- **カイパーベルト**: a = 39–48 AU、cold 集団(i < 5°、e < 0.1)と hot 集団(i 0–30°、
  e 0–0.3)を別の `PointFieldDef` として重ねる。両者は力学的に別起源で、
  1つの分布で表すと i の二峰性が消える。
- **散乱円盤**: a = 48–1000 AU、e 0.3–0.9、i 0–40°。近日点が 30–40 AU に集中する
  ため、`aRange` ではなく近日点距離で分布を定義する必要がある — **これだけ
  パラメータの形が違う**ので、`PointFieldDef` に `perihelionRange` を持たせ、
  `aRange` との排他とする。
- **ヒルダ群**: a ≈ 3.972 AU(3:2 共鳴)、e 0.1–0.3。**任意時刻での見え方が三角形状**に
  なるのは、木星との会合に同期して近日点が L4/L5/木星対蹠点の3箇所に寄るため。
  `librationAboutDeg: [60, 180, -60]` で近似できる。
- **火星トロヤ群**: 火星の L4/L5、既知は10体未満なので点群ではなく個別天体
  (エウレカのみ §2.2 に入れた)。**点群としては実装しない**(NF-2)。
- **小惑星族**: §4.6 の通り proper elements の一次データが未取得。
  取得できた族だけ実装し、できなければ非実装(NF-2)。

第1次計画 D-4 が挙げた 4:1/3:1/5:2/2:1 の間隙に、**7:3 = 2.958 AU を追加する**(§4.6)。

### E-12 テクスチャ — 実写のある天体だけ

§4.1 の「テクスチャ」列が実装の指針になる。**全球モザイクが存在するのは以下だけ**:

| ミマス・エンケラドゥス・テティス・ディオネ・レア・イアペトゥス | Cassini(USGS Astrogeology) |

- 残る全天体は単色(F-7)。第1次計画 D-7 の階層表の「低」に該当する。
- **NF-3 の 15MB 予算に対し、テクスチャを持つのは Cassini 系6体 + カロン**。

## 7. 検証方針

- 各フェーズで `npm run typecheck`(常時)+ `npm run test:physics`
  (physics/ を触るフェーズ: EP1, EP2, EP3, EP5, EP6, EP7)。
- 追加するテストの型は第1次計画 §7 を継承 — 公転周期のケプラー第3法則一致、
  既知の幾何値のピン留め、高離心率ソルバの往復精度、リファクタの非破壊性。
  本計画で新しく加わる型:
  - **最適化の結果不変性**(E-1 の足切りが全走査と一致する)
  - **積分・予測・計画の3経路が同じ重力窓を選ぶ**(E-13。これだけは性能ではなく
    正しさのテストで、破れると「予測線が実際の軌道とずれる」形でしか表面化しない)
  - **基準面の取り違え検出**(天王星系が黄道基準で登録されていたら i が 98° ずれる)
  - **形状の外接性**(`radius >= max(shape の3軸)`)
  - **連星重心の実在性**(冥王星本体の振幅が自身の半径を超える)
- 実行時確認(`/verify`)はユーザーが求めたときのみ。フェーズ受け入れの「見える」系
  条件は `npm run dev` での目視を想定する。

## 8. 将来拡張(本計画の非目標だが要求が出うるもの)

- **ヤヌス/エピメテウスの軌道交換**(N-4)。4年周期・半長軸差48km の区分ケプラー軌道の
  切替。視覚的には意味があるが、この系だけのための機構になる。
- **トロヤ衛星**(テレスト・カリプソ・ヘレネ・ポリデュークス)。前3者は
  「親衛星と同一要素 + 平均黄経 ±60°」で表せる(§4.6)。ポリデュークスの秤動は
  閉形式の公開値がない。
- **探査機由来の形状モデルメッシュ**(N-3)。エロス・イトカワ・ベンヌ・リュウグウ・67P。
  `tools/export-models.mjs` 型のアセットパイプラインで PDS の形状モデルを
  低ポリゴン化して焼き込めば NF-3 に収まる可能性がある。
- **彗星の非重力加速度の評価**(N-2)。天体位置を積分に切り替える必要がある。
- **彗星の尾**(第1次計画 §8 を継承)。反日方向のイオンテイルと軌道遅れ方向のダストテイル。
- **半球だけ観測されている天体の「未観測」表現**(E-12)。天王星系の5衛星は
  南半球のテクスチャしか存在しない。
- **小惑星族の proper elements**(N-6、§4.6)。AstDyS からの取得が前提。
- **TNO の海王星共鳴の秤動**(N-4)。プルーティノ・トゥーティノの分類ごとの表現。
- **`hitCelestialBody` の楕円体化**(E-5)。土星の極方向で 10% 保守的になっている
  現状が、実際に問題になった場合。
- **地球以外の天体の `degree2`**(E-13 の副次要求)。火星の J2 = 1.96e-3 は
  地球の 1.08e-3 より大きく、火星低軌道の昇交点歳差に効く。木星・土星の J2 は
  1.47e-2 / 1.63e-2 とさらに一桁大きく、ガリレオ衛星軌道以内の運用では無視できない。
  フライバイでは影響しないが、周回ミッションを設計する時点で必要になる。
- **天体ごとの大気と表面接触 margin**(E-13 の副次要求)。`atmosphere.ts` は地球専用、
  `hitCelestialBody` の margin は全天体一律。火星・金星・タイタン・トリトンには
  大気があり、逆に無大気天体では現状の margin が表面すれすれの飛行を不当に禁じる。
  エアロブレーキを使う遷移や、月面・小惑星への接近運用を作る時点で必要になる。
