# クリエイティブモード・マップビュー軽量化／品質調整計画

## 目的と設計原則

対象はクリエイティブモードのマップビュー、とくに等速時と時間加速時である。目的は、表示の意味と物理計算の再現性を守りながら、CPU・GPU・メモリの費用を端末能力と画面上の必要性に合わせること、ならびに ESC メニューから理解しやすく調整できるようにすることである。

実装は既存クラスへ低品質条件を継ぎ足さず、最初から作るなら自然に得られる次の責務分離を採る。

- シミュレーションは正しさを担当する。品質設定で物理精度やイベント結果を変えない。
- 表示ポリシーは「今、何を詳しく見せる必要があるか」を一か所で決める。
- スケジューラは「何 Hz で更新するか」を決め、各表示機能は時刻と dirty revision を受け取る。
- 品質設定は型付き・版付きの単一モデルとし、UI、保存、適用を分離する。
- 地球–月系を通常の詳細作業集合とする。遠方の惑星系は消すのではなく、点・ラベル・軌道などの安価な表現を保ち、注目・接近・航路指定時に即座に詳細化する。

## 現行負荷モデル

以下はコードから得たオーダー推定であり、割合は計測前の仮説である。`N` は実体エンティティ数、`H` は艦数（クリエイティブでは最大 50）、`A` は近傍重力源数、`S` は一描画フレーム中の物理サブステップ数、`P` は予測積分予算（現在マップで最大 500 step/frame）、`R` は計画軌道の積分ステップ数（通常約 100/周、最大 20,000）、`C` はカタログ天体数（101）、`Q` は小天体点群（11,200 点）、`L` は表示軌道線の頂点数、`M` はマーカー／ラベル候補数とする。

### 時間加速なし

一フレームの概算は次である。

`T = O(N·A + N + H)physics + O(P·A + N)prediction + O(R·(C + N + A))plan + O((M + L)·C + Q/8)presentation + GPU(pixels, triangles, draws)`

通常は `S=1`。現在、計画軌道へ渡す重力源 provider の revision に連続変化する `simTime` が含まれ、PlanArc は revision 変更時に再積分するため、時間が進む限り計画軌道が実質毎フレーム再計算される。これは CPU と一時 allocation の最有力候補である。

加えてマップ表示中は毎フレーム、天体更新、エディタ、赤道交点、ピッキング候補、カメラ、全エンティティ同期、マーカー、HUD、軌道線を処理する。候補ごとの遮蔽判定は概ね `O((M+L)·C)`、小天体点群は 8 分割更新済みだが約 1,400 点/frame、天体は非表示でも同期経路へ入り、地球は 1024×768 分割球と高解像度テクスチャ、renderer は devicePixelRatio 等倍・antialias 有効である。

CPU 内訳の初期仮説は、計画軌道 30–60%、候補・遮蔽・ラベル 15–35%、予測 15–40%、実シミュレーション 5–25%（区間は重なり、合計値を意図しない）。GPU を含む frame time では高 DPI の地球描画が支配する場合がある。表示天体数、艦数、計画期間で大きく入れ替わるため、割合そのものを仕様にはしない。

### 時間加速あり

物理費用は概ね次になる。

`S ≈ ceil(realDt · warp / hmax)`

通常の `hmax` は 20 秒、再突入域では 1 秒である。したがって高倍率では、

`Twarp = O(S·(N·A + N + H)) + O(P·A + N) + O(C + Q/8 + L + M) + GPU(...)`

となる。各サブステップで全体走査、重力積分、姿勢、艦イベント確認が入り、時間加速に比例して物理が支配的になる。予測は 500 step/frame に上限があるが、実状態との乖離による再構築が増える。対して表示同期と GPU 描画は倍率に関係なく毎描画フレーム発生するため、物理が重い時にも固定費として残る。

60 fps を仮定した通常軌道での概算は、×1〜1024 が 1、×4096 が約 4、×16384 が約 14、×65536 が約 55、×131072 が約 110 substeps/frame である。低高度の一個体が `hmax=1s` を要求すると、現行の全体共通刻みでは最大倍率で約 2,185 substeps/frame になり、その個体以外も同じ細かさで進む。高ワープ最適化で最初に除くべき構造的増幅点はここである。

初期仮説は、×1–256 では等速時に近く、×1024–4096 では物理 30–70%、×16384 以上または再突入近傍では物理 70–95%。現行の受動弾丸・破片の高ワープ LOD は有効だが、艦とイベント走査には倍率由来の費用が残る。

### GPU・メモリ

地球の詳細 mesh は 1024×768 分割（約 78.8 万頂点、約 157 万三角形）であり、renderer は端末の devicePixelRatio を上限なしで使う。DPR 2 なら描画ピクセルは 4 倍、DPR 3 なら 9 倍なので、render scale は端末差へ最も直接効く。

地球、雲、月、星空には 8192×4096 級の画像資源があり、RGBA 展開の単純概算では各 128 MiB、4 枚で 512 MiB、mipmap を含めれば約 680 MiB となる（実際の GPU 形式・ブラウザ実装で変動）。また約 100 天体を起動時に構築する。したがって描画解像度だけでなく、texture/geometry tier と遠方天体の遅延構築を別の軸として扱う必要がある。

## 先に追加する計測

最適化の採否を割合の推測だけで決めない。既存の update/sync/render 計測を、次の排他的な区間へ細分化する。

- simulation: サブステップ数、積分 entity-step 数、重力源候補数、イベント走査数
- prediction: 消費 step、再構築数、追跡艦数
- map presentation: environment、plan/editor、picking、camera
- sync: celestial、entities、orbit lines、markers/HUD
- renderer: CPU submit、描画ピクセル数、可能なら GPU timestamp、draw call、triangle
- 状態量: `N/H/A/Cvisible/Qdirty/L/M`、現在倍率、注目系、DPR

固定ベンチマークを保存し、中央値だけでなく p95 と最大フレームを比較する。

1. 地球–月系、艦 0/1/10/50、×1
2. 同条件で ×1024/4096/131072
3. 地球低軌道、月近傍、再突入境界
4. 木星を注目した状態（遠方系の詳細昇格確認）
5. 小天体・全ラベル・軌道計画を表示した上限条件

## 目標アーキテクチャ

### 1. PerformanceSettings

版付きの純データとして `PerformanceSettings` を定義する。`PerformanceSettingsStore` が既定値、検証、migration、localStorage 保存だけを担当し、DOM を知らない。`SettingsPanel` は値を表示して変更 intent を通知するだけとする。

適用は `PerformanceController` が担当し、起動前設定を renderer 生成へ、実行時設定を各ポリシー／スケジューラへ配る。各機能が localStorage や preset 名を直接読む実装は禁止する。

設定は `preset: auto | quality | balanced | performance | minimum | custom` と少数の型付き上書きから成る。preset は初期値を展開する便宜であり、内部コードの分岐キーにしない。

### 2. MapWorkingSetPolicy

全マップ機能が共有する一つの relevance 判定を設ける。

- hot: 注目対象、選択対象、操作艦、計画航路、カメラ近傍。詳細 mesh、軌道、ラベル、pick を通常頻度で更新
- warm: 地球、月、太陽とその必要な従属物。詳細表示するが更新頻度を下げられる
- cold: その他の惑星系・遠方小天体。点／簡易 billboard、主要ラベル、解析軌道だけを低頻度更新
- dormant: 画面寄与がなく選択対象でもないもの。メタデータだけ保持

地球–月系は既定で hot/warm とする。ただし木星を検索・注目、カメラ接近、または計画航路に含めた瞬間に、その系を hot へ昇格する。距離だけでなく画面サイズ、選択状態、航路依存を入力にすることで、将来ほかの惑星へ移動しても特例追加を不要にする。

天体 mesh、ラベル、ピッキング、参照軌道、小天体点群は同じ判定結果を消費する。機能ごとに別の「遠いから非表示」条件を持たせない。

### 3. MapPresentationScheduler

毎 rAF 実行を前提にせず、次の更新帯を持つ。

- every-frame: カメラ、操作中の node、注目マーカー
- interactive: hot 表示、pick、主要ラベル（目安 30/20/15 Hz）
- background: warm/cold 天体、非注目ラベル、参照線（目安 10/5/2 Hz）
- dirty-only: topology、表示集合、軌道要素、設定が変わった時だけ再構築

時刻加速中は表示時刻の変化量と画面誤差で更新を起こし、単純な「倍率が高いほど遅くする」条件にはしない。カメラと注目対象は滑らかに補間する。ピッキングはポインタ移動・クリック・カメラ revision で dirty にし、静止中の全候補 refresh を止める。

各表示機能が天体状態、可視集合、遮蔽候補を別々に再構築しないよう、一更新 tick につき一つの immutable `MapFrameSnapshot` を作って共有する。snapshot は working set、display state、pick/label 候補、天体状態と revision を保持する。

### 4. TrajectoryComputationService

計画軌道の再計算条件を、経過時刻そのものではなく意味のある依存 revision にする。

- node／burn／計画 anchor の変更
- 表示期間・必要精度の変更
- 重力モデルまたは計算対象 working set の変更
- 計画経路へ影響する動的対象の変更
- live anchor の画面誤差または軌道誤差が閾値を超えた時

計算結果、表示線への resampling、衝突照会を分離する。単なる memoization を PlanArc に足すのではなく、依存関係を明示する計算サービスを正本とする。

### 5. SimulationScheduler（表示設定とは分離）

高ワープ物理は品質オプションで粗くしない。まず次を順に行う。

- クリエイティブ艦の次イベントを毎サブステップ全走査せず、時刻付き priority queue で管理する。
- 変化しない重力源分類と環境値を有効時間付き snapshot として共有する。
- entity ごとの許容誤差と力学 regime に基づく multi-rate 積分を導入する。注目・推力中・大気圏・遭遇近傍は細かく、安定した弾道飛行は大きな刻みにする。
- propagator の切替には位置／速度誤差上限、昇格条件、境界での連続性を持たせる。「entity 種別が debris だから粗い」のような個別条件を増やさない。

実時間内に要求倍率を処理できない場合、精度を黙って落とさず、達成倍率を表示する。将来、決定論的なバックログ処理を導入する場合も UI と保存時刻の意味を明示する。

## ESC メニューの軽量化オプション

通常画面は preset と「自動調整」だけを前面に置き、詳細設定は展開式にする。

| 項目 | 値 | 適用 | 主な効果 |
|---|---|---|---|
| 品質プリセット | 自動／高／標準／軽量／最軽量 | 即時 | 下記の安全な表示設定を一括設定 |
| 自動調整 | on/off、目標 30/45/60 fps | 即時 | ヒステリシス付きで render scale と背景更新率を調整 |
| 描画解像度 | 100/85/70/55% | 即時 | GPU fill と高 DPI 費用を削減 |
| 天体詳細 | 高／標準／軽量 | 即時または資源再生成 | sphere 分割、texture、atmosphere。注目対象は最低品質を保証 |
| マップ背景密度 | 高／標準／低／非表示 | 即時 | 小天体点数、遠方ラベル、補助軌道を調整 |
| 背景更新頻度 | 高／標準／低 | 即時 | warm/cold presentation の Hz を調整 |
| 軌道予測表示 | 高／標準／低 | 即時 | 一フレーム予算と表示線密度を調整。計画計算の判定精度は変えない |
| エフェクト量 | 高／標準／低 | 即時 | 粒子・破片の表示上限と遠距離 LOD |

WebGPU renderer の antialias は生成時指定なので、初版では独立設定として露出しない。必要なら「再起動後に適用」と明記した起動設定として後から追加する。技術的な定数を十数個並べず、各項目には予想効果と適用タイミングを表示する。

自動調整はフレーム時間の短い揺れで品質を往復させない。p95 の移動窓、低下と回復で異なる閾値、変更後の cooldown を持たせる。変更順は render scale → cold 更新率 → 背景密度とし、注目対象、操作 UI、物理、保存結果は変更しない。

## 実装フェーズと優先度

### P0: 計測と品質設定の基盤

1. 詳細計測と固定ベンチマークを追加する。
2. `PerformanceSettings`、store、controller、preset 展開を追加する。
3. ESC パネルを設定 view として接続し、保存・復元・不正値 fallback を実装する。

完了条件: 同一シナリオの区間別 p50/p95、状態カウンタを比較でき、全設定が再起動後も復元される。物理状態の hash が表示設定間で一致する。

### P1: 即効性の高い表示費用削減

1. PlanArc の時刻依存 revision を、`TrajectoryComputationService` の意味的 revision へ置き換える。
2. 一更新 tick 一個の `MapFrameSnapshot` を導入し、可視性、候補、天体状態、遮蔽入力を共有する。
3. render scale を即時適用する。
4. `MapWorkingSetPolicy` を導入し、地球–月系中心の hot/warm/cold 表現を天体、ラベル、pick、軌道線で共有する。
5. 非表示天体の詳細 sync を止め、cold 系の詳細 resource を遅延生成・解放可能にする。
6. `MapPresentationScheduler` を導入し、pick、cold 天体、ラベル、参照線を dirty／多段 Hz 更新へ移す。
7. 点群の再入場時全点更新を分割し、密度と更新帯を設定へ接続する。

期待値（要実測）: ×1 の CPU map presentation 30–60%減、低～中 GPU で frame time 20–50%減、高 DPI では render scale により GPU 35–65%減。木星注目時は必要な系だけ費用が戻る。

### P2: 予測・軌道表示の予算化

1. prediction の計算結果と線生成を分離し、表示線のサンプル密度だけを品質設定へ接続する。
2. 予測計算は操作艦、計画依存艦、画面内艦へ優先配分し、公平性と starvation 上限を持たせる。
3. 設定変更や時間加速で全列を一斉破棄せず、revision と誤差に基づいて段階更新する。

期待値: 艦 50 の ×1 map で prediction p95 を 30–60%減。計画結果と衝突・イベント判定は品質設定で変化させない。

### P3: 高ワープの構造改善

1. クリエイティブ plan event を priority queue 化する。
2. 重力源 snapshot と環境評価を時間 bucket 内で共有する。
3. 誤差制御付き multi-rate propagator を導入し、regime 境界と保存／再開の決定性を検証する。
4. 表示側は達成倍率と backlog を可視化し、重い時も操作入力を every-frame で処理する。

期待値: 艦 50 の高ワープで全艦全サブステップ走査を除き、イベントの少ない巡航時を次数・定数の両面で改善する。これは高リスクなので P1/P2 の計測後に着手する。

### P4: 天体 resource tier

地球・月・注目惑星の geometry、texture、atmosphere を tier 化し、同じ semantic body model から view resource を再生成できるようにする。初期ロード、VRAM、切替スパイクを計測し、非同期準備後に原子的に差し替える。

## 検証

- `npm run typecheck`、`npm run build`、既存 physics test を各フェーズで通す。
- 計画を変更しない ×1 マップで PlanArc 再積分回数が毎フレーム増えず、node、表示期間、重力モデル変更では必ず増える。
- 同じ入力・初期 snapshot・経過 sim time に対し、全表示 preset で物理 state hash、イベント順、破壊／接触結果が一致する。
- hot への昇格は focus、検索、航路選択、接近の同フレームで始まり、cold 表現から欠落せず遷移する。
- ESC 設定中は意図した pause 規則を保ち、設定変更、閉じる、再起動、旧版設定 migration を確認する。
- 自動調整は 10 分の負荷変動で振動せず、手動 custom 値を勝手に上書きしない。
- 比較は平均 FPS だけでなく p95 frame time、最大停止時間、初期／再入場スパイク、VRAM 推定で行う。

## 実装前の決定事項

初版は P0 と P1 を一つの成果単位とする。P2 は予測の用途（表示と計画依存）を型で分離してから行い、P3 は計測で高ワープ物理が支配的と確認できた場合に進める。preset の具体値は端末名で決めず、固定ベンチマークの p95 と見た目の許容差から決定する。

この順序なら、現行の個別最適化を温存するための抽象化ではなく、simulation、relevance、presentation cadence、resource quality という本来独立な軸から実装を組み立てられる。
