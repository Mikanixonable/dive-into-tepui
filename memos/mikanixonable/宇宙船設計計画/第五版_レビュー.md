# 第五版 計画のレビュー

第五版の3巻（`第五版_1_推進系と推進剤.md` / `第五版_2_船体設計システム.md` / `第五版_3_配管・多段・ペイロード.md`）を、現在の実装との整合、実装可能性、宇宙工学的な妥当性、実装順、ゲーム性の5つの観点で点検した結果を挙げる。

重大度は次の3段階で示す。

- **重大** — 着手前に判断しないと実装が止まる、または誤った実装になる
- **中** — 実装中に判断すればよいが、計画に書いておくべき
- **軽** — 数値や表現の精度の問題

---

## 1. 現在の実装と矛盾する箇所

### 1-1. 【重大】接触・被弾の形状が球のままである

`GameEntity.radius` は単一のスカラーであり、`PLAYER_HULL_RADIUS`（2.6 m）が剛体接触と被弾判定の両方に使われる。`simulation/contact.ts` の全ての判定、`physics/sphere-contact.ts` の掃引球、`physics/attractor.ts` の `reachedBody` がこの球を前提にしている。

背骨断面システムは、長さ数十メートルの細長いロケットや、扁平な機体を作れるようにする。これらを1つの球で表すと、当たり判定が形状とまったく合わない。**3巻のどこにもこの問題への言及がない。**

判断が必要な選択肢:

| 案 | 内容 | 費用 |
|---|---|---|
| A | 球のまま。半径は外接球とする | 最小。ただし細長い機体の当たり判定が破綻する |
| B | 球のまま。半径は体積等価球とする | 最小。長さ方向で当たらず、横方向で当たりすぎる |
| C | エッジごとにカプセルを持ち、カプセル群として判定する | 中。`SpatialGrid` の近傍探索はそのまま使え、掃引球をカプセル対カプセルに拡張する |
| D | 凸包を持ち、GJK で判定する | 大 |

**C を推奨する。**背骨のエッジはすでにカプセルに近い形をしており、`sweptSphereToi` をカプセル対応に拡張する費用は限定的である。被弾位置からどの部品が損傷するかも、そのカプセルに割り当てられた搭載要素から自然に決まる。第2巻に節を追加すべきである。

### 1-2. 【重大】`bcInv` と `srpCoeff` が現在すでに食い違っている

`const.ts` の定義は次のようになっている。

```
SHIP_BCINV     = 3.3e-3   // コメント: Cd≈2.2, A≈12m², m≈8t
SHIP_SRP_COEFF = 1.56e-2  // コメント: C_R≈1.3, A≈12m², m=PLAYER_MASS
PLAYER_MASS    = 1000
```

`bcInv` は質量 8 t を仮定し、`srpCoeff` は 1000 kg を仮定している。同じ機体に対して8倍異なる質量が使われている。第2巻が両方を形状と実質量から導出すればこの食い違いは自然に解消するが、**計画には `Cd` と `C_R` の決め方が書かれていない。**参照断面積は導出できても、係数がなければ `bcInv` は決まらない。

`Cd` は形状に依存する（球 0.5、円柱の側面 1.2、平板 2.0 前後）。計画に「`Cd` は姿勢と速度方向の関係から毎フレーム求めるのか、設計時に固定値を置くのか」を書く必要がある。**設計時に主軸3方向ぶんを求め、飛行中は速度方向に最も近い軸の値を使う**のが、費用と正確さの釣り合いとして妥当である。

### 1-3. 【重大】RCSスラスタと武装の取り付け位置が動的になる

`render/rcs-nozzles.ts` の `RCS_NOZZLES` は固定のテーブルであり、`RcsEffects` は各ノズルが生む τ_k = r_k × (−exhaust_k) を構築時に一度だけ求めて、噴くノズルを選んでいる。`render/ships.ts` の `MUZZLE_OFFSETS` も同様に固定である。`tools/export-models.mjs` はこのテーブルを TypeScript コンパイラ API 経由で読み、ベイク済みアセットと一致させている。

背骨設計になると、これらは**設計ごとに変わる**。第1巻はトルクの配分だけを扱い、どのスラスタが噴くかには触れていない。第2巻は搭載要素の配置を扱うが、`RCS_NOZZLES` に相当するテーブルの生成に触れていない。

必要な記述:

- 設計から `RcsNozzle[]` 相当を導出する関数（取り付けノードの位置と接続口の向きから、r_k と exhaust_k が決まる）
- 姿勢トルクの配分が、任意個・任意配置のスラスタに対して成立すること。**現在の実装は6方向固定を前提としているが、一般の配置では「要求トルクを出す推力の組み合わせ」は劣決定な線形計画問題になる。**最小二乗擬似逆行列か、推進剤消費を最小化する線形計画で解く必要がある。第1巻の `allocateTorque` はホイールとRCSの2者配分しか書いていない。
- `export-assets` の役割が変わること（自機モデルのベイクが不要になる）

### 1-4. 【中】ベルト・ラジエータ・ソーラーパネルの取り付けが固定座標である

`player/belt.ts` の弾薬ベルトは `player.obj` の子として吊るされ、`RADIATOR_HINGE` はラジエータの折り畳み起点を固定座標で持ち、`PowerSystem` は太陽電池の法線を機体固定の `(0,1,0)` としている。

背骨設計では、これらはすべて取り付けたノードの位置と向きから決まる。第2巻 §7 に「外装の搭載要素は取り付けたノードの接続口の位置と向きに置く」とあるが、**可動部（ラジエータの展開、ベルトの垂れ下がり）の取り付け規約が書かれていない。**接続口のローカル座標系（法線と基準ロール方向）を可動部の基準にする、と明記すべきである。

### 1-5. 【中】敵艦の質量特性の出所が2系統になる

`Enemy` は `inertiaForEnemyKind(enemyKind)` で慣性テンソルを得ており、`ENEMY_SCALE`（20倍）と `ENEMY_RADIUS`（180 m）を持つ。第1巻は `Vessel` への統合を扱うが、**敵が背骨を持つかどうかを述べていない。**

- 敵も背骨を持つなら、敵の設計データを用意する必要がある（作業量が大きい）
- 敵が背骨を持たないなら、`Vessel` は「背骨を持つ機体」と「持たない機体」の両方を扱うことになり、質量特性の導出が2系統になる

**当面は敵を背骨の外に置き、`MassProperties` を直接与える経路を残す**のが現実的である。第1巻に明記すべきである。

### 1-6. 【中】`Base` の格納ドックとハッチが基地モジュールに移る

`game-entity/base.ts` は `BASE_HATCH_LOCAL_POS` / `BASE_HATCH_LOCAL_NORMAL` / `BASE_DOCK_SLOTS` / `BASE_MAX_VESSELS` を持ち、`Controllable` を実装している。`Docking.checkProximity` はこれらを読んで格納判定を行う。

第1巻の `Vessel` 統合でこれらは基地モジュール部品に移るが、**ドッキングそのものは延期されている。**したがって第1巻は「現在の距離と相対速度による格納判定を、基地モジュール部品から読む形に置き換えて維持する」ことを明記する必要がある。書かれていないと、統合の途中で格納が動かなくなる。

### 1-7. 【中】`MapPickable.kind` と表示トグルが実体の統合と食い違う

`MapPickable.kind` は `'player' | 'ship' | 'ammo' | 'base'` を区別し、`MapVisibilityPolicy.entity(kind, ...)` は自艦・敵・弾薬・基地の4トグルを持つ。`CreativeStage.placeObject` は `objectType` で4種を作り分ける。`Targeter` の `CombatTarget` は `Enemy | Player` である。

`Vessel` に統合した後、これらの `kind` を何から導くかを決める必要がある。**「基地モジュールを持つか」「敵対勢力か」の2軸から導く**のが自然だが、第1巻に記述がない。

### 1-8. 【中】`Simulator` と `EntityManager` の配列走査

`Simulator.stepAttitudes` は players / enemies / casings / debris / ammos の5配列を回し、`EntityManager.all()` / `otherEntities()` / `attractors()` / `sync()` / `applyVisibility()` / `perfCounts()` がそれぞれ配列構成に依存している。`vessels` 1本への統合は、これら全てに波及する。

第1巻の §8 変更点に `entity-manager.ts` の記載はあるが、**波及範囲の一覧がない。**統合の作業量を見積もるには、影響する関数の列挙が要る。

### 1-9. 【軽】`THROTTLE_LEVELS` の4段とエンジンの絞り範囲が整合しない

`THROTTLE_LEVELS = [5.0, 20.0, 100.0, 400.0]` は加速度 [m/s²] の4段であり、キー `[1]`〜`[4]` で選ぶ。エンジンのサイクルごとの絞り範囲（20〜100%、30〜100%、60〜100%）とは意味も単位も異なる。

第1巻は絞り範囲を性能値として定義するが、**スロットル操作をどう変えるかを書いていない。**4段の絶対加速度指定を残すのか、絞り率のパーセント指定に変えるのかは、操作感に直接影響する判断である。

## 2. 実装が曖昧で判断が必要な箇所

### 2-1. 【重大】ノードの体積が誰のものか

第2巻はエッジのロフト体積を内容積とするが、**3本以上のエッジが集まるノードで、ノード自身の体積をどう扱うかが未定義である。**軸方向2本のエッジが1つのノードを共有する場合、そのノードは面であって体積を持たないので問題はない。しかし側面分岐があるノードでは、分岐部が本体の内側に食い込む。

第2巻 §1-3 は「平面同士の突き合わせであり、本体の外皮と交差しない」としているが、これは**分岐エッジが本体の外皮の外側から始まる**ことを意味する。すなわち分岐部の付け根は本体の表面であり、内側は本体の内容積のままである。この解釈を明記すべきである。この場合、分岐エッジの内容積と本体の内容積は連続していないので、**タンクをまたいで配置することはできない**。設計上の制約として書く必要がある。

### 2-2. 【重大】側面の口の「規定の幅」が未定義

第2巻 §4 は「側面の口の大きさは、その辺の長さと、辺に沿った規定の幅で決まる」とするが、幅の決定則がない。これは以下すべてに影響する。

- 分岐できる断面の最大寸法
- 円の弓形をどれだけ切り落とすか
- 分岐部が隣接する辺の口と干渉するかどうか

**幅は軸方向の長さである。**口の平面は、辺の方向（周方向）と軸方向が張る矩形になる。軸方向の幅を何で決めるか（固定値、断面の外接円半径に比例、プレイヤー指定）を決める必要がある。**外接円半径に比例させる**のが、大きな断面には大きな分岐が付けられて自然である。

### 2-3. 【中】外皮の肉厚と構造質量

第2巻 §6-3 は「構造の質量は外皮の表面積と肉厚から求める」とするが、肉厚の決定則がない。断面寸法に比例させるのか、内圧と材料強度から求めるのか、固定値かで、大型機体の質量比が大きく変わる。

**内圧を持つ区画（タンク、コックピット）は内圧と半径から薄肉圧力容器の式で求め、内圧を持たない区画は座屈に対する最小肉厚とする**のが工学的に正しく、かつ「タンクを大きくすると質量が半径に比例して増える」という設計判断を生む。

### 2-4. 【中】段跨ぎ燃焼の禁止をどう判定するか

第1巻と第3巻はともに「1つのマニューバノードの燃焼が1つの段の中で完結するよう、設計エディタと計画UIで制約する」とするが、判定式がない。燃焼中に段が尽きるかどうかは、そのノードの Δv と現在の推進剤残量から求まる。

**判定は `propellantForDv(dv, mDry, isp)` が現在の段の推進剤残量を超えるかどうか**である。超える場合、UIは「ノードを2つに分割する」ことを提案すべきである。禁止するだけでは、プレイヤーは何をすればよいか分からない。

### 2-5. 【中】生産コストの通貨と資源

第2巻 §9-3 は「資源とクレジットを消費して」とするが、資源経済は延期側の文書にある。現在の実装はクレジットのみである。**第2巻の段階では何を消費するのかを確定させる必要がある。**

### 2-6. 【軽】円の分岐で弓形を切った後の輪郭サンプリング

第2巻は輪郭を120点に等分するとするが、弦で切った円は円弧と直線の複合であり、等分の定義が変わる。弧長で等分するのか、角度で等分するのかを決める必要がある。**弧長で等分**するのが、ロフトの帯の面積が均等になり自然である。

## 3. 宇宙工学的に不自然な箇所

### 3-1. 【重大】液体酸素／シランの比推力 330 秒は高すぎる

シラン（SiH₄）の燃焼生成物は二酸化ケイ素（SiO₂）と水である。SiO₂ は燃焼室・ノズルの温度で**凝縮相**であり、凝縮相の存在は膨張過程で仕事に寄与しないため比推力を大きく下げる（固体推進剤のアルミナと同じ機構）。実測ベースの推定値は **250〜280 秒**が妥当であり、330 秒は液体酸素／メタンに近すぎる。

さらに、SiO₂ がノズルスロートに堆積するため、**連続燃焼時間に上限がある**。

**訂正案** — 比推力を 265 秒とし、「月のレゴリスと水氷だけで生産できる唯一の液体推進剤だが、性能は固体モーター並みで、燃焼時間に上限がある」という位置づけにする。これは資源進行（後述の第4巻）において「最初に自給できる液体推進剤」として正しい役割を持ち、より高性能な推進剤を求めて外へ出る動機になる。

### 3-2. 【中】ハイブリッド（ABS樹脂＋亜酸化窒素）の比推力 300 秒は高すぎる

亜酸化窒素（N₂O）は分子内の酸素比率が低く、酸化剤としての性能が液体酸素に劣る。ABS/N₂O の実測は真空で **250〜270 秒**である。300 秒に近づけたいなら酸化剤を液体酸素にする（ABS/LOX）。

**訂正案** — ABS/N₂O を 260 秒とし、ABS/LOX を 305 秒として別に登録する。N₂O は**自己加圧できる**（蒸気圧が高い）という利点があり、イナートガスタンクが不要になる。これは第3巻の与圧システムに対する明確な設計上の選択肢になる。

### 3-3. 【中】四酸化二窒素／モノメチルヒドラジンの混合比

混合比 O/F = 2.0 としているが、実機の最適混合比は **1.6〜1.7** である（Apollo SPS 1.6、Shuttle OMS 1.65）。2.0 は酸化剤過多で比推力が落ちる領域である。

### 3-4. 【中】エキスパンダーサイクルは液体水素専用ではない

「液体水素専用」としているが、メタンでも成立する。液体水素が有利なのは冷却能力と比熱が大きいためであり、専用ではない。ただし**熱交換量が推力の上限を決める**（推力は再生冷却で受け取れる熱量に制限され、おおよそ 300 kN 程度が上限）という制約は正しく、これを性能表に書くほうが本質的である。

**訂正案** — 「対応推進剤: 極低温のみ。推力に上限がある」とする。

### 3-5. 【中】フライホイールのアンローディングに磁気トルカを使える

第1巻はアンローディングをRCSのみで行うとしている。しかし**地球の磁場が使える領域では、磁気トルカによって推進剤をまったく消費せずにアンローディングできる。**実際の低軌道衛星の標準的な手法である。

これはゲーム的にも良い性質を持つ。低軌道では姿勢制御が事実上無料になり、月周辺やラグランジュ点では磁場が使えないためRCS推進剤を消費する。**活動領域によって運用の性格が変わる**という、この作品の主題に合った差になる。磁気トルカは電力を消費し、トルクは小さく、磁場に平行な軸まわりのトルクは出せない（3軸のうち1軸が瞬間的に制御できない）という実際の制約もそのまま入る。

追加を推奨する。

### 3-6. 【中】重力傾斜トルクが考慮されていない

細長い機体は重力勾配によってトルクを受け、長軸を天底方向に向けようとする。慣性テンソルの差が大きいほど強い。この作品は**ジャニベコフ効果を売りにしており、慣性テンソルを形状から導出する**のだから、重力傾斜トルクを入れないのは不自然である。

低軌道では無視できない大きさであり（角速度の時定数は軌道周期の程度）、姿勢制御の消費に効く。`physics/` の純関数として数行で書ける。

```
τ_gg = 3·(μ/r³) · (r̂ × (I·r̂))
```

追加を推奨する。

### 3-7. 【中】極低温推進剤の始動損失が考慮されていない

極低温エンジンは点火のたびに配管とポンプを冷却する必要があり（チルダウン）、推進剤を数キログラムから数十キログラム捨てる。多数回の点火を行う運用では無視できない。

第1巻はサイクルごとの再着火回数を性能値に持つので、**点火1回あたりの損失質量**を並べて持つのが自然である。「液体水素は比推力が最高だが、細かい軌道修正を何度も行うと損失が積み上がる」という、実際の運用上の判断がそのまま入る。

### 3-8. 【中】ヒドラジンの劣化機構

第1巻・第3巻は「触媒毒による自己分解」としているが、これは正確ではない。ヒドラジン自体は密閉容器内で10年以上安定である。劣化するのは**触媒床**（分解触媒の活性低下）であり、推進剤の残量ではなく**触媒の性能**が落ちる。

**訂正案** — ヒドラジン単推進剤スラスタは「累積の噴射時間に応じて比推力が低下する」とし、整備によって回復するものとする。推進剤が減るのではなく性能が落ちる、という別の劣化の形になり、極低温の蒸発損失と対比が付く。

### 3-9. 【中】推進剤の凝固点と加熱電力

日陰では推進剤が凍る。ヒドラジンの融点は 2 °C、四酸化二窒素は −11 °C であり、**常温貯蔵性推進剤ほど凍結の危険がある**。実機はタンクとバルブと配管にヒータを持ち、電力を消費し続ける。

これは電力系と推進剤の結び付きを生み、「日陰の長い軌道では常温貯蔵性推進剤の維持に電力が要る」という設計判断になる。極低温推進剤は逆に、日射で蒸発するが凍らない。**対比が明確で、電力系に意味を与える。**追加を推奨する。

### 3-10. 【軽】冷ガスにヘリウムの選択肢がない

窒素冷ガスの比推力 70 秒に対し、**ヘリウム冷ガスは 165 秒**である。イナートガスとしてヘリウムを持つなら、それをそのまま冷ガススラスタに使える。追加は容易であり、選択肢が増える。

### 3-11. 【軽】材料適合性

推進剤とタンク材料には適合性がある。過酸化水素は多くの金属と接触すると分解し、特定の材料（アルミの高純度品、一部のステンレス）しか使えない。液体水素は水素脆化を起こす。四酸化二窒素はチタンと応力腐食割れを起こす。

資源進行（後述）で入手できる金属が段階的に増える設計なら、**「この推進剤を使うにはこの金属が要る」という自然な依存**になる。

### 3-12. 【軽】ノズル膨張比と機体長

真空専用エンジンは膨張比を大きく取るためノズルが長く重い。比推力の高いエンジンほどノズルが長い。**背骨設計では、ノズルが機体の後端から突き出す長さとして目に見える。**性能値に「全長」を持たせ、設計エディタで実際に長く描くのが自然である。

## 4. 実装順について

### 4-1. 第2巻 S3 が大きすぎる

S3 は「背骨のデータ構造」「質量特性の導出」「既定設計の定義」「既存機体の置き換え」「`const.ts` の定数廃止」を1段階に含んでいる。これは第2巻で最も大きく、最も危険な段階である。

**分割案:**

- S3a — 背骨のデータ構造と既定設計の定義。質量特性は導出するが、機体には適用せず、既存の定数と一致することをテストで確かめるだけ
- S3b — 導出した質量特性を機体に適用し、`const.ts` の定数を廃止する

S3a で「導出値が既存の定数と一致する」ことを確かめてから適用すれば、姿勢運動が変わった原因が導出の誤りなのか適用の誤りなのかを切り分けられる。

### 4-2. 第3巻の順序は分離を先にすべき

第3巻は「配管 → 与圧 → 分離 → ペイロード → UI」の順である。しかし**分離（多段）は配管に依存しない**。分離の実装は運動量保存と背骨の切断であり、配管より軽く、単体で価値が大きい（多段ロケットが飛ぶようになる）。

**「分離 → ペイロード → 配管 → 与圧 → UI」を推奨する。**配管を跨ぐ分離（クロスフィード）の処理だけが後になるが、それは配管が実装されてから足せばよい。

### 4-3. 第1巻と第2巻の並行

第2巻の §3・§5・§6（断面と立体の幾何、純関数のみ）は依存がなく、第1巻と並行できる。索引に記載済みであり、妥当である。

ただし**第2巻 S3 は第1巻の完了を待つ**必要がある。`Vessel` 統合の前に背骨を入れると、`Ship` / `Player` / `Base` の3クラスすべてに背骨を持たせることになる。

## 5. ゲーム性が落ちる懸念

### 5-1. 【重大】配管の敷設が単調作業になる

第3巻は、エッジごとに推進剤の種別と口径を選んで配管を敷く操作を求める。ノード数が20を超える機体では、これは数十回のクリックになる。**タンクからエンジンへ配管を通すことは、ほとんどの場合に唯一の正解しかない。**選択の余地がない操作を数十回繰り返させるのは、作業であって遊びではない。

**「自動敷設」を既定とし、手動の敷設はその上書きとする**ことを推奨する。自動敷設は、各エンジンに対して最も近いタンクから最短経路で配管を通す。プレイヤーが手で触るのは、クロスフィードを組む場合、口径を絞って軽量化する場合、特定のタンクを特定のエンジンに割り当てる場合だけになる。**選択に意味があるときだけ操作を求める**という形になる。

### 5-2. 【中】設計エディタのモードが多い

骨格・断面・搭載・塗装に、配管と段が加わって6つになる。モードの切り替えは、プレイヤーが「今どのモードにいるか」を常に把握していなければならない負担を生む。

**骨格モードと断面モードは統合できる。**断面はノードの属性であり、ノードを選んだときに左パネルへ断面の編集欄が出れば足りる。複合断面のツリー編集だけが場所を取るが、これは折り畳める。統合すれば5つになる。

段モードは「分離順の並べ替え」と「段ごとの Δv 表示」だけであり、独立したモードにするほどの内容ではない。**右パネルの常設表示に段の一覧を置き、モードは廃止する**ことも検討に値する。

### 5-3. 【中】0.5 メートル単位の量子化が大型機で粗すぎる可能性

エッジ長と断面半径を 0.5 m 単位とするのは、小型機では適切である。しかし全長 50 m の機体では 0.5 m は 1% であり十分だが、**半径 1.0 m のタンクを 1.5 m にすると体積が 2.25 倍になる。**小型機では粒度が粗すぎる可能性がある。

半径のみ 0.25 m 単位にする、または半径の刻みを絶対値に応じて変える（2 m 未満は 0.25 m、以上は 0.5 m）ことを検討すべきである。

### 5-4. 【中】生産時間0が既定であることの扱い

第2巻は「初期状態では係数を0とし、すべての設計が即座に完成する」とする。これは正しい判断であるが、**係数を後から有効にすると、既存のセーブでいきなり待ち時間が発生する。**係数はセーブに含めるか、ステージごとの設定にするかを決めておくべきである。

### 5-5. 【軽】フライホイールの飽和が分かりにくい

飽和が近いことは HUD のメーターで示すとしているが、**飽和した瞬間に何が起きるかは分かりにくい**（姿勢制御がRCSに切り替わり、推進剤が減り始める）。切り替わりの瞬間に音か短い通知を出すのが親切である。

## 8. 優先して判断すべきこと

着手前に決めておかないと手戻りになるものを、順に挙げる。

1. **接触形状**（§1-1）— 球のままか、カプセル群か。第2巻の設計に影響する
2. **RCSスラスタの任意配置に対するトルク配分**（§1-3）— 第1巻の `allocateTorque` の設計そのものに影響する
3. **敵艦が背骨を持つか**（§1-5）— 第1巻の `Vessel` の形に影響する
4. **配管の自動敷設**（§5-1）— 第3巻の UI 設計に影響する
5. **`Cd` の決め方**（§1-2）— 第2巻の質量特性に含まれる
6. **液体酸素／シランの比推力**（§3-1）— 資源進行の設計に直接影響する
