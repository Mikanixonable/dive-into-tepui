# 第12版 主推進系の搭載計画

作成日 2026-08-20。既定の有人艦・軌道基地へ主機の推進系(酸化剤タンク・燃料タンク・配管・
加圧ガスタンク)を積む。併せて、内装要素が外装として取り付けられる不具合を直す。

---

# 1. 問題 — 「部品を足す」では済まない

調査の結果、**推進剤の量という概念が `rcs_tank` にしか無い**ことが判明した。これが計画全体の形を
決めるので、先に事実を並べる。

## 1-1. 主機は RCS のヒドラジンタンクを燃やしている

`Vessel.consumeFuel` → [part-inventory.ts:224-238](src/game/vessel/part-inventory.ts#L224-L238) は
`rcsTankRefs` だけを減らす。呼び出し元は3つで、**主機の噴射も RCS の噴射も同じ関数を通る**:

| 呼び出し元 | 何の噴射か | 実際に減るもの |
|---|---|---|
| [throttle.ts:164](src/game/vessel/throttle.ts#L164) `buildThrust` | 主機 | `rcs_tank` のヒドラジン |
| [throttle.ts:227](src/game/vessel/throttle.ts#L227) `updateTorque` | 姿勢制御 RCS | 同上 |
| [plan-executor.ts:178](src/game/plan/plan-executor.ts#L178) | 主機(自動操縦) | 同上 |

主機は四酸化二窒素を燃やすことになっているのに、減るのはヒドラジンである。

## 1-2. 主タンクは「いくら入っているか」を持てない

```ts
interface PropellantTankFields { propellant; volume; material; }   // ← 量が無い
interface RcsTankPart extends Part, PropellantTankFields { maxFuel; fuel; }  // ← ここだけ量がある
```

`oxidizer_tank`/`reductant_tank` は容積と材料しか持たない。**積んでも、入れる場所が無い。**

## 1-3. 推進剤の質量は現に効いていない

`deriveMassProperties(assembly, propellant)` の第2引数を渡している呼び出しは**1つも無い**
(全5箇所が1引数)。推進剤を積んでも機体は重くならない。

## 1-4. 検査の非対称

`checkFeedContinuity` は配管が1つも無ければ早期 return するので、**タンク不在も配管不在も報告
されない**。`checkPressurant` だけがその逃げ道を持たないため、唯一鳴っている。

## 1-5. エンジンは推進剤を1つしか名指せない

`EnginePart.propellant` は **`PropellantId` 1つ**であり、検査もすべて `part.propellant` の単数を
読む([blueprint-validation.ts:455](src/game/vessel/blueprint-validation.ts#L455)、
[:463](src/game/vessel/blueprint-validation.ts#L463)、
[:482](src/game/vessel/blueprint-validation.ts#L482))。CLAUDE.md も「エンジンはサイクル×推進剤の
対」と述べているが、この「対」は **(サイクル, 推進剤)** であって (酸化剤, 燃料) ではない。

**したがって、いまの模型では二液推進を表せない。** 酸化剤タンクと燃料タンクを両方積んでも、
`checkFeedContinuity` が要求するのは `engine.propellant` に一致するタンク1種だけで、
もう一方は**どの検査からも要求されず、消費もされない飾り**になる。

一方で `needsCatalystBed('hydrazine')`([build-cost.ts:123-125](src/game/economy/build-cost.ts#L123-L125))
と `catalystMassFor(thrust)` が既に在り、**単推進剤ヒドラジンは模型が想定している**。

## 1-6. 数値(実測)

| | 内容積 合計 | 使用 | 空き |
|---|---|---|---|
| 有人艦 | 16.09 m³ | 11.05 m³ | **5.04 m³** |
| 軌道基地 | 18,629.91 m³ | 292.11 m³ | 18,337.80 m³ |

有人艦の乾燥質量 1,153 kg。`aft` エッジ(`mid-node`→`tail`、容積 5.28 m³、使用 1.05 m³)は
`crewedAssembly` の冒頭コメントが**「推進剤区画」**と呼んでいる区画そのもので、その後端 `tail` に
主機が付いている。

# 2. 要件

**R0 が判断、R1〜R2 が模型の欠落を埋める部分、R3〜R4 が設計そのもの、R5〜R6 が周辺、R7 が別件。**
番号は依存の順ではなく、読む順に付けている —— R0 は R3 の前提であり、R1/R2 とは独立に決められる。

## R1. 推進剤の量を、タンクの種別によらず1つの概念にする

**問題**: 量を持てるのは `rcs_tank` だけ(§1-2)。しかも容量 `maxFuel` を部品が直に宣言しており、
容積 `volume` と二重に定義されている。

**要件**: どのタンクも「いま何 kg 入っているか」を持ち、**容量は宣言ではなく導出**とする。

**実装**:
- `PropellantTankFields` に `fuel: number`(現在量 [kg])を足す。
- 容量は `volume × 推進剤の密度` の導出値にする。密度は `RESOURCES[PROPELLANT_RESOURCE[id]].density`
  から引ける(ヒドラジン 1021、四酸化二窒素 1443 kg/m³ が既に在る)。導出関数は
  `propellant-compatibility.ts` に置く —— 推進剤の物性は既にそこの持ち物だから。
- **`rcs_tank` の `maxFuel` を消す。** 容量が容積から出るなら、宣言は要らない。

**責務**: 「どれだけ入るか」は推進剤の物性と容積が決めるのであって、タンクが宣言することではない。
「いまどれだけ入っているか」だけがタンクの状態である。

**決めること**: `C.CREWED_RCS_FUEL_CAPACITY` の扱い。容量が導出になると、この定数は
「RCSタンクの容積」を決める形へ変わる(意味が変わるので置き場所も見直す)。

**影響**: `parts.ts` / `part-inventory.ts` / `vessel-parts.ts` / `vessel-parts.test.ts`。

## R2. 消費を推進剤ごとに分ける

**問題**: `consumeFuel(amount)` が推進剤を問わず `rcs_tank` を減らす(§1-1)。

**要件**: 消費・補給・残量のいずれも**推進剤を指定して問う**形にする。

**実装**:
- `PartInventory`: `consumeFuel(propellant, amount)` / `refuel(propellant, amount)` /
  `fuelOf(propellant)` / `maxFuelOf(propellant)`。`totalFuel`/`totalMaxFuel` は消える。
- 呼び出し3箇所は、それぞれ自分が燃やすものを指定する —— 主機は `engine.propellant`、
  姿勢制御 RCS は `rcs_thruster.propellant`。`plan-executor.ts` は主機。
- `PlanExecutorShip`(狭い構造的インターフェース)の `consumeFuel` の形も揃える。

**責務**: 「どの推進剤を燃やすか」は噴射する部品が知っていることで、タンクの側の問題ではない。

**注意**: 「機体の推進剤は1種類」という暗黙の前提が消える。HUD の燃料表示(1本のバー)は
**推進剤ごとの表示**にする必要がある(R5)。

**影響**: `part-inventory.ts` / `throttle.ts` / `plan-executor.ts` / `vessel.ts`。

## R0. 主機が何を燃やすかを決める(**判断が要る。ここが計画の分岐点**)

**問題**: 案Bの姿(酸化剤タンク+燃料タンク)は二液推進だが、**いまの模型は二液推進を表せない**
(§1-5)。この判断をせずに R3 以降へ進むと、燃料タンクが飾りとして載るだけになる。

**取りうる3つ。いずれも「主機が自分の推進剤を持ち、それを燃やす」という目的は果たす。**

### R0-a. エンジンを推進剤の対に拡張する(案Bの字義どおり)

`EnginePart` が酸化剤と燃料の2つを名指し、混合比を持つ。`checkFeedContinuity` は両方のタンクと
配管を要求し、`consumeFuel` は混合比に従って両方から引く。

- **利点**: 二液推進が表せるようになる。比推力 320 s という現在の宣言と辻褄が合う
  (単推進剤では 230 s 級)。実機の推進系がそのまま表せる。
- **欠点**: **搭載要素の仕様(第9版)そのものを変える。** `part.propellant` を読む検査5箇所、
  `propellantVolume`、`PROPELLANT_RESOURCE` を引く経路、補給の単位が全部影響を受ける。
  この計画のどの要件よりも大きい。
- **範囲**: 実質「R0 だけで1つの計画」になる。

### R0-b. 主機を単推進剤ヒドラジンにする(模型の粒度に合わせる)

`engine.propellant` を `'hydrazine'` にし、タンク1つ・配管1つ・加圧ガスタンク1つを積む。

- **利点**: **模型を変えずに設計が正しくなる。** `needsCatalystBed`/`catalystMassFor` が既に
  この形を想定しており、触媒床の質量も自動で乗る。ヒドラジンは自己加圧しないので**加圧ガス
  タンクは依然として必要** —— いま鳴っている指摘を、逃げずに満たすことになる。
- **欠点**: 比推力を 320 → 230 s 相当へ下げるのが筋(同じ推進剤質量で Δv が約3割減る)。
  RCS もヒドラジンなので**主機と RCS が同じタンク群を共有する**ことになり、§1-1 で問題視した
  「主機が RCS のタンクを減らす」状態が、こんどは**正しい振る舞いとして**残る。
- **範囲**: R3 に吸収される。

### R0-c. 主機を単推進剤の過酸化水素にする

`engine.propellant` を `'hydrogen-peroxide'` にする。RCS のヒドラジンとは別系統になるので、
R2 の推進剤ごとの分離が実際に意味を持つ。

- **利点**: R0-b の利点に加えて、**主機と RCS のタンクが独立する。**
- **欠点**: 単推進剤の過酸化水素は比推力が更に低い(150 s 級)。資源としては
  過酸化水素合成炉が既に在る。

**この計画は R0 の答えを前提にしている。決めるまで R3 以降は着手できない。**
規模で並べると **R0-b < R0-c ≪ R0-a**。

### 決定: R0-b(単推進剤ヒドラジン)

理由:
- **R0-a は搭載要素の仕様(第9版)そのものを変える。** この計画の他のどの要件よりも大きく、
  計画自身が「R0 だけで1つの計画になる」と書いている。ここに混ぜるのは筋が通らない。
- **R0-b は模型を1行も変えずに設計を正しくする。** `needsCatalystBed('hydrazine')` と
  `catalystMassFor(thrust)` が既にこの形を想定しており、触媒床の質量も自動で乗る。
- **ヒドラジンは自己加圧しない**ので加圧ガスタンクは依然として必要 —— いま鳴っている指摘を、
  逃げずに満たすことになる。
- **主機と RCS がタンク群を共有する**のは、§1-1 で問題視した状態とは別物である。あれは
  「四酸化二窒素を燃やすと宣言しながらヒドラジンが減る」という**宣言と実態の食い違い**であり、
  R0-b では宣言と実態が一致する。同じ推進剤を配管で共有するのは実機でも普通のことで、
  `checkFeedContinuity` が配管の連結を要求する以上、**繋がっているから共有できる**という筋が通る。
- **後から R0-a へ進む道を塞がない。** 単推進剤の設計は二液の模型の上でも表せる。

併せて決めること: 比推力を単推進剤ヒドラジンの水準(230 s 級、RCS スラスタの宣言値と同じ)へ
下げる。320 s は二液推進の値であり、R0-b のもとでは宣言と実態が食い違う。

## R3. 既定設計へ推進系を積む

**要件**: 有人艦と軌道基地が、主機を実際に動かせる推進系を持つ。

**実装**(R0 の答えで積むものが変わる):

| R0 の選択 | 積むもの(有人艦の `aft` へ) |
|---|---|
| R0-a | `oxidizer_tank`(NTO・**アルミのみ**)+ `reductant_tank`(ヒドラジン・アルミ)+ `plumbing`×2 + `pressurant_tank`(ヘリウム) |
| R0-b | `reductant_tank`(ヒドラジン・アルミ)+ `plumbing`×1 + `pressurant_tank` |
| R0-c | `reductant_tank`(過酸化水素・アルミ/鉄)+ `plumbing`×1 + `pressurant_tank` |

置き場所はいずれも `aft` エッジ。`crewedAssembly` の冒頭コメントがそこを**「推進剤区画」**と
呼んでおり、後端 `tail` に主機が付いている。**設計の意図が既にその場所を空けてある。**

**決めること — 容積は Δv の目標から逆算する。空き容積いっぱいに取らない。**
`aft` の空きは 4.2 m³ で、そこを埋めると推進剤だけで約 4,300〜5,200 kg —— 乾燥質量 1,153 kg の
**4〜5倍**になる。`tuneActuators` が推力を質量から引き直すので操作の手触りは保たれるが、装甲・熱・
電力の調整値はすべて 1,153 kg の機体を前提にしている。**先に「この艦に持たせたい Δv」を決め、
比推力と合わせて容積を出す。**

**影響**: `vessel-parts.ts` / `vessel-assemblies.ts` / `const.ts`。

## R4. 推進系を積んだ設計が検査を通る

**問題**: 配管を1つでも積むと `checkFeedContinuity` の早期 return が外れ、**それまで黙っていた
検査が働きだす**(§1-4)。

**要件**: R3 の配置がすべての検査を通る。

**満たすべき条件**:
- **`checkFeedContinuity`** — 推進剤ごとに、その推進剤を運ぶ配管のエッジだけを辿った連結成分
  (`components`)の中で、エンジンの取付ノード(`mountNodes` = `tail`)と、同じ推進剤のタンクが
  載っているエッジの端点が同じ成分に属すること。**`aft` に配管とタンクを置けば `tail` に届く**
  (`aft` の端点が `mid-node` と `tail`)。
- **`checkTankMaterials`** — NTO タンクはアルミ。
- **`checkInternalVolume`** — R3 で決めた容積が `aft` の空き 4.2 m³ に収まること。
- **`checkPressurant`** — 加圧ガスタンクを積めば通る(これが今唯一鳴っている指摘)。
- **`checkStages`** — 分離順の検査。既定設計は単段なので影響しないはずだが、**要確認**。

**責務**: ここは新しい規則を書く作業ではない。**既にある検査を満たす配置を選ぶ**だけである。

## R5. 生産・補給・保存が主タンクを扱う

**要件**: 積んだ推進系が、作れて、補給でき、保存される。

**実装**:
- **生産**: `propellantTankOf` は既に `oxidizer_tank`/`reductant_tank` を見ており、殻の質量を
  `chooseTankMaterial` が選んだ材料で課金する。**新たな実装は要らない** —— アルミが基地の初期設備で
  作れるかだけ**要確認**。
- **補給**: `base-operations-window.ts` は `rcs_tank` にだけ補給ボタンを出している
  ([:522](src/game/hud/base-operations-window.ts#L522))。**R1 で量が共通化されれば、この分岐は
  「推進剤タンクなら」に広がるだけで済む。**
- **HUD**: 燃料表示を推進剤ごとにする(R2 の帰結)。
- **保存**: 部品配列ごと保存されるなら `fuel` も乗る。**要確認**。

## R6. 推進剤の質量が機体に効く

**問題**: `deriveMassProperties` の第2引数を誰も渡していない(§1-3)。積んでも重くならない。

**要件**: 積んだ推進剤の質量が、機体の質量と慣性に入る。

**範囲の判断 —— ここは意図して2段に分ける**:
- **今回の範囲**: 「満載の推進剤を含む質量」を機体の質量とする。`deriveMassProperties` は既に
  `loadedMass` を返しており、`vessel-designs.ts` がそれを読めばよい。
- **今回の範囲外**: **消費に伴って質量が減ること。** `Vessel.massProperties` は構築時に固定され
  `att.inertia` へ写されている。飛行中に変えると慣性テンソルの再導出が要り、姿勢制御・抗力・
  予測のすべてに波及する。**ツィオルコフスキーの式が効きはじめるのはこの段階であり、それ自体が
  独立した1つの変更セットに値する。**

**責務**: 「設計が何 kg か」は `mass-properties.ts`、「いま何 kg か」は `Vessel` —— この2つを
今回は分けたまま、前者だけを正す。

## R7(別件). 内装要素が外装として取り付けられる

**問題**: 部品棚は倉庫の中身を種別で絞らず並べ([assembly-panel.ts:597](src/game/hud/assembly-panel.ts#L597))、
ドラッグ経路が作る配置は `{kind: 'external', mount}` の1種類だけ
([assembly-drag-controller.ts:207](src/game/vessel/assembly-drag-controller.ts#L207))。
`validateMount` は部品の種別を見ない。生産一覧 `producibleParts()` には内装要素が多数含まれる
(バッテリー・弾倉・弾薬・RCSタンク・生命維持・フライホイール・磁気トルカ・コックピット)。

結果、**バッテリーを船体の外側に貼り付けられる**。しかも:
- 内容積の割り当てはその部品を見ない —— 容積を占めないまま載る
- `mass-properties.ts` は外装配置を平板として扱う —— 投影面積が増える
- ゴーストは `FITTINGS` に項が無く `null` —— **何も見えないまま取り付く**

**要件**: 置けないものは掴めない。

**実装**: 部品棚を `ExteriorPartType` に絞る。判定は既存の `isExterior`
([vessel-assemblies.ts:122](src/game/vessel/vessel-assemblies.ts#L122))を使い、第二の判定を
書かない —— ただし**その関数は `parts.ts` へ移す**。いまは既定設計のデータを持つモジュールの
private 関数だが、「ある種別が外装かどうか」は `ExteriorPartType` の union を定義している側の
事実であり、HUD が設計データのモジュールを読みに行くのは筋が違う。

**この要件は R1〜R6 と独立**で、先に単独で入れられる。

# 3. 実施の順序

```
R7 ────────────────────────────────  独立。先に入れられる
R1 → R2 ───────────────────────────  既定設計に触れずに入る
        R0(判断)→ R3 → R4 → R5
                        ↘ R6
```

- **R1 → R2 は分けられない。** 量の持ち方を変えれば消費の形も変わる。1つの変更セット。
- **R3 → R4 も分けられない。** 配置を決めることと検査を通ることは同じ作業の表裏。
- **R5 は R1/R2 の帰結**で、量が共通化された後なら分岐を広げるだけ。
- **R6 は R3 の後**であれば単独で入る。
- **R0 が R0-a なら、それ自体が独立した計画**になる(搭載要素の仕様を変えるため)。

## 変更セットの区切り

| # | 内容 | 要件 | R0 の答えを要するか |
|---|---|---|---|
| 1 | 部品棚を外装要素に絞る | R7 | 不要 |
| 2 | 推進剤の量を共通化し、消費を推進剤ごとに分ける | R1, R2 | **不要** |
| 3 | 既定設計へ推進系を積み、検査を通す | R0, R3, R4 | 要 |
| 4 | 生産・補給・HUD・保存を主タンクへ広げる | R5 | 要 |
| 5 | 満載質量を機体の質量にする | R6 | 要 |

**変更セット1 と 2 は R0 の判断を待たずに着手できる。** とくに 2 は既定設計に触れずに入り
(RCS タンクだけの現状でも、量の持ち方と消費の分け方はそのまま正しくなる)、これが**この計画で
最も重要な性質**である —— 模型の欠落を埋める作業と、設計に部品を積む作業を独立に検証できる。

# 4. 着手前に確かめること

計画の前提のうち裏を取ったもの:

- **`checkStages` は単段の設計に追加の要求をしない。** 分離機構が無ければ `stageOrder` は空で、
  `components` は機体全体を1段と見るので、武器と弾倉は必ず同じ段に入る。
- **アルミは初期設備で作れる。** `smelter` が `INITIAL_FACILITY_IDS` に在り、
  `molten-salt-electrolysis` の `metal-mixture` から出る。
- **加圧ガスの中身の質量は、この計画では扱わない。** `PressurantTankPart` は
  `PropellantTankFields` を継承していないので R1 の対象外であり、`build-cost.ts` の
  `pressurant_tank` も殻(`tank-shell`)と金具(`machinery`)しか課金していない。
  `RESOURCES.helium.density` は 125 kg/m³(液体)で 30 MPa の気体には過大なので、**中身を
  扱うなら気体の状態方程式が要る** —— それは加圧系を模型化する別の変更セットの仕事。
- **タンクを積むこと自体はヒドラジンもヘリウムも要求しない**(課金されるのは殻だけ)。
  ヒドラジンを要求するのは補給(`refuelBlueprintOf`)であり、`hydrazine-furnace` は初期設備に
  無いので、**補給には設備の増設が要る**。これは意図した進行のはず。

残る未確認:

- 部品の `fuel` が保存・復元の経路に乗るか(R5 —— 変更セット2 の中で確かめる)

# 5. 計画のレビュー

4つの観点で自己点検し、直したところを記す。

## 要件が問題の解決になるか

**1件、穴があったので直した。** 当初 R3 は「酸化剤タンクと燃料タンクを積む」と書いていたが、
`EnginePart.propellant` は単数であり、**燃料タンクはどの検査からも要求されず消費もされない飾りに
なる**(§1-5)。「積んだが動かない」で終わるので、要件として成り立っていなかった。
**R0(主機が何を燃やすかを決める)を立て、R3 をその答えに従属させた。**

残りの要件は、§1 に挙げた5つの事実にそれぞれ対応している:

| §1 の事実 | 対応する要件 |
|---|---|
| 1-1 主機が RCS のタンクを燃やす | R2 |
| 1-2 主タンクが量を持てない | R1 |
| 1-3 推進剤の質量が効かない | R6 |
| 1-4 検査の非対称 | R4(配管を積めば早期 return が外れる) |
| 1-5 二液推進を表せない | R0 |

## 解決方法はアドホックではなくシンプルか

- **R1** は「容量は容積と密度から出る」という**導出**にしており、値を足すのではなく**二重定義を
  1つ減らしている**(`rcs_tank.maxFuel` が消える)。
- **R2** は分岐を足すのではなく、`consumeFuel` の引数を1つ増やして**呼び出し側が自分の推進剤を
  名指す**形にした。「機体の推進剤は1種類」という暗黙の前提が、前提でなくなる。
- **R5** は R1/R2 の帰結として**分岐が広がるだけ**で、新しい仕組みを足さない。
- **R7** は既存の `isExterior` を使い、第二の判定を書かない。
- **R6 を2段に割ったのは、アドホックな先送りではない。**「設計が何 kg か」と「いま何 kg か」は
  別の問いであり、後者(消費による質量変化)は慣性テンソルの再導出を伴って姿勢制御・抗力・予測へ
  波及する。境界が概念の側に在る。

## クラスを正しく単一責務に分割できているか

| 判断 | 置き場所 | 理由 |
|---|---|---|
| 推進剤の密度 → 容量 | `propellant-compatibility.ts` | 推進剤の物性は既にそこの持ち物 |
| タンクの現在量 | 部品(`PropellantTankFields.fuel`) | 状態は部品が持つ |
| 推進剤ごとの合計・消費 | `PartInventory` | 部品の集計は元からここ |
| どの推進剤を燃やすか | 噴射する部品(`engine`/`rcs_thruster`) | タンクの側の問題ではない |
| 外装か内装かの分類 | `parts.ts` | union を定義している側の事実 |
| 設計の質量 / 実機の質量 | `mass-properties.ts` / `Vessel` | R6 で分けたまま前者だけを正す |

**1件直した。** R7 の `isExterior` を `vessel-assemblies.ts` から輸出する案は、HUD が**既定設計の
データを持つモジュール**を読みに行くことになる。分類は `ExteriorPartType` を定義している
`parts.ts` の事実なので、関数ごとそちらへ移すことにした。

## 設計が要件を満たしているか

**R0 を除いて満たす。** R0 は3つの選択肢を並べただけで、まだ答えを持っていない —— これは
**意図的**で、比推力・Δv・主機と RCS がタンクを共有するかどうかという**遊びの手触りに関わる
判断**であり、コードからは決まらない。§4 の未確認事項と併せて、着手前に決める。
