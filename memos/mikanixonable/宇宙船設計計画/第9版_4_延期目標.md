# 第4巻 — 延期目標

## 1. 対象

この文書は、**要件が固まっていないか、依存する機能が揃っていないために、実装の順序として後に置く機能**をまとめたものである。

1. 人員（§4）
2. テザー式の重力区画（§5）
3. バッチ生産と補給ミッションの自動化（§6）
4. 敵の構成（§7）

### この4つを後に置く理由

**この4つに共通するのは、実装費用の大きさではなく、決めるべきことがまだ決まっていないことである。**費用が大きいだけの機能は、決まっているならば順に払えばよい。決まっていない機能は、払い始めた先で作り直しになる。

| 機能 | 後に置く理由 |
|---|---|
| **人員** | **要件が固まっていない。**人口の上限は5つの制約の最小値で決まり、その5つがいずれも人口の関数であり、人口がその5つの関数になる。この自己参照を1フレーム内でどう解くかが決まっていない。加えて、役割の充足率が生産・整備・操艦のそれぞれに倍率として効くため、依存の向きを決めないまま書けば循環する。**依存も最も多い。**所属する基地、運ぶ手段、消費する食料と酸素、住む区画のすべてが揃って初めて動く |
| **テザー式の重力区画** | **要件が固まっておらず、依存も残る。**1つの機体が回転する部分と回転しない部分を持つため、機体の姿勢の表現を単一の剛体から拡張することが着手の前提になる。この拡張の形が決まっていない。また、回転による疑似重力の効果を測る対象は人員であり、人員が無ければ実装しても確かめる相手がいない |
| **バッチ生産と補給ミッションの自動化** | **要件が固まっていない。**どこまでを自動にし、どこからをプレイヤーの判断に残すかが、この機能の設計上の最大の論点として残っている（§6-7）。加えて、この機能が自動化するのは手で行える操作の繰り返しであり、手で行う経路が先に成立していることが前提になる |
| **敵の構成** | **要件が固まっていない。**同梱する構造データの選定、ライセンスの確認、部品数の簡約の度合い、既存の低ポリゴンの艦艇と並ぶ絵の調子——いずれも決まっていない。実装費用の大半は最後の1つに出る。他のどの機能にも依存しないため、決まりさえすればいつでも着手できる |

**回転による疑似重力を持たない期間、人員の健康が持つ重力の環境は月面重力と無重力の2種類だけである。**§5 を実装するまで、§4-4 の健康はその2種類に対してのみ定義される。

## 2. 対象外

以下はこの文書でも扱わない。

- **発注すると物資が届く仕組み**。§6 で自動化するのは、機体の生産と、保存した軌道計画の実行である。物資は必ず実在の機体が実在の軌道を飛んで運ぶ。機体・推進剤・通信圏のいずれかが欠ければ自動化は止まる。
- **人員個体の追跡**。人員は役割ごとの人数と、その集団としての健康状態で扱う。一人ひとりに名前と経歴を持たせない。
- **技術ツリー**。研究点も前提技術の木も持たない。できることが広がるのは、資源と設備の連鎖によってのみである。
- **基地内部の間取り**。区画は機体の搭載要素として配置するものであり、部屋の配置図を編集する画面は持たない。
- **シリンダー型の宇宙コロニー**。回転する居住空間は §5 のテザー方式で作る。剛体の巨大円筒は作らない。
- **船外活動**。人員の移動経路は、結合した機体の内部の連絡路に限られる。
- **月以外の天体の地形**。地形の仕組みは天体を問わない形で書くが、実際に高度場を持たせるのは月のみとする。

## 3. 前提

この文書の機能が土台に使うものを挙げる。いずれもこの文書の外で定義され、実装される。

**機体の実体と形状**

- 機体は `Vessel` であり、艦艇・軌道基地・月面基地・無人機はすべて同じ実体である。クラスを分けない。
- 形状は**ツリー**で表す。ツリーはノードとエッジからなるグラフであり、閉路を持ってよい。エッジの種別は `hull` / `truss` / `decoupler` の3種である。`hull` は内容積を持ち、`truss` は持たない。トラスには外装要素を軸に沿った任意の位置に取り付けられる。
- 機体の直径は 0.5 m 単位（断面の外接円半径は 0.25 m 単位）、エッジの長さは 0.5 m 単位で最小 0.5 m である。
- 質量・重心・慣性テンソル・接触形状は、すべて形状から導出する。

**設計・生産・資源**

- 設計は基地を操作対象にした戦闘ビューの組立モードで行い、基地の生産設備で生産する。**通貨は存在せず、市場も存在しない。**すべては資源とエネルギーを消費する生産によって賄われる。
- 基地の区画として、居住区画・農場・生命維持装置・水タンク・ドック・コンテナ接合部・コンテナがある。
- 資源は元素と物質の連鎖として扱い、設備が入力を出力へ変換する。炭素と窒素は敵の撃破によってのみ得られ、水とケイ素は月で得られる。
- 月面基地は月の南極の永久影クレーターにあり、着陸した機体として天体固定座標に静止する。採掘と生産の場である。

**通信**

- 無人機の自動操縦には、機体が通信モジュールを積んでいることと、通信圏内にいることの両方が要る。通信衛星は無人の機体として実装され、プレイヤーが設計・生産・配備する。開始時点で通信基地となっているのは月面基地と近直線ハロー軌道の基地の2つである。

**機体同士の結合**

- ドッキングポートを持つ機体同士が捕獲条件を満たすと結合し、結合体は1つの剛体として積分される。推進剤とガスを移送でき、電力と放熱は結合体全体で1つの収支になる。人員が通れるジョイントで結ばれた範囲では人員が往来できる。**テザー式の中央部への接舷は、この機構の上に置く。**

## 4. 人員

### 4-1. 人口は増えていく

**開始時の総人口は1000人である。これは、一万年にわたる宇宙生活の末に月面で生き残った人類の総数である。**

一万年のあいだ、月の基地は限られた軽元素の閉サイクルで人工生態系を回してきた。炭素・窒素・水素は月では得られず、閉サイクルは完全ではないため、これらは少しずつ失われる。補充する手立てがないまま、人口は生態系が支えられる規模まで縮み、そこで固定された。**1000人という数は、その均衡点である。**増やす方法がなかったのであり、増やさないことを選んでいたのではない。

**1000人のほぼ全員が月面基地に住んでいる。**NRHO の軌道基地に常駐するのは数人から数十人にすぎない。この偏りは放熱から直に導かれる（§4-3）。1人あたり 14〜22 kW の廃熱に対し、軌道上では 100〜150 m² の放熱板が要る。1000人ぶんでは 10〜15 万 m² であり、軌道上の基地として成立する規模ではない。一方、月面の永久影クレーターは約 40 K の巨大な熱溜めであり、同じ廃熱を捨てるのに 1人あたり 22 m²、1000人ぶんでも 21,800 m² の放熱板で足りる。**大規模な居住が月面にしか成立しないことが、人口の分布をそのまま説明する。**

敵は低軌道に限らず現れ、NRHO の軌道基地も襲われうる（§7）。これに対し月面基地は月の重力井戸の底にあり、到達に大きな Δv を要するため相対的に安全である。**これも人口の大半が月面にある理由の1つである。**

**遺伝的多様性は問題にならない。**一万年の宇宙生活のあいだに、遺伝技術によって集団の多様性を維持する手立てが確立している。保存された遺伝情報と、それを用いた多様性の管理により、1000人という規模でも近交弱勢は生じない。**人口が均衡点で固定されていたのは遺伝の問題ではなく、軽元素の閉サイクルが支えられる規模の問題である。**

**確保できる資源とエネルギーの生産量が増えると、食糧生産が増え、人口が増える。**人口はプレイヤーが直接指定する値ではなく、資源とエネルギーを広げた結果として自然に増えるものである。

- 電力が増えれば電照農場を増やせる。
- 炭素と窒素を戦闘で獲得すれば、農場の閉ループの損失を補い、栽培面積を増やせる。
- 放熱面が増えれば、農場と生命維持装置の発熱を捨てられる（§4-3）。
- 居住区画を増やせば人が住める。

**初期の月面基地の設備は、1000人をちょうど支える規模に置く。**開始時の人口は上限に等しく、余裕がない。

| 初期設備 | 値 | 支えられる人数 |
|---|---|---|
| 農場の栽培面積 | 45,000 m² | 45 m²/人 として 1000人 |
| 生命維持装置の処理能力 | 酸素 840 kg/日 | 0.84 kg/人日 として 1000人 |
| 居住区画の容積 | 100,000 m³ | 100 m³/人 として 1000人 |
| 放熱板の面積 | 21,800 m² | 21.8 m²/人 として 1000人 |

均衡点にいる集団であるから、設備を増やさない限り人口は動かない。設備の性能値を書き換えれば、支えられる人数もそのまま変わる。

人員は個体としては追跡しない。基地ごとに、役割ごとの人数と、その集団としての健康状態を持つ。

```ts
export type CrewRole = 'engineer' | 'pilot' | 'medic' | 'essential';

export interface CrewPopulation {
  readonly counts: Readonly<Record<CrewRole, number>>;  // 役割ごとの人数
  readonly health: CrewHealth;
  readonly training: readonly TrainingBatch[];          // 訓練中の人員
  readonly immature: number;                            // 出生済み・未成人の人数
}

export interface CrewHealth {
  readonly boneDensity: number;   // 0..1、1が健常
  readonly muscleMass: number;    // 0..1
  readonly radiationDose: number; // 累積被曝線量 [Sv]
  readonly incapacitated: Readonly<Record<CrewRole, number>>; // 役割を果たせない人数
}

export interface TrainingBatch {
  readonly from: CrewRole;
  readonly to: CrewRole;
  readonly count: number;
  readonly completesAt: number;  // 絶対 simTime
}
```

`incapacitated` は `counts` の内数である。ある役割で実際に働けるのは `counts[role] - incapacitated[role]` 人である。

### 4-2. 役割

人員は次の4つの役割を持ち、役割ごとに数える。

| 役割 | 担うもの |
|---|---|
| 整備士 | 機体と設備の修理・整備。部品の摩耗の回復、触媒床の交換、送電線の補修 |
| 飛行士 | 機体の操縦。同時に飛ばせる機体の数と、無人機の管制の上限を決める |
| 医師 | 健康の維持と回復。被曝と低重力の影響の緩和 |
| その他のエッセンシャルワーカー | 農場・生産設備・生命維持装置の運用。人数に比例して設備の稼働率が決まる |

**整備士が不足すると修理速度が落ちる。**部品の摩耗の回復速度と触媒床の交換速度は、整備士の人数に比例する。必要人数に対する充足率が1を下回ると、その比率がそのまま修理速度の倍率になる。整備士が0人の基地では、修理も整備も一切進まない。摩耗した部品はそのまま性能を落とし続け、劣化した触媒床は交換されないまま推力を失う。

**飛行士が不足すると同時に操作できる機体が限られる。**飛行士1人につき有人機1機を操縦でき、それとは別に無人機を規定数まで管制できる。無人機の管制には、その機体が通信モジュールを積み、通信圏内にいることが同時に要る。飛行士の人数を超える機体を同時に飛ばそうとした場合、超過分は操作対象として選べない。軌道上に置いたまま放置することはできるが、姿勢制御も推進も行われず、軌道は自然に変化する。

**通信圏が狭いあいだ、飛行士の人数がそのまま戦力の上限になる。**ただしこれが効くのは、船団を出して戦域を広げようとする段階からである。開始時点の戦域は基地の周りに限られ、そこでは基地自身が迎え撃つため飛行士を要さない（第3巻の戦域の進行）。圏外の無人機は計画を実行できないため、補給や弾薬をあらかじめ目標の軌道へ置いておけない。必要なものをすべて積んだ有人の船団を編成して出撃するほかなく、船団の規模は飛行士の数で決まる（§6-1）。同じ制約は防衛にも効く。NRHO基地が襲われたとき、そこへ向けられる機数もまた飛行士の数で頭打ちになる。

**医師が不足すると健康が落ちる。**医師1人が受け持てる人員数に上限があり、これを超える人口を抱えた基地では、健康の回復が受け持ち率に比例して遅くなる。医師が0人の基地では、負傷者も被曝者も回復せず、低重力による劣化も緩和されない。

**エッセンシャルワーカーが不足すると設備が定格で回らない。**基地に積んだ全設備の `crewRequired` の合計に対する充足率が、その基地の全設備の稼働率の倍率になる。充足率0.5であれば、農場も生産設備も生命維持装置も一律に半分の速度でしか動かない。生命維持装置が定格を割ると、そのぶん人口上限が下がる（§4-3）。

充足率は純関数として求める。

```ts
export function roleSufficiency(
  pop: CrewPopulation,
  demand: CrewDemand,       // 基地の設備・機体から導いた必要人数
): Readonly<Record<CrewRole, number>>;  // 0..1 にクランプした充足率
```

### 4-3. 人口を制約するもの

人口の上限は、次の5つのうち**最も厳しいもの**で決まる。

| 制約 | 由来 |
|---|---|
| 生命維持装置の処理能力 | 酸素の供給量、二酸化炭素の除去量、水の再生量。それぞれ1人あたりの必要量で割り、最も小さい値を採る |
| 農場の食料生産 | 食料の生産速度を1人あたりの必要量で割る。備蓄がある間はそれも算入する |
| 居住区画の容積 | 居住区画の内容積を1人あたりの必要容積で割る |
| 医療の能力 | 医師の人数と医療設備の規模から求める受け持ち可能な人数 |
| **放熱** | 放熱板の実効放熱量を、1人あたりの発熱量で割る |

```ts
export type PopulationLimit =
  | 'life_support' | 'food' | 'volume' | 'medical' | 'heat_rejection';

export function populationCapacity(
  base: BaseState,
  crew: CrewPopulation,
): { readonly capacity: number; readonly limitedBy: PopulationLimit };
```

`limitedBy` を返すのは、どれが効いているかをプレイヤーに示すためである。上限が近いことだけを表示しても、何を増やせばよいかが分からない。

**軌道上では放熱が最も厳しい制約になる。**電照農場の消費電力（1人あたり 12〜20 kW）と生命維持装置の消費電力（1人あたり 1.5〜2 kW）は、**そのすべてが最終的に熱になる**。電力を消費して仕事をした結果は、機体の外へ質量として出ていくもの（推進剤）を除けば、すべて熱として残る。したがって1人あたり 14〜22 kW を捨て続けなければならない。

軌道上での放熱板の実効性能は 50〜150 W/m² である。理論上の黒体放射は 300 K の両面で 900 W/m² を超えるが、実際には作動流体の温度が 275〜300 K にとどまり、太陽光と地球赤外の入熱があり、パネル同士が互いを見込むため、実効値はこの1桁下になる。したがって、

| 条件 | 1人あたりの発熱 | 実効放熱 | 要る放熱面 |
|---|---|---|---|
| 良好（電照12 kW、日陰、高性能パネル） | 13.75 kW | 140 W/m² | 98 m² |
| 標準 | 16 kW | 120 W/m² | 133 m² |
| 劣悪（電照20 kW、日照下、低性能パネル） | 22 kW | 50 W/m² | 440 m² |

**軌道上では1人あたりおよそ 100〜150 m² の放熱面が要る。**これは栽培面積（1人 40〜50 m²）の 2〜3 倍である。**軌道基地では、居住のための構造物のうち最も大きい面積を占めるのは農場でも居住区画でもなく放熱板になる。**

**この制約は軌道と月面で非対称である。**

| 立地 | 放熱の条件 | 帰結 |
|---|---|---|
| 軌道基地 | 太陽と地球からの入熱があり、宇宙背景（約 2.7 K）へ向く面も他のパネルや構造に遮られる。実効 50〜120 W/m² | 放熱板の面積が人口の上限を直接決める。パネルは構造の大半を占め、被弾に弱い |
| 月面（永久影） | 約 40 K の巨大な熱溜めに向かって放射でき、入熱がほぼない。実効 918 W/m²（300 K、両面放射） | 1人あたり 22 m²。栽培面積を下回るため5つのうち最も緩い制約になるが、制約であることは変わらない |

**この非対称が、大規模な居住を月面に置く理由になる。**軌道基地は放熱面のために際限なく大きくなり、月面基地は同じ廃熱を6分の1から18分の1の面積で捨てられる。プレイヤーが人口を増やそうとしたとき、軌道ではなく永久影の底を選ぶのは、この計算の結果である。

**月面でも放熱板の面積は基地の規模を決める。**1000人ぶんの 21,800 m² は一辺 148 メートルの正方形に相当する。地表に平らに敷けるため構造は容易だが、面積そのものは小さくない。人口を増やせば、そのぶん敷く面積が要る。

**いずれかが不足すると人口が減る。**現在の人口が上限を上回っている間、超過量に比例した速度で人口が減る。減り方は制約の種類によって異なる。

- 酸素と食料の不足は、速く減る。数日で結果が出る。
- 放熱の不足は、中程度の速さで減る。区画の温度が上がり、まず設備が保護停止し、次に人が耐えられなくなる。
- 居住容積の不足は、遅く減る。健康の低下を経由して減る。
- 医療の不足は、直接には減らさない。負傷者と被曝者が回復しないことを通じて、間接的に減る。

減るときは全役割から比例して減らす。特定の役割だけが先に失われることはない。

### 4-4. 健康

健康は基地ごとの集団の状態として持ち、3つの軸で扱う。

**低重力による劣化** — 骨密度と筋力が落ちる。実効重力が小さいほど速く落ちる。

- **月面重力（0.165 g）相当を得られていれば劣化は止まる。**無重力では劣化し、月面重力以上では止まる。その間は実効重力が大きいほど劣化が遅い。医学的な根拠があるわけではないが、どこに区画を置けば人が損なわれないかが一目で決まるため、遊びとしては明快な線引きになる。
- したがって月面基地に住む人員は、そもそも劣化しない。軌道上に長期滞在する人員は、重力区画がなければ劣化する。序盤のトラス式（回転半径が短く、得られるのは月面重力程度）でも劣化は止められる。
- **テザー式で地球重力を得ることは、劣化を止めるためではなく、より快適で、より長い滞在に耐えるための改善である。**
- テザー式の重力区画（§5）に滞在すれば、回転半径と角速度から得られる実効重力が適用される。滞在時間の割合で加重平均した実効重力が、その集団の劣化速度を決める。
- 劣化した骨密度と筋力は、月面重力以上の環境で時間をかければ回復する。医師がいれば回復が速い。

**放射線の被曝** — 累積する。累積線量は減らない。

- 水タンクによる遮蔽で被曝率が下がる。遮蔽の効きは水の厚さに対して指数的である。
- 地球磁場の内側（低軌道）にいる間は被曝率が大きく下がる。月周辺と惑星間ではこの保護がないため、遮蔽の有無が直に効く。
- 月面の永久影では、月体とクレーター壁が視界の大半を塞ぐため被曝率が低い。
- 太陽フレアの発生時は被曝率が跳ね上がる。遮蔽の厚い区画に人員を退避させることで凌ぐ。
- 累積線量が閾値を超えた人員から順に、役割を果たせなくなる（`incapacitated` に入る）。

**健康が落ちた人員は役割を果たせなくなる。**骨密度・筋力が閾値を下回った人員、累積被曝が閾値を超えた人員、着陸の衝撃や事故で負傷した人員は `incapacitated` に数え、その役割の実働人数から外れる。医師がいれば回復し、実働に戻る。回復速度は医師の充足率に比例する。累積被曝だけは回復しないため、被曝で外れた人員は恒久的に実働から外れる。

```ts
export function stepCrewHealth(
  health: CrewHealth,
  env: CrewEnvironment,   // 実効重力、遮蔽厚、磁気圏の内外、フレアの有無
  medicSufficiency: number,
  dt: number,
): CrewHealth;
```

純関数とし、環境と医師の充足率と経過時間から新しい健康状態を返す。

### 4-5. 人口の増減

**人口の増加率は、余裕の最も小さいものに従う。**§4-3 の5つの制約それぞれについて、上限に対する現在人口の余裕を求め、その最小値が増加率を決める。余裕がなくなれば増加は止まり、上限を割り込めば減る。増加率は上限に近づくにつれて連続的に0へ落ちるものとし、上限で不連続に止まる形にはしない。

```ts
export function populationGrowthRate(
  pop: number,
  capacity: number,
  limitedBy: PopulationLimit,
  health: CrewHealth,
): number;  // 人/秒。負なら減少
```

**出生** — 人口が上限に対して余裕を持ち、健康が良好である基地で起きる。実効重力が一定値以上であることを要する。低重力下での妊娠と出産の安全性が確保されないためである。したがって、テザー式の重力区画（§5）を持たない軌道基地では出生が起きず、月面基地では月面重力で起きる。出生した人員は `immature` に入り、成人するまで役割を持たない。成人までの期間は長い。

**移入による増加はない。**人口は生態系の中で増えるものであり、どこかから来るものではない。輸送（§4-6）は人員を移すだけであり、総数を変えない。

**死亡** — 寿命、事故、被曝、生命維持の破綻によって起きる。寿命による死亡は一定の速度で常に起きる。人口が増えるのは、出生が寿命による死亡を上回る場合のみである。

**事故** — 機体の破壊、着陸の失敗、生命維持装置の停止、送電線の断線による凍結、被弾によって、その場にいた人員が失われる。事故は該当する機体・区画に乗っていた人員に対してのみ起きる。

**機体を失えば乗員は死ぬ。**脱出も救助も持たない。ただし人口のすべてが飛行士であるわけではなく、失った飛行士は訓練によって他の役割から補充できる。訓練には時間がかかり、その時間が損耗の代償になる。したがって機体の喪失が直ちに戦力の恒久的な減少になることはないが、人口そのものが減ることの重みは残る。

**訓練による役割の転換** — ある役割の人員を、別の役割へ転換できる。転換には時間がかかり、`TrainingBatch` として保持する。

- 訓練中の人員は、元の役割としても新しい役割としても働けない。したがって訓練は一時的な人手不足を招く。
- 転換に要する時間は役割の対によって異なる。医師への転換が最も長く、エッセンシャルワーカーへの転換が最も短い。
- 訓練は医師と整備士の指導を要するため、それらの充足率が低い基地では訓練速度が落ちる。
- 成人した `immature` は、訓練を経ていずれかの役割に配分される。

### 4-6. 輸送

人員は貨物と同じく機体で運ぶ。

**コックピットと居住区画の搭乗人数が1回に運べる人数の上限である。**小型の艦艇のコックピットは1〜3人であり、これでは人員の移送はほとんど進まない。人員を多く運ぶには、居住区画を持つ大型の機体が要る。

- 搭乗人数を超える人員を乗せることはできない。
- 飛行中の機体に乗っている人員も、生命維持装置と食料を消費する。長期の航行では、乗員数に応じた消耗品の搭載が要る。同時に発熱も生じるため、放熱板を積まない機体では長期の有人航行ができない。
- 飛行中は重力が得られないため、低重力による劣化が進む。長期の輸送任務では、月面重力相当を作れる重力区画（§5）を持つ機体でなければ乗員の健康が落ちる。トラス式で足りるが、それすら持たない機体では航行時間がそのまま劣化になる。
- 飛行中の被曝は、機体の遮蔽と現在位置の磁気圏内外によって決まる。月への往復は磁気圏の外を通るため、遮蔽の薄い機体では往復1回ごとに無視できない線量を受ける。

人員の積み下ろしは、ドッキングポートで結ばれているとき（`crewPassable` が必要）、または着陸接続が成立しているときに行える。

### 4-7. 基地を失ったとき

**軌道基地が破壊されてもゲームは終わらない。**月面基地が残っている限り、そこから立て直せる。

- 軌道基地を失うと、その基地が担っていた通信圏が消え、生産設備・在庫・格納中の機体・そこにいた人員が失われる。重い後退である。
- しかし人口の大半は月面にあり、生産の基盤も、資源の産地も月面にある。**軌道基地は前線の拠点であって、文明の本体ではない。**
- 月面基地は月の重力井戸の底にあり、到達に大きな Δv を要するため相対的に安全である。この非対称が、立て直しの土台が失われないことを保証する。

### 4-9. UI — 基地ビューの人員タブ

基地ビューに人員タブを加える。表示するのは以下である。

- **人口** — 総数、現在の上限、上限を決めている制約（`limitedBy`）、現在の増加率。上限に対する余裕をメーターで示す。増加率は「1年あたり何人」の形で示す。
- **5つの制約の内訳** — 生命維持・食料・容積・医療・放熱それぞれが支えられる人数を並べ、最小のものを強調する。何を増やせば人口が増えるかが一目で分かる形にする。
- **役割ごとの内訳** — 4つの役割それぞれについて、総数・実働数・必要数・充足率。充足率が1を下回る役割は警告色で示す。
- **健康** — 骨密度、筋力、累積被曝線量。それぞれの現在値と、いまの環境での増減の向き。
- **不足の影響** — 充足率が1を下回っている役割について、それが何を引き起こしているかを文で示す（修理速度が何倍に落ちているか、何機まで同時に飛ばせるか、設備が何割で回っているか）。
- **訓練** — 進行中の訓練の一覧と、新しい訓練の開始。転換元・転換先・人数を指定する。
- **輸送** — 着陸接続またはドッキングが成立している機体との間で、人員を積み下ろす。機体の搭乗可能人数を上限として示す。

役割の充足率と人口は毎フレーム変わりうるため、行の値は毎フレーム書き換える。行そのものの構成（役割は4つ、制約は5つで固定）は変わらないため、要素を作り直さず値だけを書き換える。

## 5. テザー式の重力区画

### 5-1. 実現する内容

居住区画とカウンターウェイトを長い構造で結び、その全体を共通重心のまわりに回す。遠心力で疑似重力を作る。

```
    [居住区画] ────────── ● ────────── [カウンターウェイト]
                     共通重心
                     （ここに回転しない中央部）
```

**シリンダー型の宇宙コロニーは作らない。**巨大な剛体の円筒は、必要な構造質量が回転半径の増加に対して急速に増え、現実的な規模で作れない。張力のみを受ける構造で結べば、同じ回転半径をはるかに軽い質量で得られる。

結ぶ構造は2世代ある。

| 世代 | 結び方 | 回転半径 | 制約 |
|---|---|---|---|
| 序盤 | トラス構造 | 数十メートル | 剛体であり、曲げと座屈に耐える必要がある。長くするほど質量が急増する |
| 中盤以降 | テザー（索） | 数百メートル | 張力のみを受ける。質量は長さに比例するにとどまる。展開と制御が難しい |

### 5-2. なぜテザーなのか

**回転半径をテザーの長さで稼げるため、低い回転速度で高い加速度が得られる。**

回転による加速度は `a = ω²·r` である。角速度 ω には上限がある。回転する部屋の中を人が動くとコリオリ力を受け、内耳の平衡感覚と視覚が食い違って回転酔いを生む。この不快感は角速度が上がるほど強くなり、**毎分2回転ならほぼ問題なく、毎分4回転が実用上の限界である。**

したがって、目標の加速度を得るには回転半径のほうを伸ばすほかない。

| 目標加速度 | 毎分2回転に要する半径 | 毎分4回転に要する半径 |
|---|---|---|
| 地球重力 1 g (9.81 m/s²) | 224 m | 56 m |
| 火星重力 0.38 g (3.71 m/s²) | 85 m | 21 m |
| 月面重力 0.165 g (1.62 m/s²) | 37 m | 9.2 m |

**剛体の区画では地球重力を作れない。**毎分4回転でも半径56メートルを要し、これは断面の外接円半径の上限を大きく超える。剛体の回転区画で得られるのは月面重力相当までである。

**テザーなら 224 m は現実的である。**必要な張力は `T = m·ω²·r` であり、毎分2回転・半径224メートルで100トンの居住区画を支える場合、

```
T = 100,000 kg × (0.2094 rad/s)² × 224 m ≈ 981 kN
```

高強度繊維の比強度をおよそ 0.58 MN·m/kg（安全率4を見込んだ許容応力 0.9 GPa を密度 1,560 kg/m³ で割った値。`0.9 GPa ÷ 1,560 kg/m³ = 5.8 × 10⁵ N·m/kg`）とすると、

| 量 | 値 |
|---|---|
| 必要断面積 | 981 kN ÷ 0.9 GPa ≈ 10.9 cm² |
| テザー1本の質量 | 10.9 cm² × 224 m × 1,560 kg/m³ ≈ 381 kg |

**居住区画100トンに対してテザーは400キログラム弱である。**同じ回転半径をトラスで得ようとすれば、曲げと座屈に耐えるために質量は2桁大きくなる。これが世代交代の理由である。

**回転半径が大きいほど頭足間の重力勾配が小さくなる。**加速度は半径に比例するため、身長 1.7 m の人の頭と足では加速度が `1.7/r` の割合で異なる。

| 回転半径 | 頭足間の加速度差 | 体感 |
|---|---|---|
| 224 m | 0.76% | 感じられない |
| 56 m | 3.0% | わずかに感じる |
| 10 m | 17% | 立ち上がるだけで血流が変わる。居住に適さない |

**コリオリ力も半径が大きいほど軽い。**歩行速度 1 m/s で受けるコリオリ加速度は `2ω·v` であり、毎分2回転では 0.42 m/s²、地球重力の 4.3% にとどまる。毎分4回転では 8.5% になる。

### 5-3. 構成

```ts
export interface TetherHabitat {
  readonly id: string;
  readonly hub: Vessel;                  // 回転しない中央部
  readonly arms: readonly TetherArm[];   // 2本以上。対で釣り合わせる
  angularVelocity: number;               // 中央部から見た回転部の角速度 [rad/s]
}
export interface TetherArm {
  readonly kind: 'truss' | 'tether';
  readonly endMass: Vessel;   // 居住区画、またはカウンターウェイトに充てた機体
  length: number;             // 共通重心からの距離 [m]。テザーの場合は可変
  readonly maxTension: number; // 破断張力 [N]
}
```

- **反対側のカウンターウェイトには、質量のあるものを充てる。**貨物を積んだコンテナ、推進剤タンク、使用済みの段、もう1つの居住区画のいずれでもよい。専用の重りを作る必要はなく、すでに質量として存在するものを配置し直せばよい。
- 対になる腕の `endMass · length` の積が釣り合っていなければ、共通重心が中央部からずれ、中央部そのものが振れ回る。設計時の検証で拒否する。
- **回転しない中央部にドッキングスペースがある。**機体はそこに接舷する。回転部に直接ドッキングすることはできない。
- 中央部と回転部の間には回転継手が要る。継手を通して、電力・推進剤・人員・作動流体が流れる。

### 5-4. 回転の起動と停止

**系全体の角運動量は回転部が持ち、中央部は回らない。**居住区画とカウンターウェイトは共通重心のまわりを互いに反対側で回るため、両者の角運動量は同じ向きに足し合わさり、系全体としては大きな角運動量を持つ。これを与えることが起動であり、取り去ることが停止である。

与え方は3つあり、いずれも実装する。

| 方法 | 内容 | 代償 |
|---|---|---|
| 継手のモータ | 中央部を反力の受け手にして回す | 中央部が反対向きに回り始める。中央部の慣性は回転部よりはるかに小さいため、実用にはフライホイールとの併用が要る |
| フライホイール | 同じ角運動量を逆向きに蓄える | フライホイールの容量が回転部の角運動量以上でなければ回しきれない。容量は質量に直結する |
| 端部のスラスタ | 居住区画とカウンターウェイトの端に付けたスラスタで接線方向に押す | 推進剤を消費する。反力を系の外へ捨てるため、中央部も、フライホイールの容量も要らない |

`I = Σ m·r²` であり、100トン2つを半径224メートルで回す場合の慣性モーメントは約 1.0×10¹⁰ kg·m²、毎分2回転での角運動量は約 2.1×10⁹ kg·m²/s である。**これをフライホイールに蓄えることは現実的でない。**したがって起動と停止は端部のスラスタで行うのが主となり、微調整のみを継手のモータが担う。起動に要する運動エネルギーは `½·I·ω²` ≈ 2.2×10⁸ J であり、これは推進剤の消費として現れる。

**設計上の検証**として、`validateBlueprint` は次を拒否する。

- 対になる腕のモーメントが釣り合っていない構成。
- 目標角速度における張力が `maxTension` を超えるテザー。
- 起動手段（端部のスラスタ、または十分な容量のフライホイール）を持たない構成。

### 5-5. 運用

- **回転半径は運用中に変えられる。**テザーを巻き出せば半径が増え、角運動量が保存されるため角速度が下がる。加速度 `ω²·r` は `L²/(m²·r³)` に比例するため、**巻き出すと加速度は下がる**。逆に巻き取れば加速度が上がり、巻き取りの仕事が要る。
- 巻き取り機は電力を消費する。巻き出しでは逆に回生できる。
- **姿勢制御を行うと回転面が変わる。**系全体の角運動量ベクトルの向きを変えるには、その大きさに見合ったトルクを長時間かける必要がある。回転面を太陽に対してどう向けるかは、あらかじめ決めて回し始めるべき設計事項であり、飛行中に自由に変えられるものではない。
- **推進中は使えない。**主機を噴射すると、回転部には遠心力に加えて機軸方向の加速度が加わり、居住区画の床方向が周期的に変わる。長時間の噴射を行う機体では、噴射前に回転を止める。
- テザーの張力は微小振動を持つ。端部の質量が変われば（人員が移動する、貨物を降ろす）釣り合いが崩れ、振動が励起される。減衰機構を持たせる。

### 5-6. 姿勢の表現を拡張する必要がある

**テザー式の回転居住区は、1つの剛体として姿勢積分できない。**機体を1つの剛体として積分し、トラスを完全剛体として扱う前提は、この構成には収まらない。

- テザーは張力のみを受け、曲げに抵抗しない。系の姿勢は2つの質量の相対位置で決まり、単一の慣性テンソルでは表せない。
- 回転しない中央部と回転部の間には回転継手があり、**両者の角速度が異なる。1つの姿勢では表せない。**
- 機体が中央部に接舷すると、その質量が系の慣性モーメントを変え、角運動量保存により回転速度が変わる。

**したがって、テザー式に着手する時点で、機体の姿勢の表現を単一の剛体から拡張する必要がある。**これは姿勢積分の前提そのものに触れる変更であり、この巻の中で最も大きな作業になる。

**序盤のトラス式はこの問題を持たない。**トラスは剛体であるため、**機体を単一の剛体のまま扱える。**回転部と非回転部を分けることは依然として必要だが、テザーの柔軟性は扱わずに済む。世代交代は、質量の得と引き換えに姿勢の表現の拡張を要求するものである。

### 5-7. モジュール

```
    spinUpEnergy(inertia, omega) -> number
```

## 6. バッチ生産と補給ミッションの自動化

### 6-1. 前提 — 序盤は船団による攻勢である

ゲーム開始時点で通信基地は月面基地とNRHO基地の2つしかなく、地球低軌道の大部分は圏外である。**圏外の無人機は計画を実行できないため、補給や弾薬をあらかじめ目標の軌道へ投入しておく運用ができない。**置いたものを後から使いに行くことはできても、置きに行く工程そのものを無人には任せられない。

基地の周りの戦闘は基地自身の武装で行えるが、そこから先へ戦域を広げる（第3巻の戦域の進行）には出撃するほかない。したがって序盤の攻勢は、**必要なものをすべて積んだ有人の船団を編成して出撃し、戦って帰る**という形になる。船団の規模は飛行士の人数で決まり、**人員が直接戦力の上限になる**（§4-2）。

通信衛星を配備して圏を広げると、無人の補給機を先行させる運用に移行できる。**この節が書くバッチ生産と補給の自動化は、その転換の先にある。**

### 6-2. 解く問題

ゲーム中盤以降、低軌道や遷移軌道へ**大量の弾薬と補給を送る**運用が中心になる。1機ずつ設計し、生産し、打ち上げ、軌道に投入し、貨物を放出して帰還させる操作を手で繰り返すのは現実的でない。

一方で、**発注すると物資が届く仕組みにはしない**（§2）。物資は必ず実在の機体が実在の軌道を飛んで運ぶ。自動化するのは、プレイヤーがすでに手で1回やってみせた操作の繰り返しである。

### 6-3. バッチ生産

1つの設計を、指定した機数まとめて生産する。

```ts
export interface ProductionBatch {
  readonly blueprintId: string;
  readonly requested: number;      // 生産する機数。無限を表す値を許す
  completed: number;
  readonly destinationDockId: string;
}
```

- 資源と設備の稼働が続く限り、完成した順に指定のドックへ配備される。
- 資源が尽きれば止まり、補充されれば再開する。中断は失敗ではない。
- ドックの収容数を超える生産は、その時点で待機する。
- 進捗（完成機数、次の1機の完成予定時刻、律速している資源）を表示する。

### 6-4. 定型の軌道計画

あらかじめ作った軌道計画を保存し、生産された機体に順に割り当てる。

```ts
export interface MissionTemplate {
  readonly id: string;
  readonly name: string;
  readonly departure: { baseId: string };
  readonly plan: PlanData;              // 機動計画そのもの
  readonly payload: readonly PayloadAction[];  // どこで何を放出するか
  readonly terminal: 'return' | 'discard' | 'hold';
}
export type PayloadAction =
  | { kind: 'release_container'; atNodeIndex: number; containerSlotId: string }
  | { kind: 'dock_and_transfer'; targetVesselId: string; resourceId: string }
  | { kind: 'deploy'; atNodeIndex: number; blueprintId: string };
```

計画は絶対時刻ではなく、出発時点からの相対時刻と、軌道上の位置（近地点、昇交点、目標との会合点）で書く。同じ計画を、出発時刻の異なる複数の機体に適用できる必要があるためである。

`terminal` は任務の終わり方を決める。`return` は出発地へ帰投して再利用、`discard` は貨物を放出したまま投棄、`hold` は目標軌道に留まる（通信衛星や補給デポの配備がこれにあたる）。

### 6-5. ルーティン

「この設計をこの計画で、在庫がある限り繰り返し送り出す」という指示を1つ置けば、以後は自動で回る。

```ts
export interface SupplyRoutine {
  readonly id: string;
  readonly blueprintId: string;
  readonly templateId: string;
  readonly cargo: readonly { resourceId: string; mass: number }[];
  readonly maxConcurrent: number;   // 同時に飛ばす最大機数
  enabled: boolean;
}
```

- 出発地に機体と貨物と推進剤が揃い、飛行士（および無人機なら通信）の余裕があるとき、1機を出発させる。
- 同時に飛ぶ機数は `maxConcurrent` で頭打ちにする。飛行士と管制の上限も別途効く。
- プレイヤーが行うのは、資源の供給と、計画そのものの見直しだけである。
- **防衛のための即応もルーティンで扱う。**敵は低軌道に限らず現れ、NRHO基地も襲われうる（第3巻の軌道基地の軌道）。基地が攻撃を受けたときに迎撃機と弾薬を送り出す任務を、あらかじめルーティンとして置いておける。送り出すところまでが自動であり、戦闘そのものは手動である（§6-7）。序盤の基地は自前の武装で迎え撃つが、戦域が外へ広がるほど（第3巻の戦域の進行）基地から離れた場所での交戦が増え、この即応の価値が上がる。

### 6-6. 通信圏が前提になる

**ルーティンを回す機体は、そのほとんどが無人機である。**有人機を自動で飛ばすことはできるが、飛行士1人を1機に張り付けることになり、人員の制約（§4-2）に直ちに突き当たる。

無人機の自動操縦には、機体が通信モジュールを積んでいることと、通信圏内にいることの両方が要る。したがって、

- **圏外に出た機体は計画の実行を止める。**その場で慣性飛行を続け、圏内に戻れば再開する。予定の機動時刻を過ぎていれば、計画は破綻する。
- **ルーティンを回すには、通信衛星の配備が先に要る。**通信衛星それ自体を `terminal: 'hold'` の任務として配備できるが、その配備任務を自動化するには既存の通信圏が要る。**最初の数機は手で飛ばすほかない。**
- 通信圏の穴は運用の穴として直接現れる。月の裏側を通る計画は、そこに中継衛星がなければ自動では飛ばせない。

この依存が、通信衛星網の整備を「あったほうがよい設備」ではなく「自動化の前提条件」にする。

### 6-7. 自動化の粒度 — 論点

**どこまでを自動にし、どこからをプレイヤーの判断に残すか**は、この機能の設計上の最大の論点である。自動化しすぎればゲームが自分で進んでしまい、足りなければ作業が残る。

現時点の切り分けは次のとおりとする。

| 対象 | 扱い | 理由 |
|---|---|---|
| 生産の繰り返し | 自動 | 判断の余地がない。資源が足りるか足りないかだけである |
| 保存した計画の実行 | 自動 | プレイヤーがすでに1回設計した機動をなぞるだけである |
| 貨物の積み込み | 自動 | ルーティンが `cargo` で指定した通りに積む |
| 出発の可否判断 | 自動 | 機体・貨物・推進剤・飛行士・通信が揃っているかの機械的な判定である |
| **計画そのものの設計** | **手動** | どの軌道へどれだけ運ぶかは戦略そのものである |
| **機体の設計** | **手動** | 同上 |
| **通信衛星網の設計** | **手動** | どこに穴を残すかが運用の形を決める |
| **失敗への対処** | **手動** | 圏外離脱、推進剤不足、被撃墜はいずれも通知にとどめ、自動で補填しない |
| **戦闘** | **手動** | 自動で戦う仕組みは持たない |

**失敗を自動で埋めないことが重要である。**ルーティンが1機を失ったとき、自動で次を送り出すのは正しいが、失った原因を自動で回避することはしない。同じ経路で送り続けて損失が続くなら、計画を書き換えるのはプレイヤーの仕事である。

### 6-8. モジュール

```
src/game/logistics/production-batch.ts
src/game/logistics/mission-template.ts
src/game/logistics/supply-routine.ts     // 出発判定、機体への割り当て
src/game/logistics/routine-executor.ts   // 計画の自動実行、通信圏の判定
src/game/hud/logistics-panel.ts          // バッチ・計画・ルーティンの一覧と編集
```

計画の自動実行そのものは、既存の軌道計画の自動実行（`PlanExecutor`）を機体ごとに走らせる形で実現する。この機能が加えるのは、**どの機体にどの計画をいつ割り当てるか**の層である。

## 7. 敵の構成

### 7-1. 実現する内容

敵の機体を、**実在のタンパク質の構造ライブラリに基づいて構成する。**手で1体ずつ形を作るのではなく、実在の立体構造データから生成する。

- **アミノ酸に相当する部品**を20種類用意する。それぞれ固有の大きさ・質量・耐久・色を持つ。
- **金属錯体イオンに相当する部品**を用意する。鉄・銅・亜鉛・マグネシウム・マンガンなど。
- **糖鎖に相当する部品**を用意する。分岐した構造を取る。

敵の個体は、これらの部品が実際のタンパク質の立体構造に従って並んだものとして生成される。主鎖の折れ曲がりがそのまま機体の骨格になり、側鎖が突起になる。

**敵は地球低軌道に限らず出現する。**NRHO を含む月周辺でも、月と地球を結ぶ遷移軌道でも遭遇しうる。したがって軌道基地そのものが襲われうる（第3巻の軌道基地の軌道）一方、月の重力井戸の底にある月面基地は相対的に安全である。

### 7-2. なぜこの設計にするのか

**多様な形状が自動的に得られる。**構造データベースには十万を超える構造がある。1つの構造から1種類の敵が生成されるなら、手で作る限界をはるかに超える種類が、追加の作業なしに得られる。

**形状に意味が生まれる。**タンパク質の立体構造は、機能を果たすために特定の形をしている。この必然性がそのまま敵の性質になる。

| 構造上の特徴 | 敵における意味 |
|---|---|
| αらせん | 規則正しい螺旋の骨格。細長く、折れやすい方向がある |
| βシート | 平面的に並んだ板状の構造。面に対して強く、垂直方向に弱い |
| 金属中心を持つ活性部位 | 内部の1点に希少金属が集中する。**そこを撃ち抜けば全体が機能を失う**。急所として直接使える |
| ジスルフィド結合 | 離れた部位を留める結合。切れば構造が緩む |
| 糖鎖 | 外側に張り出した装甲。撃ち落とせるが、本体には影響しない |
| 疎水性コア | 内部に埋まった密な領域。装甲が厚い |

**急所を手で置く必要がない。**構造データの中で金属イオンが結合している座標は、そのまま急所の座標である。どこを撃つべきかという情報が、データの側にすでに入っている。

**ドロップする資源が構造から決まる。**含まれるアミノ酸の組成がそのまま炭素・窒素の量になり、結合している金属イオンがそのまま希少金属のドロップになる（第3巻の資源の一覧）。**炭素と窒素が敵からしか得られないという資源設計と、敵がタンパク質でできているという設定が、一貫する。**

### 7-3. 生成の手順

1. 構造データ（原子座標、残基の並び、結合、金属イオンの位置）を読み込む。
2. 主鎖の折れ曲がりから、機体のツリー（ノードとエッジ）を構成する。残基1つがノード1つに、ペプチド結合がエッジ1本に対応する。**閉路を持つツリーが要るのは、ジスルフィド結合と金属配位が主鎖の離れた位置を結ぶためである。**
3. 側鎖・金属中心・糖鎖を、対応するノードに搭載要素として配置する。
4. 実寸へ写像する。実際のタンパク質は数ナノメートルであり、そのままでは敵にならない。分子の慣性主軸に沿った寸法を測り、目標とする機体の全長に合わせて一様に拡大する。
5. 部品数が多すぎる場合は、二次構造の単位（1本のαらせん、1枚のβシート）にまとめて簡約する。

### 7-4. 実装の難所

- **構造データの入手と量。**構造データベースの形式（PDB / mmCIF）を読む必要がある。全体をゲームに同梱することはできないため、あらかじめ選んだ数十から数百の構造を、この計画専用の軽量な形式に変換して同梱する。変換はビルド前のツールで行う。
- **実寸への写像。**タンパク質は数ナノメートル、敵は数十から数百メートルである。10桁の拡大になる。密度をそのまま拡大すれば質量が非現実的になるため、質量は形状から独立に与える必要がある。**「実在の構造を使う」のは形状と接続関係についてのみであり、質量・強度・速度は独立に設計する。**
- **部品数と描画の負荷。**中規模のタンパク質でも残基は数百ある。1残基を1ノード・1部品として描けば、敵1体で数百のメッシュになる。二次構造への簡約、インスタンス描画、距離に応じた簡約が必須である。
- **当たり判定。**数百の部品それぞれに接触形状を持たせると、敵1体あたりの判定コストが既存の敵の2桁上になる。二次構造の単位で粗い包絡形状を持ち、急所（金属中心）のみを個別に判定する二段構えにする。
- **既存の敵との置き換え。**既存の敵は手で組んだ形状を持ち、`EnemyKind` ごとに慣性テンソルと挙動が決まっている。生成された敵は形状ごとに慣性テンソルが異なるため、AI の挙動（旋回性能、射線の取り方）が個体ごとに変わる。**同じ設定で戦って同じように振る舞うことが保証されなくなる**ため、戦闘の調整を作り直すことになる。
- **見た目の一貫性。**構造データをそのまま可視化すると、ゲームの他の部分（低ポリゴンの艦艇）と絵の調子が合わない。部品の描き方を、既存の機体と並べて成立する形に設計する必要がある。

### 7-5. モジュール

```

src/assets/structures/*.json        // 変換済みの構造データ
```

## 8. 実装費用が大きい理由

要件が固まった後、実装に着手する際に最初に解くべき課題を記す。

### 8-1. 人員

- **人員は単独では成立しない。**所属する基地（月面基地）、運ぶ手段（着陸と輸送機）、消費する食料と酸素（資源経済）、住む区画（基地の区画）のすべてが揃って初めて動く。この文書の中で最も依存の多い機能である。
- **時間経過のすべてに絡む。**健康の減衰、被曝の累積、訓練の進行、人口の増減はいずれも時間で進む量であり、時間加速の全段階で正しく振る舞う必要がある。加速倍率によって結果が変わってはならない一方で、毎フレーム全基地の全人員を計算するのは無駄である。どの量を毎フレーム進め、どの量を区間でまとめて解くかの切り分けが要る。
- **人口が増えることが、すべての制約を動的にする。**人口が固定なら、必要な酸素も食料も放熱面も定数である。増えるようにした瞬間に、5つの制約すべてが人口の関数になり、人口がその5つの関数になる。この自己参照を1フレーム内で安定に解く必要がある。
- **役割の充足率が既存の系統に横断的に効く。**整備士は部品の摩耗と触媒床に、飛行士は操作可能な機体の数に、エッセンシャルワーカーは生産設備と生命維持装置に効く。いずれも既存の計算に倍率を1つ掛ける形で入るが、その倍率の出所が人員という新しい系統になるため、依存の向きを整理しないと循環する（設備が回らないと食料が作れず、食料がないと人員が減り、人員が減ると設備が回らない）。この循環そのものは遊びとして意図したものであるが、計算の順序としては1フレーム内で解決する必要がある。
- **不足の影響をプレイヤーに伝えるのが難しい。**人口の上限が5つの制約の最小値で決まり、4つの役割それぞれに別の不足の影響があり、健康が3つの軸を持つ。どれが効いているかを示さないまま数値だけを並べても、何を増やせばよいかが分からない。`limitedBy` を返す設計と、5つの制約を並べて最小を強調する表示は、そのための最低限である。
- **輸送の上限が搭乗人数で決まることが、機体設計に新しい制約を持ち込む。**数百人を動かすには、既存の艦艇の何倍もの規模の輸送機が要る。その規模の機体が設計エディタで組め、生産でき、月面に着陸できることが前提になる。

### 8-2. テザー式の重力区画

- **1つの機体が回転する部分と回転しない部分を持つ。**既存の `Vessel` は全体で1つの姿勢を持つ前提であり、内部に別の回転系を持たない。質量特性・接触形状・描画・ドッキングのすべてが、この分割を前提としていない。
- **回転部の運動を正しく積分するのが難しい。**共通重心のまわりの回転と、系全体の軌道運動と、テザーの張力による微小振動が同時に存在する。剛体として扱えば振動が消え、質点系として扱えば計算量が増える。どこまでを剛体近似で済ませるかの判断が要る。
- **テザーの展開と巻き取りは、長さが変わる拘束である。**固定長の拘束に比べて格段に難しく、角運動量保存を数値的に保つのが容易でない。
- **中央部へのドッキングは、相手が回っていない点では通常のドッキングと同じだが、すぐ横で数百トンが回っている。**接近経路と、捕獲後の質量特性の変化（回転部の慣性に対する摂動）を扱う必要がある。
- **単一の剛体として姿勢積分できない。**テザーは曲げに抵抗せず、中央部と回転部は角速度が異なる。機体の姿勢の表現を単一の剛体から拡張することが着手の前提になり、これがこの巻で最も大きな作業になる（§5-6）。
- 回転半径・角速度・加速度・張力・頭足勾配という5つの量が互いに拘束し合うため、プレイヤーが操作するUIの設計そのものが難しい。

### 8-3. バッチ生産と補給ミッションの自動化

- **軌道計画を「使い回せる形」で保存することが難しい。**既存の計画は絶対時刻の機動ノードの列である。これを出発時刻の異なる機体に適用するには、相対時刻と軌道上の位置で書き直す必要があり、計画のデータ構造そのものを拡張することになる。
- **多数の機体が同時に自動で飛ぶ。**予測軌道の計算量が機数に比例して増える。自動で飛ぶ機体の予測をどこまで維持するか（画面外の機体の軌道を毎フレーム予測し続ける必要はあるか）の切り分けが要る。
- **通信圏の判定が全機体・全フレームに入る。**見通し線の判定は天体による遮蔽を含み、地形を持つ天体では地平線も含む。安価に済ませる方法を用意しなければ、機数に対して費用が線形に増える。
- **失敗の通知が難しい。**自動で飛ぶ機体が20機あるとき、そのうち1機が推進剤不足で計画を外れたことを、プレイヤーに気づかせなければならない。すべてを通知すれば埋もれ、しなければ気づかれない。

### 8-4. 敵の構成

- **外部データへの依存が新たに生じる。**構造データベースの取得、ライセンスの確認、専用形式への変換ツール、同梱するデータの選定という、既存のアセットとは性質の異なる作業が必要である。
- **部品数が既存の敵の2桁上になる。**描画も当たり判定も、既存の仕組みのままでは成立しない。簡約と粗い包絡形状の生成が前提であり、それ自体が独立した実装対象である。
- **敵の挙動が個体ごとに変わる。**慣性テンソルが構造から決まるため、既存の `EnemyKind` ごとの調整が使えなくなる。戦闘の難易度と手応えを作り直すことになり、実装費用の大半はここに出る。
- **絵の調子を合わせるのが難しい。**構造データをそのまま出せば、既存の低ポリゴンの艦艇と並ばない。表現の設計が要る。

## 9. 依存の順序

```
（土台：機体・設計・生産・資源採掘・月面基地・通信）
        │
        ├──► 人員 ──► テザー式の重力区画
        │
        └──► バッチ生産と補給の自動化

敵の構成（独立）
```

- **人員は、所属する基地・輸送する手段・消費する食料と酸素がすべて揃って初めて成立する。**この文書の中で最も依存の多い機能である。
- **テザー式の重力区画は人員に依存する。**回転による疑似重力の目的は健康の維持であり、人員がなければ効果を測る対象がない。加えて、姿勢の表現を単一の剛体から拡張することを要求する（§5-6）。
- **自動化は、運ぶものと運ぶ先と通信圏に依存する。**手で運べる経路が成立していることが前提であり、この機能が加えるのはその繰り返しを機械に任せる層だけである。
- **敵の構成は単独で着手できる。**この文書の他のどの機能にも依存しない。既存の敵を置き換えるだけであり、地形も人員も要らない。**独立に着手できる唯一の大型機能である。**

**着手の順序としては、人員 → テザー式の重力区画 となる。自動化は人員より前でも後でもよく、敵の構成はこの列のどこに差し込んでもよい。**
