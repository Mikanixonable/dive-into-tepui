# 設計・建造・資源 — 実装計画

## 1. 対象と第1巻・第3巻との関係

この計画は3巻からなる。3巻は実装の順に並ぶ。

**第1巻『基盤』**は、機体という物がどう成り立っているかを定める。`Vessel` への統合、搭載要素の型と性能値、断面とツリーの幾何、形状からの質量特性の導出、カプセルによる接触形状、姿勢依存の空力、外皮メッシュの生成、内容積の割り当ての規則、推進系の4系統と姿勢トルクの配分、推進剤の物性表とエンジンの型式が、そこに属する。第2巻と第3巻は、この巻の上に並列に載る。

**第2巻（この文書）**は、プレイヤーがそれをどう作り、運用し、広げるかを定める。対象は次の10である。

1. 設計データの保存と検証（§4）
2. 生産と生産可能性（§5）
3. ドック空間での設計と組み立て（§6）
4. 分離機構と多段（§7）
5. ドッキングポートによる機体の結合（§8）
6. ペイロード（§9）
7. 配管と推進剤の流路、タンクの与圧、弾薬の供給（§10〜§12）
8. 通信と自動操縦（§13）
9. 基地モジュール（§14）
10. 資源と産地、到達可能性、設備の連鎖、月面の電力と放熱（§15〜§18）、推進の世代と進行経路（§19、§20）

**第3巻『延期目標』**は、月面着陸と地形、月面基地の建設、人員、テザー式の重力区画、バッチ生産の自動化、敵の構成を定める。この巻が扱う運用のうち、月面と人員に踏み込むものはそちらに属する。

第1巻が機体の物理を与え、この巻がその上に、設計・建造・経済の層を載せる。以下、§2 前提を除き、記述はすべてこの文書の中で完結する。

## 2. 前提

第1巻で実装済みとして扱うもののうち、この巻が使うものを挙げる。

**`Vessel`** — 艦艇と軌道基地を統合した単一のエンティティクラス。ツリーと搭載要素を保持し、質量特性・推進剤・電力・熱・推進系・姿勢制御を持つ。ツリーを持たない機体（敵艦、コンテナ）のために、質量特性を直接与える経路も持つ。

**ツリー** — 船体の形状は、ノードとエッジからなるグラフ（ツリー）と、各ノードが持つ断面で定義される。外皮は、エッジの両端にある2つの断面をつないだ立体（ロフト）として生成される。**ツリーは閉路を含んでよい。**エッジは3つの種別のいずれかを持つ。

```ts
export type EdgeKind =
  | { kind: 'hull' }                                   // 外皮を作る。内側が内容積になる
  | { kind: 'truss'; radius: number }                  // 外皮を作らない構造部材
  | { kind: 'decoupler'; separationImpulse: number };  // 外皮を作らず、切り離せる

export interface TreeEdge {
  readonly id: string;
  readonly a: string;
  readonly b: string;
  readonly length: number;         // 0.5 m 単位、最小 0.5 m
  readonly kind: EdgeKind;
}

export interface VesselTree {
  readonly nodes: readonly TreeNode[];
  readonly edges: readonly TreeEdge[];
}
```

**断面と寸法の刻み** — 断面は基本断面（円・楕円・多角形・切り欠き多角形）の貼り合わせで構成される。各ノードは断面の表裏に向かう2つの軸方向の接続口と、断面形状ごとに決まる側面の接続口を持つ。**機体の直径は 0.5 m 単位であり、断面の外接円半径は 0.25 m 単位である。**刻みを寸法で場合分けする規則は持たず、直径 1 m・2 m・3 m の円筒がそのまま作れる。エッジの長さは 0.5 m 単位、最小 0.5 m である。結合はすべて平面同士の突き合わせであり、断面の面積・断面二次モーメント、ロフトの体積・表面積・重心・慣性テンソルはすべて解析式で求まる。

**搭載要素** — 搭載要素は、**外装要素**（エンジン・RCSスラスタ・武器・太陽電池パドル・放熱板・ドッキングポート・コンテナ接合部・戦闘用シールド・熱シールド・通信モジュール・ロボットアーム）と、`hull` エッジの内容積に収める**内装要素**（各種タンク・弾薬・バッテリー・燃料電池・原子力電池・コックピット・自動操縦装置・弾薬庫・配管・ペイロード倉庫・フライホイール・磁気トルカ・基地モジュール）に分かれる。

外装要素の取り付け先は2種類ある。**ノードの接続口**と、**トラスの軸に沿った任意の位置**である。大型の太陽電池パドル、大型の放熱板、ロボットアームはトラスに取り付ける。断面の接続口の数と大きさに縛られないため、機体の外形からはみ出す大きな板を、必要な枚数だけ好きな間隔で並べられる。

**RCSスラスタはプレイヤーが位置を指定できる。**ノードの接続口に加え、`hull` エッジの外表面（軸方向の位置と周方向の角度で指定する）およびトラス上の位置に取り付けられる。取り付けた位置と向きから腕の長さ `r_k` と噴射方向 `exhaust_k` が決まり、そのスラスタが生むトルクは `τ_k = r_k × (−exhaust_k)` である。要求トルクを満たす推力の組み合わせは一般に劣決定であり、その配分は第1巻が解く。この巻はその結果を使うだけである。

エッジの種別は搭載要素ではなくツリーの性質である。1つのエッジに複数の内装要素を収めてよく、実効容積を掛けた体積の和がそのエッジのロフト体積を超えないこと。

**トラスは完全剛体として扱う。**曲げ剛性・振動・座屈は計算しない。長いトラスの先に重い放熱板を並べても撓まず、折れず、揺れない。トラスの長さと断面の大きさが効くのは**質量と慣性テンソルだけ**であり、長く伸ばせば慣性モーメントが増えて姿勢制御が鈍る、という形でのみ設計に跳ね返る。

**質量特性** — 質量・重心・慣性テンソル・投影面積は定数として持たず、ツリーと断面と搭載物から導出される。

**接触形状と空力** — 剛体接触と被弾の判定は、ツリーの各エッジに対応するカプセルの集合で行う。空力の投影面積は速度方向と機体姿勢から求まる。

**熱シールド** — 外装要素であり、指定した方向の前面を覆う。アブレータを消耗して加熱率と動圧の閾値を引き上げる。大気圏突入と、大気の上層を掠めての減速の両方で機体を守る。アブレータの残量が尽きれば閾値は既定値へ戻る。

**戦闘用シールド** — 外装要素であり、指定した方向からの被弾を受け止める。自身が損耗し、覆っている方向の背後にある部位への被害を肩代わりする。

**エンジン** — エンジンは「サイクル（供給方式）」と「対応推進剤」の組で定義される。サイクルは加圧式・電気ポンプ式・ガス発生器サイクル・段階燃焼サイクル・エキスパンダーサイクル・固体モーター・ハイブリッドモーターの7種である。エンジンの比推力は `推進剤ペアの比推力 × サイクルの比推力係数` である。エンジンは推力・比推力・絞り範囲・再着火回数に加えて、次の4つを性能値として持つ。

| 性能値 | 内容 | この巻での用途 |
|---|---|---|
| 全長 | ノズル膨張比が大きいほど長い。機体の後端から突き出す長さとして目に見える | 段の外形と分離時の干渉 |
| 点火あたりの推進剤損失 | 始動シーケンスで捨てる分 | 分割したマニューバノードの2つ目に加算する |
| 連続燃焼時間の上限 | 冷却の限界。無制限のものもある | 燃焼の分割の判定 |
| 要求与圧 | タンク入口に要求する圧力。加圧式のみが高い値を要求し、ポンプ式はポンプ入口圧（NPSH）として低い値でよい。固体モーターは与圧も配管も要さない | §11 の与圧計算と推力低下 |

**燃焼計算** — `src/physics/tsiolkovsky.ts` に、質量変化を含む燃焼計算が純関数として置かれている（`dvFor` / `massAfterBurn` / `burnTimeFor` / `propellantForDv`）。推進剤流量は `推力 / (比推力 × 標準重力加速度)` である。

**加圧ガスの物性** — 与圧の計算に用いる。

| ガス | 密度（20 MPa, 常温） | 特性 |
|---|---|---|
| 窒素 | 230 kg/m³ | 常温貯蔵性推進剤に使える。重い。極低温推進剤には使えない |
| ヘリウム | 33 kg/m³ | 軽く、極低温でも凝縮しない。必要質量が窒素の約7分の1 |

**加圧ガスタンクの実効容積** — 内圧に対して最も効率のよい圧力容器は球であり、加圧ガスタンクは球状である。同じ耐圧なら球は円筒より薄い壁で済み、タンク自体の質量が小さい。一方、球は角柱状の内容積に詰めたときの充填率が悪い。この対立が、エッジの内容積に対する実効容積の係数 **0.55** として現れる。

**能力の判定** — `hasCockpit` / `hasAutopilot` / `hasBaseModule` / `hasEngine` / `hasCommunication` / `isOperable`。設計の検証と、ドック空間へ入れる条件の判定に用いる。

## 3. 設計判断

### 3-1. 設計と生産を分ける

プレイヤーは、資源を消費せずに設計を作り、名前を付けて保存し、読み込める。実機を得るには、保存した設計を指定して生産する。生産には時間がかかる仕組みを持つが、初期状態ではすべての設計の生産時間を0とする。

持っていない推進剤やエンジンを使った設計も、設計としては正当であり、保存できる。制約を受けるのは生産だけである。この扱いによって、設計は**目標を提示する装置**になる。核融合エンジンを積んだ機体を最初から設計でき、それを作るには何が要るのかが一覧として見える。

### 3-2. 設計と組み立てはドックの中で、戦闘ビューと同じ空間で行う

設計のための全画面のUIを持たない。設計と組み立ては、基地のドックモジュールの中で、**戦闘ビューと同じ3D空間**で行う。カメラはドックの内側に入り、プレイヤーは機体を実寸で見ながら組む。

ツリーのノードとエッジ、搭載要素は、その空間の中の実物として置かれる。1メートルの部品は1メートルに見え、隣に停めた既存の機体と直接比べられる。作っている物と、それが使われる場所が、同じ縮尺の同じ空間にある。

この決定は、別の場所で組み立てたモジュール同士を軌道上で結合する運用と、同じ操作の上に乗る。**結合はドッキングと同じUIで行う。**大型の機体を分けて作って軌道上でつなぐことが、ドックの中で部品をつなぐのと地続きの操作になる。

### 3-3. 段はプレイヤーが区切るのではなく、分離機構から決まる

段を明示的に定義する操作は存在しない。段は、ツリーから `decoupler` エッジを取り除いたときの連結成分である。プレイヤーが分離機構を挿すと、その両側が自動的に別の段になる。

### 3-4. 分離は自動では行わない

推進剤が尽きた段は分離の候補として提示するが、自動では分離しない。分離は運動量保存により軌道を変えるため、いつ切り離すかは軌道上の判断であり、実行はプレイヤーまたは軌道計画に委ねる。

### 3-5. 積荷の受け渡しは結合を必要としない

ペイロードの放出は、独立した物体を軌道上に生成する操作である。放出された弾薬は既存の補給パッケージと同じ実体であり、艦艇は既存の接近回収の仕組みでそれを取る。機体同士を結合する仕組みには依存しない。

### 3-6. 推進剤はタンクから配管を通ってエンジンへ流れる

配管は搭載要素の一つであり、ツリーのエッジに割り当てられる。タンクからエンジンまで配管が連続していないエンジンは点火できない。配管には口径ごとの流量上限があり、エンジンの要求流量を満たさない配管は推力を制限する。

タンクとエンジンの接続を暗黙に成立させる方式は採らない。配管が明示的な実体としてあることで、側面ブースターから中央段への推進剤の送り（クロスフィード）、分離による流路の切断、流量不足による推力制限といった、多段機の設計上の判断が、いずれも同じ一つの仕組みの帰結として現れる。

### 3-7. 配管の敷設は自動を既定とし、手動はその上書きとする

タンクからエンジンへ配管を通すことには、ほとんどの場合に唯一の正解しかない。選択の余地のない操作をエッジの数だけ繰り返させるのは作業であって遊びではない。

したがって**自動敷設を既定とする**。設計を変更するたびに自動敷設をやり直し、プレイヤーが手で触るのは、選択に意味がある次の場合だけになる。

- クロスフィードを組む
- 口径を絞って軽量化する
- 特定のタンクを特定のエンジンに割り当てる
- 分離機構を跨ぐ配管の可否を決める

手動で敷いた区間は自動敷設の上書きとして差分で保持し、やり直しの対象から外す。

### 3-8. 技術ツリーを持たない

研究点も、前提技術の木も、解禁の状態も実装しない。ある搭載要素を使った設計を生産できるかどうかは、その時点で持っている**資源・設備・電力**だけで決まる。

プレイヤーが使えるものは、**ある資源で作った設備が次の資源を生み、その資源が次の設備を可能にする**という連鎖によって広がる。この構造の要点は、**進行を止めるものが常に物理的な事実である**ことにある。メタンを作れないのは技術が未解禁だからではなく、炭素を持っていないからである。炭素を持っていないのは、月に炭素がないからである。炭素を得るには、炭素のある場所へ行くか、炭素を持つ敵を倒すしかない。

### 3-9. 通貨を持たない

**この作品に通貨は存在しない。**機体・搭載要素・区画・生産設備のすべては生産によってのみ得られ、生産が要求するのは**資源・設備・電力**の3つだけである。基地に市場はなく、資源を売買する手段もない。

作れないものは、金がないから作れないのではなく、材料か設備か電力が足りないから作れない。**遠くの資源を金で取り寄せる道がない**ため、進行を進めるには常に、その資源のある場所へ実際に到達するか、それを持つ敵を倒すしかない。到達可能性（§16）と資源の進行が一つのものであるという構造は、通貨がないことによって初めて例外なく成り立つ。

### 3-10. 生産設備そのものも生産の対象である

すべてのモジュールが生産で賄われる以上、**生産設備の建設にも資源と電力が要る。**設備は空から降ってこない。

したがって設備の一覧は、**資源の確保 → エネルギーの確保 → 生産設備の建設 → より多くの資源とエネルギーの確保**という循環が実際に回るように組む（§17）。この循環の最初の一巡だけは、月面基地が最初から持っている設備が担う。そこから先は、自分が作った設備で次の設備を作る。

### 3-11. 自動操縦には通信が要る

無人の機体が軌道計画を自動で実行するには、通信モジュールを積み、かつ通信圏の内側にいることが要る（§13）。**機上の計算機は、決められた時刻に決められた噴射を行うところまでしかできない。**圏外へ出た無人機は、実行中の噴射を最後までやり切ったのち、そこで計画の実行を止め、最後の指令を保持したまま漂流する。

これにより、無人の輸送網を広げることは、**通信の網を先に広げること**と同じになる。通信衛星は専用の実体ではなく、通信モジュールと太陽電池と自動操縦装置を積んだ小さな機体である。網を広げる操作は、機体を設計して軌道へ投入する、すでにある操作そのものになる。

## 4. 設計データの保存と検証

### 4-1. 設計データ

```ts
// src/game/vessel/blueprint.ts
export interface VesselBlueprint {
  readonly id: string;
  name: string;
  readonly tree: VesselTree;
  readonly placements: readonly PartPlacement[];
  readonly feedNetwork: FeedNetwork;    // 配管の敷設（§10）
  readonly paint: PaintScheme;
  readonly stageOrder: readonly string[];
  readonly createdAt: number;
  readonly updatedAt: number;
}
export interface PaintScheme {
  primaryColor: string;
  secondaryColor: string;
  accentColor: string;
  metalness: number;
  roughness: number;
}
```

設計は `localStorage` の `tepui.blueprints` に保存する。保存・読み込み・複製・削除・改名ができる。既存のセーブデータの入出力と同じ方式でファイルへの書き出しと読み込みも行う。

`feedNetwork` のうち自動敷設で導出できる部分は保存しない。保存するのは手動の上書き（`manual: true`）だけであり、残りは設計から毎回導出する。

### 4-2. 検証

設計の検証は独立した純関数とし、ドック空間の表示と生産の両方が同じ関数を呼ぶ。DOM にも THREE にも依存しない。

```ts
// src/game/vessel/blueprint-validation.ts
export interface BlueprintIssue {
  readonly severity: 'error' | 'warning';
  readonly targetId: string;      // ノード／エッジ／搭載要素の id
  readonly message: string;
}
export function validateBlueprint(bp: VesselBlueprint): readonly BlueprintIssue[];
```

検証する内容:

- ツリーが連結していること
- 複合断面の貼り合わせ面の長さが一致すること
- 側面の口から出るエッジの断面が、口の周方向・軸方向の両方の寸法に収まること
- 隣接する側面の口が干渉しないこと
- 1つの接続口に、エッジと外装要素が同時に割り当てられていないこと
- トラスに取り付けた外装要素どうしが、軸に沿って重なっていないこと
- `hull` エッジの外表面に取り付けた RCS スラスタが、他の外装要素と干渉しないこと
- 内容積の割り当てがロフト体積を超えないこと
- 内装要素がまたぐエッジが軸方向に連なっていること
- 推進剤とタンク材料が適合すること
- コックピットまたは自動操縦装置を1つ以上持つこと
- 自動操縦装置だけを持つ機体は通信モジュールを1つ以上持つこと
- 推力軸と重心のずれが規定内であること
- ノード数・総質量・最大寸法・複合断面の構成要素数が上限以内であること
- タンクからエンジンまで、要求する推進剤ごとに配管が連続していること
- 加圧を要するエンジンに対し、加圧ガスの供給経路があるか、自己加圧の条件を満たすこと
- 武器と弾薬庫が同じ段に属すること
- 熱シールドの覆う方向と、大気制動時の姿勢が矛盾しないこと

**生産に必要な資源と設備が揃っているかは、この検証では扱わない。**設計そのものの成立と、それを作れるかどうかは別の問いであり、後者は生産可能性の判定（§5-2）が答える。

## 5. 生産と生産可能性

### 5-1. 生産

生産は、保存した設計を指定し、**資源と設備と電力**を消費して実機を得る操作である。

```ts
export interface ProductionTask {
  readonly id: string;
  readonly blueprintId: string;
  readonly startedAt: number;      // simTime
  readonly finishAt: number;       // simTime
}
```

- 消費する資源は、搭載要素ごとの資源コストと、外皮の質量に対応する構造材の和とする。
- 生産時間は搭載要素の合計に**生産時間係数**を掛けて求める。この係数は**セーブデータに含め、ステージごとの既定値を持つ**。既定値は0であり、すべての設計が即座に完成する。係数を後から有効にしても、既存のセーブに影響しない。
- 生産キューは基地モジュールを持つ機体が保持する。完成した機体はその基地のドックに現れる。

### 5-2. 生産可能性

```ts
// src/game/economy/producibility.ts
export interface Requirement {
  readonly kind: 'resource' | 'facility' | 'power';
  readonly id: string;
  readonly needed: number;
  readonly available: number;
}
export function producibility(
  bp: VesselBlueprint,
  ledger: ResourceLedger,
  facilities: readonly string[],
  powerAvailable: number,
): readonly Requirement[];   // 空配列なら生産できる
```

要求の種別は資源・設備・電力の3つしかない。**生産の可否はこの3つだけで決まる。**

不足している要求は、ドック空間の右パネルが「何が足りないか」として表示する。さらに、その資源が**どの設備から作れるか**、その設備が**何を要するか**を `FACILITIES`（§17）から辿って表示する。プレイヤーは足りないものを起点に、必要な連鎖を遡って読める。

`producibility` はタンクを持つ設計に対して材料適合性の表（§15-2）を引き、積む推進剤に適合する材料を在庫が満たすかどうかも要求として列挙する。

この関数と、それが読む `ResourceLedger`・`FACILITIES`・`RESOURCES`・`TANK_MATERIALS` は、**DOM にも THREE にも依存しない純関数と純データとして置く。**表示は別の層が受け取った結果を描くだけである。

## 6. ドック空間での設計と組み立て

設計と組み立ては、ドックモジュールを持つ機体のドックビューで行う。カメラはドックの内側に入り、戦闘ビューと同じ3D空間の中で機体を実寸で見る。全画面のワークベンチは持たない。

### 6-1. 空間と視点

ドック空間は、基地のドックモジュールが定める直方体の作業領域である。その中に組み立て中の機体が置かれ、周囲には係留中の他の機体と基地の構造が同じ縮尺で見えている。

- カメラの操作は戦闘ビューの追従カメラと同じである。左ドラッグ／右ドラッグ／矢印キーで回転、ホイールでズーム、中ドラッグでパンする。
- ドックの最大寸法を超える設計は、作業領域の枠を突き抜けて表示され、警告になる。**枠は目に見える。**入らない機体を作っていることが、寸法の数値ではなく形として分かる。
- 選択したノード・エッジ・搭載要素は、その空間の中で強調表示される。

### 6-2. 操作モード

モードは4つである。**全画面の画面遷移ではなく、ドック空間の中で何を触れるかを切り替えるものである。**

| モード | 触れる対象 | 触れない対象 |
|---|---|---|
| **骨格** | ノード、断面、エッジ | 搭載要素 |
| **搭載** | 接続口、トラス上の位置、エッジの内容積 | ツリーの形 |
| **配管** | エッジ上の配管 | 上記すべて |
| **塗装** | 外皮の色と質感 | 上記すべて |

断面の編集は骨格モードの中で行い、独立したモードにしない。断面はノードの属性であり、ノードを選んだときに左パネルへ編集欄が出れば足りる。段の一覧も独立したモードにせず、右パネルの常設表示に置く。モードが増えるほど、プレイヤーが「今どのモードにいるか」を把握する負担が増える。

### 6-3. パネルの配置

パネルは既存のHUDの置き場の規約に従う。ドック空間は戦闘ビュー・マップビューと並ぶ1つのビューであり、そのビューのレールに専用のパネルが並ぶ。既存のウィジェットのみで構成し、生の `<button>` および `<input>` を直接書かない。

**左レール** — モードごとに内容が変わる編集パネル（§6-4〜§6-7）。個別に折り畳める。

**右レール** — モードによらず同じ内容の性能パネル。

| 行 | 内容 |
|---|---|
| 乾燥質量／総質量／全長 | ツリーと搭載物から導出 |
| Δv | 全段の合計 |
| 推力重量比 | 月面重力を基準とする |
| 慣性主軸／推力軸ずれ | 制御性の目安 |
| 電力収支／放熱余裕 | 発電・消費・廃熱の差 |
| 加圧ガス余裕 | 積んだ推進剤を押し切れるか |
| 通信 | 通信モジュールの到達距離 |
| 段の一覧 | 分離順、段ごとの乾燥質量・推進剤質量・Δv |
| 生産 | 不足している資源・設備・電力 |

性能表示は、要素を選択またはホバーしている間、その要素を追加した場合の差分を数値の横に併記する。

**下部** — 元に戻す／やり直す、および「この設計で生産」。

### 6-4. 骨格モード

左パネルの内容:

| 区画 | ウィジェット | 内容 |
|---|---|---|
| **選択中のノード** | | |
| 断面の構成 | ツリー表示（折り畳み可） | 基本断面の木構造。行を選ぶとその基本断面を編集する。単一の基本断面なら折り畳んだまま使える |
| 基本断面の形状 | `SegmentedControl<PrimitiveShape>` | 円／楕円／三角／四角／五角／六角／八角／切り欠き六角／切り欠き八角 |
| 外接円半径 | `ValueInput` | 0.25 m 刻み（直径 0.5 m 刻み）。**外接円直径に加えて、辺の長さと最大幅を併記する** |
| 楕円の短半径 | `ValueInput` | 楕円選択時のみ |
| 円の分岐数 | `SegmentedControl<2\|3\|4\|5\|6>` | 円選択時のみ |
| 基本断面の位相 | `Slider` | 選択中の基本断面の回転位相 |
| 断面全体の位相 | `Slider` | 15度刻みのスナップあり |
| 貼り付け | `Button` | 選択中の辺に新しい基本断面を貼り付ける。辺の長さが一致しない場合は警告 |
| 接続口 | 一覧 | 使用中／空きを表示し、空きを選ぶと新規ノードが生える |
| 断面の性能 | 表示 | 面積、内容積への寄与、断面二次モーメント、主軸の角度 |
| **選択中のエッジ** | | |
| 種別 | `SegmentedControl<EdgeKind>` | 外皮／トラス／分離機構 |
| 長さ | `ValueInput` | 0.5 m 刻み、最小 0.5 m |
| 付加値 | `ValueInput` | トラスの半径、分離機構の分離力積 |
| **全体** | | |
| ミラー編集 | `ToggleSwitch` | YZ平面 |
| 削除 | `Button` | 選択中のノード以下を削除 |

**寸法の刻みは外接円半径で揃えるが、多角形では外接円直径と実際の幅が一致しない。**正方形で外接円直径 1 m を指定すると、辺の長さは 0.707 m である。刻みそのものは外接円半径のまま変えず、外接円直径・辺の長さ・最大幅の3つを並べて表示することで、指定した数値と目に見える大きさの食い違いを埋める。接続口に収まるかどうかを判断するのに要るのは最大幅であり、外皮の板取りに要るのは辺の長さである。

操作:

- **ノードの追加** — ドック空間の中で、選択中のノードの空いている接続口を直接クリックする。既定の長さのエッジと、同じ断面のノードが生える。生えた先が新しい選択対象になる。左パネルの接続口の一覧から選んでも同じ操作になる。
- **ノードの移動** — エッジの長さを変えることで行う。ノードの座標を直接ドラッグする操作は持たない。位置は接続関係と長さから一意に決まる。
- **断面の編集** — ノードを選んだ状態で断面の編集に入ると、カメラがその断面の正面へ回り込み、断面を正対して見る配置になる。辺をクリックすると、その辺が「側面の口の候補」か「基本断面の貼り付け先」かを選べる。画面は切り替わらず、視点が動くだけである。
- **削除** — 選択中のノードとその先につながる部分をまとめて削除する。削除の前に、削除される範囲をドック空間の中で強調表示する。
- **ミラー編集** — 有効な間、YZ平面の片側で行った操作が反対側にも同時に適用される。
- **元に戻す／やり直す** — 設計データ全体のスナップショットを操作ごとに保持する。上限は50手とする。

### 6-5. 搭載モード

| 区画 | ウィジェット | 内容 |
|---|---|---|
| 要素パレット | 種別ごとのアコーディオン | 外装要素と内装要素の一覧。生産に必要な資源または設備が揃っていないものは淡色で表示し、何が不足しているかを示す。選択して設計に含めることはできる |
| 選択中の要素 | 表示 | 質量・性能値・資源コスト。エンジンは全長・比推力・絞り範囲・要求与圧・点火あたりの損失も表示する |
| 選択中のエッジの内容 | 一覧 | そのエッジに収めた内装要素。追加・削除ができる。軸方向に連なるエッジへ拡張するボタンを持つ |
| | 表示 | ロフト体積、実効容積の合計、残容積、収容質量、タンク材料の適合 |
| トラス上の配置 | 一覧＋`ValueInput` | そのトラスに取り付けた外装要素と、軸方向の位置 |

操作:

- 要素パレットで外装要素を選び、ドック空間の中のノードの空いている接続口をクリックすると装着する。装着できない口はクリックできず、理由をヒントで示す。
- **トラスへの取り付け**は、トラスの軸上の任意の点をクリックして行う。位置は 0.5 m 刻みにスナップし、左パネルの数値でも調整できる。大型の太陽電池パドル、大型の放熱板、ロボットアームはここに付く。
- **RCSスラスタは、上の2つに加えて `hull` エッジの外表面にも付く。**エッジの側面をクリックすると、その軸方向の位置と周方向の角度に取り付く。腕を長く取れば同じ推力で大きなトルクが出る。
- ホバー中は、装着した場合の外観をその場に半透明で表示し、右パネルの性能に差分を表示する。
- エッジをクリックすると、その内容積の割り当てを編集する。

パレットの表示は生産可能性を反映する。

- **生産できる要素** — 通常表示
- **資源が足りない要素** — 淡色表示。不足している資源と、その入手先を表示する
- **設備がない要素** — 淡色表示。必要な設備と、その建設に要るものを表示する
- **タンク材料が適合しない組み合わせ** — 推進剤を選んだ時点で、要求する材料と在庫を表示する

いずれも**選択して設計に含めることはできる**。生産のときにだけ拒否される。

### 6-6. 配管モード

左パネルの主眼は「自動敷設の結果の確認」と「手動の上書き」である。

| 区画 | ウィジェット | 内容 |
|---|---|---|
| 自動敷設 | `Button` | 自動敷設をやり直す |
| | `Button` | 手動の上書きをすべて破棄する |
| 供給の診断 | 一覧 | エンジンごとの供給状態（供給あり／配管が繋がっていない／流量不足／加圧ガス不足） |
| 分離を跨ぐ配管 | 一覧＋`ToggleSwitch` | 分離機構を跨ぐ配管の候補と、跨ぐことを許すかどうか（クロスフィード） |
| 手動で敷く | `ObjectPicker` | 通す推進剤の種別（酸化剤・還元剤・RCS推進剤・加圧ガス） |
| | `SegmentedControl` | 口径 |

ドック空間の表示は配管の重ね描きに切り替わり、推進剤の種別ごとに色分けした線をツリーに沿って描く。外皮は半透明になり、中を通る配管が見える。自動敷設された配管と手動で敷かれた配管は線種で区別する。エッジをクリックすると、そのエッジに選択中の配管を敷設または撤去し、その区間は手動の上書きになる。

供給されていないエンジンは赤く強調し、原因を表示する。分離を跨ぐ配管の一覧で跨ぐことを許すと、そのエンジンへ自動敷設が届くようになる。

### 6-7. 塗装モード

左パネルに、基本色・副色・アクセント色のカラー選択、金属感と粗さのスライダー、および既定の配色プリセットを置く。ドック空間の機体に即座に反映する。ドックの照明は基地の日照に従うため、**塗った色が実際の光の下でどう見えるかがその場で分かる。**

### 6-8. 段の一覧

段は独立したモードを持たない。段の一覧は右レールに常設し、どのモードで作業していても見える。段の内容はモードを切り替えるほどの分量ではない。

| 区画 | ウィジェット | 内容 |
|---|---|---|
| 段の一覧 | リスト（分離順） | 各行に段の乾燥質量・推進剤質量・その段の Δv・主機の有無 |
| | 上下ボタン | 分離順の並べ替え |
| Δv の積み上げ | グラフ | 全段の Δv を積み上げて表示 |

各段の Δv はツィオルコフスキーの式により、その段を点火する時点の総質量と、燃焼終了時の総質量から求める。行を選択すると、ドック空間でその段を強調表示する。

### 6-9. 別の場所で組んだモジュールの結合

ドックの寸法を超える機体は、複数のモジュールに分けて設計し、それぞれを生産して軌道上で結合する。**結合の操作はドッキング（§8）そのものである。**ドッキングポートを持つ2つの機体を接近させ、捕獲条件を満たして結合すると、2つのツリーが1つになる。専用の操作も専用の機構も要らない。

- 結合後のツリーは、両者のドッキングポートを1つのノードとして継いだものになる。質量特性・配管・段の分割は、結合の時点で一度だけ再計算する。
- 結合した機体は、ドックに入れば1つの設計として保存できる。
- 分解はジョイントの取り外し（§8-6）であり、分離機構と同じ経路を通る。

この扱いにより、**ドックの最大寸法は機体の最大寸法ではない。**ドックに入る大きさのモジュールを何個でも作り、軌道上でつなげば、ドックより大きな構造物が作れる。結合そのものは §8 の機構として成立しているため、ここで新たに要るのは、結合したクラスタを1つの設計として保存する経路だけである。

### 6-10. データの流れ

```
DesignEditorState (編集中データ、Undo/Redo のスタックを持つ)
    │  編集操作ごとに
    ▼
VesselBlueprint
    ├─► validateBlueprint()        → 左パネルとドック空間の問題表示
    ├─► sectionMoments()           → 断面の性能表示
    ├─► deriveMassProperties()     → 右パネルの質量・重心・慣性・投影面積
    ├─► deriveCapsules()           → 接触形状の表示（デバッグ表示）
    ├─► autoRouteFeed()            → 配管の敷設（手動の上書きを保持）
    ├─► resolveFeed()              → 配管モードの診断
    ├─► deriveStages()             → 右パネルの段の一覧と Δv
    ├─► producibility()            → 右パネルの不足の表示
    └─► buildLoftMesh()            → ドック空間の外皮表示
```

性能計算は編集操作のたびに実行する。計算はすべて解析式であり、ノードとエッジの数に対して線形であるため、毎操作の実行で問題にならない。外皮メッシュの生成のみ、編集が一定時間止まってから実行する。

**この列のうち、`buildLoftMesh` を除くすべては DOM にも THREE にも依存しない純関数である。**ドック空間の表示はその結果を受け取って描くだけであり、逆向きの依存を持たない。

### 6-11. 飛行中のHUD

飛行中に置くパネルのうち、この巻が担当するものは3つである。いずれも個別に折り畳める。

- **段** — 段の一覧、次に分離する段、段ごとの残 Δv。分離の実行ボタン。
- **ペイロード** — ペイロード倉庫の内容と、放出の実行ボタン。
- **通信** — 通信圏の内か外か、最寄りの中継点、到達距離の余裕。

加圧ガスの残量と、その残量での残り燃焼可能時間は、推進系パネルの主機の行に表示する。磁気トルカが働いているかどうか（§15-4）は姿勢制御の行に常時表示する。熱シールドのアブレータ残量は、大気に入る軌道を持つ機体に対して常時表示する。

## 7. 分離機構と多段

### 7-1. 段の定義

段は、ツリーから `decoupler` エッジを取り除いたときの連結成分である。

```ts
// src/game/vessel/assembly.ts
export interface VesselStage {
  readonly id: string;
  readonly edgeIds: readonly string[];
  readonly hasCockpit: boolean;
  readonly hasAutopilot: boolean;
  readonly hasCommunication: boolean;
  readonly dryMass: number;
  readonly propellantMass: number;
}
export function splitStages(tree: VesselTree, parts: readonly AnyPart[]): readonly VesselStage[];
```

コックピットを含む段は分離後も操作できる。自動操縦装置と通信モジュールを含む段は、通信圏の内側にいる限り自動制御の対象になる。どちらも欠く段は、分離後は制御不能な物体として軌道上に残る。

### 7-2. 分離の物理

分離は運動量保存を満たす。分離前の質量を `m_total`、分かれる2つを `m_a` / `m_b`、分離機構の力積から求まる相対速度増分を `Δv_sep` とすると、

```
v_a = v + (m_b / m_total) · Δv_sep
v_b = v − (m_a / m_total) · Δv_sep
```

角運動量も同様に分配する。分離直後の一定時間は、分かれた2つの間の接触判定を無効にする。

分離後、本体はツリー・質量・重心・慣性テンソル・推進剤残量・配管の流路を再計算する。分離機構を跨いでいた配管は切断される。

### 7-3. 燃焼の順序

同時燃焼（並列に束ねたブースター）と逐次燃焼（直列の多段）の両方を許す。段の一覧は分離順に並べ替えられ、飛行中はその順序に従って次に分離する段をHUDに表示する。

推進剤が尽きた段は分離の候補として提示するが、自動では分離しない。

### 7-4. 段を跨ぐ燃焼の判定と分割

段の切り替わりを跨ぐ燃焼は加速度が不連続になり、閉形式の点火時刻計算が成立しない。1つのマニューバノードの燃焼が1つの段の中で完結する必要がある。

**判定式は、そのノードの Δv に対する `propellantForDv(dv, mDry, isp)` が、そのノードを実行する段の推進剤残量を超えるかどうかである。** 超えない場合は何もしない。

超える場合、UIは**禁止するのではなく、ノードを2つに分割することを提案する**。分割は、その段の推進剤で出せる Δv までを1つ目のノードとし、残りを2つ目のノードとする。1つ目の燃焼終了後に段を分離し、2つ目を次の段で実行する。2つ目のノードには、次の段のエンジンの点火あたりの推進剤損失が加算される。

禁止するだけでは、プレイヤーは何をすればよいか分からない。分割案を提示し、受け入れるかどうかを選ばせる。

連続燃焼時間の上限を持つエンジンについても同じ判定を行う。要求される燃焼時間が上限を超える場合、上限までを1つ目のノードとして同じ形で分割を提案する。

## 8. ドッキングポートによる機体の結合

ドッキングポートを持つ機体同士が接近し、双方のポートの位置・向き・相対速度・相対角速度がすべて捕獲条件を満たしたとき、機体が結合する。結合後は、ポート軸まわりの相対回転（位相角）を任意に変えられ、推進剤とガスを移送でき、電力は結合体全体で1つの収支として計算される。

この機構の上に、次の運用が成立する。

- 軌道上にあらかじめ投入しておいたブースターと合流し、結合してその推進剤で基地へ帰投する。
- 艦艇同士を結合し、推進剤と電力を融通する。
- 軌道基地に艦艇を接舷して格納する。
- ドックに入らない大きさの構造物を、モジュールに分けて作り、軌道上でつなぐ（§6-9）。

### 8-1. ドッキングポート部品

```ts
export interface DockingPortPart extends Part {
  readonly type: 'docking_port';
  readonly portClass: 'small' | 'medium' | 'large'; // 同一クラス同士のみ結合できる
  readonly androgynous: boolean;                    // false の場合 probe と drogue の対でのみ結合
  readonly role: 'probe' | 'drogue' | 'both';
  readonly localPos: Vec3;        // 機体ローカル座標のポート面中心
  readonly localAxis: Vec3;       // ポート面の外向き法線
  readonly localRollRef: Vec3;    // 位相角0を定義する基準方向（localAxis に直交）
  readonly transferRate: number;  // 推進剤移送速度 [kg/s]
  readonly powerBridge: boolean;  // 電力を橋渡しするか
}
```

ドッキングポートは外装要素であり、ツリーのノードの空いている接続口に装着する。ポートの軸はその接続口の方向と一致する。

### 8-2. 捕獲条件

2つのポート A・B が以下をすべて満たすとき、捕獲が成立する。値は `const.ts` に置く。

| 条件 | 内容 |
|---|---|
| 適合 | `portClass` が一致し、`androgynous` 同士、または `probe` と `drogue` の対である |
| 軸方向距離 | ポート面中心間の距離が捕獲距離以内 |
| 横方向ずれ | A の軸に投影したときの横方向オフセットが許容半径以内 |
| 軸の対向 | A の軸と B の軸のなす角が180度から許容角度以内 |
| 接近速度 | 最小値以上・最大値以下。速すぎればラッチが損傷し、遅すぎれば噛まない |
| 横方向相対速度 | 許容値以下 |
| 相対角速度 | 許容値以下 |

捕獲が成立すると、ポート面同士を厳密に一致させる位置と姿勢へ両機を補正する。補正は運動量と角運動量を保存する形で行い、余剰は減衰として捨てる。これはラッチの衝撃吸収に相当する。

条件を満たさずに接触した場合は、通常の剛体接触として処理する。跳ね返り、および相対速度に応じた損傷が生じる。

### 8-3. 結合体

結合した複数の `Vessel` は、1つの剛体として積分する。

```ts
export interface DockingCluster {
  readonly id: string;
  readonly members: readonly Vessel[];
  readonly root: Vessel;                    // 積分の主体。KinematicState と Attitude を持つ
  readonly joints: readonly DockingJoint[];
}
export interface DockingJoint {
  readonly portA: { vesselId: string; partId: string };
  readonly portB: { vesselId: string; partId: string };
  phaseAngle: number;   // ポート軸まわりの相対ロール [rad]
}
```

- 積分は `root` の状態に対してのみ行う。他の構成機体の位置と姿勢はジョイントの連鎖から毎フレーム導出する。
- クラスタの質量・重心・慣性テンソルは、全構成機体のものを平行軸定理で合成する。推進剤が減れば変わるため、質量が一定量変化したときに再計算する。
- クラスタの主機・RCS・フライホイールは全構成機体のものの合計として扱う。主機の推力軸がクラスタ重心を外れる場合、そのぶんのトルクが実際に発生する。
- 同一クラスタの構成機体同士は接触判定を行わない。

### 8-4. 位相角の調整

ジョイントの `phaseAngle` を連続的に変えられる。ポート軸まわりに片側を回すことに相当し、機体全体の姿勢を変えずに構成機体の相対的な向きだけを変える。

- 回転速度に上限があり、電力を消費する。
- 回転させると結合体の慣性テンソルが変わるため、角運動量保存により全体の角速度が変化する。この効果はフライホイールと同じ内部トルクの一種として正しく計算する。
- 用途は、太陽電池を太陽に向ける、放熱板を日陰に入れる、武装の射界を確保する、固定脚の向きを揃える、である。

### 8-5. 移送と電力・放熱の統合

**推進剤とガスの移送** — 結ばれた機体の間で移送できる。

- 移送できるのは、送り側と受け側のタンクが同じ推進剤種別に適合している場合のみ。極低温と常温貯蔵性の推進剤は互いに移送できない。
- 移送速度は両ポートの `transferRate` の小さいほうで律速する。
- 移送中は電力を消費する。
- 移送に伴って両機の質量と重心が変わるため、質量特性を更新する。クラスタ全体の重心は移動しないが、慣性テンソルは変わる。

**電力統合** — `powerBridge` を持つジョイントで結ばれた範囲は、1つの電力系として計算する。発電量は全構成機体の太陽電池・燃料電池・原子力電池の合計であり、太陽電池の向きと日照は個別に評価したうえで合計する。蓄電容量はバッテリーの合計、消費は全構成機体の合計とする。不足が生じた場合は、優先度の低い消費から順に停止する。

**放熱の統合** — 電力統合を行う範囲では、発熱と放熱も1つの収支として計算する。放熱面が足りない構成機体があっても、結合相手に余剰があれば作動流体の循環によって融通できる。融通できるのは `powerBridge` を持つジョイントで結ばれた範囲に限る。

### 8-6. 分離

結合の解除は、ジョイントを取り除いてクラスタを分割することである。分割後は、分かれた側それぞれが独立した運動状態を持ち、運動量と角運動量が保存されるように速度と角速度を分配する。解除時に小さな分離速度を与える。分割の物理は分離機構（§7-2）と同じ経路を通る。

### 8-7. ドッキング支援の表示

ドッキングポートを目標に選ぶと、以下を表示する。

- 目標ポートの位置と軸を示すマーカー、および自機ポートとの相対位置。
- 横方向のずれと軸の対向角を示す十字型のインジケータ。
- 相対距離、接近速度、横方向相対速度、相対角速度と、それぞれの許容範囲。
- 捕獲条件を条件ごとに満たしているかどうかの一覧。

    captureCorrection(...) -> { stateA, stateB }   // 運動量保存を満たす補正

## 9. ペイロード

ペイロード倉庫は、軌道上へ運ぶものを収める。エッジの内容積に対する実効容積の係数は 0.90 であり、容積と最大積載質量の両方で制限される。

```ts
export type PayloadKind =
  | { kind: 'ammo'; magazines: number }
  | { kind: 'propellant'; propellantId: string; mass: number }
  | { kind: 'part'; partIds: readonly string[] }
  | { kind: 'none' };

export interface PayloadBayPart extends Part {
  readonly type: 'payload_bay';
  readonly volume: number;
  readonly maxMass: number;
  payload: PayloadKind;
}
```

**弾薬をペイロードとして運ぶ運用** — 弾薬を積んだ無人ブースターを、自動操縦で目的の軌道に投入する。到達後、ペイロード倉庫を開いて弾薬を放出すると、既存の補給パッケージと同じ実体が軌道上に生成される。艦艇はそれに接近して回収する。この運用は通信圏の内側でしか成立しない（§13）。

この運用は機体同士の結合を必要としない。放出された弾薬は独立した物体として軌道を回り、艦艇は既存の接近回収の仕組みでそれを取る。

放出は、プレイヤーの明示的な操作、または軌道計画上の指定時刻に行う。放出時には小さな分離速度を与え、ブースター本体と弾薬が離れる。

ペイロード倉庫は機体内部の容積であり、機体の外形に現れない。着脱して軌道上に置ける規格化された容器はコンテナ（§14-5）であり、こちらは外装要素として取り付ける。**輸送にはコンテナが向き、投下にはペイロード倉庫が向く。**

## 10. 配管と推進剤の流路

推進剤はタンクからエンジンへ、配管を通って流れる。

```ts
// src/game/vessel/feed-network.ts
export interface FeedNetwork {
  readonly links: readonly FeedLink[];   // 配管が敷かれたエッジ
}
export interface FeedLink {
  readonly edgeId: string;
  readonly propellantId: string;   // この配管が通す推進剤
  readonly diameter: number;       // m
  readonly maxFlowRate: number;    // kg/s
  readonly manual: boolean;        // 手動の上書きか（自動敷設のやり直しで保持される）
}
export function resolveFeed(
  network: FeedNetwork,
  tanks: readonly TankPart[],
  engines: readonly EnginePart[],
): readonly EngineFeedResult[];
```

規則:

- 配管は1本につき1種類の推進剤しか通さない。酸化剤と還元剤を同じエンジンへ送るには、配管が2本必要である。加圧ガスも同様に別の配管を要する。
- タンクとエンジンが、同じ推進剤の配管で連続して繋がっていることが点火の条件である。繋がっていないエンジンは点火できず、ドック空間と飛行中HUDがその旨を表示する。
- 配管の口径から決まる最大流量が、エンジンの要求流量（`推力 / (比推力 × 標準重力加速度)`）を下回る場合、エンジンの推力はその流量で制限される。
- タンクとエンジンが同じエッジの内容積に同居する場合、配管は不要である。
- 分離機構のエッジを配管が跨ぐ場合、分離と同時に配管が切断される。跨ぐことを許すかどうかはプレイヤーが選ぶ。跨ぐ配管を敷けば、側面ブースターのタンクから中央のエンジンへ推進剤を送る運用（クロスフィード）ができ、分離時点で中央段のタンクを満載のまま残せる。
- 外皮のない `truss` エッジにも配管を敷ける。この場合、配管は外部に露出したものとして描画する。

配管がエッジの内容積を占める量は、口径から決まる。エッジの長さと口径の断面積の積である。

### 10-1. 自動敷設

```ts
// src/game/vessel/auto-route.ts
export function autoRouteFeed(
  tree: VesselTree,
  placements: readonly PartPlacement[],
  overrides: readonly FeedLink[],   // 手動の上書き（manual: true のもの）
): FeedNetwork;
```

規則:

- 各エンジンに対して、そのエンジンが要求する推進剤（酸化剤・還元剤・加圧ガス）ごとに、その推進剤を持つ最も近いタンクから最短経路で配管を通す。距離はエッジの長さの和とする。
- 口径は、そのエンジンの要求流量を満たす最小のものを選ぶ。同じエッジを複数のエンジンが共有する場合、口径は要求流量の和を満たす最小のものになる。
- 既定では分離機構を跨がない。跨がなければ届かないエンジンについては、跨ぐ経路を提示するが敷設はせず、供給なしとして診断に出す。クロスフィードは選択に意味のある判断であり、自動で決めない。
- 手動で敷かれた区間（`manual: true`）は保持し、自動敷設はその上に足りない分だけを敷く。手動の区間だけでエンジンへ届く場合、自動敷設はそのエンジンに対して何もしない。
- 設計を変更するたびに、この関数を呼び直す。エッジ数に対して線形である。

自動敷設の結果は手動の敷設と同じ `FeedNetwork` であり、`resolveFeed` は両者を区別しない。

## 11. タンクの与圧

液体推進剤のタンクは、推進剤を押し出すために内部を加圧する必要がある。方式は4つある。

| 方式 | 対象 | 内容 |
|---|---|---|
| **自己加圧** | 極低温推進剤 | 蒸発した推進剤自身の気体でタンクを加圧する。加圧ガスを積む必要がない代わりに、蒸発損失が増える。**極低温推進剤の既定はこれである** |
| **自己加圧** | 亜酸化窒素 | 蒸気圧が高く、そのままタンクを加圧できる。加圧ガスタンクが不要になる |
| **窒素加圧** | 常温貯蔵性推進剤 | 窒素を高圧で積む。極低温推進剤には使えない（凝縮する） |
| **ヘリウム加圧** | 全般 | 必要質量が窒素の約7分の1で済む。極低温でも凝縮しない。**月では少量しか採れず、木星大気に到達して初めて標準になる** |

**加圧ガスを積む必要がないことが、極低温推進剤の既定の姿である。**蒸発損失という代償と引き換えに、加圧ガスの質量と容積が丸ごと消える。窒素は常温貯蔵性推進剤のためにある。

**ヘリウムは早い段階から少量だけ手に入る。**月のレゴリスを加熱すれば太陽風起源のヘリウムが得られるが（§15-3、§17-4）、産出量は微々たるものであり、**全機体をヘリウム加圧にするには到底足りない。**したがってヘリウムは「どの機体に使うか」を選ぶ資源になる。加圧ガスの質量が最も効く機体——小型で質量比を詰めたい機体、極低温推進剤を大流量で長く噴射する機体——に優先して配り、残りは窒素加圧か自己加圧で済ませる。木星大気に到達すると産出量の制約が消え、**ヘリウム加圧が標準になる。**

- 消費するガス量は、押し出した推進剤の体積とタンクの与圧の積に比例する。
- 要求与圧はエンジンのサイクルによって決まる。**加圧式エンジンは要求与圧が高く、大量の加圧ガス（または大きな蒸発損失）を要する。ポンプ式エンジンは低い与圧で足り、消費が少ない。** この差が、単純な加圧式と、複雑だが効率のよいポンプ式との設計上の対立になる。

### 11-1. 与圧低下による推力低下

加圧ガスが減るとタンクの与圧が下がり、エンジンの推力が下がる。与圧が要求値を下回った時点から、推力を与圧に比例して下げ、下限を割った時点で燃焼を停止する。

- **加圧式**は与圧が燃焼室圧を直接決めるため、影響が大きい。与圧の低下がそのまま推力の低下になる。
- **ポンプ式**はポンプ入口圧（NPSH）が下限を割るとキャビテーションを起こし、そこから急に推力を失う。要求値を上回っている限り影響はない。

加圧ガスが尽きると、推進剤が残っていてもエンジンは推力を失う。自己加圧の機体では、蒸発が追いつかないほど高い流量で長く噴射したときに同じことが起きる。これは実機の失敗様態と同じである。HUD には加圧の余裕と、その余裕で燃焼を続けられる残り時間を表示する。

計算は純関数として置く。

```
src/physics/pressurant.ts   (純関数)
    pressurantMassFor(propellantVolume, tankPressure, gasType, temperature) -> number
    autogenousBoiloffRate(propellantId, tankPressure, flowRate) -> number
    remainingBurnTime(pressurantMass, flowRate, tankPressure, gasType) -> number
    thrustScaleFromPressure(tankPressure, requiredPressure, cycle) -> number
```

## 12. 弾薬の供給

武器は弾薬庫から弾薬の供給を受ける。**弾薬そのものが搭載要素である。**弾薬庫は弾薬を収める内装要素であり、弾薬は生産の対象であり、資源を消費して作られる。

武器と弾薬庫が同じ段に属していれば供給される。段が異なる場合は供給されない。分離によって弾薬庫を失った武器は、装填済みの分を撃ち尽くした時点で沈黙する。

## 13. 通信と自動操縦

### 13-1. 自動操縦の条件

**この世界には高性能な計算機が存在しない。**一万年の宇宙生活のあいだに失われ、作り直せていない。自動操縦装置が自力で行えるのは、**あらかじめ決められた時刻に、決められた向きへ、決められた量の噴射を行うこと**までである。

| 機上で行えること | 外部からの指令が要ること |
|---|---|
| 時刻で駆動する噴射シーケンスの実行 | 自動でのドッキング |
| 姿勢の保持 | 軌道の誤差を見ての修正 |
| 既に計画済みのマニューバノードの実行 | 目標の捕捉と追尾 |
| | 状況に応じた計画の変更 |

右の列に並ぶのはいずれも、**観測して判断する処理**である。何かを測り、その値に応じて次の行動を決めることが、機上の計算機では扱えない。左の列は、測る必要がない。時計と、あらかじめ書き込まれた数値の列があれば足りる。

したがって無人の機体が軌道計画を自動で実行するには、次の2つがともに要る。

1. 自動操縦装置を積んでいること
2. **通信モジュールを積み、かつ通信圏の内側にいること**

判断は基地の計算設備が行い、その結果が通信で機体へ届く。通信が切れれば、届くのは何もなくなる。

コックピットを持つ有人の機体は、この制約を受けない。人が乗っていれば、圏外でも操作できる。**人の判断が、機上にない計算能力の代わりになる。**

**より高性能な計算機は、進行の後半で作れるようになる余地を残す。**高純度のケイ素と希少な金属を要する設備であり、それが揃えば機上で行える判断の範囲が広がり、通信圏への依存が緩む。どこまで緩めるか——軌道の誤差修正までか、自動でのドッキングまでか、目標の追尾までか——は今後の判断であり、ここでは余地を置くにとどめる。

### 13-2. 通信圏

通信圏は、中継点との**見通し線が通り**、かつ**距離が通信モジュールの到達距離以内**であることで決まる。見通し線の判定は、天体の球によって遮られるかどうかであり、既存の遮蔽判定と同じ形の純関数である。

**通信圏の判定はこの巻がすべて持つ。**第1巻は、自動操縦の可否が通信圏の問い合わせを引数に取るという形だけを定め、実装には踏み込まない。判定の関数は `isInCommRange` の1つであり、これと別の到達距離の関数を置かない。

```ts
// src/game/comms/coverage.ts
export interface CommRelay {
  readonly id: string;
  readonly pos: Vec3;         // ECI
  readonly range: number;     // m。この中継点が届く距離
  readonly isGround: boolean; // 通信基地か（網の起点になる）
}

/** 通信基地から前方に閉じて求めた、この時点で有効な中継点の集合。 */
export function activeRelays(
  relays: readonly CommRelay[],
  attractors: readonly Attractor[],
): readonly CommRelay[];

export function isInCommRange(
  pos: Vec3,
  activeRelays: readonly CommRelay[],
  ownRange: number,
  attractors: readonly Attractor[],
): boolean;
```

**中継は多段である。**中継点が有効であるのは、その中継点自身が通信基地であるか、または他の**有効な**中継点との見通しと距離を満たしているときだけである。通信網は基地から順に伸びていく。孤立した中継点は、どれほど強力であっても周囲の機体を圏内にしない。

- 有効な中継点の集合は、通信基地から出発して前方に閉じることで求める。設備の連鎖の到達可能性（§17）とまったく同じ形の閉包である。
- 機体が圏内であるとは、有効な中継点のいずれか1つとの見通しと距離を満たすことである。
- 中継点の数は多くないため、毎フレームではなく数秒ごとに求め直せば費用は問題にならない。通信圏の内外は秒の単位で変わるものであり、フレーム単位の精度を要さない。

**この規則により、通信衛星は「網として」配備することになる。**目標の軌道の傍に1つ置けば済むのではなく、基地からそこまで繋がる列を作る必要がある。月の裏側を圏内にするには、裏側を見る衛星と、その衛星を基地から見る衛星の両方が要る。**どこに何個置けば繋がるかを考えること自体が、配備の遊びになる。**

| 通信モジュール | 到達距離 | 質量の目安 |
|---|---|---|
| 小型 | 5,000 km | 20 kg |
| 中型 | 100,000 km | 120 kg |
| 大型 | 2,000,000 km | 800 kg |
| 深宇宙用 | 5 AU | 3,000 kg |

到達距離は、機体側と中継点側の小さいほうで決まる。小型の通信モジュールしか積んでいない機体は、どれほど強力な中継点の傍にいても 5,000 km までしか届かない。**これは単純化である。**実際の通信の到達距離は送受信双方のアンテナ利得の積で決まり、片側が強ければもう片側の弱さをある程度は補える。ここでは、積んだ通信モジュールの等級がそのまま届く距離になるという分かりやすさを取る。

### 13-3. 通信基地と通信衛星

**中継点には2種類ある。**

**通信基地** — 基地モジュールの1つであり、大型の通信設備を持つ。ゲーム開始時点で、**月面基地と近直線ハロー軌道の基地の2つ**がこれを持っている。

**通信衛星** — **専用のクラスを作らない。**通信モジュールと太陽電池と自動操縦装置を積んだ小型の機体を軌道に置くと、そこが中継点になる。設計も生産も配備も、他のあらゆる機体とまったく同じ手順で行う。

したがって通信網を広げる操作は、新しい仕組みを覚えることではなく、**すでに知っている操作の適用先が増えることである。**小さな機体を設計し、生産し、狙った軌道に投入する。それだけで圏が広がる。

### 13-4. 初期の通信圏と、その穴

月面基地と近直線ハロー軌道の基地の2点だけでは、通信圏には大きな穴が開く。

| 領域 | 状態 | 理由 |
|---|---|---|
| 月の裏側 | 圏外 | 月に遮られる |
| 地球低軌道 | ほぼ圏外 | 距離が遠く、地球に遮られる時間が長い |
| 地球の裏側 | 圏外 | 地球に遮られる |
| 近直線ハロー軌道の周辺 | 圏内 | 基地の傍である |
| 月面基地の周辺 | 圏内 | 基地の傍である |

**戦闘は、序盤は有人でしか行えない。**無人のブースターで弾薬を運ぶ運用（§9）を成立させるには、まずその領域に通信衛星を配備しなければならない。この順序が、進行に自然な段取りを与える。

### 13-5. 通信圏が狭いことの帰結 — 船団による攻勢

**圏外へ物を先回りさせられない。**無人の補給機や弾薬をあらかじめ目標の軌道へ投入しておく運用は、その軌道が圏内にあって初めて成立する。ゲーム開始時点の2点の中継点では、敵の出現する領域の大半が圏外である。

したがって序盤の戦闘は、**必要なものをすべて積んだ有人の船団を編成して出撃し、戦って帰る**という形になる。

- **船団の規模は、操縦できる人数で決まる。**有人機の数がそのまま同時に動かせる機体の数であり、無人機で頭数を水増しすることができない。
- **往復ぶんの推進剤と弾薬を最初から積んでいく。**補給を前もって置けないため、目標へ届く Δv ではなく、目標から帰る Δv までを1機の中に収める必要がある。これが機体設計に直接効き、序盤の機体は「戦闘力」より「往復できること」で形が決まる。
- 現地で消耗を読み違えれば、帰るための推進剤を撃ち尽くす。**引き際の判断が、そのまま設計の余裕の大小として現れる。**
- 圏外では基地からの遠隔操作も効かないため、**防衛も同じ制約を受ける。**離れた基地が襲われたとき、そこへ送れるのは有人の船団だけである。

通信衛星を配備して圏を広げると、この形が変わる。**無人の補給機を先行させ、弾薬と推進剤を目標の軌道に置いてから、身軽な戦闘機体で出る**運用に移行できる。船団方式から補給方式へのこの転換が、序盤から中盤への最も大きな段差である。

### 13-6. 圏外に出たときの挙動

圏外へ出た無人機は、**実行中の噴射を完遂したのち、計画の実行を止め、最後の指令を保持したまま漂流する。**

- **実行中の燃焼は完遂する。**噴射シーケンスは時刻で駆動するものであり、機上の計算機だけで最後までやり切れる（§13-1）。通信が途絶しても噴射だけは機上で完遂するのは、実在の宇宙機の運用と同じである。
- 未実行のマニューバノードは消えず、そのまま残る。
- 姿勢制御は最後に指定された姿勢を保つ。
- 圏内に戻れば、残っているノードから実行を再開する。**圏外にいる間に通過したノードは実行されない。**点火時刻の決定には、その時点の軌道を見て判断する処理が要るためである。

圏外に出ることそのものは失敗ではない。しかし、圏外にいる間に通過するはずだった噴射は行われないため、**機体はしばしば意図しない軌道に乗る。**通信圏の穴を通る計画を立てないことが、無人運用の設計の一部になる。

飛行中の通信パネルは、圏内か圏外か、最寄りの中継点、到達距離の余裕を表示し、**圏外に出た瞬間に通知を出す。**

## 14. 基地モジュール

基地モジュールを持つ機体（軌道基地・月面基地）が積む区画を、搭載要素として定義する。いずれも内装要素であり、`hull` エッジの内容積に収める。

**この節は性格の異なる2群を含む。**農場・生命維持装置・水タンクは資源の生産と消費に関わり、§15 以降の資源の層に直結する。ドック・コンテナ接合部・通信基地は機体の運用に関わり、§7〜§9 の多段とペイロードの側に属する。読む順序はどちらからでもよい。

**基地は武装を積める。**基地は `Vessel` であり、艦艇と同じ実体である。武器・弾薬庫・戦闘用シールド・放熱板を、艦艇とまったく同じ手順で搭載できる。エンジンを持たないことと、基地モジュールを持つことだけが艦艇との違いであり、戦闘に関わる搭載要素の扱いに違いはない。

**序盤の防衛は、これによって行う。**開始時点では通信圏が狭く、船団を遠くへ出せない（§13-5）。近直線ハロー軌道の基地は、そこへ来る敵を自分で迎え撃つ。**基地は移動しない戦闘艦艇として働く。**推進剤を消費せず、放熱板と電力に余裕があるため、同じ質量の艦艇より重い武装と厚いシールドを積める。動けないことが唯一かつ決定的な弱点である。

回転による疑似重力の区画はここに含まない。**回転する居住区画はテザー方式で実現し、第3巻が扱う。**剛体の腕で回す方式は、必要な半径が機体の寸法の上限を大きく超えるため採らない。

### 14-1. 農場

光・水・二酸化炭素を消費し、食料と酸素を生む。

**人1人を養うのに必要な栽培面積はおよそ40〜50平方メートルである。**この面積は、必要な熱量と、栽培可能な作物の面積あたり収量から決まる。

光は2つの方式から選ぶ。

| 方式 | 消費 | 制約 |
|---|---|---|
| 電照 | 栽培面積あたり 300〜400 W。人1人ぶんで 12〜20 kW | 電力さえあればどこでも成立する |
| 太陽光導入 | 導光と追尾の機構の電力のみ | 太陽から遠ざかるほど集光面積が要る。木星では地球の27倍 |

**電照農場は電力の要求が極めて大きい。**居住人数が増えるほど、基地の電力収支に占める農場の比重が上がる。太陽光導入は電力を食わない代わりに、集光機構が機体の外形と姿勢を制約する。

農場は生命維持の閉ループの一部を担う。二酸化炭素を吸って酸素を出すため、生命維持装置の消耗品の消費を減らす（§14-2）。

#### 廃熱 — 農場は栽培面積より放熱面積のほうが大きい

**電照農場が消費する電力は、すべて熱になる。**光は植物に吸収され、ごく一部が化学エネルギーとして固定される以外は熱に変わる。生命維持装置の 1.5〜2 kW も同様である。したがって**1人あたり 15〜22 kW を捨てなければならない。**

放熱板の実効性能は、軌道上で **50〜150 W/m²** である（国際宇宙ステーションはおよそ 1,700 m² の放熱面で 70〜90 kW を処理する）。1人あたり 20 kW を捨てるには **100〜150 m² の放熱面**が要る。

**栽培面積（1人 40〜50 m²）より、放熱板のほうが 2〜3 倍大きい。**軌道上の基地は、農場を作ろうとした瞬間から、農場そのものより大きな放熱板の板を並べることになる。これは設計上の最も強い制約の一つであり、かつ見た目にそのまま現れる。

**太陽光導入を選んでも、放熱の要求は減らない。**発電の損失は避けられるが、居住区画に入った光は結局同じだけ熱になる。太陽光導入が節約するのは発電側の電力だけであり、捨てるべき熱の量は変わらない。

放熱の要求は農場と生命維持装置の性能値に含める。

| 区画 | 電力 | 廃熱 | 要る放熱面（軌道上） |
|---|---|---|---|
| 農場（電照、1人分） | 12〜20 kW | 12〜20 kW | 80〜130 m² |
| 農場（太陽光導入、1人分） | 0.5 kW | 12〜20 kW | 80〜130 m² |
| 生命維持装置（1人分） | 1.5〜2 kW | 1.5〜2 kW | 10〜20 m² |

月面の永久影ではこの要求が大きく下がる（§18-3）。**大規模な農場は軌道上より月面に向く。**

### 14-2. 生命維持装置

二酸化炭素の除去、酸素の供給、水の再生、温度と湿度の管理を行う。収容人数に比例して電力と消耗品を消費する。

1人あたりの1日の収支はおおよそ次のとおりである。

| 項目 | 量 |
|---|---|
| 酸素の消費 | 0.84 kg |
| 二酸化炭素の排出 | 1.0 kg |
| 飲用水 | 2.5 kg |
| 生活用水（衛生を含む） | 20〜25 kg |
| 食料（乾燥質量） | 0.6 kg |

**閉ループ率が消耗品の補給量を決める。**水の再生だけを行う開ループでは酸素と食料を運び続けることになり、農場と組み合わせて酸素と食料を内部で作れば、補給は損失ぶんだけになる。

| 構成 | 閉ループ率 | 1人1日あたりの補給 |
|---|---|---|
| 生命維持装置のみ | 水 90%、酸素なし | 酸素 0.84 kg + 食料 0.6 kg + 水の損失 |
| 生命維持装置 + 農場 | 水 95%、酸素ほぼ閉 | 損失ぶんのみ |

電力は収容人数あたり 1.5〜2 kW である。これは農場の電照よりは小さいが、常時消費される。

### 14-3. 水タンク

水を貯蔵する。飲用・農場・電解の原料になる。

**水タンクは放射線の遮蔽として働く。**水は水素を多く含み、単位質量あたりの遮蔽性能が金属より高い。遮蔽の能力は放射線が通る経路の面密度（g/cm²）で決まり、水の密度は 1 g/cm³ であるから、面密度はそのまま**タンクの厚み（cm）**になる。

| 対象 | 必要な面密度 | 水の厚み |
|---|---|---|
| 太陽粒子線イベント | 10 g/cm² | 10 cm |
| 銀河宇宙線（実用的な低減） | 20〜30 g/cm² | 20〜30 cm |

**居住区画を水タンクで囲む配置に意味が生まれる。**ツリーの配置がそのまま遮蔽の配置になり、居住区画の外周に水タンクを置いた設計は、置かなかった設計より被曝が少ない。核熱推進の炉心に対する遮蔽（§19-3）も同じ仕組みで働き、炉心と居住区画の間に水タンクを挟む配置が有効になる。

遮蔽の評価は、居住区画の各方向について、そこに至る経路上の水タンクの厚みの和を求める形で行う。全方向を囲む必要はなく、**太陽粒子線に対しては1区画だけを厚く囲った退避区画で足りる**（イベントは数時間から数日で終わるため）。銀河宇宙線は常時降り注ぐため、居住区画そのものを囲う必要がある。

### 14-4. ドック

機体を係留し、設計と組み立てを行う区画である（§6）。収容数と、収容できる機体の最大寸法を持つ。

| 性能値 | 内容 |
|---|---|
| 収容数 | 同時に係留できる機体の数 |
| 最大寸法 | 収容できる機体の全長と最大断面半径。ドック空間の作業領域の枠になる |
| 電力 | 係留中の機体への給電と、組み立て作業の消費。1機あたりの上限を持つ |

係留の判定は、一定距離内かつ相対速度が小さいときに機体を格納するものとする。

生産（§5-1）で完成した機体は、その基地のドックに現れる。ドックの収容数を超える生産は、完成した時点で拒否されるのではなく、生産の開始時点で拒否する。

**ドックは拡張できる。**最大寸法は固定ではない。ドックモジュールをより大きなものに置き換えるか、増設することで、作れる機体の最大寸法が上がる。拡張には資源と設備が要り、他のあらゆるモジュールと同じ生産の対象である。したがって「大きな機体を作れるようにすること」自体が、資源を投じる先の1つになる。

**ドックの最大寸法は、作れる機体の最大寸法ではない。**拡張してもなお超える構造物は、複数のモジュールに分けて作り、軌道上で結合する（§6-9、§8）。

### 14-5. コンテナ接合部とコンテナ

**コンテナは規格化された貨物容器である。**

**コンテナは、ツリーを持たない `Vessel` として実装する。**第1巻の `Vessel` は、ツリーを持たない機体のために質量特性を直接与える経路をすでに持っており（敵艦がその1例目）、コンテナはその2例目になる。接触形状は単一のカプセルとし、能力（`hasCockpit` / `hasAutopilot` / `hasBaseModule` / `hasEngine` / `hasCommunication` / `isOperable`）はすべて偽である。予測軌道・マップ上の表示・保存形式は、他の `Vessel` とまったく同じ経路を通る。切り離されたコンテナが軌道上で他の物体と衝突することも、そのまま成立する。

```ts
export interface ContainerDef {
  readonly id: string;
  readonly size: 1;                 // 規格の単位数。定義されている規格は1種類だけである
  readonly volume: number;          // m³
  readonly maxMass: number;         // kg
  contents: ContainerContents;
}
export type ContainerContents =
  | { kind: 'resource'; resourceId: string; mass: number }
  | { kind: 'propellant'; propellantId: string; mass: number }
  | { kind: 'part'; partIds: readonly string[] }
  | { kind: 'empty' };
```

**規格は1種類だけである。**一辺2.0メートルの立方体、容積8 m³、最大積載10トンとする。液体用の別規格は用意しない。**この寸法は機体の直径の刻み（0.5 m）の整数倍であり、コンテナ接合部を持つ機体の断面と整合する。**規格が1つしかないため、どの接合部にもどのコンテナも付き、積み替えに適合の判定が要らない。

この比は 1,250 kg/m³ である。金属鉱石（2,000〜3,000 kg/m³）を積むと質量で先に頭打ちになり容積が半分以上余り、液体水素（71 kg/m³）を積むと 568 kg にしかならず質量枠の6%しか使えない。**極低温推進剤はコンテナでは運ばない。**専用のタンク機で運ぶ。

**コンテナ接合部**は外装要素であり、コンテナを1つ保持する。ノードの接続口またはトラス上に取り付ける。

- 規格が1種類であるため、接合部とコンテナの適合は常に成立する。1つの接合部が保持するコンテナは1つである。
- 保持したコンテナの質量と慣性は、機体の質量特性に加わる。接合部の位置がそのまま重心のずれになるため、**非対称なコンテナの積み方は推力軸のずれを生む。**
- 切り離すと、コンテナは独立した `Vessel` として軌道上に残る。小さな分離速度を与える。
- 回収は接合部への再結合による。一定距離内かつ相対速度が小さいときに保持する。

推進剤を積んだコンテナを接合部に保持している間、そのコンテナはタンクと同じく配管の接続先になる。接合部の付いたノードから配管を敷けば、コンテナの推進剤をエンジンへ送れる。切り離すと配管は切断される。

**ペイロード倉庫（§9）との違い。**ペイロード倉庫は機体内部の容積であり、外形に現れず、中身を放出することしかできない。コンテナは外付けで着脱でき、切り離した後も回収して再利用できる。**輸送にはコンテナが向く。**軌道上の基地へ資源を運ぶ運用では、満載のコンテナを接合部ごと切り離して基地のコンテナ接合部が受け取り、空のコンテナを持ち帰る形になる。

### 14-6. 通信基地

大型の通信設備を持つ区画である（§13-3）。基地をそのまま通信網の中継点にする。

| 性能値 | 内容 |
|---|---|
| 到達距離 | この中継点が届く距離。深宇宙用の通信モジュールと同等かそれ以上 |
| 電力 | 常時消費。到達距離の2乗に比例する |

ゲーム開始時点で、月面基地と近直線ハロー軌道の基地がこれを持つ。

### 15-2. 材料適合性 — 推進剤がタンクの金属を要求する

推進剤は、どんな容器にでも入るわけではない。**推進剤の選択は、その推進剤に耐える金属を持っているかどうかに縛られる。**

| 推進剤 | 使える材料 | 理由 |
|---|---|---|
| 液体水素 | **アルミ合金**、特定のステンレス | 水素脆化。ふつうの合金は水素が拡散して脆くなる。実機のタンクもアルミリチウム合金が主流である |
| 四酸化二窒素 | アルミ合金 | **チタンとは応力腐食割れを起こす。**チタン製タンクには入れられない |
| 過酸化水素 | 高純度アルミ、特定のステンレス | 多くの金属と接触すると分解する |
| 液体酸素・液体メタン・シラン | アルミ合金、ステンレス、チタン | 特段の制約はない |
| ヒドラジン | アルミ合金、ステンレス | タンク自体の制約は緩い。**触媒床にイリジウム（白金族）が要る** |

```ts
// src/game/economy/propellant-compatibility.ts
export interface TankMaterialRequirement {
  readonly propellantId: string;
  readonly allowedMaterials: readonly string[];  // 資源 id。いずれか1つで足りる
}
export const TANK_MATERIALS: readonly TankMaterialRequirement[];
```

この適合性は、資源の依存としてそのまま働く。**アルミは液体水素にも四酸化二窒素にも使える最も汎用な材料であり、月のレゴリスの電解から真っ先に得られる。**月面の基地はこの層の制約を最初から満たしている。

**ヒドラジン単推進剤スラスタだけは、月の資源だけでは作れない。**触媒床のイリジウムは白金族であり、白金族は敵のドロップかM型小惑星からしか得られない。姿勢制御と軌道修正に最も扱いやすいこの推進系は、戦闘を経るか、小惑星へ出るかしなければ手に入らない。

### 15-3. 産地

| 産地 | 得られる元素 | 手段 |
|---|---|---|
| **月レゴリス** | O, Si, Fe, Ti, Mg, Al | 溶融塩電解。酸素と金属の混合物が同時に得られる |
| **月レゴリス（加熱抽出）** | **He**, H, C, N（いずれも微量） | レゴリスを加熱し、太陽風起源の吸着ガスを追い出す。電力を大量に食い、産出は微々たるものである |
| **月のアパタイト** | **F, Cl, P**（Ca₅(PO₄)₃(F,Cl)） | 採掘と分離。**溶融塩電解の媒体となる塩化カルシウムの原料である** |
| **月南極の永久影** | H₂O（→ H, O） | 氷の採掘 |
| **月の KREEP 岩** | Th, U, 希土類, P | 精錬。産出量は少ない |
| **敵の残骸** | C, N, S, Cu, 白金族, 希土類 | 戦闘。地球低軌道に限らず、月周辺・遷移軌道・その他の領域でも得られる |
| **近地球小惑星（C型）** | H₂O, C, 有機物 | 採掘 |
| **近地球小惑星（M型）** | Fe, Ni, Cu, 白金族, 希土類 | 採掘 |
| **ケレス** | H₂O（大量）, 炭酸塩（C）, アンモニア塩（N） | 採掘。小惑星帯で最も水が豊富 |
| **火星** | CO₂ 大気（C, O）, 水氷, N₂ 大気（2.8%）, Ar 大気（2%） | 大気捕集と採掘 |
| **金星** | N₂ 大気（3.5%）, CO₂ 大気（96%）, 硫酸雲（S） | 大気捕集。着陸はしない |
| **木星大気** | H₂, **He**, ³He | 大気捕集。深い重力井戸からの脱出が課題 |
| **カリスト** | H₂O | 採掘。木星系で放射線が最も弱く、拠点に適する |
| **イオ** | S, SO₂ | 採掘。木星系で放射線が最も強い |
| **タイタン** | CH₄, C₂H₆（C, H）, N₂ 大気 | 採掘と大気捕集。炭素と窒素が事実上無尽蔵 |
| **エウロパ・ガニメデ** | H₂O | 採掘 |

**月には炭素と窒素が事実上ない。**これがこの進行全体の出発点にある制約である。レゴリスの加熱抽出で太陽風起源の炭素と窒素も微量に出るが、**農場を回すにも高分子を合成するにも桁が足りず、あくまで補助である。**月の資源だけで閉じる経路は存在するが、そこで得られる推進剤は性能が限られる。実用的な量の炭素と窒素を得るには、敵を倒すか、月を出るしかない。**農場の食料も炭素と窒素を要する**ため、月の資源だけで自立している間、居住人数は補給に縛られる。

**敵は地球低軌道に限らず出現する。**近直線ハロー軌道を含む月周辺でも、月と地球を結ぶ遷移軌道でも、その他の領域でも遭遇しうる。したがって敵のドロップは低軌道でしか得られないものではない。ただし**出現の頻度と敵の強さは領域によって異なり**、同じ資源を得るのに要る戦力も変わる。**基地そのものが襲われうる。**近直線ハロー軌道の基地は月から遠く、そこにあるすべて——ドック、生産設備、在庫——を失いうる以上、防衛は基地の設計の一部である。

**アパタイトの採掘は、レゴリスの電解より先に来る。**溶融塩電解には媒体となる溶融塩そのものが要り、その塩化カルシウムはアパタイトの塩素から作る。氷とレゴリスがあっても、塩がなければ金属は取り出せない。

**ヘリウムは月でも少量得られるが、大量には木星大気からしか得られない。**月のレゴリスには太陽風起源のヘリウムが吸着しており、濃度はレゴリス1トンあたり数グラムから数十グラムの桁である。加熱抽出設備で追い出せるが、**膨大な量のレゴリスを加熱するだけの電力を食い、それでいて産出は数機ぶんの加圧ガスにしかならない。**ヘリウム加圧とヘリウム冷ガスは、序盤では**限られた機体にだけ配る贅沢な選択肢**であり、木星大気に到達して初めて標準の手段になる。

### 15-4. 磁気トルカとフライホイール — 要る資源が違う

姿勢制御には磁気トルカが使える。機体の電磁石が周囲の磁場と作るトルクでフライホイールをアンロードするもので、**推進剤をまったく消費しない。**

**磁気トルカは導線を巻いたコイル（多くは鉄芯入り）であり、永久磁石を使わない。**希土類が要るのは**フライホイールの駆動モーター**のほうである。

| 要素 | 要る資源 | 得られる場所 |
|---|---|---|
| **磁気トルカ** | 導線（アルミまたは銅）＋ 鉄芯 | **アルミと鉄は月のレゴリスから得られる。月の資源だけで作れる。**銅を使えば同じ質量で磁気モーメントが大きくなるが、月にはほぼ無く、M型小惑星か敵のドロップが要る |
| **フライホイール** | 希土類（駆動モーターの永久磁石） | 月の KREEP 岩、敵のドロップ、M型小惑星 |

**この違いは進行の形を決める。**アルミ巻きの磁気トルカは月の資源だけで作れるため、低軌道での姿勢制御は最初から推進剤ゼロで成立する。一方、フライホイールは希土類を待つ。磁場のない月周辺で推進剤を使わずに姿勢を保つ手段は、希土類を手に入れるまで存在しない。

磁気トルカが働くのは磁場のある場所だけである。

| 活動領域 | 磁場 | 姿勢制御の性格 |
|---|---|---|
| 地球低軌道 | 強い | 磁気トルカが使え、アンローディングが事実上無料になる |
| 近直線ハロー軌道・月周辺 | ほぼ無い | フライホイールのアンロードにRCS推進剤を消費する |
| 惑星間・小惑星帯 | ほぼ無い | 同上 |
| 木星系 | 極めて強い | 磁気トルカが使える。ただし放射線帯が厳しい |

**低軌道での活動は姿勢制御が安価であり、月周辺へ出るとRCS推進剤の消費が効いてくる。**同じ機体でも、どこで運用するかによって推進剤の収支が変わる。磁気トルカは電力を消費し、トルクは小さく、磁場に平行な軸まわりのトルクは出せない（3軸のうち1軸が瞬間的に制御できない）。

## 16. 到達可能性

### 16-1. Δv が進行そのものである

どこへ行けるかは、機体が出せる Δv で決まる。Δv はツィオルコフスキーの式により、比推力と質量比で決まる。比推力は推進剤で決まり、推進剤は持っている元素で決まる。**したがって、資源の進行と到達可能性の進行は同じものである。**通貨がないため、この対応に抜け道はない。

### 16-2. Δv の表

代表的な区間の Δv を示す。単位は km/s である。右列は、大気の上層を掠めて減速する運用（大気制動）を使った場合の値であり、**熱シールドを積んでいることが条件である。**

| 区間 | Δv（推進のみ） | Δv（大気掠めを使う） |
|---|---|---|
| 月面 → 低月軌道 | 1.9 | — |
| 低月軌道 → 近直線ハロー軌道 | 0.7 | — |
| 月面 → 近直線ハロー軌道 | 2.7 | — |
| 近直線ハロー軌道 → 地球低軌道 | 3.2 | **0.7** |
| 地球低軌道 → 近直線ハロー軌道 | 3.4 | — |
| 地球低軌道 → 到達しやすい近地球小惑星 | 4.5 | — |
| 地球低軌道 → 一般の近地球小惑星 | 6.0 | — |
| 地球低軌道 → 火星周回 | 5.7 | **3.6** |
| 地球低軌道 → 金星周回 | 6.8 | **3.5** |
| 地球低軌道 → ケレス | 9.5 | — |
| 地球低軌道 → 木星系（カリスト） | 11.0 | **6.5** |
| カリスト → イオ | 3.5 | — |
| 地球低軌道 → タイタン | 12.0 | **7.5** |
| 木星大気の捕集 → 木星脱出 | 20.0 | — |

### 16-3. 大気掠めによる減速 — 熱シールドが炭素を要求する

**大気のある天体では、捕獲の Δv がほぼ不要になる。**地球・火星・金星・タイタン・木星がこれにあたる。双曲線軌道のまま大気の上層を通し、空力抵抗で減速して捕獲される。上の表の右列がその値であり、化学推進の到達範囲を1世代ぶん広げるほどの差になる。

**この運用に要るのが熱シールドである。**熱シールドは第1巻の搭載要素であり、アブレータを消耗して加熱率と動圧の閾値を引き上げる。制動の間、機体の前面は高温の衝撃層に晒される。アブレータは**炭素繊維複合材**で作るため、**大気掠めを使うには炭素が要る。**

| 天体 | 大気の性格 | 熱シールドの負担 |
|---|---|---|
| 火星 | 薄い | 軽い。1回の通過で捕獲できず、複数周にわたる |
| 地球 | 中程度 | 中。既存の突入加熱と動圧の実装がそのまま働く |
| タイタン | 厚く低重力 | 軽い。速度が小さいため加熱が穏やか |
| 金星 | 極めて厚い | 重い。突入速度が大きく、加熱が厳しい |
| 木星 | 極めて厚く高重力 | 極めて重い。捕獲は可能だが脱出は別問題である |

制動の1回ごとに、受けた総熱量に応じてアブレータが減る。使い切れば防護能力を失い、以後の突入では既定の閾値に戻る。**アブレータの補充には炭素が要る**ため、炭素の供給地から遠い運用では、大気掠めを何回使えるかが計画の一部になる。

熱シールドを積んでいない機体が大気掠めを試みた場合の挙動は、現在の再突入とまったく同じである。**新しい失敗の形は増えない。**

炭素を持たない段階では大気掠めは使えない。**つまり、月の資源だけで自立している間は、右列の値には手が届かない。**炭素を得ることは、推進剤の性能を上げるだけでなく、Δv の表そのものを書き換える。

### 16-4. 推進系ごとに届く範囲

質量比を現実的な範囲（乾燥質量に対する初期質量が3〜6倍）に置くと、推進系ごとの到達範囲はおおよそ次のようになる。

| 推進系 | 比推力 | 実用的な Δv | 届く範囲 |
|---|---|---|---|
| 固体・貯蔵性化学 | 230〜320 s | 3〜5 km/s | 月面と近直線ハロー軌道、地球低軌道 |
| 液体酸素／シラン | 265 s | 3〜5 km/s | 同上。月の資源だけで作れる |
| 極低温化学（メタン） | 370 s | 5〜7 km/s | 近地球小惑星、火星、金星 |
| 極低温化学（水素） | 450 s | 6〜8 km/s | 火星、金星。蒸発損失のため長期の航行には不利 |
| 核熱推進 | 900 s | 12〜16 km/s | ケレス、木星系 |
| 電気推進 | 3000 s | 30 km/s 以上 | 太陽系内のどこへでも。ただし推力が小さく、時間がかかる |
| 核融合推進 | 10⁴ s 以上 | 100 km/s 以上 | 木星の重力井戸からの脱出 |

## 17. 設備の連鎖

### 17-1. 進行を止める4つの制約

| 制約 | 内容 | 解消の手段 |
|---|---|---|
| **資源** | 必要な元素を持っていない | その元素のある場所へ行く、または敵から得る |
| **設備** | 変換する設備を持っていない | 設備の建設に必要な資源と電力を確保する |
| **電力** | 設備を動かす電力が足りない | 太陽電池を増やす。太陽から遠い場所では原子炉が要る |
| **到達可能性** | その場所へ行くだけの Δv が出せない | より比推力の高い推進系、多段化、または大気掠め |

**この4つは互いに絡み合っている。**遠くへ行くには高い比推力が要り、高い比推力の推進剤には特定の元素が要り、その元素は遠くにしかなく、そこへ行くには電力を生む原子炉が要り、原子炉の燃料もまた特定の場所にしかない。**通貨で迂回できる辺は1本もない。**

### 17-2. 設備の定義

設備は、電力を消費して入力資源を出力資源に変換する。**設備そのものの建設にも資源と電力が要る。**

```ts
// src/game/economy/facility.ts
export interface FacilityDef {
  readonly id: string;
  readonly name: string;
  readonly inputs: readonly { resourceId: string; rate: number }[];   // kg/s
  readonly outputs: readonly { resourceId: string; rate: number }[];  // kg/s
  readonly powerDraw: number;         // W
  readonly buildCost: readonly { resourceId: string; mass: number }[];
  readonly requiresFacility: readonly string[];  // これを作るのに要る別の設備
}
export const FACILITIES: readonly FacilityDef[];
```

`requiresFacility` は技術の前提ではなく、**物理的な前提**である。液化装置がなければ極低温タンクに詰められない、圧延機がなければ金属の塊を板にできない、という類の関係だけを表す。

### 17-3. 最初から持っている設備

月面基地は、地球から運ばれた最初の一組を持って始まる。**この一組だけが与えられ、以後のすべては自分で作る。**

| 設備 | 役割 |
|---|---|
| 太陽電池アレイ（永久日照の峰） | 発電（§18） |
| 送電網 | 峰から永久影の基地へ電力を送る（§18-1） |
| 氷採掘機 | 永久影から水を採る |
| アパタイト採掘機 | アパタイトから F・Cl・P を採る |

**最初の目標は、機体を作ることではなく、機体を作れる工場を作ることである。**

### 17-5. 電力が最初の壁になる

**溶融塩電解は極めて大きな電力を要する。**アルミの電解精錬は工業的に最も電力を食う工程の一つであり、月のレゴリスから金属と酸素を取り出す工程も同様である。

したがって進行の最初の段階は「電力を確保すること」になる。太陽電池を増やすにはケイ素が要り、ケイ素を得るには電解が要り、電解には電力が要る。**この循環は、最初の小さな設備から徐々に規模を拡大していく形でしか抜けられない。**

太陽から遠ざかると太陽光が弱くなる（木星では地球の27分の1）。外惑星で設備を動かすには原子炉が要る。原子炉の燃料は月の KREEP 岩か M型小惑星から得る。**農場の電照（§14-1）と重水素・ヘリウム3の同位体分離（§17-4）も同じ電力を奪い合う。**居住人数を増やすことと、核融合燃料を作ることは、同じ電力収支の上で競合する。

## 18. 月面の電力と放熱

月面基地は、南極の**永久影のクレーター**に作る。氷があるのはそこだけであり、放熱にも圧倒的に有利だからである。しかし永久影には**日射が一切ない。**

### 18-1. 発電は峰で行い、電力を送る

太陽電池は基地には置けない。**永久日照の峰**に建設し、送電網で永久影の基地へ送る。

- 峰は月の南極のクレーター縁にあり、日照率はおよそ 80〜90% である。完全な永久日照ではないため、影になる期間を越えるだけの蓄電が要る。
- 送電網は**導体としてアルミを消費する。**必要な導体の質量は、送る距離と電力に比例する。
- 損失は導体の質量に反比例する。細い線で送れば軽いが失われ、太い線で送れば重いが届く。**目安として、距離 10 km・送電 1 MW に対し、アルミ 20 トンで損失 5% である。**

```ts
// src/game/economy/power-grid.ts
export function gridConductorMass(distance: number, power: number, lossFraction: number): number;
export function gridLoss(distance: number, power: number, conductorMass: number): number;
```

**峰と基地の距離が、そのまま送電網に食われるアルミの量になる。**近い峰ほど価値が高く、遠い峰は同じ発電量に対して割高になる。

### 18-2. 峰の太陽電池は垂直に立てる

**峰では太陽が地平線の近くから横向きに差す。**極域だからである。太陽高度はおおむね 0〜2 度の範囲にとどまる。

したがって太陽電池パネルを地面に水平に敷くと、入射角がほぼ 90 度になり、ほとんど発電しない。**パネルは垂直に立てる。**

- 垂直に立てたパネルは、太陽高度が低いほど有利になる。極域は太陽電池の設置条件として例外的に良い。
- 追尾機構を持てば、**方位角の追尾だけで済む。**仰角はほぼ動かさなくてよい。1軸の追尾で、水平パネルの数倍の発電量が得られる。
- 立てたパネルは互いに影を落とすため、間隔を空けて並べる。設置面積あたりの発電量は、水平に敷いた場合より低くなる。

### 18-3. 永久影は巨大な熱溜めである

永久影のクレーター底は**およそ 40 K** である。太陽系で最も冷たい場所の一つであり、放熱には極めて有利である。

放熱量は `σ(T⁴ − T_sink⁴)` で決まる。放熱板を 300 K で運用するとき、40 K の背景は 300 K に対して**無視できる**（40⁴ / 300⁴ ≈ 0.03%）。加えて、月面では地面への伝導も使える。

| 環境 | 放熱板の実効性能 | 1人あたりの廃熱 20 kW に要る面積 |
|---|---|---|
| 地球低軌道 | 50〜150 W/m²（地球からの赤外線と日射を受ける） | 130〜400 m² |
| 惑星間空間 | 100〜150 W/m² | 130〜200 m² |
| **月の永久影** | **200〜400 W/m²** | **50〜100 m²** |

**永久影では、放熱面が栽培面積を下回る。**軌道上では農場の 2〜3 倍の放熱板が要るのに対し、永久影では農場より小さくて済む。

この差により、**大規模な農場と生産設備は、軌道上より月面のほうが向く。**軌道基地は少人数の中継点と造船所に、月面基地は人口と工業の中心になる。この役割分担は、遊びの都合ではなく熱力学から出てくる。

## 19. 推進の世代

### 19-1. 第1世代 — 貯蔵性化学推進

月の資源と敵のドロップだけで成立する。

| 推進剤 | 比推力 | 必要な元素 | 産地 |
|---|---|---|---|
| 固体（過塩素酸アンモニウム + HTPB + Al） | 265 s | Al, C, H, N, O, **Cl** | Al と Cl は月、C と N はドロップ |
| 液体酸素 / シラン | **265 s** | Si, H, O | **すべて月で得られる** |
| 四酸化二窒素 / モノメチルヒドラジン | 320 s | N, H, O, C。**タンクに Al** | N と C はドロップ |
| ヒドラジン単推進剤 | 230 s | N, H。**触媒床に白金族（Ir）** | ドロップまたはM型小惑星 |
| 窒素冷ガス | 70 s | N | ドロップ |
| ヘリウム冷ガス | 165 s | He | 月のレゴリスの加熱抽出（少量）、木星大気（大量） |

**液体酸素／シランは、月の資源だけで作れる唯一の液体推進剤である。**燃焼生成物の二酸化ケイ素が凝縮相であり、膨張過程で仕事に寄与しないため比推力は 265 秒にとどまる。さらに二酸化ケイ素がノズルスロートに堆積するため、**連続燃焼時間に上限がある。**性能は固体モーター並みであり、長い連続噴射はできない。

それでも、外部からの補給がまったくなくても月面と近直線ハロー軌道と地球低軌道の間を往復できる。**これがこの作品の自立の最低線である。**そして、より高性能な推進剤を求めて外へ出る動機でもある。

**冷ガススラスタの2つの選択肢は、この世代の両端にある。**窒素冷ガスは比推力 70 秒と低いが、窒素は敵のドロップで早く手に入る。ヘリウム冷ガスは 165 秒と大幅に高い。ヘリウムは月のレゴリスの加熱抽出で少量なら早くから採れるが、大量に得られるのは木星大気に届いてからである。ヘリウムを加圧ガスとして積んでいる機体は、それをそのまま冷ガスの推進剤にも使える。**少量のヘリウムをどの機体に積むかは、加圧と冷ガスの両方を一度に決める判断になる。**

### 19-2. 第2世代 — 極低温化学推進

水と炭素が要る。

| 推進剤 | 比推力 | 必要な元素 | 産地 |
|---|---|---|---|
| 液体酸素 / 液体水素 | 450 s | H, O。**タンクにアルミ合金** | 月の水氷 |
| 液体酸素 / 液体メタン | 370 s | C, H, O | C はドロップ、小惑星、火星、タイタン |

液体酸素／液体水素は月の水だけで作れる。水素の密度が低いため巨大なタンクが要り、蒸発損失があるため長期の航行には向かない。タンクはアルミ合金でよく、これは月のレゴリスの電解と製錬から真っ先に得られる金属である。**したがってこの推進剤は、月の資源だけで完全に閉じる。**液体酸素／液体メタンは密度が高く貯蔵しやすいが、炭素が要る。

**この世代で近地球小惑星と火星に届く。**小惑星からは水と炭素と白金族と希土類と銅が、火星からは炭素と窒素とアルゴンが得られる。**炭素と窒素の供給が敵のドロップから独立する**のが、この世代の最大の意味である。

そして炭素が手に入ることで、**炭素繊維複合材のアブレータが作れるようになる。**熱シールドが実用になり、大気掠めによる減速が使えるようになり、火星・金星・地球の捕獲に要る Δv が大きく下がる。同じ推進系のまま届く範囲が広がるのは、この世代だけの性質である。炭素はまた**農場を可能にする**ため、恒久的な居住が成立するのもこの世代である。

### 19-3. 第3世代 — 核熱推進

固体炉心の原子炉で水素を加熱して噴射する。比推力 900 秒、推力は化学推進に匹敵する。

- 燃料はウランまたはトリウム。月の KREEP 岩、または M型小惑星から得る。
- 作動流体は水素。核分裂の熱で加熱するだけなので、酸化剤を必要としない。**水さえあればどこでも補給できる。**
- 炉心は重く、乾燥質量が大きい。小型の機体には向かない。
- 放射線遮蔽が要る。乗員のいる区画との間に遮蔽材を置く必要があり、機体の形状が制約を受ける（遮蔽の影の中に居住区を置く配置）。**ツリーによる設計はこの制約を素直に表現でき、水タンク（§14-3）がそのまま遮蔽になる。**

**この世代でケレスと木星系に届く。**ケレスは水が豊富で、核熱推進の補給地として最適である。

### 19-4. 第4世代 — 電気推進

原子炉または大型太陽電池の電力で推進剤を電離・加速する。

| 方式 | 比推力 | 推力 | 推進剤 |
|---|---|---|---|
| ホールスラスタ | 1600 s | 中 | Xe, Ar, Kr |
| イオンエンジン | 3000〜4000 s | 小 | Xe |
| 磁気プラズマ推進 | 5000 s | 小 | Ar, H |

- 推進剤は火星の大気（アルゴン 2%）から、あるいは希ガスの捕集から得る。
- 磁気回路に希土類が要る。フライホイールの駆動モーターと同じ資源の上に載る。
- **推力が極めて小さい。**加速度は 10⁻⁴ m/s² の程度であり、大きな Δv を得るのに数か月から数年かかる。戦闘には使えない。
- 電力が要る。太陽電池は太陽から遠ざかるほど無力になるため、外惑星では原子炉が前提になる。

電気推進は**戦闘用ではなく輸送用**である。ゆっくりでよい大量の物資を運ぶ無人ブースターに積む。これは「戦闘は化学推進、輸送は電気推進」という役割の分化を生み、機体設計の目的が明確に分かれる。トラスにコンテナ接合部を並べた電気推進の無人輸送機が、この分化の典型である。**そしてそれは、通信網が届いている範囲でしか動かせない。**

### 19-5. 第5世代 — 核融合推進

重水素とヘリウム3の反応を用いる。比推力 10⁴ 秒以上。

- 重水素は水から分離する。ヘリウム3は木星の大気から捕集する（月のレゴリスにも太陽風起源のヘリウム3が含まれるが、濃度が極めて低く、大量には得られない）。
- **重水素とヘリウム3の反応は中性子をほとんど出さない**（副反応の重水素同士の反応を除く）。荷電粒子が主生成物であるため、磁場で直接噴射方向へ導ける。これが高い比推力の理由である。
- ヘリウム3の同位体分離には極めて大きな電力が要る。原子炉が前提になる。
- 木星の大気を捕集し、その重力井戸から脱出するには 20 km/s 級の Δv が要る。**核融合推進なしにはヘリウム3を持ち帰れず、ヘリウム3なしには核融合推進が作れない。**この循環は、最初の一回だけ核熱推進と電気推進を組み合わせた片道の大型機で破る。

この作品はすでに中性子線ビームを敵への有効な攻撃手段として構想している。核融合の実現は、推進だけでなく武装の世代も変える。

### 20-1. 戦域の広がり

**戦域は基地の周りから始まり、外へ広がる。**広がりの順序は Δv と通信圏の両方から決まる。

| 段階 | 戦域 | 前提 |
|---|---|---|
| 1 | 近直線ハロー軌道（基地の周り） | 基地自身が迎撃する |
| 2 | 他の月周回軌道 | 船団を出せる推進剤と、往復ぶんの余裕 |
| 3 | 静止軌道 | より大きな Δv。地球圏への進出 |
| 4 | 地球低軌道 | 通信衛星の配備、または往復ぶんを全積みした船団 |
| 5 | 地球-月 L1 | 中継点の配備が進んでいること |

**第1段階では、戦うのは基地である。**開始時点で通信圏は基地の周辺にしか及ばず、無人機を先行させられず、有人の船団も往復ぶんをすべて積まねばならない。この時点で確実に戦えるのは、燃料を使わず動かない基地だけである。基地は武装と戦闘用シールドを積み、そこへ来る敵を迎え撃つ（§14）。

近直線ハロー軌道の敵を掃討したのち、戦域は移動する艦艇によって外へ広がる。**第2段階から先は、どこまで出られるかが往復の Δv で決まり、どこまで無人化できるかが通信圏で決まる。**この2つが別々に伸びるため、「届くが無人では運用できない領域」と「圏内だが Δv が足りない領域」が同時に存在する。どちらを先に埋めるかがプレイヤーの判断になる。

### 20-2. 経路は一本ではない

**各段階は、前の段階で得た資源がなければ始まらない。**しかし段階を飛ばすことはできる。近地球小惑星から白金族と鉄が十分に得られれば、火星を経由せずに核燃料の精製へ進める。経路は一本ではない。

## 21. 段階的な実装計画

各段階は、それ単体で検証できる状態で区切る。順序の原則は次のとおりである。

- **資源・設備のデータ定義と生産可能性の判定（純関数）は依存がないので最初に置く。**
- **到達可能性の閉包の検証を早期に置く。**設備の連鎖が詰まらないことを、機体側の実装に入る前に確かめる。
- **分離（多段）は配管に依存しないので、機体側の先頭に置く。**実装が軽く、単体で価値が大きい（多段ロケットが飛ぶようになる）。
- **ドッキングも配管に依存しないので、分離の直後に置く。**分離と同じ運動量保存の計算を逆向きに使うものであり、続けて実装するのが最も安い。軌道上での結合はこの上に載る。
- **通信は自動操縦の前提なので、無人ブースターの運用より前に置く。**
- **ドック空間での設計は、設計データと生産が揃ってから置く。**作ったものをその場で生産できない設計の操作は、確かめようがない。

## 23. 技術的リスク

### 23-1. 設備の連鎖が詰まる

ある資源を得るのに必要な設備が、その資源自身を必要とする循環が生じると、進行が止まる。これは**到達可能性の閉包を求める問題であり、テストで機械的に検証できる。**

```ts
// tests/physics/resource-closure.test.ts
// 初期資源の集合から出発し、不動点に達するまで前方に閉じる
function reachableClosure(
  initial: ReadonlySet<string>,          // 資源 id
  initialFacilities: ReadonlySet<string>,// §17-3 の最初から持っている設備
  facilities: readonly FacilityDef[],
  deposits: readonly DepositDef[],
  reachableBodies: (owned: ReadonlySet<string>) => ReadonlySet<AttractorId>,
): ReadonlySet<string> {
  const owned = new Set(initial);
  const builtIds = new Set(initialFacilities);
  for (;;) {
    const before = owned.size + builtIds.size;
    // 1. 今の資源で建てられる設備を全て建てる
    for (const f of facilities) {
      if (!f.buildCost.every((c) => owned.has(c.resourceId))) continue;
      if (!f.requiresFacility.every((id) => builtIds.has(id))) continue;
      if (!f.inputs.every((i) => owned.has(i.resourceId))) continue;
      builtIds.add(f.id);
      for (const o of f.outputs) owned.add(o.resourceId);
    }
    // 2. 今の推進剤で届く天体の産地を全て採る
    for (const d of deposits) {
      if (!reachableBodies(owned).has(d.bodyId)) continue;
      owned.add(d.resourceId);
    }
    if (owned.size + builtIds.size === before) break;   // 不動点
  }
  return owned;
}
```

テストは、§17-3 の最初から持っている設備と、それが直ちに産出できる資源から始めてこの閉包を求め、**`RESOURCES` のすべての id が閉包に含まれることを確かめる。**含まれないものがあれば、その資源に至る経路が存在しないということであり、データの誤りである。

**設備そのものが生産の対象になったことで、この検証は設備の集合についても閉包を取る必要がある。**資源だけを追っていては、「資源はあるが、それを加工する工場を作る手立てがない」という詰まりを見逃す。上の実装が `builtIds` を不動点の判定に含めているのはそのためである。

`reachableBodies` は、その時点で持っている推進剤の最良の比推力と、現実的な質量比（3〜6）から Δv を求め、§16-2 の表と突き合わせて届く天体を返す。**炭素を持っているかどうかで大気掠めの可否が変わるため、この関数は所持資源に依存する。**閉包の反復のたびに再評価する。

### 23-2. 意図した循環と、それを破る質量比

木星大気のヘリウム3は、核融合推進なしには持ち帰れず、核融合推進はヘリウム3を必要とする（§19-5）。これは意図した循環であり、核熱推進と電気推進を組み合わせた片道の大型機で破る設計になっている。

**§23-1 の閉包の検証は、この経路を「破れる」と正しく判定しなければならない。**そのためには、核融合以外の推進で木星大気から脱出できる質量比が実際に存在することを、数値で確かめる必要がある。

```ts
// tests/physics/jupiter-escape.test.ts
const G0 = 9.80665;
const dv = (isp: number, massRatio: number) => isp * G0 * Math.log(massRatio);

// 第1段: 核熱推進（Isp 900 s）で大気圏から脱出速度へ
// 第2段: 電気推進（Isp 3000 s）で惑星間軌道へ
const stage1 = dv(900, 6);     // ≈ 15.8 km/s
const stage2 = dv(3000, 1.5);  // ≈ 11.9 km/s
assert(stage1 + stage2 >= 20_000);
```

第1段が核熱推進でなければならないのは、木星の大気圏内から脱出速度まで加速するのに電気推進の推力（10⁻⁴ m/s²）ではまったく足りないためである。逆に第2段が電気推進でよいのは、重力圏を出た後は時間をかけられるためである。**この役割分担そのものが、テストの構造として表れている。**

### 23-3. 計算層が DOM と THREE に依存してしまう

`tsconfig.test.json` の `lib` は `ES2022` のみであり、DOM も THREE も無い。`game/economy/`・`game/vessel/`・`game/comms/` の計算部分が表示側の型に触れていると、**書いたテストが最初からコンパイルできない。**

分離は設計の時点で決めておく必要があり、後から剥がすのは難しい。判定と計算の関数は、引数として素の数値・文字列・データ構造だけを取り、`THREE.Vector3` も `HTMLElement` も受け取らないこと。ドック空間の表示は、その結果を受け取って描くだけの層とする。

### 23-4. 分離後の状態の再構成

分離はツリー・質量・重心・慣性テンソル・推進剤残量・流路のすべてを変える。これらを一箇所で一括して再計算し、どれか一つだけが古い値のまま残ることのないようにする。分離直後の接触判定の無効化も、この再構成と同じ時点で行う。コンテナの切り離しと回収、軌道上での結合（§6-9）も同じ経路を通す。

### 23-5. 段を跨ぐ燃焼の分割

分割したノードは、段の分離と次の段の点火を挟む。1つ目の燃焼終了時刻・分離時刻・2つ目の点火時刻の3つが、点火あたりの推進剤損失を含めて整合している必要がある。分割の提案を受け入れた時点で3つをまとめて生成し、後から片方だけを編集できないようにする。

### 23-6. 自動敷設の安定性

設計を変更するたびに自動敷設をやり直すため、無関係な編集で配管が別の経路に移ると、プレイヤーには不可解に見える。最短経路が同距離で複数ある場合の順序を、エッジIDによる決定的な規則で固定する。

### 23-7. 手動の上書きと設計変更の衝突

手動で敷いた区間のエッジが削除されたり、種別が変わったりすると、上書きが宙に浮く。参照先を失った上書きは破棄し、破棄したことを診断に出す。黙って消すと、プレイヤーは自分の設定が効いていない理由を追えない。

### 23-8. 配管の探索コスト

流路の解決は、タンクとエンジンの組ごとにグラフ上の経路を探すことになる。エッジ数に対して線形になるよう、推進剤の種別ごとに連結成分を1度だけ求め、タンクとエンジンが同じ連結成分に属するかで判定する方式にする。

### 23-9. クロスフィードと分離順の整合

分離機構を跨ぐ配管は、分離順によっては、まだ燃焼中のエンジンへの供給を断つ。分離順の並べ替えの時点で、その順序で断たれる供給を検出して警告する。

### 23-10. 推力軸のずれによる制御不能

側面に非対称にブースターを束ねると、推力軸が重心を大きく外れる。トラスに外装要素を非対称に並べた場合や、コンテナを非対称に積んだ場合も同じことが起きる。ドック空間での警告と、ジンバル補償の両方が必要である。補償しきれない設計は生産を拒否する。

### 23-11. ドック空間のカメラが機体に埋まる

ドックの内側にカメラを入れるため、組み立て中の機体の内部にカメラが入り込む状態が起きる。外皮の内側から見た表示、断面の編集時の視点移動、大きな機体を組んでいるときの全体把握の3つが、いずれも扱いを要する。外皮を選択的に半透明にする表示と、機体全体を収める視点へ戻す操作を用意する。

### 23-12. 通信圏の穴が分かりにくい

圏内と圏外の境界は、天体の影と距離の球面が交わる複雑な形をしており、**軌道上のどこで切れるかが直感に反する。**マップ上に通信圏を可視化し、計画した軌道が圏外を通る区間を線の色で示す必要がある。圏外に出た瞬間の通知だけでは、その時点で手遅れになっている。

### 23-13. 送電網の距離が見えにくい

峰の太陽電池と永久影の基地の距離は、月面の地形の上の距離である。**月面の地形そのものは第3巻の対象であり、それが実装されるまで距離は抽象的な数値でしかない。**この段階では、基地の設定値として距離を持ち、地形が入った時点で実際の位置から求める形へ移す。移行で送電網の構成が壊れないように、保存形式は距離ではなく峰の識別子を持つこと。

### 23-14. 保存形式の互換性

設計データ・配管の上書き・基地の在庫・設備・送電網・コンテナの内容が保存形式に加わる。読み替え不能な保存データは明示的に拒否し、破損した機体を生成しないこと。

### 23-15. 進行が長すぎる

月面から核融合までの道のりは長い。各段階で何が新しくできるようになるかが明確でないと、進行が作業に感じられる。段階ごとに「新しく届く場所」が増えることを、地図の上で見えるようにする必要がある。**大気掠めの解禁（炭素の入手）は Δv の表そのものを書き換えるため、地図上の変化が最も大きい瞬間になる。**ここを見せ場として扱う。**通信圏の拡大も同じ性質を持つ**ため、圏の可視化はそのまま進行の実感になる。

### 23-16. 資源の種類が多すぎる

20種を超える元素と、そこから作られる推進剤・構造材・アブレータ・食料を合わせると、在庫の一覧が長くなる。用途ごとにまとめて表示し、使わないものは折り畳む必要がある。設備の一覧も同じ問題を持つため、在庫と設備は同じ分類でまとめる。

### 23-17. 電気推進の時間スケール

加速度が 10⁻⁴ m/s² の程度であるため、意味のある Δv を得るのに数か月かかる。この作品は時間加速を持つため成立するが、**時間加速の上限（131072倍）でも数分の実時間がかかる。**電気推進の機体は計画に任せて放置し、他の機体を操作している間に進む、という運用になる。これが成立するかは、複数機体の同時運用の使い勝手と、その航路が通信圏に収まっているかに依存する。

### 23-18. 磁気トルカの領域依存が分かりにくい

低軌道では姿勢制御が無料であり、月周辺では推進剤を消費する。**この差は、切り替わった瞬間には見えない。**月へ向かった機体の推進剤が思ったより速く減る、という形でしか現れない。磁気トルカが働いているかどうかを HUD に常時表示し、働かなくなった瞬間に通知を出す必要がある。

### 23-19. UIの総量

ドック空間は4つの操作モードと右レールの常設表示を持ち、飛行中に段・ペイロード・通信の3つのパネルを加える。基地ビューにも生産・在庫・設備・ドックが並ぶ。既存のパネルへ統合できないかを追加のたびに確認し、置き場の規約に従うこと。
