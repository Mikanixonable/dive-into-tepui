# 第11版 組立の不具合と設計の是正計画

作成日 2026-08-20。組立ウィンドウで報告された3件の不具合を調べ、その場しのぎではない直し方を
決める。あわせて、資源から船・貨物・人工衛星を作ってドックへ格納するまでの経路を追って見つけた
不具合と、組立まわりの設計の不備を記録する。

# 第1部 報告された3件と、その直し方

## 根にあるもの — 「編集を拒む門」と「設計の出来」が1つの真偽値に潰れている

3件のうち最も重い1件目は、単体の不具合ではなく**検証の層が混ざっていること**から出ている。
組立まわりには本来3つの別々の問いがある:

| 問い | 何を見るか | いつ答えるべきか |
|---|---|---|
| **構造として組み上がるか** | ノード位置とエッジ長の整合、0.5m 量子化、ポートの排他 | 編集のたび |
| **実機の一貫性を壊さないか** | 基地のドック口が収容中の艦を下回らないか、基地モジュールが1つか | 編集のたび・確定時 |
| **設計として成り立つか(飛べるか)** | 推力軸、電力・熱の予算、加圧、寸法・質量の上限 | 表示するだけ |

実装ではこの3つが `WorkbenchValidation.valid` という**1つの真偽値**へ潰されている。
`BlueprintIssue.severity === 'error'` は「この設計は飛べない」の意味なのに、
「この編集を許してはならない」として読まれている。**この取り違えが1件目の直接の原因**であり、
3件目・2件目にも同じ形の混同(責務の置き場所の誤り)がある。

## 1. 部材が配置されない — 検証の層を分ける

### 症状と原因

緑のゴーストが出た状態でクリックしても部材が置かれず、undo 履歴にも残らない。実測:

```
memberAdditionAt accepted: true   []
crewedAssembly blueprint error: 加圧式のエンジンですが、加圧ガスタンクも自己加圧の条件もありません
applyAssemblyEdit valid: false    [ '加圧式の…' ]
canUndo: false
```

`DockWorkbenchSession.applyAssemblyEdit`([dock-workbench.ts:188-194](src/game/vessel/dock-workbench.ts#L188-L194))が
編集の適用後にセッション全体を `validate()` し、通らなければ `restore(before)` で巻き戻す。その
`validate()` は `targetValidation`([docking.ts:826-835](src/game/docking.ts#L826-L835))を経て
`assemblyError` → `validateBlueprint` を丸ごと走らせる。**既定設計は編集の前から通らない**ので、
編集の内容と無関係に必ず巻き戻る。

**部品の取り付けだけが効いていたのは、そちらが `mutate()` という検証も巻き戻しもしない別経路を
通っているため**([dock-workbench.ts](src/game/vessel/dock-workbench.ts))。同じセッションの
同じ種類の操作が、2本の別々の経路を通っているのが混乱の元になっている。

さらに `base-assembly-validation.ts` は冒頭のコメントで「一般のツリー・断面の検査は共有の
assembly editor に置き、作業台が基地にだけ弱い模型を与えてしまわないようにする」と述べ、意図して
`validateBlueprint: false` を渡している。**その意図を `targetValidation` が上書きしている** ——
docking.ts の内部で矛盾している。

### 直し方

**巻き戻しの仕組みそのものは正しい**(ドック口を減らして収容中の艦が居場所を失う編集は拒むべき)。
誤っているのは**何を拒む理由とみなすか**。

1. `WorkbenchTargetValidation` を、真偽値1本から**2つの並び**へ分ける。
   - `blocking: readonly string[]` — 適用すると実機の一貫性が壊れるもの。これだけが編集と確定を拒む。
   - `issues: readonly BlueprintIssue[]` — 設計の出来。`severity` を保ったまま持ち回り、**表示だけ**する。
   - `valid` は `blocking.length === 0` の導出値にする(呼び出し側の分岐はそのまま動く)。
2. `docking.ts` の `targetValidation` から `assemblyError` を外す。基地は
   `validateBaseAssembly` の**基地固有の項目だけ**を `blocking` に、`validateAssembly` の構造の
   error も `blocking` に入れる。`validateBlueprint` の結果は `issues` へ回す。
3. `applyTargetAssembly`(確定)も同じ区別に揃える。**飛べない船を組めること自体は正しい** ——
   飛べないだけであって、世界の一貫性は壊れない。
4. 部品の取り付けが通っている `mutate()` 経路を `applyAssemblyEdit` へ寄せ、**編集の経路を1本にする**。
   `AssemblyEditResult` を返す編集も、在庫を動かす編集も、同じ門を通るようにする。
5. `AssemblyPanel.syncErrors` を、`blocking`(赤)と `issues`(severity 別)に分けて出す形にする。
   いま検証欄は文字列の平坦な列で、severity を捨てている。

これで**既定設計のままでも編集と確定が通る**ようになり、「加圧ガスタンクが無い」は
**警告として画面に出続ける**(消えるのではなく、直すべきものとして見える)。

### 併せて直すべき、模型の穴

- **既定設計に加圧ガスタンクが無い。** `pressurant_tank` は部品の種別・既定値・建造費・内容積の
  係数・質量の扱いがすべて揃っているのに、**それを積んだ設計が `src/` に1つも無い**。
  有人艦・軌道基地とも `pressure_fed` × 四酸化二窒素(自己加圧ではない)なので、模型としては
  検証の指摘が正しく、設計の側が欠けている。積むのが正しい直し方(`tuneActuators` が質量から
  推力・トルクを引き直すので、HUD の数値は自動で追従する。`vessel-parts.test.ts` /
  `mass-properties.test.ts` の乾燥質量の固定値は更新が要る)。
- **基地に艦の寸法・質量上限が課されている。** `DEFAULT_BLUEPRINT_LIMITS`(2000 t / 120 m)は
  艦の上限であって、3000 t・145 m の軌道基地には元から合わない。`validateBlueprint` は既に
  `limits` を引数に取るので、**対象の種別ごとに上限を渡す**だけで済む。

上の 1〜5 が入れば、この2つは「通らなくする」ためではなく「模型を正す」ために直すことになる。

### 影響範囲

`dock-workbench.ts` / `docking.ts` / `assembly-panel.ts` / `base-assembly-validation.ts` と、
`dock-workbench.test.ts`(巻き戻しを固定している試験1件の期待値)。

## 2. 下書きを削除できない — 下書きの持ち主を1つにする

### 症状と原因

`drafts.delete` は `buildDraft` の中にしかない([docking.ts:752](src/game/docking.ts#L752))。
削除の入口が無く、`endAssembly` も `drafts` に触れないので、**建造する以外に消えず、セッションを
閉じても `Docking` に残る**(次に開くとタブに並んだまま)。

根にあるのは**二重帳簿**。`createDraft` は同じ構成を2箇所へ入れている:

```ts
this.drafts.set(id, draft);                              // Docking 側
this.assembly?.session.createNewVesselDraft(id, assembly); // セッション側
```

`applyTargetAssembly` はセッション側の構成を `Docking` 側へ写し戻している。
**下書きのデータの持ち主が2人居る**のが、寿命も削除も決まらない理由。

### 直し方

**下書きのデータはセッションが唯一の持ち主にする。** `DockWorkbenchSession` は既に
`new-vessel-draft` 種別の対象を持っているので、器は在る。

1. `DraftEntry` から `assembly` を落とし、`Docking` が持つのは **THREE の描画の写し**
   (`render`)と**倉庫由来の部品の id**(`ownedPartIds`)だけにする。構成はセッションから読む。
2. `DockWorkbenchSession.removeTarget(id)` を足す(`new-vessel-draft` 種別だけ受け付ける ——
   基地や格納艦は作業台が消してよいものではない)。undo 履歴に乗るので元に戻せる。
3. `AssemblyPanel` の対象タブに、下書きのときだけ削除ボタンを出す。
4. **取消でセッションごと捨てれば下書きも消える。**現状の持ち越しは意図されたものではなく、
   二重帳簿の副作用として残っていたもの。

### 影響範囲

`dock-workbench.ts` / `docking.ts` / `assembly-panel.ts`。

## 3. 下書きが基地から 360 m 離れる — 建造後と同じ場所に置く

### 症状と原因

`targetPose` が下書きの位置を `base.state.r + 姿勢回転(0, 0, offset)` で決めており
([docking.ts:533-535](src/game/docking.ts#L533-L535))、`offset` は
`DRAFT_OFFSET_BASE = 360` m、2つ目以降は +30 m ずつ([docking.ts:49-50](src/game/docking.ts#L49-L50))。
基地本体が全長 145 m なので、その外側の何も無い一点に浮かぶ。ドック口(`getSlotWorldPos`)は
**建造が成功して実艦になった時点で初めて使われる**。

### 直し方

**下書きを作る時点で空きドック枠を1つ確保し、そこに置く。**

1. `createDraft` で `getAvailableSlotIndex()` を引き、**空きが無ければ下書きの作成そのものを断る**
   (現状は建造の瞬間まで待って断る。作れないものを作らせない方が正しい)。
2. `DraftEntry` に確保した `slotIndex` を持たせ、`targetPose` / `syncDraftRenders` はドック口の
   位置と法線から姿勢を組む —— **格納艦と同じ式**([docking.ts:540-544](src/game/docking.ts#L540-L544))
   を使い、下書きだけの別式を持たない。
3. `buildDraft` は確保済みの枠へ入れる(枠探しを繰り返さない)。
4. `DRAFT_OFFSET_BASE` / `DRAFT_OFFSET_STEP` / `draftOffset` を消す。

これで**下書きの見え方と建造後の置かれ方が一致する**。「どこに建つのか」が組み立てている最中に
見えるようになる。空き枠の確保は 2 の削除と対になる(下書きを消せば枠が戻る)。

### 影響範囲

`docking.ts` のみ。

## 着手の順序

**1 → 3 → 2。** 1 が通らないと他を直しても体験は変わらない(何をしても巻き戻る)。
3 は 1 と独立に効く。2 は 3 の枠の確保と対になるので最後。

# 第2部 資源から完成品までの経路で見つけた不具合

「資源 → 部品生産 → 組立 → 建造・格納 → 確定 → 発進」を通しで追って見つけたもの。
第1部の3件と既知の7件(`第11版_実装中の決定事項.md`)は除く。**いずれもコードで裏を取った。**

## 4. 「建造して格納」がセッションの編集を丸ごと無視する — 貨物も人工衛星も作れない

**症状**: 下書きに部品を取り付け、部材を伸ばし、断面を編集してから「建造して格納」を押しても、
実際に組み上がるのは**常に手つかずの既定の有人艦**。編集は1つも反映されない。
**このUIから既定の有人艦以外を建造することは現状できない** —— 貨物も人工衛星も作れない。

**場所**: [docking.ts:740](src/game/docking.ts#L740) / [docking.ts:759-761](src/game/docking.ts#L759-L761)

**原因**: 第1部 §2 で挙げた**二重帳簿**の帰結。`DockWorkbenchSession.addTarget` は
`cloneTarget(normalized)` で**独立した複製**を積むので、セッション中の編集はすべてその複製に
当たる。`DraftEntry.assembly` が書き換わるのは [docking.ts:689](src/game/docking.ts#L689) の
1箇所だけで、そこへ到達する呼び出し元は `commitAssembly()` のみ。**`buildDraft` はセッションを
一切参照せず** `draft.assembly`(= 手つかずの `crewedAssembly`)を `createBlueprint` へ渡す。

「先に確定を押す」経路も塞がっている —— 第1部 §1 の巻き戻しにより編集自体が残らない。
**どちらの順でも、編集した設計は建造できない。**

**併発する2件**(同じ箇所):
- **二重課金**: `draft.ownedPartIds` は `commitAssembly` のループでしか埋まらない
  ([docking.ts:366-370](src/game/docking.ts#L366-L370))ので、`buildDraft` を直接押す経路では
  常に空。倉庫から取り付けた部品は生産時と建造時の2回課金される。
- **検証の素通し**: `buildDraft` は `assemblyError` を一度も呼ばずに `new Vessel(...)` する。
  `commitDockedAssembly` / `commitBaseAssembly` が必ず通す構造検証を経由しない。

**確度**: 確実。`draft.assembly` への代入箇所とその呼び出し元をコード上で機械的に確認した。

**直し方**: 第1部 §2 の「下書きのデータの持ち主をセッション1つにする」でそのまま消える。
持ち主が1人なら、`buildDraft` が読む構成と編集した構成が同じものになる。
`ownedPartIds` も、倉庫から出た時点(`workbench.drop`)で記録すれば確定に依存しなくなる。

## 5. 「発進」が `dockedVessels` から二重に取り除き、無関係な格納艦が消える

**症状**: ドックに2隻以上あるとき、末尾以外の艦を発進させると、その艦は正しく出るが
**別のもう1隻の台帳だけが消える**(メッシュと `Vessel` は残ったまま一覧とドック空き数から外れ、
実体と食い違う)。

**場所**: [base-operations-window.ts:654-663](src/game/hud/base-operations-window.ts#L654-L663) と
[docking.ts:786-791](src/game/docking.ts#L786-L791)

**原因**: `Docking.launch` が自分で `findIndex` → `splice` して発進艦を取り除いたあと、
呼び出し元の `handleLaunch` が**発進前の `index` でもう一度 `splice(index, 1)`** する。
配列は既に1つ短いので、後ろにあった別の艦が繰り上がってその位置で消される。
発進艦が末尾だったときだけ2回目が範囲外になり、無害に見える。

**確度**: 確実。

**直し方**: 台帳から外すのは `Docking.launch` の責務(発進の一部)。**呼び出し元の `splice` を
消す**。`handleLaunch` は `refresh()` だけを行う。

## 6. 貨物を発進させると、操作できないまま宇宙へ出る

**症状**: コア部品(コックピット / 自動操縦装置)を持たない貨物を建造・格納すると、「発進」は
常に押せる。押すと実際にドックから射出されるが、`ActiveVesselController.set()` は貨物を拒むので
どのUIからも操作対象にできない。

**場所**: [docking.ts:809-813](src/game/docking.ts#L809-L813) /
[base-operations-window.ts:336-340](src/game/hud/base-operations-window.ts#L336-L340)

**原因**: `launch` は `activeVessels.set(ship)` の成否を見ない。`set()` は貨物なら hint を出して
黙って `return` するだけなので、**「操作できない」という判断が「発進を止める」判断として使われて
いない。** 発進ボタン自体にもコア部品の有無の判定が無い。

**確度**: 「チェックが無く、拒否を無視して `addVessel` まで進む」ことは確実。
「以後どの手段でも回収できない」は**推測** —— 他の艦による捕獲経路(`canCapture`)まで追い切って
いない。ヘッドレス実行で貨物を発進させ、回収手段が無いことを確かめれば確定する。

**直し方**: `set()` が真偽値を返すようにするのが素直だが、それでは**発進してから拒まれる**。
発進ボタンの側で `hasCorePart` を見て**押せなくする**(理由をラベルに出す)のが正しい。
貨物を意図的に軌道へ置く用途は将来あり得るので、発進そのものを禁じるのではなく、
「操作対象にできないが出すか」を明示する形が望ましい。

# 第3部 組立まわりの設計の不備

不具合ではなく、**設計として直すべき形**。重要度順。

## 7. 「編集中の設計は部分的である」という規則が、呼び出し側の任意引数に委ねられている

**最も重い設計上の不備。第1部 §1 と同じ混同の、もう一段下の層での現れ。**

`AssemblyEditorOptions.validateBlueprint` は**既定が `true`**
([assembly-editor.ts:55-61](src/game/vessel/assembly-editor.ts#L55-L61))。
ドラッグ経路と部材追加は、コメントで理由を述べたうえで `{ validateBlueprint: false }` を
**明示的に**渡している([assembly-drag-controller.ts:209-215](src/game/vessel/assembly-drag-controller.ts#L209-L215)、
[member.ts:88](src/game/vessel/member.ts#L88))。ところが組立パネルの
**ノード削除・エッジ削除・断面編集だけが渡し忘れている**
([assembly-panel.ts:524](src/game/hud/assembly-panel.ts#L524)、
[assembly-panel.ts:536](src/game/hud/assembly-panel.ts#L536))。

**実害**: パネルの「選択を削除」と断面編集は、`assembly-editor` の段階で `accepted: false` になり、
**第1部 §1 の巻き戻しに到達する前に失敗している。**つまりこの2つは**Fix 1 を入れても開通しない** ——
独立した2つ目の原因を持つ。

**あるべき形**: 「セッション中の編集は部分設計として扱う」は**1つの設計判断**であって、呼び出しの
たびに思い出すべき引数ではない。`DockWorkbenchSession` / `DockWorkbenchController` を経由する
編集は常に部分設計として扱い、**完成設計としての検査は確定の1点だけで課す**。そうすれば
渡し忘れる余地が消える。第1部 §1 の「編集の経路を1本にする」と同じ方向で、同時に直すのが自然。

## 8. 「接続口が塞がっているか」が3箇所に独立して書かれている

`occupiedPorts`([assembly-editor.ts:534-546](src/game/vessel/assembly-editor.ts#L534-L546))は
まさにこの規則を1箇所へまとめるために export されており、`mount-candidates.ts` と
`validateNewEdge` は正しくそれを使っている。にもかかわらず:

- 同じファイルの `validateMount`([assembly-editor.ts:553-567](src/game/vessel/assembly-editor.ts#L553-L567))が、
  エッジ側を `tree.edges.some(...)`、部品側を手書きのループで**同じ判定を書き直している**
- `blueprint-validation.ts` の `checkPortExclusivity` が、`Map` を2つ組んで**また同じ規則を判定している**

ポートの種別が増えたときに、3箇所のうち1つを直し忘れれば黙って食い違う。

**あるべき形**: `occupiedPorts` に `ignoredEdgeId` と対になる `ignoredPlacementId` を足し、
`validateMount` はそれを引いて `has` を見るだけにする。`checkPortExclusivity` も同じ集合を使い、
**違うのはエラー文言だけ**という形に揃える。

## 9. 「掴んだ元」が3つの独立したフィールドで表されている

`DragState` は `sourceTargetId: string | null` / `sourceTargetKind: WorkbenchTargetKind | null` /
`sourceInventory: boolean` の3本で「棚から掴んだのか、機体から掴み上げたのか」を表している
([dock-workbench-controller.ts:27-33](src/game/vessel/dock-workbench-controller.ts#L27-L33))。
`sourceInventory === true` なら `sourceTargetId` は必ず `null`、という不変条件は呼出規約として
在るだけで、型は `{ sourceTargetId: '艦体X', sourceInventory: true }` を許してしまう。
分岐は `drag.sourceTargetId && !drag.sourceInventory` として**都度組み立て直されている**。

`/refactor-fixed` の「あるものが『無い』ことは、その値自身の `null` だけで表す。代役も、別の真偽値も
立てない」に照らして、これは真偽値と id が同じ選言を2つに割ってしまっている形。

**あるべき形**: 判別共用体1つにする。
```ts
type DragSource =
  | { readonly kind: 'inventory' }
  | { readonly kind: 'target'; readonly id: string; readonly targetKind: WorkbenchTargetKind };
```

# 実装後の記録

## 実装中に判断したこと

- **§7 の「セッションを通る編集は部分設計」は `DockWorkbenchController` のメソッドに置いた**
  (`removeNode`/`removeEdge`/`editSection`)。`AssemblyEditorOptions.validateBlueprint` の既定値を
  `false` へ変える案は採らなかった —— 編集の途中かどうかは編集器ではなく**セッションの側の事情**で
  あり、編集器を単体で使う呼び出し(ドラッグ中の可否判定)は今のまま明示的に渡すのが正しい。
- **`portOwners` は `assembly-editor.ts` ではなく `port-occupancy.ts` に置いた。** 編集器に置くと
  `blueprint-validation.ts` が編集器を import することになり、既存の逆向きの import と循環する。
  接続口を誰が使っているかは編集にも検証にも属さない下位の事実なので、どちらでもない位置に出した。
- **下書きの作成・削除は undo 履歴に乗る**(`addTarget`/`removeTarget` が `mutate` を通る)一方、
  表示の写しとドック枠は乗らない。取り消すと両者がずれるので、`reconcileDrafts`(update)で
  顔ぶれを合わせ、`syncDraftRenders`(sync)がその結果を THREE へ反映する形にした。
  **副産物として、下書きだけは編集の結果が確定を待たずに見えるようになった** —— 他の対象は
  第11版_実装中の決定事項.md §3 の制約のまま。
- **建造時に倉庫の部品を基地の在庫から引く**(`consumeMountedInventory`)。確定まで待つと、
  建造してから取消したときに同じ部品が実機と在庫の両方に残る。

## 直さずに残したこと

**「ポートの排他」の分類が、第1部の表と実装で食い違っている。** 表は「構造として組み上がるか」
(=拒む理由)に数えているが、実装の `checkPortExclusivity` は `validateBlueprint` の中にあり、
分離後は `issues`(拒まない)側へ入る。**現状これが問題を起こす編集経路は無い** ——
`validateMount` と `validateNewEdge` が、競合を作る編集そのものを先に拒むため。
`checkPortExclusivity` は「編集器を通らずに作られた設計」に対する最後の網であり、そこでは
拒む/拒まないの区別に意味が無い(既に出来上がっている)。表の側が実装より粗い、という記録に留める。

## 併せて残る既知の制約

- 既定の有人艦・軌道基地とも `validateBlueprint` の error(加圧ガスタンクが無い)を抱えたまま。
  **組立は通るようになったが、指摘としては画面に出続ける。**模型の穴なので、既定設計へ
  `pressurant_tank` を積むのが正しい直し方(質量・内容積・調整値が動くので別の変更セットで)。
- 基地・格納艦の編集は確定するまで実機に映らない(下書きを除く)。
