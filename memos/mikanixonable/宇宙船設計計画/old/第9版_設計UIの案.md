# 宇宙船の設計・建造UIの案

## 1. この文書が扱うもの

宇宙船の設計と建造を、プレイヤーがどう操作するかの案を並べ、1つを推奨する。**扱うのは操作の形だけである。**設計データの型（`VesselBlueprint`）、その検証（`validateBlueprint`）、生産可能性の判定（`producibility`）、ツリーと断面の幾何（`VesselTree` / `CrossSection`）、質量特性の導出（`deriveMassProperties`）は、いずれも既に定まっており、どの案を採っても変わらない。案が違うのは、**それらをプレイヤーがどの順序で、どの操作で与えるか**だけである。

### 1-1. どの案も満たす前提

4つの前提はどの案も満たす。これらは案の選択肢ではない。

| 前提 | 内容 |
|---|---|
| **場所** | ドックモジュールを持つ基地を操作対象にしたときの戦闘ビューの中で行う。専用のビューも全画面のワークベンチも持たない。カメラは基地を追う戦闘ビューのカメラのままである |
| **表示** | 組み立て中の機体は3Dモデルとして実寸で置かれる。周囲の基地の構造や係留中の他の機体と同じ縮尺・同じ空間にある |
| **資源** | 資源と設備と電力を消費してモジュールを生産し、それを配置して機体を建てる。通貨はない |
| **形状** | 形はノードとエッジのツリーと、各ノードの断面で決まる。エッジは `hull` / `truss` / `decoupler` の3種。ツリーは閉じた構造を含んでよい。**直径もエッジの長さも 0.5 メートル単位**である |

### 1-2. 案が分かれる軸

| 軸 | 取りうる立場 |
|---|---|
| **生産と配置の順序** | 形を全部決めてから一括生産する／先に実物を作って在庫から置く／置くことが生産の発注そのものである |
| **形を決める操作** | ノードを置いてエッジで繋ぐ／接続口を掴んで引き出した先にノードができる／実物の突き合わせが接続を作る |
| **自動に委ねる範囲** | 配管・段の割り当て・構造材・断面寸法のうち、どこまでを系が埋めるか |
| **失敗の見せ方** | 作業領域に入らない設計・検証に落ちる設計・資源が足りない設計を、どの時点でどう見せるか |
| **既存の操作系との関係** | 戦闘ビューのカメラ・右クリックのプロパティーウィンドウ・マップビューと、どう役割を分けるか |

### 1-3. 既存の実装で、どの案も使えるもの

**費用の見積もりはこの一覧を基準に読む。**下の表にあるものは、どの案でも新規に書く必要がない。

| 既にあるもの | 場所 | 状態 |
|---|---|---|

### 1-4. どの案でも新たに要るもの

**この費用はどの案にも共通に乗る。**案ごとの見積もりは、この上に載る差分として書く。

| 要るもの | 内容 |
|---|---|
| **ロフトメッシュの生成** | `src/render/hull/loft-mesh.ts`。エッジごとに120分割の帯を張り、露出した端面に蓋をし、1つのジオメトリへ結合する。`sectionOutline` と `alignOutlines` は既にあるため、要るのは頂点バッファの組み立てとトラスの骨組み描画である。**現在の自機は事前生成のモデルで描かれており、設計と見た目が対応しない。**これが無ければ、どの案も画面に何も出せない |
| **在庫を持つ実体** | 基地モジュールを持つ `Vessel` が `ResourceLedger` を保持する。保存形式への追加を含む |
| **生産の経路** | `ProductionTask`、生産キュー、完成した機体をドックに現す処理、在庫の消費 |
| **3D空間での指定** | 接続口・エッジ・エッジ外表面・トラス上の点を、画面座標から選ぶ処理。`portFrame` / `mountFrame` が船体ローカル座標を返し、既存の `ProjectFn` が画面座標へ移すため、要るのは最近傍の判定と 0.5 m へのスナップである |
| **編集状態とUndo** | 編集中の設計と、操作ごとのスナップショットの積み上げ |
| **組立モードの開閉と作業領域の枠** | 基地を操作対象にしたときのモードの開閉、左右のレールへのパネルの出し入れ、ドックの最大寸法を線として描くこと |

## 2. 案A — 図面を引き切ってから一括生産する

### 2-1. 最も重んじるもの

**作る前に、作った結果の全体が分かること。**

### 2-2. 操作の流れ

```
基地を操作対象にする
   └─ 戦闘ビューに [組立] が現れる
        │
        ▼  組立モードを開く
   作業領域の枠が線として空間に現れる。左右のレールに編集パネルが加わる
        │
        ▼  骨格モード
   最初のノードが枠の中央に1つ置かれている。断面を選ぶ(左パネル)
   ノードの空いている接続口を空間の中でクリック → エッジとノードが生える
   エッジを選び、長さを 0.5 m 刻みで与える。種別を hull / truss / decoupler から選ぶ
        │
        ▼  搭載モード
   左パネルのパレットからエンジンを選び、後端の接続口をクリック → 装着
   タンクを選び、エッジをクリック → そのエッジの内容積に収める
   コックピットを同じ要領で収める
        │
        ▼  配管モード
   自動敷設の結果を確認する。供給されていないエンジンは赤い
        │
        ▼  塗装モード → 右レール下部の [この設計で生産]
   資源・設備・電力の不足が無ければ生産が始まり、完成した機体がドックに現れる
```

**資源が問われるのは最後の1回だけである。**それまでは、持っていない資源を要求する部品も設計に含められる。

### 2-3. 画面に何が出るか

**3D空間** — 作業領域の直方体の枠。組み立て中の機体の外皮メッシュ（生成済み・完成品と同じ見た目）。選択中のノード・エッジ・搭載要素の強調。空いている接続口の印。検証に落ちた箇所の赤い強調。

**左レール** — モードごとに変わる編集パネル。骨格モードなら断面の構成のツリー表示、基本断面の形状の `SegmentedControl`、外接円半径の `ValueInput`、位相の `Slider`、接続口の一覧、エッジの種別と長さ。

**右レール** — モードによらず同じ性能パネル。乾燥質量／総質量／全長／Δv／推力重量比／慣性主軸と推力軸ずれ／電力収支と放熱余裕／加圧ガス余裕／通信の到達距離／段の一覧／生産の不足。要素を選択またはホバーしている間、その要素を追加した場合の差分を数値の横に併記する。

**下部** — 元に戻す／やり直す／[この設計で生産]。

### 2-4. 資源と生産がどう絡むか

**設計は形の記録であり、資源を消費しない。**搭載モードのパレットは、資源または設備が足りない要素を淡色で表示し、何が不足しているかを示すが、**選択して設計に含めることはできる。**拒否されるのは [この設計で生産] を押した瞬間だけである。右レールの生産の行は、その時点の不足を常時表示する。

### 2-5. 得意なこと／苦手なこと

**得意** — 質量比・Δv・推力軸ずれといった全体量を、生産の前に確定させられる。設計を保存・複製・改名・ファイル入出力できる資産として扱える。持っていない資源の設計を先に描いておき、資源が揃った時点で生産できる。既存の `blueprint-validation.ts` の19項目がそのまま画面の警告になる。

**苦手** — 資源と形が切り離れているため、**在庫が形の判断に効いてこない。**「アルミが2トンしかないから、この機体は諦めて小さく作る」という判断が、生産ボタンを押すまで発生しない。またモード（骨格・搭載・配管・塗装）が4つあり、いま何を触れるかを覚える負担がある。最初の1機に到達するまでの操作数が最も多い。

### 2-6. 実装費用

**新たに要るもの**（§1-4 の共通分を除く）

- 4つの操作モードと、その切り替え（`TabBar`）
- 骨格モードの左パネル。断面の構成のツリー表示は既存ウィジェットに無く、新規に要る（折り畳み可能な木のリスト）
- 搭載モードの要素パレット（種別ごとのアコーディオン）と、装着可否の淡色表示
- 配管モードの重ね描き（外皮を半透明にし、推進剤ごとに色分けした線をツリーに沿って描く）
- `autoRouteFeed` と `resolveFeed` の実装
- 塗装モードのカラー選択
- ホバー中の半透明のゴースト表示
- 性能パネルの差分表示

**再利用できるもの** — 検証（`validateBlueprint` の19項目をそのまま左パネルと3D強調に流す）、性能パネルの全行（`deriveMassProperties` / `sectionMoments` / `internal-volume` / `producibility` の戻り値を並べるだけ）、保存（`BlueprintLibrary` をそのまま繋ぐ）、ウィジェット一式。

**費用は4案の中で最大である。**モードが4つあり、そのそれぞれが専用のパネルと3D側の表示切り替えを要求する。

### 2-7. 決まること／決まらないこと

**決まる** — 設計は再利用可能な資産である。同じ設計から何機でも生産できる。設計のファイル入出力が意味を持つ。生産可能性は生産の直前にだけ問われる。

**決まらない** — 生産に時間がかかる場合（生産時間係数が非0）、その間プレイヤーが何を見るか。作りかけの機体という状態が存在するのかどうか。

## 3. 案B — 生産した実物を掴んで突き合わせる

### 3-1. 最も重んじるもの

**手に持っている物だけで組めること。設計図ではなく実物を組むこと。**

### 3-2. 操作の流れ

```
基地を操作対象にする → 組立モードを開く
        │
        ▼  作業領域の枠と、その脇の「部材の棚」が空間に現れる
   棚は空である。まだ何も生産していない
        │
        ▼  右レールの [部材を生産]
   生産する部材を選ぶ:  外皮区間 / トラス区間 / 分離機構 / 搭載要素
   外皮区間なら、両端の断面と長さをその場で指定する(0.5 m 刻み)
   資源が足りなければ生産できない。不足がその場に出る
        │
        ▼  生産した部材が棚に実物として現れる
        │
        ▼  棚の部材をクリックして掴む → 作業領域へ運ぶ
   最初の1本は空中に固定される。以後の部材は、既に置いた部材の
   空いている接続口に近づけると吸着し、突き合わさる
        │
        ▼  エンジン・タンク・コックピットも同じ操作で、口と内容積へ収める
        │
        ▼  右レールの [完成とする]
   組み上がった物がそのまま実機になり、ドックに係留される
   同時に、その形がツリーとして読み取られ、設計として保存できる
```

**ツリーは操作の対象ではなく、突き合わせの結果として立つ。**プレイヤーはノードもエッジも直接触らない。触るのは部材である。

### 3-3. 画面に何が出るか

**3D空間** — 作業領域の枠。**その脇に、生産済みの部材を並べた棚**（実寸の3Dモデルが並ぶ）。掴んでいる部材は手前に浮き、吸着の候補になっている接続口が光る。既に組んだ部分は実物の外皮として描かれる。

**左レール** — 部材の生産パネル。種別の `TabBar`、外皮区間なら両端の断面（`SegmentedControl` と `ValueInput`）と長さ、生産に要る資源とその不足。掴んでいる部材があるときは、その部材の諸元。

**右レール** — 案Aと同じ性能パネル。ただし表示するのは**いま組み上がっている実物の**性能であり、これから作るものの見積もりではない。棚に残っている部材の一覧も出す。

**下部** — 元に戻す（＝直前に付けた部材を外して棚へ戻す）／[完成とする]。

### 3-4. 資源と生産がどう絡むか

**資源は部材を生産する瞬間に消費される。**組み立ての操作は資源を一切消費しない。したがって在庫の残りが、次に何を作れるかを常に制約する。**「アルミが尽きたのでトラスに切り替える」という判断が、組み立ての最中に発生する。**外した部材は棚へ戻り、資源は返らない。

### 3-5. 得意なこと／苦手なこと

**得意** — 資源が形の判断に直結する。この作品が「通貨を持たず、進行は物理的な事実で止まる」ことを、操作そのもので表す。突き合わせの操作は3Dで直感的であり、断面の一致という制約が「入るか入らないか」として手に伝わる。モードが1つしかない。

**苦手** — **設計が資産にならない。**同じ機体を10機作るのに、10回同じ組み立てをすることになる。既存の `BlueprintLibrary` と `blueprint-transfer.ts` のファイル入出力が、ほぼ意味を失う（読み取ったツリーを保存できても、それを組み直す経路が「同じ部材を生産して同じ手順を踏む」しかない）。エッジの長さを後から変えられない（実物だから）ため、設計の反復が「作り直す」ことになり、資源を捨てる。閉じた構造（三角形・梯子状）を組むとき、最後の1本が両端で同時に吸着しなければならず、寸法が合わないと入らない——これは現実的だが、操作としては厳しい。

**この苦手は決定的である。**§14-4 が定めるドックの拡張、§6-9 の軌道上での結合、第2巻 §18 の想定される進行経路は、いずれも同型の機体を複数作ることを前提にしている。

### 3-6. 実装費用

**新たに要るもの**

- 部材の棚（作業領域の脇に実寸の3Dモデルを並べ、選択できるようにする）
- 掴む／運ぶ／吸着する操作。**ドラッグ中の部材の位置を、カメラの奥行きに対してどう決めるかという問題が新たに生じる。**戦闘ビューのカメラは6自由度で回るため、画面上のドラッグから3D位置を一意に決められない。吸着の候補を接続口の集合に限れば回避できるが、最初の1本の置き方は別に決めることになる
- 実物の集合からツリーを読み取る処理（`VesselTree` の逆生成）。突き合わせた口の対応から `TreeEdge` の `portA` / `portB` を復元する
- 部材ごとの生産（`producibility` は設計全体を受け取る形（`ProducibilityBlueprint`）であるため、部材1つぶんの要求を組み立てる薄い層が要る）
- 「組み立て途中の物」という状態。これは `Vessel` でも `VesselBlueprint` でもない第3の状態であり、保存形式に加わる

**再利用できるもの** — 断面の幾何、質量特性、内容積の割り当て、ウィジェット。**`blueprint-validation.ts` の19項目の大半が使えない。**突き合わせの操作が成立した時点で、連結性・口の寸法・排他といった制約は既に満たされているためであり、残るのは推力軸のずれ・材料適合性・上限といった全体の制約だけである。

**費用は案Aと同程度だが、内訳が違う。**パネルは少ないが、3Dの操作と新しい状態の導入が重い。

### 3-7. 決まること／決まらないこと

**決まる** — 資源が形を制約する。設計より実物が先である。組み立て途中という状態が存在する。

**決まらない** — 同型機を複数作る手段。掴んだ部材の3D位置の決め方。外した部材の資源の扱い。

## 4. 案C — 置くことが建造の発注であり、機体は時間の中で建つ

### 4-1. 最も重んじるもの

**作ることが出来事であること。設計と建造を分けないこと。**

### 4-2. 操作の流れ

```
基地を操作対象にする → 組立モードを開く
        │
        ▼  作業領域の枠が現れる。中央に建造の起点となるノードが1つ
        │
        ▼  接続口をクリック → その方向にエッジが「ゴースト」として伸びる
   ドラッグで長さが 0.5 m 刻みに伸縮する。離すと確定し、先にノードができる
   確定した区間は線画のゴーストのままである。まだ実物ではない
        │
        ▼  同じ要領で、搭載要素もゴーストとして置く
   置いた瞬間に、その要素に要る資源が右レールの「発注」に積まれる
        │
        ▼  右レールの [建造開始]
   ドックのロボットアームが動き、資源を消費しながら1区間ずつ実体化していく
   ゴーストが手前から順に外皮の実物へ変わっていく
        │
        ▼  資源が尽きると、そこで建造が止まる
   止まった機体は、実体化した部分だけが実物として、残りはゴーストのまま空間に残る
   資源を持ち帰れば、続きから建造が再開される
        │
        ▼  全区間が実体化した時点で完成し、ドックに係留される
```

**設計データは「建造指示の集合」である。**保存できるし、複製もできる。同型機を作るには同じ指示をもう一度出す。

### 4-3. 画面に何が出るか

**3D空間** — 作業領域の枠。**実体化した区間は外皮メッシュ、未実体化の区間は線画のゴースト**として、同じ機体の中に混在して見える。**建造の進捗が形として見える。**ロボットアームが実際に動き、いま実体化している区間を指している。

**左レール** — 骨格の編集（断面・長さ・種別）と搭載要素のパレット。案Aの骨格モードと搭載モードを1枚に畳んだもの。**ゴーストの区間は編集でき、実体化した区間は編集できない。**編集できない区間は、パネル上でも淡色になる。

**右レール** — 性能パネル（完成時の値）と、**発注の一覧**。区間ごとに「要る資源／消費済み／残り」を並べる。建造中はどの区間を作っているかが光る。

**下部** — 元に戻す（ゴーストの区間のみ）／[建造開始] ／[建造中断]。

### 4-4. 資源と生産がどう絡むか

**資源は建造が進むにつれて、連続的に消費される。**発注の一覧が「これから何を食うか」を示し、在庫が減っていくのが見える。資源が尽きれば建造が止まり、**止まった位置が形として画面に残る。**足りないことを文章で説明せず、建ちかけの機体として示す。

生産時間係数（§5-1、既定値0）が0のとき、この案は全区間が即座に実体化するため、案Aの [この設計で生産] とほぼ同じ挙動になる。**係数が非0のとき、この案だけが「その間何を見るか」に答えを持つ。**

### 4-5. 得意なこと／苦手なこと

**得意** — 設計と建造が1つの操作で、モードの切り替えが最小である。資源が形の判断に効く（案Bと同じ利点）一方、設計データは資産として残る（案Aと同じ利点）。**両者の利点を同時に持つ。**建造の進捗と資源の不足が、どちらも形として見える。実体化した区間を編集できないことが、「作り直すには壊すか、別に作る」という物理的な制約として自然に出る。

**苦手** — **実体化した区間を編集できないことは、設計の反復と噛み合わない。**Δv が足りないと分かったときに、既に建った区間は動かせない。これを緩めて「ゴーストに戻せる（資源は一部返る）」とすると、案Aとの差が薄れる。また、建造中の機体という状態が保存形式に加わり、その状態の `Vessel` が軌道上に存在することになる（基地に係留された、まだ飛べない機体）。

### 4-6. 実装費用

**新たに要るもの**

- ゴースト表示。**ロフトメッシュを2通りの見た目で描く必要がある。**線画は既存の `src/render/curve.ts` の `Curve` でエッジの稜線を引けば足り、外皮メッシュとは別経路になる
- 建造の進行（区間ごとの実体化、資源の逐次消費、中断と再開）
- 建造中の機体という状態と、その保存
- 区間ごとの資源要求の算出。`producibility` は設計全体を受け取るため、**区間1つぶんの要求を切り出す層が要る**（案Bと同じ層であり、共通に使える）
- ロボットアームの動き（既に外装要素としてロボットアームが定義されているため、その3Dモデルと関節の動きが要る）

**再利用できるもの** — 検証の19項目（ゴーストの段階で全て働く）、性能パネル、保存、ウィジェット、`producibility`。**案Aで要る4つのモードのうち、配管モードと塗装モードだけが独立に残る。**

**費用は案Aよりやや大きい。**案Aの費用に、ゴーストと建造の進行が乗る。ただし4つのモードのうち2つが統合されるぶん、パネルの費用は下がる。

### 4-7. 決まること／決まらないこと

**決まる** — 生産時間係数が非0のときの表示。建造の中断と再開。資源不足が形として現れること。設計は資産として残る。

**決まらない** — 実体化した区間を壊せるかどうか、壊したとき資源が返るかどうか。建造中の機体が被弾したときの扱い。ロボットアームを持たない基地でも建造できるのかどうか。

## 5. 案D — 要求を与え、系が細部を埋める

### 5-1. 最も重んじるもの

**プレイヤーが決めるべきことだけを決めさせること。**

### 5-2. 操作の流れ

```
基地を操作対象にする → 組立モードを開く
        │
        ▼  左レールの「要求」パネルに、作りたい機体の要件を入れる
   Δv [m/s] / 推力重量比 / 乗員 [人] / ペイロード質量 [kg] / 到達目標(月周回・L1・静止軌道…)
   有人か無人か。大気に入るか
        │
        ▼  [構成案を出す]
   系が、在庫にある資源と建設済みの設備の範囲で、要件を満たす構成を1つ提示する
   作業領域に、その構成の機体が実寸のゴーストで現れる
   満たせない要件があれば、どの要件がどれだけ不足しているかを出す
        │
        ▼  提示された構成を、骨格の押し出しで直す
   接続口を掴んで引き出す → エッジが伸び、離した所にノードができる
   断面は口から継承され、必要なら後で変える
   タンクを大きくすれば Δv が上がり、右レールの要件の充足が更新される
        │
        ▼  配管・段の分離順・構造材・外皮の肉厚は、系が常に自動で埋める
   プレイヤーはそれらを見ることはできるが、既定では触らない
        │
        ▼  [この設計で生産]
```

**押し出しは案A/Cの「口をクリックして生やす」と違う。**クリックではなくドラッグであり、伸ばしている間ずっと長さが 0.5 m 刻みにスナップして見える。ノードは操作の対象ではなく、押し出しの終端として生じる。

### 5-3. 画面に何が出るか

**3D空間** — 作業領域の枠。機体のゴーストまたは実物。押し出し中は、伸びている区間の長さが空間の中に数値として付く。断面を編集するときはカメラがその断面の正対へ回り込む。

**左レール** — 「要求」パネル（`ValueInput` と `SegmentedControl` の列）。その下に、選択中のノード／エッジの編集。配管と段は既定で折り畳まれており、開けば自動の結果が見え、そこで初めて手動の上書きができる。

**右レール** — **要件の充足**。要求した各項目に対し、現在の構成が出す値と、満たしているかどうかを `Meter` で並べる。その下に案Aと同じ性能パネルと、生産の不足。

### 5-4. 資源と生産がどう絡むか

**在庫が構成案の生成に入る。**系が提示する構成は、**いま持っている資源と設備で作れるものに限られる。**アルミしか無ければアルミのタンクを提案し、機械工場が無ければエンジンを含む構成を提案しない代わりに「機械工場が要る」と告げる。プレイヤーが手で直した結果が在庫を超えた場合は、案Aと同じく生産の時点で拒否する。

### 5-5. 得意なこと／苦手なこと

**得意** — 最初の1機に到達するのが最も速い。断面の位相・貼り付け・配管・段割りといった細部を知らなくても、機体が1つ手に入る。**在庫と設備が構成案に入るため、進行の状態が提案そのものに現れる。**押し出しの操作は、ノードとエッジという抽象を意識させずに形を与えられる。

**苦手** — **構成案を出す処理が、この作品で最も難しい実装である。**要件（Δv・推力重量比・乗員・ペイロード）から機体構成を逆に解くことは、ツィオルコフスキーの式・タンク容積・肉厚・搭載要素の性能値・材料適合性・配管・段割りが絡む探索であり、素直な解法が無い。粗い規則で済ませれば「提案がいつも同じ形」になり、凝れば実装が膨らむ。また、自動に委ねた部分（配管・段）が意図と違ったとき、プレイヤーは何が起きているか分からない。**「高性能な計算機が存在しない」という作品の方針とも噛み合わない。**機上で自力にできることを噴射シーケンスと姿勢保持までに絞っておきながら、設計の自動最適化を系が行うのは、同じ世界の中で辻褄が合わない。

### 5-6. 実装費用

**新たに要るもの**

- **構成案の生成。**上記のとおり、素直な解法が無い。既存の実装で使えるのは評価側（`deriveMassProperties` / `producibility` / 燃焼計算）だけであり、探索そのものは全て新規である
- 押し出しの操作（ドラッグ中の長さのスナップと、その場での数値表示）
- 要件の充足パネル
- 自動の段割り（`decoupler` の位置を系が決める）
- `autoRouteFeed`（案Aと共通）

**再利用できるもの** — 評価に要る計算はすべて既にある。**探索の内側でそれらを何度も呼ぶことになり、`deriveMassProperties` が線形時間であることがここで効く。**

**費用は4案の中で最大であり、しかも見積もりの幅が最も広い。**構成案の生成の出来次第で、この案の価値そのものが変わる。

### 5-7. 決まること／決まらないこと

**決まる** — 形を決める操作は押し出しである。配管と段はプレイヤーが触らないことを既定とする。在庫が提案に入る。

**決まらない** — 構成案の生成が満たすべき品質。提案が要件を満たせないときに、どこまで理由を説明するか。自動の段割りが、プレイヤーが手で置いた `decoupler` とどう共存するか。

## 7. 推奨 — 案C（置くことが建造の発注であり、機体は時間の中で建つ）

### 7-1. 理由

**案Cだけが、資源が形の判断に効くことと、設計が資産として残ることを同時に満たす。**

この作品は「通貨を持たない」「技術ツリーを持たない」「進行は物理的な事実で止まる」という3つの方針を骨格に置いている。**そのどれも、資源の不足が操作の途中で目に見えることによってしか成立しない。**案Aは資源を生産ボタンの内側に閉じ込めてしまい、設計をしている間ずっと、進行の状態が形の判断に入ってこない。案Bは資源を形に効かせるが、その代償として設計を資産でなくしてしまい、§14-4 のドックの拡張・§6-9 の軌道上での結合・§18 の進行経路がいずれも前提にしている「同型機を複数作る」ことができなくなる。案Cは、置いた瞬間に発注が積まれ、資源が減りながら建ち、尽きればそこで止まる——**資源の不足が、建ちかけの機体という形として画面に残る。**そして指示の集合は設計データとして保存され、同じ指示をもう一度出せば同型機が建つ。

**案Cは、生産時間係数に答えを持つ唯一の案である。**§5-1 は生産時間係数をセーブデータに含め、既定値を0（即座に完成）としながら、後から有効にできると定めている。案A・B・Dは、係数を非0にした瞬間に「その間プレイヤーは何を見るのか」という未定の問いを生む。案Cはその問いを構造として先に解いており、**係数が0のときは全区間が即座に実体化して案Aと同じ挙動に退化する。**既定値のままでも損をせず、有効にしたときだけ価値が現れる。

**既存の実装との噛み合いも最良である。**`blueprint-validation.ts` の19項目はゴーストの段階で全て働き、`BlueprintLibrary` はそのまま設計の保管庫として生き、`producibility` は区間ごとの要求を積み上げる形で使える。案Bはこのうち2つを失う。

**段階的に作れる。**ゴーストの表示と骨格の編集までを先に通せば、それだけで「ツリーを編集する手段が無い」という現在の欠落が埋まる。建造の進行はその後に足せる。案Dは構成案の生成が完成するまで画面に何も出ないため、この分割ができない。

### 7-2. 案Cを採るとき、案Aから引き継ぐもの

案Cは案Aの骨格を土台にしている。**引き継ぐのは、右レールの性能パネル（全行）、配管モード、塗装モード、検証の表示、[元に戻す／やり直す] の50手の上限である。**捨てるのは、骨格モードと搭載モードを別のモードに分けることだけであり、両者は1枚のパネルに畳む。

### 7-3. 案Cを採るとき、直ちに決めなければならないこと

**実体化した区間を壊せるかどうか。**§4-7 に挙げたとおり、この一点が案Cの性格を決める。壊せないなら設計の反復が資源を捨てることになり、壊せて資源が全額返るなら案Aとの差が消える。**推奨は「壊せるが、資源は返らない」である。**分解は物理的な行為であり、外皮を切り離した金属が元の板に戻ることはない。この扱いは、案Bが持っていた「作り直しは高くつく」という手触りを、設計の資産性を失わずに引き継ぐ。

## 8. どの案を採っても残る、別途の判断が要る事項

| 事項 | 内容 |
|---|---|
| **最初の1つのノードがどこから来るか** | どの案も、空の作業領域から始めるには最初のノードが要る。系が置くのか、プレイヤーが断面を選んで置くのか、既定の設計を1つ与えて改造から始めるのかが決まっていない |
| **カメラが機体に埋まること** | 第2巻 §22-10 が挙げるリスクである。戦闘ビューの追従カメラは基地を追うため、作業領域の内側へ入り込む。組立モードのために別のカメラを持たない以上、埋まったときの扱い（外皮を半透明にする・近接面をクリップする・カメラを押し出す）を決める必要がある |
| **断面の編集に入ったときのカメラの回り込み** | 「カメラがその断面の正面へ回り込む」ことは、追従カメラの向きを系が動かすことである。プレイヤーの操作したカメラ位置を上書きしてよいのか、戻せるのかが決まっていない |
| **`decoupler` の分離順の初期値** | `stageOrder` は分離機構のエッジ id の並びだが、新しく `decoupler` を置いたときに列のどこへ入るかが決まっていない |
| **ミラー編集の適用範囲** | YZ平面のミラーが、骨格だけに効くのか、搭載要素と配管にも効くのかが決まっていない |
| **作業領域に入らない設計を保存できるか** | §6-9 は「保存は形の記録であり、作業領域に収まることを要さない」と定める一方、どの案も編集は作業領域の中で行う。枠の外へはみ出した状態で編集を続けられるのか、はみ出した部分を触れるのかが決まっていない |
| **在庫がどの基地のものか** | 在庫は基地モジュールを持つ `Vessel` が保持し、移送は輸送しかない。組立モードで参照する在庫は、その基地自身のものだけである——このことが操作の上でどう見えるか（他の基地の在庫が見えるのか、見えないのか）が決まっていない |
| **敵に襲われている最中に組立モードを開けるか** | 組立モードを開いている間も世界の描画と時間の進行は戦闘ビューのままである。基地が交戦中でも開けるのか、開いている間に被弾したらどうなるかが決まっていない |
