# 配管・多段ブースター・ペイロード — 実装計画

この文書は、宇宙船を「タンクからエンジンへ推進剤を流す機体」および「分離して段に分かれる機体」として成立させるための計画である。対象は次の5つである。

1. 多段ブースターシステム（段の定義・分離の物理・燃焼の順序）
2. ペイロード倉庫と、弾薬を含む積荷の軌道投入
3. 推進剤の流路（配管）と、その自動敷設
4. タンクの与圧と、イナートガスの消費
5. 弾薬の供給と段の関係

**他の巻との関係** — この巻は『推進系と推進剤』の巻と『船体設計システム』の巻の両方に依存する。前者がエンジンのサイクルと推進剤の物性を与え、後者が背骨のグラフ構造・エッジの種別・搭載要素の内容積割り当てを与える。この巻はその上に、配管という搭載要素と、分離という背骨の操作を載せる。

以下、§2 前提を除き、記述はすべてこの文書の中で完結する。

---

## 1. 対象外

断面の幾何、外皮の生成、質量特性の導出、設計エディタの骨格モード・搭載モード・塗装モード、設計の保存と生産、資源と生産可能性、主機／並進RCS／フライホイールの分離、推進剤の物性表そのもの、`Vessel` への実体統合は、この巻の対象に含めない。

## 2. 前提

第1巻・第2巻で実装済みとして扱うもののうち、この巻が使うものを挙げる。

**背骨** — 船体の形状は、ノードとエッジからなるグラフ（背骨）と、各ノードが持つ断面で定義される。背骨は閉路を含んでよい。エッジは3つの種別のいずれかを持つ。

```ts
export type EdgeKind =
  | { kind: 'hull' }                                   // 外皮を作る。内側が内容積になる
  | { kind: 'strut'; radius: number }                  // 外皮を作らない構造材
  | { kind: 'decoupler'; separationImpulse: number };  // 外皮を作らず、切り離せる

export interface SkeletonEdge {
  readonly id: string;
  readonly a: string;
  readonly b: string;
  readonly length: number;         // 0.5 m 単位
  readonly kind: EdgeKind;
}

export interface VesselSkeleton {
  readonly nodes: readonly SkeletonNode[];
  readonly edges: readonly SkeletonEdge[];
}
```

**搭載要素** — 搭載要素は、ノードの接続口に取り付ける外装要素（エンジン・RCSスラスタ・武器・太陽電池パドル・放熱板・ドッキングポート）と、`hull` エッジの内容積に収める内装要素（各種タンク・バッテリー・コックピット・自動操縦装置・弾薬庫・配管・ペイロード倉庫・フライホイール・基地モジュール）に分かれる。エッジの種別は搭載要素ではなく背骨の性質である。1つのエッジに複数の内装要素を収めてよく、実効容積を掛けた体積の和がそのエッジのロフト体積を超えないこと。

**姿勢制御アクチュエータの配置** — RCSスラスタは任意の個数・任意の位置・任意の向きに取り付けられる。取り付けたノードの接続口の位置と向きから、各スラスタの腕の長さ `r_k` と噴射方向 `exhaust_k` が決まり、そのスラスタが生むトルクは `τ_k = r_k × (−exhaust_k)` である。要求トルクを満たす推力の組み合わせは一般に劣決定であり、その配分は第1巻が解く。この巻はその結果を使うだけで、配分そのものには関与しない。

**エンジン** — エンジンは「サイクル（供給方式）」と「対応推進剤」の組で定義される。サイクルは加圧式・電気ポンプ式・ガス発生器サイクル・段階燃焼サイクル・エキスパンダーサイクル・固体モーター・ハイブリッドモーターの7種である。エンジンの比推力は `推進剤ペアの比推力 × サイクルの比推力係数` である。エンジンは推力・比推力・絞り範囲・再着火回数に加えて、次の4つを性能値として持つ。

| 性能値 | 内容 | この巻での用途 |
|---|---|---|
| 全長 | ノズル膨張比が大きいほど長い。機体の後端から突き出す長さとして目に見える | 段の外形と分離時の干渉 |
| 点火あたりの推進剤損失 | 配管とポンプの冷却（チルダウン）で捨てる質量。極低温で顕著 | 段ごとの実効 Δv、分割したノードの再点火コスト |
| 連続燃焼時間の上限 | アブレーティブ冷却の加圧式、および凝縮相を生む推進剤に上限がある。無制限のものは `Infinity` | 1つのノードの燃焼が完結するかの判定 |
| 要求与圧 | タンク入口に要求する圧力。加圧式のみが高い値を要求し、ポンプ式はポンプ入口圧（NPSH）として低い値でよい。固体モーターは与圧も配管も要さない | §5 の与圧計算と推力低下 |

**質量特性** — 質量・重心・慣性テンソルは定数として持たず、背骨と断面と搭載物から導出される。

**燃焼計算** — `src/physics/tsiolkovsky.ts` に、質量変化を含む燃焼計算が純関数として置かれている（`dvFor` / `massAfterBurn` / `burnTimeFor` / `propellantForDv`）。推進剤流量は `推力 / (比推力 × 標準重力加速度)` である。

**イナートガスの物性** — 与圧の計算に用いる。

| ガス | 密度（20 MPa, 常温） | 特性 |
|---|---|---|
| ヘリウム | 33 kg/m³ | 軽く、極低温でも凝縮しない。必要質量が小さい |
| 窒素 | 230 kg/m³ | 安価だが重い。極低温推進剤には使えない |

**イナートガスタンクの実効容積** — 内圧に対して最も効率のよい圧力容器は球であり、イナートガスタンクは球状である。同じ耐圧なら球は円筒より薄い壁で済み、タンク自体の質量が小さい。一方、球は角柱状の内容積に詰めたときの充填率が悪い。この対立が、エッジの内容積に対する実効容積の係数 **0.55** として現れる。

## 3. 設計判断

### 3-1. 段はプレイヤーが区切るのではなく、分離機構から決まる

段を明示的に定義する操作は存在しない。段は、背骨から `decoupler` エッジを取り除いたときの連結成分である。プレイヤーが分離機構を挿すと、その両側が自動的に別の段になる。

### 3-2. 分離は自動では行わない

推進剤が尽きた段は分離の候補として提示するが、自動では分離しない。分離は運動量保存により軌道を変えるため、いつ切り離すかは軌道上の判断であり、実行はプレイヤーまたは軌道計画に委ねる。

### 3-3. 積荷の受け渡しは結合を必要としない

ペイロードの放出は、独立した物体を軌道上に生成する操作である。放出された弾薬は既存の補給パッケージと同じ実体であり、艦艇は既存の接近回収の仕組みでそれを取る。機体同士を結合する仕組みには依存しない。

### 3-4. 推進剤はタンクから配管を通ってエンジンへ流れる

配管は搭載要素の一つであり、背骨のエッジに割り当てられる。タンクからエンジンまで配管が連続していないエンジンは点火できない。配管には口径ごとの流量上限があり、エンジンの要求流量を満たさない配管は推力を制限する。

タンクとエンジンの接続を暗黙に成立させる方式は採らない。配管が明示的な実体としてあることで、側面ブースターから中央段への推進剤の送り（クロスフィード）、分離による流路の切断、流量不足による推力制限といった、多段機の設計上の判断が、いずれも同じ一つの仕組みの帰結として現れる。

### 3-5. 配管の敷設は自動を既定とし、手動はその上書きとする

タンクからエンジンへ配管を通すことには、ほとんどの場合に唯一の正解しかない。選択の余地のない操作をエッジの数だけ繰り返させるのは作業であって遊びではない。

したがって**自動敷設を既定とする**。設計を変更するたびに自動敷設をやり直し、プレイヤーが手で触るのは、選択に意味がある次の場合だけになる。

- クロスフィードを組む
- 口径を絞って軽量化する
- 特定のタンクを特定のエンジンに割り当てる
- 分離機構を跨ぐ配管の可否を決める

手動で敷いた区間は自動敷設の上書きとして差分で保持し、やり直しの対象から外す。

## 4. 多段ブースターシステム

### 4-1. 段の定義

段は、背骨から `decoupler` エッジを取り除いたときの連結成分である。プレイヤーが段を明示的に区切る操作は存在せず、分離機構を挿すと自動的に分かれる。

```ts
// src/game/vessel/assembly.ts
export interface VesselStage {
  readonly id: string;
  readonly edgeIds: readonly string[];
  readonly hasCockpit: boolean;
  readonly hasAutopilot: boolean;
  readonly dryMass: number;
  readonly propellantMass: number;
}
export function splitStages(skeleton: VesselSkeleton, parts: readonly AnyPart[]): readonly VesselStage[];
```

コックピットまたは自動操縦装置を含む段は、分離後も操作または自動制御の対象になる。どちらも含まない段は、分離後は制御不能な物体として軌道上に残る。

### 4-2. 分離の物理

分離は運動量保存を満たす。分離前の質量を `m_total`、分かれる2つを `m_a` / `m_b`、分離機構の力積から求まる相対速度増分を `Δv_sep` とすると、

```
v_a = v + (m_b / m_total) · Δv_sep
v_b = v − (m_a / m_total) · Δv_sep
```

角運動量も同様に分配する。分離直後の一定時間は、分かれた2つの間の接触判定を無効にする。

分離後、本体は背骨・質量・重心・慣性テンソル・推進剤残量・配管の流路を再計算する。分離機構を跨いでいた配管は切断される。

### 4-3. 燃焼の順序

同時燃焼（並列に束ねたブースター）と逐次燃焼（直列の多段）の両方を許す。段の一覧は分離順に並べ替えられ、飛行中はその順序に従って次に分離する段をHUDに表示する。

推進剤が尽きた段は分離の候補として提示するが、自動では分離しない。分離は軌道を変えるため、実行はプレイヤーまたは計画の判断に委ねる。

### 4-4. 段を跨ぐ燃焼の判定と分割

段の切り替わりを跨ぐ燃焼は加速度が不連続になり、閉形式の点火時刻計算が成立しない。1つのマニューバノードの燃焼が1つの段の中で完結する必要がある。

**判定式は、そのノードの Δv に対する `propellantForDv(dv, mDry, isp)` が、そのノードを実行する段の推進剤残量を超えるかどうかである。** 超えない場合は何もしない。

超える場合、UIは**禁止するのではなく、ノードを2つに分割することを提案する**。分割は、その段の推進剤で出せる Δv までを1つ目のノードとし、残りを2つ目のノードとする。1つ目の燃焼終了後に段を分離し、2つ目を次の段で実行する。2つ目のノードには、次の段のエンジンの点火あたりの推進剤損失が加算される。

禁止するだけでは、プレイヤーは何をすればよいか分からない。分割案を提示し、受け入れるかどうかを選ばせる。

連続燃焼時間の上限を持つエンジンについても同じ判定を行う。要求される燃焼時間が上限を超える場合、上限までを1つ目のノードとして同じ形で分割を提案する。

## 5. ペイロード

ペイロード倉庫は、軌道上へ運ぶものを収める。エッジの内容積に対する実効容積の係数は 0.90 であり、容積と最大積載質量の両方で制限される。

```ts
export type PayloadKind =
  | { kind: 'ammo'; magazines: number }
  | { kind: 'propellant'; propellantId: string; mass: number }
  | { kind: 'part'; partIds: readonly string[] }
  | { kind: 'none' };

export interface PayloadBayPart extends Part {
  readonly type: 'payload_bay';
  readonly volume: number;
  readonly maxMass: number;
  payload: PayloadKind;
}
```

**弾薬をペイロードとして運ぶ運用** — 弾薬マガジンを積んだ無人ブースターを、自動操縦装置による自動操縦で目的の軌道に投入する。到達後、ペイロード倉庫を開いて弾薬を放出すると、既存の補給パッケージと同じ実体が軌道上に生成される。艦艇はそれに接近して回収する。

この運用は機体同士の結合を必要としない。放出された弾薬は独立した物体として軌道を回り、艦艇は既存の接近回収の仕組みでそれを取る。

放出は、プレイヤーの明示的な操作、または軌道計画上の指定時刻に行う。放出時には小さな分離速度を与え、ブースター本体と弾薬が離れる。

## 6. 推進剤の流路（配管）

推進剤はタンクからエンジンへ、配管を通って流れる。

```ts
// src/game/vessel/feed-network.ts
export interface FeedNetwork {
  readonly links: readonly FeedLink[];   // 配管が敷かれたエッジ
}
export interface FeedLink {
  readonly edgeId: string;
  readonly propellantId: string;   // この配管が通す推進剤
  readonly diameter: number;       // m
  readonly maxFlowRate: number;    // kg/s
  readonly manual: boolean;        // 手動の上書きか（自動敷設のやり直しで保持される）
}
export function resolveFeed(
  network: FeedNetwork,
  tanks: readonly TankPart[],
  engines: readonly EnginePart[],
): readonly EngineFeedResult[];
```

規則:

- 配管は1本につき1種類の推進剤しか通さない。酸化剤と還元剤を同じエンジンへ送るには、配管が2本必要である。イナートガスも同様に別の配管を要する。
- タンクとエンジンが、同じ推進剤の配管で連続して繋がっていることが点火の条件である。繋がっていないエンジンは点火できず、エディタと飛行中HUDがその旨を表示する。
- 配管の口径から決まる最大流量が、エンジンの要求流量（`推力 / (比推力 × 標準重力加速度)`）を下回る場合、エンジンの推力はその流量で制限される。
- タンクとエンジンが同じエッジの内容積に同居する場合、配管は不要である。
- 分離機構のエッジを配管が跨ぐ場合、分離と同時に配管が切断される。跨ぐことを許すかどうかはプレイヤーが選ぶ。跨ぐ配管を敷けば、側面ブースターのタンクから中央のエンジンへ推進剤を送る運用（クロスフィード）ができ、分離時点で中央段のタンクを満載のまま残せる。
- 外皮のない `strut` エッジにも配管を敷ける。この場合、配管は外部に露出したものとして描画する。

配管がエッジの内容積を占める量は、口径から決まる。エッジの長さと口径の断面積の積である。

### 6-1. 自動敷設

自動敷設は純関数として置く。

```ts
// src/game/vessel/auto-route.ts
export function autoRouteFeed(
  skeleton: VesselSkeleton,
  placements: readonly PartPlacement[],
  overrides: readonly FeedLink[],   // 手動の上書き（manual: true のもの）
): FeedNetwork;
```

規則:

- 各エンジンに対して、そのエンジンが要求する推進剤（酸化剤・還元剤・イナートガス）ごとに、その推進剤を持つ最も近いタンクから最短経路で配管を通す。距離はエッジの長さの和とする。
- 口径は、そのエンジンの要求流量を満たす最小のものを選ぶ。同じエッジを複数のエンジンが共有する場合、口径は要求流量の和を満たす最小のものになる。
- 既定では分離機構を跨がない。跨がなければ届かないエンジンについては、跨ぐ経路を提示するが敷設はせず、供給なしとして診断に出す。クロスフィードは選択に意味のある判断であり、自動で決めない。
- 手動で敷かれた区間（`manual: true`）は保持し、自動敷設はその上に足りない分だけを敷く。手動の区間だけでエンジンへ届く場合、自動敷設はそのエンジンに対して何もしない。
- 設計を変更するたびに、この関数を呼び直す。エッジ数に対して線形である。

自動敷設の結果は手動の敷設と同じ `FeedNetwork` であり、`resolveFeed` は両者を区別しない。

## 7. タンクの与圧

液体推進剤のタンクは、推進剤を押し出すために内部を加圧する必要がある。加圧にはイナートガス（ヘリウムまたは窒素）を用いる。

- 消費するガス量は、押し出した推進剤の体積とタンクの与圧の積に比例する。
- 要求与圧はエンジンのサイクルによって決まる。**加圧式エンジンは要求与圧が高く、大量のイナートガスを要する。ポンプ式エンジンは低い与圧で足り、ガスの消費が少ない。** この差が、単純な加圧式と、複雑だが効率のよいポンプ式との設計上の対立になる。
- ヘリウムは極低温でも凝縮しないため極低温推進剤に使える。窒素は安価だが重く、極低温推進剤には使えない。

### 7-1. 与圧低下による推力低下

イナートガスが減るとタンクの与圧が下がり、エンジンの推力が下がる。与圧が要求値を下回った時点から、推力を与圧に比例して下げ、下限を割った時点で燃焼を停止する。

- **加圧式**は与圧が燃焼室圧を直接決めるため、影響が大きい。与圧の低下がそのまま推力の低下になる。
- **ポンプ式**はポンプ入口圧（NPSH）が下限を割るとキャビテーションを起こし、そこから急に推力を失う。要求値を上回っている限り影響はない。

イナートガスが尽きると、推進剤が残っていてもエンジンは推力を失う。これは実機の失敗様態と同じである。HUD には加圧ガスの残量と、その残量で燃焼を続けられる残り時間を表示する。

### 7-2. 自己加圧

イナートガスタンクを持たずに済む方式が2つある。どちらも与圧の要求を推進剤自身で満たすため、イナートガスの質量と容積を丸ごと削れる。

- **極低温推進剤の自己加圧** — 蒸発した推進剤自身の気体を加圧に用いる。イナートガスが不要になる代わりに、蒸発損失が増える。
- **亜酸化窒素の自己加圧** — ハイブリッドモーターの酸化剤である亜酸化窒素は蒸気圧が高く、それ自体でタンクを加圧できる。イナートガスタンクが不要になる。低性能なハイブリッドモーターを選ぶ理由の一つがこれであり、機体全体の乾燥質量では加圧式の液体エンジンに対抗しうる。

計算は純関数として置く。

```
src/physics/pressurant.ts   (純関数)
    pressurantMassFor(propellantVolume, tankPressure, gasType, temperature) -> number
    remainingBurnTime(pressurantMass, flowRate, tankPressure, gasType) -> number
    thrustScaleFromPressure(tankPressure, requiredPressure, cycle) -> number
```

## 8. 弾薬の供給

武器は弾薬庫からマガジンの供給を受ける。武器と弾薬庫が同じ段に属していれば供給される。段が異なる場合は供給されない。分離によって弾薬庫を失った武器は、装填済みのマガジンを撃ち尽くした時点で沈黙する。

## 9. UI

### 9-1. 段の一覧（右パネルの常設表示）

段は独立したモードを持たない。段の一覧は右パネルに常設し、どのモードで作業していても見える。設計エディタのモードを増やすと、プレイヤーが「今どのモードにいるか」を把握する負担が増える。段の内容はモードを切り替えるほどの分量ではない。

右パネルに置く内容:

| 区画 | ウィジェット | 内容 |
|---|---|---|
| 段の一覧 | リスト（分離順） | 各行に段の乾燥質量・推進剤質量・その段の Δv・主機の有無 |
| | 上下ボタン | 分離順の並べ替え |
| Δv の積み上げ | グラフ | 全段の Δv を積み上げて表示 |

各段の Δv はツィオルコフスキーの式により、その段を点火する時点の総質量と、燃焼終了時の総質量から求める。行を選択すると、3Dビューポートでその段を強調表示する。

3Dビューポートの段の色分けは、表示切り替えの1つとして残す。色分けを有効にすると、分離機構を跨ぐ配管を別色で表示する。

### 9-2. 配管モード

左パネルの主眼は「自動敷設の結果の確認」と「手動の上書き」である。

| 区画 | ウィジェット | 内容 |
|---|---|---|
| 自動敷設 | `Button` | 自動敷設をやり直す |
| | `Button` | 手動の上書きをすべて破棄する |
| 供給の診断 | 一覧 | エンジンごとの供給状態（供給あり／配管が繋がっていない／流量不足／イナートガス不足） |
| 分離を跨ぐ配管 | 一覧＋`ToggleSwitch` | 分離機構を跨ぐ配管の候補と、跨ぐことを許すかどうか（クロスフィード） |
| 手動で敷く | `ObjectPicker` | 通す推進剤の種別（酸化剤・還元剤・RCS推進剤・イナートガス） |
| | `SegmentedControl` | 口径 |

中央のビューポートは配管表示に切り替わり、推進剤の種別ごとに色分けした線を背骨に沿って描く。自動敷設された配管と手動で敷かれた配管は線種で区別する。エッジをクリックすると、そのエッジに選択中の配管を敷設または撤去し、その区間は手動の上書きになる。

供給されていないエンジンは赤く強調し、原因を表示する。分離を跨ぐ配管の一覧で跨ぐことを許すと、そのエンジンへ自動敷設が届くようになる。

### 9-3. 性能計算の呼び出し

編集操作のたびに、編集中の設計データから次を呼ぶ。

```
VesselBlueprint
    ├─► autoRouteFeed()            → 配管の敷設（手動の上書きを保持）
    ├─► resolveFeed()              → 配管モードの診断
    └─► deriveStages()             → 段の一覧と Δv
```

いずれも解析式であり、エッジ数に対して線形であるため、毎操作の実行で問題にならない。

### 9-4. 飛行中のHUD

飛行中に置くパネルのうち、この巻が担当するものは2つである。いずれも個別に折り畳める。

- **段** — 段の一覧、次に分離する段、段ごとの残 Δv。分離の実行ボタン。
- **ペイロード** — ペイロード倉庫の内容と、放出の実行ボタン。

加圧ガスの残量と、その残量での残り燃焼可能時間は、推進系パネルの主機の行に表示する。

## 10. 段階的な実装計画

各段階は、それ単体で検証できる状態で区切る。分離を先に置くのは、分離が配管に依存せず、実装が軽く、単体で価値が大きい（多段ロケットが飛ぶようになる）ためである。配管を跨ぐ分離（クロスフィードの切断）は、配管が入ってから足す。

| 段階 | 内容 | 依存 | 検証 |
|---|---|---|---|
| A | `splitStages` と分離の物理を実装する。分離後の背骨・質量特性の再計算を含む。段を跨ぐ燃焼の判定と、ノードの分割提案を計画UIに入れる | 第1巻・第2巻 | 単体テスト（連結成分の分割、運動量保存、`propellantForDv` による分割点の一致）。実行時検証（分離して2つの物体が別々の軌道に乗る） |
| B | ペイロード倉庫と放出を実装する。弾薬の放出が既存の補給パッケージと同じ実体を生成する。弾薬供給の段による制約を含む | A | 無人ブースターで弾薬を軌道に投入し、艦艇が既存の接近回収で取れること |
| C | 配管を搭載要素として定義し、`autoRouteFeed` と `resolveFeed` を実装する。推進剤の種別ごとに連結成分を1度だけ求め、タンクとエンジンが同じ連結成分に属するかで供給を判定する。流量制限と、分離による流路の切断・再計算を含む | A | 単体テスト。自動敷設が繋がった構成を作ること、手動の上書きがやり直しで保持されること、流量不足の構成で期待どおりの `EngineFeedResult` が返ること |
| D | `pressurant.ts` を実装し、与圧の消費と与圧低下による推力低下を燃焼に組み込む。イナートガス枯渇による推力喪失と、極低温・亜酸化窒素の自己加圧を含む | C | 加圧式とポンプ式の同一機体で、同じ Δv を得るのに必要なイナートガス質量が期待どおり差を持つこと。与圧低下時に加圧式は比例して、ポンプ式は下限で急に推力を失うこと |
| E | 設計エディタの配管モードと右パネルの段一覧、飛行中の段パネル・ペイロードパネルを実装する | A〜D | 実行時検証 |

A・C が構造的な山場である。A で機体が1つの実体でなくなり、C で流路が機体の性能を決めるようになる。

## 12. 技術的リスク

1. **分離後の状態の再構成** — 分離は背骨・質量・重心・慣性テンソル・推進剤残量・流路のすべてを変える。これらを一箇所で一括して再計算し、どれか一つだけが古い値のまま残ることのないようにする。分離直後の接触判定の無効化も、この再構成と同じ時点で行う。
2. **段を跨ぐ燃焼の分割** — 分割したノードは、段の分離と次の段の点火を挟む。1つ目の燃焼終了時刻・分離時刻・2つ目の点火時刻の3つが、点火あたりの推進剤損失を含めて整合している必要がある。分割の提案を受け入れた時点で3つをまとめて生成し、後から片方だけを編集できないようにする。
3. **自動敷設の安定性** — 設計を変更するたびに自動敷設をやり直すため、無関係な編集で配管が別の経路に移ると、プレイヤーには不可解に見える。最短経路が同距離で複数ある場合の順序を、エッジIDによる決定的な規則で固定する。
4. **手動の上書きと設計変更の衝突** — 手動で敷いた区間のエッジが削除されたり、種別が変わったりすると、上書きが宙に浮く。参照先を失った上書きは破棄し、破棄したことを診断に出す。黙って消すと、プレイヤーは自分の設定が効いていない理由を追えない。
5. **配管の探索コスト** — 流路の解決は、タンクとエンジンの組ごとにグラフ上の経路を探すことになる。エッジ数に対して線形になるよう、推進剤の種別ごとに連結成分を1度だけ求め、タンクとエンジンが同じ連結成分に属するかで判定する方式にする。
6. **クロスフィードと分離順の整合** — 分離機構を跨ぐ配管は、分離順によっては、まだ燃焼中のエンジンへの供給を断つ。分離順の並べ替えの時点で、その順序で断たれる供給を検出して警告する。
7. **推力軸のずれによる制御不能** — 側面に非対称にブースターを束ねると、推力軸が重心を大きく外れる。設計エディタでの警告と、ジンバル補償の両方が必要である。補償しきれない設計は生産を拒否する。
8. **UIの総量** — この巻はエディタに配管モード1つと右パネルの常設表示、飛行中に2つのパネルを加える。既存のパネルへ統合できないかを追加のたびに確認し、置き場の規約に従うこと。
