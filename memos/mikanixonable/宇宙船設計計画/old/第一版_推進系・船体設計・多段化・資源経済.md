## 0. 要件に対する修正提案（先に読むところ）

| # | 元の要件 | 修正/廃止 | 理由 |
|---|---|---|---|
| 0-1 | 固体ブースターは「アルミナ、ABS樹脂」を選べる | **アルミナ → アルミ粉末**に訂正。固体は「酸化剤(AP/AN) × 燃料兼バインダ(HTPB, Al粉末)」の組で選ぶ。ABS は**ハイブリッド**（固体燃料 + 液体/亜酸化窒素酸化剤）枠へ移す | アルミナ(Al₂O₃)はアルミ燃焼の**生成物**であって推進剤ではない。ABS は実在のハイブリッドロケット燃料（3Dプリント燃料グレイン）で、固体一体型とは着火・スロットリング特性がまったく違う — この差はゲーム的にも意味がある（ハイブリッドは再着火・絞りができる） |
| 0-2 | 液体燃料は「液水、液酸、メタン、ヒドラジン、シラン」から酸化剤と還元剤を選ぶ | 枠組みは維持。ただし**「任意の組み合わせ」ではなく登録された推進剤ペア(`PropellantPair`)から選ぶ**形に限定 | 任意組み合わせは Isp が定義できない（実測値が要る）。ペア表なら実データを持てて、かつ選択肢の数は十分多い（後述の表で8種） |
| 0-3 | RCS ガスを消費しないフライホイール | 採用。ただし**角運動量飽和(saturation)とアンローディング**を必ず入れる | 入れないと「電力さえあれば無限に姿勢制御できる」ため RCS が死ぬ。飽和 → RCS で吐き出す、という往復が入って初めて両者が併存する。実機（ISS の CMG デサチュレーション）そのままでもある |
| 0-4 | ノードとエッジで骨格を組み、一定距離に外皮が生成される | 採用。ただし**外皮はエッジ半径のカプセル和(smooth union)**として定義し、外皮の体積・慣性テンソル・断面積(抗力)を**そこから導出**する | 「外皮の内容積でタンクが置ける」を成立させるには体積が要る。同じ形状から慣性テンソルまで出せば、`PLAYER_INERTIA_*` の手置き定数が消え、扁平な船は本当に回りにくくなる（ジャニベコフ効果も設計由来になる） |
| 0-5 | 外皮を形成しないデタッチできるエッジで束ねる | 採用。これを**そのままデカプラ(§4)にする** — 「外皮を作らない構造エッジ」= ステージ間結合。要件2と要件3を別機構にせず1つに統合する | 別機構にすると「束ねる」と「多段」でUIが二重になる。骨格エディタの中で完結させる |
| 0-6 | ブースターを自動操縦で軌道投入し軌道上で接合 | 採用。ただし**新しい誘導系は作らない** — 既存 `PlanExecutor`（`'powered'` 実行モード）+ 既存ドッキング判定を再利用する | すでに「計画軌道を自動で焼く」実装がある。ランデブー最終接近だけ足りないので、そこだけ追加（§4-4） |
| 0-7 | 月面基地とその鉱山を操作できる | 採用。ただし**月面基地は「船で行く場所」ではなく、当面は基地ビュー上の生産・輸送パネル**として実装 | 月面着陸・上昇は別ゲーム1本分の仕事量（降下誘導、地形、着陸脚）。経済ループ（採掘→生成→NRHOへ輸送→使用）だけ先に閉じれば、要件の狙いは満たせる。着陸は将来のフェーズに置く |
| 0-8 | （追加提案）推進剤の劣化 | ボイルオフ（極低温）と分解（ヒドラジン）を**保管中のみ**モデル化。飛行中は無視 | 飛行中の毎フレーム計算に見合う面白さがない。「NRHO に液水を貯めておくと減る」ほうが備蓄判断として効く |
| 0-9 | （追加提案）推力軸と重心のずれ | **フェーズ後回しにするが、データ上は最初から持つ** | 骨格から重心が出るので、非対称にエンジンを付けると勝手にトルクが出る。面白いが、`PlanExecutor` の焼き込み精度を壊すので、まず「重心を自動で合わせる」補正 ON をデフォルトにして、OFF を上級者オプションにする |

## 2. 推進系の分離（エンジン / 並進RCS / フライホイール）

### 2-1. 現状

`PlayerThrottle` が並進推力も姿勢トルクも1つの `ThrusterPart` から取り、燃料は `RcsTankPart` から `Ship.consumeFuel` で引いている。つまり **3つの物理的に別のシステムが1つのパーツに畳まれている**。

### 2-2. 分離後のモデル

| システム | 役割 | 推進剤 | Isp | 特性 |
|---|---|---|---|---|
| **主機 (EngineBank)** | 軌道変更（Δv） | 液体/固体/ハイブリッド | 300〜450 s | 推力大、ジンバル or 固定、始動/停止コスト |
| **並進RCS (TranslationRcs)** | 近接機動・ドッキング・姿勢制御の飽和解除 | 単推進剤 or 冷ガス | 60〜230 s | 推力小、全6方向、応答即時 |
| **フライホイール (ReactionWheels)** | 姿勢制御のみ | **推進剤を消費しない**（電力のみ） | — | トルク小・連続、**角運動量が飽和する** |

**姿勢制御の調停** — 新設する `AttitudeControlSystem` が、`PlayerThrottle`（手動）と `PlanExecutor`（自動操縦）が要求したトルクを1か所で受けて配分する:

1. 要求トルク τ を、まずホイールで出せるだけ出す（`min(τ, wheelMaxTorque)`、かつ各軸の蓄積角運動量 `h` が `hMax` に達していない範囲で）。
2. 出したぶんホイールは逆向きに角運動量を溜める: `h += -τ_wheel · dt`。同時に電力を消費（`P = |τ·ω_wheel|` の近似、`power.ts` から引く）。
3. 足りないぶん、または飽和した軸は **RCS が出す**（推進剤消費）。
4. `|h|` が `hMax·DESAT_THRESHOLD` を超えたら**アンローディング**: RCS で外部トルクを与えつつホイールを減速して `h` を吐き出す。自動（既定）/手動（HUDボタン）を選べる。

これで「静穏時はホイールだけで無限に姿勢を保てる（推進剤ゼロ）／激しい戦闘機動の後は必ず RCS を吐く」という緊張が生まれ、RCS タンク残量が戦闘の資源になる。

**要件外だが必須の帰結**: `Ship.totalTorque` は今後 `AttitudeControlSystem` が持つ「今この瞬間出せる最大トルク」に置き換わる。飽和状態によって値が変わるので、HUD の姿勢制御表示（新設）に `h/hMax` のメーター（`widgets/meter.ts`）を出す。

### 2-3. 新規/変更するモジュール

```

    allocateTorque(request, wheelState, wheelSpec, rcsSpec) -> {wheel, rcs, powerDraw}
    desaturationTorque(h, hMax, spec) -> Vec3
src/game/player/attitude-control-system.ts (新規)
    ReactionWheels の h を保持し、上の純関数を毎 update 呼ぶ。PlayerThrottle と PlanExecutor の
    両方から torque 要求を受ける唯一の窓口。

    updateThrustState は EngineBank / TranslationRcs のどちらを使うかを推力方向と大きさで選ぶ
    （前後の大推力 = 主機、それ以外 = RCS、が既定。手動オーバーライド可）。
```

## 3. 骨格式の船体設計（ノード・エッジ・外皮）

### 3-1. データモデル

```ts
// src/game/vessel/skeleton.ts
export interface SkeletonNode {
  readonly id: string;
  readonly pos: Vec3;          // 船体ローカル座標 [m]
}
export type EdgeKind =
  | { kind: 'hull';    radius: number }   // 外皮を作る。内側が与圧/タンク容積になる
  | { kind: 'strut' }                     // 外皮を作らない構造材。束ねるときのつなぎ
  | { kind: 'decoupler'; separationImpulse: number }; // 外皮を作らず、切り離せる（§4）
export interface SkeletonEdge {
  readonly id: string;
  readonly a: string; readonly b: string; // node id
  readonly kind: EdgeKind;
}
export interface VesselSkeleton {
  readonly nodes: readonly SkeletonNode[];
  readonly edges: readonly SkeletonEdge[];
}
```

- **閉路を許す**（要件どおり）。したがって「ツリー」ではなくグラフとして扱う。三角形・はしご状に組めば扁平な船になる、という要件はこれで満たされる。
- エッジの**長さと角度は連続値ではなく量子化**する: 長さは 0.5 m 刻み、角度はノードから伸びる方向を 15° グリッドにスナップ。完全自由だと「モデリングをさせたくない」という要件に反し、また対称な船が作れなくなる。
- **対称ミラー編集**を必須機能とする（YZ 平面ミラー）。片側を編集すると反対側が同時に生える。非対称機は明示的にミラーを切ったときだけ作れる。

### 3-2. 外皮の生成 — 何を計算するか

外皮は「hull エッジそれぞれを半径 r のカプセル（円柱＋両端半球）とし、その和集合を smooth-min で滑らかにつないだ立体」と定義する。一本のエッジなら円筒＋半球端 = ロケット形になり、要件の「一本のツリーなら円筒形のロケット」と一致する。

この立体から、**ゲームが必要とする5つの量**を出す:

| 量 | 用途 | 計算法 |
|---|---|---|
| 体積 V | タンク容積の上限 | 解析（カプセルの体積和 − 交差の重複補正）でよい。交差はノードごとに球1個ぶん引く近似で誤差数% |
| 重心 CoM | 推力軸ずれ、回転中心 | 質量分布（構造 + 搭載物の配置座標）から解析 |
| 慣性テンソル I | 姿勢運動（`stepAttitude`） | 各カプセルの慣性テンソルを平行軸定理で合成 |
| 参照断面積 A | 抗力 `bcInv = Cd·A/m` | 主軸3方向の投影面積。実際は速度方向で変わるので、当面は最大値を使う（保守的） |
| 表面積 S | 放熱の上限、被弾面積 | カプセル側面積の和 − 交差補正 |

**全部が解析式で出る**ので、マーチングキューブや数値積分は不要。これが「カプセル和」を選んだ理由（メタボール的な真の smooth union だと数値積分が要る）。描画だけ smooth union の見た目にし、物理量はカプセル和で計算する — 見た目と物理の乖離は数%で、`/refactor-fixed` の「physics の純度」を犠牲にしない。

```
src/physics/hull-solid.ts   (新規, 純関数, test:physics 対象)
    capsuleUnionVolume(edges) / capsuleUnionInertia(edges, density)
    capsuleUnionProjectedArea(edges, axis) / centerOfMass(...)
```

テストは「単一カプセル → 解析値と一致」「同一カプセル2本を重ねる → 1本ぶん」「L字 → 慣性主軸が対角化されて3値とも異なる（＝ジャニベコフ効果が起きる形）」を pin する。

### 3-3. 内容積の割り当て

外皮の内容積 V に対して、プレイヤーは「どのエッジ区間に何のタンクを置くか」を割り当てる。UI としては**エッジをクリックしてそこに入るものを選ぶ**（そのエッジのカプセル体積が上限）。

- 極低温タンク（液水/液酸/液メタン）は**断熱材ぶん実効容積が減る**（係数 0.85）。液水は特に密度が低いので、同じ Δv を出すのに巨大な外皮が要る — これがそのまま「液水機は太い」という見た目になる。
- 常温タンク（ヒドラジン/NTO）は係数 0.95。
- 固体グレインは**タンクではなくエッジそのもの**（ケースが構造材を兼ねる）。したがって固体ブースターは外皮エッジ1本 = モーター1基。

要件の「セントールのように外部に配管が露出する」は、**液体エンジンを持つステージには自動で外部配管メッシュを生やす**ことで表現する（骨格エッジに沿ってチューブを走らせる。プレイヤーは配置しない）。シールドは hull エッジに付ける装甲パーツとして、可動シールドは §3-5 の可動部として扱う。

### 3-4. 描画

```
src/render/hull/hull-mesh.ts (新規)
    buildHullMesh(edges, lod) -> THREE.BufferGeometry
```
- 実装は**カプセルごとのメッシュを生成して結合し、接合部をノード球でごまかす**方式を第一候補にする（マーチングキューブは頂点数と生成コストが重く、`InstancedPool` にも乗らない）。
- 設計変更のたびに1度だけ生成し、`Object3D.toJSON()` 相当でキャッシュ。毎フレーム生成しない（既存の「build は構築、sync は追従」の分離を守る）。
- LOD は既存 `render/screen-lod.ts` の考え方を流用し、遠距離では単一カプセルの近似に落とす。

### 3-5. 可動部（ラジエータ・シールド・ソーラー）

既存のラジエータ（アコーディオン）と同じく、**ノードに取り付ける可動アタッチメント**として扱う。骨格が変わっても取り付け規約（ノード + ローカル軸）が同じなら既存の `radiator.ts` の折り畳み計算はそのまま使える。

## 4. 多段ブースターシステム

### 4-1. ステージの定義 — 新しい概念を足さない

**ステージ = 骨格グラフから decoupler エッジを取り除いたときの連結成分**。これだけ。プレイヤーは「ステージ1」「ステージ2」と明示的に区切るのではなく、デカプラを挿すと自動的に分かれる。KSP の「ステージング編集画面」に相当するものは、**分離の順序を並べ替える小さなリスト**だけで済む。

```ts
// src/game/vessel/assembly.ts
export interface VesselStage {
  readonly id: string;
  readonly edgeIds: readonly string[];   // この連結成分に属するエッジ
  readonly hasCockpit: boolean;          // コックピットを含む = 分離後も操作対象
}
export function splitStages(skeleton: VesselSkeleton): readonly VesselStage[];
export function separationOrder(skeleton: VesselSkeleton): readonly string[]; // decoupler id 列
```

- **コックピットを含むステージが本体**。それ以外はブースター。
- 分離すると、切り離されたステージは**新しい `GameEntity`（`Booster extends Ship`）として生成**され、`separationImpulse` で相対速度を得て離れる。誘導装置を積んでいれば自機と同様に `Plan`/`PlanExecutor` を持ち、積んでいなければただの `DebrisPiece` 相当（ただし質量と慣性は本物）。
- 分離後の本体は**その場で骨格・質量・慣性・タンク残量を再計算**する。既存の `Ship.refreshFromParts()` の位置に `Vessel.refreshFromAssembly()` が入る。

### 4-2. 分離の物理

分離は `KinematicState` の不連続な上書き（`GameEntity.state` setter = `DynamicTrajectory.reset`）で表現する。運動量保存を守る:

```
m_total·v = m_upper·v_upper + m_lower·v_lower
v_upper = v + (m_lower/m_total)·Δv_sep,  v_lower = v − (m_upper/m_total)·Δv_sep
```

`Δv_sep` は decoupler の `separationImpulse / 換算質量`。既存の `simulation/collision-response.ts` の考え方と同じで、実装も同じ形にできる（衝突の逆）。分離直後は両者が接触しうるので、分離後 N 秒は互いの `contactsWith` を無効にする（`attachedTo` の既存機構を流用）。

### 4-3. 燃焼シーケンス

- **同時燃焼**（束ね式・ブースタ並列）と**逐次燃焼**（直列多段）の両方を許す。`EngineBank` は「今アクティブなステージ群のエンジン集合」であり、`PlanExecutor` はそこから `totalThrust / mass` を得る。
- 推進剤が尽きたステージは**自動分離を提案**（HUD ヒント）するが、自動では切らない — 切ると軌道が変わるので、プレイヤー（または `PlanExecutor` の計画）の判断に委ねる。
- `PlanExecutor` の `burnDurationFor` は現状「一定加速度」を仮定しているが、多段では**燃焼中に質量が減って加速度が上がる**。ここは**ツィオルコフスキー式に置き換える**必要がある:

```
src/physics/tsiolkovsky.ts (新規, 純関数)
    dvFor(m0, mf, isp) / burnTimeFor(dv, m0, thrust, isp, g0) / massAfterBurn(...)
```
`plan-executor-math.ts` の `burnDurationFor(dvMag, accel)` を `burnTimeFor(dv, m0, thrust, isp)` に差し替える。既存テスト `plan-executor-math.test.ts` は「無限大を返す」等の境界を保ったまま拡張する。**これは要件に書かれていないが、多段を入れるなら必須の訂正**（一定加速度仮定のままだと、質量比の大きい機体で点火時刻が実際より遅れ、ノードを外す）。

### 4-4. 軌道上でのブースター接合（要件 0-6）

「戦闘後の帰投用ブースターを先に軌道へ上げておき、あとで合体する」というループ。必要なのは3つだけ:

1. **自動投入** — 既存 `PlanExecutor` の `'powered'` モードをブースターにも許す（`Player` 専用ではなく `Ship` の機能に上げる）。基地からブースターを「この軌道へ」と指定して発進させる。
2. **ランデブー最終接近** — 相対距離 < 数百 m、相対速度 < 数 m/s になったら、既存 `Docking.checkProximity` と同じ判定でドッキング可能にする。ここは**新規に誘導を書かず、ドッキング判定の対象を「基地」から「ドッキングポートを持つ任意の `Ship`」に一般化**するだけ。
3. **結合** — 双方の骨格を、ドッキングポートのノード同士で接合した1つの `VesselSkeleton` にマージする。デカプラが1本挿さった状態と等価になるので、そのあとの分離もそのまま動く。

これで `dev.md` L76 の「船と船をドッキングし、電力と物資の融通を行えるようにしたい」も同じ機構で満たされる（結合中は `PropellantStore` と `PowerSystem` を共有）。

## 5. 推進剤の種類

### 5-1. 物性表（`src/physics/propellant.ts`, 純関数 + データ）

実データに基づく。Isp は真空値、密度は貯蔵状態。

**液体（酸化剤 × 還元剤のペアで登録する）**

| ペア | 真空 Isp [s] | 混合比 O/F | 平均密度 [kg/m³] | 保管 | 月での調達 |
|---|---|---|---|---|---|
| LOX / LH₂ | 450 | 5.5 | 360 | 極低温・ボイルオフ大 | ◎ 水氷の電解のみ |
| LOX / LCH₄ | 370 | 3.5 | 830 | 極低温・ボイルオフ中 | △ 炭素が要る |
| LOX / SiH₄（シラン） | 330 | 3.0 | 900 | 酸化剤のみ極低温・自己着火 | ◎ レゴリスのケイ素 + 水素 |
| NTO / MMH | 320 | 2.0 | 1200 | 常温・長期可・毒性 | × 窒素が要る |
| H₂O₂ / ケロシン | 310 | 7.0 | 1290 | 常温・分解あり | × 炭素が要る |

**単推進剤（RCS向け）**

| 推進剤 | Isp [s] | 密度 | 備考 |
|---|---|---|---|
| ヒドラジン（触媒分解） | 230 | 1010 | 長期保管で徐々に分解、毒性 |
| 過酸化水素 | 160 | 1400 | 無毒、分解速い |
| 冷ガス（N₂） | 70 | 高圧タンク | 最も単純、電力すら要らない |

**固体・ハイブリッド**

| 種別 | Isp [s] | 密度 | 特性 |
|---|---|---|---|
| APCP（AP + HTPB + Al粉末） | 265 | 1800 | **点火したら止まらない・絞れない・再点火不可** |
| ハイブリッド（ABS + N₂O） | 300 | 1100 | 絞れる・止められる・再点火可、密度不利 |

**ゲーム的な意味**: 固体は「安く、密度が高く、一度きり」— 帰投用の使い捨てブースターに最適。液水は「Isp 最高だが巨大＆ボイルオフ」— 長期の遠征に向くが放置できない。ヒドラジン系は「性能中位だが常温で何年でも待てる」— 軌道上に置いておく待機ブースターに最適。**シランは月産の目玉**（レゴリス由来のケイ素で作れる中性能・自己着火）で、月面基地の生産チェーンの到達点にする。

### 5-2. 劣化（保管中のみ）

```
src/physics/propellant-decay.ts (新規, 純関数)
    boiloffRate(propellant, tankInsulation, sunlitFraction) -> kg/s
    decayedMass(mass, propellant, elapsedSec) -> kg
```
- **極低温**: 日射に依存したボイルオフ。断熱材と日除け（シールド）で減らせる。NRHO 基地に液水を貯めると数日で目減りするので、「使う直前に作る」運用になる。
- **ヒドラジン**: 触媒毒による自己分解。年単位なのでゲーム内ではほぼ無視できるが、フレーバーとして残量表示に反映。
- **固体**: 劣化なし（グレインのクラックは扱わない）。

飛行中は計算しない（§0-8）。基地の在庫更新時と、船が軌道上で待機している間の**イベント時刻ベース**（`Simulator` の `nextEventTime` に乗せるのではなく、在庫を読むときに経過時間から一括計算）で処理する — 毎フレームのコストをゼロにするため。

## 6. 資源経済（月面基地 / NRHO / 敵ドロップ）

### 6-1. 資源

| 資源 | 産地 | 用途 |
|---|---|---|
| 水 (H₂O) | 月南極の永久影クレーター（採掘） | 電解 → LH₂ + LOX |
| 酸素 | 水の電解、レゴリス還元 | 酸化剤全般 |
| ケイ素 | レゴリス精錬 | シラン、構造材 |
| アルミ | レゴリス精錬 | 固体燃料の Al 粉末、構造材 |
| **炭素** | **敵ドロップのみ** | メタン、HTPB/ABS、ケロシン |
| **窒素** | **敵ドロップのみ** | ヒドラジン、NTO、冷ガス |
| 希少金属 | 敵ドロップ | 高性能エンジン・ホイールの製造 |

要件どおり、**炭素と窒素は月では手に入らない** — これは実際の月資源分布と一致し、かつゲーム的に「低軌道の戦闘に出続けないと、メタンもヒドラジンも作れない」という強制力になる。水とケイ素だけで閉じるルート（LOX/LH₂ と LOX/SiH₄）が存在するので、戦闘を避けても詰まない。

### 6-2. 施設と生産（月面基地）

```
src/game/economy/lunar-base.ts (新規)
  facilities: 採掘機 / 電解装置 / レゴリス精錬炉 / シラン合成炉 / 固体グレイン成形機 / 極低温貯蔵
  各施設は「電力を消費し、入力資源を出力資源に一定レートで変換する」だけの単純なモデル
src/game/economy/resource-ledger.ts (新規)
  月面基地と NRHO 基地それぞれの在庫。輸送はこの2つの間の移動。
src/game/economy/transfer.ts (新規)
  月面 → NRHO の輸送。Δv と輸送機の質量比から「1回に何 kg 運べるか」を計算し、
  輸送に実時間（シミュレーション時間）がかかる。到着はイベントとしてキューに積む。
```

**月面基地は当面 3D 実体を持たない**（§0-7）。基地ビューに「月面基地」タブを足し、施設の稼働状況・在庫・輸送キューを表示・操作する。電力は昼夜（月の 14 日昼 / 14 日夜）で変動させると、蓄電池の設計が意味を持つ — 月の南極なら「ほぼ常時日照の峰」を選べる、という実際の設計判断もそのまま入る。

### 6-3. NRHO 基地

クリエイティブモードとストーリーモードの初期基地を NRHO（近直線ハロー軌道）に置く。既存実装との適合を確認済み:

- `physics/halo.ts` に L1/L2 のハロー軌道の初期状態生成がすでにある。NRHO は地球-月 L2 の南方ハローファミリーの一種なので、**振幅を大きく取った halo 初期状態**として置ける。
- ただし **`halo.ts` の状態は1次近似で、本物の多体積分に投入すると発散する**（`CLAUDE.md` に明記済み）。NRHO を「基地がずっと居る場所」にするには、**station-keeping** が要る。実装は簡単で、基地に小さな `PlanExecutor` を持たせ、近月点通過ごとに数 m/s の維持バーンを自動で焼く。これは実際の Gateway の運用そのままで、かつ「基地も推進剤を消費する」という経済圧になる。
- 代替案として、基地だけ多体積分から外して**解析的な NRHO 軌道を辿らせる**手もある（`CelestialBody` に近い扱い）。実装は軽いが、「基地も物理に乗っている」という一貫性を失う。**station-keeping を推奨**。

## 10. 主なリスク

1. **`render/ships.ts` の事前ベイク前提が崩れる** — 現状は `npm run export-assets` で焼いた JSON を読むだけ。骨格生成は実行時生成なので、生成コストと `WebGPURenderer` のジオメトリキャッシュ（差し替え不可）の両方に注意が要る。設計変更時に1度だけ生成し、以後は差し替えない運用を守ること。
2. **`PlanExecutor` の精度** — 質量変化を入れると点火時刻の閉形式が消える（`burnTimeFor` は解析で出るが、途中で段が切れると不連続）。段の切り替わりを跨ぐ燃焼は**段ごとに分けて計画する**のが正解で、跨ぐ計画は UI で禁止するのが安全。
3. **セーブ互換** — 船の表現が根本から変わるので、旧セーブは「既定の骨格に読み替える」以上のことはできない。`SAVE_VERSION` を上げ、読み替え不能な場合は明示的に拒否する（黙って壊れた船を出さない）。
4. **UI の総量** — 骨格エディタ + ステージ + 推進剤 + 経済で、基地ビューのタブが一気に増える。`DESIGN-RULES.md` の置き場規約に沿って、タブを増やす前に「これは既存タブの中に入らないか」を毎回問うこと。
5. **NRHO の維持** — §6-3。1次近似の初期状態をそのまま多体積分に入れると発散する。station-keeping を最初から入れないと、基地が数日で行方不明になる。
