# 第11版_1 着手可能な実装計画

作成日 2026-08-20。状態: 未着手。

第10版までの計画・仕様文書に残っていた未実装項目のうち、**いま着手して完了まで持っていけるもの**を
집めた。判断が要る設計上の穴が残っているもの、既存の中核概念の作り替えを伴うものは
`第11版_2_保留する目標.md` へ分けた。

## 1. 実現性の判定基準

次の4つをすべて満たすものをこの文書に置く。1つでも欠ければ第11版_2 へ回す。

1. **決めるべき設計判断が残っていない** — 何を作るかが既に定まっており、着手前に答えを出さねば
   ならない問いが無い。
2. **拠り所がコードに在る** — 必要な純関数・データ・描画機構が既に実装済みか、既存のものから
   素直に導ける。「概念そのものがコードベースに存在しない」ものは含めない。
3. **既存の中核の作り替えを伴わない** — `GameEntity.att` のような、多数の消費者が単一値を前提に
   している表現を拡張する必要が無い。
4. **1つの変更セットで閉じられる** — 他の未実装項目の完成を待たない。

## 2. A. 組立UIの残作業

`old/第10版_3_Operationsビュー組立UI_残作業実装計画.md` の内容を、上の基準で選別したもの。
そこに書いた技術的制約(辺長の 0.5m 量子化、`mateVerdict` の空の契約、lateral ポートが候補に
上がらないこと、ドラッグ状態機械が部品型に固定されていること)はすべてこの文書でも前提とする。

**その計画で「未決定」としていた「組立セッション中のクリックの持ち主」は、調べた結果すでに
解決している** — `Docking.startAssembly` は `pauseGame()` を呼び、`Game.handlePointerInput` は
先頭で `if (this._isPaused …) return;` する。一方 `docking.updateAssembly` はポーズの外で
呼ばれている。**セッション中はクリックキューが誰にも消費されない**ので、順序の入れ替えも
入力ゲートの変更も要らない。

### A1. 3D選択と、クリック操作の一本化 — 他の前提

`AssemblyDragController` の `document` `pointerup` 購読をやめ、掴み・置き・3Dからの掴み上げを
`Docking.updateAssembly` 内の `input.takeClicks(...)` 1箇所へ集約する。同じキューを1箇所で
消費するので「離した瞬間に置いて、同じ離しで拾い直す」取り違えが構造的に起きない。
`DEVELOP/DESIGN-RULES.md` §7 が禁じる `document` 直付けも1つ消える。

`AssemblyDragController.pickAt(...)` を足し、対象の描画オブジェクトへレイキャストして
`userData['partVisualRef']` / `['assemblyNodeId']` / `['assemblyEdgeId']` を読む。
**この3つの目印は `hull-mesh.ts` と `render/vessel-wireframe.ts` が今も書いており、
読む側だけが不在**なので、目印を付け直す作業は要らない。

- 拠り所: レイの向きとカプセル広域絞り込みは `AssemblyDragController` に実装済み。
- **副産物として「格納艦どうしの部品移送」が満たされる** — `beginDrag(part, sourceTargetId, …)` と
  `drop(targetId)` は既に移送元と移送先を別々に取り、`dragTarget` は現在のタブの対象を返すので、
  「艦Aで掴む → タブ切替 → 艦Bで離す」で `session.movePlacement(A, B, …)` が走る。
  独立した移送UIは足さない。

### A2. 組立対象へのカメラ寄せ

`ChaseCamera.update` が対象から読むのは `state.r` と `att.q` の2つだけなので、引数を
`{ position: Vec3; attitude: Quat } | null` という狭い構造的インターフェースへ広げる
(`PlanExecutorShip` / `DisplayDurationSource` / `CapabilityVessel` と同じ流儀)。実体から姿勢を
取り出すのは `CameraSystem`/`CombatCameraSystem` 側の1行になる。

これで**実体を持たない下書きと、`state` が止まっている格納艦**も対象にできる —
`Docking.targetPose` が3種すべてについて `{position, attitude}` を既に返している。

距離は `deriveCapsules` と `tree.nodes` の `circumradius` から外接半径を求め、新設の
`ASSEMBLY_CAMERA_DISTANCE_MARGIN` を掛ける。**`deriveCapsules` は分離機構の辺を飛ばす**ので、
カプセルだけでは分離機構の先を取りこぼす。ノード位置も併せて見る。
`ChaseCamera.dist` は public な可変フィールドなので代入で足りる。

### A3. 新規船下書きの入口

`Docking.createDraft`/`buildDraft` は public で動作するが、`src/` に呼び出し側が1つも無い。
`AssemblyPanel` に「新規船下書き」ボタンと、対象が下書きのときだけ出る「建造して格納」ボタンを
足して配線する。建造は資源を引くので、不足内容の但し書きは `base-operations-window.ts` の
生産タブが既に持つ形(`producibility` の結果を文言へ畳む)をそのまま使う。

### A4. ノード・エッジの削除と、既存の原始図形の断面編集

`removeNode`/`removeEdge`/`editSection` は実装済みで、`DockWorkbenchSession.applyAssemblyEdit` が
**任意の `AssemblyEditResult` を1つの取り消し可能なコマンドとして適用する汎用の口**として
既にある(呼び出し側が `src/` に1つも無いだけ)。A1 が3D選択を与えれば、あとは
`AssemblyPanel` に選択中ノードの面を足して繋ぐだけ。

範囲は**既に在る原始図形の編集に限る** — `shape`(種別・`sides`/`branchCount`・半径)と
`phaseAngle`。いずれも `SegmentedControl` と `ValueInput` で組める。
**原始図形の追加・削除(`attachment` による貼り合わせ)は第11版_2 へ回す**(§2-F)。

確定1回で1履歴(`old/第10版_3_Operationsビュー組立UI実装中の決定事項.md` §9-4 の決定)。

### A5. 構造材のドラッグ生成(片端が自由な場合) — この節で最大

棚に**部材**(種別・長さ・断面)を並べ、空きポートへ吸わせて離すと、反対側の端に新しいノードが
`portFrame.origin + portFrame.z × 長さ` に生成され、部材自身が辺になる。
`addNode({node, edge})` 1回で済み、確定は `applyAssemblyEdit` を通す。

**長さを先に決めるので、辺長の 0.5m 量子化は構成上つねに満たされる** — 棚が 0.5m 刻みの長さしか
提供しなければ、`validateTree` に弾かれる経路が存在しなくなる。カーソルの指す任意の位置に
ノードを置く操作は提供しない(ノードは接続の結果として立つ)。

必要な作業は4つ。いずれも拠り所がある。

1. **lateral ポートの列挙** — `mount-candidates.ts` は今のところノードの軸ポートとエッジ外表面
   しか候補にしない。`placeSectionPrimitives(node.section)` で原始図形を並べ、面ごとに
   `portFrame` を求め、`occupiedPorts` で空きを見る。**占有判定を新しく書かない**
   (`/add-feature` の規則)。部品用の既存の呼び出しの答えを変えないよう、ポート種別で絞れる形にする。
2. **ドラッグ状態機械の一般化** — `DragState.part: AnyPart` と `SnapCandidate.placement: PartPlacement`
   を、部品と部材の判別共用体へ広げる。部材の確定は `DockWorkbenchController.drop` を通らず
   `applyAssemblyEdit` へ抜ける。
3. **部材のゴースト** — 2ノード1エッジの使い捨て `VesselTree` を組み、`hullShapeOf` →
   `buildLoftGeometry` に通せば、本物の外皮と同じ経路で作れる。新しいメッシュ生成器は要らない。
4. **3D上の既存の辺を掴んで外す**(`removeEdge`、端のノードが孤立するなら `removeNode` も)。

### A6. 重複した判定語彙の廃止

`assembly-mode.ts` の `mateVerdict` は真偽値をラベルへ写すだけの純関数で、5項目のうち
`occupied` と `lengthFits` は `assembly-editor.ts` の `occupiedPorts` / `validateTree` と判定が
重複し、`widthFits` / `phaseFits` / `withinWorkArea` には実装がどこにも無い
(特に「作業範囲」という概念はコードベースに表現が存在しない)。現に動いている部品ドラッグも
`mateVerdict` を呼ばず `MateVerdict` を手で組んでいる。

**接続可否の正本を `assembly-editor.ts` 1箇所に閉じ**、`assembly-mode.ts` から `src/` の誰も
使っていない輸出を削除する。`SnapCandidate.verdict` は `AssemblyEditResult` から直に持つ形へ
変える(表示に要るのは可否と理由の文言だけで、後者は `AssemblyEditError.message` が既に
日本語で持っている)。`DockWorkbenchController.failureText` も不要になる。

同じ変更セットで `tests/unit/assembly-mode.test.ts` と `tests/unit/dock-workbench.test.ts` を直す。
削除範囲を決める前に、`AssemblyDraft`/`blueprintFromDraft` が第2巻 §4 の設計データで要るかどうかを
突き合わせる。

## 3. B. 機体の種別を積荷から導く

このプロジェクトの方針は「艦種は継承ではなく積荷である」(CLAUDE.md `src/game/vessel/`)。
述語も派生の仕組みも既にあるのに、**種別が実際の判断に効いていない**、あるいは
**構築時に一度決めたきり再導出されない**箇所が2つ残っている。どちらも同じ原因なので併せて直す。

### B1. 宇宙船と貨物の分類を、実際の判断へ接続する

`old/第10版_3_推進・建造・運用.md` §3.2:
> 「この分類を、操作対象選択、自動操縦、ドッキング、基地ドック、HUD、セーブへ接続する。」

`vessel/capabilities.ts` の `isCargo` は実装済みで単体テストもあるが、**`src/` に呼び出し側が
1つも無い**。分類が存在するだけで、何の判断にも効いていない。

- `ActiveVesselController.set`/`setOrNull` が貨物を操作対象にするのを断る。
- 部品の着脱で宇宙船⇄貨物が変わることを、**適用の前に**知らせる(同 §9 の
  「分解によってコア部品が失われる場合、宇宙船から貨物への降格を適用前に表示する」)。
  `Docking.commitAssembly` は今のところ構造の検証しかしておらず、コア部品の有無を見ていない。
- HUD のどこかに種別を出す(プロパティウィンドウの行が素直)。

拠り所は述語そのもの。作業は配線と、降格判定を確定経路へ1つ足すこと。

### B2. 船に基地モジュールを結合して基地にできるようにする

`crewedShipDesign` と `orbitalBaseDesign` は `vessel-designs.ts` で別々の定義として並んでおり、
CLAUDE.md 自身がここを「艦・基地・敵対機の違いを知っている唯一の場所」と書いている。
**基地であることを、設計の出自ではなく `base_module` を積んでいるかどうかだけから導く。**

#### これは新機能ではなく、既に到達できて既に食い違っている経路である

`default-blueprints.ts` の `producibleParts()` は `orbitalBaseAssembly` の部品を含むので、
**`base_module` は今の生産タブで倉庫に作れる。**そして現行の部品ドラッグで格納艦へ取り付けられる。
確定すると `Docking.commitDockedAssembly` が `blueprintDesign` から `Vessel` を作り直し、
コンストラクタの `hasBaseModule(this)` が真になって `baseState` が生える —
**基地への昇格は既に半分動く。**残り半分が揃っていない。

#### 何が積荷から導かれていて、何が導かれていないか

| 要素 | 導出元 | 再導出されるか |
|---|---|---|
| `baseState` / `collisionGeom` / `equatorNodes` | `hasBaseModule`(積荷) | **構築時の1回だけ** |
| `dockPorts` / `dockCapacity` | 基地モジュール部品 + 形状 | 都度 |
| `renderObject` / `massProperties` / `parts` / `radius` | 設計の工場 | 適用経路による |
| `hpRegenRate` / `reentryAltMargin` | 設計の工場 | **`private readonly`、一度も再導出されない** |

#### 3つの具体的な食い違い

1. **確定の経路が2つあり、選ぶ設計の工場が非対称。**
   格納艦は `commitDockedAssembly` → `blueprintDesign`(すべて積荷から導く汎用の艦)で作り直され、
   基地は `commitBaseAssembly` → `Vessel.replaceAssembly` が**その場で** `orbitalBaseDesign` を
   決め打ちする。**どちらの工場の数値になるかが、積荷ではなく「どの適用経路を通ったか」で決まる。**
   `replaceAssembly` は先頭で `if (!this.baseState) return { ok: false, reason: '基地ではありません' }`
   と断るので、その場での昇格・降格はそもそもできない。

2. **昇格した艦は基地の数値を受け取らない。** `orbitalBaseDesign` は `hpRegenRate: 0` /
   `radius: Math.max(330, hullRadiusOf(assembly))` だが、`blueprintDesign` は
   `hpRegenRate: C.HP_REGEN_RATE` / 下限無しの `hullRadiusOf`。**自己修復する基地**という、
   既存の基地には無い個体ができる。

3. **名簿の分類キャッシュが積荷の変化に気付かない。** `EntityManager.rebuildCachesIfNeeded` は
   `collectionRevision`(登録・除去・prune でしか動かない)が変わったときだけ
   `hasBaseModule(v)` を評価し直す。**名簿の顔ぶれが変わらないまま積荷だけが変わっても、
   `ownShips()`/`baseVessels()` は古い分類のままになる。**しかも3つの分類は
   `else if` で排他なので、昇格は「`ownShips()` から消えて `baseVessels()` に現れる」という
   移動になる。`ActiveVesselController.reclaimDead()` は `ownShips()` を掃くので、
   操作中の艦を昇格させたときの扱いを決める必要がある。

   さらにセーブは `players: ownShips().map(serializeAsShip)` と
   `bases: baseVessels().map(serializeAsBase)` の**2つの配列**へ、この分類のまま書き出す
   (復元も `savedShip`/`savedBase` の別経路)。キャッシュが古いままスナップショットを取ると、
   昇格した艦が艦として保存され、基地の在庫と収容艦を失う。

#### やること

- **設計の工場の選択を積荷から決める。** `replaceAssembly` の `orbitalBaseDesign` 決め打ちをやめ、
  両方の適用経路が同じ規則(`hasBaseModule` を見て工場を選ぶ)を通るようにする。
  併せて `replaceAssembly` の「基地ではありません」の門を外し、昇格・降格を扱えるようにする。
- **構築時にしか決まらない要素を再導出できるようにする。** `baseState` の生成/破棄、
  `collisionGeom`、`equatorNodes`、`hpRegenRate`、`reentryAltMargin`。
- **名簿の分類に無効化の合図を足す。** 積荷が変わったときに `collectionRevision` を進めるか、
  分類専用の世代値を持つ。「操作中の艦が昇格したら操作対象をどうするか」もここで決める。
- **セーブの往復を通す。** 2配列のまま昇格した艦を移すか、1配列にして種別を積荷から導くか。
  後者のほうが方針には合うが、`PlayerSaveData` と `BaseSaveData` は形が違うので影響を見てから決める。
- **降格の規則**: 収容中の艦・在庫・資源が残っている基地から `base_module` を外すことは断る。
  `base-assembly-validation.ts` の `validateBaseAssembly` が既に同じ性格の禁止
  (ドック口の占有、基地モジュールの維持)を持っているので、そこへ揃える。ただし現在
  `Docking.targetValidation` は `target.kind === 'base'` のときしかこれを適用しないため、
  **昇格しうる格納艦にも効く形へ広げる**必要がある。

拠り所はすべて在る(`hasBaseModule`、`blueprintDesign` の積荷からの導出、
`deriveBaseDockingPorts`、`validateBaseAssembly`)。作業は、一度きりの決定を再導出可能にすることと、
2つある適用経路を1つの規則へ揃えること。**この節は横断範囲が広いので、A1〜A6 の後に置く。**

## 4. C. 設計の横断検証

同 §6.2 が求める「配管、電力、通信、熱、推進、姿勢制御」の一括検証のうち、**収支で言えるもの**を
`BlueprintIssue` として足す。`validateAssembly` は今のところ木・接続・断面・配置参照と
`validateBlueprint` の構造検査しか行わず、「発電が消費を賄えているか」「推進剤が全エンジンへ
届くか」「フライホイールを外した後も姿勢制御が縮退していないか」を見ていない。

拠り所: 合計の算術は `part-inventory.ts` に既にある(`totalPowerDraw`/`totalPowerGeneration`/
`totalCoolingRate`/`totalWasteHeat`/`totalThrust`/`totalTorque` 等)。**新しい物理は要らず、
既存の合計を検証項目へ畳むだけ**である。

姿勢制御の縮退は `physics/attitude-control.ts` の割り当てが既に階数落ちを扱えるので、
「要求に対して有限で非負の推力が出せるか」を設計時に問う形にできる。

## 5. D. 組立描画のインスタンシング

同 Phase 7。`AssemblyRenderObject` は部品1つにつき1メッシュを作り、同一種別の繰り返しに対する
インスタンシングを行っていない(有人艦は RCS スラスタだけで12基ある)。
`render/instanced-pool.ts` の `InstancedPool` が既にあり、`point-field-view.ts` が同じ形で使っている。

実現性は高いが**優先度は低い** — 現状の部品数では描画負荷として表面化していない。
A1〜A6 が終わってから、`PerfMeter` の描画行で実際に効いていることを確かめたうえで着手する。

## 6. 依存と着手順

```
A1(3D選択・クリック一本化) ─┬─→ A4(断面編集・ノード/エッジ削除)
                             └─→ A5(構造材ドラッグ)
A2(カメラ)   ── 独立
A3(下書き入口) ── 独立
A6(語彙の廃止) ── 独立(ただし A5 が SnapCandidate を触るので、A5 と同時か直後が無駄が無い)
B1(貨物の分類の接続) ── 独立
B2(基地への昇格・降格) ── A1〜A6 の後(横断範囲が広く、組立UIが固まってから触るほうが安全)
C(横断検証)   ── 独立
D(インスタンシング) ── A1〜A6 の後、計測してから
```

A1 → A2 → A3 を先に片付けると、A4・A5 に入る前に「3Dで選べて、対象が見えていて、下書きが作れる」
状態になり、以降の作業を実際に触って確かめられる。

B2 は既に到達できる経路の食い違いを直すものなので、**先送りしても既存の不整合が消えるわけではない**
— A 群の後、できるだけ早く着手する。B1 と C は独立なので、A 群と並行して差し込める。

## 7. 着手前に通す手順

- **`/ui-design`** — A1・A3・A4・A5 はいずれも HUD/DOM/CSS に触れる。特に A4 の断面フォームと
  A5 の部材棚は新しい UI の塊なので飛ばさない。`DEVELOP/DESIGN-RULES.md` のウィジェット語彙・
  置き場・タッチ規約に沿わせる。
- **`/add-feature`** — A5 の lateral ポート列挙は、既存の `nearestMountCandidate` と
  `occupiedPorts` を呼ぶ形にできるかを先に確かめる。新しい占有判定を書かない。
- **検証** — `npm run typecheck` と `npm run test:unit` の両方。`typecheck` は `tests/` を
  コンパイルしないので、単体テストを別に走らせないと型の不整合を見落とす。

1. 装着済みの部品を3D上で掴んで、別の取り付け位置へ動かす・倉庫へ戻すことができる。
2. 掴んだまま対象タブを切り替えて別の格納艦へ落とせる。
3. 部材棚から外皮エッジ・トラス・分離機構を出し、空きポートへ吸わせてノードと辺を生成できる。
4. 3D上の辺を掴んで取り外せる。
5. 選択中ノードの既存の原始図形の断面(種別・寸法・位相)を数値で編集でき、確定1回が1履歴になる。
6. 「新規船下書き」と「建造して格納」に UI からの入口がある。
7. 組立を始めるとカメラが対象を収める位置へ寄る。
8. `mateVerdict` を含む `assembly-mode.ts` の死んだ輸出が `src/` から消え、接続可否の判定が
   `assembly-editor.ts` の1箇所に閉じている。
9. 貨物は操作対象に選べず、コア部品を失う編集は適用前に警告が出る。
10. 艦に基地モジュールを取り付けて確定すると基地になり、在庫・収容・ドック口・赤道交点マーカー・
    衝突形状・自己修復の有無が、`orbitalBaseDesign` から作った基地と同じ振る舞いになる。
    取り外して基地でなくなる経路も同様に成り立ち、収容中の艦や在庫が残っているときは断られる。
11. 昇格・降格した機体が `ownShips()`/`baseVessels()` の分類に即座に反映され、
    その状態でスナップショットを取って読み直しても種別と持ち物が保たれる。
12. 電力・熱・推進・姿勢制御の収支が設計の検証項目に入っている。
13. `npm run typecheck` と `npm run test:unit` の両方が通る。
14. `CLAUDE.md`/`DEVELOP/CALLSTACK.md`/`DEVELOP/OWNERSHIP.md`/`DEVELOP/SPEC.md` が同じ変更セットで
    更新されている。
