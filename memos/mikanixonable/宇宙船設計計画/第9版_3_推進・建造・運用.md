# 推進・建造・運用 — 機体を飛ばす仕組み、作る仕組み、触る仕組み

## 1. この文書が扱うもの

機体は `Vessel` という単一の実体であり、その形はノードとエッジのツリーで表され、質量・重心・慣性テンソル・投影面積は形状から導かれる。搭載要素の一覧があり、性能値はその合成である。設計データの型があり、検証がある。資源と設備の連鎖が定義され、その連鎖が詰まらないことが検査されている。通信圏の判定があり、圏外の無人機は実際に計画の実行を止める。

**この文書が扱うのは、その上に載る実装である。**内訳は3つある。

1. **機体を飛ばす仕組み** — 姿勢制御系の配分、推進剤とエンジンの型式、ツィオルコフスキーによる燃焼、推力軸のずれ、外皮メッシュ、接触形状のカプセル。機体は形を持つが、その形に応じて姿勢が制御され、その形が外皮として描かれ、その形で当たるところまでは実装されていない。
2. **機体を作る仕組み** — 設計から資源と設備と電力の要求を集計して実機を得る生産、組立モードによる設計の編集、基地の区画、資源設備の稼働、月面の採掘と輸送。設計データと資源の帳簿は型として存在するが、設計から実機へ至る経路が存在せず、資源が生まれる場所も無い。
3. **機体に触る仕組み** — 飛行中のモジュール単位のプロパティーウィンドウ、推進系パネル、通信パネル、段とペイロードのパネル。機体は搭載要素ごとに装甲を持ち、要素ごとに壊れるが、それを飛行中に見る手段が1つも無い。

多段・ドッキング・ペイロード・配管・与圧は、この3つのすべてに関わる。分離すれば機体は2つになり、結合すれば1つになり、配管が繋がっていなければエンジンは点火せず、加圧ガスが尽きれば推進剤が残っていても推力を失う。

**段階の記号は作業項目の識別子であり、番号は連番ではない。**`F` は機体そのものの系列、`B` は設計・建造・資源の系列、`L` は月面と採掘の系列を表す。

## 2. 土台として存在するもの

この文書の段階が前提にできるものを挙げる。いずれもこの文書の外で定義され、実装されている。

**機体の実体**

- 機体は `Vessel` という単一のクラスである。艦艇・軌道基地・敵艦・コンテナ・無人機はすべて同じ実体であり、クラスを分けない。能力（`hasCockpit` / `hasAutopilot` / `hasBaseModule` / `hasEngine` / `hasCommunication` / `isOperable`）はすべて搭載要素から導かれる。
- 形状は**ツリー**である。ノードは断面を持ち、エッジはノードを結ぶ。エッジの種別は `hull`（内容積を持つ外皮）／`truss`（内容積を持たない骨組み）／`decoupler`（分離機構）の3種である。ツリーは閉路を持ってよい。
- 断面は基本断面（円・楕円・三角から八角・切り欠き多角形）の貼り合わせであり、面積・重心・断面二次モーメントは閉形式で求まる。
- 外接円半径は 0.25 m 単位、エッジの長さは 0.5 m 単位で最小 0.5 m である。
- 搭載要素は**外装要素**（ノードの接続口・`hull` エッジの外表面・トラス上の任意位置に取り付ける）と**内装要素**（`hull` エッジの内容積に収める）に分かれる。取り付け位置は `MountPoint` として機体ローカル座標に解ける。
- 質量・重心・慣性テンソル・主軸投影面積は、すべて形状と搭載要素から導出される。姿勢積分は非対角成分を持つ慣性テンソルを扱える。
- 抗力係数は自由分子流域の 2.2 の定数であり、`bcInv` は姿勢に依存する投影面積から求まる。太陽輻射圧の係数も同じ投影面積を用いる。
- 熱シールドはアブレータを消耗し、加熱率と動圧の閾値を引き上げる。尽きれば閾値は熱シールドなしの値に戻る。
- 重力傾斜トルクは全機体の姿勢積分に外部トルクとして加わる。地球磁場の双極子近似と、そこから磁気トルカのトルクを求める純関数がある。

**設計データ**

- `VesselBlueprint` はツリー・搭載要素の配置・タンクの中身・塗装を持つ。検証（`validateBlueprint`）は、接続口の重複、外装要素の干渉、内容積の超過、材料の適合を判定する。
- `assemblyOf` は設計から `VesselAssembly`（取り付け位置が解けた搭載要素の集合）を作る。
- 設計ファイルの入出力がある。

**資源と設備**

- 資源・産地・設備の定義と `ResourceLedger`（在庫）がある。
- `producibility()` は、ある物を作れるかどうかを判定し、不足を資源・設備・電力の3種として返す。材料適合性（推進剤がタンクの金属を要求する規則）を含む。
- 設備の連鎖が閉じていること——最初から持っている設備が出す資源から出発して全資源に到達でき、その経路上のすべての設備が初期の発電容量で動くこと——は検査済みである。

**通信と自動操縦**

- `CommNetwork` が有効な中継点の閉包を求め、見通しと到達距離から圏内外を判定する。判定は毎フレーム更新される。
- 無人機は圏外では燃焼を完遂したうえで次のノードから停止し、圏内復帰で再開する。

**テストの置き場**

- `tests/physics/` は `src/physics/` の純関数の回帰試験、`tests/unit/` は `src/physics/` の外にある純関数（設計の検証、生産可能性、通信圏など）の試験である。どちらも `lib` が `ES2022` のみであり、**DOM と THREE に依存するコードはコンパイルできない。**計算部分は最初から純関数として切り出す。

## 3. 全体像と着手順

### 3-1. 実装が届いていない3つの断絶

**設計から実機へ至る経路が無い。**`VesselBlueprint` を生成する箇所も、それを設計層の外から参照する箇所も存在しない。`ResourceLedger` を生成する箇所も、`producibility()` を呼ぶ箇所も存在しない。設計データと資源の帳簿は、型として正しく、テストで正しさが固定されていながら、実行時には誰も触れない。**この断絶を埋めるのが B6 である。**

**設計を編集する手段が無い。**編集の入口は組立モードであり、組立モードは組んだ形が実寸の外皮として見えることを前提とする。断面の指定が意図した形になっているかは、数値では判断できない。**この前提を与えるのが F12 である。**

**飛行中の機体に触る手段が無い。**機体は搭載要素の合成として性能を持ち、装甲も要素ごとに減るが、飛行中にそれを見る口が1つも無い。全画面のドックの画面は格納中の機体しか扱わない。**この口を開けるのが B17 である。**

### 3-2. 着手の先頭

**F12・B6・F9 を並行して始める。**この3つは互いに依存せず、それぞれが別の断絶を崩す。

- **F12（外皮メッシュの生成）を最優先に置く。**後続を最も多く抱えている。B7 → B8 → B12 → B13 という最長の連鎖の先頭がここで開き、B17 を確かめられる状態になるのもここである。機体が設計から生成した外皮で描かれて初めて、画面上で指した位置と搭載要素の取り付け位置が対応する。
- **B6（生産）を同時に始める。**設計データと資源の帳簿の両方を、到達不能なコードから実行時の経路へ移す。通れば、設計ファイルを手で書いて新しい機体を作れる状態に初めて到達する。
- **F9（姿勢制御系の分離）を3本目に置く。**F10 → F13 と F10 → B10・B16 を塞いでいるのは F9 だけであり、機体の系列でこれ以上先へ進む道はここを通る以外に無い。磁気トルカの配線も同時に片付く。

**B1（分離の物理）と F8（接触形状のカプセル化）は、上の3本と並行できる。**B1 は通れば B2・B4・B9 が開く。F8 は他の何も塞いでいないが、細長い機体の貫通が捕まらないことを直すものであり、機体が長くなる多段と同時期に要る。

**B11 の通信パネルは、どれとも独立にいつでも置ける。**通信圏の判定は動いていて無人機の計画実行を実際に止めているのに、プレイヤーには**なぜ無人機が動かないのかが分からない。**パネル1枚で、既に払った実装の費用が初めて見える。

**その後の順序は依存に従う。**F10 は F9 の直後に置き、通れば F13 と B16 が開き、B1 の段を跨ぐ燃焼の判定も足せる。B9（配管）と B10（与圧）は B1 と F10 の両方が済んでから続けて通す。B2（ドッキング）は B1 の逆向きの計算であり、B1 の直後が最も安い。

**月面の系列（L1〜L4）は、B6 と B13 が通ってから着手する。**L4 の採掘が生む資源を消費する先が、B6 の生産と B13 の設備だからである。逆に、L4 が無ければ資源は敵のドロップからしか入らず、月で閉じる経路が存在しない。

### 3-3. 設計UIは案B（実物を突き合わせる）である

**組立モードの操作の形は、`第9版_設計UIの案.md` の案B——生産した実物を掴んで突き合わせる——に決まっている。**資源を消費して部材を実物として生産し、棚から掴んで既に置いた部材の空いている接続口へ突き合わせる。ノードもエッジも直接触らず、形状ツリーは突き合わせの結果として立つ。モードは1つであり、骨格・搭載・配管・塗装をモードとして分けない。

**案Bは、そのままでは設計が資産として残らない。**突き合わせた結果はその場の1機であり、同型機の量産ができない。**この文書は、組み上がった物の形を形状ツリーとして読み取り、設計データとして保存し、保存した設計から一括で再生産できるようにすることでこれを解く。**理由と、それによって保たれるものは §14-1 にある。

**組立モードの実装は B7 と B8 に、その全体は §14 に置く。**B7 が組立モードの開閉と部材の生産まで、B8 が突き合わせと、実機・設計への変換までを持つ。B11 の配管モードは、突き合わせで立ったツリーに対する自動敷設の結果を重ねて見せるものになる。

**組立モードに依存しない部分は独立に成立する。**生産（B6）、外皮メッシュの生成（F12）、飛行中のモジュールのプロパティーウィンドウ（B17）、飛行中の各パネル（B11 の配管モード以外）は、いずれも組立モードの形とは無関係に置ける。

### 3-4. 搭載要素の性能値は33種すべてが定まっている

**搭載要素の実数値は `第9版_搭載要素の性能値.md` が33種すべてについて定めている。**質量・消費電力・廃熱を全種が持ち、機体の大小で桁が変わる種別には3〜4段の等級が置かれ、各値は実在の宇宙機の文献値・そこからの導出・遊びの都合による設計値のいずれであるかが項目ごとに区別されている。**一度も実数値を持たなかった16種——戦闘用シールド・ロボットアーム・ドッキングポート・コンテナ接合部・酸化剤タンク・還元剤タンク・加圧ガスタンク・水タンク・燃料電池・原子力電池・自動操縦装置・配管・ペイロード倉庫・磁気トルカ・農場・ドック——も、そこに値を持つ。**

**値を先に揃えたのは、性能値どうしが互いを縛るからである。**配管の口径はエンジンの要求流量と推進剤の密度の3者で決まり、農場の消費電力は放熱板の面積を決め、ドックの収容数は基地モジュールの格納数と対になる。1種ずつ埋めると、後から埋めた値が先に埋めた値と噛み合わないことが、噛み合わない両方が実装に入ってから分かる。**したがって、パレットに出す種別を段階ごとに選ぶ必要はない。値が 0 の種別はもう存在しない。**

**性能値を読む段階は B6・B7・B8・B12・B13 と、F9・F10・F13 である。**生産は建造費と質量を、組立モードはドックの作業領域と部材の寸法を、基地の区画は農場・生命維持装置・通信基地の電力を、姿勢制御と推進系はフライホイール・磁気トルカ・触媒床の値を読む。各段階の要件は、値そのものを再掲せず同文書を出典として指す。**値を2箇所に書けば必ず片方が古くなる。**

**同文書が求める型の追加は4つある。**`RobotArmPart.powerDraw` / `DockPart.powerDraw` / `RtgPart.thermalOutput` / `RcsThrusterPart`・`EnginePart` の `catalystMass` である。追加は B6 で行う（§6）。**同文書が実装の欠陥として記録したものは3つある。**敵対機のフライホイールの最大トルクの単位（F9）、RCS推進剤タンクの容積と最大充填の不整合（F10）、既定の有人艦の生命維持装置の消費電力と発電の不足（B12）であり、それぞれ該当する段階の作業として置く。

## 4. 機体の物理と描画

### F8. 接触形状のカプセル化

**背景と目的** — 剛体接触と被弾の判定は、機体全体を1つの外接球として行う。機体の形がツリーと断面から決まり、細長い機体も分岐した機体も作れる以上、外接球はその形をほとんど表さない。細長い機体では球の内側の大半が空であり、弾丸はそこを通っても当たったことになり、逆に高速の弾丸は球の直径ぶんの隙間を1ステップで飛び越える。**機体のどこに当たったかが決まらなければ、何が壊れたかも決まらない。**要素ごとの装甲は既にあるのに、当たりの側がそれに追いついていない。

**実装する要件**

- ツリーの各エッジに対応するカプセルの集合で狭域の判定を行う。`hull` エッジと `truss` エッジがカプセルを持ち、`decoupler` エッジは両端のカプセルが接するため独自のカプセルを持たない。カプセルの半径は両端の断面の外接円半径の平均、トラスは断面の大きさとする。
- 外接球は残す。空間格子による広域の絞り込みと、天体表面への到達判定は球で行う。**球が交わる場合にのみカプセルの判定へ進む。**
- 判定はカプセル対球（弾丸・破片・薬莢）とカプセル対カプセル（機体同士）の2種であり、いずれも掃引で行う。1ステップが長い時間加速下でも貫通を捕まえる。
- 被弾したカプセルから損傷する搭載要素が決まる。そのエッジの内容積に収めた内装要素と、そのエッジに取り付けた外装要素が候補になる。
- 戦闘用シールドはこの判定の前に立つ。被弾方向がシールドの遮蔽する立体角の内側であれば、シールドが先に損傷を受け、背後の要素は守られる。
- **投影面積の畳み方を同時に直す**（T-10）。主軸投影面積は、エッジごとの射影を「向きとエッジ軸が平行に近いものは最大値、それ以外は和」として畳む。平行でありながら横へずれて並ぶエッジは和になるべきところを最大値で畳んでしまう。また外装要素は質量にだけ算入され、投影面積に寄与しない。展開した放熱板は船体全体の投影面積より大きいため、抗力にも輻射圧にも寄与しないことは投影面積の定義から外れている。
- **外装要素は投影面積に算入する。**放熱板・太陽電池パドル・熱シールドは、その主軸3方向への射影を投影面積に加える。既定の有人艦では放熱板だけで左右合計 50 m² であり、船体全体の投影面積（6.8〜12.5 m²）を超える。**展開したまま低軌道に留まることが無償である状態は、放熱板が設計上の最も強い制約の一つであることと両立しない。**低軌道で放熱板を畳むという判断がここで生まれる。
- **熱シールドを投影面積に算入することは、大気掠め（B14）が機体の設計に依存するための前提である。**熱シールドが投影面積に寄与しなければ、熱シールドを積んだ機体と積まない機体で1回の通過あたりの減速量が同じになり、熱シールドは「同じ減速を壊れずに耐える」ためだけの部品になる。算入すれば、**大きな熱シールドを積むほど速く減速でき、そのぶんアブレータの消耗も速い**という釣り合いが、追加の規則なしに出る。
- **予測の空力は、主軸3方向の投影面積の平均で行い、姿勢に依存させない。**実際の積分は姿勢依存のままとする。予測は未来の姿勢を持たないため、現在の姿勢の値を固定して使うと「いまの姿勢を保ち続ける」という、プレイヤーが選んでいない仮定を予測が勝手に置くことになる。平均は「姿勢について何も仮定しない」中立な仮定であり、そのうえで実際とのずれが**姿勢を保てば予測より落ちにくく、回せば予測より速く落ちる**という一方向の性質になる。**この一方向性を再突入の表示に書く。**姿勢制御に意味を与えるという目的は、予測を姿勢に依存させなくても損なわれない。
- ツリーとカプセルの開発用線画を同じ段階で用意する。既定の設計が1つしかない段階では、外皮メッシュの完成を待たずに物理量が意図どおりかを確かめる手段が要る。

接触の解決そのものは既存の剛体接触の経路を通す。変わるのは狭域の当たりの形だけであり、力積の解決・損傷・音・破壊の側は触らない。投影面積の畳み込みは質量特性の導出の中にあり、そこへ外装要素の面積と、横並びのエッジの和を加える。

**検証** — `tests/physics/capsule-contact.test.ts`。両端が一致するカプセル（＝球）同士の掃引が既存の掃引球と一致すること。細長い機体を1ステップで貫く弾丸が捕まること。すれ違いが偽陽性にならないこと。`tests/unit/mass-properties.test.ts` に、展開した放熱板が投影面積に寄与すること、熱シールドが投影面積に寄与すること、横へずれて並ぶ平行なエッジの射影が和になることを足す。予測の空力が3方向の平均を用い、機体を回しても予測が変わらないことを固定する。**ステージ側の再突入の高度と時間の調整をこの段階の変更セットに含める。**外装要素の算入で抗力が最大5倍前後になるため、既存の調整はそのままでは成立しない。

### F9. 姿勢制御系の分離

**背景と目的** — 姿勢トルクは、手動操作と自動操縦がそれぞれ機体のトルクを直接書いている。アクチュエータという概念が無いため、フライホイールも磁気トルカも存在せず、姿勢制御はいつでも同じだけ効く。**機体の形が自由になった以上、姿勢制御の効きも形の帰結でなければならない。**スラスタをどこに何基付けたかで出せるトルクが変わり、フライホイールを積めば推進剤を使わずに向きを変えられ、地球磁場のある領域では磁気トルカがほとんど無料で働く。活動する領域によって運用の性格が変わることが、姿勢制御を系統として分ける目的である。

**実装する要件**

- 姿勢トルクを要求する主体（手動操作・自動操縦）は、アクチュエータを直接動かさず `AttitudeControlSystem` へ要求を出す。**要求元の一元化がこの段階の核である。**片方でも直接トルクを書いていると、フライホイールの角運動量を更新せずにトルクが出て、飽和の計算が合わなくなる。
- 配分は3段の優先順位で行う。**磁気トルカ**（推進剤を消費せず電力も微小。ただし τ = m × B であり、B に平行な成分は原理的に出せない。磁場のない領域では何も出せない）→ **フライホイール**（電力のみ。最大トルクと蓄積角運動量の上限の両方に縛られる）→ **RCSスラスタ**（出しきれなかったぶんを出す。推進剤を消費する）。
- RCSスラスタの取り付け位置と噴射方向は設計ごとに決まる。要求トルクと要求並進推力を同時に満たす推力の組は一般に劣決定であり、配置によっては厳密解が存在しない。**減衰最小二乗（Tikhonov 正則化した擬似逆行列）で解く。**正則化項は、要求を厳密に満たすことより推力の総量を抑えることを優先する重みであり、そのまま推進剤消費を抑える働きをする。**正則化重みは λ = (行列 A の最大特異値 × 1e-3)² とする。**特異値の2乗で入るのは `A Aᵀ` の対角に足すためであり、1e-3 という相対値は「6基未満または偏った配置で解が存在しない方向」だけを丸める大きさである。対称6基配置では実質的に無影響になる。**絶対値で置かないのは、機体の大小でスラスタの推力が桁で変わるためである。**得られた推力は 0 以上・最大推力以下にクランプし、クランプで残った差は出せなかったぶんとして扱う（再配分しない）。
- 蓄積角運動量が上限の **0.85** を超えるとアンローディングを開始し、**0.30** を下回った時点で終了する。開始が高いのは通常の運用で排出が頻発しないためであり、終了が低いのは1回の排出で当分は再発しない余裕を作るためである。**この2値の比が大きいほど、開始と終了を短周期で往復する発振から遠い。**外部トルクを与えながらホイールを減速し、角運動量を外部へ捨てる。外部トルクは磁気トルカを優先し、磁場が足りないぶんだけRCSが補う。自動実行を既定とする。
- **磁気トルカを実際に配線する。**地球磁場の双極子近似と、そこからトルクを求める純関数は存在するが、参照する側が無い。読み手はアンローディングと配分の第1段である。
- 噴くノズルの選択を配分の結果から読む。固定のノズルテーブルを廃し、機体ごとのアクチュエータ集合から取る。
- **`Vessel.planExecution` をメソッドに閉じる**（T-7）。この値はヒント通知を伴って書き換えられる一方、外部から直接代入されている。状態変更に副作用がある以上、所有者を1つに定める。**`PlanExecutorShip` インターフェースの変更を伴い、`tests/physics/plan-executor.test.ts` の代役が壊れる。代役が壊れることは、代役が現在の契約を写していることの証拠であり、変更しない理由にはならない。**同じ変更セットで代役を新しい契約へ揃える。
- **敵対機のフライホイールの最大トルクの単位の誤りを直す。**`hostileParts` は `maxTorque: C.MAX_ANG_ACCEL` と書いており、**角加速度 [rad/s²] の値をトルク [N·m] にそのまま代入している。**`tuneActuators` は `maxTorque = MAX_ANG_ACCEL × maxMoment` と正しく計算するため、それが後に走る経路では上書きされて表面化しない。走らない経路では敵対機のフライホイールが 1.4 N·m しか出さず、既定の有人艦（2,240 N·m 相当）の 1,600 分の1になる。**アクチュエータ集合を設計から導くこの段階が、両方の経路を1つに揃える場所である。**
- フライホイールと磁気トルカの性能値——最大トルク・蓄積角運動量の上限・最大磁気モーメント・消費電力——は `第9版_搭載要素の性能値.md` §5-14・§5-15 を出典とし、この段階で別の値を定義しない。

**実装内容**

```
src/physics/attitude-control.ts   (純関数)
    allocateTorque(request, actuators, wheelState, magneticField) -> Allocation
    desaturationRequest(wheelState, hMax) -> TorqueRequest | null
src/game/vessel/attitude-control-system.ts
```

`ActuatorSet`（スラスタの位置・噴射方向・最大推力、フライホイール、磁気トルカ）は設計から導く。`Allocation` は各アクチュエータへの指令に加えて、実際に出せたトルクと並進推力、および消費電力を返す。

**検証** — `tests/unit/attitude-control.test.ts`。減衰最小二乗の配分が、解の存在する配置で要求トルクを満たすこと。対向するスラスタが同時に噴かないこと（正則化重みが小さすぎると、要求をわずかに良く満たすために両方を噴かせる解が選ばれる）。厳密解の無い配置でも有限の解が返ること。飽和と排出が別々の閾値を持ち、短周期の往復に落ちないこと。`tests/unit/magnetorquer.test.ts`。磁場のない領域でトルクが 0 になること、磁場に平行な軸まわりのトルクが 0 になること、平行成分が必ず次の段へ落ちること。

### F10. 推進剤とエンジンの型式、ツィオルコフスキーによる燃焼

**背景と目的** — 推力は機体の定数であり、燃焼は一定加速度で計算され、スロットルは4段の離散値である。**推進剤という物が存在しない。**タンクに何を積んだかで比推力が変わることも、燃焼で質量が減って加速度が上がることも、極低温推進剤が蒸発することも、常温貯蔵性推進剤が凍ることも表せない。質量比の大きい機体では一定加速度の仮定が点火時刻を外し、マニューバノードを外す。**推進剤の選択が電力系・タンク材料・貯蔵期間と結び付くことが、機体設計を成り立たせる中心の1つである。**

**実装する要件**

- **成分ごとに物性を定める。**推進剤のペアに1つの温度を与えることはできない。酸化剤と還元剤は別のタンクに入り、それぞれ別の温度帯で保たれる。沸点・凝固点・密度・貯蔵方式を成分ごとに持つ。極低温の成分は沸点を超えて蒸発し残量が減る。常温貯蔵性の成分は凝固点を下回れば凍り、ヒータの電力を消費し続ける。**極低温は日射で蒸発するが凍らず、常温貯蔵性は蒸発しないが凍る。**この対比が推進剤の選択を電力系の設計と結び付ける。
- **推進剤の組み合わせを登録された表から選ぶ。**液体（酸化剤と還元剤のペア）・単推進剤・固体・ハイブリッドの4種。各組は真空比推力・混合比・平均密度・日あたり損失率・タンク材料の要求・毒性を持つ。混合比はいずれも化学量論比より燃料過多側に置く（燃焼温度を抑え、平均分子量を下げるため）。
- **エンジンは「サイクル（供給方式）」と「対応推進剤」の組で定義する。**サイクルは比推力係数・推力重量比・要求与圧・絞り範囲・再着火回数・連続燃焼時間の上限を持つ。エンジン部品の比推力は `推進剤ペアの比推力 × サイクルの比推力係数` とする。要求与圧が加圧式（2〜3 MPa）とポンプ式（0.2〜0.4 MPa）で10倍違うことが、そのまま加圧ガスの消費量の差になる。エンジンは全長を持ち、比推力の高いエンジンほどノズルが長い。点火1回あたりの推進剤損失を持ち、極低温エンジンは配管とポンプの冷却で数キログラムから数十キログラムを捨てる。
- **燃焼は質量変化を含めて計算する。**質量比から Δv、Δv から推進剤質量、Δv から燃焼時間を求める。点火損失は燃焼に要る推進剤とは別に、点火の時点で一括して差し引く。Δv がごく小さいノードでは損失のほうが上回ることがある。
- **スロットルは絞り率 0〜100% の連続値とする。**加速度による段階指定を持たない。同じ絞り率でも機体の質量と積んだエンジンによって加速度が変わり、燃焼中は質量が減るぶん加速度が上がる。キー `[1]`〜`[4]` は **5%・25%・50%・100%** のプリセットに割り当てる。**等間隔にしないのは、サイクルごとの絞り下限が 20〜60% と幅を持つためである。**等間隔の 25/50/75/100% では、加圧式（下限 40%）を積んだ機体で最小段がそもそも押せない。5% を最下段に置くことで、下限を下回る指定がエンジンを1基ずつ落とすという挙動が、プリセット操作から直接見える。**最小段が近接機動の並進に足りるかどうかは問わない。**下限を下回る出力は主機ではなく並進RCSの仕事である。サイクルごとの絞り下限を下回る指定は下限にクランプし、下限を下回る出力が要るときは主機ではなく並進RCSを使う。複数のサイクルを混載した機体では、下限を下回る絞り率を指定されたエンジンは下限で噴くのではなく停止する。**絞り率を下げていくとエンジンが1基ずつ落ちる。**
- **RCS推進剤タンクの容積と最大充填の不整合を直す。**既定の有人艦は容積 1.0 m³・実効容積係数 0.95 に対し最大充填 1,000 kg を持つが、ヒドラジンの密度 1,021 kg/m³ で入るのは 970 kg であり、**最大充填が容積を 3% 超えている。**現状は最大充填を独立に持つため表面化しないが、**容積と密度から容量を導く経路をこの段階が入れる。**入った時点で食い違うため、同じ変更セットで容量を導出に一本化する。
- 推進剤の物性、エンジンのサイクル、タンクの容積・断熱等級・要求与圧・材料の値は `第9版_搭載要素の性能値.md` §5-1〜§5-3 と §4-2・§4-3 を出典とし、この段階で別の値を定義しない。
- タンクの加圧方式を3つ持つ。自己加圧（極低温と亜酸化窒素の既定。加圧ガスの質量が丸ごと消える代わりに蒸発損失が増える）・窒素加圧（常温貯蔵性向け。極低温には使えない）・ヘリウム加圧（必要質量が窒素の約7分の1。最も軽いが調達が難しい）。この段階では方式の選択と加圧ガスの積載までを持ち、消費と与圧低下は B10 が扱う。

**実装内容**

```
src/physics/tsiolkovsky.ts   (純関数)
    dvFor(m0, mf, isp)
    massAfterBurn(m0, dv, isp)
    burnTimeFor(dv, m0, thrust, isp)
    propellantForDv(dv, mDry, isp)
```

推進剤の物性表とエンジンのサイクル表は純データとして置く。燃焼時間と点火時刻を求める既存の計算を質量変化を含む式に置き換え、点火損失を差し引き、燃焼中の加速度を毎ステップ再評価する。スロットルの絞り率は機体の状態として持ち、姿勢制御の要求と同じく `PropulsionSystem` を通す。1ステップが数十秒に達する時間加速下ではステップ内の質量変化が無視できないため、燃焼中のステップは閉形式で質量を進めるか、燃焼の開始と終了の時刻でステップを区切る。

**検証** — `tests/physics/tsiolkovsky.test.ts`（質量比から Δv、Δv から推進剤質量の往復が機械精度で閉じること、点火損失が Δv に依らず一定量として引かれること）。`tests/physics/plan-executor-math.test.ts` の拡張（燃焼時間が質量変化を含む式になり、質量比の大きい機体で点火時刻が一定加速度の仮定と有意に違うこと）。実行時検証（同じ絞り率で、機体設計により出る加速度が変わること。燃焼中に加速度が上がること）。

### F12. 外皮メッシュの生成

**背景と目的** — 自機は事前生成のモデルで描かれる。形状はツリーと断面から自由に決まるのに、画面に出るのは常に同じ1つの形である。**組んだ形が見えないことが、設計を編集する手段を持てない理由である。**断面の指定が意図した形になっているかは数値では判断できない。同じ理由で、飛行中に機体上のモジュールを指すこともできない——画面上の位置と搭載要素の取り付け位置が対応しないためである。

**実装する要件**

- エッジごとにロフト帯を生成し、露出した端面を蓋で閉じ、全体を1つのジオメトリに結合する。トラスは断面の大きさに応じた骨組みとして描く。
- 生成は**形状が変わったときに1度だけ**行う。遠距離では分割数を下げた別のジオメトリを用いる。
- **描画側の制約を守る。**`Mesh` のジオメトリは最初の描画時にキャッシュされるため、生成済みメッシュのジオメトリを差し替えてはならない。形状の変更時は `Mesh` ごと作り直す。
- 外装の搭載要素は取り付け位置に置く。接続口に付いたものはその座標系に、外表面とトラス上に付いたものは指定された軸方向位置と周方向角度に置く。可動部はその座標系を基準に動く。エンジンは全長ぶんノズルが機体後端から突き出す。
- 自機のモデルを事前生成アセットからロフト生成に置き換える。敵艦・破片・薬莢は事前生成アセットのままとする。
- **敵対機を質量特性の導出へ移す**（T-12）。敵対機は質量特性を直接指定する経路にあり、その参照断面積 15 m² は3方向とも同じ値である。導出を通す経路は存在するが本番から到達不能であり、参照はテストだけである。**同じ空を飛ぶ2種類の物体が違う空力に従う状態を残さない。**細長い機体を横に向ければ抗力が数倍になるという性質は、自機にだけ効いて敵に効かないのでは物理ではなく自機の特性になる。導出へ移すと敵の弾道係数が姿勢で変わるため、**低軌道の敵の軌道減衰の調整をこの段階の変更セットに含める。**
- **質量特性を直接指定する経路は、コンテナの恒久的な入口として残す。**コンテナはツリーを持たない機体であり、これは進行によって変わらない。**敵艦はこの経路の恒久的な住人ではない。**敵の構成（`第9版_4_延期目標.md` §7）は構造由来の敵をツリーとして生成するため、既存の手で組んだ敵が導出へ移り、構造由来の敵がツリーを持ち、直接指定に残るのはコンテナだけになる。

**実装内容**

```
src/render/hull/loft-mesh.ts
    buildLoftMesh(tree, lod) -> THREE.BufferGeometry
```

断面をまたぐ頂点の対応は、弧長による等分点と、対応距離の総和を最小にする割り当てで解く。辺数の異なる断面や回転位相の異なる断面をつなぐとき、対応を誤ると外皮がねじれる。

**検証** — 目視確認。既定の設計の外皮が実寸として妥当な大きさに見えること。断面をまたぐ頂点の対応で外皮がねじれないこと。両端の位相差が大きい構成での見た目。形状の変更で `Mesh` ごと作り直していること（ジオメトリの差し替えを行わないことを実装で守る）。開発用の線画（F8）と外皮の輪郭が一致すること。

### F13. 推力軸のずれと推進系のHUD

**背景と目的** — 主機の推力軸が重心を通らなければトルクが生じる。機体の形が自由であり、コンテナを非対称に積めることも許す以上、この効果は必ず現れる。**推力軸のずれを計算しなければ、非対称な設計が何の代償も払わない。**同時に、推進系の状態——絞り率、推進剤の残量、蓄積角運動量、磁気トルカが働いているか、電力収支と放熱余裕——を見る手段が無ければ、プレイヤーは推進剤が尽きた理由も、姿勢制御が急に推進剤を食い始めた理由も知りようがない。

**実装する要件**

- 主機の推力軸と重心のずれから生じるトルクを正しく計算する。ジンバル機構を持つ主機はずれを打ち消す方向に首を振る。**ジンバルは可動角に加えてジンバル速度の上限を持ち、速い姿勢変化には追従できない。**追従しきれないぶんと可動角で打ち消しきれないぶんは姿勢制御系が補償する。ジンバルを持たない主機のずれは補償されず、機体が回る。
- 飛行中に**推進系パネル**を置く。主機（絞り率、推進剤の種別ごとの残量、加圧の余裕とその余裕で燃焼を続けられる残り時間）・並進RCS（残量）・フライホイール（蓄積角運動量と上限の比）・磁気トルカ（現在の磁場強度に対して出せるトルクの目安、働いているかどうか）の4行を持つ。アンローディングの手動実行ボタンを置く。熱収支の余裕を1行として置く。
- **フライホイールが飽和してRCSに切り替わる瞬間に、短い通知音とヒントを出す。**推進剤の消費が始まる瞬間であり、プレイヤーが知るべき出来事である。アンローディングが終わってフライホイールに戻る瞬間には通知しない。**資源の消費が始まるほうだけを知らせる。**
- **劣化を実装する。**極低温推進剤は沸点を超えて蒸発し残量が減る（補給でしか埋まらない）。ヒドラジン単推進剤スラスタは触媒床の活性が累積噴射時間で低下し比推力が落ちる（整備で回復する）。原子力電池は半減期に従って出力が下がる。固体推進剤・加圧ガス・常温貯蔵性の二液推進剤は劣化しない。**推進剤が減る劣化と、性能が落ちる劣化は別のものである。**計算は毎フレームでは行わず、値を読む時点で前回の評価時刻からの経過時間（または累積噴射時間、累積入熱）に基づいて一括で行う。
- **合成した消費電力と廃熱を熱収支へ繋ぐ**（T-13）。搭載要素から合成された消費電力・廃熱・蓄電容量は値としては求まっているが、読み手がいない。電力は最終的にすべて熱になるという規則があり、繋ぐ先がある。推進系パネルが電力収支と放熱余裕を表示するため、繋ぎ先がこの段階で同時に要る。**B6 が追加する `RobotArmPart.powerDraw` / `DockPart.powerDraw` / `RtgPart.thermalOutput` の3フィールドの読み手は、ここである。**原子力電池の崩壊熱は電力の14〜16倍あり、そのほぼ全量が廃熱になる。定格出力からは導けないため独立のフィールドを持つ（`第9版_搭載要素の性能値.md` §5-7）。**電力を経由しない廃熱の経路を持つのは、原子力電池と太陽光導入農場の2つだけである。**

**実装内容**

```
src/physics/thrust-alignment.ts   (純関数)
    resultantThrust(engines, throttles, centerOfMass) -> { force, torque }
    gimbalCorrection(engines, request, dt) -> readonly number[]
```

`gimbalCorrection` が `dt` を取るのは、ジンバル速度の上限によって1フレームで到達できる角度が制限されるためである。推進系パネルは既存のウィジェットのみで構成し、生の `<button>` および `<input>` を書かない。

**検証** — `tests/physics/thrust-alignment.test.ts`。重心を外れた推力が生むトルクが、位置ベクトルと力の外積に一致すること。ジンバル速度で追随しきれない構成が検出されること。可動角の上限で打ち消しきれないぶんが残差として返ること。実行時検証（推進系パネルが電力収支と放熱余裕を表示し、合成された消費電力が熱収支の入力に現れること。フライホイールが飽和したときに通知が出て、戻るときには出ないこと）。

## 5. 構造の分割と結合

### B1. 分離機構と多段

**背景と目的** — 機体は1つの実体であり、分かれることがない。推進剤を使い切ったタンクとエンジンを捨てられなければ、Δv は質量比によって頭打ちになり、月の重力井戸を出入りする設計そのものが成立しない。**多段は Δv の表を書き換える最も安い手段であり、ツリーが `decoupler` エッジを種別として持つ以上、形の側はすでにそれを表せる。**足りないのは、分けたときに何が起きるかである。

**実装する要件**

- 段は、ツリーから `decoupler` エッジを取り除いたときの連結成分とする。**プレイヤーが段を区切るのではなく、分離機構を置いた場所から段が決まる。**
- 段はそれぞれ、コックピット・自動操縦装置・通信モジュールを含むかどうかを持つ。コックピットを含む段は分離後も操作できる。自動操縦装置と通信モジュールを含む段は、通信圏の内側にいる限り自動制御の対象になる。**どちらも欠く段は、分離後は制御不能な物体として軌道上に残る。**
- 分離は運動量保存を満たす。分離前の質量 `m_total`、分かれる2つを `m_a` / `m_b`、分離機構の力積から求まる相対速度増分を `Δv_sep` として、`v_a = v + (m_b / m_total)·Δv_sep`、`v_b = v − (m_a / m_total)·Δv_sep` とする。角運動量も同様に分配する。分離直後の一定時間は、分かれた2つの間の接触判定を無効にする。
- 分離後、本体はツリー・質量・重心・慣性テンソル・推進剤残量・配管の流路を再計算する。分離機構を跨いでいた配管は切断される。
- 同時燃焼（並列に束ねたブースター）と逐次燃焼（直列の多段）の両方を許す。**推進剤が尽きた段は分離の候補として提示するが、自動では分離しない。**
- **段を跨ぐ燃焼を判定し、ノードの分割を提案する。**段の切り替わりを跨ぐ燃焼は加速度が不連続になり、閉形式の点火時刻計算が成立しない。判定式は、そのノードの Δv に対する `propellantForDv(dv, mDry, isp)` が、そのノードを実行する段の推進剤残量を超えるかどうかである。超える場合、**禁止するのではなく、その段の推進剤で出せる Δv までを1つ目、残りを2つ目とする分割を提案する。**2つ目には次の段の点火損失が加算される。連続燃焼時間の上限を持つエンジンにも同じ判定を行う。禁止するだけではプレイヤーは何をすればよいか分からない。
- **アブレータの減少分を機体質量から差し引く**（T-11）。熱シールドのアブレータは加熱に応じて減るが、機体質量は構築時に一度きり決まるため変わらない。分離が質量特性を再計算する経路を作るこの段階で、質量が構築時に固定される形を崩す。

**実装内容**

```ts
// src/game/vessel/assembly.ts
export interface VesselStage {
  readonly id: string;
  readonly edgeIds: readonly string[];
  readonly hasCockpit: boolean;
  readonly hasAutopilot: boolean;
  readonly hasCommunication: boolean;
  readonly dryMass: number;
  readonly propellantMass: number;
}
export function splitStages(tree: VesselTree, parts: readonly AnyPart[]): readonly VesselStage[];
```

分離で生じた段を実体として登録する経路をエンティティ管理へ持たせる。軌道計画のノードに分離の指定時刻を持たせ、1つのノードを2つに分割する操作を持たせる。**段を跨ぐ燃焼の判定だけは F10 の `propellantForDv` を要求する。分離の物理そのものは要求しないため、先に通してよい。**

**検証** — `tests/unit/stage-split.test.ts`。`decoupler` を取り除いた連結成分が段と一致すること。分離の前後で運動量と角運動量が保存すること。分離後の質量特性が、分かれた側のツリーから導いた値と一致すること。実行時検証（分離して2つの物体が別々の軌道に乗ること。アブレータが尽きた機体の質量が減っていること。段を跨ぐ Δv のノードで分割が提案され、受け入れると2つのノードになること）。

### B2. ドッキングポートによる結合

**背景と目的** — 分離が機体を2つにするなら、結合は2つを1つにする。**同じ運動量保存の計算を逆向きに使うものであり、分離の直後に置くのが最も安い。**この機構の上に、軌道上に置いたブースターとの合流、艦艇同士の推進剤の融通、基地への接舷、そしてドックに入らない大きさの構造物の組み立てが成立する。結合を持たなければ、作れる機体の最大寸法はドックの寸法で永久に頭打ちになる。

**実装する要件**

- ドッキングポートは外装要素であり、ノードの空いている接続口に装着する。ポートの軸はその接続口の方向と一致する。ポートは等級（同一等級同士のみ結合）・両性か否か・移送速度・電力を橋渡しするかを持つ。
- **捕獲条件は、適合・軸方向距離・横方向ずれ・軸の対向角・接近速度（最小値以上・最大値以下。速すぎればラッチが損傷し、遅すぎれば噛まない）・横方向相対速度・相対角速度のすべてを満たすこととする。**成立するとポート面同士を厳密に一致させる位置と姿勢へ両機を補正する。補正は運動量と角運動量を保存する形で行い、余剰は減衰として捨てる。条件を満たさずに接触した場合は通常の剛体接触として処理する。
- 結合した機体は1つの剛体として積分する。積分は代表となる1機の状態に対してのみ行い、他の構成機体の位置と姿勢はジョイントの連鎖から毎フレーム導出する。質量・重心・慣性テンソルは全構成機体のものを平行軸定理で合成し、質量が一定量変化したときに再計算する。**主機の推力軸がクラスタ重心を外れる場合、そのぶんのトルクが実際に発生する。**同一クラスタの構成機体同士は接触判定を行わない。
- ジョイントのポート軸まわりの相対回転（位相角）を連続的に変えられる。回転速度に上限があり電力を消費する。**回転させると結合体の慣性テンソルが変わるため、角運動量保存により全体の角速度が変化する。**この効果はフライホイールと同じ内部トルクの一種として正しく計算する。用途は、太陽電池を太陽に向ける、放熱板を日陰に入れる、武装の射界を確保する、固定脚の向きを揃えることである。
- 推進剤とガスを移送できる。送り側と受け側のタンクが同じ推進剤種別に適合している場合のみであり、極低温と常温貯蔵性は互いに移送できない。速度は両ポートの移送速度の小さいほうで律速する。移送に伴って両機の質量と重心が変わる。
- 電力を橋渡しするジョイントで結ばれた範囲は、1つの電力系として計算する。発電は全構成機体の合計（太陽電池の向きと日照は個別に評価したうえで合計する）、蓄電容量はバッテリーの合計、消費は全構成機体の合計とし、不足時は優先度の低い消費から順に停止する。**放熱も同じ範囲で1つの収支とする。**放熱面が足りない構成機体があっても、結合相手に余剰があれば作動流体の循環によって融通できる。
- 結合の解除はジョイントを取り除いてクラスタを分割することであり、**分割の物理は分離機構と同じ経路を通る。**
- ドッキングポートを目標に選ぶと支援表示を出す。目標ポートの位置と軸、自機ポートとの相対位置、横方向のずれと軸の対向角を示すインジケータ、相対距離・接近速度・横方向相対速度・相対角速度とそれぞれの許容範囲、捕獲条件を条件ごとに満たしているかどうかの一覧。

**実装内容**

```
src/physics/docking-capture.ts   (純関数)
    captureCheck(portA, portB, stateA, stateB, limits) -> CaptureResult
    captureCorrection(...) -> { stateA, stateB }
src/game/vessel/docking-cluster.ts
src/game/vessel/docking-system.ts
src/game/hud/docking-guidance-panel.ts
```

既存の格納の判定（一定距離内かつ相対速度が小さければ格納する）は基地への収容として残し、ドッキングポートによる結合は捕獲条件の判定に基づく別の経路として置く。

**検証** — `tests/unit/docking-capture.test.ts`。捕獲条件が条件ごとに判定され、どれが外れたかが返ること。補正が運動量と角運動量を保存すること。分割が結合前の運動量に戻ること。実行時検証（2機を結合して1つの剛体として飛び、位相角を回すと全体の角速度が変わり、切り離せること）。

### B4. ペイロード倉庫と弾薬

**背景と目的** — 弾薬は補給パッケージとして軌道上に湧く。**運ぶという行為が存在しない。**無人ブースターに弾薬を積み、自動操縦で目的の軌道へ投入し、そこで放出して艦艇が回収する——この運用が成立すれば、弾薬は湧くものではなく運ぶものになり、通信圏の広さがそのまま補給の届く範囲になる。弾薬そのものを搭載要素にすることは、弾薬を生産の対象にすることでもある。

**実装する要件**

- ペイロード倉庫は内装要素であり、エッジの内容積に対する実効容積の係数は 0.90 とする。容積と最大積載質量の両方で制限される。中身は弾薬・推進剤・部品のいずれかである。
- 弾薬の放出は、**既存の補給パッケージと同一の実体を生成する。**艦艇は既存の接近回収の仕組みでそれを取る。**この運用は機体同士の結合を必要としない。**
- 放出は、プレイヤーの明示的な操作、または軌道計画上の指定時刻に行う。放出時に小さな分離速度を与える。**圏外では放出の指令が実行されない。**
- 弾薬を搭載要素とする。弾薬庫は弾薬を収める内装要素であり、弾薬は生産の対象であり、資源を消費して作られる。
- **武器と弾薬庫が同じ段に属していれば供給される。段が異なる場合は供給されない。**分離によって弾薬庫を失った武器は、装填済みの分を撃ち尽くした時点で沈黙する。
- **弾薬の自動補給の間隔を、ステージごとに設定できるようにする。**自動補給は当面残す。この段階が与えるのは「1機ずつ手で打ち上げる」経路であり、自動補給を廃止する条件——バッチ生産と補給の自動化（`第9版_4_延期目標.md` §6）——はまだ揃わない。**間隔をステージごとの設定にしておけば、揃った時点で 0 にするだけで廃止でき、廃止のための変更が要らなくなる。**
- ペイロード倉庫は機体内部の容積であり、機体の外形に現れない。着脱して軌道上に置ける規格化された容器はコンテナ（B12）であり、こちらは外装要素として取り付ける。**輸送にはコンテナが向き、投下にはペイロード倉庫が向く。**

**実装内容** — ペイロード倉庫を搭載要素の一覧に加え、放出の経路を既存の補給パッケージの生成へ繋ぐ。弾薬と弾薬庫を搭載要素として加え、武器の弾薬供給を段の同一性で判定する。軌道計画のノードにペイロード放出の指定時刻を持たせる。

**検証** — 実行時検証。無人ブースターで弾薬を軌道に投入し、艦艇が既存の接近回収で取れること。圏外では放出の指令が実行されないこと。弾薬庫を含む段を分離した後、武器が装填済みの分だけ撃って沈黙すること。

### B9. 配管と推進剤の流路

**背景と目的** — タンクとエンジンは搭載要素として存在するが、両者の間に何もない。**タンクをどこに置いてもエンジンは同じように点火する。**配管を実体にすれば、機体の形が推進の可否そのものを決めるようになる。側面ブースターのタンクから中央のエンジンへ推進剤を送る運用（クロスフィード）が、分離順と流路の設計として現れる。

**実装する要件**

- 配管は1本につき1種類の推進剤しか通さない。酸化剤と還元剤を同じエンジンへ送るには2本要り、加圧ガスも別の1本を要する。
- **タンクとエンジンが同じ推進剤の配管で連続して繋がっていることが点火の条件である。**繋がっていないエンジンは点火できず、組立モードの診断と飛行中のHUDがその旨を表示する。
- 配管の口径から決まる最大流量が、エンジンの要求流量（`推力 / (比推力 × 標準重力加速度)`）を下回る場合、エンジンの推力はその流量で制限される。
- タンクとエンジンが同じエッジの内容積に同居する場合、配管は不要である。配管がエッジの内容積を占める量は、エッジの長さと口径の断面積の積である。
- **分離機構のエッジを配管が跨ぐ場合、分離と同時に配管が切断される。**跨ぐことを許すかどうかはプレイヤーが選ぶ。跨ぐ配管を敷けば、分離時点で中央段のタンクを満載のまま残せる。
- 外皮のない `truss` エッジにも配管を敷ける。この場合は外部に露出したものとして描画する。
- **自動敷設を既定とし、手動はその上書きとする。**各エンジンに対して、要求する推進剤ごとに、その推進剤を持つ最も近いタンクから最短経路（距離はエッジの長さの和）で配管を通す。口径は要求流量を満たす最小のものを選び、同じエッジを複数のエンジンが共有する場合は要求流量の和を満たす最小のものになる。**既定では分離機構を跨がない。**跨がなければ届かないエンジンについては、跨ぐ経路を提示するが敷設はせず、供給なしとして診断に出す。クロスフィードは選択に意味のある判断であり、自動で決めない。
- 手動で敷かれた区間は保持し、自動敷設はその上に足りない分だけを敷く。設計を変更するたびに呼び直す。エッジ数に対して線形とする。

**実装内容**

```ts
// src/game/vessel/feed-network.ts
export function resolveFeed(
  network: FeedNetwork,
  tanks: readonly TankPart[],
  engines: readonly EnginePart[],
): readonly EngineFeedResult[];
// src/game/vessel/auto-route.ts
export function autoRouteFeed(
  tree: VesselTree,
  placements: readonly PartPlacement[],
  overrides: readonly FeedLink[],
): FeedNetwork;
```

推進剤の種別ごとに連結成分を1度だけ求め、タンクとエンジンが同じ連結成分に属するかで供給を判定する。自動敷設の結果は手動の敷設と同じ `FeedNetwork` であり、解決する側は両者を区別しない。**自動敷設の結果は設計から再導出できるため保存しない。手動で上書きした区間だけを保存する。**

**検証** — `tests/unit/feed-network.test.ts`。自動敷設が繋がった構成を作ること。手動の上書きが自動敷設のやり直しで保持されること。流量不足の構成で期待どおりの結果が返ること。分離で流路が切れ、切れた側のエンジンが供給なしになること。

### B10. タンクの与圧

**背景と目的** — 推進剤が残っていてもエンジンが推力を失うという失敗の形が無い。**加圧ガスは実機で最も地味に効く資源であり、加圧式とポンプ式の10倍の要求与圧の差が、単純だが重い設計と複雑だが軽い設計の対立を作る。**ヘリウムが序盤にわずかしか手に入らないことは、この差を「どの機体にヘリウムを使うか」という判断に変える。

**実装する要件**

- 消費するガス量は、押し出した推進剤の体積とタンクの与圧の積に比例する。要求与圧はエンジンのサイクルによって決まる。
- **加圧ガスが減るとタンクの与圧が下がり、エンジンの推力が下がる。**与圧が要求値を下回った時点から推力を与圧に比例して下げ、下限を割った時点で燃焼を停止する。加圧式は与圧が燃焼室圧を直接決めるため影響が大きく、**ポンプ式はポンプ入口圧が下限を割るとキャビテーションを起こしてそこから急に推力を失う**（要求値を上回っている限り影響はない）。
- 自己加圧の機体では、蒸発が追いつかないほど高い流量で長く噴射したときに同じことが起きる。
- HUD に加圧の余裕と、その余裕で燃焼を続けられる残り時間を表示する（推進系パネルの主機の行）。

**実装内容**

```
src/physics/pressurant.ts   (純関数)
    pressurantMassFor(propellantVolume, tankPressure, gasType, temperature) -> number
    autogenousBoiloffRate(propellantId, tankPressure, flowRate) -> number
    remainingBurnTime(pressurantMass, flowRate, tankPressure, gasType) -> number
    thrustScaleFromPressure(tankPressure, requiredPressure, cycle) -> number
```

推力の低下は燃焼の出力に反映する。加圧ガスの消費は配管の流路を通るため、B9 の解決の結果を入力に取る。

**検証** — `tests/physics/pressurant.test.ts`。加圧式とポンプ式の同一機体で、同じ Δv を得るのに要る加圧ガス質量が期待どおり差を持つこと。自己加圧で蒸発損失が増えること。与圧低下時に加圧式は比例して、ポンプ式は下限で急に推力を失うこと。

### B15. 軌道上での結合

**背景と目的** — ドックの作業領域は有限であり、それを超える構造物は1機として作れない。**モジュールに分けて作り、軌道上で結合できれば、ドックの最大寸法は機体の最大寸法ではなくなる。**結合の機構そのものは既に成立しているため、ここで要るのは、結合したクラスタを1つの設計として保存する経路だけである。

**実装する要件**

- 結合後のツリーは、両者のドッキングポートを1つのノードとして継いだものになる。質量特性・配管・段の分割は、結合の時点で一度だけ再計算する。
- 結合した機体は、基地を操作対象にして組立モードを開けば、1つの設計として保存できる。**保存は形の記録であり、作業領域に収まることを要さない。作業領域に収まることを要求するのは生産だけである。**
- 分解はジョイントの取り外しであり、分離機構と同じ経路を通る。

**実装内容** — 2つのツリーを1つにする関数と、その結果を設計データとして書き出す経路。結合そのものは B2 の機構をそのまま用い、新たな捕獲の仕組みを作らない。

**検証** — 実行時検証。ドックの最大寸法を超える構造物が組め、1つの設計として保存できること。保存した設計を読み込むと同じ形になること。生産しようとすると作業領域を超えることを理由に拒否されること。

## 6. 設計と生産

### B6. 生産と生産可能性の統合

**背景と目的** — 設計データの型があり、その検証があり、資源の帳簿があり、生産可能性の判定がある。**それらを繋ぐものが無い。**設計を実機に変える経路が存在しないため、設計データを生成する箇所も、在庫を生成する箇所も、生産可能性を問う箇所も、実行時には1つも存在しない。**この段階が置くのは、その1本の経路である。**通れば、設計ファイルを手で書けば新しい機体が作れる状態に初めて到達し、資源の帳簿に初めて読み手ができる。

**実装する要件**

- 生産は、保存した設計を指定し、**資源と設備と電力**を消費して実機を得る操作である。
- 消費する資源は、搭載要素ごとの資源コストと、外皮の質量に対応する構造材の和とする。
- **生産時間は搭載要素の合計に生産時間係数を掛けて求める。**この係数はセーブデータに含め、ステージごとの既定値を持つ。**既定値は 0 であり、すべての設計が即座に完成する。**係数を後から有効にしても既存のセーブに影響しない。
- 生産キューは基地モジュールを持つ機体が保持する。完成した機体はその基地のドックに現れる。**ドックの収容数を超える生産は、完成した時点ではなく生産の開始時点で拒否する。**
- 生産の可否は既存の生産可能性の判定に委ねる。**この段階が持つのは、その判定に渡す要求を設計から集計することと、返ってきた不足を表示することだけである。**要求の種別は資源・設備・電力の3つしかない。
- 不足している要求は、その資源が**どの設備から作れるか**、その設備が**何を要するか**を設備の定義から辿って表示する。プレイヤーは足りないものを起点に、必要な連鎖を遡って読める。
- **搭載要素ごとの建造費の表を埋める**（T-4）。搭載要素の一覧は性能値だけを定めており、それを作るのに要る資源を持たない。生産可能性の判定は設計が申告する資源量を積み上げる形で経路だけが用意されている。**表が空では在庫を消費できない。**質量と等級は `第9版_搭載要素の性能値.md` が33種すべてについて定めているため、この段階が置くのは**その質量を資源の内訳へ割り振る表**である。**建造費を持たない搭載要素が1つも残らないことを、テストで機械的に固定する。**
- **型に4つのフィールドを足す。**`RobotArmPart.powerDraw` / `DockPart.powerDraw` / `RtgPart.thermalOutput` / `RcsThrusterPart`・`EnginePart` の `catalystMass` である（`第9版_搭載要素の性能値.md` §2-4）。**性能値を実装へ入れる最初の段階がここであり、フィールドが無ければ値の置き場が無い。**電力と廃熱の2つを熱収支へ繋ぐのは F13 である。
- **ヒドラジンの触媒床に要る白金族の質量を、推力に比例する資源要求として定める**（T-5）。要求はタンクではなく**スラスタとエンジンに付ける。**触媒床は物理的に燃焼室の中にあり、その質量は推力に比例する。推進剤の種別に紐付けたままでは、比例させる相手（推力）がその場に無い。**推力 25 N までは 1.09×10⁻³ kg/N、それを超えると 5.45×10⁻³ √F kg、うちイリジウムが 32 wt% である**（`第9版_搭載要素の性能値.md` §6）。スラスタの建造費は `catalyst-bed` を `catalystMass` だけ要求し、触媒床製造炉は `platinum-group` をその 0.32 倍消費する（残る 0.68 はアルミナ担体であり、月の資源で足りる）。**二液推進剤は自己着火性であり触媒を要さない。**既定の有人艦では主機が触媒床を持たず、RCSスラスタだけが持つ（5,000 N に対し触媒床 385 g、イリジウム 123 g）。**この形にして初めて、艦隊を50機に増やせばイリジウムが 6.2 kg 要る。1グラムを一度手に入れれば済むということがなくなる。**
- **基地が保有する資源を手動で増やせるようにする。**基地の在庫に対し、資源 id と質量を指定して加算する操作を置く。**これはデバッグのための手段である。**建造費の表が埋まっても在庫が1グラムも無ければ何も作れず、生産の経路が通ったかどうかを確かめられない。資源が生まれる場所——月面の採掘（§9 の L1〜L4）と敵のドロップ（B13）——は、いずれもこの段階より後にある。**したがってこの手段は、生産が最初に動くための足場である。**操作は基地のドックの画面に置き、加算した資源と量をその場に表示する。**ステージの進行や勝敗には一切影響させず、分岐も切り替えも設けない。**加算する対象は現在操作している基地の在庫だけであり、他の基地や機体には及ばない。**着陸と採掘（L1〜L4）が実装された時点で、この手段は不要になる。**そのとき資源はゲーム内で確保するものになり、手動の加算は削除する。
- **生産時間係数は、当面すべてのステージで 0 に固定する。**ステージごとの値の表を作らない。係数を持つ仕組みとセーブへの格納は置くが、値は 0 のままとし、すべての設計が即座に完成する。**遊びとして時間を掛けさせたい場面が具体的に見つかるまで、値の表を増やさない。**
- **設計ファイルの入出力を既存のセーブと共通化する**（T-15）。設計ファイルの入出力は、セーブファイルの入出力とほぼ逐語で重複している。ダウンロードとファイル名の生成にドメイン知識は無いため、共通の補助へ切り出せる。生産が設計ファイルの読み込みを実際に使う最初の場所である。

**実装内容** — 設計から要求を集計する関数、在庫を消費して実機を構築する経路、生産キューを保持する基地側の状態、完成した機体をドックに置く処理。**全画面のドックの画面からショップと市場を削除し、代わりに生産キューと在庫と設備の一覧を置く。**部品の入手はすべて生産に移る。**この段階の完了条件に「ドックの画面から通貨が消えていること」を含める。**この作品に通貨は存在せず、部品の価格表と所持金の表示は実装にだけ残っている。**削除は生産と同じ変更セットで行う。**部品の入手を生産へ移す先が無いまま市場だけを消すと、部品を替える手段が丸ごと失われる。**船体の作成はこの画面に置かない。**この画面が扱うのは既に存在する機体と物であり、形を作ることは扱わない。

**検証** — `tests/unit/production.test.ts`。要求の集計が搭載要素と外皮の構造材の和になること。在庫が要求どおり減ること。生産時間係数 0 で即時完成すること。**建造費を持たない搭載要素が1つも存在しないこと**（表の網羅を機械的に固定する）。触媒床の要求が推力に比例し、二液推進剤のエンジンでは 0 になること。実行時検証（設計ファイルを読み込んで実機が得られ、在庫が減ること。不足があれば拒否され、何が足りず、それがどの設備から作れるかが示されること。**在庫が空の状態で手動の加算を行うと、その資源だけが指定した量だけ増え、直後に同じ設計の生産が通ること。**ドックの画面に通貨の表示が1つも無いこと）。

### B7. 組立モードの入口と部材の生産

**背景と目的** — 設計を編集する手段が無い。設計ファイルを手で書けば機体は作れるが、断面の指定が意図した形になっているかは書いた数値からは判断できない。**形は実寸の3次元空間でしか判断できない。**一覧と数値の画面でしか扱えないものは形を持たない。

**操作の形は案B（生産した実物を掴んで突き合わせる）である。**プレイヤーは資源を消費して部材を実物として生産し、それを棚から掴んで既に置いた部材の空いている接続口へ突き合わせる。ノードもエッジも直接触らない。**形状ツリーは操作の対象ではなく、突き合わせの結果として立つ。**この段階が置くのは、組立モードの開閉と、部材を生産して棚に並べるところまでである。突き合わせと、組み上がった物を実機と設計に変えるところは B8 が置く。実装の全体は §14 にある。

**実装する要件**

- **入口は「基地を操作対象にすること」である。**基地モジュールを持つ機体を操作対象に選ぶと、その基地の戦闘ビューに組立モードの開閉が現れる。開くと戦闘ビューの左右のレールへパネルが加わり、ドックモジュールの定める作業領域の枠が空間の中に線として現れる。**作業領域は3段階であり、初期が 50 m 立方、中期が 100 m 立方、後期が 200 m 立方である**（`第9版_搭載要素の性能値.md` §5-19）。枠は単一のスカラであり、**機体の外接直方体がすべての軸でその値を下回ることを要求する。**閉じれば同じ戦闘ビューがそのまま基地の通常の操作に戻る。**専用のビューを増やさない。**
- カメラは基地を追う戦闘ビューの追従カメラそのものである。組立モードのために別のカメラを持たない。**組み立て中の機体は実寸であり、隣に係留した既存の機体と直接比べられる。**世界の描画と時間の進行は戦闘ビューのままであり、基地は軌道を回り続け、日照は変わり続ける。
- **部材は生産した時点で実物になる。**生産できる部材は4種である。外皮区間（両端の断面と長さを指定する）・トラス区間（断面の大きさと長さを指定する）・分離機構（断面と分離推力を指定する）・搭載要素（一覧から1つ選ぶ）。寸法の刻みは 0.5 m である。
- **生産は資源・設備・電力を消費し、足りなければ生産できない。**不足はその場に、資源名・要る量・在庫の量として出る。**組み立ての操作そのものは資源を一切消費しない。**したがって在庫の残りが、次に何を作れるかを常に制約する。
- 生産した部材は作業領域の脇の棚に、実寸の3Dモデルとして現れる。棚は基地の持ち物であり、組立モードを閉じても残る。
- **寸法の刻みは外接円半径で揃えるが、多角形では外接円直径と実際の幅が一致しない。**正方形で外接円直径 1 m を指定すると辺の長さは 0.707 m である。刻みは変えず、外接円直径・辺の長さ・最大幅の3つを並べて表示する。接続口に収まるかを判断するのに要るのは最大幅であり、外皮の板取りに要るのは辺の長さである。
- **作業領域の枠を超える組み立ては、超えた部分がそのまま枠の外へ出て見える。**入らない機体を作っていることが、寸法の数値ではなく形として分かる。
- **3段階の枠が対応しているのは、そのつど何を作れるようになるかである。**初期の 50 m が開くのは**基地そのものの複製**である。既定の基地モジュールの外形はおよそ 33 m × 42 m × 33 m であり、50 m の枠はこれを 8 m の余裕で収める。基地を増やせなければ生産設備も倉庫もドックも増やせないため、**50 m は「基地が基地を産めるようになる」ための最小の枠である。**既定の有人艦は全長 4.5 m 級であるから、艦艇を作る限り枠は一度も当たらない。**枠が当たるのは、艦艇を作るのをやめて基地を作りにいったときである。**中期の 100 m が開くのは**農場を持つ基地**であり、乗員8人ぶんの放熱板は展開した差し渡しが 50 m を確実に超える。後期の 200 m が開くのは、それらを1機に統合した構造物である。
- **枠を超える構造物は、軌道上で結合して作る**（B15）。テザー式の重力区画（`第9版_4_延期目標.md` §5）は回転半径が数百メートルから数キロメートルに及び、**後期の 200 m の枠でも作れない。**枠の拡張と軌道上での結合は、代替ではなくそれぞれの領分を持つ。
- **パレットには33種すべてを出す。**値が定まっていない種別は無い（§3-4）。
- **右レールの性能パネルはこの段階で要る。**乾燥質量／総質量／全長、Δv、推力重量比、慣性主軸と推力軸のずれ、電力収支と放熱余裕、加圧ガス余裕、通信の到達距離、段の一覧。**表示するのはいま組み上がっている実物の値であり、これから作るものの見積もりではない。**掴んでいる部材があるあいだは、それを付けた場合の差分を数値の横に併記する。
- **性能計算は部材を置くたび・外すたびに実行する。**計算はすべて解析式であり、ノードとエッジの数に対して線形であるため、毎操作の実行で問題にならない。

**実装内容** — 組立モードの開閉と、掴んでいる部材の状態を持つ `AssemblyMode`。生産した部材の在庫を持つ `PartStock`。部材1つぶんの生産要求を組み立てる純関数 `partOrderProducibility`。左レールの生産パネルと右レールの性能パネル・棚の一覧。クラスの割り当ては §14-2、パネルの割り当ては §14-4 にある。

**検証** — `tests/unit/part-order.test.ts`（§14-7）。手動確認（基地を操作対象にすると組立モードの開閉が現れ、開くと左右のレールへパネルが加わり、閉じると取り除かれること。作業領域の枠が線として見えること。資源が足りない部材が生産を拒否され、何が足りないかが示されること。生産した部材が棚に実寸で現れること）。**組んだ形が外皮として見えなければ操作を確かめられないため、F12 が先に要る。**開発用の線画は輪郭を示すだけであり、外皮の見え方の代わりにはならない。

### B8. 突き合わせによる組み立てと、設計としての記録

**背景と目的** — 生産した部材が棚にあっても、それを突き合わせる操作が無ければ機体にならない。搭載要素は取り付け位置を持ち、位置がそのまま重心のずれとトルクの腕になる。**腕を長く取れば同じ推力で大きなトルクが出るという関係は、取り付け位置を選べて初めて意味を持つ。**そして、突き合わせて立った形をその場の1機で終わらせると、同型機を作るたびに同じ組み立てを繰り返すことになる。**組み上がった形を設計として記録し、記録した設計から一括で再生産できることが、この段階の要件に含まれる。**

**実装する要件**

- **掴む・運ぶ・突き合わせるが操作のすべてである。**棚の部材をクリックすると掴み、作業領域へ運ぶ。最初の1本は作業領域の中央に固定して置かれる。以後の部材は、既に置いた部材の空いている接続口へ近づけると吸着し、突き合わさる。**掴んでいる部材の位置は、画面上のドラッグから3次元の位置を直に決めるのではなく、空いている接続口の集合の中から画面最近傍のものを選ぶことで決める**（§14-5）。
- **突き合わせられない口は吸着せず、理由をその場に出す。**理由は、口が既に埋まっている・断面の最大幅が口に収まらない・断面の辺数か位相が合わない・閉じる構造の最後の1本で両端の距離が部材の長さと合わない・作業領域の枠を超える、の5つである。
- 搭載要素も同じ操作で置く。外装要素はノードの空いている接続口に吸着する。**トラスへの取り付けはトラスの軸上の任意の位置で、0.5 m 刻みにスナップする。**大型の太陽電池パドル、大型の放熱板、ロボットアーム、コンテナ接合部はここに付く。**RCSスラスタは、上の2つに加えて外皮区間の外表面にも付く。**軸方向の位置と周方向の角度を指定する。内装要素は外皮区間の内容積に収める。ロフト体積・実効容積の合計・残容積・収容質量・タンク材料の適合を表示する。軸方向に連なる区間へ内容積の割り当てを拡張できる。
- 元に戻すは、直前に付けた部材を外して棚へ戻す操作である。**外した部材は棚へ戻り、資源は返らない。**分解は物理的な行為であり、切り離した金属が元の板に戻ることはない。
- **[完成とする] を押すと、組み上がった物の形が形状ツリーとして読み取られ、実機になってドックに係留される。**読み取りは、突き合わせた口の対応から共有ノードを立て、部材1つを1エッジとして起こす（§14-3）。
- **読み取ったツリーは、そのまま設計データとして保存できる。**保存した設計は保管庫に入り、複製・改名・ファイル入出力の対象になる。**設計の検証19項目は、この読み取りの直後に通す**（§14-6）。突き合わせの操作が成立している時点で連結性・口の寸法・排他は満たされているため、そこで実際に働くのは推力軸のずれ・材料適合性・配管の連続性・段の成立・熱シールドの向き・上限といった全体の制約である。**警告に落ちても実機にすることは拒否しない。**設計として成り立たない誤り（`error`）だけが完成を拒む。
- **保存した設計は一括で再生産できる。**設計が要求する部材の列を起こし、棚にあるものを充当し、足りないものを生産にかけ、突き合わせを系が再現する。**プレイヤーが同じ組み立てを繰り返すのは、初めて作る1機のときだけである。**資源または設備が足りなければ、何が何個足りないかを部材ごとに示して止まる。
- 塗装は基本色・副色・アクセント色と、金属感と粗さを持ち、設計データの一部として保存する。**照明は戦闘ビューの光そのものであり、基地の日照に従う。**組み上がった物に対して随時変えられる。

**実装内容** — 組み立て途中の物を持つ `AssemblyDraft`、突き合わせの成否を判定する `mateVerdict`、突き合わせからツリーを起こす `treeFromDraft`、設計として記録する `blueprintFromDraft`、設計から部材の列と不足を起こす `rebuildPlan`。いずれも DOM にも THREE にも依存しない純関数である（§14-2・§14-3）。3D側は掴んでいる部材のゴーストと吸着候補の口の強調（§14-5）。

**検証** — `tests/unit/mate-verdict.test.ts` / `tests/unit/tree-from-draft.test.ts` / `tests/unit/blueprint-from-draft.test.ts` / `tests/unit/rebuild-plan.test.ts`（§14-7）。手動確認（棚の部材を掴んで突き合わせられること。突き合わせられない口が吸着せず理由を示すこと。取り付け位置を変えると右レールの推力軸のずれと慣性主軸が変わること。[完成とする] で実機がドックに現れ、同じ形が設計として保管庫に入ること。その設計から一括再生産した機体が、元の機体と同じ質量特性を持つこと。塗った色がドックの照明の下で見えること）。

## 7. 基地の区画と資源設備

### B12. 基地モジュールの区画

**背景と目的** — 基地は機体であり、艦艇と同じ実体である。基地を基地たらしめるのは、積んでいる区画である。**農場・生命維持装置・水タンク・ドック・コンテナ接合部・通信基地——この6つが、資源の層と機体の運用の層を実際に繋ぐ。**とりわけ農場と生命維持装置は、電力と廃熱を通じて基地の形そのものを決める。

**実装する要件**

- **農場**は光・水・二酸化炭素を消費し、食料と酸素を生む。人1人を養うのに要る栽培面積はおよそ 40〜50 m² である。光は電照（栽培面積あたり 300〜400 W、人1人ぶんで 12〜20 kW）と太陽光導入（導光と追尾の機構の電力のみ。太陽から遠ざかるほど集光面積が要る）から選ぶ。二酸化炭素を吸って酸素を出すため、生命維持装置の消耗品の消費を減らす。
- **電照農場が消費する電力はすべて熱になる。**光は植物に吸収され、ごく一部が化学エネルギーとして固定される以外は熱に変わる。1人あたり 15〜22 kW を捨てなければならない。放熱板の実効性能は軌道上で 50〜150 W/m² であり、**1人あたり 100〜150 m² の放熱面が要る。栽培面積より 2〜3 倍大きい。**軌道上の基地は、農場を作ろうとした瞬間から農場より大きな放熱板を並べることになる。**太陽光導入を選んでも放熱の要求は減らない。**節約されるのは発電側の電力だけであり、居住区画に入った光は結局同じだけ熱になる。
- **生命維持装置**は二酸化炭素の除去・酸素の供給・水の再生・温度と湿度の管理を行い、収容人数に比例して電力（1人あたり 1.5〜2 kW）と消耗品を消費する。**既定の有人艦の生命維持装置は乗員2名に対し 400 W、すなわち1人あたり 200 W であり、1桁小さい。この段階で 1.5〜2 kW へ直す。**200 W では放熱が人口の制約にならず、`第9版_4_延期目標.md` §4-3 の人口上限の計算（1人あたり 14〜22 kW の廃熱）が根拠を失う。**同じ変更セットで発電側を直す。**1人 1.75 kW × 2名では消費が 3,590 W になり、追尾を持たない太陽電池 7.2 m² の日照中の平均発電 780 W では日照中ですら 4.6 倍足りない。**二軸追尾を付ければ 11 m² で足りる**（`第9版_搭載要素の性能値.md` §9-3）。追尾の可否は発電量を3倍変える。**閉ループ率が補給量を決める。**水の再生だけを行う開ループでは酸素と食料を運び続けることになり、農場と組み合わせて酸素と食料を内部で作れば補給は損失ぶんだけになる。
- **水タンク**は放射線の遮蔽として働く。遮蔽の能力は経路の面密度で決まり、水の密度は 1 g/cm³ であるから、面密度はそのまま厚み（cm）になる。太陽粒子線イベントには 10 g/cm²、銀河宇宙線の実用的な低減には 20〜30 g/cm² を要する。**居住区画を水タンクで囲む配置に意味が生まれ、ツリーの配置がそのまま遮蔽の配置になる。**評価は、居住区画の各方向について、そこに至る経路上の水タンクの厚みの和を求める形で行う。太陽粒子線に対しては1区画だけを厚く囲った退避区画で足り、銀河宇宙線は常時降るため居住区画そのものを囲う必要がある。
- **ドック**は機体を係留し、組立モードの作業領域を定める。収容数と最大寸法と電力を持つ。**3段階であり、初期が 50 m 立方・収容2機・8 kW、中期が 100 m 立方・収容4機・30 kW、後期が 200 m 立方・収容8機・120 kW である**（`第9版_搭載要素の性能値.md` §5-19）。電力は照明が作業領域の表面積に比例し、係留中の機体への給電が1機あたり 3 kW である。**ドックは拡張できる。**より大きなものに置き換えるか増設することで、作れる機体の最大寸法が上がる。拡張には資源と設備が要り、他のあらゆるモジュールと同じ生産の対象である。**「大きな機体を作れるようにすること」自体が、資源を投じる先の1つになる。**
- **コンテナは規格化された貨物容器であり、ツリーを持たない `Vessel` として実装する。**質量特性を直接与える経路は既にあり、コンテナはその2例目になる。接触形状は単一のカプセルとし、能力はすべて偽である。予測軌道・マップ上の表示・保存形式は他の機体とまったく同じ経路を通る。**規格は1種類だけである。**一辺 2.0 m の立方体、容積 8 m³、最大積載 10 トンとする。**この寸法は機体の直径の刻み（0.5 m）の整数倍であり、接合部を持つ機体の断面と整合する。**規格が1つしかないため、どの接合部にもどのコンテナも付き、積み替えに適合の判定が要らない。密度の上限は 1,250 kg/m³ であり、金属鉱石を積むと質量で先に頭打ちになり、液体水素を積むと質量枠の6%しか使えない。**極低温推進剤はコンテナでは運ばない。**専用のタンク機で運ぶ。
- **コンテナ接合部**は外装要素であり、コンテナを1つ保持する。保持したコンテナの質量と慣性は機体の質量特性に加わり、**接合部の位置がそのまま重心のずれになる。**切り離すと独立した機体として軌道上に残り、回収は再結合による。推進剤を積んだコンテナは、保持している間はタンクと同じく配管の接続先になる。
- **通信基地**は到達距離の大きい通信モジュールを積んだ基地であり、別種の搭載要素ではない。**開始時点の通信基地が積む通信モジュールの到達距離は、地球と月の距離（約 3.84×10⁸ m）より短い。**基地側が地球まで届くと、機体側の等級だけで地球低軌道が圏内になり、通信衛星を配備するという遊びが1手で消えるためである。**これは開始時点の条件であり、恒久的な不変条件ではない。**大型（2.0×10⁹ m）や深宇宙用（5 AU）の通信モジュールは進行に伴って誰でも作れるようになる搭載要素であり、それを基地に積み替えて到達距離が伸びること自体は正しい進行である。**禁じるのは開始時点で地球低軌道が圏内になることだけであり、積み替えの操作を拒否しない。**
- **通信基地の電力は到達距離の2乗に比例し、比例係数は 1.0×10⁻¹² W/m² である**（`第9版_搭載要素の性能値.md` §7-5）。既定の通信基地（2.0×10⁸ m）で 40 kW、地球-月間（3.84×10⁸ m）まで届かせるには 147 kW を要する。**通信基地が地球まで届かないのは、そう決めたからだけではなく、届かせる電力を払えないからでもある。**147 kW は農場を持つ8人の基地の全発電量に匹敵する。**この比例は中継点にだけ適用し、機体が積むモジュールには適用しない。**中継点は多数の機体へ常時送信し続けるのに対し、機体は1つの中継点へ間欠的に送るだけであり、同じ式を機体に適用すると大型等級が 4 MW を要求して艦艇の発電量を桁で超える。
- **機体が積む通信モジュールは、4等級のいずれか1つを選ぶ。**小型 5.0×10⁶ m / 中型 1.0×10⁸ m / 大型 2.0×10⁹ m / 深宇宙用 5 AU であり、等級表の外の値を持たせない。**既定の有人艦は 4.0×10⁸ m を積んでおり、4等級のどれでもないうえ地球-月間を超えている。中型（1.0×10⁸ m、消費電力 80 W）へ直す。**消費電力の 80 W は上の生命維持装置の見直しと同じ電力収支に入る。**帯域と指向は残し、それぞれに働きを与える。**帯域は中継点が同時に管制できる無人機の数を決め（1機あたり 64 kbit/s）、指向を持つモジュールは姿勢を失った機体では到達距離が小型等級まで落ちる（`第9版_搭載要素の性能値.md` §7-4）。**これにより、小型モジュールを大型と併せて積む理由が生まれる。**
- **基地は武装を積める。**基地は機体であり、武器・弾薬庫・戦闘用シールド・放熱板を艦艇とまったく同じ手順で搭載できる。エンジンを持たないことと基地モジュールを持つことだけが艦艇との違いである。**推進剤を消費せず、放熱板と電力に余裕があるため、同じ質量の艦艇より重い武装と厚いシールドを積める。動けないことが唯一かつ決定的な弱点である。**
- 回転による疑似重力の区画はここに含まない。

**実装内容** — 6つの区画を搭載要素の一覧に加え、農場と生命維持装置の収支、水タンクの遮蔽の評価、ドックの寸法から作業領域を導く経路、コンテナをツリーを持たない機体として登録する経路を置く。

**検証** — `tests/unit/habitat.test.ts`。閉ループ率ごとの補給量。廃熱から求まる要求放熱面積が、栽培面積の 2〜3 倍になること。水タンクの経路長から求まる遮蔽面密度。コンテナの切り離しと回収は実行時検証（切り離したコンテナが独立した物体として軌道を回り、再結合で回収できること。非対称に積むと推力軸がずれること）。

### B13. 設備の稼働と送電網

**背景と目的** — 資源の帳簿と設備の定義があり、設備の連鎖が閉じていることも検査されている。**しかし設備は動かない。**入力を出力へ変換する処理が無く、電力を消費することもない。資源が増える経路——敵のドロップと設備の変換——が無ければ、在庫は減る一方であり、生産は最初の1回で止まる。

**実装する要件**

- **設備は電力を消費して入力資源を出力資源へ一定の速度で変換する。**電力が不足した場合、停止する順序を定める。
- **敵の撃破が炭素・窒素・希少金属を落とす。**炭素と窒素は月では得られない。したがってメタン系・ヒドラジン系の推進剤を使い続けるには戦闘を継続する必要がある。**一方、水とケイ素だけで閉じる経路（液体酸素／液体水素、液体酸素／シラン）が存在するため、戦闘を行わなくても機体の運用は継続できる。**
- **初期設備は同時には動かせない。どれを動かすかを選ぶことが、最初の意思決定である。**初期設備10基の消費電力の合計は 4,200 kW であり、初期の太陽電池アレイの発電 2,000 kW の 2.1 倍である。**発電を引き上げてこの差を消さない。**電力が最初の壁であることが、資源の連鎖の入口に置かれた設計そのものである。初期設備の一組が保証するのは、資源の循環に現れるすべての入力を**最初の一度だけ**供給できることであって、10基が同時に回ることではない。
- **電力が不足したときの停止順は、プレイヤーが決められる。**設備ごとに優先度を持ち、供給が要求を下回ったときは優先度の低いものから止める。**自動で決めない。**どれを止めるかは、いま何を作ろうとしているかによって変わり、系が知り得ない。優先度を設定していない設備は、既定として一覧の後ろから止まる。
- **送電網を実体として持つ。**発電地点と消費地点を結ぶ線であり、長さに比例した損失を持ち、資源（アルミ）を消費して敷設する。被弾・断線は電力を失わせるため、冗長な経路を敷けるようにする。
- **月面の発電は峰で行い、電力を送る。**永久影のクレーターには日射が一切ない。クレーターの縁の峰は年間を通じてほぼ常時日照であり、そこに太陽電池を置いて数キロメートルから十数キロメートルの送電線で結ぶ。**峰の太陽電池は垂直に立てる。**太陽は地平線すれすれを一周するため、水平に置いたパネルは入射角が浅くほとんど発電しない。垂直に立てて水平面内で追尾する形が最も効率がよい。峰の日照は完全な常時ではなく、年に数回、数日から数十時間の中断がある。**この中断を凌ぐ蓄電容量が要る。**

**実装内容** — 設備の稼働（入力の引き当て、出力の計上、電力の消費、不足時の停止順）、敵の撃破からドロップを生成する経路、送電網の敷設と損失の計算。

**検証** — `tests/unit/facility.test.ts`（電力不足時の停止順がプレイヤーの設定した優先度に従うこと、変換の収支が入力と出力で閉じること、原料を持たない状態で設備が動かないこと、初期設備10基を同時に稼働させると電力が不足し、選んで動かせば進めること）。`tests/unit/power-grid.test.ts`（距離と送電量に対する導体質量と損失）。実行時検証（敵を撃破すると炭素と窒素が在庫に入り、それを使う設備が動き出すこと）。

### B14. 大気掠めと産地の拡張

**背景と目的** — **大気のある天体では、捕獲の Δv がほぼ不要になる。**双曲線軌道のまま大気の上層を通し、空力抵抗で減速して捕獲される。これは化学推進の到達範囲を1世代ぶん広げるほどの差になる。この運用に要るのが熱シールドであり、アブレータは炭素繊維複合材で作るため、**大気掠めを使うには炭素が要る。**炭素は敵からしか得られない。**炭素を得ることは、推進剤の性能を上げるだけでなく、到達可能な範囲の表そのものを書き換える。**

**実装する要件**

- 大気掠めによる減速を実装する。制動の1回ごとに、受けた総熱量に応じてアブレータが減る。**使い切れば防護能力を失い、以後の突入では既定の閾値に戻る。**アブレータの補充には炭素が要るため、炭素の供給地から遠い運用では、大気掠めを何回使えるかが計画の一部になる。
- 天体ごとに熱シールドの負担が異なる。火星は薄く軽い（1回の通過で捕獲できず複数周にわたる）、地球は中程度、タイタンは厚く低重力だが速度が小さいため加熱は穏やか、金星は極めて厚く突入速度が大きいため加熱が厳しい、木星は極めて厚く高重力で捕獲は可能だが脱出は別問題である。
- **熱シールドを積んでいない機体が大気掠めを試みた場合の挙動は、既存の再突入とまったく同じである。新しい失敗の形は増えない。**
- **大気捕集による産地を加える。**火星と木星の大気からキセノンなどの希ガスを捕集する。捕集は大気に入る運用であり、熱シールドを前提とする。
- **永久影の放熱を実装する。**永久影のクレーター底はおよそ 40 K であり、300 K の放熱板から見て無視できる（40⁴ / 300⁴ ≈ 0.03%）。放熱板の実効性能は軌道上の 50〜150 W/m² に対して **400 W/m²** になる。**理論上の黒体放射は 300 K の両面で 918 W/m² に達するが、実効値はその半分未満に置く。**作動流体の温度が 275〜300 K にとどまることと、パネル同士が互いを見込むことは、入熱の有無に依らず効くためである。永久影で消えるのは入熱だけであり、他の2つは軌道上と同じく効く。**永久影では放熱面が栽培面積を下回る。**軌道上では農場の 2〜3 倍の放熱板が要るのに対し、永久影では農場より小さくて済む。**この差により、大規模な農場と生産設備は軌道上より月面のほうが向く。**軌道基地は少人数の中継点と造船所に、月面基地は工業の中心になる。この役割分担は遊びの都合ではなく熱力学から出てくる。なお月のレゴリスは熱伝導率が 0.01 W/(m·K) 前後の断熱体であり、地面へ伝導で熱を捨てることはできない。放熱はあくまで放射で行う。

**実装内容** — 大気掠めの減速とアブレータの消耗を既存の突入加熱の計算の上に置く。放熱板の実効性能を背景温度の関数にする。大気捕集の産地を資源の定義に加える。

**検証** — `tests/unit/aerobraking.test.ts`（大気掠めのアブレータ消耗と減速量、使い切り後に既定の閾値へ戻ること）。`tests/unit/radiator.test.ts`（背景温度による実効性能の差が、40 K と軌道上の環境で期待どおりの比になること。永久影の実効性能が 400 W/m² であり、理論値をそのまま用いていないこと）。実行時検証（火星と木星の大気捕集でキセノンが得られること）。

### B16. 核熱・電気・核融合のエンジン型式

**背景と目的** — 化学推進の実用的な Δv は 5〜8 km/s であり、ケレスにも木星系にも届かない。**推進の世代が変わらなければ、戦域は月周辺で止まる。**エンジンの型式を表すデータ構造とツィオルコフスキーの計算が揃っていれば、新しい世代は型式の追加として入る。

**実装する要件**

- **核熱推進**（比推力 900 秒、推力は化学推進に匹敵）。固体炉心の原子炉で水素を加熱して噴射する。燃料はウランまたはトリウム。**作動流体は水素だけであり、酸化剤を必要としないため、水さえあればどこでも補給できる。**炉心は重く乾燥質量が大きいため小型の機体には向かない。**放射線遮蔽が要る。**乗員のいる区画との間に遮蔽材を置く必要があり、機体の形状が制約を受ける。ツリーによる設計はこの制約を素直に表現でき、水タンクがそのまま遮蔽になる。
- **電気推進**（ホールスラスタ 1600 秒、イオンエンジン 3000〜4000 秒、磁気プラズマ推進 5000 秒）。推進剤は火星の大気や希ガスの捕集から得る。磁気回路に希土類が要り、フライホイールの駆動モーターと同じ資源の上に載る。**推力が極めて小さく、加速度は 10⁻⁴ m/s² の程度である。大きな Δv を得るのに数か月から数年かかり、戦闘には使えない。**電気推進は戦闘用ではなく輸送用であり、「戦闘は化学推進、輸送は電気推進」という役割の分化を生む。
- **核融合推進**（比推力 10⁴ 秒以上）。重水素とヘリウム3の反応を用いる。重水素は水から分離し、ヘリウム3は木星の大気から捕集する。**この反応は中性子をほとんど出さず、荷電粒子が主生成物であるため磁場で直接噴射方向へ導ける。**これが高い比推力の理由である。ヘリウム3の同位体分離には極めて大きな電力が要り、原子炉が前提になる。
- **意図した循環を1つ残す。**木星の大気を捕集し、その重力井戸から脱出するには 20 km/s 級の Δv が要る。核融合推進なしにはヘリウム3を持ち帰れず、ヘリウム3なしには核融合推進が作れない。**この循環は、最初の一回だけ核熱推進と電気推進を組み合わせた片道の大型機で破る。**その質量比が有限に収まることを検証で確かめる。

**実装内容** — エンジンのサイクルの表に3つの型式を加える。ヘリウム3の同位体分離を設備として加える。核熱推進の遮蔽の要求は、水タンクの遮蔽の評価と同じ経路（経路上の面密度の和）を通す。

**検証** — `tests/physics/tsiolkovsky.test.ts` の拡張。`tests/unit/jupiter-escape.test.ts`（木星大気の捕集地点から脱出するのに要る質量比が、核熱推進と電気推進の組み合わせで有限に収まること）。

## 8. 飛行中の表示と操作

### B11. 飛行中のパネル

**背景と目的** — 通信圏の判定は毎フレーム更新され、圏外の無人機の計画実行を実際に止めている。**しかしプレイヤーには、なぜ無人機が動かないのかが分からない。**熱シールドのアブレータは加熱に応じて減り、尽きれば閾値が戻るが、残量を見る手段が無い。段は分離順を持ち、ペイロード倉庫は中身を持つが、いずれも飛行中に見えない。**払った実装の費用が、パネル1枚で初めて見えるようになる。**

**実装する要件**

- **通信パネル** — 通信圏の内か外か、最寄りの中継点、到達距離の余裕。**このパネルは他のどれとも独立に、いつでも置ける。**読むのは既に動いている判定の結果だけであり、段の一覧やペイロードのパネルが要求するものを何も共有しない。**圏内・圏外の2値だけにしない。**なぜ圏外なのかが分からなければ、どちらへ動けば繋がるかも分からない。最寄りの中継点と到達距離の余裕を併記して初めて、圏外という表示が行動の指示になる。
- **マップ上への通信圏の可視化は、このパネルと同時には置かず、B11 の本体と同じ時期に置く。**圏外に出た瞬間の通知だけでは、その時点で手遅れになっている——計画を立てる前に穴が見えることが要る。**しかし圏の形は、天体の影と到達距離の球面が交わる複雑な形であり、パネル1枚とは費用が桁で違う。**先に置いたパネルだけでも、通信圏の判定に既に払った実装の費用が初めて画面に現れる。
- **段パネル** — 段の一覧、次に分離する段、段ごとの残 Δv、分離の実行ボタン。
- **ペイロードパネル** — ペイロード倉庫の内容と、放出の実行ボタン。
- **熱シールドのアブレータ残量** — **大気に入る軌道を持つ機体に対して常時表示する。**尽きた時点で防護能力を失うため、尽きる前に知る必要がある。
- 配管モードの左パネル（自動敷設のやり直し、手動の上書きの破棄、エンジンごとの供給状態の診断、分離を跨ぐ配管の許可、手動で敷く操作）と、右レールの段の一覧。**配管モードの操作の形は決まっていない**（`第9版_設計UIの案.md`）。要件は、自動敷設の結果を確認できること、手動で上書きできること、供給されていないエンジンとその原因が示されること、分離を跨ぐことを許すと自動敷設がそのエンジンへ届くようになることである。
- いずれのパネルも個別に折り畳める。既存のウィジェットのみで構成し、生の `<button>` および `<input>` を直接書かない。

**実装内容** — 各パネルは表示専用であり、他のモジュールの状態を読むだけで、書き込まない。通信パネルは通信圏の判定の結果を読む。段パネルは段の分割の結果を読み、分離の実行だけを呼ぶ。加圧ガスの残量とその余裕での残り燃焼可能時間は、推進系パネルの主機の行に置く（F13）。磁気トルカが働いているかどうかも推進系パネルの姿勢制御の行に置く。**同じ値を2つのパネルが別々に表示しない。**

**検証** — 実行時検証。圏外の無人機で通信パネルが圏外と最寄りの中継点を示すこと。大気に入る軌道の機体でアブレータ残量が常時見えること。分離を跨ぐ配管を許すと診断の供給なしが解消すること。

### B17. モジュールのプロパティーウィンドウ

**背景と目的** — 機体は搭載要素の合成として性能を持ち、装甲も要素ごとに減り、要素はそれぞれ機体上の取り付け位置を持つ。**そのどれも、飛行中に見る手段が無い。**全画面のドックの画面は格納中の機体しか扱わない。機体の装甲が半分であることと、コックピットが半分であることと、放熱板だけが失われていることは、まったく違う状態である。**モジュールのウィンドウは、その内訳を見る唯一の手段である。**

戦闘ビューでは機体が実寸で描かれ、搭載要素はそれぞれ取り付け位置を持つ。したがって画面上のどこを指したかは、どの機体かだけでなく、**その機体のどのモジュールか**まで決まっている。**マップビューの右クリックは機体単位のままである。**マップ上で機体は1つのマーカーであり、モジュールは画面上に存在しない。存在しないものを指すことはできない。

**実装する要件**

- 判定は2段階である。まず画面座標から機体を選び、次にその機体のモジュールの集合に対して同じ最近傍の判定を行う。**モジュールの当たりは、それが画面上で占めている領域そのものである。**見えている場所を指せばそれが選ばれる、という以上の規則を持たない。
- **内装要素は外から見えないため、当たりを持たない。**内装要素を収めた `hull` エッジは、そのエッジの外皮を当たりとし、指すとそのエッジに収めた内装要素の一覧を持つウィンドウが開く。1つのエッジに複数の内装要素が同居しうる以上、外から1つを撃ち分けることはできない。
- **外装要素と、その背後の `hull` エッジが重なる場合は外装要素を優先する。**外側にあるものが先に見えている。外装要素どうしが重ならないことは設計の検証が保証しているため、外装要素の間で取り合いは起きない。
- **どのモジュールにも当たらなかった場合は、その機体の操作モジュールを指したものとして扱う。**機体の輪郭に当たった以上、機体そのものを指したことは確かである。
- **画面上の見かけの直径が 12 px を下回るモジュールは、判定の候補から外す。**遠くの機体は全体が数ピクセルであり、モジュールを撃ち分けることが物理的にできない。**12 px は戦闘ターゲットの選択半径と同じ桁であり、モジュールを指す操作と機体を指す操作の手触りが揃う。**候補から外れたモジュールは、ホバー時の強調表示が出ないことで示す。近づけば選べたはずのものが選べないことは起きるが、**選べないことが操作の前に見える。**この場合は機体単位の判定だけが残る。**距離によって粒度は落ちるが、粒度が落ちても答えは常に存在する。指した先が無いという結果を返さない。**
- **ウィンドウは既存のプロパティーウィンドウをそのまま用いる。**ヘッダ／プロパティ行／操作項目の3段、ヘッダのドラッグによる移動、クリップ、クリップした複数枚の並置は機体単位のウィンドウとまったく同じである。**新しいウィンドウの実装を作らない。**
- 表示するのは、装甲（そのモジュールの残 HP と最大 HP）・状態（稼働／停止／損傷／機能喪失）・質量（乾燥質量と内容物を含む現在質量）・電力（消費または発電）と、**種別ごとの性能値**である。**種別ごとの行は搭載要素の一覧を唯一の出典とし、この段階で別の性能値を定義しない。**一覧が定めるのは設計上の定数であり、ウィンドウはそれに実機の現在値を並べる。エンジンなら、対応推進剤・サイクル・推力・比推力・全長・ジンバル可動角・絞り範囲・再着火回数・点火損失・連続燃焼時間の上限という定数に、現在の絞り率・供給の状態・与圧の余裕・残りの再着火回数を並べる。タンクなら、対応推進剤・容積・断熱等級・要求与圧・材料という定数に、現在の残量と蒸発損失率を並べる。放熱板なら、面積・放熱効率・展開の可否に、現在の展開角と実際に捨てている熱量を並べる。
- **機体全体のウィンドウは、操作モジュールのウィンドウである。**機体を操作する主体になっているモジュール——有人艦ならコックピット、基地なら基地モジュール、無人機なら自動操縦装置——を右クリックしたときに開くのは、そのモジュールに固有のウィンドウではなく機体全体のウィンドウである。**これは例外ではない。**機体を操作するとは操作モジュールを通して操作することであり、機体全体の集計値はその主体から見た値である。総推力とは、コックピットに座った者が出せる推力のことである。候補が複数ある場合の序列は**コックピット → 基地モジュール → 自動操縦装置**とする。人が乗っているなら、その人が主体である。
- **操作項目は、そのモジュール自身に閉じたものだけを置く。**エンジンは有効・無効の切り替えと供給の診断、タンクは結合相手への移送、太陽電池パドルと放熱板は展開・収納と追尾の入切、武器は射撃の許可・禁止、通信モジュールは指向の対象、ドッキングポートはドッキングの目標に設定、分離機構は「ここで分離」、シールドは向きの指定と残量の確認、ペイロード倉庫は開閉と放出、内装要素を収めたエッジは収めた要素の一覧である。**機体全体に効く操作（操作対象の切り替え、軌道計画の実行、複製、削除）は操作モジュールのウィンドウにしかない。モジュールを1つ選んだつもりで機体ごと消える、ということが起きない。**
- **分離機構の「ここで分離」がモジュール側にあるのは、それがその分離機構自身に閉じた操作だからである。**どの段を切り離すかは、どの分離機構を指したかで決まっており、段の番号を選び直す必要がない。**指すことがそのまま選ぶことになっている。**
- **操作モジュールを持たない機体の扱いを定める。**ツリーを持たない機体（コンテナ・敵艦）はモジュールの判定を行わず、機体単位のウィンドウを開き、質量特性から分かる範囲と外から観測できる範囲だけを表示する。**内訳が隠されているのではなく、その機体に内訳という構造が無い。**ツリーを持ち操作モジュールを持たない機体（推進剤を使い切って切り離した空段、自動操縦装置を積まないブースター）ではモジュールの判定はそのまま働き、どのモジュールにも当たらなかったクリックが開くのは**集計値だけを表示し操作項目を1つも持たない機体全体のウィンドウ**である。操作できないことが、操作する口が無いこととして画面に現れる。**理由を文章で説明しない。**敵対勢力の機体はツリーを持つならモジュールの判定が働き、外から観測できる情報だけを表示して操作項目を持たない。**どこに主機があり、どこにタンクがあり、どこが既に壊れているかが見えることは、そこを狙うという判断の材料である。**

**実装内容**

戦闘ビューの右クリックを受け取るのは既存の右クリックの経路であり、判定の結果に応じて開くウィンドウの内容を切り替える。ウィンドウの実装は既存のもの、当たり判定の射影は既存のものを用い、どちらにも並行する実装を作らない。

**判定の純関数とプロパティ行の組み立ては今すぐ書け、単体テストだけで検証できる。しかしそれだけでは画面に何も現れない。**戦闘ビューへ配線して答えが正しいことを確かめるには、自機が設計から生成した外皮で描かれていることが要る。事前生成のモデルで描かれている間は、画面上で指した位置と搭載要素の取り付け位置が対応せず、指した先が合っているかを判断できない。**したがって F12 の直後に配線する。**同じ機体を組み立てるのに使った外皮が、そのままモジュールを指すための当たりになる。分離機構の「ここで分離」だけは B1 を要するが、それ以外の種別の行と操作項目は B1 と無関係に揃う。

## 9. 月面と資源採掘

**この4つを実装の対象に置く理由** — 資源の帳簿・生産可能性の判定・設備の定義は揃っており、生産（B6）と設備の稼働（B13）がそれを動かす。**しかし資源が生まれる場所が無い。**敵のドロップは炭素・窒素・希少金属を与えるが、水とケイ素とアルミは月の南極からしか得られず、そこへ降りて掘るという経路が存在しなければ、月で閉じる資源の連鎖は成立しない。**採掘が無ければ、帳簿も生産設備も動かす材料が無い。**要件はいずれも固まっており、決まっていないことは残っていない。実装費用は大きく、とりわけ地形は既存の天体が球のみで描かれていることを崩すが、費用の大きさは順序を後に置く理由にはなっても、対象から外す理由にはならない。

### L1. 月の地形

**背景と目的** — 天体は球として描かれ、球として接触が判定される。**永久影と永久日照の峰という立地は、地形が無ければ存在しない。**月面基地がそこにあることも、太陽電池を峰に建てて送電することも、放熱が極端に有利であることも、すべて地形の起伏に立っている。

**実装する要件**

- 月の表面を球面上の高度場として表す。全球は粗い解像度で表し、機体の周囲のみ細かい格子を生成する。**細部は決定的な擬似乱数で生成し、同じ座標では常に同じ地形になるようにする。**
- 粗い全球データと局所生成の境界で高度が不連続にならないよう、**局所生成は全球データを基準面として、その上に細部を加算する形とする。**
- 座標は天体固定座標（月とともに自転する座標系）で扱う。慣性座標との変換は既存の自転位相を用いる。
- **南極域は永久影クレーターと、その周囲の永久日照の峰を含むよう構成する。**日照の判定は太陽方向に加えて地形の地平線を考慮し、クレーター底部が常に日陰に、峰の頂が年間を通じてほぼ常時日照になるようにする。**この2つが近接して存在することが、月面基地の立地の前提である。**
- 地形メッシュの生成と、カメラ距離に応じた解像度の切り替えを持つ。
- **天体表面への到達判定は、地形を持つ天体に対してのみ高度場との判定に置き換える。**地形を持たない天体は球のままとする。この判定は全エンティティの毎ステップで走るため、分岐の費用を意識する。

**実装内容**

```
src/physics/terrain/height-field.ts   (純関数)
    heightAt(bodyId, latRad, lonRad) -> number   // 基準球半径からの高度 [m]
    normalAt(bodyId, latRad, lonRad) -> Vec3     // 地形法線（天体固定座標）
    surfacePointAt(bodyId, latRad, lonRad) -> Vec3
```

**検証** — `tests/physics/height-field.test.ts`。同じ座標が常に同じ高度を返すこと。粗い全球データと局所生成の境界で高度が連続であること。永久影クレーターの底が全期間にわたって日陰であり、峰の頂がほぼ常時日照であること。目視確認（地形メッシュの解像度の切り替えが見えないこと）。

### L2. 着陸

**背景と目的** — 機体は天体表面に到達すると失われる。**降りるという操作が存在しない。**月面基地が着陸した機体である以上、また月面で生産した物資を軌道へ運ぶ以上、降りて留まり、再び上がることが要る。

**実装する要件**

- 固定脚を搭載要素として持つ。接地点の機体ローカル座標・緩衝行程・損傷なく吸収できる接地速度・収納の可否を持つ。**3本以上を装着した機体のみ着陸できる。**
- 固定脚の接地点それぞれを接触点として扱う。接触点が地形面より下に入った場合、法線方向の反力と接線方向の摩擦を与える。**固定脚を持たない部位が地形に接触した場合は損傷を与える。**
- 接地の瞬間に、垂直速度・水平速度・傾斜（機体の脚面法線と地形法線のなす角）・角速度・接地脚数のすべてが許容範囲に収まる場合、着陸が成立する。いずれかを外れた場合、超過量に応じて固定脚および接触部位に損傷を与え、大きく外れた場合は機体を破壊する。
- **着陸が成立した機体は着陸状態を持ち、天体固定座標に静止する。静止中は軌道積分を行わず、天体の自転に従って位置と速度を導出する。**静止した機体を数値積分し続けると、重力と反力の釣り合いの誤差が蓄積して沈み込みまたは浮上が生じる。積分から外すことがこの扱いの目的である。
- 離陸は、主機の推力が機体重量（その天体の表面重力加速度と機体質量の積）を上回った時点で着陸状態を解除し、通常の積分に戻すことで行う。**着陸状態への遷移と解除が短時間に繰り返されないよう、遷移条件に履歴を持たせる。**

**実装内容** — 固定脚を搭載要素の一覧に加え、着陸状態を機体の状態として持ち、積分の対象から外す経路を置く。接地点ごとの接触は既存の剛体接触とは別の処理として書く。

**検証** — `tests/unit/landing.test.ts`（着陸の成立条件が条件ごとに判定されること、超過量に応じた損傷が単調であること、遷移条件の履歴が振動を抑えること）。実行時検証（着陸した機体が沈み込みも浮上もせずに静止し続けること、時間加速中も静止が保たれること、離陸して通常の軌道に戻れること）。

### L3. 月面基地

**背景と目的** — **月面基地は、固定脚を持ちエンジンを持たない機体である。**艦艇や軌道基地と同じ実体であり、クラスを分けない。基地がそこにあることは、資源の産地の上に生産の場を置くことである。

**実装する要件**

- 月面基地は月の南極の永久影クレーターの中に置く。立地の理由は3つである。**氷がある**（永久影のレゴリスには水の氷が含まれ、水は推進剤・飲用・農場・遮蔽のすべての起点になる。採掘地の上に基地を置けば運ぶ距離が最短になる）。**放熱が極端に有利である**（底は約 40 K であり、300 K の両面放射の理論値は `2 × σ × (300⁴ − 40⁴) ≈ 918 W/m²` に達する。**実効値はその半分未満の 400 W/m² を採る。**作動流体の温度が 275〜300 K にとどまることと、パネル同士が互いを見込むことは、入熱の消える永久影でも軌道上と同じく効くためである。それでも軌道上の実効値 50〜150 W/m² の 3〜8 倍である）。**恒常的な遮蔽が得られる**（月体そのものが下半球を遮り、クレーターの壁が視界の大半を塞ぐ。同じ水量の遮蔽でも軌道上より被曝が小さい）。**代償は日照がまったく得られないことである。**
- 月面に静止した機体では、いくつかの区画の働きが軌道上と異なる。居住区画は回転させなくても月面重力が常時かかる。**農場は永久影には日照がないため完全に電照であり、太陽光導入は使えない。**放熱板は 40 K に向かって放射するため、栽培面積より小さくて済む。地面への伝導は使えない。ドックは着陸してきた機体を受け入れ、着陸接続が成立している機体との間で資源をやり取りできる。コンテナ接合部は採掘した資源と生産した物資の貯蔵に用いる。
- **月面基地は複数機を結合して拡張できる。**結合はドッキングポートによって行い、電力は統合され、資源は移送できる。**したがって基地の拡張と、軌道上での機体の結合は同一の機構である。**
- 月面基地は通信基地である。ここから見通しの立つ範囲が通信圏の一部になる。月の裏側と、南極から見えない軌道を通信圏に含めるには通信衛星の配備が要る。
- **設置地点の選択が運用に効く。**永久影への近さ、日照の峰への近さ、地形の平坦さの3つが相反する。氷と放熱には永久影の底がよく、電力には峰が近いほうがよく、大型の基地を置くには平坦な地形が要る。峰から遠い底に置けば送電損失が増え、峰に近い斜面に置けば平坦地が足りない。
- 月面基地は設計エディタで設計する。エンジンを積まず固定脚を積んだ設計であり、他の機体と同じ手順で生産する。生産した月面基地は、輸送機で月面まで運ぶか、月面で直接生産する。

**実装内容** — 月面基地は着陸状態の機体であり、新しい実体を作らない。設置地点の選択は着陸地点の選択そのものである。区画の働きが月面で異なる点は、放熱の背景温度と農場の光の方式として表す。**永久影の底と永久日照の峰という離れた2地点を1つの基地が持つ形は、送電網（B13）が結ぶ2つの機体として表し、1つの機体が離れた2地点に部分を持つ構成にしない。**

**検証** — 実行時検証。月面基地が永久影に静止し、峰の太陽電池から送電を受けて設備が動くこと。ドッキングポートで結合して拡張できること。通信圏が月面基地から伸びること。設置地点を変えると送電損失が変わること。

### L4. 資源採掘・生産・輸送

**背景と目的** — **資源が生まれる場所が要る。**水は月の南極の永久影クレーターの採掘から、酸素・ケイ素・アルミはレゴリスの精錬から得る。炭素と窒素は月では得られず、敵の撃破からのみ得られる。**したがって、メタン系・ヒドラジン系の推進剤を使い続けるには戦闘を継続する必要がある。一方、水とケイ素だけで閉じる経路が存在するため、戦闘を行わなくても機体の運用は継続できる。**この非対称が、資源の設計の中心にある。

**実装する要件**

- 採掘設備が、月面基地の立地からレゴリスまたは氷を掘り出す。産地は地点に紐づき、そこに静止した基地だけが掘れる。
- **月面で生産した物資を軌道基地へ運ぶ手順を成立させる。**月面基地に着陸した機体のコンテナまたはペイロード倉庫に、月面基地の倉庫から資源を積み込む（両者がドッキングポートで結ばれているとき、または着陸接続が成立しているときに行える）。離陸し、月面から目的の軌道への遷移を行う。軌道基地とドッキングし、貨物と推進剤を移送する。
- **貨物の質量は機体の総質量に加算されるため、輸送量を増やすほど必要な Δv に対する推進剤が増える。**この関係により、1回の輸送量には設計上の最適点が生じる。**輸送そのものが遊びの対象になる。**
- 軌道基地は近直線ハロー軌道に置く。**この軌道の初期状態は線形近似であり、多体重力を含む数値積分に投入すると発散する。**したがって軌道基地は近月点通過ごとに数 m/s の維持バーンを軌道計画の自動実行によって行い、そのぶんの推進剤を消費する。**軌道基地の維持そのものが資源の消費先になる。**この基地は月の南極と地球の双方に対して見通しが長く保たれるため通信基地であり、それがこの軌道が選ばれている理由である。
- **軌道基地は襲われうる。**敵は低軌道に限らず出現し、月周辺にも現れる。軌道基地は月の重力井戸の外にあり小さな Δv で到達できるため、防衛を考える必要がある。武装と戦闘用シールドを積むか、即応できる艦艇を接舷させておくか、いずれかが要る。**月面基地は井戸の底にあり到達に大きな Δv を要するため、相対的に安全である。**
- **序盤、基地は自ら敵と交戦する。**開始時点では通信圏が狭く船団を遠くへ出せないため、近直線ハロー軌道の基地はそこへ来る敵を自分で迎え撃つ。基地は移動しない戦闘艦艇として働く。**近直線ハロー軌道の敵を掃討したのち、戦域は移動する艦艇によって外へ広がる。**

- **この段階が通った時点で、基地の在庫を手動で増やす手段（B6）を削除する。**資源はゲーム内で確保するものになり、デバッグのための足場は要らなくなる。**削除まで行って初めて、進行を止めるものが常に物理的な事実であるという骨格が実際に成立する。**

**実装内容** — 採掘設備を設備の一覧に加え、産地を地点に紐づける。積み込みは、ドッキングまたは着陸接続が成立している2機の間の資源の移送であり、B2 の移送の経路をそのまま通す。**新しい輸送の仕組みを作らない。**軌道基地の維持バーンは既存の軌道計画の自動実行を使う。

**検証** — 実行時検証。月面基地で水を採掘し、電解して液体水素と液体酸素を得て、それを積んだ機体が離陸して軌道基地とドッキングし、移送できること。輸送量を増やすと必要な推進剤が増え、最適点が存在すること。軌道基地が維持バーンを行わなければ軌道を外れること。

## 13. 技術的リスク

1. **減衰最小二乗の正則化重み**（F9） — 重みが小さすぎると、要求をわずかに良く満たすために対向するスラスタを同時に噴かせ、推進剤を無駄に消費する解が選ばれる。大きすぎると要求トルクを十分に出せない。重みは行列の特異値の大きさに対する相対値として決めること。

2. **アンローディングの発振**（F9） — 飽和と排出は互いを打ち消す方向に働くため、閾値と排出量の取り方によっては短周期で往復する状態に落ち込む。**排出の開始と終了に別々の閾値を設けること。**

3. **磁気トルカで出せない軸**（F9） — τ = m × B は B に平行なトルクを出せない。B に垂直な成分だけを扱い、**平行成分は必ず次の段へ落とすこと。**

4. **姿勢制御の要求元の一元化**（F9） — 手動操作と自動操縦の両方を要求に置き換えないと、フライホイールの角運動量を更新せずにトルクを出すことになり、飽和の計算が合わなくなる。**片方でも直接書いていれば成立しない。**

5. **時間加速中の燃焼**（F10） — 1ステップが数十秒に達する時間加速下では、ステップ内での質量変化が無視できない。燃焼中のステップは閉形式で質量を進めるか、燃焼の開始と終了の時刻でステップを区切ること。

6. **カプセル判定の費用**（F8） — 機体1機がエッジの数だけカプセルを持つため、機体同士の判定は組み合わせになる。**外接球による広域の絞り込みを必ず先に通し、球が交わる場合のみカプセル同士を総当たりする。**エッジ数の上限が判定の上限を決める。

7. **断面をまたぐ頂点の対応**（F12） — 辺数の異なる断面や、回転位相の異なる断面をつなぐとき、頂点の対応を誤ると外皮がねじれる。弧長による等分と、対応距離の総和を最小にする割り当てで解決するが、両端の位相差が大きい場合の見た目は確認が要る。

8. **描画メッシュの生成コスト**（F12） — 実行時生成であり、ジオメトリは最初の描画時にキャッシュされる。**生成は形状の変更時のみとし、既存メッシュのジオメトリを差し替えない運用を守ること。**

9. **姿勢依存の弾道係数と予測**（F8） — 予測は未来の姿勢を持たないため、予測では現在の姿勢の値を固定して使う。姿勢を保っている機体では正確であり、回転している機体では平均から外れる。**再突入の予測が姿勢に依存することを画面で示す必要がある。**

10. **分離後の状態の再構成**（B1） — 分離は、ツリー・質量特性・推進剤残量・配管の流路をすべて再計算する。1つでも古い値が残れば、分離後の機体は存在しない部品の性能で飛ぶ。**再計算の入口を1つに絞り、部分的な更新の経路を作らないこと。**

11. **段を跨ぐ燃焼の分割**（B1, F10） — 分割の提案は、1つ目の燃焼が終わった時点の質量と、2つ目の段の点火損失を正しく織り込む必要がある。**分割した2つのノードの Δv の和が、元のノードの Δv と一致しない**（点火損失のぶん増える）ことを、表示の上でも隠さないこと。

12. **自動敷設の安定性**（B9） — 最短経路の選択が、辺の長さの僅かな差で切り替わると、設計を少し変えるたびに配管が飛び回る。**経路の選択に安定な順序を与え、同じ設計からは常に同じ配管が出ること。**

13. **手動の上書きと設計変更の衝突**（B9） — 手動で敷いた区間のエッジが削除されたとき、その上書きは行き場を失う。**削除で失われた上書きを黙って捨てるか、警告するかを決めておくこと。**

14. **クロスフィードと分離順の整合**（B9, B1） — 分離を跨ぐ配管を許した構成では、分離の順序によって供給が途切れる先が変わる。**分離順を並べ替えたときに、供給の診断が追随すること。**

15. **推力軸のずれによる制御不能**（F13, B2, B12） — 主機を非対称に積む、コンテナを非対称に積む、結合体の重心が偏る——いずれも推力軸が重心を大きく外れる。**ジンバル補償で打ち消しきれない構成は、警告を出したうえで、それでも機体が回ることを許すか拒否するかを決めておくこと。**

16. **組立モードのカメラが機体に埋まる**（B7） — カメラは基地を追う戦闘ビューのカメラであり、組み立て中の機体はその近くにある。**大きな機体を組むと、カメラが外皮の内側に入る。**この状態での見え方を決めておくこと。

17. **モジュールを撃ち分けられる距離が限られる**（B17） — 見かけの直径が閾値を下回るモジュールは候補から外れるため、遠距離では機体単位の判定しか残らない。**粒度が落ちることをプレイヤーが理解できるようにすること。**指した先が無いという結果は返さない。

18. **意図した循環と、それを破る質量比**（B16） — 木星大気のヘリウム3は核融合推進なしには持ち帰れず、核融合推進はヘリウム3を必要とする。**この循環は、核熱推進と電気推進を組み合わせた片道の大型機で破る設計になっている。その質量比が有限に収まることを、実装の前に数値で確かめること。**

19. **電気推進の時間スケール**（B16） — 加速度が 10⁻⁴ m/s² の程度であるため、意味のある Δv を得るのに数か月から数年かかる。**時間加速の上限と、その間の予測の維持費用が問題になる。**

20. **静止した機体の積分**（L2） — 静止した機体を数値積分し続けると、重力と反力の釣り合いの誤差が蓄積して沈み込みまたは浮上が生じる。**静止状態を積分から外して天体固定座標に固定する扱いが必須である。**着陸状態への遷移と解除の条件を明確にしないと、遷移の前後で状態が振動する。

21. **地形の到達判定の費用**（L1） — 天体表面への到達判定は全エンティティの毎ステップで走る。**地形を持つ天体に対してのみ高度場との判定に切り替える分岐が、その頻度で入る。**分岐の費用と、高度場の参照の費用を測ること。

22. **保存形式の互換性**（B1, B6, B9, B12） — 設計、手動で上書きした配管、段の分離順、ペイロード倉庫とコンテナの内容、基地の資源在庫、建設済み設備、送電網の構成、熱シールドのアブレータ残量、生産時間係数を保存する。**自動敷設の結果は設計から再導出できるため保存しない。**読み替え不能な保存データは明示的に拒否し、破損した機体を生成しないこと。

23. **計算層が DOM と THREE に依存する**（全段階） — テストの `lib` は `ES2022` のみであり、DOM も THREE も無い。**新設する純関数は必ずこの制約の内側に置くこと。**計算部分と描画・DOM に触れる部分を最初から分けておかないと、書いたテストがコンパイルできない。

24. **UIの総量**（F13, B7, B8, B11, B17） — 推進系パネル、通信パネル、段パネル、ペイロードパネル、組立モードの左右のレール、モジュールのプロパティーウィンドウが加わる。**既存のパネルへ統合できないかを確認し、置き場の規約に従うこと。**同じ値を2つのパネルが別々に表示しないこと。

25. **掴んでいる部材の3次元の位置**（B8） — 戦闘ビューのカメラは6自由度で回るため、画面上のドラッグから3次元の位置を一意に決められない。**掴んだ部材の位置を自由に決めさせないこと。**空いている接続口の集合に対する画面最近傍の選択に限れば、決め方は一意になる（§14-5）。最初の1本だけは吸着先が無いため、作業領域の中央に固定して置く。

26. **閉じる構造の最後の1本**（B8） — 三角形や梯子状の構造は、最後の1本が両端で同時に吸着しなければ閉じない。**両端の口の距離が部材の長さと一致しない限り吸着させないこと。**一致しないまま置けば、`validateTree` がエッジの長さとノードの距離の不一致として拒否する設計が立つ。吸着を拒む時点で、要る長さと持っている部材の長さを並べて示すこと。

27. **一括再生産が元と同じ機体を出すこと**（B8） — 設計から起こした部材の列で組み直した機体は、元の機体と同じ形状ツリーを持たなければならない。**部材の列に、断面・長さ・位相・種別のすべてが乗ること。**1つでも落ちれば、同じ設計から別の形が出る。読み取りと再生産が互いの逆であることを、質量特性の一致で機械的に固定すること（§14-7）。

## 14. 案Bの実装 — 部材の生産と突き合わせによる建造

**この節は B7 と B8 の実装の全体を定める。**操作の形は `第9版_設計UIの案.md` の案Bである。要件は B7・B8 が持ち、この節はそれをどのクラスとどの HUD で実装するかを持つ。

### 14-1. 設計を資産として残すこと

**案Bは、そのままでは突き合わせた結果がその場の1機で終わる。**同じ機体を10機作るには10回同じ組み立てをすることになり、3つのものが壊れる。設計データの保管庫（`src/game/vessel/blueprint-library.ts` の `BlueprintLibrary` と `blueprint-transfer.ts` のファイル入出力）は保存する対象を失う。設計の検証19項目（`src/game/vessel/blueprint-validation.ts` の `validateBlueprint`）は通される機会を失う。ドックの拡張・軌道上での結合（B15）・想定される進行経路は、いずれも同型の機体を複数作ることを前提としている。

**採る解き方は、組み上がった物を設計として記録し、記録した設計から一括で再生産できるようにすることである。**

- **記録** — [完成とする] を押した時点で、突き合わせた口の対応から形状ツリーを起こす（§14-3）。起こしたツリーは `VesselBlueprint` として保管庫に入り、保存・複製・改名・ファイル入出力の対象になる。**保管庫も検証もファイル入出力も、そのまま生きる。**
- **再生産** — 保存した設計から、それを組むのに要る部材の列を起こす（§14-3 の `rebuildPlan`）。棚にある部材を充当し、足りないものを生産にかけ、突き合わせを系が再現する。**プレイヤーが手で組むのは、初めて作る1機のときだけである。**

**この解き方が案Bの利点を損なわない理由は、記録が組み立ての後に来ることにある。**資源は部材を生産する瞬間に消費され、組み立ての操作は資源を一切消費しない。**「アルミが尽きたのでトラスに切り替える」という判断は、初めて作る1機の組み立ての最中に、そのまま発生する。**記録はその判断が済んだ後に形を写し取るだけであり、判断に先回りしない。一括再生産も、要る部材を生産する時点で同じ資源の壁に当たる——設計を持っていることは、資源を持っていることを意味しない。**設計は形の記録であって、物を作る権利ではない。**

**別の解き方を採らない理由。**同型機の複製を「実機をコピーする」形で与えれば記録は要らないが、資源を消費せずに機体が増える経路になり、通貨を持たず進行が物理的な事実で止まるという方針を壊す。組み立ての手順そのものを記録して再生する形も採らない——手順は形より多くの情報を持ち、途中で外した部材や置き直しまで記録することになる一方、再現に要るのは最終的な形だけである。**記録するのは形である。**

**状態の所有者は3つに閉じる。**

- **部材の在庫は `PartStock` が持ち、`PartStock` は基地モジュールを持つ `Vessel` が1つ持つ。**`ResourceLedger` と同じ場所であり、同じ保存形式に乗る。在庫は基地ごとであり、移送は輸送しかない。
- **組み立て途中の物は `AssemblyDraft` が持ち、`AssemblyDraft` は `AssemblyMode` が1つ持つ。**これは `Vessel` でも `VesselBlueprint` でもない第3の状態であり、その基地に紐づいて保存形式に加わる。組立モードを閉じても消えない。

**`AssemblyMode` は `update` と `sync` に分ける。**`update(input, dt)` が掴む・運ぶ・突き合わせる・外すを進め、`sync(fo, camera, project)` が `AssemblyView` の3Dと左右のパネルへ結果を押し込む。**`update` は THREE に触れない。**吸着候補の解決は画面座標を要するため、その1点だけは前フレームの `ProjectFn` を `update` が読む——`sync` が毎フレーム押し込む値であり、1フレーム古い投影で候補を選ぶことは、選び直しが毎フレーム走る以上、見えない。

**層を跨ぐ口は狭い構造的インターフェースにする。**`AssemblyMode` は `Vessel` を持たず、在庫と棚と設備と電力だけを答える口を持つ。

```ts
// src/game/build/assembly-mode.ts
export interface AssemblyHost {
  readonly ledger: ResourceLedger;
  readonly stock: PartStock;
  readonly facilities: readonly FacilityId[];
  readonly powerAvailable: number;
  readonly workArea: WorkArea;          // ドックモジュールが定める作業領域
  moorVessel(assembly: VesselAssembly, paint: PaintScheme): void; // 完成した実機をドックへ
}
```

基地の `Vessel` はこの形を構造的に満たす。`AssemblyMode` から `Vessel` の他の全てへ手が届かないことが、この口の目的である。

**部材1つが1エッジになり、突き合わせた口の対が1ノードになる。**これが読み取りの全体であり、ノードは口の対の側に立つのであって、部材の側には無い。


**5つの拒否理由は、突き合わせの操作が成立した時点で満たされていてほしい制約そのものである。**口が既に埋まっていないこと・断面が口に収まること・辺数と位相が合うこと・閉じる構造で長さが合うこと・作業領域に入ること。`mateVerdict` が真を返した突き合わせだけを `AssemblyDraft` に積むため、**積んだ物からは必ず `validateTree` を通るツリーが起きる。**

### 14-6. 検証19項目をいつ通すか

**`validateBlueprint` は、[完成とする] を押して `treeFromDraft` がツリーを起こした直後に、`blueprintFromDraft` の中で通す。**

```ts
// src/game/vessel/build/blueprint-from-draft.ts
export interface DraftBlueprintResult {
  readonly blueprint: VesselBlueprint;
  readonly issues: readonly BlueprintIssue[];
}

export function blueprintFromDraft(
  draft: AssemblyDraft, id: string, name: string, now: number,
  limits: BlueprintLimits,
): DraftBlueprintResult | null;
```

**通す時点が組み立ての後であることが、19項目の働き方を2つに分ける。**

- **突き合わせの操作が既に満たしているもの**——連結性・接続口の排他・側面の口の寸法の適合・隣接する口の干渉・トラス上の混み合い・外表面のRCSの干渉。これらは `mateVerdict` が吸着を拒むことで、そもそも成立しない配置が積まれない。**検証としては通るが、通ることが `mateVerdict` の正しさの証明になる**——落ちたなら `mateVerdict` に穴がある。
- **組み上がって初めて分かるもの**——内容積の割り当て・タンク材料の適合・操縦系の有無・配管の連続性・加圧の経路・段の成立・熱シールドの向き・推力軸と重心のずれ・ノード数と総質量と最大寸法の上限。**ここが実際に働く。**

**`error` は完成を拒み、`warning` は拒まない。**成り立たない設計から実機を作らないことと、性能が悪い設計を作る自由を残すことは別である。拒んだときは `BlueprintIssue.targetId` が指す部材を3Dで赤く強調する——`targetId` はノード・エッジ・搭載要素の id であり、`treeFromDraft` が返す `edgeIdOfPlacement` の逆写像で、置いた部材へ辿れる。

**一括再生産では検証を通さない。**保存した設計は保存の時点で検証を通っており、そこから起こした部材の列は同じ形を再現する。**同じ形に対して同じ判定を2度行わない。**
