1. ドッキングポートによる機体の結合（§3）
2. 月の地形と着陸（§4）
3. 月面基地（§5）
4. 資源採掘・生産・輸送（§6）

### 他の巻との関係

計画は2巻構成である。

| 巻 | ファイル | 扱うもの |
|---|---|---|
| 第1巻 | `第七版_1_基盤.md` | 機体の実体、断面と背骨による形状、形状から導く質量特性と接触形状、物理、推進系 |
| 第2巻 | `第七版_2_設計・建造・資源.md` | 設計エディタ、生産、配管、多段、基地モジュール、資源進行 |

この文書が扱う5つの機能は、**その両方に依存する**。

- ドッキングと着陸は、機体の実体・質量特性・接触形状・推進系（第1巻）の上に載る。

## 2. 対象外

以下はこの文書でも扱わない。

- **月以外の天体の地形**。地形の仕組みそのものは天体を問わない形で書くが、実際に高度場を持たせるのは月のみとする。火星・小惑星への着陸は、地形データを追加すれば同じ機構で動く。
- **自動化された輸送キュー**。資源の輸送は常にプレイヤーが機体を飛ばして行う。発注すると物資が届く仕組みは持たない。
- **人員個体の追跡**。人員は役割ごとの人数と、その集団としての健康状態で扱う。一人ひとりに名前と経歴を持たせない。
- **技術ツリー**。研究点も前提技術の木も持たない。できることが広がるのは、資源と設備の連鎖によってのみである。
- **基地内部の間取り**。区画は機体の搭載要素として配置するものであり、部屋の配置図を編集する画面は持たない。

## 3. ドッキングポートによる機体の結合

### 3-1. 実現する内容

ドッキングポートを持つ機体同士が接近し、双方のポートの位置・向き・相対速度・相対角速度がすべて捕獲条件を満たしたとき、機体が結合する。結合後は、ポート軸まわりの相対回転（位相角）を任意に変えられ、推進剤とガスを移送でき、電力は結合体全体で1つの収支として計算される。

この機構により、以下が可能になる。

- 軌道上にあらかじめ投入しておいたブースターと合流し、結合してその推進剤で基地へ帰投する。
- 艦艇同士を結合し、推進剤と電力を融通する。
- 軌道基地に艦艇を接舷して格納する。
- 月面基地の区画同士を結合して拡張する（§5）。
- 人員を乗せた区画ごと結合し、基地の居住容積を増やす（§7）。

### 3-2. ドッキングポート部品

```ts
export interface DockingPortPart extends Part {
  readonly type: 'docking_port';
  readonly portClass: 'small' | 'medium' | 'large'; // 同一クラス同士のみ結合できる
  readonly androgynous: boolean;                    // false の場合 probe と drogue の対でのみ結合
  readonly role: 'probe' | 'drogue' | 'both';
  readonly localPos: Vec3;       // 船体ローカル座標のポート面中心
  readonly localAxis: Vec3;      // ポート面の外向き法線
  readonly localRollRef: Vec3;   // 位相角0を定義する基準方向（localAxis に直交）
  readonly transferRate: number; // 推進剤移送速度 [kg/s]
  readonly powerBridge: boolean; // 電力を橋渡しするか
  readonly crewPassable: boolean; // 人員が通れるか
}
```

ドッキングポートは背骨のノードに装着する。装着できるのは、そのノードの空いている接続口である。ポートの軸はその接続口の方向と一致する。

`crewPassable` は人員の移動可否を決める。これを持たないポートで結ばれた機体の間では、推進剤と電力は流れるが人員は移らない。船外活動による移動は扱わないため、人員の移動経路は `crewPassable` なジョイントの連鎖に限られる。

### 3-3. 捕獲条件

2つのポート A・B が以下をすべて満たすとき、捕獲が成立する。値は `const.ts` に置く。

| 条件 | 内容 |
|---|---|
| 適合 | `portClass` が一致し、`androgynous` 同士、または `probe` と `drogue` の対である |
| 軸方向距離 | ポート面中心間の距離が捕獲距離以内 |
| 横方向ずれ | A の軸に投影したときの横方向オフセットが許容半径以内 |
| 軸の対向 | A の軸と B の軸のなす角が180度から許容角度以内 |
| 接近速度 | 最小値以上・最大値以下。速すぎればラッチが損傷し、遅すぎれば噛まない |
| 横方向相対速度 | 許容値以下 |
| 相対角速度 | 許容値以下 |

捕獲が成立すると、ポート面同士を厳密に一致させる位置と姿勢へ両機を補正する。補正は運動量と角運動量を保存する形で行い、余剰は減衰として捨てる。これはラッチの衝撃吸収に相当する。

条件を満たさずに接触した場合は、通常の剛体接触として処理する。跳ね返り、および相対速度に応じた損傷が生じる。

### 3-4. 結合体

結合した複数の `Vessel` は、1つの剛体として積分する。

```ts
export interface DockingCluster {
  readonly id: string;
  readonly members: readonly Vessel[];
  readonly root: Vessel;                    // 積分の主体。KinematicState と Attitude を持つ
  readonly joints: readonly DockingJoint[];
}
export interface DockingJoint {
  readonly portA: { vesselId: string; partId: string };
  readonly portB: { vesselId: string; partId: string };
  phaseAngle: number;   // ポート軸まわりの相対ロール [rad]
}
```

- 積分は `root` の状態に対してのみ行う。他の構成機体の位置と姿勢はジョイントの連鎖から毎フレーム導出する。
- クラスタの質量・重心・慣性テンソルは、全構成機体のものを平行軸定理で合成する。推進剤が減れば変わるため、質量が一定量変化したときに再計算する。
- クラスタの主機・RCS・フライホイールは全構成機体のものの合計として扱う。主機の推力軸がクラスタ重心を外れる場合、そのぶんのトルクが実際に発生する。
- 同一クラスタの構成機体同士は接触判定を行わない。

### 3-5. 位相角の調整

ジョイントの `phaseAngle` を連続的に変えられる。ポート軸まわりに片側を回すことに相当し、機体全体の姿勢を変えずに構成機体の相対的な向きだけを変える。

- 回転速度に上限があり、電力を消費する。
- 回転させると結合体の慣性テンソルが変わるため、角運動量保存により全体の角速度が変化する。この効果はフライホイールと同じ内部トルクの一種として正しく計算する。
- 用途は、ソーラーパネルを太陽に向ける、ラジエータを日陰に入れる、武装の射界を確保する、着陸脚の向きを揃える、重力区画の回転面を確保する、である。

### 3-6. 移送と電力統合

**推進剤とガスの移送** — 結ばれた機体の間で移送できる。

- 移送できるのは、送り側と受け側のタンクが同じ推進剤種別に適合している場合のみ。極低温と常温貯蔵性の推進剤は互いに移送できない。
- 移送速度は両ポートの `transferRate` の小さいほうで律速する。
- 移送中は電力を消費する。
- 移送に伴って両機の質量と重心が変わるため、質量特性を更新する。クラスタ全体の重心は移動しないが、慣性テンソルは変わる。

**電力統合** — `powerBridge` を持つジョイントで結ばれた範囲は、1つの電力系として計算する。発電量は全構成機体のソーラーパネルの合計であり、各パネルの向きと日照は個別に評価したうえで合計する。蓄電容量はバッテリーの合計、消費は全構成機体の合計とする。不足が生じた場合は、優先度の低い消費から順に停止する。停止の順序は、生産設備 → 位相角の回転 → 重力区画の回転 → 生命維持装置とする。生命維持装置を最後に置くのは、これが止まると人員が死ぬためである。

**人員の移動** — `crewPassable` なジョイントで結ばれた範囲の中では、人員を任意に移せる。移動は即座に完了するものとし、通路の長さや移動時間は扱わない。

### 3-7. 分離

結合の解除は、ジョイントを取り除いてクラスタを分割することである。分割後は、分かれた側それぞれが独立した運動状態を持ち、運動量と角運動量が保存されるように速度と角速度を分配する。解除時に小さな分離速度を与える。

分離する時点で、各側に乗っている人員はそのまま各側に留まる。生命維持装置を持たない側に人員が残る分離は、警告を出したうえで実行を許す。

### 3-8. ドッキング支援の表示

ドッキングポートを目標に選ぶと、以下を表示する。

- 目標ポートの位置と軸を示すマーカー、および自機ポートとの相対位置。
- 横方向のずれと軸の対向角を示す十字型のインジケータ。
- 相対距離、接近速度、横方向相対速度、相対角速度と、それぞれの許容範囲。
- 捕獲条件を条件ごとに満たしているかどうかの一覧。

## 4. 月の地形と着陸

### 4-1. 地形

月の表面は、球面上の高度場として表す。

```
src/physics/terrain/height-field.ts   (純関数)
    heightAt(bodyId, latRad, lonRad) -> number   // 基準球半径からの高度 [m]
    normalAt(bodyId, latRad, lonRad) -> Vec3     // 地形法線（天体固定座標）
    surfacePointAt(bodyId, latRad, lonRad) -> Vec3
```

- 全球は粗い解像度の高度場で表し、機体の周囲のみ細かい格子を生成する。細部は決定的な擬似乱数（`physics/random.ts` の `mulberry32`）で生成し、同じ座標では常に同じ地形になるようにする。
- 座標は天体固定座標（月とともに自転する座標系）で扱う。慣性座標との変換は `Ephemeris` の自転位相を用いる。
- 南極域は永久影クレーターを含むよう地形を構成する。日照の判定は太陽方向に加えて地形の地平線を考慮し、クレーター底部が常に日陰になるようにする。
- 粗い全球データと局所生成の境界で高度が不連続にならないよう、局所生成は全球データを基準面として、その上に細部を加算する形とする。

### 4-2. 地表との接触

高度が一定値を下回った機体に対して、以下を行う。

- 天体固定座標での緯度経度を求め、その点の地形高度と機体各部の高度を比較する。
- 固定脚の接地点それぞれを接触点として扱う。接触点が地形面より下に入った場合、法線方向の反力と接線方向の摩擦を与える。
- 固定脚を持たない部位が地形に接触した場合は損傷を与える。

球面としての天体表面到達判定は、地形を持たない天体に対してのみ適用する。地形を持つ天体では高度場との接触判定に置き換える。

### 4-3. 着陸

接地の瞬間に以下をすべて満たす場合、着陸が成立する。値は `const.ts` に置く。

| 条件 | 内容 |
|---|---|
| 垂直速度 | 接地面法線方向の速度が許容値以下 |
| 水平速度 | 接地面接線方向の速度が許容値以下 |
| 傾斜 | 機体の脚面法線と地形法線のなす角が許容値以下 |
| 角速度 | 許容値以下 |
| 接地脚数 | 固定脚のうち規定数以上が同時に接地 |

いずれかを外れた場合、超過量に応じて固定脚および接触部位に損傷を与える。大きく外れた場合は機体を破壊する。

乗っている人員は、接地の衝撃が許容値を超えた場合に負傷する。負傷した人員は役割を果たせなくなり、医師による回復を要する（§7-4）。

着陸が成立した機体は着陸状態を持ち、天体固定座標に静止する。静止中は軌道積分を行わず、天体の自転に従って位置と速度を導出する。これにより、静止した機体を数値積分し続けることによる誤差の蓄積（沈み込みまたは浮上）を避ける。

離陸は、主機の推力が機体重量（その天体の表面重力加速度と機体質量の積）を上回った時点で着陸状態を解除し、通常の積分に戻すことで行う。着陸状態への遷移と解除が短時間に繰り返されないよう、遷移条件に履歴を持たせる。

### 4-4. 固定脚

```ts
export interface LandingGearPart extends Part {
  readonly type: 'landing_gear';
  readonly localPos: Vec3;        // 接地点の船体ローカル座標
  readonly strokeLength: number;  // 緩衝行程 [m]
  readonly maxImpactSpeed: number; // 損傷なく吸収できる接地速度 [m/s]
  readonly deployable: boolean;   // 収納できるか
}
```

固定脚は背骨のノードに装着する。3本以上を装着した機体のみ着陸できる。

## 5. 月面基地

月面基地は、固定脚を持ちエンジンを持たない `Vessel` である。艦艇や軌道基地と同じ実体であり、クラスを分けない。

- 着陸状態で天体固定座標に静止し、生産設備と基地モジュールを積む。
- 基地モジュールは、重力区画居住施設・農場・生命維持装置・水タンク・ドック・コンテナ接合部・コンテナである。月面基地はこれらを月面で運用する。
- 生産設備は電力を消費し、入力資源を出力資源へ一定の速度で変換する。稼働率はエッセンシャルワーカーの人数に依存する（§7-2）。
- 電力はソーラーパネルとバッテリーから得る。月の自転周期に伴って日照が変動するため、蓄電容量の設計が運用に影響する。南極の高地は日照率が高く、クレーター底部は常に日陰である。
- 月面基地は複数機を結合して拡張できる。結合はドッキングポート（§3）によって行い、電力は統合され、資源は移送でき、人員は往来できる。したがって基地の拡張と、軌道上での機体の結合は同一の機構である。

### 5-1. 月面における基地モジュールの扱い

月面に静止した機体では、いくつかのモジュールの働きが軌道上と異なる。

| モジュール | 月面での扱い |
|---|---|
| 重力区画居住施設 | 回転させなくても月面重力（地球の約6分の1）が常時かかる。回転区画を併設すればさらに大きい実効重力を得られるが、月面では回転面を水平に保つ必要があり、設置に地形の平坦さを要求する |
| 農場 | 日照が自転周期に従って変動するため、人工照明の電力が夜間分だけ余計に要る。南極の高日照率の地点はこの負担が小さい |
| 生命維持装置 | 働きは軌道上と同じ。処理能力が人口の上限を決める |
| 水タンク | 遮蔽として働く。月面では月体そのものが下半球を遮るため、同じ水量でも軌道上より被曝が小さい |
| ドック | 着陸してきた機体を受け入れる。着陸接続が成立している機体との間で資源と人員をやり取りできる |
| コンテナ接合部・コンテナ | 採掘した資源と生産した物資の貯蔵に用いる。輸送機への積み込みはここから行う |

### 5-2. 設計と設置

月面基地は設計エディタで設計する。エンジンを積まず固定脚を積んだ設計であり、他の機体と同じ手順で生産する。生産した月面基地は、輸送機で月面まで運ぶか、月面で直接生産する。

設置地点の選択は運用に効く。日照率、地形の平坦さ、永久影クレーターへの近さの3つが相反するためである。氷を採るには永久影に近いほうがよく、電力を得るには日照率の高い高地がよく、大型基地を置くには平坦な地形が要る。

## 6. 資源採掘・生産・輸送

### 6-1. 資源

| 資源 | 産地 | 用途 |
|---|---|---|
| 水 | 月の南極の永久影クレーターの採掘 | 電解して液体水素と液体酸素にする。飲用。遮蔽 |
| 酸素 | 水の電解、レゴリスの還元 | 酸化剤。呼吸 |
| ケイ素 | レゴリスの精錬 | シラン、構造材 |
| アルミ | レゴリスの精錬 | 固体推進剤の燃料成分、構造材 |
| 炭素 | 低軌道に出現する敵の撃破によるドロップ | メタン、末端水酸基ポリブタジエン、ABS樹脂、ケロシン。食料生産 |
| 窒素 | 低軌道に出現する敵の撃破によるドロップ | ヒドラジン、四酸化二窒素、冷ガス。農場の大気と肥料 |
| 希少金属 | 敵のドロップ | 高性能なエンジン、フライホイール、電子機器、医療設備 |
| 食料 | 農場での生産 | 人員の維持 |

炭素と窒素は月では得られない。したがって、メタン系・ヒドラジン系の推進剤を使い続けるには低軌道での戦闘を継続する必要がある。一方、水とケイ素だけで閉じる経路（液体酸素／液体水素、液体酸素／シラン）が存在するため、戦闘を行わなくても機体の運用は継続できる。

ただし**人員の維持は炭素と窒素に依存する**。農場は炭素と窒素を消費して食料を生産する。閉じた再生系に近づけるほど必要量は減るが、事故と漏出による損失はゼロにならない。人口を増やすには戦闘による炭素と窒素の獲得が要る。

### 6-2. 生産設備

```ts
export interface ProductionPart extends Part {
  readonly type: 'production';
  readonly recipe: ProductionRecipe;
  readonly crewRequired: number;  // 定格で回すのに要るエッセンシャルワーカーの人数
}
export interface ProductionRecipe {
  readonly id: string;
  readonly inputs: readonly { resourceId: string; rate: number }[];   // kg/s
  readonly outputs: readonly { resourceId: string; rate: number }[];  // kg/s
  readonly powerDraw: number;  // W
}
```

設備は、採掘機（レゴリスまたは氷を掘り出す）、電解装置（水を水素と酸素に分ける）、レゴリス精錬炉（ケイ素とアルミと酸素を取り出す）、シラン合成炉、固体グレイン成形機、極低温液化装置である。

`crewRequired` の合計に対してエッセンシャルワーカーが不足している場合、その基地の全設備の稼働率が一律に下がる（§7-2）。

### 6-3. 輸送

月面基地で生産した物資を軌道基地へ運ぶ操作は、プレイヤーが行う。自動化された輸送キューは持たない。

1. 月面基地に着陸した機体のコンテナまたはペイロード区画に、月面基地の倉庫から資源を積み込む。積み込みは、両者がドッキングポートで結ばれているとき、または着陸接続が成立しているときに行える。
2. 離陸し、月面から目的の軌道への遷移を行う。
3. 軌道基地とドッキングする。
4. 貨物と推進剤を移送する。

貨物の質量は機体の総質量に加算されるため、輸送量を増やすほど必要な Δv に対する推進剤が増える。この関係により、1回の輸送量には設計上の最適点が生じる。輸送そのものが遊びの対象になる。

人員の輸送も同じ手順で行うが、運べる人数はコックピットの搭乗人数によって上限が決まる（§7-6）。

### 6-4. 軌道基地の軌道

軌道基地は近直線ハロー軌道に置く。

- 初期状態は既存のハロー軌道の生成関数（地球-月 L2 の南方ハロー、大きな面外振幅）から得る。
- この初期状態は線形近似であり、多体重力を含む数値積分に投入すると発散する。したがって軌道基地は維持バーンを行う。近月点通過ごとに数 m/s の維持バーンを軌道計画の自動実行によって行う。
- 維持バーンは推進剤を消費する。軌道基地の維持そのものが資源の消費先になる。

## 7. 人員

### 7-1. 総人口

ゲームは**総人口1000人**から始まる。この1000人は月面基地と軌道基地に分布して所属する。人員は資源と同じく輸送の対象であり、機体で運ぶ。

人員は個体としては追跡しない。基地ごとに、役割ごとの人数と、その集団としての健康状態を持つ。

```ts
export type CrewRole = 'engineer' | 'pilot' | 'medic' | 'essential';

export interface CrewPopulation {
  readonly counts: Readonly<Record<CrewRole, number>>;  // 役割ごとの人数
  readonly health: CrewHealth;
  readonly training: readonly TrainingBatch[];          // 訓練中の人員
}

export interface CrewHealth {
  readonly boneDensity: number;   // 0..1、1が健常
  readonly muscleMass: number;    // 0..1
  readonly radiationDose: number; // 累積被曝線量 [Sv]
  readonly incapacitated: Readonly<Record<CrewRole, number>>; // 役割を果たせない人数
}

export interface TrainingBatch {
  readonly from: CrewRole;
  readonly to: CrewRole;
  readonly count: number;
  readonly completesAt: number;  // 絶対 simTime
}
```

`incapacitated` は `counts` の内数である。ある役割で実際に働けるのは `counts[role] - incapacitated[role]` 人である。

### 7-2. 役割

人員は次の4つの役割を持ち、役割ごとに数える。

| 役割 | 担うもの |
|---|---|
| 整備士 | 機体と設備の修理・整備。部品の摩耗の回復、触媒床の交換 |
| 飛行士 | 機体の操縦。同時に飛ばせる機体の数と、無人機の管制の上限を決める |
| 医師 | 健康の維持と回復。被曝と低重力の影響の緩和 |
| その他のエッセンシャルワーカー | 農場・生産設備・生命維持装置の運用。人数に比例して設備の稼働率が決まる |

**整備士が不足すると修理速度が落ちる。**部品の摩耗の回復速度と触媒床の交換速度は、整備士の人数に比例する。必要人数に対する充足率が1を下回ると、その比率がそのまま修理速度の倍率になる。整備士が0人の基地では、修理も整備も一切進まない。摩耗した部品はそのまま性能を落とし続け、劣化した触媒床は交換されないまま推力を失う。

**飛行士が不足すると同時に操作できる機体が限られる。**飛行士1人につき有人機1機を操縦でき、それとは別に無人機を規定数まで管制できる。飛行士の人数を超える機体を同時に飛ばそうとした場合、超過分は操作対象として選べない。軌道上に置いたまま放置することはできるが、姿勢制御も推進も行われず、軌道は自然に変化する。

**医師が不足すると健康が落ちる。**医師1人が受け持てる人員数に上限があり、これを超える人口を抱えた基地では、健康の回復が受け持ち率に比例して遅くなる。医師が0人の基地では、負傷者も被曝者も回復せず、低重力による劣化も緩和されない。

**エッセンシャルワーカーが不足すると設備が定格で回らない。**基地に積んだ全設備の `crewRequired` の合計に対する充足率が、その基地の全設備の稼働率の倍率になる。充足率0.5であれば、農場も生産設備も生命維持装置も一律に半分の速度でしか動かない。生命維持装置が定格を割ると、そのぶん人口上限が下がる（§7-3）。

充足率は純関数として求める。

```ts
export function roleSufficiency(
  pop: CrewPopulation,
  demand: CrewDemand,       // 基地の設備・機体から導いた必要人数
): Readonly<Record<CrewRole, number>>;  // 0..1 にクランプした充足率
```

### 7-3. 人口を制約するもの

人口の上限は、次の4つのうち**最も厳しいもの**で決まる。

| 制約 | 由来 |
|---|---|
| 生命維持装置の処理能力 | 酸素の供給量、二酸化炭素の除去量、水の再生量。それぞれ1人あたりの必要量で割り、最も小さい値を採る |
| 農場の食料生産 | 食料の生産速度を1人あたりの必要量で割る。備蓄がある間はそれも算入する |
| 居住区画の容積 | 重力区画居住施設の内容積を1人あたりの必要容積で割る |
| 医療の能力 | 医師の人数と医療設備の規模から求める受け持ち可能な人数 |

```ts
export function populationCapacity(
  base: BaseState,
  crew: CrewPopulation,
): { readonly capacity: number; readonly limitedBy: PopulationLimit };
```

`limitedBy` を返すのは、どれが効いているかをプレイヤーに示すためである。上限が近いことだけを表示しても、何を増やせばよいかが分からない。

**いずれかが不足すると人口が減る。**現在の人口が上限を上回っている間、超過量に比例した速度で人口が減る。減り方は制約の種類によって異なる。

- 酸素と食料の不足は、速く減る。数日で結果が出る。
- 居住容積の不足は、遅く減る。健康の低下を経由して減る。
- 医療の不足は、直接には減らさない。負傷者と被曝者が回復しないことを通じて、間接的に減る。

減るときは全役割から比例して減らす。特定の役割だけが先に失われることはない。

### 7-4. 健康

健康は基地ごとの集団の状態として持ち、3つの軸で扱う。

**低重力による劣化** — 骨密度と筋力が落ちる。実効重力が小さいほど速く落ちる。重力区画居住施設に滞在する時間で緩和される。

- 月面重力（地球の約6分の1）相当でも、無重力よりは大きく改善する。無重力での劣化速度を1とすると、月面重力ではおよそ4分の1程度に落ちる。線形ではなく、わずかな重力が大きく効く。
- 回転する重力区画居住施設は、回転半径と角速度から実効重力を得る。滞在時間の割合で加重平均した実効重力が、その集団の劣化速度を決める。
- 劣化した骨密度と筋力は、実効重力の高い環境で時間をかければ回復する。医師がいれば回復が速い。

**放射線の被曝** — 累積する。累積線量は減らない。

- 水タンクによる遮蔽で被曝率が下がる。遮蔽の効きは水の厚さに対して指数的である。
- 地球磁場の内側（低軌道）にいる間は被曝率が大きく下がる。月周辺と惑星間ではこの保護がないため、遮蔽の有無が直に効く。
- 太陽フレアの発生時は被曝率が跳ね上がる。遮蔽の厚い区画に人員を退避させることで凌ぐ。
- 累積線量が閾値を超えた人員から順に、役割を果たせなくなる（`incapacitated` に入る）。

**健康が落ちた人員は役割を果たせなくなる。**骨密度・筋力が閾値を下回った人員、累積被曝が閾値を超えた人員、着陸の衝撃や事故で負傷した人員は `incapacitated` に数え、その役割の実働人数から外れる。医師がいれば回復し、実働に戻る。回復速度は医師の充足率に比例する。累積被曝だけは回復しないため、被曝で外れた人員は恒久的に実働から外れる。

```ts
export function stepCrewHealth(
  health: CrewHealth,
  env: CrewEnvironment,   // 実効重力、遮蔽厚、磁気圏の内外、フレアの有無
  medicSufficiency: number,
  dt: number,
): CrewHealth;
```

純関数とし、環境と医師の充足率と経過時間から新しい健康状態を返す。

### 7-5. 人口の増減

**出生** — 人口が上限に対して余裕を持ち、健康が良好で、居住区画の実効重力が一定値以上である基地でのみ起きる。低重力下での妊娠と出産の安全性が確保されないためである。出生した人員は成人するまで役割を持たない。成人までの期間は長く、人口を増やす主要な手段にはならない。

**死亡** — 寿命、事故、被曝、生命維持の破綻によって起きる。寿命による死亡は一定の速度で常に起きる。

**事故** — 機体の破壊、着陸の失敗、生命維持装置の停止、被弾によって、その場にいた人員が失われる。事故は該当する機体・区画に乗っていた人員に対してのみ起きる。

**訓練による役割の転換** — ある役割の人員を、別の役割へ転換できる。転換には時間がかかり、`TrainingBatch` として保持する。

- 訓練中の人員は、元の役割としても新しい役割としても働けない。したがって訓練は一時的な人手不足を招く。
- 転換に要する時間は役割の対によって異なる。医師への転換が最も長く、エッセンシャルワーカーへの転換が最も短い。
- 訓練は医師と整備士の指導を要するため、それらの充足率が低い基地では訓練速度が落ちる。

### 7-6. 輸送

人員は貨物と同じく機体で運ぶ。

**コックピットの搭乗人数が1回に運べる人数の上限である。**小型の艦艇のコックピットは1〜3人であり、これでは人員の移送はほとんど進まない。人員を多く運ぶには、居住区画を持つ大型の機体が要る。

- 搭乗人数を超える人員を乗せることはできない。
- 飛行中の機体に乗っている人員も、生命維持装置と食料を消費する。長期の航行では、乗員数に応じた消耗品の搭載が要る。
- 飛行中は重力が得られないため、低重力による劣化が進む。長期の輸送任務では、回転する重力区画を持つ機体でなければ乗員の健康が落ちる。
- 飛行中の被曝は、機体の遮蔽と現在位置の磁気圏内外によって決まる。月への往復は磁気圏の外を通るため、遮蔽の薄い機体では往復1回ごとに無視できない線量を受ける。

人員の積み下ろしは、ドッキングポートで結ばれているとき（`crewPassable` が必要）、または着陸接続が成立しているときに行える。

### 7-7. モジュール

```
src/physics/crew/population.ts    (純関数)
    populationCapacity(base, crew) -> { capacity, limitedBy }
    roleSufficiency(pop, demand) -> Record<CrewRole, number>
    stepPopulation(pop, capacity, dt) -> CrewPopulation
src/physics/crew/health.ts        (純関数)
    stepCrewHealth(health, env, medicSufficiency, dt) -> CrewHealth
    shieldingFactor(waterThicknessM) -> number
    gravityDegradationRate(effectiveG) -> number
src/game/crew/crew-system.ts      // 毎フレームの進行、事故の適用、訓練の完了
src/game/crew/crew-transfer.ts    // 積み下ろしと基地間の移動
src/game/hud/base-crew-tab.ts     // 基地ビューの人員タブ
```

`physics/crew/` は純関数のみとし、DOM にも THREE にも依存させない。人口上限の算出、健康の減衰と回復、役割の充足率はいずれも入力から出力が一意に決まる計算であり、テストで固定できる。

### 7-8. UI — 基地ビューの人員タブ

基地ビューに人員タブを加える。表示するのは以下である。

- **人口** — 総数、現在の上限、上限を決めている制約（`limitedBy`）。上限に対する余裕をメーターで示す。
- **役割ごとの内訳** — 4つの役割それぞれについて、総数・実働数・必要数・充足率。充足率が1を下回る役割は警告色で示す。
- **健康** — 骨密度、筋力、累積被曝線量。それぞれの現在値と、いまの環境での増減の向き。
- **不足の影響** — 充足率が1を下回っている役割について、それが何を引き起こしているかを文で示す（修理速度が何倍に落ちているか、何機まで同時に飛ばせるか、設備が何割で回っているか）。
- **訓練** — 進行中の訓練の一覧と、新しい訓練の開始。転換元・転換先・人数を指定する。
- **輸送** — 着陸接続またはドッキングが成立している機体との間で、人員を積み下ろす。機体の搭乗可能人数を上限として示す。

役割の充足率は毎フレーム変わりうるため、行の値は毎フレーム書き換える。行そのものの構成（役割は4つで固定）は変わらないため、要素を作り直さず値だけを書き換える。

## 8. 実装費用が大きい理由

各機能を当面の実装対象から外した理由を記す。実装に着手する際、以下がそのまま最初に解くべき課題になる。

### 8-1. ドッキング

- 結合体を1つの剛体として積分する仕組みは、既存の単体機体を前提とした積分・接触判定・予測軌道・マーカー表示のすべてに影響する。
- 構成機体それぞれの推進剤消費によって結合体の重心と慣性テンソルが連続的に変化するため、再計算の頻度と姿勢積分の安定性の両立が必要である。
- 捕獲の瞬間の位置と姿勢の補正は、運動量と角運動量を保存しつつ不連続に状態を書き換える処理であり、予測軌道の破棄と再生成を伴う。
- ドッキング支援の表示は、既存のどのマーカーとも異なる新しい種類の表示である。

### 8-2. 月の地形

- 月の全球を実寸で扱うため、全球の高度場を高解像度で保持することはできない。粗い全球データと機体周辺のみの局所生成の組み合わせが必須であり、境界での不連続を避ける補間が要る。
- 地形メッシュの生成と、カメラ距離に応じた解像度の切り替えが必要である。既存の天体は球のみを描画しており、この仕組みを持たない。
- 天体表面への到達判定を球から高度場へ切り替えるため、`physics/attractor.ts` の到達判定に分岐が入る。この関数は全エンティティの毎ステップの判定に使われる。

### 8-3. 着陸

- 静止した機体を数値積分し続けると、重力と反力の釣り合いの誤差が蓄積して沈み込みまたは浮上が生じる。静止状態を積分から外して天体固定座標に固定する扱いが必須である。
- 着陸状態への遷移と解除の条件を明確にしないと、遷移の前後で状態が振動する。
- 固定脚の接地点ごとの接触と、複数点接触時の姿勢の安定は、既存の球同士の剛体接触とは別の処理である。

### 8-4. 資源経済

- 資源・設備・レシピ・在庫・輸送という新しい系統が加わり、既存の購入の仕組みと併存させる設計判断が要る。
- 月面基地の運用画面、資源の在庫表示、積み込み操作という新しいUIが必要である。
- ドッキングと着陸の両方に依存するため、単独では実装できない。

### 8-5. 人員

- **人員は単独では成立しない。**所属する基地（月面基地）、運ぶ手段（ドッキングと着陸）、消費する食料と酸素（資源経済）、住む区画（基地モジュール）のすべてが揃って初めて動く。この文書の他の4機能すべてに依存する、最も後ろに位置する機能である。
- **時間経過のすべてに絡む。**健康の減衰、被曝の累積、訓練の進行、人口の増減はいずれも時間で進む量であり、時間加速の全段階で正しく振る舞う必要がある。加速倍率によって結果が変わってはならない一方で、毎フレーム全基地の全人員を計算するのは無駄である。どの量を毎フレーム進め、どの量を区間でまとめて解くかの切り分けが要る。
- **役割の充足率が既存の系統に横断的に効く。**整備士は部品の摩耗と触媒床に、飛行士は操作可能な機体の数に、エッセンシャルワーカーは生産設備と生命維持装置に効く。いずれも既存の計算に倍率を1つ掛ける形で入るが、その倍率の出所が人員という新しい系統になるため、依存の向きを整理しないと循環する（設備が回らないと食料が作れず、食料がないと人員が減り、人員が減ると設備が回らない）。この循環そのものは遊びとして意図したものであるが、計算の順序としては1フレーム内で解決する必要がある。
- **不足の影響をプレイヤーに伝えるのが難しい。**人口の上限が4つの制約の最小値で決まり、4つの役割それぞれに別の不足の影響があり、健康が3つの軸を持つ。どれが効いているかを示さないまま数値だけを並べても、何を増やせばよいかが分からない。`limitedBy` を返す設計と、不足の影響を文で示す表示は、そのための最低限である。
- **輸送の上限がコックピットの搭乗人数で決まることが、機体設計に新しい制約を持ち込む。**1000人を動かすには、既存の艦艇の何倍もの規模の輸送機が要る。その規模の機体が設計エディタで組め、生産でき、月面に着陸できることが前提になる。

## 9. 依存の順序

```
ドッキング ──┬──────────────────► 資源採掘・生産・輸送 ──► 人員
             │                          ▲                    ▲
月の地形 ──► 着陸 ──► 月面基地 ─────────┴────────────────────┘
```

- **ドッキングは単独で着手できる**。軌道上での機体の結合、推進剤の移送、艦艇の接舷はこれだけで成立する。
- **月の地形は単独で着手できる**。地形の生成と描画は、着陸を実装しなくても見て確かめられる。
- **着陸は月の地形に依存する**。地表との接触判定が地形の上に立つ。
- **月面基地は着陸に依存する**。月面に静止する機体という扱いが要る。
- **資源経済は月面基地とドッキングの両方に依存する**。産地が月面にあり、輸送に結合が要る。
- **人員は月面基地・資源経済・ドッキングのすべてに依存する**。所属する基地、輸送する手段、消費する食料と酸素のすべてが揃って初めて成立する。
