# 基地本体カスタム形状作業台実装計画

作成日: 2026-08-19  
対象: 第10版 第3巻「推進・建造・運用」未実装追加項目  
状態: 実装前の計画（完全3D造船の実現性レビュー反映済み）

レビュー結論: 変更前の計画だけでは、ノード・エッジ・外皮を自由に編集する完全な3D造船は実現しない。編集コマンド、断面・外皮編集、3Dギズモ、新規船下書き、建造確定、旧直接新造経路の削除を本計画へ追加した。

## 1. 目的

基地本体を、固定された一枚のモデルではなく、3Dモデルを持つ部品の集合として作業台で直接編集できるようにする。

基地のドック作業台では、ドック中の船と同じ操作体系で基地本体の部品を選択・移動・取り外し・取り付けできるようにする。ただし、基地は単なる船体ではなく、ドック、在庫、製造設備、燃料、ドッキング中の船を所有する運用主体でもある。そのため、見た目の編集だけでなく、基地機能・ドック占有状態・衝突形状・保存データを一つのトランザクションとして扱う。

## 2. 現在のコードベース

調査時点では、次の状態である。

- `src/game/vessel/vessel-assemblies.ts` の `orbitalBaseAssembly()` が基地のトポロジーと部品配置を固定生成している。中心ノード、船体エッジ、トラスエッジ、外部・内部部品をここで決めている。
- `src/game/vessel/vessel-designs.ts` の `orbitalBaseDesign()` が上記アセンブリを使って基地設計を生成する。基地の描画は `AssemblyRenderObject` に接続済みだが、旧来の固定モデル生成経路との視覚差分は残っている。
- `src/game/vessel/vessel.ts` は `assembly` を持ち、基地の `BaseState`（在庫、ドック中の船、資源台帳）は別に保持している。`baseModule`、`dockCapacity`、`getSlotWorldPos()`、`getSlotWorldNormal()` は、現在は部品上の固定ハッチと `dockSlots` を参照する。
- `src/game/save-data.ts` の `PlayerSaveData` には `assembly` があるが、`BaseSaveData` には基地本体の `assembly` がまだない。`restoreBase()` と `resolveDesign(savedBase)` は、カスタム基地形状を復元せず既定基地へフォールバックする。
- `src/game/docking.ts` と `src/game/hud/base-view.ts` の作業台は、現在はドック中の船を選んで編集するUIである。基地本体を編集対象として選択する入口、基地アセンブリへの適用、基地用の取り外し制約はない。
- `DockWorkbenchSession` は複数の編集対象と在庫、スナップショット、Undo/Redoを扱える純粋な基盤を持つが、ランタイムのドッキング作業台は独自のチェックポイント処理を使っている。基地本体を含める際に、対象識別子・検証・確定/取消の境界を統一する必要がある。
- `AssemblyRenderObject`、`hull-mesh.ts`、`vessel-wireframe.ts` により、外部部品、内部部品マーカー、ノード、エッジを作業台で可視化・選択する土台はある。`dock` の内部マーカーはオレンジで表示される。
- 基地の物理衝突は `BaseCollisionGeometry`、ドックのワールド位置・法線は `Vessel` の固定的な基地モジュール情報に依存している。形状変更後にこれらを再生成・再同期しないと、描画形状と実際のドック位置・衝突判定がずれる。

したがって、今回の中心課題は「基地を編集可能な対象として作業台へ追加すること」と「編集結果を基地の実体・機能・保存へ原子的に反映すること」である。

## 3. スコープ

### 実装するもの

1. 基地本体のカスタムアセンブリを設計データとして保持する。
2. 基地ドックの3D作業台で、基地本体を編集対象として選択できるようにする。
3. ノード、エッジ、外皮、部品を既存のスナップ・選択・プロパティー表示の仕組みで操作できるようにする。
4. 基地固有の構造・ドック・機能制約を編集中と確定時に検証する。
5. 確定時に基地の描画、衝突形状、ドック位置、ドック中の船の取り付け位置を原子的に更新する。
6. 取消、エラー時ロールバック、作業台退出時の未確定変更破棄を実装する。
7. 基地本体のカスタムアセンブリを保存・復元し、旧セーブを既定基地として読み込めるようにする。
8. 基地本体編集に関するユニットテスト、保存互換テスト、作業台の統合テストを追加する。
9. 現行の「設計から船を新造する」導線を削除し、部品・構造を3D作業台で組み立てて建造を確定する導線へ置き換える。
10. 船についても、ノード・エッジ・外皮・部品を編集コマンドで直接変更できる完全な3D造船機能を実装する。

### 今回は実装しないもの

- 基地の新しい部品カテゴリや3Dアセットの大量追加。
- 基地の機能そのもの（製造、電力、放熱、生活支援など）の新規設計。
- 基地を宇宙空間で自由に操作・移動する機能。
- 複数基地を同時に同じ作業台で編集する機能。
- 作業台外からの直接ファイル編集や、任意のJSONを無検証で読み込む機能。

### 3.1 「設計から船を新造する」機能の削除計画

ここで削除するのは、Operationsの「生産」タブで `VesselBlueprint` を選び、資源を消費して完成済みの船を直接ドックへ生成する経路である。部品を作って倉庫へ入れる機能、設計データを編集・保存する機能、既存船の保存・復元は削除対象にしない。

#### 削除対象

- `BaseView` の設計一覧・「生産」ボタン・設計ごとの不足資源表示。
- `BaseView.onProduceVessel` と、設計を引数に取る直接生成コールバック。
- `Docking.produceVessel()`、設計から `new Vessel({ blueprintShip: ... })` を作る基地生産経路。
- 上記経路だけのために残る `productionBlueprintOf()` の利用、設計一覧の表示用処理、不要な `BlueprintLibrary` の依存。削除前に他の設計編集・保存・インポート経路がないかを調査し、共有利用されている型や保存データは削除しない。

#### 残すもの

- 「部品の生産」を使って部品を基地倉庫へ作る機能。完全3D作業台から部品を取り付けるために必要である。
- `VesselBlueprint` / `VesselAssembly` の設計表現、既存セーブの読み込み、設計の保存・インポート。これらは3D作業台の下書き・共有形式として再利用する。
- 既存の完成済み船、旧セーブ、ドック中の船。削除は既存資産を消去せず、今後の直接生産だけを停止する。

#### 置き換え後の新造フロー

設計から完成船を即時生成する代わりに、3D作業台へ `new-vessel-draft` 対象を追加する。

1. 作業台で「新規船」を選び、空の設計、または既存設計を編集用下書きとして読み込む。
2. ノード、エッジ、外皮、部品を編集する。
3. 構造・機能・資源・ドック容量を検証する。
4. 「建造を確定」を押した時だけ、必要資源を消費して船を生成し、空きドックへ格納する。

この「建造を確定」は、既存の設計行から船を直接生成する機能とは別の、編集済みアセンブリを検証して実体化するトランザクションとする。建造失敗時は資源、在庫、下書き、ドックを変更しない。新規船の建造をまだ実装しない段階では、設計を保存できても「生産」タブから完成船が生成されないことを明示する。

#### 削除の手順

1. 参照検索で、`onProduceVessel`、`produceVessel`、設計一覧、生産資源計算の利用箇所を分類する。
2. 新規船下書きの作成・検証・建造確定のAPIを先に用意する。
3. UIから設計生産行と直接生成コールバックを削除し、残った画面を「部品生産」として再構成する。
4. `Docking` の直接生成処理と不要な依存を削除する。
5. 既存セーブの完成船、保存済み設計、倉庫部品を保持したまま起動できることを確認する。
6. 「設計を選ぶだけで船が増える」経路がなく、建造確定は3D作業台の検証を通ることをテストする。

## 4. 設計方針

### 4.1 基地の「形状」と「運用状態」を分離する

基地のアセンブリは形状・トポロジー・部品配置を表す設計データとし、次の運用状態とは分離する。

- 在庫と資源台帳
- 製造キュー、燃料、ダメージ、温度などのランタイム状態
- ドック中の船の実体と各スロットの占有状態
- 現在の基地の軌道状態、姿勢、選択状態

形状変更で `Vessel` を再構築する場合も、運用状態は検証済みの新形状へ引き継ぐ。部品のHPや機能が形状依存の場合は、引き継ぎ可能な値と再計算する値を明示的に分ける。

### 4.2 編集対象を共通化する

作業台の対象を「ドック中の船」だけに固定せず、次の共通型へ拡張する。

```ts
type WorkbenchTarget =
  | { kind: 'base'; id: string; assembly: VesselAssembly }
  | { kind: 'docked-vessel'; id: string; assembly: VesselAssembly };
```

実装上は既存の `DockWorkbenchSession` の `WorkbenchTarget` を拡張し、UIの選択対象、スナップショット、変更履歴、検証結果が対象の種類を失わないようにする。部品の所有者を `targetId` として保持し、基地在庫から基地へ戻す操作と、船から基地在庫へ戻す操作を混同しないようにする。

### 4.3 基地の不変条件を設計段階から定義する

基地は一般船と同じ `validateBlueprint()` を通すだけでは不十分である。少なくとも次を基地固有の検証として定義する。

- 必須の `base_module` がちょうど1つ存在する。
- `base_module` が他の必須構造へ接続され、孤立していない。
- 基地本体を構成するコアと船体・トラスの連結性が保たれている。
- 必要数の `dock` 接続点／ハッチが存在する。
- 編集後のドック容量が、現在ドック中の船の数以上である。
- 現在船が占有しているドック接続点を削除・移動していない。
- 基地機能に必要な部品（例: 製造設備、電力、放熱、通信）がある場合、その依存関係を満たす。
- 最大寸法、部品数、質量、接続可能距離、重複・干渉の制約を満たす。
- 衝突形状を生成でき、全ての必須ドック位置に有効なワールド座標と法線を求められる。

`base_module` の削除を常に禁止するか、別の基地コアへ交換可能にするかは実装時に固定する。本計画では安全側として、初期版では削除・複数化・占有スロットの移設を禁止し、別部品への交換は別機能として扱う。

### 4.4 完全な3D造船機能の実現性レビュー

現行計画をそのまま実装しても、ノードや外皮を自由に編集する完全な3D造船機能は実現しない。理由は、現在の計画が「ノード・エッジ・外皮を操作する」という受け入れ側の記述に留まり、編集操作がアセンブリデータへ変換される純粋な編集モデル、3Dギズモ、作成・削除操作、外皮断面の編集、船の新規下書きから建造までを定義していないためである。

コードベース上も、次の制約がある。

- `VesselTree` はノード、エッジ、断面を表現できるが、ノード移動、ノード追加・削除、エッジ接続・切断、断面変更を行う編集コマンドはない。
- `assembly-mode.ts` の `treeFromDraft()` と `mateVerdict()` は下書き生成と接続判定の補助であり、3D操作から不変な新ツリーを作る編集エンジンではない。
- `DockWorkbenchSession` と `DockWorkbenchController` は主に既存 `PartPlacement` の追加・削除・移動を扱う。ツリーそのものを変更する履歴・Undo/Redoはない。
- `vessel-wireframe.ts` はノード・エッジを描画し、選択用IDを付けるが、クリックした要素をギズモで動かす処理はない。
- `AssemblyRenderObject` は既存アセンブリを描画・選択するもので、外皮を構成する `CrossSection` や外皮エッジを編集するUIではない。
- 現行の倉庫部品取り付けは最初の船体エッジ等へ既定配置するだけで、ドロップ位置から任意のノード・ポート・外表面を決定しない。

したがって、以下の編集エンジンと操作仕様を本計画へ追加し、単なる表示・部品換装と完全3D造船を明確に分ける。

#### 編集対象の拡張

作業台の対象を基地・既存船だけでなく、新規建造下書きまで含める。

```ts
type WorkbenchTarget =
  | { kind: 'base'; id: string; assembly: VesselAssembly }
  | { kind: 'docked-vessel'; id: string; assembly: VesselAssembly }
  | { kind: 'new-vessel-draft'; id: string; assembly: VesselAssembly; name: string };
```

新規下書きは、最小の空間だけを持つ初期状態、または既存設計を複製した状態から開始する。空のまま建造確定はできず、有人船なら有人コア、自動船なら自動操縦コアなど、船の操作要件を満たすまで確定できない。コアを持たない下書きは貨物として保存・ドッキングできるが、操作対象として発進させない既存ルールを維持する。

#### ツリー編集コマンド

DOMイベントやThree.jsオブジェクトを直接書き換えず、次の純粋なコマンドを `VesselAssembly` のコピーへ適用する。各コマンドは成功時に新しいアセンブリと影響範囲を返し、失敗時は元のアセンブリを変更しない。

- `addNode` / `moveNode` / `removeNode`
  - ノード位置、断面、軸、位相を編集する。
  - 位置は `DIMENSION_UNIT` にスナップし、軸・断面・位相は有限値と設計上の範囲を検証する。
  - ノード移動時は接続エッジの長さをノードのポート間距離から再計算する。`TreeEdge.length` だけを書き換えてノード位置と不一致にする操作は許可しない。
  - ノード削除時は接続エッジと、そのエッジを参照する外部部品・内部部品を列挙し、部品を在庫へ戻すか操作を拒否する。
- `addEdge` / `moveEdge` / `removeEdge`
  - 2ノードの未使用ポートを選び、`hull`、`truss`、`decoupler` の種類を指定して接続する。
  - 接続口の断面・幅・位相、最小長、量子化、既存ポート占有、作業範囲を検証する。
  - エッジ削除時は接続性、外皮の開口、部品配置、ドック占有を検証し、切断される構造を残さない。
- `editSection`
  - ノード断面の円、楕円、多角形、切欠き、複合断面のプリミティブを追加・削除・寸法変更・位相変更する。
  - `PrimitiveAttachment` の親子関係、面の存在、重複、面積、外皮の自己交差を検証する。
  - 断面変更により接続口が無効になった場合、接続先エッジや外皮部品を自動で壊さず、修正または明示削除を要求する。
- `movePlacement` / `removePlacement` / `installPlacement`
  - 外部部品をポート、外表面、トラス上の任意の `MountPoint` へスナップする。
  - `along`、`around`、接続口を3D候補から確定し、既定の最初の船体エッジへの暗黙配置を廃止する。

#### 外皮編集の意味

外皮は独立したポリゴンメッシュを手作業で直接変形するのではなく、`hull` エッジと両端ノードの `CrossSection` から決まるロフトとして編集する。これにより、描画、内容積、質量、熱・圧力、衝突形状を同じ設計データから再計算できる。

- `hull` エッジの追加・削除・接続変更で外皮の区画を増減する。
- ノード断面、軸、位相を変更して外皮の断面とねじれを変える。
- 外皮編集時はロフトの閉鎖、自己交差、断面の面積、内部部品の収容可能性を検証する。
- `truss` と `decoupler` は外皮を作らないことを表示上も明示し、外皮編集と構造材編集を混同させない。

この方式なら「自由に編集する」は、物理・接続・製造制約の範囲で任意の有効な形状を組み立てることを意味する。制約を無視した任意メッシュ編集を提供するものではない。

## 5. データモデルと保存

### 5.1 基地設計スナップショット

既定基地とカスタム基地を同じ `VesselAssembly` で扱い、基地固有のメタデータは別の型にする。

```ts
interface BaseAssemblyDesign {
  assembly: VesselAssembly;
  formatVersion: number;
  dockBindings: BaseDockBinding[];
}

interface BaseDockBinding {
  dockId: string;
  nodeId: string;
  portId: string;
  occupiedVesselId?: string;
}
```

`dockBindings` は部品配列のインデックスではなく、安定したノード・ポート・船IDで表す。アセンブリの配列順が変わっても、保存された船のドック位置を再解決できるようにする。

ただし、既存の `VesselAssembly` がポート情報を十分に持っていない場合は、まず `dock` 部品またはエッジに安定した `dockId` / `portId` を付与する。固定された `baseModule.hatch` の座標だけを継続利用する設計は、基地形状を編集可能にする目的と衝突するため避ける。

### 5.2 `BaseSaveData` の拡張

`src/game/save-data.ts` の `BaseSaveData` に、後方互換な任意フィールドとして基地アセンブリを追加する。

```ts
assembly?: {
  tree: VesselAssembly['tree'];
  placements: VesselAssembly['placements'];
  formatVersion: number;
  dockBindings?: BaseDockBinding[];
};
```

実際の型は既存の `PlayerSaveData.assembly` と重複しない共通シリアライズ型へ整理する。保存時にはランタイムオブジェクト、Three.jsオブジェクト、循環参照、編集履歴を含めない。

- `SAVE_VERSION` またはアセンブリの `formatVersion` を更新する。
- `assembly` がない旧セーブは `orbitalBaseAssembly()` を使用する。
- `assembly` があるが不正な場合は、セーブ全体の復元を壊さず、既定基地へフォールバックしてHUDへ警告を出す。
- 不正アセンブリをそのまま再保存して固定化しない。
- ドック中の船は既存の船IDを保ち、基地形状復元後に `dockBindings` を検証して再接続する。

## 6. 作業台の操作仕様

### 6.1 作業台への入口

基地の Operations（内部ID `combat` はセーブ互換のため維持）から、既存の `3D作業台` タブを開く。作業台上部に対象セレクターを追加する。

- `基地本体`
- `ドック中の船: <船名>`

初期選択は基地本体とする。基地本体を選択した場合、基地の全アセンブリを表示し、ドック中の船は別の対象として表示する。基地にドック中の船がある場合は、船の描画を基地座標へ配置したまま、編集中の基地部品と船を視覚的に区別する。

### 6.2 共通の3D操作

既存の `DockWorkbenchController` と `AssemblyRenderObject` を再利用し、対象ごとに次の操作を提供する。

- 外皮・外部部品をドラッグして移動する。
- 部品を在庫または別対象からドロップして取り付ける。
- ノードを選択して接続可能な候補を表示する。
- エッジを選択して長さ・向き・接続先を編集する。
- 外皮を選択して寸法・断面・材質など、既存の設計データが許すプロパティーを編集する。
- 部品を選択して個別プロパティーウィンドウを表示する。編集途中の基地部品にも同じ参照解決を適用する。
- ゴースト、スナップ候補、接続不可、占有中ドックを色とHUDメッセージで表示する。
- Undo/Redo、変更を確定、変更を取消を対象横断で利用する。

操作対象のメッシュには `partVisualRef`、ノードには `assemblyNodeId`、エッジには `assemblyEdgeId` を必ず付与し、基地本体だけ別の選択経路を作らない。

### 6.3 基地固有の操作制限

初期実装では、ランタイム破壊を避けるため次を禁止する。

- `base_module` の削除。
- ドック中の船が接続しているドック部品・ポートの削除、切断、位置変更。
- ドック容量を現在のドック中船数未満にする変更。
- 製造中、打ち上げ準備中、ドック移送中、別の基地トランザクション中の基地形状変更。
- 未検証の部品を取り付けた状態での確定。

占有中のドックを変更したい場合は、先に対象船を安全に離脱させる操作を実装する。初期版では作業台からの自動離脱を行わず、明示的に船を空けるまで候補を赤表示して確定を拒否する。

### 6.4 完全3D造船の操作仕様

完全3D造船を「既存部品の換装」と区別するため、選択モードと編集モードを明示する。

#### 対象選択

- `基地本体`、`ドック中の船`、`新規船`を対象セレクターから選ぶ。
- `新規船`では、空の下書き、既定の最小コア、保存済み設計の複製から開始できる。
- 3Dビューでは、基地・船・ゴーストを別レイヤーにし、レイキャスト結果に `targetId` を持たせる。
- 選択対象は部品、ノード、エッジ、外皮区画のいずれか一つとし、選択中要素のプロパティーウィンドウを開く。

#### ノード編集

- ノードをクリックして選択し、移動ギズモまたは数値プロパティーでX/Y/Zを変更する。
- グリッド・寸法単位にスナップし、ドラッグ中は接続するエッジ、部品、外皮をプレビュー更新する。
- 軸と位相を回転ギズモまたは数値入力で変更する。
- 「ノードを追加」で既存ポートを起点に新ノードを作り、接続先候補を表示する。
- 「ノードを削除」は、接続エッジ、部品、占有ドック、連結性への影響を確認してから実行する。

#### エッジ編集

- ノードの接続口を選んで「エッジを追加」し、相手側の未使用ポートへスナップする。
- エッジの種類を `hull`、`truss`、`decoupler` から選び、必要な断面サイズ・分離条件を入力する。
- エッジをドラッグすると接続ノードまたはポート候補へ再接続し、長さは端点から自動計算する。
- エッジを削除する前に、切断されるサブツリー、外皮開口、部品、ドックをプレビューする。

#### 外皮・断面編集

- `hull` エッジまたは端部ノードを選び、断面プリミティブの種類、寸法、位相、複合断面の貼り合わせを編集する。
- 断面変更はロフト外皮、内容積、質量、衝突形状、内部部品の収容状態へ即時プレビューする。
- 自己交差、閉鎖不能、面積ゼロ、過小断面、内部部品との干渉は赤色表示し、確定を禁止する。
- 外皮メッシュを直接編集するモードは提供せず、設計データから再生成できる操作だけを許可する。

#### 部品編集と建造

- 倉庫部品を3Dビューへドラッグし、接続口・外表面・トラスの候補へスナップする。
- 既存部品をドラッグして取り付け位置を変更し、ダブルクリックまたは削除キーで倉庫へ戻す。
- 取り付け候補は `MountPoint` として保持し、単なる画面座標を保存しない。
- `新規船`は「設計を保存」と「建造を確定」を分ける。「設計を保存」は下書きを保存するだけで、「建造を確定」だけが資源を消費してドックへ実体を生成する。

#### 履歴・検証

- ノード、エッジ、断面、部品、塗装の各操作を一つの編集コマンドとしてUndo/Redoする。
- ドラッグ中は仮アセンブリを表示し、ドロップ時だけ履歴へ積む。無効な候補は履歴へ入れない。
- 検証結果は対象要素とエラーコードに紐付け、3D表示、プロパティー、HUDで同じ理由を示す。
- 「建造を確定」「基地変更を確定」は、対象横断の全検証が成功してから原子的に適用する。

## 7. 実体への適用

### 7.1 トランザクション境界

作業台へ入った時点で次のスナップショットを保持する。

- 基地の `BaseAssemblyDesign`、在庫、ドックバインディング。
- ドック中の全船のアセンブリと、船ID・スロット対応。
- 基地の形状から導出される衝突形状・ドック座標の再生成に必要な値。

「変更を確定」では、作業台内の全対象をまとめて検証し、全て成功した後に一度だけ実体へ反映する。基地だけ先に更新して船の再接続に失敗する、という部分適用を許さない。

### 7.2 基地の再構築

`Vessel` の既存設計復元処理を整理し、基地アセンブリから次を再構築できるファクトリーまたは専用の置換処理を追加する。

1. 新しい基地設計を検証する。
2. 新しい `VesselDesign` と `AssemblyRenderObject` を生成する。
3. `BaseCollisionGeometry` を新アセンブリから作り直す。
4. 安定した `dockId` / `portId` からドックのワールド位置・法線・スロット容量を再計算する。
5. 旧基地の軌道状態、姿勢、燃料、資源台帳、在庫、ドック中船の実体を引き継ぐ。
6. 船の取り付けメッシュを新しいドック座標へ一括で再配置する。
7. HUD、Operations表示、ターゲット・カメラ・アクティブ対象を再同期する。
8. 旧描画オブジェクト、衝突形状、購読・イベント参照を破棄する。

再構築途中に例外や検証失敗が発生した場合は、旧基地を表示・運用可能な状態のままにする。新旧の `Vessel` を一時的に保持し、置換完了まで旧オブジェクトを破棄しない。

### 7.3 確定後の編集状態

確定後は、既存の作業台トランザクションと同様に新しいチェックポイントを作成する。確定済みの形状をさらに編集して取消した場合、直前の確定状態へ戻す。ドック退出、戦闘・Operationsビューへの切替、セーブ実行時には、未確定変更の扱いを既存の「確定または取消」ポリシーに統一する。

## 8. 実装フェーズ

### フェーズ0: 仕様・不変条件の固定

- `BaseAssemblyDesign`、`BaseDockBinding`、アセンブリ保存形式を定義する。
- `base_module`、必須ドック、占有中ポート、機能依存の検証規則をテストケースとして先に書く。
- 完全3D造船の編集コマンド、ノード・エッジ・断面・部品の操作契約と、無効化・ロールバック規則を定義する。
- 「設計から船を新造する」経路の削除範囲と、「部品生産」「設計保存」「3D作業台からの建造確定」の境界を定義する。
- 旧固定基地モデルの見た目と、現行 `AssemblyRenderObject` の差分を確認し、今回直す表示差分と別タスクを分ける。

成果物: 型・検証仕様・移行方針・失敗時のHUD文言。

### フェーズ1: 基地設計モデルと保存・復元

- `orbitalBaseAssembly()` を既定値生成として残し、カスタムアセンブリを渡せる `orbitalBaseDesign(assembly?)` へ整理する。
- `BaseSaveData` にアセンブリとドックバインディングを追加する。
- `serializeAsBase()`、`resolveDesign(savedBase)`、`restoreBase()` をカスタム基地に対応させる。
- 旧セーブ、不正アセンブリ、欠落ポート、重複IDの移行テストを追加する。
- `new-vessel-draft` の保存・読み込み形式を追加し、保存済み設計を直接実体化せず編集下書きとして扱えるようにする。
- 既存の完成船・保存済み設計・部品在庫を破壊しない移行処理を追加する。

依存: フェーズ0。  
並列可能: 保存型・移行テストと、基地設計ファクトリーの純粋関数部分。

### フェーズ1.5: 設計からの直接新造経路の削除

- `BaseView` の設計別船体生産UIと `onProduceVessel` を削除する。
- `Docking.produceVessel()` と、設計を受け取って完成船を生成する直接経路を削除する。
- `productionBlueprintOf()`、`BlueprintLibrary`、`LocalStorageBlueprintStore` のうち、削除対象経路だけが使う依存を整理する。設計保存・インポート・3D下書きで使うものは残す。
- 生産タブを部品生産中心の表示へ変更し、部品生産から倉庫へ入れた部品を3D作業台で利用できることを確認する。
- 旧保存済み設計を読み込めても、設計選択だけで船が生成されないことを確認する。
- 新しい3D下書きの建造確定が実装されるまで、ユーザーが船を作れない状態を明示するか、機能フラグで段階的に切り替える。

依存: フェーズ0、フェーズ1の保存・下書き方針。
並列可能: フェーズ2、フェーズ3と並行。ただし、直接生成APIを削除する前に新造下書きの受け皿を確定する。

### フェーズ2: 作業台セッションの対象一般化

- `DockWorkbenchSession` の対象を基地、ドック中船、新規船下書きの共通型へ拡張する。
- スナップショット、Undo/Redo、在庫移動、部品所有者、対象ごとの検証結果を共通化する。
- 基地専用の検証を `validateBaseAssembly()` として分離し、一般船の `validateBlueprint()` と合成する。
- 新規船下書きの「設計保存」と「建造確定」を分離し、確定前に実体・資源・ドックを変更しない。
- 実体への適用はまだ行わず、純粋な編集セッションのテストを完成させる。

依存: フェーズ0。  
並列可能: フェーズ1の保存実装と並行。ただし型の最終形は共有する。

### フェーズ2.5: 完全3Dアセンブリ編集エンジン

- `VesselAssembly` を変更する `addNode`、`moveNode`、`removeNode`、`addEdge`、`moveEdge`、`removeEdge`、`editSection`、部品配置変更の純粋コマンドを実装する。
- ノード位置からエッジ長を再計算し、`validateTree()` と既存の設計検証を各コマンド後に実行する。
- 断面プリミティブの追加・削除・寸法変更・貼り合わせを実装し、外皮ロフト、内容積、質量、衝突形状を同じ下書きから再計算する。
- `MountPoint` のポート・外表面・トラス候補を3D座標から生成し、現在の最初の船体エッジへの暗黙配置を置き換える。
- 編集コマンドを履歴へ積み、複数対象をまたぐ操作でもUndo/Redoと取消が原子的になるようにする。
- ノード・エッジ・断面・部品の参照が変わる操作で、関連する部品、ドック、塗装、保存IDの扱いを定義する。

依存: フェーズ0、フェーズ2。
並列可能: 形状コマンド、断面編集、マウント候補生成は互いに純粋な境界を共有すれば並行できる。

### フェーズ3: 基地のドック・座標・衝突導出

- ドックを固定 `hatch` 座標ではなく、アセンブリの安定ポートから解決する。
- `getSlotWorldPos()`、`getSlotWorldNormal()`、`dockCapacity` をカスタムアセンブリに対応させる。
- `BaseCollisionGeometry` をアセンブリから再生成する。
- 占有中のドックの固定、ドック中船メッシュの再配置、重複・干渉検出を実装する。
- カスタム形状でも船のドッキング、離脱、基地との衝突判定が一致することを確認する。

依存: フェーズ1、フェーズ0のドックポート仕様。  
並列可能: 衝突形状生成と座標解決。ただし同じポート表現を使う。

### フェーズ4: 作業台UIと3D編集

- `base-view.ts` に基地本体の対象選択、基地専用の制限表示、検証エラー表示を追加する。
- 既存の3Dステージ、レイキャスト、ノード・エッジ・外皮・部品の選択を基地・船・新規下書きへ接続する。
- ノード・エッジ用の移動／回転ギズモ、接続口候補、断面プロパティー、外皮プレビューを追加する。
- 部品ドラッグ、任意の接続口・外表面・トラスへのスナップ、取り外し、在庫からの取り付け、プロパティーウィンドウを基地と船に適用する。
- 新規船下書きの作成、設計保存、建造確定をUIへ追加する。
- 占有中ドック、必須部品、切断されるサブツリーを視覚的に表示する。
- 基地とドック中船の選択色・ラベル・編集対象を混同しないようにする。

依存: フェーズ2、フェーズ2.5、フェーズ3。
並列可能: DOM/UI組み立てと、3D選択・ゴースト表示。ただし対象IDの仕様を共有する。

### フェーズ5: 原子的なランタイム適用

- `docking.ts` に基地アセンブリ用のコミット・取消・ロールバックを追加する。
- 基地の再構築、衝突形状再生成、ドック中船の再接続、HUD同期を一つの適用処理へまとめる。
- 新規船下書きの建造確定でのみ資源を消費し、船をドックへ格納する。設計データから直接生成する旧経路は存在しないことを確認する。
- 製造、打ち上げ、移送、ドック退出など既存の操作に「未確定の基地・船編集」ガードを追加する。
- 置換失敗時に基地、船、在庫、ドック占有が元へ戻ることを確認する。

依存: フェーズ2、フェーズ2.5、フェーズ3、フェーズ4。
並列不可: 基地置換とドック再接続は同じトランザクション境界で実装する。

### フェーズ6: 保存・復元の統合確認

- 作業台で確定した基地形状を保存し、再起動後に同じ形状・ポート・ドック中船を復元する。
- 旧セーブを既定基地として読み込む。
- 不正保存を安全にフォールバックし、カスタムアセンブリを破損したまま再保存しない。
- セーブ中、作業台編集中、取消直後の各状態を検証する。

依存: フェーズ5。  
並列可能: セーブ移行テストとUIのアクセシビリティ確認。

### フェーズ7: 回帰確認と仕上げ

- typecheck、unit test、production buildを実行する。
- 既存の有人艦、敵艦、貨物、基地の描画・選択・保存を回帰確認する。
- WebGPU上でのレイキャスト、透明ゴースト、内部マーカー、カメラ操作を確認する。
- 変更点と判断保留事項を `第10版_3_実装中の追加事項.md` に記録する。

依存: フェーズ6。

## 9. 作業の分割と依存関係

```text
フェーズ0 ──┬──> フェーズ1 ──> フェーズ1.5 ──┐
            │                                 ├──> フェーズ2 ──> フェーズ2.5 ──┐
            └──> フェーズ3 ───────────────────┘                                 ├──> フェーズ4 ──> フェーズ5 ──> フェーズ6 ──> フェーズ7
                                                                                  └──（フェーズ4はフェーズ3の座標契約にも依存）
```

依存関係のない範囲は、次の単位で別worktreeへ分けて実装できる。

- 保存型・移行テスト（フェーズ1）
- 旧直接新造経路の削除（フェーズ1.5）
- 基地アセンブリ検証と共通作業台セッション（フェーズ2）
- 完全3Dアセンブリ編集エンジン（フェーズ2.5）
- ドックポート導出と衝突形状生成（フェーズ3）
- 作業台UIと3D選択表示（フェーズ4）

ただし、フェーズ5のランタイム置換は、これらの成果物をレビューしてから一つの統合worktreeで実装する。特に `BaseDockBinding` の表現、基地アセンブリの不変条件、`Vessel` の再構築方法は、並列実装前に確定させる。

## 11. テスト計画

### 純粋関数・データ

- 既定基地アセンブリから `BaseAssemblyDesign` を生成できる。

- カスタム基地を保存して同一のツリー、配置、ポート対応を復元する。

- 保存・復元後も在庫、資源台帳、燃料、ドック中船のIDが維持される。
- 新規船下書きを保存・再読み込みでき、下書きの読み込みだけでは船・資源・ドックが変化しない。

### 作業台・ランタイム

- 基地を選択して部品を外し、在庫へ戻せる。
- 在庫部品を基地へ取り付け、スナップ候補とプロパティーを表示できる。
- 新規船下書きを作り、ノード・エッジ・外皮・部品を3D操作で追加・変更・削除できる。
- ノード・エッジ・外皮・部品の選択と表示が対象種類を問わず一致する。
- 3Dドラッグ中はゴーストと検証結果が表示され、無効なドロップは履歴・在庫・実体を変更しない。
- 有効な新規下書きだけが「建造を確定」でき、確定時に必要資源を一度だけ消費してドックへ格納される。
- 設計を選択するだけの旧直接新造経路がなく、部品生産だけは継続して利用できる。
- 変更中は製造、打ち上げ、移送、作業台退出のガードが働く。
- 確定失敗時に基地形状、描画、衝突、ドック中船、在庫が全て変更前に戻る。
- 確定後にドック中船のメッシュが新しいポート座標へ追従する。

## 12. リスクと判断事項

### 旧直接新造経路の削除と新造不能期間

設計からの直接新造を先に削除すると、3D下書きから建造を確定する経路が完成するまで船を増やせなくなる。削除と置換を同じリリースで完了するか、3D建造確定を先に機能フラグで導入し、旧経路を停止しても明示的な案内が出るようにする。部品生産と既存船の編集を巻き込んで停止しない。

### 完全3D編集と物理モデルの一貫性

ノード・エッジ・断面を直接編集できても、外皮、内容積、質量特性、推進軸、電力・熱・配管、衝突形状が更新されなければ見かけだけの造船になる。編集コマンドの適用後に全ての導出モデルを同じアセンブリから再計算し、どれか一つが生成できなければ下書きを確定しない。

### 自由度と検証制約のバランス

「自由に編集する」は、任意の無効メッシュを許可することではない。`DIMENSION_UNIT`、最小エッジ長、ポート排他、断面の有効面積、外皮の閉鎖、部品の接続、コア要件、作業範囲をUI上で可視化し、無効操作は履歴へ入れずに理由を表示する。制約を増やす場合は、編集可能な自由度を意図せず削らないようにテストで境界を固定する。

### `base_module` と基地機能の結合

基地の容量や設備が `base_module` 固有の名前・折り目・固定座標に結び付いている場合、単純に部品を移動すると実体と描画がずれる。基地機能の参照を安定した部品ID・ポートIDへ移し、形状編集で変わってよい値と変わってはいけない値を分ける。

### ドック中の船を伴う形状変更

基地の移動でドック中の船を自動的に動かすと、別の部品との干渉や船同士の衝突が起きる可能性がある。初期版では占有ポートの変更を禁止し、基地本体の他部分だけを編集可能にする。将来、ドックモジュールの移設を許可する場合は、全船の再配置・干渉検証・離脱可能性を同じトランザクションで追加する。

### 旧固定モデルとの差

`AssemblyRenderObject` で描画できても、旧 `buildBaseModel()` の装飾、スケール、マテリアル、選択タグが完全に一致するとは限らない。形状編集の受け入れ条件と、見た目の再現を同じ完了条件にせず、必要な視覚回帰を別の差分として記録する。

### 衝突形状の近似

アセンブリから生成する衝突形状が粗すぎると、作業台では接続できるのに実際の基地で衝突する、またはその逆が起きる。まずは安全側の包絡形状で確実性を優先し、必要なら部品単位の形状へ細分化する。作業台の干渉表示とゲーム中の衝突判定が同じ導出元を参照することを条件にする。

### 保存形式の将来拡張

基地のアセンブリをそのまま保存すると、将来の部品・ポート形式変更で復元できなくなる。保存形式にはバージョンを持たせ、移行不能時は明示的に既定基地へフォールバックする。移行処理でユーザーの在庫やドック中船を失わないことを優先する。
