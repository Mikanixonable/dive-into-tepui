## 1. 未解決の阻害要因 — 組立の確定が既存の検証で塞がっている

**A群の実装中に見つけた、計画に無かった既存の不具合。判断が要るのでここに残す。**

### 症状

`Docking.applyTargetAssembly` は対象の種別を見る前に `assemblyError(assembly, name)` を通す。これは
`createBlueprint` してから `validateBlueprint` を全部走らせ、`severity === 'error'` の最初の1件で
確定を拒否する。ところが**出荷済みの既定設計はどちらもこの検証を通らない。**

| 設計 | error |
|---|---|
| `crewedAssembly` | 加圧式のエンジンですが、加圧ガスタンクも自己加圧の条件もありません |
| `orbitalBaseAssembly` | 同上 / 最大寸法 145.2 m が上限 120 m を超えています / 総質量 3004645 kg が上限 2000000 kg を超えています |

したがって**組立ウィンドウの「確定」は、既定の有人艦でも軌道基地でも成功しない。**
これは第11版_1 の完了条件1〜5(取り付け・移動・取り外し・部材生成・断面編集がいずれも確定を伴う)を
そのまま塞ぐ。

### 原因

- `checkPressurant` は `cycle: 'pressure_fed'` のエンジンに加圧ガスタンクか自己加圧推進剤を要求する。
  有人艦・基地とも `pressure_fed` × `nitrogen-tetroxide`(自己加圧ではない)を積んでおり、
  **`pressurant_tank` を置いている設計は `src/` に1つも無い** — 部品の種別も内容積の係数も質量の
  扱いも揃っているのに、実際に積んだ設計が存在しない。
- `checkLimits` の `DEFAULT_BLUEPRINT_LIMITS`(最大 2e6 kg / 120 m)は艦の寸法であって、
  3000 t・145 m の軌道基地には元から合わない。
- `validateBaseAssembly` は意図して `validateAssembly(assembly, { validateBlueprint: false })` を
  呼び、基地には全体設計の規則を課さない作りになっている。**その意図を `assemblyError` が
  上書きしている** — docking.ts の内部で矛盾している。

### 取りうる案(いずれも設計判断なので、この実装では選ばない)

1. 既定設計へ `pressurant_tank` を積む。模型としては最も正しいが、質量・内容積・アクチュエータの
   調整値が動く。
2. 既定設計のエンジンを `pump_fed` にする。同じく調整値が動く。
3. `checkPressurant` を warning へ下げる。最小だが、意図のある規則を弱める。
4. 基地には艦の寸法上限を課さない(`assemblyError` を対象の種別ごとの検証へ揃える)。
   **上記の内部矛盾そのものの是正なので、これだけは単独でも正しい。**ただし加圧の件は残る。

**この不具合は今回の作業が原因ではなく、A群の着手前から在る。**A群のUI実装はこれとは独立に
正しく積み上がるので実装は続けたが、**確定が通るようになるまでプレイヤーには何も届かない。**

  `AssemblyEditError.message` をそのまま)に置き換えた。

  程度の設計を組めなくしてしまう。単一部品の喪失で軸を失う構成は warning(現在の欠陥ではなく脆さ)。
- **C は既定設計に新しい error を1件も足していない**(足したのは基地への warning 1件のみ)。
  上記 §1 の error はすべて C の変更前から在ることを、変更を外した状態と比較して確認した。

## 3. 実装中に判明した計画外の変更点

### セッション中の編集は確定するまで世界に映らない

A1 で「3D上の部品を掴み上げる」を入れて表面化した。掴んでいる間は元のメッシュを隠すが、
離して**取り付けが成功しても、対象のメッシュはセッションの構成から作り直されない** —
確定を押すまで、部品は元の位置に戻って見える。倉庫からのドロップも同様に、確定まで何も変わらない。

つまり**組立ウィンドウの操作は、確定するまで一切の視覚的な手応えが無い。**A1 の実装はこの既存の
模型に合わせただけで、悪化させてはいない(掴んでいる間だけ隠すのは、2つ見えるよりは正しい)。

直すには「実機ではなくセッションの構成を描く」仕組みが要る — 実機へ書き戻すのは確定の瞬間だけ、
というセッション設計そのものと両立させる必要があるので、A群の範囲を超える。
**A4 の断面編集も A5 の部材生成も同じ制約を受ける**(編集しても確定まで形が変わらない)ため、
第11版_2 側の項目として起こすべき事柄。

### B1 の前提は誤っていた — 分類は既に効いている

計画 §3 B1 は「`isCargo` に呼び出し側が1つも無く、分類が何の判断にも効いていない」と書いたが、
**誤り**。`isCargo(v)` は `!hasCorePart(v)` そのもので、`hasCorePart` の側は
`ActiveVesselController` のコンストラクタ・`set`・`claimIfNone`・`reclaimAfterLoss` の
すべてで既に門になっており、`set` の拒否メッセージは既に「貨物です」と言っている。

正しくは「**輸出名 `isCargo` に呼び出し側が無い**」だけで、判断そのものは実装済みだった。
したがって門を二重に足すことはせず、`set` の条件を `isCargo` へ言い換える(メッセージが
名指す概念とコードの語が一致する)に留め、**本当に欠けていた「種別が画面のどこにも出ない」**
の側だけを足した。

### B2(基地への昇格・降格)は未完了

着手したが、保存形式まで含めた横断範囲が大きく、途中で止まった。型エラーを残した中途半端な状態は
一貫性そのものが要点の変更では危険なので、**その場の変更は破棄し、B2 は未着手のまま残した**。
判明していた5つの不整合(計画 §3 B2)はそのまま有効なので、次に着手するときはそこから読む。

ただし B2 の一部で、単独でも明らかに正しい2点だけは先に入れた:
- `ActiveVesselController` のコンストラクタが `activePlayerId` を `ownShips()` の中だけから
  解決していた点(基地に分類された操作機を復元できない)を `entities.vessels` へ広げた。
  `set()` は元から基地を受け付けるので、コンストラクタだけが狭かった。
  `reclaimAfterLoss` は `ownShips()` のままにした — 喪失後に自動で基地へ操作を渡すかどうかは
  復元とは別の判断であり、渡さないのが現在の設計。

次に着手するときは、**保存形式に触れる部分(B2b)と触れない中核(B2a)を分けて進める**。
B2a = 設計工場の選択を積荷から決める / `baseState` 等の再導出 / `replaceAssembly` の昇格・降格 /
名簿の分類の追従。B2b = `serializeAsShip` の非 null 表明 / 2配列の扱い / 復元時の解決。

### ノード・エッジは既定で見えないまま選択できてしまう

ノードとエッジの目印を持つのは `render/vessel-wireframe.ts` の描画で、その表示は
`GraphicsSettings.current.wireframe` に従う — **既定は off**。一方 `THREE.Raycaster` は
`visible` を見ないので、ワイヤーフレームを消していてもノード・エッジは拾える。
**見えないものを選べる**状態なので、A4 で断面編集を入れるときに、組立セッション中は
ワイヤーフレームを強制的に表示する扱いにする。

## 4. 最終コードレビューで残した指摘(直さず記録)

以下は最終レビューで挙がったもののうち、今回の変更セットでは直していないもの。直したものは
コミット済みで、ここには残さない。

### 下書きだけワイヤーフレームを持たない

`Vessel` を伴わない下書きは `render/vessel-wireframe.ts` の描画を持たないので、A4 の断面編集と
A5 の部材生成は**下書きに対してだけノード・エッジを選べない**(基地本体と格納艦では選べる)。
新規造船が最も編集を要する対象なので、実用上いちばん痛い穴。上の §3「セッション中の編集は
確定するまで世界に映らない」を直す仕組み(セッションの構成を描く)が入れば同時に解ける。

### 検証が毎フレーム走る

`AssemblyPanel.sync` は毎フレーム `validateBlueprint` を呼び、その中で `deriveMassProperties` が
3回走る(C で足した電力・熱・姿勢の3項がそれぞれ独立に呼ぶ)。有人艦で概ね 30ms 規模。
セッション中は時間が止まっているので操作感には出ていないが、`validateBlueprint` 自体が
「設計が変わったときだけ」の計算であり、毎フレーム走らせる形は誤り。構成の版数で持ち回すべき。

### assembly-panel と docking の層が反転している箇所がある

`AssemblyPanel` は表示の持ち主だが、部材棚の押下が `AssemblyDragController.beginDrag` を直接
呼んでいる。掴みの開始は `Docking.updateAssembly` が一手に持つ約束(クリック待ち行列を1本に
した理由そのもの)なので、棚からの掴みだけがその外にある。

### `MateOutcome.reason` を誰も読んでいない

A6 で `MateVerdict` を `{accepted, reason}` へ置き換えたが、`reason` を画面に出す経路が無い。
なぜ取り付けられないかが利用者に届かない(色が赤くなるだけ)。

### Stefan-Boltzmann の式が2箇所にある

C の `checkThermalBudget` が `vessel/thermal.ts` と同じ放熱の式を持っている。設計時の見積もりと
実機の挙動が別々に書かれているので、片方を調整したときに黙って食い違う。

### 追従カメラの距離へ外から手が伸びている

`Docking.frameAssemblyCamera` が `cameraSystem.chaseCamera.dist` を直接書いている。
`setChaseCameraOverride` が姿勢だけを受け取る形なので、距離だけがこの経路の外にある。
