## 優先度の高い不整合・再現候補

### 1. 視点中心 cap の半径上限時は、スナップによる中心ずれを覆えない

**判定: 境界ケースの覆い保証が成立しない。高高度・遠距離からの表示で追加の欠けが出る可能性。優先度 P2。**

`capRadiusFor()` は遠距離で必要半径を `π/2` に制限する。コードコメントもこの距離では余白が取れないことを認めている。さらに `snapCap()` は中心を地表格子へ丸めるため、丸め前の直下点との距離が必ずしも 0 ではない。現在の `cloud-cap.test.ts` は `min(need + offset, π/2)` を比較して中心ずれを上限で切り捨てるため、上限に達するケースでは実際の必要範囲を覆っていることを検査していない。これは「全域を覆う」という保証が半径上限の範囲では成立しないことを示す。スナップ分の追加欠けが見えるかは実画像で未確認。

**影響候補:** cap 外は `CloudFieldSampler` が雲なしを返すため、球面の縁に近い領域で雲が欠ける。発生位置が視点高度や cap の格子点に依存し、視点移動時の見え方の変化として現れる可能性がある。

**改善案:** 半径上限に達したときの許容欠け・描画可能範囲を明記し、中心スナップによる追加欠けが許容範囲か実画像で確認する。必要なら cap 中心をスナップしない、投影範囲を分割する、描画可能範囲を仕様として狭める等を比較する。どれを採るかは見え方を変えるため、実装前に判断する。テストは `min` で上限ケースの保証をぼかさず、上限に達した状況で何を保証するかを明示する。

### 2. 生成雲場のベイク後、雲表面サンプラーの混合率が更新されない

**判定: フレーム間の更新順序の不整合。生成雲で混合率・投影が更新されたフレームに一時的な誤読が起こりうる。優先度 P1。**

`GamePresentation.syncWorld()` は天体を同期した後に `bakeClouds()` を呼ぶ。雲表面は `CloudPresentation.syncGraphics()` / `aim()` 中に `surface.bind(renderInput)` され、その bind は `CloudFieldSampler` 自身の `parity`・`fraction` uniform へ値をコピーする。続く `CloudPresentation.bake()` は `source.prepare()` でテクスチャと混合率を更新するが、ベイク後に `surface.bind()` を呼ばない。

特に cap の投影版が変わったとき、生成場は一方のテクスチャを新しい投影へ焼き直す。描画側の混合率は前フレームの値のままなので、そのフレームだけ異なる投影で焼いた2枚を混ぜる可能性がある。次フレームの `syncGraphics()` で再 bind されるため、一フレームのちらつき・ずれに見える条件がある。

**改善案:** ベイクで更新された `CloudRenderInput` のどの値を各読み手へいつ反映するかを一か所で定め、描画前に新しい混合率・投影・世代をそろえる。回帰テストは「投影版変更」「時間刻みで parity が切り替わる」「大きな時刻ジャンプ」を分けて、ベイク直後にサンプラーが読む状態まで検査する。

### 3. 描画設定の旧「積雲オフ」値が新しいトグルへ移行されない

**判定: 現在の未コミット設定変更に対する保存互換性の欠落。優先度 P1。**

変更前の `CUMULUS_DETAIL` では `off: 0` が保存値で、「積雲の殻・影を描かない」意味を持っていた。現在の差分は候補から `0` を外し、`cumulus` / `cirrus` の独立トグルを追加している。`parseGraphics()` は候補外の選択値を既定へ置き換え、存在しない新トグルも既定で補う。従って、旧データ `{"clouds":true,"cumulusDetail":0}` は、現状では新しい `cumulus=true` と標準の精細度へ復元される。以前オフだった積雲がオンになり、描画負荷も増える。

**改善案:** 旧値 `cumulusDetail: 0` を認識し、新しい保存形式では `cumulus: false` に写す移行を `parseGraphics()` に置く。旧形式と新形式をそれぞれ入力にした回帰テストを追加する。単なる候補値の削除・追加で意味が変わる設定を今後も扱うなら、設定スキーマの版管理か、明示的な移行表を設ける。

### 4. 再突入エフェクトが「表示時刻の位置」と「現在時刻の対気速度・動圧」を混ぜる

**判定: 表示時刻がシミュレーション現在時刻と異なる場合の時刻軸不一致。優先度 P1。**

`DynamicView.place()` は `source.stateAt(viewFrame.displayTime)` から表示位置を作る。ゲーム側の `displayTime` は未来ゴーストのスライダー分だけ先取りされる場合がある。一方、モジュール船の `renderSource()` は現在の `motion.aero.airspeed` と `qdyn` を渡し、再突入エフェクトはそれらを `displayed` 状態と組み合わせる。

その結果、表示中の船は将来位置にいるのに、再突入光の方向と強度は現在の大気・速度から取る、という混在が成立する。通常時刻一致では目立たないが、未来表示・遅延表示では効果の向きや有無が船の表示状態と合わない可能性がある。

**改善案:** 再突入表示に必要な運動・大気の値を同じ `displayTime` で導出して一つの表示スナップショットとして渡す。未来側の大気状態を求められない場合は、表示時刻が現在時刻と異なるときの効果をどう扱うか決め、現在値を暗黙に混ぜない。未来ゴーストを有効にしたケースで方向・強度を検査する。

## 将来の不具合・管理負担につながりやすい構造

### 5. 雲場の時間挙動を source のオブジェクト同一性で決めている

`CloudPresentation.bake()` は `this.source === this.sources.generated` のときだけ細部時計を進める。現在の2種類では成立するが、動的な別 source を追加すると、`generated` 以外は静的として時計を止める。時間挙動が `CloudFieldSource` の契約に含まれず、呼び出し側が具体インスタンスを知っている。

**改善案:** `CloudFieldSource` が時間挙動を宣言する、または表示時刻・細部時計を source が返すなど、種類追加時に分岐の修正漏れが型・テストで見える契約へ寄せる。

### 6. 雲の種類別表示フラグが複数の描画経路で別々に合成される

全体の `clouds`、`cumulus`、`cirrus` の組み合わせを `CloudPresentation` が導出し、天体表面・大気中の巻雲・天体照・影の経路がそれぞれ独立に参照する。現在の差分では配線されているが、1経路だけ新トグルを参照し忘れると、本体・大気・影の不一致になる。`cloudShadowKinds()` の単体テストはあるが、設定から各描画経路までを通す組み合わせテストは不足している。

**改善案:** 表示可否の正本と組み合わせ規則を一か所に置く。設定の真理値表（全体オフ、積雲のみ、巻雲のみ、両方オフ）を、表面・大気・影・天体照の各出力に対するテストで固定する。

### 7. cap の半径段と中心格子が高度に依存し、段境界にヒステリシスがない

`snapCap()` は必要半径を段階化し、その半径から中心格子の幅も計算する。視点距離が境界を往復すると半径段と中心格子が切り替わり、投影の再ベイクが短時間に繰り返される可能性がある。現在のテストは半径の値の個数や格子の覆いを確認するが、境界を往復するカメラでの絵の連続性・再ベイク頻度は確認していない。

**改善案:** `rho` を各段境界の前後で往復させ、cap の配置・projection revision・生成雲の再ベイク回数と画像差分を測る。頻繁な切替が実際に問題なら、段境界を安定化する方式を検討する。

### 8. `EngagementZoneBuilder` の返り値は次回 build で中身が書き換わるが、型上は通常の readonly 配列に見える

ビルダは配列・zone・anchor 配列を再利用する。コメントで「次の build までに使い切る」と説明され、現行 `Simulator` の使用は各ステップ内で完結している。一方、返り値の型は寿命を表さず、将来の呼び出し側が保持・非同期処理へ渡すと、後の build で過去結果が静かに変わる。

**改善案:** 一時借用であることを API 名・スコープ・消費コールバックなどで表し、呼び出し側が保持できない形へ寄せる。少なくとも将来参照用に保存する値はコピーが必要だと、呼び出し面で明確にする。現状の hot path では再利用の性能利点があるため、単に配列を毎回コピーする変更はベンチマークなしに行わない。

### 9. 描画設定はスキーマ版を持たず、旧値を「候補外なら既定へ落とす」

これは今回の積雲設定移行だけの問題ではない。`parseGraphics()` は、未知のキーを無視し、候補外の値を既定へ落とす汎用方針である。今後、設定項目の意味変更・削除・値の再利用が起きると、データ自体は読み込めてもユーザーの意図が失われる。エラーにもならず既定が適用されるため発見が遅い。

**改善案:** 表示品質設定を後方互換にする方針（意味を維持する、移行する、意図的にリセットする）を明確にし、非互換変更は `parseGraphics()` の移行と旧形式テストを必須にする。値を再利用・詰め直さないという既存方針も維持する。

### 10. 配置方法が増えた UI の条件分岐が1つの大きなパネルへ集まっている

`src/game/creative/object-placer-panel.ts` は調査時点で694行。`placementMode` が `elements` / `lagrange` を切り替え、フォーム構築・値の読取・確定値の組み立てに分岐する。前回の `refactoring-candidates_2026-10-18.md` でも分割候補として記録されており、現在も規模とモード分岐が残っていることを確認した。

**リスク:** 配置方法や入力項目の追加時に、表示・入力値の検証・確定データの discriminated union の更新漏れが起きやすい。単にファイルを小さくするのではなく、各配置方法が独立したフォーム状態・構築・読取の責務を持てるかを診断する価値がある。

**改善案:** 新しい配置方式を追加する前に、elements / lagrange の状態とフォーム操作を分ける境界を検討する。既存フォームの責務を保ったまま分けられる単位を確認し、表示・入力・確定値のテストを方式ごとに整理する。
