# 船体アセンブリ移行 残課題修正計画

作成日: 2026-09-19  
計画の基準コミット: `884e6720c`  
状態: 計画作成。実装は未着手。

## 目的

船体アセンブリ移行後に残る、建造状態の引き継ぎ、保存データの整合性、建造中の入力境界、接舷 UI、
統合回帰テストを整備する。

建造 UI の実行経路未接続(P0)は現在対応中のため、この計画の実装対象から除外する。P0 の配線が利用可能に
なったことを前提に、その後の船体状態を壊さずに扱えることを完成条件とする。

## 決めたこと

- 建造中はシミュレーションを停止し、カメラの回転・ズーム、建造操作、ESC だけを受け付ける。
  現在入っている `pausesGame: true` と通常ポインタの差し替えは維持し、残る入力漏れを塞ぐ。
- 建造ドラフトは `ShipAssembly` の付属 UI 状態ではなく、船体と一緒に移動・保存されるゲーム状態とする。
  ドッキング、接続解除、デカプラー分離で参照 ID を失ったり、無言で破棄したりしない。
- 建造を開始できる接舷部は `dock` に限定する。`docking_port` を建造予約だけ受け付ける現行の
  `ShipDockState` API は、UI・開始処理・保存復元と一致するよう整理する。
- 保存復元では、ID が存在するだけでなく、ドラフトがドックから伸びる1枝を正しく指していることを検証する。
- 最近傍ポートへの自動選択は接舷確定の入口として残さない。ユーザーが接続先ポートを選び、条件と結果を
  確認してから接舷する経路を用意する。
- 資源コスト・建造時間・設計図ライブラリは今回の移行残課題には含めない。別のゲームデザイン決定後に扱う。

## 現時点で計画対象外とする実装済み事項

`HEAD` では、`GamePresentation` から `ShipConstruction` / `ModuleWindows` を生成し、建造中の同期・
ポインタ優先順位・時間停止・ラン終了時の dispose まで接続されている。また建造終了は追加枝を分離せず、
編集セッションだけを閉じる挙動になっている。これらを再実装しない。

## 達成目標

- ドッキング後も、相手側にあった建造ドラフトがモジュール ID・接続 ID の写し替え後に再開できる。
- 接続解除またはデカプラー分離後、両船体のどちらにも存在しないモジュールを指すドラフトが残らない。
  曖昧なドラフトは無言で捨てず、操作を拒否するか、明示的な破棄・移管を行う。
- 不正な保存ドラフトを読み込むと決定的に拒否され、正しい建造途中状態は保存・復元を往復できる。
- 建造中に飛行、射撃、時間加速、ターゲット変更、ビュー切替、ヘルプ、視点追従切替が発生しない。
  ESC だけは建造オーバーレイを閉じる。
- 接舷時に最近傍の候補へ勝手に接続せず、選択したポートの距離・角度・相対速度・所属条件を表示する。
- 建造・接舷・接続解除・デカプラー分離・保存復元を、ドメインテストとゲーム層テストで検出できる。

## 手順

### 1. 建造中の入力境界を完成させる

#### 目的

`gameInputMode()` の契約と実際の入力ポートを一致させ、建造モードから許可されていない単発操作を遮断する。

#### 変更箇所

- `src/game/input/game-input-ports.ts`
  - 建造中の `hud`(H) と `camera-command`(G) を無効にする。
  - 建造中のプロパティ窓ショートカットを通さない。ESC の最前面閉鎖だけは既存の pause port に残す。
  - 建造操作とカメラの連続入力を分け、カメラ回転・ズーム以外のゲーム操作へフォールバックしない。
- `src/game/input/game-input-router.ts`
  - 必要なら建造専用の優先順位を型で表現する。単なる呼び出し側の条件重複は増やさない。
- `tests/game/construction-input-routing.test.ts`
  - H/G、ワープ、ビュー、ターゲット、操縦、射撃が建造中に消費されないことを追加する。
  - ESC は建造オーバーレイだけを閉じ、何も開いていないときだけ pause menu へ進むことを確認する。

#### 達成条件と検証

- 建造中に禁止されたコマンドの handler が呼ばれない。
- カメラの回転・ズームと建造候補のクリックは従来どおり通る。
- `npm run typecheck`
- `npm run test:game`

### 2. ドッキング・接続解除・デカプラー分離で建造ドラフトを移管する

#### 目的

船体グラフのトポロジーが変わっても、建造途中の枝とその編集位置を船体状態として保つ。

#### 変更箇所

- `src/game/ship/ship-dock-state.ts`
  - ドラフトをモジュール ID と接続 ID の写し替え、または assembly の所属集合で分割する操作を追加する。
  - `dock` 限定の開始条件を公開し、`docking_port` を建造予約へ入れない。
  - ドラフトの重複、所属不明、枝を跨ぐ参照を保持できないようにする。
- `src/game/ship/modular-ship.ts`
  - `dock()` で `other.docks` を `merged.moduleIds` / `merged.connectionIds` に従って取り込む。
  - `separateConnection()` で retained / detached assembly の所属に応じてドラフトを移管する。
  - `decouple()` でも同じ移管を行う。どちらにも所属できないドラフトは、操作を中止するか明示的に破棄する。
  - `dockedVessels` の移管処理と同じ場所で行い、片方だけが移る状態を作らない。
- `src/game/ship/ship-save.ts`
  - ID の写し替え後も保存形が復元条件を満たすよう、移管処理と検証処理の責務を分ける。
- `tests/game/ship-construction.test.ts`
  - 相手船体の未完成枝をドッキング後に再開できることを追加する。
  - 接続解除・デカプラー分離でドラフトが正しい船体へ移ること、曖昧なケースが無言で消えないことを追加する。

#### 達成条件と検証

- ドッキング前後で、各ドラフトの `dockId`、`addedIds`、`axialTailId`、`firstConnectionId` が対応する
  新 ID へ写し替わる。
- 接続解除・分離後に `serialize()` が存在しない module / connection ID を出力しない。
- `npm run typecheck`
- `npm run test:game`

### 3. 保存ドラフトの構造検証を強化する

#### 目的

「参照先 ID が存在する」だけでは検出できない、別枝の混入や編集順序の破壊を復元時に拒否する。

#### 変更箇所

- `src/game/ship/ship-save.ts`
  - `dockId` が健全で空の `dock` であることを検証する。
  - `addedIds` の重複、`dockId` の混入、ドラフト間の重複を拒否する。
  - `firstConnectionId` が dock から始まる構造 edge であり、その child が `addedIds[0]` であることを検証する。
  - `addedIds` が `firstConnectionId` 以下の同一枝だけを含み、`axialTailId` がその枝の dock または軸方向末尾で
    あることを検証する。ドッキング edge、別枝、中間の既存 module を編集対象として受け入れない。
  - `firstConnectionId === null` と `addedIds` 空の組み合わせだけを未配置の建造途中として受け入れる。
- `tests/game/ship-construction.test.ts` または新設 `tests/game/ship-save.test.ts`
  - 正常な建造途中の round-trip。
  - 未知 module、別枝 module、重複 module、誤った first connection、誤った axial tail、接舷済み dock の拒否。

#### 達成条件と検証

- 不正データは読み込み時に例外となり、部分的な船体だけを公開しない。
- 正常な建造途中の保存・復元で、配置済み module と次の候補位置が変わらない。
- `npm run typecheck`
- `npm run test:game`

### 4. 接舷先ポートの明示選択を追加する

#### 目的

複数候補があるときに最近傍ポートへ暗黙に接続する不確定な操作をなくし、仕様どおり選択した接舷部を確定する。

#### 変更箇所

- `src/game/pickable/module-windows.ts`
  - `dockNearest()` を直接確定の入口にしない。
  - 候補船体・ポートを一覧または選択可能な接舷候補 UI へ渡し、選択した ID で `ModularShip.dock()` を呼ぶ。
- `src/game/ship/ship-docking.ts`
  - 候補列を距離順に安定して返す読み取り API を追加する場合、可否理由を候補ごとに保持する。
  - 接舷確定時には再度 eligibility を評価し、表示後の状態変化を拒否する。
- `src/game/pickable/ship-inspection.ts` / HUD の関連項目
  - 空いている dock / docking_port ごとに「ドッキング」と無効理由を表示できるようにする。
- `tests/game/ship-docking.test.ts`（新設）
  - 複数候補から選択したポートだけが統合されること、条件不成立の候補が確定できないことを確認する。

#### 達成条件と検証

- 同じ距離帯に複数候補があっても、ユーザーが選択しない限り接舷しない。
- 距離・正対角・相対速度・所属条件を候補ごとに表示または通知できる。
- `npm run typecheck`
- `npm run test:game`

### 5. 船体アセンブリ移行の統合回帰テストを補う

#### 目的

ドメイン単体の木構造テストだけでは検出できない、entity・registry・選択・物理状態・保存状態の連携を固定する。

#### 変更箇所

- `tests/game/ship-docking.test.ts`（新設）
  - 接舷条件、接続点一致、質量加重速度、接続 identity、操作対象の維持・切替。
  - 接続解除後のポート残存、identity の復元、衝突猶予。
- `tests/game/ship-decoupling.test.ts`（新設）
  - decoupler の消費、二つの assembly、質量比の分離速度、運動量保存、debris 登録。
  - 分離後の操作基準 cockpit、燃料・点火・建造ドラフトの継承。
- `tests/game/ship-save.test.ts`（新設）
  - assembly、建造途中、接舷 identity、衝突猶予の round-trip。
  - malformed save の拒否。
- `tests/game/ship-construction.test.ts`
  - 現在の `ShipDockState` の基本テストを、実際の `ModularShip` 操作と結び付ける。

#### 達成条件と検証

- 物理量は実装値の写しではなく、質量保存・接続点一致・参照整合性などの不変条件で検証する。
- `npm run typecheck`
- `npm run test:game`
- ゴーストやモジュール描画に変更が及んだ場合だけ `npm run test:render` も実行する。

## 強く推奨するが今回の移行完了条件には含めない機能

### 設計図の保存と再生産

現在は船体の実行時 snapshot は保存できるが、建造した構成を名前付き設計として保存し、別の dock から同じ構成を
再生産する機能はない。モジュール定義 ID、接続木、初期状態の扱いを設計図として定義できれば、反復建造の操作負担と
保存データの再利用性が大きく改善する。これはゲーム仕様上も候補として明示されているため、資源経済と併せて別計画にする。

### 任意の接続先を選ぶ建造編集

現行の建造セッションは `axialTailId` を中心に追加・末尾撤去を行い、側面部品もその編集位置に限定される。中間挿入、
並べ替え、枝の切替、複数枝同時編集は未実装である。MVPの単純性を保つなら仕様上の制約として明示し、拡張するなら
側面スロット・自由端の選択表示と撤去影響のプレビューを先に設計する。

### 建造資源・時間・在庫

建造は現在、部品を即時追加し、資源・待ち時間・在庫を消費しない。これは移行の残バグではないが、建造をゲームループの
意思決定へ発展させるなら、部品の供給源、建造可能 dock、資源質量、キャンセル時の扱いを一体で設計する必要がある。

## 見積り

相対的な実装工数を次の分解で見積もる。

- 入力境界: 2入力ポート群の制御 + 4系統の回帰確認 = 約1.5人時
- ドラフト移管: ドッキング・接続解除・デカプラーの3操作 × 状態分割／ID写し替え = 約4人時
- 保存検証: 5種類の不正形 + round-trip = 約2人時
- 明示的な接舷先選択: 候補 API・UI・確定再検証 = 約3人時
- 統合テストと修正反復 = 約3人時

合計は約13.5人時。DOM の既存 widget を再利用できること、実機確認をこの計画に含めないことを前提とする。
接舷候補 UI を既存窓に収められない場合は、約2人時を追加する。

## リスクと落とし穴

| リスク | 影響 | 対策 |
| --- | --- | --- |
| ID 写し替え漏れ | ドッキング後の再開・保存でドラフトが壊れる | `moduleIds` と `connectionIds` を使う専用移管 API と round-trip テストを先に作る |
| 分離時にドラフトが枝を跨ぐ | 次回保存または復元で例外、状態の無言消失 | 曖昧な分離を拒否するか、明示確認で破棄・移管する |
| 建造中の入力ポート漏れ | 飛行・ヘルプ・視点設定が停止中に動く | `gameInputMode` だけでなく全 command port の実ルーター試験を追加する |
| 保存検証の厳格化 | 既存の不完全な v4 記録を読めなくなる | 受け入れる旧形を先に列挙し、拒否理由と互換方針をテストに残す |
| 候補表示後の状態変化 | 他船の移動や先取り接続で誤接舷する | 確定直前に `dockingEligibility` を再計算する |
| 物理テストが調整値を固定 | 分離速度などの調整変更で無意味に壊れる | 運動量・重心速度・接続点一致などの不変条件を検証する |
| UI とモデルの責務混在 | 建造・接舷操作が別経路で不整合になる | モデル層に状態移管・候補判定を置き、UI は選択と通知だけにする |

## 最終検証

実装完了時に、変更箇所に対応して次を実行する。

1. `npm run typecheck`
2. `npm run test:game`
3. ゴースト・モジュール描画を変更した場合のみ `npm run test:render`

実機での開始から建造、保存、再開、接舷、接続解除、デカプラー分離を確認する作業は、ユーザーが実行時確認を
依頼した段階で別途 `npm run smoke:browser` を用いて行う。
