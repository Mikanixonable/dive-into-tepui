# ゲーム基幹の律速の解消計画(2026-11-22)

作業場所: worktree `../dive-into-tepui-game-core`(ブランチ `perf/game-core`。feat/enemy-lab に workspace3 を
取り込んだ a57dde8ec が起点)。計測の道具はセッションの scratchpad にある `cpu-profile.mjs`(CDP の CPU
プロファイルをソースマップで ts へ戻し、self/total を集計)と `tree.mjs`(呼び出し木・呼び出し元の集計)。
scratchpad が消えていたら、同じものを `tools/` へ足してから続ける。

## 目的

ゲーム全体を CPU 4 倍減速(モバイル相当)で計測した結果、フレームの CPU 時間は 25〜110ms あり、律速は
次の 5 系統に集中していた(割合はフレームの CPU 時間に対するもの。stage1 戦闘は 27.5ms/フレーム)。

| 系統 | 割合 | 原因 |
| --- | --- | --- |
| インスタンス属性の再転送 | 戦闘 9〜10% | `InstancedPool` が属性を `DynamicDrawUsage` にしており、three はその属性を使う**描画パスごとに**バッファ全体を `writeBuffer` する(G バッファ・影の各スロット×2 層・…) |
| 地表タイルの選択とページ表 | 戦闘 12%・地図 23% | 投影の作り直し(100ms ごと)のたびに文字列キーでタイルを選び直し、512×256×4 のページ表を毎回組み直して 3 回走査し複製し GPU へ送る |
| 影マップの描画 | 戦闘 16〜25% | スロットごとに近層・遠層・空戻しで scene 全体を描く。中身の半分は上の再転送 |
| 物理の進行 | 敵の多い面 30%・破片 500 で 22〜36% | 個体ごとの積分(重力加速度)と、弾×船の掃引接触 |
| 天体照の選択 | 3〜4% | 全天体ぶん、他の全天体を遮蔽体にした日照率を毎フレーム解く(O(N²)) |

ワープ時は加えて、雲の焼き直しのたびの低気圧の配置計算(×1024 で 16%)、予測の延長と軌道線の同期
(×65536 で 30% 超)が乗る。

これらを、**物理と描画の結果を変えずに**削り、削る過程で責務の置き場を整える。

## 決めたこと

- **物理(`physics/`)の結果は変えない。** 近似を入れる案(遠方天体の省略など)は採らない(CODING-RULE 1.1)。
  積分・接触の高速化は、同じ演算を同じ順で行う書き換え(割り当ての削減・再計算の省略)に限る。
- **絵を変えない。** 地表タイルの LOD 選択、影、天体照は、選ばれるもの・描かれるものを変えない書き換えに限る。
  例外は手順 3 の「表に参照されない層の使用中扱い」(下の「直す挙動」)。
- 効果の大きい順ではなく、**後戻りが安く独立して測れる順**に並べる。各手順の後に同じ条件で計測し直し、
  次の手順の優先度を実測で決め直す。

## 変えない挙動

保存する挙動(SPEC/RENDERING.md の地表・影・天体照、ORBIT/FLIGHT の積分・接触):

- 地表: 同じ投影から選ばれるタイル候補・先読み候補・その優先順、ページ表の中身(層・親層・z・フェード)、
  要求の上限(同時 8・先読み 2)、LRU による回収順。
- 影: スロットの枠・近層/遠層の振り分け・空の texel の深度。
- 天体照: 選ばれる天体とその順、放射輝度・放射照度の値。
- 物理: 同じ入力から同じ状態(ビット一致を目標にする。テスト `npm run test:physics`・`test:game` が通る)。

直す挙動:

- 地表の「使用中の層」を、ページ表を走査して得た層ではなく、表示中のタイルの層と親層の集合で判定する。
  表示中だが細かいタイルに覆われてページ表に現れない層も、回収の対象から外れるようになる(より保守的)。
  回収は可視候補を常に除外しているので、可視の範囲では差が出ない。

## 達成目標

CPU 4 倍減速・1280×720・同じ 9 条件(stage1 戦闘/地図/戦闘×1024/地図×65536、stage00 戦闘、stage3/4 戦闘、
高負荷の戦闘/地図×1024)で:

- stage1 戦闘のフレームの CPU 時間が 27.5ms から 20ms 以下になる。
- 地図(stage1)の地表タイル同期が 1555ms/8s から 300ms/8s 以下になる。
- `writeBuffer` の呼び出し元に `updateAttribute ← Attributes.update`(描画パスごとの再転送)が残らない。
- `npm run typecheck`・`test:render`・`test:physics`・`test:game` が通る。render-lab の撮影が揺らぎ内。

### 手順 5. 遮蔽体の分類をフレームに 1 回へ(ユーザーの承認待ち)

- 目的: ワープ時(地図×65536)の物理の半分(フレームの約 19%)は `SubstepCelestialBodies.beginSubstep` の
  `ShadowCasters.classify` で、全天体(約 100 体)の ECI 状態をサブステップ(最大 64)ごとの新しい基準時刻で
  引いている。重力源の分類と同じくフレームに 1 回へ寄せ、サブステップでは候補の天体だけをその基準時刻で引く。
- 承認が要る理由: フレーム基準で除いた天体が、サブステップ基準の外挿でも影を落とさないことを厳密に示すには、
  2 つの基準時刻からの 2 次外挿の差の上界(天体の加加速度の上界)が要る。上界を「フレームの移動量(drift)を
  2 倍にした余裕」で置くと、外挿そのものが破綻しない範囲(ωΔt ≲ 1)では保守的だが、厳密な保証ではない
  (CODING-RULE 1.1「近似を採用してよいかをユーザーに問う」)。
- 変更が必要な箇所: `src/physics/shadow.ts`(フレーム基準の分類と、サブステップ基準へ候補だけ引き直す口)、
  `src/game/dynamic/substep-celestial-bodies.ts`(resetFrame で分類、beginSubstep で引き直し)。
- 達成条件と検証: `npm run test:physics`・`test:game`。地図×65536 で `classify` が 1354ms/8s から 1/10 以下。

### 手順 6. 残りの候補の結末

- 済み: 地表の常駐の整数索引(1bdf910d5)、大気天体の選択の重複(79fa7a331)。
- 見送り: 線(軌道線・基準線)の焼き直しを同じ入力なら省く案。地図で費用が大きいのは天体の軌道線
  (104ms/8s)と船の軌道線(72ms/8s)だが、どちらも軌道要素とカメラから見た原点が毎フレーム動くので、
  入力がビット一致するのは一時停止中にカメラも止めたときだけ。厳密なキャッシュはほぼ当たらず、緩めれば
  描く頂点が変わる。
- 見送り: 個体ごとの熱の状態を木の全ノードへ配る `syncThermalState`(s1-combat で 0.24ms)。値は熱の
  積分で毎フレーム動き、モデルの木は構築の途中で枝が増えるので、値の一致で省くと新しい枝が古い値のまま残る。
- ユーザーの判断待ち(GPU 側。このマシンでは計測していない): レンズの回折光条(8 腕 × 2 段 × 12 タップを
  半解像度)。`DIFFRACTION_LEVEL` を 1 へ上げると光条が 2 倍太くなる見た目の変更。

## 見積り

- 手順 1: s1-combat で `writeBuffer ← updateAttribute` 604ms/8s = 2.1ms/フレーム(×4 減速)が消える。
  影マップの `_update` 444ms/8s もその内数。→ フレーム 27.5ms から約 2ms 減。
- 手順 2: `FV`(shadowedFraction)self 123ms/8s + 選択の self 61ms/8s ≈ 0.7ms/フレーム(s4)が 1/5 程度に。
- 手順 3: s1-combat 805ms/8s ≈ 3.5ms/フレーム、s1-map 1555ms/8s ≈ 11ms/フレーム(15fps 時)の大半。

## リスクと落とし穴

| リスク | 影響 | 露見する場所 |
| --- | --- | --- |
| `DynamicDrawUsage` を外したあと `needsUpdate` を立てない経路が残る | その個体が動かない・消えない | 手順 1: 弾・破片・閃光・煙・方向マーカー・点群を目で見る |
| WebGL2 経路で `bufferSubData` の更新範囲がずれる | 一部の個体だけ古い位置 | 手順 1: `?renderer=webgl`(あれば)で同じ確認 |
| 日照率の遅延評価で、同点の並び順が全数評価と変わる | 天体照の枠の入れ替わり | 手順 2: 全数評価との一致テストで同点を含める |
| ページ表を差分で組み直すとき、フェード中のタイルの更新が漏れる | 新着タイルがフェードせず現れる/消える | 手順 3: フェードの進行中は毎フレーム組み直す。テストで確かめる |
| 使用中の層の判定を変えて、表示中の層を解放してしまう | GPU 層の二重使用で地表が化ける | 手順 3: `releaseLayer` の使用中検査(throw)が残っていること |
| 計測の揺らぎ(共有 GPU・他エージェント) | 効果の誤読 | 各手順: 同じ条件で A/B を交互に取り、中央値で比べる |
