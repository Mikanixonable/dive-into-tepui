# 仕様不変リファクタリングによる軽量化調査・結論

## この文書の目的

この文書は、`/Users/pandeaconica/lab/dive-into-tepui` の LEO 軌道シューティングゲームについて、ゲーム仕様、物理結果、入力応答、描画の意味を変えずに、リファクタリングだけで CPU 使用量・JavaScript の一時オブジェクト生成量・GC 負荷を減らせる箇所を調査した結果を記録する。

調査基準日は 2026-08-11、基準コミットは `8aee674e876b62a7cccb885c475bfb94dbbbc7cd`（`味方機の方位マーカーを小型三角形に変更`）である。調査対象のソースコードはこのコミット時点の内容である。

現在進行中の計測カウンタ実装には手を入れていない。調査中にソースコードの変更は行っていない。`memos/mikanixonable/dev.md` の既存の作業ツリー変更も変更・復元していない。調査時点で `npm run typecheck` は成功している。

## 「仕様を変えない」の定義

この調査で安全な軽量化とみなすには、次の条件をすべて満たす必要がある。

- 軌道積分の数値式、サブステップ数、積分順序、衝突の解決順序を変更しない。
- `simTime`、`displayTime`、時刻窓、計画軌道のサンプル、衝突地点、近地点・遠地点の結果を変更しない。
- マップ候補、選択可能性、表示・非表示、ラベル、マーカーの順序と位置を変更しない。
- 入力イベントの処理順序、カメラ更新順序、`update()` と `sync()` の境界を変更しない。
- 描画解像度、LOD、更新頻度、天体・オーロラ・マーカーの品質を意図的に下げない。
- キャッシュやオブジェクトプールは、値が変わるべき時に古い値を返さない。キャッシュ無効化条件を明示できないものは安全な候補に分類しない。

したがって、毎フレーム処理を数フレームに一度へ間引く方法、予測積分の予算を減らす方法、物理演算を近似する方法は、この文書の対象外である。

## 現在の処理経路

通常のメインループは次の順序である。

```text
Game.update(dt)
  ├─ 入力処理
  ├─ 物理シミュレーション
  ├─ 予測軌道更新
  ├─ Environment / Plan / MapPicker / Camera の表示用更新
  └─ 戦闘ターゲット更新

AutoSave.update(game)

Game.sync()
  ├─ 表示時刻・表示窓の確定
  ├─ カメラ行列と浮動原点の同期
  ├─ Environment / Entity / OrbitLine の同期
  ├─ 戦闘・マップ・計画・HUD マーカーの同期
  └─ Three.js / DOM / SVG の描画状態更新
```

この構造から、現在の主な軽量化余地は GPU の描画品質ではなく、次の 3 種類に分かれる。

1. 同じフレームで同じ時刻・同じ対象集合を再構築している処理の共有。
2. `filter`、`map`、スプレッド構文、`new Map`、`new Set`、マーカー DOM の一時生成の削減。
3. 結果が変わらない期間に、物理的に不変な情報を再計算しないための明示的なキャッシュ。

## 結論

仕様を変えずに実施できるリファクタリング余地は残っている。特に効果と安全性のバランスがよい順に、次の 5 つが第一候補である。

1. 同一フレームの表示窓・天体スナップショット・合流済み重力源をフレームコンテキストとして共有する。
2. `MapVisibilityPolicy` の判定結果をポリシー単位でメモ化し、`Game` と `EnvironmentScene` で同じポリシーを共有する。
3. `FocusMarkers.update()` と `bodyPickables()` の重複した天体位置・ラグランジュ点計算を一度にする。
4. `PlanPath` の表示座標変換で、同一更新内に固定される un-bake 変換を一度だけ生成する。
5. `PointBody`、`MapPicker`、`MarkerManager`、衝突処理の一時配列・マップ・SVG ノードをプールする。

これらは「処理を省く」のではなく「同じ結果を再利用する」変更であり、計測カウンタが完成するまでに着手できる候補である。

一方、計画軌道の再積分を止める変更は効果が最も大きくなる可能性があるが、現状の `planAttractorProvider` は動的エンティティの将来予測を含む。単純に revision を固定すると、表示中の計画軌道が古い重力源・衝突源を参照する。これは仕様変更ではなく表示物理の破壊になるため、予測の無効化世代を設計してから実装する必要がある。

## 詳細な調査結果

### 1. 表示窓の解決と天体集合のフレーム共有

対象箇所:

- `src/game/game.ts:315-327` — `resolveWindow()` と `currentOrbitPeriod()`。
- `src/game/game.ts:409-558` — `Game.update()`。
- `src/game/game.ts:576-602` — `updateMapPresentation()`。
- `src/game/game.ts:701-850` — `Game.sync()`。

`resolveWindow()` は `displayTimeManager.window()` を呼び、周期の計算のために `ephemeris.attractorsAt(simTime)` と `strongestAttractor()`、`player.orbitalElementsAround()` を実行する。通常のメインループでは、物理積分後の `Game.update()` と直後の `Game.sync()` が同じ `simTime` に対して表示窓を解決している。

また、`updateMapPresentation()` の `:598` と `Game.sync()` の `:717` は、同じ `simTime` に対して `ephemeris.attractorsAt()` と `mergeAttractors()` をそれぞれ実行している。`Ephemeris.attractorsAt()` 自体は内部キャッシュを持つが、`mergeAttractors()` の合流配列は呼び出しごとに作られる。

安全な方針は、`resolveWindow()` を無条件に削除することではない。`Game.update()` と `Game.sync()` が個別に呼ばれる経路を壊さないため、次のようなフレーム状態を設けるべきである。

```ts
interface FrameDisplayContext {
  readonly stateRevision: number;
  readonly simTime: number;
  readonly displayTime: number;
  readonly window: DisplayWindow;
  readonly simAttractors: readonly Attractor[];
  readonly mergedAttractors: readonly Attractor[];
}
```

`stateRevision` は物理積分、セーブ復元、プレイヤー差し替え、エンティティ追加・削除など、表示窓と合流済み集合を無効化する操作で増やす。`sync()` は同じ revision のコンテキストを再利用し、単独呼び出し時だけ再構築する。この仕組みなら、通常フレームの重複計算を除去しつつ、フレーム外の状態変更を古い表示へ固定しない。

ただし、`displayAttractors = ephemeris.attractorsAt(displayTime)` と `simAttractors` は別の時刻のスナップショットである。両者を同一配列として扱ってはならない。

### 2. マップ可視性判定の再利用

対象箇所:

- `src/game/celestial/map-visibility.ts:49-110` — `MapVisibilityPolicy`。
- `src/game/game.ts:725-732,753-779` — エンティティごとの判定。
- `src/game/celestial/environment-scene.ts:132-160,183` — 環境描画側の判定。

`MapVisibilityPolicy.body(id)` と `MapVisibilityPolicy.entity(kind, isActive)` は、同一ポリシーの寿命中は同じ引数に対して同じ不変結果を返す。しかし現在は呼び出しのたびに可視性オブジェクトを構築している。`Game.sync()` ではプレイヤー、敵、弾、基地、軌道線のループから同じ判定を何度も呼んでいる。

ポリシー生成時に次のキャッシュを持たせる変更は安全性が高い。

- 天体 ID ごとの `MapVisibility` キャッシュ。
- `player` / `ship` / `ammo` / `base` と active フラグの組み合わせごとの固定キャッシュ。
- `bodyClassOf()` のようなレジストリ由来の分類結果のポリシー内キャッシュ。

ポリシーは toggles、focus、nearby system の集合を受け取って生成されるため、ポリシー自体をフレーム間で雑に共有してはならない。キャッシュの寿命は一つのポリシーの中に限定する。

`EnvironmentScene.sync()` は、`Game.sync()` が既に作った `MapVisibilityPolicy` と同じ条件で別のポリシーを作り、`systemMembersAt()` も再度実行している。`EnvironmentScene.sync()` に既存ポリシーを渡し、参照線同期へ同じポリシーを引き回せば、表示順序を変えずにこの重複を除去できる。

### 3. FocusMarkers と MapPicker の重複

対象箇所:

- `src/game/camera/focus-markers.ts:120-193`。
- `src/game/map-picker.ts:107-179`。

`FocusMarkers.update()` は、天体スナップショット、系の所属集合、天体の表示位置、ラグランジュ点位置を計算する。その直後に `MapPicker.refresh()` が `FocusMarkers.bodyPickables()` を呼ぶため、`bodyPickables()` は天体スナップショット、天体位置マップ、ラグランジュ点位置を再び構築している。

この重複はマップ表示時に毎フレーム発生する。安全な変更は次のとおりである。

- `FocusMarkers.update()` の結果として得られた天体表示位置とラグランジュ点位置を保持する。
- `bodyPickables()` は保持済みの位置・ラベル・IDを読み、渡された可視性ポリシーだけを適用する。
- `MapPicker.refresh()` の呼び出し順序と、更新時点のカメラ位置を変更しない。

`MapPicker.refresh()` はカメラ更新前の `activeCameraPos` を使う経路があるため、単純に `FocusMarkers.update()` を `cameraSystem.update()` の後へ移動してはならない。重複計算だけを共有し、現在の時刻とカメラ更新順序は維持する必要がある。

`MapPicker.refresh()` 自体も、全候補について `{ ...item, detail, distance, inFocusedSystem }` を作り、最後に `filter()` で別配列を作っている。内部の候補レコードを ID 単位で再利用し、公開される `this.items` の順序と内容だけを同じにする実装が可能である。候補を外部へ渡した後に再利用オブジェクトを変更しない設計、または refresh の終了までに消費されることを保証する設計が必要である。

### 4. PlanPath の表示変換キャッシュ

対象箇所:

- `src/game/plan/plan-path.ts:169-195` — `toDisplay()`、`toDisplayDir()`、`toDisplayTangent()`。
- `src/game/plan/plan-path.ts:211-225` — `nearestSample()`。

一つの `PlanPath.update()` から次の update まで、`frame`、`unbakeTime`、`attractors` は同じ表示文脈を表す。ところが `toDisplay()`、`toDisplayDir()`、`toDisplayTangent()` は、各呼び出しのたびに同じ `frameTransformAt(frame, unbakeTime, attractors)` を生成している。

`nearestSample()` では既に un-bake 側の変換をループ外で一度だけ生成している。この考え方を `PlanPath` 全体へ適用し、`update()` 時に un-bake 変換を保持するか、`frame`・`unbakeTime`・`attractors` の変更時だけ再生成すれば、変換結果を変えずに一時オブジェクトを削減できる。

サンプル時刻 `t` ごとの bake 変換はサンプルごとに異なるため、全サンプルで共有してはならない。共有できるのは表示時刻側の un-bake 変換だけである。

### 5. PlanArc の再積分は大きな候補だが、単純なキャッシュ化は禁止

対象箇所:

- `src/game/plan/plan-arc.ts:169-207` — キャッシュキーと source revision。
- `src/game/plan/plan-arc.ts:263-340` — 軌道積分。
- `src/game/simulation/attractors.ts:34-93` — 計画用重力源・衝突源プロバイダ。
- `src/game/game.ts:580-585` — `planAttractorProvider()` の revision 引数。

現在、`Game.updateMapPresentation()` は `planAttractorProvider()` へ `simTime` を revision として渡している。`PlanArc` のキャッシュキーは provider の revision を比較するため、計画ノードが存在する場合でも simTime の進行ごとに再積分される構造になっている。

しかし、provider は解析天体だけでなく、動的エンティティの将来 `displayState(t)`、衝突候補、重力を持つエンティティを含む。`simTime` だけを固定したり、ノード編集以外の revision を無視したりすると、次の状態変化を計画軌道へ反映できない。

- 弾・敵・小惑星などの動的予測が無効化された。
- 予測軌道のカバレッジが計画区間の終端まで延長された。
- エンティティが追加・削除・死亡した。
- 現在の計画、アンカー、表示期間、重力源の状態が変更された。

根本的な解決には、単一の時刻値ではなく、計画軌道が依存する将来情報の世代を revision として持たせる必要がある。例えば「依存する各動的ソースの予測世代」「必要な終端時刻までの予測カバレッジ」「計画ノード世代」を組み合わせた semantic source signature を用いる。必要な範囲が変わっていない arc だけを再利用し、範囲不足または世代変更時だけ再積分する設計にする。

この修正は効果が大きい可能性があるが、計測カウンタと固定入力での結果比較を先に用意するべきである。`PlanArc` の revision を機械的に固定する変更は実施してはならない。

### 6. PointBody の同一値再計算

対象箇所:

- `src/game/celestial/point-body.ts:93-185`。

`PointBody.sync()` の戦闘表示分岐では、同じ `pos` と `displayTime` に対して `ephemeris.sunDirFrom()` を複数回呼んでいる。ローカル変数 `sunDirection` を combat 分岐でも使用すれば、結果を変えずに同一計算を削減できる。

また、環を持つ天体の `outerRadius` は `rings.bands.reduce()` で求めているが、環の帯定義は `PointBody` の寿命中に変わらない。構築時に最大外径を確定して保持すれば、毎フレームの走査を除去できる。

この 2 件はキャッシュ無効化の難しさがほとんどなく、計測カウンタ完成前に実施できる最も安全な小規模候補である。

### 7. Ship のパーツ getter

対象箇所:

- `src/game/game-entity/ship.ts:201-289`。
- `src/game/player/player.ts:192-236`、および推力・トルク・発射・環境更新の呼び出し側。

`totalTorque`、`totalThrust`、`totalFuelConsumptionRate`、`totalCoolingRate`、`totalPowerGeneration`、`aliveWeapons`、`radiatorParts`、`solarParts` は、少数のパーツ配列に対して毎回 `filter()` と `reduce()` を行う。`radiatorParts` と `solarParts` は構成が変わらない限り同じ 2 要素を返すにもかかわらず、getter 呼び出しごとに配列を作っている。

安全な段階的方針は次のとおりである。

1. 放熱板・太陽電池・武器・推力部品の参照を構成変更時だけ作る。
2. 構成が固定された部品の「全量」値は直接参照する。
3. HP に依存する値は、`applyDamageToParts()`、`restoreOverallHp()`、`selfRepair()`、`refreshFromParts()`、ドック修理など、HP を変更する全経路で invalidation する。
4. 燃料値はフレーム中に変化するため、燃料合計をキャッシュする場合は `consumeFuel()` と復元処理を含む全変更経路で差分更新する。難しい場合は getter の配列生成だけを除去し、直接ループへ置き換える。

この箇所は物理計算に近いため、キャッシュ不備が戦闘結果へ直結する。最初の実装では、数値キャッシュよりも「固定参照の再利用」と「同じ filter をしない直接ループ」を優先するべきである。

### 8. MarkerManager と FocusMarkers の一時構造

対象箇所:

- `src/game/marker/marker-manager.ts:196-326`。
- `src/game/camera/focus-markers.ts:197-250`。

`MarkerManager.resolveCollisions()` は、毎フレーム active 配列を作り、5 回の衝突解決反復ごとにグリッド用 `Map<string, number[]>` と候補配列を再構築する。`FocusMarkers.syncLabels()` も投影配列、非表示集合、セルマップ、表示 ID 集合を毎フレーム作る。

衝突回数 5 回、候補の走査順、同距離時の sort、画面上の最終表示順を維持したまま、次の scratch 領域だけをインスタンス内で再利用できる。

- active レコード配列。
- セル `Map` とセル内インデックス配列。
- 候補インデックス配列。
- 反復ごとの temporary Set。
- SVG の `<line>` ノード。

SVG ノードの再利用は GC 削減が見込めるが、`innerHTML` を毎フレーム消去する現在の処理と DOM ノードの所有関係が変わるため、マーカー数が増減するケース、非表示化、古い属性のリセットを確認してから実装する。数値結果を変えない一方、実装規模は小さくないため、計測カウンタ完成後に優先度を決める。

### 9. 衝突処理の scratch 再利用

対象箇所:

- `src/game/simulation/contact.ts:114-181`。
- `src/game/simulation/simulator.ts:79-96`。

接触解決は substep ごとに対象配列、`Set`、作業 `Map`、`SpatialGrid` を生成する。これはマップ描画専用ではないが、物理更新時間と GC の両方に影響する。

`SpatialGrid.neighborsInto()` が既に出力配列を受け取れる構造を持っているため、接触処理側の配列・集合・グリッドを simulator または contact resolver の寿命に持ち上げ、呼び出しごとに `length = 0` または `clear()` する方向が適している。

ただし、衝突のペア解決順と `changed` 判定のタイミングを保持する必要がある。`Set` の代替としてソート済み配列を使う、ペアキーの表現を変える、グリッドの走査順を変えると、衝突後の状態が変わる可能性があるため、最初の変更では行わない。

## すぐに実施できる候補と、計測後に実施する候補

### 計測カウンタ完成前に実施できる候補

次の候補は、値の再利用範囲を局所化でき、仕様差分の検証もしやすい。

- `PointBody` の `sunDirFrom()` 重複呼び出し削減。
- `PointBody` の環外径を構築時に確定。
- `MapVisibilityPolicy` のポリシー内結果キャッシュ。
- `FocusMarkers.update()` と `bodyPickables()` の計算結果共有。
- `PlanPath` の un-bake 変換キャッシュ。
- `Game.sync()` 内の `getCombatTargets()` と alive target 配列の一フレーム共有。
- `MapPicker` の候補レコード・可視候補配列の再利用。
- `Game` と `EnvironmentScene` 間の同一可視性ポリシー共有。
- `EquatorNodeMarkers.mapPickables()` の固定ペアに対する flat 配列再利用。

### 計測カウンタ完成後に実施する候補

次の候補は効果が期待できるが、実行頻度・メモリ保持量・無効化条件を計測してから着手する。

- `MarkerManager` の衝突 scratch と SVG ノードプール。
- `FocusMarkers.syncLabels()` の投影・セル scratch プール。
- contact resolver の `Map`、`Set`、`SpatialGrid` の再利用。
- Ship の HP 依存性能値の世代キャッシュ。
- PlanArc の semantic source signature に基づく再積分抑制。

## 最初の実装単位としての推奨方針

一度に全箇所を変更せず、次の順で小さい変更を積み上げるべきである。

1. `PointBody` の同一値再利用を実装する。
2. `MapVisibilityPolicy` のポリシー内キャッシュを実装する。
3. `FocusMarkers` の更新結果を `bodyPickables` が再利用するようにする。
4. `PlanPath` の un-bake 変換を保持する。
5. フレームコンテキストを導入し、`resolveWindow()` と合流済み attractor 配列を update/sync 間で共有する。
6. カウンタでマーカー・衝突・Ship getter の時間を確認し、必要な領域だけプール化する。
7. 最後に、予測世代を設計してから PlanArc の再積分キャッシュを見直す。

フレームコンテキストは、最初から `MapVisibilityPolicy` やカメラ位置まで一つに統合しない。`MapPicker.refresh()` がカメラ更新前の位置を使う現在の順序を維持するため、次の情報を分離する必要がある。

- update フェーズで確定する時刻窓、simTime の天体、合流済み重力源。
- displayTime に基づく天体スナップショット。
- cameraSystem.update() 前の MapPicker 用視点。
- cameraSystem.sync() 後の描画・Environment 用視点。

## 変更してはいけない候補

今回の「仕様を変えない」という条件では、次の施策を軽量化として採用しない。

- `Earth.tick()`、オーロラ、点群、マーカーの更新頻度を下げる。
- `PlanArc` の再積分を revision 設計なしに止める。
- Predictor の予測期間・ステップ数・サンプル数を減らす。
- Simulator のサブステップ数や接触判定を減らす。
- Three.js の解像度、DPR、ジオメトリ解像度、LOD、透明オブジェクト数を下げる。
- 物理計算を scalar 化して演算順序を変える。
- マップの `refresh()` や `sync()` を時間間引きする。

これらは軽量化効果があっても、表示品質、入力応答、物理精度、衝突結果のいずれかを変える可能性がある。仕様不変リファクタリングの範囲では採用しない。

## 検証方法

各変更は、コードレビューだけで完了扱いにせず、同一入力による旧実装・新実装の結果比較を行う。

最低限、次の比較対象を固定する。

- `simTime`、`displayTime`、`DisplayWindow` の全フィールド。
- プレイヤー・敵・弾・基地の状態、軌道要素、alive 状態。
- マップ候補の ID、種別、並び順、`pickable`、`category`、`orbit`、距離。
- 天体・ラグランジュ点・エンティティの表示位置と可視性。
- 計画軌道のサンプル数、サンプル時刻、衝突地点、近地点、遠地点。
- マーカーの ID、表示文字列、画面位置、衝突後のグループ構成。
- 勝敗、発射、接触、ドッキング、セーブ・ロードのイベント列。

検証コマンドは次のとおりである。

```text
npm run typecheck
npm run build
```

このリポジトリには npm 経由で実行される自動テストスイートがないため、純粋な物理関数の既存テスト・Node 実行可能な検証と、固定入力を使ったブラウザ再生を組み合わせる必要がある。特に pooling を導入した場合は、フレームをまたいで参照を保持する呼び出し元がないこと、`clear()` 漏れで前フレームの ID・属性・候補が残らないことを確認する。

## 最終判断

計測カウンタ完成前に進めるべき作業は存在する。最初に行うべきなのは、表示品質や更新頻度を下げることではなく、同一フレームの入力を「時刻・天体集合・可視性ポリシー・表示変換」という不変文脈にまとめ、各消費者がそれを再利用する設計へ整理することである。

最も根本的な設計課題は、`Game.update()` と `Game.sync()` が同一フレームの文脈を個別に再構築していること、`FocusMarkers` と `MapPicker` が同じ天体情報を二重に作っていること、`PlanArc` の再積分キャッシュが `simTime` を粗い revision として使っていることである。

このうち、前二者は仕様を変えずに安全に解消できる。PlanArc は、動的予測の世代とカバレッジを表す revision を新設してから解消すべきである。計測カウンタが完成した後は、上記の順序で各領域の実時間と allocation/GC の寄与を確認し、効果のないプール化や広範なキャッシュを追加しないことが、保守性と根本解決を両立する方針となる。
