# 推進系・船体設計・多段化・ドッキング・月面・資源経済 — 実装計画 第二版

この文書は、以下の7つの機能群をこのリポジトリに追加するための計画である。各節は単独で読めるように、前提と用語をその節の中で定義する。

1. 艦艇・軌道基地・月面基地を単一のエンティティ `Vessel` に統合する（§2）
2. 主機・並進RCS・フライホイールを分離した推進系（§3）
3. ドッキングポートによる結合と、結合後の位相調整・推進剤移送・電力統合（§4）
4. ノードとエッジの骨格から外皮を生成する船体設計（§5）
5. 多段ブースターシステム（§6）
6. 推進剤の種別と実データに基づく性能（§7）
7. 月の地形・着陸と、月面から軌道基地への物資輸送を含む資源経済（§8）

---

## 1. 設計判断と根拠

実装に入る前に確定させておく判断を先に置く。以降の節はすべてこの判断の上に立つ。

### 1-1. 実体は `Vessel` 一種類のみとする

艦艇・軌道基地・月面基地は、いずれも「骨格の上に部品が載った物体」であり、物理的な差は積んでいる部品だけである。したがってエンティティのクラスを分けない。

- **軌道基地** = 基地モジュール部品（格納庫・倉庫・生産設備）を積んだ `Vessel`。
- **月面基地** = 固定脚部品を積み、エンジンを積まない `Vessel`。
- **艦艇** = コックピット部品とエンジンを積んだ `Vessel`。

「これは基地か」「これは船か」という判定は存在せず、代わりに部品の有無から導かれる能力（`hasCockpit` / `hasBaseModule` / `hasLandingGear` / `hasEngine`）だけを問う。基地が推進剤を積んで軌道を変えることも、月面基地にエンジンを付けて飛ばすことも、部品を足せば自然に可能になる。

### 1-2. ドッキングはポート同士の結合として実装する

ドッキングは「一定距離内で相対速度が小さい」という領域判定ではなく、**双方のドッキングポートの位置・向き・相対速度・相対角速度がすべて捕獲条件を満たすこと**として判定する。ポートは部品であり、船体ローカル座標上の位置・軸・基準ロール方向を持つ。

結合した2機は1つの剛体として積分され、結合後は位相角（ポート軸まわりの相対ロール）を任意に変えられ、推進剤とRCSガスを移送でき、電力は結合体全体で1つの収支として計算される。

### 1-3. 物資輸送はプレイヤーが船で行う

月面基地から軌道基地への物資の移動は、自動キューではなく、プレイヤーが貨物区画を持つ `Vessel` に積み込み、月面から離陸し、軌道基地にドッキングし、移送する、という一連の操作として行う。輸送そのものが遊びの対象になる。

### 1-4. 月は地形を持ち、着陸できる

月の表面は球ではなく高度場（ハイトフィールド）を持つ。着陸判定は固定脚の接地点と地形の接触で行い、接地時の垂直速度・水平速度・傾斜がすべて許容範囲内であれば着陸成功、外れれば損傷または破壊とする。着陸した機体は月の自転座標系に静止する。

### 1-5. 物理量は形状から導出する

質量・重心・慣性テンソル・断面積は定数として持たず、骨格と搭載物から毎回導出する。これにより、扁平な機体は本当に回りにくく、非対称な機体は本当に重心がずれる。

### 1-6. 推進剤は登録されたペアからのみ選ぶ

比推力は実測値であり、任意の酸化剤と還元剤の組み合わせに対して定義できない。したがって推進剤は「酸化剤と還元剤のペア」「単推進剤」「固体グレイン」「ハイブリッドの組」として表に登録されたものからのみ選ぶ。表は §7-1 に置く。

## 2. `Vessel` — 単一の実体

### 2-1. クラス構成

```
GameEntity
  └─ Vessel            … 骨格・部品・推進剤・電力・熱を持つ唯一の実体クラス
```

`Vessel` が持つもの:

| フィールド | 内容 |
|---|---|
| `assembly: VesselAssembly` | 骨格（§5）と、その上に配置された部品の集合 |
| `massProperties: MassProperties` | 乾燥質量・搭載物質量・重心・慣性テンソル。`assembly` と推進剤残量から導出し、変化時のみ再計算 |
| `propellant: PropellantStore` | 推進剤の種別ごとの残量。タンク部品の集合から容量が決まる |
| `power: PowerSystem` | 発電・蓄電・消費。結合時は結合体で統合（§4-5） |
| `thermal: ThermalSystem` | 熱収支 |
| `propulsion: PropulsionSystem` | 主機・並進RCS・フライホイール（§3） |
| `attitudeControl: AttitudeControlSystem` | 姿勢トルクの配分（§3-2） |
| `docking: DockingState` | ポートの状態と、結合しているクラスタへの参照（§4） |
| `landing: LandingState \| null` | 固定脚を持つ場合の接地状態（§8-3） |
| `plan: Plan` / `planExecutor: PlanExecutor` | 軌道計画とその自動実行 |
| `parts: AnyPart[]` | 部品。HP と性能の唯一の源 |

### 2-2. 能力は部品から導く

```ts
// src/game/vessel/capabilities.ts
export function hasCockpit(v: Vessel): boolean;      // 人が操作できる
export function hasGuidance(v: Vessel): boolean;     // 無人で計画を実行できる
export function hasBaseModule(v: Vessel): boolean;   // 格納・倉庫・生産ができる
export function hasLandingGear(v: Vessel): boolean;  // 接地できる
export function hasEngine(v: Vessel): boolean;       // 主機を持つ
export function isOperable(v: Vessel): boolean;      // hasCockpit || hasGuidance
```

操作対象に選べるのは `isOperable` を満たす機体である。基地ビュー（格納・倉庫・生産・市場）を開けるのは `hasBaseModule` を満たす機体、またはそれに結合している機体である。

### 2-3. 部品の種別

```ts
export type PartType =
  | 'structure'        // 骨格エッジに対応する構造材
  | 'cockpit'          // 有人操作
  | 'guidance'         // 無人誘導（計画の自動実行）
  | 'armor'            // 被弾軽減
  | 'shield'           // 可動遮蔽（日除け・被弾遮蔽）
  | 'engine'           // 主機
  | 'rcs_thruster'     // 並進RCS・姿勢RCS
  | 'reaction_wheel'   // フライホイール
  | 'tank'             // 推進剤タンク（推進剤種別ごとに適合が決まる）
  | 'solid_motor'      // 固体モーター（ケースが構造を兼ねる）
  | 'decoupler'        // 分離機構
  | 'docking_port'     // ドッキングポート
  | 'radiator'
  | 'solar_panel'
  | 'battery'
  | 'weapon'
  | 'cargo_hold'       // 貨物区画（資源・部品を運ぶ）
  | 'base_module'      // 格納庫・倉庫・生産設備
  | 'landing_gear'     // 固定脚
  | 'production'       // 採掘機・電解装置・精錬炉などの生産設備
```

各部品は共通に `id` / `type` / `name` / `dryMass` / `maxHp` / `hp` を持ち、種別ごとの性能値を追加する。機体の総合HPは全部品のHPの和であり、コックピットまたは主要構造が失われた時点で0とする。

### 2-4. 状態の所有

`Vessel` の集合を持つのは `EntityManager` であり、`vessels: Vessel[]` という単一の配列にする。操作対象は `ActivePlayerController` が `Vessel | null` として保持する。ドッキングして格納された機体は `EntityManager` の配列から外され、格納先の `Vessel` の基地モジュール部品が保持する。

## 3. 推進系 — 主機・並進RCS・フライホイール

### 3-1. 3つのシステムの役割

| システム | 役割 | 推進剤 | 比推力 | 特性 |
|---|---|---|---|---|
| **主機（EngineBank）** | 軌道変更のための大きな Δv | 液体・固体・ハイブリッド | 265〜450 s | 推力大。始動と停止にコストがある。固体は停止も再着火もできない |
| **並進RCS（TranslationRcs）** | 近接機動・ドッキング・姿勢制御の補助 | 単推進剤または冷ガス | 70〜230 s | 推力小。船体6方向すべてに出せる。応答は即時 |
| **フライホイール（ReactionWheels）** | 姿勢制御のみ | 消費しない（電力のみ） | — | トルク小・連続。**角運動量が飽和する** |

### 3-2. 姿勢トルクの配分

姿勢トルクを要求する主体は、手動操作（`PlayerThrottle`）と自動操縦（`PlanExecutor`）の2つである。両者は `AttitudeControlSystem` に要求を出し、実際にどのアクチュエータが出すかはそこが決める。

配分の規則:

1. 要求トルク τ のうち、各軸でフライホイールが出せるぶんを出す。出せる条件は、そのホイールの最大トルクを超えないことと、蓄積角運動量 `h` が上限 `hMax` に達していないことの両方である。
2. ホイールが τ_wheel を出すと、反作用として角運動量が `h += -τ_wheel · dt` だけ溜まる。同時に電力を消費し、`PowerSystem` から引く。
3. ホイールで出せなかったぶん、および飽和した軸は、RCSスラスタが出す。RCSは推進剤を消費する。
4. `|h|` が `hMax` の既定割合（アンローディング閾値）を超えると、**アンローディング**を行う。RCSで外部トルクを与えながらホイールを減速し、`h` を外部に捨てる。自動実行を既定とし、手動実行のボタンをHUDに置く。

この規則により、静穏時は推進剤を消費せずに姿勢を保ち、激しい機動の後は必ずRCS推進剤を消費する、という往復が生まれる。RCS残量が戦闘の資源になる。

### 3-3. 並進推力の選択

並進の要求推力に対して、主機とRCSのどちらを使うかは以下で決める。

- 要求が主機の推力軸と一致し、かつ要求の大きさが RCS の最大推力を超える場合は主機を使う。
- それ以外はRCSを使う。
- プレイヤーは HUD で「主機を使わない」「主機のみ」を明示的に選べる。ドッキング中は既定で主機を禁止する。

### 3-4. モジュール

```
src/physics/attitude-control.ts        (純関数)
    allocateTorque(request, wheelState, wheelSpec, rcsSpec) -> {wheel, rcs, powerDraw}
    desaturationTorque(h, hMax, spec) -> Vec3
src/game/vessel/attitude-control-system.ts
    ホイールの蓄積角運動量 h を保持し、上の純関数を毎 update で呼ぶ。
    姿勢トルク要求の唯一の窓口。
src/game/vessel/propulsion-system.ts
    主機・RCS の推力合計、推進剤消費、比推力の解決。
```

検証は `tests/physics/attitude-control.test.ts` に置き、角運動量の収支が閉じること、飽和境界での配分が連続であること、アンローディングのトルク方向が `h` を減らす向きであることを固定する。

## 4. ドッキング

### 4-1. ドッキングポート

```ts
// src/game/game-entity/parts.ts
export interface DockingPortPart extends Part {
  readonly type: 'docking_port';
  readonly portClass: 'small' | 'medium' | 'large'; // 同一クラス同士のみ結合できる
  readonly androgynous: boolean;                    // false の場合 probe と drogue の対でのみ結合
  readonly role: 'probe' | 'drogue' | 'both';
  readonly localPos: Vec3;      // 船体ローカル座標のポート面中心
  readonly localAxis: Vec3;     // ポート面の外向き法線（船体ローカル）
  readonly localRollRef: Vec3;  // 位相角0を定義する基準方向（localAxis に直交）
  readonly transferRate: number; // 推進剤移送速度 [kg/s]
  readonly powerBridge: boolean; // 電力を橋渡しするか
}
```

### 4-2. 捕獲条件

2つのポート A・B が以下をすべて満たすとき、捕獲（ソフトドック）が成立する。値は `const.ts` に置く。

| 条件 | 内容 |
|---|---|
| 適合 | `portClass` が一致し、`androgynous` 同士、または `probe` と `drogue` の対である |
| 軸方向距離 | ポート面中心間の距離が捕獲距離以内 |
| 横方向ずれ | A の軸に投影したときの横方向オフセットが許容半径以内 |
| 軸の対向 | A の軸と B の軸のなす角が 180° から許容角度以内（正面から向き合っている） |
| 相対速度 | 接近速度が最小値以上・最大値以下（速すぎれば損傷、遅すぎればラッチが噛まない） |
| 横方向相対速度 | 許容値以下 |
| 相対角速度 | 許容値以下 |

捕獲が成立すると、ポート面同士を厳密に一致させる位置・姿勢へ両機を補正し、ハードドックへ移行する。補正は運動量と角運動量を保存する形で行い、余剰は減衰として捨てる（ラッチの吸収に相当）。

条件を満たさずに接触した場合は、既存の剛体接触として処理する（跳ね返り、および相対速度に応じた損傷）。

### 4-3. 結合体（クラスタ）

結合した複数の `Vessel` は、**1つの剛体として積分される**。

```ts
// src/game/vessel/docking-cluster.ts
export interface DockingCluster {
  readonly id: string;
  readonly members: readonly Vessel[];   // 結合している全機体
  readonly root: Vessel;                 // 積分の主体。KinematicState と Attitude を持つ
  readonly joints: readonly DockingJoint[]; // ポート対と位相角
}
export interface DockingJoint {
  readonly portA: { vesselId: string; partId: string };
  readonly portB: { vesselId: string; partId: string };
  phaseAngle: number; // ポート軸まわりの相対ロール [rad]
}
```

- 積分は `root` の `KinematicState` と `Attitude` に対してのみ行う。他の構成機体の位置・姿勢は、ジョイントの連鎖から毎フレーム導出する。
- クラスタの質量・重心・慣性テンソルは、全構成機体の `MassProperties` を平行軸定理で合成して求める。推進剤が減れば変わるので、変化時に再計算する。
- クラスタの主機・RCS・フライホイールは、全構成機体のものの合計として扱う。ただし主機の推力軸がクラスタ重心を外れる場合は、そのぶんのトルクが実際に発生する。
- 接触判定において、同一クラスタの構成機体同士は接触しない。

### 4-4. 位相角の調整

ジョイントの `phaseAngle` を連続的に変えられる。これはポート軸まわりに片側を回すことに相当し、機体全体の姿勢を変えずに構成機体の相対的な向きだけを変える。

- 回転速度は上限を持ち、電力を消費する。
- 回転させると結合体の慣性テンソルが変わるため、角運動量保存により全体の角速度が変化する。この効果は正しく計算する（ホイールと同じ内部トルクの一種として扱う）。
- 用途は、ソーラーパネルを太陽に向ける、ラジエータを日陰に入れる、武装の射界を確保する、着陸脚の向きを揃える、など。

### 4-5. 推進剤・RCSガスの移送と電力統合

**移送** — `powerBridge` を持つジョイントで結ばれた機体の間で、推進剤を移送できる。

- 移送できるのは、送り側のタンクと受け側のタンクが同じ推進剤種別に適合している場合のみ。極低温と常温貯蔵性の推進剤は互いに移送できない。
- 移送速度は両ポートの `transferRate` の小さいほうで律速する。
- 移送中は電力を消費する（ポンプ）。
- 移送に伴って両機の質量と重心が変わるため、`MassProperties` を更新する。クラスタ全体の重心は移動しないが、慣性テンソルは変わる。

**電力統合** — クラスタは1つの `PowerSystem` として計算する。発電量は全構成機体のソーラーパネルの合計（それぞれの向きと日照を個別に評価したうえで合計）、蓄電容量はバッテリーの合計、消費は全構成機体の合計とする。クラスタ内で電力の不足が生じた場合は、優先度の低い消費（生産設備、位相角の回転）から順に停止する。

### 4-6. 分離

ドッキングの解除は、ジョイントを取り除いてクラスタを分割することである。分割後は、分かれた側それぞれが独立した `KinematicState` を持ち、運動量と角運動量が保存されるように速度と角速度を分配する。解除時に小さな分離速度を与える。

## 5. 骨格式の船体設計

### 5-1. 骨格

機体の形は、ノードとエッジからなるグラフで定義する。

```ts
// src/game/vessel/skeleton.ts
export interface SkeletonNode {
  readonly id: string;
  readonly pos: Vec3;  // 船体ローカル座標 [m]
}
export type EdgeKind =
  | { kind: 'hull'; radius: number }                  // 外皮を作る。内側が内容積になる
  | { kind: 'strut' }                                 // 外皮を作らない構造材
  | { kind: 'decoupler'; separationImpulse: number }; // 外皮を作らず、切り離せる
export interface SkeletonEdge {
  readonly id: string;
  readonly a: string;
  readonly b: string;
  readonly kind: EdgeKind;
}
export interface VesselSkeleton {
  readonly nodes: readonly SkeletonNode[];
  readonly edges: readonly SkeletonEdge[];
}
```

- グラフは閉路を含んでよい。三角形やはしご状に組めば扁平な機体になる。
- エッジの長さは 0.5 m 刻み、ノードから伸びる方向は 15° グリッドにスナップする。連続値にすると対称な機体を作るのが困難になるため、量子化する。
- YZ平面のミラー編集を持つ。片側を編集すると反対側に同じ構造が生える。ミラーを明示的に切ったときのみ非対称な機体を作れる。

### 5-2. 外皮

外皮は、`hull` エッジそれぞれを半径 `radius` のカプセル（円柱と両端の半球）とし、その和集合として定義する。エッジ1本だけの骨格は、円筒に半球端を付けた形すなわちロケット形になる。

外皮から次の量を導出する。すべて解析式で求まるため、数値積分は行わない。

| 量 | 用途 | 求め方 |
|---|---|---|
| 内容積 V | タンク容量の上限 | カプセルの体積の和から、ノードでの重複を球1個ぶん差し引く |
| 表面積 S | 放熱面積の上限、被弾面積 | カプセル側面積の和から重複を差し引く |
| 重心 | 推力軸のずれ、回転中心 | 構造質量と搭載物の配置座標から |
| 慣性テンソル I | 姿勢運動 | 各カプセルの慣性テンソルを平行軸定理で合成 |
| 参照断面積 A | 抗力係数 `bcInv = Cd·A/m` | 主軸3方向の投影面積のうち最大値 |

```
src/physics/hull-solid.ts   (純関数)
    capsuleUnionVolume(edges)
    capsuleUnionSurfaceArea(edges)
    capsuleUnionInertia(edges, density)
    capsuleUnionCenterOfMass(edges, density)
    capsuleUnionProjectedArea(edges, axis)
```

検証は `tests/physics/hull-solid.test.ts` に置く。単一カプセルが解析値と一致すること、同一位置に重ねた2本が1本ぶんになること、L字形の慣性主軸が3値とも異なること（すなわちジャニベコフ効果が発生する形状であること）を固定する。

### 5-3. 内容積の割り当て

プレイヤーは、各 `hull` エッジの内容積に何を入れるかを指定する。そのエッジのカプセル体積が上限である。

- 極低温タンク（液体水素・液体酸素・液体メタン）は断熱材のぶん実効容積が 0.85 倍になる。
- 常温貯蔵タンク（ヒドラジン・四酸化二窒素・過酸化水素）は 0.95 倍。
- 高圧ガスタンク（冷ガス）は容器の肉厚のぶん 0.70 倍。
- 固体モーターはタンクではなくエッジそのものであり、ケースが構造材を兼ねる。したがって固体ブースターは外皮エッジ1本がモーター1基に対応する。
- 貨物区画は容積と最大積載質量の両方で制限される。

液体推進剤を使うエンジンを持つ区画には、外部配管を自動生成して外観に反映する。プレイヤーは配管を配置しない。

### 5-4. 描画

```
src/render/hull/hull-mesh.ts
    buildHullMesh(edges, lod) -> THREE.BufferGeometry
```

カプセルごとのメッシュを生成して結合し、ノード位置に球を置いて接合部を埋める方式とする。生成は設計が変わったときに1度だけ行い、結果を保持する。毎フレームの生成は行わない。遠距離では単一カプセルの近似に落とす。

`WebGPURenderer` は `Mesh` のジオメトリを最初の描画時にキャッシュするため、生成済みメッシュのジオメトリを差し替えてはならない。設計変更時は `Mesh` ごと作り直す。

## 6. 多段ブースターシステム

### 6-1. ステージの定義

ステージは、骨格グラフから `decoupler` エッジを取り除いたときの連結成分である。プレイヤーがステージを明示的に区切る操作は存在せず、デカプラを挿すと自動的に分かれる。

```ts
// src/game/vessel/assembly.ts
export interface VesselStage {
  readonly id: string;
  readonly edgeIds: readonly string[];
  readonly hasCockpit: boolean;
  readonly hasGuidance: boolean;
}
export function splitStages(skeleton: VesselSkeleton, parts: readonly AnyPart[]): readonly VesselStage[];
```

コックピットまたは誘導装置を含むステージは、分離後も操作または自動制御の対象になる。どちらも含まないステージは、分離後は制御不能な物体として軌道上に残る。

### 6-2. 分離の物理

分離は運動量保存を満たすように行う。分離前の質量を `m_total`、分かれる2つを `m_a` / `m_b`、デカプラの分離力積から求まる相対速度増分を `Δv_sep` とすると、

```
v_a = v + (m_b / m_total) · Δv_sep
v_b = v − (m_a / m_total) · Δv_sep
```

分離直後の一定時間は、分かれた2つの間の接触判定を無効にする。

### 6-3. 燃焼と質量変化

同時燃焼（並列ブースター）と逐次燃焼（直列多段）の両方を許す。燃焼中は推進剤の消費により質量が減り、加速度が上がる。したがって燃焼時間と点火時刻はツィオルコフスキーの式に基づいて求める。

```
src/physics/tsiolkovsky.ts   (純関数)
    dvFor(m0, mf, isp)              // Δv = Isp·g0·ln(m0/mf)
    massAfterBurn(m0, dv, isp)
    burnTimeFor(dv, m0, thrust, isp) // 推進剤流量 = thrust/(Isp·g0) から求める
    propellantForDv(dv, mDry, isp)
```

`PlanExecutor` の点火時刻の算出はこの関数群を用いる。一定加速度を仮定すると、質量比の大きい機体で点火が遅れてノードを外すため、質量変化を必ず含める。

ステージの切り替わりを跨ぐ燃焼は、加速度が不連続になり閉形式で扱えない。したがって1つのマニューバノードの燃焼が1つのステージ内で完結するよう、設計エディタと計画UIで制約する。

推進剤が尽きたステージは、分離の候補としてHUDに提示するが、自動では分離しない。分離は軌道を変えるため、実行はプレイヤーまたは計画の判断に委ねる。

### 6-4. 無人ブースターの軌道投入と軌道上での結合

誘導装置を持つステージは、単独で `Plan` と `PlanExecutor` を持ち、指定された軌道へ自動で投入できる。投入後、軌道上でドッキングポートによって他の機体と結合できる（§4）。

この機構により、戦闘後の帰投に使うブースターをあらかじめ軌道上に置いておき、戦闘終了後に合流して結合し、その推進剤で基地へ戻る、という運用が可能になる。

## 7. 推進剤

### 7-1. 物性表

比推力は真空値、密度は貯蔵状態の値である。

**液体（酸化剤と還元剤のペア）**

| ペア | 真空比推力 [s] | 混合比 O/F | 平均密度 [kg/m³] | 貯蔵 | 月での生産 |
|---|---|---|---|---|---|
| 液体酸素 / 液体水素 | 450 | 5.5 | 360 | 極低温・蒸発損失大 | 水氷の電解のみで両方作れる |
| 液体酸素 / 液体メタン | 370 | 3.5 | 830 | 極低温・蒸発損失中 | 炭素が必要 |
| 液体酸素 / シラン | 330 | 3.0 | 900 | 酸化剤のみ極低温・自己着火 | レゴリスのケイ素と水素から作れる |
| 四酸化二窒素 / モノメチルヒドラジン | 320 | 2.0 | 1200 | 常温・長期貯蔵可・毒性 | 窒素が必要 |
| 過酸化水素 / ケロシン | 310 | 7.0 | 1290 | 常温・徐々に分解 | 炭素が必要 |

**単推進剤（RCS向け）**

| 推進剤 | 比推力 [s] | 密度 [kg/m³] | 特性 |
|---|---|---|---|
| ヒドラジン（触媒分解） | 230 | 1010 | 長期貯蔵で徐々に分解。毒性 |
| 過酸化水素（触媒分解） | 160 | 1400 | 無毒。分解が速い |
| 窒素冷ガス | 70 | 高圧貯蔵 | 最も単純。電力も点火も不要 |

**固体・ハイブリッド**

| 種別 | 比推力 [s] | 密度 [kg/m³] | 特性 |
|---|---|---|---|
| 固体（過塩素酸アンモニウム + 末端水酸基ポリブタジエン + アルミ粉末） | 265 | 1800 | 点火後は停止も絞りも再点火もできない |
| ハイブリッド（ABS樹脂 + 亜酸化窒素） | 300 | 1100 | 絞れる・停止できる・再点火できる。密度で不利 |

固体推進剤の燃料成分はアルミ粉末であり、酸化アルミニウム（アルミナ）はその燃焼生成物である。ABS樹脂はハイブリッドロケットの固体燃料側であり、液体または亜酸化窒素の酸化剤と組み合わせて使う。

**選択の意味** — 固体は安価で高密度、ただし一度きりであり、使い捨ての帰投ブースターに適する。液体酸素／液体水素は比推力が最も高いが、密度が低く巨大なタンクを要し、蒸発損失があるため長期の待機に向かない。ヒドラジン系は性能が中位だが常温で長期間待機でき、軌道上に置いておくブースターに適する。液体酸素／シランは月のレゴリスと水氷だけで生産でき、外部からの資源供給が途絶えても運用を継続できる唯一の高性能な組である。

### 7-2. 劣化

```
src/physics/propellant-decay.ts   (純関数)
    boiloffRate(propellant, tankInsulation, sunlitFraction) -> kg/s
    decayedMass(mass, propellant, elapsedSec) -> kg
```

- **極低温推進剤** — 日射に応じた蒸発損失が生じる。断熱材の等級と遮蔽（日除けシールド、位相角の調整による日陰入り）で低減できる。
- **ヒドラジン系** — 触媒毒による自己分解が生じる。時定数は年単位であり、残量表示に反映する。
- **固体推進剤** — 劣化しない。

劣化の計算は毎フレームでは行わない。在庫や残量を読む時点で、前回の評価時刻からの経過時間に基づいて一括で計算する。

## 8. 月・着陸・資源経済

### 8-1. 月の地形

月の表面は、球面上の高度場として表す。

```
src/physics/terrain/height-field.ts   (純関数)
    heightAt(bodyId, latRad, lonRad) -> number   // 基準球半径からの高度 [m]
    normalAt(bodyId, latRad, lonRad) -> Vec3     // 地形法線（天体固定座標）
    surfacePointAt(bodyId, latRad, lonRad) -> Vec3
```

- 全球は粗い解像度の高度場で表し、機体の周囲のみ細かい格子を生成する。細部は決定的な擬似乱数（`physics/random.ts` の `mulberry32`）で生成し、同じ座標では常に同じ地形になるようにする。
- 座標は天体固定座標（月とともに自転する座標系）で扱う。慣性座標との変換は `Ephemeris` の自転位相を用いる。
- 南極域は永久影クレーターを含むよう地形を構成する。日照の判定は既存の太陽方向計算に加えて地形の地平線を考慮し、クレーター底部が常に日陰になるようにする。

### 8-2. 地表との接触

高度が一定値を下回った機体に対して、以下を行う。

- 天体固定座標での緯度経度を求め、その点の地形高度と機体各部の高度を比較する。
- 固定脚の接地点それぞれを接触点として扱う。接触点が地形面より下に入った場合、法線方向の反力と接線方向の摩擦を与える。
- 固定脚を持たない部位が地形に接触した場合は損傷を与える。

球面としての天体表面到達判定は、地形を持たない天体に対してのみ適用する。地形を持つ天体では、高度場との接触判定に置き換える。

### 8-3. 着陸

接地の瞬間に以下をすべて満たす場合、着陸が成立する。値は `const.ts` に置く。

| 条件 | 内容 |
|---|---|
| 垂直速度 | 接地面法線方向の速度が許容値以下 |
| 水平速度 | 接地面接線方向の速度が許容値以下 |
| 傾斜 | 機体の脚面法線と地形法線のなす角が許容値以下 |
| 角速度 | 許容値以下 |
| 接地脚数 | 固定脚のうち規定数以上が同時に接地 |

いずれかを外れた場合、超過量に応じて固定脚および接触部位に損傷を与える。大きく外れた場合は機体を破壊する。

着陸が成立した機体は `LandingState` を持ち、天体固定座標に静止する。静止中は軌道積分を行わず、天体の自転に従って位置と速度を導出する。これにより、静止した機体を数値積分し続けることによる誤差の蓄積を避ける。

離陸は、主機の推力が機体重量（その天体の表面重力加速度と機体質量の積）を上回った時点で `LandingState` を解除し、通常の積分に戻すことで行う。

### 8-4. 月面基地

月面基地は、固定脚を持ちエンジンを持たない `Vessel` である。着陸状態で天体固定座標に静止し、生産設備部品と基地モジュール部品を積む。

- 生産設備は電力を消費し、入力資源を出力資源へ一定の速度で変換する。
- 電力はソーラーパネルとバッテリーから得る。月の自転周期に伴って日照が変動するため、蓄電容量の設計が運用に影響する。南極の高地は日照率が高く、クレーター底部は常に日陰である。
- 月面基地は複数機を結合して拡張できる。結合はドッキングポートによって行い、電力は統合され、資源は移送できる（§4-5）。したがって基地の拡張と、軌道上での機体の結合は同一の機構である。

### 8-5. 資源

| 資源 | 産地 | 用途 |
|---|---|---|
| 水 | 月の南極の永久影クレーターの採掘 | 電解して液体水素と液体酸素にする |
| 酸素 | 水の電解、レゴリスの還元 | 酸化剤 |
| ケイ素 | レゴリスの精錬 | シラン、構造材 |
| アルミ | レゴリスの精錬 | 固体推進剤の燃料成分、構造材 |
| 炭素 | 低軌道に出現する敵の撃破によるドロップ | メタン、末端水酸基ポリブタジエン、ABS樹脂、ケロシン |
| 窒素 | 低軌道に出現する敵の撃破によるドロップ | ヒドラジン、四酸化二窒素、冷ガス |
| 希少金属 | 敵のドロップ | 高性能なエンジン、フライホイール、電子機器 |

炭素と窒素は月では得られない。したがって、メタン系・ヒドラジン系の推進剤を使い続けるには低軌道での戦闘を継続する必要がある。一方、水とケイ素だけで閉じる経路（液体酸素／液体水素、液体酸素／シラン）が存在するため、戦闘を行わなくても運用は継続できる。

### 8-6. 輸送

月面基地で生産した物資を軌道基地へ運ぶ操作は、プレイヤーが行う。

1. 月面基地に着陸した機体の貨物区画に、月面基地の倉庫から資源を積み込む（両者はドッキングまたは着陸接続によって結ばれている）。
2. 離陸し、月面から目的の軌道への遷移を行う。
3. 軌道基地とドッキングする。
4. 貨物と推進剤を移送する（§4-5）。

貨物区画は容積と最大積載質量の両方で制限される。積載質量は機体の総質量に加算されるため、輸送量を増やすほど必要な Δv に対する推進剤が増える。この関係により、1回の輸送量には設計上の最適点が生じる。

### 8-7. 軌道基地の軌道

軌道基地は近直線ハロー軌道（NRHO）に置く。

- 初期状態は既存のハロー軌道の生成関数（地球-月 L2 の南方ハロー、大きな面外振幅）から得る。
- この初期状態は線形近似であり、多体重力を含む数値積分に投入すると発散する。したがって軌道基地は維持バーンを行う。近月点通過ごとに数 m/s の維持バーンを `PlanExecutor` によって自動で実行する。
- 維持バーンは推進剤を消費する。したがって軌道基地の維持そのものが資源の消費先になる。

## 12. 主要な技術的リスク

1. **結合体の積分** — 結合した機体を1つの剛体として扱う際、構成機体それぞれが持つ推進剤の消費によって重心と慣性テンソルが連続的に変化する。再計算の頻度と、姿勢積分の安定性の両立が必要である。再計算は質量が一定量変化したときのみ行い、その間は固定値を用いる。
2. **地形の解像度とデータ量** — 月の全球を扱うため、全球の高度場を高解像度で保持することはできない。粗い全球データと、機体周辺のみの局所生成の組み合わせが必要であり、境界での不連続を避ける補間が要る。
3. **着陸状態の物理** — 静止した機体を数値積分し続けると、重力と反力の釣り合いの誤差が蓄積して沈み込みまたは浮上が生じる。静止状態は積分から外し、天体固定座標に固定する扱いが必要である。離着陸の遷移条件を明確にしないと、遷移の前後で状態が振動する。
4. **描画メッシュの生成コスト** — 骨格から生成するメッシュは実行時生成であり、`WebGPURenderer` はジオメトリを最初の描画時にキャッシュする。生成は設計変更時のみとし、既存メッシュのジオメトリを差し替えない運用を守る必要がある。
5. **軌道基地の軌道維持** — 近直線ハロー軌道の線形近似による初期状態は、多体重力を含む積分では発散する。維持バーンを実装しない場合、軌道基地は数日で意図した軌道から外れる。
6. **保存形式の互換性** — 機体の表現が部品の配列から骨格とアセンブリの構造へ変わるため、旧形式の保存データは既定の設計への読み替え以上のことはできない。読み替え不能な保存データは明示的に拒否し、破損した機体を生成しないこと。
7. **UI の総量** — 設計エディタ・ドッキング支援・段管理・結合管理・月面基地の5つのパネルが追加される。既存のパネルへ統合できないかを追加のたびに確認し、置き場の規約に従うこと。
