# ゲームサイクルに対する実装の過不足監査 — 2026-10-18

スナップショット: `cdb65c836` (workspace3)。行番号はこの時点のもの。
調査方法: サブエージェント4件(計画・マップ / 船・基地・建造 / 戦闘・動的エンティティ / 天体・描画)+ 自分での確認。

## 0. 判定基準

ユーザーが示したゲームサイクル:

> **月軌道の基地から艦を発進し、地球低軌道などで敵と戦闘し、基地へ帰投する。**

これを分解すると、実装に要求されるものは:

| 段 | 要求される機能 |
| --- | --- |
| 前提 | 月軌道に基地があること、基地に艦がドッキングしていること |
| 発進 | 基地から艦が分離・出発できること |
| 遷移 | 月→LEO 等の目標への移動手段(遷移計画・実行)。往復できるだけの Δv 管理 |
| 戦闘 | 敵との射撃戦、被弾・損傷、撃破 |
| 帰投 | 基地へのランデブー・ドッキング |
| 整備 | 修理・給油・弾薬補給・(発展形として)建造・改造 |

なお長期の構想(宇宙農場・資源採取・他惑星進出)は `memos/mikanixonable/ゲームデザイン/` と
`orbit-navigation-autopilot-proposal_2026-10-18.md` にある。「その構想に繋がる基盤か」も併記する。

## 1. サイクル各段の適合状況

| 段 | 現状 | 判定 |
| --- | --- | --- |
| 基地の存在 | `ModularShip` role='base'(cockpit+dock で動的導出)、基地プリセットあり(`ship-presets.ts:32-`)。**配置できるのは CREATIVE の物体配置のみ**で、どのストーリーステージにも基地は出てこない | 部品はある、サイクルは無い |
| 発進 | `undock` で分離・新船体生成(相対分離速度 8 m/s,`ship-decoupling.ts:7` + `modular-ship-connection-operations.ts:99-`)。booster/decoupler モジュールは実装済みだが **両プリセットとも未搭載**で、発進に使う台本もない | 機構だけある |
| 遷移 | マニューバノードの手動編集は充実(plan-editor 580行・PlanPath ~450行・NodeGizmo ~300行)。**遷移ソルバ・自動操縦・操作対象外艦への指令経路はすべて無い**。自動実行は燃焼しない瞬間置換で CREATIVE 限定 | **最も欠けている部分**(提案書 §3.2 と同結論) |
| 戦闘 | 機関砲・プラズマ弾・偏差射撃・交戦圏(30km)・被弾モデル・撃破デブリ・時間加速制限: 実装済みで動く。武器は gatling 1種のみ。敵は3系統(metal/protein/assembly) | 芯はある、広がりが無い |
| 帰投 | ドッキング機構あり(距離3m・正対10°・相対速度1m/s,`ship-docking.ts:7-9`)。**ランデブー誘導・自動帰投・ドッキング補助表示は無い** | 最後の数mの機構だけある |
| 整備 | ドック接続中の全HP修理あり(コスト無し,`ship-repair.ts`)。**給油・弾薬補給の経路は無い**(`refuelFuel` に本番呼出し元なし)。建造はコスト無しで無制限 | 修理だけある |

**総括**: サイクルの「周縁の機構」(モジュール・ドッキング・分離・修理)は揃っているが、
サイクルを**駆動するもの**(どこへ・いつ・何で行き、帰るか)がほぼ無い。実装の重心は
「マップ上での軌道実験環境 + LEO での即席戦闘」にあり、基地発進・帰投のループはまだ配線されていない。

## 2. 足りないもの(サイクル駆動に必須)

`orbit-navigation-autopilot-proposal_2026-10-18.md` §3.2 を踏襲し、今回の調査で見つけた分を追記する。

### 遷移・航行(提案書で既出)

1. **遷移ソルバ** — ホーマン/二重楕円/位相合わせ/ランベルト/大気減速。どれも未実装
2. **有限燃焼の自動操縦** — 全時間倍率で燃焼を続けられる機構。現行 'instant' は `motion.reset` による置換
3. **操作対象でない艦への指令経路** — 指令入力は「操作可能な個体」にだけ1フレームずつ通され(`dynamic-system.ts:215`)、対象外の艦は指令を受けられない。並行派遣ができない
4. **Δv 予算の計算** — 計画が燃料を参照しない
5. **軌道標識**(理想化した参照軌道の配置・ターゲット化) — 提案書 §4.1
6. **終端誘導**(CW 2インパルス + 保持点手順)と**ドッキング補助表示**
7. **現実的な推進系スペック** — 現行 Δv ≈ 580 km/s で事実上無限。遷移方式の選択が遊びにならない(提案書 §7)

### 基地サイクル(今回の調査で追加分)

8. **サイクルそのものの台本(ステージ)** — 「月基地発進→LEO戦闘→帰投→整備」を課すステージが無い。
   現行ステージ(0/00/1/2)はすべて地球低軌道開始・その場戦闘で、基地も往復も登場しない
9. **基地からの発進 UX** — 艦に航行指令を出したときの「分離→安全距離→出発燃焼」の流れが無い
10. **帰投コマンド** — 「基地へ帰投」という指令の入口が無い(右クリックメニュー等)
11. **給油** — 基地タンク→艦タンクの燃料移送が無い。`ModularShip.refuelFuel`(主燃料,`modular-ship.ts:155`)には呼び出し元が無い(`refuelRcsFuel` だけが RCS ピックアップと CREATIVE の補給ボタンから呼ばれる)。弾薬補給も基地経由ではなく軌道ピックアップのみ
12. **建造・修理の資源コスト** — 現状は dock さえあれば無制限。サイクルに組み込むと無限修理になる
13. **基地ビュー(整備画面)** — 独立した画面は無く、モジュール検査窓の集まりで済ませている
    (SPEC は旧ドックビュー→基地ビューの構想あり)

### 戦闘・経済

14. **武器の多様性** — `weaponType` に 'cannon'/'missile' の型だけ存在(`dynamic-entity/parts.ts:51`)し実装は gatling のみ
15. **敵の機動 AI** — 敵は射撃のみで、追跡・回避・フォーメーション飛行の指令系が無い
16. **敵が僚艦・基地を狙えない** — 照準は player 固定(`dynamic-entity/enemy-fire-controller.ts:72`)。基地防衛戦が組めない
17. **敵の弾薬無限**
18. **撃破敵からの資源回収** — ゲームデザインの「敵を倒して資源(軽元素)を得る」に対応する実装が無い
19. **敵の長距離移動・襲撃** — 現在の敵は自機近傍にしか湧かない。「軌道暦としての襲撃予報」
    (SPEC 未確定案)に相当する仕組みが無い

### 演出

20. **発進/帰投/ドッキング完了の音・演出** — SE に decouple/clank はあるが、サイクルの節目を祝うものが無い

## 3. 過剰な実装 — 廃止案(詳細)

「過剰」の判定基準: **今回のサイクルに直接効かず、かつ規模・保守コスト・認知負荷が大きいもの**。
長期構想(宇宙農場・他惑星資源)に接続しうるものは「完全削除」ではなく「隔離/縮小」案も併記する。

### 案 A: 太陽系全域の天体登録を絞る — 最大の過剰

- **対象・規模**: `src/game/celestial/solar-system/` の地球-月-太陽以外の全部 —
  `inner-planets.ts`(水星・金星)、`mars-system.ts`、`jupiter-system.ts`(衛星14)、`saturn-system.ts`(衛星14)、
  `uranus-system.ts`(衛星6)、`neptune-system.ts`、`dwarf-planets.ts`(15)、`small-bodies.ts`(34天体・600行)、
  `point-field.ts`(小天体点群 ~9,000点)、`rings.ts`(6天体分)。計 ~2,300行 + 惑星テクスチャ約 7MB
  (`2k_*.jpg`×11) + ラグランジュ軌道カタログ5系(jupiter-europa/mars-phobos/saturn-enceladus/
  saturn-titan/sun-mars,`src/assets/orbits/`)。
- **現状の役割**: 全97天体が重力源として登録され(`celestial-system.ts:111`)、マップ表示・
  フォーカス・物体配置の基準天体・ラベル・検索・可視性ポリシー・セーブ形式に波及している。
- **過剰の根拠**: サイクルの舞台は月軌道と地球低軌道だけ。木星系14衛星や34小天体は戦闘・往復・
  帰投のいずれにも寄与しない。UI 上は配置先・フォーカス・メニューの選択肢を増やすだけで、
  「基地発進→LEO戦闘→帰投」を覚える段階では認知ノイズになる。
- **波及・削除時に潰れるもの**: `solarSystem()` 呼び出し側は基準天体を 'earth' 固定なので本体は無傷。
  波及は (a) マップの天体一覧・ラベル間引き (b) 物体配置フォームの基準天体選択肢
  (c) 右クリックメニューの対象 (d) セーブ内の天体 id(旧セーブで消えた天体を指す参照の扱い)
  (e) `DisplayTimeline` の座標系選択肢 (f) 惑星テクスチャのアセット import。
- **手順案(段階)**:
  1. `solarSystem(origin)` の登録を選択制にし、既定を太陽・地球・月のみへ(各系ファイルは残し、
     `solar-system.ts` の組み立てから外すだけ)。これで UI 選択肢と同期コストが減る
  2. 小天体点群(`point-field.ts`)と非地球-月の環(`rings.ts` の木星〜海王・カリクロー・クワオア)は
     ファイルごと削除候補
  3. 完全削除は長期構想(セレスの水・イオの硫黄・木星圏)と衝突するので、実施するなら
     `assets-src/` の orbit カタログとテクスチャも一緒に畳む。SPEC/CELESTIAL.md §1 が全系登録を
     既定にしているため、**廃止は `docs(spec):` での仕様変更を伴う**
- **注意**: 天体登録数によるフレームコストは未計測(解析式評価なので軽い可能性が高い)。
  過剰の主理由は「計算負荷」ではなく **UI の広がり・認知負荷・保守面**。

### 案 B: 軌道ガイド動物園の縮小 — 実装規模に対し使われていない

- **対象・規模**: `viewer/orbit-guide-settings.ts`(313行)+ `hud/panels/orbit-guide-tab.ts`(577行)+
  `celestial/orbit-guide/orbit-guide-model.ts`(463行)+ `zero-velocity-model.ts`(224行)+
  `orbit-guide-kind-ids.ts`(168行)+ `orbit-guide-catalog.ts`(116行)+ render 側 ~480行 +
  `src/assets/orbits/` の焼き込みカタログ ~13MB + 生成ツール(`export-lagrange-orbits.mjs` 等)。
  種類は CR3BP 族(lyapunov/halo/axial/vertical/short/longp/dpo/lpo/resonant/butterfly/dragonfly)×7系
  + リサジュー + 太陽同期 + ドーンダスク + モルニヤ + ツンドラ + ゼロ速度曲線 + 静止軌道。
- **現状の役割**: マップ上の参照表示のみ。既定 ON は geostationary と earth-moon 系だけで、
  他は全部既定 OFF。航行・誘導・ターゲットとは接続していない。
- **過剰の根拠**: サイクルの移動は「基地→目標軌道」の往復であり、族カタログの鑑賞表示は
  サイクルに入ってこない。実装量(~2,300行+ツール)に対し露出が薄い。
- **注意(保留理由)**: 自動航行提案の「軌道標識」はラグランジュ族メンバーを標識化する構想
  (提案書 §4.1)で、族カタログはその土台になり得る。**全削除は提案書 P1 と衝突しうる**。
- **手順案(段階)**:
  1. まず UI 側を縮める — ガイドタブを既定で畳む/上級者向けへ隔離する
  2. earth-moon 系と静止軌道以外のカタログ配信を止め、他系の焼き込みを凍結
     (生成ツールは残す)
  3. 軌道標識が実装されたら、ガイドの描画経路を標識側へ統合し、「ガイド」という独立機能を畳む
- **判断材料**: この機能は「没入型太陽系シミュレータ」としての側面の一部でもある。
  削るかどうかはゲームの志向(シミュレータ寄りか、サイクル寄りか)の宣言が先。

### 案 C: 敵の3系統を1〜2系統へ — 実装とアセットの集中

- **対象・規模**: `MetalEnemy`/`ProteinEnemy`/`AssemblyEnemy` の3系統。
  protein は `src/game/protein/`(~976行)+ `src/render/protein/`(~1,900行)+ アセット JSON 約 92MB
  (ATPシンテターゼ 37+17MB、ルビスコ 16+8.2MB、5I4R 8+3.8MB、ミオグロビン ~1.8MB)。
  assembly は `src/game/assembly/`(239行)+ `render/assembly/`。
- **現状の役割**: 3系統とも出現経路を持つ(stages の spawner・CREATIVE 手動スポーン)。
  陣形(5I4R攻撃・ルビスコ盾・ATP供給)は protein が担う。
- **過剰の根拠**: サイクルに必要なのは「撃ち合える敵」1種類であり、世界観の看板は protein 系。
  metal は最小の敵として残す価値があるが、assembly は3系統目としての必然性が薄い。
  protein のミオグロビン(1MBN)は陣形の役に含まれず、単体スポーンの選択肢としてのみ存在する。
- **波及**: `enemy-generator.ts`・`manual-spawn.ts`・`stage-controls-panel.ts` の敵種別選択肢、
  セーブの敵種別タグ、SPEC/PROTEIN.md・ASSEMBLY.md。
- **手順案**:
  1. AssemblyEnemy を CREATIVE スポーン選択肢から外し、部品参照を棚上げ
     (完全削除は ASSEMBLY.md の仕様判断を伴う)
  2. ミオグロビンだけはアセット・カタログ・選択肢から外しても矛盾が少ない(~1.8MB の削減)
  3. protein 基盤自体は看板なので残し、92MB の JSON を必要時ロードへ整理する方向は既に実現済み
     (fetch 分割) — さらに絞るなら motion JSON の分割粒度の見直し
- **注意**: 敵の多様性自体は dev.md の要求(「敵集団を多様に、複雑に」)なので、
  削るなら「種類」ではなく「系統」を減らす判断である。

### 案 D: 補給ピックアップ系の再編 — 基地補給ができるまでの保留

- **対象・規模**: `dynamic-entity/pickup.ts`(AmmoPickup/RcsFuelPickup 313行)+ `stage-utils/logistics.ts`(282行)+
  `pickup-view`・補給マーカー・CREATIVE 設定パネルの自動投入トグル2種 + SPEC GAME.md §8。
- **現状の役割**: 軌道上に弾薬・RCS燃料パケットを浮かべ、接近で回収。stage0 は初期配置、
  stage00 は「弾薬確保まで波が来ない」仕掛けの一部。
- **過剰の根拠**: サイクルでは「基地に帰れば補給される」が正本になるはずで、軌道上を追いかけて
  拾う方式はその間の繋ぎ。**ただし stage0/00 の遊びはこれに依存するため、単独では廃止できない。**
- **手順案**:
  1. 基地給油・弾薬移送(§2-11)を先に実装する
  2. 実装後、CREATIVE の自動投入は既定 OFF のまま維持し、ピックアップを「放棄物資/敵ドロップの
     回収」へ転用する(撃破敵から資源回収の受け皿にする案 — dev.md「敵ドロップの資源を作る」と整合)
  3. stage0/00 を残すならピックアップも残す。ステージ自体を畳むなら同時に畳める
- **注意**: SPEC GAME.md §8 がピックアップを規定している。廃止・転用は仕様判断。

### 案 E: 'instant' 自動実行(瞬間置換)の位置づけ固定 — 廃止ではなく格下げ

- **対象・規模**: `PlanExecutionMode='instant'`、`executeInstantNodesUpTo`(`modular-ship.ts:335-350`)、
  `instantNodeTime`、`creative-stage.ts:259-271` の `applySimulationEvents`/`nextSimulationEventTime`、
  メニュー「軌道計画の実行」巡回(`player-plan-settings.ts`)。
- **現状の役割**: ノード時刻に状態をそのまま置き換えるデバッグ的な実行。CreativeStage でのみ動く。
- **過剰の根拠**: 燃焼しないので「計画実行」としては本来のものではない。提案書 §4.5 で
  「CREATIVE の検証用に残す」と決定済み。
- **手順案**: 自動操縦(有限燃焼)の導入後、実行モードを「なし/自動操縦/理想実行」の3段にし、
  instant を「理想実行(検証用・CREATIVE のみ)」へ改名・隔離。その後で削除するか残すかを決める。
- **波及**: メニュー巡回の文言、`Stage.executesPlans` の判定、セーブの `planExecution` 値。

### 案 F: booster・decoupler — 廃止ではなく「未配線の完成部品」として繋ぐ

- **対象・規模**: `booster-standard`/`decoupler-standard` カタログ、`modular-ship.ts:370-406` の
  booster 燃焼管理、`ship-decoupling.ts`(分離+パネル debris 8枚)、burn-management UI の対応部。
- **現状の役割**: 機能は完成しているが、既定戦闘艦にも基地プリセットにも搭載されず、
  発進・多段分離の台本も無い。**実装済みだが何にも繋がっていない。**
- **判断**: 廃止候補ではなく「使い道を繋ぐべき死に機能」。dev.md の構想(緊急減速ブースター、
  多段ロケット、戦闘領域外へのブースター随伴)に沿って、発進シナリオか非常用減速へ配線するのが筋。
- **削除する場合**: dev.md の構想を捨てる判断が先に要る。

### 案 G: stage0(スコアアタック)/stage00(無限サバイバル) — サイクル実装後に再判断

- **現状の役割**: 唯一「今すぐ遊べる」戦闘ステージ。
- **過剰の根拠**: サイクルの本編ではない。ただし今すぐ遊べるのはこれだけなので、
  **サイクルが実装されるまで廃止は非現実的**。
- **手順案**:
  1. サイクルステージ(§2-8)の実装が先
  2. その後 stage0/00 を「デバッグ・訓練ステージ」へ格下げ(タイトル画面の扱いを変える)、

- **波及**: `stage-utils` の各クラス、`Stage` 基底の scoreCounter/logistics 配線、
  アンロック(`isUnlocked`)、セーブのステージ id。

### 案 H: 敵の被弾モデルの二重構造 — 統合候補

- **対象・規模**: `parts.ts`/`part-inventory.ts`/`part-damage-model.ts`/`part-based-enemy.ts`/
  `ship-default-parts.ts`(敵側だけが使う旧パーツ系)vs 船側の `ShipAssembly`/`ShipModuleInstance` 系。
- **現状の役割**: 敵(MetalEnemy,AssemblyEnemy は PartBasedEnemy)の部位破壊を担う。
- **過剰の根拠**: 船はモジュール系へ移行済みで、敵だけが旧パーツ系に残っている。
  CONTEXT.md の方向(船・基地を同一基盤)から見て、敵側だけ別モデルは整合しない。
- **手順案**: 廃止というより「敵も ShipAssembly 系の下位モデルへ寄せる」統合判断。
  敵の部位破壊の見せ方(部位単位の外観分離)をモジュール系で表せるかが設計論点。
- **注意**: PartBasedEnemy は「部品が見える敵」の実装で、PROTEIN/ASSEMBLY の仕様が
  部位破壊を要求する。単純削除ではなく置き換え設計が要る。

## 4. 廃止しないが留意するもの

| 対象 | 理由 |
| --- | --- |
| 地球地表タイル基盤(~2,800行+R2配信+pythonパイプライン) | LEO の見た目の主役でコンセプトの中核。サイクルには必須ではないが没入感の要。維持コストは大きい |
| 雲気象モデル+立体積雲+雲影(~1,900行+) | 同上。生成経路・実写経路の2系統を常時抱えている点は管理コスト |
| BGM 基盤(3作曲器・7曲) | 必要。ただし ui-sfx は 'warp' 1種のみで最小 — サイクルの節目(発進/帰投/ドッキング)の音が無いのは不足側 |
| セーブ/スロット/アンロック(launcher 3,300行) | 必要。サイクル実装後は「ミッション中断再開」の意味づけが要る |
| 建造 UI(ShipConstruction) | 機能の完成度は高いが、サイクルへの接続(資源コスト・製造時間)が無い。廃止ではなく配線待ち |
| HUD の二層(src/hud=汎用ウィジェット庫 / src/game/hud=アプリパネル) | 棲み分けは妥当。重複ではなく役割分担 |
| デバッグステージ×3(debug/debug-alt-system/debug-load) | タイトルに出ない開発用として正当 |

## 5. 優先順位の提案(まとめ)

### 今すぐ効く(削除・縮小してもサイクルは壊れない)

1. **直列化タグ残骸・entity-inspection.ts** — デッドコード。消すだけ
2. **週単位→月、Mm→km** — dev.md で既に決めている整理
3. **ミオグロビン(1MBN)** — 陣形の役に入らないアセット。カタログと選択肢から外すだけ
4. **ガンサイトズーム** — 未使用の申告あり。キー割当と配線を外す(小さい)

### 判断を先に要する(SPEC 変更を伴う)

5. **太陽系の登録を絞る(案 A)** — 効果は最大だが、CELESTIAL.md の全系登録仕様と長期構想
  (他惑星資源)に触れる。「既定を地球-月-太陽に絞る段階案」が無難
6. **軌道ガイド動物園(案 B)** — 完全削除は軌道標識の構想と衝突しうる。「UI 縮小→標識への統合」が順当
7. **敵系統の整理(案 C)** — 「敵集団を多様に」の要求と「系統は1〜2で足りる」のバランス判断
8. **補給ピックアップの転用(案 D)** — 基地補給の実装が先。転用先(敵ドロップ回収)の方が有望
9. **'instant' → 理想実行への格下げ(案 E)** — 自動操縦の導入とセット

### 廃止ではなく「繋ぐ」べきもの

- booster/decoupler(案 F): 発進・非常用減速へ配線
- stage0/00(案 G): サイクル実装後に訓練/デバッグへ格下げ
- parts 系敵モデル(案 H): モジュール系への統合設計が先

### 不足の補填は別の計画書で

「足りないもの」は `orbit-navigation-autopilot-proposal_2026-10-18.md` が P1〜P8 の段階に既に割っている。
今回の調査で追加された不足(基地経由の補給・建造コスト・サイクルステージ・敵の機動AI・資源回収)は
同計画の P4/P8 に相当する。
