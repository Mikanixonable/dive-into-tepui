## 目標
シミュレーションを広域（惑星間軌道など）に拡張するため、月と太陽以外の天体の万有引力を賢く考慮したい。
そのために、
1. 重力を及ぼし、重力の影響を受けないもの - 太陽、木星、地球などの主要天体。他の天体に重力は及ぼすが、自身の軌道は解析的な楕円軌道を使う。
2. 重力を及ぼし、重力の影響を受けるもの - 楕円軌道で近似できない小惑星など。未実装。
3. 重力を及ぼさず、重力の影響を受けるもの - 十分に軽い宇宙船やデブリなど。
を扱いたい。
現状、3のみをOrbitEntityやEntityManagerが計算しており、1については月と太陽がEphemerisにハードコードされた状態になっていて、拡張性がないので、この設計を改善してリファクタリングしたい。

全体の計算量について、重力を及ぼすもの（1と2）の総数をN、重力を受けるもの（2と3）の総数をMとすると、愚直な実装では計算量はO(N*M)となる。Mはデブリなどによって十分に大きくなるので、2を安直に増やすと計算量が爆発する。
そこで、賢い計算量削減方法を思いついた。以下に示す。


## 計算量削減方法

ある半径があって、その半径より外側では重力が十分に小さいので無視する、という近似をする。しかし、これだけだと意味なくて（効果範囲にいるかの判定が重力の積算と同程度にハイコストになるから）ここをうまいこと空間アルゴリズム的なのを使って高速化したい。

影響を受ける半径を天体質量に依存して変化するように実装すると、等間隔メッシュを切ってspacialHash法を使うことができなくなってしまう。そこで、太陽系の天体がのほとんどすべてが十分に小さいということを利用する。
つまり、グローバルに、ある質量Mと半径Rを決め打ちして、「質量Mより軽い天体は半径R以内でのみ計算する」「質量Mより重い天体は常に影響を計算する」とすると、無数にある小惑星や衛星にはspacial hash法を使い、デカい太陽や惑星は常に計算することでかなり計算コストを抑えられる。

しかしこの実装は無数の小惑星を実装する段階になってからでよい(計画素案step3)。
それまでは当面単純にNの数を減らすつまり「ある質量Mより重い天体は常に影響を計算する」「質量Mより軽い物体は無視する」というハードリミットで簡易的に対応してよい(計画素案Step2)。

現状(この時点で済んでいること):
- 天体は恒星/惑星/衛星の3分類(`physics/attractor.ts` の `StarId`/`PlanetId`/`SatelliteId`)で
  固定されており、静的事実は `physics/solar-system.ts` の `SOLAR_SYSTEM` レジストリに集約されている。
  天体を1つ増やすには `PlanetId`(または `SatelliteId`)に id を1つ足し、`SOLAR_SYSTEM` と
  `game/celestial/celestial-registry.ts` の2つのレジストリを埋めるだけでよい(木星がこの手順の
  実例)。
- `Ephemeris`(`physics/ephemeris.ts`)は `stateOf`/`positionOf`/`attractorsAt` などの
  「id と時刻を渡すと状態が返る」API に統一されており、解析軌道であることを外部へ漏らさない。
  小惑星を積分側(`OrbitEntity`)から合流させるときも、この API 形状を変えずに済むはずである。
- 座標系は `physics/frame.ts` の `Frame = {center: AttractorId, rotatingWith: OrbitingId | null}`
  (原点天体 × 回転の直積)に一本化されており、太陽中心系・月中心系・木星中心系はすでに選べる。
  点(`FramePoint`)と方向(`FrameDir`)は型で区別されている。
- 小惑星を追加する際、恒星/惑星/衛星の判別 union は広げない(小惑星は解析軌道で表せないから
  小惑星なのであって、4つ目の分類ではない)。`OrbitEntity` 側の存在として `attractorsAt` へ
  合流させる形にする。
