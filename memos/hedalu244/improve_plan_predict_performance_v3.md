# 第2章 残っている問題の論点と原因

## 計画の積分ステップ数が二峰性で、フレームを 120ms 動かす

`map ×65536 node1` の `plan-steps` は、**ラウンドごとに約 212 か約 420 のどちらかに落ち、
中間の値を取らない。** そして安い側か高い側かで `update` が 120ms 動く。

| | 安い側(≈212 steps) | 高い側(≈420 steps) |
|---|---|---|
| `update` | 495〜542ms | 617〜650ms |
| `eph-attr miss` | 753〜757 | 1166〜1176 |
| `eph-all miss` | 143,367〜143,646 | 182,148〜183,042 |

**当初、これを一連の変更の成果だと読み違えた。** 5ラウンドでは base が 1/5・head が 4/5 で
安い側に落ち、中央値が 419 → 212(−49%)と出たため。しかし同条件を10ラウンドずつ足すと
**base 7/10・head 5/10 と逆転した。** 15ラウンドずつの合計は base 8/15・head 9/15 で、
**両ビルドは区別できない。** 前段の「−49%」は撤回する。

原因は第2章の末尾「実測1」で特定した。次の2節がその結論。

## 【解決】二峰性の正体はノード位置。バグではない

`plan-steps` は **1ラウンドの中では完全に一定**(実測 424 / 212 / 211)で、**ラウンド間でだけ
違う。** フレームごとの揺れではなく、そのラウンドでノードをどこへ置いたかで決まる定数である。

刻み幅は `plan-arc.ts` の `stepDt` が返す「軌道項と接近項の小さい方」だが、LEO 420km では
**接近項が支配している**: `(420km ÷ 7660m/s) × APPROACH_STEP_SAFETY(0.5) = 27.4s` に対し
軌道項は `5578s ÷ PLAN_ARC_STEPS_PER_REV(100) = 55.8s`。**したがって1周 ≈ 204 step。**

- ノードが自機の直下(t ≈ 現在)に落ちれば第1区間は 0 step、末尾区間だけで ≈ 212。
- ノードが約1周後に落ちれば第1区間も ≈ 212 step になり、合計 ≈ 424。

**描かれる折れ線は1周ぶんなので、始点と終点は画面上ほぼ同じ位置(自機のところ)に重なる。**
プローブの `attemptPlaceNode` は自機マーカー中心をクリックするので、数 px のずれで「今」にも
「1周後」にも落ちる。実測でもクリック座標が (660,385) だった5ラウンドはすべて 211/212 側、
(620,415) だった1ラウンドだけが 424 側だった。

**「フレーム時間の 20% がノード位置で決まる」は実機の性質としても正しい** — 計画の積分コストは
計画の総スパンにほぼ比例し、ノード位置がそれを決める。**ここに直すべきものはない。**
測定条件として固定したければプローブ側でノード時刻を決め打ちすればよい。

## 【本命】高ワープでは、画面に出ていない計画を毎フレーム全区間積分し続けている

二峰性を追う過程で見つかった、**別の・はるかに大きい問題**。

`map ×65536 node1` では、ある時点を境に **2区間とも毎フレーム `new PlanArc` で作り直される**
状態へ入り、そのままラウンド終了(simTime にして約10万秒)まで戻らない。しかもその頃には
**折れ線は表示窓より完全に過去へ落ちていて、画面には1点も出ていない。**

### 引き金は `planEnd` を simTime が追い越すこと

`PlanEditor.update` は `attractors.resolve(..., this.lastPlanEnd, simTime)` を毎フレーム呼ぶ。
`lastPlanEnd` は **前フレームの** `PlanPath.timeRange()?.max`、すなわち折れ線を表示窓
`[currentTime, currentTime + duration]` でクリップした終端なので、実質
**「前フレームの simTime + duration」** という simTime 追従値である。

`planSourceRevision` は `!(planEnd > simTime)` のとき `unresolvedPlanEndTick`(モジュール連番)を
畳み込んで返す。つまりこの分岐に入ると **毎フレーム必ず異なる revision** になり、
`PlanArc.represents` の `sourceRevision` 判定を毎回破って全区間が作り直される。

追い越す条件はそのまま **「1フレームの simTime 前進量が表示期間を超えること」**:

- `duration`(既定 `'orbit'` プリセット = 自機の現在軌道周期)は実測 ≈ **5561s**
- ×65536 では `dt` が `Math.min(dtRaw, 0.1)` の上限に貼り付くので `simDt ≈ 0.1 × 65536 =` **6553s/frame**
- **6553 > 5561 なので必ず追い越す。**

実測の遷移(round1): `t=4001.2, planEnd=7919.1, rebuilt=0` → 次フレーム
`t=10554.8, planEnd=9539.6(< t), rebuilt=2`。

さらに数フレーム後、折れ線全体が `displayFrom = currentTime` より過去へ落ちて `timeRange()` が
null を返すようになり、`planEnd` は **NaN へ固定**される(`!Number.isFinite(planEnd)` も同じ分岐)。
**一度入ると抜ける経路が無い。**

### 何が無駄になっているか

`PlanArc.integrateTo` は1ステップにつき `provider.at()` を開始・中点・終了の3時刻で引く。
revision が毎フレーム動くので `PlanAttractors` の保持スロットは毎フレーム捨てられ、
**同一フレーム内の重複しかヒットしない。**

上の表の `eph-attr miss` の差 **1170 − 755 = 415** は、`plan-steps` の差 **420 − 212 = 208** の
ちょうど2倍。**1積分ステップあたり `attractorsAt` 2ミス**という読みが裏付けられる
(101天体の合成をフレームあたり 400〜850 回)。**そしてその積分結果は1ピクセルも描かれない。**

### 【修正済み】planEnd を計画自身の終端にした

`PlanPath` に `plannedEnd`(`buildSegments` が組んだ区間列の終端。表示窓でクリップしないので
anchor / ノード / 暦 / 表示期間だけから決まり、`simTime` に依らない)を足し、`planEnd` をそこから
取るようにした。あわせて `planSourceRevision` のガードを `!Number.isFinite(planEnd)` だけにした
— 計画の終端が過去にあることは異常ではなく、そのとき全予測列が `COVERS_PLAN` で安定する。
これで `simTime` は `planSourceRevision` / `resolve` のどちらからも読まれなくなったので落とした。

### なぜ低ワープでは起きないか

×1 では 271/261/283 フレームを通して `rev` の変化 **0 回**、`rebuilt` 常に 0、`steps` 常に 0。
`simDt = 0.0167s ≪ duration` なので分岐に入らない。**「ノードを置けば anchor もノードも凍結され、
毎フレームの再積分は走らない」という設計意図は、低ワープでは完全に成立している。**

### 実測1 — 使い捨て計装によるフレーム単位の記録

`PlanEditor.update` の1箇所に、そのフレームの
`{t, planEnd, dur, rev, nodes, rebuilt, steps}` を配列へ push するだけの計装を入れ、
CDP ドライバで stage1・マップビュー・ノード1個を作ってから10秒ぶんの全フレームを読み出した。
条件は ×65536 と ×1 の2つ、各3ラウンド(ページ読み込みからやり直し)。計装は測定後に revert 済み。

| 条件 | フレーム数/10s | `rev` が動いたフレーム | `rebuilt` の分布 | `steps` |
|---|---|---|---|---|
| ×65536 r1 | 32 | 51.6% | {0:16, 2:16} | 0 または 424 |
| ×65536 r2 | 34 | 54.5% | {0:16, 2:18} | 0 または 212 |
| ×65536 r3 | 36 | 54.3% | {0:17, 2:19} | 0 または 211 |
| ×1 r1〜r3 | 271/261/283 | **0%** | **{0: 全件}** | **0** |

×65536 で `rebuilt=0` が半数を占めるのは、ワープを段階的に上げる前半フレームぶん。
**ワープが ×65536 に達した後は一度も 0 に戻らない。** `nodes` は6ラウンドとも 1 のまま
(マップビュー中は `PlanGuide.update` が `editMode` で早期 return するのでノードが消化されない)。

## 【解決】予測の刻み幅が「残り時間」で切られ、届いた後は毎フレーム1歩ずつ進んでいた

`Predictor.advanceBudget` の刻み幅はこうだった:

```
const remaining = simTime + horizon - tipState.t;
const dt = Math.min(remaining, Math.max(PREDICT_MIN_STEP_DT, 局所周期/PREDICT_STEPS_PER_REV, horizon/PREDICT_MAX_STEPS));
```

`remaining` は **毎フレーム simTime に追従する値**なので、先端がホライズンへ届いた後は
`dt` がそのフレームの `simDt` に貼り付く。×1 なら 0.017〜0.04 秒。**その 0.04 秒を進めるためだけに、
1歩あたり `predictedAttractorsAt` + `classifyAttractors` を2回払い続ける。**

**「予測は原理上シミュレーションより粗い」という前提が、届いた後だけ崩れていた。** 加えて
`const.ts` の「本体シミュレーションより細かくする理由がないため同じ値」というコメントも関係を
取り違えていた — 細かくする理由が無いのではなく、固定予算でホライズンまで届かせるために
**粗く刻む理由がある**。両方を直した(`4016f47f` / `dd9b2722`)。

### 遠方の個体では、1歩がまるごと1フレームぶんになる

`max(...)` の軌道項は「先端で最も強く引く天体まわりの周期 ÷ 600」。地球から離れた個体では
最強重力源が太陽になるので、**この項は horizon より桁で大きくなる**:

| | 局所周期 ÷ 600 | horizon(自機 LEO 周期) |
|---|---|---|
| LEO の艦・敵 | 5578s ÷ 600 = **9.3s**(→ 下限 20s が効く) | 5578s |

**全個体がきっちり毎フレーム1歩ずつ進んでいた。**

### 【修正済み】上限を horizon そのものにし、覆っている先端は伸ばさない

`remaining` を落として `Math.min(horizon, Math.max(...))` にした。先端はホライズンを少し越えて
止まり、`simTime` が追いつくまでの数フレームは伸ばす必要がなくなる。あわせて
`!(remaining > 1e-9)` のガードを**ループ冒頭の `if (tipState.t >= simTime + horizon) break;` へ移した** —
以前はこの判定が最初の重力源解決の後にあったので、覆っている個体でも1回ぶん払っていた。

**上限を `horizon` に残したのは意図的。** `remaining` と違い `horizon` は simTime に依らない。
落とすと、上表の小惑星が1歩 52,579s(窓の9.4倍)を飛び、表示窓の中身が両端からの補間だけに
なる。なお **`CLAUDE.md` と `DEVELOP/CALLSTACK.md` は元から `min(horizon, ...)` と書いており、
「先端はホライズンを越えて止まる設計」とも書いてあった** — コードの側が文書から外れていた。

## 【再検討・結論: 落とせない】刻み幅を定数へ簡略化できるか

## 【計測環境】フレーム率の指標8項目が「1フレームだけのスナップショット」

`PerfMeter.flush()` は 500ms ごとに `perfCounts()` を**1回だけ**呼び、その戻り値をそのまま
文字列にする。ms 系のように `PhaseStats` へ毎フレーム積む経路を通らない。ところが `PerfCounts`
には性質の違う3種類が混ざっている:

- **状態量**(その瞬間の在庫): エンティティ数・`mapMode`・`warp`・`gravitySources`。スナップショットで正しい。
- **累積カウンタ**: 暦キャッシュの hit/miss。`PerfMeter` が前回 flush との差を取っており正しい。
- **フレームあたりの率**: `predicted` / `predictComplete` / `predictDiscarded` / `predictorSteps`
  (`Predictor.update` の冒頭で毎フレーム 0 にリセット)、`simSubsteps` / `orbitSteps` /
  `gravitySources`(`Simulator.advance` の冒頭で同じ)、`planArcs` / `planSteps`
  (`PlanPath.update` の冒頭で同じ)。
  **この9項目は、500ms ごとに1フレームだけ覗いた値だった。**

影響: 第2章 A-4 の「6体全部が**毎フレーム**破棄され、1体も完成しない」は、実際には
「覗いたそのフレームでは 6/0 だった」までしか言えていない。`plan-arcs` が常に 2 という観測も同様。
今回の実測1では、まさにこの9項目のうち2つ(`planArcs`/`planSteps`)がフレームごとに 0 と
212/424 を往復していることが分かった。**平均でも最大でもない値を読んでいたことになる。**

**対応済み** — 9項目を `RATE_COUNTS` の表に集め、ms 系と同じ `PhaseStats` へ毎フレーム積んで
`avg / max` で出すようにした。`record` が `perfCounts()` を1フレームに1回だけ解決し、解決済みの
`PerfCounts` を `flush` へ渡す。行とグループの並びは変えていない。
**以後の計測は、この形で取り直した値を基準にする。**

## A-4: 予算の崖は変わっていない

`map ×65536` は base/head とも `pred-discard` 6 / `pred-complete` 0 / `pred-steps` 458。

**ただしこの4項目はフレーム率で、500ms ごとに1フレームだけ覗いた値である**(第2章「計測環境」)。
「毎フレーム」と読めるだけの根拠は無い。実態は集計を直してから読み直す。

外挿を入れたことで「破棄された列の先を落とさず外挿で埋める」ようになったため、
**症状としては見えにくくなったが、原因はそのまま残っている。**
むしろ外挿の基準となる先端が毎フレーム作り直されるので、外挿区間が揺れる形で出うる。

**実測3(集計を直した後)で読み直した値**: `map ×65536` は `pred-discard` avg 6 / max 6、
`pred-complete` avg 0 / max 0、`pred-steps` avg 458 / max 458。**avg と max が一致している
ので、これは本当に「毎フレーム」である。** 旧・スナップショット読みの疑いは晴れ、
第2章 A-4 の記述はそのまま正しい。刻み幅の修正の前後で1つも動いていない。

## 判断1(決着・対応済み): 二峰性は解明。潰すべきは下にあった別の問題だった

二峰性そのものは**ノード位置が決める定数**で、直すべきものではなかった。測定条件として
固定したければプローブ側でノード時刻を決め打ちすればよい。

代わりに、**高ワープでの毎フレーム全再積分**(第2章「本命」)が新しい第1段になる。
直し方の候補は2つあり、**(ii) を採って修正済み**(第2章「修正済み」「実測2」):

- **(i) `unresolvedPlanEndTick` の連番をやめる** — 分岐に入っている間は毎フレーム別の
  revision になる、という症状だけを止める。ただし「計画の終端が分からない」という状態は
  そのまま残るので、`predictionCoverage` の判定基準が無いままになる。対症療法。
- **(ii) `planEnd` を表示窓でクリップしない値にする** 【採用】 — `planEnd` は
  `predictionCoverage` が「予測列が計画の span を覆っているか」を判定するためだけに使われる。
  計画自身の積分終端(= `buildSegments` が anchor / ノード / 暦だけから決める `end`、simTime に
  一切依存しない)を渡せば、**そもそも simTime 追従値でなくなる。** `timeRange()` が表示用に
  クリップした値を revision の材料に流用していたことが設計上の誤りだった。

なお **(ii) を入れても、画面外の計画を積分し続けること自体は残る**(revision が動かなくなるので
再積分はしなくなるが、初回の積分結果は保持され続ける)。表示窓から完全に外れた計画をどう
扱うかは別の判断で、この修正の前提にはならない。
