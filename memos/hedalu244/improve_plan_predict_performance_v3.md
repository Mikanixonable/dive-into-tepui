## 計測の前提

**ベースライン = `c1bf918e`(`7d92169` の直前。v2 の r2 `aedde272` + 線の改名1件)、
比較対象 = `f564c84a`(現 HEAD)。同一セッション・同一マシンで、
base → head の順ではなく head1 → base1 → head2 → base2 の順に4ラウンド取った。**

条件は v2 と同じ6本(`stage1` の `map ×1 node0/node1`・`map ×65536 node0/node1`・
`combat ×65536`、`creative map ×65536 艦なし`)。

### 【重要・v2 の前提が甘かった】run-to-run の振れは ±30% では収まらない

**同一ビルドの base1 と base2 が、`combat ×65536` の update で 413.4 → 253.7ms(+63%)、
`map ×1 node1` の frame で 44.1 → 24.5ms(+80%)食い違った。**
`map ×65536 node1` は HEAD 側でも 507 → 1030ms(+103%)振れている。

- v2 は「高ワープの ms は ±30%」と書いたが、**×1 の条件でも 80% 振れる**。
- したがって **1条件1回の ms は、高ワープでも低ワープでも使えない。**
- 本メモが結論として扱うのは **離散カウンタだけ** に絞る。ms は「変わっていないことの確認」に
  しか使わない。

振れの下限を与える対照として `creative ×65536 艦なし` がある。**この条件は一連の変更が
1行も通らない経路**(エンティティ0体・予測0体・計画なし)で、4ラウンドの
`ephAttr miss` / `ephAll miss` がビット単位で一致(984 / 149568)しているのに、
update は 185.6 / 172.1 / 162.2 / 169.1ms と ±7% 振れた。**これが最良条件での ms の分解能。**

### 離散カウンタの読み方(v2 から訂正)

`暦キャッシュ` の2行は **500ms の flush 期間の累計差分**なので、その期間に何フレーム
入ったかで値が変わる。`combat ×65536` の `ephAttr miss` が base1=656 / base2=984 /
head1=984 / head2=656 と**ビルドではなくラウンドで対になる**のがその証拠(2フレーム期間と
3フレーム期間、いずれも1フレームあたり 328 で一致)。
frame > 500ms の条件では1フレーム = 1期間なので生値がそのまま1フレームぶんになる。
**本メモの比較は、frame > 500ms でフレーム数が揃っている条件だけで行う。**

# 第1章 v2 の記録と比べて改善・解消したもの

## 1-1. 責務漏洩そのものが消えた(本題)

v2 の作業中に発見された「`supersedesAnalyticEllipse` → `OrbitLine.setSuppressed` と
3モジュールを貫く整合性保持」は無くなった。到達点は次の形:

- 予測線・過去線・軌道楕円の3種すべてが「**線を持っているか = 描くか**」になり、
  生成と破棄は `show*Line()` / `hide*Line()` が担う。`OrbitLine` から表示フラグが消えた。
- 予測が表示期間に届かないときの解析楕円へのフォールバックが廃され、
  線の末尾を先端からの二体ケプラー外挿で継ぐ形になった。`Player` は `orbitLine` を持たない。
- 「どこで描くかを決めるか」は `EntityManager.syncOrbitLines` /
  `syncPlayerTrajectoryLines` の2箇所に閉じた。

## 1-2. 計画の再積分が半減した 【確定・最大の成果】

`map ×65536 node1`(frame > 500ms、4ラウンドとも1フレーム/期間):

| 指標 | base1 | base2 | head1 | head2 | 変化 |
|---|---|---|---|---|---|
| `plan-steps`(計画の積分step) | 420 | 419 | **212** | **213** | **−49%** |
| `ephAttr miss` | 1172 | 1170 | **755** | **757** | **−35%** |
| `ephAll miss` | 182334 | 182148 | **143553** | **143739** | **−21%** |

**両側とも2回ずつで再現しており、振れの範囲(±0.2%)が変化幅(−21〜−49%)を大きく下回る。**
`plan-arcs` は両側 2 のままなので、区間の作り直し回数ではなく **1区間あたりの積分量**が
減っている。原因は重力源が「答えられない天体を落とす」から「外挿で埋める」へ変わり、
`PlanAttractors` の保持が効くようになったこと。

### v2 の未検証事項1 が決着した

v2 は「`map65536-node1` の `plan-steps` が r1 で 212 → 420 に倍増し、r2 では 212 に戻った。
高ワープの振れと区別が付いていない」と書いていた。**振れではなかった。**
420 はベースライン(`c1bf918e`)の実挙動で、2回とも 420/419。HEAD は 2回とも 212/213。

## 1-3. 挙動が変わっていないことを確認できた経路

- **`combat ×65536`**: `pred-steps` 128 / `sim-orbit` 1968 / `pred-discard` 1 /
  1フレームあたりの `ephAttr miss` 328 が **4ラウンドすべてで一致**。挙動不変。
  update の 413 → 232ms は base1 の外れ値によるもので、base2(253.7)と head(232.2/241.6)は
  ±9% の範囲に収まる。**改善とは言えない。**
- **`creative ×65536 艦なし`**: 4ラウンドで全カウンタがビット単位一致。予告どおり手つかず。

## 1-4. 潜在バグを2件塞いだ

- **死にコード `attractorsNear`**: `src/` からの呼び出しが0件(全て `attractorsNearInto`)。
  自己除外の引数まで足されていたので、関数ごと削除して文書を実態へ直した。
- **`planSourceRevision` が予測の打ち切りを畳んでいなかった**: 外挿を入れたことで
  「届いていない列」も先端から外挿できるようになったが、打ち切られた列だけはできず、
  その個体が重力源・衝突体の一覧から丸ごと落ちる。世代値は「届いていない」のまま動かないので、
  `PlanArc` が落ちる前の積分を保持し続けていた。4値目を足して塞いだ。

## 1-5. 計測が安定した

v2 は `creative` 条件が r1/r2 とも `attempt=1`(レンダラが落ちて張り直し)だったが、
今回は4ラウンド × 6条件 = 24回のうちリトライは2回(base1 の map65536-node0、
head2 の creative)。**ヘッドレスの安定性自体は改善している。**

# 第2章 残っている問題の論点と原因

## A-0: 積分がいまも最大の単一項目(未着手)

`creative ×65536 艦なし` は 162〜186ms。**エンティティ0体・予測0体・計画なしでこれ。**
中身は `Simulator.substep` が毎サブステップ行う天体窓の構築だけで、
`sim-substeps` = 328 × 1フレームあたり `ephAll miss` 49,856。

**v2 から一切動いていない。** 一連の変更は表示側の責務整理だったので当然だが、
**依然としてここが最大。**

## A-1: 予測の暦解決は1ステップ2回のまま(v2 の第1段が未実施)

`map ×65536` の `予測` は 168〜187ms で、`積分`(70〜83ms)の2倍以上ある。
`Predictor.advanceBudget` は1ステップにつき `predictedAttractorsAt` を
開始時刻と中点時刻の2回引く構造のまま。

v2 の実験5-D が「6/7 regime でビット単位一致したまま解決回数がちょうど半分になる」ことを
確認済みで、**推奨(a)のまま着手されていない。**

一連の変更で `strongestAttractor` の重複呼び出し(`localOrbitPeriod` 内部)は1回に減ったが、
これは窓の構築そのものには効かない。

## A-4: 予算の崖は変わっていない

`map ×65536` は base/head とも `pred-discard` 6 / `pred-complete` 0 / `pred-steps` 458。
**6体全部が毎フレーム破棄され、1体も完成しない。**

外挿を入れたことで「破棄された列の先を落とさず外挿で埋める」ようになったため、
**症状としては見えにくくなったが、原因はそのまま残っている。**
むしろ外挿の質が毎フレーム揺れる形で顕在化しうる。

## B-1(新規・小さい悪化): 低ワープの暦引きが 6〜12% 増えた

`map ×1 node1` の `ephAll miss`: base 2584 / 2584 → head 2736 / 2888。
**ベースライン側は2回とも 2584 でぴたりと一致しており、増加は再現している。**

`displayState(t, ephemeris)` が中心天体の `stateOf` を引くようになったぶん。
frame は 24.5 / 24.1 / 25.1ms(base2/head1/head2)で差が出ていないので、
**今のところ ms には現れていない。**

## B-2(未計測): 外挿区間の焼き直し頻度

`TrajectoryLine` は、外挿区間を持つ間は `to`(= `simTime + duration`)が
外挿1サンプルぶんの間隔以上動いたら焼き直す。**高ワープでは `simTime` が毎フレーム
大きく動くので、毎フレーム焼き直しになりうる。** 1回の焼き直しで最大
`MAX_EXTRAPOLATED_SAMPLES` = 2048 回の `ephemeris.stateOf` が走る。

今回の計測は表示期間が既定(`stage1` で 2h、`creative` で 1d)なので、
**28日プリセットでのコストは測れていない。** サンプル間隔が長くなるほど
焼き直し閾値も緩むので相殺される可能性はあるが、確認していない。

## B-3(未計測): マップビューで全自艦が予測線を持つ

`show = isActive || overviewMode` になったので、マップビューでは表示され得る全自艦が
`TrajectoryLine`(1本 16384 頂点)を持つ。`MAX_PLACED_SHIPS` = 50 で、
頂点バッファだけで約 10MB。**`stage1` は自艦1隻なので今回の計測には現れていない。**

`heap` 行は 106〜378MB の範囲で GC のタイミングに支配されており、この規模の差は読めない。

## B-4: 軌道線の生成をやめても draw call は減らない

`map ×65536 node0` の `draw-calls` は base2 298 / head 297/297 で変わらない。
**敵の軌道線は `BodyClassToggles` の既定で元から非表示**(`Orbit` 系は `planetOrbit` 以外すべて既定オフ)で、
ベースラインでも `setDisplayEnabled(false)` により draw call には出ていなかった。

**今回の変更の効きは「頂点バッファを確保しない」ことであって、描画コストではない。**
効果が出るのはトグルを開いた状態か、敵が多いステージ(`stage00` の波状攻撃)で、
そこは測っていない。

## C: 線が船体から離れる/振動する(未着手・独立)

v2 の分析のまま。A-4 が直って破棄が止まってからでないと着手できない。

## D / A-3 / A-5: 棄却済み(v2 のまま)

予測と計画の列の統合、`always`/`grid` で更新頻度を分ける、`horizon` を個体ごとに変える —
いずれも v2 で棄却済みで、今回覆す材料は出ていない。

# 第3章 私が判断すべきこと

## 判断1: 計測手法を先に直すか 【推奨あり】

**今回いちばん重い発見は、1条件1回の ms が使えないこと。**
同一ビルドで +63〜103% 振れる以上、v2 の r0/r1/r2 の比較のうち ms を根拠にした部分は
すべて信用できない(離散カウンタを根拠にした部分は生きている)。

- **(a) `tools/perf-probe.mjs` に条件ごとの繰り返し(既定3回・中央値)を足す** 【推奨】
  → 1ラウンドの所要は3倍になるが、以後の判断がすべて数字で言えるようになる。
- (b) 離散カウンタだけで判断し続ける
  → 今回はそれで足りたが、A-0/A-1 は **ms でしか効果が測れない**(カウンタは変わらない設計)。
- (c) 現状維持

**推奨は (a)。** 特に **A-1(第1段)は「暦解決が半分になる」施策で、
`pred-steps` は変わらない設計なので、ms が測れないと効果を確認できない。**

## 判断2: v2 の第1段(予測の暦解決を1ステップ1回)にいま着手するか

実験5-D で精度側の確認は済んでおり、`予測` が `map ×65536` の最大項(168〜187ms)。
**判断1(a) の後にやれば効果が測れる。** 順序をどうするか。

## 判断3: v2 の判断2(`predictedAsPlanCollider` を読ませるか)は未決のまま

宣言だけ足されて誰も読んでいない状態が、今回の変更を通しても続いている。
現状は「予測列を持っている物体がたまたま計画の衝突体になる」という副作用で決まっており、
弾・自艦・基地・弾薬が計画線の終端相手になっている。**目に見える挙動変更なので判断が要る。**
私の見立ては v2 と変わらず「読ませるべき」。

## 判断4: v2 の判断3(予測要否のフレーム可変ゲート)の範囲

A-4 が残っている以上、これが次に効く。範囲 (i)(予測線を描いていない個体だけ止める)と
(ii)(表示時刻が現在を指している間は `predictedForGhost` を成立させない)の選択は未決のまま。

**外挿を入れたことで (ii) の代償が変わった。** v2 は「止めた個体はスライダを引いた瞬間に
伸び切っていない」ことを懸念していたが、いまは外挿が繋ぐので**位置は答えられる**
(精度は落ちる)。(ii) を採りやすくなっている。

## 判断5: 低ワープの暦引き +6〜12% を受け入れるか

第2章 B-1。外挿が中心天体の `stateOf` を引くぶんで、ms には出ていない。
受け入れるなら記録だけして進む。

## 判断6: v2 の判断4(月近傍の dt² 誤差)・判断5(A-0)は持ち越し

どちらも今回動いていない。A-0 は依然として最大の単一項目。

# 第4章 これからの作業計画

**順序は「測れるようにする → 効果が大きい順 → 正しさに関わる判断」。**

### 第0段: プローブに繰り返しと中央値を足す 【判断1(a) 承認後】

条件ごとに3回走らせて中央値を採る。**これが無いと第1段以降の効果を数字で言えない。**
今回の4ラウンドのデータをそのまま回帰の基準に使える。

### 第1段: 予測の暦解決を1ステップ1回にする 【判断2 承認後】

`Predictor.advanceBudget` の刻み幅決定を、1歩前の中点で解決済みの重力源から行う。
実験5-D で6/7 regime ビット単位一致を確認済み。

計測: `map ×65536` / `combat ×65536` の `予測 ms` が半分近くになるか。
**`pred-steps` は変わらないはずなので、そこが変わったら実装が間違っている。**

### 第2段: 予測要否のフレーム可変ゲート 【判断4 で範囲確定後】

分解済みの3条件を update フェーズで評価し、どれも立たない個体の予測を破棄する。

### 第3段: A-4(予算の崖)

第1段で単価が下がった後に測り直し、`pred-complete` が 0 のままなら
degradation を持たせる設計(足りない個体は列を全損させない)へ進む。

### 第4段: 外挿の実コストを測る 【B-2 / B-3】

表示期間を 28日プリセットにした条件と、`creative` で自艦を複数配置した条件を
プローブの条件マトリクスへ足す。**いまの6条件はどちらも突いていない。**

### 第5段: A-0(積分の天体窓)【判断6 の結論による】

いちばん大きいが、いちばん判断が要る。

### 第6段: 論点C(線が船体から離れる/振動する)

A-4 が直って破棄が止まってから。

### やらないこと(v2 から変更なし)

- `ATTRACTOR_REBUILD_SEC` 相当の据え置きを戻す
- `always`/`grid` で更新頻度を分ける
- 予測と計画の列を統合する
- `horizon` を個体ごとに変える
- `PREDICT_STEP_BUDGET` を上げる
