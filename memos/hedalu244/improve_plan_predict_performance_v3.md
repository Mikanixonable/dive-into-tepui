## 計測の前提 — 手法を直してから測った

ベースライン = `c1bf918e`(`7d92169` の直前。v2 の r2 `aedde272` + 線の改名1件)、
比較対象 = `454fac7b`(現 HEAD)。

### v2 の「±30%」は大幅な過小評価だった

最初、条件ごと1回の計測で base/head を2ラウンドずつ取ったところ、
**同一ビルドの2ラウンドが `combat ×65536` の update で 413.4 → 253.7ms(+63%)、
`map ×1 node1` の frame で 44.1 → 24.5ms(+80%)食い違った。**
高ワープに限らず ×1 でも振れる。**1条件1回の ms は、いかなる比較にも使えない。**

そこで `tools/perf-probe.mjs` を先に直した(`454fac7b`):

- `PERF_REPEATS`(既定3)回、そのつどページ読み込みからやり直して測り、行ごとに
  **ラウンド間の中央値**を採る。
- 中央値だけでは信じてよいか判断できないので、**各ラウンドの値と振れ幅(spread)を併記**する。
- `hit / miss` 行も数値として集計対象に入れた(それまで文字列としてしか出ていなかった)。

過去のコミットへ持っていく方法は、`src/` だけをそのコミットの内容へ戻してビルドし、
プローブ自身は現在の版のまま走らせる(プローブはビルド済みの `docs/` を外側から駆動するだけ):

```
git restore --source=<commit> --worktree src/ && npm run build && node tools/perf-probe.mjs
git restore --worktree src/
```

これをプローブ冒頭の使い方にも書いた。**次回からは今回の `PERF_REPEATS=5` の値をベースラインにできる。**

### 直した後の計測

6条件 × 5ラウンド × 2ビルド。全60ラウンドが `attempt=0`(リトライなし)で完走した。

対照は `creative ×65536 艦なし` — 一連の変更が1行も通らない経路(エンティティ0体・
予測0体・計画なし)。**update が base 170.1ms / head 169.8ms、spread ±1〜2%、
暦カウンタは完全一致。これが計測の分解能の下限。**

v2 の作業中に発見された「`supersedesAnalyticEllipse` → `OrbitLine.setSuppressed` と

- 予測が表示期間に届かないときの解析楕円へのフォールバックが廃され、

- 「どこで描くかを決めるか」は `EntityManager.syncOrbitLines` /
  `syncPlayerTrajectoryLines` の2箇所に閉じた。

## 1-2. 潜在バグを2件塞ぎ、死にコードを1つ消した

- **死にコード `attractorsNear`**: `src/` からの呼び出しが0件(全て `attractorsNearInto`)。
  それと知らずに自己除外の引数まで足していたので、関数ごと削除して文書を実態へ直した。
- **`planSourceRevision` が予測の打ち切りを畳んでいなかった**: 外挿を入れたことで
  「届いていない列」も先端から外挿できるようになったが、打ち切られた列だけはできず、
  その個体が重力源・衝突体の一覧から丸ごと落ちる。世代値は「届いていない」のまま動かないので、
  `PlanArc` が落ちる前の積分を保持し続けていた。4値目を足して塞いだ。
- **自己引力の除外に書いた理由が誤りだった**(`refactor_orbitline_visiblity.md` を訂正済み)。
  `attractorAccel` は距離 1m 未満の直達項を落とすので発散しない。さらに一覧は先端時刻ちょうどで
  組むため自分自身は距離ちょうど 0 になり `strongestAttractor` にも選ばれない。
  **この変更で観測できる挙動は何も変わっていない。**

# 第2章 残っている問題の論点と原因

## 【新発見】計画の積分ステップ数が二峰性で、フレームを 120ms 動かす

`map ×65536 node1` の `plan-steps` は、**ラウンドごとに約 212 か約 420 のどちらかに落ち、
中間の値を取らない。** そして安い側か高い側かで `update` が 120ms 動く。

| | 安い側(≈212 steps) | 高い側(≈420 steps) |
|---|---|---|
| `update` | 495〜542ms | 617〜650ms |
| `eph-attr miss` | 753〜757 | 1166〜1176 |
| `eph-all miss` | 143,367〜143,646 | 182,148〜183,042 |

**当初、これを一連の変更の成果だと読み違えた。** 5ラウンドでは base が 1/5・head が 4/5 で
安い側に落ち、中央値が 419 → 212(−49%)と出たため。しかし同条件を10ラウンドずつ足すと
**base 7/10・head 5/10 と逆転した。** 15ラウンドずつの合計は base 8/15・head 9/15 で、
**両ビルドは区別できない。** 前段の「−49%」は撤回する。

原因は未特定。`plan-arcs` は常に 2 で、212 と 420 はほぼちょうど2倍なので、
2区間のうち片方だけを積分し直すラウンドと両方積分し直すラウンドがある、という形に見える。
**プローブがノードを置く位置がラウンドごとに違う**(`attemptPlaceNode` は描かれた線上を
クリックする)ため、そこが効いている可能性が高いが、確認していない。

**これは一連の変更とは独立した、既存の論点である。** 高ワープでノードを1つ置いたときの
フレーム時間の 20% が、ノードをどこに置いたかで決まっている。

## A-0: 積分がいまも最大の単一項目(未着手)

`creative ×65536 艦なし` は 169.8ms(spread ±1%)。**エンティティ0体・予測0体・計画なしでこれ。**
中身は `Simulator.substep` が毎サブステップ行う天体窓の構築だけで、
`sim-substeps` = 328、`eph-all miss` = 149,568。**v2 から一切動いていない。**

## A-1: 予測の暦解決は1ステップ2回のまま(v2 の第1段が未実施)

`map ×65536` の `予測` は 175〜181ms で、`積分`(74〜77ms)の2倍以上。最大項。
`Predictor.advanceBudget` は1ステップにつき `predictedAttractorsAt` を
開始時刻と中点時刻の2回引く構造のまま。

v2 の実験5-D が「6/7 regime でビット単位一致したまま解決回数がちょうど半分になる」ことを
確認済みで、**推奨(a)のまま着手されていない。**

一連の変更で `strongestAttractor` の重複呼び出し(`localOrbitPeriod` 内部)は1回に減ったが、
窓の構築そのものには効かないので、上表のとおり `予測` は動いていない。

## A-4: 予算の崖は変わっていない

`map ×65536` は base/head とも `pred-discard` 6 / `pred-complete` 0 / `pred-steps` 458。
**6体全部が毎フレーム破棄され、1体も完成しない。**

外挿を入れたことで「破棄された列の先を落とさず外挿で埋める」ようになったため、
**症状としては見えにくくなったが、原因はそのまま残っている。**
むしろ外挿の基準となる先端が毎フレーム作り直されるので、外挿区間が揺れる形で出うる。

## B-1(撤回): 低ワープの暦引きの増加は再現しなかった

初回の計測で `map ×1 node1` の `eph-all miss` が 2584 → 2736/2888 と 6〜12% 増えて見えたが、
5ラウンド中央値では base 2677 / head 2660(−1%、spread ±1〜5%)。**ノイズだった。**

## B-2(未計測): 外挿区間の焼き直し頻度

`TrajectoryLine` は外挿区間を持つ間、`to`(= `simTime + duration`)が外挿1サンプルぶんの
間隔以上動いたら焼き直す。**高ワープでは `simTime` が毎フレーム大きく動くので、
毎フレーム焼き直しになりうる。** 1回で最大 `MAX_EXTRAPOLATED_SAMPLES` = 2048 回の
`ephemeris.stateOf`。

今回の6条件は表示期間が既定(`stage1` で 2h、`creative` で 1d)なので、
**28日プリセットでのコストは測れていない。**

## B-3(未計測): マップビューで全自艦が予測線を持つ

`show = isActive || overviewMode` になったので、マップビューでは表示され得る全自艦が
`TrajectoryLine`(1本 16384 頂点)を持つ。`MAX_PLACED_SHIPS` = 50 で頂点バッファだけ約 10MB。
**`stage1` は自艦1隻なので今回の条件には現れていない。**

## B-4: 軌道線の生成をやめても draw call は減らない

`draw-calls` は全条件で base/head 一致(298/297、338/338、352/352、72/72)。
**敵の軌道線は `BodyClassToggles` の既定で元から非表示**(`Orbit` 系は `planetOrbit` 以外すべて既定オフ)なので、
ベースラインでも描画には出ていなかった。

**今回の変更の効きは「頂点バッファを確保しない」ことであって、描画コストではない。**
効果が出るのはトグルを開いた状態か敵の多いステージ(`stage00` の波状攻撃)で、そこは測っていない。

## C: 線が船体から離れる/振動する(未着手・独立)

v2 の分析のまま。A-4 が直って破棄が止まってからでないと着手できない。

## D / A-3 / A-5: 棄却済み(v2 のまま)

予測と計画の列の統合、`always`/`grid` で更新頻度を分ける、`horizon` を個体ごとに変える —
いずれも v2 で棄却済みで、今回覆す材料は出ていない。

# 第3章 私が判断すべきこと

## 判断1: 二峰性(第2章 冒頭)を先に潰すか 【推奨あり】

高ワープでノードを1つ置いたときのフレーム時間の 20%(120ms)が、ノードをどこに置いたかで
決まっている。**しかもこの揺れがある限り、この条件では他のどんな改善も測れない**
(ラウンド間の spread が ±11% ではなく二峰の間を跳ぶため、中央値が安定しない)。

- **(a) 原因を特定して潰す** 【推奨】 — 計測の前提が整い、かつ実利もある。
- (b) プローブ側でノード位置を固定する — 測れるようにはなるが、実機の揺れは残る。
- (c) 放置する。

## 判断2: v2 の第1段(予測の暦解決を1ステップ1回)にいま着手するか

`予測` は `map ×65536` の最大項(175〜181ms)で、実験5-D により精度側の確認は済んでいる。
**計測手法が直ったので、今度は効果を数字で確認できる。**
判断1 と順序をどうするか。

## 判断3: v2 の判断2(`predictedAsPlanCollider` を読ませるか)は未決のまま

宣言だけ足されて誰も読んでいない状態が続いている。現状は「予測列を持っている物体が
たまたま計画の衝突体になる」という副作用で決まっており、弾・自艦・基地・弾薬が
計画線の終端相手になっている。**目に見える挙動変更なので判断が要る。**
私の見立ては v2 と変わらず「読ませるべき」。

## 判断4: v2 の判断3(予測要否のフレーム可変ゲート)の範囲

A-4 が残っている以上、これが次に効く。範囲 (i)(予測線を描いていない個体だけ止める)と
(ii)(表示時刻が現在を指している間は `predictedForGhost` を成立させない)の選択は未決。

**外挿を入れたことで (ii) の代償が変わった。** v2 は「止めた個体はスライダを引いた瞬間に
伸び切っていない」ことを懸念していたが、いまは外挿が繋ぐので**位置は答えられる**
(精度は落ちる)。(ii) を採りやすくなっている。

## 判断5: 測る条件を足すか

いまの6条件は B-2(28日プリセット)も B-3(自艦複数)も B-4(軌道線トグルを開く・
敵の多いステージ)も突いていない。**足すぶんだけラウンド時間が伸びる**
(現行6条件 × 5ラウンドで片側おおよそ10分)ので、どこまで足すかは判断が要る。

## 判断6: v2 の判断4(月近傍の dt² 誤差)・判断5(A-0)は持ち越し

どちらも今回動いていない。A-0 は依然として最大の単一項目。

# 第4章 これからの作業計画

**順序は「測れるようにする → 効果が大きい順 → 正しさに関わる判断」。**
