# OrbitLine の表示条件の散在 — 実施済み

予測が表示期間に届かないときに解析楕円へ切り替える機構を廃し、線の末尾をケプラー外挿で継ぐ形へ
置き換えた。「フォールバックするか」の判断が `TrajectoryLine` → `GameEntity` → `EntityManager` →
`OrbitLine.setSuppressed` と3モジュールを貫いていた整合性保持責務の漏洩は解消した。

## 出発点の誤り(記録)

最初の分析は「概念として軌道線を持つ物体が積分線に代替される」と書いていた。逆で、実際は
**積分線を出したい物体が、出せないときに OrbitLine へフォールバックする**。正常系は積分線、
異常系が楕円。この取り違えが「楕円の側に抑制フラグを立てる」という原因と結果が逆の API を
正当化していた。

2版目は「外挿を `at()` に入れると近似が物理へ混入する」として `DynamicTrajectory` への配置を
退けたが、これも誤り。比較対象が「近似 vs 正確」ではなく **「近似 vs 天体まるごと欠落」**
だった(`plan-attractors.ts` の `if (state === null) continue;` はその天体の引力を 100% ゼロにする)。
`simulation/attractors.ts` の「現在位置で凍結すると『その時刻に居ない場所』から引くことになる」
というコメントは**凍結への反論**であって、外挿への反論ではなかった。

| コミット | 内容 |

| `feat: 予測線の末尾をケプラー外挿で継ぎ、解析楕円への切替を廃す` | `TrajectoryLine` が末尾を継ぐ。`supersedesAnalyticEllipse`/`setSuppressed`/`Player.orbitLine` が消える |
| `feat: 計画・予測の重力源を、落とさずケプラー外挿で埋める` | `displayState(t, ephemeris?)`。計画・予測の重力源解決が外挿を使う。あわせて積分対象の自己除外 |
| `refactor: 軌道線を描くかの判断を1箇所へ集める` | `EntityManager.syncOrbitLines` へ集約。`syncOrbitLine` の `show` 引数が消える |

### 確定した設計

- **中心天体の候補は解析天体に限る**(`id in ephemeris.registry`)。動的重力源を中心にすると
  その位置が `displayState` 経由になり再帰と処理順依存が生まれる。**候補から外す**ことで
  「中心が決まらないから外挿しない」という縮退自体が無くなり、中心は必ず `positionOf` で引ける。
- **先端時刻の中心天体は追加コストゼロで得られた。** `predictor.ts` が刻み幅のために毎ステップ
  呼んでいた `localOrbitPeriod` の内部が `strongestAttractor` なので、それを1回に共有した。
- **問い合わせ時刻の中心位置は呼び出し側が渡す。** `DynamicTrajectory` は `Ephemeris` を持たない。
  物理側の呼び出しは同じ `t` の解析天体窓を先に引いているので、中心の `stateOf` は中間キャッシュに
  当たり追加の暦引きは実質発生しない。
- **外挿は明示オプトイン。** `at()` の既定の挙動は不変で、`PlanArc` は中心天体を渡さないので
  天体貫入で打ち切られた区間が外挿されることはない。
- **再 bake の条件**: 外挿区間を持たないときは従来と完全に同一。持つ間だけ、`to` が外挿1サンプル
  ぶんの間隔以上動いたときに焼き直す(`to` は毎フレーム動くので、素直に条件へ足すと毎フレーム
  焼き直しになる)。

### 途中で覆した判断

- **自己引力は除いたが、当初書いた理由は誤りだった。** 「距離が 0 に寄ると発散しうる」と
  書いたが、`attractorAccel` は距離 1m 未満の直達項を落とすので発散しない。さらに一覧は
  先端時刻ちょうどで組むため自分自身は距離ちょうど 0 になり、`strongestAttractor` に
  選ばれることもない。**この変更で観測できる挙動は何も変わっていない。**
  正しい理由は「自分の引力を自分に加算しない」という一点で、`attractorsNearInto` に除外 id を
  足す形にした(`Simulator.substep` にも同じ構造が元からあったのでそちらも塞いだ)。
  除外は各自の取り出しにしか効かないので相互作用の対称性は崩れない。
  `mu === 0` の個体は一覧に載り得ないので、除外の走査ごと省いている。
- **`Targeter` の2本の `OrbitLine` は残す。** 当初案の「エンティティ自身の線を役割で塗り替える」は
  成立しない — 自機は `orbitLine` を持たなくなり、戦闘ビューでは `Predictor` が操作艦しか
  予測しないので非操作艦には予測線も無い。ターゲットのハイライトを描けるのは `Targeter` 自身の
  線だけになる。
- **双曲線ソルバは入れない。** `OrbitLine` は元から `e >= 0.98` で線を消すので、外挿しなくても
  回帰にならない。`DEVELOP/SPEC.md`「実装される可能性のある機能」へ記録した(順方向の
  `timeSincePeriapsis` は既に双曲線を扱っているので、欠けているのは逆方向の Newton 法だけ)。
- **`OrbitLine.sync` の `force` は残す。** 「渡す呼び出し側がもう無い」という私の前提が誤りで、
  `creative-stage.ts` の配置プレビューが `true` を渡していた(閾値未満の編集でも毎フレーム
  焼き直させるため)。

## 残っている論点

- **外挿区間の `positionOf` コスト**は既定の表示期間についてだけ測った(perf memo v3)。
  `map ×1 node1` の暦ミスが 2584 → 2736/2888 と 6〜12% 増えるが、frame には現れていない。
  **28日プリセットでの焼き直し頻度は未計測。**
- **`predictionCoverage` は4値になった。** 打ち切られた列だけは外挿できず個体ごと一覧から
  落ちるのに、3値では「届いていない」と区別が付かず `PlanArc` が古い積分を保持していた。
- **`TrajectoryLine` の容量**: マップビューでは非操作艦も予測線を持つ。1本 16384 頂点
  (`OrbitLine` は 4096)で、`MAX_PLACED_SHIPS` は 50。種別ごとに容量を変えられるようにするかは
  実測してから。
- **`Enemy`/`Base` は閉じた解析楕円のまま**なので、自機だけが「表示期間ぶんの前向きの弧」になる。
  既定プリセット(1周期)では一致するが、期間を変えると揃わない。
- **perf memo v2 の A-4**(高ワープのマップビューで予測が毎フレーム全個体破棄され1体も完成しない)
  は未解決。外挿の前提条件ではないが、残っていると外挿区間が毎フレーム大きく揺れる形で見える。
