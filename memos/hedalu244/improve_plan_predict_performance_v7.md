# 計画・予測の負荷改善 v7 — 統一予測弧を前提とした実施計画

計画と予測の積分は統一積分弧(`game/simulation/predicted-arc.ts` の `PredictedArc`)へ統合済みで、
負荷の主戦場は「弧が1歩ごとに払う天体窓の値段」へ移った。この文書は、その現状を前提として
残る改善案を優先度順に並べ、第三者がそのまま実装へ着手できる粒度で記述する。

最優先は**案1(弧ごとの天体リスト化 — 暦を必要な天体だけ引く)**。実測で1歩の値段の98%超が
天体窓の構築であり、統一予測弧には Simulator のような同時性(1回組んで全員で使い回す)が
無いため、「全数を組んで返す」暦の窓口そのものを置き換える必要がある。

# 第1章 現在の前提と問題構造

## 1-1. 二つの経路と同時性

実行時に軌道積分を回す経路は2つに統合されている。以下、**N = 重力/衝突天体数、
M = 積分対象の物体数、k = 1フレームのサブステップ数/歩数**とする。

| 経路 | 何を積分するか | 天体窓の引き方 | 同時性 | 実効オーダー |
|---|---|---|---|---|
| `Simulator`(`game/simulation/simulator.ts`) | 全エンティティの実状態 | サブステップ中点で1回窓を組み(`simulator.ts:198`)、`classifyAttractors` で分類して全エンティティが `attractorsNearInto` で近傍を引く | **同一時刻** — 窓1回を M 体で共有 | **O(k(N+M))** |
| 統一予測弧 `PredictedArc`(`game/simulation/predicted-arc.ts`) | 実体の予測列 + 計画区間(どちらも同じクラス) | 1歩 = 中点1時刻で `FutureAttractors.at(t)` を1回(`predicted-arc.ts:105`、前歩の窓は `carriedSources` で持ち越し) | **弧ごとに別時刻** — 窓を共有できない | **O(kNM)** |

**この2経路は問題の形が逆で、同じ手が効かない**:

- `Simulator` は **M が多い代わりに同時性が使える**。窓の構築+分類(O(N))はサブステップに
  1回で、M 体はその結果を共有して近傍だけを読む — だから O(kN + kM) = **O(k(N+M))** に
  既に落ちている。N・M 側にこれ以上削る構造は無く、残る改善は **k の調整**(warp に比例して
  上限328まで張り付く固定床、1-3)で十分に効く(→ 案5。終点窓の重複だけは別途 1-4 → 案3)。
- 統一予測弧は **k が大きく M が小さい**(弧は通常数本、歩数は予算300/frame)問題なのに、
  弧ごとに毎歩 O(N) の全数窓を組むため **O(kNM)** になってしまっている。同時性が無いので
  Simulator 式の共有では落ちない — **N をリスト(~15体)へ落とす方向で是正する**(→ 案1)。
  1フレームの総歩数 kM は予算で頭打ちだが、その予算1歩ごとに O(N) を丸ごと払っているのが
  歩単価 0.7〜1.0 ms の正体である。

`FutureAttractors.at(t)`(`game/simulation/future-attractors.ts:131-158`)は毎回、
`ephemeris.attractorsAt(t)` を**全101体**で呼び、衝突体配列(101体+動的衝突体)・`collisionById` Map・
重力源配列(mu≠0)・動的重力源(生存エンティティの `displayState(t)` 走査)・`classifyAttractors`
(ソート+SpatialGrid 構築)を**その場で全部組み直す**。結果を保持するキャッシュは無い
(弧の1歩が引く中点時刻は毎回一意で、同じ時刻を引き直す読者がいないため)。

つまり統一予測弧の1歩の構造は:

1. `FutureAttractors.at(中点t)` — 全数窓の構築+分類。**ここが1歩の値段のほぼ全部**(1-3)
2. `strongestAttractor` ×2(重力側・解析側、それぞれ全走査)
3. `stepDt` の接近項 — **衝突候補101体を全走査**(`predicted-arc.ts:133-151`)
4. RK4 本体 — こちらは `attractorsNearInto` で絞った ~15体+近傍しか読まない(`predicted-arc.ts:106-110`)
5. `ApsisTrack.observe`(通常 O(1))
6. `checkImpact` → `reachedBody` — **衝突候補101体へ掃引判定**(`predicted-arc.ts:157-164`)

**積分そのもの(4)は既に絞られている。毎歩払っているのに捨てているのは、窓の構築と
分類(1)と、衝突側の全数走査(3・6)である。**

## 1-2. 暦(Ephemeris)の窓口の現状

- 登録天体は**101体**(恒星1・planet 49・satellite 51)。うち **mu≠0 は65体**、mu=0(質量未実測)が36体。
- **天体1つぶんの `Attractor` を引く公開 API が無い。** `attractorAt(id, t)` は private
  (`physics/ephemeris.ts:541-547`)。`stateOf`/`positionOf` は `KinematicState`/`Vec3` しか返さない。
  `Attractor` 一式(mu・radius・degree2・isStar 込み)が要る呼び出し側は、
  `attractorsAt(t)`(101体)/`gravityAttractorsAt(t)`(65体)で**必ず全数**を組むしかない
  (`ephemeris.ts:526-538` — ミス時 `this.ids.map(...)`)。
- 時刻キャッシュは `TimeRing` 32段・**時刻の厳密一致**(`ephemeris.ts:64,83-92`)。
  サブステップ中点や弧の中点時刻は毎回一意なので**原理的に当たらない**。
- 高精度パック(Chebyshev)の収録は **11体**(太陽・水金地火木土天海・冥王星・月)。
  残り90体は解析経路。収録外の衛星は「precise の親 + 解析の惑星相対モデル」で合成される
  (`ephemeris.ts:317-321`)。解析経路の惑星は重心補正のため**その惑星の全衛星**を評価する
  (`ephemeris.ts:268-291`)が、8惑星+冥王星は全て pack 収録なのでこのファンアウトが起きるのは
  pack 非収録の解析惑星だけ — 現レジストリで衛星を持つのは quaoar/orcus/didymos(各1衛星)のみ。
- `OriginCenteredEphemeris.stateOf` は **body と origin(地球)の2回**を毎回引き、origin 側に
  キャッシュが無い(`physics/absolute-ephemeris.ts:45-55`)。全数窓の構築でも pack 収録11体ぶん
  origin を重複評価している。
- `degree2At`/`orientationOf` はキャッシュ無しで `attractorAt` ごとに再計算(`ephemeris.ts:511-521,
  485-507`)。ただし `pole` を持つ天体は11体、`degree2` を持つのは2体(地球・月)で、いずれも定数時間。

## 1-3. コストの実測台帳

**node マイクロベンチ**(`tests/perf/exp3-gravity-cost.ts`、毎回異なる t でリングキャッシュを外す):

| 操作 | 実測 |
|---|---|
| `attractorsAt(t)`(101体) | **976.12 µs** |
| `gravityAttractorsAt(t)`(65体) | **747.94 µs** |
| `classifyAttractors` | 37.35 µs |
| `attractorsNear`(always 15体 + 近傍) | 0.92 µs |
| **`stepDynamics`(RK4 物理そのもの、64体固定)** | **11.56 µs** |

**⇒ 予測1歩の値段の98.8%は暦の窓であって、積分ではない**(窓+分類 1013 µs 対 積分 11.6 µs)。

node は pack(fetch 必須)を読めず**101体すべてが解析経路**を通るので、pack 収録11体が
二分探索+Clenshaw で済むブラウザより窓が高く出る。窓と積分の比の構造を見るのが node の役割で、
歩単価の絶対値はブラウザで測る。

**ブラウザ実測(perf-probe)**: 条件ごとの値は第3章の基準表(3-3)が正本。要点だけ:

- 統一弧の歩単価: **~0.7〜1.0 ms/歩**(101体窓の解決+分類+掃引到達判定込み)。
  `ARC_STEP_BUDGET` = 300 なので、成長中の予測・計画が1フレームに使うのは **~210〜300 ms** まで。
- `積分` はエンティティ0体でも **1.32 ms/substep**(下記 1-4)。×65536 の 328 substep で
  **434 ms** — 実体が1体も無くてもこれだけ払う。
- **`積分` が `予測` を大きく上回る**: ×65536 の stage1 で `積分` 514〜684 ms 対
  `予測` 122〜203 ms(4〜6倍)。フレーム時間は 0.5〜1.0 秒で、要求ワープには遠く届いていない。

**サブステップ数は上限に飽和している**: `dt = min(dtRaw, 0.1)` と `SUBSTEP_MAX_DT` = 20 s から、
1フレームの substep 数の上限は `ceil(0.1 × warp / 20)` — fps に依らない固定値。

| warp | substeps/frame 上限 |
|---|---|
| ×1024 | 6 |
| ×16384 | 82 |
| ×65536 | **328** |
| ×131072 | 656 |

×65536 の実測 328 はこの上限そのもの。高ワープの重さは発散ではなく固定床で、重くなるほど
「実効ワープが要求に届かなくなる」(×65536・2fps → 実効 ×13,107)。

## 1-4. Simulator は1サブステップに窓を2回組んでいる

`Simulator.advance` のループは、1サブステップあたり別々の窓を2回引く:

- **中点で重力窓**(65体+動的重力源): `substep()` 内 `attractorsAt(ephemeris, entities, simTime + dt/2)`
  (`simulator.ts:198`)。分類して全エンティティで共有 — こちらは既に最適な形。
- **終点で全天体窓**(101体): `advance()` 内 `attractorsNow = this.ephemeris.attractorsAt(this.simTime)`
  (`simulator.ts:94`)。消費者は `contactPhysics.resolveSubstep`(高ワープでは
  `resolveCollision` が偽で呼ばれない)と `entities.cleanup` の `checkLoss` の2つだけ。

**⇒ ×4 を超えるワープでは、101体の窓は表面接触判定(`checkLoss`)のためだけに毎サブステップ
組まれている。** node 値では `747.94(中点65体) + 37.35(分類) + 976.12(終点101体) = 1.76 ms/substep`。
ブラウザ実測は 1.32 ms/substep(エンティティ0体、`軌道積分数` = 0 なので**ほぼ全部が窓**)で、
pack 収録11体ぶんブラウザが速いことと整合する — **その半分強が終点の101体窓**(→ 案3)。

## 1-5. 表示側の現状 — 線は消費者駆動になっている

- 軌道線・予測線・過去線の出し消しは `game/entity-line-manager.ts` の `EntityLineManager` が
  外部から `showOrbitLine(style)`/`showPredictedLine(style)`/`showActualLine(style)` を呼んで決める。
  線を出す・消す判断はエンティティ自身にもビューにも埋まっていない。
- **戦闘ビューの操作艦は解析楕円で描かれ、予測線は描かれない**(`entity-line-manager.ts:41-47` —
  `ownEllipse`)。予測線が出るのはマップビューだけ。
- `GameEntity.predictsFuture` は「未来が読まれる理由」4つの畳み込み(`game-entity.ts:109-112`):
  `predictedAsGravitySource`(mu≠0)/ `predictedAsPlanCollider` / `predictedForGhost` /
  `predictedLine !== null`。ゴーストは戦闘ビューでは `forceCurrent` により
  `displayTime === simTime` へ固定され、予測を読まない。
- **一方 `Predictor` の伸長対象と予算はビューで分岐したまま**(`predictor.ts:59-66,72-87`):
  マップは全対象を `ARC_STEP_BUDGET`(300)、戦闘は「操作艦+重力源/衝突体」を
  `ARC_COMBAT_STEP_BUDGET`(128)で伸ばす。**戦闘ビューの操作艦の予測には読み手が1つも無い**
  (線は解析楕円、ゴーストは現在固定、mu=0 なので重力源でもない)のに、毎フレーム128歩
  (~123 ms)を払い続けている(→ 案2)。
- `Player.behave` は噴射中(`thrust` 非 null)毎フレーム `invalidatePrediction()` を呼ぶので、
  **低ワープで実際に飛ばしている最中も、戦闘ビューでは毎フレーム128歩を捨てて積み直している。**
- 乖離判定(`discardPredictionIfDiverged`)はビューに依らず毎フレーム全対象
  (`predictor.ts:49-57`)。ここは1フレームに1回 `gravityAttractorsAt(simTime)` + 分類1回で済んでおり、
  リングキャッシュにも当たる(同一フレーム内は同じ simTime)。

## 1-6. 済んでいて、この文書が前提として扱うもの

- 計画と予測の積分・衝突検出は `PredictedArc` に統一済み。ノード0本の計画区間は自機の弧の
  借用(`PlanPath` の `SegmentSource`、再積分なし)、ノード設置後の区間は予算成長
  (設置フレームの同期スパイクは存在しない)、`represents()`(revision・間引き下限・state0 参照
  同一性)による弧の使い回し。
- 刻みと予算の定数は遠端誤差の実測で決定済み: `ARC_MIN_STEP_DT` 20 / `ARC_STEPS_PER_REV` 300 /
  `ARC_MAX_STEPS` 20000 / `ARC_STEP_BUDGET` 300。根拠: 28日プリセットの LEO で位相誤差は
  数千 km 出るが**閉軌道の重ね描きでは見えず**、形の誤差(Δa)は −6.9 km = 全周表示で 1px 未満。
  刻み下限20 s は低月周回の1周あたりドリフト(0.71 km)が乖離許容(500 m)と釣り合う点で決まって
  おり、月が決めている。
- 重力の絞り込み定数: `GRAVITY_ALWAYS_COUNT` = 15 / `GRAVITY_NEGLIGIBLE_ACCEL` = 1e-8 m/s²。
  `always` の15体は「これ以上減らすとグリッドのセル一辺が破綻する」水準でほぼ最適
  (木星を grid へ落とすとセル一辺 3.6e12 m = 24 AU で太陽系全体が1セルになる)。
- 予測・計画の予算パスは `Game.update` 本流で無条件(ポーズ中・決着後も伸びる)。

## 1-7. 問題の再定式化

三つの独立な浪費が残っている:

1. **統一予測弧の1歩が、~15体しか積分しないのに101体の窓を組んで捨てる**(1-1, 1-3)。
   同時性が無いので Simulator 式の共有は使えない。**解は「必要な天体だけ引く」**(案1)。
2. **読み手のいない伸長**(戦闘ビューの操作艦、1-5)に予算を払っている(→ 案2)。
   **完成し得ない伸長**(1フレームの時間送りが表示期間を超える高ワープ)も残っているが、
   表示を解析楕円へ切り替える解は却下済みで、表示を変えない解決策は未定(→ 案4 の記録)。
3. **Simulator の1サブステップが、高ワープでは消費者が `checkLoss` しかない101体窓を
   毎回組む**(1-4)。substep 数自体も固定床に張り付いている(案5)。

## 案1 弧ごとの天体リスト化 — 暦を「必要な天体だけ」引く【最優先】

### 趣旨

統一予測弧の1歩の値段の98%超は天体窓の構築であり(1-3)、その窓の中身のうち積分が実際に
読むのは ~15体+近傍(RK4 は既に絞られた配列を受けている、1-1)。残りは「組んでから捨てる」
ためだけに毎歩全数評価されている。暦が「全数を組んで返す」窓口しか公開していないことが
問題の本質で、同時性の無い統一予測弧では全数キャッシュも原理的に当たらない。

**各弧が「重力を加味する天体の id リスト」と「要衝突監視の id リスト」を保持し、暦へは
リスト内の天体だけを単体問い合わせする。** リストの正しさは低頻度の巡回(または期限つき
再訪)で維持する。弧ごとに独立して解けるので、Simulator 式の空間グリッドは組まない。

### リストの契約

- **重力リスト**: 成員は「その弧の現在位置で `|attractorAccel|` が `GRAVITY_NEGLIGIBLE_ACCEL`
  (1e-8 m/s²)以上でありうる天体」。**既に定数化されている「無視してよい重力の大きさ」に
  そのまま準拠する** — `always`/grid の種別(Simulator の同時多物体用の機構)はここでは使わない。
  `attractorAccel` は ECI 原点補正項込みなので、月のような「遠いが原点補正が大きい」天体は
  自動的に成員に残る(位置非依存の項だから)。閾値にはヒステリシスを持たせる
  (追加は ε 以上、除去は ε の数分の1未満)。**リストは空にしない** — 最強天体
  (中心解決・外挿・アプシス検出が要る)は寄与が ε を割っても残す。
- **衝突監視リスト**: 候補天体(mu=0 の表示天体36体を含む全101体+動的衝突体)のうち、
  「近い将来に表面へ届き得るもの」だけ。判定は距離−半径和と相対速さの上限から出る
  **保守的な最短到達時刻**で行い、その時刻までは再訪しなくても接触し得ないことを保証する。
  重力よりはるかに厳しく絞れる — LEO の艦にとって監視対象は実質、地球1体。

積分に入る天体集合は現行(`always` 15 + グリッド近傍)とほぼ同じ ε 基準の切り捨てなので、
**物理入力はほぼ変わらない。変わるのは集合の求め方**(毎歩の全数構築+分類 → 保持リスト+
単体問い合わせ)である。現行の `always`/grid も予測(弧)と実状態(Simulator)で微妙に違う
集合を積分しており、差は ε 級寄与の出入りだけ — 加速度差 ~2ε が1周(5580 s)積もっても
`½·2ε·T² ≈ 0.3 m` で、乖離判定の許容(500 m + 補間誤差ぶんの拡大)より2桁小さい。
**乖離破棄ループを新たに招く構造ではない。**

### リスト維持のアルゴリズム

比較した3案:

| 案 | 内容 | 判定 |
|---|---|---|
| 低頻度の全数走査 | 数秒に一度、全天体を走査してリストを全更新 | **不採用**。負荷がスパイクし、フレーム単位の測定も困難になる |
| **巡回 + 閾値**(採用の基底) | リスト外の候補を毎歩1〜3体ずつ巡回評価して追加判定。リスト内は評価がほぼ無料(中点解決時に `\|attractorAccel\|` を1体1回計算するだけ)なので、閾値を割ったら落とす | **重力側はこれで足りる**。mu≠0 の65候補を3体/歩なら22歩で1巡。重力場が ε を跨ぐ変化は天体への接近で起き、その接近には日単位かかる(月の ε 到達距離 `sqrt(μ/ε)` = 2.2e10 m を横切るのに km/s で数百日)ので、巡回1周ぶんの遅れで取りこぼす寄与は高々 ε 級・短時間 |
| **期限つき再訪**(衝突側は必須) | 巡回の順番を固定周期でなく候補ごとの期限で決める。訪問時に「この天体は最短でもあと t_safe 秒は効き得ない」を保守的に計算し、期限が来た候補だけ再評価する | **衝突監視はこれで正しさを構成的に保証する**(巡回だと高速フライバイのすり抜けを原理的に否定できない)。期限式の例: `t_safe = (距離 − 半径和 − 余裕) / (現在の相対速さ × 安全率 + 加速余裕)`。LEO から見た月なら `~3.8e8 m / 2e4 m/s ≈ 5時間` — 28日プリセットの dt=121 s でも ~160歩に1回の再訪で済む |

**推奨: 重力・衝突とも期限つき再訪の1機構に載せ、期限式だけを別にする**(重力側の期限は
「ε に届き得る最短時刻」、届かない遠方天体は長い期限がつき自然に訪問頻度が下がる)。
実装を単純にしたければ重力側は固定巡回でもよい — 上の誤差論証が成り立つ範囲で。

弧同士で巡回予算を分配・平滑化する必要は現時点では無い: 巡回1歩ぶんのコストは単体問い合わせ
1〜3回(数 µs)で、弧の数(通常 ≤10)を掛けても誤差の範囲。多数弧で巡回コストが実測に出たら
そのとき検討する。

### 動的天体(重力を持つエンティティ・衝突体)の扱い

候補集合は「レジストリの101体」+「生存する `predictedAsGravitySource`/`predictedAsPlanCollider`
エンティティ」。動的個体の位置解決は `displayState(t, ephemeris)`(外挿込み)で、これは
現行 `resolveAt` の per-entity ロジックをそのまま単体窓口へ切り出す。ロースターの増減は
`EntityManager.collectionRevision` の変化で検知し、新規 id を「期限即時」の候補として足す。
**`FutureAttractors.at(t)` が毎歩払っていた生存エンティティ全走査(debug-load の小惑星300体で
`displayState` 48万回/frame 実測)も、リスト成員+期限到来ぶんだけに縮む** — 本案は
「窓が小さい条件では窓を、動的個体が多い条件では走査を」切る同じ1つの機構である。

  しか無く、上位15体はすべて pack 収録かその衛星)。ブラウザ倍率込みで

- **効く範囲が最も広い**: ワープ帯・ビュー・ノード有無を問わず、弧が伸びるすべての瞬間に効く。

## 案2 伸長対象を「消費者の有無」から導出する — ビュー分岐と戦闘予算の廃止

### 趣旨

線の表示は既に消費者駆動(外部から `showPredictedLine` を呼べば誰の予測線でも出る、1-5)なのに、
**伸長側だけがビューで分岐している**。予測を伸ばすべきかはビューの名前ではなく
「読み手がいるか」で決まるべきで、その理由は `GameEntity` が既に宣言している
(`predictedAsGravitySource` / `predictedAsPlanCollider` / `predictedForGhost` /
`predictedLine !== null`)。ゴーストが未来を読めるか(`forceCurrent` の否定)だけが
外から渡すべき残りの1量。

伸長対象を

```
predictedLine !== null || predictedAsGravitySource || predictedAsPlanCollider
  || (predictedForGhost && ghostReadable)
```

から導出すれば、マップビューの対象集合は現行と一致し、戦闘ビューでは
「解析楕円で描かれている操作艦」が自然に対象から外れる。**ビュー分岐と
`ARC_COMBAT_STEP_BUDGET` は削除できる**(コードは減る)。予測弧が1本も要らない状態の
コストは、明示的なオフではなく**対象集合が空になることで自然に0になる**。

### 期待される効果

- 戦闘 ×65536: `予測` **~41 ms(`pred歩` 128 × 0.32 ms)→ ~0**(通常ステージでは重力源/
  衝突体エンティティが0体なので対象集合が空)。
- **低ワープで噴射している最中**(戦闘ビュー): `Player.behave` が毎フレーム
  `invalidatePrediction()` を呼ぶため、毎フレーム128歩 ≈ **~41 ms/frame** を積み直していた —
  これも ~0。推進が効くのは ×4 以下だけなので、**実際に飛ばしている、最も応答性が要る
  瞬間に効く**。
- 乖離判定・`FutureAttractors` の revision は現行のまま(予測列が存在する限り正しさ維持は
  必要で、コストは1フレーム1回の窓+分類だけ)。

### 実現可能性

**高。** `predictor.ts:59-66` の対象集合と `:72-87` の予算分岐の書き換え+定数1個の削除。

## 案4 完成不能な予測の伸長ゲートと解析楕円への退避【却下 — 問題の記録のみ】

### 概要

1フレームの時間送り `simDt` が表示期間 `horizon` を超える条件では、予測が答えるべき窓が
毎フレーム丸ごと入れ替わるので、**予測は原理的に完成しない**(×65536・1周プリセットで
比 6553.6/5580 = 1.17。実測でも `pred-discard` が毎フレーム全対象・`pred-complete` 0・
`pred-steps` が予算張り付き)。この案は、その条件で実体弧の伸長を止め、その間マップの
予測線を解析楕円で描く(表示の退避先は `EntityLineManager` の `ownEllipse` と同じ経路)
というものだった。

### 却下理由

**絵が大きく変わる。** ワープを上げるたびにマップの予測線が解析楕円 — J2・第三体・抵抗の
下で積分軌道と半径が食い違う線 — へ置き換わるのは表示の大変更であり、許容しない。
予測が伸長し切らない問題は、**表示を変えない別の方法**で解決すべき。

### 残っている問題(未解決)

- ×65536・1周プリセットで、完成し得ない線に `予測` ~203 ms/frame(予算張り付き)を
  払い続けている。案1(歩単価3〜5倍)で額は ~15〜20 ms へ下がるが、
  「完成しないものに払う」構造そのものは残る。
- 毎フレームの全破棄→再成長で `samplesOldestFirst()` が新配列を返し続け、
  `TrajectoryLine` の参照同一性ガードが効かず `sync` 側の焼き直しも毎フレーム走る。
- 解決策を設計する際の制約を2つ記録しておく: (a) 「`predicted === null` になったら表示を
  切り替える」形は、低ワープでも噴射のたびに `invalidatePrediction()` が呼ばれるため
  1フレームのちらつきを生む。(b) 乖離判定は何があっても止めない — 止めると古い予測列が
  計画の重力源・衝突体として読まれ続ける。

## 案5 Simulator — 1フレームのサブステップ数上限

### 趣旨

`積分` の値段は「1フレームの時間送り ÷ 刻み幅 × 1サブステップの値段」。刻み幅の上限が
`SUBSTEP_MAX_DT` = 20 s の固定値なので、substep 数はワープ倍率に正比例し ×65536 で 328(1-3)。
**1フレームに許す substep 数の上限 K** を1つ足し、高ワープでは刻み幅の側を伸ばす。
再突入中の細分化(1 s)だけはこれに優先させる — 加熱と動圧の積分結果が艦の生死を決め、
それをプレイヤーが観測するため。

### 期待される効果(案3の前の値からの導出)

| K | ×65536 の substep 幅 | `積分` の見積り(434.4 ms から) |
|---|---|---|
| 328(現状) | 20.0 s | 434.4 ms |
| 128 | 51.2 s | 170 ms |
| 64 | 102.4 s | 85 ms |
| 32 | 204.8 s | 42 ms |

案3と乗算的(案3後は 1 substep が ~0.3 ms になり、この表の値も概ね半分)。
**×1024 以下では substep が既に少なく効かない。高ワープ専用の手。**

### 精度の代償 — 正直に書く

LEO の周期は 5,580 s。K=64 は 1周を55歩で刻むことになり、RK4 でも軌道要素が目に見えて動く。
**LEO に艦を置いたまま ×65536 で軌道精度を保つのは原理的に無理**で、これは
「×4 を超えると推進・射撃・敵AI・剛体衝突が既に無効 = 高ワープは待つための時間帯」という
既存の設計に「軌道積分の精度も落ちる」を足すかどうかの判断。

中間案: K をワープ倍率でなく「生存する艦の局所周期 / 歩数」から決める
(`adaptiveSimulationMaxStep` は既に艦の状態から上限を決める関数なので置き場はある)。
LEO に艦がいなければ(月周回・L点)自然に大きな刻みが許される。

### 実現可能性

**高。** `Simulator.adaptiveMaxStep()` の `normalMaxStep` 引数に
`Math.max(C.SUBSTEP_MAX_DT, simDt / K)` を渡すだけ。**`Math.max` を返り値側へ掛けては
いけない** — 再突入中の 1 s 上限まで押し上げてしまう。`normalMaxStep` 側へ入れれば
再突入優先が自動で守られる。`time-step.ts`(純関数)は無変更。

### 実装手順

| # | 内容 | 検証 |
|---|---|---|
| **5-1** | `const.ts` に `SUBSTEP_MAX_COUNT` を足す。初期値は挙動を変えない 400 | `npm run typecheck` |
| **5-2** | `adaptiveMaxStep()` に `simDt` を渡し、`normalMaxStep = Math.max(C.SUBSTEP_MAX_DT, simDt / C.SUBSTEP_MAX_COUNT)` | `npm run typecheck` |
| **5-3** | 値を決める。`?stage=creative` で LEO に艦を置き ×65536 で K = 328→128→64→32 を順に見る。**精度の許容は数値ではなく見た目で決まる**ので、軌道が視覚的に破綻する手前を採る。const のコメントには倍率でなく「×65536 の LEO で1周あたり何歩か」を書く | K ごとに perf-probe |
| **5-4** | 文書更新: CLAUDE.md の `Simulator` 節(「substep 数は fps に依らない」の記述に上限を反映) | `/develop-docs` |

### 必要な判断

- **高ワープで軌道精度を落とすことを許すか**(上記)。表示・体験の判断で、A/案1〜4 とは独立。
- **関連する既存の崖(この変更セットに含めない)**: 再突入中は maxStep が 1 s になるので、
  ×65536 では 6,554 substeps/frame ≈ 1フレーム数秒。K はこの崖に効かないし、効かせてもいけない
  (再突入優先は仕様)。「高ワープでは再突入する艦を待たない」は艦が焼けるかどうかの結果が
  変わる**仕様の判断**なので、`DEVELOP/SPEC.md` の「実装される可能性のある機能」節へ論点として
  記録するに留める。

## 案7 共有時刻グリッド掃引【保留】

### 趣旨

全個体の予測先端を共有の時刻グリッドで足並みそろえて進め、窓構築を M 体で1回にする —
問題構造の側を Simulator に寄せる案。効果は M に比例し、多数個体条件(小惑星300+破片500
規模)で桁の差になる。

### 保留の理由

- **案1が同じ条件の支配項を先に消す**: 窓構築の値段そのもの(リスト化で数分の1)と、
  動的個体の `displayState` 全走査(リスト成員のみに縮む)の両方。案1後にこの案の旨味が
  どれだけ残るかは実測してからでないと分からず、先にやると効果を過大評価したまま
  見た目を変えることになる。
- **代償が UX に出る**: 共有カーソルは「一定間隔で線が0から伸び直す」演出になり、噴射した
  瞬間に線が変わらないのは `invalidatePrediction()` の明示的な応答性要件と衝突する。
  やるなら操作艦だけ現行の個別方式を残す(操作艦は M=1 で共有の得が無く、応答性が観測される
  のも操作艦だけ)。
- **共有できるのは「窓を引く時刻」であって「刻み幅」ではない**: 刻みは個体ごとに局所周期で
  決まる(LEO 20 s、遠方小惑星は数千秒)。グリッドは最小刻みに合わせ、他の個体は間引いて
  踏む形になり、素朴な M 倍には届かない。

### 着手条件

多数個体のゲームプレイ(小惑星帯ステージ等)を本格化させ、かつ案1後の debug-load 実測で
予測が依然フレームの支配項であるとき。それまでは着手しない。

# 第3章 測定・検証方法

## 3-1. 読み方の規律

- **主指標は離散カウンタ**(`pred-steps`/`plan-steps`/`sim-substeps`/`pred-tracked`/
  `pred-complete`/`pred-discard`/`eph-attr`/`eph-all`)。ms はその帰結として読む。
- **1回の run の絶対値を信用しない。** 同一ビルド・同一条件でも run 間で `積分` が 17〜35% 振れ、
  最悪の条件では **2.7×** 違った(`creative ×65536 艦なし` が 434 ms と 1189 ms。後者はレンダラの
  クラッシュを挟んで2ラウンドしか測れていない run の値で、外れ値)。**行ごとに
  `measuredRounds` とラウンド間スプレッドを必ず併記し、スプレッドの大きい行は結論に使わない。**
- **比較は「同じ条件を、同じ並び順の同じ位置で測った run 同士」に限る。** したがって
  **条件マトリクスは run をまたいで固定する** — 条件を1つ減らすだけで後続条件の位置が前へ動く。
  歩単価(セクション ms ÷ 歩数)と、変更が触っていない行との比での正規化を併用する。
- **物理的に成り立たない大小関係が出たら、その run の値を疑う。** 例: エンティティ0体の
  `creative ×65536 艦なし` が、6体いる `stage1 戦闘 ×65536` より高い ms/substep を出したら、
  それは測定の外れ値であって発見ではない(`軌道積分数` が 0 対 1968 なのだから、前者が
  下回らなければおかしい)。
- ビルドと測定の間には数分の冷却を挟む。
- **セーブ復帰の混入**: プローブは Chrome プロファイルをマトリクス全体で使い回す。
  `AutoSave` が書いた(または起動リトライで時間を食ううちに書かれた)スナップショットは、
  同じステージの次の起動で `Launcher.initialSaveFor` に拾われる — `Stage.checkWin()` が常に
  false のステージでは `SaveSlots.noteRunEnded` が呼ばれず `lastStageId` が残り続けるので、
  一度書かれると以後ずっと復帰する。復帰した起動では `Stage.begin()` が `init()` を飛ばし
  (`stage.ts:169`)、**スナップショットに載らない種類のエンティティ(小惑星・破片)は
  世界から消える**(`snapshot-service.ts:79-95` / `entity-manager.ts:81-97` は
  players/enemies/ammos/bases しか往復しない)。
- **セクションの意味**: `予測` = 全ての弧の積分成長(計画の弧を含む。`Predictor.update` を包む)。
  `計画` = 区間列の組み立てと表示物の導出+`Targeter.updateEquatorNodes` 等+`PlanGuide.update` の
  合算(3箇所が同一セクションに enter/exit する)。`plan歩` は `Predictor` 計上の計画弧の歩数。
- ポーズ中・決着後も予測・計画は伸びる(予算パスは無条件)— settle 待ちで測る条件では
  この挙動を踏まえる。

## 3-2. 道具

**固定条件マトリクス**(この順で回す。3-1 のとおり並びは変えない):

- 計測環境の宿題(未解決のまま): A/B をラウンドごとに交互に回すプローブ(マシン速度
  ドリフト対策)、settle 自動判定。
