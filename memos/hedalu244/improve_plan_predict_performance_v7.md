# 計画・予測の負荷改善 v7 — 統一予測弧を前提とした実施計画

計画と予測の積分は統一積分弧(`game/simulation/predicted-arc.ts` の `PredictedArc`)へ統合済みで、
負荷の主戦場は「弧が1歩ごとに払う天体窓の値段」へ移った。この文書は、その現状を前提として
残る改善案を優先度順に並べ、第三者がそのまま実装へ着手できる粒度で記述する。

予測側の歩単価は案1(弧の天体一覧化)、実シミュレーションの終点全天体窓は案3、ワープ倍率に
正比例していたサブステップ数は案5(上限64)で片付いた。**最高ワープのフレーム時間は
0.7〜0.9 秒から 50〜90 ms(10〜18fps)になり、`積分` は残り 36〜49 ms**(3-3)。
残る案は効果の小さいもの(案6)、条件付きのもの(案7)、UX(案8)、および表示を変えずに
解く必要のある未解決問題(案4)だけ。

# 第1章 現在の前提と問題構造

## 1-1. 二つの経路と同時性

実行時に軌道積分を回す経路は2つに統合されている。以下、**N = 重力/衝突天体数、
M = 積分対象の物体数、k = 1フレームのサブステップ数/歩数**とする。

| 経路 | 何を積分するか | 天体窓の引き方 | 同時性 | 実効オーダー |
|---|---|---|---|---|
| `Simulator`(`game/simulation/simulator.ts`) | 全エンティティの実状態 | サブステップ中点で1回窓を組み、`classifyAttractors` で分類して全エンティティが `attractorsNearInto` で近傍を引く | **同一時刻** — 窓1回を M 体で共有 | **O(k(N+M))** |
| 統一予測弧 `PredictedArc`(`game/simulation/predicted-arc.ts`) | 実体の予測列 + 計画区間(どちらも同じクラス) | 1歩 = 中点1時刻で、弧が保持する一覧(`ArcBodies`)の成員だけを `bodyAt` で単体解決(前歩の窓は `carriedSources` で持ち越し) | **弧ごとに別時刻** — 窓を共有できない | **O(kM·L)**, L = 一覧長 ≈ 6 |

**この2経路は問題の形が逆で、同じ手が効かない**:

- `Simulator` は **M が多い代わりに同時性が使える**。窓の構築+分類(O(N))はサブステップに
  1回で、M 体はその結果を共有して近傍だけを読む — だから O(kN + kM) = **O(k(N+M))** に
  既に落ちている。N・M 側にこれ以上削る構造は無く、残る改善は **k の調整**(warp に比例して
  上限328まで張り付く固定床、1-3)で十分に効く(→ 案5。終点窓の重複だけは別途 1-4 → 案3)。
- 統一予測弧は **k が大きく M が小さい**(弧は通常数本、歩数は予算300/frame)問題で、
  同時性が無いので Simulator 式の共有は使えない。**N を弧ごとの一覧 L(実測 6体)へ落として
  是正済み**(案1)。1フレームの総歩数 kM は予算で頭打ちなので、残る費用は L に比例する。

統一予測弧の1歩の構造は:

1. `ArcBodies.resolve(中点t)` — 一覧の成員(実測 6体)を単体解決。期限が来た候補があれば追加訪問
2. `strongestAttractor` ×2(重力側・解析側、一覧を走査)
3. `stepDt` の接近項 — 一覧の衝突体を走査
4. RK4 本体 — 一覧の重力源を読む
5. `ApsisTrack.observe`(通常 O(1))
6. `checkImpact` → `reachedBody` — 一覧の衝突体へ掃引判定

## 1-2. 暦(Ephemeris)の窓口の現状

- 登録天体は**101体**(恒星1・planet 49・satellite 51)。うち **mu≠0 は65体**、mu=0(質量未実測)が36体。
- 天体1つぶんの `Attractor` を引く公開 API は `Ephemeris.attractorAt(id, t)`。全数窓
  (`attractorsAt(t)` 101体 / `gravityAttractorsAt(t)` 65体)は Simulator と表示系が使う。
- 時刻キャッシュは `TimeRing` 32段・**時刻の厳密一致**。サブステップ中点や弧の中点時刻は
  毎回一意なので**原理的に当たらない**。
- 高精度パック(Chebyshev)の収録は **11体**(太陽・水金地火木土天海・冥王星・月)。
  残り90体は解析経路。収録外の衛星は「precise の親 + 解析の惑星相対モデル」で合成される。
  解析経路の惑星は重心補正のため**その惑星の全衛星**を評価するが、8惑星+冥王星は全て pack
  収録なのでこのファンアウトが起きるのは pack 非収録の解析惑星だけ — 現レジストリで衛星を
  持つのは quaoar/orcus/didymos(各1衛星)のみ。
- `OriginCenteredEphemeris.stateOf` は origin 側を1スロットでメモ化しており、同一時刻で
  複数体を引くバッチでは origin の評価が1回で済む。
- `degree2At`/`orientationOf` はキャッシュ無しで `attractorAt` ごとに再計算。`pole` を持つ天体は
  11体、`degree2` を持つのは2体(地球・月)で、いずれも定数時間 — ただし一覧化で1歩の分母が
  6体まで縮んだので、歩単価に占める割合は上がっている(→ 案6)。

## 1-3. コストの実測台帳

**node マイクロベンチ**(`tests/perf/exp3-gravity-cost.ts`、毎回異なる t でリングキャッシュを外す):

| 操作 | 実測 |
|---|---|
| `attractorsAt(t)`(101体) | **976.12 µs** |
| `gravityAttractorsAt(t)`(65体) | **747.94 µs** |
| `classifyAttractors` | 37.35 µs |
| `attractorsNear`(always 15体 + 近傍) | 0.92 µs |
| **`stepDynamics`(RK4 物理そのもの、64体固定)** | **11.56 µs** |

全数窓の値段は積分そのもの(11.6 µs)の 87 倍で、**全数窓を組む経路がある限りそこが値段の
ほぼ全部になる**。Simulator はサブステップに1回だけ組んで M 体で共有するのでこれで釣り合うが、
弧は歩ごとに別時刻を引くので釣り合わない — 案1 が一覧化で解いたのはこの一点。

node は pack(fetch 必須)を読めず**101体すべてが解析経路**を通るので、pack 収録11体が
二分探索+Clenshaw で済むブラウザより窓が高く出る。窓と積分の比の構造を見るのが node の役割で、
歩単価の絶対値はブラウザで測る。

**ブラウザ実測(perf-probe)**: 条件ごとの値は第3章の基準表(3-3)が正本。要点だけ:

- 統一弧の歩単価: **0.025〜0.055 ms/歩**(一覧6体の解決+掃引到達判定込み)。
  `ARC_STEP_BUDGET` = 300 なので、成長中の予測・計画が1フレームに使うのは **~7〜17 ms** まで。
- `積分` はエンティティ0体でも **0.56 ms/substep**。×65536 の 64 substep で **35.9 ms** —
  実体が1体も無くてもこれだけ払う。中身はサブステップ中点の重力窓(65体+動的重力源)。
- **`積分` はまだ最大項だが桁が変わった**: ×65536 の stage1 マップで `積分` 49 ms 対
  `予測` 9 ms。フレーム時間は 50〜90 ms(10〜18fps)。

**サブステップ数は2つの上限の小さいほうで決まる**: 刻み幅から来る `ceil(0.1 × warp / 20)` と、
`SUBSTEP_MAX_COUNT` = 64。どちらも fps に依らない。

| warp | 刻み幅由来 | 実際の substeps/frame |
|---|---|---|
| ×1024 | 6 | 6 |
| ×4096 | 21 | 21 |
| ×16384 | 82 | **64** |
| ×65536 | 328 | **64** |
| ×131072 | 656 | **64** |

×16384 以上では回数が頭打ちになり、刻み幅の側が伸びる。高ワープの重さは発散ではなく固定床で、
重くなるほど「実効ワープが要求に届かなくなる」(×65536・11fps → 実効 ×7.2万相当)。

## 1-4. Simulator が1サブステップに引く窓

`Simulator.advance` は、1サブステップにつき窓を1つだけ組む — 中点(`simTime + dt/2`)の重力窓
(65体 + 動的重力源)。分類して全エンティティで共有し、剛体接触を解決しないワープ帯では
表面接触判定と `Player.stepEnvironment` の日照遮蔽もこの窓を使う(`surfaceBodies`)。
剛体接触を解決する帯だけ、接触相手に mu=0 の表示天体も要るので終点の全天体窓を追加で組む。

ブラウザ実測は **0.56 ms/substep**(エンティティ0体、`軌道積分数` = 0 なので**ほぼ全部が窓**)。
×65536 の 64 substep で 35.9 ms。

## 1-5. 表示側の現状 — 線は消費者駆動になっている

- 軌道線・予測線・過去線の出し消しは `game/entity-line-manager.ts` の `EntityLineManager` が
  外部から `showOrbitLine(style)`/`showPredictedLine(style)`/`showActualLine(style)` を呼んで決める。
  線を出す・消す判断はエンティティ自身にもビューにも埋まっていない。
- **戦闘ビューの操作艦は解析楕円で描かれ、予測線は描かれない**(`entity-line-manager.ts:41-47` —
  `ownEllipse`)。予測線が出るのはマップビューだけ。
- `GameEntity.hasFutureReader(canDisplayFuture)` が「未来が読まれる理由」4つの畳み込み:
  `predictedAsGravitySource`(mu≠0)/ `predictedAsPlanCollider` / `predictedForGhost` /
  `predictedLine !== null`。ゴーストだけが引数に依り、戦闘ビューでは `forceCurrent` により
  `displayTime === simTime` へ固定されて予測を読まない。
- `Predictor` の伸長対象はこの述語から出る。戦闘ビューでは操作艦の線が解析楕円・ゴーストが
  現在固定・mu=0 なので、通常ステージでは対象集合が空になり `予測` は 0。予算はビューに依らず
  `ARC_STEP_BUDGET` 一本。
- 乖離判定(`discardPredictionIfDiverged`)はビューに依らず毎フレーム全対象
  (`predictor.ts:49-57`)。ここは1フレームに1回 `gravityAttractorsAt(simTime)` + 分類1回で済んでおり、
  リングキャッシュにも当たる(同一フレーム内は同じ simTime)。

## 1-6. 済んでいて、この文書が前提として扱うもの

- 計画と予測の積分・衝突検出は `PredictedArc` に統一済み。ノード0本の計画区間は自機の弧の
  借用(`PlanPath` の `SegmentSource`、再積分なし)、ノード設置後の区間は予算成長
  (設置フレームの同期スパイクは存在しない)、`represents()`(revision・間引き下限・state0 参照
  同一性)による弧の使い回し。
- 刻みと予算の定数は遠端誤差の実測で決定済み: `ARC_MIN_STEP_DT` 20 / `ARC_STEPS_PER_REV` 300 /
  `ARC_MAX_STEPS` 20000 / `ARC_STEP_BUDGET` 300。根拠: 28日プリセットの LEO で位相誤差は
  数千 km 出るが**閉軌道の重ね描きでは見えず**、形の誤差(Δa)は −6.9 km = 全周表示で 1px 未満。
  刻み下限20 s は低月周回の1周あたりドリフト(0.71 km)が乖離許容(500 m)と釣り合う点で決まって
  おり、月が決めている。
- 重力の絞り込み定数: `GRAVITY_ALWAYS_COUNT` = 15 / `GRAVITY_NEGLIGIBLE_ACCEL` = 1e-8 m/s²。
  `always` の15体は「これ以上減らすとグリッドのセル一辺が破綻する」水準でほぼ最適
  (木星を grid へ落とすとセル一辺 3.6e12 m = 24 AU で太陽系全体が1セルになる)。これは
  Simulator の分類の話で、弧の一覧(`ArcBodies`)は同じ `GRAVITY_NEGLIGIBLE_ACCEL` を距離条件
  として使うだけで `GRAVITY_ALWAYS_COUNT` を読まない。
- 弧が引く天体の一覧化は済み(案1)。歩単価 0.025〜0.055 ms、一覧長は LEO で 6 体。
- 予測・計画の予算パスは `Game.update` 本流で無条件(ポーズ中・決着後も伸びる)。

## 1-7. 問題の再定式化

二つの独立な浪費が残っている:

1. **完成し得ない伸長**(1フレームの時間送りが表示期間を超える高ワープ)に予算を払っている。
   表示を解析楕円へ切り替える解は却下済みで、表示を変えない解決策は未定(→ 案4 の記録)。
   案1 で額が 203 → 6.9 ms になったので、優先度は下がった。
2. **再突入域では刻みが 1 s まで細かくなり、この細分化はサブステップ数の上限に優先する。**
   ×65536 では 6,554 substeps/frame ≈ 1フレーム数秒。上限を効かせれば軽くなるが、加熱と
   動圧の積分結果 = 艦が焼けるかどうかが変わるので、性能ではなく仕様の判断(案5 の末尾)。

## 案1 弧ごとの天体リスト化 — 暦を「必要な天体だけ」引く【実施済み】

### やったこと

- **`game/simulation/arc-bodies.ts` の `ArcBodies` を新設。** 1本の弧が引く天体の一覧を保持し、
  暦へは一覧の成員だけを単体で問い合わせる。成員は毎歩解決するついでに抜ける条件を見て、
  成員でない候補は「最短でもこの時刻までは効き得ない」期限(`nextVisitT`)が来たときだけ訪問する。
  重力・衝突の両方をこの1機構に載せ、判定式だけを分けた。
- **成員判定は距離の一本。** 重力は `min(問い合わせ位置からの距離, ECI 原点からの距離)` が
  `sqrt(2mu/GRAVITY_NEGLIGIBLE_ACCEL)` 以下(直達項 mu/d² と原点補正項 mu/D² の和が
  `2mu/min(d,D)²` を超えないことから来る保守的な上界)、衝突は距離が半径以下。どちらにも
  刻み幅の `ARC_BODY_LEAD_STEPS` = 4 歩ぶんの先読みを足す。期限は同じ余裕を
  `(相対速さ + 天体自身の速さ) × ARC_BODY_CLOSING_SAFETY + ARC_BODY_CLOSING_MARGIN` で割って出す。
- **ヒステリシスは持たせなかった。** 境界上の天体は期限が 0 になって毎歩訪問されるので、
  成員かどうかに依らず費用は「解決1回」で変わらない — チャタリングに費用が無いなら幅は要らない。
- **最も重い解析天体だけは寄与に依らず成員のまま**(`pinned`)。中心天体の解決
  (`strongestAttractor`)が空の一覧を引かないようにするため。
- 暦側は `Ephemeris.attractorAt(id, t)` を公開しただけ。加えて `OriginCenteredEphemeris` へ
  原点天体の1スロットメモを足した(同一時刻で複数体を引くバッチの重複排除)。
- `FutureAttractors` は候補の列挙(`candidates`/`candidateRevision`)と1体の解決(`bodyAt`)へ。
  全数窓を組む経路(`at`/`FutureSourcesAt`/`resolveAt`)は読み手が無くなったので削除した。
- seam 型 `FutureAttractorProvider`/`FutureBodyCandidate` は消費側の `arc-bodies.ts` へ置いた。
  `future-attractors.ts` は `EntityManager` を型参照するので、そこに契約を置いたままでは
  `PredictedArc` を node 単体でコンパイルできない(`plan.ts` の `DisplayDurationSource` と同じ理由)。

| 6. stage1 マップ ×1 28日 | 278 → 278 | 0.885 → **0.054** ms/歩 | 246.0 → **15.1** ms | 404 → 225 |

新設カウンタ: **`解決天体` = 1668/frame = 1歩あたり 6.0 体**(候補は101体)、**`期限訪問` = 0**。

### 分かったこと

- **歩単価は 16〜23 倍になった。** 見込み(3〜5倍)を大きく上回る。単体問い合わせの按分
  (976µs ÷ 101体)だけを見た見積りには、同時に消える費用が2つ入っていなかった —
  毎歩の `classifyAttractors`(mu の全ソート + SpatialGrid 構築)と、`reachedBody` の101体掃引。
  実測の per-body は 0.025ms ÷ 6体 = **4.2 µs/体**で、node 按分の 9.7 µs/体 と桁が合う
  (pack 収録天体はブラウザのほうが安い)。
- **一覧は 6 体で足りている。** LEO の艦の成員は太陽・地球・月と、距離条件を満たす惑星数体。
  `always` 15体に入っていた木星圏の衛星・海王星は、ECI での寄与が潮汐残差の ~1e-15 m/s²
  しかなく、落としても差が出ない(上の検証表)。
- **期限訪問が 0 だった。** 月ですら LEO からの期限は5時間ぶんあり、10秒程度の測定窓では
  1回も期限が来ない。巡回コストは実測に出る水準に無く、弧同士で巡回予算を分配する仕組みは
  当面要らない。
- **`積分`(Simulator)は無変更なので動かない。** `frame` の改善は `予測` ぶんで、`積分` が
  支配する条件(1・5)の増減は run 間のばらつきの中に埋もれている(3-1)。
- **`pred破棄` は条件2で毎フレーム全破棄のまま。** 案1 は歩単価を下げただけで、
  「完成しないものに払う」構造(案4 の残る問題)は手つかず。ただし払う額が 203 → 6.9 ms に
  なったので、この問題の優先度は大きく下がった。

### 残っている判断

- **CREATIVE で小惑星がいる戦闘ビューの上限復活**(案2 から持ち越し)は、歩単価が 23 倍に
  なったので不要になった公算が大きい — 300歩でも ~8 ms。`debug-load` で測ってから畳む。
- **`ARC_BODY_LEAD_STEPS` = 4 の妥当性は未測定。** 一覧に入る前に表面を跨ぐ取りこぼしは、
  重力の到達半径(地球で 2.8e11 m)が半径より桁違いに大きいおかげで mu≠0 の天体では
  原理的に起きない。危険が残るのは mu=0 の36体と小質量の動的個体だけで、そこは `exp7` の
  範囲外。高速フライバイを作る条件が出てきたら測る。

## 案2 伸長対象を「消費者の有無」から導出する【実施済み】

## 案3 Simulator — 終点の全天体窓を高ワープで組まない【実施済み】

### やったこと

- **`surfaceBodies(resolveCollision, gravityBodies)` が「このサブステップで表面を持つ相手として
  扱う天体」の唯一の規則。** 剛体接触を解決するワープ帯では、接触解決のために組む終点の全天体窓
  (mu=0 の表示天体も相手になる)をそのまま使い、解決しない帯では積分のために中点で組んだ重力窓を
  使い回す。「そのサブステップが既に持っている窓を使う」という一文に畳んだので、分岐は1つで済む。
- **窓の構築を `substep` から `advance` へ引き上げた。** `substep` は simTime を進める副作用を
  持っていたので、そこから窓という副産物を持ち出せない。時計は `advance` が進める形にし、
  `substep(dt, sources, passiveWarpLod)` は積分だけを行う。
- **`Player.stepEnvironment` にも同じ窓を渡す。** これが3つめの消費者だった(下記)。
- `stepPassiveWarpEntities` へ渡す窓も重力窓へ揃えた。mu=0 天体の寄与は恒等的にゼロなので
  物理は変わらず、動的重力源(小惑星)が加わるぶんだけ正しくなる。

### 実測(ブラウザ、×65536)

| 条件 | `積分` | 窓部(`積分`−`軌道積分`) | 窓部/軌道積分 | `frame` |
|---|---|---|---|---|
| 1. stage1 戦闘 | 380 → **158** | 231 → **20.1** | 1.55 → 0.15 | 393 → 168 |
| 2. stage1 マップ | 481 → **205** | 292 → **23.4** | 1.55 → 0.13 | 517 → 245 |
| 5. creative 艦なし | 724 → **152** | 439 → **1.7** | 1.54 → 0.011 | 761 → 173 |

等速帯(#3・#4・#6)は `resolveCollision` が真で従来どおりの経路なので、差はすべてばらつき。

ゲート測定(終点窓の構築を潰した切り分け)は 5ラウンドで `積分` 161 ms、完成した実装は 152 ms
(艦なし)で一致した。**サブステップ1回の値段は 2.2 → 0.46 ms。**

### 分かったこと

- **終点の全天体窓の消費者は3つあった。** `contactPhysics.resolveSubstep` と
  `entities.cleanup` に加えて、**`Player.stepEnvironment` が毎サブステップ独立に
  `ephemeris.attractorsAt(simTime)` を引いていた**(日照率の遮蔽体と恒星の取り出しのため)。
  `advance` 側だけを直した段階では、艦がいる条件で窓部がまったく減らなかった —
  艦のいない条件(#5)だけ 439 → 3.75 ms へ落ち、艦のいる条件(#1・#2)は 231 → 319 /
  292 → 334 と横ばいだった。**「同じ時刻の同じ窓を別の場所が引いていないか」は、消費者を
  数える前に grep で確かめる。**
- **窓部/軌道積分の比は run をまたいでも意味を持つ。** ms の絶対値は run 間で 1.5〜2倍
  振れるが、同じ run 内の2つのセクションの比は機械の速さに依らない。1.55 → 0.13 は
  この比で読んだ値で、ばらつきの影響を受けない唯一の指標だった(3-1 への追加規律)。
- **残る `積分` はほぼ全部が中点の重力窓**(#5 で 152 ms / 328 substep = 0.46 ms、
  `軌道積分数` = 0)。ここから先は窓を安くするのではなく、サブステップ数そのものを
  減らす手(案5)しかない。

### 割り切り(実施済みの仕様変更)

- 高ワープ中だけ、mu=0 の表示天体36体を相手にした再突入判定と日照遮蔽を失う。質量未実測の
  小天体へ突っ込んだ破片が消えないだけで、プレイヤーが観測できる差は実質無い。
- 中点窓は動的重力源を含むので、**表面接触と日照遮蔽の相手に `Asteroid` が加わる。**
- 中点時刻での天体据え置きは、`reachedBody` が `prevState → state` の区間を掃引する以上
  むしろ整合が良い(終点で据えるより偏りが小さい)。
- 等速帯(×4以下)の挙動は変わらない。

## 案4 完成不能な予測の伸長ゲートと解析楕円への退避【却下 — 問題の記録のみ】

### 概要

1フレームの時間送り `simDt` が表示期間 `horizon` を超える条件では、予測が答えるべき窓が
毎フレーム丸ごと入れ替わるので、**予測は原理的に完成しない**(×65536・1周プリセットで
比 6553.6/5580 = 1.17。実測でも `pred-discard` が毎フレーム全対象・`pred-complete` 0・
`pred-steps` が予算張り付き)。この案は、その条件で実体弧の伸長を止め、その間マップの
予測線を解析楕円で描く(表示の退避先は `EntityLineManager` の `ownEllipse` と同じ経路)
というものだった。

### 却下理由

**絵が大きく変わる。** ワープを上げるたびにマップの予測線が解析楕円 — J2・第三体・抵抗の
下で積分軌道と半径が食い違う線 — へ置き換わるのは表示の大変更であり、許容しない。
予測が伸長し切らない問題は、**表示を変えない別の方法**で解決すべき。

### 残っている問題(未解決)

- ×65536・1周プリセットで、完成し得ない線に予算を張り付かせ続けている。案1 で額は
  203 → **6.9 ms/frame** へ落ちたが、「完成しないものに払う」構造そのものは残る。
  額としてはもう `積分` の 1.4% でしかないので、優先度は低い。
- 毎フレームの全破棄→再成長で `samplesOldestFirst()` が新配列を返し続け、
  `TrajectoryLine` の参照同一性ガードが効かず `sync` 側の焼き直しも毎フレーム走る。
- 解決策を設計する際の制約を2つ記録しておく: (a) 「`predicted === null` になったら表示を
  切り替える」形は、低ワープでも噴射のたびに `invalidatePrediction()` が呼ばれるため
  1フレームのちらつきを生む。(b) 乖離判定は何があっても止めない — 止めると古い予測列が
  計画の重力源・衝突体として読まれ続ける。

## 案5 Simulator — 1フレームのサブステップ数上限【実施済み】

### やったこと

- `const.ts` に `SUBSTEP_MAX_COUNT` = 64 を足し、`adaptiveMaxStep(simDt)` が
  `normalMaxStep = max(SUBSTEP_MAX_DT, simDt / SUBSTEP_MAX_COUNT)` を渡す。
  **下駄は `adaptiveSimulationMaxStep` の通常時上限へ掛ける** — 返り値へ掛けると再突入中の
  1 s 上限まで押し上げてしまい、再突入優先が壊れる。`time-step.ts`(純関数)は無変更。
- 上限に達するのは ×16384 以上。×4096 以下では刻み幅が 20 s のままなので、挙動も費用も動かない。

### 値の根拠(node、`tests/perf/exp8-substep-accuracy.ts`)

×65536 の刻み幅で1日ぶん積分し、dt=1s の基準積分と軌道要素を比べた。

| K | ×65536 の刻み | LEO 1周の歩数 | LEO ΔPe | モルニヤ ΔAp | 低月周回 Δinc |
|---|---|---|---|---|---|
| 328 | 20.0 s | 278 | −0.00 km | −0.00 km | −0.014° |
| 128 | 51.2 s | 109 | −0.01 km | −0.09 km | −0.093° |
| **64** | 102.4 s | 54 | **−0.42 km** | **−2.0 km** | **−0.36°** |
| 32 | 204.8 s | 27 | −13.1 km | −52 km | −1.27° |
| 16 | 409.6 s | 14 | 発散 | −1075 km | −2.67° |

**判断の物差しは「見た目」ではなく実ドラッグとの比になった。** 基準積分そのものが、実際の
大気抵抗で1日に 14 km の近地点高度を失っている(420 → 406 km)。数値的な減衰をこれと比べると:
K=128 で 0.07%、**K=64 で 3%**、K=32 で 93%。K=32 は待つだけで艦が倍の速さで落ちることになり、
再突入で艦を失う時期がワープ倍率で変わってしまう。K=64 を採る。

### 実測(ブラウザ、×65536、substeps 328 → 64)

| 条件 | `積分` | `frame` | fps |
|---|---|---|---|
| 1. stage1 戦闘 | 158 → **40.2** | 168 → **51.9** | 18 |
| 2. stage1 マップ | 205 → **49.4** | 245 → **91.4** | 9.5 |
| 5. creative 艦なし | 152 → **35.9** | 173 → **56.6** | 15 |

×1 の条件(#3・#4・#6)は substeps 1 のままで、差はすべてばらつき。

### 分かったこと

- **1 substep の値段は 0.46 → 0.56 ms へ上がった。** 刻みが 5 倍長くなっても窓の構築費用は
  変わらないので、substep あたりの固定費が薄まらないぶん平均が上がる。線形の見積り(30 ms)は
  そのぶん楽観で、実測は 35.9 ms だった。
- **上限が効く帯は ×16384 以上。** ×4096 以下は `simDt / 64` が 20 s を割るので刻み幅が
  変わらず、精度も費用もそのまま。「高ワープは待つための時間帯」という既存の設計と、
  精度を落とす帯が一致している。

### 残っている崖(この変更では触らない)

再突入域(高度 200 km 以下、またはそこへ降下中)では刻みが 1 s になり、この細分化は上限に
優先する。×65536 では 6,554 substeps/frame ≈ 1フレーム数秒。上限を効かせれば軽くなるが、
加熱と動圧の積分結果が変わる = 艦が焼けるかどうかの結果が変わるので、性能ではなく仕様の判断。
`DEVELOP/SPEC.md`「実装される可能性のある機能」節へ論点として記録済み。

### 決めること

| 論点 | 現状 | 判断材料 |

## 案7 共有時刻グリッド掃引【保留】

### 趣旨

全個体の予測先端を共有の時刻グリッドで足並みそろえて進め、窓構築を M 体で1回にする —
問題構造の側を Simulator に寄せる案。効果は M に比例し、多数個体条件(小惑星300+破片500
規模)で桁の差になる。

### 保留の理由

- **案1が同じ条件の支配項を先に消した**: 窓構築の値段そのもの(一覧化で 23分の1)と、
  動的個体の `displayState` 全走査(一覧成員のみに縮んだ)の両方。この案の旨味がどれだけ
  残っているかは `debug-load` の実測を見てから判断する。
- **代償が UX に出る**: 共有カーソルは「一定間隔で線が0から伸び直す」演出になり、噴射した
  瞬間に線が変わらないのは `invalidatePrediction()` の明示的な応答性要件と衝突する。
  やるなら操作艦だけ現行の個別方式を残す(操作艦は M=1 で共有の得が無く、応答性が観測される
  のも操作艦だけ)。
- **共有できるのは「窓を引く時刻」であって「刻み幅」ではない**: 刻みは個体ごとに局所周期で
  決まる(LEO 20 s、遠方小惑星は数千秒)。グリッドは最小刻みに合わせ、他の個体は間引いて
  踏む形になり、素朴な M 倍には届かない。

### 着手条件

多数個体のゲームプレイ(小惑星帯ステージ等)を本格化させ、かつ `debug-load` の実測で
予測が依然フレームの支配項であるとき。それまでは着手しない。

## 案8 シミュレーション精度の設定化【最後】

### 趣旨

「時間を加速して観察するデバッグ・遊び方があるので、設定画面でシミュレーション精度を
調整したい」という要望への回答。**アルゴリズムが定まる前にパラメーター調整はできない**ので、
案5(K)の値が実測で決まってから着手する。

# 第3章 測定・検証方法

## 3-1. 読み方の規律

- **主指標は離散カウンタ**(`pred-steps`/`plan-steps`/`sim-substeps`/`pred-tracked`/
  `pred-complete`/`pred-discard`/`eph-attr`/`eph-all`)。ms はその帰結として読む。
- **1回の run の絶対値を信用しない。** 同一ビルド・同一条件でも run 間で `積分` が 17〜35% 振れ、
  最悪の条件では **2.7×** 違った(`creative ×65536 艦なし` が 434 ms と 1189 ms。後者はレンダラの
  クラッシュを挟んで2ラウンドしか測れていない run の値で、外れ値)。**行ごとに
  `measuredRounds` とラウンド間スプレッドを必ず併記し、スプレッドの大きい行は結論に使わない。**
- **同じ run 内の2つのセクションの比は、機械の速さに依らない唯一の指標。** ms の絶対値は
  run 間で 1.5〜2倍振れるが、例えば「窓部(`積分` − `軌道積分`)÷ `軌道積分`」は同じフレームの
  中の比なのでドリフトの影響を受けない。窓の構築のように「どのセクションに乗るか」が分かって
  いる費用は、この比で読むと ms の絶対値より確実に判定できる。
- **比較は「同じ条件を、同じ並び順の同じ位置で測った run 同士」に限る。** したがって
  **条件マトリクスは run をまたいで固定する** — 条件を1つ減らすだけで後続条件の位置が前へ動く。
  歩単価(セクション ms ÷ 歩数)と、変更が触っていない行との比での正規化を併用する。
- **物理的に成り立たない大小関係が出たら、その run の値を疑う。** 例: エンティティ0体の
  `creative ×65536 艦なし` が、6体いる `stage1 戦闘 ×65536` より高い ms/substep を出したら、
  それは測定の外れ値であって発見ではない(`軌道積分数` が 0 対 1968 なのだから、前者が
  下回らなければおかしい)。
- ビルドと測定の間には数分の冷却を挟む。
- **各ラウンドは必ず新規の周回として始まる**: プローブは Chrome プロファイルをマトリクス全体で
  使い回すので、`Page.navigate` の直前に `Storage.clearDataForOrigin` で localStorage を消す。
  これが無いと、(a) `AutoSave` のスナップショットが同じステージの次の起動で復帰し、
  復帰した周回では `Stage.init()` が走らず**スナップショットに載らない小惑星・破片が
  世界から消える**、(b) 表示パネルのトグルが後続の条件へ持ち越される。
- **セクションの意味**: `予測` = 全ての弧の積分成長(計画の弧を含む。`Predictor.update` を包む)。
  `計画` = 区間列の組み立てと表示物の導出+`Targeter.updateEquatorNodes` 等+`PlanGuide.update` の
  合算(3箇所が同一セクションに enter/exit する)。`plan歩` は `Predictor` 計上の計画弧の歩数。
- ポーズ中・決着後も予測・計画は伸びる(予算パスは無条件)— settle 待ちで測る条件では
  この挙動を踏まえる。

# 第4章 作業中に見つかった別件

この文書の主題(計画・予測の負荷)ではないが、作業中に確認できた問題。

## 4-1. 条件マトリクスに再現性の穴が2つある

- **`stage1 マップ ×65536` の `軌道積分数` が run により 1968 / 2296 と揺れる**(= 6体 / 7体)。
  同じ URL・同じ settle 時間で、エンティティの顔ぶれが再現していない。カウンタ一致を前提に
  比で正規化する 3-1 の手順が、この条件では成り立たないラウンドがある。
- **run 全体が 1.5〜2倍のドリフトを起こすことがある。** 同じビルド・同じ条件で、`積分` の
  スプレッドが ±43〜91% に達した run が複数あった(そのとき 0体の `creative ×65536 艦なし` が
  6体の `stage1 戦闘 ×65536` より高く出るという、3-1 が「物理的に成り立たない」と名指しする
  状況も起きた)。**ドリフトした run でも、同じフレーム内のセクション比(3-1)は正しく読める** —
  案3 の判定はこれで通した。

どちらも計測環境の宿題(3-2 末尾の A/B 交互実行)と同じ根。**`積分` を触る案の判定は、ms の
絶対値ではなくセクション比で行い、絶対値は複数ラウンドの中央値とスプレッドを併記して読む。**

## 4-2. 残留 Chrome プロセスが後続の計測を壊す

perf-probe を途中で止めると Chrome の子プロセスが 40 個ほど残り、その状態で
`tools/browser-smoke.mjs` を走らせると「60 フレーム描けない」で失敗する。プローブ側の
`finally` は `browser.kill(SIGTERM)` しか撃たないので、Windows では子プロセスまで落ちない。
止めたあとは `taskkill /F /IM chrome.exe /T` で掃除してから次の計測へ進む。

## 4-3. `ARC_STEP_BUDGET` のコメントが実測と食い違っていた

「1歩 ≈ 0.32ms、1フレーム ~95ms まで」と書かれていたが、案1前の実測は 0.58〜0.89 ms/歩・
210〜300 ms/frame で、2〜3倍ずれていた。案1 の実測値(0.025〜0.055 ms/歩)へ書き換え済み。
