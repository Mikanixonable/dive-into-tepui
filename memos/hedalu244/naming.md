# 命名・設計規約の統合前退避

`DEVELOP/CODING-RULE.md`「命名規則 > 個別の使い分け」および「設計方針」へ昇格させるかを
1件ずつ判断するための控え。判断が済んだ項目はここから削除する。

出典は2つ:

- **A. 横断的な責務境界** — このプロジェクトで確定済みとされていた横断的な責務境界を、
  1件につき1エントリで転記した。
- **B. 命名規約** — 命名と、命名に直接関係する TypeScript の書き方の規約を、
  同じく1件につき1エントリで転記した。

各エントリの「種別」は転記者の見立てであり、確定した分類ではない。

## A. 横断的な責務境界

### A-1. `Game` はロジックを持たない
**種別**: 設計方針
**要約**: `game.ts`/`main.ts` はサブシステムの生成・配線と呼び出し順の決定だけを行う。分岐・状態組み立て・座標計算は置かない。所有者が複数モジュールにまたがるときの解決は「一方へ寄せる」か「横断そのものを責務とするモジュールを立てる」の2択のみ。

`game.ts` / `main.ts` に書いてよいのは**サブシステムの生成・配線と、呼び出し順の決定**だけ。
条件分岐を伴う判断、状態の組み立て、メニュー項目表、座標計算は、たとえ1箇所からしか
使われなくても Game に置かない。

**「所有者が複数モジュールにまたがるから `Game` が持つ」は理由にならない。**
またがるときの選択肢は2つだけ:

1. どちらか一方の所有者へ寄せる。
2. **その横断そのものを責務とするモジュールを1つ立てる**(`ViewManager` / `MapContextActions` /
   `FrameControls` / `ActivePlayerController` / `DisplayWindowManager` がその形)。

`Game` はそれを1行呼ぶだけになる。この判断に例外はない。

**`Game` 自身の状態と、それを切り替えるだけのメソッドは配線の一部**として残してよい
(`isPaused` と `pause`/`resume`)。分岐も組み立ても持たず、自分のフィールドを書いて各所有者へ
1行ずつ知らせるだけのものは、外へ出しても薄すぎるラッパーにしかならない。境界は行数ではなく
**分岐と組み立ての有無**。操作対象艦の切替はこの境界の外側にある — 切替に伴って
カメラ・計画編集・ターゲット・SFX へ伝播させ、削除・全滅からの引き継ぎまで判断するので、
`ActivePlayerController` が持つ。

**`Game` に `for` 文を書かない。** 配列を回したくなったら、その配列を持つモジュール(または
それに近い責務を持つモジュール)にその処理をさせる。回す対象を持たない `Game` が回し方を
知っているのは、その処理が本来そちらの責務だという徴候である。

**`Game` に「どのステージ/モードか」の分岐を書かない。**

**メタのフェーズ管理を `game/` へ漏らさない。** 再出撃・ステージ選択・スナップショットのロード・
スロット切替のように、**`Game` インスタンスそのものを捨てて次の周回へ移る**判断は、`Game` にも
`game/` 配下のどのモジュールにも置かない。持ち主は `main.ts` かその直属モジュール
(`Launcher` / `SnapshotControls`)で、**`game/` の中に `location.assign`/`replace`/`reload` を
書かない。**

`Game` は自分が生きている間のことだけを知り、自分の次に何が起きるかを知らない。したがって
`game/` 側が持つのは**遷移の判断材料を値として持つところまで**で(`Stage.phase` /
`Stage.result`)、遷移そのものは main 側が起こす。main 側が知る手段は2つだけ:

1. **毎フレーム読みに来る**(`Launcher.update(game)` が `Stage.phase` の決着を見る)。
2. **入力エッジを取る**(`Game.update` の後に残ったものだけを見る、`SnapshotControls` と同じ形)。

逆向き — `game/` 側が main 側のオブジェクトを参照する・コールバックで呼び返す — は作らない。
結果画面のように「決着を表示し、次の周回を選ばせる」GUI は、その GUI が書き換える状態
(=メタのフェーズ)の持ち主である main 側が所有し、`game/` 側の型に触る必要が
あるときは**狭いインターフェースを `game/` 側に置いて main 側がそれを満たす**
(`ResultScreen` が受ける `RunTransitions`。`DisplayDurationSource` と同じ手法)。

### A-2. `update` と `sync` を混ぜない
**種別**: 設計方針
**要約**: `update` は論理値の更新のみ(THREE/DOM に触らない)、`sync` は計算済みの論理状態を THREE.Scene と DOM へ反映するのみ(論理値を書き換えない)。判定はメソッド名ではなく中身で行う。

- **`update`** … 論理値の更新だけを行う。THREE のオブジェクトにも HUD の DOM にも触らない。
  **`update` から `sync` を呼ばない。**
- **`sync`** … `update` が計算し終えた論理状態を THREE.Scene と DOM へ反映するだけ。
  **論理値を書き換えない**(時間を進めない・寿命を判定しない・積分しない・次フレームが
  読む値を作らない)。**`sync` から `update` を呼ばない。**

判定するのは名前ではなく中身。`sync` が `dt` を引数に取っているなら、まず何かを進めている
疑いがある。表示のためだけに要る値でも、それが「前フレームからの変化」で決まるなら
`update` 側の持ち物。逆に、`update` の中で見た目を整えたくなったら、その値を論理状態として
持たせて `sync` に読ませる。

`build`(シーンへの登録)と `render`(`renderer.render` を呼ぶもの)を含めた命名規則は
CLAUDE.md の「Naming: render / update / build / sync」節。

### A-3. 座標系の境界 — 独自 `Vec3`/`KinematicState` は ECI、`THREE.Vector3` は描画後、それ以外は `frame.ts` の branded type
**種別**: 設計方針
**要約**: `Vec3`/`THREE.Vector3` の境界をフローティングオリジンの補正前後の境界に一致させる。独自 `Vec3`/`KinematicState` は既定で ECI を表し、ECI 以外の座標系(太陽中心系・月回転系など)の値は `physics/frame.ts` の branded type(`FramePoint`/`FrameDir`)だけが表せる。

#### `Vec3` と `THREE.Vector3` の境界(フローティングオリジン)

フローティングオリジンは、GPU が巨大な数値を単精度で扱うことによる描画破綻を防ぐための措置で、
CPU 側で事前に平行移動して自機・カメラ付近の浮動小数精度を高めるためのものである。
補正前か補正後かを型安全に扱うため、**この境界を独自 `Vec3` と `THREE.Vector3` の境界に
一致させる。**

- `THREE.Vector3` は描画のための座標なので、フローティングオリジンを引いた後のものだけを扱う。
- 変換は必ず `FloatingOrigin` の変換関数(`RtoThreeV3` / `VtoThreeV3`)を経由する。

#### 独自 `Vec3`/`KinematicState` は ECI が既定、それ以外は `frame.ts` の branded type

独自 `Vec3` / `KinematicState` は**地球中心慣性系(ECI)** を表す。これが既定であり、シミュレーションは
すべてこの系で回る(太陽・月・木星の位置も含め、`physics/attractor.ts` の `Attractor.state` は
常に ECI)。

ECI 以外の座標系(太陽中心系・月回転系など)の値は、生の `Vec3` に持たせない。
`physics/frame.ts` が持つ branded type だけがそれを表せる:

- **点**(位置。原点移動 + 回転で変換)は `FramePoint`。
- **方向**(変位・速度差・上方向など。回転のみで変換)は `FrameDir`。
- **点と方向を混ぜない。** 原点が動く座標系ではこの取り違えが静かに壊れる —
  `OverviewCamera` の視点オフセット/パン/上方向はすべて方向であり、点として扱うと座標系を
  切り替えた瞬間に視点が天体の位置ぶん飛ぶ。

ECI との変換は必ず `Ephemeris.frameTransformAt(frame, t)` が返す `FrameTransform` を経由する
(`toFramePoint`/`toInertialPoint`/`toFrameDir`/`toInertialDir`/`toFrameState`/`toInertialState`)。
天体の位置を自分で引き算して座標系を作らない。

天体の静的事実(質量・半径・軌道)の定義元は `physics/solar-system.ts` の `SOLAR_SYSTEM` 、
表示名と見た目の定義元は `game/celestial/celestial-registry.ts` の `CELESTIAL_BODIES`。
**`AttractorId` に対する網羅的 `switch` を新規コードに書かない** — 常にこの2つのレジストリを
引く鍵として扱う。例外は `solar-system.ts` の `CelestialBodyDef.kind`(恒星/惑星/衛星)に対する
`switch` で、これは天体の分類がこの3種で閉じているという物理的主張そのものなので、網羅性検査が
働く方が正しい。

軌道要素の**基準面**は `kepler-orbit.ts`'s `KeplerOrbit.basisToEci` が持つ — 評価側
(`normalFromAngles`/`directionFromAngles`/`rotationFromAngles`/`keplerOrbitState`)は基準面を
固定しない。既定は黄道面(`ECLIPTIC_BASIS`、export)で `planet-orbit.ts` は常にこれを使うが、
`satellite-orbit.ts`'s `satelliteOrbit` は `basisToEci` を上書きできる。衛星が親惑星の赤道面を
基準に取る場合の基底組み立て(自転軸から `body-orientation.ts`'s `equatorBasisToEci` 経由で
組む)は `solar-system.ts` の宣言時に一度だけ行う — 評価側の `kepler-orbit.ts` には惑星ごとの
極を知る責務を持たせない。

### A-4. `physics/` / `render/` / `game/` の境界
**種別**: 設計方針
**要約**: `physics/` は THREE 非依存の物理・軌道力学そのもの、`render/` は THREE 依存部分のみ、`game/` は両方に依存する部分のみ。`physics/` では物理的正確さが最優先で勝手な近似を持ち込まない。接触判定・その帰結の責務分界も含む。

- **`physics/`** … THREE.js に依存しない**物理・軌道力学そのもの**。純関数が多いが、
  THREE 非依存であれば状態を持つクラスを置いてもよい。
- **`render/`** … THREE.js に依存する部分のみ。上記の理由により独自 `Vec3` 座標は極力持ち込まない。
- **`game/`** … その両方に依存する部分のみ。

#### `physics/` では物理的な正確さが最優先される

**勝手な近似を持ち込まない。**「これくらいなら見た目には分からない」という判断を `physics/` の
中で下してはいけない。パフォーマンスが問題になったときは、メモ化・呼び出し側での刻み幅制御・
解析解への置換など、**正確さを損なわずに速くする方法を探す。** それでも成立しないと分かった
場合は、近似を採用してよいかを**ユーザーに問う**(勝手に倒して先へ進まない)。

採用したモデルとその適用範囲・限界は、そのモジュールの先頭コメントに書く。

#### `physics/` に物理でないものを持ち込まない

THREE 非依存かつ純粋であっても、次のものは `physics/` に置かない。

- **ゲームバランスの調整値** — 散布界の倍率、命中判定の甘さ、ダメージ量、演出のための補正。
- **見やすさのための歪め** — 表示距離の圧縮、フェード、マーカーの寄せ。
- **フローティングオリジン** — 描画のための平行移動であって物理ではない。
- **THREE.js への依存。**

境界は「用途が表示かどうか」ではなく「**厳密な数学・物理そのものか、調整の入った歪めか**」。
直交座標から射影座標への変換(`projection.ts` のピンホール投影)は表示のために使われるが、
調整値を含まない厳密な幾何なので `physics/` に属する。同じ理由で、視点からある点までの視線が
天体の球体に遮られているかどうか(`occlusion.ts` の `isOccluded`、レイと球の交差判定)も
調整値を含まない厳密な幾何であり、`physics/` に属する — マップビューでのアイコン表示可否と
ピック候補の可否という2つの `game/` 側の用途がこの1関数を共有することで、両者が食い違わない。
逆の例が `game/celestial/ring-view.ts` の環の面/線の切り替え判定 — 帯の実幅が画面上で 1px を
割ったら線として描く、という比較そのものは純粋な計算だが、閾値が見やすさのための調整値なので、
`physics/` ではなく `game/` に置く(`body-visibility.ts` と同じ扱い)。

物理的に正しい計算を調整値で歪めて使う場合は、`physics/` から素の値を引いて `game/` 側で歪める。
`physics/` は現実の法則を計算する場所で、そこに調整値が混ざると「この式は物理的に正しいのか、
それとも遊びやすさのために歪めてあるのか」が読んで区別できなくなる。

#### 接触判定は重力の関心事ではない

2球が触れているかどうか(`physics/sphere-contact.ts` の掃引 TOI・幾何的な内外判定)と、
触れたときにどう跳ね返るか(`physics/collision-response.ts` の逆質量・反発係数からの撃力解決)は
`occlusion.ts` の視線遮蔽判定と同じ理由で `physics/` に属する厳密な幾何・力学であり、
「重力源かどうか」(`attractor.ts`)や「大気を持つかどうか」(`atmosphere.ts`)とは無関係な
別の関心事である。`attractor.ts` は何が何を**引くか**にだけ答え、何が何に**触れたか**には
一切答えない — 天体の表面に沈み込んだかどうかを尋ねる関数を重力モジュールに置いてはならない
(触れたら死ぬ、という帰結のほうも重力の関心事ではない。次項)。同じ理由で、大気による焼失
(`atmosphere.ts` の `isBurnedUp`、地球にしか無い現象)と固体表面への接触(天体一般に効く幾何)は
別の判定であり、どちらか一方のマージンをもう一方の代用にしてはならない。

#### a と b の接触の帰結は a と b の責務であって、検出側やオーケストレータの責務ではない

「2つの物体が触れたときに何が起きるか」(ダメージ・破壊・音・エフェクト)は、接触を検出した
モジュール(`game/simulation/contact.ts`)にも、まして `Game`(`game.ts`)にも書かない。
`GameEntity` の各サブクラス自身の `collideWith` に、**自分が受けるものだけ**を書く —
相手が受けるものは相手の `collideWith` が書くので、二重に効くことも抜け落ちることもない。
列挙・順序付けの層はペアを見つけて剛体解決を通し、両当事者に接触の記述(`Contact`)を渡すだけで、
ダメージも音も消滅も一切知らない。`a === player && b instanceof Enemy` のような当事者の型を
検出側やオーケストレータで分岐するコードは、この境界が破れているサインである。

### A-5. 物理的正確さ・実装の適切さ・実行時パフォーマンス・変更コストの優先順位
**種別**: 設計方針
**要約**: この4つをこの順で優先する。physics/ 内では物理的正確さが最優先。オーダー改善は定数倍高速化より優先度が高い。変更コストが最も低優先度で、歴史的経緯を残す理由にならない。

1. 物理的正確さ
特にphysics/フォルダ内においては最優先。地球の公転が円軌道で近似されていたのは不適切だったので、修正すべき。
提案の「ケプラー木構造」案は興味深いが、衛星の場合は太陽から受ける摂動の影響が大きいため、惑星に対するケプラー軌道は実態からずれた近似となる。月を削除するのは問題なので暫定的に/簡易的に導入してもよいが、最終的には衛星軌道は積分によって計算されるべきだと思われる。この件はbetter_simulationのstep3に追記した。

2. 実装の適切さ
物理的な概念やゲーム上の概念が自然な形で実装に現れていること。将来の保守性(将来の変更コストの抑制)のために必要。責務分割や疎結合化、命名の是正、物理的な数式表現が素直にそのまま実装されていることなどを含む。

3. 実行時パフォーマンス
これは重要ではあるが、上記二つに比べると優先度が低い。

オーダー改善の優先度は定数倍高速化よりも高い。明らかに計算量の爆発が見込まれるオーダー計算量が悪い実装が存在する場合、その改善をする優先度は高い。実測できたか否かに関わらず、改善を行う。可能であればオーダーが爆発する状況を再現、実測してから、オーダー改善を実施し、実施後に効果があったかの確認を行う。

定数倍高速化については、実測を行って、どうしても無視できない効果がある場合にのみ実施する。定数倍高速化のために実装が長大化したり、責務分割が不自然になることは望ましくない。一旦高速化のことを忘れてリファクタリングをした後、必要に応じてメモ化などの最適化を行う。

4. 変更コスト
最も優先度が低い。現状のコードがそうなっているからというだけの理由ではその変更を行わない理由にならない。歴史的経緯を残すべきでないという方針にも一致する。将来書き換える箇所を減らすためであれば、今は最大の努力を払って積極的にコードを大きく書き換える。
ただし、一度の変更ですべてを書き換えるとバグが生じたときの原因の切り分けに苦労するため、今回のような大きな変更は小さな段階にわけ、各段階で問題が生じていないことの確認を取りながら進める。すべてのステップを踏むことで、歴史的経緯なく、当初の目的であった大きな変更が達成されていることを確認する。

### A-6. `ctx` / `context` / `opt` / `params` といった引数を使わない
**種別**: どちらとも言えない(関数シグネチャの設計方針だが、`snapshot` という名の禁止は命名規約そのもの)
**要約**: 場当たり的なオブジェクト引数は禁止。明示的な引数か、事前に共有した参照で渡す。唯一残る例外は `Player.behave`。`snapshot` という名も同じ理由で禁止(「集め方」を説明するだけで「何であるか」を言っていない)。

場当たり的なオブジェクト引数は禁止。明示的な引数か、事前に共有した参照で渡す。既存の
`*Ctx` はほぼすべて展開済みで、唯一残る例外が `Player.behave` のパラメータオブジェクト。
新規追加も、この生き残りを広げることも禁止。

**`snapshot` という名も同じ理由で未来永劫禁止。** 「ある瞬間の値をひとまとめにした」という
**集め方**を説明しているだけで、それが**何であるか**を言っていない — ctx と同型の問題。
見つけたら次のどちらかで直す:

1. 場当たり的な寄せ集めであるべきでない(個々の値を直接渡せば足りる、その場しのぎの
   まとめ方でしかない)なら、集める処理自体をやめて値を直接渡す。
2. その時点の値をまとめて1回で扱うこと自体に意味がある(例: 同じ瞬間の重力源一覧を
   全エンティティで使い回さないと処理順に依存した誤差が入る、など呼び直してはいけない
   具体的な理由がある)なら、集める処理は残してよい。ただし名前は「集め方」ではなく
   「何が集まっているか」で呼ぶ(値の型と一致させる — 例えば `Attractor[]` を集める
   関数・メソッドは `attractors`/`attractorsAt`)。

### A-7. 渡すのはクロージャではなくオブジェクトの参照
**種別**: 設計方針
**要約**: 他モジュールのデータ・処理へ届かせたいとき、転送クロージャを作って渡さず、そのオブジェクトの参照そのものを渡す。いつ渡すかは使うタイミングで決める。`ProjectFn` だけが例外。

他モジュールのデータや処理へ届かせたいとき、`(t) => other.sample(t)` のような**転送クロージャを
作って渡さない。** そのオブジェクトの参照そのものを渡す。クロージャ注入は「誰が誰を呼んで
いるか」を型からも呼び出し元からも隠し、配線が増えるほど実行順序が読めなくなる。

- **いつ渡すかは、使うタイミングで決める。** 毎フレームの呼び出しの中だけで使うなら引数で渡す。
  DOM の pointer イベントなど**フレームの流れの外**で使うなら、コンストラクタで受けて保持する。
- **`ProjectFn` だけは関数で渡す。** これは処理の委譲ではなく「その瞬間の視点」という値で、
  `CameraSystem.activeCameraProjection` は呼んだ時点のアクティブカメラのスナップショットを返す。
  したがって**受け取った側が保持してはいけない** — 毎フレーム渡し直し、受け手は per-frame の
  表示文脈として上書きする。

### A-8. 「たまたま」同時に切り替わるフラグは別個にする
**種別**: 設計方針
**要約**: 一つのフラグで本質的に異なる多数の挙動が切り替わる形を禁止。「たまたま」一致するだけのものは別個のフラグにし、同時に切り替える必要があるなら切り替える側(トグラー)を一箇所に置いて両方を書き換える。

一つのフラグによって本質的に異なる多数の挙動が切り替わる形は、責務の疎結合を妨げる。
「たまたま」一致しているだけのものは別個のフラグに分離し、同時に切り替える必要があるなら、
**切り替える側(トグラー)を一箇所に置いて両方を書き換える**(A-1の2番目の選択肢と同じ形)。

- `PlanEditor.editMode`(入力・編集の可否)・`CameraSystem.overviewMode`(視点・描画)・
  `DisplayWindowManager.forceCurrent`(未来表示の可否) → 同時トグルは `ViewManager.applyChrome()` の責務。
- `OverviewCamera.cameraFrame`(視点が固定される座標系)と `DisplayWindowManager.frame`
  (計画軌道・予測軌道線・交点マーカーなど未来表示を描く座標系) → プレイヤーが独立に選ぶ別々の値。
  `ReferenceFrame` 自体が「原点 × 回転」の直積(`physics/frame.ts`)なので、UI(`hud/frame-controls.ts`)
  もその形に合わせて4ゾーン(カメラ/カメラ回転/並進/計画軌道回転)に分かれ、`FrameControls` は
  両方の状態へ書き込む横断モジュールではあっても、書き込み先の2つの正本(`OverviewCamera`・
  `DisplayWindowManager`)を1つに統合したり同時に切り替えたりはしない — カメラの原点・回転を
  変えても `frame` は動かず、その逆も同様。
- `BodyClassToggles` のクラス別の軌道線表示(`*Orbit`)・アイコン表示(`*Icon`)・
  ラベル表示(`*Label`)→ プレイヤーが独立に選ぶ3つの値。読む側も別で、アイコン/ラベルは
  `visibleBodyIds`/`bodyIconLabel`、軌道線は `EnvironmentScene.showsReferenceLine`。

### A-9. `plan` / `predict` / `display` の語を混ぜない
**種別**: 命名
**要約**: 未来の軌道を扱う系統が複数あるため語を固定する。`plan`=計画軌道、`predict`=予測軌道、`display`=表示時刻。計画側の識別子・コメント・パネル文言に `predict`/「予測」を使わない(逆も同様)。

未来の軌道を扱う系統が複数あるので、語を固定する。混ぜると、どちらの未来の話をしているのか
識別子から判別できなくなる。

- **`plan`(計画軌道)** … プレイヤーがマニューバノードを置いて組み立てた意図そのもの。
- **`predict`(予測軌道)** … 現在の状態のまま自由飛行した未来。
- **`display`(表示時刻)** … そのどちらでもない「いつの状態を表示するか」。

計画側の識別子・コメント・パネル文言に `predict` /「予測」を使わない(定数名も含む)。
逆に予測側を「計画」と呼ばない。

### A-10. 軌道まわりの語族 — `orbit` / `ephemeris`・`celestial` / `dynamic`
**種別**: 命名
**要約**: 判定基準は「そのモジュールの実装が何に限定されているか」。`orbit`=解析的に解ける軌道、`ephemeris`=時刻→位置を答える仕組み、`celestial`=天体という存在、`dynamic`=RK4積分に基づくもの。族語は `orbit` に統一し `orbital*` は新設しない。

**判定基準は「そのモジュールの実装が何に限定されているか」であり、外部でどう使われているかではない。**

- **`orbit`** … 解析的に解ける軌道。時刻→位置が閉じた式で決まるもの。
  `OrbitalElements` / `KeplerOrbit` / `OrbitLine` / `localOrbitPeriod` / `orbitAxes` がここ。
- **`ephemeris` / `celestial`** … `ephemeris` は「時刻→位置を答える仕組み」、`celestial` は
  「天体という存在」。責務が違うので統一しない。
- **`dynamic`** … RK4 積分に基づくもの。`dynamics.ts` / `stepDynamics` / `DynamicTrajectory`。
- **どの族にも限定されないものには族語を付けない。** `KinematicState`(t/r/v しか持たない)、
  `stepRK4`(汎用 ODE ステッパ)がここ。

語形は **`orbit` に統一**し、例外は定訳を採る `OrbitalElements` の1語だけ。`orbital*` を新設しない。
点列を折れ線として描く共通描画基盤は `TrajectoryLine`(`OrbitLine` の兄弟) — 実装が限定されるのは
「点列が積分済みであること」自体で、その点列を発生させたのが計画区間(`PlanPath` の
`SegmentSource`)が持つ `PredictedArc` であっても描画側の族語は変わらない。

計画した経路は `path`(`PlanPath`)、積分した軌跡は `trajectory`(`DynamicTrajectory`)。
この2語は概念が違うので共存させる。

### A-11. `body` は天体、機体座標系は `ship`、重力源の値は `attractor`
**種別**: 命名
**要約**: 無標の `body` を天体の意味に残し、機体座標系を `ship` で有標にする。`Attractor` 型の値は `attractor`/`attractors`(楕円の中心は `center`)。`AttractorId` は一般の `string`。`Ephemeris` はレジストリ・原点をインスタンスごとに持つ。

天文シミュレーションで無標の `body` が機体座標系に奪われるのは苦しいので、機体の側を有標にする。

- **`body` は天体の意味に残す** … `CelestialBody` / `CelestialBodyDef` / `bodyDef` /
  `MapPickKind` の `'body'`。
- **機体に固定した座標系は `ship` で有標にする** … `shipNormal` / `axisShip` / `aThrustShip`。
  剛体一般(デブリ・薬莢)の固定座標系に名前が要るようになったら、`ship` は使えないので別途決める。
- **`Attractor` 型の値は型名と一致させて `attractor` / `attractors`。** ただし楕円の中心として
  渡すものは `center`(`OrbitalElements.center` と一致させる)。**`bodies` が `Attractor[]` を
  指す箇所は0件**であること。
- **`AttractorId`/`Attractor.id` は登録天体とは限らない、一般の `string`。** レジストリが実行時に
  差し替え可能である以上、汎用 API 側(`physics/attractor.ts`)でこの型を閉じた union にできない。
  網羅性の強制は失ってはならない一次情報なので、**具体レジストリ側が自分のデータから `keyof` で
  自分の ID 型を自己生成する**(`solar-system.ts`: `SOLAR_SYSTEM` を `satisfies CelestialRegistry`
  で宣言し `SolarSystemId = keyof typeof SOLAR_SYSTEM` を導出。天体を1体足すと `SolarSystemId` が
  自動的に広がり、`game/celestial/celestial-registry.ts` の `Record<SolarSystemId, …>` がすぐさま
  コンパイルエラーになる)。**汎用 API に手書きの union を書き足す形へ戻さない。**
- **`Ephemeris` はどのレジストリ・どの ECI 原点を使うかをインスタンスごとに持つ**
  (`registry`/`originId`/`epochOffsetSec`、コンストラクタ引数、省略時は現実の太陽系・地球原点)。
  「今どの天体が登録されているか」はモジュールレベルの `SOLAR_SYSTEM` 定数ではなく、この
  インスタンスの実行時状態そのものなので、`physics/frame.ts` のような周辺モジュールが
  `SOLAR_SYSTEM` を直接読んで座標系一覧を組む形(旧 `FRAMES`)は禁止 — 座標系一覧
  (`Ephemeris.frames`/`inertialFrame`/`frameFor`)も `Ephemeris` 自身が持つ。

### A-12. GUI とマーカーの所有者
**種別**: 設計方針
**要約**: GUI は、その GUI が書き換える状態の所有者が持つ。所有者が1つに定まらない GUI は分割する。マーカーも同じ原則。物体に1つ付く表示物は物体自身が `T | null` フィールドとして持つ。線の描画順は `LINE_RENDER_ORDER` に一元化。GUI の重なり順は `overlay-layer.ts` の固定レイヤのみで決める。ESC・ショートカット・外側クリック・入力ゲートは `OverlayManager` に一元化。

> **GUI は、その GUI が書き換える状態の所有者が持つ。所有者が1つに定まらない GUI は、
> GUI の方を分割する。** 表示・非表示も所有者が自分の `sync` で押し出す。
> GUI の見た目を維持することを制約にしない。

マーカーも同じ原則。**マーカーは対象の持ち主が自分の `sync` の中で出す**(`syncMarker` を
別途公開しない)。対象が1つに定まらないマーカーだけが `marker/` に置かれる。
**「どう置くか」(投影・方向・画面端の方位)は `MarkerManager` に集める** — 持ち主が決めるのは
「何を・どの記号で出すか」だけ。**記号そのものの語彙は `marker/marker-glyphs.ts` に3族
(実体=塗り / 方向=矢 / 軌道上の点=中空)として置き、持ち主はそこから選ぶ** — 選ぶ判断は
持ち主に残したまま、同じ意味の記号が別々の字形になるのを防ぐ。UI の縦方向の折りたたみ
(`hud/hud-root.ts` の `▸`/`▾`)はこの3族の外に置き、字形を重ねない。

#### 物体に付随する表示物は、その物体自身がフィールドとして持つ

軌道線(`OrbitLine`)・軌跡線(`TrajectoryLine`)・マーカーのように**1つの物体に1つ付く表示物**は、
その物体自身が `T | null` のフィールドとして持ち、自分の `sync` の中で世話をする。
**外部に `Map<GameEntity, T>` や配列を置いて対応付けるモジュールを作ってはいけない。**
表示しないものは `null` にすればよく、生成・破棄・描画の判断はすべて持ち主の中で閉じる。

記録側(`DynamicTrajectory` を `GameEntity` が持つ)が分散しているのに描画側だけ外部で集約
されている、という非対称は実装のぎこちなさとして表面化する — 対応付けだけを責務とする
モジュールは、持ち主が既に持っているはずの参照を外から作り直しているだけで、生存期間の
管理を二重に持つ。**1つの物体に1つ付く表示物に対して、対応付けの層を作らない。**

**線の描画順も同じ形で1箇所に集める。** 透明な線どうしの前後は `renderOrder` でしか決まらず、
同値だと不定になる — つまり描画順は線どうしの相対関係でしか意味を持たないので、各線が自分の
値を単独で決めてはいけない。`const.ts` の `LINE_RENDER_ORDER` が唯一の割り当て表で、線は
その値をコンストラクタ引数として受け取る(生成後に `line.renderOrder` を書き換えない)。

**GUI の重なり順はレイヤと DOM 順だけで決める。個々の GUI が自分で z-index を持ってはいけない。**
`hud/overlay-layer.ts` の7段の固定レイヤ(奥から手前へ `marker`/`panel`/`window`/`popup`/`view`/
`notify`/`system`)が唯一の正本で、z-index を割り当てるのはこのモジュールだけ。GUI の所有者が
決めるのは自分がどのレイヤの子になるか(コンストラクタ引数で受け取る `panelRoot`/`popupRoot` など、
根は必ず `Hud.layers` まで遡れる)だけで、同じレイヤ内の前後は DOM 順、最前面化は
`bringToFront()` の呼び出しだけが動かす。**`ContextMenu`/`ObjectPicker` のようなポップアップの
親は必ず `popup` レイヤ** — `document.body` や、それを開いた側(パネルなら `panel` レイヤ、
プロパティウィンドウなら `window` レイヤ)と同じレイヤに直接ぶら下げてはいけない。同じレイヤに
置くと開いた側より奥へ回り込みうるが、`popup` レイヤは `panel`/`window` の両方より手前に固定
されているので、ポップアップはどちらから開かれても常にその手前に出る — 開いた瞬間に自分自身へ
`bringToFront()` を呼ぶのは、同じ `popup` レイヤ内で先に開いている別のポップアップより手前へ
出すためであって、パネル/ウィンドウとの前後関係はレイヤ分割そのものが保証する。

例外として扱ってよいもの:

- `PauseMenu`(BGM・一時停止・タイトルへ戻る)… **複数モジュールにまたがることが本質**の
  GUI なので、所有者を `main.ts` に置く。
- `Hud.hint()` / `toast()` / `WorldSfx`/`UiSfx` … 共有サービス。所有者の議論の対象外。
- `hud/context-menu.ts` / `hud/widgets/`(押せる/切り替えられる/入力できる DOM は
  `Button`/`ToggleSwitch`/`SegmentedControl`/`HoldButton`/`CloseButton`/`ValueInput`/`Meter`/
  `TabBar`/`buildCollapseToggle`/`Slider` の10種に限り、これ以外を自作しない)/ `hud/frame-labels.ts` …
  DOM・イベント・表示文字列だけを担う共有部品。状態を持たないので「所有者」を問う必要がない。
  **この形は積極的に増やしてよい。**押せる/切り替えられる/入力できる DOM を自作している呼び出し側を
  見つけたら `hud/widgets/` の対応するウィジェットへ置き換える(`hud/buttons.ts` は無い —
  10 種すべてが `hud/widgets/` 直下の1ウィジェット1ファイルで、旧名への互換委譲層は存在しない)。
- `hud/status-panel.ts`/`orbit-panel.ts`/`target-panel.ts`/`contacts-panel.ts`/`global-status-bar.ts`/
  `map-scale-badge.ts` の6クラス(常設パネル、いずれも `sync(game, ...)`)… 1クラス1パネルへ分割済みでも、
  各パネルが読む値の組み合わせはパネルごとに違うため、共通の狭い ctx を切り出す方が却って
  A-6(`ctx` 引数の禁止)に反する。`Game` を丸ごと読んでよいが、**表示専用**であること(他モジュールの状態や
  DOM を書き換えないこと)は維持する。

#### ESC・項目ショートカット・外側クリック・入力ゲートの正本は `OverlayManager` 1箇所

**個々のオーバーレイ(モーダル/ポップアップ/ウィンドウ)は自分で `window` の `keydown` も
`document` の `pointerdown` も張ってはいけない。** `hud/overlay-manager.ts` の `OverlayManager`
が唯一の台帳で、`kind`/`closeOnEscape`/`closeOnOutsideClick`/`gatesInput`/`exclusiveGroup` を
登録時に宣言し、`open`/`close`/`reconfigure` を自分自身に対して呼ぶだけにする(`OverlayHandle`
= `contains`/`close`、加えて項目ショートカットを持つオーバーレイだけが任意の `handleShortcut`
を実装する)。ESC は `Game.handleInput` が `Input` のエッジキュー経由で取った1回だけを
`OverlayManager.closeTopmostOnEscape()` へそのまま渡す — 個々のオーバーレイが `window` へ
直付けした瞬間、`Input` の先着順消費と同じフレームで競合し、どちらが先に見えるかが生成順に
依存してしまう。項目ショートカット(`[F]`等のヒントを出す項目)も同じ理由で、`Game.handleInput`
が `Input.takeKeys` 経由で1フレーム分の未消費キーを `OverlayManager.dispatchShortcut(code)` へ
そのまま渡す — `closeTopmostOnEscape` と同じ「最前面から順に、対応できるものが見つかるまで
下へ通す」形で配送し、`handleShortcut` を実装しない/一致しないハンドルは透過して1つ下へ渡る
(クリップ中の `PropertyWindow` は常に `false` を返すので、複数開いていても一時ウィンドウ1枚だけが
実際に受け取る)。外側クリックも同じ理由で `OverlayManager` の1本のキャプチャリスナへ集約する。
例外は**入力欄フォーカス中の element-level `keydown`** だけ(`widgets/value-input.ts` の
`ValueInput` — Enter/Escape/blur。フォーカスがある要素の `keydown` は伝播を自分で止めるので
`Input` のエッジキューには届かず、競合しない)— それでも `dispatchShortcut` 自身は
`document.activeElement` を見て独立にテキスト入力中を弾く、後から入力欄以外の経路が増えても
崩れない側の安全策として。「同じ対象への操作は常に同じ種類の UI で受ける」(例: 右クリックは
ビューを問わず `PropertyWindow`)も、この一元化の一部として扱う — ビューごとに別のポップアップ
実装を持たない。

#### 入力欄は必ず `keydown` の伝播を止める

`input/input.ts` の `Input` は `window` でキー入力を購読しているので、**HUD の入力欄で
止めなかった打鍵はそのままゲーム操作になる**(検索欄に "w" と打つと機体が噴射する)。
`hud/widgets/value-input.ts` の `ValueInput` がテキスト・数値・検索入力の唯一の実装 —
新しい入力欄はこれを使い、自作しない。`keydown` の伝播抑止・Enter/blur=確定・Escape=破棄
(既定 `'revert'`、検索欄限定で `'clear'`)を内包しており、打鍵ごとに値を適用しない
(打ちかけの数値が一瞬でも設定値として使われないようにするため)。

#### 排他選択の走査範囲に DOM の親子関係を流用しない

「同じ列の中で1つだけ選択状態にする」実装で、`parent.querySelectorAll('button')` のような
DOM 検索を排他の範囲にしない。同じ親に**独立した状態を持つ別のボタン**(近傍トグルなど)が
同居した瞬間、それも一緒に解除されてしまう。排他の範囲は、そのグループのボタンだけを入れた
配列として明示的に持つ。

### A-13. 二段初期化を作らない — 初期状態はコンストラクタで受ける
**種別**: 設計方針
**要約**: 生成後に「初期化メソッドをもう一度呼ばないと使えない」形を作らない。初期状態はコンストラクタ引数で受け、生成後に中身を丸ごと差し替えるメソッド(`restore` の類)を作らない。

生成後に「初期化メソッドをもう一度呼ばないと使えない」形を作らない。呼び忘れが型で守られない。
リソースの注入が必要なら、注入は**1つのメソッドに1回だけ**にし、あるサブクラスだけが要る
リソースでもその引数を増やす。サブクラス固有の初期化は `super(...)` の後に書く
(`Stage` の具象クラスが `super(saved, ...deps)` の後に自分のフィールドを組み立て、
末尾で `begin()` → `init()` を呼ぶ形)。

**状態も同じで、初期状態はコンストラクタ引数で受ける。** 生成後に中身を丸ごと差し替える
メソッド(`restore` の類)を作らない。既定状態を組んでから上書きする形は、「上書き前の状態」
という誰も望んでいない中間状態を必ず1つ作り、その間に走る処理が何を見るかを非自明にする。

  セーブ由来の値自体はコンストラクタで受けて控えておく(`Stage` が `Logistics` に対して行う形)。

### A-15. 一般化しないと決めたもの
**種別**: 設計方針
**要約**: 似た形の実装でも「個別に調整される要素」はまとめない(ステージ挙動、自機と敵の戦闘挙動)。逆に参照が1箇所でも分割するのは「一般化した側を今後使う可能性がある」とき(連星系、3階層を超える公転階層、地球依存の物理モデルの一般化、ゲームデザイン上のプリセットの他天体への一般化)。

似た形の実装があっても、**個別に調整される要素**なのでまとめない。判断基準そのものは
`/refactor` の「重複実装の禁止と早急な一般化の分かれ目」。

- **`stages/` 配下の各ステージの挙動。** すべて並列に実装されているし、そうあるべき。共通化するのは
  `Stage` 基底と `stage-utils/` に既に括り出したもの(補給・スコア・タイマー・ウェーブ)まで。
- **自機と敵の戦闘挙動。** 武装も観測機器も別物という設定なので、射撃・照準・散布界・被弾判定などは
  今たまたま同じ式でも**将来別々に調整される前提**で、`player/` 側と `Enemy` 側にそれぞれ実装する。
  同じ関数が2箇所にあってよい。共通化してよいのは、どちらの調整とも無関係な純粋な物理・幾何だけ。

逆に、**参照が1箇所しかなくても分割する**のは、一般化した側を今後使う可能性があるとき、および
巨大な責務を切り分けるとき。

- **恒星が2つ以上、相互に公転しあう連星系。** `Ephemeris` のレジストリ注入・原点一般化は主星が
  0または1つの星系のみ対象で(`solar-system.ts`'s `starOf` が2つ以上見つかると例外にする)、
  相互に比較可能な質量が複雑な軌道を描く状況は解析的なケプラー軌道の適用範囲外 — その表現は
  `Asteroid` の数値積分の役目であり、レジストリの一般化では担わない。
- **3階層(恒星/惑星/衛星)を超える公転階層。** `CelestialBodyDef` の `kind` 3分類自体は変えない。
- **地球の大気圏熱管理・機体初期配置・エネミー生成式を天体非依存に一般化すること。** レジストリに
  地球以外の天体しかないステージでもクラッシュしないことまでを保証し、それらの物理モデル自体は
  一般化しない(桁違いに大きい別作業)。
- **静止軌道高度・太陽同期傾斜角のプリセット、基地配置を月に限定するルールの、他天体への一般化。**
  ゲームデザイン上の判断、または天体の自転周期という現状のスキーマに無いデータを要求するため。

### A-16. 天体の自転軸・自転位相は重力場の付属物ではない
**種別**: 設計方針
**要約**: 「天体がどこにいるか」「天体がどちらを向いているか」「重力場がどう効くか」は3つの別の問いで、それぞれ別の場所に置く。自転軸・位相のモデル(`PoleModel`)は `CelestialBodyDef` 直下、`Degree2GravityDef` は j2/c22/refRadius のみ持つ。

**「天体がどこにいるか」「天体がどちらを向いているか」「重力場がどう効くか」は3つの別の問い**で、
それぞれ別の場所に置く。

- **自転軸・自転位相のモデル(`PoleModel`)は `CelestialBodyDef` 直下の `pole?: PoleModel`**
  (`solar-system.ts`)に置く。`Degree2GravityDef`(同じく `solar-system.ts`)は j2/c22/refRadius
  という重力場の係数だけを持ち、`PoleModel` を持たない。理由は、自転軸を持つが2次重力場は持たない
  天体(水金火天海の5惑星 — `'iau'` の pole はあるが `degree2` は無い)が実在し、逆に重力場だけ持って
  自転を表示しない天体があってもよいはずだからで、どちらか一方に従属させると片方だけの天体を
  型で表現できなくなる。
- **時刻ごとの実ベクトルへ解決するのは `ephemeris.ts` の仕事。** `Ephemeris.poleAt(id, t)` が
  `PoleModel.kind` だけで分岐する唯一の解決経路(`private orientationOf`)を通り、公開 API として
  自転軸・位相を返す。`private degree2At` の重力場側 pole/長軸解決も同じ `orientationOf` を必ず
  経由する — 表示側の自転軸と重力場側の pole が別の式で計算されて食い違う、という事故はこの一本化で
  構造的に起こらない。
- **姿勢を実際にメッシュへ書き込むのは `game/celestial/sphere-body.ts` の仕事。** `SphereBody.sync`
  は `Ephemeris.poleAt` の結果を `physics/body-orientation.ts` の `spinOrientation(axis, spinAngle)`
  に渡してクォータニオンを得るだけで、`Object3D.lookAt` のような「見た目だけ合わせる」上書きは
  一切行わない — 月の潮汐固定も、同期回転の自転位相(`spinPhaseOf` が平均黄経の反対方向から導出)が
  正しく効いた結果として現れるべきもので、`SphereBody` 側で親の方向を向かせて再現するものではない。

### A-17. 天体の形状(歪み)は `physics/` のデータ、メッシュへの反映は `SphereBody`/`PointBody` の1箇所
**種別**: 設計方針
**要約**: `ShapeDef` と `shapeAxes` は `physics/solar-system.ts` に置く。`Attractor.radius` は楕円体化せず最長軸まで引き上げる。メッシュへの反映は `SphereBody`/`PointBody` の各コンストラクタで1回だけ。

- **`ShapeDef` と、それを3軸スケールへ変換する `shapeAxes(radius, shape)` は `physics/solar-system.ts`
  に置く。** 三軸半径は pck00011.tpc という物理データの一次ソースから来る量であり、表示側の都合では
  ない — `celestial-registry.ts` 側に置くと、値の意味(半径か直径か、どの軸が極か)が表示コードの
  中に埋もれて次に足す人が誤読しやすくなる。`Attractor.radius`(衝突球・高度基準のスカラー)は
  楕円体化しない — 極方向で最大 10%(土星)保守的になる外接球のまま、`shape` を足すたびに
  その最長軸まで引き上げる。理由は A-16 と同じ形: 「衝突判定がどう働くか」は「見た目がどう歪むか」
  とは別の問いで、どちらか一方の都合で他方の精度を上げ下げしない。
- **メッシュへの反映は `SphereBody`/`PointBody` の各コンストラクタで `shapeAxes` を1回呼ぶだけ**
  (毎フレームではない — 形状は天体固有の定数なので、姿勢のように時刻依存で解決し直す理由がない)。
  `sync` は保存済みの軸ベクトルを `mesh.scale` に書くだけで、`ShapeDef` の中身を知らない。
  戦闘ビューの視距離圧縮(`visDist/dist`)は3軸へ同じ係数を掛けるだけで、真の視角を保つ性質を
  壊さない。
- **scale は自転クォータニオンより「内側」の座標で効く** — THREE は position/quaternion/scale を
  代入順ではなく行列合成の規約(scale→rotation→translation)で解決するため、`mesh.quaternion` と
  `mesh.scale` をどちらを先に書いても、scale は常に天体自身のローカル軸(赤道断面が X-Z、極が Y)
  に対して効く。形状は自転軸に固定される天体固有の量であって ECI 軸には固定されない、という
  A-16 の姿勢の理屈をそのまま裏返した帰結。

**種別**: 設計方針

- `player/thrust-effects.ts` の `ThrustEffects.sync(fo, pos, thrust, maxAccel, alive, audible, camera)`
  も同じ形に揃えてある。`thrust: Vec3 | null` は `ship.thrust` そのもの、`maxAccel` は

  はもう SFX を触らず、ベルト物理向けの `thrustAccelVec` を戻すだけの役に絞られている。

### A-21. 不在は `T | null` で表す — 代役も、別の真偽値も立てない
**種別**: 設計方針
**要約**: あるものが「無い」ことは、その値自身の `null` だけで表す。代役の空インスタンスや別の真偽値を立てない。受け手が自決できるなら呼び出し側にガードを書かせない。所有者とその持ち物を別々の引数で受けない。

**あるものが「無い」ことは、その値自身の `null` だけで表す。** 型の上で常に非 null に保つために
代役の空インスタンスを置くと、「本当にあるか」を別の真偽値で持つ形になり、持ち物があるのに
「持っていない」と言う嘘のフラグが生まれる。

- **受け手が「無ければ何もしない」を自決できるなら、呼び出し側にガードを書かせない。**
  `if (x) receiver.f(x)` は、受け手の引数を `T | null` にして先頭で早期 return できるなら
  二重判定。受け手側へ倒して呼び出し側の `if` を消す。自決できないのは、受け手がその型を
  そもそも知らない場合(`TouchControls` は `Player` ではなくプリミティブと述語関数を受ける)だけで、
  そのときだけ呼び出し側にガードが残る。
- **「出すか」の真偽値引数は、値自身を `T | null` にできるなら潰す。**
  `update(plan: Plan | null)` は `null` が「出さない」を表すので `show` は要らない。
- **所有者とその持ち物を別々の引数で受けない。** 艦を受け取る側は `Player | null` を受け、
  艦の持ち物(`plan`)は `player.plan` から自分で引く。両方を受けると、ある艦と別の艦の計画という
  あってはならない組を渡せる引数の形になる。
- **既定値で埋めてよいのは、そのゼロ値が単位元として意味を持つときだけ。** 速度差の基準
  (`FloatingOrigin` の `v`)のゼロは「基準なし」として意味を持つが、位置のゼロは「原点にいる」
  という別の意味になる。座標スケール的にたまたま実害が出ないことを根拠に既定値で埋めない。
- **実体の死は除去であって、亡骸を配列に残したまま別の真偽値で「無い」と言わない。** 自機も
  他の `GameEntity` と同じく `alive` を失った時点で取り除かれ、「操作できる艦が無い」は
  `ActivePlayerController.current === null` だけが表す。亡骸を残すと、その配列を回る全ての
  読み手が「これは受け取ってよい相手か」を `alive` で判定し直すことになり、判定を1箇所でも
  忘れると死んだ相手に対して処理が走る。**亡骸に用があるように見えるモジュール(追従カメラなど)が
  あるとしても、そのために実体の生存期間を延ばさない** — 用がある側が、自分が要るものを
  自分で持つ(追従カメラが持つのは最後に組んだ視点であって、艦への参照ではない)。

### A-22. ステージは一般形の特殊化であって、特別扱いの分岐ではない
**種別**: 設計方針
**要約**: 一般形は「自機0..n隻・勝敗なし・任意配置」で、攻略ステージがその特殊化。「モード」という第二の軸を作らない。`Game` はどのステージが動いているかを知らない。能力(capability)はステージ側が宣言し `Game` はその値を読むだけ。

**一般形は「自機0..n隻・勝敗なし・任意配置」で、攻略ステージのほうがその特殊化**である
(自機を1隻に固定し、それが撃墜されたら敗北にする、という制限がかかったもの)。逆ではない。
したがって**あるモードでしか使えない機能というものは存在しない** — すべての機能は一般機能であり、
ステージ側がそれを制限する。

- **「モード」という第二の軸を作らない。** ステージを指す識別子は `StageId` ひとつだけで、
  「ステージか、それ以外か」を表す型(`GameMode` / `LaunchSelection` の類)を作らない。
  最も制限の無いステージも `StageId` の一員として `STAGE_CLASSES` に並び、`?stage=<id>` で起動し、
  `stage-dictionary.ts` の `*For(stageId)` を他と同じように引かれる。**レジストリの外に置いて
  特別に `new` する経路を作らない。**別の軸を立てた瞬間、起動解決・セーブのメタ・選択画面・
  `Game` の生成の4箇所すべてに同じ分岐が生える。
- **`Game` はどのステージが動いているかを知らない。** `instanceof` も `mode === 'creative'` も
  書かない。ステージごとに違う挙動が要るなら、それは**ステージ側が宣言する能力(capability)**
  であり、`Game` はその値を読むだけ。
  - 実行時に問い合わせる能力 → `Stage` のインスタンスフィールド(`freeProcurement`、
    `executesPlans`)。既定値は基底クラスが持ち、制限/拡張するステージだけが上書きする。
  - `Stage` の生成より前に要る能力 → ステージクラスの static 宣言を `stageClass` から直接読む
    (`ephemerisConfig`)。
- **基底の既定実装は一般形の側に寄せる。** 制限の無いステージが「何もしない」で済むよう既定を置き、
  制限するステージが上書きする(`Stage.init` の既定は初期配置を何も置かない)。既定を攻略ステージ
  向けに置くと、制限の無いステージのほうが空の override を持つことになり、どちらが一般形か
  コードから読めなくなる。
- **起動時の状態は、モードではなく状態から導く。** 「クリエイティブだからマップで始める」ではなく
  「艦が0隻だから戦闘ビューに入れず、マップで始める」。前者は条件が増えるたびに分岐が増え、
  後者は増えない。
- **選択画面のための宣言(`select*`)は見た目だけを決める。** `selectGroup`(どのタブに並べるか)・
  `selectLabel` / `selectSub` / `selectKeys` / `hiddenFromSelect` は選択画面の表示のためだけにあり、
  **挙動の分岐に読んではいけない。**ここを挙動の判定に使うと、UI の都合で付けた分類がそのまま
  モードとして復活する。
- **能力の名前はモードを指さない。** `creative` ではなく、それが実際に何を許すのか
  (`freeProcurement` = 調達が無償、`executesPlans` = 艦が自分の軌道計画を実行する)で名づける。
  モード名で名づけると、同じ挙動を別のステージにも許したくなった瞬間に嘘になる。
- **一般形との差はステージが「制限する」ことだけで、一般形の側に特例を彫り込まない。**
  ある挙動をステージごとに切り替える能力フラグを足したくなったら、まずその挙動が
  一般形として1つに定まらないかを疑う。定まるなら、フラグではなく一般形の方を直す。
- **文書も同じ構造で書く。** 節を立てるなら他のステージ(`DEVELOP/SPEC/` の「第二ステージ」
  「ステージ00」)と同じ粒度の**ステージ1つとして**立て、モードという第二の軸として説明しない。
  他との差は能力の言葉(`freeProcurement` / `executesPlans` / `authoring`)で書き、
  **「〜モードでのみ」という書き方をしない** — 実際の条件は能力の有無であって、ステージの名前ではない。
  文書の構造そのものが次の実装者に事実誤認を作り、分岐として実装へ戻ってくる。

## B. 命名規約

### B-1. 識別子の基本表記
**種別**: 命名
**要約**: クラス/interface/type/enum は PascalCase、関数/メソッド/getter/setter/フィールド/変数/引数は camelCase、ファイル名/ディレクトリ名は kebab-case、モジュール定数・static定数は UPPER_SNAKE_CASE。略語は1単語として扱う。

- クラス、interface、type、enum は `PascalCase` とする。
- 関数、メソッド、getter、setter、フィールド、変数、引数は `camelCase` とする。
- TypeScript ファイル名とディレクトリ名は `kebab-case` とする。
- 固定値として共有するモジュール定数と static 定数は `UPPER_SNAKE_CASE` とする。単に `const` で
  宣言したローカル変数は `camelCase` とする。
- 略語は `camelCase` / `PascalCase` の中では一つの単語として扱う。`bodyId`、`toEci`、
  `projectToNdc`、`sphereLodLevel`、`headingHpMarkerSvg`、`setRcs`、`jdTdb` の形を使う。
  `UPPER_SNAKE_CASE` では `SIM_EPOCH_JD_TDB` のように略語も大文字にする。
- JavaScript、Web API、ライブラリが定めた `URLSearchParams`、`getUTCDate`、`WebGPU` などの表記は
  変更しない。
- 一文字名は、短い数式、狭いコールバック、ループ添字など、意味が慣習とスコープから一意に決まる
  場所に限る。

### B-2. クラスメンバーと公開範囲
**種別**: どちらとも言えない(アクセス修飾子の設計方針だが、`_` プレフィックスは命名規約そのもの)
**要約**: クラスのメンバーには `public`/`protected`/`private` を明示する。公開getterの正本となるprivateフィールドだけ `_name` を付ける。コンストラクタ引数プロパティは値をそのままフィールド保持する場合に使う。

#### アクセス修飾子

- クラスのメンバーには `public`、`protected`、`private` のいずれかを明示する。
- 外部利用をそのクラスの契約として意図したメンバーだけ `public` にする。
- 継承先へ提供することを意図したメンバーだけ `protected` にする。
- それ以外は `private` にする。現在外部から使われていないという理由だけではなく、その操作を外部へ
  約束するかどうかで判断する。
- 外部へ公開するフィールドは原則 `readonly` とする。mutable な public フィールドは禁止しないが、
  状態の所有者と変更条件を明確にできる場合に限る。
- 状態変更時に不変条件、連動する更新、副作用がある場合は、public フィールドへの代入ではなく、
  状態を所有するクラスのメソッドに変更を閉じる。

```ts
class Player {
  private _hp = 100;

  public get hp(): number {
    return this._hp;
  }

  public applyDamage(damage: number): void {
    this._hp = Math.max(0, this._hp - damage);
  }
}
```

#### 公開依存とアクセサ

- クラスが保持する別オブジェクトを外部へ公開するときは、private フィールドを正本とし、public getter
  から渡す。
- 公開getter `name` の正本となるprivateフィールドだけ `_name` とする。
- 対応する公開getterまたはsetterがないprivateフィールドには `_` を付けない。
- `_` は「private」「内部用」「未使用」を一般的に表す接頭辞として使わない。

```ts
class Game {
  public constructor(private readonly _input: Input) {}

  public get input(): Input {
    return this._input;
  }
}
```

公開しない依存には `_` を付けない。

```ts
class PlanGuide {
  public constructor(
    private readonly hud: Hud,
    private readonly uiSfx: UiSfx,
  ) {}
}
```

#### コンストラクタ引数プロパティ

- コンストラクタ引数を同じ値のままフィールドとして保持するときは、コンストラクタ引数プロパティを
  使う。
- 値の検証、変換、条件付き代入、遅延初期化が必要なときはフィールドを別に宣言する。
- コンストラクタにも `public` を明示する。

```ts
class Controller {
  public constructor(
    private readonly hud: Hud,
    private readonly input: Input,
  ) {}
}
```

### B-3. 名前が表す文法と意味
**種別**: 命名
**要約**: 名前と所属先を合わせて「何が何をするか」が分かる名前にする。モジュール関数では動詞の対象を名前に含める。メソッドでは対象がクラス自身なら重ねない。同じ概念には同じ語を使う。

- 名前と所属先を合わせて「何が何をするか」が分かる名前にする。
- モジュール関数では、原則として動詞の対象を名前に含める。
- メソッドでは、対象がクラス自身であることが明白なら対象を重ねない。`plan.clearPlan()` ではなく
  `plan.clear()` とする。
- `process`、`execute`、`handle`、`change` のように対象も結果も示さない動詞だけの名前を避ける。
- `update`、`sync`、`render`、`clear`、`reset`、`dispose` など、意味が所属先の責務から一意に決まる
  標準操作は動詞だけでもよい。
- 同じ概念には同じ語を使う。既存の正本となる名前がある場合、類義語を新設しない。
- 一般語より、その領域で意味が確立した語を優先する。`integrate`、`interpolate`、`project`、
  `collide` などの専門語を曖昧な一般動詞へ置き換えない。

---

### B-4. 基本動詞
**種別**: 命名
**要約**: 同じ操作に複数の動詞を並立させないため、一般的な操作には決まった語を使う(読み取りと計算/生成/状態変更/イベント・消費・解放/変換/フレーム処理で予約する動詞/イベントの入口と通知の各カテゴリ)。

同じ操作に複数の動詞を並立させないため、一般的な操作には次の語を使う。ここにない専門動詞は、
既存の語と意味が重複せず、動作をより正確に表す場合に使える。

#### 読み取りと計算

- `get` — 保持済みの値を副作用なく返す。状態を変更しない。
- `find` — 条件に合うものを検索する。見つからない結果を取り得る。
- `compute` — 入力から値を副作用なく計算する。一般的な計算に `calculate` を新設しない。
- `is` / `has` / `can` — boolean または型述語を返す。

#### 生成

- `create` — 新しい値またはインスタンスを作る。一般的な生成に `make` を新設しない。
- `build` — Three.js のメッシュやオブジェクトを構築し、シーンへ登録する。
- `generate` — 乱数、規則、入力集合から複数または手続き的なデータを生成する。

#### 状態変更

- `set` — 指定された値へ置き換える。
- `add` — 集合または所有対象へ追加する。
- `remove` — 集合または所有対象から取り除く。
- `clear` — 保持内容を空にする。
- `reset` — その型が定める初期状態へ戻す。
- `update` — 時間、入力、イベントに応じて論理状態を進める。
- `sync` — 計算済みの論理状態を、既存の表示物またはDOMへ反映する。

#### イベント、消費、解放

- `handleX` — 入力またはイベント `X` を処理する。`handle` だけでは使わない。
- `takeX` — `X` を返すと同時に保管場所から取り除く。
- `dispose` — GPU資源、DOM、イベント購読など、そのオブジェクトが所有する資源を解放する。

#### 変換

- `toX` — 現在の値を `X` へ変換する。
- `fromX` — `X` から現在の型または表現を作る。

#### フレーム処理で予約する動詞

- `render` — three.js renderer の `render(scene, camera)` を実際に呼ぶ処理にだけ使う。
- `update` — 論理状態またはシミュレーション状態を進める。THREE.js オブジェクトを変更しない。
- `build` — 表示オブジェクトを構築してシーンへ登録する。
- `sync` — 既に登録済みの表示オブジェクトまたはHUDを論理状態に一致させる。論理状態を進めない。
- `draw` は使わない。
- top-level のフレーム処理は `update` → `sync` → `render` の境界を守る。`dt` を受け取るのは
  `update` 側だけとする。

#### イベントの入口と通知

- `handleX` は、外部から受け取ったイベントまたは入力 `X` をその場で処理するメソッドに使う。
- `onX` は、`X` が起きたときに呼び出されるコールバックまたはコールバックプロパティに使う。
- `handleX` と `onX` を同じ意味で使わない。

---

### B-5. boolean
**種別**: 命名
**要約**: `isX` はboolean/型述語だけを表す。`isX`=状態、`hasX`=所有・存在、`canX`=実行可能性、`shouldX`=方針評価の結果、`forceX`=通常の省略・キャッシュ・選択条件を明示的に無視する指定。booleanは原則肯定形。

- `isX` で始まるフィールド、変数、getter、関数、メソッドはbooleanまたは型述語だけを表す。
- `isX` は状態、`hasX` は所有・存在、`canX` は実行可能性を表す。
- `shouldX` は、条件や方針を評価した結果「Xするべき」を表す。現在の状態には使わない。
- `forceX` は、通常の省略、キャッシュ、選択条件を明示的に無視してXを行わせる指定にだけ使う。
  通常状態には使わない。選択肢が二つを超える場合はbooleanではなくunionやenumを使う。
- booleanは原則として肯定形にする。
- 非表示、抑制、禁止など、否定状態そのものが領域上の意味を持つ場合は `hidden`、`suppressed`、
  `blocked`、`disabled` を使える。
- `isNotX`、`hasNoX` のような否定接頭辞は使わない。否定は利用箇所の `!` で表すか、意味のある
  肯定状態へ言い換える。

---

### B-6. 単位と座標系
**種別**: 命名
**要約**: シミュレーション内部の正本はSI単位に統一。外部データ・ブラウザAPI・UI入出力の境界では自然な単位を使い `Deg`/`Days`/`Ms`/`Au` などを名前に含めて境界で一度だけSIへ変換する。公開API・クラスフィールド・モジュール境界では基準系と物理量を名前で示す。

#### 単位

- シミュレーション内部の正本はSI単位に統一する。
- 外部データ、ブラウザAPI、UI入出力では、その境界に自然な単位を使える。その場合は `Deg`、
  `Days`、`Ms`、`Au` などを名前に含め、境界で一度だけSIへ変換する。
- 同じスコープに異なる単位が共存する場合は `Sec`、`Ms`、`M`、`Km`、`Mps`、`Mps2`、`Rad`、
  `Deg`、`Kg` などのサフィックスで区別する。`Mps2` は `m/s²` を表す。
- 型、関数の契約、狭い数式から単位が一意に決まる場合は、すべての名前へ単位を重ねない。
- 数値の単位と座標系を名前だけで十分に表せない場合は、コメント規約に従って `// ECI [m/s]` の
  ように記す。

#### 座標系と物理量

- 公開API、クラスフィールド、モジュール境界では、`eciPosition`、`eciVelocity`、`bodyTorque`、
  `cameraPosition`、`scenePosition`、`displayPosition`、`relativePosition` のように基準系と物理量を
  名前で示す。
- `world` は ECI 絶対座標と Three.js の floating-origin 座標の両方に解釈できるため、単独で
  座標系名に使わない。
- `local` は、何に対するローカル座標かが型または所属先から一意に決まる場合だけ使う。
- 相対量は、必要に応じて `targetRelativePosition`、`cameraRelativePosition` のように基準対象も示す。
- 短い純粋関数と数式に対応する狭いスコープでは、`r`、`v`、`a`、`t`、`dt`、`mu` を使える。
- 変換関数は `toEci`、`fromOrbitAxes` のように変換先または変換元を名前に含める。

---

### B-7. コレクションと派生状態
**種別**: 命名
**要約**: 配列/Set/Iterableなど複数要素を表す名前は複数形。Mapはキーが重要なら `valuesByKey` の形。件数は `Count`、公開または長寿命の添字は `Index`(`Idx` は使わない)。`Cache`/`Pool`/`Scratch`/`Queue`/`Revision` の使い分け。

- 配列、Set、Iterableなど複数要素を表す名前は複数形にする。
- Mapはキーが意味上重要なら `valuesByKey` の形にする。例: `bodiesById`、`textureByBodyId`。
- データ構造自体が処理上重要でない限り、`List`、`Array`、`Map`、`Set` を名前に含めない。
- 件数は `Count`、公開または長寿命の添字は `Index` とする。新しい名前に `Idx` を使わない。
- 短いループ添字は `i`、`j` を使える。
- 再計算を避ける保存値は `Cache`、再利用するオブジェクト群は `Pool`、一時計算用に使い回す領域は
  `Scratch`、順序付き待ち行列は `Queue`、変更世代は `Revision` とする。
- `items`、`data`、`list` のような一般名は、対象が所属先または狭いスコープから一意に分かる場合だけ
  使う。

---

### B-8. 未使用引数
**種別**: 命名
**要約**: `_name` は固定シグネチャ(interface/継承/コールバック)により宣言が必要だが意図的に使わない引数にだけ使う。自分でシグネチャを変更できる関数では未使用引数を削除する。未実装・実装途中を理由に使わない。

- `_name` は、interface、継承、コールバックなど固定されたシグネチャにより宣言が必要だが、その実装
  では意図的に使わない引数にだけ使う。
- 自分でシグネチャを変更できる関数では未使用引数を削除する。
- `_` 単独ではなく、`_event`、`_dt`、`_player` のように引数の意味を残す。
- 未実装、実装途中、将来使う予定という理由で `_name` を使わない。
- `_name` を使うようになった時点で `name` に改名する。

---

### B-9. 型と不変性
**種別**: どちらとも言えない(TypeScript の型設計方針であり、命名というより書き方の規約)
**要約**: 公開契約・実装できる契約には `interface`、union/intersection/mapped type/関数型には `type` を使う。再代入しないフィールド・入力データ型のプロパティは原則 `readonly`。exported関数とpublic/protectedメソッドは戻り値型を明示する。

- オブジェクトの公開契約と、クラスが実装できる契約には `interface` を使う。
- union、intersection、mapped type、関数型には `type` を使う。
- 再代入しないフィールドは原則 `readonly` とする。
- 入力データ型のプロパティは原則 `readonly` とする。
- 読み取り専用の配列引数と返り値は `readonly T[]` とする。所有者自身が変更する配列だけ `T[]` とする。
- exported関数とpublic/protectedメソッドは戻り値型を明示する。

---

### B-10. クラスの役割名
**種別**: 命名
**要約**: 接尾辞は、そのクラスが何を所有し、いつ動くかを表す場合だけ付ける(単に具体的に見せるために付けない)。`Manager`/`Controller`/`System`/`Service`/`View`/`Panel`/`Editor`/`Picker`/`Registry`/`Guide` の使い分け。

接尾辞は、そのクラスが何を所有し、いつ動くかを表す場合だけ付ける。単に名前を具体的に見せるために
`Manager`、`System`、`Service` を付けない。

- `Manager` — 一つの概念に属する状態、選択、方針を所有し、その概念に対する操作をまとめる。
- `Controller` — 入力または外部からの命令を受け、複数の状態変更を調整する。
- `System` — フレーム処理または多数の対象にまたがる一つの機能を構成し、下位オブジェクトを統括する。
- `Service` — 呼び出し単位の処理を提供する。画面やフレーム周期の状態を所有せず、保存、読込、変換などの
  ユースケースを実行する。
- `View` — 表示物を所有し、論理状態を表示へ反映する。ゲーム状態の正本を所有しない。
- `Panel` — 一つのまとまったDOM UIを所有するViewに使う。
- `Editor` — 既存の領域モデルを選択・編集する操作と編集中の状態を所有する。
- `Picker` — ポインター位置や候補集合から、選択対象を特定する。
- `Registry` — idなどの安定したキーから定義を参照する正本を提供する。
- `Guide` — 既存状態から案内情報を導出し、通知または表示へ渡す。

複数の役割に見える場合は、主要な所有状態とpublic APIが表す一つの責務を選ぶ。選べない場合は、名前を

### B-11. ファイルとexport
**種別**: どちらとも言えない(ファイル構成規約と命名の両方に跨る)
**要約**: 一つのファイルには原則一つの主要な公開クラス/主要概念を置き、ファイル名を主要exportに対応させる。default exportは使わずnamed exportを使う。`index.ts` の一括再exportは意図的に設計したディレクトリに限る。

- 一つのファイルには原則として一つの主要な公開クラスまたは主要概念を置き、ファイル名を主要export
  に対応させる。
- default exportは使わず、named exportを使う。
- `index.ts` による一括再exportは、公開境界として意図的に設計したディレクトリに限る。
- importは、外部パッケージ、プロジェクト内のvalue import、`import type` の順にまとめる。

### B-12. 構文とフォーマット
**種別**: どちらとも言えない(主に書式・構文の規約で、命名との関わりは薄い)
**要約**: `const` を原則とし `var` は使わない。インデントは空白2文字。シングルクォート、文末セミコロン、複数行の末尾カンマ。exported関数・public/protectedメソッドの名前は呼び出し側が実装を読まずに結果と副作用を判断できるものにする。数値に領域上の意味・単位・複数利用箇所があれば名前付き定数にする。

- `const` を原則とし、再代入が必要な変数だけ `let` を使う。`var` は使わない。
- インデントは空白2文字とし、タブを使わない。
- 文字列は、文字列内の引用符との衝突を避ける場合を除いてシングルクォートを使う。
- 文末にはセミコロンを付ける。
- 複数行の配列、オブジェクト、引数、型引数には末尾カンマを付ける。
- 一行には一つの文または一つのメンバー宣言を書く。
- 一行120文字を目安とし、名前や文字列を不自然に分割せず、意味のまとまりで改行する。
- 一行のガード節では波括弧を省略できる。複数の処理を持つ条件分岐では波括弧を使う。
- exported関数、publicメソッド、protectedメソッドの名前は、呼び出し側が実装を読まずに結果と副作用を
  判断できるものにする。
- 型アサーション `as` と非nullアサーション `!` は、その前提が型以外の仕組みで保証されている場合に
  限る。
- 数値に領域上の意味、単位、複数の利用箇所がある場合は名前付き定数にする。短い数式に固有の係数は
  数式の近くに置ける。
- クラスメンバーは機械的なアクセス範囲順ではなく、責務ごとに関連するフィールド、アクセサ、メソッド
  を近くへ置く。
