# 予測と実シミュレーションの二重実装を解消する

## この計画が正すもの

**天体との接触が、判定される経路によって違う答えを出していること。** 同じ「個体1つが天体の
表面へ届いたか」という問いが `src/` に3箇所あり、走る時間加速帯も、相手にする天体の顔ぶれも、
起きる結果も揃っていない。

原因は2つに分かれ、**片方がもう片方を生んでいる。**

- **(A) 実シミュレーションが時間加速で物理を変えている**(第3章)。倍率で判定を呼んだり
  呼ばなかったり、相手にする天体を替えたりしている。
- **(B) 天体を相手にする絞り込みが実シミュレーション側に無い**(第4章)。全天体を総当たりする
  以外の手段が無いので、(A) の分岐が「費用を賄う唯一の方法」として居座っている。

**(B) を先に潰さなければ (A) は直せない。** 逆に (B) だけを潰しても、倍率で結末が変わる構造は
残る。両方やる。

正した先で得たいのは対称性ではない(第1章)。`Simulator` と `Predictor` は役割が違い、その違いから
出ている差は揃えてはならない。吸収するのは **役割の違いに由来しない差だけ。**

## この計画が前提にしていること

- **2球体の掃引接触判定器は `physics/sphere-contact.ts` の `sweptSphereContact` ただ1つで、
  解法を1つしか持たない。** 常に三次曲線で解き、近似を選ぶ引数は無い。したがって本計画で測る
  失敗は、近似の粗さと混ざらない。精度を落として費用を買う調整は本計画の範囲外で、
  **判定回数を減らしてもなお費用が残ったときに初めて検討する。**
- **重力を及ぼす `GameEntity` は存在しない。** 重力源も表面を持つ相手も `Attractor` だけ。
- **焼失(大気密度の状態判定)と衝突(掃引の離散事象)は別の判定・別のパラメータ・別の死因で
  ある。** 本計画は焼失に触れない — 扱うのは衝突側の呼び出し経路だけ。
- **`PredictedArc` は焼失を判定しない。** 弧の打ち切りは、非有限値の検出を除けば表面到達だけで
  起きる。本計画で「弧が接触で打ち切る」と言うとき、それは弧の唯一の打ち切り条件を指す。
- 既定レジストリ `SOLAR_SYSTEM` は **101 体**。うち `mu: 0` が 36 体なので重力源は 65 体、
  `atmosphere` を持つのは 1 体。

# 第1章 役割の違い — 揃えるものと揃えないもの

`Simulator`(実シミュレーション)と `Predictor` / `PredictedArc`(予測)は、どちらも「1つの物体を
1歩進める」処理を持つ。しかし**扱っているものが違う** — 前者は相互作用し、多態の反応を持ち、
姿勢と環境を運ぶ `GameEntity` を数百体、後者は自由落下だけを積む `PredictedArc` を数本。
**1本にはまとめられない。**

各論点は、まず**その差が 1-1 / 1-2 から出ているか**で仕分ける。出ていないものだけを吸収する。

## 1-1. 同時性

`Simulator` は生存する全個体を、**同じ1つの瞬間で同時に**進める。`PredictedArc` は選ばれた少数の
弧を1本ずつ、**それぞれ別の先端時刻で**伸ばす。ここから:

| | 実シミュレーション | 予測 |
|---|---|---|
| 重力源の絞り込み | サブステップに1つ分類を組み、全個体で共有 | 弧ごとの成員判定 + 期限つき再訪 |
| 個体どうしの接触 | 解ける | 解けない |
| 天体を相手にする絞り込み | **共通の瞬間を持つので、全個体で1つの構造を共有できる**(第4章) | 弧ごとにしか組めない |

分類を1回だけ組んで全個体で使い回すのは計算量オーダーの話であると同時に**正しさの要件**でもある —
A→B と B→A を別々の瞬間に組んだ構造から引くと、対称であるべき相互作用に処理順依存の誤差が入る。
弧にはその「共通の瞬間」が無いので、この共有はできない。

**ただし「個体どうしの接触」と「天体との接触」は別の問い。** 前者は同時性を要するが、後者は
天体側へ及ぶ反作用が(質量比により)無いので、相手の状態を書き換える必要がない。
**この非対称が第4章の設計の土台になる。**

## 1-2. 刻みの決まり方

`Simulator` は毎フレーム `simTime + simDt` へ**必ず到達しなければならない**ので、刻みはそのフレームの
時間送りから決まる。`PredictedArc` は `simTime` を追い越されない範囲で先へ伸びればよいので、
1フレームの歩数を予算(`ARC_STEP_BUDGET`)で切り、足りなければ遅れる — 追い越された弧は読まれ
なくなり、その個体は実シミュレーションの積分へ落ちるだけで壊れない。

## 1-3. 仕分けの結果

| 層 | 共通化するか | 理由 |
|---|---|---|
| RK4 の1歩 | **済**(`DynamicTrajectory.step` → `stepDynamics`) | — |
| 掃引接触の幾何 | **済**(`sweptSphereContact` 1つ) | — |
| 天体の**探し方**(絞り込みの機構) | **しない** | 1-1 由来の正当な差 |
| 天体の**窓の定義**(どの天体が表面を持つか) | **する** | 役割の違いではない |
| **刻みの規則**(再突入細分化) | **する**(対象集合だけ呼び出し側) | 役割の違いではない |
| **天体接触の反応** | **しない** | 出力先が別 — 実体は `collideWith`、弧は打ち切り |
| **時間加速による物理の分岐** | **無くす** | 弧の側に対応物が無い。役割の違いではない |

## 2-3. 2本の木から読めること

1. **底(RK4・掃引の幾何・刻みの式)は既に共有されている。** 二重なのはその上の**窓と絞り込みと
   結末**だけ。
2. **絞り込みの構造が非対称。** 弧は重力にも表面到達にも `ArcBodies` という1つの絞り込みを通す。
   実シミュレーションは重力にだけ `classifyAttractors` を持ち、**表面到達と天体接触には何も無い。**
3. **同じ問いが3つの入口から入る** — `computeAttractorResponse`(×4 以下)、`checkLoss`(常時)、
   `checkSurfaceReach`(弧)。前2つは同じ substep の中で連続して走る。
4. **`surfaceBodies` は表面判定専用の窓ではない。** `stepEnvironment` の恒星の取り出しと日照率の
   遮蔽体にも同じ配列が渡る。窓を変えると熱・電力の入力も変わる。
5. **接触は予測を捨てる経路でもある。** `applyCandidate` は変化の有無を見ずに当事者を `changed` へ
   積み、`e.state` への書き戻しが `invalidatePrediction` を呼ぶ。**触れられた側の弧が毎回捨てられる。**
6. **ゲームバランスの量が物理の質量を経由している。** ダメージは撃力を自分の質量で割って出しており、
   接触解決の内部量(`impulse`)がそのまま戦闘の調整値になっている(第6章)。

# 第3章 論点A: 時間加速が物理を変えている

## 3-1. 倍率を見て物理を切り替えている箇所

| 箇所 | 何が変わるか |
|---|---|
| `canResolvePhysicalCollisions`(×4 以下) | 接触解決を丸ごと呼ばない。**天体接触も個体どうしの接触も走らない** |
| `passiveWarpLod`(×4 超かつ `simDt > SUBSTEP_MAX_DT`) | 弾・破片を substep から外し、フレーム末尾で1歩にまとめる。イベント境界の候補からも外れる |
| `Simulator.surfaceBodies`(×4 で切替) | 表面を持つ相手を 101 体 ↔ 65 体で入れ替える |
| `base-collision.ts` の `warpLevel`(×1 / ×16 で切替) | 基地の衝突形状を フルポリゴン BVH / 低ポリゴン BVH / 複合 OBB で切り替える。**倍率で近似そのものを変えている** |

**最後の1つは死んでいる。** `warpLevel` を渡す呼び出し元が `src/` に無く
(`computeEntityResponse` は既定値のまま呼び、`map-context-actions.ts` は `1` を直書き)、
**常に LOD 0 が選ばれている。** 3-3 の「どの近似で解くか」を倍率で変えてはならないという規則に
真っ向から当たる分岐が、たまたま到達不能なだけで残っている。

**今回は `computeEntityResponse` の引数を落とすところまでにする**(段6)。`base-collision.ts` の
分岐そのものは base 側の変更を最小限に留めるため触らず、**到達不能のまま残す。**
基地の仕様が固まったときに消す。

## 3-2. 帰結

**(a) 同じ物理事象がワープ倍率で違う結末になる。** `Simulator.advance` の1サブステップは
接触解決 → `cleanup`(= `checkLoss`)の順。×4 以下では `ContactPhysics` が先に当たって
`collideWith` の多態(自機なら「高速接触により機体を喪失した」)へ落ち、×4 超では接触が走らないので
`checkLoss` が当たって「天体の地表へ到達し機体は失われた」になる。

**(b) ×4 超で敵が天体をすり抜ける。** `Enemy.checkLoss` は焼失しか見ておらず、固体表面は
`ContactPhysics` 任せ。その `ContactPhysics` が×4 超で走らない。**一方その敵の予測線は表面で
止まる** — 弧は倍率に依らず `checkSurfaceReach` を通るため。線と実体が食い違う。

**(c) `mu = 0` の 36 体が、×4 超では表面を失う。** 重力を及ぼすかと表面を持つかは別の性質で、
`mu: 0` の天体にも `radius` はある。**重力の有無で表面到達の有無が変わる理由は無い。**

**(d) `stepEnvironment` の入力も倍率で変わる。** (c) と同じ窓が恒星の取り出しと日照率の遮蔽体に
渡っているので、倍率を跨ぐと遮蔽体の顔ぶれが 101 ↔ 65 で入れ替わる。

## 3-3. 仕様判断

**`simSpeed` と密結合な分岐を物理に残さない。** 倍率で変えてよいのは**1歩をどれだけ細かく
刻むか**までで、次を変えてはならない。

- 判定を呼ぶか呼ばないか
- どの近似で解くか
- どの個体を判定の対象にするか
- どの天体を相手にするか

**対象外**: `canShipAct`(高倍率で自機の推進・射撃と敵の射撃が成立しない)と `canResupplyAmmo` は
**入力とゲーム進行の側の判断**であり、同じ入力に対する物理の答えを変えない。本計画は触らない。

**個体どうしの接触ゲート(×4 以下)は残す。** 天体との接触と違って個体どうしは**相手の状態も
積分で決まる**ので、20 s 刻みでの撃力交換が何を意味するかが天体接触と同じではない。
1-1 の非対称(反作用の有無)がそのまま根拠になる。

## 3-4. `passiveWarpLod` は種別で分けているのでアドホックだが、まだ捨てられない

`passiveWarpLod` は「弾と破片だけ」という**種別による**場合分けで、3-3 の精神に反する。
避けられるなら避けたい。

**妨げているのは性能と精度の二律背反で、いまは断言できない。** 廃止すると破片 500 体の RK4 が
1 歩から 64 歩へ増える(積分費用が 64 倍。12-1 の見積り)。一方、残せば弾・破片の区間が
1フレーム全体を張り、イベント境界も無視される。

→ **判断を保留する。** 他の論点をすべて解消し、可能なパフォーマンス改善を全て入れた状態で
再実測してから決める(段10)。ただし**判定からの除外だけは段7 で先に解消する** — 天体接触の
判定は倍率にも種別にも依らず全生存個体が受ける。保留されるのは**積分の刻みを種別で分けている
ことだけ**になる。

## 3-5. 費用の賄い方

3-1 の分岐はどれも「全帯域で判定すると費用が合わない」ことへの対処である。**その費用は
第4章の絞り込みで落とす。** 落とせなければ 3-3 の判断そのものを取り下げることになるので、
**第4章を先に入れる。**

# 第4章 論点B: 天体を相手にする絞り込みが実シミュレーション側に無い

## 4-1. 同じ判定が3箇所にある

| 判定する場所 | 走るワープ帯 | 対象 | 相手の窓 | 結末 |
|---|---|---|---|---|
| `ContactPhysics.computeAttractorResponse` | ×4 以下のみ | `collides` を立てた個体 | 総当たり 101 体 | `collideWith` — **既に多態** |
| `GameEntity.checkLoss` 系 | 常時・毎 substep | 全生存個体 | 総当たり 101/65 体 | `alive = false` + 種別ごとの演出 |
| `PredictedArc.checkSurfaceReach` | 常時(弧の伸長時) | 弧 | `ArcBodies` の成員 | `_impact` + `_truncated` |

**`ContactPhysics` は既に天体を `invMass: 0` の接触相手として扱い、反応の多態も `collideWith` で
成立している。** 求める形の半分は既にある。`checkLoss` の幾何判定はそれが×4 超で走らないことの
穴埋めであり、×4 以下では**同じ個体 × 同じ天体を同じ substep で2回掃引にかけている。**

## 4-2. 総当たりの費用は、いま既に払っている

**これは計画が新たに持ち込む費用ではない。** `EntityManager.cleanup` は倍率に依らず毎 substep、
全生存個体 × 全天体を掃引にかけている。

`?stage=debug-load`(破片 500)+ ×131072 での見積り:

- `simDt = dt × 131072`。60 fps 想定 `dt = 1/60` で `simDt ≒ 2185 s`。
- `maxStep = max(SUBSTEP_MAX_DT 20, 2185/64) = 34.1 s` → **substep 数 = 64**。
- 掃引回数 = 生存個体 501 × substep 64 × 天体 65 = **約 208 万回/フレーム**。
- 棄却1回 ≈ **77 ns**(`tests/perf/exp10-sphere-contact.ts` の「周回中の地球(触れない)」)
  → **約 160 ms/フレーム**。

**この数字は現状の測定対象であって、計画後の予測ではない。** 段0 で実測して確かめる。

## 4-3. 絞り込みに課す条件

1. **常に安全側へ倒す。** 通す候補が増えるのは構わないが、接触しうるペアを落としてはならない。
   絞り込みは判定器の答えを変えない — これが broad phase の唯一の正しさの条件。
   区間内に接触があるなら、区間始点の距離は
   `半径和 + |Δr_個体| + |Δr_天体| + 弦と弧の乖離` 以下(三角不等式)。乖離の項は上限で取る。
2. **種別・時間加速・「動いていないから」で除外しない。** 除外の根拠は距離と区間変位という
   物理量だけにする。
3. **個体側のグリッドを流用しない。** 天体の半径は数百 m から 7×10⁸ m まで7桁ちがい、
   一様グリッドのセル一辺を両方に効かせられない。`attractors.ts` の重力グリッドも流用できない —
   あちらのセル一辺は重力到達距離で、表面接触には粗すぎる。
4. **1個体・1 substep あたりの掃引呼び出しが天体数に比例しないこと。**

**採る形(2段)** — 1-1 の同時性がここで効く。参加者は全員同じ substep 区間を共有するので、
1段目を substep に1回だけ組んで全個体で使い回せる。

- **1段目(substep に1回)**: 参加者全員を覆う境界体積と、各天体の膨らませた球(半径 + 天体の
  区間変位 + 参加者の最大区間変位 + 乖離の上限)を突き合わせ、**この substep で誰かが触れうる
  天体の短い一覧**を作る。費用は天体数に比例するが、**個体数には比例しない**(101 回/substep)。
- **2段目(個体ごと)**: 短い一覧に対してだけ安価な距離判定を掛け、通ったものだけ
  `sweptSphereContact` へ渡す。

参加者が太陽系全体に散っていて1段目が短くならない場合は、境界体積を空間グリッドの占有セル単位へ
落として同じことを繰り返す。**そこまで要るかは段0 の実測が決める** — 実地では個体は自機の周りに
固まっており、1段目を通る天体は 1〜3 体になるはず。

## 4-4. 天体接触は個体ごとに独立に解ける

`ContactPhysics.resolveInOrder` が持っている仕掛け — 作業マップ、TOI 昇順の大域ループ、
解決回数の上限(`CONTACT_MAX_RESOLUTIONS_PER_SUBSTEP = 8`)、dirty な候補の引き直し —
は**すべて「解決が相手の状態を変え、それが別のペアの答えを変える」ことへの対処**である。

**天体との接触にはその連鎖が無い。** 天体は無限質量で状態を書き換えられず、個体 A の解決は
個体 B の答えに影響しない。したがって天体接触は

> 個体ごとに、その区間で最も早く触れる天体を1つ求め、反発を当て、`collideWith` を呼ぶ

という素朴なループで解ける。**大域ループも作業マップも上限も要らない。**

- **上限が要らないことの効き目**: 全生存個体へ広げても「1 substep で 8 件までしか解決されず、
  残りが次の substep へ持ち越されて天体の内側に留まる」という壊れ方が原理的に起きない。
- **「最も早く触れる天体を1つ」は `reachedBody` がすでに答えている。** 弧が打ち切りに使っている
  関数と同じ問いで、実シミュレーション側は答えを打ち切りではなく反発と `collideWith` へ渡す。

**代償**: 天体接触と個体どうしの接触の間で TOI 昇順が保証されなくなる(2つのパスに分かれるため)。
天体接触を先に解決する規則にし、SPEC へ明記する(段3)。**同じ substep で天体と個体の両方に
触れる配置は実地に出ない** — ×4 以下の substep は通常 0.064 s で、その間に惑星と別の個体の
両方へ届く軌道は作れない。

## 4-5. 個体どうしの側

個体どうしは既に空間グリッドで 27 近傍へ絞れており、この計画で走るワープ帯も変えない。ただし
天体側を足すときに以下を壊さないこと。

- **候補列に載せたペアは、解決ループが最大8回ぜんぶ舐める**(`earliestContact`)。天体側の
  ペアを候補列へ混ぜると、絞り込みを通った数がそのまま 8 倍で効く。**4-4 のとおりパスを分けるので
  混ざらない。**
- `contactCellSize` は**全参加者の最大到達量**でセル一辺を決めるので、1体の速い個体が全体のセルを
  膨らませる。天体側とは別のグリッドなので影響は閉じるが、**個体側の費用として段0 で測る。**

# 第5章 論点C: 天体接触への反応が揃っていない

判定を接触経路へ寄せると、**天体接触の帰結は `collideWith` だけが決める。** 現状のままでは
何も起きない種別が残る。

| 種別 | `collideWith` | 天体接触の帰結 | 寄せたとき |
|---|---|---|---|
| `Player` | あり | 物理ダメージ → HP 0 で喪失 | **そのまま** |
| `Enemy` | あり | 同上 → 撃破記録(`'collision'`) | **そのまま** |
| `Bullet` | あり | `alive = false` | **そのまま** |
| `DebrisPiece` | あり | 弾と薬莢の音だけ。**天体接触で何も起きない** | **要追加** |
| `AmmoPickup` | 無し(基底の no-op) | 何も起きない | **要追加** |
| `Base` | 無し(基底の no-op) | 何も起きない | **要追加** |
| `RadiatorFold` | あり(艦へ委譲) | 艦へダメージ | **参加者から外す**(5-3) |
| `BeltSection` | 無し | 何も起きない | **参加者から外す**(5-3) |

## 5-1. 基底の既定を置く

**基底 `GameEntity.collideWith` の既定を「相手が天体であれば `alive = false`」にする。**
`Player` / `Enemy` / `Bullet` は既に上書きしているので影響を受けず、`AmmoPickup` / `Base` は
いまの `checkLoss` と同じ帰結(消滅)を得る。`DebrisPiece` は自分の分岐のあとで基底へ委譲する。

## 5-2. 条件は肯定形で書く

**「相手が `GameEntity` でなければ」と書いてはならない。「相手が天体であれば」と書く。**
挙動は同じだが、否定形は接触の相手に第3の種別が増えた瞬間に**黙って**誤った側へ落ちる。

`Attractor` は class ではなく型なので `instanceof` が使えない。型述語を1つ置き、**判定の中身を
そこへ閉じ込める。**

```ts
// src/game/simulation/contact-target.ts
import type { Attractor } from '../../physics/attractor';
import type { GameEntity } from '../game-entity/game-entity';

// 接触の相手。個体か、無限質量の天体か。
export type ContactTarget = GameEntity | Attractor;

// 相手が天体か。重力定数 mu を持つのは天体だけ。
export function isAttractor(target: ContactTarget): target is Attractor {
  return 'mu' in target;
}
```

**型だけを import するので、`contact.ts` ↔ `game-entity.ts` の実行時循環を作らない。**

同じ形の否定が `Enemy.collideWith` の死因の出し分け
(`other instanceof GameEntity ? 'killed' : 'collision'`)にもあるので、
`isAttractor(other) ? 'collision' : 'killed'` へ直す。

**触らないもの**: `Bullet.contactsWith` と `contact.ts` 内部の `instanceof GameEntity` は
**個体の側を肯定的に取り出す**ための分岐で、この論点には当たらない。

## 5-3. 接触代理は天体接触の参加者にしない

`RadiatorFold` / `BeltSection` は艦に取り付いた局所の接触代理で、**独立に消えることに意味が
無い。** 基底の既定(`alive = false`)をそのまま当てるのは誤り。

→ **天体との接触の参加者は独立した実体だけとし、接触代理は含めない。** 艦本体が天体に触れれば
艦の側が判定される。放熱板の張り出し(数 m)ぶんだけ判定が遅れるが、艦の接触半径 2.6 m に対して
意味のある差ではない。

**副次的な利益**: `Player.collisionFolds` を毎 substep 組む必要が無くなるので、高倍率で艦の姿勢から
折りを置き直す費用が消える。

## 5-4. 相対速度ゼロで天体の内側に湧いた個体

`ContactPhysics.applyCandidate` は反発が起きなかった接触を通知しない。天体へ向かって接近している
限り法線方向相対速度は負なので反発は起きるが、**相対速度ゼロで天体の内側に現れた個体は通知
されない。** 現状の `checkLoss`(位置だけを見る)はこれを拾っている。

→ **今回は塞がない。** 天体の内側に静止して湧く経路は、ステージの配置とクリエイティブモードの
設置しかなく、後者には設置位置の検証がある。**着陸を実装するとき(接地したまま留まる状態を
表現するとき)に、同じ穴をまとめて塞ぐ。**

# 第6章 論点D: 物理の質量とゲームバランスのダメージが1つのスカラーへ潰れている

**2つの別々の量が `impulse` という1つのスカラーを共有している。** 分けてから、それぞれを正す。

| | 何で決まるか | いまの実装 |
|---|---|---|
| **物理: 接触時の速度変化** | 相手の運動量(相対速度 × 質量) | `impulse × invMass` |
| **ゲームバランス: ダメージ** | **相手の種別と相対速度** | `impulse / 自分の質量` |

**後者に質量を掛けて力積へ潰したのが早急な一般化だった。** ダメージという調整値が、物理の質量を
経由して決まるようになり、質量を動かすとゲームバランスが動く構造になっている。

## 6-1. 物理側 — 薬莢・破片・弾薬ピックアップの質量を 0 にする

**`DebrisPiece` の全種別(薬莢・撃破デブリ・欠片)と `AmmoPickup` の質量を 0 とする。
弾の質量は正のまま。**

`AmmoPickup` を含めるのは同じ理由による — 質量 50 kg で `collides` を立てており `collideWith` を
持たないので、接触は跳ね返るだけだが、**回収しに近づいた艦に速度変化が入って予測が捨てられる。**
質量 0 なら艦は押されず、ピックアップの側だけが完全に弾かれる。

接触時の速度変化は相手の運動量で決まるので、**質量が 0 なら相手に与える速度変化も 0 になる。**
`GameEntity.state` への書き込みは `invalidatePrediction` を呼ぶので、いまは薬莢が艦に触れるたびに
**艦の予測弧が捨てられ、作り直しになる**(2-3 の 5)。射撃中は薬莢が絶え間なく出るので、これは
常時起きている。質量 0 にすれば速度変化が消え、**予測の再計算がなくなる。**

質量 0 の意味は **「相手に力を及ぼさないが、自分は完全に跳ね返される」= 試験粒子**。
天体(無限質量)の反対側の極で、同じ体系の両端になる。

**これはダメージの話ではない。** 質量 0 でデブリのダメージが 0 になるのは、いまダメージが力積を
経由しているからにすぎない。ダメージは 6-2 で別に決める。

## 6-2. ゲームバランス側 — ダメージを接近速度と相手種別から出す

**ダメージの根拠を `impulse` から外し、接触時の法線方向相対速度(接近速度)と相手の種別にする。**

材料は `Contact` に既にある — `selfState` / `otherState` / `normal` から
`接近速度 = −dot(sub(selfState.v, otherState.v), normal)`。3箇所で同じ式を書かないよう、
`contact.ts` に関数を1つ置く(値として求まるので、`Contact` のフィールドにはしない)。

**しきい値は、いまの定数の逆算元へ戻す。** `const.ts` のコメントが経緯をそのまま記録している —
現行の `COLLISION_DAMAGE_MIN_DV = 700/11 ≒ 63.6`、`FULL_DV = 7000/11 ≒ 636.4` は、
**旧来の接触速度しきい値 50 m/s / 500 m/s** に、艦どうし(自機 1000 kg ⇔ 敵 10000 kg、
反発係数 0.4)の換算係数 14/11 を掛けて逆算したものである。接近速度で書き直せば
**50 m/s / 500 m/s に戻る。**

**相手種別の重みは `game/` に明示的に置く。質量比から導かない** — 導いた瞬間に、物理の
パラメータがゲームバランスを動かす構造へ戻る。

### 6-2-1. 重み(暫定)

| 相手 | 重み |
|---|---|
| 解析天体 | **1.0** |
| 艦(`Player` / `Enemy`) | **1.0** |
| 基地 | **1.0** |
| `DebrisPiece` の全種別(薬莢・撃破デブリ・欠片) | **0** |
| `AmmoPickup` | **0** |

弾は `collideWith` の先頭で武装のダメージへ分岐するので、この表には現れない。

**現状の実効値との差**(参考。現状は `k = 1.1 × m_相手 / (m_自分 + m_相手)`):

| 受け手 × 相手 | 現状の実効 k | 新しい重み | 差 |
|---|---|---|---|
| 自機 × 天体 / 基地 | 1.10 | 1.0 | ほぼ同じ |
| 自機 × 敵(10000 kg) | 1.00 | 1.0 | 同じ |
| 自機 × バレル/弾倉(20 kg) | 0.0216(実効しきい値 ≒ 2,300 m/s) | 0 | 実質同じ |
| 自機 × 薬莢(1 kg) | 0.0011(同 ≒ 45,000 m/s) | 0 | 実質同じ |
| **敵 × 自機(1000 kg)** | **0.10** | **1.0** | **敵がラミングで受ける被害が約 10 倍になる** |

**最後の1行だけが実際のバランス変更になる。** 「敵は重いので衝撃を受けにくい」という現行の非対称を
引き継がず、艦どうしを対称にする判断である。

### 6-2-2. 重み 0 は「判定から外す」ではない

**種別に関わらず入り口を通す。** 重み 0 のデブリも接触の判定・解決・`collideWith` の呼び出しを
通常どおり通り、**ダメージの段で 0 が掛かるだけ**にする。判定の手前で種別を見て飛ばす実装に
してはならない — それをやると、後からデブリを凶器に戻すときに simulation 側へ手が入る。

**重みを差し替えるだけで挙動が変わる状態を保つ。** 重みの引き方は `game/` に1つ置き
(相手が解析天体なら 1.0、`GameEntity` ならその個体が持つ値)、`Player` / `Enemy` はそれを
掛けるだけにする。受け手ごとに違う重みを入れたくなったら、各自の `collideWith` の中で
上書きできる — その入り口も残す。

## 6-3. いまの式は質量 0(逆質量 ∞)で壊れる

`resolveSphereCollision` は受け持ち割合をすべて `invMass / (invMa + invMb)` の形で書いている。
`invMass = 1/0 = ∞` が入ると:

| 式 | 質量 0 の個体が絡むとき | 結果 |
|---|---|---|
| `c = a.r·(B/invM) + b.r·(A/invM)` | `∞/∞` | **NaN**(位置) |
| `rA = c − offset·(A/invM)` | `∞/∞` | **NaN**(位置) |
| `pCorr·a.invMass`(重なりフォールバック) | `(pen/∞)·∞` | **NaN**(位置) |
| `vA = a.v − normal·(impulse·a.invMass)` | `(−0)·∞` | **NaN**(速度) |

**壊れるのは稀な経路ではない。** 薬莢と破片は個数が多く、密集して現れ、互いに軌道上の物体なので、
**質量 0 どうし・質量 0 × 艦の接触は、個体どうしの接触の中でいちばん頻出する。**

さらに `contact.ts` 側:

- `collectParticipants` の参加者検査が `mass > 0` を要求するので、**質量 0 の個体はそもそも
  接触に参加できない。**
- `computeEntityResponse` の `Base` 枝は `invM = 1/other.mass` から独自に撃力と速度を書いており、
  **同じ壊れ方をする。**
- `applyCandidate` のゲートが `response.impulse === 0`。**質量 0 の個体は撃力が常に 0 なので、
  `collideWith` が永久に呼ばれない** — 判定を接触経路へ寄せたあとでは、これは
  **破片が天体をすり抜けること**を意味する。

## 6-4. 直し方 — 解析天体は質量を持たない

**解析天体が接触の反作用を受けないのは、質量が大きいからではない。速度を上書きする入り口が
そもそも無いからである** — 天体の状態は天体暦が決めており、接触解決が書き込む先が存在しない。
それを質量 ∞(逆質量 0)という値で表現するのをやめ、**解析天体の側は質量を持たない**ことにする。

いま接触に現れうる組み合わせは5通りで、2つの世界に分かれている。

| | 重力(`mu`) | 衝突の反作用 |
|---|---|---|
| 解析天体 — `mu > 0`(65 体) | 及ぼす | **受けない**(書き込む先が無い) |
| 解析天体 — `mu = 0`(36 体) | 及ぼさない | **受けない**(同上) |
| ゲームオブジェクト — 質量 0 | 及ぼさない | 受ける(全部自分で受け持つ) |
| ゲームオブジェクト — 質量が正 | 及ぼさない | 受ける(質量比で分ける) |
| ゲームオブジェクト — 質量 ∞ | 及ぼさない | 受けない(**基地。ただし理由も構造も天体とは別** — 6-4-1) |

**`mu` と質量は別の軸である。** 反作用を受けないことと重力を及ぼすことは無関係で、`mu = 0` の
36 体も同じく不動である。**両方を同じ物体に持たせると「`mu = 0` の天体は軽いから押せる」と
読み違える余地が残る。** 解析天体に質量を持たせず、ゲームオブジェクトに `mu` を持たせなければ、
その余地は型の段階で消える — **解析天体には `mu` だけ、ゲームオブジェクトには質量だけがあり、
前者は重力に、後者は衝突の反作用に使われる。両者に互換性は無い。**

→ **接触解決の入口を2つに分ける。**

- **個体 × 解析天体**: 相手は `{ state, radius }` だけを持つ(**質量を渡さない**)。受け持ちは
  常に個体が 100%。**割合の計算も場合分けも無い** — 質量 0 の個体でもそのまま通る。
- **個体 × 個体**: 双方が質量を持つ。受け持ちを割合で分ける。

  ```
  wa = (a が質量 0) ? ((b が質量 0) ? 0.5 : 1) : a.invMass / (a.invMass + b.invMass)
  wb = 1 − wa
  ```

  双方が不動(質量 ∞)なら解決しない — いまの `!(invM > 0)` のガードがそのまま担う。

**幾何(掃引・法線・重なりフォールバック)は2つの入口で共有する。分かれるのは分配だけ。**

- 位置: `c = a.r·wb + b.r·wa`、`rA = c − offset·wa`、`rB = c + offset·wb`。
  重なりフォールバックは `rA = a.r − normal·pen·0.8·wa`(同様に `rB`)。
  天体側の入口では `wa = 1` が畳み込まれて、個体の位置が半径和ちょうどへ揃うだけになる。
- 速度: `Δv_a = −(1+e)·vn·wa`、`Δv_b = +(1+e)·vn·wb`。**`impulse` を経由しない。**
- 反発したかどうかは **`vn < 0`(接近していたか)** を真偽値で持つ。
- **`impulse` は `CollisionResponse` からも `Contact` からも落とす。** 6-2 でダメージが接近速度へ
  移るので、読み手がいなくなる。物理は幾何と運動学だけを返し、ゲームバランスの量はゲーム側が
  接触の材料から組む。
- **`computeAttractorResponse` が書いている `invMass: 0` が消える。** 解析天体の質量はこの1箇所
  でしか綴られていないので、それで読み手がいなくなる。
- 天体側の入口は個体の側の状態だけを返せばよい(天体は書き換えられない)。4-4 で天体接触を
  個体ごとの独立ループへ出すのと同じ非対称がここにも現れる。

### 6-4-1. 基地の不動は、天体の不動と同じものではない

`computeEntityResponse` の `Base` 枝は、基地の状態を書き換えないことで**基地を不動として扱って
いる**。見た目は「相手が 100% 受け持つ」形で天体側と同じだが、**理由も構造も違う。**

| | 不動である理由 | 構造 |
|---|---|---|
| 解析天体 | 状態を天体暦が決める | **速度を上書きする入り口がそもそも無い** |
| 基地 | 押されないというゲーム側の判断 | **入り口(`e.state`)はあるが、呼ばない** |

→ **この2つを同じ入口へ束ねてはならない。** `Base` は `GameEntity` なので **個体 × 個体の入口を
通す。**

**不動であることは、`Base` 自身が持つ接触用の質量 ∞ で表す。**

- `GameEntity` に**接触で使う質量**を1つ置く。既定は `mass` をそのまま返し、`Base` だけ ∞ を返す。
- `Base.mass = 3e6` は**触らない** — `totalThrust / mass` で推力加速度の分母を兼ねており
  (`base.ts`、`plan-executor.ts`、`player-throttle.ts` が読む)、∞ にすると基地の推進が止まる。
- 逆質量 0 は受け持ち割合の式にそのまま入るので、**場合分けは1つも増えない。**
- contact.ts の `Base` 枝から「基地の状態を書き換えない」の直書きが消え、残るのは**形状判定だけ**
  になる。

これで 6-4 の表の「ゲームオブジェクト — 質量 ∞」が実在するようになる。**天体の不動(書き込む先が
無い)とは別物のまま、同じ分配の式で扱える。**

**`mass` が衝突の反作用と推力加速度の2つの軸を兼ねていること自体は、6-2 と同じ形の問題である。**
接触用の質量を分けることで、その分離の入り口だけは作る。**推力側の整理は本計画では触らない** —
基地の仕様は未確定事項が多く、別の作業とぶつかる。

`contact.ts` 側:

- 参加者検査を `mass > 0` から **`mass ≥ 0`**(NaN は除外され、0 と ∞ は通る)へ。
- **状態が実際に変わっていない当事者を `e.state` へ書き戻さない。** 質量 0 にする目的
  (触れられた側の予測が捨てられないこと)は、この書き戻しを止めて初めて達成される。
  `applyCandidate` が `working` へ差し替えるときに、位置・速度がどちらも変わっていない当事者は
  `changed` へ積まない。

## 6-5. ゲームオブジェクト側を `mass` と `invMass` のどちらで渡すか

**据え置き(`invMass`)を推すが、積極的な理由は無い。**

6-4 で解析天体が質量を持たなくなると、残る値は `質量 0 / 正 / ∞`(逆質量 `∞ / 正 / 0`)の
3通りだけになる。どちらの表現でも**質量 0 の端に場合分けが1つ要る**ことは変わらない。

| 表現 | 割合 `wa` が素の式で出ないのは |
|---|---|
| `invMass`(`wa = A/(A+B)`) | `A = ∞`(自分が質量 0)。相手が質量 0 の側は `A/∞ = 0` で正しく出る |
| `mass`(`wa = m_b/(m_a+m_b)`) | `m_b = ∞`(相手が不動)と、双方 0 |

条件の数はほぼ互角で、逆数を呼び出し側で払うか関数の内側で払うかの違いも互角。
**変える理由が見つからないので変えない**、というのが据え置きの根拠のすべてである。

# 第7章 論点E: 同じ規則が二度綴られている

## 7-1. 再突入細分化の2定数

関数(`adaptiveSimulationMaxStep`)は共有しているが、**境界高度と細分化の刻みという2つの定数を
両方の呼び出しが別々に綴っている。**

```
Simulator.adaptiveMaxStep:
  adaptiveSimulationMaxStep(生存する艦・敵の状態列, ephemeris.atmosphereAttractorsAt(simTime),
                            REENTRY_SUBSTEP_ALT, simulationMaxStep(…), REENTRY_SUBSTEP_MAX_DT)
PredictedArc.stepDt(consumable):
  adaptiveSimulationMaxStep([tip], collisionBodies,
                            REENTRY_SUBSTEP_ALT, this.simulationMaxStep, REENTRY_SUBSTEP_MAX_DT)
```

対象集合が違う(生存する艦・敵 / 弧の先端だけ)のは 1-1 由来の正当な差。大気天体の窓の渡し方が
違うのも実害は無い — `nearestAtmosphereBody` が `atmosphere === null` を落とすので、弧が衝突窓を
そのまま渡しても同じ1体に落ち着く。**第3の細分化帯を足すときに片方だけ直せてしまう点だけが問題。**

→ 2定数を関数の内側へ入れ、`reentryAwareMaxStep(states, atmosphereBodies, normalMaxStep)` にする。
**大気天体の窓は呼び出し側に残す** — 実シミュレーションは天体暦を、弧は `ArcBodies` を持っており、
出どころを1本にできない。

## 7-2. 重力絞り込みが同じ許容量から別の距離を導いている

両者とも許容加速度は `GRAVITY_NEGLIGIBLE_ACCEL = 1e-8 m/s²` だが、そこから導く距離の式が違う。

- `attractors.ts` の `gridCellSize`: `sqrt(最も重い grid 天体の mu / GRAVITY_NEGLIGIBLE_ACCEL)` を
  **全 grid 天体に共通のセル一辺**として使い、27近傍を引く。加えて mu の重い順
  `GRAVITY_ALWAYS_COUNT = 15` 体を常に含める。
- `arc-bodies.ts` の `gravityReach`: `sqrt(2 · その天体自身の mu / GRAVITY_NEGLIGIBLE_ACCEL)` を
  **天体ごと**に持つ。加えて最も重い天体1体を常に含める。

セル一辺は最も重い天体基準を全部に適用するので緩く、弧の側は天体ごとなので厳しい。したがって
**弧は実シミュレーションが加算する天体を落としうる。差の上限は測られていない。**

→ **測る前に式を動かさない。** 不一致が出た場合の是正方向は `attractors.ts` の側
(セル一辺を天体ごとの到達距離へ)。`arc-bodies.ts` の √2 係数は直達項と ECI 原点補正項の和から
導かれているので動かさない。

## 7-3. 掃引に渡す半径和が経路で違う

`reachedBody` は半径和に **天体の半径だけ**を渡し、個体の半径を無視する(点として扱う)。
`computeAttractorResponse` は **個体の半径 + 天体の半径**を渡す。

- **弧にとっては前者が正しい** — 弧は質量も大きさも持たない自由落下の経路である。
- **個体にとっては後者が正しい** — 個体には半径があり、表面が触れた時点が接触である。

判定を接触経路へ一本化すると、個体の側が自動的に後者へ揃う。艦 2.6 m 対 地球 6.4×10⁶ m なので
到達時刻の差は測れない大きさだが、**「なぜ2つあったか」を混同しないために書いておく。**

# 第8章 着陸を後から実装できる基盤にする(着陸自体は実装しない)

**達成すべきは、着陸が自機の多態を書き換えるだけで実装できる状態になっていること。**

`GameEntity.collideWith(other, contact, activeStage)` と `Contact` は既に必要な材料を運んでいる:

| 着陸の実装に要るもの | 現状 |
|---|---|
| 相手そのもの | `other` — 天体なら `Attractor`(`id` / `radius` / `mu` で特定できる) |
| 接触時の自分・相手の状態 | `contact.selfState` / `contact.otherState`(いずれも反応**前**) |
| 相対速度 | 上の2つの差 |
| 接地の法線 | `contact.normal`(self → other 向きの単位法線) |
| 垂直/水平成分の分解 | 法線と相対速度から出る — 「ゆっくり降りたが横に滑っている」を区別できる |
| 接触点・接触時刻 | `contact.point` / `contact.t` |

足りていないのは**呼び出し経路のほう**だけで、それを直すのが第3章・第4章である。

**今回課す制約: `selfState` / `otherState` / `normal` / `point` / `t` を落とさないこと。**
とくに状態と法線をスカラー1つへ畳んではならない — 畳むと着陸の実装が接触判定側の変更を要求する
ようになり、「多態を書き換えるだけ」という目標が崩れる。

**`impulse` は落とす**(6-4)。着陸が要るのは相対速度と法線であって撃力ではなく、6-2 で
ダメージが接近速度へ移れば読み手がいなくなる。**運ぶ情報はむしろ増える** — 撃力へ潰す前の
状態と法線が唯一の材料になる。

## 段10 の判断 — `passiveWarpLod` を廃止する

**廃止の理由は費用ではなく、物理的な誤りである。** `passiveWarpLod` の間、弾・破片は全
substep を飛ばされ、フレーム末尾の1歩だけで進む。その1歩は最高倍率で約 9 時間 = 地球低軌道の
約 6 周回にあたる。この区間を三次曲線1本で表すと、接線の大きさ(`v·dt` ≈ 2.5×10⁸ m)が
弦(6 周回後の位置差)に対して桁違いに大きくなり、**制御点が実際の軌道からはるかに外へ
飛び出す。** 掃引はその曲線に対して当たり判定を掛けるので、

- 実際には近づきもしない天体に当たったことになる(偽陽性)
- 実際には貫いた天体を見逃す(偽陰性)

の両方が起こる。**物理的正しさは性能に優先する**ので、費用を理由に残すことはしない。

費用は実測した(`?stage=debug-load` + ×131072、substep 64、破片 500、静かなマシン)。

| | 据え置き | 廃止 |
| --- | --- | --- |
| frame | 190.7 ms | **355.6 ms** |
| 軌道積分 | 44.7 ms | 187.9 ms |
| 姿勢 | 0.6 ms | 32.6 ms |
| 接触 | 45.0 ms | 51.8 ms |
| 積分ステップ/フレーム | 481 | 21,175 |

廃止は frame を 1.87 倍にするが、**着手前の 871.9 ms に対しては依然 2.45 倍速い。** この計画の
本題は密結合の是正であって性能改善ではなく、改善は「物理的な嘘を正しても悪化しない算法を
与えた結果」として付いてきたものである。その順序を守る。

これで積分から種別による場合分けが消え、軌道力学に従うものはすべて同じサブステップで積む。
