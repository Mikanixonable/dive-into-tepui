## この計画の前提

着手時点で次が成立している。

- **`Asteroid` 型(`GameEntity` の派生クラス)は廃止済みで、存在しない。** 本文書では扱わない。
  結果として**重力を及ぼす `GameEntity` は存在しない**(全個体の `mu` が 0)。
  `mu ≠ 0` の個体を前提にした経路がコードにどこまで残っているかは、着手時に確認する。
- **大気は天体ごとのパラメータになっている。** 焼失(連続量の状態判定)と衝突(離散事象の

  余裕は全天体で 0。**本文書は焼失に触れない** — 扱うのは衝突側の呼び出し経路だけ。

  本文書で「弧が接触で打ち切る」と言うとき、それは弧の**唯一の**打ち切り条件を指す。
- **2球体の接触判定器は1つに集約されている。** `reachedBody` は判定器を天体一覧に対して回す
  だけのラッパで、幾何を持たない。**本文書は判定器の中身に触れない** — 扱うのは
  「どこから何回呼ぶか」だけ。

# 第1章 共通化してはいけない部分(役割の違い)

`Simulator`(実シミュレーション)と `Predictor` / `PredictedArc`(予測)は、どちらも
「1つの物体を1歩進める」処理を持つ。両者を1本にまとめることはできない。違いは2点しかなく、
両者の設計の差はすべてこの2点から出ている。

## 1-1. 同時性

`Simulator` は生存する全個体(破片・薬莢・弾まで含めて数百体)を、**同じ1つの瞬間で同時に**進める。
`PredictedArc` は選ばれた少数の弧を1本ずつ、**それぞれ別の先端時刻で**伸ばす。ここから:

| | 実シミュレーション | 予測 |
|---|---|---|
| 重力源の絞り込み | サブステップに1つ分類を組み、全個体で共有(`classifyAttractors` → `attractorsNearInto`) | 弧ごとの成員判定 + 期限つき再訪(`ArcBodies`) |
| 個体どうしの接触 | 解ける | 解けない |

分類を1回だけ組んで全個体で使い回すのは計算量オーダーの話であると同時に**正しさの要件**でもある —
A→B と B→A を別々の瞬間に組んだ構造から引くと、対称であるべき相互作用に処理順依存の誤差が入る。
弧にはその「共通の瞬間」が無いので、この共有はできない。

**ただし「個体どうしの接触」と「天体との接触」は別の問い。** 前者は同時性を要するが、後者は
天体側へ及ぶ反作用が(質量比により)無いので、相手の状態を書き換える必要がなく、
**弧が1本だけで判定できる**。第3章の分割はここに立脚する。

## 1-2. 刻みの決まり方

`Simulator` は毎フレーム `simTime + simDt` へ**必ず到達しなければならない**ので、刻みはそのフレームの
時間送りから決まる(`simulationMaxStep(simDt, SUBSTEP_MAX_DT, SUBSTEP_MAX_COUNT)`)。
`PredictedArc` は `simTime` を追い越されない範囲で先へ伸びればよいので、1フレームの歩数を予算
(`ARC_STEP_BUDGET`)で切り、足りなければ遅れる — 追い越された弧は読まれなくなり、その個体は
実シミュレーションの積分へ落ちるだけで壊れない。

# 第2章 論点

## 2-1. 「天体に接触したか」が3箇所で判定されている

天体との接触は、被積分剛体どうしの接触と**物理的に同じ現象**である。違いは、
(i) 剛体どうしは同時性を要するので `Simulator` にしか扱えない、
(ii) 天体との接触は質量比により天体側へ及ぶ反作用が無い、の2点だけ。
接触したことで何が起きるか(消滅か着陸か被弾か)は型による多態であって、判定そのものではない。

にもかかわらず、判定が3箇所にある。

| 判定する場所 | 走るワープ帯 | 対象 | 反応 |
|---|---|---|---|
| `ContactPhysics.computeAttractorResponse` | **×4 以下のみ** | `collides` を立てた個体 × 天体 | `collideWith(body, contact)` — **既に多態** |
| `GameEntity.checkLoss` 系 | 常時 | 全生存個体 × 天体 | `alive = false` + 種別ごとの演出・ステージ記録 |
| `PredictedArc.checkImpact` | 常時(弧の伸長時) | 弧 × 衝突窓の天体 | `_impact` + `_truncated` |

**`ContactPhysics` は既に天体を `invMass: 0` の接触相手として扱っており、反応の多態も
`collideWith` で成立している。** つまり求める形の半分は既に存在していて、`checkLoss` の
幾何判定はそれが×4超で走らないことの穴埋めとして置かれた二重実装である。

### 2-1-1. 帰結: 同じ事象がワープ倍率で違う結末になる

`Simulator.advance` の1サブステップは 接触解決 → `entities.cleanup`(= `checkLoss`)の順。
自機が地球へ到達したとき:

- **×4 以下**: `ContactPhysics` が先に当たり、`Player.collideWith` → `applyCollisionDamage` →
  「高速接触により機体を喪失した」。
- **×4 超**: 接触が走らないので `checkLoss` が当たり、「天体の地表へ到達し機体は失われた」。

**同じ物理事象に対して、ワープ倍率だけで喪失理由が変わる。** 弾も同様で、×4 以下では
`Bullet.collideWith` が、×4 超では `Bullet.checkLoss` の点判定が消している。

### 2-1-2. 帰結: `Enemy` が×4超で天体をすり抜ける

`enemy.ts:239` の `checkLoss` は焼失しか見ておらず、固体表面は `ContactPhysics` 任せに
なっている(コメントもそう明言している)。しかし `ContactPhysics` は
`canResolvePhysicalCollisions`(×4 以下)でしか走らない。

- **再現**: ×4 超のワープで、敵の軌道が天体と交差する状況を作る。敵は天体をすり抜ける。
  一方その敵の予測線は表面で止まる(弧は margin 0 の地表到達を持っているため)。

### 2-1-3. `Bullet` だけが点判定である

`Bullet.checkLoss` は `containingBody` による**ステップ終端の1点**の判定を使っている。
弾は最も速い個体なので、点判定はすり抜けを許す(1 substep で `BULLET_SPEED × dt` 進む一方、
判定は終端の1点だけ)。

ただし `Bullet` は既に `collides = true` で `ContactPhysics` の天体接触に載っており、×4 以下では
`collideWith` が消している。**ゲートを分割すれば、`Bullet.checkLoss` の天体判定はまるごと不要になる**
(距離と寿命だけが残る)。つまりこれは「点判定を掃引へ差し替える」ではなく「点判定を削除する」で
片づく。`containingBody` 関数そのものは `reachedBody` 内のフォールバック(区間長ゼロ・開始時点で
内側)で使われているので残る。

## 2-2. 反応の多態が揃っていない

判定を接触経路へ寄せると、**天体接触の帰結は `collideWith` だけが決める**ことになる。
現状の実装状況は次のとおりで、**そのまま寄せると3種別が天体に当たっても消えなくなる**
(反発だけして地表で跳ね続ける)。

| 種別 | `collideWith` | 天体(`Attractor`)接触の帰結 | 寄せたときに必要な追加 |
|---|---|---|---|
| `Player` | あり | `applyCollisionDamage(impulse/mass)` → HP 0 で喪失 | **不要**(低速なら生き残る = 着陸) |
| `Enemy` | あり | 同上 → HP 0 で撃破記録 | **不要** |
| `Bullet` | あり | `alive = false` | **不要** |
| `DebrisPiece` | あり | 弾と薬莢の音だけ。**天体接触で何も起きない** | **要** |
| `AmmoPickup` | 無し(基底の no-op) | 何も起きない | **要** |
| `Base` | 無し(基底の no-op) | 何も起きない | **要** |
| `RadiatorFold` / `BeltSection` | あり / あり | 艦への振り分け・ベルトの反発 | 天体接触で何が起きるべきかを**決めていない**(第4章) |

→ **基底 `GameEntity.collideWith` の既定を「相手が `GameEntity` でなければ(= 天体なら)
`alive = false`」にする**のが最小の解決。`Player` / `Enemy` / `Bullet` は既に上書きしているので
影響を受けず、`DebrisPiece` は基底へ委譲する分岐を1つ足せば済み、残り2種別は現状の `checkLoss` と
同じ帰結(消滅)を得る。

**併せて注意が要る穴が1つ**: `ContactPhysics.applyCandidate` は `response.impulse === 0` のとき
`collideWith` を呼ばずに戻る(離反中の接触は通知しない)。天体へ向かって接近している限り
`vn < 0` なので撃力は正になり通常は問題ないが、**相対速度ゼロで天体の内側に湧いた個体は
通知されない**。現状の `checkLoss`(位置だけを見る)はこれを拾っている。

## 2-3. 刻みの規則 — 再突入細分化の引数が2箇所

関数(`adaptiveSimulationMaxStep`)は共有しているが、**境界半径と細分化の刻みという2つの定数を
両方の呼び出しが綴っている**。

```
Simulator.adaptiveMaxStep:
  adaptiveSimulationMaxStep(生存艦の状態列, R_EARTH + REENTRY_SUBSTEP_ALT,
                            simulationMaxStep(simDt, SUBSTEP_MAX_DT, SUBSTEP_MAX_COUNT),
                            REENTRY_SUBSTEP_MAX_DT)
PredictedArc.stepDt(consumable):
  adaptiveSimulationMaxStep([tip], R_EARTH + REENTRY_SUBSTEP_ALT,
                            this.simulationMaxStep, REENTRY_SUBSTEP_MAX_DT)
```

対象集合が違う(生存艦全部 / 弧の先端だけ)のは 1-1 由来の正当な差。第3の細分化帯を足すときに
片方だけ直せてしまう点だけが問題。**なお `R_EARTH` を基準にしている点も別途の問題**
(細分化の境界が地球中心からの距離で決まっており、他の天体への降下では効かない)。

## 2-4. 「表面を持つ天体」の窓の定義が3通り

| | 中身 | 体数(既定レジストリ) |
|---|---|---|
| `Simulator.surfaceBodies`(×4 以下) | `ephemeris.attractorsAt(simTime)` = 登録天体の全数 | **101** |
| `Simulator.surfaceBodies`(×4 超) | そのサブステップ中点の重力窓 = `mu ≠ 0` の登録天体 | **65** |
| `ArcBodies` の `collision` | 登録天体の全数 + 生存する `predictedAsPlanCollider` 個体 | **101** + 動的 |

(101 は `SOLAR_SYSTEM` の登録数。うち `mu: 0` が 36 体なので重力源は 65 体。)

**×4 超では実体だけが 36 体の表示天体への表面判定を失い、弧は失わない。**

## 2-5. 重力絞り込みが同じ許容量から別の距離を導いている

両者とも許容加速度は `GRAVITY_NEGLIGIBLE_ACCEL = 1e-8 m/s²` だが、そこから導く距離の式が違う。

- `attractors.ts` の `gridCellSize`: `sqrt(最も重い grid 天体の mu / GRAVITY_NEGLIGIBLE_ACCEL)` を
  **全 grid 天体に共通のセル一辺**として使い、27近傍を引く。加えて mu の重い順
  `GRAVITY_ALWAYS_COUNT = 15` 体は常に含める。
- `arc-bodies.ts` の `gravityReach`: `sqrt(2 · その天体自身の mu / GRAVITY_NEGLIGIBLE_ACCEL)` を
  **天体ごと**に持つ。加えて最も重い解析天体1体を常に含める。

セル一辺は最も重い天体基準を全部に適用するので緩く、弧の側は天体ごとなので厳しい。
したがって**弧は実シミュレーションが加算する天体を落としうる**。**差の上限は測られていない。**

## 2-6. 天体側の broad phase が弧にしか無い

| 呼び出し側 | 個体どうしの broad phase | 天体の broad phase |
|---|---|---|
| `ContactPhysics` | 空間グリッド 27近傍(`contactCellSize`) | **無し**(`attackers × bodies` の総当たり) |
| `GameEntity.checkLoss` | — | **無し**(全天体を総当たり) |
| `PredictedArc` | — | `ArcBodies`(成員判定 + 期限つき再訪) |

判定器の一本化とは独立の課題で、**判定器の外側の責務**。

**broad phase の妥当性**: 区間内に接触があるなら、区間始点の距離は
`半径和 + |Δr_個体| + |Δr_天体| + 弦と弧の乖離` 以下(三角不等式)。これを超えていれば接触しえない。
乖離の項は上限で取る — **絞り込み側で安全側に倒すのは正当**(通す候補が増えるだけで、判定器の
答えは変わらない)。

## 2-7. 動かない個体の判定を毎 substep 繰り返している

`EntityManager.cleanup` は substep ごとに `all()` 全数へ `checkLoss` を回す。×4 超では
`Bullet` / `DebrisPiece` が `Simulator.substep` から外れる(まとめ積分に回る)が、
**`cleanup` からは外れない — 状態が変わっていないのに同じ判定を毎 substep 繰り返している。**

## 2-8. 既に共通化されているもの(目標にする形)

- `DynamicTrajectory.step` — RK4 の呼び出し。両者がここを通る。**モデルケース。**
- `trajectorySampleInterval` — 保持列の間引き間隔の式。`GameEntity.sampleInterval` と
  `PredictedArc.step` が同じ関数を呼び、`keepDuration` の与え方だけが呼び出し側にある。
- `simulationMaxStep` — 刻み上限の式。

いずれも**「式は1本、引数は呼び出し側」**という形。以下の共通化もこの形を目標にする。

## 2-9. 二重に見えるが実際には二重でないもの(触らない)

- **姿勢積分・`stepEnvironment`(熱/電力/放熱板)**: 実シミュレーションにしか無い。弧は姿勢も
  熱の蓄積状態も運んでいないので、原理的に再現できない。
- **イベント境界での切り**: 実シミュレーションにしか無い概念。弧の消費者は境界を要求しない。
- **非有限値の検出**: 弧は `_truncated` へ、実シミュレーションは `NanWatchdog` の報告へ落とす。
  目的が違う(前者は自分の伸長を止める、後者は最初に壊れたフェーズを特定する)。

## 2-10. 依存関係で確認が要るもの

- **`GameEntity.predictedImpact`(`game-entity.ts:144`)に読み手が無い。** `src/` にも `tests/` にも
  参照が無く、計画側の ✕ アイコンは `PlanPath` が弧の `impact` を直接読んでいる(`plan-path.ts:426`)。
  **削除できるはず** — 着手時に再確認する。
- **`src/game/nan-watchdog.ts` の冒頭コメント**が「`checkLoss` の大気突入・天体表面接触判定は
  どちらも NaN で false になる」と述べている。地表到達が接触経路へ移ると記述が古くなる。
- `Simulator.surfaceBodies` は `stepEnvironment`(恒星の取り出しと日照率の遮蔽体)にも渡っている。
  **窓の定義を変えると熱・電力側の入力も変わる** — 表面判定だけの話ではない。

# 第3章 いまのところ固まっている方向

**まだ決定ではない。第4章の未決を潰してから確定させる。**

## 3-1. 判定は1本、反応は多態

**接触の判定(幾何)は1つの原始関数に統一し、接触への反応だけを型で多態化する。**

| 層 | 共通化するか |
|---|---|
| 天体の**探し方**(broad phase) | **しない**(1-1 由来の正当な差) |
| 天体の**窓の定義** | **する** |
| **刻みの規則** | **する**(対象集合だけ呼び出し側) |
| **RK4 の1歩** | **済**(`DynamicTrajectory.step`) |
| **掃引接触の幾何** | **済**(判定器1つへ集約) |
| **天体接触の反応** | **しない**(出力先が別 — 実体は `collideWith`、弧は打ち切り) |

## 3-2. 天体接触の判定を `ContactPhysics` へ寄せ、ワープゲートを分割する

- **個体どうしの接触**は `canResolvePhysicalCollisions`(×4 以下)で従来どおり切る。同時性を要し、
  20 s 刻みでの撃力交換は意味を持たないため。
- **天体との接触は決して切らない。** 反作用が無いので相手の状態を書き換える必要がなく、掃引判定は
  どの刻み幅でも成立する。反応は `collideWith` の多態に委ねる。
- これにより `checkLoss` から**地表到達の判定が消える**。残るのは大気での焼失と、種別固有の条件
  (弾の距離・寿命、薬莢の寿命、自機の熱・動圧)だけになる。

**時間加速帯による分岐そのものは残ってよいが、残ってよいのは「判定を呼ぶか呼ばないか」だけ**で、
判定器の実装や精度が帯域によって変わってはならない。

## 3-3. `collides` の意味を分ける

現状の `collides` は「個体どうしの接触に参加するか」と「天体との接触に参加するか」を兼ねている。
`fragment` な `DebrisPiece` は `collides = false` なので、いまは `ContactPhysics` に載らず
`checkLoss` だけが天体到達を見ている。判定を `ContactPhysics` へ寄せると、この個体が天体を
すり抜けてしまう。

→ **`collides` は個体どうしの接触だけを支配し、天体との接触は全生存個体が無条件に参加する。**
破片が艦をすり抜けつつ惑星には当たる、という現状の意図がそのまま表現できる。

## 3-4. 予測の弧は天体接触で必ず打ち切る

反応が多態になると「艦は低速接触なら生き延びる(= 着陸)」が成立しうるが、**弧はそれでも接触時点で
打ち切る**。接触後の軌道は跳ね返りや接地の帰結であって、`PredictedArc` が積分している自由落下の
埒外だから。判定器を共有しても、この打ち切り規則は弧側の判断として残る。

## 3-5. 着陸を後から実装できる基盤にする(着陸自体は実装しない)

**このリファクタは着陸機能の前段階であり、着陸そのものは実装しない。** 達成すべきは、着陸が
**自機の多態性を書き換えるだけで実装できる状態**になっていること。

### 3-5-1. 必要な情報は既に届いている(実地確認)

`GameEntity.collideWith(other: GameEntity | Attractor, contact: Contact, activeStage: Stage)` と
`Contact` が現時点で運んでいるもの:

| 着陸の実装に要るもの | 現状 |
|---|---|
| 相手そのもの | `other` — 天体なら `Attractor`(`id` / `radius` / `mu` で天体を特定できる) |
| 接触時の自分の状態 | `contact.selfState`(反応**前**) |
| 接触時の相手の状態 | `contact.otherState`(天体なら `body.state`) |
| 相対速度 | `sub(selfState.v, otherState.v)` で出る |
| 接地の法線 | `contact.normal`(self → other 向きの単位法線) |
| 垂直/水平成分の分解 | 上の2つから出る — 「ゆっくり降りたが横に滑っている」を区別できる |
| 接触点・接触時刻 | `contact.point` / `contact.t` |

**基盤としての情報は既に足りている。** `Player.collideWith` はいま `contact.impulse / this.mass` と
いう1つのスカラーしか読んでいないが、これは `(1 + 反発係数) × 法線方向の接近速度` に比例する量で、
必要なら上の材料から垂直・水平の成分へ分解し直せる。

### 3-5-2. 足りていないのは呼び出し経路のほうだけ

- **天体接触が×4超で `collideWith` に届かない**(2-1-1)。→ 3-2 で解消する。
- **`applyCandidate` は `impulse === 0` のとき `collideWith` を呼ばない**(2-2)。接近中なら撃力は
  正なので接地の瞬間は届くが、**接地後に静止した状態は通知されない**。着陸を「接地したまま留まる」
  状態として実装するなら、この穴は着陸の実装時に埋める。**今回は塞がない** — 今回の帰結(消滅)には
  影響しないため。

### 3-5-3. 今回課す制約

**`Contact` の情報を減らさないこと。** とくに `selfState` / `otherState` / `normal` は、撃力スカラー
1つへ畳んではならない — 畳むと着陸の実装が接触判定側の変更を要求するようになり、
「多態を書き換えるだけ」という目標が崩れる。

# 第7章 見積り

## 7-1. 既存コストの見積り(**実測が要る**)

- 掃引を回す個体数(上限)= `MAX_DEBRIS` 600 + `MAX_CASINGS` 260 = **860**
  (`MAX_BULLETS` 400 はいまは点判定なので掃引には乗らないが、段3 で接触経路へ移ると乗る)。
- 高ワープの substep 数 = `SUBSTEP_MAX_COUNT` = **64**。
- 天体数 = 高ワープ帯の表面窓 **65**。
- → 860 × 64 × 65 = **約 358 万回/フレーム**。棄却経路 1 回あたり約 70 演算として
  **2.5 億演算/フレーム**。60 fps では 15 G演算/s 相当で、JS では明らかに成立しない規模。
  **まずここを実測する。**

削減の効き方(3つは独立に効く):

| 施策 | 後の回数 | 比 |
|---|---|---|
| 天体側の事前棄却(2-6)— 1回 70 演算 → 約 10 演算 | 358 万回のまま | **7.0×** |
| 動かない個体を毎 substep 判定しない(2-7)— passive-warp の 1260 体を最終ステップの1回だけに | 動く個体 ≈ 30 × 64 × 65 = 12.5 万 + 1260 × 1 × 65 = 8.2 万 ≈ **20.7 万回** | **17×** |
| 表面窓を 101 体へ広げる(2-4 の統一、逆向き) | 358 万 → 556 万回 | **0.64×**(悪化) |

**「動かない個体を毎 substep 判定しない」が最大の効き。** しかもこれは純粋な無駄の除去で、
挙動を1ミリも変えない(状態が変わっていない個体に同じ判定を繰り返しているだけ)。

**broad phase の棄却は解法の選択とは無関係に効く** — 判定器の中身を触らずに、判定器を呼ぶ前に
落とすため。判定器の内部で半径を膨らませる類の近似とは別物である点に注意(あちらは答えそのものを
歪める)。
