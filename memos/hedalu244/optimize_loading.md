# ロードの軽量化 — 調査結果と修正案

対象コミット `50a623be`(2026-09-04 時点の origin/main)。作業ブランチ `optimize-load-and-runtime`。

## 実施状況(2026-09-04)

**B・D・E は実施済み。G は実施したが効き目が出ていない。A は `optimize_shader_compile.md` へ
引き継いだ。C・F は破棄した。**
実施後のヘッドレス実測(素のサイズ): stage 1 が 47.13 → **38.77 MB**、
creative が 140.75 → **60.31 MB**。

- **B 実施** — creative 起動時の protein 取得が 8ファイル(93.62 MB)→ 2ファイル(25.02 MB)。
- **D 実施** — フォントの取得が 5.55 → 1.57 MB。
- **E 実施** — `main.js` が 10.27 → 6.12 MB。索引は 4.1 KB。焼き直しの副産物として、
  旧 `lagrange-orbits.json` の `familyIndex` が系ごとのファイルと食い違っていたのも直った。
- **G 実施したが効いていない** — 取得の起点は `syncLod()` へ移り、開始時刻は 2.9 秒
  (ローディング表示の中)から 4.5 秒(最初のフレーム)へ動いたが、`2k_*.jpg` 13枚のうち
  12枚は依然として取得される。**原因は特定済み**: 見かけ直径を深度で測っているため、
  カメラの背後にある天体が床打ちされて「目の前にある」のと同じ大きさになる
  (`game/camera/camera-system.ts` の `radialScaleFromViewpoint` のコメントが、この床打ちを
  明記している)。**閾値の判定を半径方向の尺度へ替えれば直るが、それは「どの天体を球として
  描くか」を変える描画の変更なので、目視の確認が要る。**

## 何のための文書か

「ステージに入るときのロードが 83% で長時間固まる」「固まっている途中で BGM だけ流れ始める」の
原因、ロードしているデータの内訳、モデル JSON をどこまで小さくできるか、を測った結果と修正案。
**スナップショットであって、コードの現状を説明する文書ではない。** 実施したら消す。

## 測り方と、その限界

`npm run build` した `docs/` を静的配信し、ヘッドレス Chrome を CDP で駆動して `?stage=1` と
`?stage=creative` を開き、次を同時に取った。

- ローディング表示の円形ゲージの表示値と、それが変わった時刻
- `requestAnimationFrame` が来た時刻(**来ない時間 = 画面が1枚も更新されていない時間**)
- Long Task / Resource Timing / CPU プロファイル(サンプリング 1ms)

**限界(重要)。**

- **GPU が実機と違う。** 以下に出てくる「数十秒」という絶対値は実機の値ではない。
  信じてよいのは段の比と、どこで何を待っているかという形だけ。
- 配信は無圧縮・無遅延。実配信の転送量は公開先(GitHub Pages)の HTTP ヘッダで別途実測した。

## 分かったこと

### 1. 83% で止まるのはアセットのロードではない — 最初のフレームのシェーダ構築

83% という数字はゲージの実装がそのまま説明する。`game/loading-progress.ts` の段の重みは
system 0.72 / bodies 0.11 / run 0.17 で、**0.72 + 0.11 = 0.83 は `run` 段へ入った瞬間に
報告される値**。「83% で固まる」は「run 段(= `new Game()` と、その後にゲームが最初の絵を出す
まで)で止まっている」以上の意味を持たない。

stage 1・1回目の実測:

| 時刻 | 起きていること |
| --- | --- |
| 1047 ms | ローディング表示(0%) |
| 2337 ms | 72% — 星系の構築(暦 pack の受信と展開)が終わる |
| 2656 ms | 83% — `run` 段へ入る |
| 2955 ms | `new Game()` が終わり、ローディング表示を DOM から外す |
| 2955〜4900 ms | **JS が 1.9 秒**。CPU プロファイルは three.js TSL のノードグラフ構築(`build` / `_getChildren` / `getDataFromNode` / `removeChain`)で埋まる |
| 4900〜89700 ms | **85 秒、JS スレッドは完全に idle**(この区間のプロファイルの 99.6% が `(idle)`)。rAF が1回も来ない |
| 99290 ms | 60 フレーム完走 |

**0% から 83% までは 1.6 秒しかかかっていない。** 体感している「ロード」のほぼ全部が、
そのあとの最初の1フレームである。

正体の裏付け:

- 同じブラウザプロファイルのまま開き直すと **99.3 秒 → 19.3 秒 → 24.3 秒**。Chrome の
  GPU ディスクキャッシュに載ると消える種類の費用 = **WebGPU のパイプライン(シェーダ)構築**。
- ヘッドレス専用フラグ `--run-all-compositor-stages-before-draw` を外しても 84.8 秒で変わらない。
  計測環境が作り出した現象ではない。
- **stage 1 は run 段で何も取りに行っていない。** アセットは原因ではない。

キャッシュに載ると消えるということは、**実機でも「デプロイのたびに1回目だけ長い」**という
形で出ているはず(バンドルが変わればシェーダ本文も変わり、キャッシュは無効になる)。

### 2. だから「BGM だけ流れ始める」

固まっている間、**JS スレッドは暇**。`setInterval` で回っている BGM のスケジューラも入力
ハンドラも普通に動く。止まっているのは絵だけ。

絵が 83% のまま残るのは、ローディング表示を DOM から外した直後に `animate()` が最初の
`render()` を投げてしまうため。**DOM から表示を外した変更を映すフレームは、その GPU 仕事が
終わるまで提示されない。** 結果、最後に画面へ出たフレーム = 83% のゲージが数十秒残る。

### 3. ステージに入るときに取りに行くデータの内訳

Resource Timing の実測。「転送」は公開先が実際に返している `Content-Encoding: gzip` を
前提にした値(`.js` `.json` `.epk` は gzip、画像とフォントは無変換 — 公開先のヘッダで確認)。

| 区分 | stage 1 素 | stage 1 転送 | creative 素 | creative 転送 |
| --- | --- | --- | --- | --- |
| protein の structure / motion JSON(8ファイル) | — | — | 93.62 MB | 25.24 MB |
| テクスチャ(jpg / png 17枚) | 27.18 MB | 27.18 MB | 27.18 MB | 27.18 MB |
| JS バンドル `main.js` | 10.27 MB | 4.24 MB | 10.27 MB | 4.24 MB |
| フォント(HackGen) | 5.55 MB | 5.55 MB | 5.55 MB | 5.55 MB |
| 天体暦 `.epk` 1本 | 4.12 MB | 3.01 MB | 4.12 MB | 3.01 MB |
| **合計** | **47.13 MB** | **39.98 MB** | **140.75 MB** | **65.22 MB** |

目立つものと、その理由:

- **creative へ入ると protein 4体ぶん8ファイル(93.6 MB / 転送 25.2 MB)を全部取りに行く。**
  `game/creative/stage-controls-panel.ts` が敵の形状一覧を組んだ時点で全 asset の取得を
  起こしているため。**開始はちょうど 83% の直後**(実測 2590 ms)。取得も `JSON.parse` も
  非同期なので固まりはしないが、通信量としては最大。
- **テクスチャ 27.18 MB には圧縮の余地がない**(既に jpg / png)。最大は `cloud-field.png`
  **13.00 MB**(4096×2048 RGB8、R=被覆率 / G=雲頂高度 / B=薄い雲 τ で3チャンネルとも使用中)。
  次が `earth.jpg` 4.35 MB(8192×4096)、`8k_moon.jpg` 2.96 MB。惑星・衛星の `2k_*.jpg` 13枚
  (計 4.9 MB)は、画面上で数ピクセルでも起動直後に全部取りに行っている。
- **フォント 5.55 MB。** `main.ts` 冒頭のコメントは「太さは 400 のみを読み込み、bold 指定は
  ブラウザの合成に任せる」と書いてあるが、実際に import している CSS は 400 と 700 の両方を
  宣言しているので **700 も落ちてくる**。しかも実測では Bold の woff2(1.63 MB)と
  woff(2.35 MB)が**両方**来ている(Regular の woff は来ていない)。
- **`main.js`(10.27 MB)にいちばん大きく効いているのが `assets/orbits/lagrange-orbits.json`**
  (地球-月と太陽-地球の CR3BP カタログ)。他の5系は動的 import で分割済みなのに、この2系だけ
  静的同梱されている。webpack の module 一覧(minify 前の素のサイズ)で並べると
  `lagrange-orbits.json` 4.25 MB > three.js 3.53 MB > `models/ammo.json` 1.39 MB >
  `player.json` 0.52 MB > `moon-features.json` 0.47 MB。

### 4. モデル JSON の minify と圧縮でどこまで減るか(→ 修正案 C は破棄)

**structure は既に minify 済み。** 先頭の数十行だけが整形されていて、実体である巨大配列は
1行に詰まっている(`JSON.parse` → `JSON.stringify` しても 100.0%)。
**motion は整形されたまま**で、minify だけで 55〜57% になる。

それとは別に、値そのものに2つの無駄がある。

- **motion の `modes[].displacements` が float64 の全桁**(例 `0.007681022863835096` = 20 byte)。
  正規化された固有ベクトル成分で、`displayRmsAngstrom`(0.25 Å)を掛けて使う量なので、
  **5桁に丸めれば半分以下**になり見た目は変わらない。`residues.centers` も3桁で足りる。
- **structure の `ribbon.mesh.chain` と `surface.mesh.component` が1頂点1文字列**
  (ATP synthase で 1.02 MB + 0.92 MB)。同じファイルの `atoms.chainTable` / `atoms.chains` と
  同じく「表 + 索引」にすれば消える。

実測(単位 MB、gzip は level 6):

| ファイル | いま 素 | いま gz | minify 素 | minify gz | 丸め+表化 素 | 丸め+表化 gz |
| --- | --- | --- | --- | --- | --- | --- |
| atpSynthase6n2yStructure | 37.16 | 10.57 | 37.16 | 10.57 | 35.09 | 9.75 |
| atpSynthase6n2yMotion | 17.60 | 4.10 | 9.97 | 3.81 | **5.37** | **1.48** |
| rubisco8rucStructure | 16.45 | 4.79 | 16.44 | 4.79 | 15.36 | 4.42 |
| rubisco8rucMotion | 8.58 | 1.98 | 4.85 | 1.85 | **2.58** | **0.69** |
| pdb5i4rStructure | 8.04 | 2.37 | 8.04 | 2.37 | 7.51 | 2.19 |
| pdb5i4rMotion | 4.05 | 0.94 | 2.24 | 0.88 | **1.18** | **0.33** |
| myoglobin1mbnStructure | 1.17 | 0.36 | 1.17 | 0.36 | 1.08 | 0.33 |
| myoglobin1mbnMotion | 0.58 | 0.13 | 0.30 | 0.12 | **0.16** | **0.05** |
| **合計** | **93.63** | **25.24** | **80.17** | **24.75** | **68.33** | **19.24** |

読み方:

- **配信は既に gzip されている**(公開先の実測: protein 8ファイルの転送量は合計 25.69 MB、
  `main.js` は 10.8 MB → 4.49 MB)。だから **minify 単体は転送にほとんど効かない**
  (25.24 → 24.75 MB)。転送に効くのは **値の精度を落とすこと**(→ 19.24 MB、-24%)。
- 一方 **minify は素のサイズを 93.6 → 80.2 MB へ減らす**ので、`JSON.parse` に渡る文字列と
  メモリには効く(creative の実測では、8ファイルが届いた 5.0〜8.0 秒の区間の主スレッドが
  1.25 秒ぶん `(program)` = `JSON.parse` などのネイティブ処理で埋まっていた)。
- **structure の8割は `surface.mesh.index` / `ribbon.mesh.index` と、それぞれの `position`**
  (ATP synthase で 37.2 MB 中 31.8 MB)。既に整数と4桁固定小数なので、JSON のままでは
  これ以上減らない。**減らすならメッシュを間引くか、量子化したバイナリにするしかない。**
  なお量子化なしの Float32/Uint32 バイナリは、gzip 後で比べると今より**大きくなる**ので、
  バイナリ化は転送量ではなく `JSON.parse` の費用とメモリのための手段として考えること。
- 参考: 三角形数は ATP synthase で surface 480,009 / ribbon 533,472、rubisco で 239,951 /
  240,976。**敵1体としては桁が2つ多い。** 間引きの余地がいちばん大きいのはここ。

## 修正案(効果の大きい順)

### A. 最初のフレームのシェーダ構築を、ローディング表示を出したまま行う

**「83% で固まる」への直接の答え。** `Renderer.compileAsync(scene, camera)` は three.js 0.185
にあり、シェーダとパイプラインの生成だけを先に走らせる。ローディング表示を消す前にこれを待つと
どうなるかを、使い捨てのパッチを当てて実測した(この変更はコミットしていない)。

- **コンパイル中もフレームは 110 ms 間隔で来続けた。** つまり `render()` を投げていない限り
  **画面は生きていて、ローディング表示は描き替わる**。狙いどおり動く。
- ただし `compileAsync(scene, camera)` が吸収したのは **85 秒のうち 5.3 秒だけ**だった。
  残りはそのまま最初の `render()` に残る。

**足りない理由は分かっている。** `render/pipeline/` の各パス(gbuffer / 遮蔽 / 影 /
light prepass / material / 大気 / overlay / AA / lens / composite)のマテリアルは `scene` の
下に居ないので `compileAsync(scene, ...)` では拾えない。**パイプライン側にも同じ入口を作り、
段(`LoadingPhase`)へ `compile` を足して、そこで待つ**必要がある。

なお「ローディング表示の下でパイプラインを1回 `render()` して暖める」だけの手も試したが、
**レンダラごと落ちた**(`sync()` を通していない状態で `pipeline.render()` を呼んだため)。
暖めるなら1フレームぶんの `update`/`sync` を先に通す必要があり、それは素直な作りではない。
`compileAsync` 相当の入口をパス側に用意するほうを採るべき。

段を足せば、`compileAsync` はオブジェクト単位でも呼べる(`compileAsync(object, camera, scene)`)
ので、天体・機体・線・各パスの単位で分けて呼べば **ゲージが実際に進む**。

**効果の性質**: 総時間は縮まない。**「固まって見える」を「進んで見える」に変える。**
総時間そのものを縮めたいなら、パイプライン(マテリアルの種類 × パス)の数を減らす別の検討が要る。

### B. creative に入った瞬間に protein 4体を全部取りに行くのをやめる

`stage-controls-panel.ts` が形状の一覧を組む時点で全部の取得を起こしている。一覧に並べるだけなら
asset は要らない。**選ばれた1体だけを取りに行く**ようにすれば、creative の転送量は
25.24 MB → 最大でも 10.57 MB(ATP synthase)、たいていはそれ未満になる。
`dynamic-system.ts` の `spawnEnemyWhenReady` が「準備できるまで実体化を遅らせる」機構を既に
持っているので、取得の起点を選択の側へ移すだけで足りるはず。

### D. フォントの 700 を積まない

`main.ts` のコメントどおり 400 だけを読む(`@sarap422/font-hackgen` のパッケージ CSS を
そのまま import せず、Regular の woff2 だけを指す `@font-face` を自前で書く)。実測で来ていた
Bold の woff2 + woff = **4.18 MB** が消える。HUD には `font-weight: 600/700` を使う箇所が
あるので、**合成 bold に変わって見た目が少し変わる**(コメントが宣言している状態そのもの)。

### E. `lagrange-orbits.json`(4.25 MB)を動的 import へ回す

他の5系と同じ扱いにする。ただし起動直後に要るのは `familyIndex`(数 KB)と各系の `mu` だけなので、
**索引と本体を別ファイルに分ける**のが素直。`main.js` は 10.27 → 約 6 MB(転送 4.24 → 約 2.5 MB)。

### G. 惑星・衛星テクスチャ(4.9 MB)の取得を遅らせる

`CelestialSurface.addTo()` が全部の `DeferredTexture.request()` を呼んでいる。見かけ直径が
閾値を超えたときに初めて取りに行く形にできる(`syncLod()` が既に見かけ直径を受け取っている)。
**「近づいた瞬間に無地の球が見える」ことになるので、これも見た目の判断が要る。**
