# 計画・予測の負荷改善 v6 — 前提の変化と、3案の評価

v5 の時点でコードは1行も変わっていなかった。変わったのは**前提**で、それによって v5 で棄却した手の
いくつかが解禁された。

この文書は、(1) 前提の変化を確定させ、(2) v5 の枠組みを v1〜v3 の実測値で埋め直し、
(3) 新しい3案と v5 の残件を**同じ尺度**で評価する。埋め直しの過程で
「1サブステップは天体窓を2回組んでいる」という未報告の事実が出たので、それを第8章に置く。

**現況: 提案A(計画と予測の統合)は実装済みで、効果も測った(§3-0)** — ノード0本の条件で
`計画` が消え(`plan歩` 210〜2000 → 0)、28日プリセットでは `sync` も半減した。残る判断は
A-7(遠端精度の値段、§3-1)。B は main のマージが前提なので着手できない。
次の作業は **A-7 の判断 → マージ → B → 再測定**(§7「推奨する順序」)。

**各案の節は単体で実装計画書として読める形にしてある** — 趣旨、実装で見落とせない点、
そして `npm run typecheck` と1コミットが通る粒度に区切った実装手順を、案ごとに持つ。
手順の中の設計判断(何を切り出し、何を切り出さないか)は `/refactor` の原則に沿って
その場で理由を書いた。

# 第1章 変わった前提

## 1-1. 予測線はマップビューでしか描かない 【最大の変化】

`main` の `a6a3dcf6 feat: 戦闘ビューの自機の軌道を解析楕円で描く` で、戦闘ビューの操作艦は
積分予測線ではなく解析楕円になった。`entity-line-manager.ts`:

```ts
// 戦闘ビューの操作艦は、積分した予測線ではなく解析楕円で軌道を描く。
const ownEllipse = showLines && !overviewMode;
if (asTarget !== null && visible) ship.showOrbitLine(asTarget);
else if (ownEllipse) ship.showOrbitLine(C.LINE_STYLE.playerOrbit);
else ship.hideOrbitLine();
if (showLines && !ownEllipse) ship.showPredictedLine(C.LINE_STYLE.playerPredicted);
else ship.hidePredictedLine();
```

非操作艦は `showLines = (isActive || overviewMode) && …` が偽なので、戦闘ビューでは
**どの艦の予測線も描かれない。**

### これが解禁するもの

v5 までの最適化方針は「予測線が戦闘ビューで振動/ドリフトして見えない精度」を下限に置いていた。
その下限が消えた。より重要なのは**棄却理由の失効**で、v5 は予測のワープゲートを

> 「ゲートすると予測が恒久的に不在になり、静かに `OrbitLine` の解析楕円へフォールバックする。
> その楕円は J2・第三体・抵抗の下で積分軌道と半径が食い違う」

という理由で退けていた。**その解析楕円フォールバックは、いま戦闘ビューの正式な表示として
採用済みである。** 同じ絵が一方では「静かな誤り」で他方では「仕様」ということはない。
→ 第4章 B-2。

### 即座に導かれる帰結: 戦闘ビューの予測には消費者がいない

`predicted` / `displayState` の全読み手を洗った結果:

| 読み手 | 戦闘ビューで操作艦の `predicted` を読むか |
|---|---|
| `GameEntity.syncTrajectoryLines` → `predictedLine.syncGeometry` | **読まない**(`predictedLine` が `null`) |
| `displayState(displayTime)`(ゴースト・マーカー・ピック候補) | **読まない**。戦闘ビューは `forceCurrent` で `displayTime === simTime`、`t <= actual.state.t` なので `actual` 側の枝 |
| `predictedAttractorsAt` の動的重力源 | **読まない**。`Player.mu === 0` なので `entities.attractors()` に載らない |
| `PlanAttractors.predictionCoverage` | 同上 |
| `DisplayWindowManager.predictionCoverageRatio` | `predicted?.state.t` を1回読むだけ(PREDICT パネル用、マップ専用の表示) |

**⇒ 戦闘ビューで `Predictor` が使う `PREDICT_COMBAT_STEP_BUDGET = 128` 歩/frame は、
main をマージした時点で丸ごと消費者のいない仕事になる。**

しかも `Player.behave` は `thrust` が非 null のフレームで毎回 `invalidatePrediction()` を呼ぶので、
**噴射している間は毎フレーム 128 歩を捨てて積み直す。** いちばん重い瞬間にいちばん無駄が出る。

## 1-2. `Curve` の頂点予算 — 解決済み

`origin/workspace6` の `234c7b14 perf: 折れ線の頂点予算を実測した収束点に合わせて切り下げる` で
`TrajectoryLine` の `MAX_VERTICES` が 16384 → 4096(1/4)。v5 P-8(自艦50隻で 34.4 MB)は
34.4 → 8.6 MB になり、**論点から降ろす。焼き直しコストも以後は考えない。**

**ただし注意**: この変更は `origin/workspace6` にあり、`main` にも `workspace4` にも入っていない
(両ブランチとも `MAX_VERTICES = 16384`)。**v5 のベースライン数値の `sync` 側には旧値が乗っている。**

## 1-3. ブランチの乖離 — 測定と設計のずれ

`workspace4`(性能作業)と `main` は `src/` の68ファイルで乖離しており、うち
`plan-arc.ts` 106行・`predictor.ts` 35行・`curve.ts` 46行。方針どおり main を workspace4 へ

# 第2章 問題の再定式化 — O(kNM) の枠を実測値で埋める

## 2-1. 三経路の N・M・k

| | N(重力/衝突) | M | k(1フレームの歩数) | 同時性 | 実効オーダー |
|---|---|---|---|---|---|
| `Simulator` | 64 / 101 | 全エンティティ | substeps ≤ `ceil(0.1·warp / 20)` | **同一時刻**(substep 中点) | O(k(N+M)) |
| `Predictor` | 64 | 予測対象 | `PREDICT_STEP_BUDGET` = 500 | 個体ごとに別時刻 | O(kN) ×(消費フレーム数) |
| `PlanArc` | 64 / 101 | 1 | `PLAN_ARC_MAX_STEPS` = 20000/呼び出し | 歩ごとに別時刻 | O(kN) |

`N` は `SOLAR_SYSTEM` の実数で、**101体(恒星1・planet 49・satellite 51)、うち `mu !== 0` が64体。**
`gravityAttractorsAt` が 64、`attractorsAt`(衝突候補・中心天体解決)が 101。

## 2-2. サブステップの正のフィードバックは、上限で飽和している

v1 の「サブステップ数が正のフィードバックを持つ」は正しい。ただし v1 §A-0-1 自身が
`dt = Math.min(dtRaw, 0.1)` と `328 = 0.1 × 65536 / 20` を書いているとおり、
**そのフィードバックは既に上限へ張り付いていて、いま観測されている高ワープの重さは
発散ではなく固定床である。** ここを明示的に扱っていなかったのが v1〜v5 の抜け。

`simDt = dt · simSpeed` なので **1フレームの substep 数の上限は
`ceil(0.1 · simSpeed / SUBSTEP_MAX_DT)` で、fps に依らない固定値。**

| warp | simDt/frame の上限 | substeps/frame の上限 |
|---|---|---|
| ×1024 | 102.4 s | 6 |
| ×16384 | 1638.4 s | 82 |
| ×65536 | 6553.6 s | **328** |
| ×131072 | 13107.2 s | 656 |

v1・v2・v3 が3回とも観測した `substeps = 328` はこの上限そのもの。**×65536 では既に
飽和しているので、そこから先は発散しない。** 代わりに出るのは別の症状で、
**要求ワープに実効ワープが届かない**:

- ×65536 で 2 fps のとき、1秒間に進む sim 時間は `6553.6 × 2 = 13,107 s` → **実効 ×13,107。
  要求値の 1/5。**

**⇒ 「重くなるほどサブステップが増える」局面は既に通り過ぎていて、いま起きているのは
「重くなるほど時間が進まなくなる」。** これは対処の形を変える: 減らすべきは substep の
**数**ではなく**幅**であり、`dt` クランプが既に「1フレームの substep 数の上限」として
機能している以上、そこに定数を1つ足すだけで済む(→ B-1)。

## 2-3. 支配項は M でも k でもなく「1回の窓構築 × k」— 物理は 1%

**この文書のすべての見積りが乗っている土台は、v1 §A-1 の node マイクロベンチ(v1-T4)である。**

| 操作 | 実測 |
|---|---|
| `gravityAttractorsAt(t)`(64天体・毎回異なる t) | **176.68 µs** |
| `attractorsAt(t)`(101天体) | **283.37 µs** |
| `classifyAttractors` | 15.09 µs |
| `attractorsNear` | 0.53 µs |
| **`stepDynamics`(物理そのもの)** | **2.76 µs** |
| `advanceBudget` 1反復(当時、窓を歩あたり2回引いていた) | 388.36 µs |

`2 × 176.68 + 15.09 + 0.53 + 2.76 = 371.7 µs` ≈ 実測 388.36 µs。**内訳が閉じている。**
その後 v2 の実験5-D を経て中心天体の窓が前回の中点から使い回されるようになり
(`centerWindow ?? predictedAttractorsAt(...)`)、歩あたりの窓は2回→1回になった。
`176.68 + 15.09 + 0.53 + 2.76 = 195 µs` — **v5 のゲーム側実測「予測 0.19 ms/歩」と一致する。**

**⇒ 予測1歩の値段の 98.5% は暦の窓であって、積分ではない。** 同じことが計画側でも成り立つ
(v5 P-9: 窓と候補集合で約96%、判定 2.4%)。**三経路とも、削るべきは歩数か窓であって、
物理計算ではない。**

v5 P-4 の `creative ×65536 艦なし` = `積分` 190.6 ms / `軌道積分` = 0(エンティティ0体)。

```
190.6 ms / 328 substeps = 0.58 ms/substep   ← エンティティ 0 体でこの値
```

substep 1回の中身は、**天体窓2回 + 分類1回**(第8章):

```
176.68 (中点の重力窓 64体) + 283.37 (終点の全窓 101体) + 15.09 (分類) = 475 µs
```

ブラウザは node より遅いので、実測 0.58 ms/substep と整合する。

**同じ式が計画側でも合う。** ×65536・28日プリセットの `plan歩` 実測 251 に対し:

```
simDt/frame / stepDt = 6553.6 / 26.3 = 249  歩   (実測 251)
249 歩 × 0.61 ms/歩 = 152 ms                     (実測 155.5 ms)
```

**⇒ 三経路とも「1回の天体窓の値段 × 歩数」で説明でき、歩数は
`1フレームの時間送り ÷ 刻み幅` で決まる。** モデルは実測と一致している。以後この式で見積もる。

# 第3章 提案A — 計画と予測の統合【実装済み。残るのは A-7 のみ】

ノードが1本も無いとき、計画軌道の唯一の区間は自機の予測軌道そのものを答える
(`plan/predicted-arc.ts` の `PredictedArc`)。その条件では計画側の積分は走らない。
近地点/遠地点・✕・ルーラー目盛・クリック判定・赤道交点は供給元が予測列へ替わっただけで、
出るものは変わらない。

**効果は測った(§3-0)。見積り(×65536・28日 `計画` 155.5 → 10 ms、×1・28日 1,242 → 95 ms)に対し、
実測は 154.8 → 0.3 ms / 1,237.1 → 1.45 ms。** ベースライン側は見積りとほぼ一致し、残差は
見積りより1〜2桁小さい。

計画側に残る定常コストは `buildSegments` が区間長と `apsisCenter` のために毎フレーム
引く `ephemeris.attractorsAt(state0.t)`(101体、283 µs)1回だけ。`state0.t` は自機の
状態時刻 = `simTime` なので、同じフレームの他の消費者とリングキャッシュを共有できる位置にある。

### 予測側に退行が無いことの確認

A は `Predictor` の予算・刻み幅・終了条件には触っていないが、`GameEntity.stepPredicted` が
1歩ごとに掃引到達判定(`reachedBody`)とアプシス検出(`ApsisTrack.observe`)を新たに払うので、
そこだけ切り分けて測った。

- **離散カウンタが全条件で完全一致**: `pred-tracked` / `pred-complete` / `pred-discard` /
  `pred-steps` / `sim-substeps` はワープを揃えた全条件でベースラインと同値(例: ×65536 マップで
  6 / 0 / 6 / 458 / 328)。**予算・刻み幅・終了条件は動いていない。**
- **1歩あたりの増分は node マイクロベンチで +0.9 µs**(LEO 420km・近傍窓15体・dt=121s):
  置き換えられた点判定 `containingBody` 45.6 ns に対し掃引 `reachedBody` 801 ns、
  `ApsisTrack.observe` は交差しない歩で 19 ns・交差する歩で 2,164 ns(28日プリセットでは
  46歩/周に2回 = 4.3% の歩)。合計 867 ns は **1歩 約190 µs の +0.46%**。
  掃引の値段は天体数にほぼ比例する定数コストで(地球1体 43.5 ns / 他14体 692 ns = 1体約49 ns)、
  近い天体で再帰に入るからではない。
- **ゲーム実測の `予測` は −2.6%〜+4.2%/歩** で、上記のドリフト幅(`積分` の −3.8〜+2.3%)に
  埋もれる。**マイクロベンチの +0.46% は計測床より小さい。**

## 3-1. A-7 — 遠端精度の値段を1箇所で決める【未決】

統合したので、計画線は予測の刻みに従う。予測は分配項 `horizon / PREDICT_MAX_STEPS` を
持つので、28日プリセットでは **dt = 2.42e6/20000 = 121 s** で刻み、20,000歩で覆い切る
代わりに **435周を46歩/周で刻んだ結果、遠端で 13,500 km ずれる**(P-3)。

つまみの両端は物理側で測ってある(v3-T13、H=28日・LEO):

| 分配項 | 採用 dt | 総歩数 | 遠端誤差 |
|---|---|---|---|
| あり(現状) | 121 s | 20,001 | **13,500 km** |
| なし | 20 s | 120,960 | **6.4 km** |

**6倍の歩数で誤差が 2100分の1。** 中間が取れる形(分配項の分母を可変にする、あるいは
遠端だけ粗くする)を選べるかどうかが判断の本体。

これは統合が持ち込んだ退行ではない — 統合前は同じ絵の上に二重に払っていた(マップビューで
ノード0本のとき、予測線と計画線が同じ軌道を重ねて描いていた)。**いま初めて「遠端の精度を
いくらで買うか」が1箇所で決められる。**

| 軸 | 評価 |
|---|---|
| **実現可能性** | 高。定数1個で済む形を選ぶ |
| **効果** | 性能ではなく**正しさ**。遠端誤差が 13,500 km か 6.4 km か |
| **前提条件** | D-3(長い表示期間の扱い)と同じ判断。**B-2 の閾値もここで決まる** |

**コード変更を伴わない、純粋な表示判断が先。** 決めた内容を定数へ落とすのはそのあと。

# 第4章 提案B — サブステップ数と積分予算

## 4-0. 【前提変化の直接の帰結】戦闘ビューの予測を止める

第1章 1-1 のとおり、main をマージすると戦闘ビューの `predicted` には消費者がいない。

- **変更**: `Predictor.update` の `'combat'` 経路を廃止する(`overviewMode` でなければ何もしない)。
- **効果**: 戦闘ビューの `予測` セクションが 0。**`stage1 combat ×65536` の `予測` は実測で
  49.5〜87.4 ms**(v1-T2 で 57.3、v3-T6 で 49.5 / 87.4。いずれも `pred-steps` 128・
  `pred-complete` 0 で予算に張り付いた状態)。**これが丸ごと消える。**
- 低ワープの戦闘では予測が完成済みなので `予測` は 0.2 ms(v1-T2)で普段は差が出ない。
  ただし**噴射中は `Player.behave` が毎フレーム `invalidatePrediction()` を呼ぶので、
  128歩を積み直し続ける** — v5 の 0.19 ms/歩 なら約24 ms/frame。推進が効くのは ×4 以下だけなので、
  **これは「低ワープで実際に飛ばしている最中」に効く。この値は未測定。**
- **実現可能性**: **高**。分岐1つ。ただし `PREDICT_COMBAT_STEP_BUDGET` と `'combat'` モードごと
  消せるので、むしろコードは減る。
- **注意**: **workspace4 では効果が出ない**(戦闘ビューでも予測線を描いているため)。
  main のマージが前提。

### 趣旨

戦闘ビューで予測線を描かないなら、その予測には読み手がいない。**読み手のいない仕事を
1フレーム128歩ぶん払うのをやめる。** 表示を切り替える(解析楕円へ)のと、伸長を止めるのは
別の変更で、**表示を先に切り替える** — 順序を逆にすると線が消えたフレームが出る。

### 実装で見落とせない1点: 動的重力源

1-1 の読み手の全数調査は**自機の**予測について取った表であって、`predictedAttractorsAt` /
`PlanAttractors.resolveAt` は**他の重力を持つ個体**(`Asteroid`)の `displayState(t)` を読む。
計画の折れ線は**戦闘ビューでも描かれる**ので、戦闘ビューで予測を丸ごと止めると、
CREATIVE に小惑星が居る条件で「戦闘ビューとマップビューで計画線の形が変わる」。

**⇒ 対象集合を絞る条件は「ビュー」ではなく「線以外の消費者を持つか」にする。**
`GameEntity` は既にその理由を分けて宣言している(`predictedAsGravitySource` /
`predictedAsPlanCollider` / `predictedForGhost` / `predictedLine !== null` の4つを
`predictsFuture` が畳んでいる)ので、戦闘ビューの対象集合は前2つで絞れる。
通常のステージでは該当0体なので、コストはやはり0になる。

## 4-1. Simulator — 減らすべきは substep の「数」ではなく「幅」

2-2 で見たとおり `dt` クランプが既に「1フレームの substep 数の上限」として働いている。
やるべきことは、その上限を**定数 1 個で下げられるようにする**こと。

**置き場は `adaptiveSimulationMaxStep` の `normalMaxStep` 引数。**

```ts
// Simulator.advance: 通常上限だけを K で押し上げる
adaptiveSimulationMaxStep(states, reentryRadius,
  Math.max(C.SUBSTEP_MAX_DT, simDt / K),   // ← ここだけ
  C.REENTRY_SUBSTEP_MAX_DT)
```

- `K` = 1フレームに許す substep 数の上限。現状は実質 `K = ceil(0.1·warp/20)`。
- **`Math.max` を返り値側へ掛けてはいけない** — 再突入中の 1 s 上限まで押し上げてしまう。
  加熱と動圧の積分結果が艦の生死を決め、それをプレイヤーが観測する以上、
  **再突入の細分化だけは K に優先させる。** `normalMaxStep` 側へ入れればその順序が自動で守られる。
- **パラメーターは1個しか増えない。** ユーザーの案のうち
  「最大サブステップ数(高加速時に効く)」がこれ。

**関連する既存の崖(新規指摘)**: 再突入中は `maxStep` が 1 s になるので、×65536 では
`6553.6 / 1 = 6,554 substeps/frame`(通常の20倍)。0.58 ms/substep なら**1フレーム 3.8 秒**。
高ワープで艦が大気圏へ入る瞬間にこれが起きる。K はこの崖には効かない(上のとおり
再突入を優先させるので)。**別途「高ワープでは再突入する艦を待たない」を決める必要がある** —
ただしその判断は「艦が焼けるかどうかの結果が変わる」ので、性能ではなく仕様の問題。

### 効果

| K | ×65536 の substep 幅 | `積分` の見積り(190.6 ms から) |
|---|---|---|
| 328(現状) | 20.0 s | 190.6 ms |
| 128 | 51.2 s | 74 ms |
| 64 | 102.4 s | 37 ms |
| 32 | 204.8 s | 19 ms |

### 精度の代償 — ここは正直に書く

LEO の周期は 5580 s。`K = 64` は **1周を55歩**で刻むことになる。RK4 でも 1/55 周期刻みは
軌道要素が目に見えて動く。**LEO に艦を置いたまま ×65536 で軌道精度を保つのは原理的に無理。**

これは新しい割り切りではない。**×4 を超えると推進・射撃・敵AI・剛体衝突が既に無効**であり、
「高ワープはプレイする時間帯ではなく、待つための時間帯」という設計が既にある。
そこに「軌道積分の精度も落ちる」を足すかどうかの判断。

**中間案**: `K` をワープ倍率ではなく **`adaptiveMaxStep` と同じ形で「生存する艦の局所周期」から
決める** — `maxStep = min(SUBSTEP_MAX_DT, 最短局所周期 / SUBSTEPS_PER_REV)` かつ
`max(…, simDt / K)`。LEO の艦がいなければ(月周回・ラグランジュ点)自然に大きな刻みが許される。
`adaptiveSimulationMaxStep` は既に「艦の高度から上限を決める」関数なので、
**置き場は決まっている。**

### ユーザーの「dt 下限値(低加速時に効く)」について

現状 ×1 では `ceil(simDt/20)` が既に 1 substep なので、substep 幅の下限を足しても効かない。
**効くとすれば `nextEventTime` に切り詰められた極小 substep のほう**で、これは別問題かつ小さい
(イベント境界は本来そこで解決したいもの)。**採用するのは `K` だけでよい。**

### 判定

| 軸 | 評価 |
|---|---|
| **実現可能性** | **高**。`adaptiveMaxStep` に1項。定数1個 |
| **効果** | **大**。×65536 で `積分` 190.6 → 37 ms(K=64)。ただし**高ワープ限定**で、×1024 以下では substep が既に少ないので効かない |
| **前提条件** | 「高ワープで軌道精度を落とすことを許すか」の表示・体験判断。**A/C とは独立** |

### 趣旨

`積分` の値段は「1フレームの時間送り ÷ 刻み幅 × 1サブステップの値段」。刻み幅の上限が
`SUBSTEP_MAX_DT = 20 s` の固定値なので、substep 数はワープ倍率に正比例する(×65536 で 328)。
**1フレームに許す substep 数の上限**を1つ足して、高ワープでは刻み幅の側を伸ばす。
再突入中の細分化(1 s)だけはこれに優先させる — 加熱と動圧の積分結果が艦の生死を決め、
それをプレイヤーが観測するため。

### 実装手順

| # | 内容 | 検証 |
|---|---|---|
| **B-1-1** | **`const.ts` に `SUBSTEP_MAX_COUNT` を足す。** 意味は「1フレームに許すサブステップ数の上限」。初期値は現状の挙動を変えない大きな値(400)にして、値の決定は B-1-3 へ回す | `npm run typecheck` |
| **B-1-2** | **`Simulator.adaptiveMaxStep()` に `simDt` を渡し、`normalMaxStep` 引数を `Math.max(C.SUBSTEP_MAX_DT, simDt / C.SUBSTEP_MAX_COUNT)` にする。** `simDt` は `advance` が既に受け取っている。**`Math.max` を `adaptiveSimulationMaxStep` の返り値側へ掛けてはいけない** — 再突入中の 1 s 上限まで押し上げてしまう。`adaptiveSimulationMaxStep` は再突入域の艦がいれば `reentryMaxStep` を即 return するので、`normalMaxStep` 側へ入れれば優先順序が自動で守られる。`time-step.ts`(純関数)は無変更 | `npm run typecheck`。挙動は初期値では変わらない |

**この変更セットに含めないもの**: 4-1 で挙げた再突入中の崖(×65536 で `maxStep = 1 s` により
6,554 substeps/frame = 1フレーム3.8秒)。K はこの崖に効かないし、効かせてもいけない。
「高ワープでは再突入する艦を待たない」は**艦が焼けるかどうかの結果が変わる**ので性能ではなく

## 4-2. Predict / Plan — ワープゲート(v5 で棄却したが、前提が変わって解禁)

v5 S-2 の帰結を数字にする。ゲートすべき条件は **`1フレームの時間送り / horizon`**:

| 条件 | simDt/frame | horizon | 比 | 使い回しは成立するか |
|---|---|---|---|---|
| ×65536・1周 | 6553.6 s | 5,580 s | **1.17** | **窓が毎フレーム丸ごと入れ替わる。原理的に不成立** |
| ×65536・28日 | 6553.6 s | 2.42e6 s | 0.0027 | 成立 |
| ×1024・28日 | 102.4 s | 2.42e6 s | 4e-5 | 成立 |

**⇒ 比が 1 を超える条件では、予測は完成しない。** v5 P-2 の
`pred-discard 6 / pred-complete 0 / pred-steps 458 が avg・max とも一致` は、
バグではなくこの比の帰結。v3 が同条件で実測した `予測` は **175〜181 ms**
(v3 §A-1: 「`積分`(74〜77 ms)の2倍以上。最大項」)、v1-T2 では **210.7 ms**。
**完成しない線に、フレーム最大の項を払っている。**

**対処**: 比が閾値を超えたら予測を伸ばさず、`OrbitLine` の解析楕円へ落とす。
1-1 のとおり、**その落とし先は main が戦闘ビューで既に採用した表示。**

副次的に、v5 P-2 の症状(`samplesOldestFirst()` が毎フレーム新配列を返すことによる
`TrajectoryLine` の焼き直し、`map ×1 28日` の `sync` 7.3 → 72.1 ms)も同時に消える。
**症状を隠すのではなく、原因の側で消える。**

### 判定

| 軸 | 評価 |
|---|---|
| **実現可能性** | **高**。ゲート1つ。閾値は `simDt/frame` と `horizon` の比という**既にある2量の比**なので新しい定数は1個 |
| **効果** | **大**。×65536・1周で `予測` **175〜210 ms**(実測)→ 0、`sync` の焼き直しも同時に解消 |
| **前提条件** | 「高ワープのマップで予測線が解析楕円に変わることを許すか」。**1-1 により、この判断は戦闘ビューで既に一度下されている** |

### 趣旨

`1フレームの時間送り / horizon` が1を超える条件では、予測が答えるべき窓が毎フレーム丸ごと
入れ替わる。**その条件では予測は原理的に完成しない**(v5 P-2 の
`pred-discard 6 / pred-complete 0 / pred-steps 458 が avg・max とも一致` はその帰結)。
完成しない線にフレーム最大の項(実測 175〜210 ms)を払うのをやめ、解析楕円へ落とす。

### 実装で見落とせない1点: 何で切り替えるか

**「`predicted === null` になったら楕円」にしてはいけない。** 低ワープでも噴射のたびに
`Player.behave` が `invalidatePrediction()` を呼ぶので、噴射の瞬間だけ楕円が1フレーム出て
ちらつく。**ゲートはフレーム単位の判断なのでちらつかない** — `Predictor` が「このフレームは
伸ばしたか」を公開し、表示側はそれを読む。

**乖離判定は止めない。** 止めると古い予測列が残り、計画の重力源・衝突体として読まれ続ける。
予算だけ0にすれば乖離判定は毎フレーム走り、高ワープでは必ず乖離するので列は1〜2フレームで
空になる。

## 4-3. パラメーターを増やさない形について

ユーザーの懸念(「アルゴリズムが定まる前にパラメーター調整はできない」「安易に軽量モードを
足すと収拾がつかない」)に同意する。この章の提案は意図的に**新しい定数を2個**(B-1 の `K`、
B-2 のゲート比)に抑えてある。

設定画面へ出す段は、**B-1 と B-2 が決まってから**。そのとき露出すべきは個々の定数ではなく
「1周あたり何歩刻むか」という1つの派生量であるべきだが、**それを決めるのは実装の後**。

### 趣旨と、着手できる条件

要望は「時間を加速してわかるデバッグがあるので、設定画面でシミュレーション精度を調整したい」。
**アルゴリズムが定まる前にパラメーター調整はできない**ので、この案は A/B/C の結論待ちで、
単独では着手しない。

**着手できる条件**: `SUBSTEP_MAX_COUNT`(B-1)と `PREDICT_WARP_GATE_RATIO`(B-2)の値が
実測で決まっていること。この2つが決まれば、露出すべき派生量は
**「1周あたり何歩刻むか」1つ**に畳める — B-1 の K は `simDt / K` を通じて、
`PLAN_ARC_STEPS_PER_REV` / `PREDICT_STEPS_PER_REV` は直接、いずれもこの量の別表現だから。

### 実装手順(前提が揃ってから)

| # | 内容 |
|---|---|

## 5-1. 案②(個体ごとに「効く天体の ID リスト」をキャッシュ)

### これは v1 の A-3 そのもので、一度も実装されていない

v1 §A-3 が既に測っている: **「`attractorsNear` の実測では LEO で 64→15 に絞られ、
グリッド側の寄与は 0 体」。** つまり LEO の艦にとって効く天体は `always` の15体ちょうどで、
残り49体は**評価してから捨てられている**。v1 はその按分値も出している —
「49体ぶんで約135 µs、1ステップ2回で約270 µs = 388 µs の約7割」。

**⇒ 提案②は新案ではなく、v1 で特定され、v2〜v5 のどこでも実装されなかった項目。**
止まっていた理由は v1 未検証事項3 に書かれている:

> `gravityAttractorsAt` が体数に線形か未確認。A-3 の「15体なら約41µs」は 176.68/64×15 の按分。
> 天体ごとに合成の段数が違うので線形とは限らない。

**この1つの測定が C-1 全体のゲート。** 5-0 の調査結果はそれを裏付ける方向を示している
(高精度パック収録の11体は独立な二分探索+Clenshaw で厳密に per-body、
`computePlanetHelioState` の衛星ファンアウトは収録惑星では起きない)が、**測っていない。**

### 重力側の上限は実測で 64 → 15、約4.3倍

近傍リストの中身は `always`(15体)+ グリッド27近傍。**LEO では後者が実測 0 体**なので、
64 → 15 で **4.3倍**。しかもその 4.3倍が乗るのは **予測1歩の 98.5%**(2-3)なので、
**予測の歩あたりコストがほぼそのまま 1/4 になる。**

**`always` を減らして更に伸ばすことはほぼできない**ので、過大評価しないこと。理由:

- `always` を「ECI 原点補正項 μ/D² が `GRAVITY_NEGLIGIBLE_ACCEL` を超えるもの」で切り直せば、
  ガリレオ衛星群(Io で μ/D² ≈ 1.5e-14、閾値 1e-8 の 100万分の1)は落とせて 15 → 約10 になる。
- しかし落とした天体は grid へ入り、**セル一辺 `sqrt(最重量の grid 天体の μ / ε)` が伸びる。**
  Io を grid へ落とすとセルは 1.2e10 → 2.4e10 m(2倍、許容)。**火星・水星まで落とすと 6.5e10 m、
  地球・金星で 2e11 m、木星に至っては 3.6e12 m = 24 AU で太陽系全体が1セルになり grid が壊れる。**
- **⇒ `GRAVITY_ALWAYS_COUNT = 15` はほぼ最適。C-1 の重力側の利得は 4.3倍で頭打ち。**

### 予測対象が多い条件では、窓ではなく `displayState` の走査が支配する

v3 §A-1 の実測: `debug-load`(小惑星300+破片500)では
**「801体の `displayState(t)` を1歩につき2回引くので、301歩なら 48万回/frame」** で、
`eph-attr miss` は 2/500ms しか立っていない — **暦のリングはほとんど触っていない。**
`predictedAttractorsAt` の中身のうち、この条件で効いているのは
`for (const e of entities.attractors())` のループのほう。

**近傍リストはこれも同時に切る**(小惑星から見て効く相手も数体)。**⇒ C-1 は
「窓が小さい条件では窓を、動的重力源が多い条件では走査を」切る、同じ1つの機構。**

### 衝突側の効果ははるかに大きい: 101 → 実質2〜3

LEO の艦が1歩(26 s)で表面に到達しうる天体は**地球だけ**。にもかかわらず現状は:

1. `stepDt` が毎歩 101 体の clearance/closingSpeed を回す
2. `provider.at()` が毎歩2回、101体ぶんの collision 配列と `collisionById` Map を組む
3. `integrateTo` が毎歩、start(101) + end(101) を dedupe Map へ詰め直す
4. `findImpact` が候補全部に掃引判定をかける

v5 P-9 の内訳(1歩 1.19 ms を 100% として)では **1+2 で約96%、3 が「衝突体の配列と Map の
構築 × 2」で約46%**。判定そのもの(4)は 2.4%。

**⇒ 計画側の C の利得は、重力側の 4.3倍ではなく、衝突候補側の 101 → 数体のほう。**

### 更新頻度の正しさは構成的に保証できる

近傍リストの寿命 = グリッドのセル一辺 ÷ 移動速度 = `1.2e10 m / 7.7 km/s` ≈ **15日**。
28日プリセットの予測を伸ばし切る間に **1〜2回**引き直せば足りる。
判定は「前回リストを組んだ位置から、セル一辺の何分の1動いたか」— 位置差なので
v5 S-3 の「同一性は時刻差ではなく位置差で測る」に沿う。

### 置き場

構造を持っている。予測側に同型のものを置く(`Predictor` が `stepAttractorsScratch` を持っている

### 実装で見落とせない1点: 「1体だけ引く」は体数に線形ではない

`stateOf` は天体ごとに以下の段数の違う経路を通る:

| 天体 | 経路 |
|---|---|
| 恒星 | 即値(原点静止) |
| 高精度パック収録の11体 | 独立な二分探索 + Clenshaw |
| 未収録の衛星 | 親の日心状態 + 惑星相対モデル |
| 未収録の惑星 | 重心の日心状態 − **その惑星の全衛星**の相対状態の質量加重和 |

最後の1行が効く。**`always` の15体は `mu` の重い順なので木星・土星・天王星・海王星が入っており、
木星を1体引くだけでその衛星14体の相対状態が評価される**(重心補正のため)。
つまり 64 → 15 に絞っても暦のコストは 15/64 にはならない。
**§9-2 の体数線形性の測定は「線形かどうか」ではなく「実際に何倍になるか」を出すために要る。**

さらに `degree2At` / `orientationOf` は**時刻キャッシュを持たず `attractorAt` ごとに再計算する**。
こちらは体数にきれいに比例するので、絞ればそのぶん丸ごと落ちる(C-3d と同じ論点で、
**C-1 と同じ変更セットで測る**)。

## 5-2. 案①(問題構造を Simulator 側へ寄せる = 共有掃引)

全個体の予測先端を**共有の時刻グリッド**で足並みそろえて進め、窓構築を1回にする。

- **効果は M 倍**(窓構築が 1/M)。`debug-load-map-warp1`(小惑星300 + 破片500)のような条件では圧倒的。
  stage1(最大7体)でも 7倍。
- **代償は応答性。** 噴射した瞬間に線が変わらない。これは `Player.behave` が `thrust` 非 null で
  即座に `invalidatePrediction()` を呼ぶという**明示的な UX 要件**と正面から衝突する。
- **代償は見た目。** 「一定間隔で線が0から伸び直す」演出になる。

### この文書からの折衷案

**操作艦だけ現行の個別方式を残し、それ以外を共有掃引へ移す。**

- 操作艦は M = 1 なので、そもそも共有して得をする相手がいない。応答性が観測されるのも操作艦だけ。
- 他個体の予測線は 1-1 によりマップビューでしか出ないうえ、ゴーストの位置は数秒の遅れが分からない。
- v5 は「先端時刻が個体ごとに違う以上、`Simulator` のような共有は成立しない」と書いたが、
  **「揃えればよい、ただし操作艦を除いて」**と読み替えられる。

### 判定

| 軸 | 評価 |
|---|---|
| **実現可能性** | **低〜中**。再計算ポリシーと見た目が変わる。`Predictor` の予算分配・カーソル・破棄判定を全部組み直す規模 |
| **効果** | **M に比例**。stage1(7体)で窓構築7倍、debug-load(800体)で桁違い。**stage1 系の条件では A/B/C-1 より小さい** |
| **前提条件** | C-1 の後。C-1 で1回の窓が 4.3倍安くなれば、共有の相対的な旨味は減る |

### 趣旨

`Simulator` は「同一時刻の多数の物体」を解くので窓を1回組んで使い回せる。`Predictor` は
「物体ごとに別時刻」なのでそれができない。**問題構造の側を変えて `Simulator` と同じ手を
使えるようにする** — 全個体の予測先端を共有の時刻グリッドで揃え、窓構築を1回にする。
効果は M 倍(窓構築が 1/M)だが、**再計算ポリシーと見た目が変わる。**

### 実装で見落とせない1点: 刻み幅を揃えると精度が揃わない

現状の刻み幅は個体ごとに `その場の局所周期 / PREDICT_STEPS_PER_REV` で決まる。
LEO の艦は 20 s、遠方の小惑星は数千秒になる。**共有の時刻グリッドへ載せると、
遠方の個体には無駄に細かく、近傍の個体には粗くなる** — 「1周あたりの歩数を固定すると
高度・離心率によらず精度が揃う」という現在の設計そのものが崩れる。

**⇒ 共有できるのは「窓を引く時刻」であって「刻み幅」ではない。** 実装するなら、
グリッドの刻みを最も細かい個体に合わせ、他の個体はグリッドを**間引いて**踏む(k歩に1回だけ
進める)形になる。窓は毎グリッド1回で済むので効果は残るが、**「窓を引いたのに進めない個体」が
出るぶん、素朴な M 倍には届かない。** この点は v5 にも v6 の判定表にも書かれていなかった。

### 実装手順(着手判断が先。実現可能性 低〜中)

## 推奨する順序

**判断の小さい順ではなく、「決めなければ他が決まらない順」に並べる。**

着手できない。したがって残りは **マージ → B → 再測定** の順に通す。

0. **`gravityAttractorsAt` の体数線形性を node で1回測る**(§9-2 の1行目 = **C-1-0**)。
   C-1 の可否がこれだけで決まり、他の作業と一切干渉しない。

1. ~~**A の測定**~~ **済み(§3-0)。** `plan歩` が 210〜2000 → 0、`計画` が最大 1,237 → 1.45 ms。
2. **P-3 / D-3 を決める**(長い表示期間の遠端をどう扱うか = **A-7**、§3-1)。
   B-2 の閾値もここで決まる。**コード変更を伴わない、純粋な表示判断。**
3. **main のマージ**。B-0 は main の変更が無いと効果が測れない(§9-3)。
4. **B-0 + B-2**(予測を止める2つのゲート = **B-0-1〜5 / B-2-1〜6**。
   `Player.createOrbitLine()` は共通なので、先にやった側で1回書けば足りる)。
   どちらも高・大・低リスク。2 が決まっていれば閾値も決まる。
5. **B-1b**(終点の101体窓を落とす = **B-1b-0〜4**)。精度判断が要らず、`積分` だけを動かす。

7. **C-1**(近傍リスト = **C-1-1〜8**)。0 が通っていて、ここまでで残った経路が確定してから。

# 第8章 【新規】1サブステップは天体窓を**2回**組んでいる

第2章のモデルを詰めている途中で見つけた、v1〜v5 のどこにも書かれていない事実。

`Simulator.advance` のループ本体は、1サブステップあたり**別々の窓を2回**引いている:

```ts
// substep() の中 — 中点で「重力源」の窓(64体)
const sources = attractorsAt(this.ephemeris, this.entities, simTime + dt / 2);
//                ↑ simulation/attractors.ts の attractorsAt = gravityAttractorsAt + 動的重力源

// advance() の中、substep() から戻った直後 — 終点で「全天体」の窓(101体)
const attractorsNow = this.ephemeris.attractorsAt(this.simTime);
```

`attractorsNow` の消費者は2つだけ:

| 消費者 | 高ワープでの状態 |
|---|---|
| `contactPhysics.resolveSubstep` | **`resolveCollision` が偽なので呼ばれない** |
| `entities.cleanup` の `checkLoss` → `reachedBody` | 毎サブステップ走る |

**⇒ ×4 を超えるワープでは、101体ぶんの窓は `checkLoss` の表面接触判定のためだけに
毎サブステップ組まれている。**

`Ephemeris` は `attractorsAt` と `gravityAttractorsAt` を**別のリング**で持つので、
同じ `t` でも一方の結果を他方へ流用できない。しかも時刻が違う(中点 vs 終点)ので
そもそも当たらない。node 実測を当てると:

```
176.68 (重力64) + 283.37 (全101) + 15.09 (分類) = 475 µs / substep
```

対して実測は **0.58 ms/substep**(190.6 ms ÷ 328)。**ブラウザ倍率を考えれば内訳は閉じており、
半分以上が「衝突判定が無効な高ワープで、表面接触のためだけに引く 101体の窓」。**

## B-1b の趣旨と実装手順

**趣旨**: 高ワープでは終点の101体窓の消費者が `checkLoss` の表面接触判定しか残らない。
その判定を、同じサブステップが**中点で既に組んでいる重力窓**(64体 + 動的重力源)で行い、
101体の窓を組むのをやめる。

### 実装で見落とせない1点: 副産物を返す関数を作らない

いま `sources`(中点の重力窓)は `substep()` の中に閉じている。これを外へ持ち出すために
`substep` の返り値を増やすのは、`/refactor` の「**状態を更新し、副産物を返す関数を作らない**」に
反する(`substep` は `simTime` を進める副作用のある関数)。
**⇒ 窓の構築を `advance` 側へ引き上げ、`substep(simTime, dt, sources, passiveWarpLod)` にする。**
`substep` は渡された窓で積分するだけになり、`lastGravitySourceCount` の記録も `advance` 側へ移る。

### 副次的に変わること(退行ではない)

中点の重力窓は、終点の全窓と**2点で違う**:

- **時刻が中点**。`reachedBody` は `prevState → state` の区間を掃引するので、区間の中点で天体を
  据えるのはむしろ整合が良い(終点で据えるより偏りが小さい)。
- **動的重力源を含む**。いままで解析天体しか相手にしていなかった表面接触が、`Asteroid` も
  相手にするようになる — 破片が小惑星へ突っ込めば消える。**これは正しい方向の変化。**
