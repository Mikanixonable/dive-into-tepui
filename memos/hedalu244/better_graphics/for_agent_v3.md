## 1. 確定した判断

### 1-1. 露出 — 放射照度を基準に取り、既存の手調整値は捨てる

**方針(確定)**: HDR 線形空間へ移した上で、物理的根拠のある式へ組み替える。視覚的な問題が出たら
**HDR 空間の上で**再調整する。LDR 時代の手調整値へ戻す方向の調整はしない。

したがって「既存の手調整値が全面的に合わなくなる」は、
**回避すべき事態ではなく通過すべき工程**である。画像回帰シーンは「変更前後の一致」を
判定するためではなく、「どこがどう変わったか」を人が読むために撮る。

**基準の取り方(確定)**: 太陽放射照度を一次基準とする。

```text
E(d) = SOLAR_CONSTANT * (AU / d)^2      [W/m^2]    — 距離 d における放射照度
L_surface = E(d) * albedo / pi          [W/m^2/sr] — 完全拡散反射面の放射輝度
exposure  = 1 / L_ref                              — L_ref を中間グレーへ写す係数
```

必要な量は**すべて既にある**:

- `SOLAR_CONSTANT = 1361` [W/m²] — `game/const.ts:65`(ラジエータと電力が既に使用)
- `ASTRONOMICAL_UNIT = 1.495978707e11` — `physics/srp.ts:9`
- 逆二乗則の実装 — `physics/srp.ts:24`
- `STEFAN_BOLTZMANN` / `HULL_EMISS` — `game/const.ts:44-45`(砲身赤熱を黒体で導ける)
- 機体温度 [K] — `game/const.ts:47-51`

**唯一の欠落はアルベドである。** 天体表面は 101 天体ぶんの 16 進直書き色(85 リテラル、ユニーク 63 種、
`celestial-registry.ts:88-195`)しか持たず、アルベド値は 1 つも無い。色の決め方に根拠コメントも無い。
**これが露出フェーズの最大の実作業になる。**

第三版では、この作業の重みがさらに増した。**地球照を面光源として扱う(§1-6)には、天体の
アルベドが「見た目の色」ではなく「反射光源の強さ」として使われる**からである。アルベドは
もはや表面の見え方だけの量ではなく、他の物体を照らす光量そのものになる。

補足すべき事実として、`SOLAR_PRESSURE_1AU = 4.56e-6`(`physics/srp.ts:6`)は
`SOLAR_CONSTANT / c` と同じ量の二重表現である。露出基準を入れる際に、片方をもう片方から
導出する形へ統一すること(定数が2つある状態で放射量の基準を名乗らない)。

**既にこの基準で書かれている部分がある。** リングだけが完全な放射伝達モデルになっている —
`RingOpticsDef` の単一散乱アルベド(0.35〜0.6)・法線光学的厚さ(2e-8〜8)・HG 非対称因子(0.05〜0.9)が
全 35 帯に出典コメント付きで入っており、`physics/ring-optics.ts:50-64` の `ringSingleScattering` は
「等方散乱=1 の相対放射輝度」という明示された単位を持つ。現状はこれを
`RADIANCE_SCALE = 0.72`(`render/ring.ts:30`)という**手調整係数 1 個**で LDR へ押し込んでいるだけである。

> **露出の校正はリングを基準に取る。** 唯一、放射量として意味の定まっている系だから。
> `RADIANCE_SCALE` が 1.0 になる(= 押し込み係数が消える)ことを、露出フェーズの完了条件の一つにする。

**HDR 化で構造変更が要る箇所**: `Billboard` は `MeshBasicMaterial.opacity`(0..1 クランプ)で
明るさを表しており、`transparent + AdditiveBlending` の 5 経路のうち最大のものがここを通る
(`render/billboard.ts:16-18`。太陽・惑星輝点・噴射・RCS・再突入・全フラッシュが共有)。
1 を超える輝度を出せないので、`colorNode` を持つノードマテリアルへ置き換える必要がある。
**太陽ビルボードは opacity 固定 1**(`render/stars.ts:50`)で、現状は白飛びすら起きていない。

### 1-2. 座標境界 — 浮動原点を描画から切り離す(グラフィック以前の問題)

**方針(確定)**: 描画はすべてフローティングオリジン座標系(`THREE.Vector3`)で行い、
GPU に ECI 座標(独自 `Vec3`)が渡らないことを徹底する。`game/` から `render/` へ情報が渡る
**前後のできるだけ早い段階**で変換する。可能なら `render/` に ECI 座標が入ること自体を避ける。

これは描画品質の話ではなく、ゲームと描画の疎結合化の話である。

現況(調査で確定):

- **`render/` の `FloatingOrigin` 依存は 2 箇所だけ** — `orbit-line.ts:119`、`sampled-line.ts:197`。
  どちらも `line.position` を置くためだけに使っている。
- **ECI 絶対座標が uniform で GPU へ渡っている箇所は 0 件。** シェーダに入る位置ベクトルは
  すべて描画フレーム相対(`earth.ts` の `earthCenter`、`ring.ts` の `bodyCenter`、
  `celestial-surface.ts` の 32 バンド `center`)か単位方向。**現時点で単精度の破綻は無い。**
- ただし**大きな絶対値が f32 バッファに載る系統が 2 つある**(下記)。
- `ring.ts` / `earth.ts` / `billboard.ts` / `stars.ts` は既に「THREE 型 + 数値のみ」で目標状態。
  `game/celestial/ring-view.ts` が境界の担い方の見本になっている。
- **本丸は `sampled-line.ts`** — `KinematicState` / `ReferenceFrame` / `Attractor` / `Ephemeris` に加え、
  **絶対 ECI 位置を引数に取る関数型 `ScaleAtFn`(`sampled-line.ts:28`)を `render/` 自身が定義している**。
  `fo` を外しただけでは目標状態にならない。

**f32 精度の実在リスク(要実測)**:

| 系統 | 座標の基準 | 最大絶対値 | f32 量子化 | 見えうる条件 |
|---|---|---|---|---|
| `orbit-line.ts:76,261-263` の頂点 | 中心天体相対 | 海王星軌道 ~4.5e12 m | ~3e5 m | 海王星付近まで寄った状態でその軌道線を描くと ~3 px 相当 |
| `point-field-view.ts:92-96` の `instanceMatrix` | 太陽中心 | カイパー帯 ~7.5e12 m | ~5e5 m | 同上 |

いずれも ECI 絶対ではないが「絶対に近い大きさ」であり、フローティングオリジンの恩恵を受けていない。
**引きの絵では画素以下だが、寄ると露見する。**

**切り離しの方法(2段)**:

1. **上り(生成側)と下り(アップロード側)を割る。** `sampled-line` の bake + Hermite 細分は
   THREE を一切使わない座標計算で、`Float32Array` への書き込みだけが描画側である
   (`sampled-line.ts:113-151` を確認済み)。頂点列の生成を `game/` 側へ出し、
   `render/` は「頂点バッファと材質を持ち、渡された配列をアップロードする」だけにする。
2. **表示ポリシーは `render/` に残す。** 弦数の決め方(画面上のサグ `MAX_EDGE_SAG_PX = 0.5`、
   折れ角上限 5°)は描画の判断なので `render/` が持つ。ただし ECI を取らない純関数
   `chordCountFor(turnRad, chordLen, metersPerPixel) -> number` として公開し、`game/` が呼ぶ。
   これで「表示 LOD は `render/`、座標は `game/`」が両立する。

`orbit-line` も同型(楕円頂点の生成は `OrbitalElements` からの幾何、アップロードは描画)。

**完了条件**: `src/render/**` から `physics/vec3` の `Vec3`、`KinematicState`、`ReferenceFrame`、
`Attractor`、`Ephemeris`、`FloatingOrigin` への import が 0 件。
公開 API の引数が `THREE.*` と数値と描画専用型だけになる。

### 1-3. 深度カスケード — 測ってから決める。変換は一か所に閉じる

**方針(確定)**: 距離圧縮の撤去は GPU 上の深度精度が担保できるかが鍵であり、
やってみないと分からない。**全体と密結合にならないよう、順変換と逆変換を一か所へ切り出しておく。**

**スパイク → 測定 → 判断 → 本実装**の順にする。判断が否なら距離圧縮は残り、
後続フェーズは圧縮を前提に進む(その場合の影響は §1-4 と §6 に明記)。

調査で判明した、判断を楽にする事実:

- **`physics/projection.ts` は near/far に一切依存しない。** `Viewpoint` が near/far を持たず
  (`projection.ts:10-16`)、`projectToNdc` も `metersPerPixel` も near/far を読まない
  (`projection.ts:19-37, 53-57`)。
  → **カスケード間で fov/aspect を共有する限り、`ProjectFn` / `ScaleFn` の全消費者(マーカー約10系統、
  picking 5系統、plan 系、`sampled-line` の頂点密度、`ring-view` の LOD、`point-body` の 2px 判定)は
  無変更で通る。** カスケードは「Viewpoint 1 つ + (near, far) N 組」で足りる。
- **投影行列を書く箇所は `camera/camera-system.ts:73` の 1 箇所しかない。**
  `updateProjectionMatrix()` の呼び出しは src 全体でここだけ。
- `PerspectiveCamera` は 2 個(戦闘 / 広範囲)だけ。
- **`COMBAT_CAMERA_FAR = 6e7` は `MOON_VIS_DIST = 4.5e7` から逆算された値である**
  (`const.ts:120-123` のコメントが明記)。圧縮を撤去すれば far の制約がそのまま解ける。
- **地球だけは既に真位置・実半径で描かれている**(`earth-body.ts:34`)。真スケール描画の前例が既にある。

**カスケードと浮動原点の相互作用**: カスケードごとに原点を変える必要はない。
浮動原点は 1 つのまま、カスケードは投影行列の near/far だけを持つ。f32 の精度は原点からの距離で
決まるが、遠方カスケードでは要求される絶対精度もその分緩いので釣り合う。**ただしこれは仮説であり、
スパイクの測定対象そのものである。**

**変換の切り出し(要件)**: 現況、ECI → 描画位置の順変換は **5 種類に分散**しており共通ヘルパが無い。
逆変換は **1 つも存在しない**。

1. `FloatingOrigin.RtoThreeV3(pos)` — 真スケール配置
2. `cam.position + dir * visDist`, `scale = visDist*r/d` — `sphere-body.ts:76-81`, `point-body.ts:141-147`
3. `cam.position + dir * SUN_DISTANCE` + 固定サイズ — `sun-body.ts:54-62`
4. `cam.position + dir * STAR_SHELL_RADIUS` — `point-body.ts:177-181`
5. `mesh.position = cam.position` + `setScalar` — `environment-scene.ts:170-171`, `celestial-grid.ts:249-250`

これらを 1 モジュール(`render/view-space.ts` 等)へ集約し、次を公開する:

```text
toRender(eciPos)        -> THREE.Vector3     順変換
toEci(renderPos)        -> Vec3              逆変換(現在は存在しない。作る)
cascadeOf(eciPos)       -> number            どの深度レンジに属するか
cascadeNearFar(i)       -> {near, far}
```

**圧縮を採るにせよ撤去するにせよ、この集約は先にやる。** 圧縮方式そのものがこのモジュールの
実装詳細に落ちるので、後で差し替えられる。

**スパイクの測定項目**: (a) 分割数 2 / 3 / 4 での z-fighting の有無、(b) パス増加によるフレーム時間、
(c) `depthTest: false` の 3 箇所(星殻 `stars.ts:28`、大気リム `earth.ts:92`、
Δv ギズモ `plan-gizmo-3d.ts:32`)がカスケード間の深度クリアと衝突しないか、
(d) `frustumCulled = false` が広範(13 箇所)なので `camera.layers` による振り分けが機能するか。

**先行して必要な小作業**: `types/three-shims.d.ts` に `clearDepth()` が無い(`:6-19`)。カスケードには要る。

### 1-4. 遮蔽 — 「太陽可視率」を単一の問いへ統一する

**方針(確定)**: 惑星のリングの影・艦のセルフシャドウ・艦が惑星の影に入る現象は同じ物理であり、
同じ基盤で表現されているのが自然。現存のリング影方式をそのまま遅延化するのは
リングへのアドホック実装を温存するだけなので採らない。

**統一の実体は、実装ではなくインターフェースである。**

```text
sunVisibility(worldPos, normal) -> [0, 1]      受け手はこれしか呼ばない
```

受け手(天体表面 / 艦の BRDF / リング / 大気)はこの 1 関数しか知らない。
遮蔽器の側だけが種類を持つ。

> **第三版での変更**: 太陽を面光源として扱う(§1-5)ことにより、この関数の戻り値
> `[0, 1]` は「半影のどのくらいの割合が見えているか」という**元々の物理的な意味を取り戻す**。
> 第二版では実質二値だったものが、面光源化によって連続量として意味を持つ。
> インターフェース自体は変えなくてよい。

**なぜ単一のシャドウマップではできないか(数値)**: 同一シーン内で影に関わる寸法が **1e0 〜 1e10 m** に開く。

| 遮蔽の対象 | 寸法 |
|---|---|
| 艦の構造 | 数 m(`PLAYER_HULL_RADIUS = 2.6`、全長 5〜6 m) |
| 追跡カメラ距離 | 12〜8000 m |
| 戦闘域(弾の消滅 / 敵スポーン) | 10〜30 km |
| 惑星本体 | 1.7e6〜7.2e7 m |
| リング系 | 6.7e7 〜 **1.3e10 m**(土星フェーベ環) |
| **最細のリング帯** | **幅 1.5e3 m @ 半径 4.2e7 m(天王星 λ 環)= 比 3.6e-5** |

天王星の λ 環 1 本に 1 テクセルを割り当てるだけでも約 2.8 万テクセル/軸が要る。
フェーベ環まで含めればさらに 2 桁悪化する。**シャドウマップでリングは解けない。**
逆に、球とリング平面には**閉じた解析解があり、離散サンプリングより精度が高い。**

**したがって遮蔽器は 3 層に分ける(実装の分岐であって、概念の分岐ではない)**:

| 遮蔽器 | 手法 | 適用範囲 | 現況 |
|---|---|---|---|
| 天体本体(球/回転楕円体) | 解析的レイ・球交差 + **有限角直径の半影** | 1e6〜1e11 m | **CPU と GPU に別実装が既存**。`physics/shadow.ts` の `sunlitFactor` と `render/ring.ts:71-77` の `inBodyShadow` |
| リング平面(帯ごとの τ) | 解析的レイ・平面交差 + Beer–Lambert | 1e7〜1e10 m | `render/celestial-surface.ts:63-91` に**固定長 32 バンド**で既存 |
| 艦・デブリ・基地 | シャドウマップ(**CSM + PCSS**) | 1e0〜3e4 m | **存在しない**(`castShadow`/`shadowMap` は src に 0 件) |

3 層目の適用範囲は 10 m 〜 30 km の 3 桁強で、CSM 3 枚なら 1 枚あたり 1 桁。標準的な使い方に収まる。

**「同じ基盤」が現実に破れている箇所(これが本題)**:

1. **物理側と描画側が同じ問いに別々に答えている。** `sunlitFactor`(`physics/shadow.ts:8-13`)は
   **地球固定の円柱影**で、`R_EARTH` 直書き、他天体の影が存在しない。これを読んでいるのは
   照明(`environment-scene.ts:130-132`)・ラジエータ熱入力(`player.ts:230-233`)・
   電力(`player.ts:235`)・SRP(`dynamics.ts:120-123`)の 4 系統。
   → **月の影に入ってもラジエータは冷えず、SRP は効き続ける。これは描画の問題ではなく物理の欠陥である。**
   遮蔽の統一は、まずここを全天体へ一般化することから始まる。
   なお **円柱影は「太陽を点光源として扱った近似」そのもの**であり、§1-5 の面光源化はこの
   物理側の修正と同じ 1 つの作業になる。円錐(本影 + 半影)へ置き換えれば、描画・熱・電力・SRP の
   4 消費者が同時に正しくなる。
2. **リング影シェーダが「真の方向 × 偽の位置」を混ぜている。**
   `sunDirNode` は天体の**真の ECI 位置**から引いた方向(`sphere-body.ts:64-65`)なのに、
   `positionWorld` と 32 バンドの `center` / `inner` / `outer` は**圧縮された描画位置・描画長**
   (`celestial-surface.ts:128-150` が `band.innerRadius / bodyRadius * displayScale` で換算)。
   `ring.ts` の `bodyRadius` にも描画スケールが入る(`ring-view.ts:117-124`)。
   → **距離圧縮を撤去しない限り、遮蔽を物理的に正しく統一することはできない。**
   これが §1-3 のカスケード判断と影の統一を結びつける唯一かつ決定的な依存関係である。
3. **CPU/GPU 二重実装が既にある。** `physics/ring-optics.ts:67-78` の `ringPlanetShadow` は
   `render/ring.ts:71-77` の TSL 版と同じ幾何だが、**src のどこからも呼ばれていない**(§3-5)。

**天体別シェーディング入力テーブル(シェーディングコンテキストID)は不要。** これを立てる主根拠だった
「リング影 32 バンドの固定長 uniform 配列を G-buffer に載せずに済ませる」は、影が遮蔽基盤へ移れば消える。
必要なのは「遮蔽器のリスト」だけであり、それは ID で引くテーブルではなく遮蔽問い合わせの内部構造である。

### 1-5. 太陽を面光源として扱う(第三版の追加)

**方針(確定)**: 太陽の視直径を無視しない。点光源近似をやめ、有限の立体角を持つ面光源として扱う。
帰結として**半影(ソフトシャドウ)が要る**。

**なぜ必要か(数値)**:

| 距離 | 太陽の視半径 | 半影の幅 |
|---|---|---|
| 1 AU(地球近傍) | 0.266° = 4.65 mrad | 遮蔽器から距離 d の面で **d × 9.3e-3** |
| 艦の自己影(d = 5 m) | 同上 | 4.7 cm — 艦の寸法 5 m に対して約 1% |
| 地球の影(d = 1 本影長) | 同上 | 本影 ~1.4e6 km に対し半影は円錐として広がる |
| 月軌道での地球の影 | 同上 | 本影半径 ~4600 km に対し半影半径 ~8100 km |

**近距離では半影は細く、遠距離では支配的になる。** 艦のセルフシャドウでは「ほんの少し柔らかい影」
だが、地球の影に艦が入る瞬間には**半影を横切る時間が数十秒〜数分あり、その間の減光が連続的に効く**。
現状の `SHADOW_PENUMBRA = 6e4` はこの現象を線形ぼかしで模した手調整値であり、**本来は幾何から導ける量である**。

**実装の分解**:

1. **解析遮蔽器(球)** — 光源球と遮蔽球の 2 つの円盤の**重なり面積比**で可視率を出す。閉じた解が
   あり、`smoothstep` 近似より正確で、しかも同程度に安い。§1-4 の `sunVisibility` の戻り値が
   ここで初めて連続量として意味を持つ。**円柱影 → 円錐影(本影 + 半影)への置き換えは、
   描画ではなく `physics/shadow.ts` の修正である。**
2. **シャドウマップ側(艦・デブリ・基地)** — PCSS(Percentage-Closer Soft Shadows)。ブロッカー
   探索で遮蔽器までの距離を推定し、光源の角半径からフィルタ半径を決める。太陽の角半径が
   `4.65 mrad` の定数なので、**フィルタ半径はチューニング値ではなく物理量から出る**。
3. **BRDF 側** — 面光源に対する鏡面反射は点光源の Phong/GGX では表せない。§1-7 のライティング
   パスで LTC(Linearly Transformed Cosines)により球光源を積分する。太陽は角半径が小さいので
   近似の誤差も小さいが、**地球照(§1-6)は同じ仕組みでなければ表せない**ため、実装は共通化する。

**この判断が波及する既存コード**:

- `physics/shadow.ts` の `SHADOW_PENUMBRA = 6e4` 直書き → 太陽視半径から導出。
- `render/ring.ts:71-77` の `inBodyShadow` が**二値**である点 → 半影を持つ連続量へ。
- `render/celestial-surface.ts` のリング影バンドの遮蔽 → 同上(リング帯が落とす影も、
  太陽が面光源である以上、帯の縁でぼける)。

### 1-6. 地球照を面光源として扱う(第三版の追加)

**方針(確定)**: 天体からの反射光(地球照 / earthshine)を、無視できない距離では
**面光源として扱う**。点光源近似も、一様な環境光近似も使わない。

**なぜ必要か(立体角)**: LEO(高度 420 km)から見た地球は**視半径 約 70°、立体角 約 3.9 sr** —
全天 4π sr の **31%** を占める。点光源として扱うのは論外であり、方向を持たない環境光として
扱うのも同じくらい誤りである。**艦の地球を向いた面と宇宙を向いた面で明るさが桁で違う**という、
軌道上の絵の最も特徴的な性質がそこから出る。

| 位置 | 地球の視半径 | 立体角 | 全天に占める割合 |
|---|---|---|---|
| LEO 420 km | 70.0° | 3.90 sr | 31% |
| 静止軌道 35786 km | 8.6° | 0.071 sr | 0.56% |
| 月軌道 384400 km | 0.95° | 8.6e-4 sr | 0.007% |

**距離とともに滑らかに点光源へ縮退する**ので、近距離用と遠距離用に別モデルを持つ必要はない。
面光源の積分がそのまま両方を覆う。

**光源としての強さ**:

```text
L_body = E_sun(d_body) * albedo * phase(alpha) / pi     [W/m^2/sr]  天体表面の放射輝度
E_at_ship = L_body * Omega_visible_lit                  [W/m^2]     艦が受ける放射照度
```

- **アルベドが光源の強さそのものになる**(§1-1)。これが第三版でアルベド調査の重みが増した理由。
- **位相**を無視できない。地球の昼側だけが光る。艦から見た地球の**照らされている部分だけ**が
  光源であり、三日月形になる。円盤光源では表せず、**球光源 × 太陽方向による切り取り**が要る。
- 地球は色を持つ(海の青、雲の白、陸の褐色)ので、**地球照は色付きの光源である**。艦の影側が
  青みを帯びるのは、この効果の最も分かりやすい現れ方になる。

**実装の分解**:

1. **光源の生成** — 各天体を「球光源 + 太陽方向による位相」として §1-7 のライティングパスへ渡す。
   数は少ない(実用上は最も近い 1〜2 天体で足りる)。可視率の判定は §1-4 の遮蔽基盤を共有する
   (地球照を落とす天体自身が太陽の影に入っていれば光らない)。
2. **積分** — LTC で球光源に対する diffuse / specular を積分。§1-5 の太陽と**同一の仕組み**。
   太陽は「小さくて強い球光源」、地球照は「大きくて弱い球光源」で、パラメータが違うだけになる。
3. **アルベドとの結合** — 光源の色と強さは天体の albedo テクスチャの平均値から引く。局所的な
   分布(雲がある側が明るい)は将来の改良で、初版は全球平均でよい。

**現状との差**: 今は `AmbientLight(0x8899bb, 0.25)`(`environment-scene.ts:87`)という
**方向も距離も位相も持たない定数**が、地球照・星明かり・多重散乱の全部を兼ねている。
面光源化はこの定数を消す作業でもある。

### 1-7. ライトプリパス(3 パス構成)へ移行する(第三版の追加)

**方針(確定)**: 第二版の 2 パス遅延シェーディング(ジオメトリ → ライティング)をやめ、
**3 パスのライトプリパス**(ジオメトリ → ライティング → レンダリング)を採る。

```text
Phase A  ジオメトリパス   → 深度 + 法線 + 粗さ            (幾何だけ。マテリアルの色を持たない)
Phase B  ライティングパス → 拡散照度バッファ + 鏡面照度バッファ
                            エリアライト積分・遮蔽問い合わせはここに閉じる
Phase C  レンダリングパス → 再度ジオメトリを描き、照度バッファを読み、
                            マテリアル(アルベド・金属性・自前の表面モデル)を掛ける
Phase D  半透明 + ポストプロセス
```

**なぜ 2 パス遅延シェーディングでは足りないか**: 遅延シェーディングでは
「エリアライトの立体角積分」と「その物体固有の BRDF 評価」が**ライティングパスの中で同じ一つの
シェーダに同居する**。光源の形(球・円盤・位相で切り取られた三日月)を増やすたびに、
そのシェーダが持つマテリアル分岐と掛け算になって膨らむ。§1-5 / §1-6 で光源の種類を増やす
以上、この密結合は正面から効いてくる。

ライトプリパスは**照度(irradiance)という中間表現で両者を切る**:

- **ライティングパスは「その点にどの向きからどれだけ光が来ているか」だけを答える。**
  受け手が金属か、天体表面か、リングかを知らない。
- **レンダリングパスは「来た光をこの材質がどう返すか」だけを答える。**
  光源が球か三日板か、影がどう計算されたかを知らない。

これは §1-4 の `sunVisibility` を単一の問いにしたのと**同じ形の分離**である。あちらは
「遮蔽器の種類を受け手から隠す」、こちらは「光源の形を受け手から隠す」。

**トレードオフ(承知の上で採る)**:

| 項目 | 遅延シェーディング(2 パス) | ライトプリパス(3 パス) |
|---|---|---|
| ジオメトリを描く回数 | 1 回 | **2 回**(ドローコールが増える) |
| G-buffer の幅 | 広い(albedo + normal + rough/metal + viewZ) | **狭い**(normal + rough + depth。albedo を載せない) |
| マテリアルの多様性 | ライティングパスに分岐が集まる | **レンダリングパスへ分散でき、光源側と独立** |
| エリアライトの追加 | BRDF と混ざる | **ライティングパス内で閉じる** |
| 鏡面反射の正確さ | 完全 | **粗さ以外のマテリアル依存が近似になる**(下記) |

**既知の限界と対処**: 鏡面反射は本来「入射方向 × 視線方向 × 材質」に依存するので、
照度バッファ 1 枚には畳み込めない。標準的な対処は**粗さをジオメトリパスに書き、
ライティングパスがその粗さで LTC 積分した鏡面項を別バッファに出す**ことで、これで
「粗さ依存は正確、フレネル・金属色はレンダリングパス側」という分割になる。
本プロジェクトの絵(拡散反射が支配的な天体表面 + 少数の金属的な艦船)では
この近似の破綻は小さいと見込む。**破綻したら、艦船だけを前方描画へ逃がす**
(ドローコールは既に 2 回なので、逃がしても構成は壊れない)。

**器を先に作る**: エリアライトの具体的な実装(LTC、位相による切り取り、PCSS)は終盤でよい。
だが**そのとき 2 パス構成だと、載せる場所が無い**。したがって
**ライトプリパスの器は Phase 4 で先に作り、その時点では単一の平行光(現状と同じ絵)を通す。**
絵が変わらないことをもって器の正しさを確認し、エリアライトは後から光源の種類として足す。

### Phase 3 — HDR 線形パイプラインと露出基準

§1-1。**すべての後続フェーズの前提。**

1. HDR レンダーターゲット(`rgba16float`)へ描き、出力段で `toneMapping` を経て sRGB へ。
2. 露出基準を実装: `E(d) = SOLAR_CONSTANT * (AU/d)^2` を一次基準とし、`exposure` を手動で持つ。
   自動露出は後回し。`SOLAR_PRESSURE_1AU` を `SOLAR_CONSTANT / c` から導出する形へ統一。
3. **101 天体のアルベドを入れる。** 現在の 16 進直書き色(63 種)を、幾何アルベド + 色度へ置き換える。
   **本フェーズ最大の実作業。** 出典をコメントに残す(`RingOpticsDef` の帯コメントが手本)。
   **§1-6 により、この値は「表面の見え方」ではなく「他の物体を照らす光源の強さ」でもある。**
   Phase 8 の地球照はここで入れた値をそのまま光源強度として使う。
4. `Billboard` をノードマテリアル化し、1 を超える輝度を出せるようにする。
   `opacity` による明るさ表現をやめる。太陽・惑星輝点は等級 → 放射照度へ置き換える。
5. `RADIANCE_SCALE = 0.72`(`ring.ts:30`)を 1.0 にする。
6. 砲身赤熱を機体温度 + `STEFAN_BOLTZMANN` + `HULL_EMISS` の黒体放射へ置き換える。
7. 手調整値(`NIGHT_AMBIENT`、`SUN_INTENSITY`、各エフェクトの opacity、`ZOOM_MUZZLE_FLASH_SCALE`)は
   **温存せず捨てる。**

**完了条件**: リングの `RADIANCE_SCALE` が消える。ズーム時のマズルフラッシュ減光(`0.02`)のような
LDR クリップ回避のための係数が不要になる。露出を 1 段変えると全体が一様に明るく/暗くなる。

### Phase 4 — ライトプリパス基盤の導入

§1-7。**このフェーズの目的は絵を変えることではなく、器を作ることである。**
エリアライト(Phase 8)は器が無いと載せられないので、序盤に置く。

```text
Phase A  render/gbuffer.ts        深度 + 法線(oct符号化, rg16float) + 粗さ(r8unorm)
Phase B  render/light-prepass.ts  拡散照度 (rgb16float) + 鏡面照度 (rgba16float)
Phase C  render/material-pass.ts  ジオメトリ再描画。照度を読み、アルベド/金属性を掛ける
```

1. 上記 3 パスを組み、**光源は現状と同じ単一平行光 1 個だけを通す。**
   `AmbientLight` も現状の定数のまま残す(Phase 8 で地球照に置き換わる)。
2. **絵が Phase 3 の時点と一致することを完了判定にする。** 器の正しさは「何も変わらない」ことで確かめる。
3. 艦船の `MeshStandardMaterial` と天体の自前 Lambert が**Phase C で 1 つの BRDF に統合される**。
   `NIGHT_AMBIENT = 0.04` の天体別複製が消える。
4. 遮蔽の問い合わせ口 `sunVisibility(worldPos, normal)`(§1-4)を Phase B に置く。
   **中身は当面 `environment-scene.ts:147-148` の現行スカラ変調を移設しただけでよい。**
   Phase 7 でこの関数の中身だけが差し替わる。
5. `earth.ts` の地表シェーダを分解: BRDF 部分は Phase A/C へ、もや(`:67-71`)・夕焼け(`:59-64`)は
   Phase 10 の大気パスへ移すため**一旦そのまま残す**。
6. **鏡面の近似の限界を実測する**(§1-7)。艦船の金属表現が破綻するようなら、
   艦船だけ前方描画へ逃がす経路を用意しておく。

**なぜ線形深度を別チャンネルに持つか**: 戦闘カメラの near/far 比は 3e7。24bit ハードウェア深度からの
位置復元は遠方で桁落ちする。深度バッファは可視性判定にのみ使い、シェーディング用の深度は
線形値を別チャンネルに書く。**Phase 5 のカスケード導入後は比が縮むので、この判断は見直す。**

**完了条件**: 3 パス構成で Phase 3 と同じ絵が出る。光源を 1 個増やすのに
レンダリングパスのシェーダを触らなくてよい。天体を 1 つ追加してもシェーダコードが増えない。

### Phase 7 — 遮蔽の統一 + ソフトシャドウ

§1-4 + §1-5。**Phase 6 に依存する**(圧縮下では「真の方向 × 偽の位置」が解消しないため)。

1. **`physics/shadow.ts` の `sunlitFactor` を全天体へ一般化し、同時に円錐影(本影 + 半影)へ置き換える。**
   地球固定の円柱影をやめ、`Attractor[]` を取る形にする。太陽の視半径から半影幅を導き、
   `SHADOW_PENUMBRA = 6e4` の直書きを消す(§1-5)。
   これは描画以前に**物理の欠陥修正**であり、ラジエータ・電力・SRP の 4 消費者がそのまま恩恵を受ける。
2. 解析遮蔽を CPU/GPU 共通の 1 モデルへ集約。`ringPlanetShadow`(未使用の CPU 版)と
   `inBodyShadow`(TSL 版、**二値なので半影へ**)の二重実装を解消する。
3. `celestial-surface.ts:63-91` の**固定長 32 バンド uniform 配列を廃止**し、
   遮蔽器リストとして引く形にする。バンド数の上限をシェーダから追い出す。
4. Phase 4 で置いた `sunVisibility(worldPos, normal)` の中身を、上記の解析遮蔽器へ差し替える。
   **呼び出し側は一切変わらない**のが Phase 4 で器を先に作った狙い。
5. 艦・デブリ・基地のシャドウマップを遮蔽器の 3 種目として追加。**CSM 3 枚 + PCSS**
   (10 m 〜 30 km。フィルタ半径は太陽の角半径 4.65 mrad から導く — チューニング値ではない)。
   `castShadow` / `receiveShadow` は現状 0 件なので新規。
   **Phase 4 で BRDF が統合済みなので、第二版で懸念していた「CSM と `MeshStandardMaterial` の
   経路差による二重管理」は発生しない**(v2 §6 の未決事項はこの順序変更で解消)。

**完了条件**: 月の影に入るとラジエータの熱入力・電力・SRP・見た目が同時に落ちる。
艦が自分の構造で影を落とし、その影の縁が距離に応じてぼける。
リング影のバンド数上限がシェーダから消える。同じ遮蔽現象について CPU と GPU に別実装が無い。

### Phase 8 — エリアライト(太陽 + 地球照)

§1-5 + §1-6。**Phase 4 の器と Phase 7 の遮蔽が前提。**
第三版で追加された表現目標の本体であり、**変更は Phase B(ライティングパス)の中に閉じる。**

1. **LTC(Linearly Transformed Cosines)による球光源の積分**を Phase B に実装。
   拡散項と鏡面項を照度バッファへ出す。**太陽と地球照は同じコードを通る**
   — 前者は「小さくて強い」、後者は「大きくて弱い」という違いしかない。
2. **太陽**: 角半径 4.65 mrad(1 AU)を距離から導出。Phase 7 の半影と整合させる
   (同じ角半径から、シャドウマップのフィルタ半径と LTC の光源サイズの両方が出る)。
3. **地球照**: 各天体を球光源として生成。強さは Phase 3 で入れたアルベド × その天体が受ける
   放射照度。**太陽方向による位相の切り取り**(昼側だけが光る)を入れる。
   可視率は Phase 7 の遮蔽基盤を共有(光源天体自身が影に入っていれば光らない)。
4. **光源天体は近い順に 1〜2 個で足りる。** 立体角が距離の 2 乗で落ちるので、
   打ち切りの基準は距離ではなく立体角の閾値にする(§1-6 の表)。
5. `AmbientLight(0x8899bb, 0.25)` を削除。地球照が置き換える(§3-1)。
6. 色を持つ光源として扱う。艦の影側が地球の色を帯びることを検証ケースにする。

**完了条件**: LEO で艦の地球を向いた面と宇宙を向いた面の明るさが桁で違う。
高度を上げていくと地球照が滑らかに弱まり、月軌道では点光源と区別がつかなくなる。
新月側(地球が三日月形に見える位置)で地球照が弱く色付く。
`AmbientLight` が src から消える。

### Phase 9 — 半透明パスの統合

不透明の深度を読む前方描画パス。`renderOrder`(§3-3)を規約へ置き換える。

1. `render/transparent-pass.ts`: 不透明カスケード解決後に描画。`viewportDepthTexture` / `linearDepth`。
2. 「視線に沿って不透明面までメディアを積分する」共通ヘルパ。**大気・オーロラ・プルーム・リングが
   これを共有するのが本フェーズの目的。**
3. `earth.ts:86-124` の大気リム球を廃止 — `depthTest:false` + 自前球交差の回避策が不要になる。
4. `aurora.ts` の CPU 頂点更新(`:66-107`)を GPU へ。
5. `depthTest: false` の 3 箇所を規約内へ回収する。
6. **`LINE_RENDER_ORDER` を `render/` へ移し、線以外の半透明物(ビルボード・大気リム・オーロラ・リング)を
   同じ表へ統合する。** 値 5 の衝突(予測線 vs `Billboard` 既定)はこの統合で解消する。
7. 加算合成の上限は Phase 3 の露出基準に従う。

**完了条件**: 半透明が不透明面に正しく遮蔽される。`renderOrder` が規約化された少数の値へ収束。

### Phase 10 — 大気散乱(指数密度)

`EARTH_MOON_GRAPHICS_PROPOSAL.md` の「大気パス」(Bruneton型LUT)と整合させる。

1. 透過・単散乱・多重散乱近似を LUT 化(オフライン生成も可)。カメラが大気圏内外どちらでも同じモデル。
2. Phase 9 のレイ積分枠組みへ載せ、エアリアルパースペクティブを不透明深度に対して積分。
   `earth.ts:67-71` のもや(`ATMO_HAZE_TAU0 = 0.34`)を置換。
3. 夕焼けを光路長から導出し、`vec3(1,0.4,0.1)` の固定補間(`:59-64`)を削除。
4. 雲は当面 Phase 4 の Phase C 内 2 層サンプリング。太陽方向に追従する雲影で
   `earth.ts:55-56` の UV ずらしを置換。**太陽が面光源なので、雲影の縁も半影を持つ**(§1-5)。

### Phase 11 — ポストエフェクト

1. 露出 → ブルーム(`bloom` ノード)→ レンズフレア/グレア → トーンマッピング → sRGB。
2. ブルーム対象は Phase 3 で HDR 化済みの発光体(太陽・噴射・撃破フラッシュ・マズルフラッシュ・
   再突入プラズマ・惑星輝点)。**再突入プラズマは既に動圧という物理量から強度を引いている**
   (`REENTRY_GLOW_MIN_Q` / `_FULL_Q`)ので、HDR 化の妥当性を検証する基準ケースに使える。
3. TAA/SSAA は Phase 2 のトグル配下で任意。AO は優先度低。

### Phase 12 — ボリュームレンダリング

Phase 9 のレイ積分枠組みが前提。プルーム・RCS・再突入・オーロラを板ポリゴンから参加媒質へ。
手調整の size/opacity 式が密度分布へ置き換わる。

「何 px だから点で描く」「`renderOrder` は 3」「色は `0x9a8a7a`」は `render/` の判断。
そして `render/` は ECI を受け取らない — 位置は `THREE.Vector3`(描画座標)で渡る。

## 7. 最初の一歩

**Phase 0 から着手する。** グラフィックの構成を触る前に、描画負荷を下げる。
後続フェーズはすべて負荷を増やす方向なので、土台を軽くしてから積む。

着手順:

1. `perf-meter.ts` にドローコール数・三角形数を出す(Phase 2 から前借り。効果を測れないと LOD は入れられない)。
2. **地球の `SphereGeometry(R_EARTH, 1024, 768)` を距離依存の分割数へ。** 単体で最大のジオメトリ負荷。
3. 弾・薬莢・デブリのインスタンシング。ドローコール数で最大。

Phase 0 は他のどのフェーズにも依存せず、他のどのフェーズもここでの決定に縛られない
(唯一、Phase 1 の「表示 LOD ポリシーは `render/` に残す」方針と揃えること)。

Phase 3 のアルベド調査は他フェーズと独立に進められるので、Phase 0/1/2 と並行して始めてよい。
**第三版ではこの調査が Phase 8(地球照)の前提でもあるため、早く始めるほど効く。**

Phase 2 の冒頭でデッドコード 3 系統を消す(§3-5)。

対象を取り違える。
