# レンズエフェクト

**前提は [`pipeline.md`](pipeline.md)。** とくに §1-5(明るさの目盛り)。
出力段(`render-pipeline.ts`)の中身が担当範囲。

**露出は範囲外**(現状は [`pipeline.md`](pipeline.md) §1-6、残件は
[`exposure_backlog.md`](exposure_backlog.md))。ここが持つのはレンズ由来の像だけで、
**どちらを先に着手してもよい** — 理由は §1 の末尾。

---

## 1. 順序

```text
露出 → ブルーム → レンズフレア/グレア → トーンマッピング → sRGB
```

**ブルームは最小限。** グローの代用にしない — **グローは大気散乱として実装する**
([`atmosphere.md`](atmosphere.md))。ここが持つのは**レンズ由来のもの**だけで、
**由来で分ける。**

対象は HDR 化済みの発光体。**再突入プラズマは既に動圧という物理量から強度を引いている**
(`REENTRY_GLOW_MIN_Q` / `_FULL_Q`)ので、検証の基準ケースに使える。

**レンズ効果を線形演算に保つ限り、この並びの中で露出とレンズの前後は入れ替えても同じ絵になる**
(`L(e·x) = e·L(x)`)。だから露出とレンズはどちらを先に着手してもよく、**片方が他方を
作り直させることはない。** 閾値(ニー)を1つでも入れた瞬間、この性質は失われる。

---

## 2. レンズ効果 — 何が欲しいか

**欲しいのはグレア(滲み)・スミア(条)・ゴースト。** どれも実在のレンズ/センサに由来する像で
あって、大気やボリュームの発光とは別物。

- **グレア**: 明るい点の周りの淡いハロー。**広がりは画面上の角度で決まる**(目やレンズの応答なので、
  光源が遠いほど狭くなることはない)。
- **スミア**: 極端に明るい点から伸びる放射状の条。**向きは画面に固定**され、光源に貼り付いて
  回ることはない。
- **ゴースト**: 絞りの反射像。画面中心を挟んだ反対側へ淡く色づいた像を落とす。

**これらは光を増やさない。** レンズへ入った光を画面の中で配り直したものなので、
**滲んだぶんだけ元の光点は暗くなる。**

いま太陽が持っている「実半径の 12.3 倍の板に貼ったグロー」は、**由来で分ければレンズ側のもの**
(仕様も「肉眼で見た太陽が視直径そのものより大きく滲む」と書いている)。しかも
**広がりが太陽の実半径に比例して縮む**ので、角度で決まるべき応答としては向きが逆。
**レンズ段が引き取って廃止するのが筋。**

## 3. 太陽が 1px を切る問題

**本作では、遠くから見た太陽が極めて小さな点として描かれうる。**

| 太陽までの距離 | 戦闘視点(55°/1080px)での見かけ径 | `render-lab`(50°/540px)での見かけ径 |
| --- | --- | --- |
| 1 AU | 10.5 px | 5.8 px |
| 5.2 AU(木星) | 2.0 px | 1.1 px |
| 9.6 AU(土星) | 1.1 px | 0.60 px |
| 30 AU(海王星) | 0.35 px | 0.19 px |

ガンサイトズーム(6°)では 9 倍細かくなるので、ちらつく距離もそのぶん遠のく。

### 3-1. 何が起きるか

太陽面の表示値は **4.62e4**(= (AU/R_sun)²)で、画面の白の 4 万倍以上ある。
見かけ径が 1px を切ると、その巨大な値が**乗るか乗らないか**でしか画面に入らない。
4 サンプルの MSAA を掛けても被覆率が 1/4 刻みに量子化されるだけで、
**30 AU では「0」と「4.62e4 の 1/4」を往復する** — サブピクセルの移動に対して総光量が
0 と 2.6 倍(真値比)の間を跳ぶ。

### 3-2. レンズ効果はこの問題を隠さない、**広げる**

**「大気やブルームで既に広がっているから分岐は要らない」は成り立たない。**
広がっているのは**出力**であって、レンズ段の**入力**である太陽の画素値は広がっていない。
しかもレンズ段は線形なので、入力の変動をそのまま出力の変動として運ぶ。

いまは芯の画素がトーンマッピングで白に張り付いていて、**ちらつきが飽和の中に隠れている。**
グレアを入れると、同じ変動が**飽和していないハローの明るさとして画面の広い範囲に出る。**
つまりレンズ効果は、この問題を**見えるようにする側**である。

### 3-3. 論点1 — 効果が二重に掛かることをどう防ぐか

**レンズ段を線形に保てば、防ぐ必要そのものが消える。**

`out = (1−w)·I + w·(K∗I)` の形(K は総和 1 の核)なら、`I = I_太陽 + I_その他` を
分けて計算した結果は分けない結果と厳密に一致する。だから将来「太陽だけ解析合成へ切り出す」を
やるときも、**太陽をバッファから抜いて、抜いたぶんを解析で足し直すだけ**で済み、
他の画素の絵は 1 ビットも変わらない。

- **バッファを分ける必要も、描画順を組み替える必要も、いまは無い。**
- **必要になったときに要る拡張性は 2 つだけ**: レンズ段が線形であることと、太陽が world パスの
  単独の描画物であること(いまも成立している)。
- **閾値(ニー)を 1 つ入れた瞬間にこれが崩れる。** 太陽を抜いた途端、他の物の滲み方まで
  変わってしまう。**閾値を持たないことが、この問題に対する唯一の拡張性の担保。**

### 3-4. 論点2 — つなぎ目で絵が飛ばないようにするには

**両方式が同じ総光量と同じ核を名乗るなら、つなぎ目は原理的に飛ばない。**
飛ぶのは「解析側とラスタ側で明るさの根拠が違う」ときだけ。したがって
**どのサイズで切るかは自由度が高く、そこを詰めるのは本質ではない。**

揃えるなら **2px** — 全天体が既に「見かけ直径 2px 未満では球として描かない」で切っていて、
惑星はそこで輝点へ丸ごと入れ替わる。**太陽だけがこの規則の外にいる**(実装は距離によらず球を
描き続ける)。「常に太陽だけ別方式」も選べるが、そちらは論点4を全距離で自前で解く必要が出る。

### 3-5. 論点3 — 「太陽が小さい」をどう判定するか

**見かけ径では判定しない。**

判定したいのは「ラスタライズが総光量をどれだけ取りこぼすか」であって、それは
**サブピクセル移動に対する画面の総光量の変動**として直接測れる(測り方は実装計画の手順2)。
分岐を作るときの**実行時の条件**は連続量(見かけ径)でよい。**分岐が要るかどうかの判断**は
実測でやる。

### 3-6. 論点4 — 小さな太陽が遮蔽されずに見えることをどう判定するか

**既に答えがある。** 「描画座標の任意の点へ届く恒星光の透過率」を返す関数が 1 本あり
(`pipeline.md` §1-4 の遮蔽の合成規約)、**カメラ位置でそれを評価すればよい。**
天体の球・環の帯・メッシュの影マップが全部同じ規約で効き、半影ぶん連続に変化するので
**遮蔽の判定自体はちらつかない。**

深度バッファを 1 テクセル読む方式は採らない — サブピクセルの太陽に対しては二値でちらつき、
問題を別の場所へ移すだけになる。

### 3-7. いまの立場と、分岐が要ると分かったときの候補

**いまの立場: 分岐は作らない。** まず線形のフラグメント方式を入れ、4-5 の測り方で実測してから
決める。**論点1〜4 はどれも「作る前に決めなければならないこと」ではない**ことが上で片付いた。

分岐が要ると分かったときの候補(優先順):

- **(a) 太陽の点像に角度の下限を与える。** 惑星の輝点(星殻上の固定角の板・全天体一律の表示応答)と
  同じ扱いへ寄せる。滲みの広がりは目/レンズの応答であって光源の大きさではないので、
  **太陽だけが実半径比例で縮んでいる現状のほうが物理的におかしい。**
  実体/輝点の切り替えは全天体が既に 2px で持っている。
  **これはレンズ段の分岐ではなく光源側の表現の切り替えなので、論点1〜4 のどれも発生しない。**
- **(b) 太陽だけ解析合成する。** 論点1〜4 を全部引き受ける。(a) で足りなかったときだけ。
- **(c) SSAA を上げる。** 4 倍でも量子化が 1/16 になるだけで、0.19px の太陽には効かない。**却下。**

# 実装計画 — フラグメントのみのレンズ効果

## 目的

**§2 のレンズ効果を、画面バッファだけを読むフラグメント方式で出力段へ入れる。**
そのうえで **§3-5 の測り方で太陽のちらつきを実測し、解析合成の分岐(§3-7 (b))が要るかどうかを
数値で決められる状態にする。**

**露出は範囲外**(§1 冒頭)。レンズ段が線形である限り、既に入っている露出がレンズを
作り直させることは無い(§1 末尾)。

## 決めたこと

**どれもユーザーが覆せる。覆されたときにどの手順が変わるかを併記する。**

1. **レンズ効果は線形演算にする。閾値(ニー)を持たない。**
   根拠は §3-3 — 将来の分岐に対する拡張性がこれ 1 つに掛かっている。副次的に、露出との順序が
   自由になる。**覆すなら手順3が変わり、§3-3 の結論も無効になる。**
2. **合成は加算ではなく配り直し** — `out = mix(base, K∗base, w)`、`K` は総和 1 の核、
   `w` はレンズが本来の道から外す光の割合。総光量が保存されるので、解析側とラスタ側が
   同じ量を名乗れる(§3-4)。**覆すなら手順3・4・5 の合成式と、各手順の「較正が動かない
   こと」の検証が変わる。**
3. **太陽の 3D グロービルボードは、レンズ段が引き取って廃止する。**
   根拠は §2 末尾。**残すなら滲みが二重に掛かる。** 覆すなら手順3の `stars.ts` /
   `sun-view.ts` の変更と、手順1の仕様の 1 文が変わる。
   なお **1 AU での見た目の規模はほぼ変わらない** — 現状のグローは幅 129px でほぼ全面が
   白に飽和しており、`w = 0.03` のグレアが作る飽和域は半径 53px(幅 106px)。
4. **解析合成の分岐(§3-7 (b))はこの計画では作らない。** 拡張余地は「線形であること」と
   「太陽が world パスの単独の描画物であること」の 2 つで確保し、仕様の「未確定の案」へ
   1 行だけ残す。
5. **判断の指標は「太陽の見かけ径」ではなく、サブピクセル移動に対する画面平均輝度の変動。**
   閾値は **1/255(表示の 1 LSB)** — これを超えたら目に見える。

## 達成目標

- 戦闘視点で太陽・爆発・噴射炎の周りに滲みと条とゴーストが出る。描画品質設定でオフにすると
  絵から消える。
- デバッグ表示で「レンズ」を選ぶと、配り直された光だけが単独で出る。
- 負荷計測に「レンズ」の行が出て、0 でない値を持つ。
- **較正が動いていない** — `albedo` ケースの最も明るい画素が sRGB (241, 231, 215)、
  `saturn` ケースの環と本体の比が 0.20(どちらも ±1 LSB)。
- **太陽を 1 AU / 5.2 AU / 30 AU に置いた 3 ケース × サブピクセル 4 位相の平均輝度が、
  レンズ導入の前後それぞれについて表になっている。**
- **その数値に基づく「分岐が要るか」の判断が §3-7 へ書かれている。**
- `npm run typecheck` / `npm run test:physics` / `npm run build` が通る。

### 手順2. `render-lab` に太陽を出し、**レンズ以前**のちらつきを測る

**目的**: 以降の手順はどれも「太陽が写った絵」を見ないと判断できないが、いま `render-lab` には
太陽の球もグローも無い(恒星は向きと放射照度だけ)。見る場所を作り、同時に**比較の基準になる
現状の数値**を取る。**この時点で絵の出方は変えない。**

**変更が必要な箇所**

| ファイル | すること |
| --- | --- |
| `tools/render-lab/cases.ts` | `LabCase` へ `sunDistance?: number` を足す(既定は 1 AU)。恒星の置き場所とそこから引かれる放射照度を 1 つの数から出すため |
| 同 | `sun-1au` / `sun-5au` / `sun-30au` の 3 ケースを足し、`CASES` の表へ追記する |
| `tools/render-lab/lab.ts` の `render()` | `SUN_POSITION` の距離を `AU` 固定から `this.current.sunDistance ?? AU` へ |

**ケースの組み方**(3 ケース共通、距離だけが違う)

- `createSun()` の球とグローを距離 d に置く。球のスケールは実半径 `R_SUN`。
- **太陽を画面中心から外して置く** — 中心に置くとカメラ方位を回しても画面上で動かず
  (`camera.lookAt(pivot)` が中心へ固定する)、サブピクセル移動が作れない。
- **手前 10m に艦を 1 隻置き、`viewTarget` をその艦にする。** カメラはこの近点を軸に回るので、
  遠くの太陽は方位の変化ぶんそのまま画面上を動く。艦の縁で太陽が隠れる様子も同じ絵で読める。
- グローのビルボードは `saturn` ケースの `RingView.sync` と同じく**組み立て時に 1 回だけ**
  ケースのカメラへ正対させる。測定で使う回転は 0.1° 未満なので、正対のずれは効かない。

**測り方**(一時スクリプト。`tools/chrome-session.mjs` を使い、**scratchpad に置いて commit しない**)

`window.renderLab` は既に `shoot` / `setView` / `capture` を公開している。ケースを出してから
位相をずらして撮り、ページ側で平均輝度を数える:

```js
// カメラは -Z を向いているので既定の方位は 0。50°/540px = 0.0926 °/px の 1/4 ずつずらす。
(async () => {
  const out = [];
  for (let k = 0; k < 4; k++) {
    window.renderLab.setView({ cameraAzimuthDeg: k * 0.0926 / 4 });
    const url = await window.renderLab.capture();
    const img = new Image(); img.src = url; await img.decode();
    const c = document.createElement('canvas'); c.width = 960; c.height = 540;
    const g = c.getContext('2d'); g.drawImage(img, 0, 0);
    const d = g.getImageData(0, 0, 960, 540).data;
    let all = 0, dim = 0, dimCount = 0;
    for (let i = 0; i < d.length; i += 4) {
      const y = 0.2126 * d[i] + 0.7152 * d[i + 1] + 0.0722 * d[i + 2];
      all += y;
      if (y < 250) { dim += y; dimCount++; }   // 飽和した芯を除いた平均も要る
    }
    out.push([all / (960 * 540), dim / dimCount]);
  }
  return out;
})()
```

**達成条件と検証**

- `npm run render-lab:shot` が通り、`.render-lab/shots/sun-1au.png` / `sun-5au.png` /
  `sun-30au.png` の 3 枚に太陽が写っている。
- 3 ケース × 4 位相の「全画素平均」「飽和を除く平均」が §3 の下へ表として書かれている。
- `npm run typecheck`。

**予測**(外れたら測り方を疑う): 30 AU では位相によって太陽の画素が出たり消えたりする。
ただし**この時点では全画素平均の差は 1/255 に届かないはず** — 変動が飽和した芯の中に
隠れているため(§3-2)。届いていたら、レンズ以前に既に見えるちらつきがあることになる。

### 手順3. レンズ段(滲み)を出力段へ入れる

**目的**: フラグメント方式のレンズ効果の本体。明るい画素の光を、画面上の角度で決まる広がりへ
配り直す。あわせて、由来が重複する太陽のグロービルボードを廃止する(決めたこと 3)。

**変更が必要な箇所**

| ファイル | すること |
| --- | --- |
| `src/render/pipeline/lens-pass.ts`(新規) | 半解像度から 5 段の縮小チェーンと、加算しながら戻る拡大チェーンを持ち、**半解像度 1 枚(`K∗base`)**を出す。ターゲットは `HalfFloatType` / `depthBuffer: false` |
| `src/render/pipeline/render-pipeline.ts` | world パスの後・composite の前でレンズ段を回す。`compositeMaterials` は `DebugTargetId` で引く表のまま残し、**レンズ有りの通常表示だけを別フィールドで 1 枚持つ**。`render()` の末尾で `debugTarget === 'off'` かつトグルが真のときだけそちらを選ぶ。`applyGraphics` でトグルを受ける。`setSize` と `dispose` を配線する |
| 同 `PIPELINE_GRAPHICS_KEYS` | `lens` を足す(描画テスト環境から切り替えられるようにするため) |
| `src/gpu-timings.ts` | `GPU_PASS` へ `lens`(`composite` / `overlay` を 1 つ後ろへ)、`GPU_PASS_LABELS` へ「レンズ」。**`resolve()` の `elapsedMs[pass] = duration` を `+=` にする** — レンズ段は 1 パスで 9 回 `render()` を呼ぶので、いまのままでは最後の 1 回しか記録されない |
| `src/render/pipeline/debug-target.ts` | `lens` を `DebugTargetId` と `DEBUG_TARGETS`(ラベル「レンズ」)へ足す |
| `src/render/graphics-settings.ts` | `lens` トグル(`group: 'element'`、ラベル「レンズ効果」、presets low:false / medium:true / high:true) |
| `src/render/stars.ts` | `createSun()` からビルボードを外し、`STAR_GLOW_SIZE_RATIO` / `SUN_GLOW_RADIANCE` を消す(他に参照は無い) |
| `src/game/celestial/sun-view.ts` | グローの同期・表示切り替え・破棄を消す。`cameraSystem.overviewMode` の分岐もこれで消える |
| `tools/render-lab/cases.ts` | 手順2で置いたグローの `sync` 呼び出しを消す |

**縛るのはこの 3 点だけで、残りは実装の裁量**

- **線形**。閾値・ニー・トーンマップ前の切り落としを持たない。
- **配り直し**: `out = mix(base, K∗base, w)`。`K` は総和 1(係数の直書きではなく**正規化で**
  保証する)。`w` はレンズが本来の道から外す光の割合で、実在のレンズの veiling glare が
  1〜3% であることから **0.03**。
- 広がりは**画面上の角度**で決まる(縮小段数を解像度に対して固定にすれば自然にそうなる)。

**踏む地雷**

- **模式図スタイルではレンズ段を呼ばない。** マテリアル/大気/world を通らないので入力が無い。
- **half float の上限は 65504 で、太陽面の 4.62e4 はすぐ隣。** 重みの和が 1 を超える畳み込みを
  当てると Inf になり、`mix` を通って画面全体が NaN(真っ白か真っ黒)になる。**無音で壊れる。**
- 共有 HDR ターゲットは `antialias` のとき 4 サンプルの MSAA。読み出しは three が解決するので
  そのまま `texture()` で読めるが、**`antialias` オン/オフの両方で確かめる。**
- レンズの出力は半解像度なので、合成側は `screenUV` で線形補間して読む(ぼけた像なので
  それで足りる)。

**達成条件と検証**

- `npm run typecheck`。
- `npm run render-lab:shot` の `sun-1au.png` で太陽の周りに滲みが出ている。
- **`leo.png` の艦のハイライトには目に見える滲みが出ない** — 閾値を持たないのに暗いものが
  滲まないことの確認(表示値 20・面積 4px² のハイライトを半径 30px へ配ると 1e-3 の桁)。
- `albedo.png` の最も明るい画素が sRGB (241, 231, 215) のまま(±1 LSB)。
- `render-lab` の描画設定で「レンズ効果」をオフにすると滲みが消える。
- デバッグ表示「レンズ」で配り直された光だけが出る。
- `render-lab` の計測に「レンズ」の行が出て 0 でない。**`+=` への変更前後で値が変わることを
  確かめる**(変わらないなら計測が結び付いていない)。
- 模式図スタイルへ切り替えて `leo` が白背景の輪郭図のままであること。

### 手順4. 条(スミア)

### 手順6. ちらつきを測り直し、分岐の要否を判断する

**目的**: この計画の本題。**フラグメントのみのレンズ効果を入れた状態で、仕様の要求
(「1ピクセルを切った光点の滲みがちらついたり消えたりしてはならない」)を満たすかを測って
決める。**

**やること**

1. 手順2と同じ一時スクリプトで、3 ケース × 4 位相を測り直す。
2. 位相間の差(全画素平均・飽和を除く平均のそれぞれ)が **1/255** を超えるケースを列挙する。
3. 超えていたら **§3-7 の候補から選び、選んだ理由と測った数値を §3-7 へ書く。**
   **実施はこの計画に含めない**(別の計画になる)。
4. 超えていなければ、その旨と数値を §3-7 へ書く。**分岐は作らない。**
5. 手順2の基準値(レンズ以前)と並べて表にする。**グロービルボードを外したぶんの悪化と、
   レンズ段が広げたぶんの悪化を分けて読む。**

**達成条件と検証**

- §3 の下に、レンズ導入前後 × 3 ケース × 4 位相の表がある。
- §3-7 の「いまの立場」が、測った数値を根拠にした 1 文へ書き換わっている。
- **main へ送るので、変更箇所によらず全部回す**: `npm run typecheck` /
  `npm run test:physics` / `npm run build`。

## 見積り

**GPU** — 1920×1080・rgba16f(8 B/px)で、レンズ段が読み書きするバイト数から:

| 内訳 | バイト数 |
| --- | --- |
| 縮小 5 段(全解像度読み 16.6MB + 半解像度書き 4.1MB、以降 1/4 ずつ) | 約 27 MB |
| 拡大 4 段(各段で下地読み + 書き) | 約 15 MB |
| 条(1/4 解像度の読み書き) | 約 4 MB |
| ゴースト(1/8 解像度) | 約 1 MB |
| 合成が半解像度のレンズを追加で読む | 4.1 MB |

合計 **約 51 MB/frame**。帯域 100 GB/s なら 0.51ms、200 GB/s なら 0.26ms。
**既存の world パスが 2.6ms なので、この見積りなら受け入れられる。**
実測は `render-lab` の計測が出す「レンズ」の行で置き換える。

**CPU** — `renderer.render()` の呼び出しが 11 回増える(縮小 5・拡大 4・条 1・ゴースト 1)。
**1 回あたりの発行コストの手持ちの実測が無いので、これは見積れない。** 手順3の前後で
`render-lab` の `cpuRenderMs` を比べて実測へ置き換える。**0.5ms を超えたら縮小段数を 5→4 へ
落とす**(広がりの上限が半分になるだけで、他の設計は変わらない)。

**滲みの規模**(`w = 0.03`、1/r² の広がりを 1〜1000px で正規化した粗い見積り):
1 AU の太陽(表示値 4.62e4・面積 86.6px²)が配る光は 1.2e5 で、半径 53px までが表示値 1 を
超える = 白に飽和する。**現状のグロー(幅 129px・表示値 240)とほぼ同じ規模**なので、
1 AU での見た目は大きく変わらない。
