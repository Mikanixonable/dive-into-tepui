# 影の残件処理 — 自己影が出ない原因の究明と、描画テスト環境の作り直し

**この文書のコード上の事実・行番号は、リビジョン `87467a4b`(main を取り込んだ後)時点で確認した
もの。** 描画の作業手順は `/rendering-workflow`、仕様の書き方は `DEVELOP/SPEC/README.md` が正本。

---

## 目的

3 つある。

1. **`render-lab` の `leo` で自機の自己影が確認できない原因を特定し、直す。** タンパク質の
   `5i4r-molecular-1` では自己影が見えるので、シャドウアトラスの経路そのものは動いている。
   艦だけが出ない理由を切り分ける。
2. **`render-lab` を「2 経路の絵を保つ器」から「1 経路の絵を読む器」へ作り替える。** 絵を保つ
   段階は終わっているのでフォワード経路との比較を落とし、代わりにゲーム本体と同じ中間バッファの
   デバッグ表示を載せ、スロットの適応割り当てを目で読めるケースを足す。
3. **影まわりに残った二重評価・二重実装を落とす。** 大気パスが遮蔽度を画面全体で 2 回計算し
   直していること、ライト空間の深度マップを撮る機構が 2 つあること。

## 決めたこと

**ユーザーはここを覆せる。覆したときにどの手順が変わるかまで書く。**

### 1. 自己影が見えない原因は 2 系統あると見て、両方に手を打つ

**構図の側。** `tools/render-lab/cases.ts:44` の `SUN_DIR = (1, 0.35, 0.5).normalize()` は z
成分が正で、ケースのカメラは原点から −Z を見る(`cases.ts:59-60`)。つまり **全ケースで太陽は
カメラの背後にある。** 順光で照らされた艦は、自己影が落ちる面がすべてカメラの裏を向くので、
影が正しく出ていても画面には現れない。`5i4r-molecular-1` で見えるのは、球の集合はどの向きから
照らしても手前の球が奥の球へ影を落とすため — **種別で分岐しているのではなく、形と光の向きの差。**

なお `5i4r-molecular-1` には半透明外殻が無い(外殻を持つのはシルエット表現だけで、
`src/render/protein-silhouette-view.ts:89` でだけ外殻の印が付く)。**そこで見えている影は外殻の
ものではなく、`phase_6_7.md` の作業で足したシャドウアトラスそのものの結果である。**

**実装の側。** 影パスはフレームの先頭で走り(`src/render/pipeline/render-pipeline.ts:200-205`)、
そこで `Box3.expandByObject` が遮蔽器の箱を作る。`expandByObject` は `updateWorldMatrix(false,
false)` しか呼ばない — **親の変換は更新しない。** そのフレームでまだ誰も `updateMatrixWorld` を
呼んでいない時点では、親グループの位置が抜けた箱になる。`render-lab` はケースを選ぶたびに
**1 フレームしか描かない**(`tools/render-lab/lab.ts:119` / `tools/render-lab/main.ts:30-31`)ので、
この誤った箱が常に採用される。

`leo` の自機は親グループの (0, −1, −10) が抜けて原点付近の箱になる。カメラは原点なので depth が
0 になり、`metersPerPixelAtDepth` の 1e-6 の床が効いて 1 texel = 1.7e-9 m と出る。塊はどの
スロット条件も満たさないまま 1 枚を占有し、ライトカメラは原点へ向く。実際に描く段では
`renderer.render` が行列を更新するので艦は 10 m 先に居り、**枠の外なので深度マップは空になる。**
受け手側の AABB も原点付近を指すので、そもそも引かれない。

**覆されたら**: 構図だけが原因だと判断するなら手順 8 が消える。実装だけだと判断するなら手順 6 の
斜光ケースが消える。

### 2. タンパク質の自己影パスは、コメントアウトではなく削除する

半透明外殻の自己影は `DEVELOP/SPEC/` のどこにも書かれていない。**未実装の仕様が残るのは正常な
状態だが、誰も意図していない機構がコードに残るのは正常ではない。** コメントアウトで残せば、次に
読む人は「意図の無い機能が、動かない形で置いてある」を読み解く羽目になる。**消したものは
git history が持っている。**

副産物として、次の 3 つが同時に片付く。

- 遮蔽源が球・環の帯・メッシュの 3 つに揃い、`OcclusionSources` から画面空間のマスクを前提と
  する項が消える。
- ライト空間の深度マップを撮る機構が 1 つになる(いまは正射カメラの箱合わせ・線形深度の
  マテリアル・視線と平行な up の回避が 2 か所に同じ形で書かれている)。
- 1024² の深度マップ 1 枚と画面サイズの受け手マスク 1 枚が返る(内訳は見積り)。

**見た目は変わる。** シルエット表現の内部リボンから外殻の影が消えて明るくなる。SPEC はこの影に
ついて何も述べていないので、消しても仕様から外れない。**SPEC を直す必要も無い。**

**覆されたら**: 手順 2 が「`RenderPipeline` から `ProteinShadowPass.render()` の呼び出しだけを
外し、クラスは残す」に縮む。その場合、機構の重複と `OcclusionSources.protein` は残る。

### 3. 大気の「もや」は遮蔽度を計算し直さず、遮蔽パスが書いた 1 枚を読む

大気パスは遮蔽関数を 2 回評価している。リム光が評価する大気シェル上の点は G バッファの画素位置とは
別の点なので計算し直すしかないが、**もやが評価する点は G バッファ深度から復元した位置そのもの** —
遮蔽パスが同じ点で同じ関数を評価した結果を、すぐ隣のバッファに持っている。

**絵は変わる。** もやにメッシュの影が乗るようになる。物理的にはそちらが正しい。

**覆されたら**: 手順 3 の前半が消える。後半(環の項を落とす)は独立して残る。

### 4. 遮蔽器の見かけの大きさは、枝の箱の対角ではなく「その枝が持つ単一個体の大きさ」で測る

影パスはシーン直下の枝を 1 遮蔽器として扱う。`InstancedPool` はシーン直下に 1 本の
`InstancedMesh` として居るので、**薬莢や破片が散らばるとプール全体が 1 個の巨大な遮蔽器になる。**
箱の対角で見かけの大きさを測ると、この雲が常に最大の遮蔽器として並びの先頭に来て、収まらない塊
として 1 スロットを占有し、さらにその箱と交差する艦をすべて棄却する。

**射撃後に薬莢が周囲に漂っている間、自機と敵艦の影が丸ごと消える。** これは推論であって実測では
ないが、経路は塞ぐ。あわせて、重なりによる棄却はやめて吸収へ倒す — 重なった塊の受け手は片方の
遮蔽器を取りこぼすが、遮蔽器を丸ごと捨てるよりは軽い壊れ方である。

**覆されたら**: 手順 7 が消える。薬莢・破片を遮蔽器から外す(`markSunShadowCaster` を呼ばない)
だけの手当てに置き換わる。

### 5. `render-lab` の撮影出力はケースあたり 1 枚にする

フォワード経路が消えるので、`<case>-prepass.png` / `<case>-forward.png` / `<case>-diff.png` の
3 枚組は `<case>.png` の 1 枚になる。計測のベースライン JSON も 2 経路の組から 1 本になるので、
`schemaVersion` を 2 へ上げて撮り直す。

**覆されたら**: 手順 1 でファイル名を `<case>-prepass.png` のまま据え置く。

### 6. 手順は「削る → 明らかな修正 → 掃除 → 基盤整備 → 原因究明」の順に並べる

消せるものを先に消し、絵を変えない掃除で密結合を落としてから切り分けに入る。**消える予定のコードと
二重実装が残ったまま壊れた影の原因を探すと、問題箇所の切り分けに失敗する。** したがって手順 4 の
掃除は、いま把握している逸脱だけでなく、**手順 1〜3 が新たに生んだ逸脱と死にコード**も対象にする。

代償として、**手順 5〜7 の検証では自己影がまだ絵に出ない** — 決めたこと 1 の実装側(ワールド行列)が
手順 8 まで残るためである。この 3 手順で読むのは「影」表示のスロットの中身であって、船体に落ちた
影ではない。**絵として確かめるのは手順 8 に集約する。**

**覆されたら**: 原因究明を先に片付けるなら、手順 5 と手順 8 を先頭へ移し、掃除が最後尾へ回る。
その場合、掃除の対象は手順 8 が触ったコードまで広がる。

`npm run render-lab` を開き、`saturn` で「遮蔽」を選ぶと環の影が濃淡として読めること。
`leo` で「影」を選び、**スロット 4 枚のうち何が写っているかを記録する** — これが手順 8 の
原因究明そのものになる。空(真っ白)なら決めたこと 1 の実装側、艦のシルエットが写っているなら
構図側が主因である。

---

### 手順 6. ケースごとの太陽方向を持てるようにし、自己影と複数スロットのケースを足す

**目的.** いまは全ケースで太陽がカメラの背後にあるため、自己影が落ちる面が常にカメラの裏を向く。
ケース単位で太陽方向を選べるようにし、**自己影を読むための斜光ケース**と、**スロットの適応割り当てを
読むための複数塊ケース**を足す。

**変更が必要な箇所.**

| ファイル | 何をするか |
| --- | --- |
| `tools/render-lab/cases.ts` | `LabCase` に太陽方向の任意項目を足す。新ケース 3 本を追加し `CASES` 表へ載せる — `ship-selfshadow`(艦 1 隻を斜光〜半逆光で、突起の影が船体に落ちる構図)、`ship-cluster`(艦 3〜4 隻を互いに離して置き、塊が複数になる構図)、`ship-in-debris`(`ship-selfshadow` と同じ艦に、広く散らばった小片群を 1 本の枝として足したもの) |
| `tools/render-lab/lab.ts` | 恒星の位置とシーン光源の向きを、ケースの太陽方向から毎フレーム引く |

**達成条件と検証.** `npm run typecheck`。
`npm run render-lab` で 3 ケースが選べ、明暗の境界がケースごとに指定した太陽方向と合っていること。
**この時点で自己影が絵に出ていなくてよい**(決めたこと 6)。読むのは「影」表示のスロットで:

- `ship-cluster` で、**スロットが 2 枚以上埋まっている。**
- `ship-selfshadow` と `ship-in-debris` で、それぞれ何がスロットを取ったかを記録する
  — 後者で小片群が先頭を占めていることが、手順 7 の出発点になる。

---

### 手順 7. 散らばった遮蔽器が、艦のスロットを奪う経路を断つ

**目的.** シーン直下の 1 本の枝にまとまった大量の小片(薬莢・破片・弾のプール)が、箱の対角で
測ると常に最大の遮蔽器として並びの先頭に来て、収まらない塊としてスロットを 1 枚占有し、その箱と
交差する艦をすべて棄却してしまう。**占有したスロットは 1 texel が個体より大きいので、影は何も
写らない。**

**変更が必要な箇所.**

| ファイル | 何をするか |
| --- | --- |
| `src/render/pipeline/sun-shadow-maps.ts` | 見かけの大きさを、枝の箱の対角ではなく「その枝が持つ単一個体の大きさ」で測る(手順 4 で `InstancedPool` が公開した口から読む)。塊どうしが重なるときの棄却をやめ、収まるなら吸収へ倒す |

**達成条件と検証.** `npm run typecheck`。
`npm run render-lab` の `ship-in-debris` の「影」表示で、**小片群がスロットを 1 枚も取っておらず、
スロットの割り当てが `ship-selfshadow` と同じになること。** 自己影が絵として出るかどうかは、
ワールド行列を直す手順 8 まで判断しない。

---

### 手順 8. 遮蔽器の箱を、そのフレームのワールド行列が確定してから作る

**目的.** 影パスはフレーム最初にシーンを走査する側なので、ワールド行列が前フレームのまま
(`render-lab` では一度も更新されないまま)の状態で遮蔽器の箱を決めている。箱がずれると
ライトカメラの枠と受け手の AABB の両方が同時にずれ、**絵は「影が無い」としか言わない。**

**変更が必要な箇所.**

| ファイル | 何をするか |
| --- | --- |
| `src/render/pipeline/sun-shadow-maps.ts` | 遮蔽器を集める前に、そのシーンのワールド行列を確定させる |

**達成条件と検証.** `npm run typecheck`。
`npm run render-lab` の `leo` で「影」を選び、**スロット 0 に自機のシルエットが写ること。**
手順 5 で記録した状態と比べて、白紙だったスロットが埋まること。
**ここで初めて絵として確かめる** — `ship-selfshadow` の通常表示に艦の突起の影が船体へ落ちて見え、
`ship-in-debris` にも同じ自己影が出ていること(達成目標 3・5)。

## 見積り

### 手順 2 — 返るメモリ

```text
外殻の深度マップ  1024² × 8 B (RGBA half)      =  8.4 MB
その深度バッファ  1024² × 4 B (float32)        =  4.2 MB
受け手マスク      1920×1080 × 1 B              =  2.1 MB
その深度バッファ  1920×1080 × 4 B              =  8.3 MB
合計                                             23.0 MB
```

### 手順 3 — 大気パスの GPU 時間

単価は球 1 個 80 ALU、半影ありの帯 1 本 65 ALU。遮蔽器は最大 4 体、帯は最大 13 本。

```text
現状      = 2 回 × (4 × 80 + 13 × 65) = 2 × 1165 = 2330 ALU/px
手順 3 後 = 1 回 × (4 × 80) + テクスチャ 1 フェッチ = 320 ALU/px
```

1920×1080 = 2.07e6 画素。換算率は既知の対応(2.32e9 ALU = 0.77 ms、すなわち 3.01e12 ALU/s):

```text
削減 = (2330 − 320) × 2.07e6 = 4.16e9 ALU
     = 4.16e9 / 3.01e12 = 1.38 ms
```

**低軌道の構図で 1.4 ms 前後。** 遮蔽パスの帯を切り分けて得た改善(0.77 → 0.22 ms、0.55 ms)より
大きい。

### 手順 7 — 散らばった遮蔽器が占有していたスロットの無駄

薬莢が 200 m の範囲へ散った場合、その塊のスロットは 1 texel = 200 / 1024 = 0.20 m。薬莢の全長は
0.1 m 前後なので **1 texel も埋めない。** スロット 1 枚 = 1024² × 4 B = 4.2 MB と、そこへの
描画呼び出しが丸ごと無駄になっている。

### 手順 1・5・6 — GPU への影響

無い。器の作り替えとケースの追加なので、ゲーム本体の描画には触らない。

## リスクと落とし穴

| リスク | 影響 | 露見する場所 |
| --- | --- | --- |
| **フォワード経路を落とすときに、光源のチャンネル付与まで一緒に落とす** | `NodeMaterial` はカメラのチャンネルと重なる光源が 1 つも無いと照明モデルを組まない。**マテリアルパスはカメラを 1 チャンネルへ絞るので、そこに光源が居ないと絵が丸ごと真っ黒になる** | **手順 1。** `render-lab` の `leo` が黒一色になる |
| **撮影の出力名を変えたのに、古い PNG が残って新旧が混ざる** | `.render-lab/shots/` に `*-prepass.png` と `<case>.png` が同居し、どちらを見ているのか分からなくなる | **手順 1。** 撮影後にディレクトリを一覧して枚数を数える |
| **タンパク質の `userData` を落とすときに、半透明外殻を G バッファから外す判定まで一緒に落とす** | 外殻が不透明として G バッファへ入り、**内部リボンの深度と法線を上書きする。** 絵は「リボンが消えて外殻だけになる」 | **手順 2。** `render-lab` の `5i4r-silhouette-1` |
| **もやが遮蔽バッファを読むようにした結果、大気の外の画素まで暗くなる** | 遮蔽バッファは G バッファの深度が書かれていない画素(虚空)でも値を持つ。もやの適用範囲の判定が甘いと、地平線の外側に暗い帯が出る | **手順 3。** `render-lab` の `earth` で、地球の縁の外側を見る |
| **`spheres` フラグを落とすときに、環だけの呼び出しがあると思い込んで条件を残す** | 落とし切れずに分岐が残る。型検査は通る | **手順 4。** `grep -rn "spheres" src/` が 0 件になるまで |
| **`RingVisualState` から太陽方向を落としたら、位相関数の向きが変わる** | 環の前方散乱・後方散乱の非対称が反転しうる。**明るさは変わるが「それらしく」見えるので気付きにくい** | **手順 4。** `npm run render-lab:shot` の `saturn` / `saturn-shadow` を実施前と画素で比べる |
| **デバッグ表示を切り替えても絵が変わらない** | `render-lab` はケースを選んだときにしか描かない。選択を `pipeline.debugTarget` へ書くだけでは前の絵が残り、**「影バッファが空だ」と読み違える** | **手順 5。** 「法線」を選んで絵が変わらなければ、これ |
| **タンパク質の運動が影へ伝わっているかどうかが、three の実装依存のまま残る** | シャドウアトラスは override マテリアルで描くので、揺れの位置ノードが伝わらないと**影だけが静止位置から落ちる。** 揺れは小さいので、影がわずかにずれるだけで気付きにくい | **手順 5。** 手順 2 で伝播の明示を消しているので、デバッグ表示が載った時点で `5i4r-molecular-1` を動かし、「影」表示のスロットの中身が揺れているかを見る |
| **斜光ケースの太陽方向を、恒星の位置には反映したがシーン光源には反映し忘れる** | 遮蔽と自己影は新しい向きで出るのに、拡散反射だけが元の向きのまま。**影と陰影の向きが食い違うが、どちらも「それらしく」見えるので気付きにくい** | **手順 6。** `ship-selfshadow` で、影の向きと明暗の境界の向きが合っているかを見る |
| **単一個体の大きさで測るようにしたら、大きな基地が落ちる** | 基地は 1 個の巨大メッシュではなく多数の部材の集合なので、「単一個体」の測り方によっては見かけが小さいと判定され、影を落とさなくなる | **手順 7。** ゲーム本体で基地へ接近し、影が消えないことを見る |
| **重なりによる棄却をやめた結果、重なった塊の受け手が片方の遮蔽器を取りこぼす** | 受け手は入っている最初のスロットしか引かないので、2 つの塊が重なる帯では片方の影だけが出る | **手順 7。** `ship-cluster` の艦の間隔を詰めていくと、ある距離で片方の塊が吸収される(絵として影が消えるのが見えるのは手順 8 以降)。**許容する** |
