# Phase 5 — 物理量と表示値の分離、アルベドの物理量化、露出・トーンマッピングの本実装

**コード上の事実・行番号は、リビジョン `02f5548f`(2026-08-24)時点で確認したもの。**

## 目的

描画に残っている手調整の明るさ係数をすべて捨て、**アルベド(反射率)と放射照度**という 2 つの
物理量へ組み替える。Phase 4 までで器(7 パス構成)・座標(実 ECI・実半径)・受け手(照度バッファ
経由の標準 BRDF)は揃っていて、**量だけが偽物のまま**残っている。ここを埋めると物理ベース
レンダリングの前提が完成し、Phase 8(エリアライト)は「点光源を有限の立体角へ広げる」だけになる。

**その前に、物理量で描くものと表示値で描くものをパスで分ける。** 軌道線・軌跡線・天球グリッド・
縮尺グリッド・Δv ギズモは 3D 空間に居るが、**アルベドも放射輝度も持たない** — UI テーマの色を
そのまま画面へ出すべき表示物である(`theme.ts` から既に色を引いている)。いまはこれらが world
パスで HDR ターゲットへ描かれているので、**露出とトーンマッピングを浴びる。** 露出を触る前に
外に出しておかないと、物理量として扱うべきでないものが露出の調整対象に混ざる。

いま偽物なのは次の 6 つ。

| いまの姿 | 何が偽物か |
| --- | --- |
| `SUN_INTENSITY = 6.9`(`game/const.ts:122`) | 光の単位に根拠がない。1 天文単位での放射照度を 6.9 と置いただけ |
| `ALBEDO_FROM_LIT_COLOR = π / SUN_INTENSITY`(`celestial-surface.ts:11`) | 天体の直書き色を「1 AU で照らされた見え方」とみなして割り戻す繋ぎ。アルベドは 1 つも無い |
| `EXPOSURE = 0.72`(`render-pipeline.ts:29`) | 環の単一散乱輝度が LDR で飽和しないよう手で置いた係数 |
| `render/ring.ts` の単一散乱 | 放射照度の項を持たない。土星が受ける光は地球の 1/92 なのに、環だけがその減衰を受けていない |
| `Billboard` の `opacity`(`billboard.ts:16-18,38`) | 明るさを不透明度で表している。量の取り違えで、加算合成でしか成り立たない |
| 軌道線・グリッド・ギズモが world パスに居る(`curve.ts` / `celestial-grid.ts` / `spatial-grid.ts` / `plan-gizmo-3d.ts`) | 表示値なのに HDR ターゲットへ描かれ、露出とトーンマッピングを浴びる |

**距離依存はもう入っている。** ライティングパスは画素ごとに `intensity / |p - p_sun|²` を掛けており
(`light-prepass.ts:79-81`)、天体表面は既に太陽からの距離で暗くなる。**road_map の Phase 5 完了条件
「天体の明るさが太陽からの距離に応じて変わる(現状は変わらない)」は古い** — 変わらないのは環・
太陽・惑星輝点・大気の 4 つだけで、そこがこのフェーズの実質的な中身になる。

## 決めたこと

**ユーザーはここを覆せる。** 覆したときにどの手順が変わるかを各項に書く。

### 決定 1. 描画が扱う放射照度の単位を「1 AU で π」に取り、露出係数を 1.0 にする

road_map §1-1 の式 `exposure = 1 / L_ref` は、係数を出力段に置くか単位の取り方に畳むかの自由が
ある。**単位に畳む。** 描画内部の放射照度の単位を `SOLAR_CONSTANT / π = 433.2 W/m²` に取ると、
1 天文単位での太陽の放射照度はこの単位で π になり、ランバート BRDF の 1/π と打ち消し合って

> **太陽に正対したアルベド A の完全拡散面は、1 天文単位で表示値 A になる。**

**根拠は 2 つ。**

1. road_map §1-1-2 が完了条件に挙げる「`EXPOSURE` が 1.0 になる」を、文字どおり満たす唯一の
   取り方である。SI 単位(W/m²/sr)を描画内部へ通すと露出は `π / 1361 = 2.31e-3` になり、1.0 に
   ならない。
2. **HDR パスに残る手書きの発光値(プルーム・RCS・フラッシュ・オーロラ・点群・弾のハロー・
   プラズマ弾)を、いまの数値のまま置いておける。** 露出が 1 以外だと、これら 8 箇所ほどの
   マテリアルすべてに `1/露出` の持ち上げが要る。これらが物理量になるのは Phase 12
   (ボリュームレンダリング)なので、それまで手書きの表示値を持ち続ける。

**表示値の色のうち、線・グリッド・ギズモは決定 7 で HDR パスの外へ出る**ので、この 2 番目の
根拠は当初より弱い。**それでも 1 番目の根拠だけで足りる。**

**覆した場合**: 描画内部を SI 単位にするなら、手順 4 に「HDR パスに残る手書きの発光値を
`SOLAR_CONSTANT/π` 倍する」作業(`point-field-view.ts:56` / `aurora.ts:46` / `stars.ts:26` /
`billboard.ts` の呼び出し 5 箇所 / `ships.ts` の非標準マテリアル 5 箇所)が加わる。

### 決定 2. トーンマッピングは `neutralToneMapping`(Khronos PBR Neutral)を使う

1 を超える値(太陽面は表示値で 4.6e4、鏡面ハイライト、噴射炎)を切り落とさずに白へ寄せる。
PBR Neutral を選ぶのは、**圧縮開始点 0.76 より下では色相・彩度を保ったまま素通しする**ため —
決定 1 の「表示値 = アルベド」という校正が、中間調では検証可能なまま残る。

**ただし恒等写像ではない。** three の実装は最小チャンネルから `offset`(0.08 以上で 0.04)を
引くので、**中間調が線形値で 0.04 だけ暗くなる。** これは承知の上で採る。曲線の最終決定は
Phase 11(露出 → ブルーム → フレア → トーンマッピング → sRGB)の仕事で、ここでは
「1 を超える値が飛ばない」ことだけを満たす。

**覆した場合**: `agxToneMapping` は黒の持ち上げと彩度低下が大きく、`acesFilmicToneMapping` は
中間調を暗く色を濃くする。どちらも「表示値 = アルベド」の検証ができなくなるので、手順 4 の
達成条件から画素値の照合を落とすことになる。

### 決定 3. `Billboard` の明るさを `opacity` から `color` へ移す(ノードマテリアル化はしない)

**問題**: `Billboard.sync` は明るさを `material.opacity` に入れている(`billboard.ts:38`)。
加算合成での画面への寄与は `texRGB × material.color × (texA × opacity)` で、太陽面は表示値で
4.6e4 が要る。

**選択肢は 3 つある。**

| 案 | 中身 | 変更量 |
| --- | --- | --- |
| **(A) 明るさを `color` へ移す** | `sync` の第 3 引数を明るさとして受け、`color = 基準色 × 明るさ`、`opacity` は 1 固定 | `billboard.ts` 2 箇所 + 呼び出し 5 箇所の引数名 |
| (B) `opacity` のまま 1 を超える値を入れる | 何もしない | 0 行 |
| (C) `MeshBasicNodeMaterial` + `colorNode`(road_map の記述) | ユニフォームを自前で配線する | `billboard.ts` 全面 + `getGlowTexture()` のマップ経路の組み直し |

**(B) は実際に動く。** three の `NodeMaterial.setupOutput` は
`vec4(outgoingLight, diffuseColor.a).max(0)` で**下限だけ**を切り、上限は切らない
(`node_modules/three/src/materials/nodes/NodeMaterial.js:535`)。`Material.opacity` も JS 側で
クランプされず、WebGPU の blend factor `src-alpha` は float ターゲットで飽和しない。
**それでも採らない。**

- **`opacity`(不透明度 = 背景をどれだけ置き換えるか)と明るさは別の量である。**
  CODING-RULE 2.1「振る舞いと扱い方が明快な命名」に反する。デバッグで `opacity: 46000` を読む
  ことになる。
- **加算合成でしか成り立たない。** Phase 9 で半透明パスを統合して通常アルファ合成へ移った瞬間、
  `src·a + dst·(1−a)` の `1−a` が負になり背景を黒く抉る。**無言で壊れる経路を残すことになる。**

**(C) を採らない理由**: (A) と同じ絵に、ユニフォーム配線とマップ経路の組み直しが増えるだけ。
`THREE.Color` の各成分は素の float で three は上限をクランプしないので、ノードへ降りる必要がない。

**(A) を採るもう 1 つの根拠**: `flashResources()` +`InstancedPool` の経路は**既に (A) の形**に
なっている — 明るさは `fx.color = baseColor × opacity` として `instanceColor` へ畳まれており
(`flash-effect-manager.ts:73`)、`Float32Array` なので 1 を超えられる。(A) は
`Billboard` をその形へ揃えるだけで、**2 つあった流儀が 1 つになる。**
`flashResources()`(`billboard.ts:47-58`)自体は変更不要。

**覆した場合**(= 検証で色がクランプされていた場合): 手順 7 が (C) になり、`InstancedPool` の
`instanceColor` を `instancedBufferAttribute` で明示的に掛け直す作業が加わる。判定は手順 7 の
検証で付く。

### 決定 4. 太陽光の色 `0xfff4e0` は捨てず、根拠を付けて `render/` へ移す

`COLOR_SUN`(`game/const.ts:121`)は 5772 K の黒体の色とほぼ一致する。手調整値ではなく物理量
だったので、出典コメントを添えて残す。**実測して sRGB 8bit で 1 段を超えてずれていたら黒体色へ
差し替える。**

### 決定 5. `game/const.ts` の配色の移動は、3D 描画に出るものだけに絞る

road_map §4 の移す表は「エフェクトの size/opacity 式・配色 → `render/`」を Phase 5 に置いている。
**3D の絵に出る色・寸法だけを移し、HUD/DOM が使う色(`COLOR_MARKER_*`・HP バー等)は
UI 側の管轄として触らない。** ステージ定義が選ぶ敵のアクセント色・陣営ごとの軌道線色
(`COLOR_STAGE0_GROUP_ACCENTS` / `COLOR_ENEMY_ORBIT_LINE` / `COLOR_BASE_ORBIT_LINE`)は、
「どう見えるか」ではなく「どの勢力か」を表すコンテンツなので同じく残す。

**覆した場合**: 手順 10 の対象が広がる。画素は 1 つも変わらないので、どこまで運ぶかは分量の判断に
なる。

### 決定 6. 太陽系外縁が暗いことは、このフェーズが引き起こす問題ではない

海王星(30 AU)の表面は現状すでに「色 / 900」で描かれている(`SUN_RADIANT_INTENSITY / d²` と
`ALBEDO_FROM_LIT_COLOR / π` を畳むと `色/900` が残る)。**マップビューで外惑星が黒いのは
Phase 4 からの既存の挙動で、Phase 5 はそこを変えない。** マップビュー専用の露出を持つかどうかは
別の判断で、この計画には入れない。

### 決定 7. 3D UI パスは合成パスの後ろへ置き、深度は合成パスがキャンバスへ書く

**軌道線・軌跡線・天球グリッド・縮尺グリッド・Δv ギズモを world パスから外し、露出と
トーンマッピングの後ろに置いた 3D UI パスへ移す。**

**なぜ world パスのままではいけないか。** これらは 3D 空間に居るが物理量を持たない。色は
`theme.ts` の UI テーマ(`entity-line-manager.ts:10` / `plan-gizmo-3d.ts:3` / `player.ts:32` /
`enemy.ts:29` / `base.ts:36` が既に読んでいる)から来る**表示値**で、露出やトーンマッピングを
掛ける対象ではない。UI-DESIGN §2 が「UI の色とゲーム世界の色は別管理」と定めているのと同じ
分界を、**描画パスの側でも引く。**

**どこへ描くか。** 合成パスと同じくキャンバスへ直接描く。**深度は合成パスが書く** —
合成パスのマテリアルへ `depthNode = texture(gbuffer.depthTexture, screenUV).r` と
`depthWrite: true` を与えると、フルスクリーン矩形がキャンバスの深度バッファへシーンの深度を
そのまま複製する。3D UI パスはそれに対して普通に深度テストするだけでよく、**線のマテリアルを
ノード化する必要がない**(`Curve` は `LineBasicMaterial` / `LineDashedMaterial` のまま)。
**アンチエイリアスもキャンバス側のマルチサンプルがそのまま掛かる** — 3D UI が最後段に来るのは
このためでもある。

**G バッファの深度を使う**(HDR 共有ターゲットの深度ではない)。共有ターゲットは
`antialias` 時に 4 サンプルで、**マルチサンプル深度テクスチャは通常のサンプリングができない。**
G バッファは 1 サンプルで、既に遮蔽・ライティング・大気・デバッグ表示がサンプルしている。

**帰結 1**: G バッファに居ない不透明物 — **太陽の球と弾薬ビーコン**(どちらも
`MeshBasicMaterial` なので world パス側)— は 3D UI を遮らなくなる。太陽は 1 AU 先にあり、
その手前に軌道線が来る構図では線が見えるほうが正しい。**これは受け入れる。**

**帰結 2**: 3D UI は環・大気・オーロラ・プルームより**必ず手前**になる(それらは深度を
書かないため)。土星の環の向こう側を通る軌道線が、環に隠れず透けて見える。
**UI としては正しく、絵としては変化がある** — 手順 3 の目視で判断する。

**帰結 3**: アルファ合成がキャンバスの色空間(sRGB 符号化後)で起きるようになる。いまは線形
HDR 空間で混ざっている。**暗い背景の上の薄い線がわずかに濃く見える** — DOM の UI と同じ
混ざり方になるので UI としては自然だが、変化ではある。

**覆した場合**: キャンバスの深度バッファが使えない、または帰結 1〜3 が許容できないなら、
**LDR 中間ターゲット + ブリット**へ切り替える — 共有ターゲットの深度テクスチャを
アタッチメントとして共有する同サイズ・同サンプル数のターゲットを 1 枚足し、そこへ合成 → 3D UI
の順に描いてから 1 回ブリットする。深度は完全に正しくなり合成も線形空間のままになるが、
**全画面 rgba16f × 4 サンプルで約 66 MB** と 1 パス分の帯域が増える。

### 決定 8. ガンサイトズーム中のマズルフラッシュ減光は残す(物理からの意図的な例外)

road_map §1-1 は手調整値を捨てると定め、Phase 5 の項目にも `ZOOM_MUZZLE_FLASH_SCALE` が
挙がっていた。**残す。**

実際の閃光の明るさは画角によって変わらないので、これは物理的には嘘である。**だが意図的な嘘で
ある** — 視野角を 55° から 6° へ絞ると銃口が画面上で大きく写り、発砲のたびに閃光が照準を覆って
狙えなくなる。物理を優先するという原則の例外として、**ゲームプレイのために残す。**

**この例外は SPEC へ明記した**(`DEVELOP/SPEC/COMBAT.md`「発光フラッシュ」節、リビジョン
`02f5548f` 時点で追記済み)。**仕様が覆ったときに初めて外す** — 実装の都合で勝手に外さない。

**帰結**: `ZOOM_MUZZLE_FLASH_SCALE`・`dimsInGunsight`・`zoomActive` の配線は手順 10 の対象外に
なる。「手調整値が `src/` から 0 件」という達成目標も、この 1 つを除いた形になる。

### 決定 9. 天体に入れるのはボンドアルベド。幾何アルベドは使わない

**天文の 2 つのアルベドは別の量である。**

- **幾何アルベド $p$** — 位相角 0(太陽を背にして真正面から見た状態)での明るさを、同じ半径の
  **完全拡散・完全反射の平板円盤**と比べた比。**方向を 1 つ選んで測った量**なので 1 を超えうる。
- **ボンドアルベド $A_B$** — 天体が受けた全放射のうち、全方向・全波長へ返す割合。**エネルギーの
  収支そのもの**なので 1 を超えない。
- 両者は位相積分 $q$ で結ばれる: $A_B = p q$。

**レンダリングの拡散アルベド $\rho$ に対応するのはボンドアルベドである。** ランバート球
(各面が受けた放射の $\rho$ を全方向へ均等に返す球)を考えると、返す総量は定義から
$\rho$ そのものなので **$A_B = \rho$。** 同じ球の幾何アルベドは $p = \tfrac{2}{3}\rho$ で、
位相積分は $q = \tfrac{3}{2}$ になる。**完全反射のランバート球ですら $p$ は 2/3 にしかならない。**

**したがって $\rho = A_B$ を入れる。** これで Phase 8 で天体を光源にしたときのエネルギーが
そのまま正しくなる(§1-1-1 が要求している「同じ値が表面色と光源強度の両方に使われる」の
前提でもある)。

**代償**: 現実の $q$ は 1.5 より小さい天体が多い(後方散乱が強い)ので、
**位相角 0 付近での明るさが $\tfrac{2}{3}q$ 倍に落ちる。** 満月・満エンケラドゥスのような
「太陽を背にして見る」構図で、写真より暗く写る。**これは衝効果(opposition surge)を
モデル化していないことの正しい帰結であって、アルベドを盛って埋めてはならない。**
埋めるなら再帰反射項を足す — 置き場はライティングパスで、ランバート球近似そのものを
問い直す Phase 8 の議論に属する。

**GGX の粗さ・鏡面成分では代用できない。** GGX の鏡面ローブは**鏡面方向**にピークを持ち、
衝効果は**入射方向へ返る**(視線 = 光源方向)ピークなので、幾何が逆である。鏡面成分を足すと
別物(海面のサングリントのような効果)が増えるだけになる。

**覆した場合**: 幾何アルベドをそのまま入れるなら、エンケラドゥスのように 1 を超える天体を
どこかで切る規則が要り、Phase 8 の光源強度が $1/q$ 倍(天体によっては 2〜3 倍)過大になる。
手順 5 の値の集め方と、手順 8 の輝点の式が同時に変わる。

## 達成目標

全手順の実施後、次がすべて満たされていること。

0. **物理量で描くものと表示値で描くものがパスで分かれている。** 軌道線・軌跡線・天球グリッド・
   縮尺グリッド・Δv ギズモが 3D UI パス(露出とトーンマッピングの後ろ)で描かれ、露出を
   何倍に変えても**画面上の色が変わらない。**
1. **手調整の明るさ係数が `src/` から消えている。** `EXPOSURE` / `SUN_INTENSITY` /
   `AMBIENT_INTENSITY` / `ALBEDO_FROM_LIT_COLOR` を `src/` で grep して 0 件。
   **`ZOOM_MUZZLE_FLASH_SCALE` だけは残る**(決定 8。SPEC が定めたゲームプレイ上の例外)。
2. **`src/render/` から `src/game/const` への import が 0 件。**
   `grep -rn "game/const" src/render/` が 0 行。
3. **101 天体が RGB のアルベドを持ち、輝度を 1 つも持たない。** 単色球 82 体は出典コメント付きの
   アルベド値、テクスチャ 15 体は円盤平均が公表幾何アルベドに合う倍率を持つ。
   `celestial-registry.ts` に色リテラルが 0 件。
4. **露出が 1.0 で、出力段はトーンマッピングを通る。** `render-pipeline.ts` に露出ユニフォームと
   `.mul(this.exposure)` が残っていない。
5. **アルベド 1 の完全拡散面を 1 AU で太陽に正対させると、トーンマッピング前の線形値が 1.0 に

## リスクと落とし穴

| リスク | 影響 | それが露見する場所 |
| --- | --- | --- |
| **合成パスがキャンバスの深度バッファへ書けない** | 3D UI が深度テストに落ちず、**軌道線が地球や艦を貫通して常に手前へ出る。** 例外は出ないので、絵を見るまで気付けない | **手順 3** の `leo-prepass.png`(艦の向こう側の線が隠れるか)。落ちたら決定 7 の「覆した場合」へ |
| **`render-lab` のフォワード経路が `OVERLAY_LAYER` をチャンネル 0 へ潰す** | `order-forward.png` から線だけが消える。シェーディング経路の差と読み違える | **手順 3** の `order-forward.png` |
| **3D UI のアルファ合成がキャンバスの色空間で起きる** | 薄い線が暗い背景の上でわずかに濃くなる。バグではなく仕様の帰結だが、気付かないまま「線が太った」と誤診しうる | **手順 3** の実機目視(決定 7 の帰結 3)|
| **フォワード経路の光源強度を単位に合わせ損ねる** | `render-lab` の 2 経路が食い違い、以後どの手順でも差分画像が判定に使えなくなる。**絵は壊れないので気付けない** | **手順 4** の `leo-diff.png`。ここを最初の関門にする |
| **`THREE.Color` が 1 を超える値でクランプされる** | 太陽・輝点・噴射炎が 1 で頭打ちのまま。トーンマッピングの肩に乗らず、Phase 11 のブルーム対象が消える | **手順 7** の飽和確認。ここで変化が出なければ決定 3 が外れている |
| **幾何アルベドをそのままレンダリングのアルベドにする** | エンケラドゥス($p$≈1.4)のような天体が受けた光より多く返す。1 未満の天体でも光源強度が $1/q$ 倍(2〜3 倍)過大になり、**Phase 8 で天体を光源にするまで表面化しない** | **手順 5** の「1 を超えるアルベドが無いこと」の grep と、値ごとのコメントに $q$ の出典があること(決定 9)|
| **テクスチャの明るさをアルベドとみなす** | 実写テクスチャは撮影・処理で任意にスケールされている。月(アルベド 0.12)が地球(0.30)と同じ明るさに見える現状は、まさにこれが原因 | **手順 5** の目視(月と地球を並べる) |
| **環へ放射照度を渡す配線で `render/` へ ECI が漏れる** | road_map §1-2 の不変条件が壊れ、太陽系スケールで f32 量子化が出る | **手順 6** の `grep -rnE "\bVec3\b\|Ephemeris" src/render/ring.ts` |
| **デバッグ表示の照度バッファがトーンマッピングを通らず全面白になる** | 「拡散照度」「鏡面照度」表示が 1 AU で π を超えて読めない。パスが壊れたのと区別が付かない | **手順 4** の実機目視(デバッグ表示 4 種) |

| **金属度を 0 にした結果、艦が「明るいがのっぺりした白い箱」になる** | 鏡面ハイライトが減り立体感が落ちる。物理的には正しいので、直すのは金属度ではなく粗さ | **手順 9** の `leo-prepass.png` |
| **物理ベース化の勢いでマズルフラッシュのズーム減光まで捨てる** | ガンサイトズーム中の発砲が照準を覆い、狙えなくなる。**物理的には正しくなるのでレビューで見逃しやすい** | **手順 10** の `grep -rn "ZOOM_MUZZLE_FLASH_SCALE" src` が 1 件以上残ること(決定 8)|
