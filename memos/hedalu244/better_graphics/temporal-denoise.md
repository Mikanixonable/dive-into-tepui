## 目的

近傍拡散補正のちらつきを消す。ちらつきの元は 3 つあり（決めたこと 8）、どれも「フレームごとに動かしてから時間方向に平均する」で
治る見込み:

1. **走査の乱数** — ブルーノイズは画面（走査の画素）に貼り付いているので、カメラが動くと同じ表面の点が違う乱数を引く。1 パスの
   雑音（色ムラ・粒・最後の拡大の疎なタップのざらつき）もこれ。
2. **走査のダウンサンプリング** — 走査は 1/4 の解像度で、4×4 の G バッファの画素のうち決まった 1 つ（ブロックの中心 —
   `gbufferTexelOf`）を代表にする。かすめる面（視線にほぼ平行な側面。0〜2 px でしか写らない）を代表が踏むかで、切片の方式が
   鋭敏に変わる（`screenspace-diffuse.md`「仮置きの推定量の既知の問題」）。
3. **幾何のラスタライズ** — 全解像度の G バッファでも、かすめる面の写り方は画素の中心に乗るかで決まる。全解像度の B にも輝点がある。

2 と 3 の輝点は、カメラと物の位置関係が動かなければ動かない — そのまま時間方向に平均しても消えず、位置関係が少し動くと鋭敏に
変わってちらつく。だから意図的にジッターで動かしてから平均する。前フレームの補正を再投影して混ぜる時間方向の蓄積（temporal AO）を
足し、1〜3 を動かして均す。

## 決めたこと

### ユーザーが決めたこと

1. **蓄積するのは、最後の拡大の後（描画バッファの解像度）の補正項 ΔE だけ**（2026-10-12）。拡散照度（遠方光 + ΔE）や陰影は
   蓄積しない。最後の拡大の確率的な粒も均すため、拡大の前の C_0 ではなく後で混ぜる。描画バッファの解像度の、拡大済みの補正項
   単体の描画先は残る — 拡散側では、最後の拡大をライティングの読みへ畳む案をこれを理由に取り下げた（拡大の費用の主因は読み書き
   ではなくタップ数で、タップによるざらつきは蓄積で治す）。
2. **再投影は動きベクトルで行う**（2026-10-12）。カメラの動きだけでなく、動く物（自機・敵・天体の自転と公転）も追う。求め方は決めたこと 7。
3. **履歴の重みも積算する**（2026-10-07）。単に重みで前フレームと混ぜるだけだと、最新のフレームがつねに最大の影響力を持つ
   （ユーザーが以前、別のプロジェクトでそう実装した）。積算された過去フレームの価値を見積もる重み（履歴の長さ）を画素ごとに運ぶ。
4. **残像に上限を置く**（2026-10-07）。受け手の幾何が動かなくても、送り手やその明るさが動くと影や照り返しが残る。過去フレーム側の
   最大の重みを制限し、一定の時定数で消えるようにする。残像は、ちらつきや静止時の色ムラより品質への罰が小さい。
5. **時定数は独立なスライダーにする**（2026-10-12）。スライス数と組にしない — 拡散側の決めたこと 28 の「処理時間の分散」（スライス数と
   時定数を 1 軸に組む）は、拡散側の決めたこと 40 で覆った。プリセットの値は `graphics-settings-feature.md` の手順5で決める。この計画では
   時定数を描画設定の値として受け、範囲と既定を仮置きする。
6. **評価は静止画で比べられない**（2026-10-07）。動く絵の道具を作る。
7. **動きベクトルはカメラとの相対座標から求める**（2026-10-12）。物が動いていなくてもカメラが動けば追うべきで、そもそもこの
   ゲームでは全ての物が軌道の上を動いていて静止した物が無い — 物の絶対座標（ECI）の動きを動きベクトルにすると、おかしくなる。
   カメラとの相対の位置関係は CPU の側で解けていて、カメラの位置を 0 にして与えている（浮動原点 = カメラの ECI 位置）。カメラの
   回転は解けていないので、CPU か GPU のどちらかで入れる。
8. **ちらつきの元を 3 つに分け、どれも動かしてから時間方向に平均する**（2026-10-12）。今あるものを時間方向に平均するだけでは
   ちらつきを抑えられない見込みがある — 走査の乱数が変わって生じるちらつき（当初の計画）のほかに、側面のラスタライズに由来する
   ちらつきがあり、1/4 の走査解像度へダウンサンプリングしているので影響が大きい。これは、カメラや物が動かなければ動かない輝点として
   残り、位置関係が動くと鋭敏に変わるので、意図的にジッターで動かしてから平均しないとちらつきになる。TAA のように、ダウンサンプリング
   とラスタライズをジッターするところまで視野に入れる。どれが原因かを評価するときは、ほかのジッターを止めて切り分ける（例: 2 を
   評価するときは 1 と 3 を動かさない）。場合によっては、拡散補正項の蓄積だけでは目的を達せない（手順7）。
9. **ダウンサンプリングのジッターの形は事前に決めず、試して判断する**（2026-10-12）。縮小写しにジッターを入れると、走査のときの幾何
   からの復元まで影響が出る。画素ごとに代表の選び方を乱択する形は、走査の際に別種のアーティファクトを生むおそれがある。ピクセル
   グリッド全体をオフセットする形は、そのような弊害はない反面、照り返しの全体が平行移動で振動しているかのように見えるちらつきが
   出るおそれがある。両方リスクがあるので事前には決められない — 実装してみて、懸念した問題が起きているかを目視または定量評価で
   判断し、問題が気になれば別の方法を試す。

### 前提として守る契約

並行する拡散側の作業（`screenspace-source.md`・手順9〜11）と衝突させないため。

- **蓄積は `src/render/pipeline/screen-space/` の中に閉じる。** 補正を読む側は、今と同じく `DiffuseCorrection.texture`（`at` / `atUv`）を
  読み、それが蓄積後の値になる。読む側のコードと `render-pipeline.ts` の実行順は変えない — 読む側はいまライトプリパスの光源
  `DiffuseCorrectionSource` で、`screenspace-source.md` の後はマテリアルと映り込みの像の元になる。最後の拡大の出力（蓄積の前）は別の
  描画先にし、デバッグ表示を足す（`/rendering-workflow`「中間バッファを観測可能にする」）。**ラスタライズのジッター（手順7）は画面全体を
  揺らすので、この契約の外にある** — 手順6 までは render-lab の中だけで作る。
- **走査の代表の動かし方（ダウンサンプリングのジッター）は `screen-space/` の中に閉じる** — 代表の選び方（と、格子をずらす形なら全解像度と走査の
  画素の写像）だけを動かす。走査の幾何の復元には影響が出る（決めたこと 9）。ずれの幅は走査の画素の幅（描画バッファ / 走査の解像度）から
  決め、1/4 に決め打たない（拡散側の手順9 が走査の解像度を 1/2・1・1/8 にする。1 で消える）。
- **動きベクトルは G バッファに 1 枚足す。** いまの 4 枚（rg16f・r8・rgba16f・rgba16f）で 1 標本あたり約 22 B、rg16f を足して約 26 B で、
  WebGPU の既定の上限 32 B（`maxColorAttachmentBytesPerSample`）に収まる。`requiredLimits` は触らない（拡散側の手順10 が触る）。
  **動きベクトルにジッターを含めない**（前後ともジッターなしの射影で写す） — 手順7 を足すときに書き直さない。
- **render-lab の道具は新しいファイルに置き、`tools/render-lab/lab.ts` への変更を最小にする**（拡散側の手順9〜11 も触る）。
- **局所反射**は、像の元が ΔE を含む照度を読むので、蓄積後の ΔE が映り込みにも入る（意図どおり）。局所反射の追跡と置換重み w は、
  時間方向の蓄積を使わない（`screenspace-specular.md`「前提として守る契約」）。走査の代表の動かし方も局所反射には掛けない（局所反射は走査の面の
  写しを読まない — `acea60fc6` の時点）。

## 変えないもの

- 時定数を最小（履歴を使わない）にした絵が、蓄積を入れる前と同じ。**このとき、フレームごとに動かす入力（seed・走査の代表）も止まる。**
- 走査の代表の既定（null）が、いまの代表の選び方と同じ絵になる。
- 同じ入力と同じ履歴からは同じ画像になる（render-lab の撮影は、履歴を消して決まったジッターの列で N フレーム積んだ画像を 1 枚にする）。
- 補正は拡散照度にだけ掛かる。鏡面・直射・影は変えない。

## 達成目標

1. カメラを少しずつ動かした連続フレームで、同じ表面の点の補正のフレーム間の揺れが蓄積の前より小さく、ユーザーがちらつきを容認する。
2. 静止したカメラで N フレーム積んだ画像に、カメラが動かないと動かない輝点が残らず（採ったジッターの源の平均 — 手順3 — に収まる）、
   同じ仮想のスライス数の 1 フレーム（スライスを増やした raw）と同等以上に見える（ユーザーの目視）。
3. 送り手・光源を動かしたときの影と照り返しの残像が、時定数どおりのフレーム数で消える。
4. 動く物（自機・敵・天体の自転）の上とその縁に、履歴の取り違えによる尾が出ない。
5. 時定数を最小にした render-lab の撮影が、蓄積の前の組と `npm run render-lab:compare` の封筒内。
6. 費用（再投影して混ぜる行、動きベクトルの書き込みの増分）と中間 target の増分の表がある。
7. ちらつきの源（走査の乱数・走査のダウンサンプリング・ラスタライズ）ごとの寄与の表と画像がある（手順3。蓄積の後の残りは手順6）。
8. `npm run typecheck` / `npm run check:boundaries` / `npm run test:render` / `npm run test:settings` が通る。

## 手順

### 手順の組み立て（2026-10-12、エージェント）

- **源の寄与を、動きベクトルと蓄積を作る前に量る（手順3）。** 静止したカメラで 1 つの源の位相だけを振り、ほかを止めて N 枚撮れば、
  その平均がその源を動かして蓄積したときの収束先、平均からの分散が位置関係が動いたときのちらつきの強さになる（動くと位相が変わる
  ため）。拡散側の「総合的な品質の検査の 4 種」を、seed だけでなく走査の代表・ラスタライズのずれへ広げたもので、蓄積も動きベクトルも
  要らない。動きベクトル（4 h）と蓄積（3.5 h）の前に済ませれば、(a) どのジッターを本番に入れるか、(b) ラスタライズのジッター（画面全体の
  TAA）が要るか、(c) 全部を動かして平均しても残る輝点（推定量の偏り — 時間方向では治らない）があるか、が先に分かる。(c) が大きければ、
  蓄積を作り込む前にユーザーへ返す。
- **源を入れる順は 1 → 2 → 3**（費用と影響範囲の小さい順）。1 は seed の uniform（`ScreenSpacePass.setSeed`）が既にある。2 は走査の中
  （全解像度と走査の画素の写像）に閉じる。3 は G バッファの射影を動かすので画面全体が揺れ、決めたこと 1 と契約（蓄積は `screen-space/` に
  閉じる）に収まらない — 手順3・6 で要ると分かったときだけ手順7 で扱う。2 と 3 は尺度で分担する: 2 は走査の画素の中を描画バッファの
  画素の刻みで、3 は描画バッファの画素の中を動かす。
- **2 の形は 1 つずつ試す**（決めたこと 9）。格子全体のずらし → 気になれば画素ごとの乱択、の順（理由は手順3）。どちらも同じ口
  （`setScanJitter`）の 2 つの種類で、代表を選ぶ 1 か所に閉じるので、切り替えの費用は小さい。懸念が出ているかは、乱択の弊害（走査の
  幾何の復元）なら蓄積の前の手順3 で、ずらしの弊害（全体の振動）なら蓄積の時定数に依るので、手順3 の静止時の模擬と手順6 の動く絵で読む。
- **止め方は、カメラが止まっているかで変える。** 静止したカメラでは、ほかの源を止めれば 1 つの源だけが動く（ユーザーの切り分け）。動く
  カメラでは、止めた源も位置関係の変化で動いてしまうので、止める代わりに各フレームの中で平均して消し、源を 1 つずつ剥がす（手順3）。
- **二度手間を避けるための共通化**
  - ジッターの口は 1 つ（`frameJitterAt`）。手順3 の計測、手順5 の本番、手順6 の切り分けが同じ口を使い、成分ごとに止められる。
  - 手順2 の道具の**参照の再投影**（深度とカメラの前後の行列から写す）は、ちらつきの指標（同じ表面の点の揺れ）と、手順4 の動きベクトルの
    検算の両方に使う。
  - 手順3 の源ごとの静止時の平均は、手順6 で蓄積の静止時の収束を源ごとに検算する参照になる。
  - 動きベクトルは最初からジッターを含めない形で書き、ジッターの口は成分を足せる形にする — 手順7 を足すときに書き直さない。手順7 を
    採っても、ΔE の蓄積（雑音の多い信号を近傍 clamp なしで積む）は最終の色の TAA と分けて残る（前例の形）。

### 手順 3. ちらつきの源を切り分ける — ジッターの口と、源ごとの寄与

**目的** — 3 つの源が、どこでどれだけちらつきを作るかを量り、本番に入れるジッターと手順7 の要否を決める（手順の組み立て）。

**ジッターの口**

- **1 seed** — `ScreenSpacePass.setSeed`（既存。走査の回転・歩みと丸めのずれ・最後の拡大の回転をまとめて動かす）。
- **2 走査の代表の選び方** — `setScanJitter`。既定（null）はいまの代表（`gbufferTexelOf` の (2p + 1)·full / (2·scan)）と一致させる
  （変えないもの）。代表を選ぶのは `gbufferTexelOf` / `gbufferUVOf`（面の写しと源の標本が共有する）の 1 か所で、後の段は代表の G バッファの
  画素の座標を持ち回る。ジッターを入れると走査の幾何の復元まで影響が出るので、形は事前に決めず、試して判断する（決めたこと 9）。
  - **格子全体のずらし（grid。先に試す）** — 全ての走査の画素の代表を、同じずれだけ動かす。走査の標本は規則的な格子のまま並ぶので、
    いまの鎖・拡大の調整（κ・帯・拡大の半径）がそのまま効き、ラスタライズのずれ（3）と同じ形でもある — 先に試すのはこのため。
    **懸念** — 照り返しの全体が平行移動で振動して見える。蓄積の前の 1 パスでは必ず振動する（ジッターは蓄積と組でしか出さないので、
    それだけでは棄てない）。問題は蓄積した後に残る振動で、時定数が短いほど残る（時定数はスライダーなので短い値もありうる）。
    **写像** — 代表だけをブロックの中で動かす（走査の画素への写し方は固定）か、全解像度と走査の画素の写像 — 走査が標本の位置を走査の
    画素へ写す所、最後の拡大の `position`（`correction-reconstruction.ts`。いまはブロックの中心を仮定する） — も同じずれで揃えるか。
    最後の拡大の `position` を直さないと、補正がフレームごとに最大 2 px（1/4 で、いまの代表 4p + 2 から 4p〜4p + 3 へ）ずれ、振動が
    増えて平均も余分にぼける（リスク表）。着手時に写像の箇所を数えて決める。
  - **画素ごとの乱択（perPixel。格子のずらしの懸念が気になったら試す）** — 走査の画素ごとに、ブロックの中の代表を乱数で選ぶ。全体の
    振動は出ない（ずれが画素ごとに独立なので、残りは粒の雑音になる）。代表の座標は画素ごとに持ち回るので、写像はいまのままでよい。
    **懸念** — 標本の並びが不規則になり、走査の際に別種のアーティファクトが出る（切片の方式は隣の標本と継ぐので、並びの不規則さに
    鋭敏なおそれ）。1 パスにも平均にも出るので、蓄積の前に読める。
  - 両方が気になったら、ユーザーと次の手を決める（例: 走査の画素の数十画素四方のタイルごとにずれを変え、タイルの中は格子のまま —
    振動はタイルごとに独立になるが、走査がタイルの境をまたぐ所に継ぎ目が出うる）。
- **3 ラスタライズのずれ** — render-lab の中だけで、カメラの射影を描画バッファの画素の 1 未満ずらす（`setViewOffset`。`ScreenSpacePass` は
  毎フレーム `camera.projectionMatrix` を写すので、走査も同じずれで読む）。`src/` へは入れない（手順7）。
- フレーム番号から 1・2 の位相を返す口（`frameJitterAt`）。この手順では列を仮置きし、下の「決めること」で決めた列にする。

**撮るもの**（`bay-earth-open`・`cornell-box`・`bay-dark`。最後の拡大の出力で読む — 蓄積はその後に入るため）

- **静止したカメラで、1 つの源だけを振る**（ほかの源は止める）。源ごとに seed 32 通り、走査の代表は格子のずらしなら 1/4 で 16 通りを
  全部（乱択なら番号 32 通り）、ラスタライズのずれは Halton(2,3) の 16 点で、拡散側の 4 種（1 パス・平均・平均からの偏差・分散）。3 つ全部を同時に振った組（位相の組 64 程度）も。
  - **読み方** — 分散の地図が、位置関係が動いたときのその源のちらつきの強さ。平均が、その源を動かして蓄積したときの収束先。位相を
    止めた 1 パスにあって平均に無い輝点はジッターと蓄積で消え、3 つ全部の平均にも残る輝点は推定量の偏りで、時間方向では治らない
    （拡散側「仮置きの推定量の既知の問題」へ返す）。
  - **混ざり** — 走査の代表を動かすと、走査の画素に貼り付いた乱数が表面に対して少し動くので、2 の分散に 1 が少し混ざる。次の剥がしと
    突き合わせて読む。
- **動くカメラで、源を 1 つずつ平均して剥がす**（手順2 の列）。各フレームで (a) そのまま、(b) seed を平均、(c) seed と走査の代表を平均、
  (d) 3 つ全部を平均、の 4 列を撮る。平均する源の位相は同時に振った組で取り（低食い違い列で 32〜64 組。直積にしない）、(b)(c) は G バッファを
  描き直さず走査より後だけを、(d) はフレーム全体を描き直す。隣り合う列の揺れの差が、その源の動いたときの寄与。(d) は、蓄積が動く
  カメラで目指す揺れの下限。
- 静止時の分散が剥がしの寄与を予見しているかを当てる。合えば、手順6 の源ごとの比較を静止時の 4 種で軽く済ませられる。

**2 の形の判断**（決めたこと 9 — 懸念した問題が起きているかを目視と数で読み、気になれば別の形を試す）

- **格子のずらし — 全体の振動が残るか**
  - 数: 位相ごとの偏差のうち、平均をその位相のずれだけ平行移動した差で説明できる割合（大きいほど、揺れが全体の平行移動に見える）。
    **蓄積の模擬** — 静止したカメラでは再投影が要らないので、蓄積を作る前に正確に模擬できる。位相の列を決めた順に回し、時定数 N
    （スライダーの範囲の数点）の指数移動平均を取った列の隣り合うフレームの差（手順2 の指標）を、seed だけを回した同じ模擬と並べる。
  - 目視: 模擬の列を手順2 で決めた見せ方で、時定数の短い端から。
  - 動くカメラで残る振動（再投影の双線形の読みが加わる）は手順6 で読み、そこで気になったときも乱択へ戻る。
- **画素ごとの乱択 — 走査に別種のアーティファクトが出るか**
  - 数: 代表を止めた 1 パスと比べた 1 パスの揺れの増え方（帯 0 の分散と、画素ごとの最大偏差と RMS の比 — 拡散側「輝点の見つけ方」の
    指標。白色雑音で約 2、1 回だけの輝点で √32 ≈ 5.7）と、平均の B からのずれ（構造誤差。代表を止めた平均・格子のずらしの平均と並べる —
    平均が動くなら、推定量の収束先そのものを変えている）。平らな面（`plane-case` など）と側面の ROI（拡散側の W1・W3）を分けて読む。
  - 目視: 1 パスと平均を、代表を止めた組との比較対照画像で。
- 先に試した形の懸念が気にならなければ、もう一方は試さない。試したら両方の数と画像を並べ、ユーザーの判定（原文のまま）を判断材料へ。

   扇形の丸めのずれをフレーム番号で回す。8-4 の決定的な散りばめは整列ブロックで層別しているので、フレームごとに回しても層別を保つか —

### 手順 4. 動きベクトル — カメラとの相対で

**目的** — 前フレームの画素を引く。画面上の動きは、いまと前フレームの**カメラとの相対の**位置を、それぞれのフレームのカメラの回転と
射影で写した差（決めたこと 7）。物の絶対座標の動きは使わない。

**形**

- **前フレームの位置** = 前フレームの描画の座標（カメラが原点）での物の model 行列 × 頂点。描画の座標は CPU が毎フレームカメラを原点に
  作り直すので、前フレームの `matrixWorld` を持っておけば、カメラの並進・物の軌道運動・自転がまとめて入る。浮動原点を別に扱う必要は
  無い（旧計画の「浮動原点の移動も対応づけに入れる（推測）」を取り下げる）。大きな並進は CPU の倍精度で引いた後の値だけが GPU へ渡る
  — 前フレームの値も前フレームに CPU が作った値なので、精度の扱いは今と同じ。
- **カメラの回転** — CPU が前フレームのカメラの回転（カメラは原点にあるので `matrixWorldInverse` は回転だけ）と射影を uniform で持ち、GPU が
  前フレームの clip 座標を作る。
- three 0.185.1 の `velocity`（`VelocityNode`）がちょうどこの形 — 物ごとに前フレームの `matrixWorld`、カメラごとに前フレームの
  `matrixWorldInverse` と射影を持つ。描画物がこの前提に乗るなら使い、乗らない描画物だけ同じ形の uniform を自前で持つ。
- **ジッターを含めない** — 射影は前後ともジッターなしのもの（`VelocityNode.setProjectionMatrix`。`TRAANode` の形）。

**コードの現状**（`acea60fc6` の時点で確かめた。着手時に確かめ直す）

- 描画の原点はアクティブカメラの ECI 位置で、カメラの `position` はつねに 0（`camera-view.ts` の `sync` → `syncCameraToViewpoint` と
  `FloatingOrigin(position, …)`）。姿勢は `lookAt` で毎フレーム置く。
- 描画のどこにも、前フレームの履歴の target・TAA・動きベクトル・前フレームの view / projection・再投影が無い（`ScreenSpacePass` は
  描画のたびにいまの projection を受け取る）。
- `VelocityNode` は、物の前フレームの行列を物を描いた後（`updateAfter`。物ごと）に写し、カメラの前フレームの行列はフレーム番号ごとに
  1 度だけ進める。速度のノードは G バッファの MRT にだけ置くので、マテリアルパス・世界パスで同じ物を描き直しても前フレームの行列は
  進まない見込み（確かめる）。G バッファは層ごとに 2 回描くが、描く物は重ならない。
- 前フレームに描かれなかった物（視野の外・LOD のタイルの切り替え・新しい物）の前フレームの行列は、古いか今と同じになる — 棄却（手順5）に頼る。
- `InstancedMesh` のプール（`instanced-pool.ts`。弾・薬莢・飛散片・天体の点群）は毎フレーム積み直すので、個体の番号と実体の対応が
  フレームで変わる。`VelocityNode` は個体の前フレームの行列を持たない — G バッファに入る（lit の）プールは、実体ごとに前フレームの
  行列を持つか、棄却に回す。
- 透視と平行投影でカメラの実体が別（`CameraView` の 2 つ）なので、切り替えたフレームは履歴を捨てる（`reset`）。
- render-lab の場面は世界に静止し、カメラは原点に無い（`lab-case.ts` などが `camera.position` を置く） — ゲームの形とは違う。

**変更が必要な箇所**

| --- | --- |
| `src/render/pipeline/gbuffer.ts` | 動きベクトルの出力（rg16f）。`velocity` ノードを使うか、前フレームの行列を自前で持つかは上の形に当てて決める |
| 独自の頂点シェーダを持つ G バッファの描画物（雲殻・天体の表面・タンパク質の motion など）と、lit の `InstancedMesh` のプール | 動きベクトルを正しく書くか、書けないなら棄却に回るか |

ゲームの自転する天体・動く船 — 全てが軌道を回る場面）で、表示の動きと動きベクトルが一致する（デバッグ表示）。

### 手順 5. 蓄積

**着手時に決めること**（どれもユーザーと決める）

1. **棄却の判定** — 深度・法線の面の重み（拡散側の `SurfaceWeight`）を流用するか。雑音の多い 1 パスの信号に TAA の近傍 clamp / variance
   clipping を使うと、正しい履歴を切り詰めて暗部・接地の影を偏らせ、ちらつきを増やしうる（前例の注意）。
2. **履歴の上限 N と時定数の対応**と、照明の変化の検出（anti-lag）の要否。
3. **撮影の再現性** — 同じ入力と同じ履歴からは同じ画像にする形（例: 履歴を消して、手順3 で決めたジッターの列で N フレーム積む）。

ジッターの列は手順3 で決めたものを `frameJitterAt` でフレーム番号から回す。時定数を最小にしたら、蓄積と一緒にジッターも止める
（変えないもの）。成分ごとに止める口は、デバッグと render-lab に残す（手順6 の切り分け）。

**先行研究**（Luna の調査。実装の前に原典で式と既定値を確かめる — 未確認の値がある）

- **履歴の長さを画素ごとに運ぶ**（決めたこと 3） — 新しいフレームの重みを α = 1/(n+1)（n は積んだフレーム数。蓄積の初めは算術平均）
  とし、上限 N からは α = 1/N の指数移動平均にする。NRD の REBLUR / RELAX（https://github.com/NVIDIA-RTX/NRD の README）は履歴の
  長さと上限 `maxAccumulatedFrameNum`（= 残像の時定数）を持ち、確からしさで縮める — REBLUR は
  `historyLength *= lerp(confidence, 1, 1/(1+historyLength))`、RELAX は `historyLength = min(historyLength, maxAccumulatedFrameNum·confidence)`。
  SVGF（Schied ら 2017）も時間方向の蓄積と再投影の検証を持つ（α の既定値は未確認）。
- **静止時の実効の標本数** — 上限 N の算術平均なら N、α 固定の指数移動平均なら (2 − α)/α。時間相関・棄却・動きがあると積だけでは
  決まらない。ジッターの列の周期（格子のずらしは 1/4 で 16）が N より短いと、層別の利得が周期で頭打ちになる。
- **照明の変化で履歴を縮める** — A-SVGF の temporal gradient（Schied ら 2018）、NRD の anti-lag / HistoryFix。追加のバッファと計算が要る。
  最大の重みの制限（決めたこと 4）で残像が許せないときの次の手。
- **再投影と棄却** — 前フレームの位置を動きベクトルで引き、深度・法線（平面距離）で履歴を棄却し、双線形で読む。
- **フレームごとの乱数** — XeGTAO・GTAO は回転と歩のずれを時間方向にも変える。Spatiotemporal Blue Noise（Wolfe ら 2022）は画面と時間の
  両方でブルーノイズ。8-4 の散りばめをフレームごとにどう回すかの前例は見つからなかった。
- **ジッターと動きベクトル** — three の `TRAANode` は Halton(2,3) のずれを `setViewOffset` で入れ、動きベクトルはジッターなしの射影で書く。
- Split RC も 1 フレームと時間方向の蓄積の両方で評価している（組み合わせの前例）。

### 手順 6. 評価とユーザーの判定

- **源ごとの切り分け**（決めたこと 8） — 静止したカメラで、1 つの源だけジッターを入れて（ほかは止めて）蓄積した絵が、手順3 のその源の
  平均へ収束するか（蓄積の検算。収束しなければ蓄積か再投影の誤り）。動くカメラで、ジッターを 1 → 1 + 2 の順に足して蓄積した揺れを、
  手順3 の剥がしの (b)〜(d) と並べ、残った揺れがどの源かを読む。
- **2 の形の振動**（格子のずらしを採ったとき。決めたこと 9） — 動くカメラで、時定数の短い端から、照り返しの全体が平行移動で振動して
  見えないかを目視し、手順3 の蓄積の模擬と並べる。気になれば画素ごとの乱択を試し（手順3 の口と判断のやり方で）、ここへ戻る。
- **ちらつき** — カメラを少しずつ動かした連続フレームで、同じ表面の点の値のフレーム間の揺れを、蓄積の前後で比べる（手順2 の指標）。
- **静止時の収束** — 静止したカメラで N フレーム積んだ画像を、B と、同じ仮想のスライス数の 1 フレーム（スライスを増やした raw）と比べる。
  動かない輝点が残っていないか（達成目標2）。
- **残像** — 送り手・光源を動かしたとき、影と照り返しの残像が消えるまでのフレーム数（時定数どおりか）。手順2 の道具は光源の方位を
  回す列（`light`）だけを持つ — 送り手の幾何（光る箱・立方体など）を動かす列は、ケースの物を動かす口を足してから撮る。
- **費用** — 再投影して混ぜる行と動きベクトルの書き込みの増分（同じページで交互に）と、中間 target の増分。
- **見せ方** — 動く絵は手順2 で決めた形で。静止時の収束は比較対照画像（補正項だけ・全体・撮影ごとに一貫した露出・候補をボタンで
  切り替え、動かさない値を書く）。

**達成条件** — 達成目標1〜4・6・7 の表と画像、ユーザーの判定（原文のまま）を判断材料へ。時定数の範囲と既定の仮置き。ラスタライズの
ジッターが要るかの結論（手順7 へ進むか）。

### 手順 7. ラスタライズのジッター（条件つき — 手順3 か 6 で要ると決めたときだけ）

**目的** — 1 と 2 を動かして蓄積しても、ラスタライズ由来のちらつきが容認できないとき、G バッファの射影を描画バッファの画素の 1 未満ずつ
フレームごとにずらす。

**この手順だけ契約の外にある** — 射影をずらすと画面全体が揺れる（縁が ±½ px 動く）ので、ΔE の蓄積の中に閉じない。最終の色の時間方向の
解決（TAA。three の `TRAANode` が前例）が要り、仕様、いまのアンチエイリアスの選択肢（なし / FXAA / SMAA）、決めたこと 1、`render-pipeline.ts`
の実行順にかかる。**このブランチで進めるか、別の計画にするかをユーザーと決めてから着手する**（見積りもそのとき）。

**二度手間にならない部分** — 動きベクトル（手順4 でジッターを含めない形）、ジッターの口（成分を 1 つ足す）、ΔE の蓄積（雑音の多い信号は
近傍 clamp なしで積み、最終の色の TAA と分ける — 手順5 は残る）、手順2・3 の道具（ラスタライズのずれは render-lab で作ってある）。

### 手順 8. 送り返す

**目的** — `screenspace-temporal` を push し、`screen-space-lighting` の側が取り込めるようにする。

**達成条件**

- 達成目標を 1 つずつ当てた結果と、`screen-space-lighting` の側へ伝えることをこの文書に書く: 新しい描画先・GPU の行・デバッグ表示・描画設定の
  項目、時定数の仮置きの値、走査の代表の口と採った形（拡散側の手順9 で走査の解像度を変えても、動かす幅は走査の画素の幅から決まり、1 で消える）、
  拡散側の 13-a（最後の拡大のタップ数）は蓄積を入れた絵で読むこと、手順3 で見つかった時間方向では治らない輝点。
- `screen-space-lighting` の側で取り込んだら、この計画ファイルを消すか残すかをユーザーに問う（`memos/` は人間が管理する）。

## 判断材料

### 手順1 の仕様（2026-10-12、`a086bd6c7`）

`DEVELOP/SPEC/RENDERING.md` に 2 か所を書いた。「近似が生む揺らぎ」節に、近くの構造による拡散光の遮蔽と照り返しは時間の正確さも
譲ってよい（INVARIANTS §2 の例外。遮る構造・照り返す面・光の当たり方の変化に遅れて追いつき、残像は時定数のうちに消える。受け手や
カメラが動いても受け手の面とともに動き、尾を引かない）。「描画品質設定」節に「遮蔽と照り返しの時定数」（長いほど揺らぎが均され残像が
長い、最小では前のフレームを引き継がず残像は出ない）。ちらつかないこと・動かない輝点を残さないことは一般則（INVARIANTS §1・§7、
「近似が生む揺らぎ」節）が言うので書かない（ユーザー）。時定数の単位・範囲・既定は書いていない。ラスタライズのジッター（画面全体の
TAA）は、手順7 で採るときに仕様を書く。

### 手順2 の道具と再現（2026-10-12、`bb69da6bb`。周回の列は `c20fa4375`）

**道具** — `node tools/render-lab-motion.mjs <組の名前> [--scenes=…] [--sequences=…] [--frames=N] [--average=K]`（先に `.render-lab/` を
組む）。`.render-lab-shots/<組の名前>/` へ、場面と列ごとのフレームの PNG（全体・補正・補正の差 ×4。`--average` を渡すと seed K 個の
平均の補正とその差も）、`report.md`（列ごとの揺れの表）、`metrics.json`（フレームごとの要約）、`index.html`（見るページ）を書く。

- **列** — `still`、`translate-{0.25,0.5,1,2,4,8}px`（並進）、`rotate-{同じ}px`（カメラを中心とする回転）、`orbit-{同じ}px`（周回の
  中心 = 注視点を中心とする回転）、`light`。1 フレームの動きは、並進は周回の中心の深さの点の、回転と周回は無限遠の点の、描画バッファの
  画素で与え、向きは横から 30°（画素の格子に沿う向きは走査の格子の決まった位相だけを踏む）。周回は周回の中心を画面の中心に留め、
  面を見る向きを同じ画素の並進と同じだけ変える（s px で s / 焦点距離 [rad]。中の設定の画角 50° で 1 px ≈ 0.1°）。
  `orbit` はユーザーの依頼で足した（2026-10-12、原文「カメラの列として、平行移動とカメラを中心とした回転がありますが、対象（注視点）を
  中心とした回転を追加してください。側面の面積が変化するため時間変化の影響が大きく出るはずです。」）。
  `light` は光源の方位を 0.5°/フレーム回す（bay-earth-open は地球、cornell-box は恒星。bay-dark は光源が光る箱だけなので無い）。各 16 フレーム。
- **撮影の設定** — 映り込み・レンズ効果・アンチエイリアスを切り、照り返しまで描く。seed はフレームごとに (0, 0)（本番と同じ）。
- **指標** — 前のフレームの補正を参照の再投影（`tools/render-lab/reference-reprojection.ts`。いまの深度から位置を戻し、前のフレームの
  カメラで写す。倍精度。前のフレームの 2×2 の近傍の素の深度が写した点に比 1e-3 で合わない画素と、近傍が画面に収まらない画素を除く）で
  双線形に読み、いまの補正から引いた差。再投影のある画素の q = 露出係数·ΔE/π の成分の RMS（差・値）と、差 / 値、|差| の 99% 分位と最大。
- **口（手順3 以降が使う）** — `LabView.setCameraShift`（カメラの座標の剛体の変換を重ねる）、`readFloat('depth')`、
  `averageCorrection(seeds)`（同じ G バッファのまま補正を seed の列で描き直した平均。`PassAccumulator`）、`captureSettled`（public へ）。
  `MotionSequence`（`reset` / `moveCamera` / `frame(averagedSeeds)`。補正の列 single / averaged ごとに前のフレームを持つ）。手順3 の
  剥がしの (c)(d) は、`frame` の列と、平均する位相の種類を足して作る。

**自己検算**

- 止めた列: 差 RMS 2e-16〜2e-15、|差| 最大 2e-14〜1.1e-13 — 倍精度の丸め（写した座標が画素の中心から 1e-13 px ほどずれた双線形）で、
  0 に一致。再投影の割合は 0.994〜0.998 で、除いたのは画面の端の画素（丸めで画面の外へ出る）と、面の無い画素に接する画素。
- `averageCorrection` に seed (0, 0) を 1 つ渡した平均は、そのフレームの 1 パスの補正と PNG がバイト一致（cornell-box の 4 フレーム）。

**再現**（`.render-lab-shots/temporal-step2/`。差 / 値 — 隣り合うフレームの同じ表面の点の補正の差の RMS と、補正の RMS の比）

- 周回は、同じ画素（面を見る向きの変化が同じ）の並進・回転より揺れが小さく、遅いほど差が開く（周回 / 並進・回転は 0.25 px で 0.44〜0.52、8 px で 0.92〜1.09）。

  面を見る向きの変化（側面の写る面積の変化）より、面に対して画面が滑ること（画面に貼り付いた乱数と走査の格子が面の上を動くこと）の
  ほうが、いまの揺れの大半を作っている見込み。手順3 の剥がしで確かめる。
- `light` の差は、光源が動いたことによる補正の本当の変化も含む（ちらつきだけではない）。手順6 の残像の列として使う。

回す形だけにした（2・4・8・15・30 fps、←/→ でコマ送り、空白で回す/止める）。

**手順2 から外したもの** — 送り手の幾何を動かす列は手順6 へ（ケースの物を動かす口が要る）。履歴を消して決まったジッターの列で
