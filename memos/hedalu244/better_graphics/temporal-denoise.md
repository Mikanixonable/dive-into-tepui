## 目的

近傍拡散補正のちらつきを消す。ちらつきの元は 3 つあり（決めたこと 8）、どれも「フレームごとに動かしてから時間方向に平均する」で
治る見込み:

1. **走査の乱数** — ブルーノイズは画面（走査の画素）に貼り付いているので、カメラが動くと同じ表面の点が違う乱数を引く。1 パスの
   雑音（色ムラ・粒・最後の拡大の疎なタップのざらつき）もこれ。
2. **走査のダウンサンプリング** — 走査は 1/4 の解像度で、4×4 の G バッファの画素のうち決まった 1 つ（ブロックの中心 —
   `gbufferTexelOf`）を代表にする。かすめる面（視線にほぼ平行な側面。0〜2 px でしか写らない）を代表が踏むかで、切片の方式が
   鋭敏に変わる（`screenspace-diffuse.md`「仮置きの推定量の既知の問題」）。
3. **幾何のラスタライズ** — 全解像度の G バッファでも、かすめる面の写り方は画素の中心に乗るかで決まる。全解像度の B にも輝点がある。

2 と 3 の輝点は、カメラと物の位置関係が動かなければ動かない — そのまま時間方向に平均しても消えず、位置関係が少し動くと鋭敏に
変わってちらつく。だから意図的にジッターで動かしてから平均する。前フレームの補正を再投影して混ぜる時間方向の蓄積（temporal AO）を
足し、1〜3 を動かして均す。

## 決めたこと

### ユーザーが決めたこと

1. **蓄積するのは、最後の拡大の後（描画バッファの解像度）の補正項 ΔE だけ**（2026-10-12）。拡散照度（遠方光 + ΔE）や陰影は
   蓄積しない。最後の拡大の確率的な粒も均すため、拡大の前の C_0 ではなく後で混ぜる。描画バッファの解像度の、拡大済みの補正項
   単体の描画先は残る — 拡散側では、最後の拡大をライティングの読みへ畳む案をこれを理由に取り下げた（拡大の費用の主因は読み書き
   ではなくタップ数で、タップによるざらつきは蓄積で治す）。
2. **再投影は動きベクトルで行う**（2026-10-12）。カメラの動きだけでなく、動く物（自機・敵・天体の自転と公転）も追う。求め方は決めたこと 7。
3. **履歴の重みも積算する**（2026-10-07）。単に重みで前フレームと混ぜるだけだと、最新のフレームがつねに最大の影響力を持つ
   （ユーザーが以前、別のプロジェクトでそう実装した）。積算された過去フレームの価値を見積もる重み（履歴の長さ）を画素ごとに運ぶ。
4. **残像に上限を置く**（2026-10-07）。受け手の幾何が動かなくても、送り手やその明るさが動くと影や照り返しが残る。過去フレーム側の
   最大の重みを制限し、一定の時定数で消えるようにする。残像は、ちらつきや静止時の色ムラより品質への罰が小さい。
5. **時定数は独立なスライダーにする**（2026-10-12）。スライス数と組にしない — 拡散側の決めたこと 28 の「処理時間の分散」（スライス数と
   時定数を 1 軸に組む）は、拡散側の決めたこと 40 で覆った。プリセットの値は `graphics-settings-feature.md` の手順5で決める。この計画では
   時定数を描画設定の値として受け、範囲と既定を仮置きする。
6. **評価は静止画で比べられない**（2026-10-07）。動く絵の道具を作る。
7. **動きベクトルはカメラとの相対座標から求める**（2026-10-12）。物が動いていなくてもカメラが動けば追うべきで、そもそもこの
   ゲームでは全ての物が軌道の上を動いていて静止した物が無い — 物の絶対座標（ECI）の動きを動きベクトルにすると、おかしくなる。
   カメラとの相対の位置関係は CPU の側で解けていて、カメラの位置を 0 にして与えている（浮動原点 = カメラの ECI 位置）。カメラの
   回転は解けていないので、CPU か GPU のどちらかで入れる。
8. **ちらつきの元を 3 つに分け、どれも動かしてから時間方向に平均する**（2026-10-12）。今あるものを時間方向に平均するだけでは
   ちらつきを抑えられない見込みがある — 走査の乱数が変わって生じるちらつき（当初の計画）のほかに、側面のラスタライズに由来する
   ちらつきがあり、1/4 の走査解像度へダウンサンプリングしているので影響が大きい。これは、カメラや物が動かなければ動かない輝点として
   残り、位置関係が動くと鋭敏に変わるので、意図的にジッターで動かしてから平均しないとちらつきになる。TAA のように、ダウンサンプリング
   とラスタライズをジッターするところまで視野に入れる。どれが原因かを評価するときは、ほかのジッターを止めて切り分ける（例: 2 を
   評価するときは 1 と 3 を動かさない）。場合によっては、拡散補正項の蓄積だけでは目的を達せない（Backlog「ラスタライズのジッター」。
   決めたこと 11）。
9. **ダウンサンプリングのジッターの形は事前に決めず、試して判断する**（2026-10-12）。縮小写しにジッターを入れると、走査のときの幾何
   からの復元まで影響が出る。画素ごとに代表の選び方を乱択する形は、走査の際に別種のアーティファクトを生むおそれがある。ピクセル
   グリッド全体をオフセットする形は、そのような弊害はない反面、照り返しの全体が平行移動で振動しているかのように見えるちらつきが
   出るおそれがある。両方リスクがあるので事前には決められない — 実装してみて、懸念した問題が起きているかを目視または定量評価で
   判断し、問題が気になれば別の方法を試す。
10. **本番のジッターは seed と走査の代表（格子のずらし）の両方で、乱択は試さない**（2026-10-13）。原文「OK、私にも平行移動の問題は
    特に見えなかったので、代表の乱択を試す必要はないと判断した。seed+representativeで良いだろう。」列は手順3 で実装したもの
    （`frameJitterAt` — seed は R2 列、代表は Bayer 順の周期 16。判断材料「手順3 の口と道具」）。
11. **ラスタライズのジッターは Backlog へ回し、将来実装する**（2026-10-13）。原文「ラスタライズのジッターは有効ではあるが、SSGIに効くと
    いうよりAAに効いている部分もあるため、補正項だけでなく別（最終出力など）で蓄積を取るのが良いと思う。計画の範囲を超えるため、
    backlogへ回し、将来実装する。」旧手順7 は Backlog「ラスタライズのジッター」へ移した。
12. **render-lab に、毎フレーム積み直すプールと動く物を再現するケースを作る**（2026-10-13）。原文「まず、labにInstancedMeshのケースがない
    ことや、動くもののテストケースがない点が問題。できる限り実機の状況を再現するというのが目的なので、（物理とかはいらないが）毎フレーム
    詰み直されるInstanced-poolを確認できるケースが必要。一つのケースで得られる情報を多くするため、cornell-boxのような部屋に多数の薬莢が
    instanced-poolで置かれているようなケースがあるとよいと思う。カメラや通常の物体の動きも適宜labで検証できるようにしないといけない。」
    手順4-1。

### エージェントが決めたこと（2026-10-13。ユーザーが覆せる）

three 0.185.1 の読みは `node_modules/three/src/` の行番号で、`f10576e80` の時点。

14. **three の `velocity`（`VelocityNode`）を使わず、前フレームの記録を自前で持ち、呼び出し側が渡すフレーム番号で回す。** three の記録は
    このゲームと lab の形に合わない:
    - 物の前フレームの行列を、**描くたびに**今の行列で上書きする（`VelocityNode.js:152-154`。フレームの区切りを見ない）。lab は 1 つの
      フレームを 2〜6 回描く（`captureSettled`）ので、物の動きが 0 になる。
    - カメラの前フレームの行列は three 自身の rAF の tick（`frameId`）で回る（`Animation.js:71-79`）。描画の呼び出しと揃わない。
    - `InstancedMesh` の前フレームの行列は**枠の番号ごと**で（`Instance.js:215-229`）、しかも描く直前に今の行列で上書きするか、最初の値の
      まま送り直されない（器の版を上げない）。積み直すプールでは別の実体を引く。
    - `positionNode` の変位を前フレームの側に足さない（`positionPrevious` は素の頂点 — `Position.js:54`）。変位が静止していても動きになる。
    - 隠れた・視野の外の物は前フレームの行列が古いまま残り、再び出たフレームで何フレームぶんもの動きになる。

    覆すと: 4-3 の `MotionHistory` が three の `velocity` と回避策に替わり、lab の撮影は 1 フレームを 1 度だけ描く形に縛られる。
15. **MRT の名前は `motion` にする（`velocity` にしない）。** `velocity` の名前があると、three は G バッファの全 `InstancedMesh` へ枠の番号で
    引く前フレームの器を付けて容量ぶんの写しを描くたびに走らせ（`NodeBuilder.js:3449-3455`・`Instance.js:219-225`）、そのパスで描いた
    影を落とす物には以後ずっと前フレームの仕掛けを付ける（`ShadowNode.js:55-58`・`741-748`）。
16. **前フレームが無い画素は棄却の印を書く。** 前フレームが無い（初めて描く・番号が飛んだ・カメラの実体が替わった・プールに現れた実体）
    物は前の行列を零にし、前の clip の w ≤ 0 の画素は画面の外を指す値を書く。読む側は「前の uv が画面の外なら捨てる」の 1 つの判定で
    落とせる。覆すと: 手順5 が印を別の判定で読む。
17. **タンパク質の残基の変位は前フレームも今の変位で写し、雲殻は深度へ書く交点で写し、天体の分割段は親を履歴の鍵にする。** タンパク質は
    残基の変位の器を 1 枚しか持たず毎フレーム上書きする（`protein-motion-material.ts`）ので、前フレームの変位を残すには器を足すことになる —
    誤差（変位の 1 フレームの変化）を 4-3 で測り、0.5 px を超えたら問う（超えたので問い、棄却の印になった — 決めたこと 20）。雲殻は殻の頂点で写すと、殻と交点の奥行きの差だけ視差が誤る。
    分割段は同じ親へ単位の変換で置かれているので、親を鍵にすれば段が替わったフレームも前フレームを引ける。
18. **lab のケースは本番の `CasingPool` へ直に積み、動きの参照は CPU のレイで実体ごとに求める。** `CasingView`（`DynamicView`）は通さない —
    置き方は位置と姿勢を写すだけで、積み直しの経路（`InstancedPool.push`）は同じ。参照を GPU と同じ行列の組み方（深度から戻す・番号で
    引く）で作ると、同じ誤りを見逃す。

19. **動きの参照の自己検算は CPU の経路どうしで取り、GPU の深度との差はラスタライズの丸めの上限と比べる。** 4-2 の当初の条件
    「レイの参照と深度による参照の再投影の差の最大 1e-6 px（2 つの独立な CPU の経路）」は、深度の参照が GPU の深度を読むことを
    見落としていた — GPU は頂点の画面の位置を画素の 1/256 の格子へ丸めるので、画素の中心の深度は「深度の勾配 × 最大 1/512 px」
    ずれ、深度の参照の動きは「動き × 深度の相対誤差」だけずれる（並進 4 px で 1e-4 px。回転は深度に依らず 1e-13 px）。そこで
    （A） レイの当たりの点の深度を深度の参照と同じ写像へ通した動きとレイの参照の差を 1e-6 px 以下、（B） 当たりの深さと G バッファの
    深度の相対差 ρ を近傍のレイの深さの勾配 g からの上限 2⁻⁹·g + 1e-6 と比べる、に改めた。輪郭には、近傍のレイが別の実体へ当たる
    画素のほか、近傍の深さの 2 階差が 1e-3·d を超える画素（自己遮蔽の縁・折れ目）も含める。4-3 の許す誤差（0.01 px 以上）はこの
    丸めより十分大きいので変えない。覆すと: （A） の閾値を GPU の深度の参照へ当て直すことになり、並進・周回の列は通らない。
21. **動きの uniform は、three が物ごとの更新を飛ばす条件に合わせて分ける。** three 0.185.1 は、行列も材質も前の描画から変わらない物の
    物ごとの更新（`updateType = OBJECT` の `update`・`onObjectUpdate`）と束縛の更新を飛ばす（`Renderer._renderObjectDirect` の
    `needsRefresh`、`NodeMaterialObserver.needsRefresh:718-741`。observer は同じ材質の描画物で 1 つ。材質が節の属性を持つ・初回・MRT が
    `velocity` を持つ・その observer で描画の最初の 1 物、のときだけ必ず更新する）。前の clip の行列を物ごとに渡す当初の形では、静止した物の
    動きが古い値のまま残った。共有の uniform buffer（`sharedUniformGroup`）へ物ごとに書く形も、WebGPU では全物体が最後に書いた値で描かれる。
    そこで、カメラの 今・前 の射影 × view と番号を描画ごとの組（`renderGroup`）へ、物ごとには前の model 行列とそれを書いた番号だけを置き、
    番号が古い物（前回の更新から行列が変わっていない）は今の `modelWorldMatrix` を前にも使う。割り切り: (a) 前の clip を CPU の倍精度で
    1 つの行列にする当初の形をやめ、GPU の単精度で組む（描画の座標はカメラが原点なので、今の絵を描くのと同じ精度。照合の許す誤差に
    収まった）。(b) 行列が変わらない物は前フレームに描かれたかを確かめられない — 隠れていた静止物が同じ行列で再び出たフレームは、棄却の
    印ではなくカメラの動きだけの動きになる（幾何としては正しい。浮動原点のゲームでは、ほとんどの物が毎フレーム行列を変える）。
    覆すと: MRT の名前を `velocity` にして全物を毎回更新させる（決めたこと 15 の費用を払う）か、物ごとの番号を storage へ置く形に作り直す。
### 前提として守る契約

並行する拡散側の作業（`screenspace-source.md`・手順9〜11）と衝突させないため。

- **蓄積は `src/render/pipeline/screen-space/` の中に閉じる。** 補正を読む側は、今と同じく `DiffuseCorrection.texture`（`at` / `atUv`）を
  読み、それが蓄積後の値になる。読む側のコードと `render-pipeline.ts` の実行順は変えない — 読む側はいまライトプリパスの光源
  `DiffuseCorrectionSource` で、`screenspace-source.md` の後はマテリアルと映り込みの像の元になる。最後の拡大の出力（蓄積の前）は別の
  描画先にし、デバッグ表示を足す（`/rendering-workflow`「中間バッファを観測可能にする」）。**ラスタライズのジッター（Backlog）は画面全体を
  揺らすので、この契約の外にある** — render-lab の中だけで作る。
- **走査の代表の動かし方（ダウンサンプリングのジッター）は `screen-space/` の中に閉じる** — 代表の選び方（と、格子をずらす形なら全解像度と走査の
  画素の写像）だけを動かす。走査の幾何の復元には影響が出る（決めたこと 9）。ずれの幅は走査の画素の幅（描画バッファ / 走査の解像度）から
  決め、1/4 に決め打たない（拡散側の手順9 が走査の解像度を 1/2・1・1/8 にする。1 で消える）。
- **動きベクトルは G バッファに 1 枚足す。** いまの 4 枚（rg16f・r8・rgba16f・rgba16f）で 1 標本あたり約 22 B、rg16f を足して約 26 B で、
  WebGPU の既定の上限 32 B（`maxColorAttachmentBytesPerSample`）に収まる。`requiredLimits` は触らない（拡散側の手順10 が触る）。
  **動きベクトルにジッターを含めない**（前後ともジッターなしの射影で写す） — Backlog のラスタライズのジッターを足すときに書き直さない。
  MRT の名前は `motion`（決めたこと 15）。
- **描画パイプラインはフレーム番号を受ける**（`RenderPipeline.render` の引数。決めたこと 14）。同じ番号で呼び直すと、動きベクトルの記録を
  回さない — 手順5 の履歴とジッターの列も同じ番号で回す。ゲームは描画ごとに 1 つ進め、lab は論理フレームごとに 1 つ進める。
- **render-lab の道具は新しいファイルに置き、`tools/render-lab/lab.ts` への変更を最小にする**（拡散側の手順9〜11 も触る）。手順4 で `lab.ts` に
  足すのは `setFrame`、ケースの `dispose?` の呼び出し、`readFloat('motion')`、`pipeline.render` へ番号を渡すことだけ。
- **局所反射**は、像の元が ΔE を含む照度を読むので、蓄積後の ΔE が映り込みにも入る（意図どおり）。局所反射の追跡と置換重み w は、

  写しを読まない — `acea60fc6` の時点）。

## 変えないもの

- 時定数を最小（履歴を使わない）にした絵が、蓄積を入れる前と同じ。**このとき、フレームごとに動かす入力（seed・走査の代表）も止まる。**
- 走査の代表の既定（null）が、いまの代表の選び方と同じ絵になる。
- 同じ入力と同じ履歴からは同じ画像になる（render-lab の撮影は、履歴を消して決まったジッターの列で N フレーム積んだ画像を 1 枚にする）。
- 補正は拡散照度にだけ掛かる。鏡面・直射・影は変えない。
- 動きベクトルを足しても、最終の絵は変わらない（手順4 の時点 — `render-lab:compare` で 0 件封筒外）。

## 達成目標

1. カメラを少しずつ動かした連続フレームで、同じ表面の点の補正のフレーム間の揺れが蓄積の前より小さく、ユーザーがちらつきを容認する。
2. 静止したカメラで N フレーム積んだ画像に、カメラが動かないと動かない輝点が残らず（採ったジッターの源の平均 — 手順3 — に収まる）、

3. 送り手・光源を動かしたときの影と照り返しの残像が、時定数どおりのフレーム数で消える。
4. 動く物（自機・敵・天体の自転）の上とその縁に、履歴の取り違えによる尾が出ない。
5. 時定数を最小にした render-lab の撮影が、蓄積の前の組と `npm run render-lab:compare` の封筒内。

## 手順

### 手順の組み立て（2026-10-12、エージェント）

- **源の寄与を、動きベクトルと蓄積を作る前に量る（手順3）。** 静止したカメラで 1 つの源の位相だけを振り、ほかを止めて N 枚撮れば、
  その平均がその源を動かして蓄積したときの収束先、平均からの分散が位置関係が動いたときのちらつきの強さになる（動くと位相が変わる
  ため）。拡散側の「総合的な品質の検査の 4 種」を、seed だけでなく走査の代表・ラスタライズのずれへ広げたもので、蓄積も動きベクトルも
  要らない。動きベクトル（4 h）と蓄積（3.5 h）の前に済ませれば、(a) どのジッターを本番に入れるか、(b) ラスタライズのジッター（画面全体の
  TAA）が要るか、(c) 全部を動かして平均しても残る輝点（推定量の偏り — 時間方向では治らない）があるか、が先に分かる。(c) が大きければ、
  蓄積を作り込む前にユーザーへ返す。
- **源を入れる順は 1 → 2 → 3**（費用と影響範囲の小さい順）。1 は seed の uniform（`ScreenSpacePass.setSeed`）が既にある。2 は走査の中
  （全解像度と走査の画素の写像）に閉じる。3 は G バッファの射影を動かすので画面全体が揺れ、決めたこと 1 と契約（蓄積は `screen-space/` に
  閉じる）に収まらない — 手順3 の実測の後、ユーザーが Backlog へ回した（決めたこと 11）。2 と 3 は尺度で分担する: 2 は走査の画素の中を
  描画バッファの画素の刻みで、3 は描画バッファの画素の中を動かす。
- **2 の形は格子全体のずらし**（決めたこと 9 → 10）。乱択は同じ口（`setScanJitter`）のもう 1 つの種類として残るが、試さない。
- **止め方は、カメラが止まっているかで変える。** 静止したカメラでは、ほかの源を止めれば 1 つの源だけが動く（ユーザーの切り分け）。動く
  カメラでは、止めた源も位置関係の変化で動いてしまうので、止める代わりに各フレームの中で平均して消し、源を 1 つずつ剥がす（手順3）。
- **二度手間を避けるための共通化**
  - ジッターの口は 1 つ（`frameJitterAt`）。手順3 の計測、手順5 の本番、手順6 の切り分けが同じ口を使い、成分ごとに止められる。
  - 手順2 の道具の**参照の再投影**（深度とカメラの前後の行列から写す）は、ちらつきの指標（同じ表面の点の揺れ）と、手順4 の動きベクトルの
    検算の両方に使う。
  - 手順3 の源ごとの静止時の平均は、手順6 で蓄積の静止時の収束を源ごとに検算する参照になる。
  - 動きベクトルは最初からジッターを含めない形で書き、ジッターの口は成分を足せる形にする — Backlog のラスタライズのジッターを足すときに
    書き直さない。採っても、ΔE の蓄積（雑音の多い信号を近傍 clamp なしで積む）は最終の色の TAA と分けて残る（前例の形）。
  - 手順4-1 の通常物体の部屋（動く物・少数の熱した薬莢）と大量薬莢のケース（積み直すプール）、フレーム番号で状態を置く口は、手順6 の
    残像の列（送り手の幾何を動かす）と動く物の尾の確かめにも使う。描画パイプラインのフレーム番号（手順4-3）は、手順5 の履歴と
    ジッターの列も回す。
- **手順4 は再現と参照を先に作る**（2026-10-13、エージェント）。lab にはプールを毎フレーム積み直す場面も動く物も無く（決めたこと 12）、
  いまの参照の再投影は世界の静止を前提にする。動きベクトルを書く前に、ゲームの状況を再現するケース（4-1）と、GPU と経路を共有しない
  参照（4-2）を作り、通常の物（4-3、絶対目標）とプール（4-4、努力目標）をそれで確かめる。

### 手順 5. 蓄積

**着手時に決めること**（どれもユーザーと決める）

1. **棄却の判定** — 深度・法線の面の重み（拡散側の `SurfaceWeight`）を流用するか。雑音の多い 1 パスの信号に TAA の近傍 clamp / variance
   clipping を使うと、正しい履歴を切り詰めて暗部・接地の影を偏らせ、ちらつきを増やしうる（前例の注意）。
2. **履歴の上限 N と時定数の対応**と、照明の変化の検出（anti-lag）の要否。
3. **撮影の再現性** — 同じ入力と同じ履歴からは同じ画像にする形（例: 履歴を消して、手順3 で決めたジッターの列で N フレーム積む）。
   同じフレーム番号で描き直しても履歴を進めない（lab の `captureSettled` は 1 つのフレームを 2〜6 回描く）。
4. **カメラの切り替えで履歴を捨てる口** — 動きベクトルは、照準の出入り・注視の切り替え・戦闘とマップの切り替えでも幾何として正しい
   （手順4）が、大きく跳んだ再投影が偶然合う面を引きうる。`reset` をゲームのどこから呼ぶか（`camera-system.ts` の切り替え・
   `display-phase.ts` の戦闘とマップ）。透視と平行の切り替えは、動きベクトルが全面を棄却の印にするので要らない。

ジッターの列は手順3 で決めたものを `frameJitterAt` で、描画パイプラインが受けたフレーム番号（手順4-3）から回す。時定数を最小にしたら、蓄積と一緒にジッターも止める
（変えないもの）。成分ごとに止める口は、デバッグと render-lab に残す（手順6 の切り分け）。

**先行研究**（Luna の調査。実装の前に原典で式と既定値を確かめる — 未確認の値がある）

- **履歴の長さを画素ごとに運ぶ**（決めたこと 3） — 新しいフレームの重みを α = 1/(n+1)（n は積んだフレーム数。蓄積の初めは算術平均）
  とし、上限 N からは α = 1/N の指数移動平均にする。NRD の REBLUR / RELAX（https://github.com/NVIDIA-RTX/NRD の README）は履歴の
  長さと上限 `maxAccumulatedFrameNum`（= 残像の時定数）を持ち、確からしさで縮める — REBLUR は
  `historyLength *= lerp(confidence, 1, 1/(1+historyLength))`、RELAX は `historyLength = min(historyLength, maxAccumulatedFrameNum·confidence)`。
  SVGF（Schied ら 2017）も時間方向の蓄積と再投影の検証を持つ（α の既定値は未確認）。
- **静止時の実効の標本数** — 上限 N の算術平均なら N、α 固定の指数移動平均なら (2 − α)/α。時間相関・棄却・動きがあると積だけでは
  決まらない。ジッターの列の周期（格子のずらしは 1/4 で 16）が N より短いと、層別の利得が周期で頭打ちになる。
- **照明の変化で履歴を縮める** — A-SVGF の temporal gradient（Schied ら 2018）、NRD の anti-lag / HistoryFix。追加のバッファと計算が要る。
  最大の重みの制限（決めたこと 4）で残像が許せないときの次の手。
- **再投影と棄却** — 前フレームの位置を動きベクトルで引き、深度・法線（平面距離）で履歴を棄却し、双線形で読む。
- **フレームごとの乱数** — XeGTAO・GTAO は回転と歩のずれを時間方向にも変える。Spatiotemporal Blue Noise（Wolfe ら 2022）は画面と時間の
  両方でブルーノイズ。8-4 の散りばめをフレームごとにどう回すかの前例は見つからなかった。
- **ジッターと動きベクトル** — three の `TRAANode` は Halton(2,3) のずれを `setViewOffset` で入れ、動きベクトルはジッターなしの射影で書く。
- Split RC も 1 フレームと時間方向の蓄積の両方で評価している（組み合わせの前例）。

### 手順 6. 評価とユーザーの判定

- **源ごとの切り分け**（決めたこと 8） — 静止したカメラで、1 つの源だけジッターを入れて（ほかは止めて）蓄積した絵が、手順3 のその源の

  手順3 の剥がしの (b)〜(d) と並べ、残った揺れがどの源かを読む。
- **2 の形の振動**（格子のずらしを採ったとき。決めたこと 9） — 動くカメラで、時定数の短い端から、照り返しの全体が平行移動で振動して
  見えないかを目視し、手順3 の蓄積の模擬と並べる。乱択は試さない（決めたこと 10） — 振動が気になったら、数と画像を判断材料へ書いて
  ユーザーへ返す。
- **ちらつき** — カメラを少しずつ動かした連続フレームで、同じ表面の点の値のフレーム間の揺れを、蓄積の前後で比べる（手順2 の指標）。
- **静止時の収束** — 静止したカメラで N フレーム積んだ画像を、B と、同じ仮想のスライス数の 1 フレーム（スライスを増やした raw）と比べる。
  動かない輝点が残っていないか（達成目標2）。
- **残像** — 送り手・光源を動かしたとき、影と照り返しの残像が消えるまでのフレーム数（時定数どおりか）。光源は手順2 の `light` の列で、
  送り手の幾何は手順4-1 の `casing-room`（動く通常の物・熱した薬莢）をフレーム番号で動かして撮る。
- **動く物の尾**（達成目標4） — `casing-room` の動く物と少数の薬莢、および `casing-pool` の積み直す薬莢（4-4 を棄却したなら、棄却の印の
  画素で履歴が切れて尾が出ないこと）の上と縁。
- **費用** — 再投影して混ぜる行と動きベクトルの書き込みの増分（同じページで交互に）と、中間 target の増分。
- **見せ方** — 動く絵は手順2 で決めた形で。静止時の収束は比較対照画像（補正項だけ・全体・撮影ごとに一貫した露出・候補をボタンで

### 手順3 の口と道具（2026-10-12）

**口（`src/render/pipeline/screen-space/`）**

- **`frame-jitter.ts`** — `JitterSource`（`seed` / `scanRepresentative`）、`ScanJitter`（`grid`: 全ての走査の画素の代表をブロックの中の
  同じ位置 `fraction`（走査の画素の幅に対する割合、0 以上 1 未満）に置く / `perPixel`: 画素ごとに番号 `draw` のホワイトノイズで置く）、
  `FrameJitter`（seed と `ScanJitter | null`）、`frameJitterAt(frame, sources, cellSize)`。動かす源を `sources` に並べ、含めない源は
  本番の静止画の値（seed (0, 0)・代表 null）。**フレーム 0 はどの源を動かしても本番の静止画と一致する**（テストで固定）。
  - **seed の列** — R2 列 `fract(k·(1/g, 1/g²))`（g は塑性数。拡散側の道具の `seedOf` と同じ生成元で、量子化と重複の飛ばしをしない）。
    `seed.x` は走査の回転の全画素共通のずれ、タイルのずれは歩みと丸めと最後の拡大の回転に掛かる。8-4 の決定的な散りばめ（整列ブロック
    ごとの 2 bit）は `seed.x` を足した後に `fract` するので、**フレームごとに回しても整列ブロックの層別は保たれる**（全画素に同じ
    回転の差が乗るだけ）。
  - **代表の列** — `cellSize`（走査の画素の幅 [描画バッファの画素]。`ScreenSpacePass.scanCellSize` = round(1/scale)）の 2 乗通りの
    位置を Bayer 順に巡り、先頭をブロックの中心と排他的論理和で入れ替えて、フレーム 0 を本番の代表にする。周期は 1/4 で 16。
    位置は `0.5 + (升 − cellSize/2)/cellSize`（1/4 なら 0, ¼, ½, ¾）で、`cellSize = 1` では ½ だけ（走査の解像度 1 で消える）。
- **`ScreenSpacePass.setScanJitter(jitter | null)`** と **`scanCellSize`**。代表を選ぶ 1 か所 `gbufferTexelOf` / `gbufferUVOf`
  （`hemisphere-scan.ts`）に、ブロックの中の位置 [1/`REPRESENTATIVE_STEPS` ブロック]（= 1/16。整数）を渡す形にし、面の写し（段 0）と
  走査の `gbufferUV`（照り返しの源・天体照・補正を受ける判定）が同じ位置を読む。**整数で割る形を保った** — 浮動小数の
  `floor((p + ½)·960/240)` は GPU では逆数の掛け算になり、x だけ `floor(1.999…) = 1` で全画素の代表が 1 px ずれ、`render-lab:compare` が
  74/181 封筒外になった（`scan-surface-0` の texel を before と突き合わせて特定）。整数の分母 16 なら `cellSize` 16 まで正確で、
  `(16p + 8)·full / (16·scan)` は従来の `(2p + 1)·full / (2·scan)` と同じ商になる（どの寸法でも既定が一致する）。
- **最後の拡大の写像も同じ位置で動かす** — `correction-reconstruction.ts` の `position`（全解像度の画素 → 走査の画素の座標）の `−½` を
  `−位置` にし、代表がその画素に最も近い走査の画素が整数になるようにした（既定 ½ で従来と同じ式）。格子のずらしでは代表が
  ブロックの端に寄るので、写像を据え置くと最大 2 px 遠い代表を引き、平均が ⅛ ブロックほど偏る。乱択では画素ごとの位置を持てないので
  中心（½）のまま。
- **`setScanJitter` の呼び方** — 格子のずらしは `{ kind: 'grid', fraction }`（範囲外は投げる）、乱択は `{ kind: 'perPixel', draw }`
  （ホワイトノイズの成分 3・4 — 走査のずれの 0〜2 とは独立）。既定（null）はブロックの中心で、**既定の絵は変えていない**
  （`render-lab:compare` — 下の実測）。

**道具（render-lab）**

- **`tools/render-lab/phase-sequence.ts`** — `CorrectionPhase`（`FrameJitter` + `rasterJitter`）、`PhaseSequence`（動かす源の組

## Backlog（この計画の外）

- **ラスタライズのジッター（画面全体の TAA）** — 2026-10-13、ユーザーが手順から回した（決めたこと 11）。G バッファの射影を描画バッファの
