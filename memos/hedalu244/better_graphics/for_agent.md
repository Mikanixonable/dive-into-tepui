個々の見た目の仕様は `DEVELOP/EARTH_MOON_GRAPHICS_PROPOSAL.md` /
`DEVELOP/PHYSICAL_RING_RENDERING_PROPOSAL.md` が持つ。この文書はその下に敷く土台だけを扱う。

完了したタスクは文書から削除し、残りのToDoと、後件の判断のために必要な情報だけのこす。
コードの状況についても計画開始時点の歴史的経緯を残さず、常に最新にする。

**適用範囲の前提**: LEO で優れた性能が出ることは最低要件だが、**太陽系全域で破綻しないこと**が

## 0. 光と影を分ける 4 つの軸

「光源の大きさをどう積分するか」と「影をどう作るか」は独立した問題であり、
1 つの話として設計してはならない。この文書は光と影を次の 4 軸へ分け、
**軸ごとに独立して差し替えられる形**を目指す。

| 軸 | 問い | 方針 |
|---|---|---|
| **軸 1** | **反射** — 光源の大きさを、受け手はどう積分するか | **§1-5**。太陽=球光源、天体=ランバート球。遠方で点光源へ**滑らかに縮退する単一の仕組み** |
| **軸 2** | **太陽光の遮蔽** — 影をどう作るか | **§1-6。統一するのは受け手の入口と合成の規約。実装方式は未定** — 調査は `shadow_implement.md` |
| **軸 3** | **地球照の遮蔽** | **§1-7。無視するか AO 近似。** 全天体からシャドウマップを撮るのは原理的に不可能 |
| **軸 4** | **CPU 側の日照率** — 熱・電力・SRP | **§1-8。描画とは別の問い。実装済み。** 描画へ流用するのはアドホックなので避ける |

**軸の実装順**: **軸 2 → 軸 1 → 軸 3**(軸 4 は実装済み)。ただし軸に入る前に、
器(パイプライン)・座標(距離圧縮)・量(アルベドと露出)を先に片付ける。理由は §3 冒頭。

## 1. 確定した判断

### 1-1. 露出 — 放射照度を基準に取り、既存の手調整値は捨てる

**方針(確定)**: HDR 線形空間へ移した上で、物理的根拠のある式へ組み替える。視覚的な問題が出たら
**HDR 空間の上で**再調整する。LDR 時代の手調整値へ戻す方向の調整はしない。

```text
E(d) = SOLAR_CONSTANT * (AU / d)^2      [W/m^2]    — 距離 d における放射照度
L_surface = E(d) * albedo / pi          [W/m^2/sr] — 完全拡散反射面の放射輝度
exposure  = 1 / L_ref                              — L_ref を中間グレーへ写す係数
```

必要な量は**すべて既にある**: `SOLAR_CONSTANT = 1361`(`game/const.ts:65`)、
`ASTRONOMICAL_UNIT`(`physics/srp.ts:9`)、逆二乗則(`physics/srp.ts:24`)、
`STEFAN_BOLTZMANN` / `HULL_EMISS`(`game/const.ts:44-45`)、機体温度(`game/const.ts:47-51`)。

**唯一の欠落はアルベドである。** 天体表面は 101 天体ぶんの 16 進直書き色(86 リテラル、ユニーク 63 種、
`celestial-registry.ts:103-196`)しか持たず、アルベド値は 1 つも無い。根拠コメントも無い。

#### 1-1-1. アルベドと放射照度を分離する — 輝度は持たず、毎フレーム引く

**この分離を崩すと軸 1 が成立しない。**

天体が持つのは **RGB のアルベド値**(反射率)だけであり、**輝度は持たない。**
輝度は、アルベドと**その天体が「いまいる場所」で受けている放射照度**から毎フレーム引く:

```text
L(p) = E_sun(その天体の太陽からの距離) * albedo * max(0, dot(n_p, sun_dir)) / pi
```

**この分離は直接の描画色と二次反射光源の両方に効く** — 同じアルベド値が、その天体の表面を
描くときの色にも、その天体が他の物体を照らす光源の強さにも使われる。
したがって **軸 1(§1-5)でアルベドが光源強度として使われるときも、アルベドがそのまま
光源の強さになるのではない。** アルベドは、その天体が受けている放射照度に掛かる係数である。
同じアルベドでも太陽から遠い天体は暗い光源にしかならず、その距離依存が式の中に入っていなければ、
海王星が地球と同じ明るさで艦を照らすことになる。

**直書き色をそのままアルベドとして読み替える移行は誤りである** — 現状の色は
「地球の位置で太陽に照らされた状態の見え方」に近い値へ手で寄せられており、
放射照度の項をすでに畳み込んでしまっているため、太陽光の距離減衰を実装した時に二重に掛かる。

#### 1-1-2. 校正はリングを基準に取る

**既にこの基準で書かれている部分がある。** リングだけが完全な放射伝達モデルになっている —
`RingOpticsDef` の単一散乱アルベド・法線光学的厚さ・HG 非対称因子が全 36 帯に出典コメント付きで入り、
その単一散乱の式(`render/ring.ts` の `physicalMaterial` が組む TSL グラフ)は明示された単位を持つ。
この手調整係数はもうリング固有ではない — **出力段の露出係数
`EXPOSURE = 0.72`(`render/pipeline/render-pipeline.ts`)としてフレーム全体に掛かっている。**
リング以外は一律 0.72 倍で暗い。**Phase 5 の課題は、この 1 個の係数を上の放射照度基準の式から
引き直すこと**であり、**`EXPOSURE` が 1.0 になる**ことを完了条件の一つにする。

**HDR 化で構造変更が要る箇所**: `Billboard` は `MeshBasicMaterial.opacity`(0..1 クランプ)で
明るさを表しており、`transparent + AdditiveBlending` の 5 経路の最大のものがここを通る
(`render/billboard.ts:16-18`)。1 を超える輝度を出せないので、ノードマテリアルへ置き換える。
**これは Phase 5 の作業。** 描画先は既に `rgba16float` なので、器の側の制約はもう無い。

### 1-2. 座標境界 — GPU に ECI 絶対座標を載せない

**不変条件(維持する)**: 描画はすべてフローティングオリジン座標系(`THREE.Vector3`)で行い、
GPU に ECI 座標(独自 `Vec3`)が渡らないこと。具体的には
**`src/render/**` から `Vec3` / `KinematicState` / `ReferenceFrame` / `Attractor` /
`Ephemeris` / `OrbitalElements` / `FloatingOrigin` への import が 0 件**であること。
以降のどのフェーズでもこれを崩さない。**新しいパス(G バッファ・照度バッファ・シャドウマップ)を
足すときも、シェーダへ渡す位置はすべて描画座標系である。**

**曲線については解決済み。** `render/curve.ts` は頂点を `Float64Array`(`bakedLocal`)で保持し、
カメラ近傍の pivot を引いた差分だけを f32 バッファへ書く。
`OrbitLine` / `TrajectoryLine` は `Curve` 経由なので、海王星軌道のような大きな絶対値でも
f32 量子化は起きない。

**残っている 1 箇所**: `game/celestial/point-field-view.ts:97` の `instanceMatrix` は
太陽中心の生座標(カイパー帯で ~7.5e12 m)を pivot 補正なしに f32 へ書いている(量子化 ~5e5 m)。
**引きの絵では画素以下だが、寄ると露見するはず。Phase 4 で実測する** — 距離圧縮の撤去と
同じ「真の絶対値を f32 へ載せてよいか」という問いなので、同じフェーズで測る。
`Curve` と同じ pivot 補正を入れるのが対処だが、**測ってから決める。**

### 1-3. 深度精度 — 第一候補は reversed-Z + float32。カスケードは退路

**方針(確定)**: 距離圧縮の撤去は GPU 上の深度精度が担保できるかが鍵。
**ただし第一候補は深度カスケードではなく、reversed-Z + 32bit float 深度による単一バッファである。**
**スパイク → 測定 → 判断 → 本実装を 1 つのフェーズ(Phase 4)で通す。**

#### なぜカスケードより先に reversed-Z を試すか

深度分解能 Δz(隣り合う深度値が表す距離の差)を、カメラからの距離 z ごとに:

| z | 現状(`depth24plus`・非反転・near=2) | **reversed-Z + `depth32float`** |
|---|---|---|
| 2 m(近クリップ) | 1.2e-7 m | 1.2e-7 m |
| 1e4 m | 3.0 m | 6.0e-4 m |
| 1e6 m | 3.0e4 m | 6.0e-2 m |
| 4.5e7 m(現 `MOON_VIS_DIST`) | **6.0e7 m — far より大きい。分解能ゼロ** | 2.7 m |
| 3.8e8 m(月の真位置) | far の外 | 23 m |
| 1.5e11 m(太陽の真位置) | far の外 | 8.9e3 m |
| 7.5e12 m(カイパー帯) | far の外 | 4.5e5 m |

非反転の固定小数点は `Δz = z²·2⁻²⁴/near` で**距離の二乗で悪化する**のに対し、
reversed-Z + float32 は `Δz ≈ z·2⁻²⁴` で**距離に比例する**。
1 px の world 幅も距離に比例する(`metersPerPixel ≈ 9.6e-4·z`)ので、

> **reversed-Z + float32 の深度分解能は、距離によらず画面上つねに約 6e-5 px 相当。**

**距離に対して一様である**ことが要点で、これはまさに「近くは高精度、遠くは低精度」を
浮動小数の指数部が自動的にやっている状態である。**カスケードで人為的に分ける動機が消える。**
深度カスケードは固定小数点深度バッファ時代の技法であり、
**float32 + reversed-Z の下では枚数を増やしても得るものがほとんど無い**一方、
`renderOrder`・`depthTest: false` の 3 箇所・`frustumCulled = false` の 6 箇所を
すべて段ごとに整理し直す構造的コストを丸ごと払うことになる。

原理: 非反転は `z_ndc = 1 − near/z` の形で、**1 から微小量を引く**ため
浮動小数の桁が落ちる。反転すると `z_ndc ≈ near/z` になり、
**float の指数分布が透視分割の 1/z をそのまま吸収する。**
`near = 2` / `far = 6e7` で `far − near` が `far` へ丸まる件(既に一度実害を出し、
`render-pipeline.ts` の `viewDistanceFromDepth` を組み替えて回避してある)も、
反転形の係数 `c = near/(far−near)`, `d = far·near/(far−near)` では
**桁落ちが起きる引き算そのものが式から消える**ので同時に解消する。

#### three.js 側の事実(r0.185.1、調査済み)

- **`WebGPURenderer` に `reversedDepthBuffer` は存在する**(r183 で追加、`Renderer.js`)。
  投影行列(`Matrix4.makePerspective` の `reversedDepth` 引数)・深度比較関数の反転テーブル
  (`utils.js` の `ReversedDepthFuncs`)・深度クリア値(`getClearDepth()`)が
  **レンダラー単位で一括して切り替わる。同一カメラを使い回す 5 パス構成にも一貫して効く。**
- **`depth32float` は `new THREE.DepthTexture(w, h, THREE.FloatType)` で明示指定できる**
  (`WebGPUTextureUtils` の型→フォーマット表で `FloatType → Depth32Float`。WebGPU コア機能で追加 feature 不要)。
  **暗黙の深度バッファは `reversedDepthBuffer` で自動的に `depth32float` へ切り替わるが、
  自前で `DepthTexture` を付けた RenderTarget は切り替わらない** — three 自身の `PassNode` も
  `depthTexture.type = FloatType` を手で入れている。
  **`gbuffer.ts` の `new THREE.DepthTexture(1, 1)` は既定の `UnsignedIntType`(= `depth24plus`)なので、
  ここを明示しないと反転しても精度が出ない。**
- **⚠ `0.185.1` には `reversedDepthBuffer` が `renderOrder` を全反転させるバグがある**
  (`RenderList.sort` が `reversedDepth` のとき配列全体を `.reverse()` する。
  three.js Issue #33944 / 修正 PR #33945)。
  **`LINE_RENDER_ORDER`(§2-4)の 6 段が丸ごと逆順になる。**
  修正はマイルストーン **r186(2026-08-19 予定)**。
  **Phase 4 は r186 への更新を前提に組む。** 更新が間に合わない場合のみ、
  `RenderList.sort` を回避する形(カスタムソート関数)を検討する。
- **対数深度は「併用相手」ではなく「代案」。** `logarithmicDepthBuffer` は WebGPU 経路にも
  配線されている(`NodeMaterial.setupDepth`)が、**reversed 版の
  `viewZToReversedLogarithmicDepth` が three に存在しない**ので、両方同時に有効化した場合の
  整合性は保証されていない。どちらか一方を選ぶ。

#### 判断を楽にする事実(維持)

- **`physics/projection.ts` は near/far に一切依存しない**(`:49, 53-70`)。
  → **fov/aspect を共有する限り `ProjectFn` / `ScaleFn` の全消費者(マーカー約10系統、picking 5系統、
  plan 系、`TrajectoryLine` の頂点密度、`ring-view` の LOD、`point-body` の 2px 判定)は無変更で通る。**
- **投影行列を書く箇所は `camera/camera-system.ts` の `syncCameraToViewpoint` 1 箇所だけ。**
- **`COMBAT_CAMERA_FAR = 6e7`(`const.ts:124`)は `MOON_VIS_DIST = 4.5e7` から逆算された値。**
- **地球だけは既に真位置・実半径**(`earth-body.ts`)。真スケール描画の前例が既にある。
- **マップカメラは既に破綻していない** — `near = dist/1000` / `far = dist×100` と
  near が距離に比例するので比が 1e5 に固定されている。**問題は `near = 2` 固定の戦闘カメラだけ。**
- `light-prepass.ts` の視点位置復元は `camera.projectionMatrixInverse` を渡しているので、
  **反転しても自動的に追随する**(行列そのものが反転版になるため)。
- `render-pipeline.ts` の `viewDistanceFromDepth` は分母の `near` と `far` を
  入れ替えるだけで反転形になる(`near·far / (near(1−d) + far·d)`)。デバッグ表示のみの影響。

**変換の切り出し(要件)**: ECI → 描画位置の順変換は **5 種類に分散**し、逆変換は **1 つも無い**。
`FloatingOrigin.RtoThreeV3` / `sphere-body.ts:96-115` / `point-body.ts` の 2 箇所 /
`sun-body.ts` / `environment-scene.ts`。
1 モジュール(`render/view-space.ts`)へ集約し `toRender` / `toEci` を公開する。
**圧縮を採るにせよ撤去するにせよ、この集約は先にやる。**
**カスケード選択のポリシーはここへ置かない** — 深度カスケードとシャドウマップの解像度は
別の資源を別の軸で分けており、共有してよいのは `render/screen-lod.ts` /
`physics/projection.ts` に既にある「長さ → px」の換算だけ(`shadow_implement.md` §4-1)。

**測定項目**: (a) reversed-Z + float32 単一バッファで、圧縮を外した全距離域に z-fighting が出ないか、
(b) `renderOrder` が r186 で正しく効いているか、
(c) `depthTest: false` の 3 箇所(`stars.ts:28` / `earth.ts:99` / `plan-gizmo-3d.ts:33`)が
反転後も意図どおりか、(d) フレーム時間の変化(パス数は増えないので誤差程度のはず)。
**カスケードのスパイクは (a) が否だったときにだけ行う。**

`Renderer.clearDepth()` は `@types/three` が型を持つので、必要になれば自前宣言なしで書ける。

### 1-4. ライトプリパス(3 パス構成)

**方針(確定)**: 2 パス遅延シェーディングをやめ、**3 パスのライトプリパス**を採る。

```text
Phase A  ジオメトリパス   → 深度 + 法線 + 粗さ            (幾何だけ。マテリアルの色を持たない)
Phase B  ライティングパス → 拡散照度バッファ + 鏡面照度バッファ
                            光源の形の積分・遮蔽問い合わせはここに閉じる
Phase C  レンダリングパス → 再度ジオメトリを描き、照度バッファを読み、材質を掛ける
Phase D  半透明 + ポストプロセス
```

**なぜ 2 パスでは足りないか**: 遅延シェーディングでは「光源の立体角積分」と「BRDF 評価」が
同じシェーダに同居する。§1-5 で光源の種類(球・ランバート球・点への縮退)を増やす以上、
マテリアル分岐との掛け算で膨らむ。ライトプリパスは**照度という中間表現で両者を切る**:

- **ライティングパスは「その点にどの向きからどれだけ光が来ているか」だけを答える。**
- **レンダリングパスは「来た光をこの材質がどう返すか」だけを答える。**

**トレードオフ**: ジオメトリを 2 回描く(ドローコール増)代わりに G-buffer が狭くなり、
マテリアルの多様性と光源の多様性が独立に増やせる。

**既知の限界**: 鏡面反射は「入射方向 × 視線 × 材質」に依存するので照度バッファ 1 枚に畳めない。
標準的な対処は**粗さをジオメトリパスに書き、その粗さで積分した鏡面項を別バッファに出す**こと。
拡散反射が支配的な天体表面 + 少数の金属的な艦船という本作の絵では破綻は小さいと見込むが、
**破綻したら艦船だけを前方描画へ逃がす**(ドローコールは既に 2 回なので構成は壊れない)。

**器は `src/render/pipeline/` に組み上がっている。** フレームは
G バッファ → ライティング → マテリアル → ワールド → 合成 の 5 パスで、それぞれが
負荷確認ウィンドウに独立した GPU 時間の行を持つ。光源はまだ単一の平行光 1 個。

**受け手側は既に照度バッファ経由になっている。** `MaterialPass` が
`PhysicalLightingModel` を継承し、`direct()` を空に、`indirect()` を照度バッファの読み出しへ
差し替える。BRDF・マップ・粗さ/金属度の扱いは three 標準の `MeshStandardNodeMaterial` のままなので、
**光源を増やす作業はライティングパスの中に閉じる。**

**three 側の制約(§1-5 の実装で効く)**: `NodeMaterial.setupLighting` は
`light.layers.test(camera.layers)` を通る光源が 1 つ以上あるときにしか
`setupLightingModel()` を呼ばない。マテリアルパスはカメラの層を `LIT_OPAQUE_LAYER` へ
絞るので、**シーンの光源をその層にも属させておかないとライティングモデルごと呼ばれず、
受け手が真っ黒になる。** 光源をシーンから完全に外すことはできない。

### 1-5. 軸 1 — 反射(光源の大きさをどう積分するか)

**方針(確定)**: 光源が十分近く大きいときは面光源、十分遠く立体角が小さいときは点光源。
**これを分岐ではなく、単一の式が滑らかに縮退する形で実現する。**
太陽にも地球にも月にもその他の天体にも、同じ仕組みが適用される。

**なぜ必要か(立体角)**:

| 光源 | 視点 | 視半径 | 立体角 | 全天比 |
|---|---|---|---|---|
| 太陽 | 1 AU | 0.266° | 6.8e-5 sr | 5.4e-6 |
| 太陽 | 水星近日点 0.31 AU | 0.86° | 7.1e-4 sr | 5.6e-5 |
| 地球 | LEO 420 km | **70.0°** | **3.90 sr** | **31%** |
| 地球 | 静止軌道 | 8.6° | 0.071 sr | 0.56% |
| 地球 | 月軌道 | 0.95° | 8.6e-4 sr | 0.007% |
| 木星 | エウロパ軌道 | 11.5° | 0.126 sr | 1.0% |

**太陽ですら完全な点ではなく、地球は LEO で全天の 31% を占める。**
そして**同じ地球が月軌道では点光源と区別がつかない。** 近距離用と遠距離用に別モデルを持つのではなく、
**距離とともに連続に縮退する 1 つのモデル**でなければ、遷移する場所で絵が飛ぶ。

#### 1-5-1. 太陽(恒星) — 一様球光源

最も単純な形。球全体が一様な放射輝度を持つ。**一様球光源からの拡散照度には閉じた解があり、
その式は距離が大きくなると自動的に逆二乗則へ縮退する。** したがって
**「遠いときは点光源に切り替える」という分岐は書かない** — 同じ式が両方を覆う。

分岐が要るのは鏡面項だけ。LTC(Linearly Transformed Cosines)による球光源の積分は
角半径が小さいと数値的に無駄なので、閾値で点光源近似へ落としてよい
(拡散項と違い、鏡面のハイライトは光源が小さければ本当に点と区別がつかない)。

#### 1-5-2. 惑星・衛星 — ランバート球(部位によって照度が違う球)

**太陽と決定的に違うのは、球面の一部しか光っていないこと。** 昼側だけが光り、
艦から見ると三日月形になる。一様球光源では表せない。

**近似(確定)**: **ランバート球**として扱う。球面上の各点の放射輝度が §1-1-1 の式で与えられる球。
**入力は 2 つ — その天体のアルベド(色度込み)と、その天体が太陽から受けている放射照度**であり、
**アルベド単独では光源の強さは決まらない。** 太陽からの距離が式に入っていることが要件。

- **一様球ではないので LTC の標準的な適用範囲外である。** これは承知の上で採る近似であり、
  検証ケース(三日月形に見える位置での地球照)で妥当性を確かめる必要がある。
- 実装の候補は 2 つある。(a) 照らされている半球を**等価な円盤へ代表させ**、その円盤に LTC を適用する
  (位相角に応じて円盤の面積と位置をずらす)。(b) 球光源の閉じた解に**位相係数**を掛ける
  (正しくない — 明るさは合うが、光が来る「向き」の偏りが表現されない)。
  **(a) を採る。** 光が来る向きの偏りこそが軌道上の絵の特徴だから。
- **色を持つ光源になる。** 地球は海の青・雲の白・陸の褐色を持つので、艦の影側が青みを帯びる。
  初版は全球平均色でよく、局所分布(雲がある側が明るい)は将来の改良。

#### 1-5-3. 光源の打ち切り

**打ち切りの基準は距離ではなく立体角。** 立体角が閾値を下回った光源は
点光源として扱う(縮退は式が自動でやるので、実際には「LTC を使うか点光源で済ますか」の判断だけ)。
さらに小さければ照度そのものが無視できるので光源リストから外す。
**太陽系全域で、光源リストは実用上「太陽 + 最も近い 1〜2 天体」に収まる。**

#### 1-5-4. 現状との差

今は `AmbientLight(0x8899bb, 0.25)`(`environment-scene.ts:90`)という
**方向も距離も位相も持たない定数**が、地球照・星明かり・多重散乱の全部を兼ねている。
軸 1 の完成はこの定数を消す作業でもある。

#### 1-5-5. なぜ軸 1 を後回しにできるか

**ライティングパス(Phase B)とレンダリングパス(Phase C)が分離されていれば、
軸 1 の変更は Phase B の中に閉じる。** 最初は太陽も天体も点光源として実装しておき、
後から球光源・ランバート球へ差し替えられる。**受け手側のコードは一行も変わらない。**
これが軸 2 より優先度を下げられる理由である。

### 1-6. 軸 2 — 太陽光の遮蔽

**方針(確定)**: 太陽光の遮蔽は無視できず、**ソフトシャドウ的な照度変化の再現が要る。**
太陽の立体角が小さくても、**半影のスケールは遮蔽器までの距離に比例して大きくなる**ので無視できない。
そして以下はすべて**同じ現象**である:

- 地球の影に出入りする艦の照度変化
- 艦のセルフシャドウ・艦どうしの相互影
- 月食 / 日食の境界
- 土星のリング影の境界

#### 1-6-1. 実装方式は未定 — `shadow_implement.md` が調査の正本

**「解析的な遮蔽で表すか、シャドウマップで表すか、両方をどう組み合わせるか」は未決である。**

物理量の見積もり・既存 3 実装の棚卸し・両案の実装イメージと実現性・
テクセルと Z 精度の状況別の内訳・組み合わせ方・GPU コストの見立て・先行研究・
three 側で使えるものは、すべて **`memos/hedalu244/better_graphics/shadow_implement.md`** が持つ。
**この文書には方式の詳細を書かない**(重複すると必ず食い違う)。

#### 1-6-2. 方式に依らず確定していること

- **受け手の入口は `SunLight.sunVisibility(worldPos)` のまま変えない。**
  中身だけが差し替わり、天体表面・艦の BRDF・環・大気の呼び出しは無変更。
- **置き場をライティングパスの中にしてはならない。** 環(`render/ring.ts`)と天体表面
  (`render/celestial-surface.ts`)は前方描画のままなので、同じ関数を呼ぶ必要がある。
  **環は半透明なので恒久的に前方描画側**であり、この共有は過渡的なものではない。
- **合成は透過率の積(= 光学的厚さの和)。** 不透明も τ→∞ の極限として同じ式に乗るので、
  不透明・半透明で規則を分けない。**この規約は受け手の呼び出し形を決めてしまうので、
  源の実装より先に確定させる必要がある。**
- **必要な解像度には物理的な上限がある。** 影は太陽円盤で畳み込まれているので、
  半影幅(遮蔽器までの距離 d に対して 2αd)より細かい構造は存在しない。
  **「巨大な遮蔽器には巨大なシャドウマップが要る」は成り立たない。**
- **遮蔽器を捨ててよい物理的な基準がある。** 最大遮蔽率 `min(1, (β/α)²)` が閾値を下回る遮蔽器は、
  どう表現しても画面に出ない。チューニング値ではない。

#### 1-6-3. 距離圧縮への依存

**リング影シェーダは現状「真の方向 × 偽の位置」を混ぜている。**
`sunDirNode` は天体の**真の ECI 位置**から引いた方向なのに、
`positionWorld` と 32 バンドの `center` / `inner` / `outer` は**圧縮された描画位置・描画長**
(`celestial-surface.ts:143` の `setRingShadowSystem` が受け取る `displayScale`)。
`ring.ts` の `bodyRadius` にも描画スケールが入る。

**これはどちらの方式を選んでも直らない。** 距離圧縮が残る限り、解析でもシャドウマップでも
遮蔽器の位置が偽になる。**Phase 4 を軸 2 より前に置く決定的な理由。**

### 1-7. 軸 3 — 地球照の遮蔽(優先度低)

**方針(確定)**: 太陽光と比べて照度のオーダーが小さいので、**無視するか、AO として近似する。**

**軸 2 と同じ方法は原理的に採れない。** シャドウマップは光源ごとに要る。天体は 101 個あり、
そのすべてから撮ることはできない。§1-5 で光源リストが「太陽 + 最も近い 1〜2 天体」に
収まるとしても、面光源(ランバート球)に対する影は点光源に対する影よりさらに高価である。

**採る手段**:

1. **無視する。** 初版はこれでよい。地球照は太陽光の 1e-2 〜 1e-3 のオーダーであり、
   その中の遮蔽の差はさらに小さい。
2. **AO として近似する。** 幾何的な遮蔽度(周囲がどれだけ開けているか)を
   地球照に掛ける。方向を持たない近似だが、艦の凹部が暗くなるという主要な効果は出る。

**優先度は最も低い。** 他のどの軸にも依存されない。

### 1-8. 軸 4 — CPU 側の日照率(熱・電力・SRP)

**CPU 側の日照率と GPU 側の遮蔽は別物であり、二重実装ではない。**
問いが違う — 前者は**ある 1 点の日照率**(艦を点と見なしてよい)、後者は**画素ごとの遮蔽度**
(艦は点ではなく、自己影を持つ)。したがって軸 2 が完成しても `physics/shadow.ts` は残る。

`physics/shadow.ts` の `sunlitFactor(r, star, attractors)` は実装済みで、
熱・電力(`game/player/player.ts`)と SRP(`physics/dynamics.ts`)が消費者。
**このフェーズで新たにやることは無い。**

**残っている 1 本の配線だけが軸 2 の作業対象**: 描画照明が `environment-scene.ts` 経由で
この関数を読み、`SunLight.sunVisibility()` のスカラとしてライティングパスへ渡っている
(艦を 1 点と見なした値が艦全体に一様に掛かる)。**Phase 6 の完成をもってこの経路は切れる。**

**この関数と軸 2 の実装がどう関係するかは、選ぶ方式による**(`shadow_implement.md`)。
確定しているのは**描画側がこの関数を読まなくなること**だけで、
`physics/shadow.ts` 自体は熱・電力・SRP の消費者のために残る。

## 2. 現況の事実

### 2-1. 光源と陰影の二重世界

- **光の値の正本は `render/pipeline/sun-light.ts` の `SunLight` 1 つ。** 向き・色・強度・
  日照率を持ち、`environment-scene.ts` が毎フレーム書き込む。ライティングパスがそれを読む。
  シーンの `AmbientLight`/`DirectionalLight` も同じ値から設定されるが、これらはもう値を決める
  場所ではない — **§1-4 の three 側の制約により、光源オブジェクトそのものは消せない。**
- 受け手は `MeshStandardMaterial` の層 = 艦船・デブリ・薬莢・基地・小惑星のみ
  (生成 12 箇所、すべて `render/ships.ts`)。この層は `lit-layer.ts` の `LIT_OPAQUE_LAYER` に
  **のみ**属し、G バッファパスとマテリアルパスだけが描く。
- 天体は全て `MeshBasic(Node)Material` でライト非依存。手書き Lambert + `NIGHT_AMBIENT = 0.04`
  (`celestial-surface.ts:31`)が地球にも他天体にも同じ値で掛かる。
  **これを艦船と同じ BRDF へ統合するのは Phase 4 の後**でしかできない — 天体が各自
  `sunDirection` uniform を持つのは**描画位置が距離圧縮で偽物だから**であり、シーンライト 1 本へ
  寄せると圧縮座標で誤った向きから照らすことになる(§1-6-3 と同じ構造)。
- **「艦が惑星の影に入る」は依然として日照率のスカラ変調のみ**(`SunLight.sunVisibility()`)。
  **形状に依存する影は一切無い。`castShadow` / `receiveShadow` / `shadowMap` は `src/` に 0 件。**
  この関数が軸 2 で中身だけ差し替わる継ぎ目。
- 平行光の向きは描画原点から見た恒星方向(`ephemeris.sunDirFrom`)。
- **`AmbientLight` は §1-5 の地球照の代用品として働いてしまっている。** 軸 1 の完成で消える。

`PHYSICAL_DIAMETER_THRESHOLD_PX`(2px)未満は球を描かない判定も同モジュールへ一般化されている。

### 2-6. 既にある器 — 計測と描画設定

- **計測の器**: `gpu-timings.ts` の `GpuTimings` が描画パス別の GPU 時間 [ms] を持つ器を用意している
  (`GPU_PASS` の数値インデックス + フラット `Float64Array`、`enabled` は `PerfMeter` だけが書く)。
  値は非同期に届くので、`resolve()` は窓の開閉に依らず毎フレーム呼ぶ(呼ばないと時刻印クエリが
  溜まって上限に当たる)。`trackTimestamp` はレンダラ生成時オプションなので常時オン。
  閉窓時のフレーム間隔を実測した結果、その費用は run-to-run のばらつきに埋もれた
  (ON 11.8/12.3ms、OFF 12.9/12.0ms の中央値)。

  **パス別の分解は済んでいる。** `GPU_PASS` は 5 値(G バッファ/ライティング/マテリアル/
  ワールド/合成)で、各パスの GPU 時間が独立した行として並ぶ。実現方法は次のとおり:

  `resolveTimestampsAsync` の**戻り値**はフレーム合計だが、**解決の副作用として
  `backend.timestampQueryPool['render'].timestamps`(`Map<uid, ms>`)へコンテキスト別の値が
  書かれている。** uid は `Renderer` が `inspector.beginRender(uid, ...)` へ渡すものなので、
  `InspectorBase`(`three/webgpu` から公開・型付き)を差し替えて描画呼び出しごとに捕まえる。
  パイプラインは `renderer.render()` の直前に `GpuTimings.beginPass(id)` を呼んで
  「次の呼び出しはこのパス」と申告し、Inspector が uid をそのパスへ結び付ける。
  `beginPass` を伴わない three 内部の描画は無視されるだけで、他のパスの枠を奪わない。

  **`pool.timestamps` は three 自身が空にしないので、放置すると uid が毎フレーム際限なく積もる。**
  `GpuTimings.resolve()` が読み取り後に毎回クリアしている。

- **描画設定**: `render/graphics-settings.ts` の `GraphicsSettings` が正本
  (localStorage `tepui.settings.graphics`)。**新しい描画要素を足したフェーズは、その要素の
  トグルをここへ足す** — 影(Phase 7)・大気散乱(Phase 10)・ブルーム(Phase 11)・
  ボリューム(Phase 12)。**効かないトグルを置かない**という規則は維持する:
  現在並んでいるのは、オフにすると三角形数が実測で減るものだけ
  (点群 -44,800 / 環 -5,632(土星にフォーカス時)/ オーロラ -7,680 / 大気 -4,936)。
  `lodBias` は見かけ直径へ掛ける形なので、LOD 段と `showsPhysicalSphere` の閾値が同時に動き、
  `screen-lod.ts` は純関数のままでいられる。雲(地表シェーダへ焼き込み済み)は
  単体で切れないので Phase 10 まで項目に出さない。

- **中間ターゲットの目視**: 描画設定の「デバッグ表示」が、合成パスの映す先を最終画から
  中間ターゲットへ差し替える(`render/pipeline/debug-target.ts` が選択肢の正本、
  法線/粗さ/深度/拡散照度/鏡面照度/マテリアル)。**品質設定ではないので `GraphicsSettings` に
  持たせず永続もしない**(`RenderPipeline` のセッション限定の状態)。新しいパスを足したら
  ここへ 1 行足す — 目で見て確かめられないバッファは、間違っていても気付けない。

- **three.js の版**: r0.185.1。`@types/three` が `three/webgpu` / `three/tsl` を完全に型付けする
  ので自前の型シムは無い。ノード型の語彙は `render/tsl-types.ts`。

## 3. ロードマップ

**順序の根拠**は次の 5 点。軸の実装順(軸 2 → 軸 1 → 軸 3)はこの下に入る。

**器(`src/render/pipeline/` の 5 パス構成とパス別 GPU 計測)は組み上がっている**(§1-4)。
残る順序の根拠は次の 4 点。

1. **座標(距離圧縮の撤去)が最初** — 遮蔽を物理的に正しく統一する前提(§1-6-3)。
   判断が否だった場合に後続の限定版の範囲が決まるので、早いほど計画が確定する。
   **測定と本実装は同じ変更の前後なので、1 フェーズにまとめる。**
2. **量(アルベドと露出)が次** — 影もエリアライトもこの量を消費する。実作業量が最大であり、
   他フェーズと独立に進められるので、先に始めるほど効く。
3. **軸 2(影)** — 遮蔽の合成規約(透過率の積 = 光学的厚さの和、§1-6-2)は
   **受け手の側の呼び出し形を決めてしまう**ので、源を足す前に置く必要がある。
   遮蔽器の真位置が要るので、1 の後になる。
   **規約を置く Phase 6 と、源を実装する Phase 7 を分けるのはこのため** —
   実装方式が未決のまま(`shadow_implement.md`)でも Phase 6 は進められる。
4. **軸 1(反射)、続いてその他のリッチ化** — ライティングパスとマテリアルパスが分離済みなので
   **暫定的な点光源から後でブラッシュアップできる**(§1-5-5)。受け手のコードは変わらない。
   軸 3 は無視してよく、他から依存されない。

### パイプラインの現況(組み上がっている器)

§1-4。フレームは `src/render/pipeline/` の 5 パス。**各パスは負荷確認ウィンドウに独立した
GPU 時間の行を持ち、描画設定の「デバッグ表示」で中間ターゲットを全画面に出せる。**

```text
gbuffer.ts        深度 + 法線(oct符号化, rg16float) + 粗さ(r8unorm)  — MRT
light-prepass.ts  拡散照度 + 鏡面照度(いずれも rgba16float)          — MRT
material-pass.ts  LIT_OPAQUE_LAYER を再描画。照度を読み、材質を掛ける
(world)           残りのシーン。半透明ごと前方描画のまま
render-pipeline.ts  出力段。露出を掛けてキャンバスへ
```

**WebGPU に 3 チャンネル 16bit 浮動小数点フォーマットは無い**ので、照度バッファは
`rgba16float`(a は未使用)。

**パスの順序は深度の共有で決まっている。** マテリアルパスが先に HDR ターゲットを
クリアして不透明な艦を描き、world パスが `autoClear = false` でその上へ描く。
逆順にすると、world パスが最後に描く半透明物(軌道線・プルーム・ビルボード、いずれも
深度を書かない)より後に不透明な艦が来て、艦の手前にある半透明物を艦が上書きしてしまう。

**残っている宿題:**

1. **鏡面の近似の限界を実測する**(§1-4)。鏡面照度バッファは材質の F0 を持てないので
   F0=1 で評価し、マテリアルパスが掛け直している。破綻するなら艦船だけ前方描画へ逃がす。
2. **画像回帰シーンを撮る。役割は「一致判定」ではなく「変化の可読化」**(§1-1)。
   Phase 4 / 5 が絵を大きく動かすので、その前に用意すると効く。

### Phase 4 — Z 精度の実測と距離圧縮の撤去

§1-3。**スパイク・測定・判断・本実装を 1 フェーズで通す。**
**判断が否でも項目 1 と 2 は成果として残る。**

0. **画像回帰シーンを撮る**(パイプライン現況節の宿題 2)。役割は「一致判定」ではなく
   「変化の可読化」。このフェーズは絵を最も大きく動かすので、先に用意すると以降の判定が楽になる。
1. `render/view-space.ts` を新設し、順変換 5 種を集約。逆変換 `toEci` を作る。
   **判断の結果によらず有効**なので先にやる。**カスケード選択ポリシーはここへ置かない**(§1-3 末尾)。
2. **`three` を r186 以降へ更新する。** `0.185.1` の `reversedDepthBuffer` には
   `renderOrder` を全反転させるバグ(Issue #33944)があり、`LINE_RENDER_ORDER` の 6 段が逆順になる。
   修正 PR #33945 は r186(2026-08-19 予定)。**更新できるまでこのフェーズの本体は始められない。**
3. **reversed-Z + `depth32float` の単一バッファを試す**(§1-3)。カスケードより先にこれを測る。
   - `renderer.reversedDepthBuffer = true`。
   - **`gbuffer.ts` の `DepthTexture` を `THREE.FloatType` で作り直す** — 自前でアタッチした
     深度テクスチャは自動で 32bit float にならない。HDR ターゲット側は暗黙の深度なので自動。
   - `render-pipeline.ts` の `viewDistanceFromDepth` を反転形へ(分母の `near` と `far` を入れ替え)。
   - `COMBAT_CAMERA_FAR` を圧縮撤去後の実距離(カイパー帯まで届く 1e13 程度)へ広げ、
     §1-3 の測定項目 (a)〜(d) を測る。
   **カスケード 2 / 3 / 4 枚のスパイクは、これが否だったときにだけ作る。**
4. **`point-field-view.ts:96` の f32 精度を実測する**(§1-2)。
   `instanceMatrix` に書いているのは**太陽中心の相対位置**(カイパー帯で ~7.5e12 m、量子化 ~4.5e5 m)。
   親の `mesh.position` 側だけが浮動原点補正を受けているので、instance 側は素の絶対値。
   **カメラが点群から 1e8 m まで寄ると量子化が数 px になる**はずで、そこを確かめる。
   曲線側は `Curve` の pivot 補正で解決済みなので、残るのはここだけ。
   見えたときだけ `Curve` と同じ pivot 補正を入れる。
5. **判断**。否なら距離圧縮を維持し、**Phase 6 は「圧縮空間の中で幾何を整合させる」限定版に留まる**
   (§5 に影響を明記)。以下は可の場合のみ:
6. 天体を真位置・真半径で配置。`sphere-body.ts:96-115` / `point-body.ts` のスケール計算を削除。
7. `MOON_VIS_DIST` / `PLANET_VIS_DIST` / `POINT_BODY_VIS_DIST` / `SUN_DISTANCE` / `SUN_VISUAL_SIZE` を削除。
   `STAR_SHELL_RADIUS` / `CELESTIAL_SHELL_RADIUS` を「無限遠背景」へ一本化。
8. `COMBAT_CAMERA_FAR`(`const.ts:124`)の根拠(`MOON_VIS_DIST` からの逆算)が消えるので、
   実際に描く必要のある最遠距離から引き直す。
9. `sun-body.ts` / `point-body.ts` の overview/combat 分岐を削除。§2-2 の不統一も解消。
10. シーンライトを真の太陽方向へ統一。天体ごとの `sunDirection` uniform の役目が終わる。
11. **ここで初めて天体を `LIT_OPAQUE_LAYER` へ載せられる。** 天体の自前 Lambert +
    `NIGHT_AMBIENT = 0.04` の複製を、艦船と同じマテリアルパスの BRDF へ統合する
    (§2-1)。真位置になるまでは、天体ごとに違う `sunDirection` を持つこと自体が正しいので着手できない。
    `earth.ts` の地表シェーダも同時に分解する — BRDF 部分はマテリアルパスへ、
    もや・夕焼けは Phase 10 の大気パスへ移すため**一旦そのまま残す**。

**完了条件**: 圧縮定数がゼロ件。ズームを通して天体の見かけサイズが連続。
カイパー帯へ寄っても点群の量子化が見えない。**`LINE_RENDER_ORDER` の重なり順が反転していない。**
**天体を 1 つ追加してもシェーダコードが増えない。**

### Phase 5 — アルベドの物理量化と、露出・トーンマッピングの本実装

§1-1。**実作業量が最大のフェーズ。他フェーズと独立に着手できる。**

1. **101 天体のアルベドを入れる。** 16 進直書き色(63 種)を **RGB のアルベド値**へ置き換える
   (§1-1-1)。**輝度そのものは持たない。** 出典をコメントに残す(`RingOpticsDef` の帯コメントが手本)。
   **直書き色をそのままアルベドとして読み替えてはならない** — 現状の色は放射照度を畳み込んでおり、
   そのまま使うと太陽からの距離が二重に掛かる。
2. 露出基準を実装。`SOLAR_PRESSURE_1AU`(`srp.ts:6`)を `SOLAR_CONSTANT / c` から導出する形へ統一
   (同じ量の二重表現になっている)。
3. **出力段の露出係数 `EXPOSURE` を、放射照度基準の式から引き直す。**
   **`EXPOSURE` が 1.0 になる**(§1-1-2)。
4. `Billboard` をノードマテリアル化(§1-1-2)。太陽・惑星輝点は等級 → 放射照度へ。
5. 砲身赤熱を機体温度 + `STEFAN_BOLTZMANN` + `HULL_EMISS` の黒体放射へ。
6. 手調整値(`NIGHT_AMBIENT`、`SUN_INTENSITY`、各 opacity、`ZOOM_MUZZLE_FLASH_SCALE`)は**捨てる。**

**完了条件**: LDR クリップ回避のための係数が不要になる。
露出を 1 段変えると全体が一様に明るく/暗くなる。
**天体の明るさが太陽からの距離に応じて変わる**(現状は変わらない)。

### Phase 6 — 軸 2a: 遮蔽の合成基盤と、受け手側の差し替え

§1-6。**パイプラインの器(組み上がり済み)と Phase 4 の真位置が前提。**
**このフェーズは方式に依らない部分だけを置く** — 遮蔽源が何であっても要る配線と規約。
**実装方式が未決のまま進められる**ように切ってある。

1. **`render/pipeline/occlusion.ts` を新設。** 遮蔽源の列と、
   **透過率の積(= 光学的厚さの和)による合成**(§1-6-2)。
   **合成規約はここで確定させる** — 不透明も τ→∞ の極限として同じ式に乗るので、
   Phase 7 でどんな源が加わっても規約は変わらない。**逆に、後から差し替えることはできない**
   (受け手の呼び出し形を決めてしまう)。
   **置き場をライティングパスの中にしない** — 環と天体表面が前方描画のまま同じ関数を呼ぶ(§1-6-2)。
2. `sun-light.ts` の `sunVisibility()` の中身をこの基盤へ差し替える。**呼び出し側は無変更。**
   `environment-scene.ts` が `physics/shadow.ts` を読んでスカラを渡す配線を切る(§1-8)。
3. **遮蔽器の打ち切り規則。** 最大遮蔽率 `min(1, (β/α)²)` が閾値を下回る遮蔽器を CPU 側で落とす。
   **`physics/shadow.ts` の全件走査をオラクルにして打ち切り誤差を測る。**
   方式に依らず要る(どの源に渡すかが変わるだけ)。
4. **`SHADOW_MIN_SUN = 0.04` / `SHADOW_MIN_AMBIENT = 0.35` の床は残す。**
   点近似の埋め合わせではあるが、地球照(軸 1)が入るまでは影の中が真っ暗になる。
   **捨てるのは Phase 8。**
5. **少なくとも 1 つの源を載せて、規約が実際に動くことを確かめる。**
   どの源を最初に載せるかは `shadow_implement.md` の判断に従う。

**完了条件**: 受け手側が `sunVisibility(worldPos)` 1 本で遮蔽を引いており、
源を足しても受け手のコードが変わらない。`environment-scene.ts` が `physics/shadow.ts` を読んでいない。

### Phase 7 — 軸 2b: 遮蔽源の実装

**方式は未定。** 案とその評価材料は **`memos/hedalu244/better_graphics/shadow_implement.md`**。
Phase 6 の合成規約の上へ源を足す作業であり、**受け手側は無変更。**

方式に依らず効く制約:

- **`castShadow` / `receiveShadow` / `shadowMap` は現状 `src/` に 0 件。**
  シャドウマップを採る場合、これらはすべて新規。
- **`InstancedMesh.count` を毎フレーム書き換えてはならない**制約(§6 末尾)は、
  シャドウマップへ同じジオメトリをインスタンシングで描く場合にも効く。
- **`frustumCulled = false` の箇所**(§2-5)は、影の投射側でも外接球が当てにならない。
- **`GraphicsSettings` のトグルは「効くもの」だけ**(§2-6)。
  三角形数やテクセル数が実測で減る要素にだけ足す。

**完了条件**: 艦が地球の影へ入るとき、境界が半影の幅(LEO で 3.9 km)で滑らかに暗くなる。
月食の境界が柔らかい。リング影の境界がぼけ、帯ごとの透過率の差が影の濃さに出る。
**`inBodyShadow` の二値の段差が画面から消える。**
艦が自分の構造で影を落とし、カメラから遠ざけても画面上で劣化が見えない。
太陽系全体を見ている視点で、影のための追加パスが走らない。

### Phase 8 — 軸 1: エリアライト(球光源・ランバート球)

§1-5。**Phase 5 のアルベドが前提。変更はライティングパス(`light-prepass.ts`)の中に閉じる。**

1. **太陽を一様球光源へ**(§1-5-1)。拡散項は距離とともに逆二乗則へ自動で縮退する閉じた解を使い、
   **「遠いときは点光源」という分岐を書かない。** 鏡面項だけ角半径の閾値で LTC / 点光源を切り替える。
2. **天体をランバート球へ**(§1-5-2)。照らされている半球を等価な円盤へ代表させ、LTC を適用。
   **光が来る「向き」の偏りが表現されることを完了判定にする**(単なる明るさの位相変調では不可)。
   強さは **Phase 5 のアルベド × その天体が太陽から受けている放射照度**(§1-1-1)。
   **アルベドをそのまま光源の強さにしない。**
3. **光源の打ち切りは立体角の閾値で**(§1-5-3)。実用上「太陽 + 最も近い 1〜2 天体」に収まる。
4. 光源天体自身の日照は Phase 6/7 の遮蔽基盤を共有(影に入っている天体は光らない)。
5. **受け手が乗っている天体自身を遮蔽の対象から除外する。**
   N·L を球光源の閉じた解へ替えると、終端の柔らかさを光源積分と自己遮蔽が二重に表すことになる。
   G バッファへ天体 id を書いて除外する。**Phase 7 まで許容できていた ±30 km の二重暗化
   (地球の直径の 0.2%)が、ここで許容できなくなる**(`shadow_implement.md` §3-2)。
6. **`AmbientLight(0x8899bb, 0.25)` を削除。** 地球照が置き換える(§2-1)。
   **`SHADOW_MIN_SUN` / `SHADOW_MIN_AMBIENT` の床もここで捨てる**(Phase 6 の項目 7)。
7. 色を持つ光源として扱う。**艦の影側が地球の色を帯びることを検証ケースにする。**

**完了条件**: LEO で艦の地球を向いた面と宇宙を向いた面の明るさが桁で違う。
高度を上げていくと地球照が滑らかに弱まり、月軌道では点光源と区別がつかなくなる
(**その遷移でフレームが飛ばない**)。三日月形に見える位置で地球照が弱く、光の向きが偏る。
**木星圏で艦を照らす木星照が、地球圏の地球照より暗い**(距離依存が式に入っている証拠)。
`AmbientLight` が src から消える。

### Phase 9 — 半透明パスの統合

1. `render/transparent-pass.ts`: 不透明カスケード解決後に描画。`viewportDepthTexture` / `linearDepth`。
2. 「視線に沿って不透明面までメディアを積分する」共通ヘルパ。**大気・オーロラ・プルーム・リングが共有する。**
   **環の遮蔽と同じ光学モデル(Beer–Lambert)を共有できるか検討する。**
3. `earth.ts` の大気リム球を廃止 — `depthTest:false` + 自前球交差の回避策が不要になる。
4. `aurora.ts` の CPU 頂点更新を GPU へ。
5. `depthTest: false` の 3 箇所を規約内へ回収する。
6. **`LINE_RENDER_ORDER` を `render/` へ移し、線以外の半透明物を同じ表へ統合する。**
   値 5 の衝突(§2-4)はこの統合で解消する。
7. 加算合成の上限は Phase 5 の露出基準に従う。

### Phase 10 — 大気散乱(指数密度)

1. 透過・単散乱・多重散乱近似を LUT 化(オフライン生成も可)。カメラが大気圏内外どちらでも同じモデル。
2. Phase 9 のレイ積分枠組みへ載せ、エアリアルパースペクティブを不透明深度に対して積分。
   `earth.ts` のもや(`ATMO_HAZE_TAU0 = 0.34`)を置換。
3. 夕焼けを光路長から導出し、`vec3(1,0.4,0.1)` の固定補間を削除。
4. 雲は当面マテリアルパス内の 2 層サンプリング。
   **`earth.ts` の UV ずらしによる雲影は、そのままでよい。** 雲の高度 ~1e4 m での半影幅は
   2αd = 93 m なのに対し、雲テクスチャは 8192px で赤道一周 4.0e7 m = **4.9 km/テクセル**。
   **半影がテクセルの 1/50 しかないので、ぼかすべき構造がそもそも存在しない。**
   雲を遮蔽源へ載せる価値があるとしたら、半影ではなく「雲が他の物体へ落とす影」のときだけ。
5. `GraphicsSettings` へ雲のトグルを足す(この時点で単体で切れるようになる)。

### Phase 11 — ポストエフェクト

1. 露出 → ブルーム → レンズフレア/グレア → トーンマッピング → sRGB。
2. ブルーム対象は Phase 5 で HDR 化済みの発光体。**再突入プラズマは既に動圧という物理量から
   強度を引いている**(`REENTRY_GLOW_MIN_Q` / `_FULL_Q`)ので、HDR 化の検証基準ケースに使える。
3. TAA/SSAA は `GraphicsSettings` のトグル配下で任意。AO は優先度低。

### Phase 12 — ボリュームレンダリング

Phase 9 のレイ積分枠組みが前提。プルーム・RCS・再突入・オーロラを板ポリゴンから参加媒質へ。

### Phase 13 — 軸 3: 地球照の遮蔽(任意)

§1-7。**優先度最低。無視したままでも計画は完結する。**

1. AO を導入し、地球照(および他の二次反射光)にのみ掛ける。太陽光には掛けない
   (太陽光の遮蔽は Phase 6/7 が正しく解いているので、AO で二重に暗くしてはならない)。
2. **全天体からシャドウマップを撮るという方向は採らない**(原理的に不可能、§1-7)。

## 4. 責務境界の規則(全フェーズ横断)

> **`game/` は「なにがあるか」を知り、「どう見えるか」を知らない。**
> **`render/` は「どう見えるか」を知り、「どこにあるか(ECI)」を知らない。**
> **ライティングパスは「光源の形」と「遮蔽」を知り、「材質」を知らない。**
> **レンダリングパスは「材質」を知り、「光源の形」も「遮蔽」も知らない。**

4 行目までが揃うと、軸 1(光源の形)と軸 2(遮蔽)が互いに独立に差し替えられる。
**これがこの構成の目的である。** Phase をまたいで少しずつ寄せる。一括改修はしない。

### 移す

| 対象 | 現在 | 移動先 | 対応フェーズ |
|---|---|---|---|
| **描画用の日照判定** | `environment-scene.ts` が `physics/shadow.ts` を読み `SunLight` へ渡す | **`render/pipeline/occlusion.ts` の遮蔽源。物理側の関数は残るが描画は読まない**(§1-8) | Phase 6(中身の差し替え) |
| `celestial/{sphere,point,sun,earth}-body.ts`, `ring-view.ts`, `point-field-view.ts` | `game/celestial/` | `render/celestial/` | Phase 4 |
| テクスチャURL表・101天体の配色 | `celestial-registry.ts:14-26, 103-196` | `render/`。レジストリには**表示名とidだけ**残す | Phase 5 |
| `RingOpticsDef.color` | `physics/solar-system.ts` | `render/`。τ・アルベド・位相係数は物理なので残す | Phase 5 |
| エフェクトの size/opacity 式・配色 | `vfx/`, `player/*-effects.ts`, `const.ts` | `render/` | Phase 5 |
| 参照線の色・不透明度・`renderOrder`・頂点密度方針 | `environment-scene.ts` | `render/` | Phase 9 |

### 残す

- `physics/` の THREE 非依存(**現状ゼロ件、維持する**)。
- `physics/projection.ts` — 物理・幾何として妥当。
  **`projection.ts` が near/far 非依存であることは、カスケード導入時の重要な資産**(§1-3)。
  リングの放射伝達は `render/ring.ts` の TSL グラフのみに存在する。
- **`physics/shadow.ts` の日照率(軸 4)は物理側に残す。** 熱・電力・SRP の消費者がいる。
  **ただし描画はこれを読まない**(§1-8)。同じ物理現象について CPU と GPU に別実装があることになるが、
  **問いが違う**(点の日照率 vs 画素ごとの遮蔽度)ので二重実装ではない。
- `render/ships.ts` の `game/const` 参照 — 読み取り専用の例外。Phase 5 以降は寸法のみ。
- `GameEntity.obj: THREE.Object3D` — 不透明ハンドルとして当面許容(`game/` の 47 ファイルが
  `three/webgpu` を import している)。ただし
  **`game/` 側で material / renderOrder / LOD / 色 / `castShadow` を決めるのは禁止**とする。

### 判断基準

`game/` に書いてよいのは「この天体が存在する」「この位置(ECI)にある」「破壊された」まで。
「何 px だから点で描く」「`renderOrder` は 3」「色は `0x9a8a7a`」「影を落とす」は `render/` の判断。

## 6. 次の一歩

**次に着手するのは Phase 4(Z 精度の実測と距離圧縮の撤去)。**
ただし**本体は three r186(2026-08-19 予定)を待つ** — `0.185.1` の `reversedDepthBuffer` は
`renderOrder` を全反転させる(§1-3)。

**待っている間に前倒しできるもの**(いずれも r186 に依存しない):

- **画像回帰シーン**(パイプライン現況節の宿題 2)。Phase 4 が絵を最も大きく動かすので、
  先に用意すると以降の判定が楽になる。パス別 GPU 時間と中間ターゲットのデバッグ表示は既に使える。
- **`render/view-space.ts` への順変換 5 種の集約**(Phase 4 の項目 1)。判断の結果によらず有効。
- **`point-field-view.ts` の f32 量子化の実測**(Phase 4 の項目 4)。深度とは独立した問い。
- **Phase 5 のアルベド調査** — 他フェーズと独立。**Phase 8(軸 1)の光源強度の前提でもあるので、
  早く始めるほど効く。** RGB のアルベド値として集める(§1-1-1)。
- **軸 2 の方式の決定** — `shadow_implement.md` §8 の「判断に必要だが、まだ測っていないもの」を潰す。
  Phase 6 は方式に依らないので、決まらなくてもロードマップは止まらない。

### 描画の現状の負荷(Phase 7 の余裕の根拠)

戦闘ビューで draw calls 約 165 / triangles 約 33 万(弾 347・薬莢 96・デブリ 24 が出ている状態)。
マップビューで draw calls 約 198。

連射中(弾 150 体以上)の実測:

| 条件 | fps | render (avg) | update (avg) | draw calls |
|---|---|---|---|---|
| インスタンシングあり | 45 | 1.2ms | 19.4ms | 164 |
| インスタンシングなし(個別メッシュ) | 46 | 1.8ms | 17.9ms | 388 |
| 毎フレーム メッシュ再確保 | 27 | 8.7ms | 25.2ms | 434 |

**インスタンシングは draw calls を 388→164 へ半減させるが、fps はほとんど変わらない(46→45)。**
理由は描画フェーズが 1〜2ms しかかからず、**ボトルネックが update フェーズ**(約 18〜19ms、この
グラフィック基盤ロードマップの外側の課題)にあるため。一方で毎フレームのメッシュ再確保は明確に
悪い(render 8.7ms、fps 27)。

→ **インスタンシングの価値は現時点の fps ではなく、シャドウマップを採った場合に段数だけ描く Phase 7 に
向けた余裕である。** ジオメトリ 2 回描きぶんは既に払っており、実測で draw calls は約 324。

**上表の「render」は CPU 側の壁時計時間であって GPU の実行時間ではない**ので、パスを増やした
あとの判断には使えない。パス別の GPU 時間(負荷確認ウィンドウの 描画 グループ)を見ること —
戦闘ビューでの実測は G バッファ 0.6ms / ライティング 0.5ms / マテリアル 0.6ms /
ワールド 2.6ms / 合成 0.4ms。

### `InstancedMesh.count` を毎フレーム書き換えてはならない

three の `InstanceNode` は instanceMatrix の受け渡し経路(uniform buffer か instanced attribute か)を
`count` から決め、その判断とバッファ長を最初の描画時に一度だけ確定する。弾が 0 体のフレームで
`count = 0` になると長さ 1 に固定され、以後何体積んでも描画されなくなる。
そのため `InstancedPool.count` は容量に固定し、未使用の枠をゼロ行列で潰す方式にしている。
**シャドウマップへ同じジオメトリをインスタンシングで描く Phase 7 でも同じ制約が効く。**
