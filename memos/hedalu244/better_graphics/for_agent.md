# グラフィック基盤 — ロードマップ

個々の見た目の仕様は `DEVELOP/EARTH_MOON_GRAPHICS_PROPOSAL.md` /
`DEVELOP/PHYSICAL_RING_RENDERING_PROPOSAL.md` が持つ。この文書はその下に敷く土台だけを扱う。

完了したタスクは文書から削除し、残りのToDoと、後件の判断のために必要な情報だけのこす。
コードの状況についても計画開始時点の歴史的経緯を残さず、常に最新にする。

**適用範囲の前提**: LEO で優れた性能が出ることは最低要件だが、**太陽系全域で破綻しないこと**が
同時に要件である。「LEO でしか使わないから」を実装する/しないの根拠にしてはならない。
カメラは既に太陽系全体を見渡せる(`OverviewCamera`)ので、そこで破綻する設計は採れない。

## 0. 光と影を分ける 4 つの軸

「光源の大きさをどう積分するか」と「影をどう作るか」は独立した問題であり、
1 つの話として設計してはならない。この文書は光と影を次の 4 軸へ分け、
**軸ごとに独立して差し替えられる形**を目指す。

| 軸 | 問い | 方針 |
|---|---|---|
| **軸 1** | **反射** — 光源の大きさを、受け手はどう積分するか | **§1-5**。太陽=球光源、天体=ランバート球。遠方で点光源へ**滑らかに縮退する単一の仕組み** |
| **軸 2** | **太陽光の遮蔽** — 影をどう作るか | **§1-6。全面的にシャドウマップ。** GPU に解析的な遮蔽計算を残さない |
| **軸 3** | **地球照の遮蔽** | **§1-7。無視するか AO 近似。** 全天体からシャドウマップを撮るのは原理的に不可能 |
| **軸 4** | **CPU 側の日照率** — 熱・電力・SRP | **§1-8。描画とは別の問い。実装済み。** 描画へ流用するのはアドホックなので避ける |

**実装順**: **軸 2 → 軸 1 → 軸 3**(軸 4 は実装済み)。理由は §3 冒頭。

## 1. 確定した判断

### 1-1. 露出 — 放射照度を基準に取り、既存の手調整値は捨てる

**方針(確定)**: HDR 線形空間へ移した上で、物理的根拠のある式へ組み替える。視覚的な問題が出たら
**HDR 空間の上で**再調整する。LDR 時代の手調整値へ戻す方向の調整はしない。

```text
E(d) = SOLAR_CONSTANT * (AU / d)^2      [W/m^2]    — 距離 d における放射照度
L_surface = E(d) * albedo / pi          [W/m^2/sr] — 完全拡散反射面の放射輝度
exposure  = 1 / L_ref                              — L_ref を中間グレーへ写す係数
```

必要な量は**すべて既にある**: `SOLAR_CONSTANT = 1361`(`game/const.ts:65`)、
`ASTRONOMICAL_UNIT`(`physics/srp.ts:9`)、逆二乗則(`physics/srp.ts:24`)、
`STEFAN_BOLTZMANN` / `HULL_EMISS`(`game/const.ts:44-45`)、機体温度(`game/const.ts:47-51`)。

**唯一の欠落はアルベドである。** 天体表面は 101 天体ぶんの 16 進直書き色(86 リテラル、ユニーク 63 種、
`celestial-registry.ts:103-196`)しか持たず、アルベド値は 1 つも無い。根拠コメントも無い。
**これが露出フェーズの最大の実作業になる。**
さらに §1-5 により、**アルベドは「表面の見え方」ではなく「他の物体を照らす光源の強さ」を兼ねる。**

`SOLAR_PRESSURE_1AU = 4.56e-6`(`physics/srp.ts:6`)は `SOLAR_CONSTANT / c` と同じ量の二重表現。
片方をもう片方から導出する形へ統一すること。

**既にこの基準で書かれている部分がある。** リングだけが完全な放射伝達モデルになっている —
`RingOpticsDef` の単一散乱アルベド・法線光学的厚さ・HG 非対称因子が全 36 帯に出典コメント付きで入り、
その単一散乱の式(`render/ring.ts` の `physicalMaterial` が組む TSL グラフ)は明示された単位を持つ。
現状はこれを `RADIANCE_SCALE = 0.72`(`render/ring.ts:27`)という**手調整係数 1 個**で LDR へ押し込んでいる。

> **露出の校正はリングを基準に取る。** `RADIANCE_SCALE` が 1.0 になることを完了条件の一つにする。

**HDR 化で構造変更が要る箇所**: `Billboard` は `MeshBasicMaterial.opacity`(0..1 クランプ)で
明るさを表しており、`transparent + AdditiveBlending` の 5 経路の最大のものがここを通る
(`render/billboard.ts:16-18`)。1 を超える輝度を出せないので、ノードマテリアルへ置き換える。

### 1-2. 座標境界 — GPU に ECI 絶対座標を載せない

**不変条件(維持する)**: 描画はすべてフローティングオリジン座標系(`THREE.Vector3`)で行い、
GPU に ECI 座標(独自 `Vec3`)が渡らないこと。具体的には
**`src/render/**` から `Vec3` / `KinematicState` / `ReferenceFrame` / `Attractor` /
`Ephemeris` / `OrbitalElements` / `FloatingOrigin` への import が 0 件**であること。
以降のどのフェーズでもこれを崩さない。**新しいパス(G バッファ・照度バッファ・シャドウマップ)を
足すときも、シェーダへ渡す位置はすべて描画座標系である。**

**曲線については解決済み。** `render/curve.ts` は頂点を `Float64Array`(`bakedLocal`)で保持し、
カメラ近傍の pivot を引いた差分だけを f32 バッファへ書く(`curve.ts:237-244, 318-331, 338-354`)。
`OrbitLine` / `TrajectoryLine` は `Curve` 経由なので、海王星軌道のような大きな絶対値でも
f32 量子化は起きない。

**残っている 1 箇所**: `game/celestial/point-field-view.ts:96` の `instanceMatrix` は
太陽中心の生座標(カイパー帯で ~7.5e12 m)を pivot 補正なしに f32 へ書いている(量子化 ~5e5 m)。
**引きの絵では画素以下だが、寄ると露見するはず。Phase 2 で実測する**(§3 Phase 2 の項目 0)。
`Curve` と同じ pivot 補正を入れるのが対処だが、**測ってから決める。**

### 1-3. 深度カスケード — 測ってから決める。変換は一か所に閉じる

**方針(確定)**: 距離圧縮の撤去は GPU 上の深度精度が担保できるかが鍵であり、やってみないと分からない。
**スパイク → 測定 → 判断 → 本実装**の順。判断が否なら距離圧縮は残る(影響は §1-6 と §5)。

判断を楽にする事実:

- **`physics/projection.ts` は near/far に一切依存しない**(`:10-16, 19-37, 40-46`)。
  → **fov/aspect を共有する限り `ProjectFn` / `ScaleFn` の全消費者(マーカー約10系統、picking 5系統、
  plan 系、`TrajectoryLine` の頂点密度、`ring-view` の LOD、`point-body` の 2px 判定)は無変更で通る。**
- **投影行列を書く箇所は `camera/camera-system.ts:72` の 1 箇所だけ。**
- **`COMBAT_CAMERA_FAR = 6e7` は `MOON_VIS_DIST = 4.5e7` から逆算された値**(`const.ts:120-123`)。
- **地球だけは既に真位置・実半径**(`earth-body.ts:35`)。真スケール描画の前例が既にある。

**カスケードと浮動原点**: 浮動原点は 1 つのまま、カスケードは near/far だけを持つ。
遠方カスケードでは要求される絶対精度も緩いので釣り合う。**仮説であり測定対象そのもの。**

**変換の切り出し(要件)**: ECI → 描画位置の順変換は **5 種類に分散**し、逆変換は **1 つも無い**。
`FloatingOrigin.RtoThreeV3` / `sphere-body.ts:101-106` / `point-body.ts:159-164` /
`sun-body.ts:54-62` / `point-body.ts:212-216` / `environment-scene.ts:157-158`。
1 モジュール(`render/view-space.ts`)へ集約し `toRender` / `toEci` / `cascadeOf` / `cascadeNearFar` を公開する。
**圧縮を採るにせよ撤去するにせよ、この集約は先にやる。**

**測定項目**: (a) 分割数 2/3/4 での z-fighting、(b) パス増加によるフレーム時間、
(c) `depthTest: false` の 3 箇所(`stars.ts:28` / `earth.ts:101` / `plan-gizmo-3d.ts:33`)が
深度クリアと衝突しないか、(d) `frustumCulled = false` の箇所が多いので `camera.layers` 振り分けが効くか。

`Renderer.clearDepth()` は `@types/three` が型を持つので、カスケードの深度クリアは自前宣言なしで書ける。

### 1-4. ライトプリパス(3 パス構成)

**方針(確定)**: 2 パス遅延シェーディングをやめ、**3 パスのライトプリパス**を採る。

```text
Phase A  ジオメトリパス   → 深度 + 法線 + 粗さ            (幾何だけ。マテリアルの色を持たない)
Phase B  ライティングパス → 拡散照度バッファ + 鏡面照度バッファ
                            光源の形の積分・遮蔽問い合わせはここに閉じる
Phase C  レンダリングパス → 再度ジオメトリを描き、照度バッファを読み、材質を掛ける
Phase D  半透明 + ポストプロセス
```

**なぜ 2 パスでは足りないか**: 遅延シェーディングでは「光源の立体角積分」と「BRDF 評価」が
同じシェーダに同居する。§1-5 で光源の種類(球・ランバート球・点への縮退)を増やす以上、
マテリアル分岐との掛け算で膨らむ。ライトプリパスは**照度という中間表現で両者を切る**:

- **ライティングパスは「その点にどの向きからどれだけ光が来ているか」だけを答える。**
- **レンダリングパスは「来た光をこの材質がどう返すか」だけを答える。**

**トレードオフ**: ジオメトリを 2 回描く(ドローコール増)代わりに G-buffer が狭くなり、
マテリアルの多様性と光源の多様性が独立に増やせる。

**既知の限界**: 鏡面反射は「入射方向 × 視線 × 材質」に依存するので照度バッファ 1 枚に畳めない。
標準的な対処は**粗さをジオメトリパスに書き、その粗さで積分した鏡面項を別バッファに出す**こと。
拡散反射が支配的な天体表面 + 少数の金属的な艦船という本作の絵では破綻は小さいと見込むが、
**破綻したら艦船だけを前方描画へ逃がす**(ドローコールは既に 2 回なので構成は壊れない)。

**器を先に作る**: 光源の実装(§1-5)も影の実装(§1-6)も、この器が無いと載せる場所が無い。
したがって**器は序盤に作り、その時点では単一の平行光(現状と同じ絵)を通す。**
絵が変わらないことをもって器の正しさを確認する。

### 1-5. 軸 1 — 反射(光源の大きさをどう積分するか)

**方針(確定)**: 光源が十分近く大きいときは面光源、十分遠く立体角が小さいときは点光源。
**これを分岐ではなく、単一の式が滑らかに縮退する形で実現する。**
太陽にも地球にも月にもその他の天体にも、同じ仕組みが適用される。

**なぜ必要か(立体角)**:

| 光源 | 視点 | 視半径 | 立体角 | 全天比 |
|---|---|---|---|---|
| 太陽 | 1 AU | 0.266° | 6.8e-5 sr | 5.4e-6 |
| 太陽 | 水星近日点 0.31 AU | 0.86° | 7.1e-4 sr | 5.6e-5 |
| 地球 | LEO 420 km | **70.0°** | **3.90 sr** | **31%** |
| 地球 | 静止軌道 | 8.6° | 0.071 sr | 0.56% |
| 地球 | 月軌道 | 0.95° | 8.6e-4 sr | 0.007% |
| 木星 | エウロパ軌道 | 11.5° | 0.126 sr | 1.0% |

**太陽ですら完全な点ではなく、地球は LEO で全天の 31% を占める。**
そして**同じ地球が月軌道では点光源と区別がつかない。** 近距離用と遠距離用に別モデルを持つのではなく、
**距離とともに連続に縮退する 1 つのモデル**でなければ、遷移する場所で絵が飛ぶ。

#### 1-5-1. 太陽(恒星) — 一様球光源

最も単純な形。球全体が一様な放射輝度を持つ。**一様球光源からの拡散照度には閉じた解があり、
その式は距離が大きくなると自動的に逆二乗則へ縮退する。** したがって
**「遠いときは点光源に切り替える」という分岐は書かない** — 同じ式が両方を覆う。

分岐が要るのは鏡面項だけ。LTC(Linearly Transformed Cosines)による球光源の積分は
角半径が小さいと数値的に無駄なので、閾値で点光源近似へ落としてよい
(拡散項と違い、鏡面のハイライトは光源が小さければ本当に点と区別がつかない)。

#### 1-5-2. 惑星・衛星 — ランバート球(部位によって照度が違う球)

**太陽と決定的に違うのは、球面の一部しか光っていないこと。** 昼側だけが光り、
艦から見ると三日月形になる。一様球光源では表せない。

**近似(確定)**: **ランバート球**として扱う。球面上の各点の放射輝度が
`L(p) = E_sun * albedo * max(0, dot(n_p, sun_dir)) / pi` で与えられる球。

- **一様球ではないので LTC の標準的な適用範囲外である。** これは承知の上で採る近似であり、
  検証ケース(三日月形に見える位置での地球照)で妥当性を確かめる必要がある。
- 実装の候補は 2 つある。(a) 照らされている半球を**等価な円盤へ代表させ**、その円盤に LTC を適用する
  (位相角に応じて円盤の面積と位置をずらす)。(b) 球光源の閉じた解に**位相係数**を掛ける
  (正しくない — 明るさは合うが、光が来る「向き」の偏りが表現されない)。
  **(a) を採る。** 光が来る向きの偏りこそが軌道上の絵の特徴だから。
- **色を持つ光源になる。** 地球は海の青・雲の白・陸の褐色を持つので、艦の影側が青みを帯びる。
  初版は全球平均色でよく、局所分布(雲がある側が明るい)は将来の改良。

#### 1-5-3. 光源の打ち切り

**打ち切りの基準は距離ではなく立体角。** 立体角が閾値を下回った光源は
点光源として扱う(縮退は式が自動でやるので、実際には「LTC を使うか点光源で済ますか」の判断だけ)。
さらに小さければ照度そのものが無視できるので光源リストから外す。
**太陽系全域で、光源リストは実用上「太陽 + 最も近い 1〜2 天体」に収まる。**

#### 1-5-4. 現状との差

今は `AmbientLight(0x8899bb, 0.25)`(`environment-scene.ts:88`)という
**方向も距離も位相も持たない定数**が、地球照・星明かり・多重散乱の全部を兼ねている。
軸 1 の完成はこの定数を消す作業でもある。

#### 1-5-5. なぜ軸 1 を後回しにできるか

**ライティングパス(Phase B)とレンダリングパス(Phase C)が分離されていれば、
軸 1 の変更は Phase B の中に閉じる。** 最初は太陽も天体も点光源として実装しておき、
後から球光源・ランバート球へ差し替えられる。**受け手側のコードは一行も変わらない。**
これが軸 2 より優先度を下げられる理由である。

### 1-6. 軸 2 — 太陽光の遮蔽(シャドウマップへ全面統一)

**方針(確定)**: 太陽光の遮蔽は無視できず、**ソフトシャドウ的な照度変化の再現が要る。**
太陽の立体角が小さくても、**半影のスケールは遮蔽器までの距離に比例して大きくなる**ので無視できない。
そして**以下はすべて同じ現象であり、同じ基盤(シャドウマップ)で表現されるべきである**:

- 地球の影に出入りする艦の照度変化
- 艦のセルフシャドウ
- 月食の境界
- 土星のリング影の境界

#### 1-6-1. 解像度は対象の絶対寸法ではなく、画面上で見えている範囲で決まる

**軸 2 の設計全体を貫く原則。** リング系全体を 1 枚のシャドウマップで覆おうとすると解けない —
天王星 λ 環(幅 1.5e3 m @ 半径 4.2e7 m、比 3.6e-5)に 1 テクセル割り当てるだけで
2.8 万テクセル/軸が要る。**しかし 1 枚で覆う必要がない。**

λ 環の影の境界が見えるほど寄っているとき、カスケードが覆うべき範囲も同じだけ狭い。
逆に、リング系全体が画面に収まるほど引いているなら、λ 環の影は 1 px 未満なので解像する必要がない。
**したがって「対象がどれだけ細いか」ではなく「画面上で何 px を占めるか」がテクセル密度を決める。**

同じ原則が §1-3 の深度カスケードにもある。**カスケード選択のポリシーは 1 つのモジュールが持つ。**

#### 1-6-2. カスケードの軸は「カメラからの距離(画面上のスケール)」

遮蔽に関わる寸法は **1e0 〜 1e10 m** に開く。

| 遮蔽の対象 | 寸法 |
|---|---|
| 艦の構造 | 数 m(`PLAYER_HULL_RADIUS = 2.6`、全長 5〜6 m) |
| 追跡カメラ距離 | 12〜8000 m |
| 戦闘域 | 10〜30 km |
| 惑星本体 | 1.7e6〜7.2e7 m |
| リング系 | 6.7e7 〜 1.3e10 m(土星フェーベ環) |

1 枚では不可能。しかし**カスケードを「光源からの距離」ではなく「カメラからの距離」で切れば解ける**:

- **艦がカメラから十分遠ければ(画面上で十分小さければ)、そのセルフシャドウが高解像度である必要はない。**
- **ほぼ点にしか見えない惑星の蝕は、そもそも無視できる。**

これで**艦のセルフシャドウ・月食の境界・リング影を統一的に扱える。**

#### 1-6-3. 難所 — 「地球の影に出入りする艦」

**カメラから十分に近い被遮蔽物に対して、無視できない規模の巨大な遮蔽物がある**という構造。
艦(5 m)と地球のシルエット(1.3e7 m)の比は 2.6e6 で、1 枚のマップには載らない。

**解決**: **遮蔽器を 1 枚のマップへ排他的に割り当て、受け手は自分を含む全マップに問い合わせて積を取る。**

- 地球は**粗いカスケード**の遮蔽器になる。艦はそのマップの中では点でよい。
  必要な精度は「終端(明暗境界)の位置」だけであり、これは低周波の量である。
- 艦は**細かいカスケード**の遮蔽器かつ受け手になる。ここで自己影が解像される。
- 艦は**両方の受け手**であり、遮蔽度は積で合成される。

**排他割り当てが必要な理由**: 同じ遮蔽器が 2 枚に入ると、積を取ったときに二重に暗くなる。
「各遮蔽器はちょうど 1 枚のマップに属する」を不変条件にする。

**Z 精度**: マップごとに近接範囲が決まるので、**Z 精度もマップ単位でカスケードする**のが順当。
これに失敗した場合の退路は §1-8 の CPU 側計算を描画へ流用することだが、
**これはアドホックな方法なので可能な限り避ける。**

#### 1-6-4. 太陽は方向光源ではない(全方向へ照らす)

**カメラのスケールによって、太陽が一方向と近似できる場合とできない場合がある。**

- 特定の惑星に寄って惑星や艦を見ている視点では、狭い画角のシャドウマップで足りる。
- **太陽系全体を見ている視点では、太陽は全方向へ光を放っているため、180° を超える画角が要る。**
  しかし太陽系はほとんどが虚空なので、そのほとんどの情報が捨てられる。

**解決**: **1 枚の広画角マップを組まない。オブジェクトが実際に存在する方向だけを狙い撃ちする。**

遮蔽器を空間的にクラスタリング(実質的には「惑星とその衛星と周辺の艦」の単位)し、
**クラスタごとに 1 枚のマップを組む。** 太陽から見たクラスタの角度的な広がりは常に極小
(太陽から見た地球は 4.3e-5 rad)なので、**クラスタごとに平行投影で十分**であり、
広画角の透視投影は最初から要らない。視差誤差はクラスタの角度幅で抑えられる。

さらに、**画面上で 1 px 未満のクラスタはマップを組まない。**
太陽系全体を見ている視点では、ほぼすべてのクラスタがこれに該当する。
「無駄の多い広画角マップ」は、そもそも作られない。

#### 1-6-5. 一段階抽象化した要件

以上をまとめると、必要なのは:

> **1 つの恒星に対して、複数の画角・複数の Z 精度・複数の範囲のシャドウマップを組み合わせ、
> 遮蔽度を合成する基盤。**

```text
ShadowSet
  maps: ShadowMap[]              各マップ: 投影(向き・範囲・near/far)・解像度・所属する遮蔽器
  assign(occluder) -> map        遮蔽器はちょうど 1 枚に属する(二重計上の防止)
  select(cameraDist, screenPx)   画面上のスケールで必要なマップだけを組む
  visibility(worldPos) -> [0,1]  自分を含む全マップの積
```

受け手側の入口は §1-4 で置いた `sunVisibility(worldPos, normal)` のまま変わらない。
**中身がこの合成基盤へ差し替わるだけ**であり、天体表面・艦の BRDF・リング・大気の呼び出しは無変更。

#### 1-6-6. 半影(ソフトシャドウ)

太陽の視半径は 1 AU で 4.65 mrad。**半影の幅は遮蔽器から受け手までの距離 d に対して `d × 9.3e-3`。**

| 状況 | d | 半影幅 | 対象の寸法 | 比 |
|---|---|---|---|---|
| 艦の自己影 | 5 m | 4.7 cm | 5 m | 1% — 「わずかに柔らかい」 |
| 艦が地球の影へ | 1e6 m | 9.3e3 m | 5 m | **艦は完全に階調の中** — 実質オブジェクト単位の連続値 |
| 月食の境界 | 3.8e8 m | 3.5e6 m | 月 3.5e6 m | **半影が月と同じ大きさ** — 境界が極めて柔らかい |

**遠いほど半影が支配的になる。** PCSS(Percentage-Closer Soft Shadows)でブロッカー距離を
推定し、**フィルタ半径を太陽の角半径から導く。チューニング値ではなく物理量である。**
これで `inBodyShadow`(`render/ring.ts`)が二値であることが解消する。

#### 1-6-7. 半透明な遮蔽器 — 深度だけでは足りない

**リングは不透明ではない。** `RingOpticsDef` の法線光学的厚さは 2e-8 〜 8 の範囲にあり、
帯によって透過率が桁で違う。**深度のみのシャドウマップは「遮った / 遮らない」しか表せず、
Beer–Lambert の透過率を表せない。**

したがって、**遮蔽器の種類によってマップの中身が変わる**:

| 遮蔽器 | マップに書く量 |
|---|---|
| 艦・デブリ・基地・天体本体 | 深度(不透明) |
| リング帯・(将来)大気 | **累積光学的厚さ、または透過率** |

これは既知の技法(deep shadow map / Fourier opacity map の系統)であり、
**軸 2 の基盤設計に最初から入れておく必要がある。** 後から足すと合成規則が変わってしまう。

#### 1-6-8. 距離圧縮への依存

**リング影シェーダは現状「真の方向 × 偽の位置」を混ぜている。**
`sunDirNode` は天体の**真の ECI 位置**から引いた方向(`sphere-body.ts:89-90`)なのに、
`positionWorld` と 32 バンドの `center` / `inner` / `outer` は**圧縮された描画位置・描画長**
(`celestial-surface.ts:142-164`)。`ring.ts` の `bodyRadius` にも描画スケールが入る。

**距離圧縮を撤去しない限り、遮蔽を物理的に正しく統一することはできない。**
これが §1-3 のカスケード判断と軸 2 を結びつける決定的な依存関係である。

#### 1-6-9. 廃止されるもの

軸 2 の完成に伴い、以下は GPU から消える:

- `render/celestial-surface.ts:109-116` の**固定長 32 バンド uniform 配列**と、
  それを読む TSL グラフ（`:77-105`）によるリング影。
- `render/ring.ts:74-80` の解析的 `inBodyShadow`(二値)。

**解析的な球影は CPU 側(軸 4)にのみ残る。** 描画は全面的にシャドウマップへ移る。

### 1-7. 軸 3 — 地球照の遮蔽(優先度低)

**方針(確定)**: 太陽光と比べて照度のオーダーが小さいので、**無視するか、AO として近似する。**

**軸 2 と同じ方法は原理的に採れない。** シャドウマップは光源ごとに要る。天体は 101 個あり、
そのすべてから撮ることはできない。§1-5 で光源リストが「太陽 + 最も近い 1〜2 天体」に
収まるとしても、面光源(ランバート球)に対する影は点光源に対する影よりさらに高価である。

**採る手段**:

1. **無視する。** 初版はこれでよい。地球照は太陽光の 1e-2 〜 1e-3 のオーダーであり、
   その中の遮蔽の差はさらに小さい。
2. **AO として近似する。** 幾何的な遮蔽度(周囲がどれだけ開けているか)を
   地球照に掛ける。方向を持たない近似だが、艦の凹部が暗くなるという主要な効果は出る。

**優先度は最も低い。** 他のどの軸にも依存されない。

### 1-8. 軸 4 — CPU 側の日照率(熱・電力・SRP)

**CPU 側の日照率と GPU 上のシャドウマップは別物であり、二重実装ではない。**
問いが違う — 前者は**ある 1 点の日照率**(艦を点と見なしてよい)、後者は**画素ごとの遮蔽度**
(艦は点ではなく、自己影を持つ)。したがって軸 2 が完成しても `physics/shadow.ts` は残る。

`physics/shadow.ts` の `sunlitFactor(r, star, attractors)` は実装済みで、
熱・電力(`game/player/player.ts:254`)と SRP(`physics/dynamics.ts:120`)が消費者。
**このフェーズで新たにやることは無い。**

**残っている 1 本の配線だけが軸 2 の作業対象**: 描画照明(`game/celestial/environment-scene.ts:136`)が
この関数を読んで `DirectionalLight.intensity` を変調している(`:159-160`)。
**この経路は軸 2 の完成(Phase 5/8)をもって切る。**

**描画への流用は退路であって設計ではない**: §1-6-3 の Z 精度カスケードが失敗した場合に限り、
CPU 側の点近似を艦の視覚的な照度へ流用する道が残る。**ただしこれはアドホックであり、
可能な限り避ける** — 艦は点ではないので自己影を表せず、シャドウマップ基盤の外側に
別経路を作ることになる。**採るなら、その旨をコードのコメントに明記すること。**

## 2. 現況の事実

### 2-1. 光源と陰影の二重世界

- シーンライトは **2 つだけ**: `AmbientLight(0x8899bb, 0.25)`(`environment-scene.ts:88`、
  色も強度も直書き)と `DirectionalLight(0xfff4e0, C.SUN_INTENSITY)`(`:90`)。
  受けるのは `MeshStandardMaterial` の層 = 艦船・デブリ・薬莢・基地・小惑星のみ
  (生成 12 箇所、すべて `render/ships.ts`)。
- 天体は全て `MeshBasic(Node)Material` でライト非依存。手書き Lambert + `NIGHT_AMBIENT = 0.04`
  (`celestial-surface.ts:30`)が地球にも他天体にも同じ値で掛かる。
- **「艦が惑星の影に入る」は現状 `DirectionalLight.intensity` のスカラ変調のみ**
  (`environment-scene.ts:159`、`ambient.intensity` も `:160` で同様に変調)。
  **形状に依存する影は一切無い。`castShadow` / `receiveShadow` / `shadowMap` は `src/` に 0 件。**
- 平行光の向きは描画原点から見た恒星方向(`:157-158`、`ephemeris.sunDirFrom`)。
- `AMBIENT_INTENSITY = 0.25`(`const.ts:88`)が定義済みなのに `environment-scene.ts:88` は直書き
  (毎フレーム `:160` が上書きするので実害は無いが、値が 2 箇所にある)。
- **`AmbientLight` は §1-5 の地球照の代用品として働いてしまっている。** 軸 1 の完成で消える。

### 2-2. 天体の座標系の扱いが不統一

地球のみ真位置・実半径(`earth-body.ts:35-36`、実半径は `render/earth.ts:83`)。
他天体は半径 1 の単位球(`celestial-surface.ts:36-45`)を呼び出し側がスケールする方式
(`sphere-body.ts:111` / `point-body.ts:130,166`)で、かつ距離圧縮を受ける
(`sphere-body.ts:91-107` の overview/combat 分岐)。**距離圧縮の不統一は Phase 7 で解消。**
**分割数の選び方は全天体で統一済み** — `render/screen-lod.ts` の `SPHERE_LOD_LADDER`
(見かけ直径で 64×48〜384×288 を選ぶ)へ全 101 天体が乗っており、
`PHYSICAL_DIAMETER_THRESHOLD_PX`(2px)未満は球を描かない判定も同モジュールへ一般化されている。

## 3. ロードマップ

**光と影の実装順は 軸 2 → 軸 1 → 軸 3**(軸 4 は実装済み)。理由:

- **軸 2(影)が最初** — シャドウマップの合成基盤は**パイプラインの構成そのもの**
  (パス数・バッファ・カリング・カスケード選択)と密結合しており、後から差し込めない。
  特に §1-6-7 の半透明遮蔽器は、合成規則を最初から決めておかないと後で全体が変わる。
- **軸 1(反射)が次** — ライティングパスとレンダリングパスが分離されていれば
  **暫定的に点光源で始めて後からブラッシュアップできる**(§1-5-5)。受け手のコードは変わらない。
- **軸 3(地球照の遮蔽)が最後** — 無視してよい。他から依存されない。

| Phase | 内容 |
|---|---|
| 2 | デッドコード除去・計測・描画設定GUI(残: 点群の f32 精度、直書きの重複、画像回帰) |
| 3 | HDR 線形パイプラインと露出基準 |
| 4 | ライトプリパス基盤の導入(**点光源のみ**) |
| 5 | **軸 2a: シャドウマップ合成基盤 + 近傍カスケード** |
| 6 | 深度カスケードのスパイクと判断 |
| 7 | 距離圧縮の撤去 |
| 8 | **軸 2b: 天体・リングを遮蔽器として同じ基盤へ** |
| 9 | **軸 1: エリアライト(球光源・ランバート球)** |
| 10 | 半透明パスの統合 |
| 11 | 大気散乱 |
| 12 | ポストエフェクト |
| 13 | ボリュームレンダリング |
| 14 | **軸 3: 地球照の遮蔽(任意)** |

各フェーズは独立に比較可能であること。**一度に全面置換しない。**

### Phase 2 — 残り: 点群の f32 精度と、直書きの重複

three.js は r0.185.1 へ更新済みで、`@types/three` が `three/webgpu` / `three/tsl` を完全に型付けする
ようになったため自前の型シムは無い。ノード型の語彙は `render/tsl-types.ts`。

Phase 2-a(パス単位の GPU 計測)と Phase 2-b(描画設定GUI)は完了。残っているのは次の2件:

0. **`point-field-view.ts` の f32 精度を実測する**(§1-2)。曲線側は `Curve` の pivot 補正で
   解決済みなので、残るのは `point-field-view.ts` の `instanceMatrix` だけ。
   カイパー帯へ寄って量子化(~5e5 m)が見えるかを確かめ、**見えたときだけ** `Curve` と同じ
   pivot 補正を入れる。
1. `AMBIENT_INTENSITY` の直書き重複を直す(`environment-scene.ts` が `const.ts` の定数を使わず
   `0.25` を直書きしている)。
2. 画像回帰シーンを撮る。**役割は「一致判定」ではなく「変化の可読化」**(§1-1)。

#### 後続フェーズが引き継ぐ道具

- **計測の器**: `gpu-timings.ts` の `GpuTimings` が描画パス別の GPU 時間 [ms] を持つ
  (`GPU_PASS` の数値インデックス + フラット `Float64Array`、`enabled` は `PerfMeter` だけが書く)。
  値は非同期に届くので、`resolve()` は窓の開閉に依らず毎フレーム呼ぶ(呼ばないと時刻印クエリが
  溜まって上限に当たる)。**Phase 4 で 3 パス、Phase 5 でシャドウパスを足すときは、`GPU_PASS` へ
  値を1つ足して同じ器へ載せる** — 表示側(`PerfMeter` の 描画 グループ)は無変更で1行増える。
  `trackTimestamp` はレンダラ生成時オプションなので常時オン。閉窓時のフレーム間隔を実測した結果、
  その費用は run-to-run のばらつきに埋もれた(ON 11.8/12.3ms、OFF 12.9/12.0ms の中央値)。
- **描画設定**: `render/graphics-settings.ts` の `GraphicsSettings` が正本
  (localStorage `tepui.settings.graphics`)。**新しい描画要素を足したフェーズは、その要素の
  トグルをここへ足す** — 影(Phase 5)・大気散乱(Phase 11)・ブルーム(Phase 12)・
  ボリューム(Phase 13)。**効かないトグルを置かない**という規則は維持する:
  現在並んでいるのは、オフにすると三角形数が実測で減るものだけ
  (点群 -44,800 / 環 -5,632(土星にフォーカス時)/ オーロラ -7,680 / 大気 -4,936)。
  `lodBias` は見かけ直径へ掛ける形なので、LOD 段と `showsPhysicalSphere` の閾値が同時に動き、
  `screen-lod.ts` は純関数のままでいられる。雲(地表シェーダへ焼き込み済み)は
  単体で切れないので Phase 11 まで項目に出さない。

### Phase 3 — HDR 線形パイプラインと露出基準

§1-1。**すべての後続フェーズの前提。**

1. HDR レンダーターゲット(`rgba16float`)へ描き、出力段で `toneMapping` を経て sRGB へ。
2. 露出基準を実装。`SOLAR_PRESSURE_1AU` を `SOLAR_CONSTANT / c` から導出する形へ統一。
3. **101 天体のアルベドを入れる。** 16 進直書き色(63 種)を幾何アルベド + 色度へ置き換える。
   **本フェーズ最大の実作業。** 出典をコメントに残す(`RingOpticsDef` の帯コメントが手本)。
   **§1-5 により、この値は Phase 9 で「他の物体を照らす光源の強さ」としてそのまま使われる。**
4. `Billboard` をノードマテリアル化。太陽・惑星輝点は等級 → 放射照度へ。
5. `RADIANCE_SCALE = 0.72`(`ring.ts:27`)を 1.0 にする。
6. 砲身赤熱を機体温度 + `STEFAN_BOLTZMANN` + `HULL_EMISS` の黒体放射へ。
7. 手調整値(`NIGHT_AMBIENT`、`SUN_INTENSITY`、各 opacity、`ZOOM_MUZZLE_FLASH_SCALE`)は**捨てる。**

**完了条件**: `RADIANCE_SCALE` が消える。LDR クリップ回避のための係数が不要になる。
露出を 1 段変えると全体が一様に明るく/暗くなる。

### Phase 4 — ライトプリパス基盤の導入(点光源のみ)

§1-4。**このフェーズの目的は絵を変えることではなく、器を作ることである。**

```text
Phase A  render/gbuffer.ts        深度 + 法線(oct符号化, rg16float) + 粗さ(r8unorm)
Phase B  render/light-prepass.ts  拡散照度 (rgb16float) + 鏡面照度 (rgba16float)
Phase C  render/material-pass.ts  ジオメトリ再描画。照度を読み、アルベド/金属性を掛ける
```

1. 上記 3 パスを組み、**光源は現状と同じ単一平行光 1 個だけを通す。**
   `AmbientLight` も現状の定数のまま残す(Phase 9 で地球照に置き換わる)。
2. **絵が Phase 3 の時点と一致することを完了判定にする。** 器の正しさは「何も変わらない」ことで確かめる。
3. 艦船の `MeshStandardMaterial` と天体の自前 Lambert が **Phase C で 1 つの BRDF に統合される。**
   `NIGHT_AMBIENT = 0.04` の天体別複製が消える。
4. 遮蔽の問い合わせ口 `sunVisibility(worldPos, normal)`(§1-6-5)を Phase B に置く。
   **中身は当面 `environment-scene.ts:159-160` の現行スカラ変調を移設しただけでよい。**
   Phase 5 / Phase 8 でこの関数の中身だけが差し替わる。
5. **光源インターフェースを「球光源」の形で定義しておく。** 実装は点光源(角半径 0)でよいが、
   **型として角半径と位相を持たせておく**ことで、Phase 9 の差し替えが Phase B 内に閉じる。
6. `earth.ts` の地表シェーダを分解: BRDF 部分は Phase A/C へ、もや(`:67-71`)・夕焼け(`:55-58`)は
   Phase 11 の大気パスへ移すため**一旦そのまま残す**。
7. **鏡面の近似の限界を実測する**(§1-4)。破綻するなら艦船だけ前方描画へ逃がす経路を用意する。

**完了条件**: 3 パス構成で Phase 3 と同じ絵が出る。光源を 1 個増やすのに
レンダリングパスのシェーダを触らなくてよい。天体を 1 つ追加してもシェーダコードが増えない。

### Phase 5 — 軸 2a: シャドウマップ合成基盤 + 近傍カスケード

§1-6。**軸 2 の器。パイプライン構成と密結合なので、光源の高度化(Phase 9)より先に置く。**
このフェーズでは**遮蔽器を艦・デブリ・基地に限る**(天体とリングは Phase 8)。
天体を遮蔽器にするには真位置が要る(§1-6-8)ので、距離圧縮の撤去を待つ。

1. **`render/shadow-set.ts` を新設** — §1-6-5 の合成基盤。
   複数マップの保持、**遮蔽器のマップへの排他割り当て**(二重計上の防止、§1-6-3)、
   受け手側の積による合成、**画面上のスケールによるマップ選択**(§1-6-1/§1-6-4)。
2. **カスケード選択のポリシーを 1 モジュールに置く。** §1-3 の深度カスケードと同じ原則
   (画面上のスケールで解像度を決める)なので、Phase 6 の `view-space.ts` と置き場所を揃える。
3. **クラスタごとの平行投影**(§1-6-4)。太陽から見たクラスタの角度幅が極小なので平行投影で足り、
   広画角の透視投影は要らない。**画面上で 1 px 未満のクラスタはマップを組まない。**
4. **PCSS による半影**(§1-6-6)。フィルタ半径は太陽の角半径 4.65 mrad から導く。**チューニング値にしない。**
5. **半透明遮蔽器のためのマップ種別を最初から入れる**(§1-6-7)。
   このフェーズでは不透明マップしか使わないが、**合成規則(深度の積ではなく透過率の積)を先に決める。**
   後から足すと合成規則が変わってしまう。
6. Phase 4 で置いた `sunVisibility` の中身を、この基盤へ差し替える。**呼び出し側は無変更。**
7. `castShadow` / `receiveShadow` は現状 0 件なので新規。**インスタンシングが効く**
   (シャドウマップへも同じジオメトリを描くため)。

**完了条件**: 艦が自分の構造で影を落とし、その影の縁が距離に応じてぼける。
艦をカメラから遠ざけるとシャドウマップの解像度が下がるが、画面上では劣化が見えない。
太陽系全体を見ている視点で、シャドウマップが 1 枚も組まれない(全クラスタが 1 px 未満)。

## 4. 責務境界の規則(全フェーズ横断)

> **`game/` は「なにがあるか」を知り、「どう見えるか」を知らない。**
> **`render/` は「どう見えるか」を知り、「どこにあるか(ECI)」を知らない。**
> **ライティングパスは「光源の形」と「遮蔽」を知り、「材質」を知らない。**
> **レンダリングパスは「材質」を知り、「光源の形」も「遮蔽」も知らない。**

4 行目までが揃うと、軸 1(光源の形)と軸 2(遮蔽)が互いに独立に差し替えられる。
**これがこの構成の目的である。** Phase をまたいで少しずつ寄せる。一括改修はしない。

## 6. 次の一歩

**次に着手するのは Phase 3(HDR 線形パイプラインと露出基準)。** Phase 2 の残り3件
(点群の f32 精度の実測、`AMBIENT_INTENSITY` の直書き重複、画像回帰シーン)は独立に片付けられる。

**並行して始められるもの**:

- **Phase 3 のアルベド調査** — 他フェーズと独立。**Phase 9(軸 1)の光源強度の前提でもあるので、
  早く始めるほど効く。**

### 描画の現状の負荷(Phase 4/5 の余裕の根拠)

戦闘ビューで draw calls 約 165 / triangles 約 33 万(弾 347・薬莢 96・デブリ 24 が出ている状態)。
マップビューで draw calls 約 198。

連射中(弾 150 体以上)の実測:

| 条件 | fps | render (avg) | update (avg) | draw calls |
|---|---|---|---|---|
| インスタンシングあり | 45 | 1.2ms | 19.4ms | 164 |
| インスタンシングなし(個別メッシュ) | 46 | 1.8ms | 17.9ms | 388 |
| 毎フレーム メッシュ再確保 | 27 | 8.7ms | 25.2ms | 434 |

**インスタンシングは draw calls を 388→164 へ半減させるが、fps はほとんど変わらない(46→45)。**
理由は描画フェーズが 1〜2ms しかかからず、**ボトルネックが update フェーズ**(約 18〜19ms、この
グラフィック基盤ロードマップの外側の課題)にあるため。一方で毎フレームのメッシュ再確保は明確に
悪い(render 8.7ms、fps 27)。

→ **インスタンシングの価値は現時点の fps ではなく、ジオメトリを 2 回描く Phase 4 と
シャドウマップの枚数だけ描く Phase 5 に向けた余裕である。**
また、**この「render が 1〜2ms」という数字は CPU 側の壁時計時間であって GPU の実行時間ではない**
ので、パスを増やしたあとの判断には使えない。Phase 2 の GPU 計測が要る理由がここにある。

### `InstancedMesh.count` を毎フレーム書き換えてはならない

three の `InstanceNode` は instanceMatrix の受け渡し経路(uniform buffer か instanced attribute か)を
`count` から決め、その判断とバッファ長を最初の描画時に一度だけ確定する。弾が 0 体のフレームで
`count = 0` になると長さ 1 に固定され、以後何体積んでも描画されなくなる。
そのため `InstancedPool.count` は容量に固定し、未使用の枠をゼロ行列で潰す方式にしている。
**シャドウマップへ同じジオメトリをインスタンシングで描く Phase 5 でも同じ制約が効く。**
