## 0. 光と影を分ける 4 つの軸

「光源の大きさをどう積分するか」と「影をどう作るか」は独立した問題であり、
1 つの話として設計してはならない。この文書は光と影を次の 4 軸へ分け、
**軸ごとに独立して差し替えられる形**を目指す。

| 軸 | 問い | 方針 |
|---|---|---|
| **軸 1** | **反射** — 光源の大きさを、受け手はどう積分するか | **§1-5**。太陽=球光源、天体=ランバート球。遠方で点光源へ**滑らかに縮退する単一の仕組み** |
| **軸 2** | **太陽光の遮蔽** — 影をどう作るか | **§1-6。実装済み。** 天体の球と環は解析、メッシュは適応シャドウマップの複合 |
| **軸 3** | **地球照の遮蔽** | **§1-7。無視するか AO 近似。** 全天体からシャドウマップを撮るのは原理的に不可能 |
| **軸 4** | **CPU 側の日照率** — 熱・電力・SRP | **§1-8。描画とは別の問い。実装済み。** 描画へ流用するのはアドホックなので避ける |

**軸の実装順**: **軸 2 → 軸 1 → 軸 3**(軸 4 は実装済み)。ただし軸に入る前に、
器(パイプライン)・座標(距離圧縮)・量(アルベドと露出)を先に片付ける。理由は §3 冒頭。

## 1. 確定した判断

### 1-1. 露出 — 放射照度を基準に取り、既存の手調整値は捨てる

**方針(確定)**: HDR 線形空間へ移した上で、物理的根拠のある式へ組み替える。視覚的な問題が出たら
**HDR 空間の上で**再調整する。LDR 時代の手調整値へ戻す方向の調整はしない。

```text
E(d) = SOLAR_CONSTANT * (AU / d)^2      [W/m^2]    — 距離 d における放射照度
L_surface = E(d) * albedo / pi          [W/m^2/sr] — 完全拡散反射面の放射輝度
exposure  = 1 / L_ref                              — L_ref を中間グレーへ写す係数
```

必要な量は**すべて既にある**: `SOLAR_CONSTANT = 1361`(`physics/srp.ts`)、
`AU`(`physics/planet-orbit.ts`)、逆二乗則(`physics/srp.ts`、
`physics/thermal.ts` の `solarHeating` も同じ形で使う)、`STEFAN_BOLTZMANN`
(`physics/thermal.ts:12`)、`HULL_EMISS` と温度の各しきい値(`game/const.ts:81-84`)。

**唯一の欠落はアルベドである。** 天体表面は 101 天体ぶんの 16 進直書き色(86 リテラル、ユニーク 63 種、
`celestial-registry.ts:103-196`)しか持たず、アルベド値は 1 つも無い。根拠コメントも無い。

#### 1-1-1. アルベドと放射照度を分離する — 輝度は持たず、毎フレーム引く

**この分離を崩すと軸 1 が成立しない。**

天体が持つのは **RGB のアルベド値**(反射率)だけであり、**輝度は持たない。**
輝度は、アルベドと**その天体が「いまいる場所」で受けている放射照度**から毎フレーム引く:

```text
L(p) = E_sun(その天体の太陽からの距離) * albedo * max(0, dot(n_p, sun_dir)) / pi
```

**この分離は直接の描画色と二次反射光源の両方に効く** — 同じアルベド値が、その天体の表面を
描くときの色にも、その天体が他の物体を照らす光源の強さにも使われる。
したがって **軸 1(§1-5)でアルベドが光源強度として使われるときも、アルベドがそのまま
光源の強さになるのではない。** アルベドは、その天体が受けている放射照度に掛かる係数である。
同じアルベドでも太陽から遠い天体は暗い光源にしかならず、その距離依存が式の中に入っていなければ、
海王星が地球と同じ明るさで艦を照らすことになる。

**直書き色をそのままアルベドとして読み替える移行は誤りである** — 現状の色は
「地球の位置で太陽に照らされた状態の見え方」に近い値へ手で寄せられており、
放射照度の項をすでに畳み込んでしまっているため、太陽光の距離減衰を実装した時に二重に掛かる。

#### 1-1-2. 校正はリングを基準に取る

**既にこの基準で書かれている部分がある。** リングだけが完全な放射伝達モデルになっている —
`RingOpticsDef` の単一散乱アルベド・法線光学的厚さ・HG 非対称因子が全 36 帯に出典コメント付きで入り、
その単一散乱の式(`render/ring.ts` の `physicalMaterial` が組む TSL グラフ)は明示された単位を持つ。
**Phase 5 で決着済み。** 手調整の露出係数は撤廃し、**代わりに描画内部の放射照度の単位を
「1 天文単位で π」に取った**(単位 = `SOLAR_CONSTANT/π = 433.2 W/m²`)。ランバート BRDF の
1/π がこれを打ち消すので、**太陽へ正対したアルベド A の完全拡散面は 1 天文単位で表示値 A に
なる。** 出力段はトーンマッピング(Khronos PBR Neutral)だけを通り、露出には 1 を渡す。
正本は `render/pipeline/sun-light.ts` の `SUN_IRRADIANCE_1AU`。
較正は `render-lab` の `albedo` ケース(アルベド 1 の白球を 1 天文単位へ置いたもの)で読める。

**`Billboard` の明るさは `opacity` ではなく `color` に載せた**(ノードマテリアル化はしていない)。
`THREE.Color` の各成分は素の float で three は上限をクランプしないので、太陽面の表示値
4.62e4 もそのまま入る。不透明度と明るさを別の量として保つのが目的で、Phase 9 で半透明パスを
通常アルファ合成へ統合しても無言で壊れない。

### 1-2. 座標境界 — GPU に ECI 絶対座標を載せない

**不変条件(維持する)**: 描画はすべてフローティングオリジン座標系(`THREE.Vector3`)で行い、
GPU に ECI 座標(独自 `Vec3`)が渡らないこと。具体的には
**`src/render/**` から `Vec3` / `KinematicState` / `ReferenceFrame` / `Attractor` /
`Ephemeris` / `OrbitalElements` / `FloatingOrigin` への import が 0 件**であること。
以降のどのフェーズでもこれを崩さない。**新しいパス(G バッファ・照度バッファ・シャドウマップ)を
足すときも、シェーダへ渡す位置はすべて描画座標系である。**

**曲線については解決済み。** `render/curve.ts` は頂点を `Float64Array`(`bakedLocal`)で保持し、
カメラ近傍の pivot を引いた差分だけを f32 バッファへ書く。
`OrbitLine` / `TrajectoryLine` は `Curve` 経由なので、海王星軌道のような大きな絶対値でも
f32 量子化は起きない。

**唯一の例外**: `game/celestial/point-field-view.ts` の `instanceMatrix` は太陽中心の生座標
(カイパー帯で ~7.5e12 m)を pivot 補正なしに f32 へ書いている(量子化 ~5e5 m)。
**補正は要らない、と結論した。** 誤差は親の `mesh.position`(太陽 − カメラ)と `instanceMatrix`
のどちらも「太陽からの距離 × 6e-8」で頭打ちになり、カメラをいくら寄せても絶対値が変わらない。
点は正四面体として半径 1.2e8 m で描かれるので、**刻みが点の見かけの大きさに追いつくことが
起きない** — カイパー帯(7.2e12 m)で描画半径の 0.4%、散乱円盤の遠日点(1.1e14 m)でも 7.0%。
親の誤差だけはカメラの移動で変わるが、群全体に同じ平行移動として乗るので格子にはならない。

### 1-3. 深度は「画素ごとの位置を復元する器」である

**深度バッファに求めるのは z-fighting を消すことではない。** 求めるのは
**画素ごとに、その面が描画座標(ECI − 浮動原点)のどこにあるかを正確に復元できること**である。
浮動原点はアクティブカメラの ECI 位置そのものなので、描画座標の原点はカメラであり、
**この座標系は `render/` の中で完結する**(GPU に ECI 絶対座標は渡らない)。

復元ができると**太陽を点光源として扱える** — 画素の復元位置と太陽の位置の**差分ベクトル**から、
その画素における太陽の方向と距離が正確に出る。これが軸 1(§1-5)の入口であり、
**天体ごとの `sunDirection` uniform を不要にし、天体を `LIT_OPAQUE_LAYER` へ載せる前提**でもある。
球エリアライト(Phase 8)は、この点を有限の立体角へ替えるだけになる。

復元は `getViewPosition(screenUV, depth, projectionMatrixInverse)`、すなわち
**screenUV(誤差なし)× 深度から得た距離**なので、横方向 x,y は z に比例する。
**復元位置の相対誤差は深度の相対誤差そのものである。**

**方針(確定・実装済み)**: 単一の深度バッファを **反転 Z + 32bit float** にする。
**深度カスケードは採らなかった** — 復元誤差が距離に依らず一定になるので、段で人為的に分ける
動機がそもそも消える。実測でも 1e4〜1e11 m の 4 ケースが画素単位で一致した。
**表現・精度・near/far・深度を持つターゲットの現況は §2-7。**

原理: 非反転は `z_ndc = 1 − near/z` の形で **1 から微小量を引く**ため浮動小数の桁が落ちる。
反転すると `z_ndc ≈ near/z` になり、**float の指数分布が透視分割の 1/z をそのまま吸収する。**
非反転の固定小数点が `Δz = z²·2⁻²⁴/near` と距離の二乗で悪化するのに対し、反転 + float32 は
`Δz ≈ z·2⁻²⁴`。1 px の world 幅も距離に比例する(`metersPerPixel ≈ 9.6e-4·z`)ので、

> **位置復元の相対誤差は距離によらず 6.0e-8。画面上に直すと、どの距離でも約 6e-5 px 相当。**

**正射影だけは性質が違う。** 深度が線形なので反転しても分布は変わらず、float32 が効くのは
値が 0 に近い far 側だけ。「反転したのにマップビューが改善しない」は不具合ではない。

**逆変換 `toEci` は作らない。** 必要なのは描画座標であって ECI ではなく、その逆変換は GPU 側の
`getViewPosition` がやる(`CODING-RULE.md` 1.5)。画面 → 世界の逆投影は
`physics/projection.ts` が別に持つ。

### 1-4. ライトプリパス(3 パス構成)

**方針(確定)**: 2 パス遅延シェーディングをやめ、**3 パスのライトプリパス**を採る。

```text
Phase A  ジオメトリパス   → 深度 + 法線 + 粗さ            (幾何だけ。マテリアルの色を持たない)
Phase B  ライティングパス → 拡散照度バッファ + 鏡面照度バッファ
                            光源の形の積分・遮蔽問い合わせはここに閉じる
Phase C  レンダリングパス → 再度ジオメトリを描き、照度バッファを読み、材質を掛ける
Phase D  半透明 + ポストプロセス
```

**なぜ 2 パスでは足りないか**: 遅延シェーディングでは「光源の立体角積分」と「BRDF 評価」が
同じシェーダに同居する。§1-5 で光源の種類(球・ランバート球・点への縮退)を増やす以上、
マテリアル分岐との掛け算で膨らむ。ライトプリパスは**照度という中間表現で両者を切る**:

- **ライティングパスは「その点にどの向きからどれだけ光が来ているか」だけを答える。**
- **レンダリングパスは「来た光をこの材質がどう返すか」だけを答える。**

**トレードオフ**: ジオメトリを 2 回描く(ドローコール増)代わりに G-buffer が狭くなり、
マテリアルの多様性と光源の多様性が独立に増やせる。

**既知の限界**: 鏡面反射は「入射方向 × 視線 × 材質」に依存するので照度バッファ 1 枚に畳めない。
標準的な対処は**粗さをジオメトリパスに書き、その粗さで積分した鏡面項を別バッファに出す**こと。
拡散反射が支配的な天体表面 + 少数の金属的な艦船という本作の絵では破綻は小さいと見込むが、
**破綻したら艦船だけを前方描画へ逃がす**(ドローコールは既に 2 回なので構成は壊れない)。

**器は `src/render/pipeline/` に組み上がっている。** フレームは
G バッファ → ライティング → マテリアル → ワールド → 合成 の 5 パスで、それぞれが
負荷確認ウィンドウに独立した GPU 時間の行を持つ。光源はまだ単一の平行光 1 個。

**受け手側は既に照度バッファ経由になっている。** `MaterialPass` が
`PhysicalLightingModel` を継承し、`direct()` を空に、`indirect()` を照度バッファの読み出しへ
差し替える。BRDF・マップ・粗さ/金属度の扱いは three 標準の `MeshStandardNodeMaterial` のままなので、
**光源を増やす作業はライティングパスの中に閉じる。**

**three 側の制約(§1-5 の実装で効く)**: `NodeMaterial.setupLighting` は
`light.layers.test(camera.layers)` を通る光源が 1 つ以上あるときにしか
`setupLightingModel()` を呼ばない。マテリアルパスはカメラの層を `LIT_OPAQUE_LAYER` へ
絞るので、**シーンの光源をその層にも属させておかないとライティングモデルごと呼ばれず、
受け手が真っ黒になる。** 光源をシーンから完全に外すことはできない。

### 1-5. 軸 1 — 反射(光源の大きさをどう積分するか)

**方針(確定)**: 光源が十分近く大きいときは面光源、十分遠く立体角が小さいときは点光源。
**これを分岐ではなく、単一の式が滑らかに縮退する形で実現する。**
太陽にも地球にも月にもその他の天体にも、同じ仕組みが適用される。

**なぜ必要か(立体角)**:

| 光源 | 視点 | 視半径 | 立体角 | 全天比 |
|---|---|---|---|---|
| 太陽 | 1 AU | 0.266° | 6.8e-5 sr | 5.4e-6 |
| 太陽 | 水星近日点 0.31 AU | 0.86° | 7.1e-4 sr | 5.6e-5 |
| 地球 | LEO 420 km | **70.0°** | **3.90 sr** | **31%** |
| 地球 | 静止軌道 | 8.6° | 0.071 sr | 0.56% |
| 地球 | 月軌道 | 0.95° | 8.6e-4 sr | 0.007% |
| 木星 | エウロパ軌道 | 11.5° | 0.126 sr | 1.0% |

**太陽ですら完全な点ではなく、地球は LEO で全天の 31% を占める。**
そして**同じ地球が月軌道では点光源と区別がつかない。** 近距離用と遠距離用に別モデルを持つのではなく、
**距離とともに連続に縮退する 1 つのモデル**でなければ、遷移する場所で絵が飛ぶ。

#### 1-5-1. 太陽(恒星) — 一様球光源

最も単純な形。球全体が一様な放射輝度を持つ。**一様球光源からの拡散照度には閉じた解があり、
その式は距離が大きくなると自動的に逆二乗則へ縮退する。** したがって
**「遠いときは点光源に切り替える」という分岐は書かない** — 同じ式が両方を覆う。

分岐が要るのは鏡面項だけ。LTC(Linearly Transformed Cosines)による球光源の積分は
角半径が小さいと数値的に無駄なので、閾値で点光源近似へ落としてよい
(拡散項と違い、鏡面のハイライトは光源が小さければ本当に点と区別がつかない)。

#### 1-5-2. 惑星・衛星 — ランバート球(部位によって照度が違う球)

**太陽と決定的に違うのは、球面の一部しか光っていないこと。** 昼側だけが光り、
艦から見ると三日月形になる。一様球光源では表せない。

**近似(確定)**: **ランバート球**として扱う。球面上の各点の放射輝度が §1-1-1 の式で与えられる球。
**これは光源の側の近似である** — 受け手の側の反射モデルは別の問い(Phase 8 の「受け手の側の宿題」)。
**入力は 2 つ — その天体のアルベド(色度込み)と、その天体が太陽から受けている放射照度**であり、
**アルベド単独では光源の強さは決まらない。** 太陽からの距離が式に入っていることが要件。

- **一様球ではないので LTC の標準的な適用範囲外である。** これは承知の上で採る近似であり、
  検証ケース(三日月形に見える位置での地球照)で妥当性を確かめる必要がある。
- 実装の候補は 2 つある。(a) 照らされている半球を**等価な円盤へ代表させ**、その円盤に LTC を適用する
  (位相角に応じて円盤の面積と位置をずらす)。(b) 球光源の閉じた解に**位相係数**を掛ける
  (正しくない — 明るさは合うが、光が来る「向き」の偏りが表現されない)。
  **(a) を採る。** 光が来る向きの偏りこそが軌道上の絵の特徴だから。
- **色を持つ光源になる。** 地球は海の青・雲の白・陸の褐色を持つので、艦の影側が青みを帯びる。
  初版は全球平均色でよく、局所分布(雲がある側が明るい)は将来の改良。

#### 1-5-3. 光源の打ち切り

**打ち切りの基準は距離ではなく立体角。** 立体角が閾値を下回った光源は
点光源として扱う(縮退は式が自動でやるので、実際には「LTC を使うか点光源で済ますか」の判断だけ)。
さらに小さければ照度そのものが無視できるので光源リストから外す。
**太陽系全域で、光源リストは実用上「太陽 + 最も近い 1〜2 天体」に収まる。**

#### 1-5-4. 現状との差

今は `render/pipeline/sun-light.ts` の `AMBIENT_IRRADIANCE` という**方向も距離も位相も
持たない定数**が、地球照・星明かり・多重散乱の全部を兼ねている。軸 1 の完成はこの定数を
消す作業でもある。

**この定数は低軌道での地球照の明るさに合わせただけの手書きの値で、位置によらず一定に
足される。** 太陽へ正対した面の直射と比べると、地球(1 AU)で 9%、土星(9.6 AU)で 8.5 倍、
海王星(30 AU)で 84 倍。**外惑星の天体・艦は本来の数十倍明るく写っており、「太陽から遠い
天体ほど暗い」が成り立っていない。** 直す価値があるのは地球照そのものを持つ軸 1 の中だけ
なので、それまでは触らない。

#### 1-5-5. なぜ軸 1 を後回しにできるか

**ライティングパス(Phase B)とレンダリングパス(Phase C)が分離されていれば、
軸 1 の変更は Phase B の中に閉じる。** 最初は太陽も天体も点光源として実装しておき、
後から球光源・ランバート球へ差し替えられる。**受け手側のコードは一行も変わらない。**
これが軸 2 より優先度を下げられる理由である。

**「点光源として実装しておく」の部分は入っている。** 深度から画素ごとの描画座標が復元できる
ので、太陽の位置との差分ベクトルから方向と距離が引ける(§1-3)。
**Phase 8 に残るのは、その点を有限の立体角へ広げる部分だけ**である。

### 1-6. 軸 2 — 太陽光の遮蔽

**方針(確定)**: 太陽光の遮蔽は無視できず、**ソフトシャドウ的な照度変化の再現が要る。**
太陽の立体角が小さくても、**半影のスケールは遮蔽器までの距離に比例して大きくなる**ので無視できない。
そして以下はすべて**同じ現象**である:

- 地球の影に出入りする艦の照度変化
- 艦のセルフシャドウ・艦どうしの相互影
- 月食 / 日食の境界
- 土星のリング影の境界

#### 1-6-1. 確定していること

- **受け手の入口は 1 本。** 描画座標の点に対する透過率を返す TSL の関数で、天体表面・艦の
  BRDF・環・大気がすべて同じものを読む。**置き場をライティングパスの中にしてはならない** —
  環(`render/ring.ts`)は半透明なので恒久的に前方描画側であり、この共有は過渡的ではない。
- **合成は透過率の積(= 光学的厚さの和)。** 不透明も τ→∞ の極限として同じ式に乗るので、
  不透明・半透明で規則を分けない。**この規約は受け手の呼び出し形を決めてしまうので、
  後から差し替えられない。**
- **必要な解像度には物理的な上限がある。** 影は太陽円盤で畳み込まれているので、
  半影幅(遮蔽器までの距離 d に対して 2αd)より細かい構造は存在しない。
  **「巨大な遮蔽器には巨大なシャドウマップが要る」は成り立たない。**
- **遮蔽器を捨ててよい物理的な基準がある。** 最大遮蔽率 `min(1, (β/α)²)` が閾値を下回る遮蔽器は、
  どう表現しても画面に出ない。チューニング値ではない。
- **`SHADOW_MIN_SUN = 0.04` の床は残す。** 点近似の埋め合わせではあるが、地球照(軸 3)が
  入るまでは影の中が真っ暗になる。**捨てるのは Phase 8。**

---

### 1-7. 軸 3 — 地球照の遮蔽(優先度低)

**方針(確定)**: 太陽光と比べて照度のオーダーが小さいので、**無視するか、AO として近似する。**

**軸 2 と同じ方法は原理的に採れない。** シャドウマップは光源ごとに要る。天体は 101 個あり、
そのすべてから撮ることはできない。§1-5 で光源リストが「太陽 + 最も近い 1〜2 天体」に
収まるとしても、面光源(ランバート球)に対する影は点光源に対する影よりさらに高価である。

**採る手段**:

1. **無視する。** 初版はこれでよい。地球照は太陽光の 1e-2 〜 1e-3 のオーダーであり、
   その中の遮蔽の差はさらに小さい。
2. **AO として近似する。** 幾何的な遮蔽度(周囲がどれだけ開けているか)を
   地球照に掛ける。方向を持たない近似だが、艦の凹部が暗くなるという主要な効果は出る。

**優先度は最も低い。** 他のどの軸にも依存されない。

### 1-8. 軸 4 — CPU 側の日照率(熱・電力・SRP)

**CPU 側の日照率と GPU 側の遮蔽は別物であり、二重実装ではない。**
問いが違う — 前者は**ある 1 点の日照率**(艦を点と見なしてよい)、後者は**画素ごとの遮蔽度**
(艦は点ではなく、自己影を持つ)。したがって軸 2 が完成しても `physics/shadow.ts` は残る。

`physics/shadow.ts` の `sunlitFactor(r, star, attractors)` は実装済みで、
熱(全個体 — `game/game-entity/game-entity.ts` が区間ごとに 1 回引く)・電力
(`game/player/power.ts`)と SRP(`physics/dynamics.ts`)が消費者。
**このフェーズで新たにやることは無い。**

**残っている 1 本の配線だけが軸 2 の作業対象**: 描画照明が `environment-scene.ts` 経由で
この関数を読み、`SunLight.sunVisibility()` のスカラとしてライティングパスへ渡っている
**この配線は既に切れている。** 天体を同じライティングパスの受け手にした時点で、
**一様スカラは艦と天体を区別できず、艦が地球の影に入った瞬間に地球まで暗くなる**ため、
画素ごとの遮蔽(`render/pipeline/occlusion.ts`)へ置き換えるほか無かった。

`physics/shadow.ts` 自体は熱・電力・SRP の消費者のために残る。**同じ式が CPU(全件走査)と
GPU(TSL)に並ぶが、`physics/` は THREE に依存できず TSL は TS 関数を呼べないので共有は
物理的に不可能。** 全件走査は、GPU 側が遮蔽器を打ち切ることの誤差を測るオラクルになる。

## 2. 現況の事実

### 2-1. 光と受け手

- **光の値の正本は `render/pipeline/sun-light.ts` の `SunLight` 1 つ。** 恒星の描画座標での
  位置・半径・色・放射強度と、環境光の色・強度を持ち、`environment-scene.ts` が毎フレーム
  書き込む。ライティングパス・遮蔽パス・大気パスがそれを読む。
- **シーンには値を持たない光源が 1 個だけ残っている。** three はカメラのチャンネルと重なる
  光源が 0 個だとライティングモデルごと組まないので(§1-4)、受け手を真っ黒にしないための
  置物である。色も強度もどこからも読まれない。**無言で壊れる経路なので、描画テスト環境(§2-6)の
  必須ケースに含める。**
- **受け手は `LIT_OPAQUE_LAYER` に立つ標準マテリアルのすべて** — 艦船・デブリ・薬莢・基地・
  小惑星に加えて、**天体の球と地球の地表も含む。** 自前 Lambert も `NIGHT_AMBIENT` も
  `sunDirection` uniform ももう無く、**天体と艦艇は同じ 1 つの光源・同じ BRDF で描かれる。**
  印を付けるのは `lit-layer.ts` の `markLitOpaque` 1 箇所で、判定はマテリアルが標準かどうか。
- **背景専用の第3のチャンネル `WORLD_BACKGROUND_LAYER = 2`** に星殻だけが乗り、
  マテリアルパスが不透明物より先に描く(§3 のパイプライン節)。
- **影は画素ごと。** 遮蔽パス(`occlusion.ts`)が G バッファ深度から復元した位置で天体の
  本影・半影と環の帯を解き、透過率 1 枚にして返す。**`castShadow` / `receiveShadow` /
  `shadowMap` は `src/` に 0 件のまま** — 形状に依存する影(自己影)はまだ無い。
- **`SunLight` の環境項は §1-5 の地球照の代用品として働いてしまっている。** 軸 1 の完成で消える。
  影の中に残す `SHADOW_MIN_SUN`(4%)も同じ性格の暫定値で、捨てるのは地球照が入る Phase 8。

### 2-2. 天体の座標系(統一済み)

**どの天体もどのビューでも実 ECI 位置・実半径で描く。** 描画位置はすべて
`FloatingOrigin.RtoThreeV3` を通り、`game/celestial/` に表示距離の定数もカメラ位置からの
直接配置も無い。かつての距離圧縮と、圧縮したまま深度だけを真の距離へ引き戻していた補正
(`setDepthScale` と自前の `depthNode`)は撤去済みで、**遮蔽パスへ渡る中心も半径も真の値。**
地球だけは実半径のジオメトリ、他天体は半径 1 の単位球を表示側がスケールする。
**分割数の選び方は月を除く全天体で統一済み** — `render/screen-lod.ts` の `SPHERE_LOD_LADDER`
(見かけ直径で 64×48〜384×288 を選ぶ)へ 100 天体が乗っており、`PHYSICAL_DIAMETER_THRESHOLD_PX`
(2px)未満は球を描かない判定も同モジュールへ一般化されている。**月だけがラダーに乗らず 64×32 に
固定されている** — テクスチャの経度原点を合わせるためにジオメトリを回すので、段ごとの共有
ジオメトリを使えない(回すと他の天体まで一緒に回る)。寄っても分割が上がらない。

### 2-3. 色空間とテクスチャ(点検済み)

three の出力色空間の既定は `SRGBColorSpace` なので、**欠けているのは HDR
レンダーターゲットとトーンマッピングだけ**で、前者は済んでいる。テクスチャ側の `colorSpace` は
点検済みで問題なし — 明示的に `SRGBColorSpace` を設定しているのは
`celestial-surface.ts` / `earth.ts` / `stars.ts` の 3 箇所で、
未設定なのは `8k_clouds.jpg` のみ。これは `.r` をマスクとして使うので線形扱いが正しい。

### 2-6. 既にある器 — 計測と描画設定

- **計測の器**: `gpu-timings.ts` の `GpuTimings` が描画パス別の GPU 時間 [ms] を持つ器を用意している
  (`GPU_PASS` の数値インデックス + フラット `Float64Array`、`enabled` は `PerfMeter` だけが書く)。
  値は非同期に届くので、`resolve()` は窓の開閉に依らず毎フレーム呼ぶ(呼ばないと時刻印クエリが
  溜まって上限に当たる)。`trackTimestamp` はレンダラ生成時オプションなので常時オン。
  閉窓時のフレーム間隔を実測した結果、その費用は run-to-run のばらつきに埋もれた
  (ON 11.8/12.3ms、OFF 12.9/12.0ms の中央値)。

  **パス別の分解は済んでいる。** `GPU_PASS` は 7 値(G バッファ/遮蔽/ライティング/マテリアル/
  大気/ワールド/合成)で、各パスの GPU 時間が独立した行として並ぶ。実現方法は次のとおり:

  `resolveTimestampsAsync` の**戻り値**はフレーム合計だが、**解決の副作用として
  `backend.timestampQueryPool['render'].timestamps`(`Map<uid, ms>`)へコンテキスト別の値が
  書かれている。** uid は `Renderer` が `inspector.beginRender(uid, ...)` へ渡すものなので、
  `InspectorBase`(`three/webgpu` から公開・型付き)を差し替えて描画呼び出しごとに捕まえる。
  パイプラインは `renderer.render()` の直前に `GpuTimings.beginPass(id)` を呼んで
  「次の呼び出しはこのパス」と申告し、Inspector が uid をそのパスへ結び付ける。
  `beginPass` を伴わない three 内部の描画は無視されるだけで、他のパスの枠を奪わない。

  **`pool.timestamps` は three 自身が空にしないので、放置すると uid が毎フレーム際限なく積もる。**
  `GpuTimings.resolve()` が読み取り後に毎回クリアしている。

- **描画設定**: `render/graphics-settings.ts` の `GraphicsSettings` が正本
  (localStorage `tepui.settings.graphics`)。**新しい描画要素を足したフェーズは、その要素の
  トグルをここへ足す** — 影(Phase 7)・大気散乱(Phase 10)・ブルーム(Phase 11)・
  ボリューム(Phase 12)。**効かないトグルを置かない**という規則は維持する:
  現在並んでいるのは、オフにすると実際にその要素が絵から消えるものだけ
  (点群 -44,800 / 環 -5,632(土星にフォーカス時)/ オーロラ -7,680 の三角形。大気だけは
  ジオメトリではなく全画面フィルタ 1 枚ぶん)。
  `lodBias` は見かけ直径へ掛ける形なので、LOD 段と `showsPhysicalSphere` の閾値が同時に動き、
  `screen-lod.ts` は純関数のままでいられる。雲(地表シェーダへ焼き込み済み)は
  単体で切れないので Phase 10 まで項目に出さない。

- **中間ターゲットの目視**: 描画設定の「デバッグ表示」が、合成パスの映す先を最終画から
  中間ターゲットへ差し替える(`render/pipeline/debug-target.ts` が選択肢の正本、
  法線/粗さ/深度/遮蔽/拡散照度/鏡面照度/マテリアル/大気)。**品質設定ではないので `GraphicsSettings` に
  持たせず永続もしない**(`RenderPipeline` のセッション限定の状態)。新しいパスを足したら
  ここへ 1 行足す — 目で見て確かめられないバッファは、間違っていても気付けない。

- **three.js の版**: `0.185.1`(npm 上の最新。`0.186.x` はまだ存在しない)。
  `@types/three`(`0.185.4`)が `three/webgpu` / `three/tsl` を完全に型付けするので自前の型シムは無い。
  ノード型の語彙は `render/tsl-types.ts`。**`package.json` は `^` を外してピン留めしてあり、
  `npm run ci` の `tools/check-three-pin.mjs` が版と振る舞いの両方を見張る**(§2-4)。
  上げるときの手順は `how_to_update_three.md`。

- **絵を確かめる器**: `tools/render-lab/`。ゲーム本体とは別の 1 ページで、**同じ深度構成・
  同じメッシュを「ライトプリパス」と「フォワード描画」の 2 経路で並べて描く。**
  **2 経路の違いは「メッシュとライトがどのチャンネルに居るか」だけ**で、HDR ターゲット・露出・
  合成・色空間変換は同じ `RenderPipeline` を通る。だから画面に出る差はシェーディング経路の差そのもの。

  - **口は 2 つ。** `npm run render-lab` が目視(http://localhost:8082、canvas 2 枚)、
    `npm run render-lab:shot` が撮影(本番ビルドを踏み、`.render-lab/shots/` へ
    `<case>-prepass.png` / `-forward.png` / `-diff.png` の 3 枚ずつ)。**撮影は WebGPU の提示経路も
    ヘッドレスのスクリーンショットも通らない**(`setOutputRenderTarget` +
    `readRenderTargetPixelsAsync` で画素を直接読む)。差分はレンダラーが 2 台 = デバイスも 2 つで
    GPU 上で突き合わせられないため、読み出したあと CPU で引く(`|a − b| × 8`)。
  - **描画は 960×540 固定**、near=2、球は半径 = 距離/10(見かけの大きさをケース間で揃えるため)。
    ケースは `tools/render-lab/cases.ts` の表 — `leo` / `order` / `depth-1e4` / `depth-1e6` /
    `depth-1e8` / `depth-1e11` / `eclipse` / `earth` / `far`。各ケースは `THREE.Object3D` の列と
    カメラを返す純粋な関数で、**増やすのは表への追記だけ。**
  - **この器がやらないこと**: 画素一致の判定(撮った PNG は人とエージェントが見るためのもので、
    期待値として突き合わせる基準ではない)、カメラ操作(ケースは固定)、
    ゲーム状態・HUD・DOM の持ち込み。
  - **画面空間のパス(遮蔽・大気)は G バッファを読むので、フォワード経路には効かない。**
    フォワード側はメッシュをチャンネル 0 へ戻すため G バッファに現れず、影も大気も乗らない。
    **`eclipse` と `earth` の `diff` が大きいのはこのため**で、シェーディング経路の差ではない。
    2 経路の一致で読めるのは `leo` / `order` / `far` / `depth-*`。
  - **画素一致の画像回帰は採らない。** 基準を過去の自分に取ると、いま入っているバグごと固定して
    しまう(重なり順・受け手が真っ黒・本番ビルドだけ陰影が消える、のいずれも過去に実際に起きている)。
    **基準は同じ入力に対する別経路の描画**であり、差分画像がそれをそのまま可視化する。

- **この開発環境での実行時検証には制約がある。** ヘッドレス Chrome が **1〜2fps しか出ない**
  (実測: 起動・HUD・コンソールとも正常なまま、30 秒間の rAF が 40 回)。ビルドや撮影を続けて
  回した直後は 30 秒間 0〜1 回まで落ちる。

  - **`npm run smoke:browser` は「30 秒で 60 フレーム」の判定に届かず落ちる。変更の回帰と
    読み違えない** — 落ちたのが `bootAndCheckReady` の 1 点だけで、ページ側に例外もコンソール
    エラーも出ていないなら、それは環境の速度である。**変更を stash して素の 30 秒間の rAF を
    数え直せば分かる。**
  - **`npm run ci` も最後の smoke で落ちる。** 合否は `typecheck` / `test:physics` / `build` /
    `verify:release` までで見る。
  - **目視の代わりは `npm run render-lab:shot` の PNG。** エージェントはこれを直接読める。
    ブラウザ操作が要る確認(カメラ操作・設定パネルの切り替え)は実機で人が見るしかない。
  - `tools/perf-probe.mjs` は 1 条件あたり数分かかり、高いワープ段の条件は到達しない。
    撮影の所要は本番ビルド 約 4s + 撮影 約 60s。
  - `render/geometry-validator.ts` はメッシュ作図の検査(オープンエッジ・同一平面の重複ポリゴン)
    であって、**深度バッファの精度とは無関係**。混同しない。

### 2-7. 深度バッファの現状

**表現は反転 Z + 32bit 浮動小数点(`depth32float`)** — near が 1、far が 0。
切り替えは `render/scene.ts` の `new WebGPURenderer({ reversedDepthBuffer: true })` 1 箇所で、
投影行列(`Matrix4.makePerspective` の反転分岐)・深度比較関数(`GREATER`)・深度クリア値(0)が
レンダラー単位で一括して効く。**構築時にしか渡せない** — あとから代入すると投影行列と
クリア値だけが反転し、比較関数が非反転のまま取り残される。

- 深度値は `z_ndc = near·(far − z) / ((far − near)·z) ≈ near/z`。float の指数分布が透視分割の
  1/z をそのまま吸収するので、**位置復元の相対誤差は距離に依らず 2⁻²⁴ ≈ 6e-8。**
- 復元は `getViewPosition(screenUV, rawDepth, projectionMatrixInverse)`。WebGPU 系は NDC z が
  [0,1] なので生の深度をそのまま clip z に使う実装で、**反転しても式は変わらない。**
- 逆写像は `render-pipeline.ts` の `viewDistanceFromDepth`(`near·far / (near(1−d) + far·d)`)。
  デバッグ表示だけが使う。
- **深度の疑似圧縮は全廃した。** 自前の `depthNode`・`setDepthScale`・対数深度・深度カスケードは
  `src/` に 0 件。天体は実位置・実半径で、深度もその真の位置のもの。

**⚠ `RenderTarget` の深度は明示しないと 32bit にならない。** three は暗黙の深度テクスチャを
`reversedDepthBuffer` に関係なく `UnsignedIntType`(= `depth24plus`)で作る(`Textures.js:94`)。
自動で `Depth32Float` が選ばれるのはキャンバスへ直接描く経路だけ。**深度を持つターゲットには
`new THREE.DepthTexture(w, h, THREE.FloatType)` を必ず据える。**

**深度を持つターゲットは 2 枚あり、表現は同じ。**

| ターゲット | 役割 | サンプル |
|---|---|---|
| G バッファ(`gbuffer.ts`) | 位置復元の唯一の供給元。遮蔽・大気・ライティングが読む | 1(法線を平均すると境界が壊れるので MSAA 無し) |
| HDR 共有ターゲット(`render-pipeline.ts`) | マテリアルパスが書き、大気パスと world パスが重ね描く。**z-fighting に直結するのはこちら** | `antialias` 時 4 |

同一カメラ・同一ジオメトリを描くので 2 枚が食い違うことはない。ただし**同じ不透明ジオメトリを
2 回描いて深度を 2 回書いている** — ライトプリパス構成そのものの費用。共有ターゲットの深度は
テクスチャとしてサンプルされる先が無い(デバッグの「深度」表示も G バッファ側を読む)ので、
MSAA でも困らない。

**near / far**

| ビュー | near | far |
|---|---|---|
| 戦闘 | **2 m** 固定 | **2e12 m** 固定(球として描かれる天体のうち見かけ 2px を超える最遠のもの = 最大の恒星が入る距離) |
| マップ | `min(CELESTIAL_SHELL_RADIUS·cos θ_diag·0.9, dist/1000)` | `clamp(dist × 100, 1.5e10, 1e16)` |

**反転 float32 では far を広げる費用が事実上ゼロ**なので、戦闘ビューの near/far 比 1e12 でも
復元誤差は距離 × 6e-8 のまま(1e6 m で 6cm、月距離 3.8e8 m で 23m)。
**正射影だけは性質が違う** — 深度が線形なので反転しても分布は変わらず、float32 が効くのは
値が 0 に近い far 側だけで、near プレーン付近では `depth24plus` と同等になる。

## 3. ロードマップ

**順序の根拠**は次のとおり。軸の実装順(軸 2 → 軸 1 → 軸 3)はこの下に入る。

**器(`src/render/pipeline/` の 9 パス構成とパス別 GPU 計測)は組み上がっている**(§1-4)。
順序の根拠は次の 5 点で、0 と 1 は済んでいる。

0. **絵を判定する場が先**(§2-6)。以降のどのフェーズも「変えたら何が変わったか」をそこで見て
   決める。**パスの形もここで確定した** — 以降は各フィルタの中身だけを触る。
1. **座標(距離圧縮の撤去)が次**(§2-2)。遮蔽を物理的に正しく統一する前提で、
   これが済んでいないと遮蔽器の位置が偽のままになる。

2. **量(アルベドと露出)が次** — 影もエリアライトもこの量を消費する。実作業量が最大であり、
   他フェーズと独立に進められるので、先に始めるほど効く。
3. **軸 2(影)** — 遮蔽の合成規約(透過率の積 = 光学的厚さの和、§1-6-2)は
   **受け手の側の呼び出し形を決めてしまう**ので、源を足す前に置く必要がある。
   遮蔽器の真位置が要るので、1 の後になる。
   **規約を置く Phase 6 と、源を実装する Phase 7 は、方式が決まったので 1 度にまとめて実施した。**
4. **軸 1(反射)、続いてその他のリッチ化** — ライティングパスとマテリアルパスが分離済みなので
   **暫定的な点光源から後でブラッシュアップできる**(§1-5-5)。受け手のコードは変わらない。
   軸 3 は無視してよく、他から依存されない。

| Phase | 内容 |
|---|---|
| 5 | 物理量で描くものと表示値で描くものの分離、アルベドの物理量化、露出・トーンマッピングの本実装 — **実装済み** |
| 6 | 軸 2a: 遮蔽の合成基盤と、受け手側の差し替え — **実装済み** |
| 7 | 軸 2b: 遮蔽源の実装 — **実装済み** |
| 8 | **軸 1: エリアライト(球光源・ランバート球)** |
| 9 | 半透明パスの統合 |
| 10 | 大気散乱 |
| 11 | ポストエフェクト |
| 12 | ボリュームレンダリング |
| 13 | **軸 3: 地球照の遮蔽(任意)** |
| 14 | **黒体放射の物理量化(温度を持つ全物体)** |

各フェーズは独立に比較可能であること。**一度に全面置換しない。**

### パイプラインの現況と最終形

**最終形は 4 段構え** — **不透明(ライトプリパス + 遮蔽)+ 半透明 + ポストプロセス + 3D UI。**
分割の目的は**視覚効果を疎結合にして、後から個別に品質を上げられるようにすること**である。
**このうち先頭 3 段の形は Phase 4 で確定した。以降のどのフェーズも、そこの再構成を伴ってはならない。**

**4 段目(3D UI)は Phase 5 で入った。** 軌道線・軌跡線・天球グリッド・縮尺グリッド・
Δv ギズモは 3D 空間に居るが、**物理ベースで描くべきものではない** — アルベドを持たず、
UI テーマの色をそのまま表示値として出す。`render/pipeline/overlay-pass.ts` が合成パスの後ろで
キャンバスへ直接描き、露出もトーンマッピングも浴びない。深度は合成パスが G バッファのものを
キャンバスの深度バッファへ複製するので、線のマテリアルはノード化せずに済んでいる。
アンチエイリアスもキャンバス側のマルチサンプルがそのまま掛かる。

**帰結として、G バッファに居ない不透明物(太陽の球・弾薬ビーコン)と、深度を書かない
透ける物体(環・大気・オーロラ・噴射炎)は 3D UI を遮らない。** 決定として受け入れてある。

§1-4。いまのフレームは `src/render/pipeline/` の 9 パス。**各パスは負荷確認ウィンドウに独立した
GPU 時間の行を持ち、描画設定の「デバッグ表示」で中間ターゲットを全画面に出せる。**

```text
sun-shadow-maps.ts 恒星方向の平行投影で、メッシュの遮蔽器をスロットごとの線形深度マップへ
gbuffer.ts        深度(depth32float, 反転) + 法線(oct符号化, rg16float) + 粗さ(r8unorm) — MRT
occlusion.ts      恒星の直達光の透過率(r16float)。天体の球・環の帯・影の深度マップの積
light-prepass.ts  拡散照度 + 鏡面照度(いずれも rgba16float)          — MRT
material-pass.ts  LIT_OPAQUE_LAYER + 背景チャンネルを再描画。照度を読み、BRDF を掛ける
atmosphere-pass.ts 大気。前乗算アルファで不透明の絵の上へ重ねる
(world)           残りのシーン。半透明ごと前方描画のまま
render-pipeline.ts  出力段。露出を掛けてキャンバスへ
overlay-pass.ts   3D UI。合成の後ろでキャンバスへ直接描く
```

#### 明るさの目盛り(Phase 5 で確定)

- **放射照度の単位は「1 天文単位で π」。** ランバート BRDF の 1/π と打ち消し合うので、
  **太陽へ正対したアルベド A の完全拡散面は 1 天文単位で表示値 A になる。** 出力段に露出係数は無い。
- **トーンマッピングは Khronos PBR Neutral。** 曲線の最終決定は Phase 11 の仕事。
  **0.08 未満を `x → 6.25x²` で潰す強いトウを持つ**ので、肉眼限界級の暗い点光源は黒へ落ちる。
- **天体が持つのはボンドアルベド。** 幾何アルベドしか公表の無い天体は H–G 系の位相積分
  `q = 0.290 + 0.684 G` で直してある。衝効果を入れないので位相角 0 付近が写真より暗いのは
  正しい帰結で、**アルベドを盛って埋めない。**
- **艦艇モデルの金属度は 0 か 1 の 2 値。** 金属度 1 の面ではベース色がそのまま F0 として
  読まれるので、**剥き出しの金属のベース色は実在する金属の反射率から取る。** 面ごとの違いは
  色ではなく粗さで付ける。
- **加算合成する描画物の明るさは色に載せ、不透明度は 1 に固定する。**
- **惑星輝点は放射量から引く。** 放射照度から表示値への比例係数を全天体共通で 1 つだけ持つ
  (視等級 +6 がかろうじて見える値)。
- 自照するエフェクトの手置きの明るさは残っている — `render/vfx-style.ts` の `*_BRIGHTNESS`、
  `render/aurora.ts` の `INTENSITY_SCALE`、大気パスのリム光と内部散乱色。
  **それぞれ Phase 10(大気)と Phase 12(ボリューム)が引き取る。**

**較正の読み方**: `render-lab` の `albedo` ケース(アルベド 1 の白球を 1 天文単位へ置く)の
最も明るい画素が sRGB (241, 231, 215) であること。`saturn` ケースは環と本体が同じ明るさ基準に
乗っていること(比 0.20)を見る。**恒星は他のケースと同じ 1 天文単位に置く** — 本体だけが
位置によらない環境光を受け取るので、太陽から遠ざけると比がそのぶん動く。

#### 影の構成(Phase 6/7 で確定)

**天体の球と環の帯は解析、艦艇・基地・デブリなどのメッシュは適応シャドウマップ**という複合。
分けたのは**天体と艦のスケールが桁で違い、夜(天体の影)をシャドウマップで表せない**ため。
受け手はどちらも同じ 1 つの透過率の関数から引き、複数の遮蔽は積で合成される。

- **スロットは視錐台の深度分割ではなく、遮蔽器の塊 1 つずつへ枠を合わせる。** 枠の大きさは
  **受け手が要求する texel の細かさ**(カメラから実体までの距離)から決まり、要求の厳しい
  受け手から順に配られる。最後の 1 枚は、縮めた枠がこぼしたぶんを拾う被覆枠に取ってある。
- **1 スロットは深度マップを 2 枚持つ。** 本影が残る距離の遮蔽器と、本影を失って淡い減光しか
  残さない遮蔽器を別の層へ分ける — 混ぜると、光源にいちばん近いものが勝つ深度テストで
  遠くて淡いものが至近の濃いものを追い出す。
- **半影の幅は物理から出す**(ブロッカーまでの距離 × 恒星の視半径)。PCF の頭打ちで表せない
  遠方の本影の細りは、遮蔽率 (遮蔽器の角半径 / 恒星の角半径)² を解析で掛けて補う。
- **枚数も解像度も固定**(4 枚 × 1024²、遠層は 256²)。平行投影では枠の広がりだけでテクセル
  密度を変えられるので、再確保する動機が無い。

#### いま何がどこに乗っているか

**分け目は `markLitOpaque` の判定ひとつ**(`render/pipeline/lit-layer.ts`)。マテリアルが標準
(`MeshStandardMaterial` か `MeshStandardNodeMaterial`)なら `LIT_OPAQUE_LAYER`、それ以外は
チャンネル 0 = world パスへ落ちる。**つまり world は「シーンの光を受けないもの」の受け皿**で、
分類の意図があって置かれたものと、行き場が無いだけのものが混ざっている。

| 乗り物 | 中身 |
|---|---|
| **`LIT_OPAQUE_LAYER`**(G バッファ → 遮蔽 → ライティング → マテリアル) | 艦艇・基地・デブリ・薬莢、天体の球すべて、地球の地表 |
| **`WORLD_BACKGROUND_LAYER`**(マテリアルパスで `renderOrder = -10`) | 星殻 |
| **大気パス** | 地球の大気(もや・リム) |
| **world パス**(チャンネル 0) | 下の表 |

**world パスの中身と、行き先の候補。すべて再検討の余地であって確定ではない。**

| 残っているもの | 行き先の候補 |
|---|---|
| 自機弾の本体 | **一連の不透明パスへ行くべきか。** 見た目の変更を伴うかもしれない |
| 太陽の球・星殻 | **emissive を表現できるなら不透明パスへ載せる。** emissive が障害になるなら、逆に両方を world から降ろす道もある |
| 太陽のグロー | **由来で分ける** — レンズ由来のグローはポストエフェクト、ミー散乱由来のグローは大気 |
| オーロラ・噴射プルーム・敵のプラズマ弾・自機弾のハロー | **ボリュームレンダリング化**(Phase 12)して、大気エフェクトの前か後へ |
| 小天体の点群 | **何とも言えない。** 不透明か |
| 惑星の環 | **微妙な立ち位置。** 反射するマテリアルだが半透明 |
| 惑星の輝点スプライト | 未検討。明るさは Phase 5 で放射量から引くようになった(等級 +6 が見える表示応答を 1 つだけ持つ) |
| 被弾/撃破フラッシュ・再突入エフェクト | 未検討(プルームと同じ族ならボリューム側) |

**WebGPU に 3 チャンネル 16bit 浮動小数点フォーマットは無い**ので、照度バッファは
`rgba16float`(a は未使用)。

**パスの順序は深度の共有で決まっている。** マテリアルパスが先に HDR ターゲットを
クリアして不透明な艦を描き、大気パスと world パスが `autoClear = false` でその上へ描く。
逆順にすると、world パスが最後に描く半透明物(軌道線・プルーム・ビルボード、いずれも
深度を書かない)より後に不透明な艦が来て、艦の手前にある半透明物を艦が上書きしてしまう。

**大気パスがマテリアルパスと world の間にあることの帰結**: 軌道線・軌跡線・ビルボードは
**必ず大気の手前**になる。分割前はリム光が `renderOrder = 2` で線の族の間に居たので、
ここは意図して変えた点。

**残っている宿題:**

1. **鏡面の近似の限界を実測する**(§1-4)。鏡面照度バッファは材質の F0 を持てないので
   F0=1 で評価し、マテリアルパスが掛け直している。**`leo` の構図では誤差が検出限界以下**
   (外殻の画素値 123.1)だが、**金属度の高い面を大きく写す構図は未測。**
   破綻するなら艦船だけ前方描画へ逃がす。
2. **画素一致の画像回帰は採らない。** 基準は過去の自分ではなく、物理から導いた期待値
   (「明るさの目盛り」の較正ケース)である(§2-6)。

### Phase 5 — アルベドの物理量化と、露出・トーンマッピングの本実装 — **実装済み**

§1-1。**明るさが色ではなく輝度の次元で運ばれている。** 確定した目盛りと規約は
「パイプラインの現況と最終形」の「明るさの目盛り」。物理量からの導出が要るのは PBR で描く
実写の絵(天体・艦艇・環)だけで、自照するエフェクトの手置きの明るさは Phase 10 と Phase 12
が引き取る。

後続フェーズが乗る前提:

- **Phase 8 の光源強度は、天体のボンドアルベドをそのまま使う。**
- **Phase 9 の半透明統合は 3D UI パスより前で閉じる。**
- **Phase 11(ブルーム・フレア)と Phase 12(ボリューム)は、放射照度の目盛りに乗る。**

**黒体放射(砲身赤熱・焼失する物体の赤熱・再突入の輝き)はここに含めない** — 個別の
エフェクトであり優先度が低いので Phase 14 へ逃がした。

### Phase 6/7 — 軸 2: 太陽光の遮蔽 — **実装済み**

§1-6。合成基盤(Phase 6)と遮蔽源(Phase 7)は、方式が決まった時点でまとめて実施した。
できあがった構成は「パイプラインの現況と最終形」の「影の構成」。

やったこと:

1. **受け手の入口を、描画座標の点を受け取る 1 本の透過率の関数へ広げた。** 天体表面・艦の
   BRDF・環・大気が同じものを読む。源を足しても受け手のコードは変わらない。
2. **メッシュの影を適応シャドウマップで足した。** 艦が自分の構造・隣の艦・小天体の環へ
   影を落とす。**タンパク質だけが持っていた専用の影パスは畳んで、この 1 本へ統合した。**
3. **天体の球と環の帯は解析のまま残した。** 艦のスケールでシャドウマップの枠を組む以上、
   同じ器で天体の夜を表すことはできない。境界は本影・半影が閉じた式から出る。
4. **`inBodyShadow` の二値の段差を消した。** 環が本体の影へ入る境界も、本体表面へ落ちる環の
   影の境界も、同じ 1 つの遮蔽関数から出る。
5. **大気のもやは、遮蔽パスが書いた 1 枚をそのまま読む。** もやが評価する点は G バッファ深度
   から復元した位置そのものなので、同じ点で遮蔽関数を評価し直す必要が無い。リム光だけは
   シェル上の別の点なので、そちらは評価し直す。
6. **デバッグの基盤を足した。** デバッグ表示に「影」(深度マップ 4 枚を 2×2 で)と
   「影スロット」(その画素をどのスロットが覆っているかの塗り分け)。描画テスト環境は
   1 経路の絵を読む器へ作り直し、恒星とカメラの向き・距離をスライダーで動かせるようにした。
7. **描画設定へ「メッシュの影」のトグルを足した**(天体の球と環が落とす影は消えない)。

**残っているもの**: `shadow_backlog.md`。実機でしか測れない GPU 時間と、条件付きで
先送りした改善案が入っている。

### Phase 8 — 軸 1: エリアライト(球光源・ランバート球)

§1-5。**Phase 5 のアルベドが前提。**
**Phase 4 で太陽は既に「位置と半径を持つ点光源」になっている**(画素ごとの差分ベクトルで
方向と距離を引く)。項目 1〜7 は**光源の側**の話で、ライティングパス(`light-prepass.ts`)の
中に閉じる — その点を**有限の立体角**へ広げる部分だけ。

**項目 8 だけが受け手の側の話で、閉じない**(下記)。

1. **太陽を一様球光源へ**(§1-5-1)。拡散項は距離とともに逆二乗則へ自動で縮退する閉じた解を使い、
   **「遠いときは点光源」という分岐を書かない。** 鏡面項だけ角半径の閾値で LTC / 点光源を切り替える。
2. **天体をランバート球へ**(§1-5-2)。照らされている半球を等価な円盤へ代表させ、LTC を適用。
   **光が来る「向き」の偏りが表現されることを完了判定にする**(単なる明るさの位相変調では不可)。
   強さは **Phase 5 のアルベド × その天体が太陽から受けている放射照度**(§1-1-1)。
   **アルベドをそのまま光源の強さにしない。**
3. **光源の打ち切りは立体角の閾値で**(§1-5-3)。実用上「太陽 + 最も近い 1〜2 天体」に収まる。
4. 光源天体自身の日照は Phase 6/7 の遮蔽基盤を共有(影に入っている天体は光らない)。
5. **受け手が乗っている天体自身を遮蔽の対象から除外する。**
   N·L を球光源の閉じた解へ替えると、終端の柔らかさを光源積分と自己遮蔽が二重に表すことになる。
   G バッファへ天体 id を書いて除外する。**Phase 7 まで許容できていた ±30 km の二重暗化
   (地球の直径の 0.2%)が、ここで許容できなくなる。**
6. **`AMBIENT_IRRADIANCE` を削除。** 地球照が置き換える(§2-1)。**距離を持たない定数が
   外惑星で直射を桁で上回っている状態は、ここで初めて解消する**(§1-5-4)。
   **`SHADOW_MIN_SUN` の床もここで捨てる**(Phase 6 の項目 4)。
7. 色を持つ光源として扱う。**艦の影側が地球の色を帯びることを検証ケースにする。**
8. **受け手の拡散 BRDF をランバートから進める(未確定 — どこまでやるかをここで決める)。**
   詳細は下の「受け手の側の宿題」。

#### 受け手の側の宿題(Phase 5 で判明した積み残し)

**§1-5-2 の「ランバート球」は光源の側の近似であって、受け手の側の話ではなかった。**
受け手はずっと three 標準の GGX + ランバート拡散のままという前提で、その前提を疑っていなかった。
**Phase 5 でアルベドをボンドアルベドに揃えた結果、受け手の側も足りないことが分かった。**

**何が足りないか。** 実在の天体表面は**衝効果**(opposition surge)を持つ — 視線が光源方向と
揃うほど明るくなる、数度幅のピーク。原因は (a) レゴリス粒子の影が粒子の裏へ隠れる、
(b) 往復する光路がコヒーレントに強め合う、の 2 つ。エンケラドゥスの幾何アルベドが 1.4 と
1 を超えるのはこれで、**ボンドアルベド(≈0.8)を拡散反射率に使うランバート近似では、
位相角 0 付近が 2/3·q 倍に暗くなる。**

**候補と、その効き方:**

| 候補 | 何が起きるか |
| --- | --- |
| **Oren–Nayar を拡散へ入れる** | **族としては正しい** — マイクロファセットの影と相互反射から導かれるので、光源方向への明るさの持ち上がりと**縁の平坦化**(満月が球でなく円盤に見える効果)が出る。three の標準マテリアルには無いので自前で書く |
| **GGX をスーパーラフ側で使う** | 縁の平坦化とチョーキーな見えは近づく。**ただしローブの頂点は鏡面方向のままで、再帰反射方向ではない** — 衝効果そのものは再現しない |
| **衝効果の項を明示的に足す**(Hapke の SHOE / CBOE) | 数度幅のスパイクまで出る。式は重く、パラメータが天体ごとに要る |

**積分として分離できるのか。** LTC は**クランプ済みコサインを線形変換した族**しか積分できない
ので、Oren–Nayar も衝効果の項もその外にある。**受け手の BRDF を替えると、エリアライトの
積分がその場で成り立たなくなる。**

**ただし見立てとして、分離できる可能性が高い:**

- **衝効果の幅(数度)は、太陽の視直径(1 AU で 0.53°)より一桁近く広い。** 太陽光に対しては
  光源を点とみなしたまま衝効果を評価してよく、球光源の積分と衝効果を掛け合わせる必要がない。
- **逆に、地球照のような広がった光源(LEO で 70°)に対しては衝効果が積分で均されて消える。**
  エリアライト側の受け手はランバートのままでよい。
- したがって **「恒星の直射には衝効果つきの BRDF、面光源にはランバート」**という切り分けが
  成り立つ見込みがある。**この見立ての検証が Phase 8 の最初の仕事になる。**

**パイプライン上の影響**: 受け手の BRDF はマテリアルパス(`material-pass.ts`)にあるので、
**項目 8 に手を付けた時点で「変更はライティングパスに閉じる」が崩れる。** 照度バッファが
「どの向きからどれだけ来たか」しか運ばないという §1-4 の分業も、衝効果が視線に依存する以上
そのままでは通らない — **恒星の直射だけを別の口で受け手へ渡す**必要が出る。

**Phase 5 ではここに手を付けない。** アルベドを物理量にすることが目的で、位相角 0 付近が
暗いのはその正しい帰結として受け入れる。

**完了条件**: LEO で艦の地球を向いた面と宇宙を向いた面の明るさが桁で違う。
高度を上げていくと地球照が滑らかに弱まり、月軌道では点光源と区別がつかなくなる
(**その遷移でフレームが飛ばない**)。三日月形に見える位置で地球照が弱く、光の向きが偏る。
**木星圏で艦を照らす木星照が、地球圏の地球照より暗い**(距離依存が式に入っている証拠)。
`AmbientLight` が src から消える。
**受け手の側(項目 8)は、どこまでやるかを決めて記録してあること** — 何もしないと決めるのも
結論のうちで、決めないまま次のフェーズへ送らない。

### Phase 9 — 半透明パスの統合

**Phase 4 で大気は既に画面空間のフィルタになっている**(`render/pipeline/atmosphere-pass.ts`)。
ここでやるのは、残りの半透明物をその形へ揃えることと、共通化。

1. `render/transparent-pass.ts`: 不透明解決後に描画。`viewportDepthTexture` / `linearDepth`。
2. 「視線に沿って不透明面までメディアを積分する」共通ヘルパ。**大気・オーロラ・プルーム・リングが共有する。**
   **環の遮蔽と同じ光学モデル(Beer–Lambert)を共有できるか検討する。**
   Phase 4 の大気フィルタはこのヘルパの最初の利用者になるので、**切り出す形はそこから引く。**
3. `aurora.ts` の CPU 頂点更新を GPU へ。
4. **残る `depthTest: false` の 2 箇所**(`stars.ts` / `plan-gizmo-3d.ts`)を規約内へ回収する。
   地球の大気リム球のぶんは Phase 4 で片付いている。
5. **線以外の半透明物を `LINE_RENDER_ORDER` と同じ表へ統合する**(線の族の移設は Phase 5 で済み)。
6. 加算合成の上限は Phase 5 の露出基準に従う。

### Phase 10 — 大気散乱(指数密度)

**このフェーズはパイプラインを触らない。** 触るのは
`render/pipeline/atmosphere-pass.ts` の中身だけ — Phase 4 が置き場を確定させてあるので、
ここでやるのは同じ入口・同じ出口のまま式を差し替えることに限られる。
**触らざるを得なくなったら、Phase 4 の分割が足りていない。**

1. 透過・単散乱・多重散乱近似を LUT 化(オフライン生成も可)。カメラが大気圏内外どちらでも同じモデル。
2. エアリアルパースペクティブを不透明深度に対して積分し、Phase 4 が持ってきた
   Beer-Lambert 一本のもや(`HAZE_TAU0 = 0.34`)を置換。
3. **夕焼けを光路長から導出**し、`vec3(1,0.4,0.1)` の固定補間を削除。
   分割で薄れた「雲を橙に染める項」は、ここで太陽光路の透過率として物理的に戻る。
4. 雲は当面マテリアルパス内の 2 層サンプリング。
   **`earth.ts` の UV ずらしによる雲影は、そのままでよい。** 雲の高度 ~1e4 m での半影幅は
   2αd = 93 m なのに対し、雲テクスチャは 8192px で赤道一周 4.0e7 m = **4.9 km/テクセル**。
   **半影がテクセルの 1/50 しかないので、ぼかすべき構造がそもそも存在しない。**
   雲を遮蔽源へ載せる価値があるとしたら、半影ではなく「雲が他の物体へ落とす影」のときだけ。
5. `GraphicsSettings` へ雲のトグルを足す(この時点で単体で切れるようになる)。

**Phase 4 から持ち越した既知の欠落。** どちらも「視線に沿って積分する」形へ作り直せば自然に
消えるので、個別に直さずここまで持ってくる。

- **もやが大気天体以外の不透明面にも掛かる。** いまの判定は「復元位置がシェルの内側か」だけで、
  もやの濃さはその点の動径方向を法線とみなして決まる。**シェル高度(地表 +340km)より低いところに
  いる艦・デブリは、地表と同じ光学的厚みで白む** — 通常軌道 420km は外なので平時は出ないが、
  再突入する破片では出る。光路長を実際の視線区間から積分すれば、この判定ごと要らなくなる。
- **リム光の高度減衰が定数に潰れている。** 視線とシェルの交点は定義上いつもシェル面の上なので、
  そこで測る高度は常に上限の 340km。`RIM_MIN_H`(20km)・`RIM_SCALE_H`(90km)と指数は
  exp(−320/90) = 0.0285 という 1 つの定数にしかならず、**リムは高度勾配を持たない一様な明るさ**に
  なっている。旧の加算シェルも同じ半径の球面上で評価していたので **Phase 4 の後退ではなく、
  最初から実装されていなかった**。視線に沿った積分にすれば勾配は式から出る。

### Phase 11 — ポストエフェクト

1. 露出 → ブルーム → レンズフレア/グレア → トーンマッピング → sRGB。
2. ブルーム対象は Phase 5 で HDR 化済みの発光体。**再突入プラズマは既に動圧という物理量から
   強度を引いている**(`REENTRY_GLOW_MIN_Q` / `_FULL_Q`)ので、HDR 化の検証基準ケースに使える。
3. TAA/SSAA は `GraphicsSettings` のトグル配下で任意。AO は優先度低。

### Phase 12 — ボリュームレンダリング

Phase 9 のレイ積分枠組みが前提。プルーム・RCS・再突入・オーロラを板ポリゴンから参加媒質へ。

### Phase 13 — 軸 3: 地球照の遮蔽(任意)

§1-7。**優先度最低。無視したままでも計画は完結する。**

1. AO を導入し、地球照(および他の二次反射光)にのみ掛ける。太陽光には掛けない
   (太陽光の遮蔽は Phase 6/7 が正しく解いているので、AO で二重に暗くしてはならない)。
2. **全天体からシャドウマップを撮るという方向は採らない**(原理的に不可能、§1-7)。

### Phase 14 — 黒体放射の物理量化(温度を持つ全物体)

**優先度低。個別のエフェクトであり、他のどのフェーズからも依存されない。**
**Phase 5 の HDR 化(露出が放射量基準になっていること)だけが前提。**

1. 砲身の赤熱を、固定色 + 固定 opacity(`render/ships.ts` の `heatMat`)から、機体温度 +
   `STEFAN_BOLTZMANN` + `HULL_EMISS` の黒体放射へ。色も強度も温度 1 つから出す。
2. **温度を持つのは艦だけではない** — 敵機・破片・薬莢・弾薬も同じ熱収支
   (`physics/thermal.ts`)で温まるので、焼失する物体の赤熱も同じ黒体放射から出す。
   `game/game-entity/` の各 entity が既に温度を持っているので、新しい状態は要らない。
3. 再突入の輝き(`player/reentry-effects.ts`)は現状 動圧から強度を引いている
   (`REENTRY_GLOW_MIN_Q` / `_FULL_Q`)。**周囲の空気の発光として温度から引き直す余地がある**
   (`better_simulation/backlog.md` 16)。ただし衝撃層の発光は黒体放射ではないので、
   艦体の赤熱と同じ式には乗らない — 別物として扱うか、動圧のままにするかはここで決める。

**完了条件**: 赤熱する物体の色と明るさが、温度以外のどのパラメータからも決まらない。
`render/` に固定の赤熱色・固定 opacity が残っていない。

## 4. 責務境界の規則(全フェーズ横断)

> **`game/` は「なにがあるか」を知り、「どう見えるか」を知らない。**
> **`render/` は「どう見えるか」を知り、「どこにあるか(ECI)」を知らない。**
> **ライティングパスは「光源の形」と「遮蔽」を知り、「材質」を知らない。**
> **レンダリングパスは「材質」を知り、「光源の形」も「遮蔽」も知らない。**

4 行目までが揃うと、軸 1(光源の形)と軸 2(遮蔽)が互いに独立に差し替えられる。
**これがこの構成の目的である。** Phase をまたいで少しずつ寄せる。一括改修はしない。

### 移す

| 対象 | 現在 | 移動先 | 対応フェーズ |
|---|---|---|---|
| **描画用の日照判定** | `environment-scene.ts` が `physics/shadow.ts` を読み `SunLight` へ渡す | **`render/pipeline/occlusion.ts` の遮蔽源。物理側の関数は残るが描画は読まない**(§1-8) | Phase 6(中身の差し替え) |
| `celestial/{sphere,point,sun,earth}-view.ts`, `ring-view.ts`, `point-field-view.ts` | `game/celestial/` | `render/celestial/` | **要検討**。これらは `Ephemeris` / `FloatingOrigin` / `Vec3` を読むので、そのまま移すと §1-2 の不変条件を破る。移せるのは ECI を受け取らない部分だけ。**当面は動かさない** |
| 参照線の色・不透明度・`renderOrder`・頂点密度方針 | `environment-scene.ts` | `render/` | Phase 9 |

### 残す

- `physics/` の THREE 非依存(**現状ゼロ件、維持する**)。
- `physics/projection.ts` — 物理・幾何として妥当。
  **`projection.ts` が near/far 非依存であることは、カスケード導入時の重要な資産**(§1-3)。
  リングの放射伝達は `render/ring.ts` の TSL グラフのみに存在する。
- **`physics/shadow.ts` の日照率(軸 4)は物理側に残す。** 熱・電力・SRP の消費者がいる。
  **ただし描画はこれを読まない**(§1-8)。同じ物理現象について CPU と GPU に別実装があることになるが、
  **問いが違う**(点の日照率 vs 画素ごとの遮蔽度)ので二重実装ではない。
- `GameEntity.obj: THREE.Object3D` — 不透明ハンドルとして当面許容(`game/` の 47 ファイルが
  `three/webgpu` を import している)。ただし
  **`game/` 側で material / renderOrder / LOD / 色 / `castShadow` を決めるのは禁止**とする。

### 判断基準

`game/` に書いてよいのは「この天体が存在する」「この位置(ECI)にある」「破壊された」まで。
「何 px だから点で描く」「`renderOrder` は 3」「色は `0x9a8a7a`」「影を落とす」は `render/` の判断。

## 5. リスクと未決事項

| 項目 | リスク | 備考 |

| **three の版が上がると描画順が二重反転する** | **高** | `0.185.1` は `reversedDepthBuffer` のとき `renderOrder` を全反転させる(Issue #33944)。反転比較関数で等価に打ち消してあるが、**修正済みの r186 以降へ上がるとその打ち消しが余計になり、描画順が黙って逆さになる。** `package.json` のピン留めと `tools/check-three-pin.mjs` で塞いである(`how_to_update_three.md`) |

| **昼夜境界の橙が薄い** | 中 | 雲を橙に染めていた項(`cloudColorLit`)はライティングなので、分割でアルベドから外れた。同じ見た目は大気フィルタの内部散乱色が担っているが、位相の掛け方が違うので終端の橙は薄い。**物理的な導出(太陽光路の透過率)は Phase 10** |
| **`SHADOW_MIN_AMBIENT` の廃止で食が暗い** | 中 | 環境光の変調は CPU の一様スカラが入力だったので、それを外した時点で再構成できなくなった。**その差が Phase 8 で地球照が埋めるべき量そのもの**だが、暗すぎて遊べないなら暫定の床が要る |
| **遮蔽器の打ち切り規則** | 中 | 解析の遮蔽器は視半径の大きい順に上限本数まで、影の枠は要求精度の厳しい順に 4 枚まで。選択規則を誤ると影が消える。**`physics/shadow.ts` の全件走査がオラクルになるので、解析側の誤差は直接測れる**(`shadow_backlog.md`) |
| **アルベド値の出典が一次文献まで届いていない** | 中 | Phase 5 で 101 天体すべてにボンドアルベドが入ったが、幾何アルベドしか公表の無い天体は H–G 系の位相積分 `q = 0.290 + 0.684 G` で直したもので、11 体は分類の代表値(`celestial-albedo.ts` に「分類既定」と明記)。**Phase 8 で天体を光源にすると、この値がそのまま光源強度になる** |
| **鏡面近似** | 中 | ライトプリパスは鏡面のマテリアル依存を照度バッファに畳めない(§1-4)。F0=1 で評価しマテリアルパスで掛け直している。**`leo` では検出限界以下だが、金属度の高い面を大きく写す構図は未測。破綻したら艦船だけ前方描画へ** |
| **three の内部 API への依存** | 中 | パス別 GPU 計測が `backend.timestampQueryPool`(`@types/three` に無い)と uid の紐付けに乗っている(§2-6)。**three の更新で壊れうる。** 壊れても計測が止まるだけで絵は無事 |
| **Phase 8 のランバート球の近似** | 中 | 「照らされた半球を等価な円盤で代表」は LTC の標準的な適用範囲外(§1-5-2)。三日月形の位置での検証ケースが必須 |
| **Phase 8 の受け手の BRDF** | **高** | ランバート受け手を前提に「変更はライティングパスに閉じる」と切ってあったが、**衝効果を入れるならマテリアルパスと照度バッファの規約まで届く**(Phase 8 の「受け手の側の宿題」)。Oren–Nayar も衝効果も LTC の族の外なので、エリアライトの積分と同居できない。**「恒星の直射だけ別扱い」で分離できるという見立てを、先に確かめる** |
| **遮蔽の合成規約** | 中 | 透過率の積(= 光学的厚さの和)。**不透明も τ→∞ の極限として同じ式に乗る**ので源を足しても規約は変わらないが、**受け手の呼び出し形を決めてしまうので後から差し替えられない**(§1-6-1) |
| **影のドローコール / 帯域が未実測** | 中 | 枠 1 枚につき近層と遠層の 2 回、最大 4 枚。**ヘッドレスでは GPU 時間が測れないので実機で読む**(`shadow_backlog.md`) |
| Phase 8 の LTC テーブル | 中 | three.js の `RectAreaLight` 用テーブルが流用できるか、球光源用に別途生成するか要調査 |
| G-buffer + 照度 + シャドウのバンド幅 | 中 | 解像度スケールとシャドウ解像度トグル(`GraphicsSettings`)で逃げ道を確保 |
| ライトプリパス + 半透明 | 中 | 半透明は恩恵を受けない。Phase 9 は前方描画で確定 |
| 低性能端末 | 中 | 全部オフでも動くこと。`GraphicsSettings` のプリセットが担保 |
| **既存の絵が崩れること** | — | **リスクではない**(§1-1) |

### 描画の現状の負荷

戦闘ビューで draw calls 約 165 / triangles 約 33 万(弾 347・薬莢 96・デブリ 24 が出ている状態)。
マップビューで draw calls 約 198。

連射中(弾 150 体以上)の実測:

| 条件 | fps | render (avg) | update (avg) | draw calls |
|---|---|---|---|---|
| インスタンシングあり | 45 | 1.2ms | 19.4ms | 164 |
| インスタンシングなし(個別メッシュ) | 46 | 1.8ms | 17.9ms | 388 |
| 毎フレーム メッシュ再確保 | 27 | 8.7ms | 25.2ms | 434 |

**インスタンシングは draw calls を 388→164 へ半減させるが、fps はほとんど変わらない(46→45)。**
理由は描画フェーズが 1〜2ms しかかからず、**ボトルネックが update フェーズ**(約 18〜19ms、この
グラフィック基盤ロードマップの外側の課題)にあるため。一方で毎フレームのメッシュ再確保は明確に
悪い(render 8.7ms、fps 27)。

→ **インスタンシングの価値は現時点の fps ではなく、シャドウマップを採った場合に段数だけ描く Phase 7 に
向けた余裕である。** ジオメトリ 2 回描きぶんは既に払っており、実測で draw calls は約 324。

**上表の「render」は CPU 側の壁時計時間であって GPU の実行時間ではない**ので、パスを増やした
あとの判断には使えない。パス別の GPU 時間(負荷確認ウィンドウの 描画 グループ)を見ること —
戦闘ビューでの実測は G バッファ 0.6ms / ライティング 0.5ms / マテリアル 0.6ms /
ワールド 2.6ms / 合成 0.4ms。**影・遮蔽・大気は未実測**(`shadow_backlog.md`)。
見積りは遮蔽 0.22ms / 大気 0.2〜0.5ms(どちらも全画面 1 枚)で、実機で読んで外れていたら
ここへ書き戻す。

### `InstancedMesh.count` を毎フレーム書き換えてはならない

three の `InstanceNode` は instanceMatrix の受け渡し経路(uniform buffer か instanced attribute か)を
`count` から決め、その判断とバッファ長を最初の描画時に一度だけ確定する。弾が 0 体のフレームで
`count = 0` になると長さ 1 に固定され、以後何体積んでも描画されなくなる。
そのため `InstancedPool.count` は容量に固定し、未使用の枠をゼロ行列で潰す方式にしている。
**影の深度マップへ同じジオメトリを描くときにも同じ制約が効く。**
