# 自機まわりの白い線の調査 (render/curve.ts とその利用者)

コード変更はまだ行っていない。例外として、2本の線を見分けるための色定数だけ一時的に
書き換えてある(末尾「一時的な色分け」参照 — 調査が済んだら戻すこと)。

**§2 はコードを読んで立てた仮説、§5 は色分け後の目視観察と、それに合わせた結論の訂正。
着手前に §5 を先に読むこと。§2 の優先度付けは §5 で置き換えられている。**

---

## 1. 自機のまわりに出うる曲線の一覧

`render/curve.ts` の `Curve` を使う描画は、ラッパが2種類しかない。

- `src/game/lines/orbit-line.ts` `OrbitLine` — **解析的な閉じた楕円**。`OrbitalElements` から
  離心近点角 E=t·2π で位置を出す。頂点は**中心天体相対**のまま保持し、毎フレームは
  `Object3D.position` の平行移動だけ。
- `src/game/lines/trajectory-line.ts` `TrajectoryLine` — **時刻付き点列**をエルミート補間して
  折れ線化する汎用土台。頂点は**表示座標系(planFrame)相対**で bake し、毎フレームは
  剛体 un-bake(回転)+ フローティングオリジン(平行移動)だけ。

戦闘ビューで自機の近くに出うるのは以下。

| 線 | 実体 | 色 | renderOrder | 戦闘ビューでの出方 |
|---|---|---|---|---|
| 自機の解析楕円 | `Player.orbitLine` (`player/player.ts:74`, `OrbitLine`) | `0xbfc9d4` | `shipOrbit`=1 | `game.ts:863` で常時 enable。`game.ts:931` で予測線がホライズンを覆っている間だけ suppress |
| 自機の予測軌道 | `EntityTrajectoryLine.predicted` (`entity-trajectory-line.ts:19,43`, `TrajectoryLine`) | `0xbfc9d4` | `predicted`=5 | `game.ts:922` で `overviewMode` に関係なく毎フレーム sync |
| デバッグ線 | `EntityTrajectoryLine.debug` | `0x40e0ff` | `predicted`=5 | `?debugLines=1` のときだけ。既定は無効 |
| ターゲット/副ターゲット/敵/基地の楕円 | `Targeter` / `Enemy` / `Base` | 橙・シアン・濃灰・緑 | 3/2/1/1 | 白ではないので今回の対象外 |
| 計画軌道 | `PlanArc` (`TrajectoryLine`, 破線) | 呼び出し側指定 | `plan`=4 | 破線なので見分けられる |

**「白い線が2本」の正体は上の1行目と2行目**で、`0xbfc9d4` という同一リテラルを
`player/player.ts:74` と `entity-trajectory-line.ts:19` の2箇所が独立に持っている。
1本しか見えないことがあるのは `game.ts:931` の `setSuppressed` で楕円が消えるため。

### あるべき姿(整理)

- **解析楕円**は「積分予測が表示範囲に届いていない間の代替表示」。J2/抵抗を含まない
  瞬間接触楕円なので、**その瞬間の自機位置を必ず通る**のが本来。
- **予測軌道**は「実際に起きること」を数値積分した線。**現在時刻の先端が自機位置に一致する**
  のが本来で、過去側へ伸ばす意味はない。

## 2. 症状ごとの原因

### ① 静止画では滑らかだが自機からズレる / WASD を離すまで反映されない

**これは緑(解析楕円)と赤紫(予測線)の**両方**が別々の理由で起こしている。**

**(a) 解析楕円の 120ms ゲート — `orbit-line.ts:122`**

```ts
if (now - this.lastRegen < REGEN_MIN_INTERVAL_MS) return false;  // 120ms
if (force) return true;
```

`force`(= `player.ts:473` の `this.thrust !== null`)の判定が **120ms ゲートより後ろ**に
あるため、噴射中でも楕円は最大 120ms に1回しか作り直されない。その間、自機は動き続けて
楕円は取り残される。時間加速16倍なら 120ms 実時間 ≒ 2秒シミュ時間ぶん取り残される。
→ 報告「横方向に推進すると取り残されたあと**一定間隔で**追随する」はこのゲートそのもの。
噴射をやめると `force=false` に戻り、以後は `TOL_SMA`/`TOL_ECC`/`TOL_PLANE`/`TOL_APSE`
(`orbit-line.ts:17-20`)を超えるまで一切作り直されない。

**(b) 予測線は噴射中に消える — `player/player.ts:207`**

```ts
if (this.thrust !== null) this.invalidatePrediction();
```

WASD を押している間は毎フレーム予測列が破棄され、`stepPredicted` も `thrust !== null` で
伸長を拒否する(`game-entity.ts:204`)。つまり**噴射中は予測線が存在しない**。
キーを離した瞬間に現在状態から作り直されるので自機へ吸い付く。
→ 報告「WASD から手を離すまでドリフトが反映されない」の正体。

**(c) 乖離許容が戦闘ビューには大きすぎる — `const.ts:411`**

`PREDICT_RESET_DIST = 500`(m)。`divergenceTolerance` の下限がこれなので、予測線は
**自機から最大 500m ズレていても破棄されない**。戦闘ビューの視距離は数十m なので、
画面上では完全に別物の位置に見える。

**(d) 破棄されても前フレームのジオメトリが描かれ続ける(バグ)**

`entity-trajectory-line.ts:88-92` の順序:

```ts
line.syncGeometry(samples, ...);   // samples が EMPTY_SAMPLES → baked = []
line.syncTransform(...);
line.sync(camera);                 // baked.length < 2 → curve.setVisible(false)
line.setVisible(true);             // ← wantVisible を true に戻す
```

`TrajectoryLine.sync` は `baked.length < 2` のとき `setCurve` を呼ばずに戻るため、
`Curve.vertexCount` は**前フレームの値のまま**。直後の `setVisible(true)` で
`applyVisible()` が `wantVisible && vertexCount >= 2` を満たしてしまい、
**古い頂点が描かれ続ける**。`syncTransform` は毎フレーム効くので、その古い線は
座標系の剛体運動だけで動き、自機からどんどん離れていく。
→ 報告「自機から離れていき、しばらくすると見えなくなる。噴射すると再び見える」に一致する
(「再び見える」のは噴射で楕円側の `suppressed` が外れて緑が出るため)。

### ② 小刻みな振動 / 頂点密度は足りているのにギザギザ

**(a) 主因: カメラ背後の点で適応分割の予算を食い尽くす — `curve.ts:235,245` + `projection.ts:49,54`**

```ts
const mpp = this.scaleAtLocal(mx, my, mz);          // curve.ts:235
const sagittaPx = mpp > 0 ? Math.sqrt(sagSq) / mpp : 0;
if (sagittaPx > MAX_EDGE_SAG_PX || turn > MAX_EDGE_TURN) { ...二分... }
```

`scaleAtLocal` は `metersPerPixelFromTanHalfFov(tan, depth, H)` を呼び、そこで
`depth` は `MIN_DEPTH = 1e-6` で床打ちされる(`projection.ts:49,54`)。
**視点上・視点の背後の点では mpp ≒ 1e-11 になり、sagittaPx が事実上無限大**になる。
その区間は `MAX_SUBDIVIDE_DEPTH = 24` か `maxVertices` に達するまで無条件に二分され続ける。

戦闘ビューでは自機は軌道の内側にいるので、**楕円も予測線も必ず一部がカメラの背後を通る**。
そこで頂点予算(`OrbitLine` は 4096、`TrajectoryLine` は 16384)を使い切ると、
`subdivide` は `pushBaked` が早期 return するだけになり(`curve.ts:211`)、
**残りの区間は `INITIAL_SEGMENTS = 8` 相当の粗い弦だけになる**。
→ 「頂点密度は十分なはずなのに折れ線どころではないギザギザ」、
→ 「カメラの位置や方向によって消える/形が変わる」の両方がこれで説明できる。
どのフレームでどの区間が背後に入るかはカメラ次第なので、フレームごとに配分が変わり
**小刻みな振動**にもなる。

**(b) 予測線は毎フレーム焼き直している — `curve.ts:276`**

`TrajectoryLine.syncGeometry` は `samples` の参照が変わったら `revision` を差し替える
(`trajectory-line.ts:79-82`)。予測列は `DynamicTrajectory.step` のたびに
`_samplesCache = null`(`dynamic-trajectory.ts:67`)になるので、**伸長中は毎フレーム
新しい配列参照**が返り、毎フレーム再 bake される。適応分割は決定論的でも、
入力点列が1点増えれば t の写像(`trajectory-line.ts:62` の時刻レンジ)がずれるため
全頂点が動く。→ 予測線側の細かい揺れ。

**(c) 再 bake 判定が「先頭1点」のスケールだけを見ている — `curve.ts:272-275`**

```ts
sample(0, this.scratchA);
const scaleNow = this.scaleAtLocal(...);
const scaleChanged = ... > SCALE_REBAKE_RATIO (1.2) ...
```

戦闘ビューではカメラが自機と一緒に毎フレーム並進するので、先頭1点の depth は変動する。
1.2倍を跨ぐたびに全体が焼き直され、そのたびに頂点が入れ替わる。しかも先頭点が背後に
あると `scaleNow` は MIN_DEPTH 由来の定数に張り付き、**曲線全体の解像度判断が
まったく無意味な値で行われる**。

**(d) 副次的: 頂点バッファが f32 で、頂点は天体中心相対のまま**

`Curve.positions` / `bakedLocal` は `Float32Array`(`curve.ts:134-135`)。
`OrbitLine` の頂点は中心天体相対、`TrajectoryLine` の頂点は planFrame(既定は地球中心)相対
なので、LEO では **|頂点| ≒ 6.8e6 m**。f32 の相対精度 1.2e-7 から、
**量子化幅 ≒ 0.8m** になる。戦闘ビューの視距離(数十m)ではこれが数px の階段として見える。
フローティングオリジンは `Object3D.position` 側にしか効いておらず、
頂点の絶対値の大きさは減っていない — つまり `world = position + q·vertex` の桁落ちを
GPU 側だけでなく **CPU 側の頂点格納の時点で既に確定させている**。
(a) を直しても残るので、別項目として扱うこと。

### ③ カメラ次第で消える — culling ではない

`Curve` は `frustumCulled = false`(`curve.ts:179`)なので、**フラスタムカリングは働いていない**。
消えるのは
- ②(a) の予算食い尽くしで可視区間に頂点が来ない、
- `applyVisible()` の `vertexCount >= 2` 条件(`curve.ts:403`)、
- `OrbitLine` の `snap === null`(`orbit-line.ts:92-96`, e≥0.98 など)、
- `game.ts:931` の `setSuppressed`
のいずれか。culling を疑って `frustumCulled` を触っても効果はない。

## 3. 修正方針(案)

優先度順。①〜③は独立に着手できる。

### P0-1. カメラ背後の点で分割予算を食わない (`render/curve.ts`)

`subdivide` の分割条件が「画面上のサジッタ」である以上、**画面外・視点背後の区間は
その基準が定義できない**。`MIN_DEPTH` による床打ちは値を有限にするだけで、
「無限に細かくしろ」という誤った答えを返している。

対応の方向は、`scaleAtLocal` が depth を返せるようにしたうえで、
`subdivide` で **depth <= 0(視点背後)の中点を含む区間はサジッタ判定を捨て、
`MAX_EDGE_TURN`(折れ角)だけで分割を決める**こと。折れ角は画面に依存しない
世界空間の量なので、背後でも意味のある上限として機能する。

同時に、予算切れを「静かに諦める」のではなく**曲線全体へ均等に配分する**必要がある。
現状は `bakedCount + 1 >= maxVertices` で以降が全部1弦になる(`curve.ts:226`)。
`INITIAL_SEGMENTS` の各区間に予算の 1/8 ずつを割り当てる(1区間が他区間の取り分を
食えないようにする)のが素直で、`render/curve.ts` 内で完結する。

### P0-2. 破棄された予測列で古い線が残る (`entity-trajectory-line.ts` / `trajectory-line.ts`)

`TrajectoryLine.sync` が早期 return する経路で `Curve.vertexCount` が更新されないのに、
呼び出し側が後から `setVisible(true)` を被せているのが原因。
「頂点が無い」という事実を `Curve` 側の状態へ確実に反映させる(点列が2点未満なら
`vertexCount = 0` にして drawRange を 0 にする)のが正しい。
呼び出し順序を入れ替えるだけの対処は、同じ罠を次の利用者が踏むので避けること。

### P1-1. 解析楕円が自機位置を通らない (`orbit-line.ts`)

- `needsRegen` の `force` 判定を 120ms ゲートより**前**に出す。
  噴射中・ノード編集中は「能動的に変化している」と呼び出し側が宣言している状態なので、
  実時間の間引きを適用する理由がない。
- そのうえで、`REGEN_MIN_INTERVAL_MS` が実時間基準であること自体を見直す。
  時間加速下では実時間 120ms がシミュ時間で何十秒にもなる。閾値(`TOL_*`)の方が
  本来の判定で、実時間ゲートは再生成コストの保険にすぎない — 順序を逆にするか、
  ゲートをシミュ時間基準にするか、どちらかに決める必要がある。

### P1-2. 予測線が自機から離れる許容量 (`const.ts` / `game-entity.ts`)

`PREDICT_RESET_DIST = 500m` は表示ホライズン全体に対する妥当性で決められた値で、
戦闘ビューの見え方(数十m)を想定していない。
「常に自機位置を通るように見せたい」という要求に対しては、許容量を縮めるより
**描画側で先端を現在時刻に合わせる**方が筋がよい:
予測列の先頭サンプルは作成時刻 t0 のままで、`simTime` が進んでも前へ動かない
(先端がホライズンに達すると `step` が呼ばれず `history.cleanup` も走らないため。
`game-entity.ts:214`, `dynamic-trajectory.ts:58-63`)。
**`simTime` より古い部分を描画対象から外し、`simTime` ちょうどの補間点を先頭にする**と、
線は定義上つねに自機の現在位置から始まる。どこで切るか(`TrajectoryLine` 側か
`EntityTrajectoryLine` 側か)は責務の議論が要る。

### P2. 頂点の f32 桁落ち (`render/curve.ts` + 両ラッパ)

頂点を天体中心相対ではなく**描画原点(フローティングオリジン)相対**で焼けば
桁落ちは消えるが、それは `OrbitLine`/`TrajectoryLine` の「頂点は動かさず変換だけ毎フレーム」
という設計そのものを壊す(原点が毎フレーム動くので毎フレーム再 bake になる)。
安易に変えず、まず P0/P1 を直したうえで 0.8m の量子化が実際に見えるかを確認すること。
見えるなら、`Curve` に「焼いた時点の基準点」を持たせて頂点をその相対で格納し、
`setTransform` の position にその基準点を足す、という段階を挟むのが小さい変更になる。

## 4. 検証の順序

1. 一時色分け(下記)のまま戦闘ビューで、緑と赤紫のどちらがギザギザ/どちらがズレるかを目視で確定する。
   本調査の予想は「緑=120ms 階段でズレる」「赤紫=噴射中に消える・破棄後に古い線が残る」
   「ギザギザは両方(予算食い尽くしが共通原因)」。
2. `?debugLines=1` は水色で別物なので、必ず切って確認すること。
3. 時間加速16倍で 2〜3 秒放置し、線が消えるか/古い線が残るかを見る。
   `?perf=1` の 予測 セクション(`Predictor.discarded`)が毎フレーム 1 になっていれば P1-2 が主因。

## 5. 目視観察による訂正(色分け後)

緑=解析楕円 / 赤紫=予測軌道 に色分けして戦闘ビューを目視した結果、
§2 の見立てのうち2点が誤っていた。以下が現時点の結論。

### 観察

1. ギザギザは**緑にも赤紫にも**ある。頂点密度が低いことによる粗さでは**ない** —
   頂点は十分に見えていて、そのうえで **0.8m 程度の刻みで折れ曲がっている**。
2. カメラの向きによって、線が**そもそも表示されなくなる**。
3. 噴射開始から数ミリ秒遅れて赤紫が消える。
4. 緑はむしろ噴射中にしか見えていない(ように見える)。

### 訂正1: ギザギザの主因は f32 量子化 (旧 P2 → **P0**)

観察1は §2-②(d) の症状そのもので、0.8m という刻み幅が
「LEO の頂点絶対値 6.8e6 m × f32 相対精度 1.2e-7 ≒ 0.8m」と一致する。
**§2 が主因として挙げた「予算の食い尽くし」はギザギザの原因ではない**
(あれは頂点が足りなくなる現象で、頂点が多く見えているという観察と両立しない)。
優先度を入れ替え、量子化を P0 として先に直す。

**修正の方向**: f32 のまま精度を上げることはできない(GPU の頂点バッファは f32 なので、
CPU 側を f64 で持っても最後に落ちる)。効くのは**頂点の絶対値を小さくすること**だけ。
つまり `Curve` に「焼いた時点の基準点」を持たせ、頂点をその相対で格納し、
`setTransform` の position にその基準点ぶんを足す。

基準点は**カメラの近く**に取る。頂点 v の誤差は ε|v − ref| なので、画面上の見かけの大きさは
ε|v − ref| / |v − cam| になる。ref をカメラの近くに置けば |v − ref| ≒ |v − cam| となり、
見かけの誤差は距離によらず ε ≒ 1.2e-7 rad(画面高 1000px の全画角に対して 1e-4px 未満)に
張り付く。**遠い頂点ほど誤差が大きくなるが、遠いぶん画面上では等しく小さい** — これが、
中心天体相対(現状)ではなく描画原点相対で焼くべき理由。

注意すべき副作用: 基準点をカメラに置くとカメラが動くたびに再 bake が要る。
ただし上の評価から、必要なのは「ref がカメラから、頂点までの距離に比べて遠くなりすぎない」
ことだけで、厳密な追随は要らない。焼き直し条件をどう置くか(例: ref とカメラの距離が
最近傍頂点までの距離を超えたら焼き直す)は設計判断が要る。
`OrbitLine`/`TrajectoryLine` の「頂点は動かさず変換だけ毎フレーム」という前提を
どこまで残すかも同時に決めること。

### 訂正2: 予算食い尽くしは「粗くなる」ではなく「そこで線が終わる」(P0 のまま)

§2-②(a) で「残りの区間は 8 弦相当の粗い弦になる」と書いたのは**誤り**。
`pushBaked` は満杯だと早期 return する(`curve.ts:211`)ので、
`subdivide` の予算切れ分岐(`curve.ts:226-229`)以降は**頂点が1つも積まれない**。
`rebake` は t=0 から順に進むため、結果は

- 予算が尽きるまでの区間: 密な頂点(そこに §5 の量子化ギザギザが出る)
- それ以降: **何も描かれない**(drawRange が届かない)

となる。カメラ背後の区間が t の早い側に来ると、**可視区間へ到達する前に予算が尽きて
線が丸ごと出ない**。観察1(密なのにギザギザ)と観察2(向きによって出ない)が
**同じ1つのバグの前後半**として矛盾なく説明できる。§2-P0-1 の修正方針
(視点背後ではサジッタ判定を捨てて折れ角だけで分割する + 予算を区間へ均等配分する)は
そのままでよい。

### 訂正3: 観察3・4 は「設計どおりの受け渡し」の可能性が高い(P0-2 は未確認)

観察4(緑が噴射中にしか見えない)は `game.ts:931` の `setSuppressed` そのもの。
非噴射時は予測が伸びてホライズンを覆う → 緑は抑制される。噴射すると
`player.ts:207` で予測が破棄され `coversHorizon` が false → 緑が出る。**仕様どおり。**
観察3(噴射で赤紫が消える)も `player.ts:207` の即時破棄そのもので、これも仕様どおり。

つまり観察3・4 は**組で1つの受け渡し動作**であり、単独のバグではない。
ただしこれは §2-P0-2(破棄後に古い線が描かれ続ける)の予測と**食い違う**:
コードを読む限り `vertexCount` が前フレームのまま `setVisible(true)` が被さるので、
赤紫は消えずに残るはずだった。実際には消えている。

**この食い違いは P0-2 に着手する前に解消すること。** どちらかである:
- 読み違いで、実際にはどこかで `vertexCount` が 0 に戻っている
- 残留は実際に起きているが、別の理由(訂正2 の予算切れで線が丸ごと出ない等)で
  見えていないだけ

確認方法: 噴射しながらカメラを大きく引き、自機から離れた位置に赤紫が取り残されて
いないかを見る。§5 の P0(量子化・予算配分)を先に直すと訂正2 の影響が消えるので、
**P0 を直した後に再確認する方が切り分けやすい。**

### 着手順(観察を反映した最終形)

1. **P0-a 予算の食い尽くし** — `render/curve.ts`。視点背後の区間の分割基準と、
   区間ごとの予算配分。(§2-P0-1)
2. **P0-b f32 量子化** — `render/curve.ts` + 両ラッパ。頂点をカメラ近傍基準の相対で焼く。(§5-訂正1)
3. 1・2 を直したうえで観察3・4 を再確認し、**P0-2(古い線の残留)が実在するかを判定**する。(§5-訂正3)
4. 実在すれば P0-2、その後 P1-1(120ms ゲート順序)/ P1-2(予測線の先頭を現在時刻に合わせる)。

P1-1・P1-2 は §2 のまま有効(観察と矛盾しない)だが、見た目の主症状ではないので後回しでよい。
