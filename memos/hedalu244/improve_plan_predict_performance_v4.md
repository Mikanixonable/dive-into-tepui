## 計測の前提 — 条件と再現手順

**ビルドとプローブは別々に差し替えられる。** プローブ(`tools/perf-probe.mjs`)は
ビルド済みの `docs/` を外側から CDP で駆動するだけなので、被計測側だけを過去のコミットへ
戻せる:

```
# 現在のコードを測る
npm run build && node tools/perf-probe.mjs

# 過去のコミットを測る(プローブは現在の版のまま)
git restore --source=<commit> --worktree src/ && npm run build && node tools/perf-probe.mjs
git restore --worktree src/
```

環境変数:

| 変数 | 既定 | 意味 |
|---|---|---|
| `PERF_REPEATS` | 3 | 条件ごとに、ページ読み込みからやり直す回数。行ごとにラウンド間中央値を採る |
| `PERF_SAMPLES` | 10 | 1ラウンド内で `PerfMeter` を読む回数 |
| `PERF_INTERVAL_MS` | 500 | 読み取り間隔(`PerfMeter` の flush 周期と同じ) |
| `PERF_SETTLE_MS` | 3000 | ワープ・ビュー・表示期間を整えてから測り始めるまでの待ち |
| `PERF_ONLY` | — | label 部分一致(数字境界で区切る)で条件を絞る |
| `PERF_OUT` | — | 結果 JSON の書き出し先 |

**本メモのベースライン**(第1章の表):

```
PERF_ONLY='stage1-combat-warp65536,stage1-map,creative-map-warp65536,debug-load-map-warp1' \
PERF_REPEATS=5 node tools/perf-probe.mjs
```

### 読み方の規約(v3 から引き継ぐ)

1. **1条件1回の ms はいかなる比較にも使えない。** 同一ビルドのラウンド間で ±60〜80%
   食い違った実績がある。必ず `PERF_REPEATS` の中央値と振れ幅を併記して読む。
2. **ms を run 間で直接比べてはいけない。** 同じ run の中でも条件をまたいでマシン速度が
   1.5〜2倍動く。A/B するときは、**触っていないはずの行**(離散カウンタが前後で完全一致する
   条件、例えば `積分`)を対照に取り、比で正規化する。
3. **暦キャッシュの hit/miss は 500ms の実時間窓あたりの差分**なので、fps が違う run 間では
   比べられない。フレームあたりに直してから比べる。
4. **予測を触る変更は、必ず予測対象が多い条件で測る。** 既存の stage1 系は予測対象が最大7体
   しかなく、予測側の変更はほぼ見えない。`debug-load-map-warp1`(小惑星300 + 破片500、
   マップビュー)が唯一まともに効く条件。

## 1-2. B-3(自艦を複数置いたときの頂点バッファ)— 測らずに決着した

`TrajectoryLine` は `Curve` に `maxVertices = 16384` を渡す。`Curve` が1本につき確保するのは:

| バッファ | 型 | 量 | 置き場 |
|---|---|---|---|
| `positions` | Float32Array(V×3) | 192 KB | CPU + GPU |
| `bakedLocal` | Float64Array(V×3) | **384 KB** | CPU のみ |
| `indices` | Uint32Array((V−1)×2) | 128 KB | CPU + GPU |
| 計 | | **704 KB / 本** | うち GPU 側 320 KB |

`MAX_PLACED_SHIPS = 50` まで置くと **34.4 MB**(GPU 側 15.6 MB)。過去線も出す設定なら倍。

**v3 の「頂点バッファだけ約 10MB」は `positions` しか数えておらず、最大項の `bakedLocal`
(Float64、`positions` の2倍)を落としていた。** 実際は約3.4倍ある。

これは静的に決まる値なので、計測条件を組む必要はない。**懸案としては閉じる**が、
自艦を多数置く運用を許すなら `maxVertices` の見直しが要る(1本 16384 頂点は、
`Curve` の適応分割が実際に使う数よりかなり大きい)。

## 1-3. B-2(外挿タイルの焼き直し)— 頻度は導出できる

`TrajectoryLine.syncGeometry` は、外挿区間を持つ間、
**`|to − 前回焼いた to| >= 外挿1サンプルぶんの間隔`** になったら焼き直す。
`to = simTime + duration` は毎フレーム `simDt` だけ動くので、
**焼き直しは `simDt >= サンプル間隔` になった段で毎フレームになる。**

予測列のサンプル間隔は `max(局所周期 / 32, horizon / 2000)`。LEO(周期 5578s)では:

| 表示期間 | サンプル間隔 | ×1 | ×1024 | ×65536 |
|---|---|---|---|---|
| 1周(既定) | 174.3s | 174秒毎 | 2フレーム毎 | **毎フレーム** |
| 1日 | 174.3s | 174秒毎 | 2フレーム毎 | **毎フレーム** |
| 7日 | 302.4s | 302秒毎 | 3フレーム毎 | **毎フレーム** |
| 28日 | 1209.6s | 1210秒毎 | 12フレーム毎 | **毎フレーム** |

1回の焼き直しが払うサンプル数(先端が全く伸びていない最悪時、`MAX_EXTRAPOLATED_SAMPLES`
= 2048 で頭打ち)は、1周 32 / 1日 496 / 7日 2001 / 28日 2001。
**各サンプルにつき `ephemeris.stateOf` が1回**で、しかもサンプル時刻はすべて異なるので
**暦のリングキャッシュ(32スロット)は原理的に当たらない。** さらに bake 側で
`frameTransformAt` + `toFrameState` が同数走る。

**このコストは `update` ではなく `sync` フェーズに乗る。** v3 の表は `update` 中心だったので
見えていなかった。→ 実測は 1-1 の `stage1-map-warp{1024,65536}-dur28d` の `sync` 行。

## 1-4. 【新規・純リファクタ】先端時刻側の空間分類は、作って丸ごと捨てている

`Predictor.advanceBudget` は1ステップにつきこう書かれている:

```
currentClassified = classifyAttractors(predictedAttractorsAt(..., tipState.t))  // ソート + SpatialGrid 構築
currentAttractors = attractorsNearInto(tipState.r, currentClassified, ..., selfId) // 27近傍の切り出し
rawCenter = strongestAttractor(tipState.r, currentAttractors)                    // ← 使うのはこの1つだけ
```

`currentClassified` / `currentAttractors` は `rawCenter` を出すためだけに作られ、
その後どこからも読まれない。**グリッドを作ってから線形走査するのは、
元の配列をそのまま線形走査するより常に高い。**(64天体の μ 比較 + 49件のグリッド挿入 +
27セルの参照を払って、最後に十数件を走査している。)

**答えが変わらないことの根拠**(ただしレジストリ非依存の定理ではない)。
`attractorAccel` は2項ある:

- **直達項 `μ/d²`** — 27近傍から外れた grid 天体は定義上1セル以上離れており、
  セル一辺は `√(最重グリッド μ / GRAVITY_NEGLIGIBLE_ACCEL)` なので `1e-8 m/s²` 未満。
  セル論法でそのまま抑えられる。
- **ECI 原点補正項 `μ_b/|r_b|²`** — これは問い合わせ位置 p ではなく**地球からの距離**で
  決まるので、セル論法の外にある。別に潰す必要がある。

現レジストリ(grid 最重 = トリトン μ=1.428e12)で後者を潰すと:

| p の位置 | `always` の太陽の寄与 | grid 天体がそれを超えるのに必要な「地球からの距離」 |
|---|---|---|
| 地球 | 5.93e-3 | 0.02e9 m 以内 |
| 木星 | 2.19e-4 | 0.08e9 m 以内 |
| 海王星 | 6.59e-6 | 0.47e9 m 以内 |
| セドナ遠日点 | 7.32e-9 | 13.97e9 m 以内 |

地球から 1e9 m 以内(月軌道 3.84e8 m の数倍圏内)に居る重力源は地球と月だけで、
どちらも `always`(μ順 6位・14位)。**よって現レジストリに反例は無い。**
`GRAVITY_ALWAYS_COUNT` を下げたり重い天体を新規登録したりすると崩れうるので、
実装時は assert で1周ぶん確かめてから落とす(第3章 第1段)。

なお `GRAVITY_ALWAYS_COUNT = 15` に対して**月は μ 順で14位**(ガニメデ・タイタン・
カリスト・イオが月より重い)。CLAUDE.md の「1ランクの余裕」は正しい。

## 1-5. 【新規・整合性】乖離判定の窓だけ μ=0 の37天体を含んでいる

`Predictor` の中で窓の定義が食い違っている:

- `update`(乖離判定): `classifyAttractors(ephemeris.attractorsAt(simTime))` = **全101天体**
- `advanceBudget`(伸長): `predictedAttractorsAt` → `gravityAttractorsAt` = **重力源64体**

`attractorAccel` は両項とも `μ` を掛けるので μ=0 の37天体は厳密に `v3(0,0,0)` を返す。
`always` の顔ぶれもセル一辺も変わらない(μ=0 は上位15にも最重グリッドにもならない)ので、
**揃えても挙動は厳密に同一。**

ただし**性能効果は小さい**。μ=0 の37体は TNO と外惑星の不規則衛星が主で、
セル一辺 1.195e10 m(27近傍で ±0.12 AU)の中へ地球近傍から入るものはまず無い。
**減るのは毎フレーム37件のグリッド挿入だけで、個体あたりの `attractorAccel` は減らない。**
性能項目ではなく、Predictor の中で窓の定義が2つある状態を残さないための修正として扱う。

## 1-7. 【決着】低ワープで `pred-steps` が 0 なのは正しい

v3 が「辻褄が合わない」として未特定のまま残した項目。刻み幅の修正後、
**先端はホライズンを最大 `dt` だけ越えて止まる。** 既定プリセットの LEO では
`dt = max(20, 5578/600, 5578/20000) = 20s`。×1 では `simDt ≈ 0.0167s` なので、
**次の1歩が要るまで 1200 フレーム(実時間 20 秒)かかる。**
プローブのサンプル窓は約5秒なので、ほぼ全フレームで 0 歩になる。

**測定値 0 は正しく、異常ではない。** v3 が疑問視したのは修正前のコードの挙動で、
そのコードはもう無い。使い捨て計装は不要で、この項目は閉じる。

## 1-9. 積分幅の3項は落とせない(v3 の結論をそのまま引き継ぐ)

床(20s)・周期項・分配項の3項はそれぞれ互いに素な領域を担当していて、代替できない。
物理側のコードはマージで変わっていないので、v3 の実験結果はそのまま有効:

- 3項すべてがどこかで採用値になっており、死んでいる項は無い。
- **床 20s を釘付けているのは LEO ではなく低月周回。** LEO の誤差は dt=20 で 0.29m
  (閾値 500m に対し1700倍の余裕)だが、低月周回は dt=20 で既に 419m(閾値の84%)。
  これは RK4 の打ち切り誤差ではなく中心天体を中点で凍結することによる dt² 誤差なので、
  床を 25s にするだけで破綻する。
- 離心軌道(モルニヤ)では周期項が定数刻みをパレート優位で上回る(3.6倍安く精度は同等、
  同コスト帯の定数刻みは誤差が79倍)。
- ゲーム側 A/B では、周期項を落とすと `update` が 10.2倍になる。

**副産物として残っている問題**: 28日プリセットの予測線は遠端で **13,500 km** ずれている
(地球半径より大きい)。分配項が総ステップ数を 20,000 に抑えるため dt=121s を強い、
435周を46歩/周で刻んだ結果。破棄閾値(この条件では 69.6km)を超えているのに**破棄されない** —
乖離判定が見るのは `at(simTime)` すなわち列の先頭付近で、遠端の誤差は `simTime` がそこへ
達しない限り誰も検査しない。**静かに間違った線が描かれている。**(第2章 判断5)

# 第2章 必要な判断

判断の**小さい順**に並べる(第3章の作業順と対応する)。「小さい」は影響範囲ではなく、
**決めるのに要る情報の量と、間違えたときの取り返しやすさ**で測る。

## 判断1: 先端時刻側の空間分類を落とすことを、レジストリ依存の前提のまま認めるか

第1章 1-4 の純リファクタ。挙動が変わらないことは**現レジストリでは確かめられるが、
レジストリに依らない定理ではない**(原点補正項がセル論法の外にある)。

選択肢:

- **(a) 落とす。** 実装時にデバッグビルドで「絞った窓の最強 == 全窓の最強」を assert し、
  全条件を1周流して反例が出ないことを確認してから外す。**恒久的な条件分岐は残さない** —
  分岐を残すと判定が複雑になるうえ、前提が崩れたときに気づけない。
- (b) 落とさず、`GRAVITY_ALWAYS_COUNT` を増やして前提を強くしてから落とす。
  `always` を増やすと全個体の毎ステップ走査が増えるので、本末転倒になりやすい。
- (c) 触らない。

**私の見立ては (a)。** 作って捨てているのが確実な計算であり、
残しておく理由が「証明が registry 非依存でない」ことだけなら、assert で担保すれば足りる。

## 判断2: A-1(予測の暦解決を1ステップ1回)にいま着手するか

1ステップにつき `predictedAttractorsAt` を開始時刻と中点時刻の2回引いている。
v2 の実験5-D で「6/7 regime でビット単位一致したまま解決回数がちょうど半分になる」ことは
確認済みで、以後**一度も着手されていない**。

判断が要るのは残る 1/7 regime — 刻み幅を「1歩前の中点で解決済みの重力源」から決めると、
月のように速く動く天体の近傍で刻み幅がわずかにずれる。**位置そのものはずれない**
(積分に渡す重力源は今までどおり中点で解決する)ので、影響は刻み幅の選び方だけ。

判断1 を先に入れると、この2回のうち**1回目が `strongestAttractor` 1回だけになる**ので、
A-1 の実装も測定も単純になる。**順序は判断1 → 判断2 で固定してよい。**

## 判断3: `predictedAsPlanCollider` を実際に読ませるか(v2 から未決のまま持ち越し)

宣言だけあって誰も読んでいない状態が続いている。現状は「予測列を持っている物体が
たまたま計画の衝突体になる」という副作用で決まり、**弾・自艦・基地・弾薬が計画線の
終端相手になっている**。目に見える挙動変更なので判断が要る。

私の見立ては v2/v3 から変わらず「読ませるべき」。計画線が弾で終端するのは仕様として

## 判断4: 予測要否のフレーム可変ゲートの範囲(A-4 の前段)

# 第3章 今後の作業計画

**順序は「判断が小さい順」。** 効果の大きい順ではない。理由は2つ:

- **捨てているだけの計算は、判断を要さずに落とせる。** 先に落としておくと、
  以後の測定でその分のノイズが消える。
- **キャッシュと積分幅は最後。** 積分幅を落とせば数字が良くなるのは分かっているが、
  先にやると他の問題が見えなくなる。キャッシュは、上の変更を入れた後に
  **どの呼び出し経路が残るか**が確定しないと実装可否を判断できない。

### 第1段: 先端時刻側の空間分類を落とす 【判断1 承認後 / 純リファクタ】

`Predictor.advanceBudget` の `classifyAttractors` + `attractorsNearInto` を、
先端時刻側だけ落として `strongestAttractor` を窓へ直接かける。

- **条件を足さない。** 「重力の合成に使う窓」と「最強天体を1つ選ぶための窓」が
  別物であるという1点だけを反映する。分岐やフラグは増やさない。
- 検証: デバッグビルドで両者の一致を assert し、全条件を1周流して反例0を確認。
- 計測: `pred-steps` が前後で**完全一致**すること(歩数は変わらないはず)。
  変わったら実装が間違っている。`予測 ms` と `eph-all miss` が下がる。
- 併せて `Predictor.update` の乖離判定窓を `gravityAttractorsAt` へ揃える
  (第1章 1-5、挙動は厳密に同一。性能効果は小さいが、Predictor の中で窓の定義が
  食い違っている状態を残さない)。

### 第2段: A-1 — 予測の暦解決を1ステップ1回にする 【判断2 承認後】

刻み幅の決定を、1歩前の中点で解決済みの重力源から行う。第1段の後なら、
1回目の解決は `strongestAttractor` しか使っていないので置き換えが単純。

計測: `debug-load-map-warp1` と `stage1-map-warp65536` の `予測 ms`。
`pred-steps` は変わらないはず。**`予測` を `積分` で正規化して読む**(読み方の規約2)。

### 第3段: `predictedAsPlanCollider` を読ませる 【判断3 承認後】

挙動変更なので、性能ではなく仕様として入れる。計画線の終端相手が

### 第4段: A-4(予算の崖)と、そのための可変ゲート 【判断4・判断5 と同じ変更セット】

サンプル間隔の決め方を見直す**方向で考える(条件を複雑にしない)。

### 第6段: A-0(積分の天体窓)【判断が最も大きい】

最大項。中身は「サブステップごとに、その中点時刻で全重力源の窓を組み直している」ことで、
中点時刻は毎回ユニークなので**暦のリングキャッシュは原理的に当たらない**。
ここを触ると精度の議論に直結するので最後。
