# 計画・予測の負荷改善 v4 — 残っている判断と注意点

---

# 第1章 注意点(再発防止)

## 1-1. 空間分類は「1回組んで多数の点で使い回す」ときだけ得になる

`classifyAttractors` + `attractorsNearInto` は**計算量オーダーを下げるための道具**であって、
1点あたりを速くする最適化ではない。重力源 N 体を M 点で総当たりすると O(NM) だが、分類を
1回だけ払えば以降は各点が `always` の本数と自セル近傍の密度しか見ないので N に依らなくなる。

- 分類1回のコストは **`alwaysThresholdMu` の μ 全ソート**に支配され O(N log N)。
  `SpatialGrid` 自体は3段ネストの `Map` で、挿入も27近傍参照も実質 O(1)。
- したがって **1点ごとに分類し直す使い方は、O(N) の線形走査を O(N log N) へ置き換えるだけで
  常に損**になる。1点しか引かないなら窓をそのまま走査する。

現状どの経路が成立条件を満たしているか:

| 経路 | 1回の分類を何点で使い回すか | 成立 |
|---|---|---|
| `Simulator.substep` | サブステップ中点で1回、そのサブステップの全エンティティ | ○ |
| `Predictor.update` の乖離判定 | フレームに1回、全対象 | ○ |
| `Predictor.advanceBudget` の中点評価 | 1歩1点 | **×** |
| `PlanArc.integrateTo` | 1歩1点(時刻一致の4スロット保持で歩あたり2回へ緩和) | **×** |

**× の2経路は、分類を落とせる余地が残っている。** 先端時刻側は落とし済みだが、中点側は
まだ歩ごとに分類している。落とすと絞り込みが消えるので、RK4 の1ステージで合算する項が
`always` + 近傍から窓全体(64体)へ増える。**どちらが安いかは未測定。**

## 1-2. 予測そのものは依然 O(NM) で、オーダー改善の余地が残る

分類を落としても、M 個体の予測を伸ばすのに N 体の重力源を総当たりする構造は変わらない。
先端時刻が個体ごとに違う以上、`Simulator` のような共有はそもそも成立しない。

**これはフレーム時間ではなく「予測が完成しないこと」として現れる。** 1フレームの伸長は
`PREDICT_STEP_BUDGET` で頭打ちなので、O(NM) は消費フレーム数へ転嫁される — 表示期間を
延ばすか個体数を増やすと `pred-complete` が 0 のままになる(第2章 2-1 がまさにこれ)。
**表示個体数を増やす方向へ進むなら、予測アルゴリズム側にオーダー改善が要る。**

## 1-3. エンティティ0体の計測が意味するもの

`creative ×65536 艦なし` は `軌道積分` = 0(積分したエンティティ数ゼロ)で `積分` 190.6ms。
これは**情報を捨てている問題ではない** — エンティティ0体はゲーム中ほぼ起こらないので、
0体を分岐で早期 return してもコードが煩雑になるだけで軽量化にならない。

正しい読み方は「**1回の窓構築はエンティティ数に比例しないオーバーヘッドであり、
0体の条件はそのオーバーヘッド量を単独で測る手段として有効**」。対処はオーバーヘッド自体の
軽量化か `SUBSTEP_MAX_DT` の調整であって、0体分岐ではない。

`substeps` = 328 は `simDt / SUBSTEP_MAX_DT` = 6553/20 で決まり、中点時刻は毎サブステップ
一意なので**暦のリングキャッシュは原理的に当たらない**(`eph-all miss` 149,568 ÷ 328
= 456 リング操作/substep)。

## 1-4. ケプラー外挿の中心天体は先端より古い

`DynamicTrajectory.step` は先端を進めた**後**に `extrapolationCenter` を記録するので、
中心天体の状態は先端より1歩ぶん古い。加えて `Predictor.advanceBudget` が中心天体を
1歩前の中点で解決した窓から選ぶため、半歩ぶん上乗せされる。

地球中心(ECI 原点に静止)では誤差ゼロ。月中心では dt=20s で数十 km 相当。
**外挿は先端より先の表示にしか使われない**ので現状は許容しているが、外挿の精度を
問題にするときはここを疑うこと。

## 1-5. 積分幅の3項(床・周期項・分配項)は落とせない

3項はそれぞれ互いに素な領域を担当していて代替できない。実験済み:

- 3項すべてがどこかで採用値になっており、死んでいる項は無い。
- **床 20s を釘付けているのは LEO ではなく低月周回。** LEO の誤差は dt=20 で 0.29m
  (閾値 500m)だが、低月周回は dt=20 で既に 419m(閾値の84%)。これは RK4 の打ち切り誤差
  ではなく中心天体を中点で凍結することによる dt² 誤差なので、床を 25s にするだけで破綻する。
- 離心軌道(モルニヤ)では周期項が定数刻みをパレート優位で上回る(3.6倍安く精度は同等、
  同コスト帯の定数刻みは誤差が79倍)。
- ゲーム側 A/B では、周期項を落とすと `update` が 10.2倍になる。

## 1-6. フレームを跨いで使い回す構造に「生涯累計」の上限を付けてはいけない

窓を滑らせながら生き続ける構造(`PlanArc` がそれ)に生涯累計のステップ上限を付けると、
どれだけ余裕を取っても有限フレームで必ず上限へ達し、そこから恒久的に伸びなくなる。
描く窓は進み続けるので、線は縮んでいって二度と戻らない — 第2章 2-1 の予測と同じ症状が、
破棄ではなく打ち切りという別の顔で出る。

上限は**1回の呼び出しに対して**置き、使い切っても打ち切らずに次の呼び出しへ続きを回す。
恒久的な打ち切りは物理的な終端(表面接触・焼失・非有限)と、収束していないことが
その場で判る場合(予算を使い切って先端がサンプル1つぶんも進まない)だけに残す。

## 1-7. 1フレームの時間送りが窓の長さを超えるワープでは、使い回しは原理的に成立しない

×65536 では `simTime` が1フレームで数千秒進む。表示期間が「1周」(LEO で約5580s)なら、
窓は毎フレーム丸ごと入れ替わる — 先端を継ぎ足して末尾を捨てる操作が窓全体の作り直しと
同じ量になるので、**使い回しても積分ステップ数は減らない。**

効くのは「窓の長さ ≫ 1フレームの時間送り」の条件だけ(28日プリセット × 高ワープなど)。
`plan-steps` を条件間で比べるときは、まずこの比を見ること。ある条件で減らないのは
実装の不備ではなく、その条件では減りようがないことがある。

## 1-8. 計測の読み方

1. **1条件1回の ms はいかなる比較にも使えない。** 同一ビルドのラウンド間で ±60〜80%
   食い違った実績がある。必ず `PERF_REPEATS` の中央値と振れ幅を併記して読む。
2. **ms を run 間で直接比べてはいけない。** 同じ run の中でも条件をまたいでマシン速度が
   1.5〜2倍動く。A/B するときは、触っていないはずの行(離散カウンタが前後で完全一致する
   条件、例えば `積分`)を対照に取り、比で正規化する。
3. **暦キャッシュの hit/miss は 500ms の実時間窓あたりの差分**なので、fps が違う run 間では
   比べられない。フレームあたりに直してから比べる。
4. **予測を触る変更は、必ず予測対象が多い条件で測る。** stage1 系は予測対象が最大7体しか
   なく、予測側の変更はほぼ見えない。`debug-load-map-warp1`(小惑星300 + 破片500、
   マップビュー)が唯一まともに効く条件。
5. `map ×1` の弾数はラウンドごとに 48〜165 発と違い、`sim-orbit` と `接触` がそれに
   引きずられる。この条件で ±10% 未満の差は読めない。
6. `map ×65536 node1` の `plan-steps` はノードをどこへ置いたかで約212か約424に割れる
   (実機の性質であってバグではない)。A/B の対照に使うならプローブ側で時刻を固定する。
7. `plan-steps` は区間を作り直したフレームと継ぎ足しただけのフレームで桁が違う。
   `plan-arcs`(作り直した本数)と必ず対で読む。

# 第2章 残っている問題

**この章の数値はすべて現在のコードより前のもの。次に手を入れる前にベースラインを取り直すこと。**

## 2-1. A-4 — 予算の崖(予測が伸び切らない)【判断4・判断5】

`map ×65536` は `pred-discard` 6 / `pred-complete` 0 / `pred-steps` 458 が avg・max とも一致
= **毎フレーム破棄して伸ばし直している**。`map ×1 28日` も `pred-complete` 0/7。

**B-2(外挿タイルの毎フレーム焼き直し)はこの症状のひとつ**で、独立した問題ではない。
`TrajectoryLine.syncGeometry` は `to` の移動と**保持列の配列参照の変化**の2つで焼き直すが、
支配しているのは後者 — 予測が伸び続けると `samplesOldestFirst()` が毎フレーム新しい配列を
返す。`map ×1 28日` の `sync` が 7.3 → 72.1ms になるのはこれ。**先に焼き直し側へ条件を
足すと症状を隠すだけになる**ので、A-4 と同じ変更セットで測り直す。

**判断4(予測要否のフレーム可変ゲート)**:

- (i) 予測線を描いていない個体だけ止める
- (ii) 表示時刻が現在を指している間は `predictedForGhost` を成立させない

(ii) の代償は外挿が入ったことで軽くなっている(止めた個体もスライダを引いた瞬間に位置は
答えられる)。ただし A-4 本体を直す前にゲートだけ入れると「足りない個体が減ったので崖が
見えにくくなった」だけになりうる。**A-4 の測り直しと同じ変更セットで判断する。**

**判断5(長い表示期間の扱い)**: 長い表示期間の予測は、粗すぎる(分配項あり)か
伸び切らない(分配項なし)かのどちらかで、現状どちらも成立していない。
(a) A-4 と一緒に解く / (b) 遠端を「精度保証外」として明示的に描き分ける /
(c) 選べる期間の上限を下げる。**A-4 の結論が出るまで決められない。**

計画側にも同じ判断が要る。末尾区間は選んだ表示期間の終端まで届くようになったが、その間
`PLAN_ARC_MAX_STEPS` ぶんのステップを何フレームか連続で払う(LEO・28日で概算3フレーム、
1年なら約29フレーム)。**この過渡的なコストを許すのか、長い期間だけ別扱いにするのかは
判断5 と同じ枠**で、予測側の結論と揃えて決める。

検証の指標: `map ×1 28日` の `sync` 72.1ms と `pred-complete` 0/7 が**対で**動くこと。
`sync` だけ下がって `pred-complete` が 0 のままなら症状を隠しただけ。

## 2-2. 28日プリセットの予測線は遠端で 13,500 km ずれ、しかも破棄されない

地球半径より大きい。分配項が総ステップ数を 20,000 に抑えるため dt=121s を強い、435周を
46歩/周で刻んだ結果。破棄閾値(この条件では 69.6km)を超えているのに破棄されないのは、
乖離判定が見るのが `at(simTime)` すなわち列の先頭付近だから — 遠端の誤差は `simTime` が
そこへ達しない限り誰も検査しない。**静かに間違った線が描かれている。**(判断5 と同じ根)

## 2-3. A-0 — 積分の天体窓 【判断が最も大きい・最後】

定常的な最大項(`creative ×65536 艦なし` で 190.6ms)。中身は 1-3 のとおり
「サブステップごとに、その中点時刻で全重力源の窓を組み直している」こと。
`substeps` は `simDt / SUBSTEP_MAX_DT` で決まるので、ここを触ると精度の議論に直結する。

## 2-4. 自艦を複数置いたときの頂点バッファ

`TrajectoryLine` は `Curve` に `maxVertices = 16384` を渡す。1本あたり:

| バッファ | 型 | 量 | 置き場 |
|---|---|---|---|
| `positions` | Float32Array(V×3) | 192 KB | CPU + GPU |
| `bakedLocal` | Float64Array(V×3) | **384 KB** | CPU のみ |
| `indices` | Uint32Array((V−1)×2) | 128 KB | CPU + GPU |
| 計 | | **704 KB / 本** | うち GPU 側 320 KB |

`MAX_PLACED_SHIPS = 50` まで置くと **34.4 MB**(GPU 側 15.6 MB)。過去線も出す設定なら倍。
静的に決まる値なので計測は不要。自艦を多数置く運用を許すなら `maxVertices` の見直しが要る
(1本 16384 頂点は `Curve` の適応分割が実際に使う数よりかなり大きい)。

# 第3章 作業順

**判断の小さい順**(効果の大きい順ではない)。キャッシュと積分幅は、上の変更を入れた後に
**どの呼び出し経路が残るか**が確定しないと実装可否を判断できない。

1. **A-4 と、その症状である B-2**(2-1 / 判断4・判断5)。`pred-complete` が 0 のままなら
   degradation を持たせる設計(足りない個体の列を全損させない)へ進む。2-2 もここで決める。
2. **A-0**(2-3)。判断が最も大きいので最後。
3. **中点側の空間分類を落とすかの測定**(1-1 の × 2経路)。落とすと合算する項が増えるので、
   先に他の変更を入れて残る呼び出し経路を確定させてから測る。
4. **論点C(線が船体から離れる/振動する)**。A-4 が直って破棄が止まってから。

## やらないこと(棄却済み。棄却理由ごと再掲する)

- **`always`/`grid` で重力源の更新頻度を分ける** — 重い天体だけを毎ステップ、軽い天体を
  数ステップおきに更新する案。棄却理由は、`always` に入る天体こそ動きが速い(月・木星の
  衛星群)ため、頻度を落として良いのは**位置ではなく質量順で決まらない**こと。据え置き時間を
  1つ足すと「どの天体を、どれだけ古い位置で積分したか」が経路ごとに散る。
- **予測列と計画列を統合する** — どちらも `DynamicTrajectory` なので1本にまとめる案。
  棄却理由は、予測が「実状態から乖離したら破棄して伸ばし直す」列であるのに対し、計画は
  「凍結したアンカーから決まる」列で、**無効化の条件が正反対**であること。1本にすると、
  どちらの無効化条件も他方にとって誤りになる。
- **`horizon` を個体ごとに変える** — 遠くの個体は短く予測すれば足りる、という案。棄却理由は、
  `horizon` が表示期間そのものであり、個体ごとに変えると**同じ表示時刻に対して個体ごとに
  違う未来を描く**ことになる(ゴーストの位置が揃わない)。
- **`PREDICT_STEP_BUDGET` を上げる** — 予算を増やして伸長を間に合わせる案。棄却理由は、
  崖(A-4)の原因が予算の絶対量ではなく**分配と破棄の繰り返し**にあること。上げると1フレームの
  最悪値が伸びるだけで、`pred-complete` は 0 のまま。
- **刻み幅の3項のどれかを定数へ簡略化する** — 3項それぞれを落として物理・ゲーム両面で測り、
  いずれも落とせないことを確認済み(1-5)。
- **ノードなしの計画区間の長さを表示期間から切り離す / 長い期間では計画線を出さない** —
  棄却理由は、どちらも性能のために表示を削る判断であること。同じ絵を安く出す道
  (区間の使い回し)が先にあった。

# 付録 計測の再現手順

**ビルドとプローブは別々に差し替えられる。** プローブ(`tools/perf-probe.mjs`)はビルド済みの
`docs/` を外側から CDP で駆動するだけなので、被計測側だけを過去のコミットへ戻せる:

```
# 現在のコードを測る
npm run build && node tools/perf-probe.mjs

# 過去のコミットを測る(プローブは現在の版のまま)
git restore --source=<commit> --worktree src/ && npm run build && node tools/perf-probe.mjs
git restore --worktree src/
```

環境変数:

| 変数 | 既定 | 意味 |
|---|---|---|
| `PERF_REPEATS` | 3 | 条件ごとに、ページ読み込みからやり直す回数。行ごとにラウンド間中央値を採る |
| `PERF_SAMPLES` | 10 | 1ラウンド内で `PerfMeter` を読む回数 |
| `PERF_INTERVAL_MS` | 500 | 読み取り間隔(`PerfMeter` の flush 周期と同じ) |
| `PERF_SETTLE_MS` | 3000 | ワープ・ビュー・表示期間を整えてから測り始めるまでの待ち |
| `PERF_ONLY` | — | label 部分一致(数字境界で区切る)で条件を絞る |
| `PERF_OUT` | — | 結果 JSON の書き出し先 |

ベースラインを取り直すときのコマンド:

```
PERF_ONLY='stage1-combat-warp65536,stage1-map,creative-map-warp65536,debug-load-map-warp1' \
PERF_REPEATS=5 node tools/perf-probe.mjs
```

`PERF_ONLY` のトークンは数字境界で部分一致するので、`stage1-map` は
`stage1-map-warp1-dur28d` / `-warp1024-dur28d` / `-warp65536-dur28d` / `-warp1-orbitoff`
にも一致し、結果として11条件を測る。

未測定のまま残っている条件: `stage00-map-warp1` / `stage00-map-warp1-orbitoff`
(波状攻撃で敵が増えたときの軌道線の draw call。settle 20秒 × 5ラウンドで時間がかかる)。

`map ×65536 28日` は1フレームが秒オーダーあり、プローブの1リクエスト上限
(`REQUEST_TIMEOUT_MS` = 30s)に対して余裕が少ない。5ラウンド中1ラウンドが完走しないことが
あるので、**この条件の ms は「桁」として読むこと。**

計測環境として残っている宿題:

| 項目 | 内容 |
|---|---|
| A/B のマシン速度ドリフト | 条件をラウンドごとに交互に回す(A→B→A→B)プローブにすれば、対照で正規化する手間自体が要らなくなる。ビルドを2つ同時に配信する必要があるので、静的サーバを2ポート立てる改造が要る |
