## 計測の前提 — 条件と再現手順

**ビルドとプローブは別々に差し替えられる。** プローブ(`tools/perf-probe.mjs`)は
ビルド済みの `docs/` を外側から CDP で駆動するだけなので、被計測側だけを過去のコミットへ
戻せる:

```
# 現在のコードを測る
npm run build && node tools/perf-probe.mjs

# 過去のコミットを測る(プローブは現在の版のまま)
git restore --source=<commit> --worktree src/ && npm run build && node tools/perf-probe.mjs
git restore --worktree src/
```

環境変数:

| 変数 | 既定 | 意味 |
|---|---|---|
| `PERF_REPEATS` | 3 | 条件ごとに、ページ読み込みからやり直す回数。行ごとにラウンド間中央値を採る |
| `PERF_SAMPLES` | 10 | 1ラウンド内で `PerfMeter` を読む回数 |
| `PERF_INTERVAL_MS` | 500 | 読み取り間隔(`PerfMeter` の flush 周期と同じ) |

| `PERF_ONLY` | — | label 部分一致(数字境界で区切る)で条件を絞る |
| `PERF_OUT` | — | 結果 JSON の書き出し先 |

### 読み方の規約(v3 から引き継ぐ)

1. **1条件1回の ms はいかなる比較にも使えない。** 同一ビルドのラウンド間で ±60〜80%
   食い違った実績がある。必ず `PERF_REPEATS` の中央値と振れ幅を併記して読む。
2. **ms を run 間で直接比べてはいけない。** 同じ run の中でも条件をまたいでマシン速度が
   1.5〜2倍動く。A/B するときは、**触っていないはずの行**(離散カウンタが前後で完全一致する
   条件、例えば `積分`)を対照に取り、比で正規化する。
3. **暦キャッシュの hit/miss は 500ms の実時間窓あたりの差分**なので、fps が違う run 間では
   比べられない。フレームあたりに直してから比べる。
4. **予測を触る変更は、必ず予測対象が多い条件で測る。** 既存の stage1 系は予測対象が最大7体
   しかなく、予測側の変更はほぼ見えない。`debug-load-map-warp1`(小惑星300 + 破片500、
   マップビュー)が唯一まともに効く条件。

## 1-3. 【最大の新発見】28日プリセット × 高ワープで、計画を毎フレーム全区間積分し直す

`map ×65536 28日` の `計画` は **12,208 ms/frame**。`plan-steps` は **20,000** ちょうど、
すなわち `PLAN_ARC_MAX_STEPS` の上限に貼り付いている。`plan-arcs` = 1 なので、
**区間が毎フレーム作り直されている。**

同じ ×65536 でも 1周プリセット(`node0`)は `計画` 129.2ms / `plan-steps` 209。
**ステップ比 20000/209 = 95.7 に対し ms 比 12208/129.2 = 94.5** で、
1ステップあたりの単価はプリセット間で一致する。内部整合が取れているので、
これは測定の異常ではなく実際にその回数積分している。

**なぜ毎フレーム作り直すのか。** ノードが1つも無いとき、計画の唯一の区間は起点(`state0`)が
**生きている自機を毎フレーム追う**。`PlanArc.represents` はこの場合だけ
「アンカーの時刻ドリフトが現在のサンプル間隔未満なら作り直さない」という閾値判定に落ちる。
×65536 では `simTime` が毎フレーム 6553s 進むので、**どのサンプル間隔よりも大きく、
必ず作り直しになる。**

**これは v3 が直した問題とは別の経路である。** v3 第1段は「`planEnd` が simTime 追従値
だったせいで世代値が毎フレーム動く」を直した(ノードあり = `node1` の経路)。
いま出ているのは**ノードなし = `node0` の経路**で、世代値ではなくアンカー追従の
閾値判定が原因。`node0` は1周プリセットでも `plan-arcs` = 1 / `plan-steps` = 209 と
毎フレーム作り直しており、**28日プリセットはその1回を95倍高くしただけ。**

`eph-all miss` が 3,823,993/500ms なのも、この再積分が1ステップにつき開始・中点・終了の
3時刻を引くことで説明がつく。**同じ ×65536 の他条件(142,809〜207,986)の 18〜27倍**で、
低ワープの条件(456〜3,496)とは3桁違う。

**測定上の注意**: この条件は1フレーム 12.6 秒なので、プローブの1リクエスト上限
(`REQUEST_TIMEOUT_MS` = 30s)に対して余裕が少なく、5ラウンド中1ラウンドが完走できなかった
(`attempts` に `None` が1つ)。**この条件の ms は「桁」として読み、±62% の振れ幅を
そのまま受け入れること。**

## 1-4. A-0(積分の天体窓)— 消費者ゼロで 190ms 払っている

`creative ×65536 艦なし` の内訳が、この問題を最も純粋な形で見せている:

| 行 | 値 |
|---|---|
| `積分` | **190.6 ms** |
| `軌道積分`(実際に積分したエンティティ数) | **0** |
| `substeps` | 328 |
| `eph-all miss` | 149,568 |

**エンティティが1体も居ないのに、積分だけで 190ms 使っている。**
`Simulator.substep` は毎サブステップこうなっている:

```
sources    = attractorsAt(ephemeris, entities, simTime + dt/2)  // 中点時刻で全重力源64体を組む
classified = classifyAttractors(sources)                        // μ でソート + SpatialGrid 構築
for (const e of this.entities.all()) { ... }                    // ← ここが空
```

**窓を組んでから、誰が読むかを見ている。** 328 サブステップぶんの窓構築と分類が、
このケースでは丸ごと捨てられる。`eph-all miss` 149,568 ÷ 328 substeps = **456 リング操作/substep**
で、しかも中点時刻は毎サブステップ一意なので**リングキャッシュは原理的に当たらない**。

エンティティが居る通常のプレイでは窓は必要なので、これは「無駄な計算」ではなく
**「サブステップ数 × 窓構築コスト」という設計そのもの**の問題である。
`substeps` = 328 は `simDt / SUBSTEP_MAX_DT` = 6553/20 で決まり、
`SUBSTEP_MAX_DT` を触ることは精度の議論に直結する。**だから第3章では最後に置く。**

## 1-5. 【新規・純リファクタ】先端時刻側の空間分類は、作って丸ごと捨てている

`Predictor.advanceBudget` は1ステップにつきこう書かれている:

```
currentClassified = classifyAttractors(predictedAttractorsAt(..., tipState.t))  // ソート + SpatialGrid 構築
currentAttractors = attractorsNearInto(tipState.r, currentClassified, ..., selfId) // 27近傍の切り出し
rawCenter = strongestAttractor(tipState.r, currentAttractors)                    // ← 使うのはこの1つだけ
```

`currentClassified` / `currentAttractors` は `rawCenter` を出すためだけに作られ、
その後どこからも読まれない。**グリッドを作ってから線形走査するのは、
元の配列をそのまま線形走査するより常に高い。**(64天体の μ 比較 + 49件のグリッド挿入 +
27セルの参照を払って、最後に十数件を走査している。)

**答えが変わらないことの根拠**(ただしレジストリ非依存の定理ではない)。
`attractorAccel` は2項ある:

- **直達項 `μ/d²`** — 27近傍から外れた grid 天体は定義上1セル以上離れており、
  セル一辺は `√(最重グリッド μ / GRAVITY_NEGLIGIBLE_ACCEL)` なので `1e-8 m/s²` 未満。
  セル論法でそのまま抑えられる。
- **ECI 原点補正項 `μ_b/|r_b|²`** — これは問い合わせ位置 p ではなく**地球からの距離**で
  決まるので、セル論法の外にある。別に潰す必要がある。

現レジストリ(grid 最重 = トリトン μ=1.428e12)で後者を潰すと:

| p の位置 | `always` の太陽の寄与 | grid 天体がそれを超えるのに必要な「地球からの距離」 |
|---|---|---|
| 地球 | 5.93e-3 | 0.02e9 m 以内 |
| 木星 | 2.19e-4 | 0.08e9 m 以内 |
| 海王星 | 6.59e-6 | 0.47e9 m 以内 |
| セドナ遠日点 | 7.32e-9 | 13.97e9 m 以内 |

地球から 1e9 m 以内(月軌道 3.84e8 m の数倍圏内)に居る重力源は地球と月だけで、
どちらも `always`(μ順 6位・14位)。**よって現レジストリに反例は無い。**
`GRAVITY_ALWAYS_COUNT` を下げたり重い天体を新規登録したりすると崩れうるので、
実装時は assert で1周ぶん確かめてから落とす(第3章 第1段)。

なお `GRAVITY_ALWAYS_COUNT = 15` に対して**月は μ 順で14位**(ガニメデ・タイタン・
カリスト・イオが月より重い)。CLAUDE.md の「1ランクの余裕」は正しい。

## 1-6. 【新規・整合性】乖離判定の窓だけ μ=0 の37天体を含んでいる

`Predictor` の中で窓の定義が食い違っている:

- `update`(乖離判定): `classifyAttractors(ephemeris.attractorsAt(simTime))` = **全101天体**
- `advanceBudget`(伸長): `predictedAttractorsAt` → `gravityAttractorsAt` = **重力源64体**

`attractorAccel` は両項とも `μ` を掛けるので μ=0 の37天体は厳密に `v3(0,0,0)` を返す。
`always` の顔ぶれもセル一辺も変わらない(μ=0 は上位15にも最重グリッドにもならない)ので、
**揃えても挙動は厳密に同一。**

ただし**性能効果は小さい**。μ=0 の37体は TNO と外惑星の不規則衛星が主で、
セル一辺 1.195e10 m(27近傍で ±0.12 AU)の中へ地球近傍から入るものはまず無い。
**減るのは毎フレーム37件のグリッド挿入だけで、個体あたりの `attractorAccel` は減らない。**
性能項目ではなく、Predictor の中で窓の定義が2つある状態を残さないための修正として扱う。

## 1-7. B-2(外挿タイルの焼き直し)— 頻度は導出できる

`TrajectoryLine.syncGeometry` は、外挿区間を持つ間、
**`|to − 前回焼いた to| >= 外挿1サンプルぶんの間隔`** になったら焼き直す。
`to = simTime + duration` は毎フレーム `simDt` だけ動くので、
**焼き直しは `simDt >= サンプル間隔` になった段で毎フレームになる。**

予測列のサンプル間隔は `max(局所周期 / 32, horizon / 2000)`。LEO(周期 5578s)では:

| 表示期間 | サンプル間隔 | ×1 | ×1024 | ×65536 |
|---|---|---|---|---|
| 1周(既定) | 174.3s | 174秒毎 | 2フレーム毎 | **毎フレーム** |
| 1日 | 174.3s | 174秒毎 | 2フレーム毎 | **毎フレーム** |
| 7日 | 302.4s | 302秒毎 | 3フレーム毎 | **毎フレーム** |
| 28日 | 1209.6s | 1210秒毎 | 12フレーム毎 | **毎フレーム** |

1回の焼き直しが払うサンプル数(先端が全く伸びていない最悪時、`MAX_EXTRAPOLATED_SAMPLES`
= 2048 で頭打ち)は、1周 32 / 1日 496 / 7日 2001 / 28日 2001。
**各サンプルにつき `ephemeris.stateOf` が1回**で、しかもサンプル時刻はすべて異なるので
**暦のリングキャッシュ(32スロット)は原理的に当たらない。** さらに bake 側で
`frameTransformAt` + `toFrameState` が同数走る。

**このコストは `update` ではなく `sync` フェーズに乗る。** v3 の表は `update` 中心だったので
見えていなかった。

### 実測 — 焼き直しの主因は `to` の移動ではなく「予測がまだ伸びていること」だった

`sync` の実測:

| 条件 | sync | 表示期間 | `pred-complete` / `pred-tracked` |
|---|---|---|---|
| `map ×1 node0` | 7.3 | 1周 | 7 / 7 |
| `map ×1 28日` | **72.1** | 28日 | **0 / 7** |
| `map ×1024 28日` | 41.5 | 28日 | **0 / 9** |
| `map ×65536 28日` | 39.1 | 28日 | **0 / 6** |

(`map ×1024 28日` は 1-2 の表に載せていない条件。`予測` 174.7ms / `pred-steps` 472 /
`substeps` 6 / `eph-all miss` 163,921。)

**28日プリセットは ×1 でも sync を 7.3 → 72.1ms へ押し上げる。**
上の導出は「×1 なら 1210 秒に1回」と予測したので、**これは導出と食い違う。**

原因は焼き直しの引き金が2つあることを見落としていたため。`syncGeometry` は
**保持列の配列参照が変わったときにも焼き直す**。28日プリセットでは予測が予算を飽和させて
永久に伸び続ける(`pred-complete` 0 / `pred-steps` 415)ので、`samplesOldestFirst()` が
**毎フレーム新しい配列を返し**、`to` の移動条件を待たずに毎フレーム焼き直しになる。

**つまり `to` 側の条件は実質どうでもよく、支配しているのは「予測が伸び切らないこと」。**
B-2 は独立した問題ではなく、**A-4(予算の崖)の症状のひとつ**だった。
A-4 が直って予測が伸び切れば、配列参照は止まり、`to` 側の条件だけが残って
低ワープでは 1210 秒に1回まで落ちる。**第3章では B-2 を単独の段として持たず、
A-4 と同じ変更セットで測り直す。**

## 1-8. B-3(自艦を複数置いたときの頂点バッファ)— 測らずに決着した

`TrajectoryLine` は `Curve` に `maxVertices = 16384` を渡す。`Curve` が1本につき確保するのは:

| バッファ | 型 | 量 | 置き場 |
|---|---|---|---|
| `positions` | Float32Array(V×3) | 192 KB | CPU + GPU |
| `bakedLocal` | Float64Array(V×3) | **384 KB** | CPU のみ |
| `indices` | Uint32Array((V−1)×2) | 128 KB | CPU + GPU |
| 計 | | **704 KB / 本** | うち GPU 側 320 KB |

`MAX_PLACED_SHIPS = 50` まで置くと **34.4 MB**(GPU 側 15.6 MB)。過去線も出す設定なら倍。

**v3 の「頂点バッファだけ約 10MB」は `positions` しか数えておらず、最大項の `bakedLocal`
(Float64、`positions` の2倍)を落としていた。** 実際は約3.4倍ある。

これは静的に決まる値なので、計測条件を組む必要はない。**懸案としては閉じる**が、
自艦を多数置く運用を許すなら `maxVertices` の見直しが要る(1本 16384 頂点は、
`Curve` の適応分割が実際に使う数よりかなり大きい)。

## 1-9. 【v3 の誤り】軌道線は既定で「出ている」

`DEFAULT_BODY_CLASS_TOGGLES` は
`playerOrbit: true` / `shipOrbit: true` / `ammoOrbit: true` / `baseOrbit: true`。
既定オフなのは `dwarfOrbit` / `satelliteOrbit` / `smallBodyOrbit` の3つだけで、
**しかもこれはマージベースの時点で既にそうだった**(main の変更ではない)。

v3 の B-4「敵の軌道線は既定で非表示なので、線の生成をやめても draw call は動かなかった」は
**前提が誤り**。実際は元から描かれている。v3 の A/B で `draw-calls` が一致したのは
両ビルドとも同じだけ描いていたからで、**結論(効きは頂点バッファの確保であって描画コスト
ではない)は変わらないが、理由が違う。**

実測(stage1、敵5体、基地0、マップビュー ×1):

| | draw calls |
|---|---|
| 既定(敵・基地・弾薬の軌道線オン) | 338 |
| 敵・基地・弾薬の軌道線をオフ | **333** |

**差は 5、敵の数とちょうど一致する。**(弾薬は `EntityManager.syncOrbitLines` が
敵と基地しか回さないので、そもそも線を持たない。)描画されていなければ切っても
変わらないはずなので、この5本ぶんが**元から描かれていた**ことの直接の証拠になる。

1本 = 1 draw call なので、敵の多いステージでは素直に効く。
`stage00` の波状攻撃で敵が数十体になる条件は今回のマトリクスに入れたが未測定
(1条件あたり settle 20秒 × 5ラウンドで時間がかかるため次回へ回す)。

`CLAUDE.md` も同じ誤りを書いている(「Defaults: every `Orbit` flag off except
`planetOrbit`」)。実コードへの影響がある作業はまだしない方針なので本メモでは直していない
(第2章 判断6)。

プローブ側は「押す」のではなく「その状態にする」実装に直した(`setOrbitLineFor`)。
トグルなので、押すこと自体を目的にすると初期値が変わったときに逆を向く。

## 1-10. 【決着】低ワープで `pred-steps` が 0 なのは正しい

v3 が「辻褄が合わない」として未特定のまま残した項目。刻み幅の修正後、
**先端はホライズンを最大 `dt` だけ越えて止まる。** 既定プリセットの LEO では
`dt = max(20, 5578/600, 5578/20000) = 20s`。×1 では `simDt ≈ 0.0167s` なので、
**次の1歩が要るまで 1200 フレーム(実時間 20 秒)かかる。**
プローブのサンプル窓は約5秒なので、ほぼ全フレームで 0 歩になる。

**測定値 0 は正しく、異常ではない。** v3 が疑問視したのは修正前のコードの挙動で、
そのコードはもう無い。使い捨て計装は不要で、この項目は閉じる。

## 1-11. 【決着】`npm run test:physics` の2件の失敗はマージで解消した

v3 の時点で `occlusion: マップ上の見かけ半径を基準に2Rから1.5Rでフェードする` と
`visibility policy: 操作対象の自機はカテゴリを閉じても位置を失わない` が失敗していた。
main が両方を修正しており、マージ後は **426/426 通過**。

## 1-12. 積分幅の3項は落とせない(v3 の結論をそのまま引き継ぐ)

床(20s)・周期項・分配項の3項はそれぞれ互いに素な領域を担当していて、代替できない。
物理側のコードはマージで変わっていないので、v3 の実験結果はそのまま有効:

- 3項すべてがどこかで採用値になっており、死んでいる項は無い。
- **床 20s を釘付けているのは LEO ではなく低月周回。** LEO の誤差は dt=20 で 0.29m
  (閾値 500m に対し1700倍の余裕)だが、低月周回は dt=20 で既に 419m(閾値の84%)。
  これは RK4 の打ち切り誤差ではなく中心天体を中点で凍結することによる dt² 誤差なので、
  床を 25s にするだけで破綻する。
- 離心軌道(モルニヤ)では周期項が定数刻みをパレート優位で上回る(3.6倍安く精度は同等、
  同コスト帯の定数刻みは誤差が79倍)。
- ゲーム側 A/B では、周期項を落とすと `update` が 10.2倍になる。

**副産物として残っている問題**: 28日プリセットの予測線は遠端で **13,500 km** ずれている
(地球半径より大きい)。分配項が総ステップ数を 20,000 に抑えるため dt=121s を強い、
435周を46歩/周で刻んだ結果。破棄閾値(この条件では 69.6km)を超えているのに**破棄されない** —
乖離判定が見るのは `at(simTime)` すなわち列の先頭付近で、遠端の誤差は `simTime` がそこへ
達しない限り誰も検査しない。**静かに間違った線が描かれている。**(第2章 判断5)

# 第2章 必要な判断

判断の**小さい順**に並べる(第3章の作業順と対応する)。「小さい」は影響範囲ではなく、
**決めるのに要る情報の量と、間違えたときの取り返しやすさ**で測る。

## 判断1: 先端時刻側の空間分類を落とすことを、レジストリ依存の前提のまま認めるか

第1章 1-5 の純リファクタ。挙動が変わらないことは**現レジストリでは確かめられるが、
レジストリに依らない定理ではない**(原点補正項がセル論法の外にある)。

選択肢:

- **(a) 落とす。** 実装時にデバッグビルドで「絞った窓の最強 == 全窓の最強」を assert し、
  全条件を1周流して反例が出ないことを確認してから外す。**恒久的な条件分岐は残さない** —
  分岐を残すと判定が複雑になるうえ、前提が崩れたときに気づけない。
- (b) 落とさず、`GRAVITY_ALWAYS_COUNT` を増やして前提を強くしてから落とす。
  `always` を増やすと全個体の毎ステップ走査が増えるので、本末転倒になりやすい。
- (c) 触らない。

**私の見立ては (a)。** 作って捨てているのが確実な計算であり、
残しておく理由が「証明が registry 非依存でない」ことだけなら、assert で担保すれば足りる。

## 判断1.5: 28日プリセット × 高ワープの 12.6 秒/frame を「不具合」として先に潰すか

第1章 1-3。**これは性能の劣化ではなく、その設定でゲームが成立していない**
(1フレーム 12.6 秒)。他の項目が数十〜数百 ms の話をしているのに対して桁が3つ違う。

順序の原則は「判断の小さい順」だが、**これだけは順序の外に置いて先に潰す**という
選択肢がある。判断が要るのはそこで、直し方そのものにも選択肢がある:

- **(a) ノードなしの区間を作り直さず、伸ばして使い回す。** アンカーが前へ滑っただけで
  軌道は同じなので、先端を継ぎ足して末尾を捨てれば済む。`PlanArc.setEnd` の継ぎ足しは
  既にあるので、`represents` がアンカー追従の場合に false を返す条件を見直す形になる。
  **最も筋が良いが、「どこまでのドリフトなら同じ軌道とみなすか」を決める必要がある。**
- (b) ノードなしの計画区間の長さを表示期間から切り離す。28日ぶん引く必要があるのは
  ノードを置いた先の話で、ノードなしなら現在の軌道を1周ぶん見せれば足りる、という立場。
- (c) 表示期間が長いときは計画線を出さない。いちばん安いが、見えるものが減る。

**私の見立ては (a)。** (b)(c) は見えるものを変えるので、性能のために表示を削る判断になる。
(a) は同じ絵を安く出す話で、しかも「同じ軌道なのに作り直している」という
**計算の無駄そのもの**に対応している。

ただし (a) は閾値の設計を含むので、判断1(純リファクタ)より判断は大きい。
**「不具合として先に潰す」を採るなら順序の外、そうでないなら判断2 の後。**

## 判断2: A-1(予測の暦解決を1ステップ1回)にいま着手するか

1ステップにつき `predictedAttractorsAt` を開始時刻と中点時刻の2回引いている。
v2 の実験5-D で「6/7 regime でビット単位一致したまま解決回数がちょうど半分になる」ことは
確認済みで、以後**一度も着手されていない**。

判断が要るのは残る 1/7 regime — 刻み幅を「1歩前の中点で解決済みの重力源」から決めると、
月のように速く動く天体の近傍で刻み幅がわずかにずれる。**位置そのものはずれない**
(積分に渡す重力源は今までどおり中点で解決する)ので、影響は刻み幅の選び方だけ。

判断1 を先に入れると、この2回のうち**1回目が `strongestAttractor` 1回だけになる**ので、
A-1 の実装も測定も単純になる。**順序は判断1 → 判断2 で固定してよい。**

## 判断3: `predictedAsPlanCollider` を実際に読ませるか(v2 から未決のまま持ち越し)

宣言だけあって誰も読んでいない状態が続いている。現状は「予測列を持っている物体が
たまたま計画の衝突体になる」という副作用で決まり、**弾・自艦・基地・弾薬が計画線の
終端相手になっている**。目に見える挙動変更なので判断が要る。

私の見立ては v2/v3 から変わらず「読ませるべき」。計画線が弾で終端するのは仕様として
説明できない。

## 判断4: 予測要否のフレーム可変ゲートの範囲(A-4 の前段)

- (i) 予測線を描いていない個体だけ止める
- (ii) 表示時刻が現在を指している間は `predictedForGhost` を成立させない

(ii) の代償は、外挿が入ったことで**軽くなっている** — 止めた個体もスライダを引いた瞬間に
位置は答えられる(精度は落ちる)。ただし A-4 本体(予算の崖)を直す前にゲートだけ入れると、
「足りない個体が減ったので崖が見えにくくなった」だけになりうる。**A-4 の測り直しと同じ
変更セットで判断する。**

## 判断5: 28日プリセットをどう扱うか

長い表示期間の予測は、**粗すぎる(分配項あり・遠端 13,500km ずれ)か、伸び切らない
(分配項なし)かのどちらか**で、現状どちらも成立していない。これは刻み幅の調整では解けず、
A-4(予算の崖)と同じ根を持つ。

選択肢: (a) A-4 と一緒に解く / (b) 長い期間では線の遠端を「精度保証外」として明示的に
描き分ける / (c) 選べる期間の上限を下げる。**A-4 の結論が出るまで決められない。**

## 判断6: 文書の誤りをいつ直すか

`CLAUDE.md` の「Defaults: every `Orbit` flag off except `planetOrbit`」は誤り
(第1章 1-9)。実コードへの影響がある作業はまだしない方針なので本メモでは直していない。
**次に `src/` を触る変更セットに含める**か、独立した文書修正として先に出すかの判断。
軽微なので、独立して先に出すのが素直。

# 第3章 今後の作業計画

**順序は「判断が小さい順」。** 効果の大きい順ではない。理由は2つ:

- **捨てているだけの計算は、判断を要さずに落とせる。** 先に落としておくと、
  以後の測定でその分のノイズが消える。
- **キャッシュと積分幅は最後。** 積分幅を落とせば数字が良くなるのは分かっているが、
  先にやると他の問題が見えなくなる。キャッシュは、上の変更を入れた後に
  **どの呼び出し経路が残るか**が確定しないと実装可否を判断できない。

### 第1段: 先端時刻側の空間分類を落とす 【判断1 承認後 / 純リファクタ】

`Predictor.advanceBudget` の `classifyAttractors` + `attractorsNearInto` を、
先端時刻側だけ落として `strongestAttractor` を窓へ直接かける。

- **条件を足さない。** 「重力の合成に使う窓」と「最強天体を1つ選ぶための窓」が
  別物であるという1点だけを反映する。分岐やフラグは増やさない。
- 検証: デバッグビルドで両者の一致を assert し、全条件を1周流して反例0を確認。
- 計測: `pred-steps` が前後で**完全一致**すること(歩数は変わらないはず)。
  変わったら実装が間違っている。`予測 ms` と `eph-all miss` が下がる。
- 併せて `Predictor.update` の乖離判定窓を `gravityAttractorsAt` へ揃える
  (第1章 1-6、挙動は厳密に同一。性能効果は小さいが、Predictor の中で窓の定義が
  食い違っている状態を残さない)。

### 第1.5段: ノードなしの計画区間を作り直さず使い回す 【判断1.5 承認後・順序の外もありうる】

第1章 1-3。`map ×65536 28日` の `計画` 12,208ms / `plan-steps` 20,000 を潰す。
判断1.5 の (a) を採るなら、`PlanArc.represents` の「アンカー追従時の作り直し判定」を
見直す。

- **条件を増やさない。** いま `represents` はアンカー追従のときだけ閾値判定に落ちている。
  そこを差し替えるのであって、別のフラグや経路を足さない。
- 計測: `map ×65536 28日` の `plan-steps` が 20,000 → 0 になること、
  `map ×65536 node0` の 209 → 0 も同時に落ちること。
  **`plan-arcs` が 0 にならないなら作り直しが残っている。**
- 退行の確認: `map ×1 node0` / `node1` の `plan-steps` は元から 0 なので**動いてはいけない**。
  描かれる線が同じであることは目視でも確かめる(1周プリセットで自機の直前・直後)。

### 第2段: A-1 — 予測の暦解決を1ステップ1回にする 【判断2 承認後】

刻み幅の決定を、1歩前の中点で解決済みの重力源から行う。第1段の後なら、
1回目の解決は `strongestAttractor` しか使っていないので置き換えが単純。

計測: `debug-load-map-warp1` と `stage1-map-warp65536` の `予測 ms`。
`pred-steps` は変わらないはず。**`予測` を `積分` で正規化して読む**(読み方の規約2)。

### 第3段: `predictedAsPlanCollider` を読ませる 【判断3 承認後】

挙動変更なので、性能ではなく仕様として入れる。計画線の終端相手が
小天体だけになることを確認する。

### 第4段: A-4(予算の崖)と、その症状である B-2 【判断4・判断5 と同じ変更セット】

第2段で1歩あたりの単価が下がった後に測り直し、`pred-complete` が 0 のままなら
degradation を持たせる設計(足りない個体の列を全損させない)へ進む。

**B-2(外挿タイルの毎フレーム焼き直し)はここに含める。** 第1章 1-7 のとおり、
焼き直しを駆動しているのは `to` の移動ではなく「予測が伸び切らないので保持列の配列参照が
毎フレーム変わること」なので、A-4 が直れば自然に止まる。**先に焼き直し側へ条件を足すと、
A-4 の症状を隠すだけになる。**

28日プリセットの扱い(判断5)と、遠端 13,500km のずれ(第1章 1-12)もここで決める。

計測: `map ×1 28日` の `sync` 72.1ms と `pred-complete` 0/7 が対で動くこと。
`sync` だけ下がって `pred-complete` が 0 のままなら、症状を隠しただけ。

### 第5段: A-0(積分の天体窓)【判断が最も大きい】

最大項(`creative ×65536 艦なし` で 190.6ms、消費者ゼロ)。中身は「サブステップごとに、
その中点時刻で全重力源の窓を組み直している」ことで、中点時刻は毎回ユニークなので
**暦のリングキャッシュは原理的に当たらない**。`substeps` = 328 は

### やらないこと(過去の版で棄却済み。棄却理由ごと再掲する)

- **`always`/`grid` で重力源の更新頻度を分ける** — 重い天体だけを毎ステップ、軽い天体を
  数ステップおきに更新する案。棄却理由は、`always` に入る天体こそ動きが速い
  (月・木星の衛星群)ため、頻度を落として良いのは**位置ではなく質量順で決まらない**こと。
  据え置き時間を1つ足すと「どの天体を、どれだけ古い位置で積分したか」が経路ごとに散る。
- **予測列と計画列を統合する** — どちらも `DynamicTrajectory` なので1本にまとめる案。
  棄却理由は、予測が「実状態から乖離したら破棄して伸ばし直す」列であるのに対し、
  計画は「凍結したアンカーから決まる」列で、**無効化の条件が正反対**であること。
  1本にすると、どちらの無効化条件も他方にとって誤りになる。
- **`horizon` を個体ごとに変える** — 遠くの個体は短く予測すれば足りる、という案。
  棄却理由は、`horizon` が表示期間そのものであり、個体ごとに変えると
  **同じ表示時刻に対して個体ごとに違う未来を描く**ことになる(ゴーストの位置が揃わない)。
- **`PREDICT_STEP_BUDGET` を上げる** — 予算を増やして伸長を間に合わせる案。
  棄却理由は、崖(A-4)の原因が予算の絶対量ではなく**分配と破棄の繰り返し**にあること。
  上げると1フレームの最悪値が伸びるだけで、`pred-complete` は 0 のまま。
- **刻み幅の3項(床・周期項・分配項)のどれかを定数へ簡略化する** — 3項それぞれを
  落として物理・ゲーム両面で測り、いずれも落とせないことを確認済み(第1章 1-12)。
  物理側のコードはマージで変わっていないので、この結論はそのまま有効。
