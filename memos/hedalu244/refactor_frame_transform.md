# 座標は誰が持ち、どこで変換されるのか

**争点A〜E は決着し、2.4 の形まで実施した。残っているのは 2.5 の保留2件だけ。**
0〜3節の調査結果・行番号は **`1dfd2b33`** 時点の記録で、実施によって動いている。
`refactor_orbit_ephemeris.md` の論点2(キャッシュの持ち主)はここへ引き継いだ。

---

## 0. 方針(ここは決まっている)

- **天体1体が持つのは「自分がどこにいるか」であって、他天体との関係ではない。** 原点は
  **太陽系重心**へ揃える(衛星は主天体相対のまま)。いまの `'helio'` は「太陽を原点に釘付けに
  した解析系」で、厳密な日心を必要としている天体は1つも無い(→ 争点A)。
- **ECI は game 側の都合。** `DynamicSystem` が ECI を採るのは数値精度のため —
  f64 の絶対分解能(`r × 2⁻⁵²`)は日心距離 1.5e11 m で **33 µm**、地心距離 6.8e6 m で
  **1.5 nm** と4桁以上違う。physics/celestial にこの都合を持ち込まない。
- したがって **ECI 変換は game/celestial(あるいはそこが physics/frame へ委譲する形)で行い、
  `CelestialMotion` は ECI も原点天体も知らない。**
- **分担は「個体は `CelestialEntity`、集合は `CelestialSystem`」。** 1体ぶんの ECI 変換は
  `CelestialMotion` から `CelestialEntity` へ移し、**変換した結果を集めて配列にするのは
  `CelestialSystem`。** 変換と収集は別の操作で、前者だけが個体の仕事。
- **全天体が自分の位置をキャッシュしてよい。** ECI が要るときは「その天体の値」と
  「ECI 原点天体の値」を組み合わせる。**組み合わせるのは変換側の仕事で、天体側ではない。**

## 2. 争点

### 争点A. 共有の原点を太陽系重心にするか(**方針: する。残るのはタグの切り直し**)

**「厳密な日心」は今どこにも無い。** `StarMotion.helioStateAt`(`celestial-motion.ts:257`)は
恒星を厳密に 0 に固定して返す — 惑星による振り回しはモデルに入っていない。いまの `'helio'` は
「振り回しを考慮した太陽座標」ではなく**「太陽を原点に釘付けにした解析系」**で、これを必要と
している天体は恒星自身も含めて1つも無い。

**日心値を絶対位置として使っているのは src に2箇所だけ**(残りはすべて差分なので原点に依らない)。

- `PlanetMotion.helioAccelAt`(`:433`)— 二体加速度の r を「太陽→惑星」ベクトルとして使う。
- `PlanetSystem.helioStateAt`(`planet-system.ts:21`)— 系の重心の主天体相対を、そのまま
  日心として読み替える(「原点の読み替えはここでしか起きない」)。
- ほかにテストが1件(`tests/game/point-field.test.ts:77` が木星の日心黄経を見る)。

**ラベルの付け替えでは済まない。** JPL の公開要素は日心(SPEC/CELESTIAL.md 2.1「太陽まわりの
ケプラー楕円軌道」)。**「軌道の中心」と「座標の原点」は別物**で、要素の中心は太陽のまま。
重心を名乗るには**太陽の重心相対位置を解析側で組んで足す**必要がある — `−Σ(μ_i/μ_total)·r_i`、
惑星-衛星系で既にやっている重心補正と同じ式を恒星-惑星系へもう1段。循環はしない
(要素 → 日心位置 → 太陽の重心相対位置)。足さずにラベルだけ替えると、全惑星が
**93万 km**(実測。太陽半径の 1.34 倍)ずれる。

#### 原点を揃えても「供給源を混ぜてはいけない」制約は消えない(実測)

制約の理由は原点だけではない。**モデルが違う。** 暦パックは解析暦より正確だから存在するので、
恒星中心の相対位置で比べても(= 原点の違いを相殺しても)両者は食い違う:

| 天体 | 解析暦とパックの差 | 日心距離 |
| --- | --- | --- |
| 地球 | **1,184 km** | 0.985 au |
| 金星 | 3,228 km | 0.728 au |
| 水星 | 3,021 km | 0.389 au |
| 火星 | 48,581 km | 1.402 au |
| 木星 | 418,086 km | 5.220 au |

(`modern-2026-10y.epk`、元期 +30 日での実測。)原点の違い 93万 km に比べれば2〜3桁小さいが、
**ECI 原点の位置が 1,184 km ずれれば機体の軌道は破綻する。** 混ぜてはいけないことに変わりはない。

#### ここが本題 — 2つのタグは原点ではなく「供給源」を守っている

`toEci<F>`(`kinematic-state.ts:44`)は**同じ `F` 同士しか受け付けない**ので、
「パックの天体 + 解析の原点」はいま**型エラーになる。** つまり `'helio'` と `'barycentric'` は
原点を表しているつもりで、**実際には供給源(モデル)を表していて、それが不変条件の唯一の
型レベルの守り**になっている。

**原点を重心へ揃えて2つのタグを1つに畳むと、この守りが消える。** したがって:

| | 得る | 失う |
| --- | --- | --- |
| **原点を重心へ揃え、タグは供給源で切り直す**(例: `'analytic'` / `'packed'`。どちらも重心原点) | 守りたい不変条件と型が一致する。原点が1つになり、天体の口から「どの原点か」の分岐が消える | 解析側に太陽の重心相対位置を足す実装が要る(上記2箇所の直しを含む)。**ECI 値がビット単位で動く** — `celestial-eci-baseline` の固定値を書き換えることになる |
| **現状維持(原点2つ・タグ2つ)** | 何も動かない。値も動かない | タグが原点と供給源を兼ねているのが読み取れないままになる |

#### タグ空間はどうなるか(実装者が最初に当たる)

いまの `FrameTag`(`kinematic-state.ts:14`)は5つの札で**3つの別の概念**を兼ねている —
原点(`eci` / `helio` / `barycentric` / `primaryRel`)、供給源(`helio` = 解析、
`barycentric` = パック)、軸(`icrf` はパック復号の内側だけで使う ICRF 軸。`evaluator.ts` の
3箇所)。争点A の切り直しは **`'helio'` → `'analytic'`、`'barycentric'` → `'packed'`
(どちらも太陽系重心原点)** の改名で、`'primaryRel'` / `'eci'` / `'icrf'` はそのまま残る。

**`'primaryRel'` が供給源を持たないのは穴ではなく、意図した設計。** 守るべき不変条件は
「**絶対 − 絶対は供給源を揃える**」であって、「**絶対 + 相対は混ぜてよい**」— 実際
`SatelliteMotion.packedStateAt`(`celestial-motion.ts:515`)は**パックの惑星に解析の相対軌道を
足している**(SPEC/CELESTIAL.md 2.2「高精度データに含まれない天体は、解析暦が持つ惑星本体からの
相対軌道を、高精度な惑星本体の位置に足し込む」)。型もそう書けている — `toEci<F>` は同じ `F` を
要求し、`addPrimaryRelative<F>(primary: KS<F>, rel: KS<'primaryRel'>)` は `F` を問わない。
**`'primaryRel'` を供給源つきに割ってはいけない**(この段階的な精度向上を型で禁じてしまう)。

### 争点B. `CelestialBody` の ECI を型でどう守るか(**方針: 型引数化しない。無標 ECI をやめる**)

**`CelestialBody<F>` への型引数化は採らない。** 話がややこしくなるだけで、`CelestialBody` は
**「ECI 化した `CelestialEntity` のスナップショット」**という位置づけに固定する。だから中身は
ECI で統一されているべきで、原点を選べる型にする意味がない。

代わりに守るのは **`KinematicState` の「無標 = ECI」という既定**。`kinematic-state.ts:22` `:30` の
`F extends FrameTag = 'eci'` があるために、型引数を書き忘れたコードは黙って ECI を名乗る
(ファクトリのコメントが「書き忘れると暗黙に ECI を名乗ることになる」と自認している)。

**この既定を外しても、コンパイラが新しく捕まえるものは増えない** — 無標はもともと `'eci'` に
解決されるので、機械的に `<'eci'>` を補う書き換えは意味を変えない。得られるのは
**「ECI であること」がコードに書かれる**ことと、**新しいコードが黙って ECI へ落ちなくなる**こと。

**採るのは「ファクトリ `kinematicState()` の既定だけを外す」。** 型注釈側の
`KinematicState`(型引数なし)は ECI の短縮形として残す。

| | 直す箇所 | 得る |
| --- | --- | --- |
| **採用: ファクトリだけ既定を外す** | **262 箇所 / 66 ファイル**(src 76 / tests 186) | 文書化された失敗モード(**組み立て時**の書き忘れ)にちょうど当たる。読む側の `KinematicState` は ECI の短縮形として残る |
| 型もファクトリも既定を外す | 型注釈 497 + ファクトリ 262 = **759 箇所 / 92 ファイル** | すべての `KinematicState` が原点を明示する。**払う量に対して得るものが薄い** |
| 現状維持 | 0 | 無標がどの原点かはファイルを跨いで追うしかない |

既定の危険を自認しているコメントはファクトリ側にあり、事故が起きるのも組み立て時。
tests に 186 箇所ある偏りもここを分けると効く。

**この選択は強い確信に基づくものではない。** 実際に通してみて「読む側も明示したほうが
読みやすい」となったら、型注釈側も外す方向へ広げてよい — **逆方向(やめる)以外は後戻り
不要な変更**なので、着手者の判断で広げて構わない。

### 争点C. 2段変換をどう表現し、後段へどう渡すか

2つの段は**別の演算**であることをまず押さえる。

| | stage 1(天体 → ECI) | stage 2(ECI → 参照フレーム相対) |
| --- | --- | --- |
| 演算 | **平行移動だけ**(`toEci`、`kinematic-state.ts:47`)。軸は系全体で1つなので回転は起きない | **剛体運動**(`toFrameState`、`frame.ts:124`)。回転 `q` と角速度 `ω` が入る |
| 原点の出どころ | ECI 原点天体の**暦の値**。供給源(解析/パック)を相手と揃える義務がある | ECI 値。すべて同じ供給源から来ているので揃える義務は無い |
| 出力 | `KinematicState`(時刻を持つ) | `FrameKinematicState`(**時刻を持たない**、`frame.ts:80`) |

機体・役割トークンは **stage 1 と stage 2 の間から入ってくる**(ECI しか持たない)。
これが「2段」である理由そのもの。

#### C-1. 表現の形(**決着: 別モジュール2つを直列**)

**stage 1 と stage 2 は別のモジュールにし、2段変換はその直列接続で表す。** 上表の非対称
(平行移動 / 剛体運動、供給源を揃える義務の有無、時刻を持つ / 持たない)がそのまま型に出て、
**混ぜてはいけない変換が型に現れない** — 危険な組み合わせを書きようがなくなる。代償は
モジュールが1つ増えることだけ。

採らなかった案と、そちらを選ぶと残る問題:

- **同一クラスの2インスタンスを直列。** 型と語彙は1つで済むが、stage 1 のインスタンスが
  **`q` = 恒等・`ω` = 0 という使わない欄**を常に持ち、恒等回転の `qRotate` が
  「サブステップごと × 天体数」の経路に入る(未測定。無駄であることは確か)。さらに
  `FrameKinematicState` が時刻を持たないので、stage 1 の出力である ECI 値がエポックを落とす。
- **万能変換モジュール。** **経由地を間違えると桁落ちする** — LEO の機体(地心 7e6 m)を
  ECI ↔ 月相対で往復させるのに重心を経由すると、1.5e11 m の加減算を挟んで有効桁を
  4〜5桁落とす。加えて**供給源の制約は「損をする」ではなく「禁止」**(解析の原点 × パックの
  天体は誤り)なので、許される対と許されない対の判定をモジュールの内側へ抱え込むことになる。

#### C-2. 後段への渡し方(**決着: `ReferenceFrames` を game/celestial へ移す**)

表現をどう選んでも **stage 2(`ReferenceFrames`)は ECI 値を入力に取る。** しかも
`frameRotationAt`(`reference-frames.ts:96`)は**機体の ECI 状態と天体の状態を直接引き算する**
ので、天体側も任意の t で ECI を答えられなければならない。stage 1 は game/celestial にあるので、
**`ReferenceFrames` ごと game/celestial へ移す。** ECI を知る層が game に揃い、口が増えない。

採らなかった案: **ECI 値の解決口を注入する**(`FrameAnchorSource` と同じ形)。physics に
`ReferenceFrames` を残せるが、口が1つ増える。既存の `FrameAnchorSource.bodies` は
1フレームの固定時刻スナップショットで任意の t に答えられないので流用もできない
(`frame-anchors.ts:47`)。

**残る注意:** `frame.ts`(座標変換の純関数群)は physics に残る。`ReferenceFrames` だけが
game へ出るので、両者の距離が開く — `frame.ts` が `ReferenceFrames` を import しない
(循環を作らない)という現状の取り決めは、移動後も同じく守られる。

### 争点D. 変換器とキャッシュの持ち主(**決着**)

**変換器の正本は `CelestialSystem` が持つ。** いまの `eciOriginCache` の中身 —「その時刻の
ECI 原点天体の値と、どちらの供給源か」— は天体1体のものではないので、`CelestialMotion` から
外して系へ移す。

**天体1体ぶんの ECI キャッシュは `CelestialEntity` が持つ。** 消去法で決まる:

- **ECI 変換後の状態を知っている必要がある** → `CelestialMotion` は落ちる(方針により ECI を
  知らない)。
- **集合化する前である必要がある** → `CelestialSystem` は落ちる(系が扱うのは集合)。

**配り方は参照を結ぶ形にする(`bindEphemeris` と同型)。** 引数で渡す案は
「個体の状態を減らす」動機だったが、**個体は ECI キャッシュを持つのでどのみち状態を持つ** —
減らないので動機が立たない。加えて、ECI 値を引くのは個体の内側の深い場所
(`sync` から呼ばれる `sphere-entity.ts:85` / `point-entity.ts:139` `:181` /
`star-entity.ts:58` と、`referenceElementsAt` ほか `celestial-entity.ts` の6箇所)で、
`sync` の引数(`fo` / `displayTime` / `cameraSystem` / `star` / `graphics` / `style`)には
変換器が無い。引数で配ると**この経路すべてへ引数を通すことになる。**

**キャッシュが要るかどうかは別問題。** いまの `eciCache` の実測値(太陽系98体、合成した
引かれ方)は**積分パスでヒット率 0.6%**(hits 4 / misses 644)、**表示パスで 33.3%**
(hits 98 / misses 196)。積分パスで当たらないのは、上の集合キャッシュが同じ t を先に
弾いているため。ただし**中身は引き算1回ではなく、1体あたり2回の姿勢評価**
(`degree2At` と `atmosphereAt` がそれぞれ `orientationAt` を引く)を含むので、
消すと積分パスで姿勢評価が増える経路が生まれる。**持ち主が決まっただけで、
置くかどうかは移してから測る。**

参考(同じ計測での他のキャッシュ): `eciOriginCache` は積分 98.8% / 表示 99.0%(**必須**)、
`helioCache` 78.0% / 76.0%、`relCache` 63.8% / 66.2%、`allCache` 0% / 75.0%。
**`gravityCache` と `atmosphereCache` は構造上ヒットしえない** — `gravityAttractorsAt` を
引くのは `substep-celestial-bodies.ts:23` の1箇所だけで毎回違うサブステップ中点、
`atmosphereCelestialBodiesAt` は2箇所だが `simulator.ts:178` が `simTime`・
`substep-celestial-bodies.ts:27` が中点で t が体系的に食い違う。

### 争点E. 位置の原点を型で守れるか(**実測済み: 守れる。不可能な構造は無かった**)

**`KinematicState<F>` は既に原点で branded されている**(`kinematic-state.ts:14`)が、
**`.r` / `.v` を取り出した瞬間に素の `Vec3` へ落ちる。** これが唯一の漏れ口で、
`CelestialBody.accel` / `FrameTransform.origin` / 位置を `r: Vec3` で受ける physics の
8関数(`attractorAccel` / `strongestAttractor` / `nearestAtmosphereBody` / `localOrbitPeriod` /
`srpAccel` / `sunlitFactor` / `maxOccludedFraction` / `frameKinematicState`)/ `FloatingOrigin.r`
は、そこから流れ込んだ値を受けている。

#### `Vec3` そのものを型引数化する案は採らない

`Vec3` は src の 133 ファイル・800 箇所で使われ、**位置だけでなく向き・軸・角速度も同じ型**で
表している。型引数化すると `vec3.ts` の 14 関数すべてにアフィン代数の場合分け
(位置 − 位置 = 変位、位置 + 変位 = 位置、変位 + 変位 = 変位)が要り、しかも
「向き × 向きの外積」のような原点を持たない用途と混ざる。**波及が大きすぎる。**

#### 代わりに `KinematicState<F>` の `r` / `v` を branded にする(**実測: src 全体で6件**)

`r` / `v` の型を `Vec3 & { __originOf: F }` にして型検査を通したところ、**エラーは
`src` 全体で6件だけ**だった。組み立ての唯一の入口 `kinematicState<F>(t, r, v)` が
素の `Vec3` を受けて内側で札を付けるので、**構築側は1箇所も直さなくてよい**。読み出し側も
`FramedVec3<F>` は `Vec3` の部分型なので、既存の演算にそのまま渡せる。

出た6件の内訳(**どちらも直し方が分かっている。行き詰まる構造は無い**):

| 種類 | 箇所 | 中身 |
| --- | --- | --- |
| **アフィン代数で札が落ちる**(4件) | `celestial-motion.ts:462` `:463` / `orbit-solvers.ts:53` / `plan-editor.ts:413` | `addScaled(位置, 相対, w)` や `add(中心位置, 軌道上の相対)` のように「位置 ± 変位 = 位置」を書いている場所。`add` / `sub` / `addScaled` が素の `Vec3` を返すので札が落ちる。**再付与するか、この3関数へ「位置 ± 変位 = 位置」のオーバーロードを足す** |

区別は、この形で付けられる。

**着手は争点A の後。** タグの綴りそのものが争点A で変わる(原点 → 供給源)ので、先にやると
二度手間になる。

## 2.4 ここまでで決まった形

争点A〜E を合わせると、目指す形はこうなる。

- **`CelestialMotion`** — 自分の位置だけを答える。原点は太陽系重心(衛星は主天体相対)、
  タグは供給源(解析 / パック)で切る。**ECI も原点天体も知らない。**
- **stage 1 の変換器**(新設)— 「天体の値 → ECI」の平行移動だけを行う。**供給源を揃える
  不変条件はここに閉じる。** 正本は `CelestialSystem` が持ち、`CelestialEntity` へ参照を結ぶ
  (`bindEphemeris` と同型)。純粋な値操作なので、型そのものは physics 側へ置いて
  game/celestial が組み立てる形にできる(方針の「physics/frame へ委譲する形」)。
- **`CelestialEntity`** — 変換器を使って**自分の** ECI 値を答える。1体ぶんの ECI キャッシュも
  ここが持つ(置くかどうかは移してから測る)。
- **`CelestialSystem`** — 個体が変換した結果を**集めて配列にする**。集合のキャッシュもここ。
- **stage 2** — `frame.ts`(純関数)は physics に残す。`ReferenceFrames` は
  **game/celestial へ移す**(C-2)。ECI 値を入力に取り、参照フレーム相対へ剛体変換する。
- **`KinematicState<F>` の `r` / `v`** — 原点(供給源)で branded にする。素の `Vec3` へ
  落ちる漏れ口を塞ぐ唯一の場所(E)。
- **`CelestialBody`** — 「ECI 化した `CelestialEntity` のスナップショット」として ECI 固定。
  型引数化しない。

## 2.5 別作業へ回すもの

### `FrameAnchors` の文字列キー(**保留**)

`FrameAnchors.attractorOf`(`src/game/frame-anchors.ts:31-32`, `:54-58`)は
フレーム番号・id・時刻を繋いだ**文字列キー**で直近1件を憶える — 毎フレーム走る経路に
文字列生成が入っている。この整理とは独立の別件で、**まず実測**し、効いていて
なお重いならもっといい持ち方を探して差し替える。効いていなければ消す。


### なぜ `CelestialBody`(スナップショット)が要るのか

争点B は「スナップショットである」ことを前提に型の守り方を決めただけで、**そもそも凍結した
値を配る必要があるのか**は別の問い。ここから疑うと変更が大規模になるので、別作業にする。

いま凍結している理由(コードから):

- **積分の各段で暦を引き直さないため。** `attractorAccel`(`celestial-body.ts:79`)と
  `dynamics.ts:131` は、スナップショットの `state.t` と `accel` から
  `celestialBodyPositionAt` で**その段の時刻へ2次外挿**する。凍結をやめると
  「天体数 × RK4 の段数」だけ暦の評価が走る。
- **1サブステップぶん配るため。** `SubstepCelestialBodies` が重力源・表面・大気の3組を
  区間の中で1組だけ組み、多数の個体がそれを共有する。

つまりスナップショットは「1時刻で凍結し、近傍時刻へ安く外挿できる形」であって、
**天体1体が自分で答えられること**とは別の要求。疑うなら、この2つの要求を別の形で
満たせるかから始める。
