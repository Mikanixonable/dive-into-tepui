# 方針

- トップレベルの適切なオーケストレーション化
  main.tsやgame.tsに実装が直接書かれるべきでない
- 関数、モジュールの疎結合化と責務の整理
  - 過剰責務（モジュールや関数が長すぎる）の解消
  - 過小責務（たらいまわし配線のみの関数、モジュール）の削除、解体、統合
  - 責務漏洩（この処理はこの関数にあるべきでない。この関数はこのモジュールにあるべきでない）の整理
- 重複実装、類似実装の解消、コード、値を適切に再利用する
- 不適切な命名の解消
- 不要なクロージャ注入は行わない。特定のオブジェクトに影響を及ぼしたいならそのmutableなオブジェクトを直接渡す。関数の引数にオブジェクトを作るのは柔軟性が高い反面、複雑なクロージャー関係が生まれて可読性を下げる。
- 場当たり的なオブジェクト引数の禁止。ctxやcontext、opt、paramsなどの引数は原則使わない。STOP_USING_CTX.mdを参照。

判断基準そのものは `/refactor`（一般方針）と `/refactor-fixed`（確定した責務境界）が正本。

このファイルは **todo リスト**であり、経緯を残す場所ではない。完了した項目は消す。

## コメント方針の是正
全体的にコメントの質が冗長な方向に劣化しています。

例えば、stepPredictionの周囲には、Predictor側の責務に言及したコメントや「dt を切り詰めて horizon ちょうどに着地させない」のように従来実装との変更点を示した否定形のコメントが書かれています。また、historyDurationに対するコメントは、継承先のShipでどのように使われているかが書かれていますが、これもGameEntityの責務ではなく、Shipの責務だから、書くべきではありません。

各関数にはそれが「なにをするか」「どのように使えばよいか」が簡潔なコメントとして書かれているべきで、「どのように実装されているか」「なにをしないか」「誰が使うか」「現状どのように使われているか」「過去の実装でなにをしていたか」はcontextを圧迫するので一切書くべきではないです。

関数内の実装に対しては「現状なぜそのように実装されているのか」が**相当に**非自明であるときにはそれをコメントで書くべきです。
相当に非自明というのは、複雑な計算式や複雑な実装、特殊な条件分岐がある場合などです。過去に複雑だった実装が簡潔に置き換わった実装に対しては、歴史的経緯をコメントで書くべきではありません。

特にこのようなコメントはリファクタリングや変更要求でコードを書き換える際にどんどん増えていく傾向にあります。リファクタリングは物事をよりシンプルにするために行っていて、過去の複雑な実装の経緯を知らなくても理解できるようにするのがリファクタリングの目的です。過去の複雑な実装の経緯をコメントで書いても利益がありません。

悪しきコメントを書くなということはrefactor/SKILL.mdにも書いてあります。こんなコメントを書くなとあなたに繰り返し言ってきましたが、効果がありません。また、再発を防止するため、コメントの方針、コメントのクリンナップ方針をSKILLにし、常時参照するようにしてください。

次に、現状のコードに対してコメントのクリンナップを行います。あくまでも機械的な目安ですが、モジュール先頭の責務宣言については5行、関数に対しては3行、関数内の処理については1行が目安です。複数行に連続したコメントを検索し、コメント方針（機械的な行数基準ではない、意味上の基準）に基づいて判断し、冗長であれば適切な粒度のコメントに置き換えてください。


## 参照共有を明示する命名規則
モジュールのプライベートフィールドに外部のモジュールがある場合について、そのインスタンスの保持責務を持つモジュール（コンストラクタでnewしていることなどが判断材料）と、外部から受け取って参照コピーだけ保持しているモジュールがある。これらは明確に区別できなければいけない。参照だけ保持している例において、それが外部で変更されることが重要である場合には、そもそも参照を保持するのではなく、引数で受け取るべきである。
