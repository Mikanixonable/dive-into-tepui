# 高時間加速時の「計画」「予測」負荷の調査

対象: `workspace4` HEAD=`8d7e1db1`。報告された症状は「65536倍速で『計画』約60ms、『予測』約90ms」。

## 結論(先に)

**再現した。報告値より重い。そして調べた結果、問われた2つより大きい第3の問題が同じ原因で出ている。**

**根本原因は1つ**: `Ephemeris` を**毎回異なる時刻で評価するコスト(1回 177〜283 µs)**。
これが3か所で独立に、時間加速に比例した回数だけ呼ばれている。

| 場所 | ×65536・マップでの実測 | 呼び出し回数 |
|---|---|---|
| **積分**(`Simulator.substep`) | **240.6 ms** | 328 サブステップ × 1 |
| **予測**(`Predictor.advanceBudget`) | **210.7 ms** | 458 ステップ × 2 |
| **計画**(`PlanArc.integrateTo`) | **198.3 ms** | 209 ステップ × 3 |

合計 update = **649.6 ms**(≒1.5fps)。
**問われていない「積分」が最大で、しかもエンティティが0体でも249ms かかる**(後述 A-0)。

さらに**時間加速と無関係な重大バグを1つ発見した**:
**マップでノードを1つ置くと、×1(等速)でも計画が毎フレーム全区間を再積分し、
update が 281.5 ms(≒3.5fps)になる。** これは報告された症状に含まれていないが、
高加速の問題より先に踏む可能性が高い。

独立した問題がもう1つ(論点C: 予測線の振動)。性能とは無関係で、直しても互いに影響しない。

**調査中に立てた仮説のうち2つは実測で否定・修正された。** その経緯も残す。

### 0-1-1.【重要】計測値の性質と限界

**`PerfMeter` の診断値(`plan-arcs`/`pred-discard`/`pred-steps` 等)は、
500ms ごとのフラッシュ時点における「その1フレームだけ」のスナップショットである。**
`Predictor.tracked`/`discarded` などは毎フレーム0にリセットされるので、
フラッシュ期間中の合計ではない。

つまり `pred-discard = 6` は「観測した1フレームで6体破棄された」であって、
**「毎フレーム6体破棄されている」ことの証明にはならない。**
離散イベントの真の頻度は 500ms 周期のストロボ観測では保証できない。
本メモが「毎フレーム」と書いている箇所は、**複数回のストロボで一貫して同じ値が出たことによる推定**である。
確定させるには累積カウンタが要る(後述「計装の提案」)。

また **ms の絶対値は実行環境の負荷で変動する。**
独立した2回の実行で `マップ ×65536 ノード0` の計画が 198.3 ms と 147.8 ms だった
(前者は他の計測プロセスと並行実行)。**絶対値ではなく条件間の比と桁で読むこと。**

## 論点A-0: 【最大の発見】積分が最も重く、エンティティ0体でも重い

**問われていないが、実測では「積分」が最大のセクション。**

決定的なのは `CREATIVE マップ ×65536 艦なし` の行:

- **エンティティ0体、予測0体、計画なし。軌道積分の実行回数も0回。**
- それでも **積分 = 249.0 ms**。

つまりこの249msは**エンティティを1つも動かさずに消えている**。
内訳は `Simulator.substep` が毎サブステップ行う
`attractorsAt(substep midpoint)` + `classifyAttractors` だけ。

```
249.0 ms / 328 サブステップ = 759 µs / サブステップ
```

`exp3` の `attractorsAt` = 283µs、`gravityAttractorsAt` = 177µs、`classifyAttractors` = 15µs
から見て妥当な値。**天体窓を組むコストそのもの。**

### A-0-1. サブステップ数が正のフィードバックを持つ

`substeps = ceil(simDt / SUBSTEP_MAX_DT)`、`simDt = dt × simSpeed`、
`dt = Math.min(dtRaw, 0.1)`(`game.ts:256`)。

**フレームが重くなると `dtRaw` が伸び、`simDt` が伸び、サブステップ数が増え、さらに重くなる。**
実測 `substeps = 328` は `dt` が上限 0.1s に張り付いた状態
(`0.1 × 65536 / 20 = 328`)。**上限があるおかげで発散はしないが、上限で頭打ちになっている。**

低ワープで `substeps = 1` なのは、`simDt < 20s` で1本に収まるため。
×65536 では1フレームあたり 328 回、`Ephemeris` を**すべて異なる時刻で**引く。

### A-0-2. リングキャッシュはほぼ効いていない

`eph-all` の実測(累積のフレーム差分):

| 条件 | hit | miss |
|---|---|---|
| マップ ×1 ノード0 | 11,088 | 3,648 |
| マップ ×65536 ノード0 | 103,996 | **143,286** |
| CREATIVE ×65536 艦なし | 77,859 | **149,568** |

**高ワープではミスがヒットを上回る。** リングは時刻の**厳密一致**でしか当たらず
(`ephemeris.ts` の `TimeRing`)、サブステップ中点・予測先端・計画各ステップは
すべて一意な浮動小数点値なので、原理的に当たらない。

### A-0-3. `debug-load` は別枠

`debug-load 戦闘 ×65536` の積分 4037.9 ms は、`sources=364`(小惑星300体が重力源)で
**軌道積分の実行回数が 99,181 回/フレーム**。これは天体窓のコストではなく
エンティティ間の相互重力そのもの。**本件とは別の問題**だが、同じ「高ワープで
サブステップ数が跳ねる」構造の上に乗っている。

## 論点A: 「予測」

### A-1. コストの99%は暦の評価そのもの(実測)

`Predictor.advanceBudget`(`predictor.ts:73-109`)は1ステップにつき
`classifyAttractors(predictedAttractorsAt(...))` を**2回**呼ぶ(先端時刻用と中点時刻用)。

| 操作 | 実測 |
|---|---|
| `ephemeris.gravityAttractorsAt(t)` (64天体・毎回異なる t) | **176.68 µs** |
| `ephemeris.attractorsAt(t)` (101天体) | 283.37 µs |
| `classifyAttractors` | 15.09 µs |
| `attractorsNear` | 0.53 µs |
| `stepDynamics`(物理そのもの) | **2.76 µs** |
| **`advanceBudget` 1反復** | **388.36 µs** |

**物理は総コストの 0.7%。**
→ **刻み幅を粗くしても速くならない**(ステップ数ぶんしか効かず、`exp1` の通り精度は dt⁴·⁷ で悪化)。
**ここは触るべきではない。**

### A-2. なぜキャッシュが無いのか — `57414b5e` の経緯

`ATTRACTOR_REBUILD_SEC`(=3600s)は 2026-08-11 に導入され、
**2026-08-15 の `57414b5e` "fix: refresh moving attractors during trajectory prediction" で
意図的に削除された。** 月のように速く動く天体を1時間据え置くと、
月周回の予測が固定された重力場を積分してしまうため。

**「キャッシュを戻す」は選択肢ではない。** `57414b5e` が直したバグの再発になる。
定数は `const.ts` からも消え、`src/` 全体で参照0件。正しさの修正が性能の手当てを伴わずに入った状態。

### A-3. 本当の無駄 — 捨てるものを先に計算している

`classifyAttractors` は64天体を `always`(μの重い順15体)と `grid`(残り49体)に分ける。
`attractorsNear` の実測では **LEO で 64→15 に絞られ、グリッド側の寄与は0体**。

**49体ぶんの暦を評価してから捨てている**(按分で約135µs、1ステップ2回で約270µs = 388µsの約7割)。

そして要点:

- **`always` の選抜基準は μ だけで、μ は時刻に依存しない。** どの15体かは位置を評価せずに決まる。
- **月は μ 順で14位、`GRAVITY_ALWAYS_COUNT`=15 の内側にいる。**

→ **`57414b5e` が守りたかった「月を毎ステップ引き直す」は `always` 側だけで達成できる。**
据え置いてよいのは grid 側の49体で、寄与は `GRAVITY_NEGLIGIBLE_ACCEL`=1e-8 m/s² 以下が構成上保証されている。

**前のキャッシュは、キャッシュしてはいけない側(月を含む全体)をキャッシュしていた。
正しさの修正と性能の修正は本来対立しない。**

**この修正は A-0(積分)にもそのまま効く** — `Simulator.substep` も同じ
`attractorsAt` + `classifyAttractors` を呼んでいる。

### A-4. 予算がワープ×エンティティ数に対して破綻する

追随に必要なステップ数 = `(予測対象数) × warp / (60 · dt)`。
LEO では実効 dt = 20s 固定(`exp1` 実測: `max(20, period/600, horizon/20000)` が 20.0000s で飽和)。

実測がそのまま示している: マップ ×65536 で `trk=6, comp=0, disc=6, steps=458`
— **予算500をほぼ使い切り、6体全部が毎フレーム破棄され、1体も完成しない。**

degradation が無いのが構造上の問題。**1ステップ足りなかった個体は列を全損し、
ホライズン全体の作り直しを負う。** 再成長の需要が上乗せされ、さらに足りなくなる。
**崖であって坂ではない。**

戦闘ビュー(予測1体)は `disc=1, steps=128` で予算上限に張り付くものの、
1体なので 57.3ms で頭打ちになる。**マップで多数を追うと崩れる。**

### A-5. horizon が全個体一律であること

`horizon` は `displayWindowManager.current.duration` を全個体へ一律に配る。
`game-entity.ts:93` のコメントがそれを明示している —
*「予測する長さは表示期間に追従するので、種別ごとに決まるのは可否だけ」*。

しかし**積分折れ線を描くのは `Player` だけ**(`TrajectoryLine` を作るのは `player.ts:130` のみ)。
敵・弾薬・基地は解析楕円で描かれ、予測は `displayState(t)` 経由のマーカー位置決めにしか使われない。
静止時は `displayTime === simTime` なので必要な horizon は実質ゼロ。

ただし計画が描かれている間は `collectPlanCollision` が `alive && collides && radius>0` の個体を
計画の未来時刻で引く。**必要な horizon は「そのフレームの消費者の最大値」。**

過去方向には既にこの流儀がある — `requestHistoryDuration(sec)`(`game-entity.ts:176`)。
**未来方向にだけ同じ仕組みが無い。**
これは見落としではなく上記コメントの通り明示的な決定なので、変えるなら決定の変更として扱う。

## 論点B: 「計画」

### B-1.【最重要・時間加速と無関係】ノードを置くと ×1 でも毎フレーム全区間を再積分する

実測(`stage1-map-warp1-node1`、ノード設置成功):

```
warp = ×1、substeps = 1、predDiscarded = 0、predComplete = 7/7(予測は完全に健全)
plan-arcs = 1(毎フレーム作り直し)、plan-steps = 210
計画 = 268.6 ms、update = 281.5 ms   → 約 3.5 fps
```

**等速で、予測は全く問題ない状態で、ノードを1つ置いただけで 3.5fps に落ちる。**
報告された症状には含まれていないが、**高加速の問題より先に踏む可能性が高い。**

`predDiscarded = 0` なので、後述 B-2 の「予測の破棄が世代値を変える」経路は**この条件では否定される。**
残る候補は3つで、**どれかはまだ切り分けられていない**:

1. **`represents` の間引き判定**(`plan-arc.ts:210`)
   ```ts
   const sampleInterval = (end - this.state0.t) / C.PLAN_ARC_MAX_SAMPLES;
   if (this._trajectory.sampleInterval > sampleInterval * C.PLAN_ARC_MAX_SAMPLE_COARSENING) return false;
   ```
   左辺は**実際に記録された間隔**(刻み幅で決まる)、右辺は**要求する間隔**(`区間長/2000`)。
   作り直しても左辺は縮まないので、区間が短いほど恒真に近づく。
   **ノードを置くと anchor→ノードの短い区間ができる**ので、そこで発火する筋。
2. **`planSourceRevision` の `planEnd` 未解決分岐**(`attractors.ts` 内)
   `!Number.isFinite(planEnd) || !(planEnd > simTime)` のとき **毎回異なる値を返す**。
   `lastPlanEnd` は前フレームの `PlanPath.timeRange()` 由来なので、これが解決しないと毎フレーム再構築。
3. **ノード区間の `state0` 参照が毎フレーム変わっている**(凍結されているはずだが未確認)

**独立した2回目の計測でも同じ結論に達した**(別プロセスで走らせた計測):
`マップ ×1 ノード1` で計画 158.3 ms、`plan-arcs` が常時 1〜2。さらに次を確認している:

- **ノードを置いた直後(現在時刻の近く)でも、ドラッグで先の時刻へ retiming した後でも同じ。**
  → ノードの時刻位置に依存しない。
- **戦闘ビュー(編集モードでない)でも同じ現象が出る。** ただし高ワープでは
  `NODE_EXPIRE_GRACE`(60秒)でノードが自動消化されて計画コストがゼロに戻るため見えにくい。
  マップビュー中は `PlanGuide.update` が編集モード判定で早期 return するのでこの自動消化が起きない。
- **黒箱計測だけでは機構を特定できない**という点も同じ結論。

**切り分け方**: `represents` がどの `return false` で抜けたかを数えるカウンタを一時的に入れ、
負荷ウィンドウか console に出す。3行足せば1回の起動で決まる。
**机上の算術では確定できなかった**(下記 B-1-x)ので、次はこれをやること。

> ### B-1-x. 否定された推論の記録
> 当初、この間引き判定が**既定構成で恒真**(LEO・表示期間2h で
> 実間隔34s > 要求間隔3.6s×8=28.8s)だと考え、
> 「全ワープ・全区間で毎フレーム再構築される」と結論した。
> **`マップ ×1 ノード0` の `plan-arcs = 0` で否定された** — 末尾区間だけのときは発火していない。
> 次に「原因は B-2 の伝播だけ」と修正したが、**`マップ ×1 ノード1` の
> `arcs=1, disc=0` でこれも不十分と判明した。**
> **教訓: `_trajectory.sampleInterval`(`oldestGap`)の実値を測らずに推論した。
> 刻み幅は `stepDt` の接近天体項でも動くので、机上で確定できる量ではなかった。**

### B-2. 高ワープでは予測の破棄が計画の世代値を毎フレーム変える

`planSourceRevision`(`attractors.ts:152-180`)は各個体の `predictionCoverage(e, planEnd)` を畳み込む。
これは3値の量子化(`NO_PREDICTION` / `PREDICTION_SHORT` / `PREDICTION_COVERS_PLAN`、`attractors.ts:144`)。
`represents` の**最初の**チェックは `sourceRevision !== this.sourceRevision`。

因果の鎖(実測と整合):

1. ×65536 で予測が追随できず、6体が毎フレーム破棄(`disc=6, comp=0`)
2. → `predictionCoverage` が `COVERS`↔`SHORT`/`NO_PREDICTION` を往復
3. → `planSourceRevision` が毎フレーム変わる
4. → `represents` が `sourceRevision` 不一致で false → 全区間再構築(`arcs=1`, 209ステップ)

**`マップ ×1 ノード0`(`disc=0`→`arcs=0`)と `マップ ×65536 ノード0`(`disc=6`→`arcs=1`)の
対照がこの経路を裏づける。**

量子化は「予測の成長で毎フレーム値が変わらないように」入れた工夫だが、
**破棄そのものは量子化では吸収できない** — 破棄は値を実際に往復させるので。

**つまり高ワープの計画負荷は予測の破綻の下流。予測を直せば連動して落ちる。**
一方 B-1(×1でノードを置いた場合)は独立した別経路。

### B-3. 1ステップに3回、重い解決を呼ぶ

`integrateTo`(`plan-arc.ts:309,336,355`)は `holdSources(this.provider, ...)` を
start / mid / end の**3回**呼ぶ。`provider.at(t)` = `planAttractorsAt` は
`predictedAttractorsAt`(→ `gravityAttractorsAt` 177µs)と
`collectPlanCollision`(→ `attractorsAt` 283µs、加えて **`entities.all()` の全走査**)の両方を回す。

実測 **1.28 ms/ステップ**(268.6ms / 210ステップ)。
**再構築頻度を直しても、Δv 編集直後など「本当に作り直すべき」フレームには残るスパイク。**

### B-4. 計測区間の注意 — `SECTION.plan` は `PlanEditor` だけではない

`SECTION.plan` は `Game.update` の**2箇所**から加算される(`FrameSections.exit` は積み上げ):

- `game.ts:269-273` — `editor.update` + `targeter.updateEquatorNodes` + `entities.updateBaseEquatorNodes`
- `game.ts:341-346` — `guide.update`

赤道交点マーカー2つは `overviewMode` で自己ゲートするので戦闘ビューでは空振りする
(実測でも戦闘の計画は全ワープで 0.1ms)。
マップの数値には `findEquatorCrossings` が末尾区間のサンプル列を走査するぶんも入っている。
**「計画」の ms を `PlanEditor.update` 単独と読まないこと。**

### B-5. ノード0個での再積分は編集モード限定(実測で確認)

`displayedPlan`(`plan-editor.ts:765-770`)は `!editMode && nodes.length === 0` のとき `null` を返し、
`PlanPath.update` 自体が走らない。

**実測: 戦闘ビューの計画は ×1 から ×65536 まで一貫して 0.1ms。**
「editModeのオンオフによって数値が変わる」という見立ては当たっている。

## 論点C: 予測線がプレイヤーから離れる/振動する(性能とは独立)

### C-1. 数値ドリフトでは説明できない(実測)

| 量 | 実測 |
|---|---|
| `divergenceTolerance` @ 既定プリセット | **500 m(LEO / 低月周回 / GEO 相当すべて同じ)** |
| 同 @ `28日` プリセット | 69,991 m |
| 数値ドリフトだけで500mに達する sim 時間 | **7.7〜43日** |
| 同・×1 での実時間 | **7.7日** |

既定プリセットでは `horizon/2000 < period/32` が常に成り立ち coarsening が 1.000 に固定される。
**許容量は軌道の種類によらず常に floor の `PREDICT_RESET_DIST` = 500m。**

→ **「数値誤差で乖離 → 破棄 → 跳ね戻り」は通常のプレイでは成立しない。**

**時系列サンプリングによる直接確認**(`PERF_MODE=timeseries`、0.3秒間隔):

| 倍率 | 観測時間 | 破棄の発生回数 |
|---|---|---|
| ×1 | 60 秒 | **1 回** |
| ×64 | 30 秒 | **0 回** |
| ×1024 | 30 秒 | **0 回** |

**低〜中ワープでは破棄がほぼ起きない。** そして ×16384→×65536 の間で
「たまに追いつく」から「毎フレーム破棄して予算を使い切るが完成しない」へ**閾値的に**切り替わる。
**なだらかな sawtooth ではなく崖。** これは A-4 の「崖であって坂ではない」と一致する。

**当初の自分の仮説(数値ドリフト由来の sawtooth)はこれで否定された。**
低ワープで見える振動は破棄ではなく、次の C-2 の補間誤差である。

### C-2. 振動の正体は補間の読み取り誤差

描画される折れ線の先頭頂点は、実機体の位置ではなく
**`predictedTrajectory` の間引かれたサンプル列を Hermite 補間した値**である。

- `GameEntity.syncTrajectoryLine` は `from = simTime` を渡す
- `TrajectoryLine.syncGeometry` は `startTime = max(from, baked[0].t)` にクランプ
- sampler は `startTime` を挟む2サンプル間を `hermiteInterpolate`(`trajectory-line.ts:80`)

サンプル間隔は `period/32` ≒ **174 s**、その間隔での補間誤差が
`PREDICT_SAMPLE_ERROR` = **30 m**(定数のコメントが「実測値」と言っている)。

**この誤差は区間の中央で最大、サンプル上でゼロ。
つまり先頭頂点はサンプル間隔を周期として振動する。**

| 倍率 | サンプル間隔174sの実時間 | 見え方 |
|---|---|---|
| ×1 | 174 s | ゆっくり離れて戻る(sawtooth) |
| ×1024 | 10.2 s | 目に見える脈動 |
| ×65536 | **0.16 s** | **振動** |

**報告された「sawtooth状に離れたり戻ったり」「それが高頻度になって振動」はこれで説明できる。**
残る「スラストするまで離れ続ける」は、噴射時の明示的な `invalidatePrediction()`
(`Player.behave`)が事実上唯一のリセット契機になっている状況を指していると思われる。

### C-3. 許容量が2種類の誤差を混ぜている

`divergenceTolerance` は `coarsening**4` で許容量を広げる。これは
**(a) `at()` の補間誤差**(読み取り由来、中身は正しい)を飲むための拡大。
しかし同じ閾値が **(b) 予測列そのものの発散**(中身が違う)も許してしまう。
そして描画の先頭頂点も (a) を被る。

**「線が実機体からどれだけ離れて見えてよいか」が「サンプル列がどれだけ粗いか」に
連動してしまっている。** 別の量なのに。`28日` で許容量が 69.9 km になるのはその帰結。

**キャッシュの整合性責務について**: `divergenceTolerance` は
`_predictedTrajectory.sampleInterval`(列自身が記録した粗さ)を読んでいて、その点は正しく
列の内部に閉じている。**壊れているのは整合性ではなく「何と何を比べているか」の定義の方。**

### C-4. 直し方

性能とは独立に、2つに分けて直せる:

1. **描画の先頭を実機体状態に固定する。** 先頭頂点を `predictedTrajectory.at(simTime)` ではなく
   `actualTrajectory.state` から取れば、許容量がいくつであれ線は必ず船体に付く。**C-2 の振動が消える。**
2. **乖離判定を補間しない時刻で行う。** 予測列が実際に持っているサンプル時刻で
   実軌道側(`actualTrajectory` も履歴を持つ)と突き合わせれば (a) が判定から落ち、
   閾値を (b) の純粋な精度境界まで縮められる。

## 論点D: 「空の計画で予測列を流用する」案の評価

**判定: 現状のまま統合するのは推奨しない。ただし理由は懸念されていたものとは違う。**

### D-1. horizon は既に一致している

`Predictor.update(..., horizon)` も `segmentDurationFrom(...)` も
同じ `DisplayWindowManager` の表示期間を読む。**両者は同じ長さを指している。**
「予測が伸びる前に再積分されてノードが置けなくなる」は horizon の不一致からは生じない。

### D-2. 実際の障害はサンプル密度

| | 保持サンプル間隔(LEO・既定) | 区間あたりのサンプル数 |
|---|---|---|
| 予測 | `max(period/32, horizon/2000)` = **174 s** | **32/周** |
| 計画 | 刻み幅ぶん(実測 209〜211ステップ/区間) | **約210/区間** |

**予測は計画の 1/6 程度の密度しか保持していない。**
`PlanPath.nearestSample` はサンプルを候補にノード位置を決めるので、
流用するとノード設置の時間粒度がその比で粗くなる。

一方で**刻み幅そのものは予測の方が細かい**(20s vs 実測 約34s)。
つまり予測は「細かく積分して粗く保存」、計画は「粗く積分して全部保存」。
**積分精度では予測が勝ち、保持密度では計画が勝つ。単純な上位互換関係にない。**

### D-3. 先回り量は障害にならない

`exp4` より、LEO・戦闘(128ステップ)でも ×153,600 まで先端は伸び続ける(上限は131072)。
**「予測が伸びる前に追い抜かれる」は単体では起きない。**
起きているのは A-4 の「多数個体で1体あたりの取り分が削られる」方。

### D-4. 結論

統合の障害は D-2 の1点に絞られ、**予測の保持密度を上げれば解消しうる**
(`PREDICT_MAX_SAMPLES` は2000で、既定では `period/32` 側が効いていて上限に全く届いていない)。

とはいえ警戒は妥当だと考える —
**戦闘ビューは「目の前を高精度」、編集モードは「遠くまで長期間」という用途の違いは実在し、
1本の列のチューニングでは同時に満たせない。**
`DynamicTrajectory` を共通基盤として使うのは既にそうなっており、それ以上の統合は早すぎる一般化。

**推奨: まず A-3 と B-1 を直す。** それで再積分が「毎フレーム」から「ほぼ起きない」に戻れば
(`マップ ×1 ノード0` の実測がその状態)、**統合する動機自体が消える。**

「マップビューでは予測線を非表示にして計算も止める」は、
A-5(horizon を消費者が要求する形にする)の特殊ケースとして自然に入る。
