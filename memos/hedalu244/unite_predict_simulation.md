# 予測と実シミュレーションの共通化 — 二重実装の解消

`Simulator`(実シミュレーション)と `Predictor`/`PredictedArc`(予測)は、どちらも「1つの物体を
1歩進める」処理を持つ。両者を1本にまとめることはできない(第1章)が、**まとめられない理由に
由来しない部分まで複数箇所に書かれていて、手で揃え続けている**(第2章)。本文書はその共通化の計画である。

---

# 第0章 この文書の扱い方

- 段は着手順。ある段を実施したら、その段の手順を削除し、確定した契約は第3章へ移す。
- 見積りには導出式を併記する。実測が得られたら実測値で置き換える。
- 他文書・過去版・会話への参照を置かない。必要な事実は本文へ埋め込む。

# 第1章 共通化してはいけない部分(役割の違い)

違いは2点しかなく、両者の設計の差はすべてこの2点から出ている。

## 1-1. 同時性

`Simulator` は生存する全個体(破片・薬莢・弾まで含めて数百体)を、**同じ1つの瞬間で同時に**進める。
`Predictor` は選ばれた少数の弧を1本ずつ、**それぞれ別の先端時刻で**伸ばす。ここから:

| | 実シミュレーション | 予測 |
|---|---|---|
| 重力源の絞り込み | サブステップに1つ分類を組み、全個体で共有(`classifyAttractors` → `attractorsNearInto`) | 弧ごとの成員判定 + 期限つき再訪(`ArcBodies`) |
| 個体どうしの接触 | 解ける | 解けない |
| 引き合う個体どうし | 解ける | 解けない |
| 引力を持つ個体 | 常にここが積分する | 弧は状態を決めない(線と、他者の未来重力源としてのみ読まれる) |

分類を1回だけ組んで全個体で使い回すのは計算量オーダーの話であると同時に**正しさの要件**でもある —
A→B と B→A を別々の瞬間に組んだ構造から引くと、対称であるべき相互作用に処理順依存の誤差が入る。
弧にはその「共通の瞬間」が無いので、この共有はできない。

**ただし「個体どうしの接触」と「天体との接触」は別の問い。** 前者は同時性を要するが、後者は
天体側へ及ぶ反作用が(質量比により)無いので、相手の状態を書き換える必要がなく、
**弧が1本だけで判定できる**。第3章の分割はここに立脚する。

## 1-2. 刻みの決まり方

`Simulator` は毎フレーム `simTime + simDt` へ**必ず到達しなければならない**ので、刻みはそのフレームの
時間送りから決まる(`simulationMaxStep(simDt, SUBSTEP_MAX_DT, SUBSTEP_MAX_COUNT)`)。
`Predictor` は `simTime` を追い越されない範囲で先へ伸びればよいので、1フレームの歩数を予算
(`ARC_STEP_BUDGET`)で切り、足りなければ遅れる — 追い越された弧は読まれなくなり、その個体は
実シミュレーションの積分へ落ちるだけで壊れない。

## 1-3. 小惑星を廃止しても、この二重性は残る

引き合う `Asteroid` が無くなれば「重力源は解析天体だけ・積分対象は重力を持たない」となり、
1-1 の4行目(引力を持つ個体の扱い)は消える。しかし個体どうしの接触は残り、予算管理も残るので、
**二重性そのものは残る**。よって小惑星の存廃を統一の前提条件にしない。

# 第2章 いま多重に書かれているもの

## 2-1. 「天体に接触したか」が3箇所で判定されている

天体との接触は、被積分剛体どうしの接触と**物理的に同じ現象**である。違いは、
(i) 剛体どうしは同時性を要するので `Simulator` にしか扱えない、
(ii) 天体との接触は質量比により天体側へ及ぶ反作用が無い、の2点だけ。
接触したことで何が起きるか(消滅か着陸か被弾か)は型による多態であって、判定そのものではない。

にもかかわらず、判定が3箇所にある。

| 判定する場所 | 使う幾何 | 走るワープ帯 | 対象 | 反応 |
|---|---|---|---|---|
| `ContactPhysics.computeAttractorResponse` | `resolveSphereCollision` → `sweptSphereToi`(**線形**掃引) | ×4 以下のみ | `collides` を立てた個体 × 天体 | `collideWith(body, contact)` — **既に多態** |
| `GameEntity.checkLoss` 系(5通り) | `reachedBody` → `sweptHermiteSphereToi`(**三次エルミート**の再帰細分) / `Bullet` だけ `containingBody`(**点判定**) | 常時 | 全生存個体 × 天体 | `alive = false` + 種別ごとの演出・ステージ記録 |
| `PredictedArc.checkImpact` | `reachedBody`(同上) | 常時(弧の伸長時) | 弧 × 衝突窓の天体 | `_impact` + `_truncated` |

**`ContactPhysics` は既に天体を `invMass: 0` の接触相手として扱っており、反応の多態も
`collideWith` で成立している。** つまり求める形の半分は既に存在していて、
`checkLoss` の幾何判定はそれが×4超で走らないことの穴埋めとして置かれた二重実装である。

### 2-1-1. その結果いま起きていること — 同じ事象がワープ倍率で違う結末になる

`Simulator.advance` の1サブステップは 接触解決 → `entities.cleanup`(= `checkLoss`)の順。
自機が地球へ到達したとき:

- **×4 以下**: `ContactPhysics` が先に当たり、`Player.collideWith` → `applyCollisionDamage` →
  `recordPlayerLost('高速接触により機体を喪失した')`。
- **×4 超**: 接触が走らないので `checkLoss` が当たり、
  `recordPlayerLost('天体の地表へ到達し機体は失われた')`。

**同じ物理事象に対して、ワープ倍率だけで喪失理由の文言が変わる。** 弾も同様で、×4 以下では
`Bullet.collideWith` が、×4 超では `Bullet.checkLoss` の点判定が消している。

### 2-1-2. 反応の多態はどこまで揃っているか(実地確認)

判定を接触経路へ寄せると、**天体接触の帰結は `collideWith` だけが決める**ことになる。現状の
実装状況は次のとおりで、**そのまま寄せると4種別が天体に当たっても消えなくなる**(反発だけして
地表で跳ね続ける)。

| 種別 | `collideWith` | 天体(`Attractor`)接触の帰結 | 寄せたときに必要な追加 |
|---|---|---|---|
| `Player` | あり | `applyCollisionDamage(impulse/mass)` → HP 0 で喪失 | **不要**(低速なら生き残る = 着陸) |
| `Enemy` | あり | 同上 → HP 0 で `recordEnemyDeath(…, 'killed')` | **不要** |
| `Bullet` | あり | `alive = false` | **不要** |
| `DebrisPiece` | あり | 弾と薬莢の音だけ。**天体接触で何も起きない** | **要** |
| `AmmoPickup` | 無し(基底の no-op) | 何も起きない | **要** |
| `Base` | 無し(基底の no-op) | 何も起きない | **要** |
| `Asteroid` | 無し(基底の no-op) | 何も起きない | **要** |

→ **基底 `GameEntity.collideWith` の既定を「相手が `GameEntity` でなければ(= 天体なら)`alive = false`」
にする**のが最小の解決。`Player` / `Enemy` / `Bullet` は既に上書きしているので影響を受けず、
残り4種別は現状の `checkLoss` と同じ帰結(消滅)を得る。

**併せて注意が要る穴が1つ**: `ContactPhysics.applyCandidate` は `response.impulse === 0` のとき
`collideWith` を呼ばずに戻る(離反中の接触は通知しない)。天体へ向かって接近している限り
`vn < 0` なので撃力は正になり通常は問題ないが、**相対速度ゼロで天体の内側に湧いた個体は
通知されない**。現状の `checkLoss`(位置だけを見る)はこれを拾っていたので、
段3 ではこの経路が失われることを確認する(実害があるなら `containingBody` による
最終手段の判定を接触側へ置く)。

## 2-2. 掃引接触の幾何が2実装ある

`physics/sphere-contact.ts` に2つ入っている。

| | `sweptSphereToi` | `sweptHermiteSphereToi` |
|---|---|---|
| 経路の近似 | 端点を結ぶ**線分** | 端点の速度を接線に取る**三次エルミート** |
| 解き方 | 2次方程式の閉形式 | 相対位置を3次ベジエへ変換 → 制御点凸包の箱判定 → 左右再帰細分(深さ32)→ 24反復の二分法 |
| 返り値 | `{toi, normal}` | `toi` のみ |
| 呼ぶ側 | `collision-response.ts`(= `ContactPhysics` の全経路) | `attractor.ts` の `reachedBody`(= `checkLoss` と `PredictedArc`) |

**同じ「移動する球どうしがこの区間で触れたか」を、別の近似で2回書いている。**

### 2-2-1. 線分化の誤差は両側に出る — 支配的なのは偽陽性

線分と真の曲線のずれには符号が2通りあり、**どちらも大きさは同じオーダー**である。
1歩でその天体まわりに掃く角を θ = ω·h(ω = |r × v| / |r|²)とすると、

```
弦と弧の最大乖離 ≈ r · θ² / 8
```

- **区間が近点を跨がないとき**(周回している通常の状態): 円弧の弦は中心に近いので、
  弦は弧より**天体側**にある。→ **偽陽性**。本当は逸れているのに交差と判定する。
- **区間が近点を跨ぐとき**: 真の最接近点は弦より天体側にある。→ **偽陰性**。
  既存テスト `Hermite swept sphere: 弦は外れていても曲線が膨らんで届く通過を捕まえる`
  が押さえている配置(端点 y=900・半径 700 の球に対し弦の最接近は 900 で外れるが、
  強い内向き動径速度のため曲線は 700 を割る)。

**物体はたいてい重力源のまわりを周回しているので、実地で支配的なのは前者(偽陽性)。**

したがって「半径を膨らませて偽陰性を消す」類の補正は成り立たない — 膨張量
`|Δv|·h/8 = a·h²/8 = ω²r·h²/8 = r·θ²/8` は上の乖離と**同じ大きさ**なので、
支配的な偽陽性側の誤差をちょうど2倍にするだけになる。**片側へ寄せるのではなく、
誤差そのものを小さくするしかない。**

### 2-2-2. 近似の次数と誤差(③ の判断材料)

| 近似 | 誤差のオーダー | 備考 |
|---|---|---|
| 線分(弦) | **O(h²)** = `r·θ²/8` | サジッタ項がそのまま残る。いま `ContactPhysics` が使っている |
| 二次 | O(h³) | サジッタ項を落とす。摂動・空気抵抗を無視すれば軌道は二次曲線なので、ここで大半が取れる |
| 三次エルミート | O(h⁴) | いま `reachedBody` が使っている。二次からの上積みは小さい |

**θ の実測値**(= どの近似で足りるかを決める量)

| 場面 | h | θ = ωh | `r·θ²/8`(r = 6791 km) |
|---|---|---|---|
| 実シミュレーション 通常 | 20 s | 0.0225 rad | **430 m** |
| 実シミュレーション 最高ワープ | 34.1 s | 0.0384 rad | **1.25 km** |
| 弧 最小刻み(`ARC_MIN_STEP_DT`) | 40 s | 0.045 rad | **1.7 km** |
| 弧 28日表示の粗化刻み | 121 s | 0.136 rad | **15.7 km** |

θ は `|r × v|·h / |r|²` で数演算で出せるので、**判定器が自分で「線分で足りるか」を決める
基準として使える**(③)。

いずれの値も地球半径 6371 km に対しては小さいが、`r·θ²` が二乗で効くため、
**粗い刻みほど急に悪化する**。判定器の内部で刻みに応じて次数を上げる余地があるのは
この非線形性のため。

## 2-3. 焼失と衝突が同じ「margin」に混ざっている

**この2つは別の現象である。**

| | 焼失 | 衝突 |
|---|---|---|
| 何が起きているか | 大気を持つ天体の大気圏に入り、断熱圧縮で熱に耐えられなくなる | どんな天体にもある固体表面への剛体接触 |
| 事象の性質 | **連続量による状態**(濃い空気の中にいる) | **離散的な事象**(表面に触れた瞬間) |
| 相手 | 大気を持つ天体だけ | 全天体 |
| いまの帰結 | 必ず喪失 | 必ず喪失 |
| 将来 | 熱シミュレーションによる精緻化 | 相対速度による着陸の成立 |

いま両方が `checkLoss` の中で `margin` という同じ形の数値として並んでおり、
**どちらの現象なのかがコードから読めない**。

### 2-3-1. 大気が地球にハードコードされている

`physics/atmosphere.ts` は大気を地球のものとして固定している。

| 箇所 | 地球への固定 |
|---|---|
| `burnUpBody` | `if (body.id !== 'earth') continue;` — id 文字列で地球以外を弾く |
| `atmosphericDensity` | Vallado の地球テーブル(0〜1000 km) |
| `dragAccel` | `len(r) - R_EARTH` — **ECI 原点からの距離**から地球半径を引く。地球が ECI 原点に固定されている前提 |
| `airspeed` | `EARTH_OMEGA` を Y 軸まわりに適用。同じく原点前提 |

**大気の有無と厚みは天体ごとの固有パラメータであるべきで、定数であってはならない。**
既定レジストリでは地球が ECI 原点に固定されているので `dragAccel` の前提は成り立っているが、
それは偶然であって設計ではない(2-10 の C がその帰結)。

## 2-4. 表面到達・大気での焼失の余裕(margin)が種別ごとにばらばら

| 書かれている場所 | 地表到達 | 大気での焼失 |
|---|---|---|
| `GameEntity.checkLoss`(基底) | margin 0 | `DEBRIS_REENTRY_ALT = 95 km` |
| `Player.checkLoss` | `PLAYER_MIN_ALT = 45 km` | `PLAYER_MIN_ALT = 45 km` |
| `Enemy.checkLoss` | **無し** | `REENTRY_ALT = 80 km` |
| `Bullet.checkLoss` | 0(点判定) | `DEBRIS_REENTRY_ALT = 95 km` |
| `PredictedArc.checkImpact` | 0 | `REENTRY_ALT = 80 km` |

**弧はこの最後の1通りを、弧の持ち主が誰であっても使う。** 予測を持ちかつ実シミュレーションがその弧から
状態を引く種別(`predictsFuture && consumesPrediction`)は `Player` / `Enemy` / `Base` / `AmmoPickup`
の4つで、それぞれ実体側の値と食い違う。

- **Player**: 弧は 80 km で打ち切られ、実体は 45 km で失われる。差 35 km。
  この弧の `impact` はノードの無い計画の末尾区間が借用する弧の `impact` でもあるので、
  **計画軌道の ✕ 到達アイコンが実際の喪失点より 35 km 高いところに出る**。
- **Enemy**: 焼失高度は一致(80 km)。地表到達は弧だけが持つので、×4 超では**敵が天体をすり抜け、
  予測線だけが表面で止まる**。
- **Base / AmmoPickup**: 実体は 95 km、弧は 80 km。弧の下端 15 km は実体が到達しない状態。

さらに `Player` の 45 km は「構造限界高度」— 大気由来の量なのに、`reachedBody` の margin として
**大気の無い天体にも適用されている**。自機はいま**月面の 45 km 上空で失われる**。

`GameEntity.predictedImpact` は `src/` にも `tests/` にも読み手が無い(計画側の ✕ アイコンは
`PlanPath` が弧の `impact` を直接読む)。

## 2-5. 刻みの規則 — 再突入細分化の引数が2箇所

関数(`adaptiveSimulationMaxStep`)は共有しているが、**境界半径と細分化の刻みという2つの定数を
両方の呼び出しが綴っている**。

```
Simulator.adaptiveMaxStep:
  adaptiveSimulationMaxStep(生存艦の状態列, R_EARTH + REENTRY_SUBSTEP_ALT,
                            simulationMaxStep(simDt, SUBSTEP_MAX_DT, SUBSTEP_MAX_COUNT),
                            REENTRY_SUBSTEP_MAX_DT)
PredictedArc.stepDt(consumable):
  adaptiveSimulationMaxStep([tip], R_EARTH + REENTRY_SUBSTEP_ALT,
                            this.simulationMaxStep, REENTRY_SUBSTEP_MAX_DT)
```

対象集合が違う(生存艦全部 / 弧の先端だけ)のは 1-1 由来の正当な差。第3の細分化帯を足すときに
片方だけ直せてしまう点だけが問題。

## 2-6. 「表面を持つ天体」の窓の定義が3通り

| | 中身 | 体数(既定レジストリ) |
|---|---|---|
| `Simulator.surfaceBodies`(×4 以下) | `ephemeris.attractorsAt(simTime)` = 登録天体の全数。動的個体を含まない | 101 |
| `Simulator.surfaceBodies`(×4 超) | そのサブステップ中点の重力窓 = `mu ≠ 0` の登録天体 + 重力を持つ生存個体 | 65 + 動的 |
| `ArcBodies` の `collision` | 登録天体の全数 + 生存する `predictedAsPlanCollider` 個体 | 101 + 動的 |

(101 は `SOLAR_SYSTEM` の登録数。うち `mu: 0` が 36 体なので重力源は 65 体。)

×4 超では**実体だけが 36 体の表示天体への再突入判定を失い、弧は失わない**。

## 2-7. 重力源の絞り込みが同じ許容量から別の距離を導いている

両者とも許容加速度は `GRAVITY_NEGLIGIBLE_ACCEL = 1e-8 m/s²` だが、そこから導く距離の式が違う。

- `attractors.ts` の `gridCellSize`: `sqrt(最も重い grid 天体の mu / GRAVITY_NEGLIGIBLE_ACCEL)` を
  **全 grid 天体に共通のセル一辺**として使い、27近傍を引く。加えて mu の重い順
  `GRAVITY_ALWAYS_COUNT = 15` 体は常に含める。
- `arc-bodies.ts` の `gravityReach`: `sqrt(2 · その天体自身の mu / GRAVITY_NEGLIGIBLE_ACCEL)` を
  **天体ごと**に持つ。加えて最も重い解析天体1体を常に含める。

セル一辺は最も重い天体基準を全部に適用するので緩く、弧の側は天体ごとなので厳しい。
したがって**弧は実シミュレーションが加算する天体を落としうる**。差の上限は測られていない。

## 2-8. 既に共通化されているもの(目標にする形)

- `DynamicTrajectory.step` — RK4 の呼び出し。両者がここを通る。**モデルケース。**
- `trajectorySampleInterval` — 保持列の間引き間隔の式。`GameEntity.sampleInterval` と
  `PredictedArc.step` が同じ関数を呼び、`keepDuration` の与え方だけが呼び出し側にある。
- `simulationMaxStep` — 刻み上限の式。

いずれも**「式は1本、引数は呼び出し側」**という形。以下の共通化もこの形を目標にする。

## 2-9. 二重に見えるが実際には二重でないもの(触らない)

- **姿勢積分・`stepEnvironment`(熱/電力/放熱板)**: 実シミュレーションにしか無い。弧は姿勢も熱の
  蓄積状態も運んでいないので、原理的に再現できない。
- **イベント境界での切り**: 実シミュレーションにしか無い概念。弧の消費者は境界を要求しない。
- **非有限値の検出**: 弧は `_truncated` へ、実シミュレーションは `NanWatchdog` の報告へ落とす。
  目的が違う(前者は自分の伸長を止める、後者は最初に壊れたフェーズを特定する)。

## 2-10. 確認されたバグ

以下は「共通化の副作用」ではなく**現状の欠陥**である。統一を進めるかどうかに関わらず直すべきで、
いずれも根は同じ(焼失と衝突の混同 + 大気の地球ハードコード)。

### A. `PLAYER_MIN_ALT` が天体に依らない定数として地表到達に効いている

`player.ts:382` は `reachedBody(prev, state, attractors, C.PLAYER_MIN_ALT)` — 45 km の余裕を
**全天体に**適用している。`PLAYER_MIN_ALT` は「構造限界高度」、つまり大気由来の量なのに、
大気を持たない天体にも同じ厚みの殻を作っている。

- **再現**: 自機で月へ接近する。表面まで 45 km を残して喪失する。
- **同じ理由で**: 小惑星(半径 500 m)に対しても 45 km の殻ができる。半径の 90 倍の
  当たり判定であり、その天体の近くを通るだけで喪失する。
- **正しい姿**: 剛体接触の余裕は全天体で 0。大気での焼失は大気を持つ天体にだけ効く。

### B. `Enemy` に地表到達の判定が無い

`enemy.ts:239` の `checkLoss` は `burnUpBody` しか見ておらず、固体表面は `ContactPhysics`
任せになっている(コメントもそう明言している)。しかし `ContactPhysics` は
`canResolvePhysicalCollisions`(×4 以下)でしか走らない。

- **再現**: ×4 超のワープで、敵の軌道が天体と交差する状況を作る。敵は天体をすり抜ける。
  一方その敵の予測線は表面で止まる(弧は margin 0 の地表到達を持っているため)。
- **正しい姿**: 剛体接触はワープ帯に依らず判定される(3-4)。

### C. 地球以外を原点とするレジストリで、抗力が海面密度で掛かる

`dragAccel` は高度を `len(r) - R_EARTH` で求める。`atmosphericDensity` は
`Math.max(0, alt / 1000)` で負の高度を 0 km に丸めるので、**`len(r) < R_EARTH` の位置は
すべて海面密度 1.225 kg/m³ として扱われる**。

- **再現**: `StageDebugAltSystem`(`PRIMARY_RADIUS = 3e6 m`、`PRIMARY_MU = 4e13`)。
  高度 420 km の周回位置は `len(r) = 3.42e6 m < R_EARTH = 6.371e6 m` なので高度は負に出る。
- **大きさ**: 軌道速度 `sqrt(4e13 / 3.42e6) = 3420 m/s`、`SHIP_BCINV = 3.3e-3` として
  `a = 0.5 × 1.225 × 3420 × 3.3e-3 = 6.9 m/s²`。
  その天体自身の重力 `4e13 / (3.42e6)² = 3.42 m/s²` の **2倍**。周回できない。
- **正しい姿**: 高度はその天体の中心と半径から測り、密度はその天体自身の大気モデルから引く。
  大気を持たない天体では抗力は恒等的にゼロ。

### D. 弧の打ち切り高度が持ち主に依らない(✕ アイコンの位置がずれる)

`PredictedArc.checkImpact` は `REENTRY_ALT = 80 km` を持ち主に関わらず使う(2-4)。
自機の弧は 80 km で打ち切られる一方、自機自身は 45 km(かそれ以前に熱・動圧)で失われる。
この弧の `impact` は、ノードの無い計画の末尾区間が借用する弧の `impact` でもあるので、
**計画軌道の ✕ 到達アイコンが実際の喪失点より 35 km 高いところに出る**。

- **正しい姿**: アイコンは焼失または喪失する位置に出る。弧は持ち主自身の焼失条件と
  剛体接触条件で打ち切る。

# 第3章 達成目標(変更後の契約)

## 3-1. 判定は1本、反応は多態

**接触の判定(幾何)は1つの原始関数に統一し、接触への反応だけを型で多態化する。**

| 層 | 実シミュレーション | 予測 | 共通化 |
|---|---|---|---|
| 天体の**探し方** | 共有分類 + 27近傍 | 弧ごとの成員判定 + 期限 | **しない**(1-1 由来) |
| 天体の**窓の定義** | — | — | **する** |
| **刻みの規則** | — | — | **する**(対象集合だけ呼び出し側) |
| **RK4 の1歩** | `DynamicTrajectory.step` | 同左 | **済** |
| **掃引接触の幾何** | `sweptSphereToi`(線形) | `sweptHermiteSphereToi`(三次) | **する**(判定器1つへ集約。解法の選択は判定器の内側 — 3-2) |
| **天体接触の反応** | `collideWith`(多態) | `_impact` + `_truncated` | **しない**(出力先が別) |
| **大気での焼失** | `checkLoss` に種別ごと | `checkImpact` に1通り | **する**(高度を種別ごとの値に) |

## 3-2. 接触判定器の責務

**2球体の接触判定器は1つだけ存在し、その責務は次のとおり。**

> 2球体の半径と移動前後の状態を受け取り、その区間で接触するか否か・接触の瞬間の状態・法線を
> (できるだけ正確に近似して)返す。

- **どう解くか(線分近似で足りるか、より高次で解くべきか)は判定器の内部に隠蔽される。**
  接触の種別(剛体どうし / 天体)でも、時間加速帯でも、呼び出し元でもない —
  精度と費用の釣り合いは判定器自身が持つ問題。
- **外から渡すのは解くのに必要なパラメータだけ。** 加えてよいのは、費用最適化のために
  必要な場合の**おおよその要求精度**まで。
- **どのペアを judgment にかけるか(broad phase)は判定器の外側の責務。** 呼び出し側が
  空間グリッドなり成員判定なりで絞ってから渡す。判定器自身が持ってよいのは、
  1ペアに対する安価な早期棄却(narrow phase の入口)だけ。

現状はこの責務が `physics/sphere-contact.ts` と `physics/attractor.ts` の2箇所に、
**精度違いの別実装として**置かれている。これがおかしい。

### 3-2-1. broad phase の現状(判定器の外側の話として分けて扱う)

| 呼び出し側 | 個体どうしの broad phase | 天体の broad phase |
|---|---|---|
| `ContactPhysics` | 空間グリッド 27近傍(`contactCellSize`) | **無し**(`attackers × bodies` の総当たり) |
| `GameEntity.checkLoss` | — | **無し**(全天体を総当たり) |
| `PredictedArc` | — | `ArcBodies`(成員判定 + 期限つき再訪) |

**天体側の broad phase は弧にしか無い。** 7-5 の費用はここから来ている。
判定器の一本化とは独立の課題なので、別項目として扱う。

## 3-3. 予測の弧は天体接触で必ず打ち切る

反応が多態になると「艦は低速接触なら生き延びる(= 着陸)」が成立しうるが、
**弧はそれでも接触時点で打ち切る**。接触後の軌道は跳ね返りや接地の帰結であって、
`PredictedArc` が積分している自由落下の埒外だから。判定器を共有しても、
この打ち切り規則は弧側の判断として残る。

## 3-4. 天体接触の判定は `ContactPhysics` に一本化し、ワープゲートを分割する

- **個体どうしの接触**は `canResolvePhysicalCollisions`(×4 以下)で従来どおり切る。
  同時性を要し、20 s 刻みでの撃力交換は意味を持たないため。
- **天体との接触は決して切らない。** 反作用が無いので相手の状態を書き換える必要がなく、
  掃引判定はどの刻み幅でも成立する。反応は `collideWith` の多態に委ねる。
- これにより `checkLoss` から**地表到達の判定が消える**。残るのは大気での焼失
  (連続量による条件で、接触ではない)と、種別固有の条件(弾の距離・寿命、薬莢の寿命、
  自機の熱・動圧)だけになる。

### 3-4-1. `collides` の意味を分ける

現状の `collides` は「個体どうしの接触に参加するか」と「天体との接触に参加するか」を兼ねている。
`fragment` な `DebrisPiece` は `collides = false` なので、いまは `ContactPhysics` に載らず
`checkLoss` だけが天体到達を見ている。判定を `ContactPhysics` へ寄せると、この個体が
天体をすり抜けてしまう。

→ **`collides` は個体どうしの接触だけを支配し、天体との接触は全生存個体が無条件に参加する。**
破片が艦をすり抜けつつ惑星には当たる、という現状の意図がそのまま表現できる。

## 3-5. 焼失と衝突を分ける

**2つは別の現象なので、別の判定・別の理由・別のパラメータで扱う。**

| | 焼失 | 衝突 |
|---|---|---|
| 判定 | **連続量の状態判定** — その位置の大気密度が種別ごとの閾値を超えたか。ステップ終端の1点で見る | **離散事象の掃引判定** — 統一された接触判定器(3-2)を通す |
| 相手 | 大気を持つ天体だけ | 全天体、margin 一律 0 |
| 天体側のパラメータ | `CelestialBodyDef.atmosphere`(有無と密度モデル) | `radius`(既存) |
| 種別側のパラメータ | 耐えられる大気密度の閾値 | 無し(反応が多態) |
| 反応 | 喪失。将来は熱シミュレーションへ精緻化 | `collideWith` の多態。将来は相対速度による着陸 |

### 3-5-1. 大気は天体ごとのパラメータにする

`physics/solar-system.ts` の `CelestialBodyDef` に `atmosphere?: AtmosphereDef` を足し、
`Attractor` がそれを運ぶ。`AtmosphereDef` が答えるのは**高度に対する密度**だけでよい —
`burnUpBody` の判定も `dragAccel` も、必要なのはそれ1つ。

- 地球は既存の Vallado テーブルをそのまま持つ。
- **今回登録するのは地球だけ。** 他の天体(金星・火星・タイタン・巨大惑星…)は
  `atmosphere` を持たないまま = 大気なしとして扱われ、**現状の挙動と完全に一致する**。
  実データを入れるのは別の作業で、その受け口だけを用意する。
- `atmosphere` が無い天体では、抗力は恒等的にゼロ・焼失は起こらない。
  `burnUpBody` の `id !== 'earth'` と `dragAccel` の `R_EARTH` は**両方とも消える**(2-10 C の修正)。

### 3-5-2. 種別ごとの閾値は「高度」ではなく「耐えられる大気密度」

高度は天体ごとに意味が変わるが、密度は変わらない。密度は高度に対して単調減少なので、
**地球に対しては現状の高度判定と厳密に等価**(`alt < X` ⟺ `ρ(alt) > ρ(X)`)。

現行の定数を地球のテーブルで密度へ換算した値:

| 種別 | 現行の高度 | 換算した密度の閾値 [kg/m³] | 導出 |
|---|---|---|---|
| 破片・薬莢・弾・基地・弾薬 | `DEBRIS_REENTRY_ALT` = 95 km | **1.34e-6** | 90 km 行 `3.396e-6 · exp(-5/5.382)` |
| 敵 | `REENTRY_ALT` = 80 km | **1.905e-5** | 80 km 行そのもの |
| 自機 | `PLAYER_MIN_ALT` = 45 km | **2.05e-3** | 40 km 行 `3.972e-3 · exp(-5/7.554)` |

置き方は `bcInv` / `srpCoeff` / `baseHistoryDuration` と同じ `GameEntity` の
`protected readonly` フィールドとし、`ensurePredictedArc` が `this.bcInv` / `this.srpCoeff` を
弧へ渡しているのと同じ並びに足す。**ゲームの調整値なので `physics/` へは置かない。**

### 3-5-3. 焼失は接触判定器を通さない

焼失は「濃い空気の中にいる」という連続量の状態であって、接触の瞬間を持つ事象ではない。
将来の熱シミュレーションもステップ全体にわたる積分になるので、掃引判定に載せる意味がない。
→ **ステップ終端での点判定のまま**とする。

代償: 1ステップの中で大気の殻へ入って出る軌道(かすめる再突入)を取りこぼす。
2-2-1 の乖離の式より、1ステップ内で沈み込める深さは `r·θ²/8` を超えない
(最高ワープの 34.1 s で 1.25 km)ので、近点がその範囲に入る軌道に限られる。
**現状と同じ挙動であり、熱シミュレーション化のときに自然に解消する。**

### 3-5-4. 熱・動圧による喪失は共通化しない

`ThermalSystem` の蓄積状態を弧が運んでいないので、弧は原理的に再現できない。
**弧は自機の実際の喪失点より先まで伸びうる**ことを仕様として認める。
弧が答えられるのは、上の密度閾値による焼失と、剛体接触による衝突の2つまで。

## 3-6. 着陸を後から実装できる基盤にする(着陸自体は実装しない)

**今回のリファクタは着陸機能の前段階であり、着陸そのものは実装しない。** 達成すべきは、
着陸が**自機の多態性を書き換えるだけで実装できる状態**になっていること。そのためには
「物体が他物体/天体と接触したときに呼ばれる関数」へ、相手と相対速度が届いている必要がある。

### 3-6-1. 必要な情報は既に届いている(実地確認)

`GameEntity.collideWith(other: GameEntity | Attractor, contact: Contact, activeStage: Stage)` と
`Contact` が現時点で運んでいるもの:

| 着陸の実装に要るもの | 現状 |
|---|---|
| 相手そのもの | `other` — 天体なら `Attractor`(`id` / `radius` / `mu` で天体を特定できる) |
| 接触時の自分の状態 | `contact.selfState`(反応**前**) |
| 接触時の相手の状態 | `contact.otherState`(天体なら `b.state`) |
| 相対速度 | `sub(selfState.v, otherState.v)` で出る |
| 接地の法線 | `contact.normal`(self → other 向きの単位法線) |
| 垂直/水平成分の分解 | 上の2つから出る — 「ゆっくり降りたが横に滑っている」を区別できる |
| 接触点・接触時刻 | `contact.point` / `contact.t` |

**つまり基盤としての情報は既に足りている。** `Player.collideWith` はいま
`contact.impulse / this.mass` という1つのスカラーしか読んでいないが、これは
`(1 + 反発係数) × 法線方向の接近速度` に比例する量で、必要なら上の材料から
垂直・水平の成分へ分解し直せる。

### 3-6-2. 足りていないのは呼び出し経路のほうだけ

- **天体接触が×4超で `collideWith` に届かない**(2-1-1)。着陸は低速で起きるので低ワープでも
  成立するが、「接触の帰結を決める場所が1つ」でなければ多態の書き換えだけでは済まなくなる。
  → ②で解消する。
- **`applyCandidate` は `impulse === 0` のとき `collideWith` を呼ばない**(2-1-2)。
  接近中なら撃力は正なので接地の瞬間は届くが、**接地後に静止した状態は通知されない**。
  着陸を「接地したまま留まる」状態として実装するなら、この穴は着陸の実装時に埋める。
  今回は**塞がない** — 今回の帰結(消滅)には影響しないため。

### 3-6-3. 今回課す制約

②で `Contact` の情報を**減らさないこと**。とくに `selfState` / `otherState` / `normal` は、
撃力スカラー1つへ畳んではならない — 畳むと着陸の実装が接触判定側の変更を要求するようになり、
「多態を書き換えるだけ」という目標が崩れる。

# 第4章 決定記録

## 4-1. `Bullet` の点判定を掃引へ揃える — **揃える**

- コードとして揃えるべきで、`containingBody` による点判定は残さない。弾は最も速い個体なので、
  点判定はすり抜けを許す(1 substep で `BULLET_SPEED × dt` 進む一方、判定は終端の1点だけ)。
- ただし `Bullet` は既に `collides = true` で `ContactPhysics` の天体接触に載っており、
  ×4 以下では `collideWith` が消している。3-4 でゲートを分割すれば、
  **`Bullet.checkLoss` の天体判定はまるごと不要になる**(距離と寿命だけが残る)。
  つまりこの決定は「点判定を掃引へ差し替える」ではなく「点判定を削除する」で果たされる。
- `containingBody` は `reachedBody` 内のフォールバック(区間長ゼロ・開始時点で内側)でも
  使われているので、関数そのものは残す。

## 4-2. `reachedBody` の実装が過剰 — **解法の選択を判定器の内側へ隠す**

**採用しない案**: 「線形掃引 + 半径を `δ = |Δv|·dt/8` だけ膨らませる」。
2-2-1 のとおり、膨張量は弦と弧の乖離 `r·θ²/8` と**同じ大きさ**なので、実地で支配的な
偽陽性側の誤差を2倍にするだけになる。片側へ寄せる補正では解決しない。

**採用する形**: 3-2 のとおり、**どう解くかは判定器の内部の問題**にする。線分で足りるか
高次で解くべきかは、接触の種別でも時間加速帯でも呼び出し元でもなく、判定器が精度と費用の
釣り合いを見て決める。外から渡すのは解くのに必要なパラメータと、必要ならおおよその要求精度だけ。

段取りは①②③に分ける(第8章)。**①の時点では解法を統一しない** — 集約が先で、
「線形かエルミートか」は暫定的に判定モードの引数として外に出しておき、③で内側へ畳む。
集約と精度改善を同時にやると、挙動の変化がどちらから来たのか切り分けられなくなる。

**軽量化と一元化は別の理由であることを混同しない。**

- **一元化の理由**: 同じ責務が精度違いの別実装として2箇所にあること、それ自体。
- **軽量化の理由**: 7-5 の実測。**主因は解法の選択ではなく、
  (a) 天体側の broad phase が `ContactPhysics` / `checkLoss` に無いこと(3-2-1)と
  (b) 動かない個体の判定を毎 substep 繰り返していること。**
  解法を線形へ倒しても棄却経路は 70 演算 → 21 演算(3.3×)にしかならない(7-4)。

## 4-3. 天体接触と剛体接触の一元化 — **`ContactPhysics` へ寄せる**

3-4 のとおり。`ContactPhysics` は既に天体を `invMass: 0` の相手として扱い、反応も
`collideWith` で多態化しているので、必要な変更は**ワープゲートの分割**と
**`collides` の意味の分割**の2点。

## 4-4. 焼失と衝突を区別する — **分ける**

3-5 のとおり。判定・相手・パラメータ・理由のすべてを分ける。

- **大気の有無と厚みは天体ごとの固有パラメータ**にする。定数にしない。
  今回入れるのは受け口と地球のデータだけで、他天体は `atmosphere` 無し = 現状と同一挙動。
- **剛体接触の余裕は全天体で一律 0。** `PLAYER_MIN_ALT` を全天体へ効かせている現状は
  バグ(2-10 A)。
- **喪失理由も分ける。** `Stage.recordEnemyDeath` の `cause` は現状
  `'killed' | 'reentry' | 'despawn'` で、`'reentry'` が焼失を、`'killed'` が
  (弾と天体衝突をまとめて)受けている。**`'burnup'`(焼失)と `'collision'`(天体衝突)へ
  分ける** — `Enemy.collideWith` は相手が `Attractor` か `GameEntity` かで区別できる。
  `stage.ts:252` の文言は三項演算子で書かれていて新しい cause を足すと
  「交戦圏を離脱」に落ちるので、`Record` による網羅的な引き当てへ直す。
- 自機側の理由文も同じ分割に従う。衝突側をさらに接触速度で出し分けることは今回やらない(4-5)。

## 4-5. 着陸は実装しない — 基盤だけを作る

**今回のリファクタは着陸機能の前段階であり、着陸そのものは実装しない。**
自機の衝突を接触速度で出し分ける(高速 = 喪失 / 低速 = 着陸)のも今回はやらない。

達成すべきは、**着陸が自機の多態性の書き換えだけで実装できる状態**になっていること(3-6)。
実地確認の結果、`Contact` は既に相手・両者の状態・法線を運んでおり、**情報としては足りている**。
足りないのは呼び出し経路(×4 超で `collideWith` へ届かない)だけで、それは②で解消する。

今回課す制約は1つ: **②で `Contact` の情報を減らさないこと。**

## 4-6. `Asteroid` が天体に当たったときの帰結 — **消える(据え置き)**

基底の新しい既定(2-1-2)がそのまま効き、現状の `checkLoss` と同じく消滅する。
`Asteroid` 型自体が将来廃止される可能性を視野に入れているので、挙動の細部は問わない。
今回の目標は**呼び出し経路の一元化と判定の一元化**であって、この型の挙動の作り込みではない。

## 4-7. 時間加速帯による分岐の扱い

現状の2帯域(×4 以下 = 剛体どうし + 天体、×4 超 = 天体のみ)は、物理的に不正確なまま
費用のために取られている暫定策である。**別の方法で軽くできるなら、そちらを優先する**
(7-5 の (a)(b) がその候補)。

修正後も帯域の分岐が残る可能性はあるが、**残ってよいのは「判定を呼ぶか呼ばないか」だけ**で、
判定器の実装が帯域によって変わってはならない。

乖離の項は 2-2-1 の `r·θ²/8` を上限に取る — **絞り込み側で安全側に倒すのは正当**
(通す候補が増えるだけで、判定器の答えは変わらない)。判定器の内部で半径を膨らませる案(4-2 で
棄却)とは別物である点に注意 — あちらは**答えそのもの**を歪める。

## 7-5. 既存コストの見積り(**実測が要る**)

`EntityManager.cleanup` は substep ごとに `all()` 全数へ `checkLoss` を回す。×4 超では
`Bullet` / `DebrisPiece` が `Simulator.substep` から外れる(まとめ積分に回る)が、
**`cleanup` からは外れない — 状態が変わっていないのに同じ判定を毎 substep 繰り返している。**

- 掃引を回す個体数(上限)= `debris` 600 + `casings` 260 = **860**
  (`Bullet` 400 はいまは点判定なので掃引には乗らないが、段3 で接触経路へ移ると乗る)。
- 高ワープの substep 数 = `SUBSTEP_MAX_COUNT` = **64**。
- 天体数 = 高ワープ帯の表面窓 **65**。
- → 860 × 64 × 65 = **約 358 万回/フレーム**。演算数 70 なら **2.5 億演算/フレーム**。
  60 fps では 15 G演算/s 相当で、JS では明らかに成立しない規模。**まずここを実測する。**

削減の効き方(3つは独立に効く):

| 施策 | 後の回数 | 比 |
|---|---|---|
| 事前棄却(7-4) | 358 万回のまま、1回 70 → 10 演算 | **7.0×** |
| 動かない個体を毎 substep 判定しない(passive-warp の 1260 体を最終ステップの1回だけに) | 動く個体 ≈ 30 × 64 × 65 = 12.5 万 + 1260 × 1 × 65 = 8.2 万 ≈ **20.7 万回** | **17×** |
| 表面窓を 101 体へ広げる(2-5 の統一、逆向き) | 358 万 → 556 万回 | **0.64×**(悪化) |

**「動かない個体を毎 substep 判定しない」が最大の効き。** しかもこれは純粋な無駄の除去で、
挙動を1ミリも変えない(状態が変わっていない個体に同じ判定を繰り返しているだけ)。

## 7-6. ②(段3)の副次効果 — Player の弧が余分に踏む歩数

- この帯の刻みは `REENTRY_SUBSTEP_MAX_DT = 1 s`(高度が `REENTRY_SUBSTEP_ALT = 200 km` 以下)。
- 余分な歩数 = (80 km から 45 km まで降りる時間) ÷ 1 s = 35,000 m ÷ |ṙ|。
  LEO 軌道速度 7.7 km/s に対し飛行経路角 γ ≈ 1° とすると |ṙ| ≈ 7700·sin 1° ≈ 134 m/s
  → **≈ 261 歩**。γ が 0.5°〜2° に振れると 130〜520 歩。**実測(降下中の `arcLead`)で置き換える。**
- interactive 枠 = `ARC_STEP_BUDGET 600 × ARC_INTERACTIVE_RATIO 0.5` = **300 歩/フレーム**。
  余分な 261 歩は 1 フレームぶんの予算未満で、降下の 261 秒に分散するので**無視できる**。
- ただし 1 s 刻みでは 1 フレームの伸長が最大 300 sim-s。最高ワープの `simDt` は
  131072 ÷ 60 fps = **2184.5 s/フレーム**なので、この帯では必ず追い越されて積分へ落ちる
  (壊れない。落ちた先が実シミュレーションの細分化そのものなので精度は上がる)。

## 段6 = ③. 判定モードを畳む(**優先度最低**)

①で外に出した判定モードの引数を消し、判定器が自律的に解法を選ぶようにする。

1. 判定器の内部で、その1歩がその天体まわりに掃く角 `θ = |r × v|·h / |r|²` を出す。
2. `r·θ²/8`(2-2-1 の乖離)が要求精度を下回るなら線形の閉形式で答え、上回るなら次数を上げる。
   要求精度は既定値を持ち、必要なら呼び出し側が上書きできる引数にする。
3. 上げる先の候補は**二次**(2-2-2 — 誤差 O(h³)、摂動を無視すれば軌道は二次曲線なので
   ここで大半が取れる)。三次エルミートは残すか置き換えるかを実測で決める。
   **具体的な解法は未定** — 二次の場合、球中心との距離が t の4次式になるので、
   制御点凸包での棄却 + 数回の反復で根を詰める形が素直。
4. 合格条件は、①の時点の両モードそれぞれと同等以上の精度が、モード指定なしで出ること。
   2-2-2 の θ の表が判定の妥当性を確かめる目安になる。
