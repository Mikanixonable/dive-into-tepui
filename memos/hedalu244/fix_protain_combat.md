# タンパク質敵の見た目と、判定・発射を一致させる

調べたのは 2026-09-19 で、`5ef4194d3` の時点。`path:line` もこの時点のもの。段 5.5-9 で進行側の行は変わるので、着手時はコードで引き直す。

## 目的

mikanixonable が PR #82(2026-09-16)で挙げた問題の主要因を特定する。問題は「照準している部位と、実際に発射・命中する部位が見た目で一致しない」というもの。そのうえで、アーキテクチャの例外を増やさない直し方を決める。

**「一致しない」は体験の報告で、測られていない。** 当たり判定・部位の球・銃口を画面に出すデバッグ機能は無い。

PR #82 は揺らぎを原因とみなし、規則に表示中のアンカーを読ませた。段 5.5-9 はこれを戻している(R4 違反だったため)。主要因がほかにある可能性は評価されていない。たとえば、揺らぎより判定形状の近似のほうが大きい、潜在バグがある、といった可能性である。

## 前提: 段 5.5-9 の後の状態

- **銃口と被弾部位の選択は、部位の静止座標から決まる。** View は読まない。
  - 静止座標は、アセットの `sites[].position` [Å] に `coordinateScale` と `ENEMY_MODEL_SCALE` を掛け、個体の位置と姿勢で変換したもの。
  - 被弾部位は、着弾点を半径の内に含む部位のうち、中心が最も近いものになる(`protein-combat-state.ts` の `closestSite`)。
- **部位マーカーと結合線は、表示中の揺らぎに追従する**(`ProteinEnemyView.siteMarkers` → `ProteinRuntime`)。
- **当たるかどうかは、静止した球の数珠つなぎで決まる**(`protein-sphere-collision.ts`)。表示形態にも揺らぎにもよらない。
- **SPEC の記述は、INVARIANTS §3「表示のためだけに持っている量(見た目の揺らぎ…)は判定に入らない」だけ。** PROTEIN・RENDERING にあった揺らぎと判定の個別の文は削った。削った範囲は、段 5.5-9 の `docs(spec):` の commit を見る。

## 仕組み(表示側。段 5.5-9 では変わらない)

```
ProteinEnemyView.syncModel(表示フレーム)              … 毎フレーム、描画の同期
├─ 投影直径 [px] から LOD: near ≥160 / medium ≥40 / far ≥8 / それ未満は marker(±15% の不感帯)
├─ ProteinMotionController.sampleAt(表示時刻, LOD, phase)          [CPU]
│  └─ 24 モードの OU 過程を、敵の seed と時刻から決定的に求める(protein-brownian-motion.ts)
│     ├─ 前回から 128 標本(2.13 s)以内の前進 → 逐次に進める  O(M·Δ)
│     └─ 初回・巻き戻し・それより大きな飛び → 組み直し  O(M·H)、H = 1,579
└─ ProteinRuntime.syncVisual
   ├─ 係数を GPU へ → compute が残基ごとに Σ 係数×モード変位   O(R·M)   [GPU]
   └─ 部位の残基だけ CPU でも同じ和を取る → マーカーと結合線
頂点シェーダ: 頂点ごとに残基2つの変位を補間して足す  O(V)。M にも LOD にも依らない
```

- M = 24(4 本が集団運動、20 本が局所運動)。
- H は ln(10⁴) × 60 Hz ÷ 最も遅い緩和率 0.35/s で決まる。
- 振幅は、5i4r とルビスコが B-factor による相対較正、ミオグロビンと ATP シンテターゼが表示用に選んだ値。表示の倍率は、集団運動 0.55、局所運動 0.2 である。

| 処理 | 計算量 | 実測・規模 | LOD で減るか |
| --- | --- | --- | --- |
| OU を逐次に進める | O(M) / 標本 | 1 フレーム分で 4〜8 µs | medium は 30 Hz、far は 15 Hz へ間引く |
| OU の組み直し | O(M·H) = 正規乱数 37,896 個 | 4.8〜5.8 ms | 減らない(marker の段だけ呼ばない) |
| 部位アンカーの投影 | O(部位の残基数 × M) | 1 µs 未満 | — |
| GPU compute | O(R·M) | 1 回あたり 3,672〜113,112 積和 | 発行回数だけ減る。モード数の打ち切りは係数を 0 にするだけで、ループは 24 モードを全部回す |
| 頂点シェーダ | O(V) | 1 体あたり 1 万〜27 万頂点 | 減らない |

- 飛び幅ごとの標本化のコスト(5i4r): 1/60 s で 7.5 µs、1 s で 190 µs、2 s で 341 µs、2.2 s 以上で 4.8〜5.8 ms。
- 実測が履歴に残っているのは、compute 化の前後だけ(`e6aae0518`: 6n2y で CPU 0.24 → 0.003 ms、転送 75,408 → 96 B)。LOD の medium・far・marker の段の負荷は測られていない。

## 主要因の候補(どれも未評価)

1. **判定形状の粗さ。** 球の半径の上限は、外接半径の 1/4(`SPHERE_RADIUS_DIVISOR`)。5i4r では球 1 個が半径 19 m ある。見えている構造の外で当たる距離(最大 15.6 m)は、部位アンカーの揺らぎ(最大 6.3 m)より大きい。
2. **揺らいだ主鎖のはみ出し。** 5i4r では、見えているリボンの一部が判定形状の外を最大 10 m 動く。そこを弾が抜けても当たらない。
3. **部位の球が見えない。** 部位の半径は 9〜14 Å(5i4r で 11〜17 m)で、画面にはマーカーの点しか出ない。球の境界の近くでどの部位に割り振られたかは、HP の減り方でしか分からない。部位の球の外への命中は、integrity だけを削る。
4. **部位アンカーの揺らぎ。** 5i4r で最大 6.3 m(上の表)。
5. **潜在バグの疑い(どれも確かめていない)。**
   - 着弾点を模型座標へ戻す単位が合っているか。`proteinLocalImpactPoint` は root の倍率で割り、部位の位置と半径は `coordinateScale` を掛けて比べている。
   - 判定は substep の時刻、弾と閃光の表示は表示時刻で行われる。時間加速中に、見える着弾位置と判定の着弾位置がどれだけ離れるか。
   - 発射直後の弾が、撃った敵自身の判定形状の内側から出ていないか。銃口は部位の位置で、判定の球の内側にある。
   - 表面・分子模型の表示が主鎖の判定形状より外へ張り出す量。これは測っていない。判定形状が覆うのは、主鎖とリボン断面の余裕 1.0 Å だけである。

## 調べ方

1. **見えるようにする。** 判定の球、部位の球(静止位置)、銃口を描く、一時的なデバッグ描画を入れる。デバッグコードは最小にする。定数の直書きで、1 か所から 1 回だけ描き、URL クエリや分岐や設定は足さない。残すなら、機能として `/modify-feature` を通す。
2. **再現の条件を揃える。** 5i4r(陣形の攻撃役)を、ガンサイトで 1 km 前後から撃つ。表示形態はリボンとシルエットの両方で見る。
3. **候補ごとの寄与を分ける。**
   - 揺らぎの表示を切っても一致しないなら、揺らぎは主要因でない。
   - `SPHERE_RADIUS_DIVISOR` を上げて判定の球を細かくしたとき、ずれがどう変わるかを見る。
4. **潜在バグの疑い(候補 5)を、テストか計測で一つずつ確かめる。**
5. **主要因が決まったら、直し方を選んで `/modify-feature` を通す。** 仕様をどう変えるかはユーザーに問う。

## 直し方の候補(アーキテクチャの例外を増やさない形)

**守る制約**
- 進行は View を読まない(ARCHITECTURE R4)。
- 揺らぎを進行へ入れるなら、「敵と時刻で決まる関数」を、モデル層が import できる場所に置く。表示は、その値を宣言として受ける(R6・R7)。
- 進行が毎 substep 揺らぎを進めて mutable な値として持つ形は勧めない。理由は2つある。
  - コストが時間加速の倍率に比例し、128 標本を超えると組み直し(約 5 ms)になる。
  - 表示時刻(時刻スライダー)の値を出せない。

**候補**
- **判定形状を細かくする。** `SPHERE_RADIUS_DIVISOR` を上げる。球の数が増えるぶん、接触の判定が重くなる。仕様の変更は要らない(PROTEIN.md「衝突形状は構造の隙間を埋めてよい」の範囲)。
- **揺らぎを世界に置く。** 判定形状まで揺らがせる。部位だけでは、はみ出し(最大 10 m)が残るので一致しない。
  - 揺らぎの関数(標本化とモードの投影)をモデル層へ移す。モーションのデータは、すでに `ProteinSemanticSource.motion` としてモデル層に届いている。
  - **標本化のアルゴリズムを、任意の時刻を安く求められるものへ替える。** 規則は発射と被弾の時刻に飛び飛びに問い合わせるので、いまの OU では 1 回ごとに約 5 ms かかる。
    - 候補はスペクトル合成。モードごとに、OU のスペクトルから周波数を引いた正弦波を F 本足す。
    - M = 24、F = 16 で、任意の時刻が 17〜50 µs(実測)。状態を持たない純関数になり、振幅に上限がつく(広域判定に要る)。
    - 揺れの質感が変わるので、render-lab で目で確かめる。
  - 判定の球ごとのモード変位を、アセットごとに 1 度表にする。接触の hook はすでに `selfState.t` を受けているので、掃引の両端で球の中心を動かせる。5i4r で 1 回 1,680 積和。
  - **seed を個体 id に揃える。** いまは生成時が `request.name`(`W1-ATTACKER` など、`protein-enemy.ts:160`)、復元時が個体 id(`:175`)なので、セーブをまたぐと揺れ方が変わる。
  - SPEC は INVARIANTS §3 を含めて書き直す。次の2つも決める必要がある。
    - 揺らぎの表示のオフ: オフにすると、表示が世界から揺らぎの分だけずれる。
    - critical の表示だけの 1.5 倍: 世界の振幅も上げるか、増幅をやめるか。
  - 規模は約 15 ファイル。
- **揺らぎの振幅を下げる。** 5i4r の表示の倍率(集団運動 0.55、局所運動 0.2)を下げる。
- **部位の球や命中した部位を見せる。** UI の仕様の変更になる。

## ついでに見つかったこと(表示側で、この件とは独立)

- **時間加速が 256 倍以上のとき。** 表示時刻が 1 フレームに 4.27 s 進むので、marker 以外の段の敵は毎フレーム OU を組み直す。1 体あたり約 5 ms かかる。計算上の見積りで、実機では測っていない。
- **LOD が削っている負荷は小さい。** モード数の打ち切りは、GPU の計算量を減らさない。計算量で効いているのは、組み直しを避ける marker の段だけである。
- **marker の段は静止構造ではない。** 変位 0 ではなく、最後に far で求めた変位のまま凍結する(`cd65a7206` 以降。`protein-runtime.ts:128`、`protein-enemy-view.ts:146`)。
- **seed がセーブをまたいで変わる**(上記)。表示だけの問題なので、揺れ方が変わるだけで済んでいる。
- **RENDERING.md「タンパク質敵の微細運動」(618〜633 行)は、PROTEIN.md「構造の揺らぎ」とほぼ重複している。** 段 5.5-9 の削除のあとに何が残るかを確かめ、重複をどちらかへ寄せる。
