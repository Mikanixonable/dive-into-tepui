# CODING_RULE v2(素案)

## この文書について

コーディング規約の一次情報を1本にまとめる。統合元は次の4つ。

| 統合元 | 扱い |
| --- | --- |
| `.claude/skills/refactor/SKILL.md` | **基準。** ほぼ全文を採用する |
| `.claude/skills/comment/SKILL.md` | ほぼ全文を採用する(第I部 7) |
| `.claude/skills/refactor-fixed/SKILL.md` | 取捨する。一般則は第I部へ、確定判断は第II部へ、個別の実装解説と経緯は第IV部へ |
| `DEVELOP/CODING_STYLE.md` | 取捨する。表記規則は第I部 8 へ、コードから逆算しただけの分類は第III部へ |

4つに分ける。

- **第I部 汎用コーディングスタイル** — 他プロジェクトへそのまま流用できる。踏襲すべき慣習を含む。
- **第II部 本プロジェクト特有で確定した判断** — このプロジェクトのドメインと構造に固有。確定済み。
- **第III部 暫定的な慣習・判断** — まだ確定していない、または実態と乖離している。破ってよいわけでは
  ないが、**これを根拠に設計を決めない。** 確定したら第I部か第II部へ移す。
- **第IV部 不要と判断した事項** — 統合元にあったが採らないもの。理由つき。**Step2 で削除する。**

各節の見出し末尾の `(出典: …)` は Step1 のレビュー用の注記で、Step2 で落としてよい。

# 第I部 汎用コーディングスタイル

## I-1. 基本原則 (出典: /refactor 基本原則、refactor-fixed §5)

可能な限り単純で簡潔な実装を求める。長大なファイル、非自明なコードは人間にもエージェントにも
読めないため、簡潔になるように書き直すべきである。

要求した仕様を超えて実装が複雑になるような判断を勝手に追加すべきでない。実装が自明であることは、
仕様が自明であることと相関する。非自明な実装は非自明な挙動を生み、悪いUXに繋がる。

いついかなる時も、好ましくないパターンを好ましいパターンに書き換えることは歓迎される。
好ましくないものは作るべきでないし、残すべきでない。

### 優先順位

判断が競合したときは、この順で優先する。

1. **正しさ**(仕様どおりに動くこと。本プロジェクトでは物理的正確さ — 第II部 4)
2. **実装の適切さ**(概念が自然な形で実装に現れていること。責務分割・疎結合・命名・数式の素直さ)
3. **実行時パフォーマンス**
4. **変更コスト**

- オーダー改善は定数倍高速化より優先度が高い。計算量が爆発する実装が見つかったら、実測できたか
  否かに関わらず改善する。可能なら爆発する状況を再現・実測してから改善し、効果を確認する。
- 定数倍高速化は、実測して無視できない効果があるときだけ行う。高速化のために実装が長大化したり
  責務分割が不自然になるのは望ましくない。**一旦高速化を忘れてリファクタリングした後**、必要に
  応じてメモ化などを行う。
- **「現状のコードがそうなっているから」は、変更しない理由にならない。** 将来書き換える箇所を
  減らせるなら、今、積極的に大きく書き換える。ただし一度に全部を書き換えると原因の切り分けが
  困難になるので、大きな変更は小さな段階に分け、各段階で問題が生じていないことを確認して進める。

## I-2. モジュール化 (出典: /refactor モジュール化、refactor-fixed §1 の一般則)

良いモジュール化とは、それぞれが明確に分割された単一の責務を持った、疎結合なモジュール群である。

悪いモジュール化:

- 責務が大きすぎるモジュール、関数。
- 長大なファイル、モジュール、関数。**モジュールは200行、関数は100行を基準とする。**
- 責務がないモジュール。例えば不要なたらい回しをするだけの薄すぎるラッパーなど。
- 1箇所からしか参照されていない小さな関数を、再利用性や責務の違いといった正当性なしに別モジュール
  へ置くこと。正当性が無いなら、たらい回しモジュールと同じ悪いパターンである。
- 実装の重複。同じ処理が複数箇所に分散して書かれているもの。
- 早急な一般化。

責務の有無とコードの規模には多少の相関はあるが、絶対ではない。どんなに行数が少なくても、責務を
持っているのであれば単独のモジュールとして維持すべきである。行数が長くても無駄なたらい回しを
しているだけであれば、削除すべきである。

### 責務が複数モジュールにまたがるとき

**「所有者が複数モジュールにまたがるから、上位のオーケストレータが持つ」は理由にならない。**
選択肢は2つだけ。

1. どちらか一方の所有者へ寄せる。
2. **その横断そのものを責務とするモジュールを1つ立てる。**

上位はそれを1行呼ぶだけになる。この判断に例外はない。

### トップレベルに実装を書かない

エントリポイントとオーケストレータ(本プロジェクトでは `main.ts` / `game.ts`)に書いてよいのは
**サブシステムの生成・配線と、呼び出し順の決定**だけ。条件分岐を伴う判断、状態の組み立て、
一覧表の構築、座標計算は、たとえ1箇所からしか使われなくてもそこに置かない。

**オーケストレータに `for` 文を書かない。** 配列を回したくなったら、その配列を持つモジュール
(またはそれに近い責務を持つモジュール)にその処理をさせる。回す対象を持たないモジュールが
回し方を知っているのは、その処理が本来そちらの責務だという徴候である。

## I-3. データ構造 (出典: /refactor データ構造)

良いデータ構造とは、少ないステート設計と、適切に構造化されたデータである。

悪いデータ構造:

- 正データが複数箇所に分散、重複しているデータ。
- 軽微な計算で求まるものをステートとして持っているデータ。
- 複数箇所が一定の整合性を保つことが要求されるデータ。メモ化アルゴリズムなどでどうしてもそのように
  扱わなければならない場合は、適切に隠蔽しなければならない。**整合性保持責務の漏洩は重大な違反。**
- 同一の意味、同一の情報量を持つ型を複数作ること。これは重複実装である。

### 不在は `T | null` で表す — 代役も、別の真偽値も立てない (出典: refactor-fixed §21bis)

**あるものが「無い」ことは、その値自身の `null` だけで表す。** 型の上で常に非 null に保つために
代役の空インスタンスを置くと、「本当にあるか」を別の真偽値で持つ形になり、持ち物があるのに
「持っていない」と言う嘘のフラグが生まれる。

- **受け手が「無ければ何もしない」を自決できるなら、呼び出し側にガードを書かせない。**
  `if (x) receiver.f(x)` は、受け手の引数を `T | null` にして先頭で早期 return できるなら二重判定。
  自決できないのは、受け手がその型をそもそも知らない場合だけで、そのときだけ呼び出し側にガードが残る。
- **「出すか」の真偽値引数は、値自身を `T | null` にできるなら潰す。** `update(plan: Plan | null)` は
  `null` が「出さない」を表すので `show` は要らない。
- **所有者とその持ち物を別々の引数で受けない。** 所有者を受け取る側は `Owner | null` を受け、
  持ち物は `owner.thing` から自分で引く。両方を受けると、ある所有者と別の所有者の持ち物という
  あってはならない組を渡せる引数の形になる。
- **既定値で埋めてよいのは、そのゼロ値が単位元として意味を持つときだけ。** 速度差の基準のゼロは
  「基準なし」として意味を持つが、位置のゼロは「原点にいる」という別の意味になる。たまたま実害が
  出ないことを根拠に既定値で埋めない。
- **実体の死は除去であって、亡骸を配列に残したまま別の真偽値で「無い」と言わない。** 亡骸を残すと、
  その配列を回る全ての読み手が「これは受け取ってよい相手か」を判定し直すことになり、判定を1箇所
  でも忘れると死んだ相手に対して処理が走る。**亡骸に用があるように見えるモジュールがあるとしても、
  そのために実体の生存期間を延ばさない** — 用がある側が、自分が要るものを自分で持つ。

## I-4. 値の生成と寿命 (出典: /refactor オブジェクトの流用の禁止、refactor-fixed §13)

### オブジェクトの流用の禁止

同一の参照の中身を丸ごと書き換えて別用途に転用するのは禁止。基本的なデータ型は極力 immutable に
設計するべき。状態を孕んで immutable にできないオブジェクトに関しても、丸ごと中身を差し替える
メソッドは禁止。そのような操作が発生するときは、ほぼ確実にオブジェクトの意味自体が変化しているので、
インスタンスを作り直すべきである。例外は、可読性を犠牲にするに足る相当のパフォーマンス上の理由が
ある場合のみ。

### 二段初期化を作らない — 初期状態はコンストラクタで受ける

生成後に「初期化メソッドをもう一度呼ばないと使えない」形を作らない。呼び忘れが型で守られない。
リソースの注入が必要なら、注入は**1つのメソッドに1回だけ**にし、あるサブクラスだけが要る
リソースでもその引数を増やす。サブクラス固有の初期化は `super(...)` の後に書く。

**状態も同じで、初期状態はコンストラクタ引数で受ける。** 生成後に中身を丸ごと差し替えるメソッド
(`restore` の類)を作らない。既定状態を組んでから上書きする形は、「上書き前の状態」という誰も
望んでいない中間状態を必ず1つ作り、その間に走る処理が何を見るかを非自明にする。

- 新規に始めるのか、保存状態から再開するのかは、**判別共用体の引数1つ**で表す。両方を別引数で
  受けて片方を無視しない。
- 保存状態のロードは**インスタンスを作り直す**ことで表す。実行中のインスタンスへ状態を押し込む口を
  公開しない。
- 依存リソースが後から来るためコンストラクタでは組めない持ち物があっても、**保存由来の値自体は
  コンストラクタで受けて控えておく。**

## I-5. 命名 (出典: /refactor 命名、CODING_STYLE §1/§3/§4/§5/§6/§7)

良い命名とは、振る舞いと扱い方が明快で、混同の恐れがなく、適切な長さの命名である。

悪い命名:

- 類義語の混雑。同じものを異なる言葉で指している命名。
- 曖昧な区別。区別すべきものを同じ名前で指す命名。
- 漠然とした命名。`process` や `data` などの命名は意味を持たない。
- スコープの狭さ、混同のおそれのなさに対して、不必要に長大な命名。スコープが十分に狭ければ、
  前述の漠然とした命名も許される。一行のラムダ式規模であれば一文字変数名も許される。

### 表記

- クラス、interface、type、enum は `PascalCase`。
- 関数、メソッド、getter、setter、フィールド、変数、引数は `camelCase`。
- ファイル名とディレクトリ名は `kebab-case`。
- 固定値として共有するモジュール定数と static 定数は `UPPER_SNAKE_CASE`。単に `const` で宣言した
  ローカル変数は `camelCase`。
- 略語は `camelCase` / `PascalCase` の中では一つの単語として扱う(`bodyId`、`toEci`、`projectToNdc`、
  `setRcs`、`jdTdb`)。`UPPER_SNAKE_CASE` では略語も大文字にする(`SIM_EPOCH_JD_TDB`)。
- JavaScript、Web API、ライブラリが定めた表記(`URLSearchParams`、`getUTCDate`、`WebGPU`)は変更しない。

### 名前が表す文法と意味

- 名前と所属先を合わせて「何が何をするか」が分かる名前にする。
- モジュール関数では、原則として動詞の対象を名前に含める。
- メソッドでは、対象がクラス自身であることが明白なら対象を重ねない(`plan.clearPlan()` ではなく
  `plan.clear()`)。
- `process`、`execute`、`handle`、`change` のように対象も結果も示さない動詞だけの名前を避ける。
- `update`、`sync`、`render`、`clear`、`reset`、`dispose` など、意味が所属先の責務から一意に決まる
  標準操作は動詞だけでもよい。
- 同じ概念には同じ語を使う。既存の正本となる名前がある場合、類義語を新設しない。
- 一般語より、その領域で意味が確立した語を優先する。`integrate`、`interpolate`、`project`、`collide`
  などの専門語を曖昧な一般動詞へ置き換えない。

### 基本動詞

同じ操作に複数の動詞を並立させない。ここにない専門動詞は、既存の語と意味が重複せず、動作をより
正確に表す場合に使える。

- `get` — 保持済みの値を副作用なく返す。 / `find` — 検索する。見つからない結果を取り得る。
- `compute` — 入力から値を副作用なく計算する(`calculate` を新設しない)。
- `is` / `has` / `can` — boolean または型述語を返す。
- `create` — 新しい値・インスタンスを作る(`make` を新設しない)。 / `generate` — 乱数・規則・入力集合
  から複数または手続き的なデータを生成する。
- `set` / `add` / `remove` / `clear`(空にする)/ `reset`(初期状態へ戻す)。
- `handleX` — 入力またはイベント `X` を処理する(`handle` だけでは使わない)。
- `onX` — `X` が起きたときに呼ばれるコールバック(プロパティ)。**`handleX` と `onX` を同義に使わない。**
- `takeX` — `X` を返すと同時に保管場所から取り除く。
- `dispose` — GPU資源、DOM、イベント購読など、そのオブジェクトが所有する資源を解放する。
- `toX` / `fromX` — 変換先または変換元を名前に含める。

フレーム処理で予約する動詞(`render` / `update` / `build` / `sync`、`draw` の禁止)は第II部 2。

### boolean

- `isX` で始まるものは boolean または型述語だけを表す。
- `isX` は状態、`hasX` は所有・存在、`canX` は実行可能性。
- `shouldX` は「Xするべき」という評価結果。現在の状態には使わない。
- `forceX` は、通常の省略・キャッシュ・選択条件を明示的に無視させる指定にだけ使う。選択肢が二つを
  超えるなら boolean ではなく union を使う。
- boolean は原則として肯定形。ただし非表示・抑制・禁止など**否定状態そのものが領域上の意味を持つ**
  場合は `hidden`、`suppressed`、`blocked`、`disabled` を使える。
- `isNotX`、`hasNoX` のような否定接頭辞は使わない。

### 単位

- 内部の正本は SI 単位に統一する。
- 外部データ、ブラウザAPI、UI入出力では境界に自然な単位を使える。その場合は `Deg`、`Days`、`Ms`、
  `Au` などを名前に含め、**境界で一度だけ SI へ変換する。**
- 同じスコープに異なる単位が共存する場合は `Sec`、`Ms`、`M`、`Km`、`Mps`、`Mps2`、`Rad`、`Deg`、`Kg`
  などのサフィックスで区別する。
- 型・契約・狭い数式から単位が一意に決まる場合は、すべての名前へ単位を重ねない。名前だけで十分に
  表せない場合はコメントで `// ECI [m/s]` のように記す。

### コレクションと派生状態

- 複数要素を表す名前は複数形。
- Map はキーが意味上重要なら `valuesByKey` の形(`bodiesById`、`textureByBodyId`)。
- データ構造自体が処理上重要でない限り、`List`、`Array`、`Map`、`Set` を名前に含めない。
- 件数は `Count`、公開または長寿命の添字は `Index`(`Idx` を新設しない)。短いループ添字は `i`、`j`。
- 再計算を避ける保存値は `Cache`、再利用するオブジェクト群は `Pool`、一時計算用に使い回す領域は
  `Scratch`、順序付き待ち行列は `Queue`、変更世代は `Revision`。
- `items`、`data`、`list` のような一般名は、対象が所属先または狭いスコープから一意に分かる場合だけ。

### クラスの役割接尾辞

**単に名前を具体的に見せるために `Manager`、`System`、`Service` を付けない。** 接尾辞は、そのクラスが
何を所有し、いつ動くかを表す場合だけ付ける。複数の役割に見える場合は、名前を増やすのではなく
クラスの責務分割を検討する。個々の接尾辞の定義は第III部 1(まだ運用が固まっていない)。

## I-6. 改名・移動 (出典: /refactor 改名・移動、CLAUDE.md 作業のルール)

**改名は痕跡を残さず完全に置き換える。** 歴史的経緯はコードとコメントの責務ではない(必要なら
git history が持っている)。

- 旧名が 0 件になるまで消す(コードだけでなく文書・スキル・メモも grep する)。
- **「旧」「former」「previously」「〜だった」「(旧 xxx)」と書くのは禁止。** コメント・文書には
  新しい姿だけを記述する。何を何に変えたかは、コードではなく変更セットの報告文に書く。
- 互換のための旧名エイリアス・ラッパー・再エクスポートを残さない。呼び出し側を全部直す。
- 文書の旧名も同じ変更セットで消す。

## I-7. コメント (出典: /comment 全文)

### 大原則

**そのモジュールの責務外のことに言及しない。** コメントもコードと同じく、モジュールの責務外の
ことに触れてはいけない。下の禁止リストのほとんどはここから導かれる。「どのように扱うべきか」
(= そのモジュールが提供する契約 = 責務の内側)は書き、「どのように扱われているか」(= 呼び出し側の
事情 = 責務の外側)は書かない。他モジュールの内部処理・他モジュールの責務の説明も同様に書かない。

**関数の冒頭、モジュールの冒頭のコメントでは、実装詳細に言及しない。** そこで書くのは概観と
インターフェイス(公開責務)であり、内部実装の詳細ではない。当然、他モジュールの内部実装、外部
モジュールでの扱われ方も書かない。

**コメントはコードを読む人(人間にもエージェントにも)の context を消費する。** 書いてよいのは
「コードを読んでも分からないこと」だけであり、それ以外は書かないほうが良い。分量の少なさそれ自体が
価値である。

十分に良い命名・良い設計で書かれたコードは自然言語のように読める。コメントが必要な非自明な
コードは、まず命名や設計が悪さをしていることを疑う。

**言語は日本語に統一する。**(既存が日本語のため。英語のコメントを見つけたら書き直す)

### 書いてよいもの、書くべきであるもの

- **モジュール先頭**: そのモジュールの責務(なにを担当するか)。目安 **5行**。
- **関数・フィールド**: 「なにをするか」「どのように使えばよいか」(引数と返り値、副作用、呼び出し
  規約など)。目安 **1〜3行**。**直前に1行もコメントがない関数・メソッドは、それだけで不足とみなす。**
  例外は自明なもの — 1行だけからなる getter/setter と、本文が空のもの。名前の言い換えにしかならない
  なら、**名前から読み取れない契約**(返り値が null になる条件、破壊する状態、満たすべき事前条件)を書く。
- **数値を扱う変数、定数**: 単位系や座標など必要な情報。`// ECI [m/s]` など。目安 **1行**。
- **関数内**: 「現状なぜそのように実装されているのか」が**相当に**非自明なときだけ。目安 **1行**。
  書いてよいのは次に限る:
  - **安直に単純化すると起きるバグ。** 「この項を省くと発散する」「この順序でないと〜が壊れる」など、
    次に触る人が単純化して壊す道筋が具体的に見えているもの。
  - **複雑な計算式・特殊な条件分岐の意図。** 式や分岐そのものからは読み取れない意味を1行で与える。
  - **安直に想像できる実装とコードが異なり、それが明言された仕様に基づくとき — その根拠。** 明言
    された仕様とは、コメント以外の場所(`DEVELOP/SPEC.md`・`memos/mikanixonable/dev.md` など)に
    書かれているものを指す。
  - **非コメント行が10行以上にわたる中規模以上の関数**において、**文脈**を追いやすくするための
    コメント。実装は数行単位の**意味ブロック**に分割できるはずなので、各ブロックがどのような処理で
    あるのか文脈を追いやすいよう、**数行に1行の頻度で**、ごく簡潔なコメントを追加する。どのように
    実装されているかの詳細ではなく、文脈を与えるのみにとどめる。
- **将来修正すべきこと(TODO)。** 安直に想像できる実装と異なるのに**明言された仕様に基づかない**
  箇所は、潜在的なバグか将来是正すべき箇所である可能性が高い。弁明を書いて済ませず、TODO として
  マークする。

行数は機械的な上限ではなく目安。基準は意味の側にあり、上を超えるときは「本当にその情報が要るか」を
下の禁止リストで確かめる。

### 書いてはいけないもの

以下はすべて **context を圧迫するだけで利益がない**。一切書かない。

1. **どのように実装されているか。** 実装の唯一の正はコードであり、書けば変更のたびに矛盾する。
2. **なにをしないか(否定形)。** 「〜は行わない」「〜には依存しない」「〜を持たない」「〜する必要は
   ない」「〜だけ」「〜のみ」など。責務境界を説明したいなら、そのモジュールが「なにをするか」を書く。
3. **誰が使うか・どこから呼ばれるか。** 呼び出し側の事情はそのモジュールの責務ではない。
4. **現状どのように使われているか。** 継承先での使われ方、現在の唯一の呼び出し元、「いまは使って
   いないが」の類。
5. **過去の実装でなにをしていたか・従来実装との対比。** 「旧」「以前は」「〜だった」「かつては〜して
   いた」「〜より無駄が少ない」。かつてより複雑な実装をしていた痕跡も同様、単純になった今のコードは、
   それ自体で読める。
6. **変更の差分。** 「〜を倍にした」「〜を追加した」「×0.7 でスリム化」。コードは常に「現在の姿」
   だけを語る。何を何に変えたかは変更セットの報告文と git history が持つ。
7. **外部モジュールへ委譲したことの痕跡。** 「〜は X の責務になった」「実体は X が持つ」。
8. **他モジュール・下位モジュールの内部処理の説明。** 責務外への言及。
9. **検討メモ・課題管理文書への参照。** `memos/**.md` の章番号、`BUG_REPORT.md` の項番など。
10. **コメントがコメントを参照する。** 「〜.ts のコメント参照」。
11. **引数名・型から自明な説明の列挙。** `playerPos: 自機の位置` の類。
12. **その場に書かれた実装と同じことを言っているもの。**
13. **実装と矛盾したもの・古くなったもの。**

### 採らなかった実装の弁明

想起しうる他の実装にしない理由を単に弁明として書くべきでなく、以下のいずれに該当するかを明確にする。

- **外部で(人間によって)明言された仕様に基づくなら、その根拠を書く。** 根拠はコメント以外の場所
  (`DEVELOP/SPEC.md`・`memos/mikanixonable/dev.md`)に明言されているものを引用する。
- **明言された仕様に基づかないなら、潜在的なバグか、将来是正すべき箇所である可能性が高い。** 単に
  弁明を書いて済ませず、**TODO としてマークする。**
- **今後の変更でそのような形に書き換える動機がなく、想起しえない実装に言及している場合** — 例えば、
  より複雑で安直でない過去の実装に言及しているだけなら、**その経緯はコメントに書かない。**

### なぜこの方針か

リファクタリングの目的は、**過去の複雑な実装の経緯を知らなくてもコードを理解できるようにすること**
である。経緯をコメントに残すのは、その目的を自分で打ち消す行為でしかない。

そしてこの種のコメントは、**リファクタリングや変更要求でコードを書き換えるたびに増えていく。**
「なぜ変えたか」「前はどうだったか」「他はどうしているか」を書き残したくなるのは、変更した本人の
視点であって、次にそのコードを読む人の視点ではない。**コードを書き換えたら、その変更セットの中で、
自分が書いたコメントをこの基準で必ず見直す。**

新しい冗長パターンを見つけたら、上の禁止リストへ追記する。

## I-8. TypeScript の書き方 (出典: /refactor TypeScript/CSS、CODING_STYLE §2/§8/§9/§11/§12、refactor-fixed §6/§7)

### 関数のシグネチャと副作用

- **「状態を更新し、副産物を返す関数」を作らない。** 副産物である値が欲しいときに状態が更新されて
  しまうと困る。副作用のある void 型(成否を boolean で返すくらいならよい)の関数と、副作用がなく
  返り値が意味を持つ純粋関数のいずれかであるべき。計算関数は何度呼んでも、1度だけ呼んで値を
  使いまわしても同じ結果になる — **呼び出し回数に対する冪等性**があるべき。
- **`ctx` / `context` / `opt` / `params` といった場当たり的なオブジェクト引数を使わない。** 明示的な
  引数か、事前に共有した参照で渡す。
  **`snapshot` という名も同じ理由で禁止。** 「ある瞬間の値をひとまとめにした」という**集め方**を
  説明しているだけで、それが**何であるか**を言っていない — ctx と同型の問題。見つけたら:
  1. 場当たり的な寄せ集めであるべきでない(個々の値を直接渡せば足りる)なら、集める処理自体をやめる。
  2. その時点の値をまとめて1回で扱うこと自体に意味がある(呼び直してはいけない具体的な理由がある)
     なら、集める処理は残してよい。ただし名前は「集め方」ではなく**「何が集まっているか」**で呼ぶ
     (値の型と一致させる — `Attractor[]` を集める関数なら `attractors` / `attractorsAt`)。
- **渡すのはクロージャではなくオブジェクトの参照。** 他モジュールのデータや処理へ届かせたいとき、
  `(t) => other.sample(t)` のような**転送クロージャを作って渡さない。** そのオブジェクトの参照
  そのものを渡す。クロージャ注入は「誰が誰を呼んでいるか」を型からも呼び出し元からも隠し、配線が
  増えるほど実行順序が読めなくなる。
  **いつ渡すかは、使うタイミングで決める。** 毎フレームの呼び出しの中だけで使うなら引数で渡す。
  DOM の pointer イベントなど**フレームの流れの外**で使うなら、コンストラクタで受けて保持する。
- exported 関数と public / protected メソッドは戻り値型を明示する。名前だけで、呼び出し側が実装を
  読まずに結果と副作用を判断できるものにする。

### クラスメンバーと公開範囲

- クラスのメンバーには `public`、`protected`、`private` のいずれかを明示する。コンストラクタにも
  `public` を明示する。
- 外部利用をそのクラスの契約として意図したメンバーだけ `public`、継承先へ提供することを意図した
  ものだけ `protected`、それ以外は `private`。**現在外部から使われていないという理由ではなく、その
  操作を外部へ約束するかどうかで判断する。**
- 外部へ公開するフィールドは原則 `readonly`。mutable な public フィールドは、状態の所有者と変更
  条件を明確にできる場合に限る。
- 状態変更時に不変条件、連動する更新、副作用がある場合は、public フィールドへの代入ではなく、
  状態を所有するクラスのメソッドに変更を閉じる。
- クラスが保持する別オブジェクトを外部へ公開するときは、private フィールドを正本とし、public getter
  から渡す。**公開 getter `name` の正本となる private フィールドだけ `_name` とする。**
  対応する公開 getter / setter がない private フィールドには `_` を付けない。`_` を「private」
  「内部用」「未使用」を一般的に表す接頭辞として使わない。
- コンストラクタ引数を同じ値のままフィールドとして保持するときは、コンストラクタ引数プロパティを
  使う。値の検証、変換、条件付き代入、遅延初期化が必要なときはフィールドを別に宣言する。
- クラスメンバーは機械的なアクセス範囲順ではなく、責務ごとに関連するフィールド、アクセサ、メソッドを
  近くへ置く。

### 未使用引数

- `_name` は、interface・継承・コールバックなど**固定されたシグネチャにより宣言が必要**だが、その
  実装では意図的に使わない引数にだけ使う。自分でシグネチャを変更できる関数では未使用引数を削除する。
- `_` 単独ではなく、`_event`、`_dt`、`_player` のように引数の意味を残す。
- 未実装、実装途中、将来使う予定という理由で `_name` を使わない。使うようになった時点で `name` に改名する。

### 型と不変性

- オブジェクトの公開契約と、クラスが実装できる契約には `interface`。union、intersection、mapped type、
  関数型には `type`。
- 再代入しないフィールド、入力データ型のプロパティは原則 `readonly`。
- 読み取り専用の配列引数と返り値は `readonly T[]`。所有者自身が変更する配列だけ `T[]`。
- 型アサーション `as` と非 null アサーション `!` は、その前提が型以外の仕組みで保証されている場合に限る。
- **網羅性が要る id 型は、具体のデータから `keyof` で自己生成する。** 汎用 API 側に手書きの union を
  書き足す形へ戻さない(第II部 5 が本プロジェクトでの適用例)。

### ファイルと export

- 一つのファイルには原則として一つの主要な公開クラスまたは主要概念を置き、ファイル名を主要 export に
  対応させる。
- default export は使わず、named export を使う。
- `index.ts` による一括再 export は、公開境界として意図的に設計したディレクトリに限る。
- import は、外部パッケージ、プロジェクト内の value import、`import type` の順にまとめる。

### 構文とフォーマット

- `const` を原則とし、再代入が必要な変数だけ `let`。**`var` は使わない。**
- 配列 like なものの処理は、イテレーターが存在すれば `for...of`、存在しない場合のみ `for (;;)`。
  `filter` / `map` が適している可能性があればそちらを使う。**`reduce` は総和を求めるなどの単純な
  場合を除き、使わない。**
- インデントは空白2文字、タブを使わない。文字列は原則シングルクォート。文末にセミコロン。
  複数行の配列・オブジェクト・引数・型引数には末尾カンマ。
- 一行には一つの文または一つのメンバー宣言。一行120文字を目安とし、名前や文字列を不自然に分割せず、
  意味のまとまりで改行する。
- 一行のガード節では波括弧を省略できる。複数の処理を持つ条件分岐では波括弧を使う。
- 数値に領域上の意味、単位、複数の利用箇所がある場合は名前付き定数にする。短い数式に固有の係数は
  数式の近くに置ける。

### CSS

- CSS は CSS ファイルに書き、コンポーネント側からはクラス名を指定するのみとする。
- CSS では細部までクラス名で指定するのではなく、変更されにくい文書構造に対しては子要素セレクタに
  よって指定する。

> **本プロジェクトでは適用されていない。** HUD の CSS は TS 内の文字列として注入されており、
> その運用規約は `DEVELOP/DESIGN-RULES.md` が正本。第III部 2 を参照。

## I-9. 責務分割の見つけ方 (出典: /refactor 責務分割の見つけ方、refactor-fixed §4/§8/§18)

**関数名やコメントの自然言語的な関連性には注目せず、依存関係だけに注目する。**

- クラス外から情報をもらいまくっていて、クラス内の情報に全然手を付けていない関数は、置き場所が
  適切でない懸念がある。
- 特定のクラスが常にある情報を外部からもらっているとき、その情報はそのクラスに参照コピーなどで
  事前に共有しておくべき懸念がある。特にその情報が外部で使用される頻度が低いときには、正所有権を
  そのクラスへ移動するべき懸念がある。
- 異なるクラスにまたがって存在する複数の情報が頻繁にセットで受け渡されているとき、その2つの情報は
  同じクラスに配置されるべき可能性がある。
- 漠然とした多数の情報がひとつのクラスに入っていて、関数ごとに一定のパターンが見られないときは、
  そもそもそのクラスの責務が定まっていない可能性がある。
- 外部から一度しか呼ばれていない関数は、本当にそこで処理を区切るべきだったのか熟考する必要がある。
  形式的には、多数の引数や ctx 引数を受け取っている関数は I/F の切り方に失敗している可能性がある。
  意味的には、クラスオブジェクトとして強い独立性を主張できない限り、疑いの余地がある。
- 類似した形の式、類似した形の処理が異なるモジュールに分散して書かれているときは、重複実装の疑いが
  ある。

### a と b の相互作用の帰結は、a と b の責務

「2つの物体が相互作用したときに何が起きるか」を、相互作用を**検出した**モジュールにも、まして
オーケストレータにも書かない。**当事者それぞれが「自分が受けるもの」だけを書く** — 相手が受ける
ものは相手が書くので、二重に効くことも抜け落ちることもない。検出側は当事者を見つけて両者へ相互作用
の記述を渡すだけで、帰結を一切知らない。**`a === X && b instanceof Y` のように当事者の型を検出側や
オーケストレータで分岐するコードは、この境界が破れているサインである。**

### 「たまたま」同時に切り替わるフラグは別個にする

一つのフラグによって本質的に異なる多数の挙動が切り替わる形は、責務の疎結合を妨げる。「たまたま」
一致しているだけのものは別個のフラグに分離し、同時に切り替える必要があるなら、**切り替える側
(トグラー)を一箇所に置いて両方を書き換える**(I-2 の2番目の選択肢と同じ形)。

### 複数の入力元が書きうる量は、正本フィールドを読む

**ある量を複数の入力元(手動操作・自動制御など)が書きうるとき、その量を消費する側(演出・音・
表示)は、対象自身が持つ正本フィールドを直接読み、特定の入力元が持つ表示専用の派生状態には
依存しない。** 派生状態を読む形にすると、その入力元経由でしか書かれない値を消費側が前提にして
しまい、別の入力元が同じ量を動かしても何も現れない、という食い違いが起きる。

段階的なプリセットを持つ入力元と、段階を持たない連続出力の入力元が同居しうるなら、消費側が読むのは
**両方を同じ式で表せる連続値**(「何段目か」ではなく「全開に対する比」)にする。

## I-10. 重複実装の禁止と早急な一般化の分かれ目 (出典: /refactor)

判断基準は **共通化したコードを今後も使う「可能性」があるか**。参照箇所の数ではない。

- **1箇所からしか参照されていなくても、** 一般化した側を今後使う可能性があるなら、あるいは巨大な
  責務を分割するためなら、**分割する。**
- **2箇所以上あっても、** それらが個別に調整されうる要素なら、多少の共通実装があっても**一般化しない**。

**共通化した側が変更された際に、参照側の挙動も変更されるべきであるか** で判断する。

これはコードからは判別できない。将来実装される可能性のある機能を知る必要がある。

1. `DEVELOP/SPEC.md` の「実装される可能性のある機能」節を見る(決定事項とは分けて記録してある)。
2. そこで決まらないなら **ユーザーに問う**。推測で一般化しない。
3. ユーザーが「実装するかもしれない」と言及したものは、**決定事項と区別できる形で SPEC.md の同節へ
   記録する**。次回以降の判断材料になる。

既に決着した論点は第II部 9(一般化しないと決めたもの)。そこに載っている論点は再検討しない。

## I-11. 再計算の抑制とキャッシュ (出典: refactor-fixed §20)

再計算を省く判定(キャッシュキー・参照同一性ガード・変更世代)を書くときは、**そのキーが結果を
決める入力を漏れなく含んでいるか**を、キーではなく**計算の側から**確かめる。漏れた入力は「変わった
のに古い結果を返す」形で表面化し、しかも表示が壊れるだけなので気付きにくい。

- **間引きや粗さに依存する閾値は、現在の設定値ではなく、その列自身が記録している粗さから引く。**
  設定を変えた瞬間に、既に積んだ列の粗さと閾値が食い違い、正しい列を破棄し続ける。
- 連続量を比較して「変わっていない」と判断するときは、**列が伸びても動かない点**で評価する。評価点が
  動くと、入力が静止していても値が動き、抑制が効かなくなる。
- 参照同一性で判定する側は呼び出し側にも規約が要る — 中身が空のフレームでは毎回新しい `[]` ではなく
  共有の空配列を渡す。

## I-12. GUI と表示物の所有者 (出典: refactor-fixed §12 の一般則)

> **GUI は、その GUI が書き換える状態の所有者が持つ。所有者が1つに定まらない GUI は、GUI の方を
> 分割する。** 表示・非表示も所有者が自分の `sync` で押し出す。**GUI の見た目を維持することを
> 制約にしない。**

### 物体に付随する表示物は、その物体自身がフィールドとして持つ

**1つの物体に1つ付く表示物**(軌道線・軌跡線・マーカーなど)は、その物体自身が `T | null` の
フィールドとして持ち、自分の `sync` の中で世話をする。**外部に `Map<Entity, T>` や配列を置いて
対応付けるモジュールを作ってはいけない。** 表示しないものは `null` にすればよく、生成・破棄・描画の
判断はすべて持ち主の中で閉じる。

対応付けだけを責務とするモジュールは、持ち主が既に持っているはずの参照を外から作り直しているだけで、
生存期間の管理を二重に持つ。

### 相対的にしか意味を持たない値は、1箇所の表で割り当てる

透明な線どうしの前後は描画順でしか決まらず、同値だと不定になる — つまり描画順は線どうしの相対関係
でしか意味を持たないので、**各線が自分の値を単独で決めてはいけない。** 唯一の割り当て表を1箇所に
置き、線はその値をコンストラクタ引数として受け取る(生成後に書き換えない)。

### 重なり順はレイヤと DOM 順だけで決める

**個々の GUI が自分で z-index を持ってはいけない。** 固定レイヤの並びが唯一の正本で、z-index を
割り当てるのはそのモジュールだけ。GUI の所有者が決めるのは自分がどのレイヤの子になるかだけで、
同じレイヤ内の前後は DOM 順、最前面化は `bringToFront()` の呼び出しだけが動かす。

### 排他選択の走査範囲に DOM の親子関係を流用しない

「同じ列の中で1つだけ選択状態にする」実装で、`parent.querySelectorAll('button')` のような DOM 検索を
排他の範囲にしない。同じ親に**独立した状態を持つ別のボタン**が同居した瞬間、それも一緒に解除されて
しまう。排他の範囲は、そのグループのボタンだけを入れた配列として明示的に持つ。

## I-13. デバッグ用コード (出典: CLAUDE.md 作業のルール)

**デバッグ用のコードは、頼まれたことだけを、頼まれた形でそのまま書く。** デバッグ用コードの価値は
「何が起きてほしいかがコードを読んだだけで自明」であることにあり、それを損なう実装は本番コードの
過剰実装より悪い。

よって以下は**要求されない限り一切書かない**: URL クエリ・環境変数・設定値による分岐、有効/無効の
切り替え、件数や強度のパラメータ化、毎フレーム走る仕掛け、状態(カウンタ・フラグ・「一度だけ」の
保守)、失敗時のフォールバック。

値は定数を直書きし、呼び出しは1箇所から1回にする。**「デバッグしやすいように気を利かせる」判断
そのものが要求の逸脱にあたる。**

## I-14. 仕様書とコメントの分離 (出典: /refactor 仕様書)

良い仕様書とは、適切な粒度で「どのように振舞うべきか」が書かれたものである。

仕様書はコメントとは分離される。**コードが「どのように振舞うか」を記述し、仕様書が「どのように

## II-1. `Game` / `main.ts` はロジックを持たない (出典: refactor-fixed §1)

一般則は I-2「トップレベルに実装を書かない」。本プロジェクトでの適用:

- **`Game` 自身の状態と、それを切り替えるだけのメソッドは配線の一部**として残してよい(`isPaused` と
  `pause`/`resume`)。分岐も組み立ても持たず、自分のフィールドを書いて各所有者へ1行ずつ知らせるだけの
  ものは、外へ出しても薄すぎるラッパーにしかならない。境界は行数ではなく**分岐と組み立ての有無**。
- **`Game` に「どのステージか」の分岐を書かない**(II-8 の帰結)。
- 横断そのものを責務とするモジュールを立てた実例: `ViewManager` / `MapContextActions` /
  `FrameControls` / `ActivePlayerController` / `DisplayWindowManager` / `Docking`。

### メタのフェーズ管理を `game/` へ漏らさない

再出撃・ステージ選択・スナップショットのロード・スロット切替のように、**`Game` インスタンスそのものを
捨てて次の周回へ移る**判断は、`Game` にも `game/` 配下のどのモジュールにも置かない。持ち主は
`main.ts` かその直属モジュール(`Launcher` / `SnapshotControls`)で、**`game/` の中に
`location.assign`/`replace`/`reload` を書かない。**

`Game` は自分が生きている間のことだけを知り、自分の次に何が起きるかを知らない。したがって `game/`
側が持つのは**遷移の判断材料を値として持つところまで**で(`Stage.phase` / `Stage.result`)、遷移
そのものは main 側が起こす。main 側が知る手段は2つだけ:

1. **毎フレーム読みに来る**(`Launcher.update()` が `Stage.phase` の決着を見る)。
2. **入力エッジを取る**(`Game.update` の後に残ったものだけを見る、`SnapshotControls` と同じ形)。

逆向き — `game/` 側が main 側のオブジェクトを参照する・コールバックで呼び返す — は作らない。
結果画面のように「決着を表示し、次の周回を選ばせる」GUI は、その GUI が書き換える状態(= メタの
フェーズ)の持ち主である main 側が所有し(I-12)、`game/` 側の型に触る必要があるときは**狭い
インターフェースを `game/` 側に置いて main 側がそれを満たす**(`ResultScreen` が受ける
`RunTransitions`。`DisplayDurationSource` と同じ手法)。

## II-2. `update` と `sync` を混ぜない (出典: refactor-fixed §2、CLAUDE.md Naming 節)

- **`update`** … 論理値の更新だけを行う。THREE のオブジェクトにも HUD の DOM にも触らない。
  **`update` から `sync` を呼ばない。**
- **`sync`** … `update` が計算し終えた論理状態を THREE.Scene と DOM へ反映するだけ。**論理値を
  書き換えない**(時間を進めない・寿命を判定しない・積分しない・次フレームが読む値を作らない)。
  **`sync` から `update` を呼ばない。**
- **`build`** … 新しいメッシュ/オブジェクトをシーンへ登録する(構築であって毎フレームではない)。
- **`render`** … three.js renderer の `render(scene, camera)` を実際に呼ぶ処理にだけ使う。
- **`draw` は使わない。** 見つけたら改名する。

判定するのは名前ではなく中身。**`sync` が `dt` を引数に取っているなら、まず何かを進めている疑いが
ある。** 表示のためだけに要る値でも、それが「前フレームからの変化」で決まるなら `update` 側の
持ち物。逆に、`update` の中で見た目を整えたくなったら、その値を論理状態として持たせて `sync` に読ませる。

rAF ループが `update(dt)` → `sync()` → `render()` の3相を直接呼ぶ形が、この分割の構造的な根拠。
**`dt` を受け取るのは `update` 側だけ。** 表示側の更新頻度が要るなら `performance.now()` の期限を
自分で持つ。

`sync` の名前に `Render` を足さない(`syncCamera` であって `syncRenderCamera` ではない)。

## II-3. 座標系の境界 (出典: refactor-fixed §3)

### `Vec3` と `THREE.Vector3` の境界(フローティングオリジン)

フローティングオリジンは、GPU が巨大な数値を単精度で扱うことによる描画破綻を防ぐための措置で、
CPU 側で事前に平行移動して自機・カメラ付近の浮動小数精度を高めるためのものである。補正前か補正後かを
型安全に扱うため、**この境界を独自 `Vec3` と `THREE.Vector3` の境界に一致させる。**

- `THREE.Vector3` は描画のための座標なので、**フローティングオリジンを引いた後のものだけ**を扱う。
- 変換は必ず `FloatingOrigin` の変換関数(`RtoThreeV3` / `VtoThreeV3`)を経由する。

### 独自 `Vec3`/`KinematicState` は ECI が既定、それ以外は `frame.ts` の branded type

独自 `Vec3` / `KinematicState` は**地球中心慣性系(ECI)** を表す。これが既定であり、シミュレーションは
すべてこの系で回る(`physics/attractor.ts` の `Attractor.state` は常に ECI)。

ECI 以外の座標系(太陽中心系・月回転系など)の値は、生の `Vec3` に持たせない。`physics/frame.ts` が
持つ branded type だけがそれを表せる:

- **点**(位置。原点移動 + 回転で変換)は `FramePoint`。
- **方向**(変位・速度差・上方向など。回転のみで変換)は `FrameDir`。
- **点と方向を混ぜない。** 原点が動く座標系ではこの取り違えが静かに壊れる。

ECI との変換は必ず `Ephemeris.frameTransformAt(frame, t)` が返す `FrameTransform` を経由する。
**天体の位置を自分で引き算して座標系を作らない。**

`ReferenceFrame` は `Ephemeris` だけが mint する。生成のたびに新しいオブジェクトを作ると、参照同一性
による再ベイク抑制(I-11)が静かに効かなくなる。

## II-4. `physics/` / `render/` / `game/` の境界 (出典: refactor-fixed §4)

- **`physics/`** … THREE.js に依存しない**物理・軌道力学そのもの**。純関数が多いが、THREE 非依存で
  あれば状態を持つクラスを置いてもよい。
- **`render/`** … THREE.js に依存する部分のみ。上記の理由により独自 `Vec3` 座標は極力持ち込まない。
- **`game/`** … その両方に依存する部分のみ。

### `physics/` では物理的な正確さが最優先される

**勝手な近似を持ち込まない。**「これくらいなら見た目には分からない」という判断を `physics/` の中で
下してはいけない。パフォーマンスが問題になったときは、メモ化・呼び出し側での刻み幅制御・解析解への
置換など、**正確さを損なわずに速くする方法を探す。** それでも成立しないと分かった場合は、近似を
採用してよいかを**ユーザーに問う**(勝手に倒して先へ進まない)。

採用したモデルとその適用範囲・限界は、そのモジュールの先頭コメントに書く。

### `physics/` に物理でないものを持ち込まない

THREE 非依存かつ純粋であっても、次のものは `physics/` に置かない。

- **ゲームバランスの調整値** — 散布界の倍率、命中判定の甘さ、ダメージ量、演出のための補正。
- **見やすさのための歪め** — 表示距離の圧縮、フェード、マーカーの寄せ、閾値による表現の切り替え。
- **フローティングオリジン** — 描画のための平行移動であって物理ではない。
- **THREE.js への依存。**

境界は「用途が表示かどうか」ではなく「**厳密な数学・物理そのものか、調整の入った歪めか**」。
射影変換(`projection.ts`)や視線遮蔽判定(`occlusion.ts`)は表示のために使われるが調整値を含まない
厳密な幾何なので `physics/` に属する。逆に、帯の実幅が画面上で 1px を割ったら線として描くという
判定は、比較そのものは純粋でも閾値が見やすさのための調整値なので `game/` に置く。

物理的に正しい計算を調整値で歪めて使う場合は、`physics/` から素の値を引いて `game/` 側で歪める。
`physics/` に調整値が混ざると「この式は物理的に正しいのか、遊びやすさのために歪めてあるのか」が
読んで区別できなくなる。

### 接触判定は重力の関心事ではない

2球が触れているかどうか(`sphere-contact.ts`)と、触れたときにどう跳ね返るか
(`collision-response.ts`)は、`occlusion.ts` と同じ理由で `physics/` に属する厳密な幾何・力学で
あり、「重力源かどうか」(`attractor.ts`)や「大気を持つかどうか」(`atmosphere.ts`)とは無関係な
別の関心事である。**`attractor.ts` は何が何を引くかにだけ答え、何が何に触れたかには一切答えない。**
同じ理由で、大気による焼失(地球にしか無い現象)と固体表面への接触(天体一般に効く幾何)は別の
判定であり、どちらか一方のマージンをもう一方の代用にしてはならない。

接触の**帰結**が当事者の責務であることは I-9 の一般則。

## II-5. 語彙の固定 (出典: refactor-fixed §9/§10/§11)

### `plan` / `predict` / `display`

未来の軌道を扱う系統が複数あるので、語を固定する。混ぜると、どちらの未来の話をしているのか識別子
から判別できなくなる。

- **`plan`(計画軌道)** … プレイヤーがマニューバノードを置いて組み立てた意図そのもの。
- **`predict`(予測軌道)** … 現在の状態のまま自由飛行した未来。
- **`display`(表示時刻)** … そのどちらでもない「いつの状態を表示するか」。

計画側の識別子・コメント・パネル文言に `predict` /「予測」を使わない(定数名も含む)。逆に予測側を
「計画」と呼ばない。

### `orbit` / `ephemeris`・`celestial` / `dynamic`

**判定基準は「そのモジュールの実装が何に限定されているか」であり、外部でどう使われているかではない。**

- **`orbit`** … 解析的に解ける軌道。時刻→位置が閉じた式で決まるもの。
- **`ephemeris` / `celestial`** … `ephemeris` は「時刻→位置を答える仕組み」、`celestial` は「天体と
  いう存在」。責務が違うので統一しない。
- **`dynamic`** … RK4 積分に基づくもの。
- **どの族にも限定されないものには族語を付けない**(`KinematicState`、`stepRK4`)。

語形は **`orbit` に統一**し、例外は定訳を採る `OrbitalElements` の1語だけ。`orbital*` を新設しない。
計画した経路は `path`、積分した軌跡は `trajectory`。この2語は概念が違うので共存させる。

### `body` は天体、機体座標系は `ship`、重力源の値は `attractor`

天文シミュレーションで無標の `body` が機体座標系に奪われるのは苦しいので、機体の側を有標にする。

- **`body` は天体の意味に残す。**
- **機体に固定した座標系は `ship` で有標にする**(`shipNormal` / `axisShip` / `aThrustShip`)。剛体
  一般(デブリ・薬莢)の固定座標系に名前が要るようになったら別途決める。
- **`Attractor` 型の値は型名と一致させて `attractor` / `attractors`。** ただし楕円の中心として渡す
  ものは `center`(`OrbitalElements.center` と一致させる)。**`bodies` が `Attractor[]` を指す箇所は
  0件**であること。
- **`AttractorId` は登録天体とは限らない、一般の `string`。** レジストリが実行時に差し替え可能である
  以上、汎用 API 側でこの型を閉じた union にできない。網羅性の強制は**具体レジストリ側が自分の
  データから `keyof` で自己生成する**(`SolarSystemId = keyof typeof SOLAR_SYSTEM`)。天体を1体
  足すと `SolarSystemId` が自動的に広がり、`celestial-registry.ts` の `Record<SolarSystemId, …>` が
  すぐさまコンパイルエラーになる。**汎用 API に手書きの union を書き足す形へ戻さない。**
- **`AttractorId` に対する網羅的 `switch` を新規コードに書かない** — 常にレジストリを引く鍵として
  扱う。例外は `CelestialBodyDef.kind`(恒星/惑星/衛星)に対する `switch` で、これは天体の分類が
  この3種で閉じているという物理的主張そのものなので、網羅性検査が働く方が正しい。
- **`Ephemeris` はどのレジストリ・どの ECI 原点を使うかをインスタンスごとに持つ。** 周辺モジュールが
  `SOLAR_SYSTEM` を直接読んで座標系一覧を組む形は禁止 — 座標系一覧も `Ephemeris` 自身が持つ。

## II-6. 静的事実と表示の定義元 (出典: refactor-fixed §3/§16/§17/§19)

- 天体の静的事実(質量・半径・軌道・形状・自転軸)の定義元は `physics/solar-system.ts` の
  `SOLAR_SYSTEM`。表示名と見た目の定義元は `game/celestial/celestial-registry.ts` の
  `CELESTIAL_BODIES`。
- **「天体がどこにいるか」「どちらを向いているか」「重力場がどう効くか」は3つの別の問い**で、
  それぞれ別の場所に置く。自転軸モデル(`pole`)を重力場の係数(`degree2`)に従属させない — 自転軸を
  持つが2次重力場を持たない天体が実在するので、従属させると片方だけの天体を型で表現できなくなる。
  時刻ごとの実ベクトルへの解決は `Ephemeris` の1経路に集約し、表示側の自転軸と重力場側の pole が
  別の式で計算されて食い違う事故を構造的に起こさない。
- 同様に、衝突球・高度基準のスカラー `Attractor.radius` を形状(`ShapeDef`)で楕円体化しない。
  「衝突判定がどう働くか」は「見た目がどう歪むか」とは別の問いで、どちらか一方の都合で他方の精度を
  上げ下げしない。
- 軌道要素の**基準面**は `KeplerOrbit.basisToEci` が持ち、評価側は基準面を固定しない。基準面の
  組み立ては宣言時に一度だけ行い、評価側に惑星ごとの極を知る責務を持たせない。
- **UI の見た目のトークンは `theme.ts`、ゲーム世界の色は `const.ts`。両者は互いを import しない。**
  依存させると「UI 側がゲーム世界の色をたまたま流用する」近道を作ってしまう。運用規約の全文は
  `DEVELOP/DESIGN-RULES.md` §2。

## II-7. HUD と表示物の所有者 (出典: refactor-fixed §12/§22)

一般則は I-12。本プロジェクトでの確定事項:

- **マーカーは対象の持ち主が自分の `sync` の中で出す**(`syncMarker` を別途公開しない)。対象が1つに
  定まらないマーカーだけが `marker/` に置かれる。**「どう置くか」(投影・方向・画面端の方位)は
  `MarkerManager` に集める** — 持ち主が決めるのは「何を・どの記号で出すか」だけ。**記号そのものの
  語彙は `marker/marker-glyphs.ts` に3族(実体=塗り / 方向=矢 / 軌道上の点=中空)として置き、持ち主は
  そこから選ぶ。** UI の縦方向の折りたたみ記号はこの3族の外に置き、字形を重ねない。
- 線の描画順の唯一の割り当て表は `const.ts` の `LINE_RENDER_ORDER`。
- GUI の重なり順の唯一の正本は `hud/overlay-layer.ts` の固定レイヤ(奥から手前へ
  `marker`/`panel`/`window`/`popup`/`gate`/`view`/`notify`/`system`)。**ポップアップの親は必ず
  `popup` レイヤ** — `document.body` や、それを開いた側と同じレイヤに直接ぶら下げてはいけない。
- **ESC・項目ショートカット・外側クリック・入力ゲートの正本は `hud/overlay-manager.ts` の
  `OverlayManager` 1箇所。** 個々のオーバーレイは `window` の `keydown` も `document` の
  `pointerdown` も自分で張らない。例外は**入力欄フォーカス中の element-level `keydown`** だけ
  (`ValueInput`)。開閉規約・置き場4種の全文は `DEVELOP/DESIGN-RULES.md` §4/§5。
- **押せる/切り替えられる/入力できる DOM は `hud/widgets/` の10種に限り、これ以外を自作しない。**
  自作している呼び出し側を見つけたら対応するウィジェットへ置き換える。

所有者を問わない例外:

- `PauseMenu` … **複数モジュールにまたがることが本質**の GUI なので、所有者を `main.ts` に置く。
- `Hud.hint()` / `toast()` / `Sfx` … 共有サービス。
- `hud/widgets/` / `hud/context-menu.ts` / `hud/frame-labels.ts` … DOM・イベント・表示文字列だけを
  担う共有部品。状態を持たないので「所有者」を問う必要がない。**この形は積極的に増やしてよい。**
- 常設パネルの6クラス(`status-panel` / `orbit-panel` / `target-panel` / `contacts-panel` /
  `global-status-bar` / `map-scale-badge`)… 各パネルが読む値の組み合わせが違うため、共通の狭い ctx を
  切り出す方が却って I-8(`ctx` 引数の禁止)に反する。`Game` を丸ごと読んでよいが、**表示専用**で
  あること(他モジュールの状態や DOM を書き換えないこと)は維持する。

## II-8. ステージは一般形の特殊化であって、特別扱いの分岐ではない (出典: refactor-fixed §21)

**一般形は「自機0..n隻・勝敗なし・任意配置」で、攻略ステージのほうがその特殊化**である。逆ではない。
したがって**あるモードでしか使えない機能というものは存在しない** — すべての機能は一般機能であり、
ステージ側がそれを制限する。

- **「モード」という第二の軸を作らない。** ステージを指す識別子は `StageId` ひとつだけで、「ステージ
  か、それ以外か」を表す型を作らない。**レジストリの外に置いて特別に `new` する経路を作らない。**
  別の軸を立てた瞬間、起動解決・セーブのメタ・選択画面・生成の4箇所すべてに同じ分岐が生える。
- **`Game` はどのステージが動いているかを知らない。** `instanceof` も `mode === '…'` も書かない。
  ステージごとに違う挙動が要るなら、それは**ステージ側が宣言する能力(capability)** であり、`Game` は
  その値を読むだけ。実行時に問い合わせる能力はインスタンスフィールド、生成より前に要る能力は
  ステージクラスの static。
- **基底の既定実装は一般形の側に寄せる。** 制限の無いステージが「何もしない」で済むよう既定を置き、
  制限するステージが上書きする。既定を攻略ステージ向けに置くと、制限の無いステージのほうが空の
  override を持つことになり、どちらが一般形かコードから読めなくなる。
- **起動時の状態は、モードではなく状態から導く。** 「クリエイティブだからマップで始める」ではなく
  「艦が0隻だから戦闘ビューに入れず、マップで始める」。前者は条件が増えるたびに分岐が増える。
- **選択画面のための宣言(`select*`)は見た目だけを決める。** **挙動の分岐に読んではいけない。**
  ここを挙動の判定に使うと、UI の都合で付けた分類がそのままモードとして復活する。
- **能力の名前はモードを指さない。** `creative` ではなく、それが実際に何を許すのか
  (`freeProcurement` / `executesPlans` / `authoring`)で名づける。
- **一般形の側に特例を彫り込まない。** 能力フラグを足したくなったら、まずその挙動が一般形として1つに
  定まらないかを疑う。定まるなら、フラグではなく一般形の方を直す。
- **文書も同じ構造で書く。** ステージ1つとして立て、モードという第二の軸として説明しない。
  **「〜モードでのみ」という書き方をしない** — 実際の条件は能力の有無であって、ステージの名前ではない。

## II-9. 一般化しないと決めたもの (出典: refactor-fixed §15)

似た形の実装があっても、**個別に調整される要素**なのでまとめない。判断基準そのものは I-10。

- **`stages/` 配下の各ステージの挙動。** すべて並列に実装されているし、そうあるべき。共通化するのは
  `Stage` 基底と `stage-utils/` に既に括り出したもの(補給・スコア・タイマー・ウェーブ)まで。
- **自機と敵の戦闘挙動。** 武装も観測機器も別物という設定なので、射撃・照準・散布界・被弾判定などは
  今たまたま同じ式でも**将来別々に調整される前提**で、`player/` 側と `Enemy` 側にそれぞれ実装する。
  同じ関数が2箇所にあってよい。共通化してよいのは、どちらの調整とも無関係な純粋な物理・幾何だけ。
- **恒星が2つ以上、相互に公転しあう連星系。** 相互に比較可能な質量が複雑な軌道を描く状況は解析的な
  ケプラー軌道の適用範囲外 — その表現は数値積分の役目であり、レジストリの一般化では担わない。
- **3階層(恒星/惑星/衛星)を超える公転階層。**
- **地球の大気圏熱管理・機体初期配置・エネミー生成式を天体非依存に一般化すること。** レジストリに
  地球以外の天体しかないステージでもクラッシュしないことまでを保証し、それらの物理モデル自体は
  一般化しない(桁違いに大きい別作業)。
- **静止軌道高度・太陽同期傾斜角のプリセット、基地配置を月に限定するルールの、他天体への一般化。**
  ゲームデザイン上の判断、または現状のスキーマに無いデータを要求するため。

## II-10. 焼き込みアセットと実行時が共有する値は `src/` に1つ置く (出典: refactor-fixed §14)

`tools/` の焼き込みスクリプトと実行時コードが同じ値に依存するとき、**ツール側へ数値を複製しない。**
複製した瞬間、片方だけを直しても誰も気付かない。

- 値は `src/` 配下の、**他モジュールを import しない** TS モジュールへ置く。
- ツールは TypeScript コンパイラ API (`ts.transpileModule`) でその場に JS へ変換して動的 import する
  (ts-node 等のパッケージは追加しない)。

## II-11. 独立させると決めたフラグ (出典: refactor-fixed §8 の具体例)

一般則は I-9。本プロジェクトで「たまたま同時に切り替わるだけ」と判断済みの組:

- `PlanEditor.editMode`(入力・編集の可否)/ `CameraSystem.overviewMode`(視点・描画)/
  `DisplayWindowManager.forceCurrent`(未来表示の可否)→ 同時トグルは `ViewManager.applyChrome()` の責務。
- `OverviewCamera.cameraFrame`(視点が固定される座標系)と `DisplayWindowManager.frame`(未来表示を
  描く座標系)→ プレイヤーが独立に選ぶ別々の値。カメラの原点・回転を変えても `frame` は動かず、
  その逆も同様。
- `BodyClassToggles` の軌道線表示(`*Orbit`)/ アイコン表示(`*Icon`)/ ラベル表示(`*Label`)→
  プレイヤーが独立に選ぶ3つの値。読む側も別。

# 第III部 暫定的な慣習・判断

**これを根拠に設計を決めない。** 確定したら第I部か第II部へ移す。

## III-1. クラスの役割接尾辞の定義表 (出典: CODING_STYLE §10)

`Manager` / `Controller` / `System` / `Service` / `View` / `Panel` / `Editor` / `Picker` / `Registry` /
`Guide` に次の定義が与えられている。

- `Manager` — 一つの概念に属する状態、選択、方針を所有し、その概念に対する操作をまとめる。
- `Controller` — 入力または外部からの命令を受け、複数の状態変更を調整する。
- `System` — フレーム処理または多数の対象にまたがる一つの機能を構成し、下位オブジェクトを統括する。
- `Service` — 呼び出し単位の処理を提供する。画面やフレーム周期の状態を所有せず、保存、読込、変換
  などのユースケースを実行する。
- `View` — 表示物を所有し、論理状態を表示へ反映する。ゲーム状態の正本を所有しない。
- `Panel` — 一つのまとまった DOM UI を所有する View に使う。
- `Editor` — 既存の領域モデルを選択・編集する操作と編集中の状態を所有する。
- `Picker` — ポインター位置や候補集合から、選択対象を特定する。
- `Registry` — id などの安定したキーから定義を参照する正本を提供する。
- `Guide` — 既存状態から案内情報を導出し、通知または表示へ渡す。

**暫定とする理由**: 既存クラス名から逆算した分類で、`Manager` と `System` の境界が実際には機能して
いない疑いがある(`EntityManager` は配列を所有し `EffectsSystem` は生成窓口 = `Service` の定義に近い、
`SimSpeedManager` は入力を受けて複数の状態を調整する = `Controller` の定義に近い、など)。
**「単に具体的に見せるために `Manager`/`System`/`Service` を付けない」という禁止(I-5)は確定として
第I部に置き、この定義表そのものは暫定に置く。** 命名時にこの表を根拠に接尾辞を選ばない —
「何を所有し、いつ動くか」から選ぶ。

## III-3. `_` 接頭辞の二重定義 (出典: CODING_STYLE §2 と §8)

同じ `_` 接頭辞に2つの意味が与えられている。
