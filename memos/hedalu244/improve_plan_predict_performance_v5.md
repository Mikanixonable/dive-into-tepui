# 計画・予測の負荷改善 v5

# 目的

予測(`Predictor`)と計画(`PlanArc`)は、どちらも「軌道を数値積分して先へ伸ばし、実状態から
離れたら捨てて引き直す列」になった。この2つが**別々の予算・別々の刻み幅・別々の許容誤差**を
持っているせいで、片方の条件を直すと他方が見えなくなり、フレーム時間の総量を誰も管理していない。

この文書の目的は2つ。

1. **積分コストを1箇所で管理できる形にする。** 予測と計画が同じ抽象の上に載れば、
   「このフレームで積分に使ってよい量」を1つの予算として配れる。いまは
   `PREDICT_STEP_BUDGET` と `PLAN_ARC_MAX_STEPS` が独立なので、1フレームで両方を満額使える。
2. **残っている「静かに間違った表示」を潰す。** 長い表示期間で予測線が遠端で1万km単位で
   ずれたまま破棄されない(問題3)。これは性能ではなく正しさの問題。

**データの共有は目的ではない。** 予測列と計画列を1本にまとめる案は棄却済みで、その理由は
いまも有効(下の「棄却済み」)。共有するのは**アルゴリズムとコスト管理**であって列ではない。

# 解決済みの事象(再発防止のためだけに残す)

## S-1. フレームを跨いで使い回す構造に「生涯累計」の上限を付けてはいけない

窓を滑らせながら生き続ける構造に生涯累計のステップ上限を付けると、どれだけ余裕を取っても
有限フレームで必ず上限へ達し、そこから恒久的に伸びなくなる。描く窓は進み続けるので、線は
縮んでいって二度と戻らない。上限は**1回の呼び出しに対して**置く。

恒久的な打ち切りに残してよいのは、物理的な終端(表面接触・焼失・非有限)と、収束していない
ことがその場で判る場合(予算を使い切って先端がサンプル1つぶんも進まない)だけ。

## S-2. 1フレームの時間送りが窓の長さを超えるワープでは、使い回しは原理的に成立しない

×65536 では `simTime` が1フレームで数千秒進む。表示期間が「1周」(LEO で約5580s)なら窓は
毎フレーム丸ごと入れ替わるので、**使い回しても積分ステップ数は減りようがない。**
効くのは「窓の長さ ≫ 1フレームの時間送り」の条件だけ。条件間で `plan-steps` を比べる前に、
まずこの比を見ること。

## S-3. 「同じ軌道か」は時刻差ではなく位置差で測る

起点が生きている自機を追う区間では、時刻差の閾値は判定として成立しない(ワープ倍率が上がる
だけで必ず閾値を超える)。判定は「新しい起点がその区間自身の積分結果の上に載っているか」を
位置で測る。閾値は用途で決まる — 計画線では「折れ線1区間ぶんの長さ(速度 × サンプル間隔)」、
予測では「補間誤差込みの許容量」。**この2つは単位も桁も違う**(下の判断D-2)。

## S-4. 積分幅の3項(床・周期項・分配項)は落とせない

実験済みで、3項それぞれが互いに素な領域を担当している。

- 床 20s を釘付けているのは LEO ではなく低月周回(dt=20 で既に 419m、閾値の84%)。
  これは RK4 の打ち切り誤差ではなく中心天体を中点で凍結する dt² 誤差なので、床を 25s に
  するだけで破綻する。
- 離心軌道(モルニヤ)では周期項が定数刻みをパレート優位で上回る(3.6倍安く精度は同等)。
- ゲーム側 A/B では、周期項を落とすと `update` が 10.2倍になる。

**ただし分配項は「安いが遠端が間違う」項**であって、無条件に良い項ではない(問題3)。

## S-5. 空間分類は「1回組んで多数の点で使い回す」ときだけ得になる

`classifyAttractors` + `attractorsNearInto` はオーダーを下げる道具で、1点あたりを速くする
最適化ではない。分類1回は `alwaysThresholdMu` の μ 全ソートに支配され O(N log N) なので、
**1点ごとに分類し直すと O(N) の線形走査を O(N log N) へ置き換えるだけで常に損。**

## S-6. 計画線の終端相手

解析天体は全数が終端相手(`Ephemeris.attractorsAt` をそのまま使う経路)。動的エンティティは
`predictedAsPlanCollider` を宣言したものだけ(現状 `Asteroid`)。**この2つは別の経路**なので、
片方を絞っても他方には影響しない。

# 残っている問題

## P-1. ×1 × 28日プリセットで計画の積分が毎フレーム走る 【今回作った退行】

S-1 の対処として「予算を使い切っても打ち切らず次フレームへ続きを回す」形にした結果、
28日ぶん全体を描こうとして数十フレームにわたり毎フレーム数千歩を積むようになった。

| 条件 | `計画` | `update` | `sync` | fps |
|---|---|---|---|---|
| 変更前 | 0.45 ms | 75 ms | 37.9 ms | 8 |
| 変更後 | 1,242 ms | 1,293 ms | 62.8 ms | 3 |

過渡ではある(ラウンドごとに 500〜2,500歩とばらつく)が、13秒の測定窓の最後でもまだ伸びて
いた。`sync` の増分は線が長くなったぶんで、こちらは恒久。

**未解明**: 1フレームあたり約2,000歩で止まっており、予算 20,000 に届いていない。
仮説は「28日ぶんの積分中に軌道が減衰し、`stepDt` の接近項(`clearance/closingSpeed`)が
潰れて刻み幅が小さくなっている」だが**未検証**。計画の刻み幅には予測の `PREDICT_MIN_STEP_DT`
に相当する床が無いので、潰れを止めるものが無い。**P-1 を直す前にここを確かめること** —
原因が接近項なら、対処は予算でも到達範囲でもなく床になる。

## P-2. 予算の崖 — 予測が伸び切らない

`map ×65536` は `pred-discard` 6 / `pred-complete` 0 / `pred-steps` 458 が avg・max とも一致
= **毎フレーム破棄して伸ばし直している**。`map ×1 28日` も `pred-complete` 0/7。

外挿タイルの毎フレーム焼き直しはこの症状のひとつで、独立した問題ではない。
`TrajectoryLine.syncGeometry` は `to` の移動と**保持列の配列参照の変化**の2つで焼き直すが、
支配しているのは後者 — 予測が伸び続けると `samplesOldestFirst()` が毎フレーム新しい配列を
返す。**先に焼き直し側へ条件を足すと症状を隠すだけになる。**

## P-3. 28日プリセットの予測線は遠端で 13,500 km ずれ、しかも破棄されない

地球半径より大きい。分配項が総ステップ数を 20,000 に抑えるため dt=121s を強い、435周を
46歩/周で刻んだ結果。破棄閾値(この条件では 69.6km)を超えているのに破棄されないのは、
乖離判定が見るのが `at(simTime)` すなわち列の先頭付近だから — **遠端の誤差は `simTime` が
そこへ達しない限り誰も検査しない。静かに間違った線が描かれている。**

## P-4. 積分の天体窓(A-0)

定常的な最大項(`creative ×65536 艦なし` で 190.6ms)。中身は「サブステップごとに、その
中点時刻で全重力源の窓を組み直している」こと。`substeps` は `simDt / SUBSTEP_MAX_DT` で
決まるので、ここを触ると精度の議論に直結する。

エンティティ0体の条件は**情報を捨てている問題ではない** — 0体はゲーム中ほぼ起こらないので
早期 return しても軽量化にならない。「1回の窓構築はエンティティ数に比例しないオーバーヘッド
であり、0体の条件はその量を単独で測る手段として有効」と読む。

## P-5. 予測は依然 O(NM)

M 個体の予測を伸ばすのに N 体の重力源を総当たりする構造は変わらない。先端時刻が個体ごとに
違う以上、`Simulator` のような共有は成立しない。**これはフレーム時間ではなく「予測が完成
しないこと」として現れる**(1フレームの伸長は予算で頭打ちなので、O(NM) は消費フレーム数へ
転嫁される)。表示個体数を増やす方向へ進むならオーダー改善が要る。

## P-6. 中点側の空間分類がまだ歩ごと

S-5 の成立条件を満たしていない経路が2つ残っている。

| 経路 | 1回の分類を何点で使い回すか | 成立 |
|---|---|---|
| `Simulator.substep` | サブステップ中点で1回、そのサブステップの全エンティティ | ○ |
| `Predictor.update` の乖離判定 | フレームに1回、全対象 | ○ |
| `Predictor.advanceBudget` の中点評価 | 1歩1点 | **×** |
| `PlanArc.integrateTo` | 1歩1点(時刻一致の4スロット保持で歩あたり2回へ緩和) | **×** |

落とすと絞り込みが消えるので、RK4 の1ステージで合算する項が `always` + 近傍から窓全体
(64体)へ増える。**どちらが安いかは未測定。**

## P-7. ケプラー外挿の中心天体は先端より古い

`DynamicTrajectory.step` は先端を進めた**後**に `extrapolationCenter` を記録するので1歩ぶん
古く、`Predictor.advanceBudget` が1歩前の中点で解決した窓から選ぶため半歩ぶん上乗せされる。
地球中心では誤差ゼロ、月中心では dt=20s で数十 km 相当。外挿は先端より先の表示にしか
使われないので現状は許容しているが、外挿の精度を問題にするときはここを疑う。

## P-8. 自艦を複数置いたときの頂点バッファ

`TrajectoryLine` は `Curve` に `maxVertices = 16384` を渡す。1本 704 KB(`positions` 192 KB
+ `bakedLocal` 384 KB + `indices` 128 KB、うち GPU 側 320 KB)。`MAX_PLACED_SHIPS = 50` まで
置くと **34.4 MB**(GPU 側 15.6 MB)、過去線も出すなら倍。静的に決まるので計測は不要。
自艦を多数置く運用を許すなら `maxVertices` の見直しが要る。

# 下すべき判断

## D-1. 積分の抽象化をやるか、どこまでやるか 【最大の判断】

**提案**: 許容誤差・粗さ・期間・予算をパラメータに切り出した「賢いモジュール」を作り、
そこで積分コストを管理する。`Predictor.advanceBudget` が既に成熟しているのでそれを流用する。

**この方向には賛成。** 共有できるものと、できないものを分けて記す。

### 共有できる(抽象化の本体)

- **刻み幅の決め方**: 床・周期項・分配項の3項(S-4)。計画側は現状「周期項 + 接近項」だけで
  床も分配項も無く、P-1 の未解明部分はここに起因する疑いが濃い。**共有すれば計画は床を、
  予測は接近項を、それぞれ得る。**
- **予算を配って伸ばすループ**: 「予算が尽きるか、地平に達するか、打ち切られるまで刻む」。
- **フレーム全体の積分予算**: これが最大の利得。いまは予測と計画が独立予算なので、
  1フレームで両方満額を使える。

### 共有できない(呼び出し側の方針として残す)

- **許容誤差の意味が違う。** 予測は「積分した未来が、同じ時刻の実状態からどれだけ離れたか」
  という**精度**の問い(500m を補間誤差で広げる)。計画は「この起点はまだこの弧の上か」という
  **同一性**の問い(28日プリセットで約9,200km = 折れ線1区間ぶん)。同じ「距離 vs 閾値」でも
  4桁違う。1つの `tolerance` パラメータに畳むなら、単位を「m」ではなく
  「描画解像度の何倍か」のような無次元量にしないと嘘になる。
- **打ち切り条件**: 計画は毎歩、全衝突体に対して掃引接触判定(`findImpact`)を行い、そこで
  線を終わらせるのが仕様。予測は先端で `hitCelestialBody` を見るだけ。これは性能差ではなく
  機能差なので、方針として呼び出し側に残す。
- **1歩のコストが3.2倍違う。** 実測(2条件で一致):

  | | ms/歩 |
  |---|---|
  | 予測 | 0.19 |
  | 計画 | 0.61 |

  計画の1歩は provider を3時刻ぶん引き、分類し、全衝突体へ掃引判定する。**「歩」を共通の
  予算単位にすると、この3.2倍を抽象が隠す。** 予算は時間か、重み付きの歩で持つ必要がある。

### 流用元についての注意

`advanceBudget` は**刻み幅の決め方については成熟しているが、長い地平については成熟して
いない** — 分配項が P-3(遠端 13,500km、破棄されない)の直接の原因。**そのまま計画へ流用
すると、いま計画には無い「静かに間違った線」を計画にも持ち込む。** 流用するのは
「3項の構造」であって「現在の定数と、乖離判定を先頭でしか行わない設計」ではない。

**判断すべきこと**: (a) 抽象化をやるか、(b) やるなら予算単位を何にするか(時間か重み付き歩か)、
(c) 許容誤差をどう無次元化するか。

## D-2. P-1 をいつ・どう直すか

いま HEAD に退行が入ったままである。選択肢:

- **(a) 先に原因を確かめる**(接近項の潰れか、別か)。原因が刻み幅の床なら、D-1 の抽象化で
  自然に解決する — その場合 P-1 は独立の作業ではなくなる。**見立てはこれ。**
- (b) 到達範囲を予算で頭打ちにして窓と一緒に滑らせる(初回の満額積分が届いた範囲を覚え、
  以後の終端をそこで抑える)。変更前と同じ線長・同じ性能に戻り、×65536 の改善は維持される。
  抽象化とは独立に効く応急処置。
- (c) 28日の線が全長描かれることを優先し、×1 の 3fps を許容する。

**(b)(c) は「線の長さを取るかフレームレートを取るか」の表示判断**で、D-3 と同じ枠。

## D-3. 長い表示期間の扱い

長い表示期間の予測は、粗すぎる(分配項あり → P-3)か伸び切らない(分配項なし → P-2)かの
どちらかで、現状どちらも成立していない。

- (a) P-2 と一緒に解く
- (b) 遠端を「精度保証外」として明示的に描き分ける
- (c) 選べる期間の上限を下げる

計画側にも同じ判断が要る(P-1)。**予測側と揃えて決める。**

## D-4. 予測要否のフレーム可変ゲート

- (i) 予測線を描いていない個体だけ止める
- (ii) 表示時刻が現在を指している間は `predictedForGhost` を成立させない

(ii) の代償は外挿が入ったことで軽くなっている(止めた個体もスライダを引いた瞬間に位置は
答えられる)。ただし **P-2 本体を直す前にゲートだけ入れると「足りない個体が減ったので崖が
見えにくくなった」だけになりうる。** P-2 の測り直しと同じ変更セットで判断する。

## 棄却済み(理由ごと再掲する)

- **予測列と計画列を統合する** — どちらも `DynamicTrajectory` なので1本にまとめる案。
  予測が「実状態から乖離したら破棄して伸ばし直す」列であるのに対し、計画は「凍結した
  アンカーから決まる」列で、**無効化の条件が正反対**。1本にすると、どちらの無効化条件も
  他方にとって誤りになる。**D-1 のアルゴリズム共有はこれに当たらない**(共有するのは
  刻み幅の決め方と予算であって、列でも無効化条件でもない)。
- **`always`/`grid` で重力源の更新頻度を分ける** — `always` に入る天体こそ動きが速い
  (月・木星の衛星群)ため、頻度を落として良いのは**位置ではなく質量順では決まらない**。
- **`horizon` を個体ごとに変える** — `horizon` は表示期間そのものなので、個体ごとに変えると
  **同じ表示時刻に対して個体ごとに違う未来を描く**(ゴーストの位置が揃わない)。
- **`PREDICT_STEP_BUDGET` を上げる** — 崖の原因は予算の絶対量ではなく**分配と破棄の
  繰り返し**。上げると1フレームの最悪値が伸びるだけで `pred-complete` は 0 のまま。
- **刻み幅の3項のどれかを定数へ簡略化する** — 3項とも落とせないことを確認済み(S-4)。
- **ノードなしの計画区間の長さを表示期間から切り離す / 長い期間では計画線を出さない** —
  どちらも性能のために表示を削る判断。同じ絵を安く出す道が先にあった。

# 今後の手順

**判断の小さい順**(効果の大きい順ではない)。

1. **P-1 の原因を特定する**(D-2(a))。刻み幅が実際にどこまで潰れているかを見る。
   ここが接近項なら、以降の設計が変わる。**測定ではなく観測** — 1条件で刻み幅の分布を
   出せば足りる。
2. **P-2 と、その症状である焼き直し**(D-3・D-4)。`pred-complete` が 0 のままなら
   degradation を持たせる設計(足りない個体の列を全損させない)へ進む。P-3 もここで決める。
3. **D-1 の抽象化。** 1・2 で「刻み幅と予算をどう決めるべきか」の結論が出てから切り出す。
   先に器を作ると、入れるべき方針が決まっていないまま形が固まる。
4. **P-4(A-0)。** 判断が最も大きいので最後。
5. **P-6 の測定。** 落とすと合算する項が増えるので、上の変更を入れて残る呼び出し経路を
   確定させてから測る。
6. **論点C(線が船体から離れる/振動する)。** P-2 が直って破棄が止まってから。

# 計測方法

## 読み方(先に読むこと)

1. **1条件1回の ms はいかなる比較にも使えない。** 同一ビルドのラウンド間で ±60〜80%
   食い違った実績がある。`PERF_REPEATS` の中央値と振れ幅を併記して読む。
2. **ms を run 間で直接比べてはいけない。** 同じ run の中でも条件をまたいでマシン速度が
   1.5〜2倍動く。A/B では、触っていないはずの離散カウンタが前後で一致する行を対照に取り、
   比で正規化する。
3. **主指標は離散カウンタ**(`plan-steps`/`plan-arcs`/`pred-steps`/`pred-complete`/
   `sim-substeps`)。これらは run をまたいでも比較できる。
4. **暦キャッシュの hit/miss は 500ms の実時間窓あたりの差分**なので、fps が違う run 間では
   比べられない。フレームあたりに直す。
5. **予測を触る変更は、予測対象が多い条件で測る。** stage1 系は最大7体しかない。
   `debug-load-map-warp1`(小惑星300 + 破片500)が唯一まともに効く条件。
6. `map ×1` の弾数はラウンドごとに 48〜165 発と違い、`sim-orbit` と `接触` がそれに
   引きずられる。この条件で ±10% 未満の差は読めない。
7. `plan-steps` は区間を作り直したフレームと継ぎ足しただけのフレームで桁が違う。
   **`plan-arcs`(作り直した本数)と必ず対で読む。**
8. **伸長の途中を測っていないか確かめる。** ラウンド間で `plan-steps`/`pred-steps` が
   大きくばらつくときは定常状態に達していない(P-1 がまさにこれ)。settle を延ばして
   ばらつきが消えるかを見る。

## 手順

ビルドとプローブは別々に差し替えられる。プローブ(`tools/perf-probe.mjs`)はビルド済みの
`docs/` を外側から CDP で駆動するだけなので、被計測側だけを差し替えられる。

```
# 現在のコードを測る
npm run build && node tools/perf-probe.mjs

# 変更前を測る(変更したファイルだけを戻す。src/ 全体を restore すると
# 未コミットの資産ファイルまで消えるので、ファイルを列挙すること)
git restore --source=<commit> --worktree -- <変更したファイル...>
npm run build && node tools/perf-probe.mjs
git restore --worktree -- <変更したファイル...>
```

環境変数:

| 変数 | 既定 | 意味 |
|---|---|---|
| `PERF_REPEATS` | 3 | 条件ごとに、ページ読み込みからやり直す回数。行ごとにラウンド間中央値を採る |
| `PERF_SAMPLES` | 10 | 1ラウンド内で `PerfMeter` を読む回数 |
| `PERF_INTERVAL_MS` | 500 | 読み取り間隔(`PerfMeter` の flush 周期と同じ) |
| `PERF_SETTLE_MS` | 3000 | ワープ・ビュー・表示期間を整えてから測り始めるまでの待ち |
| `PERF_ONLY` | — | label 部分一致(数字境界で区切る)で条件を絞る |
| `PERF_OUT` | — | 結果 JSON の書き出し先 |

計画側を測るときの条件(`PERF_ONLY='stage1-map'` で8条件):

```
PERF_ONLY='stage1-map' PERF_REPEATS=5 PERF_OUT=after.json node tools/perf-probe.mjs
```

予測側を測るときは `debug-load-map-warp1` を必ず含める(読み方5)。

未測定のまま残っている条件: `stage00-map-warp1` / `stage00-map-warp1-orbitoff`
(波状攻撃で敵が増えたときの軌道線の draw call。settle 20秒 × 5ラウンドで時間がかかる)。
