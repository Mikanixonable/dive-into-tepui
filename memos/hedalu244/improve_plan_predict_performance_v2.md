## 1-4. 第3ステップ: アダプティブ刻み幅を精度で評価した(`7e660737`)

`tests/perf/exp5-adaptive-step.ts` を追加。**dt 同士の比較は比例定数の取り方で
いくらでも動くので循環する**というご指摘のとおり、誤差を支配しているパラメータが
`dt[秒]` か `1周あたりステップ数`かを判定する形にした。
全 regime に同じホライズン 86400 秒を与えて dt を掃引している。

### まず、仮説の前提が git 上で否定された

「生の折れ線しか無かった時代の遺物」という読みは**時系列が逆**だった:

| 日付 | コミット | 出来事 |
|---|---|---|
| 2026-07-25 | `af823aa3` | `sampled-line.ts` = 生の折れ線描画 |
| 2026-08-01 | `6f845157` | **エルミート補間+折れ角サブディビジョン** |
| 2026-08-07 | `a9a37905` | **予測の刻み幅が `localOrbitPeriod` 基準になる** |
| 2026-08-09 | `94433cc3` | 弦分割が画面スケール依存に |
| 2026-08-12 | `18750cf8` | `render/curve.ts` へ集約 |

生の折れ線だった時期の刻み幅は `clamp(5, 600, r/8e5)` という**半径ベース**で、天体依存では
なかった。「生折れ線 × 天体依存の刻み幅」という組み合わせは一度も存在していない。
`a9a37905` の理由はコミットメッセージにあり、描画ではなく**月周回での刻み幅の破綻**
(「地心の周期を使っていたため、月周回では間隔が数万秒・刻みが 600 秒に張り付いていた」)。

**ただしその破綻は、床 `PREDICT_MIN_STEP_DT` = 20 秒だけで再現できる。**
低月周回の周期は 7066 秒、`/600` = 11.8 秒で床に負ける。実験5-C の採用 dt を見ると、
LEO・高度2000km・低月周回はすべて **20.0 秒**(床)だった。
**周期項が採用値になるのは周期 12000 秒超 = 高度約4900km より上だけで、
そこでは dt を大きくする方向にしか働かない。**

### 誤差はどちらのパラメータでも揃わなかった

同じ「1周あたりステップ数」で並べても相対誤差は揃わない:

| 軌道 | 歩/周 | 相対誤差 |
|---|---|---|
| LEO 420km | 557 | 7.3e-8 |
| 静止軌道 GEO | 539 | 2.4e-9 |
| 地心 1e8m | 492 | 1.0e-8 |
| **低月周回 100km** | **707** | **9.7e-4** |
| **月周回 5000km** | **620** | **4.7e-4** |

同じ dt でも揃わない(dt=20 で LEO 11.9m / GEO 0.0m / 低月周回 7344.7m)。
**支配しているのは軌道周期でも dt でもなく、その軌道にどんな力学が乗っているか。**

### 新発見: 低月周回の誤差は RK4 ではなく「天体位置を中点で凍結する」ことの誤差

低月周回の誤差は dt を倍にすると約4倍になる(1781 → 7344 → 3.0e4 → 1.2e5)。
**dt² であって dt⁴ではない。** RK4 の打ち切り誤差ならば dt⁴ で効くはずで、実際に
GEO は dt⁴(0.1 → 2.0 → 36.2 → 707)で効いている。

差は**支配天体が ECI 原点で動くかどうか**。地球中心の軌道では支配天体が原点に静止して
いるので誤差は純粋に RK4 のもの。月周回では支配天体である月が ECI 中を動き、
`stepDynamics` は1ステップにつき中点時刻の天体位置を1回引いてRK4の4段すべてに使い回すので、
**そこに中点則ぶん(2次)の誤差が乗る。** これが RK4 の4次を隠してしまっている。

**つまり月近傍の予測精度を決めているのは刻み幅ではなく暦を引く頻度である。**
`57414b5e`(重力源を据え置かない)が守ろうとした性質と同じ話の続きで、
据え置きどころか「1ステップに1回」でも月近傍では効いている。

### 同じコストを配ったときの精度比較(実験5-C)

現行則の総ステップ数(7 regime 合計 14798)と同じになる定数刻み = 40.87 秒:

| 軌道 | 現行(周期比例) | 定数 40.9s | 勝ち |
|---|---|---|---|
| LEO 420km | 1.75e-6 | 5.17e-5 | 現行 30倍 |
| 高度 2000km | 2.50e-7 | 6.74e-6 | 現行 27倍 |
| 静止軌道 GEO | 1.51e-9 | 1.49e-11 | 定数 100倍 |
| 地心 1e8m | 7.02e-9 | 4.38e-11 | 定数 160倍 |
| **地心 3.5e8m** | **1.96e-6** | **2.78e-10** | **定数 7000倍** |
| 低月周回 100km | 4.00e-3 | 1.68e-2 | 現行 4倍 |
| 月周回 5000km | 4.98e-4 | 1.21e-4 | 定数 4倍 |

(いずれも相対誤差 = 位置差 / 支配天体からの距離)

**どちらも一方的には勝たない。** 現行則は速い軌道(LEO・低月周回)で勝ち、
遅い軌道で負ける。最悪値は現行 4.00e-3 / 定数 1.68e-2 で現行が4倍良いが、
それは低月周回1点で決まっており、地心3.5e8では逆に7000倍負けている
(現行はそこに1日26ステップしか配らない)。

### 決定的だったのは実験5-D: 刻み幅の決定に専用の暦解決は要らない

現行は1ステップにつき暦を2回引く — 開始時刻(dt を決めるためだけ)と中点時刻(積分本体)。
dt を「1歩前の中点で解決済みの重力源」から決めれば、解決は1ステップ1回で済む。

| 軌道 | ステップ数 | 現行の解決回数 | 使い回しの解決回数 | 最終位置差 | dt比の最大 |
|---|---|---|---|---|---|
| LEO 420km | 4320 | 8640 | 4321 | **0.00e+0** | 1.000000 |
| 高度 2000km | 4320 | 8640 | 4321 | **0.00e+0** | 1.000000 |
| 静止軌道 GEO | 602 | 1204 | 603 | **0.00e+0** | 1.000000 |
| 地心 1e8m | 165 | 330 | 166 | **0.00e+0** | 1.000000 |
| 地心 3.5e8m | 26 | 52 | 27 | **0.00e+0** | 1.000000 |
| 低月周回 100km | 4320 | 8640 | 4321 | **0.00e+0** | 1.000000 |
| 月周回 5000km | 1046 | 2092 | 1046 | 1.14e+2 | 1.008999 |

**7 regime 中6つでビット単位一致したまま、暦の解決回数がちょうど半分になる。**
残る1つ(月周回5000km)も dt のずれは最大 0.9%、1日後の位置差 114m で、
その regime が元から持っている誤差 3350m の3%。

理由は明快で、床が効いている regime(LEO・2000km・低月周回)では
**そもそも dt が刻み幅決定の入力に依存していない**し、
遅い regime では周期が半歩ぶんではほとんど動かない。

# 第2章 論点ごとの残問題と原因

## A-0: 積分が最大のコストで、エンティティ0体でも重い(未着手)

`creative ×65536 艦なし` は r0/r1/r2 で 167 / 173 / 306 ms。
**エンティティ0体・予測0体・計画なし・軌道積分の実行回数0回でこれ。**
中身は `Simulator.substep` が毎サブステップ行う天体窓の構築だけ。

原因は前回メモのとおり `substeps = 328`(`dt` が上限 0.1s に張り付いた状態で
`0.1 × 65536 / 20`)× 天体窓1回。**1フレームに328回、すべて異なる時刻で暦を引く。**

**これが今のいちばん大きい単一項目で、かつ手つかず。** `main` も触っていない。

## A-1 / 1-b: 予測の暦解決が1ステップ2回(直し方が確定した)

コストの内訳は前回メモの実測どおり(1反復 388µs のうち物理は 2.76µs = 0.7%)。
**実験5-D により、2回を1回にできることが精度側から確認できた。**
これは前回メモの「1-b」そのもので、**ただし理由が変わった** —
「周期項が不要だから消せる」のではなく「周期項は残したまま、そのための専用解決が不要」。

## A-3(前回の第1段-a): 却下

`always`/`grid` で更新頻度を分ける案は、フィードバックのとおり採らない。
grid に乗せた天体の移動をどのタイムスケールまで無視できるかは質量・速度・位置で変わり、
単一定数では決まらない。**物理的正確さを落としたキャッシュのパラメータを調整し続ける道**に入る。

**そして実験5の新発見がこれを補強する** — 月近傍では既に「1ステップに1回」の解決でも
dt² の誤差が出ている。据え置きはその誤差を直接悪化させる方向で、
月周回の予測精度を決めているのが刻み幅ではなく暦の頻度である以上、
頻度を下げる最適化はいちばん触ってはいけない場所にあたる。

## A-4: 予算が破綻したままで、崖になっている

r0/r1/r2 とも `map ×65536` で `trk=6, comp=0, disc=6, steps=458` — **予算をほぼ使い切り、
6体全部が毎フレーム破棄され、1体も完成しない。** マージでも分解でも変わっていない。

degradation が無いのが構造上の問題で、1ステップ足りなかった個体は列を全損して
ホライズン全体の作り直しを負う。

## A-5 / 第4段: horizon は一律のままにする(方針確定)

フィードバックのとおり、**`horizon` を個体ごとに変えるのは採らない。**
`displayWindowManager.current.duration` 期間内で矛盾のない表示をするために一律である必要があり、
最大の消費者はたいてい最大値付近にいるので性能上の意味も薄い。

代わりに**「なぜ予測が必要なのか」の条件を精緻化した**(第1章 1-3)。
分解は済んだが、**分けた条件をまだ誰も使っていない** — 次章の判断待ち。

## B-2: 予測の破綻が計画の再構築へ伝播する経路は残っている

`map ×65536` は r1/r2 でも `plan-arcs=1`(node0)/`2`(node1)。
`predictionCoverage` の3値が `COVERS`↔`SHORT` を往復し `planSourceRevision` が毎フレーム動く経路は
`plan-attractors.ts` にそのまま残っている。**A-4 を直せば連動して落ちる下流の問題。**

## B-3: 1ステップの解決は2割減ったが、まだ 0.6 ms/step

`PlanAttractors` の4スロット時刻一致キャッシュで改善したが、
1ステップに開始・中点・終了の3時刻を引く構造は残っている。

## C: 予測線が船体から離れる/振動する(未着手・独立)

前回メモの分析(C-2: 振動の正体はサンプル間隔を周期とする補間の読み取り誤差)は
そのまま。**論点D を棄却したことで C は完全に独立な問題になった。**
前回計画の「2-a を先に単独で入れる」は、フィードバックのとおり**保留**
— 先に入れると予測列の精度と無関係に線が自機を通るようになり、
更新頻度に潜むバグの発見を遅らせる。

## D: 棄却(決定済み)

積分精度・長さ・更新頻度に加えて**間引き密度**のパラメータがあり、
戦闘ビューの表示と軌道編集のクリック判定では要求が全く違う。統合しない。
それぞれで個別にチューニングする。

# 第3章 私が下す必要のある判断

## 判断1: 予測の刻み幅の周期項をどうするか 【推奨あり】

実験5の結果、選択肢は3つ:

- **(a) 周期項を残し、専用の暦解決だけをやめる**(実験5-D の使い回し)
  → 予測の暦解決が**半分**になる。6/7 regime でビット単位一致。
- (b) 周期項を捨てて定数刻みにする
  → 遅い軌道でステップ数が跳ねる(地心3.5e8 で 26 → 4320 ステップ/日、166倍)。
     精度は上がるが、それは「コストを払った結果」であって精度が要らない場所。
- (c) 現状維持

**推奨は (a)。** 精度をまったく落とさずにコストが半減し、
「速い軌道と遅い軌道で刻みを変える必要があるか」への答えは
**「必要はあるが、そのために暦を引き直す必要は無い」**になる。

ただし (a) の後も **周期比例則そのものの是非は残る**。実験5-C のとおり、
現行則は地心3.5e8 に1日26ステップしか配らず、そこだけ相対誤差が 1.96e-6 と
LEO 並みに悪い(他の遅い軌道は 1e-9 台)。
`PREDICT_STEPS_PER_REV` = 600 を上げるか、遅い軌道側に別の下限を置くかは別途の判断。

## 判断2: 計画の衝突体集合を明示宣言にするか 【要判断・現状は事故】

`predictedAsPlanCollider` を宣言として足したが、**まだ誰も読んでいない。**
実際の衝突体集合(`plan-attractors.ts` の `collectPlanCollision`)は今も
`alive && collides && radius > 0 && displayState(t) !== null` で決まっている。

つまり現状は「**予測列を持っている物体が、たまたま計画の衝突体になる**」という
副作用で決まっており、宣言ではない。具体的な帰結:

- **弾は `collides = true, radius > 0` なので、`t ≈ 現在` では計画の衝突体になっている。**
  未来時刻では `displayState` が `null` になって落ちるだけで、意図した除外ではない。
- 自艦・基地・弾薬は今も計画線が終端する相手になっている(半径 2.6m / 330m / 数m)。

`predictedAsPlanCollider` を実際に読ませると、**計画線が自艦・基地・弾薬・弾で
終端しなくなる**(✕ 衝突マーカーが出なくなる)。これは目に見える挙動変更なので、
純リファクタには含めず判断を仰ぐ。**私の見立てでは読ませるべき**
(数分〜数日先の線が 2.6m の物体に当たる判定に意味は無く、当たっても終端すべき事象ではない)。

## 判断3: 予測要否のフレーム可変ゲートを入れるか

分解した3条件のうち `predictedForDisplay` は「表示時刻が未来を指しているときだけ」、
予測線は「描いているときだけ」意味がある。フィードバックにあったとおり
`show` を sync ではなく update で受け取れば、**理由が無い個体の予測を止められる。**

止めるときは嘘の予測を保持せず**破棄**する(数フレームで伸び切るので整合性として自然)。

判断してほしいのは**どこまでやるか**:
- (i) 予測線を描いていない個体だけ止める(戦闘ビューでは既に `mode='combat'` で
      自機以外を予測していないので、追加の効きはマップビュー限定)
- (ii) 表示時刻が現在を指している間は `predictedForDisplay` の理由を成立させない
      → マップビューでスライダを引いていない間、Ship/Base/AmmoPickup の予測が止まる。
      **ただし A-4 のとおり今は全個体が毎フレーム破棄されているので、
      止めた個体は次にスライダを引いた瞬間に伸び切っていない。**

(ii) は効きが大きいが、スライダを引いた直後の体験を悪くする。**要判断。**

## 判断4: 月近傍の dt² 誤差を受け入れるか

実験5の新発見。低月周回では RK4 の4次が中点則の2次に隠れており、
相対誤差 4.0e-3(絶対 7.3km/日)。刻みを細かくしても4次では減らない。

- (a) 受け入れる(月周回の予測は km 級にずれる)
- (b) RK4 の各段で天体位置を引き直す → **暦のコストが4倍**。論外に見える
- (c) 支配天体だけ段ごとに解析評価し、他は中点で据え置く

現状これは**バグとして報告されていない**ので、まず (a) で構わないと考えるが、
`DEVELOP/SPEC.md` に精度の限界として記録すべき事実ではある。

## 判断5: A-0(積分の毎サブステップ天体窓)にどう向かうか

**いま最大の単一項目**で、かつ触っていない。A-3 を却下したので、残る筋は:

- (a) サブステップ数そのものを減らす(`SUBSTEP_MAX_DT` を上げる / `dt` の上限 0.1s を下げる)
      → 物理の刻みが変わるので精度に直結。**要判断**
- (b) `Ephemeris` の合成そのものを速くする(1回 177〜283µs の中身の最適化)
- (c) 同一時刻の重複呼び出しキャッシュ(フィードバックのとおり**最後に**)
