# 展開式パネル(放熱板/太陽電池)の共通化計画

## 1. 現状の重複箇所

`src/game/vessel/radiator.ts`(`RadiatorSystem`)と `src/game/vessel/power.ts`(`PowerSystem`)は、
「蛇腹式に上下2枚展開するパネル」という同一の見た目・振る舞いを別々に実装している。

- **`Panel` 内部クラス**: 両ファイルとも `{ deployTarget: 0|1; deploy: number }`
  (radiator.ts:73-76, power.ts:9-12)。初期値だけ違う(放熱板は 0=収納開始、太陽電池は 1=展開開始)。
- **展開度補間**: `dt / C.RADIATOR_DEPLOY_TIME` によるランプで `deploy` を `deployTarget` へ近づける
  ロジックが radiator.ts:136-144 と power.ts:50-55 でほぼ一字一句同じ。太陽電池側のコメントに
  「同じ速度を使用」と明記されている(power.ts:50)= 名前と用途の不一致を自覚した流用。
- **折り目角度計算(even/odd交互回転)**: radiator.ts:148-160(`tilt`/`foldThetas`)と
  power.ts:73-81(`sync()` 内にインライン)。符号を side ごとに反転し、偶数折り/奇数折りで
  逆方向に振る同じ構造。放熱板は Y軸回転・0..STOW_TILT..RADIATOR_DEPLOY_TILT、太陽電池は
  Z軸回転・0..STOW_TILT..0(完全に平ら)という違いはあるが、"deploy→tilt→even/odd" の変換の形は同じ。
- **`hasSide`/`toggle`/`deployOf` 等**: radiator.ts:118-132,256 と power.ts:36-45,113 が
  ほぼ同一実装(メッシュが無い side は何もしない/欠落)。
- **メッシュ探索**: どちらもコンストラクタで `renderObject.getObjectByName` を fold 数ぶんループし、
  1つでも欠けたら側ごと欠損として進める(radiator.ts:96-108, power.ts:24-33)。放熱板は
  `RADIATOR_OBJECT_NAMES`/`RADIATOR_FOLD_COUNT`(render/ships.ts, hull/part-meshes.ts)という
  named constant 経由、太陽電池は `` `solar${Up|Down}Fold${i}` `` のリテラルかつ fold 数固定 `6`
  (これも実質 `RADIATOR_FOLD_COUNT` と同値だが独立した決め打ち)。

固有ロジックとして残るべきもの:
- 放熱板固有: `wear`(損耗度、パーツ残HP由来)、`radiatingArea`/`panelArea`(放熱面積)、
  `RadiatorFold`(接触代理オブジェクト、GameEntity派生で衝突判定に参加)、`collisionFolds`、
  `tipWorldPosition`、`solarLoad`(太陽入射)。
- 太陽電池固有: `charge`/`chargeRatio`/`chargeJ`(蓄電量)、`update()` 内の発電計算
  (`cosIncidence × sunlit × deployMult × totalPowerGeneration`)。

呼び出し元(vessel.ts:463-464 で構築、850/858 で `update()`、1110-1111 で `sync()`)は
両者を並べて同じ形で呼んでおり、呼び出し側からも「同じ種類のもの」として扱われている。

## 2. DEVELOP/OWNERSHIP.md との乖離

OWNERSHIP.md 554行目は「太陽電池の蓄電量 | `PowerSystem` | (中略)メッシュ操作なし(パネルは
固定)。`sync()` を持たない」と書いているが、実装の `PowerSystem` は
`solarFolds: Partial<Record<SolarSide, THREE.Object3D[]>>` を保持し、`sync()`(power.ts:72-91)で
毎フレーム `fold.rotation.z` を書き換えている。**これは明確な文書とコードの乖離であり、
太陽電池パドルが後から蛇腹展開式に変更された際に文書更新が追随しなかったもの**と判断できる。

## 3. 提案する設計: コンポジション(共有ヘルパークラス)を採用、継承は不採用

**継承を選ばない理由**: `RadiatorSystem`/`PowerSystem` は「同じ基底の特殊化」ではなく、
「共通の小さな振る舞い(蛇腹パネルの開閉)を、全く別の目的(放熱/発電)のシステムがそれぞれ
利用している」関係。継承にすると基底クラスが `wear`/`RadiatorFold`/`charge` のどちら向けの
拡張点も持たない中途半端な抽象になり、`/refactor-fixed` の「Gameにロジックを書かない」に類する
「責務の混在を隠す抽象化」を生む。また CLAUDE.md はクロージャ注入も禁じているため、
基底の `update`/`sync` を仮想メソッドで挟むより、**独立した値オブジェクト + 共有ヘルパー関数**の
組み合わせの方が見通しが良い。

**新規モジュール**: `src/game/vessel/deployable-panel.ts`

- `class DeployablePanel { deployTarget: 0 | 1; deploy: number }`
  (コンストラクタ引数で初期値 0/1 を選べるようにし、放熱板/太陽電池の初期状態差を吸収)
- `function stepDeploy(panel: DeployablePanel, dt: number, deployTimeSec: number): void`
  — 現在 radiator.ts:136-144 / power.ts:50-55 の補間ロジック。`deployTimeSec` を呼び出し側が
  渡す形にして、`RADIATOR_DEPLOY_TIME` の太陽電池への誤流用を解消する(§4-3ステップ参照)。
- `function foldTilt(deploy: number, stowTilt: number, deployedTilt: number): number`
  — `STOW_TILT + (deployedTilt - stowTilt) * deploy` の線形補間。放熱板は
  `deployedTilt = RADIATOR_DEPLOY_TILT`、太陽電池は `deployedTilt = 0` を渡せば両方表現できる。
- `function foldThetas(side: 'up'|'down', tilt: number): { even: number; odd: number }`
  — side 符号 × even/odd 交互反転(radiator.ts:156-160 / power.ts の該当部分と同一)。
- `function findFoldMeshes(renderObject: THREE.Object3D, namePrefix: string, foldCount: number): THREE.Object3D[] | undefined`
  — `getObjectByName` ループと「1つでも欠けたら undefined」判定の共通化
  (radiator.ts:99-103 / power.ts:27-29)。命名は呼び出し側が組み立てて渡す(放熱板は
  `RADIATOR_OBJECT_NAMES`+`radiatorFoldName`、太陽電池は同種のヘルパーを新設して渡す)。

`RadiatorSystem`/`PowerSystem` はこのモジュールの純関数群を**呼ぶ**形にとどめ、
自身の `panels: Record<Side, DeployablePanel>` は今まで通り自分で保持する
(=コンポジション。共有クラスをフィールドとして持つのではなく、値と純関数を組み合わせるだけ
なので、「所有」は従来どおり各システム自身のまま変わらない)。

`RadiatorFold`(衝突代理)と `solarLoad` の面積計算は放熱板固有のまま `radiator.ts` に残す。
太陽電池の発電計算(`cosIncidence`/`deployMult`/`charge` 更新)も `power.ts` に残す。

## 4. 変更手順(段階的)

1. **`deployable-panel.ts` を新設**し、上記4関数+`DeployablePanel`型を実装。
   既存コードの丸写しから始め、ロジックの変更はしない(純粋な抽出)。
2. **`RadiatorSystem` を書き換え**て `deployable-panel.ts` の関数を呼ぶ形にする。
   `panels`/`hinges`/`folds`/`wear` 等の既存フィールドは変えない。`tilt()`/`foldThetas()` を
   削除し `deployable-panel.ts` の同名関数へ委譲。`update()`/`sync()` の中身を置き換える。
   `test:physics` は対象外だが `npm run typecheck` を通す。
3. **`PowerSystem` を書き換え**て同様に委譲。ここで **`RADIATOR_DEPLOY_TIME` の誤流用を解消**する:
   `const.ts` に `SOLAR_PANEL_DEPLOY_TIME`(値は現状と同じでよい。挙動を変えないことを優先し、
   値の変更は本計画のスコープ外)を新設し、`PowerSystem.update` はそちらを渡す。
   `RADIATOR_DEPLOY_TIME` という名前自体は放熱板専用の意味に戻る。
4. **太陽電池側の fold 名決め打ちを解消**: `render/hull/part-meshes.ts` に
   `SOLAR_OBJECT_NAMES`(`{ up: 'solarUp', down: 'solarDown' }` 相当)+
   `solarFoldName(side, fold)` ヘルパーを追加し、`solarUpFold0` 等の文字列組み立てを
   放熱板と同じ形に揃える。`PowerSystem` のメッシュ探索もこれを使う形にする
   (`findFoldMeshes` へ渡す `namePrefix` をこのヘルパー経由で作る)。
   fold 数は既存通り `RADIATOR_FOLD_COUNT`(=6)を太陽電池も共有する — 定数名の意味論的な
   ズレ(放熱板の定数を太陽電池が読む)が気になる場合は `PANEL_FOLD_COUNT` へ改名し、
   両ファイルから読ませる案もあるが、挙動に影響しないため任意ステップとする。
5. **`npm run typecheck`** を実行し、両ファイルおよび呼び出し元(`vessel.ts`)に型エラーが
   無いことを確認。
6. **`DEVELOP/OWNERSHIP.md` を更新**(§5参照)。
7. コメント方針の点検(`/comment` に従い、共有ヘルパー側の関数直前コメントが呼出規約を
   説明しているか、`RadiatorSystem`/`PowerSystem` 側に「以前は」等の経緯が残っていないかを見直す)。

## 6. 検証方法

- `npm run typecheck`(必須、変更範囲が `src/game/vessel/*.ts` のため)。
- `src/physics/` は触らないため `npm run test:physics` は不要(CLAUDE.mdの既定方針通り)。
- 挙動確認は `/verify` を使ったヘッドレス起動で、放熱板・太陽電池パネルの展開/収納アニメーション
  が変更前と同じ速度・角度で動くこと、`Digit9`/`Digit0` トグルと HUD の展開度表示
  (`RadiatorSystem.deployOf`)が正しく動くことを目視確認する
  — ただしこれはユーザーが明示的に動作確認を求めた場合のみ実施し、本計画の必須ステップにはしない。
- リグレッションが疑わしい場合は、`stepDeploy`/`foldThetas`/`foldTilt` を旧実装の出力値と
  数点(deploy=0, 0.5, 1 / up, down)で手計算突き合わせる。

## 7. リスク・注意点・自己レビュー

- **本当にシンプルになっているか**: 抽出対象は「値の変換をする4つの小さな純関数」だけであり、
  状態(`panels`/`wear`/`charge`/`folds`)は従来通り各クラスが持ち続ける。これは
  `/refactor-fixed` が禁じる「Game 的なロジックの寄せ集め」にはならず、むしろ
  `physics/` 的な「座標・角度計算の純関数」を1箇所にまとめるだけの安全な切り出しである。
  継承を避けたことで、将来「パネルが3枚以上になる」「折り方式が変わる」等の変化があっても
  基底クラスの契約を壊さずに済む。
- **リスク1**: `findFoldMeshes` の共通化で `undefined` 判定(1つでも欠けたら側ごと欠損)の
  境界条件が既存2実装で完全に同一か要確認(読んだ限り同一)。
- **リスク2**: `PowerSystem.update` の引数に `Vessel` 型を直接取っている
  (`import('../vessel/vessel').Vessel`、循環 import 回避のためインライン型)。
  今回のリファクタでは触れないが、将来この依存も見直す余地がある(スコープ外として明記のみ)。
- **リスク3**: 定数名 `RADIATOR_DEPLOY_TIME` を太陽電池からも参照させたまま残す選択肢と、
  `SOLAR_PANEL_DEPLOY_TIME` を新設する選択肢のどちらを採るかはユーザー確認が望ましい
  (値は同じでも「名前の意味論的独立」を優先するなら新設一択、変更差分を最小にしたいなら
  据え置きも可)。本計画は新設を推奨するが、実装時に確認する。
- **やらないこと**: `RadiatorFold`(衝突代理)、`solarLoad`(太陽入射計算)、`charge`
  (蓄電量)まわりのロジック統合はしない — これらは放熱/発電という別々の物理量であり、
  無理に共通化すると却って可読性を損なう。
