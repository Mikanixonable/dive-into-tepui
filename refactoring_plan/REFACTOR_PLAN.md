# 方針

- トップレベルの適切なオーケストレーション化
  main.tsやgame.tsに実装が直接書かれるべきでない
- 関数、モジュールの疎結合化と責務の整理
  - 過剰責務（モジュールや関数が長すぎる）の解消
  - 過小責務（たらいまわし配線のみの関数、モジュール）の削除、統合
  - 混戦責務（この処理はこの関数にあるべきでない。この関数はこのモジュールにあるべきでない）の整理
- 重複実装、類似実装の解消、コード、値を適切に再利用する
- 不適切な命名の解消

## 不要なクロージャ注入
ctxと似て、脱却すべきデザインパターン。クロージャの利用の問題と改善は3種類ある

1. 外部コンテクストを取得するためのクロージャ
getExternalState が典型。 原則として、都度引数から注入するべきで、それで煩雑になる場合はモジュール内で自己解決できるように参照共有しておく形になる。

2. 外部に副作用を与えるためのコールバック
addEnemyとかが典型。広範囲に複雑な事象が起きる場合はイベント駆動のように登録せざるを得ないが、基本的には避けるべき。影響範囲が単独のクラスインスタンスであれば、引数またはコンストラクタでその参照を注入して渡して変更してもらうべき。

3. イベント登録のためのコールバック
wireHudCallbacksでの利用例が典型。問題構造は要検証。
DOMにイベントを登録するのは自然なことであるから、HUDが適切に構造化されれば修正不要である可能性もある。

## フローティングオリジン設計
このプロジェクトでは座標計算（倍精度）と描画（単精度）の両方の精度を担保するため、フローティングオリジンを採用しています。論理上は物理的な慣性系で処理し、表示のときにプレイヤー座標を原点に取り直して描画しています。
クラスのプロパティに保管される座標値はフローティングオリジン補正をする前の絶対座標系であるべきで（player.state.rとかと同じ座標系）、syncで座標変換（と言っても平行移動するだけのはずですが）します。entitiyなどが典型的な正しい実装です。

しかし、違反している例があります。
たとえば、cameraではupdateでフローティングオリジン基準の座標をフィールドに保管してしまっていて、syncが補正用の引数をもらっていません。playerも「プレイヤー座標系では常に原点になるから」とフローティングオリジンを受け取っていませんが、これは将来別の点（例えばカメラ座標）をフローティングオリジンに採用したときに壊れます。player.state.rとフローティングオリジンは別の意味論を持っていると考えて区別してください。

この設計思想をsync系全体で統一します。
floatingOrigin: FloatingOriginをgameに追加し、sync冒頭で適当な値に設定したうえでsync系全体の共通で引数として渡してください。
現時点ではプレイヤー座標をフローティングオリジンとしていますが、それが他の値に差し変わっても破綻しない（カメラとオブジェクトの相対位置が変わらない）ように設計してください。
