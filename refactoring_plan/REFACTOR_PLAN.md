# 方針

- トップレベルの適切なオーケストレーション化
  main.tsやgame.tsに実装が直接書かれるべきでない
- 関数、モジュールの疎結合化と責務の整理
  - 過剰責務（モジュールや関数が長すぎる）の解消
  - 過小責務（たらいまわし配線のみの関数、モジュール）の削除、統合
  - 混戦責務（この処理はこの関数にあるべきでない。この関数はこのモジュールにあるべきでない）の整理
- 重複実装、類似実装の解消、コード、値を適切に再利用する
- 不適切な命名の解消

## 不要なクロージャ注入
ctxと似て、脱却すべきデザインパターン。クロージャの利用の問題と改善は3種類ある

1. 外部コンテクストを取得するためのクロージャ
getExternalState が典型。 原則として、都度引数から注入するべきで、それで煩雑になる場合はモジュール内で自己解決できるように参照共有しておく形になる。

2. 外部に副作用を与えるためのコールバック
addEnemyとかが典型。広範囲に複雑な事象が起きる場合はイベント駆動のように登録せざるを得ないが、基本的には避けるべき。影響範囲が単独のクラスインスタンスであれば、引数またはコンストラクタでその参照を注入して渡して変更してもらうべき。

3. イベント登録のためのコールバック
wireHudCallbacksでの利用例が典型。問題構造は要検証。
DOMにイベントを登録するのは自然なことであるから、HUDが適切に構造化されれば修正不要である可能性もある。

## フローティングオリジン設計の一貫性
このプロジェクトでは座標計算（倍精度）と描画（単精度）の両方の精度を担保するため、フローティングオリジンを採用しています。論理上は物理的な慣性系（正確には地球原点+摂動要素かな？）で処理し、表示のときにプレイヤー座標を原点に取り直して描画しています。
**updateで計算してクラスのプロパティに保管される座標値はフローティングオリジン補正をする前の座標系であるべき** で（player.state.rとかと同じ座標系）、syncで座標変換（と言っても平行移動するだけのはずですが）します。

この設計思想をsync系全体で統一したいです。
floatingOrigin: FloatingOriginをgameに追加し、game.sync冒頭で適当な原点座標を設定したうえでsync系全体で共通の引数として渡してください。
現時点ではプレイヤー座標をフローティングオリジンとしていますが、それが他の値に差し変わっても破綻しない（カメラとオブジェクトの相対位置が変わらない）ように堅牢に設計してください。
つまり、player.state.rとフローティングオリジンは別の意味論を持っていると考え、座標系を厳密に区別すべきです。

しかし、違反している例があります。
たとえば、cameraではupdateでフローティングオリジン基準の座標をフィールドに保管してしまっていて、syncが補正用の引数をもらっていません。
playerも「プレイヤー座標系では常に原点になるから」とフローティングオリジンを受け取っていませんが、これは将来別の点（例えばカメラ座標）をフローティングオリジンに採用したときに壊れます。
OrbitEntityはfloatingOriginではなくvec3を受け取ってしまっているという点以外は、問題ありません（軽微な修正）。
その他にも違反している箇所があったら修正してください。

もちろん、updateはfloatingOriginを受け取るべきではありません。updateは物理的な慣性系での座標計算を行うので、floatingOriginとは関係ありません。べきです。もしそれが必要な箇所があったら設計がおかしいです。例えばchaseCameraはプレイヤーを追いかけるカメラであり、フローティングオリジンを追いかけるカメラではありません。mapCameraは固定座標系でのカメラなので、プレイヤー座標を受け取らないはずです。

なお、Bulletは特殊な例外で、フローティングオリジンとの相対速度によって向きを変更しています（モーションブラー的な表現）。この場合もsyncはfloatingOriginを受け取るべきという思想は一貫し、そのためにfloatingOrigin.vがあるのでそれを参照してください。

## 姿勢制御を角加速度記憶、自動加算に分離したい

## torqueとtauの一元化？
playerThrottleのtauとtorqueの関係を整理する。現在、tauはrcsEffectが参照するために出力していて、tauとtorqueが別の経路で計算されているが、よく見ると重複計算が多いし、そもそもほとんどの場合には（あるいは常に）定数倍などを除いて？一致すべきであるものであるように思える。現状の計算過程を整理して、torqueとtauにどのような対応関係があるのか整理し、torqueへの一元化を目指す。
tauにautoAlignが算入されていないのとかはバグと考えられる。論理上のトルクと視覚的なrcsは一致していてほしい。
rcsEffectはtauではなくtorqueを参照すればいいはずだ。
