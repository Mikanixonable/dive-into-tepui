## Current state

A playable LEO (low Earth orbit) shooting game: TypeScript + Webpack + npm, Three.js `WebGPURenderer` (via the `three/webgpu` entry point). Real-scale/real-time Earth orbit (player starts at 420 km / 97° inclination), body-frame RCS translation, manual rotation with RCS damping and a prograde-hold autopilot, time warp, lead-marker gunnery against enemies that shoot back with lead-aimed plasma, shell casings and destruction debris on accurate orbital physics, win on destroying all enemies, lose on being shot down or on atmospheric reentry (drag decay → adiabatic-heating overheat or dynamic-pressure breakup). Also: Earth-shadow lighting, target-board bullet-pass markers, an orbit-planning map mode ([M]: Earth-centered camera, with the camera's frame and the predicted trajectory's frame selected independently on two separate panels, click the predicted trajectory to place a maneuver node — several nodes can be chained, each frozen as an absolute post-burn state — W/S/A/D/Q/E adjust Δv, [N] auto-warps to the next node, BURN guide shows remaining Δv until the actual orbit matches the planned elements within tolerance), and four stages (stage 2 = Molniya-orbit enemies, unlocked once stage 1 has been cleared — tracked via `unlock-manager.ts`'s `UnlockManager`, which persists per-stage clear counts to localStorage and toasts newly-unlocked stages; stage 0 = near-combat training scoreattack, stage 00 = infinite survival, both always unlocked; `?stage=` URL param skips the select screen). Each frame is `Game.update` → `Game.sync` → `Game.render`; the render phase draws `cameraSystem.activeCamera` — combat chase cam (near 2 / far 6e7) or the map camera (near 1e4 / far `MAP_CAMERA_FAR` = 1.5e10) — plus a scissored second pass for the firing-time PIP gunsight. Stars/sun/moon billboards follow the active camera position so the map zoom-out doesn't exit the star shell.

`dev.md` is explicitly marked as human-authored only ("この文書は人間のみが記入できる") — do not edit it. Read it for project context, but leave modifications to the user.

### Naming: render / update / build / sync (no `draw`)

Per-frame function names must reflect what they actually do, consistently across the codebase:

- **`render`** — reserved for functions that literally call the three.js renderer's `render(scene, camera)` (only `Game.render` and `PipRenderer.renderPip` qualify). A function that only constructs or mutates scene state is not a "render" function even if it runs in the render phase (e.g. `Player.syncPlayer`, `EnvironmentScene.sync`).
- **`update`** — advances or mutates logical/simulation data (not three.js mesh state directly).
- **`build`** — registers new meshes/objects into the scene (construction, not per-frame).
- **`sync`** — matches the transform/appearance of already-registered meshes (or HUD DOM elements) to logical data that was already computed elsewhere. Prefer plain `sync*` names; don't tack `Render` onto a sync method name (e.g. `syncCamera`, not `syncRenderCamera`) — it blurs the render/sync boundary this rule exists to keep clear.
- **`draw`** is never used — rename on sight.

The rAF loop in `main.ts` makes this split structural: it calls `Game.update(dt)` → `Game.sync(dt)` → `Game.render()` as three separate top-level phases. `update` must not touch THREE.js objects; `sync` builds the frame's `FloatingOrigin` and pushes already-computed logical state into meshes/DOM; `render` only issues draw calls. Keep sub-functions on the correct side of that line — a class like `PipRenderer` should contain only render-pass code, not logical bookkeeping (state that merely happens to be read at render time still belongs with the system that owns it, e.g. `PipCamera` computes the PIP viewpoint in `update`/`sync`, and `PipRenderer` only draws it).

### Commands
- `npm run dev` — start webpack-dev-server at http://localhost:8080
- `npm run build` — production build to `docs/` (the committed GitHub Pages output — running it rewrites the published bundle)
- `npm run typecheck` — `tsc --noEmit`
- `npm run test:physics` — regression tests for `src/physics/*.ts` (pure functions, no DOM/THREE deps): compiles `tests/physics/*.test.ts` + the physics modules to CommonJS via `tsconfig.test.json` (outDir `tests/dist`, gitignored) and runs them in node with `node:assert/strict` (no extra devDependency). Covers vec3 smoke tests, orbital.ts Kepler round trips (`stateFromElements`⇄`elementsFromState`, `trueAnomalyAt`/`positionOnOrbit`/`velocityOnOrbit`), `stepOrbitRK4` one-period drift and epoch advance, `j2Accel` RAAN regression rate, attitude.ts kinetic-energy conservation + quaternion norm, atmosphere.ts density-table boundary/monotonicity, and ephemeris.ts sun/moon distance-and-period sanity. Where no clean theoretical value exists (RK4 drift, J2 rate, table-boundary continuity), the test pins the *measured* current behavior with a loose margin rather than an idealized bound — run this before/after any change under `src/physics/`.

There is no other automated test suite wired into npm beyond `test:physics`.

### Architecture

Simulation state lives in ECI coordinates (Y axis = north pole), SI units (m, m/s), as plain `{x,y,z}` data (`physics/vec3.ts`'s `Vec3` is a **branded type** — build it with `v3()`/the helpers, never with a bare object literal).

`OrbitState` is a **timed** state vector — `{t, r, v}`, where `t` is the absolute simTime epoch — and it is the *single* type used for every "state at a moment": entity state, entity history, predicted-trajectory samples, and maneuver-plan nodes. There is deliberately no second type carrying the same information (the former `TrajectorySample`, `LineSample` and `PlannedNode.time` were folded into it), so a state and its time can never be passed as two arguments that disagree. `stepOrbitRK4` advances `t` along with `r`/`v`, which is why `predictTrajectory`/`propagateState`/`toFrameState` no longer take a separate time argument.

**The base data types are immutable, with no exceptions**: `Vec3`, `OrbitState` (`physics/orbital.ts`), `Quat`/`Attitude` (`physics/attitude.ts`) are all `readonly` and are advanced by *replacement*, never by in-place mutation — `stepOrbitRK4` returns a new `OrbitState`, `stepAttitude` returns a new `Attitude`, and every owner assigns the result (`entity.state = …`, `entity.att = …`). This is a correctness invariant, not a style preference: `OrbitEntity.state`'s setter is what invalidates the memoized `elements` **and pushes the outgoing state onto `history`**, and it can only do that because nothing else can change the state behind its back. Consequences: defensive copying is unnecessary (`vec3.clone()` does not exist), and **everything under `physics/` is a pure function returning fresh values** — there are no `*Into`/`out`-parameter variants and no module-level scratch buffers. Those existed (軽量化計画 A-1) and were deliberately removed. The cost is real but small: in an isolated Node benchmark `stepOrbitRK4` went 1520 → 2190 ns/step and `stepAttitude` 218 → 414 ns/step, which at a typical ~400 live entities works out to roughly +0.35 ms per frame in the `update` phase — not distinguishable from run-to-run noise in the actual game (~5 ms update phase). The immutability that buys is what makes the `elements` memo correct, so the trade is intentional. If the entity budget grows enough for this to matter, the answer is a physics LOD (軽量化計画 B-1), not reintroducing mutable scratch into `physics/`. Rendering uses a **floating origin**: `game/floating-origin.ts`'s `FloatingOrigin` is rebuilt every `Game.sync` from the player's post-integration state, and `RtoThreeV3`/`VtoThreeV3` are the *only* bridge from logical `Vec3` to `THREE.Vector3` — so f32 GPU precision never sees absolute LEO magnitudes. Every `sync` takes the `fo` and must not use `player.state.r` as the render origin directly (the two are semantically distinct; the origin could move to the camera later). Combat camera: near=`COMBAT_CAMERA_NEAR`=2m, far=`COMBAT_CAMERA_FAR`=6e7m — no logarithmic depth needed (see comment in `const.ts`).

Physics runs on the main thread (per-entity central-gravity two-body integration is cheap); the N-body worker is **currently unused**, kept for the future cislunar (Sun-Earth-Moon) phase.

`src/game/` is an orchestrator (`game.ts`) plus subfolders grouped by concern: `player/` (player ship state), `orbit-entity/` (the shared entity base classes and their passive simulation), `camera/`, `plan/` (maneuver planning, independent of whether the map is open), `predict/` (future-trajectory display), `stages/` (per-stage behavior), `hud/` (DOM overlay), `marker/` (screen-projected markers), `vfx/`, and `input/`.

**`*Ctx` snapshot objects are a rejected pattern here** — don't add new ones and don't widen the survivors. Almost all of them have been expanded into explicit arguments or shared references; what remains is `EnvironmentSyncParams` (`render/environment-scene.ts`), `PipRenderCtx` (`pip-renderer.ts`), and `Player.behave`'s parameter object. `refactoring_plan/STOP_USING_CTX.md` (plus the open items in `refactoring_plan/refactoring_todo.md`) is the live status of that work — trust it over this file.

- `src/main.ts` — entry point: WebGPU scene init (`initScene`, with a `showLoading` overlay while the WebGPU pipeline compiles), stage resolution (`resolveStageSelection` in `stages/stage-select.ts`), an error overlay fallback, and the rAF loop (`startAnimationLoop`) driving `Game.update` → `Game.sync` → `Game.render` plus the optional `PerfMeter`. It also owns `Hud`/`Sfx`/`SettingsPanel` (`initHud`) — these are constructed before `Game` (and before the stage-select screen) because the title/select screen needs them too, so `Game` receives them as constructor arguments rather than constructing them itself. `main.ts` wires `SettingsPanel.onSettingsOpenChange` to `Game.pause()`/`Game.resume()` (the settings menu's open/close is the only driver of the pause state), `onBgmToggle` to `Sfx.setBgmEnabled`, and `onQuitToTitle` to reload without `?stage=`.
- `src/perf-meter.ts` — `PerfMeter`: `?perf=1` debug overlay (frame time split between update/sync+render, entity counts via `Game.perfCounts()`, JS heap). Owned by `main.ts`, not by `Game`.
- `src/game/game.ts` — orchestrator: owns `isPaused` (write-gated behind the public `pause()`/`resume()` methods — `main.ts` is the only caller, via the `SettingsPanel` wiring above), the frame's `FloatingOrigin`, and the top-level `update`/`sync`/`render` split (input edges → `MapModeToggler` → `Player.behave` → `Stage.update` → `Simulator.stepSimulation` → collision/board/loss/cleanup → camera → plan editing; then sync: camera → environment → player → entities → VFX → orbit lines → markers → HUD panels). It does **not** own `simTime` (that's `Simulator`) or the win/lose `phase` (that's `Stage`), and it does **not** construct `Hud`/`Sfx`/`SettingsPanel` (received from `main.ts`, see above). It constructs and drives `CameraSystem`, `Simulator`, `HitSystem`, `CollisionPhysics`, `EffectsSystem`, `Targeter`, `PlanEditor`/`PredictSystem`/`PlanGuide`, `MapModeToggler`, `SimSpeedManager`, `Ephemeris`, `MarkerManager` (plus the two marker sets no single object can own — `GroupedMarkers`/`LeadMarkers`), `UnlockManager`, `PipRenderer`, and the active `Stage`. **It no longer knows which key does what**: `handleInput` just hands `Input` to each owner in priority order (`SettingsPanel` `[Esc]` → `Hud` `[H]` → `Stage` `[R]` → `SimSpeedManager` `[,]`/`[.]`/`[N]` → `MapModeToggler` `[M]` → `PlanEditor` `[X]`), and each consumes what it owns. Keys that only make sense while playing are taken by their owner's own per-frame call further down (`Player.behave` for `[T]`/`[F]`/`[V]`/`[C]`/`[1]`-`[3]`/`[R]`, `CameraSystem.update` for `[G]`, `PlanEditor.handleMapPointer` → `CameraSystem.handleMapPointer` for map clicks, `Targeter.updateCombatTargeting` for combat right-clicks). The only thing `game.ts` decides is the *order*. Many public fields (`cameraSystem`/`player`/`activeStage`/`simulator`/`targeter`/...) exist because `hud/panel.ts`'s `HudPanels.update(game, dt)` reads the whole `Game` instance directly rather than a narrow ctx.
- `src/game/const.ts` — all gameplay tuning constants (thrust, sim speed levels, fire rate, hit radii, ammo/belt geometry, camera near/far, prediction throttles, stage tuning...).
- `src/game/floating-origin.ts` — `FloatingOrigin`: the render origin's motion state (`r`/`v`) and the sole `Vec3` → `THREE.Vector3` conversion (`RtoThreeV3` for positions, `VtoThreeV3` for relative-velocity-facing draws like bullets).

`src/game/player/` — the player ship, split by concern (all owned and composed by `Player`, which exposes read-only getters for `game.ts`/HUD):
- `player.ts` — `Player extends Ship`: initial LEO placement (`makeInitialState`/`progradeAttitude`, `INITIAL_ALT`=420 km / `INITIAL_INC_DEG`=97°), the per-frame `behave` (belt → own edge keys → torque → HP regen → fire → thrust) and `checkLoss`/`syncPlayer` entry points, damage/loss handling (`attacked`, `checkLoss` — hull heat/dynamic-pressure/reentry-altitude thresholds via `thermal`), and composes `throttle`/`fire`/`belt`/`thermal`/`thrustEffects`/`rcsEffects`/`markers`. `handleEdgePress` claims the ship-side keys (`[T]`/`[F]`/`[V]`/`[C]`/`[1]`-`[3]`/`[R]`) via `input.takeKeys()`, which consumes them so no later module double-handles. `[R]` is only consumed when a manual reload actually starts.
- `player-throttle.ts` — `PlayerThrottle`: translation input → thrust accel (`buildThrustAccel`, all 6 body-frame directions), manual rotation + RCS damping, and the prograde-hold autopilot (`autoAlignTorque`): builds a desired attitude quaternion (nose = velocity direction, roll reference = radial-out, re-orthogonalized so it's valid even for eccentric orbits where r⟂v doesn't hold exactly — see `physics/attitude.ts`'s `qFromForwardUp`), converts the quaternion error to a body-frame axis-angle, and applies a PD torque (`PROGRADE_HOLD_KP`/`_KD`). `updateTorque` only *returns* the body torque (`Player` writes it to `entity.torque`) and `updateThrustState` only returns the thrust closure — the actual attitude/orbit integration is `Simulator`'s.
- `player-fire.ts` — `PlayerFire`: gun state (mag/round/barrel counters, reload timer), `updateFireState`/`fireCycle`/`consume` (the ammo state machine, returning `ConsumeResult` = `empty`/`normal`/`mag-reload`/`barrel-reload`), `fireGun` (bullet spawn, recoil, casing eject, muzzle flash, `ScoreCounter.recordShot`), and `dropBarrel`/`spawnEjectedMagazineFrame` for reload debris. `tickMapMode` advances only the reload timer while the planner is open.
- `belt.ts` / `belt-physics.ts` — the ammo belt display split from its physics: `belt-physics.ts`'s `BeltPhysics` is a pure Vec3/Quat Verlet-chain solver (position-based dynamics, no THREE/mesh dependency) for the belt's sag/twist under the ship's thrust+spin pseudo-forces; `belt.ts`'s `Belt` owns the link meshes and derives each link's transform from `BeltPhysics`'s solved state via parallel transport.
- `thermal.ts` — `ThermalSystem`: hull heating/dynamic-pressure (Sutton–Graves + Stefan-Boltzmann, `updateThermal`) and the altitude-descent-warning EMA (`updateAltitudeAlarm`); returns a `ThermalLimit` verdict — the actual destruction (`alive = false` + effects) happens in `Player.checkLoss`.
- `thrust-effects.ts` / `rcs-effects.ts` — billboard VFX for the main engine plume and the 4 RCS thruster puffs, positioned from `render/ships.ts`'s `MUZZLE_OFFSETS`/`RCS_BLOCK_OFFSETS`.
- `player-markers.ts` — `PlayerMarkers`: the HUD markers that follow from the ship's own position/attitude — the six orbital-frame direction markers (prograde/retrograde/normal/antinormal/radial in-out, the Navball stand-in), the `┼` boresight, and the map-mode `▷` self marker. `Player.syncPlayer` drives it, so callers never see a separate marker entry point.

`src/game/orbit-entity/` — the entity base classes and their passive (non-AI, non-input) simulation:
- `entities.ts` — `OrbitEntity` (base: state/attitude/mesh, `sync(fo)`, `torque`/`thrustFn` slots the owning system writes each frame, an `elements` getter memoized behind the `state` setter — assigning a new `OrbitState` drops the memo, which is the whole reason the state is immutable — a bounded past-state `history` the same setter maintains, and a default reentry-altitude `checkLoss`), `Ship` (adds name/hp/radius), `Ammo`, `DebrisPiece` (fragment/barrel/magazineFrame/casing variants), `BeltSection` (a per-link collision proxy the belt physics exchanges with `collision.ts`).

  **History is the `state` setter's job, not the integrator's.** `historyLength` (a per-class `protected` field, default 0 = record nothing) caps how many past `OrbitState`s an entity keeps; `Ship` and `Bullet` set it to 1, which is what `prevState` (used by `hit.ts`'s segment-vs-sphere test and `targeter.ts`'s board crossings) reads. Raising it is how past-trajectory rendering would be fed — the samples are `OrbitState`s, so they can go straight into `render/sampled-line.ts`. Casings/debris/ammo keep 0 so the pools that hold hundreds of entities cost nothing. `Simulator` no longer has a `trackPrevR` flag; it just assigns `entity.state`.
- `bullet.ts` — `Bullet extends OrbitEntity`: player/enemy bullets and enemy plasma bolts (`Shooter`/`BulletType`), its own lifetime check, and a velocity-facing (not attitude-facing) `sync` override that uses `fo.VtoThreeV3`.
- `enemy.ts` — `Enemy extends Ship`: enemy AI (`behave` — burst-fire plasma at the player using `physics/intercept.ts`'s `solveLeadTime`; per-group attacker cap and burst state live here), damage/destruction (`attacked`, `checkLoss`), its own `OrbitLine`, and its HUD presentation (`accentColor`, and `markerItem()` returning the `GroupedMarkerItem` the screen-marker set is built from — the enemy states what it looks like, `GroupedMarkers` decides how the set is laid out).
- `hit.ts` — `HitSystem`: segment-vs-sphere bullet collision only (tunneling-proof, `checkBulletHits`), called per substep from `Simulator`. Target-board marker recording now lives on `Targeter`.
- `simulator.ts` — `Simulator`: owns the `enemies`/`bullets`/`casings`/`debris`/`ammos` arrays (capped, oldest evicted on overflow), **`simTime`/`lastSimDt`**, the environment-acceleration closures (`envShip`/`envBullet`/`envSmall`, built by `makeEnvAccel` over `physics/envaccel.ts`'s `envAccelInto`), the substepped RK4 integration (`stepSimulation`, higher warp → more substeps, max 20s each, ≤64), the attitude integration for *all* entities including the player (`stepAttitudes`), lifetime cleanup (`cleanup`/`prune`), and the per-entity render sync (`sync(fo)`). AI/input/spawn decisions live in `game.ts`/`stages/`/`Enemy.behave`, which add entities back in via `addXxx`.
- `collision.ts` — `CollisionPhysics`: rigid-sphere impulse resolution for casings/enemies/pickups/belt links (`resolve`, called once per `Game.update` — not per substep — and only while `SimSpeedManager.canResolvePhysicalCollisions`).

`src/game/camera/` — every camera follows the same `update` (compute the viewpoint in absolute ECI, THREE-free) / `sync(fo)` (push it into the `THREE.PerspectiveCamera` through the floating origin) / `projection` (a `ProjectFn` built from the same math, independent of both the THREE matrices and `fo`) split:
- `camera-system.ts` — `CameraSystem`: owns `ChaseCamera`/`MapCamera`/`PipCamera` and exposes the active one (`activeCamera`/`activeCameraPos`/`activeCameraProjection`); owns `mapMode`/`zoomActive`. Also owns the map focus concern (= "where the map camera looks"): the `mapMarkers` label set, the `FocusGizmo` selection menu (wiring `onMenuFocus` to set `mapCamera.focus`, exposing `handleFocusRightClick`/`closeFocusMenu` for `game.ts` to drive), and the **MAP VIEW panel** (`camera/map-view-panel.ts` — focus shortlist / camera frame / view reset). Every control on that panel writes `mapCamera` state and nothing else, so the whole HUD wiring stays inside this class; `sync(fo)` pushes the panel's visibility and highlights each frame.
- `chase-camera.ts` — `ChaseCamera`: the combat third-person view, a togglable reference frame (`camFollowAttitude`: ship-attitude-relative vs. orbital-frame-relative, toggled by `[G]` via `toggleFollowAttitude`), and the `[Z]` gunsight view (`computeGunsightView`, FOV lerped to `ZOOM_FOV`).
- `map-camera.ts` — `MapCamera`: the map Earth-centered orbit camera (near=1e4/far=`MAP_CAMERA_FAR`). Its source of truth is just two **`cameraFrame`-relative** vectors (`offset_r` = focus→camera, `pan_r` = focus→look-target), so switching to the sun-rotating frame makes the viewpoint co-rotate for free; the ECI ⇄ frame round trip is delegated to `physics/frame.ts` and the class never brands values itself. `cameraFrame` (`'inertial'`/`'sunRotating'`) is the source of truth for **the frame the viewpoint is fixed to**, and only that — the frame the predicted trajectory is *drawn* in is `PredictSystem.trajectoryFrame`, a separate value the player selects independently. Focus (a label id) is resolved to a position via the injected `MapMarkers`. The future-ghost slider belongs to `PredictSystem`.
- `pip-camera.ts` — `PipCamera`: the firing-time picture-in-picture gunsight viewpoint (nose-fixed, `ZOOM_FOV`) as its own camera plus the screen `rect` and a rect-local `projection`. Separate from `ChaseCamera` so the main view is never re-posed; `PipRenderer` only draws it.
- `map-markers.ts` — `MapMarkers`: computes/projects the focusable-target labels (Earth/Moon/Sun/Earth-Moon L1–L5/Sun-Earth L1–L2) and the label lookup (`findLabel`) used both for focus resolution and focus-menu picking. A mapCamera-side concern, owned by `CameraSystem`.
- `focus-gizmo.ts` — `FocusGizmo`: the map-label focus-selection context menu (single responsibility: the focus targetKey + focus/cancel menu items). Uses the shared `hud/context-menu.ts`.

Screen projection itself is **not** in `camera/`: `physics/projection.ts` holds the pure math (`ViewFrame`/`projectToNdc`/`ndcToScreen`/`Projected`) and each camera exposes a bound `ProjectFn` (`(worldPos: Vec3) => Projected`) that consumers receive as an argument rather than importing.

### WebGPU renderer gotchas (three.js 0.169)
- `THREE.LineLoop` and `THREE.Points` sizing are not supported; use `THREE.Line` / triangle-based sprites.
- Additive-blended materials need explicit `transparent: true`.
- Headless-Chrome screenshots work with `--headless=new --enable-gpu --enable-unsafe-webgpu --disable-gpu-sandbox --no-sandbox` (flaky; retry a few times).

## Project concept (from dev.md)

An orbital-mechanics shooting game, intended as a web game, set in the Earth-Moon system (current build: LEO only):

- Gameplay centers on realistic orbital maneuvers and physically accurate ballistic calculations, low-poly but visually appealing depictions of Earth's atmosphere, spacecraft, and spacecraft destruction.
- Orbital calculations should account for Sun-Earth-Moon three-body dynamics, atmospheric drag, and tidal forces. Reference concepts to consider: Sun-Earth and Earth-Moon Lagrange points, sun-synchronous recurrent orbits, halo orbits, low-energy transfers and ballistic capture, double lunar swingbys, and gradual altitude-raising approach maneuvers (like the Kounotori HTV's ISS approach).
- Aesthetic goals: Earth auroras, auroras from solar storms, auroras from charged particles generated by combat, shadows on Earth's evening clouds, and the Dzhanibekov effect on destroyed debris.

## Controls (current build)

**Translation is body-frame, not orbital-frame** (`PlayerThrottle.buildThrustAccel` builds a direction in body axes and rotates it by `att.q`): W or Ctrl / S or Shift = nose-forward/aft (+Z/−Z), A/D = lateral (+X/−X), Q/E = vertical (+Y/−Y). All six fire at the same selected magnitude `THROTTLE_LEVELS[throttleIdx]` (3 stages — [1]/[2]/[3] — no "cutoff" stage; thrust exists only while a direction key is held). `input.ts` calls preventDefault on Ctrl+W/A/S/D/R so browser shortcuts don't fire while Ctrl is held as forward thrust (Ctrl+W/T/N and Ctrl+digit are browser-reserved and can't be blocked).

Rotation: I/K = pitch, **L/J = yaw**, **O/U = roll** (signs per `PlayerThrottle.updateTorque`'s `inX`/`inY`/`inZ`; RCS puff directions are derived from the resulting torque's signs in `RcsEffects.sync`, so the two can no longer disagree). T = RCS rotation damping toggle, **F = prograde attitude reset** (one-shot: only sets the hold ON), **C = prograde-hold autopilot toggle** (PD controller torquing the nose to the velocity vector; any manual rotation key cancels it), **V = fine-attitude toggle**.

G = toggle whether the chase camera's reference frame follows ship attitude vs. the orbital frame (see below). Z (hold) = gunsight zoom. Space / **right click** = fire; **right click on an enemy also locks/unlocks it as target** (`Targeter.handleTargetLockByRightClick`). Target selection has no dedicated key: without a lock, the target is whichever living enemy is closest to the camera forward axis (`Targeter.resolveAutoTarget`, recomputed every frame). **left drag** or **arrow keys** = camera yaw/pitch, wheel or two-finger pinch = zoom distance, **middle drag** = pan (map mode). `,` / `.` = time warp (thrust, guns, enemy fire and contact physics are all gated above ×`MAX_PHYS_SIM_SPEED` = 4 via `SimSpeedManager.can*`). M = orbit-planning map, N = auto-warp to the next node, X = delete selected node / discard the whole plan, H = help, R = manual reload (after the game ends it instead re-launches **the same stage** — `Stage.restart` navigates to `?stage=<id>`, since a plain reload would drop you back on the stage-select screen whenever you got there without a `?stage=` param).

Esc (or the ⚙ gear) = pause menu, owned by `hud/settings-panel.ts`: `SettingsPanel.toggle` fires `onSettingsOpenChange`, which `main.ts` syncs to `Game.pause()`/`Game.resume()` (so every open/close path — Esc, gear click, [閉じる] — pauses/resumes), plus a BGM toggle and a "quit to title" button (`onQuitToTitle` → `location.assign(location.pathname)`, dropping the `?stage=` param). While paused `Game.update` returns early, so HP auto-regen (`HP_REGEN_RATE` = 1 HP/s, inside `Player.behave`) can't be farmed from the menu.

While firing, a picture-in-picture zoom window is drawn as the frame's second render pass (`pip-renderer.ts`'s `PipRenderer.renderPip`, gated on `player.isFiring && !mapMode`). The viewpoint is its own camera (`camera/pip-camera.ts`'s `PipCamera`, nose-fixed at `ZOOM_FOV`, updated/synced every frame like the other cameras) — the main camera is never re-posed. During the pass `playerShipObj` is hidden and muzzle flashes are hidden via `EffectsSystem.setMuzzleFlashesVisible` (only `FlashEffect.muzzle === true` flashes — hit sparks and destruction flashes stay visible in the PIP). The window's overlay markers are *not* the render pass's job: `marker/pip-overlay.ts`'s `PipOverlay` (owned by `PipRenderer`, driven from `PipRenderer.sync`) runs in the sync phase like every other marker — the `+` crosshair at the rect centre (`pip-crosshair`), plus the current target's ◇ frame and ✛ lead marker projected into the PIP rect with `pipCamera.projection` (`pip-tgt`/`pip-lead`). All three are label-less so marker-collision resolution ignores them, and all three hide on frames where the PIP isn't drawn. `Game.pipActive` (= `player.isFiring && !mapMode`) is the single decision, handed to both `PipRenderer.sync` and `PipRenderer.renderPip`. Firing also implies fine-attitude authority (`FINE_ATTITUDE_SCALE` = 0.5): `Player.updateTorque` passes `fineAttitude || fire.isFiring`, so releasing the trigger restores full authority with no edge-tracking state. Pausing stops firing (`Player.pause` → `PlayerFire.stopFiring`), so the PIP closes with it.

The orbital direction markers (`player/player-markers.ts`) deliberately carry no key hints in their labels: combat-view translation is body-frame, so none of those six directions has a key. The keys that *do* mean prograde/normal/radial are the map-mode Δv edit keys, and the direction markers are hidden there.

Chase camera reference frame (`camFollowAttitude` on `ChaseCamera`, default **on**, toggled via `[G]`, which `CameraSystem.update` takes for itself): the third-person camera's yaw/pitch are always defined relative to a `(fwd, up)` frame, but *which* frame is configurable. `ChaseCamera.update` computes both candidate frames each call — the ship's own attitude (`boreFwd`/`boreUp`, nose +Z / body +Y rotated by `player.att.q`, the same pair that drives the zoom gunsight view) and the orbital frame (`chaseFwd`/`chaseUp`, prograde/radial-out) — and picks between them via `computeChaseView`/`computeGunsightView` based on `camFollowAttitude`/`zoomActive`/`player.alive`. ON (default) uses the ship's own attitude, so rotating the ship with I/K/J/L/U/O visibly swings the whole camera (including its roll) right along with it, RCS-linked. OFF uses the orbital frame, which stays independent of ship attitude and only slowly co-rotates with orbital motion.

Ammo system: guns fire alternately from the two front bores and consume magazine rounds (`MAG_ROUNDS`=32/mag, `INITIAL_MAGS`=3 linked at start, `MAGS_PER_BARREL`=3 consumed before a barrel-swap reload — doubling the per-mag capacity from an original 16-round design let the visible chain be roughly half as long while carrying comparable total ammo). The belt of unused mags hangs off the ship's starboard (+X) side as child meshes of `player.obj`, and the belt slides continuously into the hull as rounds are fired (`beltFeed` = 1 − rounds/`MAG_ROUNDS` offsets the anchor by up to one pitch; on mag consumption the feed wraps 1→0 exactly when the link count drops, so the motion reads as seamless). The head link sits half-inside the hull. `BeltPhysics.update` (in `player/belt-physics.ts`) simulates the belt's sag as an actual physics chain, not a canned animation: link joints are point masses (`beltPos`/`beltPrevPos`, Verlet-integrated in the ship's body frame) connected by rigid-rod distance constraints (position-based dynamics, 6 relaxation iterations per frame) to `MAG_BELT_PITCH`. Since the ship is in free fall, ordinary gravity can't sag anything (equivalence principle — belt and hull fall together); the only real driver is the fictitious force felt in the ship's non-inertial (accelerating/rotating) frame: `-a_thrust - α×r - ω×(ω×r) - 2ω×v` (translational inertia, Euler, centrifugal, Coriolis), built from `thrustAccelVec` (world-frame thrust accel, rotated into body frame, passed in each call from `Player.behave` via `Belt.update`) and `player.att.w` (with `α` estimated by finite-differencing `w` against `prevBodyW`, both tracked inside `BeltPhysics`). When the player isn't thrusting or rotating, the chain just hangs straight — no ambient wobble is faked in.

Each link's *orientation* is derived separately from its position, via parallel transport: `qBend = qDelta * qPrev` where `qDelta` is the minimal (zero-twist) rotation taking the previous link's local +X to this link's tangent — so bending (the chain folding link-to-link) is unconstrained by construction, matching a real ammo belt's easy up/down/left/right flex. Roll (twist about the link's own +X, the one DOF parallel transport leaves undefined) is instead tracked explicitly per link in `beltTwist[]`, driven by the ship's own roll rate (`player.att.w.z * MAG_CHAIN_ROLL_GAIN`) at link 0 and propagated down the chain with a one-frame lag (`prevTwist`) and exponential smoothing (`MAG_CHAIN_ROLL_RATE`), clamped every frame to `±MAG_CHAIN_MAX_ROLL_DEG` — so however it's driven, twist can never exceed that bound. The final per-link quaternion is `qBend * qTwist(local +X)`.

`CollisionPhysics.resolve(dt, ...)` (in `orbit-entity/collision.ts`; rigid-sphere impulse resolution for casings/enemies/pickups/belt) is called once per `Game.update` call — not per substep — and only while `simSpeedManager.canResolvePhysicalCollisions`, using the real (unwarped) `dt` so it stays consistent with the belt's own real-time cadence; at higher warp it's skipped entirely (substeps up to 20s each make rigid-body contact resolution meaningless there, and it's O(n²) over every casing). It uses `PLAYER_HULL_RADIUS` (real hull size, 2.6m) for contact, deliberately smaller than `PLAYER_RADIUS` (5m, used for bullet self-hit detection only) — reusing the bullet-hit radius here would fling freshly-ejected casings (spawned ~2.9m from the hull) outward on the same frame. A casing/hull impact directly triggers `Sfx.clank()` via the `onPlayerCasingImpact` callback, rather than polling distances every frame.

When mags run low (`LOGISTICS_LOW_MAGS`), resupply pickups spawn phase-shifted 1.25–2.5 km ahead on the player's own orbit (`stage-utils/logistics.ts`'s `Logistics.spawnForPlayer`; ▣ AMMO marker, absorb within `AMMO_PICKUP_RADIUS`). Casings use a CIWS-style bottleneck profile (rim/extractor groove/tapered body/shoulder/neck via `LatheGeometry`) with **low** ejection speed/spin (previous values made them visibly spin sideways at high rate). Spin-up SFX is filtered-noise friction (no oscillator). Enemy ships are modeled at `ENEMY_SCALE` (20×) via `obj.scale.setScalar(...)` with `ENEMY_RADIUS` (180 m) matching for hit detection; their destruction VFX (`spawnFlash` sizes, `scatterFragments` size range) scale by the same factor so the explosion reads proportionate to the larger hull.

Mouse buttons are swapped from the naive default: **left button drags the camera; a left click that moves less than `CLICK_MOVE_THRESHOLD` (6px) is instead queued as a click** (used to place maneuver nodes in map mode) — see `Input.clicks()`. Right button fires (and locks targets / opens map context menus). This lets map-mode node placement and camera dragging share the left button without a modifier key.

Map mode ([M]) does not freeze physics: `Simulator.stepSimulation` runs every frame while `activeStage.isPlaying && !paused`, and ship control (thrust/fire/manual attitude) is gated on `editor.editMode` since W/S/A/D/Q/E are repurposed for Δv editing there (in the planner they mean prograde/normal/radial, not body axes) — so time warp keeps working and the player can wait for a transfer window while planning. Only `editor.updateEditing` and the pointer dispatch are layered on top of `update`; the two map-mode panels (MAP VIEW / PREDICT) show and refresh themselves from their owners' `sync`. The map camera's drag yaw sign is intentionally opposite the combat chase camera's convention (`+=` vs `-=` on `mouse.dx`) so panning left/right reads the same in both views.
