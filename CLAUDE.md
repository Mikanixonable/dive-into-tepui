# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## 作業のルール

- **全体像はコードではなく文書から掴む。** 「どこで何が起きているか」「誰が状態を持つか」「いつ走るか」
  は `DEVELOP/OWNERSHIP.md` / `DEVELOP/CALLSTACK.md` / `DEVELOP/SPEC.md` / この CLAUDE.md が一次情報。
  当たりを付けてから必要なファイルだけを読む。手順は `.claude/skills/overview/SKILL.md`(`/overview`)。
- **検証は変更箇所に対応させる。** 既定は `npm run typecheck` のみで、これは常に走らせる。
  `npm run test:physics` は `src/physics/` を触ったときだけ。ヘッドレス実行検証(`/verify`)は
  ユーザーが実行時の動作確認を明示的に求めたときだけ。変更と無関係な検証に時間を使わない。
- **リファクタリングの判断基準は `/refactor`(一般方針)と `/refactor-fixed`(このプロジェクトで確定済みの
  責務境界)。** 責務配置の判断を新たに下した/変えたら、`.claude/skills/refactor-fixed/SKILL.md` を
  同じ変更セットで書き換える(追記ではなく、全体が整合するように書き直す。古い判断は残さない)。
- **改名は痕跡を残さない。** コードにも文書にも歴史的経緯を書かない。「旧」「former」「previously」
  「〜だった」の類は禁止。互換用の旧名エイリアスも残さず、旧名は全文検索して 0 件にする。
- **コメントは `/comment` の方針に従う。あらゆる変更で、書く前と書き換えた後に必ず見直す。**
  大原則は「そのモジュールの責務外に言及しない」。書いてよいのはモジュール/関数の「なにをするか」
  「どう使うか」と、相当に非自明な実装の理由だけ。「どう実装しているか」「なにをしないか」
  「誰が使うか」「以前どうだったか」「何を変えたか」は書かない。冗長なコメントは書き換えのたびに
  増えるので、変更セットごとに自分の書いたコメントを点検する。逆に、**関数・メソッドの直前の
  呼出規約コメントと、10行以上の関数の文脈コメントは、無いこと自体が不足**とみなす。大規模な変更を
  終えた後は `/comment-cleanup` で既存コメントを一括点検する(過剰と不足の両方向)。
- **関数・機能の追加要求を受けたら、書き始める前に必ず `/add-feature` の手順を通す。** まず既存の
  類似実装を探し、再利用可能な形で適切なモジュールにあればそれを呼ぶ(追加実装しない)。そうでなければ
  適切なモジュールへ再利用可能な形で実装し、**既存側もその呼び出しに置き換えるまでを同じ変更セットで**
  行う。数行の処理でも例外にしない。
- **共通化するかどうかは、参照箇所の数ではなく「今後も使う可能性があるか」で決める。** これはコード
  からは判別できないので、`DEVELOP/SPEC.md`「実装される可能性のある機能」節を見て、決まらなければ
  ユーザーに問う。ユーザーが可能性に言及したものは同節へ記録する。
- **`memos/hedalu244/refactoring_todo.md` は todo リスト。** 経緯は残さず、完了した項目は消す
  (そこで下した責務配置の判断は消す前に `/refactor-fixed` へ移す)。
- **デバッグ用のコードは、頼まれたことだけを、頼まれた形でそのまま書く。** デバッグ用コードの価値は
  「何が起きてほしいかがコードを読んだだけで自明」であることにあり、それを損なう実装は本番コードの
  過剰実装より悪い。よって以下は**要求されない限り一切書かない**: URL クエリ・環境変数・設定値による
  分岐、有効/無効の切り替え、件数や強度のパラメータ化、毎フレーム走る仕掛け、状態(カウンタ・フラグ・
  「一度だけ」の保守)、失敗時のフォールバック。値は定数を直書きし、呼び出しは1箇所から1回にする。
  「デバッグしやすいように気を利かせる」判断そのものが要求の逸脱にあたる。

## Current state

A playable LEO (low Earth orbit) shooting game: TypeScript + Webpack + npm, Three.js `WebGPURenderer` (via the `three/webgpu` entry point). Real-scale/real-time Earth orbit (player starts at 420 km / 97° inclination), body-frame RCS translation, manual rotation with RCS damping and a prograde-hold autopilot, time warp, lead-marker gunnery against enemies that shoot back with lead-aimed plasma, shell casings and destruction debris on accurate orbital physics, win on destroying all enemies, lose on being shot down or on atmospheric reentry (drag decay → adiabatic-heating overheat or dynamic-pressure breakup). Also: Earth-shadow lighting, target-board bullet-pass markers, an orbit-planning map mode ([M]: Earth-centered camera, with the camera's frame and the planned trajectory's frame selected independently on two separate panels, click the planned trajectory to place a maneuver node — several nodes can be chained, each frozen as an absolute post-burn state — W/S/A/D/Q/E adjust Δv, [N] auto-warps to the next node, BURN guide shows remaining Δv until the actual orbit matches the planned elements within tolerance), and four stages (stage 2 = Molniya-orbit enemies, unlocked once stage 1 has been cleared — tracked via `unlock-manager.ts`'s `UnlockManager`, which persists per-stage clear counts to localStorage and toasts newly-unlocked stages; stage 0 = near-combat training scoreattack, stage 00 = infinite survival; stage 0/00 are always unlocked; `?stage=` URL param skips the select screen). Each frame is `Game.update` → `Game.sync` → `Game.render`; the render phase draws `cameraSystem.activeCamera` — combat chase cam (near 2 / far 6e7) or the map camera (near 1e4 / far `OVERVIEW_CAMERA_FAR` = 1.5e10) —. Stars/sun/moon billboards follow the active camera position so the map zoom-out doesn't exit the star shell.

### Naming: render / update / build / sync (no `draw`)

Per-frame function names must reflect what they actually do, consistently across the codebase:

- **`render`** — reserved for functions that literally call the three.js renderer's `render(scene, camera)` (only `Game.render` qualifies). A function that only constructs or mutates scene state is not a "render" function even if it runs in the render phase (e.g. `Player.syncPlayer`, `EnvironmentScene.sync`).
- **`update`** — advances or mutates logical/simulation data (not three.js mesh state directly).
- **`build`** — registers new meshes/objects into the scene (construction, not per-frame).
- **`sync`** — matches the transform/appearance of already-registered meshes (or HUD DOM elements) to logical data that was already computed elsewhere. Prefer plain `sync*` names; don't tack `Render` onto a sync method name (e.g. `syncCamera`, not `syncRenderCamera`) — it blurs the render/sync boundary this rule exists to keep clear.
- **`draw`** is never used — rename on sight.

The rAF loop in `main.ts` makes this split structural: it calls `Game.update(dt)` → `Game.sync()` → `Game.render()` as three separate top-level phases. **Only `update` takes `dt`** — nothing in the sync phase may advance anything, so no `sync` anywhere takes one (a display-side refresh cadence, e.g. `HudPanels`, holds a `performance.now()` deadline instead). `update` must not touch THREE.js objects; `sync` builds the frame's `FloatingOrigin` and pushes already-computed logical state into meshes/DOM; `render` only issues draw calls. Keep sub-functions on the correct side of that line — state that merely happens to be read at render time still belongs with the system that owns it.

### Architecture

Simulation state lives in ECI coordinates (Y axis = north pole), SI units (m, m/s), as plain `{x,y,z}` data (`physics/vec3.ts`'s `Vec3` is a **branded type** — build it with `v3()`/the helpers, never with a bare object literal).

`OrbitState` is a **timed** state vector — `{t, r, v}`, where `t` is the absolute simTime epoch — and it is the *single* type used for every "state at a moment": entity state, entity history, predicted-trajectory samples, and maneuver-plan nodes. There is deliberately no second type carrying the same information (the former `TrajectorySample`, `LineSample` and `PlannedNode.time` were folded into it), so a state and its time can never be passed as two arguments that disagree. `stepOrbitRK4` advances `t` along with `r`/`v`, which is why `toFrameState` takes no separate time argument.

**The base data types are immutable, with no exceptions**: `Vec3`, `OrbitState` (`physics/orbital-state.ts`), `Quat`/`Attitude` (`physics/attitude.ts`) are all `readonly` and are advanced by *replacement*, never by in-place mutation — `stepOrbitRK4` returns a new `OrbitState`, `stepAttitude` returns a new `Attitude`, and every owner assigns the result (`entity.state = …`, `entity.att = …`). This is a correctness invariant, not a style preference: `physics/orbit-entity.ts`'s `OrbitEntity` **pushes the outgoing state onto `history`** on every `step`/`reset`, and `game-entity/game-entity.ts`'s `GameEntity.elementsAround(body)` memoizes its result on `state`'s object identity plus `body.id` — both can only stay correct because nothing else can change the state behind its back. Consequences: defensive copying is unnecessary (`vec3.clone()` does not exist), and **everything under `physics/` is a pure function returning fresh values** — there are no `*Into`/`out`-parameter variants and no module-level scratch buffers. Those existed (軽量化計画 A-1) and were deliberately removed. The cost is real but small: in an isolated Node benchmark `stepOrbitRK4` went 1520 → 2190 ns/step and `stepAttitude` 218 → 414 ns/step, which at a typical ~400 live entities works out to roughly +0.35 ms per frame in the `update` phase — not distinguishable from run-to-run noise in the actual game (~5 ms update phase). The immutability that buys is what makes the `elements` memo correct, so the trade is intentional. If the entity budget grows enough for this to matter, the answer is a physics LOD (軽量化計画 B-1), not reintroducing mutable scratch into `physics/`. Rendering uses a **floating origin**: `game/floating-origin.ts`'s `FloatingOrigin` is rebuilt every `Game.sync` from the player's post-integration state, and `RtoThreeV3`/`VtoThreeV3` are the *only* bridge from logical `Vec3` to `THREE.Vector3` — so f32 GPU precision never sees absolute LEO magnitudes. Every `sync` takes the `fo` and must not use `player.state.r` as the render origin directly (the two are semantically distinct; the origin could move to the camera later). Combat camera: near=`COMBAT_CAMERA_NEAR`=2m, far=`COMBAT_CAMERA_FAR`=6e7m — no logarithmic depth needed (see comment in `const.ts`).

Physics runs on the main thread (per-entity central-gravity two-body integration is cheap); the N-body worker is **currently unused**, kept for the future cislunar (Sun-Earth-Moon) phase.

`src/game/` is an orchestrator (`game.ts`) plus subfolders grouped by concern: `player/` (player ship state), `game-entity/` (the entity base and derived classes, one file per class), `simulation/` (the array that holds live entities, plus the passive, non-AI/non-input systems that drive it each frame — stepping, prediction, collision, hit detection), `camera/`, `plan/` (maneuver planning and its future-trajectory display, independent of whether the map is open), `stages/` (per-stage behavior), `hud/` (DOM overlay), `marker/` (screen-projected markers), `vfx/`, and `input/`.

**`*Ctx` snapshot objects are a rejected pattern here** — don't add new ones and don't widen the survivors. Almost all of them have been expanded into explicit arguments or shared references; what remains is `Player.behave`'s parameter object.

- `src/main.ts` — entry point: WebGPU scene init (`initScene`, with a `showLoading` overlay while the WebGPU pipeline compiles), launch resolution (`resolveLaunchSelection`, below), an error overlay fallback, and the rAF loop (`startAnimationLoop`) driving `Game.update` → `Game.sync` → `Game.render` plus the optional `PerfMeter`. It also owns `Hud`/`Sfx`/`SettingsPanel` (`initHud`) — these are constructed before `Game` (and before the launch screen) because the title/select screen needs them too, so `Game` receives them as constructor arguments rather than constructing them itself. `main.ts` wires `SettingsPanel.onSettingsOpenChange` to `Game.pause()`/`Game.resume()` (the settings menu's open/close is the only driver of the pause state), `onBgmToggle` to `Sfx.setBgmEnabled`, and `onQuitToTitle` to reload without `?stage=`/`?mode=`.
- `src/game/game-mode.ts` — `GameMode` (`'stage' | 'creative'`) and `LaunchSelection` (`{mode:'stage', stage: StageId} | {mode:'creative'}`), the result type both the launch screen and the `?stage=`/`?mode=creative` URL shortcuts resolve to. No behavior — a shared type so `launch-select.ts`/`main.ts`/`game.ts` agree on the shape without importing each other's internals.
- `src/game/launch-select.ts` — `selectLaunch(unlockManager)`: the title screen, tabbed between ステージモード (built from `STAGE_DEFINITIONS`, gated per-stage by `UnlockManager.isUnlocked`, same as before) and クリエイティブモード (a single always-enabled button that resolves `{mode:'creative'}`). `main.ts`'s `resolveLaunchSelection` calls this only after checking `?mode=creative` and `?stage=` — both URL shortcuts skip the screen entirely, mirroring each other so creative mode is as scriptable/shareable as a stage link. The corner debug-stage link and the per-stage select-screen keyboard shortcuts (`Stage.selectKeys`) live here too, both scoped to the ステージモード tab.
- `src/perf-meter.ts` — `PerfMeter`: `?perf=1` debug overlay (frame time split between update/sync+render, entity counts via `Game.perfCounts()`, JS heap). Owned by `main.ts`, not by `Game`.
- `src/game/game.ts` — orchestrator, and **only** that: it constructs and wires the subsystems and decides the per-frame call order. Owns `isPaused` (write-gated behind the public `pause()`/`resume()` methods — `main.ts` is the only caller, via the `SettingsPanel` wiring above), the frame's `FloatingOrigin`, and the top-level `update`/`sync`/`render` split (input edges → `ViewManager` → `Player.behave` → `Stage.update` → `Simulator.stepSimulation` → collision/board/loss/cleanup → `Predictor.update` → `MapPicker.refresh` → camera → plan editing; then sync: camera → environment → player → entities → VFX → orbit lines → markers → HUD panels). It does **not** own `simTime` (that's `Simulator`), the win/lose `phase` (that's `Stage`), and it does **not** construct `Hud`/`Sfx`/`SettingsPanel`/`UnlockManager` (all received from `main.ts`, see above). It constructs and drives `CameraSystem`, `MapPicker`, `EntityManager`, `Simulator`, `Predictor`, `EffectsSystem`, `Targeter`, `NavTarget`, `PlanEditor`/`DisplayTimeManager`/`PlanGuide`, `ViewManager`, `Docking`, `SimSpeedManager`, `Ephemeris`, `MarkerManager` (plus the two marker sets no single object can own — `GroupedMarkers`/`LeadMarkers`), and the active `Stage`. **It does not know which key does what**: the key↔action table is `input/key-mapping.ts`'s `KEY_MAPPING`, and `handleInput` just hands `Input` to each owner in priority order (`Docking` `pauseMenu`-while-docked → `SettingsPanel` `pauseMenu` → `Hud` `help` → `Stage` `restart` → `SimSpeedManager` `warpSlower`/`warpFaster`/`autoWarpToNode` → `ViewManager` `toggleMapMode` → `PlanEditor` `deleteNode`), and each consumes what it owns. Keys that only make sense while playing are taken by their owner's own per-frame call further down (`Player.behave` for `rcsDampToggle`/`progradeReset`/`fineAttitudeToggle`/`progradeHoldToggle`/`throttle*`/`reload`, `CameraSystem.update` for `followAttitudeToggle`/`gunsightZoom`/`camera*`, `PlanEditor.handleMapPointer` → `MapPicker.handleRightClick` for map clicks, `Targeter.updateCombatTargeting` for combat right-clicks). `MapPicker.refresh()` is called once in each of `update`'s four paths (the paused early return, the no-ship early return, the stage-decided early return, and the normal path after `Simulator.stepSimulation`/`Predictor.update`) — all four go through the private `updateMapPresentation`, which refreshes the candidate set immediately before that path's `cameraSystem.update()` call — building the candidate set post-integration keeps its coordinates in step with the post-integration state `sync` renders that same frame, instead of lagging a step behind under high time-warp. Many public fields (`cameraSystem`/`player`/`activeStage`/`entities`/`simulator`/`targeter`/...) exist because `hud/panel.ts`'s `HudPanels.sync(game, bodies)` reads the whole `Game` instance directly rather than a narrow ctx.
- `src/game/const.ts` — all gameplay tuning constants (thrust, sim speed levels, fire rate, hit radii, ammo/belt geometry, camera near/far, prediction throttles, stage tuning...).
- `src/game/floating-origin.ts` — `FloatingOrigin`: the render origin's motion state (`r`/`v`) and the sole `Vec3` → `THREE.Vector3` conversion (`RtoThreeV3` for positions, `VtoThreeV3` for relative-velocity-facing draws like bullets).

`src/game/player/` — the player ship, split by concern (all owned and composed by `Player`, which exposes read-only getters for `game.ts`/HUD):
- `player.ts` — `Player extends Ship`: initial LEO placement (`makeInitialState`/`progradeAttitude`, `INITIAL_ALT`=420 km / `INITIAL_INC_DEG`=97°; `progradeAttitude`'s `inertia` is asymmetric across all three axes — `PLAYER_INERTIA_PITCH/YAW/ROLL` — so the Dzhanibekov effect isn't debris-only, and manual angular velocity has no cap: holding an RCS key keeps accelerating the spin indefinitely), the per-frame `behave` (belt → own edge keys → torque → HP regen → fire → thrust) and `checkLoss`/`syncPlayer` entry points, damage/loss handling (`attacked` — which now also banks `thermal.addImpactHeat()` and, when `radiator.damageFromHit` reports a newly-destroyed panel, triggers a one-shot debris break effect at that panel's tip — and `checkLoss(dt, simTime, activeStage, playerPos, bodies)`, which checks hull heat/dynamic-pressure via `thermal` and, independently, whether the hull has reached any attractor's surface via `attractor.ts`'s `hitsAnySurface(state.r, bodies, C.PLAYER_MIN_ALT)` — the atmospheric-heating/dynamic-pressure thresholds stay Earth-specific (only Earth has an atmosphere here), but the structural-breakup threshold is body-agnostic), and composes `throttle`/`fire`/`belt`/`thermal`/`radiator`/`power`/`thrustEffects`/`rcsEffects`/`markers`. **Every `Player` owns its own `plan: Plan`** (not just the one flying in stage mode) — `PlanEditor.plan` is a getter forwarding to whichever ship `Game.setActivePlayer` last made active, so switching the flown ship switches which plan is being edited without either class needing to know about the other's swap. There is no creative-mode subclass: a placed ship is a plain `Player` constructed with an explicit `name`/`initialState` (the constructor's defaults are what a stage-mode ship uses instead), and `followPlan` (read each frame by `CreativeStage.update` to decide whether this ship's `plan` executes itself) is a field on `Player` directly rather than something only some ships have. `syncPlayer(fo, camera, phasePlaying, paused, displayTime, isActive)` takes `isActive` because `EntityManager.players` can hold more than one ship (creative mode) — only the active one hides for the gunsight zoom and pushes `markers` (the orbital-direction/boresight/`▷` HUD markers, which describe *the* operator's frame and would be meaningless duplicated across ships). `thrustEffects`/`rcsEffects`/`reentryEffects` sync off `displayState(displayTime) ?? this.state` rather than `this.state` directly — the plume/RCS-puff/reentry-glow billboards have to sit at the same future-ghost position the hull mesh itself is drawn at, or the effect visibly detaches from the ship the moment the slider moves; when `displayState` is `null` (beyond this ship's prediction horizon) the effects are called with `alive` forced false instead of being skipped outright, so each one hides itself through its own existing dead/absent-state path rather than `syncPlayer` needing a second one. `handleEdgePress` claims the ship-side keys (`[T]`/`[F]`/`[V]`/`[C]`/`[1]`-`[3]`/`[R]`) via `input.takeKeys()`, which consumes them so no later module double-handles. `[R]` is only consumed when a manual reload actually starts. Right after `this.thrust` is set, `behave` calls `this.invalidatePrediction()` if it's non-null — the one place a `GameEntity` invalidates its own prediction *outside* `resyncPrediction`'s distance check, because the player's own burn needs to be reflected in the predicted trajectory immediately (a UX requirement `resyncPrediction`'s few-frame lag can't meet) and this is deliberately player-only, not a `thrust` setter, leaving room for `Enemy` thrust to someday *not* reset immediately.
- `player-throttle.ts` — `PlayerThrottle`: translation input → thrust accel (`buildThrustAccel`, all 6 body-frame directions), manual rotation + RCS damping, and the prograde-hold autopilot (`autoAlignTorque`): builds a desired attitude quaternion (nose = velocity direction, roll reference = radial-out, re-orthogonalized so it's valid even for eccentric orbits where r⟂v doesn't hold exactly — see `physics/attitude.ts`'s `qFromForwardUp`), converts the quaternion error to a body-frame axis-angle, and applies a PD torque (`PROGRADE_HOLD_KP`/`_KD`). `updateTorque` only *returns* the body torque (`Player` writes it to `entity.torque`) and `updateThrustState` only returns the thrust closure — the actual attitude/orbit integration is `Simulator`'s.
- `player-fire.ts` — `PlayerFire`: gun state (mag/round/barrel counters, reload timer), `updateFireState`/`fireCycle`/`consume` (the ammo state machine, returning `ConsumeResult` = `empty`/`normal`/`mag-reload`/`barrel-reload`), `fireGun` (bullet spawn, recoil, casing eject, muzzle flash, `ScoreCounter.recordShot`), and `dropBarrel`/`spawnEjectedMagazineFrame` for reload debris. `tickMapMode` advances only the reload timer while the planner is open.
- `belt.ts` / `belt-physics.ts` — the ammo belt display split from its physics: `belt-physics.ts`'s `BeltPhysics` is a pure Vec3/Quat Verlet-chain solver (position-based dynamics; otherwise no THREE/mesh dependency — see `BeltSection` below for the one exception) for the belt's sag/twist under the ship's thrust+spin pseudo-forces; `belt.ts`'s `Belt` owns the link meshes and derives each link's transform from `BeltPhysics`'s solved state via parallel transport. `belt-physics.ts` also defines `BeltSection extends GameEntity` — the per-link collision proxy `game/simulation/collision.ts` resolves against (`BeltPhysics.collisionSections`/`applyCollisionSections` convert to/from it each frame). It's declared here rather than in `game-entity/` because nothing outside the belt uses it, and its constructor needs only a placeholder `THREE.Object3D` to satisfy `GameEntity`'s constructor — it's never added to a scene or stepped, so that placeholder is the only place this otherwise THREE-free module touches THREE.
- `thermal.ts` — `ThermalSystem`: **the single source of truth for the hull's heat budget** — aerodynamic heating, gun firing heat, bullet-impact heat and radiative cooling all land in `updateThermal`, plus dynamic pressure and the altitude-descent-warning EMA (`updateAltitudeAlarm`); returns a `ThermalLimit` verdict. `addGunHeat(rounds)`/`addImpactHeat()` both bank their energy in joules into the shared `pendingHeat` rather than writing `hullTemp` directly, because `updateThermal` runs once per substep and the deposited energy must not scale with how many times that happens — the actual destruction (`alive = false` + effects) happens in `Player.checkLoss`.
- `radiator.ts` — `RadiatorSystem`: the two deployable radiator panels (deploy fraction and hinge-angle `sync`). **It does not own the panels' damage** — `wear` (0=intact, 1=destroyed) is handed to `update(dt, wear)` every frame by `Player`, derived from the two radiator *parts*' remaining HP, so the thing the dock repairs and the thing that stops radiating are one and the same. Panels therefore never self-heal in flight; repair is the dock's job alone. It **does not know the hull temperature** — it answers only `radiatingArea()` [m²] and `solarLoad(sunlit, sunDir, att)` [W], which `Player` feeds to `ThermalSystem.setRadiatorLoad` each frame, so the Stefan-Boltzmann T⁴ law stays owned by `ThermalSystem` alone and no temperature round-trips between the two; `radiatingArea` multiplies `RADIATOR_PANEL_AREA` (the modeled dimensions) by the separate `RADIATOR_EFFICIENCY_MULT` performance multiplier, so tuning the panels' cooling power never has to fight the "model dimensions and physics stay one number" rule that `RADIATOR_PANEL_AREA` itself follows. `foldThetas(side)` is shared by `sync` and the panel-normal math so the drawn angle and the illuminated angle cannot diverge; because an accordion's even and odd folds face different ways, `solarLoad` evaluates both orientations and splits the area between them. `hitRadius()` interpolates the ship's bullet-hit radius up to `render/ships.ts`'s `RADIATOR_TIP_DISTANCE`, so deploying really does make the ship easier to hit; `sideHitBy` is pure geometry — it attributes a hit to the up/down panel by the body-frame X sign, ignoring hits inside `PLAYER_HULL_RADIUS` and panels stowed below `RADIATOR_HITTABLE_DEPLOY` — and `Player.attacked` is what turns that side into `RADIATOR_HIT_DAMAGE` against the matching radiator part (lighter than a hull hit, since a panel is thin and large) and fires the one-shot break effect when that part reaches 0. `sync()` hides a destroyed panel's fold meshes for good. `tipWorldPosition` reads a fold's live world transform (post-`sync()`) for that effect's spawn point.
- `reentry-effects.ts` — `ReentryEffects`: the plasma glow ahead of the ship during reentry. **Stateless** — the intensity is derived from `ThermalSystem.qdyn` every frame (`REENTRY_GLOW_MIN_Q` → `REENTRY_GLOW_FULL_Q` mapped continuously onto scale and opacity), so there is nothing to advance in `update` and only a `sync`. It orients off the *absolute* ECI velocity rather than `fo.VtoThreeV3`, since the floating origin is the player itself and the relative velocity is therefore always zero here.
- `power.ts` — `PowerSystem`: the solar panels' charge, HUD-facing as `chargeRatio` (0..1). The panels are fixed (no deploy animation), so their normal is a constant body-frame `(0,1,0)` — `update(dt, sunlit, sunDir, att)` just rotates that one normal into world space, takes `max(0, dot(...))` (unlike `RadiatorSystem.solarLoad`'s `abs`, since a one-sided panel doesn't generate power off its back face), and banks the energy into `charge`, clamped to `POWER_CAPACITY`. Entirely numeric — no `sync()`, since there's no mesh state to push.
- `thrust-effects.ts` / `rcs-effects.ts` — billboard VFX for the main engine plume (positioned from `render/ships.ts`'s `MUZZLE_OFFSETS`) and for the attitude thrusters. `RcsEffects` builds one plume per entry of `render/rcs-nozzles.ts`'s `RCS_NOZZLES`, and picks which ones fire by the torque each nozzle *produces*: `τ_k = r_k × (−exhaust_k)` is a per-nozzle constant derived once from the table, and a nozzle fires when `dot(τ_k, torque) > 0`. Because the nozzle's own direction is fixed hardware, the plume can only ever appear at one place per nozzle — a torque-dependent exhaust direction would slide the plume continuously around its block as the commanded torque turns.
- `player-markers.ts` — `PlayerMarkers`: the HUD markers that follow from the ship's own position/attitude — the six orbital-frame direction markers (prograde/retrograde/normal/antinormal/radial in-out, the Navball stand-in), the `┼` boresight, and the map-mode `▷` self marker. `sync(currentState, displayState, att, alive, overviewMode, project)` takes two states rather than one: the combat-view markers (direction/boresight) always read `currentState`, since they represent the ship's real orbital frame regardless of the future-ghost slider, while `▷` reads `displayState` (`null` beyond the player's own prediction horizon, in which case `▷` just hides) — the two states coincide whenever the slider is at rest, which combat view always is. `Player.syncPlayer` drives it (only when that ship is the active one — see `player.ts` above), so callers never see a separate marker entry point.

`src/game/game-entity/` — the entity base and derived classes, one file per class:
- `game-entity.ts` — `GameEntity` (base: mesh/HP/alive/attitude/AI-facing state; delegates the actual "time-stamped state + its sample history + advance itself" job to `physics/orbit-entity.ts`'s `OrbitEntity`, held as the public `current` field. `state`/`prevState`/`history` are thin forwarding getters to `current` — the ~20 call sites across the codebase that only ever read `.state` are unaffected by this split. The `state` **setter** forwards to `current.reset(...)`, the sole entry point for a discontinuous external overwrite (rigid contact, recoil); `stepSim(dt, ephemeris)` never goes through it — it self-gates on `alive`, looks up this step's gravity sources once at the step's own midpoint (`ephemeris.attractorsAt(state.t + dt/2)`, reused for both the integration and the sampling-interval decision so the composition is evaluated once rather than twice) and hands `current.step(...)` that array plus the entity's own `bcInv`/`thrust`/`sampleInterval(bodies)`/`historyDuration` (integration itself is `current`'s job, not this class's). `elementsAround(body)` is the only way to get osculating elements out of an entity — there is no bare `elements` getter, since which body an ellipse is centered on is a per-call choice (typically `attractor.ts`'s `strongestAttractor`), not a fixed property of the entity; it memoizes on `state`'s object identity and `body.id`, both of which only change together with an actual new orbit. `sampleInterval(bodies)` derives the history's push interval from `attractor.ts`'s `localOrbitPeriod(state.r, bodies)` (the period around whichever body pulls hardest right now, divided by `PREDICT_SAMPLES_PER_REV`, falling back to a `SHIP_HISTORY_DURATION`-based value when no finite period exists, e.g. hyperbolic orbits) and is skipped entirely while `historyDuration === 0` (bullets/casings/debris never need it), `torque`/`thrust` slots the owning system writes each frame, and a default `checkLoss(_dt, _simTime, _activeStage, _playerPos, bodies)` that calls `attractor.ts`'s `hitsAnySurface(state.r, bodies, C.DEBRIS_REENTRY_ALT)` — surface contact with *any* attractor, not just Earth, since a stray debris piece near the moon shouldn't pass through it).

- `src/game/display-time-manager.ts` / `display-time-panel.ts` — `DisplayTimeManager`: "when to look" — the display duration (`durationKey` → `durationSec(referencePeriod)`; presets `'orbit'` (default) /`'90min'`/`'day'`/`'week'`/`'month'` plus `'manual'`), the future-ghost slider position `sliderT`, `resolveDisplayTime(simTime, referencePeriod)` for the "show the sky at a future time" query every future-aware `sync` uses, and `forceCurrent` (a get/set accessor, starting `true`, flipped by `ViewManager`; while set, `resolveDisplayTime` always returns the present, and the setter also zeroes `sliderT` — leaving combat view always resets the slider to the present rather than resuming wherever it was left, and `panel.onDurationSelect` zeroes it the same way, since switching how far the slider can reach mid-drag would otherwise leave it pointing at a now-meaningless fraction of the new span). `durationSec` holds no orbital period of its own: for `'90min'`/`'day'`/`'week'`/`'month'` it looks the constant up in a `Record<key, seconds>` table (a compile-time-exhaustive alternative to an if-chain — adding a preset without a table entry is a type error rather than a silent fallthrough), `'manual'` reads `manualDurationSec` instead, and only `'orbit'` returns `referencePeriod` as-is (falling back to `C.APERIODIC_ARC_DURATION` when it isn't finite/positive) — every caller resolves its own notion of "one orbit" and passes it in, so this class never has to decide whose orbit or around which body. `Game.currentOrbitPeriod()` supplies it for the game-wide display time (the active ship's osculating period around whichever body currently pulls hardest, `NaN` with no ship); `plan.ts`'s `segmentDurationFrom` supplies it separately for the plan's trailing segment and `Plan.nodeTimeRange`, from that segment's own start state — the two contexts can disagree about "one orbit" without either owning the other. Owned by `Game` (not `PlanEditor` — nothing here is plan-specific; `EnvironmentScene`/`CameraSystem`/`FocusMarkers` all resolve a display time too, and `PlanDisplay`'s ghost is just one more consumer), and additionally shared by reference from `Game` through `PlanEditor`/`PlanDisplay` down to `plan-trajectory.ts`'s `PlanTrajectory`, which is what lets the plan's own trailing segment track the PREDICT panel's selection (see `plan-trajectory.ts` below). `'manual'` reads `manualDurationSec` (a value+unit input in the panel, hour/day/week/year, clamped into `[DISPLAY_DURATION_MIN, DISPLAY_DURATION_MAX]` = 1 hour to 1 year — the lower bound matters because the duration doubles as the predicted list's retention window, and a zero-length window keeps no samples at all) instead of one of the fixed presets, so the slider can span durations no preset covers; `sync(simTime, referencePeriod)` also pushes the tick marks `hud/tick-scale.ts`'s `buildTicks(lastDurationSec, TICK_MAX_COUNT)` returns (positions at round multiples of a chosen interval rather than equal divisions of the span, so the panel shows scale regardless of which duration is selected) — each tick is narrow, so the absolute date is the slider label's job alone (`futureTimeLabel`, `hud/utils.ts`'s `fmtDateTime` off that module's `SIM_EPOCH_SEC`, the same epoch `hud/panel.ts`'s MET row anchors to), plus `setSliderValue(sliderT)`/`setSliderSteps(...)`/`setManualRange(DISPLAY_DURATION_MIN, DISPLAY_DURATION_MAX)` every frame so the slider DOM element and the manual-range clamp stay driven by `DisplayTimeManager`'s own state rather than only reacting to the panel's own input events — `DurationValueInput.emit` (`display-time-panel.ts`) clamps the typed value into the range its owner set and writes the clamped value back into the input field itself, so an over-range entry visibly snaps to the limit instead of silently being capped somewhere downstream; the same class also keeps the input's `min`/`max` attributes in sync with whichever unit is currently selected, so a 0-looking entry doesn't silently snap to the 1-hour floor once converted. `sliderSteps()` sizes the slider's step count from `lastDurationSec` (cached from the most recent `sync`, since the DOM `input` event that needs it fires outside the frame flow) at roughly `SLIDER_TARGET_STEP_SEC` per step, clamped to `[SLIDER_MIN_STEPS, SLIDER_MAX_STEPS]` — the `setSliderValue`/`onSliderChange` interface stays 0..1 regardless, so no caller needs to know the current step count. A T+-time jump input (also a `DurationValueInput`) resolves against the same cached `lastDurationSec` to set `sliderT` directly, and a "current" button resets `sliderT` to 0 the same way `forceCurrent`'s setter does. `DisplayTimePanel` is its DOM (duration `SegmentedControl` + manual value/unit inputs + jump value/unit inputs, both instances of the shared `DurationValueInput` + slider + reset button + tick labels + a self-sufficient hint label — the ghost marker's own label carries the richer altitude readout, since that needs `PlanDisplay`'s trajectory sample and `DisplayTimeManager` must not depend on it). The duration scales the future-ghost slider and, through `segmentDurationFrom`, the length of the plan's trailing segment and the range a node may be dragged across.
- `ammo.ts` — `Ammo`: the orbital resupply pickup `stage-utils/logistics.ts` spawns and the player absorbs on approach (`bcInv = SMALL_DEBRIS_BCINV`, `predictsFuture = true`, `collideRadius = AMMO_PHYS_RADIUS`). `id` is always set — the constructor takes an optional override (`CreativeStage` passes its own placement id), and self-generates a unique one (`ammo-${counter}`, the same module-counter pattern `Base` uses) when omitted, so every spawn — including `Logistics`' auto-resupply, which never passes one — has an id a caller can key a `MapPickable`/window on without inventing one at the call site.
- `debris-piece.ts` — `DebrisPiece`/`DebrisKind` (`bcInv = SMALL_DEBRIS_BCINV`): the one class backing fragments/ejected barrels/magazine frames/casings — `DebrisKind` picks which `render/ships.ts` builder runs and which extra `checkLoss` rule applies (only `casing` pieces expire on `CASING_LIFETIME`; the rest only via the shared any-attractor surface-contact check). `fragment` pieces get no `collideRadius` (pass through collision untouched); the others take the caller-supplied one.
- `bullet.ts` — `Bullet extends GameEntity`: player/enemy bullets and enemy plasma bolts (`Shooter`/`BulletType`), `bcInv = BULLET_BCINV`, its own loss check (**distance from the player first — `BULLET_MAX_DIST` — with the lifetime only as a backstop**, since every live bullet is its own draw call), and a velocity-facing (not attitude-facing) `sync` override that uses `fo.VtoThreeV3`. `predictsFuture` stays at the `GameEntity` default of `false`, so `displayState(displayTime)` is `null` for the entire time the future-ghost slider is active — bullets simply disappear rather than showing a nonsensical projected flight path, which is fine since their lifetime is a few seconds.
- `enemy.ts` — `Enemy extends Ship`: enemy AI (`behave` — burst-fire plasma at the player using `physics/intercept.ts`'s `solveLeadTime`; takes the `EntityManager` reference to read `enemies` for the per-group attacker cap and to `addBullet`; per-group attacker cap and burst state live here), damage/destruction (`attacked`, `checkLoss`), its own `OrbitLine`, and its HUD presentation (`accentColor`, and `markerItem(isTarget, viewerPos, pos)` returning the `GroupedMarkerItem` the screen-marker set is built from — the enemy states what it looks like, `GroupedMarkers` decides how the set is laid out; `pos` is a caller-supplied argument rather than `this.state.r` because `Game.sync` resolves it from `displayState(displayTime)` — the marker has to sit at the same future-ghost position as the enemy's own mesh, or the two visibly disagree the moment the slider moves).
- `base.ts` — `Base extends GameEntity`: a docking station placed on an orbit like any other entity — its mesh (`render/ships.ts`'s `buildBaseModel`) is built and `sync`'d through the same `GameEntity`/`EntityManager` path every other entity uses, so it is a real object in both map and combat view (`EntityManager.sync` runs unconditionally, not gated on `overviewMode`) rather than a map-only marker. Its `baseState` (`money`/`inventory: AnyPart[]`/`dockedShips: DockedShipEntry[]`) is the sole store for what the base holds — a `DockedShipEntry` snapshots a docked ship's `id`/`name`/`hp`/`maxHp` for the ship-list tab plus the `player: Player` reference `Docking`/`DockView` use to act on the real ship (`parts` is not a snapshot — it's the same array as `player.parts`, so `hud/dock-view.ts` repairs land on the ship directly and only the `hp`/`maxHp` totals need writing back). Owns its own `orbitLine: OrbitLine` (`COLOR_BASE_ORBIT_LINE`, same construction/`dispose` pattern as `Enemy`'s), synced via `syncOrbitLine(show, fo, bodies)` — `Game.sync` calls it once per `entities.bases` entry with `show = overviewMode`, map-only like `Enemy.syncBackgroundOrbitLine` since a base's full orbit is a wide-context reference not needed at combat-view zoom.

`src/game/simulation/` — the array that holds live entities, plus the systems that actually drive it each frame; split from `game-entity/` because these are updaters *over* the arrays, not entity classes themselves:
- `entity-manager.ts` — `EntityManager`: owns the `players`/`enemies`/`bullets`/`casings`/`debris`/`ammos` arrays (capped, oldest evicted on overflow via `addXxx`/`addCapped` — `players` is uncapped instead, gated by `CREATIVE_MAX_SHIPS` at the `CreativeStage.placeShip` call site since removal there is deliberate, not eviction), `findPlayer(name)` (the by-name lookup every ship-menu action and `NavTarget`'s plane resolution use to turn a `MapPickable.id`/target id back into a live `Player`), lifetime cleanup (`cleanup(dt, simTime, activeStage, playerPos, bodies)`/`prune`, which takes `simTime`/the player position (because `Bullet.checkLoss` culls by distance) and the frame's `Attractor[]` (because every `checkLoss` now checks surface contact against all of them) — `cleanup` runs `checkLoss` over `all()` uniformly but only `prune`s the five non-player arrays, since a lost ship stays around as the destroyed-effect/chase-camera anchor rather than being removed), and the per-entity render sync (`sync(fo, displayTime)`, forwarding `displayTime` to each non-player `GameEntity.sync` — see `game-entity.ts`'s `displayState` above; `players` is excluded because `Player.syncPlayer` does its own richer sync, driven by `Game.sync` looping `entities.players`). `all()` is every non-player array plus `players`; the private `otherEntities()` both `all()` and `sync()` build on top of is the one place "which arrays don't include players" is answered. It runs no simulation itself — `all()`/the arrays are handed out by reference to `Simulator`/`HitSystem`/`CollisionPhysics` (below), and to every module that only ever reads or adds entities (`Targeter`, `NavTarget`, `Enemy.behave`, `Stage`/`stages/`, `Logistics`, `EffectsSystem`, `NanWatchdog`). Owned by `Game` and exposed as the public `entities` field — the one window every other module shares by reference, which is also why `Stage.setup` now hands `Logistics` the manager directly and `EffectsSystem`'s constructor takes it directly instead of an injected `addDebris` callback (no per-owner closures).

  **The active ship is just `Game.player`'s current pointer into `players`**, not a separately-tracked identity — `players` holds every self-flown ship (stage mode's lone one included) on equal footing, and `Game.setActivePlayer` only ever reassigns which element `player` points at. Nothing filters the active ship out of `players` before processing it: `Simulator.simulationSubStep`/`stepAttitudes` step every element of `players` uniformly (the one player-specific difference is *how*, not *whether* — `stepAttitudes` integrates `players` at the frame's full `simDt` so manual rotation isn't rounded, while every other array gets `attDt = min(simDt, 0.12)`), `EntityManager.cleanup`'s `checkLoss` pass covers `players` the same as any other array via `all()`, and `CollisionPhysics.resolve` takes `entities.all()` (`players` included) as its participant list outright. The two places that still single the active ship out do so through the explicit `player` argument rather than by excluding it from an array: `Predictor.update` spends its first budget slice on `player` before round-robining the *whole* `entities.all()` (`player` included again) — the active ship can draw budget twice in one frame, deliberately, rather than being tracked and excluded from the round-robin by identity. `EntityManager.sync` is the one place `players` is genuinely skipped wholesale, since every ship (active or not) syncs itself via `Player.syncPlayer` instead (see `player.ts` above).
- `simulator.ts` — `Simulator`: the actual simulation step. Owns **`simTime`/`lastSimDt`**, `HitSystem`, `CollisionPhysics`, and takes the `EntityManager` reference in its constructor rather than holding any array itself — splitting "which entities exist" (`EntityManager`) from "how they're stepped" (`Simulator`) keeps each to one responsibility. `stepSimulation` splits the frame's `simDt` into substeps (count = `ceil(simDt / SUBSTEP_MAX_DT)` — depends only on the simulated time this frame, never on the real frame rate, and is deliberately uncapped so the step size the constant names actually holds at every warp level); each substep (`simulationSubStep`) calls every live entity's own `stepSim(dt, ephemeris)` (`game-entity/game-entity.ts`) — the orbit integration and the sun/moon lookup are both the entity's responsibility, not `Simulator`'s; `Simulator` only iterates the arrays. (Every entity in a substep looks up the same time and `Ephemeris` re-evaluates the composition each call, so the repeated work is real; it has not been measured as a frame-time problem, and the fix if it becomes one is memoization inside `Ephemeris`, not `Simulator` pre-computing and distributing the array.) It also owns the attitude integration for *all* entities including every self-flown ship (`stepAttitudes`). AI/input/spawn decisions live in `game.ts`/`stages/`/`Enemy.behave`, which add entities back in via `entities.addXxx`.
- `predictor.ts` — `Predictor`: a third updater over `EntityManager`'s arrays, symmetric with `Simulator` (①holds the arrays / ②steps them / ③predicts their future — `Predictor` is ③) rather than nested inside `Simulator`, so it doesn't inherit that class's `simTime` concerns or vice versa. Owned directly by `Game` and driven from `Game.update` right after `entities.cleanup(...)` (dead entities shouldn't get predicted, and it needs the post-integration real state to resync against) — with **no branch on viewpoint or mode**, since prediction runs whether or not anything is currently displaying it. The only state it holds is a round-robin `cursor` into `EntityManager.all()` plus the `tracked`/`complete`/`discarded` counters `?perf=1` reads via `Game.perfCounts()`. `update(simTime, player, canGrow, horizon)` takes `horizon` from `DisplayTimeManager.durationSec(referencePeriod)` (how far the future-ghost slider can currently reach) and `canGrow` from `SimSpeedManager.canGrowPrediction` (`simSpeed <= MAX_PHYS_SIM_SPEED` — above that, the real state outruns any prediction list in one frame, so growing it further would never produce a usable list). It first calls `resyncPrediction` unconditionally on every entity in `all()` (the active ship included, once, since `all()` doesn't repeat it) and tallies the counters — cheap (one binary search each) — **regardless of `canGrow`**: while growth is held back the real state keeps moving, so a prediction list left un-resynced would drift and get drawn as a stale trajectory; only the resync/discard side has to keep running to prevent that. `update` then returns early when `!canGrow`, skipping the budget pass entirely. When it does run, budget spending spends a `PREDICT_STEP_BUDGET` step budget on `player` explicitly first, then one pass through the *whole* `all()` (the active ship included again) starting at `cursor`, saving wherever it stopped as next frame's `cursor` — nothing filters the active ship out of the round-robin, so it can draw budget twice in the same frame. The private `advanceBudget(entity, budgetSteps, simTime, horizon)` returns 0 immediately for an entity with `predictsFuture === false`, so bullets/casings/debris never touch `ephemeris.attractorsAt` here at all. For a predicting entity each iteration reads the entity's current predicted-tip state (`entity.predicted?.state ?? entity.state` — before the first step this falls back to the live state, exactly what a freshly-seeded `predicted` starts from anyway), looks up that tip's own gravity sources once (`ephemeris.attractorsAt(tip.t)` — reused for both sizing `dt` and the step itself, so the composition is evaluated once per budget iteration) and sizes `dt` as `max(PREDICT_MIN_STEP_DT, localOrbitPeriod(tip.r, bodies) / PREDICT_STEPS_PER_REV, horizon / PREDICT_MAX_STEPS)` (`attractor.ts`'s `localOrbitPeriod`, `PREDICT_STEPS_PER_REV` = 600 — the period around whichever body pulls hardest at the tip, divided into a fixed step count per revolution, the same scheme `plan-arc.ts`'s `stepDt` uses with its own `PLAN_ARC_STEPS_PER_REV`; the `horizon / PREDICT_MAX_STEPS` term only bites once `horizon` grows large — e.g. the 1-year manual range — where the per-revolution step count alone would blow past a bounded step/sample budget), and calls `GameEntity.stepPrediction(bodies, simTime, dt, horizon)` — looping until either the budget runs out or a call returns `false` (horizon reached, truncated, or thrusting). Both the step-count loop and the per-step `dt`/`bodies` sizing are `Predictor`'s own, not `GameEntity`'s, matching how `Simulator.stepSimulation` decides `subDt` and owns the substep-count loop around `GameEntity.stepSim` rather than leaving either to the entity. It never asks *why* a list is short (freshly spawned vs. just invalidated) — that indifference is what keeps discards from ever spiking frame time, since a discarded list just competes for the same budget as a new one next frame.
- `hit.ts` — `HitSystem`: segment-vs-sphere bullet collision only (tunneling-proof, `checkBulletHits(simTime, player, activeStage, entities)`), called per substep from `Simulator`.
- `collision.ts` — `CollisionPhysics`: rigid-sphere impulse resolution for casings/enemies/pickups/belt links (`resolve`, called once per `Game.update` — not per substep — and only while `SimSpeedManager.canResolvePhysicalCollisions`; takes `EntityManager.all()` as a plain array, not the manager itself). `BeltSection` (the belt's collision proxy) is defined in `player/belt-physics.ts`, not here — see that entry above.

`src/game/camera/` — every camera holds a `view: ViewFrame` field (`physics/projection.ts` — `position`/`lookTarget`/`up`/`fovDeg`/`aspect`) and an `update` that computes the viewpoint in absolute ECI (THREE-free) and writes it into `view` — no camera returns its `ViewFrame` as a value, since a function that both mutates state and hands back a derived product is the anti-pattern CLAUDE.md's TypeScript rules ban. Pushing `view` into a `THREE.PerspectiveCamera` through the floating origin (`sync`) and building the `ProjectFn` the rest of the game reads screen positions through (independent of both the THREE matrices and `fo`) are **`CameraSystem`'s job alone** — no sub-camera has its own `sync`/`projection`.
- `camera-system.ts` — `CameraSystem`: owns `CombatCameraSystem`/`OverviewCamera` and exposes the active one (`activeCamera`/`activeCameraPos`/`activeCameraProjection`); owns `overviewMode` (`zoomActive` is a forwarding getter — `!overviewMode && combatCamera.zoomActive` — since only `CombatCameraSystem` holds and updates that state). Module-private `syncCameraToViewFrame(camera, view, fo)` and `projectionFromView(view)` are the sole place any sub-camera's `view` becomes a `THREE.PerspectiveCamera` update or a `ProjectFn` — `sync(fo)` calls the former on whichever of `combatCamera`/`overviewCamera` is active, and `activeCameraProjection` calls the latter. `update(player, simTime, input, dt, mapPickables)` also reads the roll keys (`K.cameraRollLeft`/`cameraRollRight`, mapped to the numeric-keypad `Numpad0`/`Numpad1` — distinct from the ship radiator toggles on the top-row `Digit9`/`Digit0`) and forwards `keyRoll` alongside `keyYaw`/`keyPitch` to whichever sub-camera is active. `mapPickables` (built fresh each frame by `MapPicker.refresh()`) is threaded through to `OverviewCamera.update` so its focus resolves against the same candidate set `MapPicker.handleRightClick` picks against — `CameraSystem` itself holds none of that set. Also owns the map focus concern (= "where the overview camera looks"): the `focusMarkers` label set — resolving a right-click against the shared candidate set is `MapPicker.handleRightClick`'s job via `map-pick.ts`'s `pickNearest` directly, so this class no longer wraps that lookup itself — and the **MAP VIEW panel** (`camera/overview-camera-panel.ts` — focus shortlist / camera frame / view reset). Every control on that panel writes `overviewCamera` state and nothing else, so the whole HUD wiring stays inside this class; `sync(fo)` pushes the panel's visibility and highlights each frame.
- `combat-camera-system.ts` — `CombatCameraSystem`: the combat view, holding its own `camera: THREE.PerspectiveCamera` and `view: ViewFrame` (the same `ViewFrame` shape `OverviewCamera` holds, so there's no second "camera view state" shape in the codebase). Owns the `[Z]` gunsight switch (`zoomActive`, read from `Input` each `update` — the key is only ever consulted while combat view is active, since `CameraSystem` doesn't call this class's `update` in map mode) and is the sole place FOV animates: each frame it picks `chase-camera.ts`'s `ChaseCamera` or `gunsight-camera.ts`'s `GunsightCamera` by `zoomActive`, calls that sub-camera's `update` (which writes its own `view`), then module-private `lerpViewFrameFov` folds the picked `view` into this class's own — position/lookTarget/up/aspect snap to the target immediately, only `fovDeg` eases exponentially — so a sub-camera never animates its own FOV and a future third view only needs to expose the same `view: ViewFrame` field. `toggleFollowAttitude`/`camFollowAttitude` are thin forwards to `ChaseCamera` (the `[G]` key's receiver, same pattern as `reset()`) — the reference-frame decision itself lives there.
- `chase-camera.ts` — `ChaseCamera`: the third-person orbit view, owning only a unit quaternion `rot` and `dist` — no Euler yaw/pitch/up-vector state, so a long drag session can't gimbal-lock or drift into an inconsistent up vector. It holds its own `player: Player` reference (constructor-injected — `game.ts` constructs `Player` before `CameraSystem`/`CombatCameraSystem`/`ChaseCamera` specifically so this reference can be a direct one rather than a lazily-resolved thunk) and reads `player.att.q`/`player.alive`/`player.state.r` directly, so `update` takes no `player` argument. `setPlayer(player)` re-points this reference — `Game.setActivePlayer` calls it through `CameraSystem.setActivePlayer` → `CombatCameraSystem.setActivePlayer`, the same forwarding chain every layer between `Game` and this field uses — without touching `rot`/`dist`, so switching the flown ship keeps the camera's current offset instead of snapping to a default view. The togglable reference frame (`camFollowAttitude`, a get/set accessor) decides what `rot` *means*: `true` — the default — makes it an offset relative to the ship's own attitude (`player.att.q`); `false` makes it the camera's own absolute orientation in ECI, fixed in inertial space until dragged. The setter reinterprets `rot` through `player.att.q` (multiply/divide) so the rendered view never jumps at the moment of the toggle. `update(mouse, keyYaw, keyPitch, keyRoll, dt)` folds `player.att.q` into a working quaternion only while `camFollowAttitude && player.alive` — once the ship is destroyed the stored `rot` is used as-is (an absolute orientation), so the camera stops chasing the ship's post-destruction tumble — then applies key/drag rotations to that working quaternion before writing it back. Mouse drag rotates around `axis = normalize(cross(dragVector, viewVector))` (`viewVector` = the camera's current look direction, `dragVector` = the drag's screen delta expressed in the camera's own current right/up axes): the axis is always ⟂ the view direction by construction, so drag can never introduce roll around the view axis, and using the *current* basis rather than a fixed reference keeps the control gimbal-lock-free at any pitch. Arrow-key yaw/pitch rotate around the same current up/right axes; `keyRoll` (the numpad-0/1 keys) rotates around `view` itself (the camera's own look direction), the one axis arrow-key yaw/pitch never touch.
- `gunsight-camera.ts` — `GunsightCamera`: the `[Z]` zoom view — stateless apart from `view`, just the ship's nose direction and position turned into a `ViewFrame` each `update`.
- `overview-camera.ts` — `OverviewCamera`: the map Earth-centered orbit camera (near=1e4/far=`OVERVIEW_CAMERA_FAR`), exposing `camera`/`view` on the same footing as `CombatCameraSystem`. Its source of truth is three **`cameraFrame`-relative** vectors (`offset_r` = focus→camera, `pan_r` = focus→look-target, `up_r` = the camera's up direction), so switching to the sun-rotating frame makes the viewpoint co-rotate for free; the ECI ⇄ frame round trip is delegated to `physics/frame.ts` and the class never brands values itself. `cameraFrame` (a `physics/frame.ts` `Frame`) is the source of truth for **the frame the viewpoint is fixed to**, and only that — the frame the planned trajectory is *drawn* in is `PlanDisplay.trajectoryFrame`, a separate value the player selects independently. `update` rotates the viewpoint around the camera's *current* up/right axes (the same construction `ChaseCamera` uses) rather than around world Y, so a rolled map still yaws and pitches the way the drag looks on screen, and it re-orthogonalizes `up_r` against the just-changed view direction before applying `keyRoll` around it. Focus (a label id) is resolved against the `candidates: readonly MapPickable[]` argument `update` receives each frame (built by `MapPicker.refresh()` — Earth/Moon/Sun/Lagrange-point labels plus every living ship plus the navigation-target AN/DN icons), falling back to Earth if the id isn't in the current set; the class holds no reference to `FocusMarkers` or any other pickable source itself. The future-ghost slider belongs to `DisplayTimeManager`.
- `focus-markers.ts` — `FocusMarkers`: the focusable-target labels, each exposed as a `MapPickable` (`kind: 'body'`). `LABEL_NAMES` is built once from `solar-system.ts`'s registered bodies — every `AttractorId` gets a label id equal to the id itself, and every orbiting one (`OrbitingId`, i.e. every non-star) additionally gets five Lagrange-point labels `${id}-l1..5`, named `${primary name}-${id name} L${n}` (e.g. `moon-l1` → `地球-月 L1`, `jupiter-l1` → `太陽-木星 L1`) — so registering a new body needs no change here, only to `solar-system.ts`/`celestial-registry.ts`. Split across the two phases like `NavTarget` is: `update(t)` re-derives every label's position from the ephemeris at the display time (a body's own position via `positionOf`, a Lagrange label via `lagrangeAt`), `syncLabels(project)` only places the markers. `MapPicker.refresh()` calls the former and reads `labels` in the same breath, so the right-click candidate set and the drawn labels are the same frame's coordinates — deriving them in `syncLabels` instead would leave the pick test one frame behind the labels (and stale altogether in combat view, where `syncLabels` never runs). An overview-camera-side concern, owned by `CameraSystem`.

Screen projection itself is **not** in `camera/`: `physics/projection.ts` holds the pure math (`ViewFrame`/`projectToNdc`/`ndcToScreen`/`Projected`) and each camera exposes a bound `ProjectFn` (`(worldPos: Vec3) => Projected`) that consumers receive as an argument rather than importing.

- `src/game/map-pick.ts` — `MapPickable`/`MapPickKind` (`'body' | 'ship' | 'player' | 'apsis' | 'relnode'`) and `pickNearest<T extends { readonly pos: Vec3 }>`: the common shape for anything on the map (or in combat) that a click can hit, and the shared "project every candidate, take the screen-nearest one within a pixel-radius" search. The type parameter only requires a world position, not the full `MapPickable` shape, so a caller with its own payload (e.g. `Targeter.pickEnemyAt`'s `{ pos, enemy }`) can pass it straight through without faking the rest of `MapPickable`. `'body'` is `FocusMarkers`' celestial labels, `'ship'` is every living `Enemy`, `'player'` is every living self-flown ship in `entities.players` — split from `'ship'` because a self-flown ship's menu offers activate/follow-plan/delete on top of what an enemy's does — `'relnode'` is `NavTarget`'s relative AN/DN icons, and `'apsis'` is `PlanDisplay`'s periapsis/apoapsis icons — each kind drives a different `MapPicker.itemsFor` item set. Used by `MapPicker` (the map's whole right-click path) and `Targeter.pickEnemyAt` (enemies only), so target-selection and map-focus/context-menu picking share one implementation instead of several near-identical screen-distance loops.
  A second `OrbitEntity` — `predicted` — is the entity's own future trajectory, driven incrementally by `game/simulation/`'s `Predictor` (below) rather than recomputed from scratch each frame: `stepPrediction(bodies, simTime, dt, horizon)` lazily creates it from `current.state` if absent, then advances its tip by exactly the caller-supplied `dt` (one RK4 step) against the caller-supplied `bodies` and returns whether it stepped. Sizing `dt`, looking up `bodies` for that tip, and deciding `horizon` are all `Predictor`'s job, not this method's — the same split as `Simulator` deciding `subDt` before calling `stepSim`. It refuses the step (returns `false`) once `predicted.state.t` already exceeds `simTime + horizon` — so the tip always ends up one step *past* the horizon rather than short of it, which is what lets `at(t)` answer exactly `simTime + horizon` by interpolation instead of needing a clamped final step (clamping would make the prediction's resolution silently depend on whether the tip happened to have caught up to the horizon yet). It also refuses to grow (returns `false`) while `thrust !== null` (a thrusting free-flight prediction is meaningless and would just be invalidated next frame anyway) and permanently stops (sets `truncated`, cleared only when a fresh `predicted` is created) if the integrated position sinks into any body's surface (`attractor.ts`'s `hitsAnySurface`, margin `REENTRY_ALT`) or goes non-finite — without that, a re-entering or NaN-corrupted entity would burn its budget forever without ever reaching the horizon. `resyncPrediction(simTime, bodies, horizon)` is the cheap per-frame correctness check, returning whether it discarded: if `predicted.at(simTime)` is absent or has drifted from `current.state.r` by more than the tolerance, it calls `invalidatePrediction()` (drops `predicted` — a zero-cost operation; the list simply regrows through the normal budget next frame, which is why discards never spike frame time). The tolerance is **not** a flat `PREDICT_RESET_DIST`: `resyncTolerance` widens it to whatever `at()`'s own cubic-Hermite interpolation error is at the list's current sample spacing (`PREDICT_SAMPLE_ERROR` scaled by the fourth power of how much `PREDICT_MAX_SAMPLES` has coarsened that spacing past `PREDICT_SAMPLES_PER_REV`). Without that, a long display duration decimates the list far enough that a *correct* prediction reads as drifted — at the 28-day preset the interpolation alone is tens of km against a 500 m threshold — and every entity would discard and restart its list every single frame, so the prediction could never finish growing. `predictsFuture` (`false` by default; `Ship`/`Ammo` set it `true`) only decides *whether* an entity predicts at all — how far ahead is `horizon`, an argument threaded down from `DisplayTimeManager.durationSec(referencePeriod)` every frame, not a per-class constant, since the prediction horizon now tracks whatever span the future-ghost slider can reach. The payoff is `displayState(t)`: `t <= current.state.t ? current.at(t) : (predicted?.at(t) ?? null)` — a two-way branch (past vs. future, nothing else) that `sync` (below) and every marker-position lookup route through, so "what does this entity look like at the currently-displayed time" has exactly one answer for meshes and markers alike.
- `src/physics/orbit-entity.ts` — `OrbitEntity`: THREE/game-independent (`physics/`, alongside `StateQueue`/`Ephemeris` as "pure but stateful"), holding **one** `OrbitState` as `state` plus a decimated `StateQueue` of samples strictly older than it (`history`). `step(dt, bodies, bcInv, thrust, sampleInterval, keepDuration)` advances via `dynamics.ts`'s `stepDynamicsRK4` against the caller-supplied gravity-source array (`bodies` — the caller's own `Ephemeris.attractorsAt(t)` result; which timestamp to sample it at, e.g. the step's midpoint, is the caller's policy, not this class's) — then — only if `keepDuration > 0` and the about-to-be-overwritten `state` is at least `sampleInterval` seconds past the newest recorded sample — pushes that pre-step state into `history` and caps the window with `history.cleanup(keepDuration, 2)` (this is where the display-resolution decimation happens; `keepDuration = 0` never touches `history` at all, so casings/debris/ammo cost nothing). `prevState` (needed every step by `hit.ts`'s segment-vs-sphere test and `targeter.ts`'s board crossings, even for entities with `keepDuration = 0`) is tracked in its own field, separate from the throttled `history` — it's simply "the state one `step`/`reset` ago". `reset(state)` is the discontinuous-overwrite counterpart to `step`: it discards any `history` samples at-or-after the new state's time (`StateQueue.discardFrom`) to keep the "history is older than state" invariant, and still advances `prevState`. `at(t)` answers any time within the retained span — `t === state.t` returns `state` itself, newer than `history.newest` but older than `state` interpolates between the two via `orbital-state.ts`'s `hermiteInterpolate`, and anything older delegates to `history.at(t)` — so callers never need to reconcile the queue and the live state themselves. `samplesOldestFirst()` flattens the retained span into the oldest-first `OrbitState[]` that `render/sampled-line.ts` wants, joining `history` and `state` in the one place that owns the invariant between them. This class holds no orbital-elements memo of its own — a state's osculating elements around a chosen body are `game-entity/game-entity.ts`'s `GameEntity.elementsAround`, since which body to center on is a per-caller decision this class has no stake in. The class is deliberately direction-agnostic — the same step/at/record operations back a **past** span (`GameEntity.current`), a **future** one (`GameEntity.predicted`, whose `history` spans "now → prediction horizon"), and a **planned** one (`plan/plan-arc.ts`'s segment). There is no second implementation of "advance a timed state while recording decimated samples" anywhere in the codebase, and adding one would be a mistake.
- `ship.ts` — `Ship` (abstract; adds name/hp/radius, `bcInv = SHIP_BCINV`, `historyDuration = SHIP_HISTORY_DURATION` — the only class that keeps a history — and `predictsFuture = true`). Base for `Player`/`Enemy`. **It also owns the parts model, and parts are the single source of truth for both health and performance.** `initDefaultParts()` splits the ship's nominal `maxHp` across a fixed `DEFAULT_PART_HP_RATIO` table (summing to 1) and then re-derives `hp`/`maxHp` from the parts it actually built, so the two can never disagree by a rounding step; radiators and solar panels come in **two parts each** because the ship physically has a left and a right panel (`radiatorParts`/`solarParts` return them in `RadiatorSide` order — `'up'` first). All damage funnels through `applyDamageToParts(amount, part?)`, which applies the best armor part's `damageReduction` and then either hits the caller-named part (when the hit location identifies one, e.g. a radiator panel) or a random surviving part; `updateOverallHp()` then sets `hp` to the sum of every part's remaining HP, overridden to 0 the moment the hull or the cockpit is gone. Performance is read the same way — `totalThrust`/`totalTorque`/`totalFuel`/`totalCoolingRate`/`totalPowerGeneration`/`totalFireRate`/`averageMuzzleVelocity` are what the throttle, thermal, power and gun systems actually consume, so swapping a part in the dock changes behaviour with no further wiring. The default thruster's `thrust` is defined as `PLAYER_MASS × max(THROTTLE_LEVELS)` precisely so a stock ship's real acceleration equals the number the HUD prints. `Bullet` carries the firing weapon's `damage`, so what a hit takes off is decided by the shooter's parts rather than a global constant. **`Part.weight` is still unread** — `mass` remains a per-class field (`Player` 1000 kg, `Enemy` 10000 kg), so a heavier part costs nothing yet; wiring it needs a decision on how an enemy's mass relates to its parts.

  The node-vs-context-menu split: in map mode `game.ts` calls `PlanEditor.handleMapPointer` then `MapPicker.handleRightClick`. The editor consumes only the right-clicks that actually hit a node, so the leftovers fall through to `MapPicker.handleRightClick`'s own `pickNearest` — the priority is expressed purely as call order, and the two gizmos never reference each other.

`src/game/plan/` — maneuver planning and its future-trajectory *display*, independent of whether the map is open. "When to look" (display duration, the future-ghost slider) is a separate, `game/`-root concern (`DisplayTimeManager` below) from "what a plan looks like when you look" (this folder):
- `src/game/map-picker.ts` — `MapPicker`: everything about the map's selectable objects — the frame's single candidate set, the right-click hit test, the per-kind menu, and the dispatch of the chosen action to its owner. `refresh(simTime, displayTime)` re-derives `FocusMarkers`' celestial-label positions and `NavTarget`'s AN/DN (both are part of the set, so the pairing is kept inside rather than imposed on callers) and rebuilds `pickables`: `FocusMarkers`' celestial labels + every living self-flown ship (`'player'`) and enemy (`'ship'`), each at its `displayState(displayTime)` so a picked ship sits at the same future-ghost position as its own mesh, + `navTarget.mapPickables()` + `PlanDisplay.apsisMarkers`. **The candidate set stays one list** — splitting it per kind guarantees a consumer that only reads one slice, which is how "the menu opens but focus jumps to Earth" bugs happen; `CameraSystem.update` (focus resolution) and `handleRightClick` (menu) both read this same `pickables`. `handleRightClick(input, simTime)` picks via `map-pick.ts`'s `pickNearest` and opens a `hud/property-window.ts` `PropertyWindow<MenuAction>` (below) built from `itemsFor`. Each open window's `entry.target` is refreshed every `sync()` from the current candidate set, and its `onSelect` reads through `entry.target` rather than the `target` captured at open time — a time-dependent action (warp/add-node) must run against the object's current position/crossing time, not a frame-old snapshot; `'empty-space'` is the one kind with nothing to show a property window about, so `handleEmptySpaceRightClick` keeps opening the plain `ContextMenu<MapPickable>` instead. `itemsFor`: `'body'`/`'ship'`/`'player'` all add the shared `navTargetItems` — set/unset nav-target, shown only when `NavTarget.canTarget` finds a resolvable orbital plane for that id, so an item is never offered and then silently refused; `'apsis'`/`'relnode'` add "add node here" (`PlanEditor.addNodeAt`) and, for `'relnode'`, "warp here" (`SimSpeedManager.startAutoWarpTo`); `'player'` additionally offers activate (`Game.setActivePlayer`)/follow-toggle/delete, the first and last simply omitted for the active ship so the action is unreachable rather than rejected. `'player'`/`'ship'`/`'ammo'`/`'base'` also offer "duplicate" (`duplicateItems()`), but only in creative mode (`isCreativeMode()` — a single `(this.game.activeStage as any).stageId === 'creative'` check shared by every kind and by `'empty-space'`'s "place object" item, so the two never drift apart) — the item is never shown in a mode where there's nowhere to route it, matching the "don't offer what would be refused" rule the whole menu follows. Choosing it (`runDuplicate` → `duplicateSourceFor`, which maps `MapPickable.kind` to the matching `EntityManager` lookup and that entity's live `state`) hands the state to `CreativeStage.openShipPlacerForDuplicate`, which converts it to a preset `ElementsForm` via `creative/duplicate-form.ts`'s `elementsFormFromState` and opens `ShipPlacerPanel` pre-filled with it — a body/`'apsis'`/`'relnode'` target has no matching `duplicateSourceFor` case (nothing to duplicate), which is exactly why those kinds don't get the item in the first place. If the state can't convert (hyperbolic/parabolic) or the converted form's reference body fails `placement-validation.ts`'s `validateBaseReferenceFields` (a base whose current orbit isn't moon-centered), `openShipPlacerForDuplicate` doesn't pass the mismatched form through at all — it hints why and opens with only the object type carried over (`ShipPlacerPreset`'s `{kind: 'objectType'}`), since applying the values while silently rejecting just the reference body would leave the panel showing a different orbit than the one displayed. `PlanEditor.handleMapPointer` runs before this and consumes the right-clicks that hit a node, so priority is expressed purely as call order and the two gizmos never reference each other. A right-click that hits nothing falls through to `handleEmptySpaceRightClick`, which opens the `'empty-space'` menu in any mode (not just creative) — its "place object" item stays creative-only, but "show the orbit object window" is offered everywhere. That item flips `objectListVisible`, which drives the panel `MapPicker` owns for it: `ObjectListPanel` (`object-list-panel.ts`, docked top-right via `hudDock(root, 'right')`) lists the current `pickables`, grouped into per-kind accordion sections (天体/自艦/敵/弾薬/基地; `apsis`/`relnode`/`eqnode`/`empty-space` are markers, not objects, and are left out), each section's header toggling its own body open/closed, and calls `overviewCamera.setFocus(id)` on a row click — so the window is just another view onto the one candidate set, not a second source of what's on the map. Its own ✕ button calls `onClose`, which `MapPicker` wires to clear `objectListVisible` (the same flag `ViewManager` clears when it leaves the map). `sync(overviewMode)` (called from `Game.sync`, alongside the other map-mode panel syncs) is the only place `pickables` reaches the DOM — and it must not do that by rewriting `innerHTML`: `ObjectListPanel.sync` keeps one persistent row element per item id (added/removed by diffing against the previous frame's id set) precisely because a full rebuild would drop each row's click listener the instant a click lands mid-frame, the same reason `stage.ts`'s radiator buttons stay off the `StageStatusPanel`'s rebuilt-every-frame center column.

The remaining kinds (celestial body/apsis/AN-DN icons) have no `alive` of their own, so they fall back to "still in this frame's `pickables`". - `src/game/nav-target.ts` — `NavTarget`: the map's *navigation* target — any `MapPickable`, not just an `Enemy`. - `src/game/view-manager.ts` — `ViewManager`: **the source of truth for which of the three views is showing** (`ViewId` = `'combat' | 'map' | 'dock'`), and the sole place a transition happens (`setView`). It co-switches the camera-side flag (`cameraSystem.overviewMode`), the plan-side editing flag (`editor.editMode`), and the future-display gate (`displayTimeManager.forceCurrent`) so they move together while staying logically independent. Combat and map are the two views that draw the 3D world; **dock is layered on top of whichever of those you came from** — `returnFromDock` remembers it, the private `worldView` getter reports it, and `applyChrome` drives the camera/plan flags off `worldView` rather than `current`. That split is what keeps map→dock from running `editor.onMapClosed()` (which prunes zero-Δv nodes) as a side effect of merely opening a dock. `handleInput` takes `[M]` (ignored entirely while in dock) and forces `'combat'` when the stage stops playing; `selectableViews(combatAvailable)` is what `ViewBadge` lists, filtering out both the current view and any view that can't be entered — `'dock'` needs `Docking.canEnterDock()`, `'combat'` needs a living ship. `Docking` registers itself after construction (`setDocking`, the same late-injection shape as `setTouchControls`) because it is built later. Rendering/viewpoint code checks `overviewMode`; input/behavior code checks `editMode`. This sits at the `game/` root because everything else about a view belongs to either the camera, the plan, or the dock concern.

  **Every way of editing Δv funnels through one method, `applyDv(axis, sign, amount)`**, which is the sole place `plan.applyNodeDv` is called from user input — so a drag, a key hold, a button hold, and a latched drag can't each compute their own rounding or sign convention, and a zero `amount` is a no-op (skipping the call, rather than letting `Plan.applyNodeDv`'s unconditional downstream-discard fire on a no-op edit). The three input paths differ only in how they arrive at `amount`: `applyAxisDrag` (short arm drags, below the latch threshold) scales pixel delta by the existing per-drag rate; `applyHeldDv` (WASDQE keys or a `dvButtons` press, checked together via `||` in `updateEditing`) accumulates a per-direction hold time in `dvHoldTime` (indexed `axis*2 + (sign<0?1:0)`) and looks it up through `rampedDvRate` — an exponential ramp from `DV_RATE_MIN` to `DV_RATE_MAX` over `DV_RATE_RAMP_SEC`, so a tap stays fine while holding sweeps up to coarse; a released direction resets its hold time to 0, so ramping always restarts from the beginning. The arm drag itself only free-drags (via `applyAxisDrag`) up to `NodeGizmo`'s own `DV_DRAG_LATCH_PX` — beyond that `NodeGizmo` stops reporting deltas and instead exposes `latch: AxisLatchState | null` (the axis/sign and the pixel excess past the threshold), which `updateEditing` reads every frame and feeds through `applyDv` at a rate proportional to the excess (capped at `DV_RATE_MAX`) — so a large, held drag keeps adding Δv even while the pointer stops moving, without the user needing to keep dragging further.
- `plan-display.ts` — `PlanDisplay`: the plan's trajectory display — `trajectoryFrame` (the coordinate frame the planned polyline is drawn in, independent of `OverviewCamera.cameraFrame` — a player selects both separately), the ⬡ `plannedPlayer` ghost marker showing where the plan puts the ship at `displayTime` (present or future alike, so it reads as "is the ship actually flying the plan" the instant the map closes — its label is `計画位置 高度 …` at or before `simTime`, `T+…h…m 高度 …` beyond it, altitude measured from whichever body pulls hardest at that position via `attractor.ts`'s `strongestAttractor`, not fixed to Earth), the ◇ Pe/Ap periapsis/apoapsis icons, the ▲▽ EqAN/EqDN equatorial-node icons (`eqNodeIconsOf`, gated on the center body's `Attractor.degree2?.pole` — the same modeled rotation axis `dynamics.ts`'s J2 term reads — so the icons only appear around a body whose equatorial plane is actually defined here (earth/moon today); a body with no `degree2` gravity model, e.g. the sun/jupiter, gets no icon rather than a fabricated axis), its own small TRAJECTORY panel (a single `SegmentedControl` over `hud/frame-labels.ts`'s `FRAME_ITEMS`, built inline rather than as its own panel class — one control doesn't earn a file, same call `PlanEditor` already makes for its own MANEUVER PLAN panel), and the `PlanTrajectory` below. **Split across the two frame phases**: `update(plan, simTime, displayTime, show)` re-integrates the polyline (via `PlanTrajectory.update`) and derives the two things the rest of the frame reads — the ghost's position/label and the apsis icons (position, label and the `MapPickable`s `MapPicker` folds into its candidate set) — while `sync(fo, project, showPanel)` only pushes those into meshes, markers and the panel. Every time value arrives as an argument (owned by `DisplayTimeManager`, resolved by `game.ts`) so it holds no duplicate state. `show` is what keeps a plan that is neither being edited nor has any node from being computed at all; the TRAJECTORY panel — a coordinate-frame *control*, meaningless outside editing — only shows while `showPanel` (`PlanEditor` passes its own `editMode`). The ghost can only sit where the polyline actually reaches (`PlanTrajectory.sampleAt(displayTime)`), so it disappears once `displayTime` runs past the trailing arc's one-revolution end. The apsis icons describe **the orbit the ship is on after its last planned burn** — `syncApsisMarkers` takes `traj.finalSegmentStart` (the trailing segment's start state, `null` once every node lies before the display window), derives `Elements` from it around whichever body pulls hardest there (`attractor.ts`'s `strongestAttractor`/`elementsAround` — so a moon-orbiting ship's Pe/Ap come out moon-centered, never forced to Earth), and places Pe/Ap analytically (`positionOnOrbit(el, 0)`/`(el, π)`) rather than by scanning the drawn polyline; below `APSIS_MIN_ECC` (0.01) the orbit is too close to circular for the apsis direction to be numerically meaningful, so both hide, and a hyperbolic orbit hides only Ap (`el.e >= 1`). `apsisTimeOf(id)` re-derives the same element set to answer the crossing time for `Game`'s "add node here" context-menu action, and `apsisMarkers` exposes the currently-shown icons as `MapPickable`s (`kind: 'apsis'`) for that same right-click to hit.
- `plan-trajectory.ts` — `PlanTrajectory`: splits the plan's corners into segments (anchor → node₁ → … → nodeₙ, plus a trailing one), owns one `PlanArc` per segment (grey before the first burn, white after it, orange beyond), and is the **single place display-frame transforms and screen picking are done** (`toDisplay`/`projectPoint`/`nearestSample`) so the drawn polyline and click hit-testing can't drift apart. `update(plan, ephemeris, frame, currentTime)` rebuilds the segments and re-integrates each `PlanArc`; `sync(fo, project)` pushes the resulting sample series into the line meshes. The display context is split along the same line — the frame and un-bake time are settled in `update` (screen picking from a DOM pointer event has to work between frames), the `ProjectFn` arrives in `sync`; the `ProjectFn` is deliberately *not* captured at construction, since `CameraSystem.activeCameraProjection` returns a snapshot of whichever camera is active *now* (capturing it once would pin picking to the chase camera's startup viewpoint). `finalSegmentStart` is a **public field** holding the trailing segment's start state (`null` if every segment ends on a node, i.e. there's no segment beyond the last burn) — the one piece of segment bookkeeping `PlanDisplay` needs for its apsis icons, so it doesn't have to know how segments are split. Owned by `PlanDisplay`; `PlanEditor` shares the same instance (`planDisplay.traj`) for its own screen picking. **How far ahead the plan is drawn is the PREDICT panel's call**: every segment ends at the next node's `t`, and the trailing one runs `plan.ts`'s `segmentDurationFrom(state0, bodies, displayTimeManager)` from its own start state — the constructor takes a `DisplayTimeManager` reference (shared from `Game` through `PlanEditor`/`PlanDisplay`, see `display-time-manager.ts` above) precisely so this length tracks the PREDICT panel's selection instead of a fixed span. The default `'orbit'` preset reproduces one orbital period around whichever body pulls hardest at that state (`attractor.ts`'s `elementsAround`'s `Elements.period` — not `localOrbitPeriod`'s circular approximation, which would return the short period of the periapsis radius for a node freshly placed on an eccentric orbit); picking a longer preset draws further, and `Plan.nodeTimeRange` (the range a node may be dragged across) grows the same way since it calls the same `segmentDurationFrom`. Beyond one revolution the polyline overlaps itself, so a click can no longer be disambiguated by screen distance alone — see `nearestSample` below. `nearestSample`'s optional `TimeRange` is how a caller restricts picking to part of the polyline; `PlanEditor` passes `Plan.nodeTimeRange` there so a node drag can only ever land on a legal time. Its tie-break is two-stage: first the screen-nearest candidate decides *which arc wins* — arc 0 (pre-burn) always has smaller `t` than the post-burn arcs, so comparing `t` across arcs at the point where two arcs visually cross would silently pick the wrong one — then, restricted to that arc's candidates within `NEAREST_SAMPLE_TIE_PX` of the screen-nearest distance, it picks whichever is closest to the caller-supplied `referenceT` (ties broken toward the earlier `t`). Both call sites in `plan-editor.ts` route through this one rule rather than branching: new-node placement (`handleMapClick`/`handleNodeRightClick`) passes `referenceT = -Infinity`, which — since every candidate is then equally "infinitely far" — degenerates to the earliest-`t` tie-break and reproduces "the first time the line reaches here"; a node drag (`dragNodeToNearestSample`) passes the node's own current time, so a click near where a later revolution's polyline overlaps an earlier one keeps the node on the revolution it was actually dragged from instead of snapping back to revolution 0. `analyticDivergent`'s `detectAnalyticDivergence` walks the first segment's samples against the anchor's elements and, the instant a sample's own strongest attractor differs from the anchor's, flags divergence immediately rather than comparing element values against it — elements taken around different centers aren't comparable, and a center switch (e.g. a lunar flyby) is itself proof the analytic ellipse no longer applies.
- `plan-arc.ts` — `PlanArc`: one segment of the plan, drawn as a polyline. It owns a `physics/orbit-entity.ts` `OrbitEntity` seeded at the segment's start state and RK4-stepped to its end (`update`; the mesh side is a separate `sync`) — so the plan reuses the same "advance a timed state while recording decimated samples" machinery every entity uses, rather than a second implementation of it. Its step size is `localOrbitPeriod(r, bodies) / PLAN_ARC_STEPS_PER_REV` (=100, `attractor.ts`'s `localOrbitPeriod` against that step's `ephemeris.attractorsAt(t)`) off the current radius, so fixing the step count per revolution keeps accuracy uniform regardless of altitude, eccentricity, or which body the segment is currently orbiting; the step count is capped at `PLAN_ARC_MAX_STEPS` (20000) as a safety bound — a segment with a deep or fast periapsis pass shrinks that local-radius-derived step size and could otherwise take an unbounded number of steps to cover its full duration — and hitting the cap truncates the segment the same way reentry does. With `PLAN_ARC_STEPS_PER_REV` fixed, this cap converts directly into a maximum revolution count per segment (≈200) regardless of which PREDICT duration is selected — see `DEVELOP/SPEC.md` for the measured truncation distances. A lower step-size floor to force a long segment to finish drawing regardless was rejected: it lets RK4 diverge into a fabricated trajectory instead of an accurate but truncated one. Decimation is `OrbitEntity`'s own `sampleInterval` (segment length / `PLAN_ARC_MAX_SAMPLES`) and `keepDuration` (the whole segment), the polyline's points are `samplesOldestFirst()`, and `at(t)` is the queue's Hermite interpolation; the draw itself is delegated to `render/sampled-line.ts`. Drag is on at `SHIP_BCINV` — the planner only ever plans the player's own orbit, so it integrates with the player's own ballistic coefficient — and integration stops when the state sinks into any body's surface (`attractor.ts`'s `hitsAnySurface`, margin `REENTRY_ALT`) or goes non-finite, in which case `endState()` is `null`. Re-integration is throttled by `update`'s `tracksLiveAnchor` argument (`PlanTrajectory` passes `true` only for the sole segment while the plan has no nodes — the only case where `state0` follows the live ship every frame): once a node is placed, `state0`/`end` only move on an actual edit, so plain identity/value equality decides whether to recompute, and an untouched arc costs nothing per frame. While `tracksLiveAnchor`, identity comparison alone is useless (`state0` is a fresh object every frame) and even the segment length isn't exactly repeatable under the `'orbit'` preset — the ship's osculating period drifts continuously under J2/drag — so both the length change and the anchor's time drift are compared against the same threshold, the current sample interval (segment length / `PLAN_ARC_MAX_SAMPLES`): below it the drawn polyline wouldn't visibly change, so the stale integration is kept; a real duration-preset change is orders of magnitude larger than that threshold and is always caught immediately. That threshold-based tolerance assumes the anchor is the *same* orbit merely ticking forward, which doesn't hold across a discontinuous re-anchor (`Game.setActivePlayer` to a different ship, a dock launch, a collision's `state` overwrite) — those can land at or before the same `t` the last recompute used, which the drift/length thresholds alone would read as "no change" and keep drawing the previous ship's orbit for up to a full sample interval. So `update` also recomputes immediately whenever `state0`'s identity changed *and* its `t` did not advance past the last recompute's — a swap that lands strictly later in time is left to the normal threshold, since by the time it would matter enough to matter visually, the drift check catches it anyway. A reusable per-segment unit — knows nothing about `Plan` — so `PlanTrajectory` composes several of these rather than predicting the whole multi-node polyline in one shot.
- `node-gizmo.ts` — `NodeGizmo`: the maneuver-node DOM pointer-events layer — node handles + Δv axis arms + the node context menu (warp/delete). A plan concern; uses the shared `hud/context-menu.ts`. An axis-arm drag accumulates its total screen-space projection (`totalProj`) from pointerdown; once `|totalProj|` exceeds `DV_DRAG_LATCH_PX` the drag latches — `onAxisDrag` stops firing per-move deltas and the public `latch: AxisLatchState | null` field instead exposes the axis/sign and the pixel excess past the threshold, for `PlanEditor.updateEditing` to read and integrate every frame at its own rate (see `plan-editor.ts` above). `latch` is cleared and the latched flag reset on pointerup/pointercancel.

- `plan.ts` — `Plan`: the node list plus the `anchor` (the plan's starting state). **Both are plain `OrbitState`s: a node *is* its frozen post-burn absolute state, not a relative Δv** — the burn time is the state's own `t`, and Δv is the derived value (node `v` − arrival velocity). The node list is a single `OrbitState[]`, always kept in execution-time order by construction: `addNode(postState)` finds the insertion point (the count of existing nodes whose `t` is earlier), truncates from there, then pushes — so the added node always lands at the end and its returned index is stable. While the plan is empty, `trackAnchor` follows the live player state; placing the first node freezes the anchor, after which prediction is a pure function of anchor + nodes and never reads `player` state. `dropNodesBefore(t)` (called by `PlanGuide.update` with `simTime - C.NODE_EXPIRE_GRACE`) removes every node whose execution time is at or before `t`, re-freezes `anchor` to the last node it removed, and returns that node (`null` if nothing was dropped) — `CreativeStage.advanceFollowPlan` uses the return value to snap a `followPlan` ship's `state` onto it, so the remaining plan is still drawn from a valid start and the already-flown segment of `PlanTrajectory` disappears on its own. Editing a node discards downstream nodes (`retimeNode`/`applyNodeDv`/`removeNode`), which is what keeps the module's one invariant true: **a node is never placed later than its predecessor's drawn segment reaches** (node *i*−1, or the anchor for node 0). `nodeTimeRange(idx, ephemeris, displayDuration)` is the single statement of that rule and `retimeNode`'s precondition — with it holding, node times are already ordered, so `retimeNode` neither sorts nor moves the node's index. `applyNodeDv` discards downstream nodes unconditionally, with no zero-Δv guard — a caller that wants to skip a no-op edit (`PlanEditor.applyDv`) checks for that itself before calling, rather than `Plan` special-casing a magnitude it has no reason to inspect. The module-level `orbitPeriodOf(state, bodies)` (`attractor.ts`'s `elementsAround`'s `Elements.period`, around whichever body pulls hardest at `state` — never a plan-level setting — falling back to `APERIODIC_ARC_DURATION` when no finite period exists, e.g. hyperbolic orbits) feeds `segmentDurationFrom(state0, bodies, displayDuration)` — the shared definition of "how long a segment starting at this state may run," which `nodeTimeRange` and `plan-trajectory.ts`'s `buildSegments` both call rather than each deriving it separately, so the legal node range and the drawn polyline can never disagree. `displayDuration` is typed as the narrow `DisplayDurationSource` interface (`{ durationSec(referencePeriod): number }`) rather than the concrete `DisplayTimeManager`, so this module — and the no-DOM `tsconfig.test.json` that compiles it directly for `test:physics` — never has to resolve `DisplayTimeManager`'s DOM-heavy dependency chain. No prediction cache lives here. **Each `Player` owns its own `Plan`** (`readonly plan = new Plan()`), which is what lets creative-mode multi-ship plans exist independently of one another.
- `plan-guide.ts` — `PlanGuide`: the combat-view execution guide for the nearest node, split across the two frame phases. `update(plan, player, simTime, editMode, bodies)` (`Game.update`, immediately before `Plan.trackAnchor` so a node dropped this frame lets the anchor resume tracking the player the same frame) drops overdue nodes via `plan.dropNodesBefore(simTime - C.NODE_EXPIRE_GRACE)`, then — once the nearest remaining node enters its execution window (`simTime >= node.t - C.NODE_APPROACH_LEAD`) — notifies approach and, once the player's and the node's strongest attractor agree and the module-level `orbitClose` also holds between the player's own elements (`player.elementsAround(strongestAttractor(player.state.r, bodies))`) and the node's target elements (`elementsAround(node, strongestAttractor(node.r, bodies))`), achievement — a node placed near a different attractor than the one the player currently orbits can never read as achieved, since comparing elements taken around different centers is meaningless; node consumption is purely time-based (`dropNodesBefore`), so the center check and `orbitClose` only gate the achievement hint. Each hint fires once per node: private `approachNotified`/`achievedNotified` hold the last-notified node and are compared by **identity**, since editing a node always replaces it with a new `OrbitState`. `sync(plan, player, simTime, editMode, project)` (`Game.sync`) only places the ◆NODE/⬢BURN markers for that same nearest node; the planned polyline itself is `PlanDisplay`'s, drawn in combat view too. `PlanGuide` takes only `Hud`/`Sfx`/`MarkerManager` — auto-warp cancellation near the node is `SimSpeedManager`'s own concern.

every DOM write it used to do is now in `syncPanel`. **A node can be created two ways**: `handleMapClick` (left-click on the drawn polyline) calls `plan.addNode` directly on the clicked `planDisplay.traj.nearestSample`, while `addNodeAt(t)` turns a *time* into a node by first resolving `planDisplay.traj.sampleAt(t)` — hinting instead of doing nothing if the plan doesn't reach that time — and is what `Game`'s "add node here" context-menu action (against a periapsis/apoapsis or relative-AN/DN icon) calls. `handleMapClick` otherwise selects the nearest existing node on a hit, else clears the selection — a click that lands on neither node nor polyline always deselects. - `src/physics/orbital-state.ts` — the `OrbitState` type (`{t, r, v}`, built only via `orbitState(t, r, v)`) plus the geometry derivable from a state vector alone: `altitudeOf(r)` — altitude above Earth specifically, for the atmosphere-only callers (`atmosphere.ts`'s density table, `thermal.ts`'s drag/heating, the descent-warning EMA); surface contact with *any* attractor is `attractor.ts`'s `hitsAnySurface` instead, which is what every `checkLoss` uses — the orbital basis `orbitalAxes(state)` → `{pro, nrm, radOut}` plus `fromOrbitalAxes(state, x)`, the one place that basis is built (the Δv edit keys, the Δv arm screen directions, the PROGRADE/NORMAL/RADIAL markers and every `norm(cross(r, v))` spelling all route through it — note `radOut` is the in-plane direction perpendicular to the velocity, which equals r̂ only when r⊥v; the name follows the HUD's RADIAL OUT/IN labels, not the true radial), and `hermiteInterpolate` (cubic Hermite between two `OrbitState`s, using their velocities as tangents; refuses a `t` outside the two epochs unless `allowExtrapolation` is passed, since the cubic diverges fast outside the span). Also holds Earth's physical constants (`MU_EARTH`/`R_EARTH`/`R_EARTH_EQ`/`SIDEREAL_DAY`) — `altitudeOf` is the only function here that reads one (`R_EARTH`); the rest are read by callers elsewhere in `physics/` (`ephemeris.ts`'s Earth `Attractor`, `dynamics.ts`'s `j2Accel`, `atmosphere.ts`'s co-rotating-atmosphere rate). Pure functions.
- `src/physics/elements.ts` — the classical orbital `Elements` type and the state↔elements conversions. **`Elements.center: Attractor` replaces a bare `mu`**: an orbit's shape alone doesn't say what it's an orbit *around*, and comparing/displaying elements needs that answer (which body's radius the apsis altitudes are measured from, which body's name a HUD readout shows) — so the element set carries its own center rather than leaving the caller to remember it separately. `elementsFromState(rel, center)` takes a **center-relative** state (not absolute ECI — the argument name and its own comment say so) and is called from exactly one place; the sole entry point every other module uses is `attractor.ts`'s `elementsAround(s, body)`, which converts the absolute ECI state itself before calling in. `keplerPeriod(a, mu)`/`semiMajorFromPeriod(T, mu)` keep a plain `mu` argument (they only ever need the number, not a full `Attractor`, and are used before any `Attractor` exists yet — e.g. `CreativeStage`'s size-from-period input mode); `keplerPeriod` is the sole place a semi-major axis becomes an orbital period, and `Elements.period` routes through it. `Elements` carries no altitude of its own — periapsis/apoapsis depend on a body radius — so `apsisAltitudes(el)` reads it off `el.center.radius`. Kepler helpers for maneuver planning (`trueAnomalyAt`, `tofBetween`, `positionOnOrbit`/`velocityOnOrbit`, `stateFromElements` — all round-trip-verified to machine precision; `stateFromElements` returns a center-relative state too, absolute ECI conversion is the caller's job). Pure functions, no Earth constants.
- `src/physics/attractor.ts` — the three-way classification of everything that exerts gravity, fixed at this depth because it tracks a physical fact rather than a convenience: the sun's mass so dominates the solar system that only a planet's own heliocentric orbit reduces to an unperturbed Kepler ellipse — a satellite orbiting a planet is still close enough to the sun to need an explicit solar-perturbation term (`satellite-orbit.ts`), and no solar-system body has a stable satellite of its own, so "satellite of a satellite" needs no representation. `StarId`/`PlanetId`/`SatelliteId` (each a closed string-literal union — adding a body means widening one of these, which is what makes the two `Record<AttractorId, …>` registries — `solar-system.ts`'s `SOLAR_SYSTEM` and `game/celestial/celestial-registry.ts`'s `CELESTIAL_VIEWS` — fail to compile until the new id is registered) and their union `AttractorId`; `OrbitingId = PlanetId | SatelliteId` excludes stars, since only a body that orbits something has a rotation basis, a normal, or Lagrange points, and narrowing the type turns "does this body have an orbit" from a runtime null check into a compile error. `Attractor` (`{id: AttractorId, mu, radius, state: OrbitState, degree2: Degree2Gravity | null}`, ECI position/velocity as one timed `OrbitState` rather than separate `r`/`v` fields — so a position and a velocity from different instants can never be paired by mistake; Earth pinned at the origin). `Degree2Gravity` (`{j2, refRadius, pole, tesseral}`) is the body's own degree-2 gravity field, resolved to concrete ECI vectors at the lookup time; `null` means "treat as a point mass", which is what keeps a body with no oblateness model from having to carry a meaningless pole. `tesseral` (`{c22, longAxis}`) is likewise `null` for an axisymmetric field. **`refRadius` is the radius the coefficients were defined against and is deliberately separate from `radius`** (the Moon's is 1738.0 km against a 1737.4 km surface radius), so updating the surface radius can never silently rescale the gravity field and the pure functions built on it: `attractorAccel(r, body)` (one body's own contribution to the ECI equation of motion — `μ_b[(r_b−r)/|r_b−r|³ − r_b/|r_b|³]`, the second term correcting for ECI itself free-falling toward that body, and each term skipped at zero distance so a body coincident with the query point — or the origin body itself — can't blow up); `strongestAttractor(r, bodies)` (the body with the largest `attractorAccel` magnitude — deliberately not the largest raw μ/d², which hands the sun a false win ~2.6×10⁵ km from Earth by ignoring that the ECI origin is comoving with it); `localOrbitPeriod(r, bodies)` (the circular period around whichever body that is — the time scale integration/sampling step sizes are derived from, independent of which body an ellipse happens to be drawn around); `frameOfAttractor(body)` (the identity-rotation `FrameTransform` centered on an already-looked-up `Attractor`, so `elementsAround` doesn't need to re-query the ephemeris for a snapshot it already has); `elementsAround(s, body)` (osculating `Elements` around a caller-chosen body, via `frame.ts`'s `toFrameState`); and `hitsAnySurface(r, bodies, margin)` (every integration-truncation check — prediction, plan arcs — and every entity's `checkLoss` stops/despawns at any body's surface through this, not just Earth's). `Ephemeris.attractorsAt(t)` (below) is the sole place all bodies' current `r`/`v` are assembled into a `bodies` array, in `SOLAR_SYSTEM`'s declared order. Code outside `solar-system.ts` must not switch exhaustively over `AttractorId` — it is always used as a registry key, never enumerated (see `solar-system.ts` below for the one exception).

  This module intentionally joins only two things — summing gravity, and handing out a body to center an ellipse on — and nothing more. Five once-conflated concerns stay structurally separate, with no umbrella concept binding them: **which gravity sources the integrator sums** (always all three, decided nowhere — `attractorAccel`/`dynamics.ts`); **which body an analytic ellipse (`Elements`) is centered on** (chosen per call site, typically `strongestAttractor` → `elementsAround`, and re-derived every frame as a point-in-time display rather than cached as if it belonged to the entity); **which frame a *sampled* trajectory is baked into for display** (the existing `Frame`/`PlanDisplay.trajectoryFrame` machinery, untouched by this module — a sampled polyline must stay in one frame for its whole length, so it is never derived from the per-frame ellipse-center choice); **where the overview camera looks and which frame it's fixed to** (`OverviewCamera.focus`/`cameraFrame`, likewise untouched); and **the time scale sizing integration/sampling steps** (`localOrbitPeriod`, independent of the ellipse-center choice). No function here derives one of these from another, and there is no GUI to pick an ellipse's center — it is always resolved via `strongestAttractor`.
- `src/physics/ecliptic.ts` — the ecliptic basis and its relation to ECI (Y = north): `Q_ECL_TO_ECI` (Z-up ecliptic → ECI, used by rotation-basis code), `Q_ECLY_TO_ECI` (Y-up ecliptic → ECI, used wherever a Kepler element set built in ecliptic coordinates is turned into an ECI state via `stateFromElements`, which assumes Y = pole), `ECL_POLE`/`ECL_POLE_ECI`/`ECL_VERNAL`, `eclToEci`/`eciToEcl`. The obliquity (23.439291°) is a fixed J2000-equivalent constant — equinox precession (25,772-year cycle, ~5.6° of equatorial drift per 1000 years) is out of scope, since it's a question of what ECI itself means (J2 axis, atmosphere co-rotation, Earth mesh spin axis, celestial grid all assume it fixed), not an orbital detail.
- `src/physics/kepler-orbit.ts` — the orbit math shared by every classification: `KeplerOrbit` (fixed ecliptic-frame Kepler elements plus each angle's secular rate) and its evaluators `keplerOrbitState`/`keplerOrbitRotation`/`keplerOrbitNormal`. Angles are composed mean longitude L (one full turn per orbital period) → mean anomaly M = L − ϖ → true anomaly ν, then u = ν + (ϖ − Ω) for the in-plane angle — computing u directly from L would let precession speed up or slow down the apparent revolution. `keplerOrbitState` reuses `elements.ts`'s `stateFromElements` (via `Q_ECLY_TO_ECI`) rather than a second position/velocity implementation; velocity adds the rotating frame's own angular velocity (ω×r, precession's contribution) on top of the radial rate. `keplerOrbitMeanDirection` returns the direction the **mean** longitude points (in-plane angle `u = L − Ω`, mean anomaly rather than true), which is what a synchronously rotating body's prime meridian tracks — a uniformly spinning body cannot follow the non-uniform true anomaly, and the two differ by the equation of center (up to 6.3° at the Moon's eccentricity). Knows nothing about stars/planets/satellites — that classification is `planet-orbit.ts`/`satellite-orbit.ts`'s.
- `src/physics/planet-orbit.ts` — a planet's orbit is its **planet-satellite system barycenter**'s heliocentric Kepler orbit, not the planet body's own (Earth is not light enough relative to the Moon, 1:81, to skip the ~4,673 km barycenter offset) — `PlanetOrbit = KeplerOrbit` plus secular element rates in deg/Julian-century (`planetOrbit`). `planetAngles` derives the sun-direction angles a satellite model needs (mean anomaly/longitude and their rates) straight from this barycenter orbit, so satellite evaluation never depends on the satellite's own state to find the sun.
- `src/physics/satellite-orbit.ts` — a satellite's orbit is a two-body Kepler ellipse around its planet **plus solar perturbation** (secular node regression/perigee advance via `raanRate`/`lonPeriRate` — the sign is this module's own, never spelled out at a call site — and periodic longitude/latitude/distance correction terms, `PerturbationTerm[]`, summed as sine/cosine series in the four fundamental arguments D/M/M′/F). Precession periods are the *measured* ones (18.612958y node / 8.85y perigee), not first-order theory's (which under-predicts perigee precession by ~2×, the historical problem Clairaut resolved with second-order terms). The two-body part alone must never duplicate the periodic table's central-difference-equivalent terms (arguments that are `m`-only or `f`-only) — that's double counting. `orbitRotationAt`/`orbitNormalAt` are built from the mean (two-body) elements only, so a satellite's true position can drift up to ~1.4° off that basis's x̂.
- `src/physics/solar-system.ts` — `CelestialBodyDef` (the star/planet/satellite discriminated union — this `kind` switch is the one exhaustive switch over `AttractorId`'s classification that's allowed, since it's a physical claim, not a registry lookup) and `SOLAR_SYSTEM: Record<AttractorId, CelestialBodyDef>`, the static numeric facts (μ, radius, orbit) for every body. `MU_SUN`/`R_SUN`/`MU_MOON`/`R_MOON` live here (Earth's own `MU_EARTH`/`R_EARTH` stay in `orbital-state.ts`, read from here rather than duplicated). The degree-2 gravity coefficients live here too — `J2_EARTH`, and `J2_MOON`/`C22_MOON`/`R_MOON_GRAVITY`/`MOON_OBLIQUITY` — all **unnormalized**, which matters because most published gravity-field files ship normalized coefficients. Each body's `degree2?: Degree2GravityDef` states its own coefficients, its own reference radius, and a `PoleModel` saying how its spin axis is determined (`'eciPole'` for the body that defines ECI, `'cassini'` for a synchronously rotating satellite plus its equatorial tilt). Omitting `degree2` makes a body a point mass. `J2_EARTH`'s outside reader is `ship-placer-panel.ts`'s sun-synchronous-inclination preset, which needs the same coefficient the integrator itself uses rather than a second copy.
- `src/physics/lagrange.ts` — the restricted three-body Lagrange points as pure geometry: `collinearGamma(mu, point)` (Newton's method for the collinear-point distance ratio from the quintic balance equation, seeded from the Hill radius) and `lagrangePoints(mu, place)` (the five points' dimensionless rotating-frame coordinates, mapped to a caller-supplied `place(x, y)`). Mass-ratio-only — no body identity, no ECI.
- `src/physics/shadow.ts` — `sunlitFactor(r, sunDir, penumbra)`: Earth's cylindrical-shadow日照率, split out of `ephemeris.ts` because it's geometry from a position and a sun direction, not "where is a body at time t" — a genuinely different question despite reading like ephemeris code. `penumbra` is a caller-supplied argument since `physics/` must not depend on `game/const.ts`.
- `src/physics/srp.ts` — `srpAccel(r, sun, srpCoeff, sunlit)`: solar radiation pressure as the standard cannonball model — the body is a sphere of constant reflectivity, so the force is along the sun→body line regardless of attitude and the coefficient and cross-section only ever appear as the product `srpCoeff = C_R·A/m` [m²/kg] (the same shape as drag's `bcInv = Cd·A/m`, and stored the same way: one constant per entity class). `SOLAR_PRESSURE_1AU` = 4.56e-6 N/m² and `ASTRONOMICAL_UNIT` are this module's own — the latter is the inverse-square reference distance, deliberately not read from `solar-system.ts`'s Earth semi-major axis, which is a different quantity that merely has a similar value. The shadow factor is supplied by the caller rather than computed here, so `shadow.ts`'s `sunlitFactor` stays the single answer to "is this point in sunlight" shared with the lighting, radiator and power systems. **Near Earth this is the smallest perturbation modeled** (~7e-8 m/s² for the player ship, about a quarter of the drag at 420 km), but drag vanishes with altitude while this does not, so out at the Lagrange points it is the only non-gravitational force left.
- `src/physics/body-orientation.ts` — a body's own orientation, as opposed to where it is: `cassiniSpinAxis(eclipticPole, orbitNormal, obliquity)` builds a synchronously rotating satellite's spin axis from Cassini's laws (spin axis, orbit normal and ecliptic pole stay coplanar, with the spin axis on the far side of the ecliptic pole from the orbit normal — so feeding it a precessing orbit normal makes the spin axis precess on the same 18.6-year period for free), and `principalLongAxis(pole, reference)` orthogonalizes a reference direction against the pole. **The orbit normal is not the spin axis** — for the Moon the two are 6.688° apart, and substituting one for the other tilts the `C22`/`J2` perturbation by that much without changing its magnitude, which is why `body-orientation.test.ts` checks the angles rather than the resulting acceleration. Pure functions, no body identity.
- `src/physics/ephemeris.ts` — `Ephemeris`: composes star → planet-satellite-system barycenter → planet/satellite (the three-stage pipeline: a planet's barycenter follows its own heliocentric Kepler orbit via `planetOrbit`/`keplerOrbitState`; each satellite's planet-relative state comes from `satelliteState` fed the planet's own `planetAngles` — the sun-direction angle a satellite's solar-perturbation terms need, taken from the barycenter's own orbit so nothing is circular; the planet body itself is then the barycenter minus Σ(μ_satellite/Σμ)·(satellite's planet-relative state), applied to both position *and* velocity, and each satellite is that planet position plus its own planet-relative state), then ECI-izes by subtracting Earth's own heliocentric state (Earth pins to exactly `(0,0,0)`/`(0,0,0)` because it subtracts itself). Holds **no name-specific branch** — every step dispatches on `SOLAR_SYSTEM[id].kind`, so adding a body needs no change here. Public surface: `stateOf`/`positionOf(id, t)`; `orbitRotationAt`/`orbitNormalAt(id: OrbitingId, t)` (`OrbitingId` excludes stars, so a caller asking for the sun's own orbit basis is a compile error, not a runtime null); `lagrangeAt(secondary: OrbitingId, t)` (primary resolved from `secondary`'s classification — a planet's primary is the star, a satellite's is its planet; x̂ is uniformly "primary → secondary", so the collinear/triangular points share one formula regardless of which system); `frameTransformAt(frame: Frame, t)` (the sole place a `Frame`'s origin/rotation is resolved into a concrete `FrameTransform` — origin from `stateOf(frame.center, t)`, rotation from `orbitRotationAt(frame.rotatingWith, t)` or the identity when `rotatingWith` is `null`); `sunDirAt(t)`; `attractorsAt(t)` (`SOLAR_SYSTEM`'s declared order — earth, moon, jupiter, sun), which also resolves each body's `Degree2Gravity` for that instant: the pole from its `PoleModel` (`body-orientation.ts`'s `cassiniSpinAxis` for a synchronous satellite, so the axis precesses with the orbit normal for free) and, for a non-axisymmetric field, the long axis from that body's own `keplerOrbitMeanDirection` orthogonalized against the pole. Holds no memoization — every call re-evaluates the composition from scratch; reintroduce caching only after measuring an actual frame-time problem, not speculatively. The constructor takes `phaseOffsets?: Partial<Record<AttractorId, number>>` (default: only the Moon's mean longitude gets a random phase, so each game starts with the moon at a different point in its orbit). THREE-independent; the single instance is **owned by `Game`** and shared by reference with `EnvironmentScene`, `Simulator`, `OverviewCamera`, `PlanEditor`/`PlanDisplay`/`PlanTrajectory`, `FocusMarkers`, `Player.behave`, and `Enemy.behave`/`Stage.behaveAllEnemies` (the latter two need it only to resolve `sunDirAt` for muzzle-flash sun-glare spread — see `player-fire.ts`/`enemy.ts` below).
- `src/physics/frame.ts` — a display coordinate system is **an origin body × an optional rotation**, `Frame = {center: AttractorId, rotatingWith: OrbitingId | null}` — a moving origin (which body is the coordinate system centered on) and a rotation (which body's revolution the axes are locked to) are independent choices, so the type is their direct product rather than a single enumerated frame name. `rotatingWith: null` is an inertial frame at `center`; otherwise the frame spins with whichever orbiting body `rotatingWith` names — for a satellite that's its planet (so `{center:'earth', rotatingWith:'moon'}` holds the moon still), for a planet that's itself (`{center:'earth', rotatingWith:'earth'}` holds the sun's apparent motion still without moving the origin off Earth) — `rotatingFrameCenterOf` resolves this from `solar-system.ts`'s classification, and a star can never be `rotatingWith` since it has no orbit to rotate with (enforced by `OrbitingId` excluding `StarId`). **`FRAMES`, generated once from `SOLAR_SYSTEM`, is the only source of `Frame` values** — one inertial frame per body plus one rotating frame per orbiting body — and every UI/display consumer must reference an element of it rather than construct a `Frame` literal: a fresh object would still be `==`-equal in content but not in reference, and `render/sampled-line.ts`'s `frame === lastFrame` re-bake guard is a reference check (silently degrading to "re-bake every frame" on a mismatch, not a crash, which is why the discipline has to be enforced by convention rather than caught by a type).

  A `Frame`'s actual motion at a moment — `FrameTransform = {origin, originVel, q, omega}` — is supplied by `Ephemeris.frameTransformAt`, which this module does not import (avoiding a `frame.ts` ⇄ `ephemeris.ts` cycle); `frame.ts` itself is pure conversion arithmetic over an already-resolved `FrameTransform`. Six conversions split by what kind of quantity is being moved: **points** (`toFramePoint`/`toInertialPoint`, affine — origin translation *and* rotation, for a position) and **directions** (`toFrameDir`/`toInertialDir`, linear — rotation only, for a displacement/velocity-difference/up-vector); their outputs are the branded `FramePoint`/`FrameDir` types so a caller can't feed a direction through the point path (or vice versa) and get a silently wrong offset the moment a frame's origin starts moving. `toFrameState`/`toInertialState` do the same split within one `OrbitState`: `v_rel = R⁻¹(v − ȯ − ω×r_rel)`, the Coriolis-like `ω×r_rel` term existing because a rotating frame's own spin contributes to the relative velocity, not just its translation. `toFrameState` bakes at the state's own epoch (`s.t`) and needs no time argument; `toInertialState` still takes one, because un-baking happens at the *display* time, not the sample time — that time becomes the restored state's epoch. Used only by display concerns (`render/sampled-line.ts` bake/un-bake, `OverviewCamera`'s viewpoint offset/pan/up — all three are directions, not points, since panning must not jump when the frame's origin moves — `PlanTrajectory`'s picking) — the simulation itself is always plain ECI.
- `src/physics/projection.ts` — the pure screen-projection math (`ViewFrame` → `projectToNdc` → `ndcToScreen`, yielding `Projected {x, y, front}`). **It lives under `physics/` deliberately**: a pinhole projection is the geometric map from Cartesian to projective coordinates, exact and free of any look-and-feel tuning — the kind of thing `physics/` is for. What would not belong here is anything that bends that map for legibility (marker nudging, distance compression, fades); those stay in `game/`. Independent of THREE.js and of the floating origin; each camera in `game/camera/` binds it into a `ProjectFn`.
- `src/physics/intercept.ts` — `solveLeadTime` (the lead/interception time for a relative position+velocity and a muzzle speed, used by the enemy AI's aim) and `leadPoint` (the world position to aim at, given two `OrbitState`s and a cut-off time; `null` when there's no usable solution). `leadPoint` is what keeps `LeadMarkers` from rolling its own lead math.
- `src/physics/halo.ts` — creative-mode-only: initial `OrbitState`s for halo/Lissajous orbits about the collinear Earth-Moon/Sun-Earth L1/L2 points. The rotating local frame (`collinearFrame`) is built entirely from existing `ephemeris.ts` API — `lagrangeAt` for the point's position, `orbitRotationAt`/`orbitNormalAt` for its rotation and plane normal — so this module adds no orbital elements or rotation axes of its own; from the point's distance ratio γ it derives Richardson's `cn` coefficients and the linear in-plane/out-of-plane frequencies λ/ωz (verified against the published values: Sun-Earth L1 λ=2.0864, ωz=2.0152, k=3.2293; Earth-Moon L1 λ=2.3344, ωz=2.2688). **Halo orbits do not exist in the linear solution** — λ ≠ ωz, so the two oscillations never close into a loop. They appear at third order, where Richardson (1980)'s amplitude constraint `l1·Ax² + l2·Az² + Δ = 0` makes the frequencies coincide; `haloState` therefore takes only the out-of-plane amplitude `Az`, solves that constraint for `Ax` (reproducing the ISEE-3 halo — Az = 110,000 km → Ax ≈ 205,000 km, Ay ≈ 662,000 km, both within 1% of the published figures) and only then drives the linear solution at the single shared frequency. `lissajousState` imposes no constraint and takes both amplitudes, leaving the two frequencies independent (an open Lissajous figure). The state itself is the first-order solution — the third-order series expansion is not included. And **the game's integrator is not a restricted three-body problem** (it's full multi-body gravity + J2 + drag, same as every other entity via `dynamics.ts`'s `stepDynamicsRK4`), so a ship placed at one of these states does **not** stay on a halo/Lissajous orbit once the simulation runs — it drifts, same as it would drift off any other idealized orbit under real perturbations. `CreativeStage.buildLibrationState` is the only caller.
- `src/physics/dynamics.ts` — the RK4 integration core, in two layers. `stepOrbitRK4(s, dt, accel)` is the bare stepper, driven entirely by a caller-supplied acceleration callback (`AccelFn`: `(rx, ry, rz, vx, vy, vz) => Vec3`, evaluated per RK4 stage) and returning the advanced `OrbitState` — epoch included — without touching its input; it holds **no gravity of its own**, so a caller wanting a bare two-body step supplies its own gravity callback (as `dynamics.test.ts` does when it checks `stepDynamicsRK4` against a hand-written legacy composition). `stepDynamicsRK4(state, dt, bodies, bcInv, thrust)` is the single RK4 step behind `physics/orbit-entity.ts`'s `OrbitEntity.step` — the one place "full multi-body gravity + J2 + drag + thrust" is composed, whether the caller is `GameEntity.stepSim` (drag on via each entity's own `bcInv`, its own `thrust`), `GameEntity.stepPrediction`, or `plan/plan-arc.ts` (`thrust = null`, since neither a prediction nor a planned trajectory thrusts). Its module-private `accel(r, v, bodies, bcInv, srpCoeff, penumbra)` sums `attractor.ts`'s `attractorAccel(r, body)` over every body (each term already carrying its own ECI non-inertial correction), this module's own `degree2Accel` for every body that carries a `degree2` field, `atmosphere.ts`'s `dragAccel` (`bcInv = 0` skips drag), and `srp.ts`'s `srpAccel` gated by `shadow.ts`'s `sunlitFactor` (`srpCoeff = 0` skips it) — `stepDynamicsRK4` adds an optional `thrust` on top and drives it all through `stepOrbitRK4`. **`accel` holds no body-specific branch**: which bodies are oblate, how oblate, and which way their poles point all ride on the `Attractor` itself, so adding an oblate body needs no change here. `degree2Accel(rRel, mu, g)` takes a *body-centered relative* position (unlike the point-mass term, which is built in ECI) and evaluates both the zonal `J2` term — `k[(1 − 5u²)r + 2(r·p̂)p̂]`, `k = −(3/2)J2·μ·R²/|r|⁵`, for an arbitrary pole `p̂` — and, when the field is not axisymmetric, the tesseral `C22` term as the gradient of `3·C22·μ·R²·(x² − y²)/|r|⁵` in the principal-axis frame. Earth uses it with the pole on Y (verified ≈ −5°/day RAAN regression at 420 km/51.6°); the Moon uses it with a Cassini-state pole and a non-zero `C22`. No out-parameter variant — see the immutability note above.
- `src/physics/attitude.ts` — rigid-body attitude: quaternion + body-frame ω via Euler's equations. ω integrated with RK4 + kinetic-energy projection (naive explicit integration diverges — this is what makes the Dzhanibekov effect on debris stable long-term); `stepAttitude` carries the sub-step ω/q as scalar locals and returns one new `Attitude`. `qFromForwardUp` (nose +Z / up +Y basis → quaternion, re-orthogonalizing, null at the fwd∥up singularity) is the shared attitude-basis builder used by `player/player.ts` (`progradeAttitude`), `player/player-throttle.ts` (`autoAlignTorque`), and `stages/spawner/enemy-generator.ts` (`generateApproachingEnemy`). Pure functions.
- `src/physics/vec3.ts` — plain-object Vec3 math helpers (all pure, all returning new immutable `Vec3`s) and the shared random helpers `randSym`/`randVec`/`randPerp`.
- `src/physics/deque.ts` — `Deque<T>`: a generic ring-buffer double-ended queue (`pushLeft`/`pushRight`/`popLeft`/`popRight`/`at`/`peekLeft`/`peekRight`/`deleteLeftN`/`deleteRightN`/`clear`), capacity doubling on overflow. No game-state dependency; a general-purpose data structure, not physics per se, but grouped under `physics/` since it's equally pure/DOM-free and covered by the same `test:physics` runner.
- `src/physics/state-queue.ts` — `StateQueue`: a `Deque<OrbitState>`-backed time series kept newest-first (`peekLeft`/`newest` = newest, `peekRight` = oldest). `push` adds the latest sample; a push whose time doesn't exceed the current newest is treated as a correction and discards everything at-or-after its own time before inserting (the same "editing invalidates downstream" rule `Plan` node edits follow), so the pushed sample always ends up as the new head. `capCount(n)` trims down to the `n` most recent samples. `cleanup(maxAge, minCount)` is the age-based sibling — this is what backs `physics/orbit-entity.ts`'s `OrbitEntity.history` window (`OrbitEntity.step` calls it with `keepDuration` on every recorded push): prunes samples older than `maxAge` relative to the newest one, never below `minCount`, and (when `maxAge` is nonzero) always leaves one sample older than the cutoff in place so `at(newest.t - maxAge)` still has a bracketing pair to interpolate against instead of falling outside the retained span. `discardFrom(t)` drops every sample at-or-after `t` without inserting anything — `OrbitEntity.reset` uses it to invalidate samples that are no longer valid after a discontinuous state overwrite. `at(t)` binary-searches the bracketing pair and reuses `orbital-state.ts`'s `hermiteInterpolate`, returning `null` outside the retained span rather than extrapolating. The private `bisect` (lower-bound over the descending series) is the single search primitive `push`/`cleanup`/`discardFrom`/`at` all share. `toArrayOldestFirst()` reverses the internal newest-first order into the oldest-first array `render/sampled-line.ts`'s `SampledLine.syncGeometry` expects — the one place this class's storage order leaks out.
- `src/physics/nbody/{bodies,integrator,physics.worker}.ts` — original N-body RK4 worker stack, unused by the LEO game; isolated in its own directory (with a `README.md` explaining why) and retained for the cislunar phase.
- `src/render/earth.ts` — realistic-style Earth at true radius: a 1024×768 indexed `SphereGeometry` textured with real photography (`assets/earth.jpg` + `assets/8k_clouds.jpg`) and shaded with TSL nodes. **The atmosphere is analytic, not geometric** — the stacked shells this file used to draw are gone. At near=2m with a 24-bit non-logarithmic depth buffer, any geometry floating tens-to-hundreds of km above the surface z-fights with it at grazing view angles (δz ≈ z²/near/2²⁴ grows with the square of distance), and neither shell spacing nor shell count fixes the quantization itself. So the invariant is **exactly one opaque depth-tested body below ~400 km**: clouds are baked into the surface albedo, and both the near haze and the limb glow are computed per-pixel from the view direction (`ATMO_HAZE_TAU0`, `ATMO_RIM_MIN_H`/`ATMO_RIM_MAX_H` = 340 km/`ATMO_RIM_SCALE_H`), with occlusion by the Earth resolved by analytic ray-sphere intersection rather than the hardware depth test. Wavy aurora curtains (4 additive curtains, two per pole at ±67° latitude, offset layers sharing a `geomSeed` so they stay parallel) remain real geometry on the spin group, animated by `Earth.tick(dt, simTime)` — which also refreshes the atmosphere shader's earth-center uniform.
- `src/render/ships.ts` — low-poly meshes, **loaded rather than built**: the primitive-assembly code lives in `tools/export-models.mjs`, which serializes each mesh with `Object3D.toJSON()` into `src/assets/models/*.json`; at runtime this file parses those with `THREE.ObjectLoader` and `clone(true)`s them, so startup never re-assembles geometry. The modeled shapes are: player ship (nose = body +Z; stubby box hull, 4 aft engines, small solar paddles, two vertical gun bores on the front face — `MUZZLE_OFFSETS` is exported so `player/player-fire.ts` fires/ejects from the exact modeled positions, and the attitude thrusters come from `render/rcs-nozzles.ts` (below); the two deployable radiators sit on the hull sides just below the solar panels (`x=±2.62, y=0.30, z=-2.20`) and are accordions: each hinge group (`RADIATOR_OBJECT_NAMES`) holds `RADIATOR_FOLD_COUNT` fold groups **nested one inside the next** (`radiatorFoldName(side, i)`), each offset along its own local +X (signed by side — `up` toward `+X`, `down` toward `-X` — both in the model's fold spacing and the panel/skeleton mesh placement within a fold, which must agree or the panel ends up facing the wrong way inside its own fold), so `player/radiator.ts` drives the whole chain by writing one `rotation.y` per fold and never recomputes segment positions. The panel's thin axis (its normal) is local Z, perpendicular to both the extend direction (X) and the solar panels' own normal (Y). Stowed (`STOW_TILT`=90°), that normal is exactly ±X — flush with the hull side, matching the panel's stowed footprint; deployed (`RADIATOR_DEPLOY_TILT`, now a near-zero residual so the accordion fold visibly straightens out), the normal swings to ±Z (fore/aft), maximizing cross-section when viewed from the front — the accordion literally unfolds flat rather than settling into a fixed pleat. `RADIATOR_TIP_DISTANCE` is computed here from the same segment length and deploy tilt the model uses, and is the reach the hit radius grows to), magazine belt links (`buildMagazineMesh`: caged 4×8 = 32 visible brass rounds — 1:1 with `MAG_ROUNDS`) and orbital ammo pickups (`buildAmmo`), enemy variants (`buildEnemyShip`/`buildStage0EnemyShip`), shared-geometry tracer bullets (`buildBulletMesh`/`buildPlasmaMesh`), CIWS-motif bottleneck casings (`LatheGeometry` profile: rim + extractor groove + tapered body + shoulder + neck), debris shards, ejected barrels/magazine frames, and the base station (`buildBaseModel`: central hub + 4 radial trusses/docking modules + 2 solar wings + an accent beacon, all primitive-built rather than loaded — the one shape here assembled directly with `THREE.*Geometry` calls at construction time instead of parsed from `src/assets/models/*.json`, the same way debris/barrels are).
- `src/render/scene.ts` — `createGameScene`: canvas → `WebGPURenderer` + `THREE.Scene`, the only place the renderer is created. `EnvironmentScene` itself now lives at `game/celestial/environment-scene.ts` (see above) — everything left under `render/` is THREE builders only.
- `src/render/celestial-grid.ts` — `CelestialGrid`: reference-only equatorial and ecliptic grids (a basis circle, latitude/longitude lines at 30° steps, and a pole marker per plane), each independently toggleable across all three parts (`CelestialGridVisibility`'s six flags — plane/pole/grid × equator/ecliptic). Vertices are built once at construction, fixed points on a unit sphere at `render/stars.ts`'s `STAR_SHELL_RADIUS` (the same camera-following fixed-radius shell the stars use, scaled up further while `overviewMode` so the grid still reads at map zoom); `sync` only toggles visibility and repositions/rescales the whole shell — it never rebuilds geometry. The equatorial basis is the game's ECI basis directly (Y = pole); the ecliptic basis is ECI rotated through `physics/ecliptic.ts`'s exported `Q_ECL_TO_ECI`, so the 23.44° tilt is never hand-written here. All six toggles default to false — nothing from this module draws until something turns them on; the toggle state itself is `Navball.gridVisibility` (see `src/game/navball/` above).
- `src/render/earthcolor.ts` — the Earth surface color (fBm-noise continents, biomes and clouds) as pure functions, **THREE-free on purpose**: `tools/export-earth-texture.mjs` imports it directly through the TypeScript compiler API and is the only consumer, making this file the single source of truth for what the baked texture contains. Nothing under `src/` imports it at runtime — `earth.ts` reads the finished image.
- `src/render/{stars,orbitline,sampled-line,billboard,glow-texture}.ts` — stars as tiny world-space triangles (WebGPU points are 1px; `THREE.Points` size doesn't work); `createSun`/`createMoon` build the sun billboard and moon mesh THREE objects that `game/celestial/{sun-body,planet-body}.ts` place and scale each frame (`SUN_DISTANCE`=4.2e7 / `MOON_VIS_DIST`=4.5e7 m, inside the 6e7 far plane); camera-facing `Billboard` sprites (flashes, plume, RCS puffs) over a shared radial-`glow-texture`. `stars.ts` exports `STAR_SHELL_RADIUS` — the star shell's fixed radius — so `CelestialGrid` can share the exact same camera-following shell radius instead of picking its own.
  - `orbitline.ts`'s `OrbitLine` draws an **analytic ellipse from `Elements`**: vertices are stored relative to whichever body the passed-in `Elements` are centered on, moved per frame only via `line.position` (through `fo`, offset by `Elements.center.state.r` — that body's own ECI position), and regenerated only when osculating elements drift past thresholds (or `force=true` during burns/node editing) — rewriting vertices in ship-relative coords every frame made the ellipse visibly jitter under J2/third-body element wobble. **`sync` takes no center argument at all**: the ellipse and its translation both come off the `Elements`, so a caller cannot draw an ellipse at a body it isn't centered on. `densifyNear` (also center-relative) densifies vertices near a given point, and callers derive it from the same `Attractor` they picked via `strongestAttractor`/`elementsAround` (`attractor.ts`). Line colors: player light gray (`renderOrder=1`), secondary target cyan (`renderOrder=2`), primary target orange (`renderOrder=3` — a rendezvous target's orbit is often nearly coincident with the player's, and transparent draw order alone made it disappear underneath), enemies `COLOR_ENEMY_ORBIT_LINE` (a dim gray, so a target/lead highlight actually stands out), reference lines `renderOrder=0`. The planned trajectory is not an `OrbitLine` — it's `PlanArc`'s `SampledLine`, drawn white at `renderOrder=4`, since a multi-node plan is a chain of arcs rather than one closed ellipse. The `renderOrder` stack is ordered least-to-most likely to need to win a coincident-orbit tie: own orbit first, then whichever target line is more likely to matter (primary over secondary), then the planned line last since it's what the player is actively editing.
  - `sampled-line.ts`'s `SampledLine` is its sibling for **arbitrary sampled point series** — it takes a plain `readonly OrbitState[]`, so predicted arcs and entity `history` both feed it unchanged: `syncGeometry` bakes samples into `Frame`-relative vertices only when the series or frame changes (non-rigid, so the vertices are rewritten in place into the constructor-allocated `MAX_VERTICES` buffer and the drawn length set with `setDrawRange` — see the WebGPU gotcha below), Hermite-subdividing each edge on the way via `orbital-state.ts`'s `hermiteInterpolate` — `toFrameState`'s frame-relative velocities are the tangents, and the chord count is how far the two endpoint tangents turn at `MAX_EDGE_TURN` (5°) per chord. Budgeting by angle rather than a fixed count makes smoothness independent of zoom (the bulge-to-chord ratio is a function of the angle alone) and decouples the sample series' own coarseness from the drawn polyline's. `syncTransform` does the per-frame O(1) work — rigid un-bake rotation via `toInertialQuat` plus the floating-origin translation.
  - Both use `THREE.Line` — **`LineLoop` is unsupported by the WebGPU renderer**; close loops manually.
- `src/types/{three-shims,png-shims}.d.ts` — three.js 0.169 ships no `.d.ts` for `three/webgpu`; minimal `WebGPURenderer` typings (remove once upstream types cover it), plus PNG import typing. Import THREE **only** from `'three/webgpu'` (mixing with `'three'` would duplicate classes at runtime).

### WebGPU renderer gotchas (three.js 0.169)
- `THREE.LineLoop` and `THREE.Points` sizing are not supported; use `THREE.Line` / triangle-based sprites.
- Additive-blended materials need explicit `transparent: true`.
- **Vertex data must be updated in place, never by swapping the geometry or the attribute.** `RenderObject` caches both the geometry and the resolved attribute list when it is first built, so assigning a new `BufferGeometry` to `mesh.geometry` — or a new `BufferAttribute` onto a live geometry — keeps drawing the original vertices. Allocate the `Float32Array` once, write into it, set `attribute.needsUpdate = true`, and vary the drawn length with `geometry.setDrawRange`. Both line classes (`render/orbitline.ts`, `render/sampled-line.ts`) are built this way, which is why their vertex capacity is a fixed constant.
- Headless-Chrome screenshots work with `--headless=new --enable-gpu --enable-unsafe-webgpu --disable-gpu-sandbox --no-sandbox` (flaky; retry a few times).

Not yet implemented: enemy *maneuvering* AI (enemies shoot back — `Enemy.behave` burst-fires lead-aimed plasma — but never thrust), solar-storm/combat auroras, ECS, full N-body cislunar phase. See `memos/mikanixonable/dev.md` for design direction.

## Project concept (from memos/mikanixonable/dev.md)

An orbital-mechanics shooting game, intended as a web game, set in the Earth-Moon system (current build: LEO only):

- Gameplay centers on realistic orbital maneuvers and physically accurate ballistic calculations, low-poly but visually appealing depictions of Earth's atmosphere, spacecraft, and spacecraft destruction.
- Orbital calculations should account for Sun-Earth-Moon three-body dynamics, atmospheric drag, and tidal forces. Reference concepts to consider: Sun-Earth and Earth-Moon Lagrange points, sun-synchronous recurrent orbits, halo orbits, low-energy transfers and ballistic capture, double lunar swingbys, and gradual altitude-raising approach maneuvers (like the Kounotori HTV's ISS approach).
- Aesthetic goals: Earth auroras, auroras from solar storms, auroras from charged particles generated by combat, shadows on Earth's evening clouds, and the Dzhanibekov effect on destroyed debris.

## Controls (current build)

**Translation is body-frame, not orbital-frame** (`PlayerThrottle.buildThrustAccel` builds a direction in body axes and rotates it by `att.q`): W or Ctrl / S or Shift = nose-forward/aft (+Z/−Z), A/D = lateral (+X/−X), Q/E = vertical (+Y/−Y). All six fire at the same selected magnitude `THROTTLE_LEVELS[throttleIdx]` (3 stages — [1]/[2]/[3] — no "cutoff" stage; thrust exists only while a direction key is held). `input.ts` calls preventDefault on Ctrl+W/A/S/D/R so browser shortcuts don't fire while Ctrl is held as forward thrust (Ctrl+W/T/N and Ctrl+digit are browser-reserved and can't be blocked).

Rotation: I/K = pitch, **L/J = yaw**, **O/U = roll** (signs per `PlayerThrottle.updateTorque`'s `inX`/`inY`/`inZ`; `RcsEffects.sync` lights the nozzles whose own torque points the same way as that commanded torque, so the visible thrusters and the key held can't disagree). T = RCS rotation damping toggle, **F = prograde attitude reset** (one-shot: only sets the hold ON), **C = prograde-hold autopilot toggle** (PD controller torquing the nose to the velocity vector; any manual rotation key cancels it), **V = fine-attitude toggle**. **`Digit9`/`Digit0`** (the top-row 9/0) toggle the `up`(right/+X)/`down`(left/-X) radiator panels' deploy state (`Player.handleEdgePress` calls `radiator.toggle('up'|'down')` directly — the same panels the status-window buttons drive) — distinct from the numeric-keypad `Numpad0`/`Numpad1` below, which roll the camera instead.

G = toggle whether the chase camera's reference frame follows ship attitude vs. the orbital frame (see below). Z (hold) = gunsight zoom. Space = fire. **Right click on an enemy** (within the same `CLICK_MOVE_THRESHOLD` click-vs-drag test the left button uses) **opens a context menu offering "set/clear target" and "set/clear secondary target"** (`Targeter.updateCombatTargeting`) — a miss instead opens a menu offering "open settings menu" (the same pause menu `[Esc]` opens). Target selection has no automatic re-pick: whichever `Enemy` was last set as target/secondary stays until explicitly cleared or replaced, even off-screen or behind the camera. The secondary target only affects what's drawn (cyan orbit line/marker/enemy-list row) — board marks, ◇/◆ bearing markers and LEAD all read the primary target only. **left drag**, **right drag**, or **arrow keys** = camera yaw/pitch, **`Numpad0`/`Numpad1`** (alt: `/`/`_`) = camera roll (around the camera's own current view axis — `ChaseCamera` in combat view, `OverviewCamera` on the map, where it rolls the map's up vector), wheel or two-finger pinch = zoom distance, **middle drag** or **`@`/`:`/`;`/`]`** (up/down/left/right) = pan — the keyboard pan keys synthesize `panDx`/`panDy` at `C.CAM_KEY_PAN_RATE` px/s in `CameraSystem.update` so they drive the exact same `ChaseCamera`/`OverviewCamera` pan code path as the middle-drag, a keyboard alternative for laptops without a usable middle-click drag. `,` / `.` = time warp (thrust, guns, enemy fire and contact physics are all gated above ×`MAX_PHYS_SIM_SPEED` = 4 via `SimSpeedManager.can*`). M = orbit-planning map, N = auto-warp to the next node, X = delete selected node / discard the whole plan, H = help, R = manual reload (after the game ends it instead re-launches **the same stage** — `Stage.restart` navigates to `?stage=<id>`, since a plain reload would drop you back on the stage-select screen whenever you got there without a `?stage=` param).

On the map, right-clicking a celestial label, a living ship, a base, an ammo pickup, a periapsis/apoapsis icon, or a relative AN/DN icon opens a **property window** for that object (`hud/property-window.ts`'s `PropertyWindow`, opened/owned by `MapPicker` — see `map-picker.ts` above): a title/subtitle, a live-updating property block (armor/temp/power/ammo for a self-flown ship; distance/closing speed/relative speed/orbital elements/relative inclination for an enemy; money/docked-ship count/distance/orbital elements for a base; distance/orbital elements for an ammo pickup; display name/kind/μ/radius/distance/orbital elements for a celestial body; altitude/time-to-crossing for an apsis or relative AN/DN icon), and the same action items `MapPicker.itemsFor` always built (by `MapPickable.kind`): every kind offers "move focus" (`overviewCamera.focus`); a ship additionally offers "set/clear navigation target" (`NavTarget.toggleTarget` — independent of `Targeter`'s combat target, see the Architecture section); an apsis or relative-AN/DN icon additionally offers "add node here" (`PlanEditor.addNodeAt`, at that icon's crossing time) and, for relative AN/DN only, "warp here" (`SimSpeedManager.startAutoWarpTo`). In creative mode only, a self-flown ship/enemy/ammo pickup/base additionally offers "duplicate" — opens `ShipPlacerPanel` pre-filled with that object's current orbital elements (基準天体/近地点+遠地点高度/傾斜角/Ω/ω/ν all copied — ν included, so the duplicate starts exactly where the original is; nothing offsets it), object type fixed to match, ready to place a lightly-tweaked copy.

A property window can be dragged by its header, and its 📌 button **clips** it — an unclipped window is a *temporary* one: at most one exists at a time (opening or right-clicking a second object closes the previous temporary window), and it closes on an outside click, on picking any action item, or on leaving the map view. A clipped window survives all of those, so several can be pinned open side by side to compare objects; only its own ✕ button, deleting the object, or the object itself vanishing (destroyed/picked up/removed) closes it. Right-clicking an object that already has an open window (of either kind) just moves that window to the click position and brings it to front, rather than opening a second one. Right-clicking empty space still opens a plain context menu (`ContextMenu`, not a property window — there's no object to show properties of) offering "show orbit object window" — a top-right list of the same candidate set, click to focus (`object-list-panel.ts`'s `ObjectListPanel`) — and "open settings menu" (`Game.openSettingsMenu`, forwarding to `SettingsPanel.toggle(true)` — the same pause menu `[Esc]` opens) — in any mode; creative mode's menu additionally offers "place object" there (`ShipPlacerPanel`, below).

Esc (or the ⚙ gear) = pause menu, owned by `hud/settings-panel.ts`: `SettingsPanel.toggle` fires `onSettingsOpenChange`, which `main.ts` syncs to `Game.pause()`/`Game.resume()` (so every open/close path — Esc, gear click, [閉じる] — pauses/resumes), plus a BGM toggle and a "quit to title" button (`onQuitToTitle` → `location.assign(location.pathname)`, dropping the `?stage=` param). While paused `Game.update` returns early, so HP auto-regen (`HP_REGEN_RATE` = 1 HP/s, inside `Player.behave`) can't be farmed from the menu. `handleInput` still runs before the pause check, so each key's owner decides for itself what a paused frame means — `ViewManager.update` leaves `[M]` unconsumed while a dock is open, and `Docking.handleInput` takes `[Esc]` before `SettingsPanel` sees it so closing a dock never also opens the pause menu.

Firing implies fine-attitude authority (`FINE_ATTITUDE_SCALE` = 0.5): `Player.updateTorque` passes `fineAttitude || fire.isFiring`, so releasing the trigger restores full authority with no edge-tracking state.

### Creative mode

The title screen (`launch-select.ts`) opens on a ステージモード/クリエイティブモード tab pair; picking クリエイティブ or loading `?mode=creative` starts `CreativeStage` with `ViewManager`'s initial view set to `'map'` (the map is where placement happens, so creative mode opens on it rather than a combat view with nothing yet to fly). `[M]` is disabled — `ViewManager.handleInput`'s `canToggleView` argument, `Game.handleInput`'s `this.player.alive` — until at least one placed ship is active, since the combat view has no meaning without a ship to fly. The マップモード-only 艦艇配置 panel (`creative/ship-placer-panel.ts`) places ships by orbital elements or by a Lagrange-point halo/Lissajous orbit (see `src/physics/halo.ts` above for why the latter drifts once the simulation runs); a placed ship's right-click menu (`kind: 'player'` in `MapPicker.itemsFor`) offers 操作対象にする (`Game.setActivePlayer`), 軌道計画への自動追従 ON/OFF (`CreativeStage`'s per-frame plan-following, see `player.ts`'s `followPlan` above), フォーカスを移動, 航法ターゲットに設定/解除 (`NavTarget`, same `navTargetItems` helper the `'body'`/`'ship'` kinds use), and 削除 — the first and last of these are simply absent from the menu for the currently-active ship (deleting it would leave `player` dangling, and it's already the one activation would select).

The orbital direction markers (`player/player-markers.ts`) deliberately carry no key hints in their labels: combat-view translation is body-frame, so none of those six directions has a key. The keys that *do* mean prograde/normal/radial are the map-mode Δv edit keys, and the direction markers are hidden there.

Chase camera reference frame (`camFollowAttitude` on `ChaseCamera`, default **on**, toggled via `[G]`, which `CameraSystem.update` forwards through `CombatCameraSystem.toggleFollowAttitude`): the third-person camera's orientation is stored as a single quaternion offset (`rot`) from a reference frame, but *which* frame is configurable. ON (default) references the ship's own attitude (`player.att.q`), so rotating the ship with I/K/J/L/U/O visibly swings the whole camera (including its roll) right along with it, RCS-linked. OFF references ECI directly, so the camera holds a fixed orientation in inertial space regardless of how the ship rotates, until dragged. Toggling reinterprets `rot` through the ship's current attitude so the view doesn't jump. While the ship is destroyed, ON stops folding in the ship's attitude (which would otherwise be its post-destruction tumble) and holds the last orientation instead. `CombatCameraSystem` itself only decides between `ChaseCamera` and `GunsightCamera` (via `zoomActive`) and animates the FOV each holds in its own `view`.

Ammo system: guns fire alternately from the two front bores and consume magazine rounds (`MAG_ROUNDS`=32/mag, `INITIAL_MAGS`=3 linked at start, `MAGS_PER_BARREL`=3 consumed before a barrel-swap reload — doubling the per-mag capacity from an original 16-round design let the visible chain be roughly half as long while carrying comparable total ammo). The belt of unused mags hangs off the ship's starboard (+X) side as child meshes of `player.obj`, and the belt slides continuously into the hull as rounds are fired (`beltFeed` = 1 − rounds/`MAG_ROUNDS` offsets the anchor by up to one pitch; on mag consumption the feed wraps 1→0 exactly when the link count drops, so the motion reads as seamless). The head link sits half-inside the hull. `BeltPhysics.update` (in `player/belt-physics.ts`) simulates the belt's sag as an actual physics chain, not a canned animation: link joints are point masses (`beltPos`/`beltPrevPos`, Verlet-integrated in the ship's body frame) connected by rigid-rod distance constraints (position-based dynamics, 6 relaxation iterations per frame) to `MAG_BELT_PITCH`. Since the ship is in free fall, ordinary gravity can't sag anything (equivalence principle — belt and hull fall together); the only real driver is the fictitious force felt in the ship's non-inertial (accelerating/rotating) frame: `-a_thrust - α×r - ω×(ω×r) - 2ω×v` (translational inertia, Euler, centrifugal, Coriolis), built from `thrustAccelVec` (world-frame thrust accel, rotated into body frame, passed in each call from `Player.behave` via `Belt.update`) and `player.att.w` (with `α` estimated by finite-differencing `w` against `prevBodyW`, both tracked inside `BeltPhysics`). When the player isn't thrusting or rotating, the chain just hangs straight — no ambient wobble is faked in.

Each link's *orientation* is derived separately from its position, via parallel transport: `qBend = qDelta * qPrev` where `qDelta` is the minimal (zero-twist) rotation taking the previous link's local +X to this link's tangent — so bending (the chain folding link-to-link) is unconstrained by construction, matching a real ammo belt's easy up/down/left/right flex. Roll (twist about the link's own +X, the one DOF parallel transport leaves undefined) is instead tracked explicitly per link in `beltTwist[]`, driven by the ship's own roll rate (`player.att.w.z * MAG_CHAIN_ROLL_GAIN`) at link 0 and propagated down the chain with a one-frame lag (`prevTwist`) and exponential smoothing (`MAG_CHAIN_ROLL_RATE`), clamped every frame to `±MAG_CHAIN_MAX_ROLL_DEG` — so however it's driven, twist can never exceed that bound. The final per-link quaternion is `qBend * qTwist(local +X)`.

`CollisionPhysics.resolve(dt, ...)` (in `game/simulation/collision.ts`; rigid-sphere impulse resolution for casings/enemies/pickups/belt) is called once per `Game.update` call — not per substep — and only while `simSpeedManager.canResolvePhysicalCollisions`, using the real (unwarped) `dt` so it stays consistent with the belt's own real-time cadence; at higher warp it's skipped entirely (substeps up to 20s each make rigid-body contact resolution meaningless there, and it's O(n²) over every casing). It uses `PLAYER_HULL_RADIUS` (real hull size, 2.6m) for contact, deliberately smaller than `PLAYER_RADIUS` (5m, used for bullet self-hit detection only) — reusing the bullet-hit radius here would fling freshly-ejected casings (spawned ~2.9m from the hull) outward on the same frame. A casing/hull impact directly triggers `Sfx.clank()` via the `onPlayerCasingImpact` callback, rather than polling distances every frame.

When mags run low (`LOGISTICS_LOW_MAGS`), resupply pickups spawn phase-shifted 1.25–2.5 km ahead on the player's own orbit (`stage-utils/logistics.ts`'s `Logistics.spawnForPlayer`; ▣ AMMO marker, absorb within `AMMO_PICKUP_RADIUS`). Casings use a CIWS-style bottleneck profile (rim/extractor groove/tapered body/shoulder/neck via `LatheGeometry`) with **low** ejection speed but widely varying per-casing spin, on an asymmetric inertia tensor so the Dzhanibekov effect shows on tumbling casings the same way it does on debris. Spin-up SFX is filtered-noise friction (no oscillator). Enemy ships are modeled at `ENEMY_SCALE` (20×) via `obj.scale.setScalar(...)` with `ENEMY_RADIUS` (180 m) matching for hit detection; their destruction VFX (`spawnFlash` sizes, `scatterFragments` size range) scale by the same factor so the explosion reads proportionate to the larger hull.

Mouse buttons are swapped from the naive default: **left button drags the camera; a left click that moves less than `CLICK_MOVE_THRESHOLD` (6px) is instead queued as a click** (used to place maneuver nodes in map mode) — see `Input.clicks()`. **Right button also drags the camera** (feeding the same `dx`/`dy` as the left drag — a two-finger trackpad drag, since right-click has no natural trackpad equivalent), and a right click within `CLICK_MOVE_THRESHOLD` (`Input.pushIfClick`, shared across left/middle/right) instead opens a target/context menu. Firing is Space-only now — right click no longer fires. This lets map-mode node placement and camera dragging share the left button, and camera dragging and menu-opening share the right button, without a modifier key.

Map mode ([M]) does not freeze physics: `Simulator.stepSimulation` runs every frame while `activeStage.isPlaying && !paused`, and ship control (thrust/fire/manual attitude) is gated on `editor.editMode` since W/S/A/D/Q/E are repurposed for Δv editing there (in the planner they mean prograde/normal/radial, not body axes) — so time warp keeps working and the player can wait for a transfer window while planning. Only `editor.updateEditing` and the pointer dispatch are layered on top of `update`; the three map-mode panels (MAP VIEW / PREDICT / TRAJECTORY) show and refresh themselves from their owners' `sync`. The map camera's drag yaw sign is intentionally opposite the combat chase camera's convention (`+=` vs `-=` on `mouse.dx`) so panning left/right reads the same in both views.
