# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Current state

A playable LEO (low Earth orbit) shooting game: TypeScript + Webpack + npm, Three.js `WebGPURenderer` (via the `three/webgpu` entry point). Real-scale/real-time Earth orbit, KSP-style frame-based RCS translation (orbital / target reference frames), manual rotation with RCS damping, time warp, lead-marker gunnery, shell casings and destruction debris on accurate orbital physics, win on destroying all 5 enemies, lose on atmospheric reentry (drag decay → adiabatic-heating overheat or dynamic-pressure breakup). Also: Earth-shadow lighting, target-board bullet-pass markers, an orbit-planning map mode ([M]: Earth-centered camera, click the player orbit to place a maneuver node, W/S/A/D/Q/E adjust Δv, [N] auto-warps to the node, BURN guide shows remaining Δv until the actual orbit matches the planned elements within tolerance), and four stages (stage 2 = Molniya-orbit enemies, unlocked once stage 1 has been cleared — tracked via `unlock-manager.ts`'s `UnlockManager`, which persists per-stage clear counts to localStorage and toasts newly-unlocked stages; stage 0 = near-combat training scoreattack, stage 00 = infinite survival, both always unlocked; `?stage=` URL param skips the select screen). The renderer draws `cameraSystem.activeCamera` — combat chase cam (near 2 / far 6e7) or the map camera (near 1e4 / far `MAP_CAMERA_FAR` = 1.5e10); stars/sun/moon billboards follow the active camera position so the map zoom-out doesn't exit the star shell.

`dev.md` is explicitly marked as human-authored only ("この文書は人間のみが記入できる") — do not edit it. Read it for project context, but leave modifications to the user.

### Naming: render / update / build / sync (no `draw`)

Per-frame function names must reflect what they actually do, consistently across the codebase:

- **`render`** — reserved for functions that literally call the three.js renderer's `render(scene, camera)`. A function that only constructs or mutates scene state is not a "render" function even if it runs during the render pass (e.g. `Player.syncTransformAtOrigin`/`syncThrustEffects`, `EnvironmentScene.sync`, `PipRenderer.renderFrame`).
- **`update`** — advances or mutates logical/simulation data (not three.js mesh state directly).
- **`build`** — registers new meshes/objects into the scene (construction, not per-frame).
- **`sync`** — matches the transform/appearance of already-registered meshes (or HUD DOM elements) to logical data that was already computed elsewhere. Prefer plain `sync*` names; don't tack `Render` onto a sync method name (e.g. `syncCamera`, not `syncRenderCamera`) — it blurs the render/sync boundary this rule exists to keep clear.
- **`draw`** is never used — rename on sight.

When a per-frame flow is split into sub-functions (as in `game.ts`'s `sync()`/`update()`), keep the split's naming and responsibility boundaries consistent with the above — a class like `PipRenderer` should only contain actual render-pass code, not unrelated logical bookkeeping (state that merely happens to be read at render time still belongs with the system that owns that state, e.g. `Player`).

### Commands
- `npm run dev` — start webpack-dev-server at http://localhost:8080
- `npm run build` — production build to `dist/`
- `npm run typecheck` — `tsc --noEmit`
- `npm run test:physics` — regression tests for `src/physics/*.ts` (pure functions, no DOM/THREE deps): compiles `tests/physics/*.test.ts` + the physics modules to CommonJS via `tsconfig.test.json` (outDir `tests/dist`, gitignored) and runs them in node with `node:assert/strict` (no extra devDependency). Covers vec3 smoke tests, orbital.ts Kepler round trips (`stateFromElements`⇄`elementsFromState`, `trueAnomalyAt`/`positionOnOrbit`/`velocityOnOrbit`), `stepOrbitRK4` one-period drift, `j2Accel` RAAN regression rate, attitude.ts kinetic-energy conservation + quaternion norm, atmosphere.ts density-table boundary/monotonicity, and ephemeris.ts sun/moon distance-and-period sanity. Where no clean theoretical value exists (RK4 drift, J2 rate, table-boundary continuity), the test pins the *measured* current behavior with a loose margin rather than an idealized bound — run this before/after any change under `src/physics/`.

There is no other automated test suite wired into npm beyond `test:physics`.

### Architecture

Simulation state lives in ECI coordinates (Y axis = north pole), SI units (m, m/s), as plain `{x,y,z}` data. Rendering uses a **floating origin**: the player ship is always at world (0,0,0) and everything else (including the Earth mesh at `-playerR`) is positioned relative to it each frame, so f32 GPU precision never sees absolute LEO magnitudes. Camera: near=2m, far=6e7m — no logarithmic depth needed (see comment in `scene.ts`).

Physics runs on the main thread (per-entity central-gravity two-body integration is cheap); the N-body worker is **currently unused**, kept for the future cislunar (Sun-Earth-Moon) phase.

`src/game/` is an orchestrator (`game.ts`) plus subfolders grouped by concern: `player/` (player ship state), `orbit-entity/` (the shared entity base classes and their passive simulation), `camera/`, `map-mode/`, `plan/` (maneuver planning, independent of map-mode), and `stages/` (per-stage behavior). Cross-module data that doesn't fit a single class is still passed as a `*Ctx` snapshot object built fresh each call (`game.ts`'s `stageCtx()`/`combatCtx()`/`fireCtx()`/`hitCtx()`/`enemyAiCtx()`/`markerCtx()`/`collisionCtx()`/`simulatorCtx()`/`planCtx()`); `refactor_plan.md` tracks the ongoing work to shrink this ctx-injection pattern.

- `src/main.ts` — entry point: WebGPU scene init (`initScene`, with a `showLoading` overlay while the WebGPU pipeline compiles), the stage-select screen (`selectStage`, built from `STAGE_DEFINITIONS`, gated per-stage by `UnlockManager.isUnlocked`; `?stage=` skips it via `resolveForcedStageFromQuery`), an error overlay fallback, and the rAF loop (`startAnimationLoop`) driving `Game.update`/`Game.render`.
- `src/game/game.ts` — orchestrator: owns `simTime`/`phase`/`paused` and the top-level `update`/`sync` split (input → `Player.behave` → `Simulator.integrateSimulation` → post-simulation hazard/collision checks → HUD/camera sync → `PipRenderer.renderFrame`). Doesn't implement gameplay systems itself — it constructs and drives `CameraSystem`, `Simulator`, `HitSystem`, `CollisionPhysics`, `EffectsSystem`, `Targeter`, `PlanSystem`, `Plan`/`PlanGuide`, `SimSpeedManager`, `EphemerisSystem`, `MarkersSystem`, `UnlockManager`, and the active `Stage`, feeding each a small `*Ctx` snapshot built per call. `handleEdgePress` maps the non-movement keys (`[G]`/`[,]`/`[.]`/`[M]`/`[N]`/`[X]`/`[H]`/`[Esc]`/`[R]`) to the relevant subsystem. Many public fields (`cameraSystem`/`player`/`activeStage`/`simulator`/`targeter`/...) exist because `hud/panel.ts`'s `HudPanels.update(game, ...)` reads the whole `Game` instance directly rather than a narrow ctx.
- `src/game/const.ts` — all gameplay tuning constants (thrust, sim speed levels, fire rate, hit radii, ammo/belt geometry, stage tuning...).

`src/game/player/` — the player ship, split by concern (all owned and composed by `Player`, which exposes read-only getters for `game.ts`/HUD):
- `player.ts` — `Player extends Ship`: initial LEO placement (`makeInitialState`/`progradeAttitude`), the top-level `behave`/`update`/`sync` per-frame entry points, damage/loss handling (`attacked`, `checkLoss` — hull heat/dynamic-pressure/reentry-altitude thresholds via `thermal`), and composes `throttle`/`fire`/`belt`/`thermal`/`thrustEffects`/`rcsEffects`.
- `player-throttle.ts` — `PlayerThrottle`: translation input → thrust accel (`buildThrustAccel`, all 6 RCS directions), manual rotation + RCS damping, and the `[C]` prograde-hold autopilot (`autoAlignTorque`): builds a desired attitude quaternion (nose = velocity direction, roll reference = radial-out, re-orthogonalized so it's valid even for eccentric orbits where r⟂v doesn't hold exactly — see `physics/attitude.ts`'s `qFromForwardUp`), converts the quaternion error to a body-frame axis-angle, and applies a PD torque (`PROGRADE_HOLD_KP`/`_KD`).
- `player-fire.ts` — `PlayerFire`: gun state (mag/round/barrel counters, reload timer), `fireGun` (bullet spawn, recoil, casing eject, muzzle flash, `ScoreCounter.recordShot`), and `dropBarrel`/`spawnEjectedMagazineFrame` for reload debris. Driven via a `FireCtx` snapshot (`game.ts`'s `fireCtx()`).
- `belt.ts` / `belt-physics.ts` — the ammo belt display split from its physics: `belt-physics.ts`'s `BeltPhysics` is a pure Vec3/Quat Verlet-chain solver (position-based dynamics, no THREE/mesh dependency) for the belt's sag/twist under the ship's thrust+spin pseudo-forces; `belt.ts`'s `Belt` owns the link meshes and derives each link's transform from `BeltPhysics`'s solved state via parallel transport.
- `thermal.ts` — `ThermalSystem`: hull heating/dynamic-pressure (Sutton–Graves + Stefan-Boltzmann, `updateThermal`) and the altitude-descent-warning EMA (`updateAltitudeAlarm`); returns a `ThermalLimit` verdict — the actual destruction (`alive = false` + effects) happens in `Player.checkLoss`.
- `thrust-effects.ts` / `rcs-effects.ts` — billboard VFX for the main engine plume and the 4 RCS thruster puffs, positioned from `render/ships.ts`'s `MUZZLE_OFFSETS`/`RCS_BLOCK_OFFSETS`.

`src/game/orbit-entity/` — the entity base classes and their passive (non-AI, non-input) simulation:
- `entities.ts` — `OrbitEntity` (base: state/attitude/mesh, `syncTransform`, default reentry-altitude `checkLoss`), `Ship` (adds name/hp/radius), `Ammo`, `DebrisPiece` (fragment/barrel/magazineFrame/casing variants), `BeltSection` (a per-link collision proxy the belt physics exchanges with `collision.ts`).
- `bullet.ts` — `Bullet extends OrbitEntity`: player/enemy bullets and enemy plasma bolts (`Shooter`/`BulletType`), its own lifetime check, and a velocity-facing (not attitude-facing) transform sync.
- `enemy.ts` — `Enemy extends Ship`: enemy AI (`behave` — burst-fire plasma at the player using `physics/intercept.ts`'s `solveLeadTime`), damage/destruction (`attacked`, `checkLoss`), and its own `OrbitLine`.
- `hit.ts` — `HitSystem`: segment-vs-sphere bullet collision (tunneling-proof, `checkBulletHits`) and target-board bullet-pass marker recording (`checkBoardCrossings`). Driven via a `HitCtx` snapshot.
- `simulator.ts` — `Simulator`: owns the `enemies`/`bullets`/`casings`/`debris`/`ammos` arrays (capped, oldest evicted on overflow), the environment-acceleration closures (`envShip`/`envBullet`/`envSmall`, built by `makeEnvAccel` over `physics/envaccel.ts`'s `envAccelInto`), the substepped RK4 integration (`integrateSimulation`, higher warp → more substeps, max 20s each), and lifetime cleanup (`cleanup`/`prune`). AI/input/spawn decisions live in `game.ts`/`stages/`/`Enemy.behave`, which add entities back in via `addXxx`.
- `collision.ts` — `CollisionPhysics`: rigid-sphere impulse resolution for casings/enemies/pickups/belt links (`resolve`, called once per `Game.update` — not per substep — and only below `MAX_PHYS_SIM_SPEED`).

- `src/physics/orbital.ts` — central-gravity RK4 for one entity with optional extra-acceleration callback (thrust, evaluated per RK4 stage), state→orbital elements, ellipse sampling for orbit lines, `j2Accel` (Earth oblateness, Y = polar axis; verified ≈ −5°/day RAAN regression at 420 km/51.6°), `thirdBodyAccel` (differential tidal accel), and Kepler helpers for maneuver planning (`trueAnomalyAt`, `tofBetween`, `positionOnOrbit`/`velocityOnOrbit`, `stateFromElements` — all round-trip-verified to machine precision). Pure functions.
- `src/physics/ephemeris.ts` — circular-orbit Sun/Moon ephemerides in game ECI (Y = north): Sun on the ecliptic (23.44° obliquity), Moon inclined 5.145° to the ecliptic with 18.61-year regressing node (equatorial inclination sweeps 18.3–28.6°, which drives real inclination perturbation of LEO orbits). All entities integrate drag + J2 + lunisolar third-body via `Simulator.makeEnvAccel` in `orbit-entity/simulator.ts`. Pure functions plus the `Ephemeris` class — holds the per-game `sunPhase0`/`moonPhase0` and the sampled current `sunPos`/`moonPos`/`sunDir` (`update(simTime)`); its `*At(t)` methods bind the phases so consumers take the object instead of threading raw phases. THREE-independent, so `predict.ts` and `envaccel.ts` consume it directly. The single `Ephemeris` **instance is owned by `render/environment-scene.ts`'s `EnvironmentScene`** (it does the initial `update(0)` and reads `sunDir` for lighting / the map-mode geo/moon reference lines); `Simulator` gets a reference (via `game.ts` passing `environment.ephemeris`) and drives the per-substep `update(simTime)` during integration, and `planSystem`/`map-markers` read it through `environment.ephemeris`.
- `src/physics/envaccel.ts` — `envAccelInto`: the single composition point for the environment acceleration (drag + J2 + lunisolar third-body; `bcInv = 0` skips drag), shared by `orbit-entity/simulator.ts`'s `makeEnvAccel` (drag on) and `predict.ts`'s `envAccel` (drag off, intentional — see comment there); also exports `airspeed`/`EARTH_OMEGA` (co-rotating atmosphere). Pure functions.
- `src/physics/attitude.ts` — rigid-body attitude: quaternion + body-frame ω via Euler's equations. ω integrated with RK4 + kinetic-energy projection (naive explicit integration diverges — this is what makes the Dzhanibekov effect on debris stable long-term). `qFromForwardUp` (nose +Z / up +Y basis → quaternion, re-orthogonalizing, null at the fwd∥up singularity) is the shared attitude-basis builder used by `player/player.ts` (`progradeAttitude`), `player/player-throttle.ts` (`autoAlignTorque`), and `stages/spawner/enemy-generator.ts` (`generateApproachingEnemy`). Pure functions.
- `src/physics/vec3.ts` — plain-object Vec3 math helpers, including the shared random helpers `randSym`/`randVec`/`randPerp`.
- `src/physics/nbody/{bodies,integrator,physics.worker}.ts` — original N-body RK4 worker stack, unused by the LEO game; isolated in its own directory (with a `README.md` explaining why) and retained for the cislunar phase.
- `src/render/earth.ts` — realistic-style Earth: high-res indexed `SphereGeometry` (512×384) with smooth per-vertex colors from deterministic 3D fBm noise (continuous smoothstep-blended biomes, no facet jitter), clouds **baked into vertex colors** (a separate cloud shell z-fights with the surface near the horizon at 24-bit depth), baked cloud shadows (offset eastward in the earth-fixed frame — an approximation that doesn't track the sun), stacked additively-blended **Lambert-lit** shells for continuous atmosphere density with a twilight gradient across the terminator — 16 FrontSide + 8 BackSide rim shells, quadratically spaced in altitude with exponentially decaying opacity so no discrete bands are visible; all Lambert (a Basic rim shell stays bright on the night side and reads as a band); max shell ≤ 340 km so the camera stays outside them at normal flight altitude — and wavy aurora curtains (vertex-color fade, additive; animated via `Earth.tick`) fixed to the spin group at ±67° latitude.
- `src/render/ships.ts` — primitive-built low-poly meshes: player ship (nose = body +Z; stubby box hull, 4 aft engines, small solar paddles, two vertical gun bores on the front face — `MUZZLE_OFFSETS` and `RCS_BLOCK_OFFSETS` are exported so `player/player-fire.ts`/`player/rcs-effects.ts` fire/eject/puff from the exact modeled positions), magazine belt links (`buildMagazineMesh`: caged 4×8 = 32 visible brass rounds — 1:1 with `MAG_ROUNDS` — dims tied to `MAG_THICKNESS` = ½ hull height) and orbital ammo pickups (`buildMagPickup`), enemy variants, shared-geometry tracer bullets, CIWS-motif bottleneck casings (`LatheGeometry` profile: rim + extractor groove + tapered body + shoulder + neck), debris shards, billboard flash.
- `src/render/{stars,orbitline}.ts` — stars as tiny world-space triangles (WebGPU points are 1px; `THREE.Points` size doesn't work), sun billboard and moon mesh — both placed along their true ephemeris directions each frame at compressed display distances (4.2e7 / 4.5e7 m, inside the 6e7 far plane) with the moon's angular size derived from its real distance, so lunar phases come free from the directional sun light; orbit ellipse lines (`THREE.Line` — **`LineLoop` is unsupported by the WebGPU renderer**, close the loop manually). OrbitLine vertices are **Earth-centered ECI**, moved per frame only via `line.position = -origin`; geometry regenerates only when osculating elements drift past thresholds (or `force=true` during burns/node editing) — rewriting vertices in ship-relative coords every frame made the ellipse visibly jitter under J2/third-body element wobble. The target's orbit line is drawn gold at `renderOrder=2` (above the player's cyan line at `renderOrder=1`) — a rendezvous target's orbit is often nearly coincident with the player's, and relying on transparent-object draw order alone made it disappear underneath.
- `src/types/three-shims.d.ts` — three.js 0.169 ships no `.d.ts` for `three/webgpu`; minimal `WebGPURenderer` typings. Remove once upstream types cover it. Import THREE **only** from `'three/webgpu'` (mixing with `'three'` would duplicate classes at runtime).

### WebGPU renderer gotchas (three.js 0.169)
- `THREE.LineLoop` and `THREE.Points` sizing are not supported; use `THREE.Line` / triangle-based sprites.
- Additive-blended materials need explicit `transparent: true`.
- Headless-Chrome screenshots work with `--headless=new --enable-gpu --enable-unsafe-webgpu --disable-gpu-sandbox --no-sandbox` (flaky; retry a few times).

Not yet implemented: enemy AI (targets are passive), solar-storm/combat auroras, ECS, full N-body cislunar phase. See `dev.md` for design direction.

## Project concept (from dev.md)

An orbital-mechanics shooting game, intended as a web game, set in the Earth-Moon system (current build: LEO only):

- Gameplay centers on realistic orbital maneuvers and physically accurate ballistic calculations, low-poly but visually appealing depictions of Earth's atmosphere, spacecraft, and spacecraft destruction.
- Orbital calculations should account for Sun-Earth-Moon three-body dynamics, atmospheric drag, and tidal forces. Reference concepts to consider: Sun-Earth and Earth-Moon Lagrange points, sun-synchronous recurrent orbits, halo orbits, low-energy transfers and ballistic capture, double lunar swingbys, and gradual altitude-raising approach maneuvers (like the Kounotori HTV's ISS approach).
- Aesthetic goals: Earth auroras, auroras from solar storms, auroras from charged particles generated by combat, shadows on Earth's evening clouds, and the Dzhanibekov effect on destroyed debris.

## Controls (current build)

W/S (or Ctrl/Shift) = prograde/retrograde, A/D = normal±. Keyboard radial translation was dropped: Q now toggles RCS rotation damping (alias of T) and E engages the prograde-hold autopilot one-shot ("reset attitude to prograde"; unlike C's toggle it only sets it ON) — both gated off in map mode where planner Δv editing still uses W/S/A/D/Q/E. Radial translation survives only on the touch pad via virtual key codes `VirtUp`/`VirtDown` (touch.ts) read by `buildThrustAccel`. `input.ts` calls preventDefault on Ctrl+W/A/S/D/R so browser shortcuts don't fire while Ctrl is held as forward thrust (Ctrl+W/T/N and Ctrl+digit are browser-reserved and can't be blocked). I/K/J/L/U/O = pitch/yaw/roll, T = RCS rotation damping, C = prograde-hold autopilot (PD controller torquing nose to velocity vector; any manual rotation key cancels it), G = toggle whether the chase camera's reference frame follows ship attitude vs. the orbital frame (see below), Tab = cycle target, Space / **right click** = fire, **left drag** or **arrow keys** = camera (both drive the same yaw/pitch — arrow keys are a convenience alias, not a separate control scheme), wheel = zoom distance, `,` / `.` = time warp (thrust and guns locked above ×4), H = help, R = manual reload / restart (after game end).

Esc (or the ⚙ gear) = pause menu: the old [P] pause and the settings panel are merged — `hud.toggleSettings` fires `onSettingsOpenChange`, which game.ts syncs to `paused` (so every open/close path — Esc, gear click, [閉じる] — pauses/resumes), plus a "quit to title" button (`onQuitToTitle` → `location.assign(location.pathname)`, dropping the `?stage=` param). HP auto-regen (1 HP/s in `Game.update`) is gated on `!paused` so the menu can't be used to heal.

While firing, a picture-in-picture zoom window renders inside `Game.render` (`pip-renderer.ts`'s `PipRenderer.renderFrame`, gated on `player.isFiring`): the main camera is temporarily re-posed along the ship nose at `ZOOM_FOV`, with `playerShipObj` hidden and muzzle flashes hidden via `EffectsSystem.setMuzzleFlashesVisible` (only `FlashEffect.muzzle === true` flashes — hit sparks and destruction flashes stay visible in the PIP). `MarkersSystem.updatePipOverlay(rect)` is called after the PIP render pass, **before** the camera pose is restored, and projects the current target's ◇ frame and ✛ lead marker into the PIP rect as HUD markers (`pip-tgt`/`pip-lead`, label-less so marker-collision resolution ignores them). Firing auto-enables fine-attitude mode (`FINE_ATTITUDE_SCALE` = 0.5, half of normal RCS authority); the falling edge of `isFiring` (tracked as `Player.prevFiring`, compared in `updateFineAttitudeFromFiring`) clears it. Pausing stops firing (`Player.pause` calls `PlayerFire.stopFiring`), so the PIP closes with it.

Chase camera reference frame (`camFollowAttitude` on `ChaseCamera`, default **on**, toggled via `[G]` → `game.ts`'s `handleEdgePress` calls `cameraSystem.chaseCamera.toggleFollowAttitude()`): the third-person camera's yaw/pitch are always defined relative to a `(fwd, up)` frame, but *which* frame is configurable. `ChaseCamera.update` computes both candidate frames each call — the ship's own attitude (`boreFwd`/`boreUp`, nose +Z / body +Y rotated by `player.att.q`, the same pair that drives the zoom gunsight view) and the orbital frame (`chaseFwd`/`chaseUp`, prograde/radial-out) — and picks between them based on `camFollowAttitude`/`zoomActive`/`player.alive`. ON (default) uses the ship's own attitude, so rotating the ship with I/K/J/L/U/O visibly swings the whole camera (including its roll) right along with it, RCS-linked. OFF uses the orbital frame, which stays independent of ship attitude and only slowly co-rotates with orbital motion.

Ammo system: guns fire alternately from the two front bores and consume magazine rounds (`MAG_ROUNDS`=32/mag, `INITIAL_MAGS`=3 linked at start, `MAGS_PER_BARREL`=3 consumed before a barrel-swap reload — doubling the per-mag capacity from an original 16-round design let the visible chain be roughly half as long while carrying comparable total ammo). The belt of unused mags hangs off the ship's starboard (+X) side as child meshes of `player.obj`, and the belt slides continuously into the hull as rounds are fired (`beltFeed` = 1 − rounds/`MAG_ROUNDS` offsets the anchor by up to one pitch; on mag consumption the feed wraps 1→0 exactly when the link count drops, so the motion reads as seamless). The head link sits half-inside the hull. `BeltPhysics.update` (in `player/belt-physics.ts`) simulates the belt's sag as an actual physics chain, not a canned animation: link joints are point masses (`beltPos`/`beltPrevPos`, Verlet-integrated in the ship's body frame) connected by rigid-rod distance constraints (position-based dynamics, 4 relaxation iterations per frame) to `MAG_BELT_PITCH`. Since the ship is in free fall, ordinary gravity can't sag anything (equivalence principle — belt and hull fall together); the only real driver is the fictitious force felt in the ship's non-inertial (accelerating/rotating) frame: `-a_thrust - α×r - ω×(ω×r) - 2ω×v` (translational inertia, Euler, centrifugal, Coriolis), built from `thrustAccelVec` (world-frame thrust accel, rotated into body frame, passed in each call from `Player.update`) and `player.att.w` (with `α` estimated by finite-differencing `w` against `prevBodyW`, both tracked inside `BeltPhysics`). When the player isn't thrusting or rotating, the chain just hangs straight — no ambient wobble is faked in.

Each link's *orientation* is derived separately from its position, via parallel transport: `qBend = qDelta * qPrev` where `qDelta` is the minimal (zero-twist) rotation taking the previous link's local +X to this link's tangent — so bending (the chain folding link-to-link) is unconstrained by construction, matching a real ammo belt's easy up/down/left/right flex. Roll (twist about the link's own +X, the one DOF parallel transport leaves undefined) is instead tracked explicitly per link in `beltTwist[]`, driven by the ship's own roll rate (`player.att.w.z * MAG_CHAIN_ROLL_GAIN`) at link 0 and propagated down the chain with a one-frame lag (`prevTwist`) and exponential smoothing (`MAG_CHAIN_ROLL_RATE`), clamped every frame to `±MAG_CHAIN_MAX_ROLL_DEG` — so however it's driven, twist can never exceed that bound. The final per-link quaternion is `qBend * qTwist(local +X)`.

`CollisionPhysics.resolve(dt, ...)` (in `orbit-entity/collision.ts`; rigid-sphere impulse resolution for casings/enemies/pickups/belt) is called from `Game.handlePostSimulation` once per `Game.update` call — not per substep — and only while `simSpeed <= MAX_PHYS_SIM_SPEED`, using the real (unwarped) `dt` so it stays consistent with the belt's own real-time cadence; at higher warp it's skipped entirely (substeps up to 20s each make rigid-body contact resolution meaningless there, and it's O(n²) over every casing). It uses `PLAYER_HULL_RADIUS` (real hull size, ~2.6m) for contact, deliberately smaller than `PLAYER_RADIUS` (5m, used for bullet self-hit detection only) — reusing the bullet-hit radius here would fling freshly-ejected casings (spawned ~2.9m from the hull) outward on the same frame. A casing/hull impact directly triggers `Sfx.clank()` via the `onPlayerCasingImpact` callback, rather than polling distances every frame.

Translation and the main engine are unified: `buildThrustAccel` fires all six directions — W/Ctrl / S/Shift fore/aft, A/D lateral, `VirtUp`/`VirtDown` (touch-only) radial — at the same selected magnitude, `THROTTLE_LEVELS[throttleIdx]` (3 stages — [1]/[2]/[3] — no separate "cutoff" stage; thrust only exists while a direction key is actually held). `RcsEffects.computeRcsTau`'s puff-direction `tau` vector must keep the exact same sign convention as `PlayerThrottle.updateAttitude`'s `inX`/`inY`/`inZ` (I/K=pitch, **J/L=yaw**, **O/U=roll**) — these were inverted for yaw and roll in an earlier pass (puffs fired backwards relative to the actual torque), so if you touch either mapping, touch both.

When mags run low (`LOGISTICS_LOW_MAGS`), resupply pickups spawn phase-shifted 1.25–2.5 km ahead on the player's own orbit (`stage-utils/logistics.ts`'s `Logistics.spawnForPlayer`; ▣ AMMO marker, absorb within `AMMO_PICKUP_RADIUS`). Casings use a CIWS-style bottleneck profile (rim/extractor groove/tapered body/shoulder/neck via `LatheGeometry`) with **low** ejection speed/spin (previous values made them visibly spin sideways at high rate) and drift back within ~3.2 m of the hull play a faint clank — but only after first travelling >6 m away (`clankArmed`), since every casing starts near the hull. Spin-up SFX is filtered-noise friction (no oscillator). Enemy ships are modeled at `ENEMY_SCALE` (20×) via `obj.scale.setScalar(...)` with `ENEMY_RADIUS` (180 m) matching for hit detection; their destruction VFX (`spawnFlash` sizes, `spawnFragments` size range) scale by the same factor so the explosion reads proportionate to the larger hull.

Mouse buttons are swapped from the naive default: **left button drags the camera; a left click that moves less than `CLICK_MOVE_THRESHOLD` (6px) is instead queued as a click** (used to place maneuver nodes in map mode) — see `Input.clicks()`. Right button fires. This lets map-mode node placement and camera dragging share the left button without a modifier key.

Map mode ([M]) no longer freezes physics: `simulate()` always runs while `phase==='playing'`, with ship control (thrust/fire/manual attitude) gated by `!this.mapMode` since WASDQE is repurposed for Δv editing there — so time warp keeps working and the player can wait for a transfer window while planning. `updateMapPlanning()` only runs the click/Δv-edit overlay on top. The map camera's drag yaw sign is intentionally opposite the combat chase camera's convention (`+=` vs `-=` on `mouse.dx`) so panning left/right reads the same in both views.
