This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## 作業のルール

- **全体像はコードではなく文書から掴む。** 「どこで何が起きているか」「誰が状態を持つか」「いつ走るか」
  は `DEVELOP/OWNERSHIP.md` / `DEVELOP/CALLSTACK.md` / `DEVELOP/SPEC.md` / この CLAUDE.md が一次情報。
  当たりを付けてから必要なファイルだけを読む。手順は `.claude/skills/overview/SKILL.md`(`/overview`)。
- **検証は変更箇所に対応させる。** 既定は `npm run typecheck` のみで、これは常に走らせる。
  `npm run test:physics` は `src/physics/` を触ったときだけ。ヘッドレス実行検証(`/verify`)は
  ユーザーが実行時の動作確認を明示的に求めたときだけ。変更と無関係な検証に時間を使わない。
- **リファクタリングの判断基準は `/refactor`(一般方針)と `/refactor-fixed`(このプロジェクトで確定済みの
  責務境界)。** 責務配置の判断を新たに下した/変えたら、`.claude/skills/refactor-fixed/SKILL.md` を
  同じ変更セットで書き換える(追記ではなく、全体が整合するように書き直す。古い判断は残さない)。
- **改名は痕跡を残さない。** コードにも文書にも歴史的経緯を書かない。「旧」「former」「previously」
  「〜だった」の類は禁止。互換用の旧名エイリアスも残さず、旧名は全文検索して 0 件にする。
- **関数・機能の追加要求を受けたら、書き始める前に必ず `/add-feature` の手順を通す。** まず既存の
  類似実装を探し、再利用可能な形で適切なモジュールにあればそれを呼ぶ(追加実装しない)。そうでなければ
  適切なモジュールへ再利用可能な形で実装し、**既存側もその呼び出しに置き換えるまでを同じ変更セットで**
  行う。数行の処理でも例外にしない。
- **共通化するかどうかは、参照箇所の数ではなく「今後も使う可能性があるか」で決める。** これはコード
  からは判別できないので、`DEVELOP/SPEC.md`「実装される可能性のある機能」節を見て、決まらなければ
  ユーザーに問う。ユーザーが可能性に言及したものは同節へ記録する。
- **`refactoring_plan/refactoring_todo.md` は todo リスト。** 経緯は残さず、完了した項目は消す
  (そこで下した責務配置の判断は消す前に `/refactor-fixed` へ移す)。

## Current state

A playable LEO (low Earth orbit) shooting game: TypeScript + Webpack + npm, Three.js `WebGPURenderer` (via the `three/webgpu` entry point). Real-scale/real-time Earth orbit (player starts at 420 km / 97° inclination), body-frame RCS translation, manual rotation with RCS damping and a prograde-hold autopilot, time warp, lead-marker gunnery against enemies that shoot back with lead-aimed plasma, shell casings and destruction debris on accurate orbital physics, win on destroying all enemies, lose on being shot down or on atmospheric reentry (drag decay → adiabatic-heating overheat or dynamic-pressure breakup). Also: Earth-shadow lighting, target-board bullet-pass markers, an orbit-planning map mode ([M]: Earth-centered camera, with the camera's frame and the predicted trajectory's frame selected independently on two separate panels, click the predicted trajectory to place a maneuver node — several nodes can be chained, each frozen as an absolute post-burn state — W/S/A/D/Q/E adjust Δv, [N] auto-warps to the next node, BURN guide shows remaining Δv until the actual orbit matches the planned elements within tolerance), and four stages (stage 2 = Molniya-orbit enemies, unlocked once stage 1 has been cleared — tracked via `unlock-manager.ts`'s `UnlockManager`, which persists per-stage clear counts to localStorage and toasts newly-unlocked stages; stage 0 = near-combat training scoreattack, stage 00 = infinite survival, both always unlocked; `?stage=` URL param skips the select screen). Each frame is `Game.update` → `Game.sync` → `Game.render`; the render phase draws `cameraSystem.activeCamera` — combat chase cam (near 2 / far 6e7) or the map camera (near 1e4 / far `OVERVIEW_CAMERA_FAR` = 1.5e10) —. Stars/sun/moon billboards follow the active camera position so the map zoom-out doesn't exit the star shell.

`dev.md` is explicitly marked as human-authored only ("この文書は人間のみが記入できる") — do not edit it. Read it for project context, but leave modifications to the user.

### Naming: render / update / build / sync (no `draw`)

Per-frame function names must reflect what they actually do, consistently across the codebase:

- **`render`** — reserved for functions that literally call the three.js renderer's `render(scene, camera)` (only `Game.render` qualifies). A function that only constructs or mutates scene state is not a "render" function even if it runs in the render phase (e.g. `Player.syncPlayer`, `EnvironmentScene.sync`).
- **`update`** — advances or mutates logical/simulation data (not three.js mesh state directly).
- **`build`** — registers new meshes/objects into the scene (construction, not per-frame).
- **`sync`** — matches the transform/appearance of already-registered meshes (or HUD DOM elements) to logical data that was already computed elsewhere. Prefer plain `sync*` names; don't tack `Render` onto a sync method name (e.g. `syncCamera`, not `syncRenderCamera`) — it blurs the render/sync boundary this rule exists to keep clear.
- **`draw`** is never used — rename on sight.

The rAF loop in `main.ts` makes this split structural: it calls `Game.update(dt)` → `Game.sync(dt)` → `Game.render()` as three separate top-level phases. `update` must not touch THREE.js objects; `sync` builds the frame's `FloatingOrigin` and pushes already-computed logical state into meshes/DOM; `render` only issues draw calls. Keep sub-functions on the correct side of that line — state that merely happens to be read at render time still belongs with the system that owns it.

Covers vec3 smoke tests, orbital.ts Kepler round trips (`stateFromElements`⇄`elementsFromState`, `trueAnomalyAt`/`positionOnOrbit`/`velocityOnOrbit`), `stepOrbitRK4` one-period drift and epoch advance, `j2Accel` RAAN regression rate, attitude.ts kinetic-energy conservation + quaternion norm, atmosphere.ts density-table boundary/monotonicity, ephemeris.ts sun/moon distance-and-period sanity, deque.ts ring-buffer push/pop ordering, capacity growth, and out-of-range error handling, and state-queue.ts's out-of-order push discarding, age/minCount-bounded cleanup, and Hermite-interpolated lookup. Where no clean theoretical value exists (RK4 drift, J2 rate, table-boundary continuity), the test pins the *measured* current behavior with a loose margin rather than an idealized bound — run this before/after any change under `src/physics/`.

There is no other automated test suite wired into npm beyond `test:physics`.

### Architecture

Simulation state lives in ECI coordinates (Y axis = north pole), SI units (m, m/s), as plain `{x,y,z}` data (`physics/vec3.ts`'s `Vec3` is a **branded type** — build it with `v3()`/the helpers, never with a bare object literal).

`OrbitState` is a **timed** state vector — `{t, r, v}`, where `t` is the absolute simTime epoch — and it is the *single* type used for every "state at a moment": entity state, entity history, predicted-trajectory samples, and maneuver-plan nodes. There is deliberately no second type carrying the same information (the former `TrajectorySample`, `LineSample` and `PlannedNode.time` were folded into it), so a state and its time can never be passed as two arguments that disagree. `stepOrbitRK4` advances `t` along with `r`/`v`, which is why `predictTrajectory`/`propagateState`/`toFrameState` no longer take a separate time argument.

**The base data types are immutable, with no exceptions**: `Vec3`, `OrbitState` (`physics/orbital.ts`), `Quat`/`Attitude` (`physics/attitude.ts`) are all `readonly` and are advanced by *replacement*, never by in-place mutation — `stepOrbitRK4` returns a new `OrbitState`, `stepAttitude` returns a new `Attitude`, and every owner assigns the result (`entity.state = …`, `entity.att = …`). This is a correctness invariant, not a style preference: `physics/orbit-entity.ts`'s `OrbitEntity` is what invalidates the memoized `elements` **and pushes the outgoing state onto `history`** on every `step`/`reset`, and it can only do that because nothing else can change the state behind its back. Consequences: defensive copying is unnecessary (`vec3.clone()` does not exist), and **everything under `physics/` is a pure function returning fresh values** — there are no `*Into`/`out`-parameter variants and no module-level scratch buffers. Those existed (軽量化計画 A-1) and were deliberately removed. The cost is real but small: in an isolated Node benchmark `stepOrbitRK4` went 1520 → 2190 ns/step and `stepAttitude` 218 → 414 ns/step, which at a typical ~400 live entities works out to roughly +0.35 ms per frame in the `update` phase — not distinguishable from run-to-run noise in the actual game (~5 ms update phase). The immutability that buys is what makes the `elements` memo correct, so the trade is intentional. If the entity budget grows enough for this to matter, the answer is a physics LOD (軽量化計画 B-1), not reintroducing mutable scratch into `physics/`. Rendering uses a **floating origin**: `game/floating-origin.ts`'s `FloatingOrigin` is rebuilt every `Game.sync` from the player's post-integration state, and `RtoThreeV3`/`VtoThreeV3` are the *only* bridge from logical `Vec3` to `THREE.Vector3` — so f32 GPU precision never sees absolute LEO magnitudes. Every `sync` takes the `fo` and must not use `player.state.r` as the render origin directly (the two are semantically distinct; the origin could move to the camera later). Combat camera: near=`COMBAT_CAMERA_NEAR`=2m, far=`COMBAT_CAMERA_FAR`=6e7m — no logarithmic depth needed (see comment in `const.ts`).

Physics runs on the main thread (per-entity central-gravity two-body integration is cheap); the N-body worker is **currently unused**, kept for the future cislunar (Sun-Earth-Moon) phase.

`src/game/` is an orchestrator (`game.ts`) plus subfolders grouped by concern: `player/` (player ship state), `game-entity/` (the shared entity base classes, their passive simulation, and the array that holds them), `camera/`, `plan/` (maneuver planning and its future-trajectory display, independent of whether the map is open), `stages/` (per-stage behavior), `hud/` (DOM overlay), `marker/` (screen-projected markers), `vfx/`, and `input/`.

**`*Ctx` snapshot objects are a rejected pattern here** — don't add new ones and don't widen the survivors. Almost all of them have been expanded into explicit arguments or shared references; what remains is `EnvironmentSyncParams` (`render/environment-scene.ts`) and `Player.behave`'s parameter object. `refactoring_plan/STOP_USING_CTX.md` (plus the open items in `refactoring_plan/refactoring_todo.md`) is the live status of that work — trust it over this file.

Many public fields (`cameraSystem`/`player`/`activeStage`/`entities`/`simulator`/`targeter`/...) exist because `hud/panel.ts`'s `HudPanels.update(game, dt)` reads the whole `Game` instance directly rather than a narrow ctx.

`src/game/player/` — the player ship, split by concern (all owned and composed by `Player`, which exposes read-only getters for `game.ts`/HUD):
- `player.ts` — `Player extends Ship`: initial LEO placement (`makeInitialState`/`progradeAttitude`, `INITIAL_ALT`=420 km / `INITIAL_INC_DEG`=97°), the per-frame `behave` (belt → own edge keys → torque → HP regen → fire → thrust) and `checkLoss`/`syncPlayer` entry points, damage/loss handling (`attacked`, `checkLoss` — hull heat/dynamic-pressure/reentry-altitude thresholds via `thermal`), and composes `throttle`/`fire`/`belt`/`thermal`/`thrustEffects`/`rcsEffects`/`markers`. `handleEdgePress` claims the ship-side keys (`[T]`/`[F]`/`[V]`/`[C]`/`[1]`-`[3]`/`[R]`) via `input.takeKeys()`, which consumes them so no later module double-handles. `[R]` is only consumed when a manual reload actually starts. Right after `this.thrust` is set, `behave` calls `this.invalidatePrediction()` if it's non-null — the one place a `GameEntity` invalidates its own prediction *outside* `resyncPrediction`'s distance check, because the player's own burn needs to be reflected in the predicted trajectory immediately (a UX requirement `resyncPrediction`'s few-frame lag can't meet) and this is deliberately player-only, not a `thrust` setter, leaving room for `Enemy` thrust to someday *not* reset immediately.
- `player-throttle.ts` — `PlayerThrottle`: translation input → thrust accel (`buildThrustAccel`, all 6 body-frame directions), manual rotation + RCS damping, and the prograde-hold autopilot (`autoAlignTorque`): builds a desired attitude quaternion (nose = velocity direction, roll reference = radial-out, re-orthogonalized so it's valid even for eccentric orbits where r⟂v doesn't hold exactly — see `physics/attitude.ts`'s `qFromForwardUp`), converts the quaternion error to a body-frame axis-angle, and applies a PD torque (`PROGRADE_HOLD_KP`/`_KD`). `updateTorque` only *returns* the body torque (`Player` writes it to `entity.torque`) and `updateThrustState` only returns the thrust closure — the actual attitude/orbit integration is `Simulator`'s.
- `player-fire.ts` — `PlayerFire`: gun state (mag/round/barrel counters, reload timer), `updateFireState`/`fireCycle`/`consume` (the ammo state machine, returning `ConsumeResult` = `empty`/`normal`/`mag-reload`/`barrel-reload`), `fireGun` (bullet spawn, recoil, casing eject, muzzle flash, `ScoreCounter.recordShot`), and `dropBarrel`/`spawnEjectedMagazineFrame` for reload debris. `tickMapMode` advances only the reload timer while the planner is open.
- `belt.ts` / `belt-physics.ts` — the ammo belt display split from its physics: `belt-physics.ts`'s `BeltPhysics` is a pure Vec3/Quat Verlet-chain solver (position-based dynamics, no THREE/mesh dependency) for the belt's sag/twist under the ship's thrust+spin pseudo-forces; `belt.ts`'s `Belt` owns the link meshes and derives each link's transform from `BeltPhysics`'s solved state via parallel transport.
- `thermal.ts` — `ThermalSystem`: hull heating/dynamic-pressure (Sutton–Graves + Stefan-Boltzmann, `updateThermal`) and the altitude-descent-warning EMA (`updateAltitudeAlarm`); returns a `ThermalLimit` verdict — the actual destruction (`alive = false` + effects) happens in `Player.checkLoss`.
- `thrust-effects.ts` / `rcs-effects.ts` — billboard VFX for the main engine plume and the 4 RCS thruster puffs, positioned from `render/ships.ts`'s `MUZZLE_OFFSETS`/`RCS_BLOCK_OFFSETS`.
- `player-markers.ts` — `PlayerMarkers`: the HUD markers that follow from the ship's own position/attitude — the six orbital-frame direction markers (prograde/retrograde/normal/antinormal/radial in-out, the Navball stand-in), the `┼` boresight, and the map-mode `▷` self marker. `sync(currentState, displayState, att, alive, overviewMode, project)` takes two states rather than one: the combat-view markers (direction/boresight) always read `currentState`, since they represent the ship's real orbital frame regardless of the future-ghost slider, while `▷` reads `displayState` (`null` beyond the player's own prediction horizon, in which case `▷` just hides) — the two states coincide whenever the slider is at rest, which combat view always is. `Player.syncPlayer` drives it, so callers never see a separate marker entry point.

`src/game/game-entity/` — the entity base classes, their passive (non-AI, non-input) simulation, and the array that holds them:
- `game-entity.ts` — `GameEntity` (base: mesh/HP/alive/attitude/AI-facing state; delegates the actual "time-stamped state + its sample history + advance itself" job to `physics/orbit-entity.ts`'s `OrbitEntity`, held as the public `current` field. `state`/`prevState`/`history`/`elements` are thin forwarding getters to `current` — the ~20 call sites across the codebase that only ever read `.state` are unaffected by this split. The `state` **setter** forwards to `current.reset(...)`, the sole entry point for a discontinuous external overwrite (rigid contact, recoil); `stepSim(dt, sunPos, moonPos)` never goes through it — it self-gates on `alive`, then hands `current.step(...)` the entity's own `bcInv`/`thrust`/`sampleInterval()`/`historyDuration` (integration itself is `current`'s job, not this class's). `sampleInterval()` derives the history's push interval from the live orbital period (`elements.period / PREDICT_SAMPLES_PER_REV`, falling back to a `SHIP_HISTORY_DURATION`-based value when no period is available, e.g. hyperbolic orbits), `torque`/`thrust` slots the owning system writes each frame, and a default reentry-altitude `checkLoss`), `Ship` (adds name/hp/radius, `bcInv = SHIP_BCINV`, `historyDuration = SHIP_HISTORY_DURATION` — the only class that keeps a history), `Ammo`/`DebrisPiece` (`bcInv = SMALL_DEBRIS_BCINV`), `BeltSection` (a per-link collision proxy the belt physics exchanges with `collision.ts`; never stepped — it isn't one of `EntityManager`'s arrays).

  A second `OrbitEntity` — `predicted` — is the entity's own future trajectory, driven incrementally by `Predictor` (below) rather than recomputed from scratch each frame: `advancePrediction(ephemeris, budgetSteps, simTime)` lazily creates it from `current.state` if absent, then extends its tip by up to `budgetSteps` RK4 steps toward `simTime + predictDuration` (step size `max(PREDICT_MIN_STEP_DT, predictStepDt(...))`, same `sampleInterval` as `current` so the past/future sample density matches), returning steps actually consumed so the caller can do the budget accounting. It refuses to grow while `thrust !== null` (a thrusting free-flight prediction is meaningless and would just be invalidated next frame anyway) and permanently stops (sets `truncated`, cleared only when a fresh `predicted` is created) if the integrated altitude drops below `REENTRY_ALT` or goes non-finite — without that, a re-entering or NaN-corrupted entity would burn its budget forever without ever reaching the horizon. `resyncPrediction(simTime, tolerance)` is the cheap per-frame correctness check: if `predicted.at(simTime)` is absent or has drifted from `current.state.r` by more than `tolerance`, it calls `invalidatePrediction()` (drops `predicted` — a zero-cost operation; the list simply regrows through the normal budget next frame, which is why discards never spike frame time). `predictDuration` (0 by default; `Ship`/`Ammo` get `PREDICT_DURATION`) is a per-class constant independent of `DisplayTimeManager` — what's shown and what's predicted are unrelated axes. The payoff both axes converge on is `displayState(t)`: `t <= current.state.t ? current.at(t) : (predicted?.at(t) ?? null)` — a two-way branch (past vs. future, nothing else) that `sync(fo, displayTime)` (below) and every marker-position lookup route through, so "what does this entity look like at the currently-displayed time" has exactly one answer for meshes and markers alike.
- `src/physics/orbit-entity.ts` — `OrbitEntity`: THREE/game-independent (`physics/`, alongside `StateQueue`/`Ephemeris` as "pure but stateful"), holding **one** `OrbitState` as `state` plus a decimated `StateQueue` of samples strictly older than it (`history`). `step(dt, sunPos, moonPos, bcInv, thrust, sampleInterval, keepDuration)` advances via `envaccel.ts`'s `stepEnvRK4`, then — only if `keepDuration > 0` and the about-to-be-overwritten `state` is at least `sampleInterval` seconds past the newest recorded sample — pushes that pre-step state into `history` and caps the window with `history.cleanup(keepDuration, 2)` (this is where the display-resolution decimation happens; `keepDuration = 0` never touches `history` at all, so casings/debris/ammo cost nothing). `prevState` (needed every step by `hit.ts`'s segment-vs-sphere test and `targeter.ts`'s board crossings, even for entities with `keepDuration = 0`) is tracked in its own field, separate from the throttled `history` — it's simply "the state one `step`/`reset` ago". `reset(state)` is the discontinuous-overwrite counterpart to `step`: it discards any `history` samples at-or-after the new state's time (`StateQueue.discardFrom`) to keep the "history is older than state" invariant, and still advances `prevState`. `at(t)` answers any time within the retained span — `t === state.t` returns `state` itself, newer than `history.newest` but older than `state` interpolates between the two via `orbital.ts`'s `hermiteInterpolate`, and anything older delegates to `history.at(t)` — so callers never need to reconcile the queue and the live state themselves. This same class is meant to back a second, forward-looking instance per entity later (predicted future samples use the identical step/at operations, just with `history` spanning "now → prediction horizon" instead of "past → now") — see `memos/hedalu244/better_predict.md`.
- `bullet.ts` — `Bullet extends GameEntity`: player/enemy bullets and enemy plasma bolts (`Shooter`/`BulletType`), `bcInv = BULLET_BCINV`, its own loss check (**distance from the player first — `BULLET_MAX_DIST` — with the lifetime only as a backstop**, since every live bullet is its own draw call), and a velocity-facing (not attitude-facing) `sync` override that uses `fo.VtoThreeV3`. `predictDuration` stays at the `GameEntity` default of 0, so `displayState(displayTime)` is `null` for the entire time the future-ghost slider is active — bullets simply disappear rather than showing a nonsensical projected flight path, which is fine since their lifetime is a few seconds.
- `enemy.ts` — `Enemy extends Ship`: enemy AI (`behave` — burst-fire plasma at the player using `physics/intercept.ts`'s `solveLeadTime`; takes the `EntityManager` reference to read `enemies` for the per-group attacker cap and to `addBullet`; per-group attacker cap and burst state live here), damage/destruction (`attacked`, `checkLoss`), its own `OrbitLine`, and its HUD presentation (`accentColor`, and `markerItem(isTarget, viewerPos, pos)` returning the `GroupedMarkerItem` the screen-marker set is built from — the enemy states what it looks like, `GroupedMarkers` decides how the set is laid out; `pos` is a caller-supplied argument rather than `this.state.r` because `Game.sync` resolves it from `displayState(displayTime)` — the marker has to sit at the same future-ghost position as the enemy's own mesh, or the two visibly disagree the moment the slider moves).
- `hit.ts` — `HitSystem`: segment-vs-sphere bullet collision only (tunneling-proof, `checkBulletHits(simTime, player, activeStage, entities)`), called per substep from `Simulator`. Target-board marker recording now lives on `Targeter`.
- `entity-manager.ts` — `EntityManager`: owns the `enemies`/`bullets`/`casings`/`debris`/`ammos` arrays (capped, oldest evicted on overflow via `addXxx`/`addCapped`), lifetime cleanup (`cleanup`/`prune`, which takes `simTime` and the player position because `Bullet.checkLoss` culls by distance), and the per-entity render sync (`sync(fo, displayTime)`, forwarding `displayTime` to each `GameEntity.sync` — see `game-entity.ts`'s `displayState` below). It runs no simulation itself — `all()`/the arrays are handed out by reference to `Simulator` (below), `HitSystem`, `CollisionPhysics`, and to every module that only ever reads or adds entities (`Targeter`, `Enemy.behave`, `Stage`/`stages/`, `Logistics`, `EffectsSystem`, `NanWatchdog`). Owned by `Game` and exposed as the public `entities` field — the one window every other module shares by reference, which is also why `Stage.setup` now hands `Logistics` the manager directly and `EffectsSystem`'s constructor takes it directly instead of an injected `addDebris` callback (no per-owner closures).
- `simulator.ts` — `Simulator`: the actual simulation step. Owns **`simTime`/`lastSimDt`**, `HitSystem`, `CollisionPhysics`, and takes the `EntityManager` reference in its constructor rather than holding any array itself — splitting "which entities exist" (`EntityManager`) from "how they're stepped" (`Simulator`) keeps each to one responsibility. `stepSimulation` splits the frame's `simDt` into substeps (count = `ceil(simDt / SUBSTEP_MAX_DT)` capped at `SUBSTEP_MAX_COUNT` — depends only on the simulated time this frame, never on the real frame rate); each substep (`simulationSubStep`) samples the sun/moon position once and hands it to every live entity's own `stepSim(dt, sunPos, moonPos)` (`game-entity/game-entity.ts`) — the orbit integration itself is the entity's responsibility, not `Simulator`'s; `Simulator` only iterates the arrays. It also owns the attitude integration for *all* entities including the player (`stepAttitudes`). AI/input/spawn decisions live in `game.ts`/`stages/`/`Enemy.behave`, which add entities back in via `entities.addXxx`.
- `predictor.ts` — `Predictor`: a third updater over `EntityManager`'s arrays, symmetric with `Simulator` (①holds the arrays / ②steps them / ③predicts their future — `Predictor` is ③) rather than nested inside `Simulator`, so it doesn't inherit that class's `simTime` concerns or vice versa. Owned directly by `Game` and driven from `Game.update` right after `entities.cleanup(...)` (dead entities shouldn't get predicted, and it needs the post-integration real state to resync against) — with **no branch on viewpoint or mode**, since prediction runs whether or not anything is currently displaying it. The only state it holds is a round-robin `cursor` into `EntityManager.all()`. `update(simTime, player)` first calls `resyncPrediction` unconditionally on every entity (player included) — cheap (one binary search each) — then spends `PREDICT_STEP_BUDGET` RK4 steps on `advancePrediction`, player first, then one pass through the array starting at `cursor`, saving wherever it stopped as next frame's `cursor`. It never asks *why* a list is short (freshly spawned vs. just invalidated) — that indifference is what keeps discards from ever spiking frame time, since a discarded list just competes for the same budget as a new one next frame.
- `collision.ts` — `CollisionPhysics`: rigid-sphere impulse resolution for casings/enemies/pickups/belt links (`resolve`, called once per `Game.update` — not per substep — and only while `SimSpeedManager.canResolvePhysicalCollisions`; takes `EntityManager.all()` as a plain array, not the manager itself).

`src/game/camera/` — every camera follows the same `update` (compute the viewpoint in absolute ECI, THREE-free) / `sync(fo)` (push it into the `THREE.PerspectiveCamera` through the floating origin) / `projection` (a `ProjectFn` built from the same math, independent of both the THREE matrices and `fo`) split:
- `camera-system.ts` — `CameraSystem`: owns `ChaseCamera`/`OverviewCamera` and exposes the active one (`activeCamera`/`activeCameraPos`/`activeCameraProjection`); owns `overviewMode`/`zoomActive`. Also owns the map focus concern (= "where the overview camera looks"): the `focusMarkers` label set, the `FocusGizmo` selection menu (wiring `onMenuFocus` to set `overviewCamera.focus`, exposing `handleFocusRightClick`/`closeFocusMenu` for `game.ts` to drive), and the **MAP VIEW panel** (`camera/overview-camera-panel.ts` — focus shortlist / camera frame / view reset). Every control on that panel writes `overviewCamera` state and nothing else, so the whole HUD wiring stays inside this class; `sync(fo)` pushes the panel's visibility and highlights each frame.
- `chase-camera.ts` — `ChaseCamera`: the combat third-person view, a togglable reference frame (`camFollowAttitude`: ship-attitude-relative vs. orbital-frame-relative, toggled by `[G]` via `toggleFollowAttitude`), and the `[Z]` gunsight view (`computeGunsightView`, FOV lerped to `ZOOM_FOV`).
- `overview-camera.ts` — `OverviewCamera`: the map Earth-centered orbit camera (near=1e4/far=`OVERVIEW_CAMERA_FAR`). Its source of truth is just two **`cameraFrame`-relative** vectors (`offset_r` = focus→camera, `pan_r` = focus→look-target), so switching to the sun-rotating frame makes the viewpoint co-rotate for free; the ECI ⇄ frame round trip is delegated to `physics/frame.ts` and the class never brands values itself. `cameraFrame` (`'inertial'`/`'sunRotating'`) is the source of truth for **the frame the viewpoint is fixed to**, and only that — the frame the predicted trajectory is *drawn* in is `PlanDisplay.trajectoryFrame`, a separate value the player selects independently. Focus (a label id) is resolved to a position via the injected `FocusMarkers`. The future-ghost slider belongs to `DisplayTimeManager`.
- `focus-markers.ts` — `FocusMarkers`: computes/projects the focusable-target labels (Earth/Moon/Sun/Earth-Moon L1–L5/Sun-Earth L1–L2) and the label lookup (`findLabel`) used both for focus resolution and focus-menu picking. An overview-camera-side concern, owned by `CameraSystem`.
- `focus-gizmo.ts` — `FocusGizmo`: the map-label focus-selection context menu (single responsibility: the focus targetKey + focus/cancel menu items). Uses the shared `hud/context-menu.ts`.

Screen projection itself is **not** in `camera/`: `physics/projection.ts` holds the pure math (`ViewFrame`/`projectToNdc`/`ndcToScreen`/`Projected`) and each camera exposes a bound `ProjectFn` (`(worldPos: Vec3) => Projected`) that consumers receive as an argument rather than importing.

- `src/game/map-mode-toggler.ts` — `MapModeToggler`: the `[M]` open/close lifecycle, the sole place that co-switches the camera-side flag (`cameraSystem.overviewMode`), the plan-side editing flag (`editor.editMode`), and the future-display gate (`displayTimeManager.forceCurrent`) so they toggle together while staying logically independent. Its single `update` takes `[M]` from `Input` and also force-closes the map when the stage stops playing. Rendering/viewpoint code checks `overviewMode`; input/behavior code checks `editMode`. This toggler sits at the `game/` root and the shared popup menu in `hud/context-menu.ts`, because everything else about the `[M]` mode belongs to either the camera or the plan concern.

  The node-vs-focus split: in map mode `game.ts` calls `PlanEditor.handleMapPointer` then `CameraSystem.handleMapPointer`. The editor consumes only the right-clicks that actually hit a node, so the leftovers fall through to focus selection — the priority is expressed purely as call order, and the two gizmos never reference each other.

`src/game/plan/` — maneuver planning and its future-trajectory *display*, independent of whether the map is open. "When to look" (display duration, the future-ghost slider) is a separate, `game/`-root concern (`DisplayTimeManager` below) from "what a plan looks like when you look" (this folder):
- `plan.ts` — `Plan`: the node list plus the `anchor` (the plan's starting state). **Both are plain `OrbitState`s: a node *is* its frozen post-burn absolute state, not a relative Δv** — the burn time is the state's own `t`, and Δv is the derived value (node `v` − arrival velocity). While the plan is empty, `trackAnchor` follows the live player state; placing the first node freezes the anchor, after which prediction is a pure function of anchor + nodes and never reads `player` state. Editing a node discards downstream nodes (`retimeNode`/`applyNodeDv`). No prediction cache lives here.
- `plan-guide.ts` — `PlanGuide`: the combat-view execution guide for the nearest node (◆NODE/⬢BURN markers, the white planned-orbit line, the `orbitClose` achievement check that consumes the node). Because the node target is a frozen post-burn state, there is no "target keeps receding while burning" hack any more.
- `plan-editor.ts` — `PlanEditor`: owns `plan`, the `editMode` flag, the `NodeGizmo`, the MANEUVER PLAN HUD panel, and `planDisplay` (below) — editing and future-display are both "what this plan is/looks like", so one owner. `sync(mapDist, displayEnd, simTime, displayTime, fo, project)` drives `planDisplay` first (grey/white/orange polyline + ⬡ ghost + its TRAJECTORY panel) and then the node gizmo, in that order, since the gizmo's screen positions read `planDisplay.traj`'s this-frame display transform. `displayEnd`/`simTime`/`displayTime` arrive as arguments from `game.ts`, resolved via `DisplayTimeManager` — `PlanEditor` never reads "when to look" itself. Click-to-place / drag-to-retime / Δv-arm drag / WASDQE Δv editing / node context menu / `[X]` delete (`clearPlanByKey`) all read `planDisplay.traj`'s screen picking (`projectPoint`/`nearestSample`) rather than a per-frame argument, since the node drag / context-menu handlers fire on DOM pointer events, outside the frame flow. Derived-only values (node arrival states, per-node Δv) are recomputed via `physics/predict.ts`, never stored.
- `plan-display.ts` — `PlanDisplay`: the plan's future-trajectory display — `trajectoryFrame` (the coordinate frame the predicted polyline is drawn in, independent of `OverviewCamera.cameraFrame` — a player selects both separately), the ⬡ `plannedPlayer` ghost marker (hidden whenever `displayTime <= simTime`, i.e. the slider is at rest), its own small TRAJECTORY panel (a single frame `SegmentedControl`, built inline rather than as its own panel class — one control doesn't earn a file, same call `PlanEditor` already makes for its own MANEUVER PLAN panel), and the `PlanTrajectory` below. `sync(plan, displayEnd, simTime, displayTime, fo, project)` takes every time value as an argument (owned by `DisplayTimeManager`, resolved by `game.ts`) so it holds no duplicate state.
- `plan-trajectory.ts` — `PlanTrajectory`: splits the plan's corners into arcs (anchor → node₁ → … → display end), owns one `PredictedLine` per arc (grey before the first burn, white after it, orange beyond), and is the **single place display-frame transforms and screen picking are done** (`toDisplay`/`projectPoint`/`nearestSample`) so the drawn polyline and click hit-testing can't drift apart. The whole display context — frame, un-bake time, and the `ProjectFn` — is refreshed by `update` every frame; the `ProjectFn` is deliberately *not* captured at construction, since `CameraSystem.activeCameraProjection` returns a snapshot of whichever camera is active *now* (capturing it once would pin picking to the chase camera's startup viewpoint). Owned by `PlanDisplay`; `PlanEditor` shares the same instance (`planDisplay.traj`) for its own screen picking.
- `predicted-line.ts` — `PredictedLine`: one numerically-predicted arc drawn as a polyline (RK4 via `physics/predict.ts`'s `predictTrajectory`, delegating the actual draw to `render/sampled-line.ts`). A reusable per-arc unit — knows nothing about `Plan` — so `PlanTrajectory` composes several of these rather than predicting the whole multi-node polyline in one shot.
- `node-gizmo.ts` — `NodeGizmo`: the maneuver-node DOM pointer-events layer — node handles + Δv axis arms + the node context menu (warp/delete). A plan concern; uses the shared `hud/context-menu.ts`.

- `src/game/display-time-manager.ts` / `display-time-panel.ts` — `DisplayTimeManager`: "when to look" — the display duration (`durationKey` → `durationSec`), the future-ghost slider position `sliderT`, `resolveDisplayTime` for the "show the sky at a future time" query every future-aware `sync` uses, and `forceCurrent` (starts `true`, flipped by `MapModeToggler`; while set, `resolveDisplayTime` always returns the present). Owned by `Game` (not `PlanEditor` — nothing here is plan-specific; `EnvironmentScene`/`CameraSystem`/`FocusMarkers` all resolve a display time too, and `PlanDisplay`'s ghost is just one more consumer). `DisplayTimePanel` is its DOM (duration `SegmentedControl` + slider + a self-sufficient "T+"-only label — the ghost marker's own label carries the richer altitude readout, since that needs `PlanDisplay`'s trajectory sample and `DisplayTimeManager` must not depend on it). `onDurationChange` is a callback `game.ts` wires to `editor.planDisplay.traj.invalidate()`, since a non-continuous duration switch (unlike the window sliding forward with `simTime`) needs the predicted polyline rebuilt immediately rather than through its usual throttle — the two live in different owners, so `game.ts` is the only place that can connect them.

- `src/game/sim-speed-manager.ts` — `SimSpeedManager`: the sim-speed stage (`SIM_SPEED_LEVELS`; shown to the player and referenced in SFX as "warp"), the `[N]`-key auto-warp-to-node behavior (`toggleAutoWarpToFirstNode`/`startAutoWarpTo`/`cancelAutoWarp`/`update`), and the **`can*` predicates** (`canPlayerThrust`/`canPlayerFire`/`canEnemyFire`/`canResolvePhysicalCollisions`) — callers ask these instead of comparing `simSpeed` against `MAX_PHYS_SIM_SPEED` themselves.

- `src/game/targeter.ts` — `Targeter`: auto-target selection (closest to camera forward) and right-click target lock, plus everything the current target puts on screen — its highlighted `OrbitLine`, the target-board bullet-pass marks (`markBoardCrossings` records the crossing points per substep-integrated bullet, `syncBoardMarkers` ages and draws them), the ◇/◆ target-bearing direction markers, and the relative AN/DN markers (where the player's orbit crosses the target's orbital plane, i.e. where a plane-change burn belongs). All of it goes out through one public `sync`.
- `src/game/vfx/effects-system.ts` / `vfx/flash-effect-manager.ts` — the flash/debris spawn API (`EffectsSystem`, the sole place `Player`/`Enemy`/`PlayerFire`/`Stage` reach to spawn VFX or add debris) and its per-frame flash lifetime/billboard sync (`FlashEffectManager`).
- `src/game/nan-watchdog.ts` — `NanWatchdog`: シミュレーション状態に非有限値(NaN/Infinity)が入った**最初のフェーズ**を捕まえてコンソールと HUD へ報告する。**Game が所有し、`update` の各フェーズ境界で呼ぶ。** 一度検出したら以後は何もしない。存在理由は、NaN が静かに伝播したあと別の顔で表面化するため — 自機が汚染されると `FloatingOrigin` 経由で全メッシュが消えて 3D だけが暗転し、敵が汚染されると `Enemy.checkLoss` の高度比較が false になって「再突入により喪失」と誤表示され、`collision.ts` は非有限の距離を弾けないので毎フレーム接触音を鳴らし続ける。伝播を止めるガードは `collision.ts` 側にあり、検出と報告はこちらの責務。
- `src/game/unlock-manager.ts` — `UnlockManager`: per-stage clear-count persistence (localStorage is the source of truth) and unlock-toast notification; `Stage.isUnlocked` stays a pure predicate over the counts.
- `src/game/input/input.ts` / `input/touch.ts` — keyboard/mouse/pointer edge-trigger queue (`Input`: `update()` freezes one frame's snapshot of presses/clicks/right-clicks/mouse deltas; middle-drag pan and two-finger pinch are folded into the same `MouseDelta`). Edges are handed out **first-come-first-served**: `takeKey(code)`, `takeKeys(handler)`, `takeClicks(handler)`, `takeRightClicks(handler)` remove any event whose handler returns true, so a later module never sees it. `down(code)`/`mouse()` stay plain reads. This is what lets each module own its own keys — see `Game.handleInput` and the touch virtual-pad overlay (`TouchControls`, feeding the same `Input.setVirtualKey`; `syncModeButtons(rcsDamp, fineAttitude, progradeHold)` is its only per-frame entry point — it owns the code↔button mapping, the caller passes only the current values).
- `src/physics/atmosphere.ts` — piecewise-exponential density model (Vallado table, 0–1000 km). Drag (Cd·A/m per entity class, co-rotating atmosphere) is applied as the RK4 extra-acceleration; player hull temp uses Sutton–Graves stagnation heating + Stefan-Boltzmann radiative cooling (see `updateThermal` in `player/thermal.ts`).

So the orbital-direction/boresight/`self` markers live in `player/player-markers.ts` (owned by `Player`, driven from `syncPlayer`), the target bearing + relative AN/DN markers in `targeter.ts`, the ▣ AMMO markers in `stages/stage-utils/logistics.ts`, the celestial labels in `camera/focus-markers.ts`, NODE/BURN in `plan/plan-guide.ts`, and the future ghost in `plan/plan-display.ts`. Only two sets stay in `marker/` because one object genuinely cannot decide them:
  - `grouped-markers.ts` (`GroupedMarkers`) [Game-owned] — takes a set of `GroupedMarkerItem`s (key/class/symbol/world position/priority/label parts/bearing color) and does the two things that need the whole set: collapsing screen-adjacent markers into one representative (highest `priority` wins; the rest lose their label) and replacing off-screen ones with a screen-edge bearing arrow. Target-agnostic and reusable; `Enemy.markerItem()` is what supplies the enemy set's content.
  - `lead-markers.ts` (`LeadMarkers`) [Game-owned] — the ✛ LEAD markers, which depend on the player *and* the enemy and so belong to neither. Owns the per-enemy last-locked time (rebuilt each frame from the live enemy list, so it can't leak) that keeps a LEAD marker up for `LEAD_HOLD_SEC` after the target moves on. Hidden entirely in map mode / when the player is dead.

- `src/physics/orbital.ts` — the `OrbitState` type (`{t, r, v}`, built only via `orbitState(t, r, v)`) and central-gravity RK4 for one entity with an optional extra-acceleration callback (`ExtraAccelFn`: `(rx, ry, rz, vx, vy, vz) => Vec3`, evaluated per RK4 stage and added to central gravity — used for thrust, environment acceleration, or both depending on the caller; `stepOrbitRK4` returns the advanced `OrbitState` — epoch included — and never touches its input), state→orbital elements, ellipse sampling for orbit lines, `j2Accel` (Earth oblateness, Y = polar axis; verified ≈ −5°/day RAAN regression at 420 km/51.6°), `thirdBodyAccel` (differential tidal accel), and Kepler helpers for maneuver planning (`trueAnomalyAt`, `tofBetween`, `positionOnOrbit`/`velocityOnOrbit`, `stateFromElements` — all round-trip-verified to machine precision), and `hermiteInterpolate` (cubic Hermite between two `OrbitState`s, using their velocities as tangents; refuses a `t` outside the two epochs unless `allowExtrapolation` is passed, since the cubic diverges fast outside the span). Pure functions.
- `src/physics/ephemeris.ts` — analytic Sun/Moon ephemerides in game ECI (Y = north): Sun on a circular ecliptic orbit (23.44° obliquity), Moon on an elliptic orbit (e = 0.0549, perigee advancing over 8.85 years) inclined 5.145° to the ecliptic with an 18.61-year regressing node (equatorial inclination sweeps 18.3–28.6°, which drives real inclination perturbation of LEO orbits). **The Moon's angles are assembled in ecliptic longitude and only converted to an argument of latitude at the end**: its mean longitude completes exactly one turn per sidereal month, so neither precession slows the orbit down (treating the mean longitude as node-relative instead costs ~19°/year of position error, which shows up as the Moon and every Earth-Moon Lagrange point drifting away from their true positions under long time warps). Pure functions plus the `Ephemeris` class, which is a **stateless sampler**: it holds only the per-game `sunPhase0`/`moonPhase0` and answers `sunPosAt(t)`/`moonPosAt(t)`/`sunDirAt(t)`/`emLagrangeAt(t)`/… — there is no `update()` and no cached "current" position, so no call-order constraints exist. THREE-independent, so `predict.ts`/`envaccel.ts`/`frame.ts` consume it directly. The single instance is **owned by `Game`** and shared by reference with `EnvironmentScene`, `Simulator`, `OverviewCamera`, `PlanEditor`/`PlanDisplay`/`PlanTrajectory`, and `FocusMarkers`.
- `src/physics/frame.ts` — time-dependent display frames (`Frame` = `'inertial' | 'sunRotating'`) and the ECI ⇄ frame-relative conversions for positions, states and the rigid-body rotation quaternion (`toFramePos`/`toInertialPos`/`toFrameState`/`toInertialState`/`toInertialQuat`). Frame-relative values are **branded types** (`RelativeVec3`/`RelativeOrbitState`) so a missing or doubled conversion is a type error. `toFrameState` bakes at the state's own epoch (`s.t`) and needs no time argument; `toInertialState` still takes one, because un-baking happens at the *display* time, not the sample time — that time becomes the restored state's epoch. Only display concerns use it (`render/sampled-line.ts` bake/un-bake, `OverviewCamera`'s viewpoint, `PlanTrajectory`'s picking) — the simulation itself is always plain ECI.
- `src/physics/projection.ts` — the pure screen-projection math (`ViewFrame` → `projectToNdc` → `ndcToScreen`, yielding `Projected {x, y, front}`). Independent of THREE.js and of the floating origin; each camera in `game/camera/` binds it into a `ProjectFn`.
- `src/physics/predict.ts` — numerical future-trajectory prediction for the planner: `predictTrajectory` (RK4 sampling into `OrbitState[]`, adaptive step via `predictStepDt`), `propagateState` (free propagation to a target time), `sampleAt` (interpolate a sample series), and `dvToWorld` (prograde/normal/radial → world Δv). All of them start from the input state's own epoch (`state0.t`) rather than a separate `t0` argument. `predictTrajectory`/`propagateState` take an optional `bcInv` (default 0 = drag-free, so the plan tool's current behavior is unchanged) — the actual step is `envaccel.ts`'s shared `stepEnvRK4` (below), called with `thrust = null` since planned trajectories never thrust. Knows nothing about `Plan`.
- `src/physics/intercept.ts` — `solveLeadTime` (the lead/interception time for a relative position+velocity and a muzzle speed, used by the enemy AI's aim) and `leadPoint` (the world position to aim at, given two `OrbitState`s and a cut-off time; `null` when there's no usable solution). `leadPoint` is what keeps `LeadMarkers` from rolling its own lead math.
- `src/physics/envaccel.ts` — `envAccel`: the single composition point for the environment acceleration (drag + J2 + lunisolar third-body; `bcInv = 0` skips drag), a plain `Vec3`-returning pure function; also exports `airspeed`/`EARTH_OMEGA` (co-rotating atmosphere). `stepEnvRK4(state, dt, sunPos, moonPos, bcInv, thrust)` composes it with `orbital.ts`'s `stepOrbitRK4` and an optional thrust into the single RK4 step shared by `physics/orbit-entity.ts`'s `OrbitEntity.step` (called from `GameEntity.stepSim` in `game-entity/game-entity.ts`, drag on via each entity's own `bcInv`, its own `thrust`) and `predict.ts`'s `stepPredict` (`bcInv` from the caller, `thrust = null`) — one integration step, not two independent copies of "central gravity + envAccel + thrust". No out-parameter variant — see the immutability note above.
- `src/physics/attitude.ts` — rigid-body attitude: quaternion + body-frame ω via Euler's equations. ω integrated with RK4 + kinetic-energy projection (naive explicit integration diverges — this is what makes the Dzhanibekov effect on debris stable long-term); `stepAttitude` carries the sub-step ω/q as scalar locals and returns one new `Attitude`. `qFromForwardUp` (nose +Z / up +Y basis → quaternion, re-orthogonalizing, null at the fwd∥up singularity) is the shared attitude-basis builder used by `player/player.ts` (`progradeAttitude`), `player/player-throttle.ts` (`autoAlignTorque`), and `stages/spawner/enemy-generator.ts` (`generateApproachingEnemy`). Pure functions.
- `src/physics/vec3.ts` — plain-object Vec3 math helpers (all pure, all returning new immutable `Vec3`s) and the shared random helpers `randSym`/`randVec`/`randPerp`.
- `src/physics/deque.ts` — `Deque<T>`: a generic ring-buffer double-ended queue (`pushLeft`/`pushRight`/`popLeft`/`popRight`/`at`/`peekLeft`/`peekRight`/`deleteLeftN`/`deleteRightN`/`clear`), capacity doubling on overflow. No game-state dependency; a general-purpose data structure, not physics per se, but grouped under `physics/` since it's equally pure/DOM-free and covered by the same `test:physics` runner.
- `src/physics/state-queue.ts` — `StateQueue`: a `Deque<OrbitState>`-backed time series kept newest-first (`peekLeft`/`newest` = newest, `peekRight` = oldest). `push` adds the latest sample; a push whose time doesn't exceed the current newest is treated as a correction and discards everything at-or-after its own time before inserting (the same "editing invalidates downstream" rule `Plan` node edits follow), so the pushed sample always ends up as the new head. `capCount(n)` trims down to the `n` most recent samples. `cleanup(maxAge, minCount)` is the age-based sibling — this is what backs `physics/orbit-entity.ts`'s `OrbitEntity.history` window (`OrbitEntity.step` calls it with `keepDuration` on every recorded push): prunes samples older than `maxAge` relative to the newest one, never below `minCount`, and (when `maxAge` is nonzero) always leaves one sample older than the cutoff in place so `at(newest.t - maxAge)` still has a bracketing pair to interpolate against instead of falling outside the retained span. `discardFrom(t)` drops every sample at-or-after `t` without inserting anything — `OrbitEntity.reset` uses it to invalidate samples that are no longer valid after a discontinuous state overwrite. `at(t)` binary-searches the bracketing pair and reuses `orbital.ts`'s `hermiteInterpolate`, returning `null` outside the retained span rather than extrapolating. The private `bisect` (lower-bound over the descending series) is the single search primitive `push`/`cleanup`/`discardFrom`/`at` all share.
- `src/physics/nbody/{bodies,integrator,physics.worker}.ts` — original N-body RK4 worker stack, unused by the LEO game; isolated in its own directory (with a `README.md` explaining why) and retained for the cislunar phase.

- `src/render/{stars,orbitline,sampled-line,billboard,glow-texture}.ts` — stars as tiny world-space triangles (WebGPU points are 1px; `THREE.Points` size doesn't work), sun billboard and moon mesh — both placed along their true ephemeris directions each frame at compressed display distances (`SUN_DISTANCE`=4.2e7 / `MOON_VIS_DIST`=4.5e7 m, inside the 6e7 far plane) with the moon's angular size derived from its real distance, so lunar phases come free from the directional sun light; camera-facing `Billboard` sprites (flashes, plume, RCS puffs) over a shared radial-`glow-texture`.

- `THREE.LineLoop` and `THREE.Points` sizing are not supported; use `THREE.Line` / triangle-based sprites.
- Additive-blended materials need explicit `transparent: true`.
- Headless-Chrome screenshots work with `--headless=new --enable-gpu --enable-unsafe-webgpu --disable-gpu-sandbox --no-sandbox` (flaky; retry a few times).

## Project concept (from dev.md)

An orbital-mechanics shooting game, intended as a web game, set in the Earth-Moon system (current build: LEO only):

- Gameplay centers on realistic orbital maneuvers and physically accurate ballistic calculations, low-poly but visually appealing depictions of Earth's atmosphere, spacecraft, and spacecraft destruction.
- Orbital calculations should account for Sun-Earth-Moon three-body dynamics, atmospheric drag, and tidal forces. Reference concepts to consider: Sun-Earth and Earth-Moon Lagrange points, sun-synchronous recurrent orbits, halo orbits, low-energy transfers and ballistic capture, double lunar swingbys, and gradual altitude-raising approach maneuvers (like the Kounotori HTV's ISS approach).
- Aesthetic goals: Earth auroras, auroras from solar storms, auroras from charged particles generated by combat, shadows on Earth's evening clouds, and the Dzhanibekov effect on destroyed debris.

## Controls (current build)

**Translation is body-frame, not orbital-frame** (`PlayerThrottle.buildThrustAccel` builds a direction in body axes and rotates it by `att.q`): W or Ctrl / S or Shift = nose-forward/aft (+Z/−Z), A/D = lateral (+X/−X), Q/E = vertical (+Y/−Y). All six fire at the same selected magnitude `THROTTLE_LEVELS[throttleIdx]` (3 stages — [1]/[2]/[3] — no "cutoff" stage; thrust exists only while a direction key is held). `input.ts` calls preventDefault on Ctrl+W/A/S/D/R so browser shortcuts don't fire while Ctrl is held as forward thrust (Ctrl+W/T/N and Ctrl+digit are browser-reserved and can't be blocked).

Rotation: I/K = pitch, **L/J = yaw**, **O/U = roll** (signs per `PlayerThrottle.updateTorque`'s `inX`/`inY`/`inZ`; RCS puff directions are derived from the resulting torque's signs in `RcsEffects.sync`, so the two can no longer disagree). T = RCS rotation damping toggle, **F = prograde attitude reset** (one-shot: only sets the hold ON), **C = prograde-hold autopilot toggle** (PD controller torquing the nose to the velocity vector; any manual rotation key cancels it), **V = fine-attitude toggle**.

G = toggle whether the chase camera's reference frame follows ship attitude vs. the orbital frame (see below). Z (hold) = gunsight zoom. Space / **right click** = fire; **right click on an enemy also locks/unlocks it as target** (`Targeter.handleTargetLockByRightClick`). Target selection has no dedicated key: without a lock, the target is whichever living enemy is closest to the camera forward axis (`Targeter.resolveAutoTarget`, recomputed every frame). **left drag** or **arrow keys** = camera yaw/pitch, wheel or two-finger pinch = zoom distance, **middle drag** = pan (map mode). `,` / `.` = time warp (thrust, guns, enemy fire and contact physics are all gated above ×`MAX_PHYS_SIM_SPEED` = 4 via `SimSpeedManager.can*`). M = orbit-planning map, N = auto-warp to the next node, X = delete selected node / discard the whole plan, H = help, R = manual reload (after the game ends it instead re-launches **the same stage** — `Stage.restart` navigates to `?stage=<id>`, since a plain reload would drop you back on the stage-select screen whenever you got there without a `?stage=` param).

Esc (or the ⚙ gear) = pause menu, owned by `hud/settings-panel.ts`: `SettingsPanel.toggle` fires `onSettingsOpenChange`, which `main.ts` syncs to `Game.pause()`/`Game.resume()` (so every open/close path — Esc, gear click, [閉じる] — pauses/resumes), plus a BGM toggle and a "quit to title" button (`onQuitToTitle` → `location.assign(location.pathname)`, dropping the `?stage=` param). While paused `Game.update` returns early, so HP auto-regen (`HP_REGEN_RATE` = 1 HP/s, inside `Player.behave`) can't be farmed from the menu. `handleInput` still runs before the pause check, so each key's owner decides for itself what a paused frame means — `MapModeToggler.update` takes `isPaused` and ignores `[M]` without consuming it (an already-open map stays open across the pause).

Firing implies fine-attitude authority (`FINE_ATTITUDE_SCALE` = 0.5): `Player.updateTorque` passes `fineAttitude || fire.isFiring`, so releasing the trigger restores full authority with no edge-tracking state.

The orbital direction markers (`player/player-markers.ts`) deliberately carry no key hints in their labels: combat-view translation is body-frame, so none of those six directions has a key. The keys that *do* mean prograde/normal/radial are the map-mode Δv edit keys, and the direction markers are hidden there.

Chase camera reference frame (`camFollowAttitude` on `ChaseCamera`, default **on**, toggled via `[G]`, which `CameraSystem.update` takes for itself): the third-person camera's yaw/pitch are always defined relative to a `(fwd, up)` frame, but *which* frame is configurable. `ChaseCamera.update` computes both candidate frames each call — the ship's own attitude (`boreFwd`/`boreUp`, nose +Z / body +Y rotated by `player.att.q`, the same pair that drives the zoom gunsight view) and the orbital frame (`chaseFwd`/`chaseUp`, prograde/radial-out) — and picks between them via `computeChaseView`/`computeGunsightView` based on `camFollowAttitude`/`zoomActive`/`player.alive`. ON (default) uses the ship's own attitude, so rotating the ship with I/K/J/L/U/O visibly swings the whole camera (including its roll) right along with it, RCS-linked. OFF uses the orbital frame, which stays independent of ship attitude and only slowly co-rotates with orbital motion.

Ammo system: guns fire alternately from the two front bores and consume magazine rounds (`MAG_ROUNDS`=32/mag, `INITIAL_MAGS`=3 linked at start, `MAGS_PER_BARREL`=3 consumed before a barrel-swap reload — doubling the per-mag capacity from an original 16-round design let the visible chain be roughly half as long while carrying comparable total ammo). The belt of unused mags hangs off the ship's starboard (+X) side as child meshes of `player.obj`, and the belt slides continuously into the hull as rounds are fired (`beltFeed` = 1 − rounds/`MAG_ROUNDS` offsets the anchor by up to one pitch; on mag consumption the feed wraps 1→0 exactly when the link count drops, so the motion reads as seamless). The head link sits half-inside the hull. `BeltPhysics.update` (in `player/belt-physics.ts`) simulates the belt's sag as an actual physics chain, not a canned animation: link joints are point masses (`beltPos`/`beltPrevPos`, Verlet-integrated in the ship's body frame) connected by rigid-rod distance constraints (position-based dynamics, 6 relaxation iterations per frame) to `MAG_BELT_PITCH`. Since the ship is in free fall, ordinary gravity can't sag anything (equivalence principle — belt and hull fall together); the only real driver is the fictitious force felt in the ship's non-inertial (accelerating/rotating) frame: `-a_thrust - α×r - ω×(ω×r) - 2ω×v` (translational inertia, Euler, centrifugal, Coriolis), built from `thrustAccelVec` (world-frame thrust accel, rotated into body frame, passed in each call from `Player.behave` via `Belt.update`) and `player.att.w` (with `α` estimated by finite-differencing `w` against `prevBodyW`, both tracked inside `BeltPhysics`). When the player isn't thrusting or rotating, the chain just hangs straight — no ambient wobble is faked in.

Each link's *orientation* is derived separately from its position, via parallel transport: `qBend = qDelta * qPrev` where `qDelta` is the minimal (zero-twist) rotation taking the previous link's local +X to this link's tangent — so bending (the chain folding link-to-link) is unconstrained by construction, matching a real ammo belt's easy up/down/left/right flex. Roll (twist about the link's own +X, the one DOF parallel transport leaves undefined) is instead tracked explicitly per link in `beltTwist[]`, driven by the ship's own roll rate (`player.att.w.z * MAG_CHAIN_ROLL_GAIN`) at link 0 and propagated down the chain with a one-frame lag (`prevTwist`) and exponential smoothing (`MAG_CHAIN_ROLL_RATE`), clamped every frame to `±MAG_CHAIN_MAX_ROLL_DEG` — so however it's driven, twist can never exceed that bound. The final per-link quaternion is `qBend * qTwist(local +X)`.

`CollisionPhysics.resolve(dt, ...)` (in `game-entity/collision.ts`; rigid-sphere impulse resolution for casings/enemies/pickups/belt) is called once per `Game.update` call — not per substep — and only while `simSpeedManager.canResolvePhysicalCollisions`, using the real (unwarped) `dt` so it stays consistent with the belt's own real-time cadence; at higher warp it's skipped entirely (substeps up to 20s each make rigid-body contact resolution meaningless there, and it's O(n²) over every casing). It uses `PLAYER_HULL_RADIUS` (real hull size, 2.6m) for contact, deliberately smaller than `PLAYER_RADIUS` (5m, used for bullet self-hit detection only) — reusing the bullet-hit radius here would fling freshly-ejected casings (spawned ~2.9m from the hull) outward on the same frame. A casing/hull impact directly triggers `Sfx.clank()` via the `onPlayerCasingImpact` callback, rather than polling distances every frame.

When mags run low (`LOGISTICS_LOW_MAGS`), resupply pickups spawn phase-shifted 1.25–2.5 km ahead on the player's own orbit (`stage-utils/logistics.ts`'s `Logistics.spawnForPlayer`; ▣ AMMO marker, absorb within `AMMO_PICKUP_RADIUS`). Casings use a CIWS-style bottleneck profile (rim/extractor groove/tapered body/shoulder/neck via `LatheGeometry`) with **low** ejection speed/spin (previous values made them visibly spin sideways at high rate). Spin-up SFX is filtered-noise friction (no oscillator). Enemy ships are modeled at `ENEMY_SCALE` (20×) via `obj.scale.setScalar(...)` with `ENEMY_RADIUS` (180 m) matching for hit detection; their destruction VFX (`spawnFlash` sizes, `scatterFragments` size range) scale by the same factor so the explosion reads proportionate to the larger hull.

Mouse buttons are swapped from the naive default: **left button drags the camera; a left click that moves less than `CLICK_MOVE_THRESHOLD` (6px) is instead queued as a click** (used to place maneuver nodes in map mode) — see `Input.clicks()`. Right button fires (and locks targets / opens map context menus). This lets map-mode node placement and camera dragging share the left button without a modifier key.

Map mode ([M]) does not freeze physics: `Simulator.stepSimulation` runs every frame while `activeStage.isPlaying && !paused`, and ship control (thrust/fire/manual attitude) is gated on `editor.editMode` since W/S/A/D/Q/E are repurposed for Δv editing there (in the planner they mean prograde/normal/radial, not body axes) — so time warp keeps working and the player can wait for a transfer window while planning. Only `editor.updateEditing` and the pointer dispatch are layered on top of `update`; the three map-mode panels (MAP VIEW / PREDICT / TRAJECTORY) show and refresh themselves from their owners' `sync`. The map camera's drag yaw sign is intentionally opposite the combat chase camera's convention (`+=` vs `-=` on `mouse.dx`) so panning left/right reads the same in both views.
